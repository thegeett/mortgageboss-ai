# LP-568 — an obligation that ends at closing must leave the DTI

**Status:** mechanism done; the detection rule is LP-569 · **Confirmed:** 2026-08-19 by the resident
domain expert

## The defect

DTI is forward-looking — it measures what is owed **after** this loan funds. `_auto_debt_lines`
counted every active liability unconditionally, and `StatedLiability` had nowhere to record that an
obligation is paid off at closing. On a refinance that charges the same house twice: once as
`housing_payment` (the new PITI) and once as the old mortgage's payment.

LF-WCHG, from the first snapshot staging ever persisted:

| | current | correct |
|---|---|---|
| housing (new PITI) | 4,418.785 | 4,418.785 |
| other debts | 3,295.00 | 109.00 |
| **back-end DTI** | **58.59%** | **34.39%** |

The 3,186.00 line is `MortgageLoan — UNITED WHSLE MORT`, the mortgage this refinance pays off. That
it secures the *subject* property is not an inference: the DTI's `housing.taxes` of 440.215/month is
5,282.58/year, and the 1098 for that mortgage reads `Property Taxes 5,282.58`. Same parcel.

**34.39% was worked by hand with the domain expert and confirmed.** 58.59% fails most conventional
overlays; 34.39% passes comfortably — the bug flips the verdict on the file.

A reconciliation check makes it visible without any of this context: back-end minus front-end should
equal the NON-housing debt as a percent of income. Here the gap was 25.03 points against 109.00 of
actual card debt (0.83 points). 97% of the "non-housing" bucket was a mortgage payment.

## Not refinance-only

The mechanism is purpose-agnostic because the question is. A purchase reaches the same defect
through a **departing residence** being sold, or a **debt paid off at closing to qualify**. Deriving
the exclusion from `loan_purpose == refinance` would have missed both, which is why the flag lives
on the liability. Rent is not modelled at all, so there is no current-housing double-count.

## The fix

`stated_liabilities` gains `paid_off_at_closing` (nullable Boolean) and `payoff_source`. The DTI
skips a line whose flag is `True`, and the line is still **emitted** — carrying its real amount,
flagged `excluded` with a reason — so a processor sees that the debt was considered and why it
dropped out. The UI renders it struck through with "not counted — paid off at closing". A debt that
silently vanishes is worse than one counted wrongly.

**Three-state, and `None` is the default on purpose.** Only `True` excludes. Excluding wrongly
understates the DTI and can pass a loan that should fail, so silence keeps the debt counted:
over-counting fails a good file visibly, under-counting passes a bad one quietly.

## MISMO already carried the answer — and it cannot be trusted in the negative

The export has `LiabilityPayoffStatusIndicator` and `LiabilityExclusionIndicator` on every
`LIABILITY_DETAIL`. The parser was reading four elements and dropping the rest, so the answer was in
the source file and never reached the DTI. It is parsed now.

But the one real fixture carries `LiabilityPayoffStatusIndicator=false` on **all ten** liabilities,
five of them mortgages. That is a serializer default, not ten determinations. So a `false` is stored
as `NULL`, not `False` — reading it as "retained" would answer the question on every file, in the
direction that removes debt from the ratio, on a value nobody set.
`test_the_real_fixture_says_false_on_every_liability` pins that premise, and fails if a future
fixture carries a meaningful `true`.

## What DT-6 does now

DT-6 ("stated housing payment vs. servicer's billed payment") is about **this same liability**, and
points the opposite way — it asks to *raise* 3,186.00 to 4,148.28. It is not wrong: its own remedy
already offers both branches ("if the property is under contract or being paid off at closing,
document that so the obligation is excluded on the correct basis"). It is `needs_review` precisely
because it cannot resolve retained-vs-paid-off alone.

Once the flag is set, DT-6 must go **`not_applicable`, carrying its reason** — not `satisfied`.
The stated and billed figures genuinely disagree and always will; they simply stop mattering for
the DTI. Calling that `satisfied` would be a false all-clear. **That scoping is not built here** —
it belongs with the detection rule (LP-569), and until then DT-6 correctly keeps asking.

## Adjacent defects found, not fixed here

- **DT-6's own numbers do not reconcile.** The statement's `principal_amount` + `interest_amount` +
  `escrow_amount` = 4,389.21, against a stated `monthly_payment` of 4,148.28 (Δ 240.93). And the
  application's 3,186.00 matches neither the P&I (3,844.82) nor the total. DT-6's prose attributes
  the whole 962.28 gap to escrow, which covers 544.39 of it.
- **The readonly views leak names and addresses.** Document `fields` return the borrower's full name
  and street address in the clear, and the DTI breakdown label embeds the borrower's first name —
  the exact columns `borrowers` and `loan_files` deliberately drop. The scrub is shape-based and
  cannot catch either. `docs/querying-staging.md` claims the views "drop or scrub every column that
  can carry an identifier"; that is currently overstated.

## Two guards fixed along the way

`test_no_model_column_drifts` caught the new columns — they are exposed in `readonly.stated_liabilities`
(a boolean and a provenance slug carry no identifier, and are exactly what diagnosing a DTI needs).
Getting them past it exposed two holes in the scanner itself:

1. It matched only `CREATE VIEW`, never `CREATE OR REPLACE VIEW` — so a replace that quietly
   *dropped* a column would have passed the guard unseen.
2. It read the whole migration file, so a `downgrade()` that recreates the previous shape won over
   the `upgrade()` — reporting a freshly exposed column as unexposed.

## Verified by removing the fix

- delete the exclusion in `_auto_debt_lines` → 4 of the 6 DTI tests fail (the two fail-closed ones
  pass either way, correctly — they assert the debt still counts)
- delete the struck-through rendering → the frontend test fails

**No snapshot version bump.** The two new `CalcBreakdownLine` fields are additive with defaults, so
v4 snapshots stay readable — the LP-421 precedent, pinned by `test_snapshot_version_unchanged`. I
bumped it first and the guard caught me.
