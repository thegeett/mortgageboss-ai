## What historical rows can and cannot supply

`b7`'s pointer going in was the right thing to settle first, and the answer is not uniform. Stated
here and in the model's own docstring, so an audit reads it rather than discovers it:

| §6 field | Before this ticket |
|---|---|
| recipient, template + version | **recoverable** — still on the `Communication` row |
| the rendered body **as sent** | **recoverable** — `send_draft` wrote the edit there |
| inbound auth verdicts | **recoverable** — on `inbound_messages` |
| attachment manifest with hashes | **recoverable** — `inbound_attachments.sha256` |
| the authenticated approver | **reconstructible** — written only into an activity log's `detail` |
| **the model draft, and therefore the diff** | **permanently absent** |

The last row is the one that matters. `send_draft` overwrote `draft.body` with the processor's edit,
so for everything sent before this ticket the composed version is **gone rather than unstored**, and
no backfill can produce it. §6 asks for the draft, the edit and the diff; historical rows supply only
the right-hand side of the third.

`body_composed` is now captured in the one statement it exists for — the line immediately before the
overwrite. A null on a historical row means *never recorded*, which is not *there was no draft*, and
the two must not be conflated.

## Why the evidence is a second table

`Communication` is soft-deletable and it is **edited**: `send_draft` overwrites `body`, LP-820
refreshes `recipient` when an address is corrected, LP-812 rebuilt part of it. Every one of those is
right for the UX and disqualifying for evidence — §6's *"must not be soft-deletable"* is a property
of the row, not a policy about it.

So `communication_evidence` has **no `deleted_at` and no `updated_at`**. The second is omitted for a
related reason: on an append-only row it can only ever lie — either it equals `recorded_at` forever,
or something updated a row that must not be updated. Asserted on the model, because a policy is a
sentence and a missing column is a type error.

Append-only is also enforced behaviourally: there is no update function, no delete function, and a
second `record_sent` for the same message is **refused with a sentence** rather than overwriting. A
retried send is the case most likely to reach that.

**The evidence is written by `send_draft`, not by the endpoint.** A record that depends on a route
remembering to ask for it is missing exactly where somebody adds a second route — and LP-820 added
one this week.

## The legal hold ships before the purge job

§6 says so explicitly, and INFRA-1 builds the S3 lifecycle expiry — **which is the purge job** — on
day one of the critical path. FRCP 37(e) is the reason: a party who knows litigation is reasonably
anticipated must suspend routine destruction, and a flag added *after* the purge is one the purge was
already running without.

Nothing in this repo purges yet. `refuse_if_held` exists before its callers do, deliberately —
"a comment is not a guard", and what makes this real when destruction arrives is that there is
something to call and a test saying what happens when it is not called.

Two deliberate asymmetries:

- **A reason is required to place a hold and never to lift one.** Placing is the decision that has to
  be justifiable later; requiring a justification to *lift* would make lifting harder than placing,
  which is the wrong way round for a control whose failure mode is holding everything forever.
- **Re-placing keeps the original `legal_hold_at`.** "Since when" is the question a court asks, and
  the answer is when it was first placed.

`legal_hold_at` is **cleared** on lift, so "is it held" and "was it ever held" stay different reads —
the first is what a purge asks, and the activity log is what remembers the second.

## The AI System Disclosure

`docs/compliance/ai-system-disclosure-email-drafting.md`, one page, per §6's field list — purpose,
model + version, inputs/outputs, where a human decides, monitoring, limitations, data handling, NIST
AI RMF mapping.

It says four things plainly rather than smoothing them, because a disclosure that reads as finished
when it is not is the failure it exists to prevent: **it has not been reviewed by the domain expert
or by counsel**; **there is no offline evaluation**, so the RMF's MEASURE function has monitoring and
no benchmark; the Bedrock retention settings are **asserted, not verified in this repo**; and
`prompt_version` **has no home yet**, so that field will be null on every row until LP-810's open
escalation is closed.

**The tests caught a defect that would have crashed every send.** `logger.info(..., event=...)`
raises `TypeError` — structlog binds `event` as the message itself, so it cannot be a keyword. The
field is `evidence_event` now. It was a one-word slip in a line that looked obviously correct, and
nothing but running it would have found it.

The readonly view drops both bodies, the subject, both addresses and the manifest — the same four
columns `readonly.communications` already drops, because an audit record is not a reason to reproduce
a borrower's mail in the analytics path. What is exposed answers *"how much was sent, under which
template, with what firing, and was it edited"* — the last as a boolean derived in the view, so the
question is answerable without either body. `legal_hold_reason` is excluded; the flag and the time
are not.

## Deliberately not done

- **No frontend.** The evidence record and the hold have endpoints and no screen. The hold in
  particular deserves one — a processor about to act on a held file should see it on the file
  header, and `GET /legal-hold` exists for that. **Escalated.**
- **`guardrail_fired`, `model_id` and `prompt_version` are always null today.** `send_draft` has no
  access to them: LP-810's drafter runs earlier and returns prose, and the guard verdict lives in
  `email_draft_prose`. Threading them through is a change to LP-810's return shape.
  **Escalated** — the columns exist so that change is a service edit rather than a migration.
- **Nothing calls `refuse_if_held`.** By construction — there is no destruction path yet. It is the
  point of shipping the flag first, and it is the thing to check when INFRA-1 applies.
- **No `received` evidence is written automatically.** `record_received` exists and
  `apply_routing` does not call it; wiring it in means an evidence row per arrival including the
  unrouted ones, which is a retention question rather than a code one. **Escalated.**

## For the reviewer

- **Tenancy** — every route is `ScopedLoanFile`; `evidence_for` filters on `loan_file_id` (tested
  same-company-two-files) and `held_file_ids` on `company_id`. Nothing derives a company.
- **Message content in logs** — the two new lines carry a loan-file id, an event and two booleans.
  Never a body, a subject or an address, all three of which are on the row the line is about.
- **AI in the decision path** — none. This ticket records what the AI did; it does not call it.

Worth a second measurement:

1. **The API returns no bodies.** `EvidencePublic` exposes `was_edited` and `has_composed_draft` and
   not the text. My reasoning: reading the actual words is a legal request, not a page load, and it
   should leave a trace this endpoint does not create. That is a product decision as much as a
   security one and is worth disagreeing with.
2. **`loan_file_id` is `RESTRICT` and `communication_id` is `SET NULL`.** Deliberately different:
   the evidence must not be deletable with the file, and must survive the message.
3. **The disclosure's four open items.** They are honest and they mean the document is not yet
   usable for the diligence purpose §6 describes. Check I have not overstated anything that *is*
   true — particularly §5's guard descriptions, which I wrote from LP-810's code.
