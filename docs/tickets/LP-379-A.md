# LP-379-A — Refresh the calibration worksheet against the current tag layer

## What this ticket is

The LF-6T3N labeling worksheet (`docs/calibration/lf6t3n-labels-{mechanical,judgment}.csv`, LP-337/338) was
generated before LP-340, LP-377-D, and LP-385. Before Priya spends hours labeling for LP-379, every row must
target a tag that actually materializes today, at its current subject/convention. This ticket verifies the
instrument against the current tag layer and regenerates it — **preserving every filled label**, labeling
nothing, calibrating nothing, changing no producer or rule.

## Acceptance criteria

- Every worksheet row targets a tag that materializes on LF-6T3N today (no row for a non-producing
  tag/doc-type).
- income_stability rows match LP-385's per-BORROWER producer (one row per borrower per tag), not the old
  per-document shape.
- Every previously-filled label survives verbatim; no golden rewritten.
- Deterministic + keyless generation; the mechanical/judgment split intact; predictions excluded.
- `ACTIVE_RULE_IDS` unchanged; full suite green. Only the worksheets + generator metadata change.

## Phase 0 — the instrument verification (the substance)

**The gate of record is the fixture + the current tag layer — it beats the ticket text.** Cross-checking all
25 generator tags against the current `tag_production.yaml`, **the only drift is the 4 income_stability
tags** (generator `document` → YAML `borrower`). The ticket predicted four changes; three are refuted:

### 1. STALE `income_amounts` rows on mortgage/tax/bank docs — DO NOT EXIST (premise refuted)
The generator's `_GROUPS` always scoped income to `("pay_stub", "w2")` (income.type / documented_monthly /
qualifying_monthly) and `+voe/offer_letter` for employer. **The worksheet never had income rows on
mortgage/tax/bank docs.** LP-377-D removed *pipeline* over-production, not worksheet rows. The CSVs confirm:
income.* rows appear only on pay_stub/w2. **Nothing to drop here.**

### 2. `employer_normalized` / `name_normalized` convention conflict — DOES NOT EXIST (premise refuted)
LP-340 decided the entity-suffix strip lives in **IN-5's RULE** (`drop_entity_suffix`), **NOT the tag**:
*"The TAG reports what the document states (`Acme Logistics Inc`, in full) — LP-335's principle intact."* So
the tag `income.employer_normalized` still reports the full stated name. Geet's 8 goldens
(`Acme Logistics Inc`, `Sterling Retail LLC`, `Northgate Warehousing`, `Cafe Bluebird`) are exactly what the
tag should produce. **No conflict; nothing to flag or re-label.** Same for `id.name_normalized` (the tag
reports the stated name; any strip is a rule concern).

### 3. income_stability NEW rows — the real change, but not labelable on the fixture (gate-of-record catch)
LP-385 made income_stability per-BORROWER: its context gathers the documents `belongs_to`-attributed to a
borrower, seen together. But the calibration **fixture** (`build_lf6t3n_snapshot`) has `mismo.absent = True`,
**zero** `borrower.{n}.borrower_id` facts, and `belongs_to = None` on every document. So the per-borrower
producer enumerates **no** borrowers → income_stability produces **zero** rows on the fixture (per-borrower
OR per-document). LP-385's probe that showed 6/8 real values ran against the real DB LF-6T3N (2 wired
borrowers) — **the fixture is not the DB.**

The current 32 income_stability rows (4 tags × 8 pay_stub/w2 docs, all in judgment.csv, **0 filled**) are
therefore stale: they target a per-document production LP-385 removed. Worse, the stale coverage table still
reported them `labelable cap=8` — a **false** capacity claim the refresh corrects to `no_subject`.

## Phase 1 — the regeneration (labels preserved)

The instrument is made borrower-aware rather than merely stripping the stale rows: `worksheet.py` gains a
`borrower` `subject_kind`. income_stability becomes a `_Group("borrower", _INCOME_STABILITY_DOCS, …)` that
emits one row per borrower per tag, keyed by `borrower_id`, whose context aggregates that borrower's
attributed income documents (`[w2] tax_year=…; employer_name=… || [pay_stub] …`). Forward-compatible: on
today's borrower-less fixture it yields 0 rows (the honest `no_subject`); the day borrowers are wired into the
fixture, correct per-borrower rows appear with **no further generator change**.

**Merge method (unchanged from LP-337):** `write_worksheets` reads the existing file, keys filled rows by the
stable `(tag_id, subject_id)` pair, and re-applies each `(golden_label, labeler_note)` onto the regenerated
row. A dropped row simply has no counterpart to carry a label onto — and here every dropped row was empty.

**Per-file counts (before / dropped / added / preserved / flagged):**

|---|---|---|---|---|---|
| mechanical.csv | 70 | 0 | 0 | 70 | 70 (byte-identical) |

The git diff confirms: mechanical.csv byte-identical; judgment.csv exactly −32 lines (8 each of
has_2yr_history / is_declining / same_line_of_work / continuance_3yr), **zero additions**.

## Assumptions & decisions

- **Borrower-aware generator over a bare row-strip.** Making income_stability a real borrower group (0 rows
  today, correct rows when wired) is the honest, forward-compatible instrument and directly matches LP-385's
  producer, versus silently deleting the rows and re-adding a generator branch later.
- **No convention flags written**, because there are no conflicts (finding #2). The employer_normalized test
  asserts the label is *preserved*, which is the correct behavior given LP-340's strip-in-rule.
- **`id.address_normalized` mislabel is surfaced, not fixed** — Geet's call (the ticket forbids rewriting his
  goldens).
- **Consuming-rule metadata left as-is.** The worksheet's `consuming_rules` are descriptive; all these rules
  are inert. Re-mapping income_stability's rules (LP-385's IN-7/10/11/13/14 analysis) is a rule concern, out
  of scope for instrument prep.
