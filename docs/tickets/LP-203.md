# LP-203 — Field-shape primitives + PII handling

## Summary

The foundation for the Stage-1 snapshot: two frozen Pydantic primitives every
snapshot fact is built from — `Field` (value + nullable confidence + origin) and
`PiiField` (masked display + keyed match-hash, **no raw value**) — plus `mask()`
and a security-critical `match_hash()`. Pure primitives, testable in isolation;
nothing consumes them yet (the snapshot model is LP-204, assemblers later).

Architectural decisions recorded in **ADR-240** (`decisions.md`).

## Acceptance criteria

- [x] Frozen Pydantic `Field` = `{ value, confidence (nullable), source ∈ {parsed, extracted} }`.
- [x] Confidence reuses LP-201's model exactly — nullable, never fabricated;
      provenance derived (`confidence_source`), never stored.
- [x] **Absent ≠ empty:** a deliberate marker distinguishes "no source supplied"
      from "present but null/empty/zero"; not collapsed into null-value.
- [x] `mask(value, kind)`: last-4 only (`***-**-4821` / `****3312`); short /
      malformed / empty / null → safe placeholder, never raw, never crash.
- [x] `match_hash`: per-loan-file salt, consistent within a file, keyed by an
      application secret so a low-entropy input isn't brute-forceable.
- [x] Frozen `PiiField` = `{ display, match_hash, confidence (nullable), source }`,
      **no raw value field**; a factory takes raw + kind + loan_file_id.
- [x] Tests: absent vs empty; nullable confidence; mask edges; the hash security
      properties (same/diff file, secret-dependence, raw not recoverable);
      PiiField never carries raw.
- [x] ADR added (ADR-240) and referenced here.
- [x] CI green: ruff, mypy, pytest.

## Phase 0 findings

- **Pydantic v2**, frozen via `model_config = {"frozen": True}`.
- **LP-201 confidence model (reused):** `confidence: float | None` (never
  fabricated) with the tag *derived* via `ConfidenceSource.for_confidence`
  (`app/models/extraction.py`). `Field`/`PiiField` hold the number and expose a
  derived `confidence_source` property — no stored tag.
- **Secret management:** the app already has a PII secret — `settings.encryption_key`
  (a Fernet key, ADR-051), used by `app/core/encryption.py`. The match-hash keys off
  it (purpose-separated), inventing no new secret store.
- **No conflict:** no existing `Field`/`PiiField` or `snapshot` module.

## What was built

`app/verification/snapshot/`:

- **`fields.py`** — `FieldSource` (`parsed`/`extracted`), `JsonScalar`, and `Field`
  (frozen, `extra="forbid"`). Factories `Field.present(value, source=…, confidence=…)`
  and `Field.missing()`; `is_present` / `absent`; derived `confidence_source`. A

- **`__init__.py`** — public exports.

Tests: `tests/verification/snapshot/test_fields.py`, `test_pii.py` (28 cases).

## Assumptions & decisions

### Absent ≠ empty (the mechanism)
An explicit `absent: bool` marker, not a null value:
- `Field.missing()` → `absent=True`, no value/source/confidence — **no source
  supplied this fact**.
- `Field.present(None, source=…)` → `absent=False`, `value=None` — **a source
  supplied an explicit null/empty** (present-but-empty; `""`, `0`, `False` likewise).

A model validator enforces the two never blur. Chosen over a sentinel object
(awkward to JSON-serialize) and over "absence = key omitted from the map" (can't
record an explicit "we looked, nothing there"). The boolean serializes cleanly and
is unambiguous — and it's load-bearing: downstream rules must not treat "MISMO never
carried this" the same as "MISMO carried a blank".

### The match-hash construction (security-critical — why it resists brute force)
```
match_hash = HMAC-SHA256(key=K, msg=f"{loan_file_id}:{normalized_value}")
K          = SHA256(b"snapshot-pii-match-hash-v1:" + settings.encryption_key)
normalized_value = lowercased alphanumerics of the value
```
- **Per-loan-file salt** — `loan_file_id` is in the HMAC message, so the same SSN in
  two different loan files → different hashes (no cross-file correlation). Consistent
  *within* a file (same value + same file → same hash) so rule-matching works;
  normalization makes `123-45-6789` and `123456789` match.
- **Application secret — the crux for a low-entropy input.** An SSN has only ~10⁹
  possibilities and `loan_file_id` is **not** secret, so a bare
  `sha256(loan_file_id + ssn)` is brute-forced by anyone holding the hash (enumerate
  all SSNs, hash each, compare). Keying the HMAC with an application secret (`K`,
  from the same Fernet `encryption_key` that already protects PII at rest) makes the
  hash reproducible **only by the system** — without `K` an attacker can't compute it
  for any candidate, defeating brute force regardless of the input's low entropy.
- **Key separation** — `K` is `SHA256(purpose ‖ encryption_key)`, not the raw Fernet
  key, so the HMAC key is cryptographically distinct from the encryption key (no
  cross-use of a Fernet key as an HMAC key) while reusing the existing secret store.

### PII masking
`mask()` shows only the last 4 (`***-**-1234` / `****3312`). Every dishonest edge —
`None`, empty, malformed, or too-short-to-mask — returns a fully-masked placeholder
(`***-**-****` / `****`), never the raw value, never a crash. `PiiField` has no raw
field and `extra="forbid"`, so a raw value can't be attached even by accident; the
`from_raw` factory masks + hashes internally and discards the raw value.

## Deferred / follow-up

- The match-hash is a **keyed pseudonym**, not encryption — one-way, un-reversible
  even by the system; only for equality-matching within a file. A future ticket that
  *persists* snapshots must treat an `encryption_key` rotation (or a `v1` purpose
  bump) as a snapshot-rebuild trigger, since it changes all hashes.
- **Out of scope (later tickets):** which fields *are* PII (per-assembler), the
  snapshot model (LP-204) and any persistence, the assemblers, and any UI.
