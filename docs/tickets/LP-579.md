# LP-579 — the Apply button that refused itself

## The symptom

Clicking Apply on DT-8 produced **"Couldn't compute the impact preview."**

## The cause

LP-576 widened the **engine** so a `needs_review` evaluation carries an apply block — DT-6 and DT-8
can never fire by design, so without it the remediation those rules exist to offer had no button.

The **write path**, one layer down, still admitted only `OPEN`:

```python
if finding.evaluation_outcome is not EvaluationOutcome.OPEN:
    raise CannotApplyError("only a fired finding can be applied — …")
```

So the button appeared and refused itself. The preview broke for the same reason and not a separate
one: `preview_finding_apply` runs the **real** `apply_finding` inside a rolled-back savepoint, so the
guard rejected the dry-run too — the dialog whose entire job is to explain a change could not compute
one.

## Why the LP-576 tests missed it

Every one of them asserted `evaluation.apply` was populated. That is the **engine's** output. Not one
of them applied a `needs_review` finding.

*The button appearing* and *the button working* are different claims, and I tested only the first.
The tests here apply for real, and the second one asserts the preview computes — the exact reported
symptom, so a regression reproduces the user-visible failure rather than an internal proxy for it.

## The fix

`OPEN` and `NEEDS_REVIEW` may be applied. `SATISFIED` and `COULDNT_CHECK` still may not, for one
reason each: satisfied has nothing to remediate, and couldnt_check is an **abstention** — applying
off "I could not tell" is the CR-1 duplicate-liability trap LP-564 was written for, and it stays
shut. Both are pinned by a parametrized test so widening the gate cannot readmit them.

## Verified by removing the fix

| removed | result |
|---|---|
| `NEEDS_REVIEW` from the applicable outcomes | `test_a_needs_review_finding_applies` **and** `test_the_preview_of_a_needs_review_finding_computes` fail |
