## The dependency question, answered by measurement

The plan lists four new dependencies. I added **one**.

### `pikepdf` — added, because `pymupdf.scrub()` does not do the job

`pymupdf` is already a dependency and has a `scrub()` that reads like it strips exactly this. It does
not. Measured on a PDF **built by pymupdf itself** and armed through **its own low-level API**, so
"the probe was malformed" cannot explain the result:

```
armed (before scrub)   /JS=YES  /OpenAction=YES  /AA=YES  /XFA=YES  /JavaScript=YES
after scrub()          /JS=YES  /OpenAction=YES  /AA=YES  /XFA=YES  /JavaScript=YES
                       catalog keys still set: ['OpenAction', 'AA', 'Names', 'AcroForm']
after pikepdf strip    /JS=no   /OpenAction=no   /AA=no   /XFA=no   /JavaScript=no
```

My first probe was a hand-written PDF with no xref table, and it produced the same answer — which I
did **not** trust, because a malformed file is a perfectly good explanation for a library doing
nothing. The second probe removed that explanation. The result held.

**`test_pymupdf_scrub_is_not_a_substitute_for_pikepdf` pins this as a test rather than a comment.**
If a future pymupdf starts removing them, that test fails and somebody gets to delete a dependency —
an outcome a comment could never produce.

### `pypdfium2` — not added

`pymupdf` rasterises, measured. A second renderer is a second thing to keep patched on a path whose
entire job is reading hostile input.

### `puremagic` — not added

The allowlist is six types. An explicit signature table over a closed set is smaller and more
auditable than a library recognising three hundred formats — on this path, more recognition is more
surface, not less.

### `mail-parser` — not added (LP-804a's decision, restated)

## The defence is rasterisation

Everything downstream reads a rendered PNG, never the original. `/JS` and `/OpenAction` cannot run
against something that never opens them, and `test_the_raster_carries_none_of_them` asserts the
rendered bytes directly.

Sanitising the original is **defence in depth** for the one case rasterising does not cover: a
processor downloading what the borrower actually sent.

## What is refused, and why each refusal says why

| Case | State | Because |
|---|---|---|
| ZIP wearing a `.pdf` name | `QUARANTINED` | the ticket's own acceptance criterion |
| declared type ≠ sniffed type, both allowed | `QUARANTINED` | the subtler half of the same rule |
| any archive | `QUARANTINED` | a container for an unbounded number of decisions |
| encrypted PDF | `QUARANTINED` | detected, **never cracked** |
| `winmail.dat` | `UNSUPPORTED` | with an actionable reason — see below |
| unrecognised bytes | `UNSUPPORTED` | not a type this system handles |
| more than 200 pages | `QUARANTINED` | a page bomb is a few kilobytes |

**`UNSUPPORTED` and `QUARANTINED` are different conversations.** One means "we do not handle this
kind of thing"; the other means "this is not what it claimed to be". Only one is worth asking the
borrower about, which is why `safety_reason` exists — a state with no reason leaves a processor a
dead end, and "quarantined" alone cannot tell them whether to ask for a resend, a different format,
or a copy without a password.

**TNEF is detected and refused rather than parsed.** Adding a TNEF library for a case Outlook
produces only in RTF mode is not worth it — but silently dropping the attachment is much worse than
telling the borrower their mail client is hiding it, which is a setting they can change.

## A surviving mutant found a branch with no test

Disabling the declared-vs-sniffed mismatch check left **all 26 tests green**. The zip case is caught
by the archive rule *before* the mismatch check is reached, so the branch had no coverage at all.

Three tests added for it: a genuine mismatch (both types allowed, bytes disagree), a matching pair,
and a missing declared type — which is ordinary, since scanner output routinely omits it, and
treating absence as disagreement would quarantine it.

---

## Nothing is safe until it has been assessed

`b7` asked for this as a **positive assertion rather than an absence**, and it is
`test_nothing_is_safe_until_it_has_been_assessed`: straight after ingest, no attachment is `SAFE` and
none carries a sniffed type.

It matters because `PENDING` genuinely persists — INFRA-2's malware scan is asynchronous — so the
danger is not a momentary gap but something downstream reading "nobody has looked" as "no problem
found".

`apply_safety_to_message` touches **only** `PENDING` rows, so a replay cannot reset a verdict a
processor has already acted on.

## Deliberately not done

- **`derived_storage_path` is not set.** The rasterised pages are produced and discarded. *Where*
  they are stored is a bucket-and-path decision belonging with LP-806, which turns an accepted
  attachment into a `Document`. Producing them proves they **can** be produced, which is the half of
  the safety decision that would otherwise be assumed.
- **No TNEF parsing.** Detected and refused with a reason.
- **No change to `services/documents.py`.** The plan notes that the *upload* path rejects TIFF and
  HEIC while `storage/base.py` permits the extensions. This ticket fixes the **inbound** allowlist;
  the upload asymmetry is real and is not mine to change from here. **Recorded as an escalation.**
- **Nothing wired into a task.** `apply_safety_to_message` is a service. What calls it, and when
  relative to the GuardDuty result event, is LP-806's triage flow.

## For the reviewer

The three standing reviewer checks:

- **Tenancy** — no `company_id` anywhere.
- **Message content in logs** — the two log lines carry a count, a state tally, and the declared and
  sniffed **types**. No filename, no bytes. The type pair is logged on a mismatch because that is the
  security event, and a content type is a closed vocabulary rather than borrower content.
- **AI in the decision path** — none. Every decision here is a byte comparison.

The judgement calls worth a second opinion:

1. **Three dependencies declined.** Each has a stated reason and `pikepdf`'s necessity is pinned by a
   test. The one I would attack is `puremagic`: my signature table is six types and hand-written, and
   a library would handle malformed containers I have not thought about.
2. **Images are returned as their own raster**, unchanged. There is no structure to strip in a JPEG,
   but a malicious image targets the *decoder*, and the decoder here is whatever reads it later.
   Rasterising an image through pymupdf would normalise it at the cost of quality on a scanned
   payslip.
3. **`MAX_PAGES = 200`.** A real bank statement can be long. I have not seen one past 200, but I have
   not looked at a corpus either.
