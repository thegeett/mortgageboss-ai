# LP-474 — the accuracy-audit layer: deterministic self-consistency checks

The pipeline measures **coverage** (did we capture the fields?) and has never measured **correctness**
(are the values right?). v2 produced nine confident-wrong values; a wrong value is worse than a missing one
because the rule computes on it and nobody knows. This layer **FLAGS, never corrects**, and is **deterministic
(no model call)** — so it keeps working when the model changes (the same error class appeared on Sonnet, and
244 resisted two escalating prompt fixes). All numbers below are measured against the **stored v2 extractions**
(`mortgageboss-batch-bench-out/8c999b3f7a1b/_records.jsonl`, 303 docs) — no re-extraction, no model calls.

---

## Phase A — design (STOP-and-report)

### A1 — what already exists: the `count_field` cross-check (LP-438/445)

A nested list may declare `count_field` in its spec (`docs/schema-specs/*.json`); the generator **emits an
inline check** into the extractor (`emitters.py:emit_count_crosscheck`): if `data.{count_field}.value !=
len(data.{list})`, downgrade `SUCCEEDED → PARTIAL`. It has earned its place (Σ tradelines = 1432 = the declared
total proved a credit report complete, LP-445). **This is a spec-declaration → a deterministic comparison → a
status downgrade.** The accuracy layer should **extend the same declaration philosophy** (a second parallel
mechanism is how things drift), with two differences from the count-check: (a) the relation is *inequality*
("these two values must DIFFER") not equality, and (b) the surface is a **finding**, not a bare PARTIAL (A5).

### A2 — the candidate checks, scored against the STORED data

The nine known-wrong values, each tested against what is *actually in the extraction* (the gate of record):

| # | doc | catchable deterministically? | evidence |
|---|---|---|---|
| 1 | **088** state tax = federal Box 2 | ✅ **YES** — `state_income_tax == federal_income_tax_withheld` | TRUE for **only 088** across 22 W-2s (**0 FP**). Jurisdiction knowledge ("TX has no state tax") is NOT needed — the generic equality catches it. |
| 2 | **049** Zelle amount = running balance | ✅ **YES** — a transaction row's `amount == running_balance` | flags **exactly 1 row** across all 24 bank statements — 049's Zelle row (**0 FP**). |
| 3 | **096** W-2 Box 12 C = Medicare value | ✅ **YES** — a `box_12` item `amount == medicare_tax_withheld` | flags **only 096** across 22 W-2s (**0 FP**). |
| 4 | **253** gift $224,307.94 vs $24k | ❌ **NO** — the gift_letter extraction has **one** amount (`gift_amount`) and **no sibling** to compare it to. A magnitude error with no internal cross-reference is invisible to a self-consistency layer. |
| 5 | **244** Box 1 = Box 10 taxes | ❌ **NO (here)** — form_1098 has **no Box-10 typed field**; the taxes landed in `other_information` free text. Catching it needs a *new extraction field* — a schema change this ticket forbids. Defer to a schema ticket. |
| 6 | **credit_report** `date_opened` day fabricated | ❌ **NO (here)** — the stored `source.snippet` for a tradeline does not contain the opened-date source ("REPORTED 06/26" is a different date), so a snippet-precision check has nothing to read. Needs the extractor to capture the field's own source precision. Defer. |
| 7 | **104** "coinsurance contract" on an HO3 | ❌ **NO** — a value-content judgment, not self-consistency. |
| 8 | **146 / 294** hallucinated DL / DL-back read as registration | ❌ **NO** — the image gap (ADR-365/371); 294 is `no_extractor`. Other tickets. |

**The full bank-arithmetic chain (beginning + deposits − withdrawals = ending / per-row reconciliation) was
tested and REJECTED:** ~10 of 24 statements break the chain from ordering / sign-label / incompleteness, not
value errors — a **~40 % false-positive rate**. That is the LP-446 anti-pattern (a guard that misfires more
than it catches). The *tighter* `amount == running_balance` signature (check 2) is the shippable subset: same
catch, 0 FP.

### A3 — where a check lives: a spec DECLARATION + one shared evaluator

Checks 1–3 are **the same primitive** — *two extracted values that should DIFFER are equal* — over three
operand shapes: two typed fields (088), two fields of one list row (049), a list-item field vs a typed field
(096). Per the LP-437/460 lesson (a declaration scaled to 60+ lists; bespoke per-type files did not), the check
is a **spec declaration** — a `must_differ` (distinctness) block naming two value-references — evaluated by
**one shared deterministic function** over the extracted data. This **extends** the `count_field` declaration
home (A1), not a second parallel mechanism. ⚠️ Note: adding a *check declaration* is **not** the forbidden
"touch the schema" — it adds no extraction field and forces no re-extraction; it is metadata the check layer
reads. (Adding a Box-10 field for 244 *would* be a schema change — hence 244 is deferred.)

### A4 — false-positive risk, per check (measured, then the residual wild risk)

| check | corpus FP | residual wild-FP risk |
|---|---|---|
| `state_income_tax` ≠ `federal_income_tax_withheld` | **0 / 22** | ~nil — two independently-computed taxes equal to the cent is astronomically unlikely except an extraction error. |
| tx `amount` ≠ its `running_balance` | **0 / 24** | low — a first-row deposit into a $0 account could legitimately equal the balance; rare, and a finding just prompts a glance. |
| `box_12` amount ≠ `medicare_tax_withheld` | **0 / 22** | low-moderate — a Box-12 amount could coincidentally equal Medicare tax; the highest-risk of the three (drop it if we want maximum precision). |

Every violation is a **needs-review finding, never a hard failure** (A5), so even a rare wild FP costs a human
glance, not a blocked file — the honest outcome the ticket requires.

### A5 — what the flag does: a distinct accuracy FINDING (not a bare PARTIAL)

The count-check sets `PARTIAL` and emits **no finding** — so a coverage PARTIAL and an accuracy problem would be
indistinguishable if the accuracy layer also just set PARTIAL (the LP-462 lesson: recording one signal as
another corrupts the audit). Therefore the accuracy layer emits a **distinct `DocumentFinding`** — a new
`DocumentFindingType` (e.g. `CONSISTENCY`), naming the two fields and their equal values
("`state_income_tax` (35312.86) equals `federal_income_tax_withheld` (35312.86) — these should differ"). The
finding is OPEN → visible to the processor, and distinct from both a coverage PARTIAL (no finding) and a
cross-document `DISCREPANCY_CANDIDATE` (this is *within*-document). It **never rewrites the value**. Adding a
finding *type* is not an extractor/schema change. (Open question for B: also set PARTIAL? Recommend **no** —
keep coverage status orthogonal so the finding is the sole, unambiguous accuracy signal.)

### A6 — scope recommendation

**Ship ONE primitive — the `must_differ` distinctness check — with THREE declared pairs (088, 049, 096).**
Catch rate **3 of 9**, at **0 false positives** across the 303-doc corpus. This is the "small, correct set beats
a complete guessy one" the ticket asks for: one declaration-driven mechanism, three proven declarations, all
zero-FP, all model-independent.

**Deferred, with the reason recorded:**
- **253** — uncatchable by any self-consistency layer (no internal cross-reference); needs a source-magnitude
  model, which this layer deliberately is not.
- **244** — needs a Box-10 extraction field (a schema change); a `must_differ` pair
  (`mortgage_interest_received` ≠ Box-10) drops in **for free** the day that field exists.
- **credit_report `date_opened`** — needs the extractor to capture per-field source precision (MM/YY vs full
  date); a `date_precision` declaration is a clean future check once the data exists.
- **full bank-arithmetic reconciliation** — rejected now (~40 % FP); revisit only with sign/order normalization.
- **104 / 146 / 294 / 293** — out of class (value-content, image gap, plausible-but-wrong) — other tickets.

### One-bug-or-many / the honest headline

Three of the nine are one primitive at zero corpus-FP; the rest are genuinely out of reach of a *deterministic
self-consistency* layer for concrete, recorded reasons. **A wrong value with no internal contradiction (253,
293) cannot be caught by consistency alone — that is the boundary of this layer**, and worth stating so the
next ticket (source cross-checks / cross-document reconciliation) owns it.

**STOP — decisions for sign-off:** (A6) ship the `must_differ` primitive with the three proven pairs?
(A5) finding-only, no PARTIAL? (A4) keep all three pairs, or drop the box_12/Medicare pair for maximum
precision?

## Phase B — built (Geet: build the three, skip the rest)

**One declaration-driven primitive.** `app/ai/extraction/consistency.py` — a `MustDiffer(left, right, label)`
declaration keyed by document_type (`CHECKS`), a value-reference grammar (`NAME`, `LIST[].FIELD`), and one
deterministic evaluator over a normalized view (`normalize_result` for the live model via `model_dump`,
`normalize_bench_record` for a stored record — one evaluator, no drift). Numeric equality only; a zero value
never flags. The three declared pairs:

| type | pair | target |
|---|---|---|
| `w2` | `state_income_tax` ≠ `federal_income_tax_withheld` | 088 |
| `w2` | a `box_12_items[].amount` ≠ `medicare_tax_withheld` | 096 |
| `bank_statement` | a `transactions[].amount` ≠ its `running_balance` | 049 |

**The flag (A5).** New `DocumentFindingType.CONSISTENCY`. On a violation the pipeline
(`document_processing._extract_branch`, at the COMPLETED path beside `record_findings_from_extraction`) creates
a `CONSISTENCY` finding naming the equal values; **coverage status is left untouched** (SUCCEEDED stays
SUCCEEDED) so an accuracy flag is distinguishable from a coverage PARTIAL. **No value is rewritten; no model
call; never a hard failure.**

**Tests.** `tests/ai/test_consistency_checks.py` (the three shapes, zero-skip, clean-is-clean, scope);
`tests/tasks/test_document_processing.py` — a W-2 with state==federal produces exactly one CONSISTENCY finding,
status stays COMPLETED/SUCCEEDED, and the stored value is unchanged (`"35312.86"`); a clean W-2 produces none.

**Not touched:** no extractor, no extraction schema/field, no re-extraction, the count-check unchanged, the
sizing guard unchanged. (Adding a *check declaration* adds no extraction field — it is metadata the check layer
reads, distinct from the forbidden "touch the schema".)

## Phase C — proof (run against the STORED v2 corpus, no model calls)

Ran the evaluator over all **303 stored extractions** (`8c999b3f7a1b/_records.jsonl`):

- **Catches: 3 / 3 targets** — 049 (`amount 732.27 == running_balance 732.27`, row 7), 088
  (`state_income_tax 35312.86 == federal_income_tax_withheld 35312.86`), 096
  (`box_12 amount 2116.92 == medicare_tax_withheld 2116.92`).
- **False positives: 0 across all 303 documents.** (The exact result A4 predicted from the per-type previews.)
- **Value immutability asserted** — the evaluator returns `Violation`s only; a deep-copied input compares equal
  after evaluation.
- **Distinguishable from coverage PARTIAL** — proven by the pipeline test: the flag is a `CONSISTENCY` finding,
  the extraction status stays SUCCEEDED.
- **Equivalence:** `ACTIVE_RULE_IDS` = 37 (unchanged — no rule touched); `SNAPSHOT_VERSION` = 4 (unchanged — no
  extraction schema touched); ruff + mypy clean; full suite green.

### The three rejections, recorded with evidence (so no one rebuilds them on the same reasoning)

- **Full bank-arithmetic reconciliation — REJECTED (~40 % FP).** Tested across all 24 stored bank statements:
  **~10 broke the running-balance chain** from transaction ordering / sign-label / incompleteness, **not value
  errors**. That is worse than no check (LP-446). The tighter `amount == running_balance` signature is the
  0-FP subset that shipped.
- **244 (Box 1 = Box 10) — deferred as "needs a typed Box-10 field", NOT "uncatchable".** form_1098 puts the
  real-estate-taxes figure in `other_information` free text; there is no field to compare `mortgage_interest_
  received` against. The day a `real_estate_taxes_paid` field is added (a schema decision a later ticket may
  make), a `must_differ` pair drops in for free.
- **253 (lone $224k gift) — uncatchable by self-consistency.** The gift_letter extraction has one amount and no
  sibling; a magnitude error with no internal contradiction is invisible to this layer by construction. Needs a
  source-magnitude / cross-document check — a different layer.
- (Also out of scope: credit_report `date_opened` needs per-field source-precision capture first; 104 / 146 /
  294 / 293 are value-content / image-gap / plausible-but-wrong — other tickets.)
