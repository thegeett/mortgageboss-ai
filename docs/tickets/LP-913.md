# LP-913 — Conditions list view (S2-01, S2-02, S2-09)

**Goal:** the processor's main screen for conditions, replacing Stage 1's read-only imported list.

`ConditionsListView` replaces `ImportedView` in **one branch** of `ConditionsDashboard` — the imported
round. Stage 1's reading, failed, empty-draft and review screens are untouched, which is the whole
change to that file.

## The URL carries the filters, and deliberately not the search

`lib/conditions/list-url.ts`, modelled on `lib/loan-files/view-url.ts` because the spec names it:
"Filters live in the URL (like the pipeline's saved views), so a refresh or a shared link keeps them."
Same flat shape, same repeated keys, same one-parser rule.

**`q` IS THE EXCEPTION AND IT IS THE REASON THIS IS A SEPARATE MODULE.** The endpoint accepts it and
the pipeline writes its own search term — but `q` here searches `verbatim_text`, the lender's words
about a borrower's file. A shared link would carry "earnest money deposit in the amount of $2,850.00",
or an employer's name, into whatever the recipient pastes it into and into their history (ADR-405 as
amended: "a filter that matches NPI stays out of the shareable URL").

So the search box holds its term in component state, there is **no field on the state object that
could serialise it**, and `the search term never reaches the URL` is a test over a fully populated
state rather than a comment. The term still goes to the SERVER — it is a server filter, and LP-911
pinned that `conditions_listed` logs only filter NAMES — because what the amendment governs is the
shareable link, not the request.

**Unknown values are filtered, never cast**, for the reason `readPipelineUrl` gives: the endpoint
types these as enums, so an unrecognised one is a 422 and a blank page. A typo in a pasted URL should
drop that filter and show *more*; the day a status is retired, every bookmark carrying it should widen
rather than fail.

## Two queries, because the settled sections must survive the filters

The live list is filtered **by the server** — those filters are what LP-911 built and pinned ("open +
owner=borrower returns exactly 7086 6132 6637"), and not using them would strand that work and put a
second, disagreeing definition of "owner=title" in the client.

But S2-09 says in as many words that with filters matching nothing, **"the Cleared section is still
shown below"**. One filtered query cannot answer both "what matches what I asked for" and "what has
already been settled on this file", so there is one of each, and `ConditionsList` takes `settledFrom`
for the second. Deriving the sections from the filtered rows would make them vanish exactly when a
processor is most likely to want one — "that was cleared on the 12th" is a question asked while
hunting for something else.

## `X-Conditions-Capped` finally has a reader

LP-911's review recorded it: the cap is reported in a header (the body's shape was a Done-when), and
`fetchConditions` returned `.data` and dropped it — so **a truncated list rendered as a complete one**,
the precise failure the cap exists to make visible.

`useConditions` now returns `{ rows, capped }`. The header is read lowercased and compared against
`"true"` rather than trusted for truthiness (the string `"false"` is truthy), and it is only readable
at all because `main.py` names it in `expose_headers` — `page-image.ts` carries the same note, having
had width and height silently read back as 0 for a whole ticket.

Both consumers moved with it; `round-review.tsx`'s count feeds a Must-match sentence, so it had to keep
counting the same thing.

## The owner override was invisible, and the unknown owner had the wrong words

Two wording/behaviour corrections that belong to this screen:

- **`effective_owner`, not `owner_hint`** — carried over from LP-916 where the sheet's Owner select
  made the override reachable. The list and the filters now read the same value the server coalesces
  in Python and in SQL.
- **"Not known", not "Owner not known".** S2-01, S2-02 and S2-03 all draw the unknown owner as "Not
  known"; the Stage 1 pack never drew one at all, so the longer label was authored rather than taken
  from a screen, and LP-909's visual check records "owner chips" without pinning the wording. Not on
  any May-differ list, so by the rule it is fixed rather than recorded. Safe to shorten because the one
  sentence that would suffer already guards the case — `history.ts` never interpolates the label for
  `unknown` ("Waiting on someone" is its own wording) — and `OWNER_ICON.unknown` is `null`, so the
  label reaches the screen only through the plain-text chip the design labels "Not known".
  The filter description keeps the long form: it stands alone in a sentence, where "Owner: Not known"
  reads as a lookup and a bare "Not known" does not say what is unknown.

A third, found while grepping: `condition-detail-sheet.tsx` built its Owner select labels inline and
agreed with `OWNER_LABEL` **only by coincidence** once the label was shortened. It reads the shared
vocabulary now — the reviewer consolidated it one ticket ago for exactly this reason.

## Decisions taken without the product owner

| # | Question | Choice, and why it is the safe one |
|---|---|---|
| 1 | Does the search term go in the URL, as the pipeline does it? | **No.** It matches the lender's wording, so a shared link would carry NPI. Every other filter stays shareable, and the state object has no field for it — the absence is structural, not a convention. |
| 2 | Filter server-side or client-side? | **Server-side for the live list**, so LP-911's tested filters are the only definition of what a filter means. A client-side copy would be a second implementation of the same rule. |
| 3 | Where do the collapsed sections get their rows? | **From an unfiltered query**, so they survive the filters (S2-09). |
| 4 | A row: `<div role="button">` or a real `<button>`? | **A real button**, with the grid moved inside it. Focus order, Enter/Space and the screen-reader role arrive for free; the div had me reimplementing three of them. Three existing tests moved from `.closest("div.grid")` to `.closest(".grid")` — **no assertion changed**, including "no row may say cleared". |
| 5 | Does clicking an active summary number clear it? | **Yes.** A filter you cannot undo with the control that set it sends a processor hunting for a Clear button to escape one click. |
| 6 | Is grouping a filter? | **No** — regrouping hides nothing, so it is excluded from "is anything filtered" and never highlighted like one. Otherwise "Clear filters" would point at the wrong control. |
| 7 | Bulk refusals: does the client need `error.data.code`? | **No, and the deferral from LP-916 is resolved rather than carried.** The bulk endpoint answers **200 with refusals as DATA** (`{applied, refused:[{condition_id, code, message}]}`), so the codes arrive in the body and never through the error envelope. `lib/errors/api-error.ts` is unchanged. |
| 8 | The Stage 1 callout "nothing here is marked cleared or removed". | **Not carried over.** It promised a screen with no status controls; this one has them, so repeating it would be false. S1-08's partial-round line **is** kept — "conditions that weren't in it were left as they are" is still true and still the sentence that stops absence reading as removal. |

## A Done-when that was not covered, and now is

*"Bulk verdict on 5 rows writes 5 verdicts and 5 events."*

The only conditions bulk test applied **two** rows and counted events per row. It never asserted that
each row ends up carrying its **own** recorded verdict — so a bulk write that moved five
`lender_status` values while recording a single verdict for the batch, or one shared event, would have
satisfied every assertion in that file.

That failure would put "Cleared" on four conditions with nothing behind it. Only a recorded verdict may
say the lender cleared anything (ADR-404), and the verdict is what names who said so and where.
`test_a_bulk_verdict_on_five_rows_writes_five_verdicts_and_five_events` asserts the five applied ids,
a verdict with its source and date on every row, and exactly one `condition_verdict_recorded` each.
