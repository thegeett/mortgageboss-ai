## The program axis — the pattern LP-509 will follow

`LoanProgram` is a two-value enum (`CONVENTIONAL`, `FHA`) reaching the snapshot as `program.type`, which
was already declared. **Fannie-vs-Freddie and DU-vs-manual remain inexpressible** — no field carries
either.

**⚠️ Scoped as an APPLICABILITY PREDICATE, never an outcome**, and on these rules the difference is
load-bearing. The applicability layer resolves an **absent or `"unknown"`** predicate tag to
`couldnt_check` and only a **definitely-false** one to `not_applicable`. As an outcome, a file that does
not state its program would be **silently skipped** — on MI-1 that is the difference between "we could
not tell whether this loan needs MI" and saying nothing at all.

All three directions are proven per rule: **FHA → `not_applicable`** on MI-1, **conventional →
`not_applicable`** on MI-4, and **no program stated → `couldnt_check`** on both. LF-6T3N states no
program, so both abstain there — the honest answer.

## MI-1 — and the limit that stops it firing

**⚠️ MI-1 can prove MI is REQUIRED; it cannot prove MI is PRESENT.** The catalog says "LTV>80 test + PMI
present". The presence half has **no deterministic source**:

- **No document type carries an MI certificate or factor.** The only mortgage-insurance field in all 121
  schema specs is `form_1098.mortgage_insurance_premiums` — a *prior-year* figure for an *existing*
  mortgage.
- `mi.certificate_present` is an **uncalibrated AI tag**, which cannot gate a live rule (LP-484).
- `housing.mi_monthly` is undeclared, has no recipe, and reaches nothing.

So LTV > 80 → **`needs_review`** ("MI is required — confirm the file carries it"). Firing would assert MI
is *missing*, which the rule cannot know. That is IH-2's shape, and a test pins that no outcome can
produce `fired`.

**⚠️ The arithmetic is not reimplemented.** The recipe calls `app/verification/ltv.py` (LP-77), so the
rule path and the display path cannot drift into two different LTVs for one file. It reads the **base**
loan amount, never the note amount — on an FHA file the note includes financed UFMIP and would overstate
LTV.

**⚠️ A defect found and fixed after MI-1 shipped, of the same shape as the LP-487 review findings.**
`property.appraised_value` is **per appraisal document**, and the first version of the recipe took
whichever subject iterated **first** — an arbitrary LTV denominator on an ordinary file (an original plus
a replacement appraisal, or a 1004D the classifier cannot tell from a full report). It now takes the
**lowest**, following the policy LP-485 already set for this document family: where the guideline is
silent, take the **conservative** value. A lower appraisal means a higher LTV, which keeps MI-1's costly
direction — an MI requirement silently cleared — closed. Pinned by **value**, not just verdict, so a
regression to first-wins cannot hide behind a fixture where both appraisals happen to clear the
threshold. `loan.amount`, `loan.note_amount` and `property.purchase_price` are loan-scoped MISMO facts
with exactly one subject, so they are unaffected.

**⚠️ `mi.required` is deliberately left inert.** It exists in `fact_tags.csv` as *"Is MI required (LTV>80
conv)"* — a conclusion with the threshold baked in. Materialising it would move an 80 that belongs in
reviewable `reference_values` into a producer. **Tags describe, rules judge**; a test asserts it stays
undeclared.

**⚠️ `calc.ltv` also stays inert, and `loan.ltv_percent` is not a duplicate of it.** `calc.ltv` is an
**object** (`{value, breakdown[]}`) built for PR-1's transparent display; a rule cannot compare an object
with a threshold. The new tag is the same fact in the shape a rule can gate on.

## MI-4 — the finding that made it buildable, and the half that is not

**⚠️ NOT an ADR-330 vacuity, and this was the decisive Phase A check.** The two operands are two
**different** MISMO elements: `TERMS_OF_LOAN/BaseLoanAmount` (which the model maps to `loan_amount` — its
own comment records the mapping) and `TERMS_OF_LOAN/NoteAmount`. On an FHA loan the borrower signs for
the base amount **plus** the financed upfront premium, so the difference between them **is** the premium.
On the three conventional MISMO fixtures in the repo the two are equal — exactly right, and the reason
MI-4 must not run on a conventional file.

**⚠️ The annual MIP leg is NOT built.** No document type carries a monthly MIP figure for this loan.
Building it would mean inventing an input. **This also removes the need for the tier-U matrix cells
entirely**: ML 2023-05's per-cell annual rates were not obtained, and **no number from them is written
anywhere**. A test asserts no annual rate appears in the spec, so a later reader cannot build against a
figure nobody read.

**⚠️ Two exemptions we cannot detect.** Section **248** (Indian Lands) requires no upfront MIP; Section
**247** (Hawaiian Home Lands) no annual MIP. No field identifies either, so a loan financing **no**
premium lands on `needs_review` — "confirm it was paid in cash or that this loan is exempt" — never on
`fired`. **Outcome ordering is load-bearing**: that row must precede the below-the-rate row, or a note
equal to its base would fire as an under-payment instead of asking.

The tag emits a **rate**, not a dollar variance, so the 175-bps figure stays in `reference_values` where
it is cited and reviewable instead of hard-coded in a producer.

## CO-1 — presence only, and the fence around it

**⚠️ Warrantability is not decided here, and is not buildable.** Priya's standing point is that condo
rules must distinguish warrantable from non-warrantable. That is CO-3/CO-5's job, and
`property.is_warrantable_condo` has **no source field in any of the 121 schema specs** (LP-487
established this) because warrantability is a project-review *conclusion* (Form 1076 / PERS), not a
readable datum. **The tag stays inert, and a test pins both that it stays inert and that CO-1 gates on
nothing but the presence tag** — so nobody wires it to an invented source and quietly widens a presence
check into a warrantability rule.

**A document-type presence read** (the IN-8/IN-9/IN-16 discipline) — the classifier's **type label**,
never extracted fields. This matters concretely: the one condo questionnaire in the corpus fills **0** of
its unit-count fields, and CO-1 is still correct to report it present.

**⚠️ An empty file abstains rather than firing.** A file with no documents is not evidence the
questionnaire is missing — it is evidence nothing has been uploaded. Firing there would put a false gap
on every condo file the moment it is created.

## AU-3 — the `is_disputed` mistake, avoided on real evidence

The catalog vocabulary for `aus.recommendation` is **DU's**: `approve_eligible` / `approve_ineligible` /
`refer` / `out_of_scope`. The **one** `aus_findings` document in the 303-document corpus is an **LPA**
whose recommendation reads **`ACCEPT`** and whose eligibility reads **`ELIGIBLE`** — **neither term is in
that vocabulary**. A rule written as `recommendation == "Approve/Eligible"` would have abstained on, or
misread, every Freddie file. **One field, two vendor encodings** — CR-12's case exactly.

So `aus.recommendation` is **derived**, not parsed: it recognises a declared closed vocabulary spanning
both engines and abstains on anything else (ADR-376).

**⚠️ n=1, and that one is the LPA.** The DU spellings are **researched, not observed** — no DU file has
ever exercised them. They abstain rather than misfire if wrong, which is why this is shippable at all,
and a test pins that **both** engines' wording stays in the vocabulary so a later prune cannot silently
break the only real file we have.

**⚠️ The DU ↔ LPA equivalence is a domain claim, not a reading.** DU splits recommendation from
eligibility; LPA gives a risk class plus eligibility. Treating LPA `Accept` as DU `Approve` is the
standard industry equivalence, recorded in `reference_values` and logged for Priya rather than buried.

**⚠️ An approval whose eligibility cannot be read abstains.** "Approve" alone is not a clearance; reading
it as `approve_eligible` would turn an unread field into a delivery clearance.

## ⚠️ RE-2 — dropped, with the evidence

**RE-2 is not buildable, and was not built hollow.**

1. **No REO or retained-property concept exists anywhere.** `grep` for `reo` / `owned_property` returns
   nothing in `mismo_section.py` and nothing in `app/models/`. The MISMO section emits **21 facts**; none
   concerns another property.
2. **The non-subject property document types exist but are empty.** `property_tax_bill_non_subject`,
   `property_profile_non_subject`, `other_property_note` — all **0 of 303**.
3. **Decisively: nothing states that a borrower RETAINS a property.** RE-2's trigger is *retained
   property → tax/insurance docs present*. Owning another property is not the same as keeping it — the
   borrower may be selling it. Inferring the trigger would make the rule wrong at its root.

Building it would have produced a rule that `couldnt_check`s on every file forever with green tests —
**the exact ADR-286/289 failure the ticket named**. It joins DT-4 (LP-485) as a documented drop, not a
deferral. Where retained-property data should come from is question §10g for Priya.

## Assumptions and decisions

1. **`input_resolves` is the LP-485 development-mode meaning** on all four bars — the inputs are
   declared, their fields exist, and the producers resolve them on real stored data. **Not** the older
   "verified end-to-end on a live loan file" meaning the 11 pre-LP-485 bars use.
2. **`validated` stays `false` on all four**, and each bar says why: `is_eligible()` reads
   `input_resolves` **alone** for `no-ai-dependency`, so setting it would be decorative. MI-4's threshold
   is tier-P regardless; that is recorded in the spec, which is the calibration record.
3. **MI-1 and MI-4 never assert what they cannot see** — a required-but-unverifiable MI certificate, and
   an undetectable Section 248 exemption, both land on `needs_review`.
4. **AU-3 is per-document**, so several AUS submissions each get a verdict (the IH-1 shape). No reliable
   "governing submission" signal exists; a superseded run can appear alongside the current one.
5. **Test-count updates are census updates.** Sites moved because four rules genuinely activated and six
   tags were added; each carries its cause. **No test was skipped, xfailed, deleted or weakened.**

## What this changes downstream

- **The program-axis pattern is established** — predicate, not outcome; prove all three directions. LP-509

## ADR

**No ADR.** Four rules on the established spec/recipe/bar mechanism, plus one documented drop. The
program axis is a *use* of the existing applicability layer, not a change to it — LP-487's ADR-332
amendment and LP-501's expressibility finding already cover the reasoning. If Fannie-vs-Freddie or
DU-vs-manual ever needs expressing, that will need its own ADR because no field carries either today.
