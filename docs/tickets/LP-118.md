# LP-118 — Rule registry: verification_rules table + version-controlled seed + rule_change_audit (hybrid storage)

**Type:** Story · **Epic:** Phase 3.5 / Epic B (Rule Engine Generalization) · **Depends:** LP-115, LP-117.5
**Status:** complete · **Date:** 2026-07-07

## What this ticket is

The STORAGE FOUNDATION for the data-driven rule engine — the locked "hybrid storage" decision.
It builds three things and nothing more: a `verification_rules` table the engine will iterate at
runtime, a version-controlled seed that authors the rows and populates the table via migration,
and a `rule_change_audits` table recording every change to a rule row. It ends with a
**populated, queryable, audited** rule table + a **read-only loader**.

**Explicitly NOT this ticket** (later, held firmly): the applicability filter (LP-119),
evaluators / any rule execution (LP-120), the runner wiring (LP-121), the params admin UI
(LP-122). **Nothing executes a rule; the live verification path is unchanged.**

## What was built

- **Models** (`app/models/verification_rule.py`): `VerificationRule` (structural + tunable split,
  `validated` gate) and `RuleChangeAudit` (compliance history; FK with no cascade-delete so a
  rule with history can't be orphaned — rules retire via `enabled=false`). Registered in
  `app/models/__init__.py`.
- **Migration** (`…d4b8f1a63c27_lp_118_rule_registry.py`): creates both tables + indexes, then
  seeds from `rule_seed.json`, auditing each insert. Downgrade drops both. Verified up/down on
  Postgres.
- **Seed generator** (`app/scripts/generate_rule_seed.py`) → `docs/rules/rule_seed.json` (140
  rows). A superset merge: the 18 live `CROSS_SOURCE_RULES` (real rule_ids, LP-117.5 playbook_ids,
  known structural fields, `enabled=true`) + the 122 playbook rows not covered by a live rule
  (`pb.<id>` rule_id, `enabled=false`, null evaluator). Generated from code + the LP-117.5
  `rule_seed.csv`, never hand-typed.
- **Loader** (`app/services/rule_registry.py`): read-only `load_enabled_rules` / `get_rule` /
  `rule_change_history`, plus the shared sync `seed_verification_rules` used by both the migration
  and the tests.
- **Tests** (`tests/services/test_rule_registry.py`, 6): seed populates + audits; the 5 live rules
  present with real ids + employer→IN-5; structural/tunable + validated gate; loader returns
  enabled + fetch-by-id (inert snapshots); audit records the seed insert; seed idempotent. None
  execute a rule.
- **Docs**: ADR-238; `docs/rules/README.md` updated (rule_seed.json as the table seed + the
  authoring-vs-runtime flow).

## Assumptions and decisions

- **The seed was GENERATED here, merging LP-117.5's playbook CSV with the live code rules.**
  LP-117.5's `rule_seed.csv` is playbook-keyed and lacks `rule_id` + the structural/tunable
  columns the table needs, so LP-118 generates the richer `rule_seed.json` (the table's authoring
  source of truth) rather than loading the CSV directly. The CSV remains the playbook-identity
  input.
- **rule_id derivation for not-yet-built rows:** playbook rows with no live rule get a derived
  `pb.<playbook_id-lowercased>` PK (e.g. `pb.as-2`). These are `enabled=false` with null
  `evaluator`; LP-120 may replace the placeholder id with a real `xsrc.*`-style id when the rule
  is actually built. Live rule_ids are **never** renamed (they are the external reference).
- **Superset seed (140 = 18 live + 122 playbook-only)** so the table both *matches reality* (every
  live rule present with its real id) and *scales to the playbook* (all 133 playbook rules
  present; 11 of them are merged into their live rows via the LP-117.5 mapping, leaving 122
  playbook-only).
- **`category`/`status`/`scope`/`layer` stored as free strings** (the playbook's real vocab kept
  verbatim, per LP-117.5), not enums — the engine treats them as data.
- **`evaluator` left null for every row** (even live rules). Assigning evaluators + running them is
  LP-120/121; storing an evaluator name now risked implying execution. LP-120 fills them.
- **`validated`:** defaults false; only `xsrc.asset.large_deposit_unsourced` (AS-1, >50%) and
  `xsrc.income.stated_vs_documented` (IN-1, >5%) seed true (Priya-confirmed). **Threshold note:**
  the seed records IN-1's Priya-confirmed **5%** while the live code rule still uses its LP-80
  grounded-starter **10%**. Nothing reads the table yet, so this is not a behavior change; LP-121
  reconciles when it wires the table into the runner. Flagged in ADR-238 + the generator.
- **Migration vs create_all seeding:** tests use `create_all` (no migrations), so the seed logic
  lives in a shared sync `seed_verification_rules(bind)` that the migration calls with
  `op.get_bind()` and the tests call via `run_sync` — one code path, verified both ways. Migration
  up/down additionally verified against the real Postgres dev DB.
- **Calculators untouched:** the existing rule-registry threshold DATA the calculators read
  (LP-115 §7) is not moved or changed; this table is additive.
