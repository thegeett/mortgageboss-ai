# LP-406-3 — Write IN-6 (pay-stub ↔ W-2 coverage), the last Bucket 2 candidate — **STOPPED at Phase 0 (D2)**

## What this ticket is

The last of the four Bucket 2 "zero-dependency" rules, and the one predicted most likely to pass: IN-6 verifies
that a borrower's pay-stub employers and W-2 employers **cover each other**, and its only AI input
(`income.employer_normalized`) is **already measured 100%** via live IN-5 — so, unlike OC-1, there is **no
calibration hold**. **D2 (expressibility) ran first, and it stops the ticket.**

**The three gates (this Bucket 2 wave's lesson), applied to IN-6:**

| gate | IN-6 | verdict |
|------|------|---------|
| 1. inputs PRODUCED | `income.employer_normalized` is produced per income document (live via IN-5) | ✅ pass |
| 2. check EXPRESSIBLE in the DSL | a **two-way employer SET-COVERAGE** — neither `ConsistencyEval` (all-equal) nor the deterministic DSL (one value per subject) can express it | ⛔ **FAIL** |
| 3. any trusted AI tag CALIBRATED | `income.employer_normalized` measured **100%** (LP-379-D, `activation_bars.yaml` IN-5 `calibratable-now`) | ✅ pass |

Only gate 2 fails — but it is fatal. IN-6's check is **set coverage** ("every pay-stub employer has a matching
W-2 and vice-versa"), a **third relation class** distinct from *all-equal* (which `ConsistencyEval` does
natively) and *ordered-pairwise* (which ADR-322 already ruled needs a derived producer). Set coverage needs a
**new derived per-borrower producer**, whose construction this ticket scopes OUT ("propose, don't build"). Per
the ticket's own guardrails and the PC-7/AS-8 precedent, I **stopped before writing the spec, changed no rule
code, and report the finding + a concrete proposal.** Deliverables: this report + ADR-323. `ACTIVE_RULE_IDS`
stays **24**.

**Bucket 2 is now fully mapped: 1 of 4 rules was actually writable now (OC-1, and it is held); the other 3 each
need a small derived producer first.** The complete producer list is the scorecard at the end — ready to ticket
as one wave.

## D2 — EXPRESSIBILITY (run first) — **NOT expressible; STOP**

**IN-6's relation is two-way set coverage,** confirmed against the actual evaluator:

- **`ConsistencyEval` is ALL-EQUAL, not set-coverage.** `consistency.py:490–491` is the whole comparison:
  ```python
  normalized = {_normalize(inst.tag.value, con.normalization) for inst in gathered}
  if len(normalized) == 1:   # ALL equal → AGREE
  ```
  It gathers one **undifferentiated multiset** of `income.employer_normalized` across the borrower's documents
  (`_borrower_documents`) and asks *"do they all reduce to one value?"*. For a legitimate **two-job** borrower
  — employers A and B, each with a pay stub and a W-2 — the gathered set normalizes to `{A, B}`, `len == 2` →
  **DIFFER** → the fuzzy judge sees two genuinely different employers → **"disagree" → fires**. But IN-6 should
  **satisfy** (both employers *are* covered both ways). So `ConsistencyEval` **conflates "multiple employers"
  with "disagreement"** — it cannot express coverage. It also cannot **partition** the gather into a pay-stub
  set vs a W-2 set (its `gather_filter` is a single `TagCondition` that restricts to one type; there is no
  two-set comparison). **IN-5's own spec says so:** *"A borrower with two legitimate jobs shows two employers —
  the set-coverage case is IN-6, deferred; here the AI judges the residue as benign or not."*
- **The deterministic DSL resolves ONE value per subject** (`deterministic.py`) — it cannot gather a set at all,
  let alone two and compare their coverage. (This is also why a deterministic IN-6 would be structurally dead —
  D7.)
- **No existing mechanism does set coverage.** The only coverage-shaped rules in the vocabulary (CR-1/CR-4
  tradeline↔liability reconciliation) are **unwritten** (Credit is 0-written) — there is no implemented
  set-coverage evaluator to reuse.

**Therefore IN-6 needs a NEW derived per-borrower producer** (or a new consistency `compare_mode`) — building it
is OUT of scope (D2 stop). This is the **third relation class** the DSL cannot express natively, extending
ADR-322 (see ADR-323). The proposal is below.

### The concrete proposal (for a build ticket — NOT built here)

**New derived tag `income.employer_coverage` (per-borrower).** It reuses the consistency evaluator's own
building blocks, so this is an established pattern, not a novel mechanism:

- **Per borrower** (subject `borrower`, mirroring the per-borrower derived `income.documented_income_shortfall_pct`,
  LP-332): reuse **`_index_borrower_documents`** (`consistency.py` — the `belongs_to` attribution, the
  LP-385/389-A primitive) to get the borrower's income documents. **Per-borrower scoping solved (D4).**
- **Partition** those documents' `income.employer_normalized` values by `document_type` into a **pay-stub set**
  and a **W-2 set** (reading each doc's tag from `snapshot.tags.by_subject[content_id]`, the same read
  `_borrower_documents` does).
- **Normalize** each with the consistency chain (`casefold` / `drop_punct` / `collapse_ws` / `strip` /
  `drop_entity_suffix` — reuse `consistency.py._normalize`, so "Acme" ↔ "Acme Corporation" ↔ "Acme LLC" match,
  the LP-340/ADR-281 convention IN-5 already uses).
- **Check bidirectional coverage:** every normalized pay-stub employer ∈ the W-2 set, and vice-versa. Emit
  `"covered"` / `"uncovered"` (name the uncovered employer + direction) / `"n/a"` (the borrower lacks one of the
  two document types — nothing to cross-check, D5) / `"unknown"` (an employer name unreadable → fail-closed).
- **Size:** ~50–70 lines + one derived-registry entry + one `tag_production.yaml` declaration + one `fact_tags.csv`
  row — the footprint of a per-borrower derived producer.
- ⚠️ **The fuzzy residue** ("fuzzy names → AI" in the rationale): deterministic normalization handles the common
  legal-vs-common variance, but a **truly ambiguous** unmatched name (a possible DBA the normalizer can't
  resolve) is the case IN-5 hands to its AI judge. A pure derived producer can only do the deterministic
  coverage; the AI-fuzzy residue is a refinement (either a follow-up, or the alternative below). Flag for the
  build — do NOT let a normalizer miss silently pass as "covered".

**Alternative (mentioned, not preferred):** a new `ConsistencyEval` `compare_mode: coverage` with a partition
key + a residue judge — but that is an **evaluator change** (new Python in `consistency.py`), heavier than the
derived-tag pattern and touching a live evaluator; the derived tag is the cleaner, lower-risk path.

**Then IN-6's spec** (a follow-up, once the tag exists) is trivial deterministic: read `income.employer_coverage`
per borrower; `uncovered → fired`, `covered → satisfied`, `unknown → couldnt_check` (gate), `n/a →
not_applicable` (applicability predicate). No per-rule Python.

## D1 — What does IN-6 actually check?

**Quoted:** `rule_kinds.csv`: *"IN-6, Pay-stub <-> W-2 coverage, Income, structural, ai_fuzzy_match, … , Set
match of employers both ways; fuzzy names → AI."*

**One plain sentence:** *IN-6 verifies that, per borrower, the employers evidenced by pay stubs and the employers
evidenced by W-2s cover each other — every pay-stub employer has a corresponding W-2 and every W-2 employer has
a corresponding pay stub, tolerant of legal-vs-common-name variance.* The description is clear (not thin). The
tag it reads is exactly right (`income.employer_normalized` per document) — no OC-1-style name/semantics trap
here; the blocker is the *relation*, not the tag.

## D3 — The read-tags + real semantics

IN-6 reads **exactly one** tag (`rule_tags.csv`):

| read-tag | producer | subject | semantics | measured? |
|----------|----------|---------|-----------|-----------|
| `income.employer_normalized` | ai (group `income_employer`, `applies_to: [pay_stub, w2, 1003, voe]`) | **document** (per income doc) | the canonicalized employer name each income document states | **100%** (LP-379-D, live via IN-5) — **gate 3 satisfied** |

Per-document is exactly what a set needs — each pay stub / W-2 contributes one employer value. Forming the two
sets and comparing coverage is the part the DSL cannot do (D2).

## D4 — Per-borrower scoping

Coverage must be **per borrower** (borrower A's W-2 must not "cover" borrower B's pay stub). This is
**achievable and already precedented**: the consistency evaluator's `_index_borrower_documents`
(`belongs_to` attribution — LP-385/389-A) groups each document under its borrower, and the proposed producer
reuses it. So per-borrower is **not** a blocker — but it is only reachable through a **gather/derived**
mechanism, not the deterministic per_borrower enumerator (which hands a rule the borrower's own tag map, not the
borrower's documents' employer values). Confirms the derived-producer route.

## D5 — Absent / empty / unknown (argued; encoded in the proposal)

| situation | outcome | rationale |
|-----------|---------|-----------|
| no income documents at all | `not_applicable` | nothing to cover |
| **only W-2s, or only pay stubs** (one type absent) | **`not_applicable`** (recommended) | coverage is a relation between two sets; with one set empty there is no cross-check to perform. *(A "you must have BOTH a stub and a W-2" requirement is a separate document-presence rule, not IN-6's coverage relation.)* This is the one-statement→not_applicable trap in another form — flagged as a **Priya/design call** for the build. |
| both types present, an employer uncovered | `fired` | a W-2 employer with no pay stub (did they leave?) or a pay-stub employer with no W-2 (new job, no history) — name the uncovered employer + direction |
| an employer name unreadable (`employer_normalized` unknown/absent) | `couldnt_check` | fewer than the needed documents state a comparable employer — never a fabricated pass |

The **only-one-type → not_applicable** call is the key design decision (mirrors AS-8's one-statement case): the
producer must emit a distinct `n/a`, and the rule uses an applicability predicate so it does **not** collapse
into `couldnt_check` and look broken on a stub-only or W-2-only borrower.

## D6 — A Priya threshold?

**No numeric threshold**, but two latent Priya items for the build: (1) the **name-match tolerance** — IN-6
inherits IN-5's `drop_entity_suffix` convention (Acme Inc ≡ Acme LLC ≡ Acme, ADR-281, a flagged trade-off), so
IN-6 would ship `validated=false` carrying that same convention; (2) a possible **temporal-alignment** rule (must
a pay stub fall within / after the W-2's tax year to "cover" it?) — the rationale does not state one, so the
default is pure name-set coverage; confirm with Priya whether coverage needs a period constraint. Neither blocks
the *shape*; both are build-time confirmations.

## D7 — The subject match (anti-structural-death)

`income.employer_normalized` is `subject: document`. A **deterministic** per_borrower IN-6 would get the
borrower's own tag map (not the documents' employer values) → nothing to read → structurally dead (the ID-5
class). A **consistency/derived** reader is the correct one: IN-5 (per_borrower consistency) already reads
document-subject `employer_normalized` via the gather (`by_subject[content_id]`), proving the subject axis is
fine **through a gather** — but the gather's *comparison* (all-equal) is the wrong relation (D2). The proposed
derived producer reads the same document subjects correctly. So D7 is not the blocker; the **relation** (D2) is.

## The IN-5 / IN-2 overlap boundary

- **IN-5 (Employer name consistency)** — *do all the mentions of the employer agree?* Gathers
  `employer_normalized` across the borrower's income docs and fires on a genuinely different employer with no
  explanation. Its spec explicitly **defers the set-coverage case to IN-6**.
- **IN-6 (Pay-stub ↔ W-2 coverage)** — *is each employer documented across both document types?* Fires on a
  **missing counterpart**, not on multiplicity.
- **The boundary is clean and complementary:** a two-job borrower is IN-5's ambiguous residue (its AI judge
  decides benign-vs-real) but IN-6's **satisfied** case (both jobs covered both ways); a single job missing its
  W-2 is IN-6's **fired** case but IN-5's **satisfied** (one consistent employer). They answer different
  questions on the same tag — no double-fire on the same finding, provided IN-6 is scoped to *coverage gaps*,
  not *employer multiplicity*. **IN-2** (pay-stub recency, dates) is unrelated. Report: no harmful overlap;
  IN-6 is a distinct concern.

## THE PROOF

None to report — no rule written. A deterministic IN-6 would be structurally dead (D7); a `ConsistencyEval`
IN-6 would **false-fire on every legitimate multi-employer borrower** (D2) — either would be a broken rule, which
the ticket forbids shipping. The fixture that *would* exercise the built rule is `eval/income_scenarios.py` (it
carries employer-change / multi-employer W-2+pay-stub borrowers) — a build-time proof, not this ticket.

## Every assumption / decision

- **The gate is producer × expressibility × calibration.** Producer read from `tag_production.yaml` (produced);
  calibration read from `activation_bars.yaml` (IN-5 `calibratable-now`, measured 100%); expressibility read
  from `consistency.py:490` (all-equal) + the deterministic operand model. Every claim is a read.
- **Set coverage ≠ all-equal**, verified against the actual `len(normalized) == 1` comparison and the
  two-job counterexample — not assumed. IN-5's spec independently confirms IN-6 is the deferred set-coverage
  case.
- **A derived per-borrower producer is the fix** (established pattern: `income.documented_income_shortfall_pct`

- **I did not invent a narrower IN-6** to force a fit; the rationale is unambiguously two-way set coverage, and
  collapsing it to all-equal would duplicate IN-5.
- No rule code changed. `ACTIVE_RULE_IDS` = 24. This report + ADR-323 are the only deliverables.

## What this means going forward

The reusable rule, now proven three times: **classify a cross-document rule's RELATION before writing it.** The
DSL expresses **all-equal** natively (`ConsistencyEval`); **ordered-pairwise** (AS-8) and **set-coverage** (IN-6)
each need a derived producer; **date-vs-today** (PC-7) needs a derived recency tag. "Inputs produced" (LP-405)
is necessary but not sufficient — the *check* must be expressible, and any trusted AI tag calibrated. Applying
all three gates up front is what turned four uncertain tickets into one clear producer wave + one calibration.

## ADR

**ADR-323** (added to `decisions.md`): set-coverage is a **third** cross-document relation class the
deterministic DSL / `ConsistencyEval` cannot express natively (extending ADR-322's ordered-pairwise finding);
`ConsistencyEval` is strictly all-equal, so set-coverage — like ordered-pairwise — must be computed in a derived
producer and read as a tag. Recorded because the ticket asked for it ("record if D2 finds set-coverage also
inexpressible") and because it completes the relation-class taxonomy the producer wave rests on.
