# LP-446 — Step F: apply the 18 extractor diffs; fix the credit report's unreliable completeness check

## What this ticket is

The schema work (LP-434–445) reached the 91 rarer document types but **never reached the 18 most-common** —
pay stubs, bank statements, W-2s, homeowners insurance. LP-440 deliberately emitted DIFF REPORTS (not patches)
for the types that already had hand-written extractors, and nobody applied them. So the live extractors feeding
live rules were still running their **original Phase-1 field lists** while the audit showed rules starved.
This applies the diffs (**Phase A: the three highest-value, then STOP**; Phase B: the remaining 15) and folds in
the credit report's `total_tradeline_count` fix from LP-445.

## D1–D5

- **D1 — a diff is safe to apply, no version bump.** Each added field is a `TypedField` with `default_factory`,
  so a stored extraction that predates it validates to an empty field; the snapshot surfaces only present
  fields. Purely additive → `SNAPSHOT_VERSION` stays **4** (the LP-421 rule; a bump breaks the v4 golden
  fixture).
- **D2 — hand-edit, not regenerate.** All three modules are hand-written, and their specs are DIFF-MODE
  (`existing_extractor` set) → the generator emits a *report*, not a module. Regeneration is not available and
  would destroy hand-written logic (bank_statement's `_parse_transactions` + deterministic `pdf_page_count` for
  AS-9, `source_payload` handling). So the ADD items are applied by hand — this is *why* the 18 lagged.
- **D3 — the insurance spec (headline foundation).** The spec `011-homeowner-s-insurance.json` DOES declare the
  dwelling-basis concept — as **`replacement_cost_or_coinsurance_basis`** (`exists_today=false`) + the
  **`forms_and_endorsements`** list — **not** under the name `loss_settlement_basis` (that lives only in LP-431,
  IH-1's ticket). That's why the audit's grep for `loss_settlement_basis` returned zero hits: the field exists
  under a different name. A wiring gap, not a spec gap.
- **D4 — lists on live extractors.** pay_stub gains `earnings_lines` + `deduction_lines`; homeowners_insurance
  gains `forms_and_endorsements`; bank_statement's generic `transactions` list is already wired (LP-443) and its
  legacy attributes are untouched. All coexist; nothing migrated.
- **D5 — the credit-report fold-in.** `total_tradeline_count` REMOVED from the status cross-check (kept for
  info, hint tightened); `public_record_count`/`inquiry_count` stay; the payment-sum check NOT added (n=1,
  unjustifiable tolerance).

## PHASE A — the three diffs, proven on real documents

### ⚠️ homeowners_insurance — the headline (the dwelling loss-settlement basis, per real policy)

+13 typed-core fields (incl. `replacement_cost_or_coinsurance_basis`, `policy_form`, `mortgagee_count`,
`document_issue_date`) + the `forms_and_endorsements` list. `_MAX_TOKENS` 4096 → 8192 (now list-bearing).

| policy (real) | dwelling basis (`replacement_cost_or_coinsurance_basis`) | forms/endorsements | verdict |
|---|---|---|---|
| Northern (39 KB) | **`replacement cost`** ✅ | 1 (dwelling-level) | explicitly stated → captured |
| **Occidental** (107 KB) | **`null`** | **11, incl. 1 personal-property replacement-cost endorsement** | **anti-conflation HELD** — the PP endorsement is a list row; the dwelling field stayed null |
| Universal (1.1 MB) | **`Replacement Cost`** ✅ | 11 | explicitly stated → captured |
| Liberty (2 KB stub) | `null` | 0 | a 2 KB stub, not a real policy |

**On the 3 real policies: the dwelling basis is reachable on 2 of 3** (vs the audit's "1 of 3, only prose in the
discarded catch-all"). On Occidental it is honestly `null` because the document only IMPLIES the basis via the
`HO 00 03` form code + a personal-property endorsement — and **the schema correctly did NOT conflate the PP
endorsement into the dwelling field** (the exact misread the audit found unprevented). Where the dwelling basis
is not explicitly stated, IH-1 still `couldnt_check` — a document/schema limit, not a wiring one.

## The credit-report fold-in (D5)

`total_tradeline_count` produced a NEW false PARTIAL after LP-445 — the model declared 20 against a correct 18
rows. It is **removed from the status cross-check** (kept for information; hint tightened to "only if explicitly
printed incl. closed; never compute/estimate/infer"). Tradelines now have **no completeness gate** — better than
a second misfiring one. `public_record_count`/`inquiry_count` stay. The `Σ(monthly_payment) ==
total_monthly_debt_payment` check was **not** added (held on n=1 but an exact/±1 gate is unjustifiable — a total
that excludes a $0-payment closed account would false-PARTIAL).

### Two STOPs (the D2 lesson — do not disturb hand-written / legacy logic)

- **tax_return `schedule_c`** — the diff proposed a generic `schedule_c` list, but that name is a **live legacy list attribute** feeding IN-12/IN-13. A generic capture would duplicate it. **List deferred; the +14 typed-core fields applied.** Proven intact on a real return: `schedule_c` still extracts **2 rows** post-diff.
- **divorce_decree `support_obligations`** — needs bespoke obligation/award parsing (amounts, payer/payee, term) a flat bare-row capture can't carry. **List deferred; the +12 typed-core fields applied.**

### Proven on real documents (the live-rule types)

| type | doc | status | typed-present | catch-all | list |
|---|---|---|---|---|---|
| w2 | real, 2 KB | SUCCEEDED | 13 | 0 | — |
| purchase_agreement | real, 2 KB | SUCCEEDED | 16 | 0 | contingencies: 1 |

The dev-DB samples are small synthetic stubs (catch-all already 0), so the Phase-A-style "catch-all fell from 57–78" number isn't reproducible on them — but the new typed fields populate and, critically, **`tax_return.schedule_c` still returns 2 rows**: the legacy list feeding IN-12/IN-13 is untouched. On a real multi-page document the same +N typed fields displace the same N prose fields from the catch-all; the structural reduction is the +field count per type above.

### A real finding fixed here — three list-bearing types were under-budgeted

`voe`, `hoa_statement`, `property_tax_bill` each gained a generic list but had been left at the 4096 scaffold budget → a real truncation risk on a document with many installments / earnings rows. Raised to **8192** (the 1-list sizing rule), mirroring homeowners_insurance in Phase A. The budget-sizing test was updated to assert it.

## NEW gaps / what remains

- **IH-1 still `couldnt_check` on a policy that never states the dwelling basis** (e.g. Occidental) — the schema
  refuses to fake it; a document limit, reported.
- **A2** (surface the catch-all / the new fields to a snapshot consumer) and **rules reading the new fields**
  (IH-1 on `replacement_cost_or_coinsurance_basis`, IN-10/IN-11 on `earnings_lines`, AS-6 on
  `account_owner_name_2`) are separate tickets — nothing here wires a rule.
- **Two bespoke lists deferred** — `tax_return.schedule_c` (duplicates the live legacy attribute) and
  `divorce_decree.support_obligations` (needs bespoke award/obligation logic). Their typed-core fields WERE
  applied; only the lists were held. Wiring them is a separate, non-generic ticket.
- **Rules reading the Phase B fields** — W-2 → IN-5/IN-6/IN-11, tax_return → IN-12/IN-13,
  purchase_agreement → PC-2/PC-7 do not yet read the new typed fields; that is the A2 follow-on, per type.
