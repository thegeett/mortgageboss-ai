# LP-461 — Schema-gap remediation, Phase 3: the missing scalar fields

The final phase from the 268-doc comparison. Unlike Phase 2 (tables, 7/7 real), this is **scalar fields**, and
LP-458 showed scalar claims from the free reader over-recall. So Phase A verifies each field against the
document before anything is built.

**Method:** three sources per claim — (1) the type's spec (`docs/schema-specs/<type>.json`) for the
SCHEMA-EMPTY check; (2) what the **trustworthy bench extractor** dumped into its catch-all (a field there is
printed-but-unslotted → REAL); (3) the source PDF for the highest-stakes / ambiguous claims. Five types were
page-verified (bank_statement, w2, drivers_license, purchase_agreement, pay_stub); the rest resolved on the
bench-vs-cowork extractions.

## ⚠️ bank_statement multi-account — options (needs a DECISION, per scope)
Confirmed data loss (057: a $54,694 savings account + its rows dropped; single-account schema). This is
structural — I did not build it. Options:
1. **`additional_accounts[]` flat_row list** (number_masked, type, beginning/ending balance) — surfaces the
   existence + BALANCES of the dropped accounts (fixes the reserves-loss) **without** restructuring
   transactions. Cheapest; LP-460 pattern; the extra account's *transactions* still aren't captured.
2. **Second account block + second transactions list** (`secondary_account_*` + `transactions_2`) — captures
   two accounts fully. Caps at 2; asymmetric/ugly; still drops a 3rd.
3. **Restructure to `accounts[]`** (each account its own balances + nested transactions) — correct, but a
   large structural change: AS-8/9/10 read the single-account typed fields today, so it needs a migration
   and touches live rules. Out of proportion to a field-addition phase.
**DECISION (Geet): Option 1.** It recovers the reserves-critical balances, is additive, and does not touch
AS-8/9/10. Option 3 is the correct end state but a field-addition phase is the wrong place to restructure the
input of three live rules — that needs its own ticket with a migration and an equivalence proof.

**⚠️ Recorded consequence (a live inaccuracy today, not just a doc note):** `additional_accounts[]` surfaces
the *existence and balances* of the extra account(s), but the extra account's **transactions remain
uncaptured** — so AS-8's chaining and AS-1's deposit sweep still see only account #1, and a rule reading
`ending_balance` on a combined statement gets only the first account's balance. A code comment is placed at
`ending_balance` / `transactions` (module + spec) where a future rule author will see it, in addition to the
future-ticket entry below.

## ADR — the verification rate establishes the standing rule
The dissolve was **real but concentrated**: `purchase_agreement` (free-text contract) verified ~1-of-8
(matching LP-458's 4-of-10), while claims on **fixed-layout forms** (W-2 boxes, DL fields, pay-stub YTD,
tax-preparer block, payoff NMLS, HOA/gift fields) verified at a high rate. With LP-460 (tables, 7/7): **a
scalar claim from the free-reader comparison needs document verification — most of all on a free-text
document; a table claim generally does not; a fixed-layout form sits in between, closer to a table.** The
most valuable finding this phase was structural, not a field (the bank_statement data loss). The one
build-side miss (143 DD) reproduced the LP-460 lesson at field granularity: strengthen once, verify, stop
before over-recall.
