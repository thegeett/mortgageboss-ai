# LP-370 — The live-rule materialization audit (READ-ONLY)

## WHAT THIS TICKET IS

"Live" has meant "in `ACTIVE_RULE_IDS`" — not "produces a verdict." Three of eleven live rules were found
silently dead, each by accident: AS-1 (income through a calc gated on an unused input — LP-366), ID-2 and
ID-3 (parsed declarations naming fields that don't exist — LP-369). **Every test was green throughout.** This
ticket checks the other eight — and re-verifies the four already touched — **on purpose.** The only deliverable
is this report; nothing was changed.

**Headline:** a **fourth** silently-dead live rule found — **OC-2** (occupancy reasonableness): its two
load-bearing tags are declared in the vocabulary but never in `tag_production.yaml`, so they never
materialize → OC-2 couldnt_checks on **every** file (the orphan shape, LP-366-A/367). One more rule, **ID-4**,
is a genuinely-hard call: its mechanism is sound but its filter gate may suppress it on most real files —
unverifiable on this one file. Of the 11, after LP-366/369's fixes: **6 produce a real verdict, 3 are
correct-but-unexercised, 1 (ID-4) is uncertain, 1 (OC-2) is a confirmed bug.**

## AUDIT METHOD (evidence at every hop)

For each live rule: spec → its load-bearing/gathered/operand tags → each tag's declaration (does it point at
something that EXISTS?) → the real snapshot's tag layer (did it materialize? how many real vs abstain vs
absent) → the verdict + its ROOT, classified. Sources: the persisted `snapshot_records` row (run `01039e93`,
the LP-365 real run); the persisted `Finding` rows (real verdicts, incl. the AI judgment rules, which a
keyless replay cannot reproduce); and a **deterministic replay** (`materialize_tags(only_groups=∅)` +
`evaluate_rules`) of the non-judgment rules with the **post-LP-366/369** declarations, to show the fixed state.

## THE BUGS, RANKED BY BLAST RADIUS

### 1. OC-2 — occupancy reasonableness — STRUCTURALLY DEAD (the orphan shape)
- **Evidence.** OC-2's `deterministic`/`judgment` block lists load-bearing tags `occupancy.stated` and
  `occupancy.consistent_with_signals` (`OC-2.yaml`). Both are in `fact_tags.csv` (lines 77–78) with producers,
  but **neither is declared in `tag_production.yaml`** (`grep` → 0 each) and **neither appears in the persisted
  snapshot** (0 instances). A judgment rule GATES its load-bearing tags fail-closed BEFORE any AI call
  (`judgment.py`; `gate.py:56` — an absent required tag → couldnt_check). **So OC-2 couldnt_checks on every
  file, structurally — no run needed to know it.** No note marks it as intentionally-pending.
- **It is FIXABLE (a missing declaration, not missing data):** `property.occupancy` EXISTS in the MISMO facts,
  so `occupancy.stated` could be `{mode: parsed, subject: loan, data: property.occupancy}`;
  `occupancy.consistent_with_signals` needs its AI group declared + run.
- **Blast radius:** occupancy reasonableness — an occupancy-fraud / misrepresentation signal — is **never
  assessed on any file.** A destroyed signal (silent false-green on a whole category). OC-2 is a JUDGMENT rule
  (ratification-pending), so it would not auto-ship a wrong answer — but it never surfaces occupancy for a human
  either. **High** (an entire live category silently unchecked).
- **Fix ticket (scoped):** declare `occupancy.stated` (parsed from `property.occupancy`) and the
  `occupancy.consistent_with_signals` AI group; verify OC-2 gets its tags and produces a judgment; re-run on a
  real file. (Mirror the LP-366-A/369 pattern; add the AI group to `_required_ai_groups` via OC-2's
  load-bearing set — which happens automatically once declared.)

### 2. ID-4 — current-address consistency — UNCERTAIN (cannot be settled on this file)
- **Evidence.** ID-4 gathers `id.address_normalized` filtered by `id.current_address_type == residence`
  (`ID-4.yaml`), and — when there are ≥2 address candidates — GATES the filter tags' confidence/known-ness
  (`consistency.py:381–395`): **if ANY candidate's `current_address_type` is `unknown`, the gate fails →
  couldnt_check** ("the address-type classification … is not trustworthy: doc… is unknown"). On LF-6T3N,
  `current_address_type` is `residence` on only the 2 driver's licences and `unknown` on the other
  address-bearing documents (bank statements, etc.) → the gate fails for both borrowers.
- **Why it is UNCERTAIN, not a clean call.** The mechanism is sound and the tags materialize — so it is not
  structurally dead like OC-2. On a file where every address-bearing document is confidently typed, ID-4 would
  compare. BUT bank statements reliably carry an address the AI types `unknown`, so **any realistic file with a
  bank statement may poison ID-4's filter gate → couldnt_check.** I cannot tell from THIS file whether ID-4
  "works but this file is thin" or "is effectively suppressed on all real files." **This is exactly the call
  that let AS-1/ID-2/ID-3 survive — so I am NOT calling it correct.**
- **Blast radius:** address consistency is an identity-fraud signal and ID-4 is a CONSISTENCY rule
  (auto-ships satisfied/fired). If it can never fire, discrepancies go unflagged — a false-green. **Medium**,
  pending confirmation.
- **What would settle it:** a file where the borrower's residence address is confidently typed on ≥2 sources
  with NO `unknown`-typed address candidate (e.g. a 1003 + a DL, no bank-statement address in the candidate
  set) — does ID-4 then compare? And a design review of whether ONE `unknown` candidate should veto the whole
  comparison, or only be excluded.

4. **Orphan shape (declared in vocab, no producer):** **FOUND — OC-2** (`occupancy.stated` /

## ASSUMPTIONS + DECISIONS (especially the "correct, not a bug" calls)

- **ID-7 / ID-9 = correct-absent-source (NOT bugs):** their applicability document types are in the classifier
  catalog; LF-6T3N simply lacks a title commitment and a POA. Evidence: `classification_prompt.py:89,134`.
- **ID-3 = correct-thin (NOT a bug):** the tag is fixed and materializes; the file has one DOB source per
  borrower and a consistency rule needs ≥2 (LP-325). Evidence: replay reason "only 1 source carry 'id.dob'".
- **ID-8 = works (needs_review is not failure):** for a judgment rule every verdict is ratification-pending;
  the gate passed (both tags present) and the AI judged. Evidence: 2 needs_review (not couldnt_check) + the
  materialized citizenship/program tags.
- **OC-2 = bug (structurally dead):** the ONE call I am most confident of — no run needed; an absent required
  tag deterministically gates to couldnt_check.
- **ID-4 = explicitly UNCERTAIN, deliberately not called "correct":** the mechanism runs, but I cannot show it
  can EVER fire on a realistic (bank-statement-bearing) file. Calling it "correct-thin" is exactly the mistake
  that hid three dead rules; I am flagging it instead.

## THE HONEST LIMIT — what one file cannot establish

LF-6T3N is **one** 2-borrower conventional purchase with **no title document, no 1003/URLA document, no VOE,
no POA, no insurance binder, and 4 untyped documents.** Consequently:
- **ID-3, ID-7, ID-9** are unexercised — a rule that couldnt_checks here for a genuinely-absent input might be
  fine or hiding a second bug; a file WITH those documents (a title commitment; a 1003 surfacing a second DOB;
  a POA) would settle each.
- **ID-4** cannot be classified — needs a file with confidently-typed addresses and no `unknown` candidate.
- **The judgment verdicts (OC-2 aside)** come from the persisted LP-365 findings (real model), not a fresh run
  — reproducible only with the model.
- **The 15 dormant rules and the income/asset tag layer** (LP-368) are entirely out of this audit's scope and
  have never run on real data.
