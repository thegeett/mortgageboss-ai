## The two STOP AND ASK points, resolved

Spec §LP-905 marks two. Both were already answered with evidence by the survey, and the product
owner confirmed both rather than changing them:

**Where the PDF is stored** — `storage.save_at()`, with **no `Document` row**. The spec's trigger is
conditional ("STOP AND ASK *if the only way* to store it would send it through classify → extract →
needs") and it does not fire: `save_at` exists precisely for bytes that are not a document and have
no derived path. A condition sheet satisfies no need and would be classified against a 166-type
*borrower* taxonomy, which is the same reasoning that produced
`AttachmentDisposition.CORRESPONDENCE`.

**Whether `CORRESPONDENCE` keeps the file retrievable** — yes, via `_attachment_bytes`, which
re-derives the bytes from the stored raw message rather than storing a second copy. Section 3 uses
it; nothing new is needed.

## Section 1 — the sheet arrives

**`condition_sheet_max_bytes`, default 20 MB.** Larger than the 10 MB MISMO cap because a two-page
UWM letter rasterised by the lender's own pipeline is routinely several megabytes, and a scan more
so. Enforced by a **chunked** read that aborts at the limit — reading the body and measuring it
afterwards means a 2 GB upload is already in memory by the time it is refused, which makes the cap a
formality rather than a defence.

**`ActivityType.CONDITION_SHEET_RECEIVED`,** its own type rather than a `DOCUMENT_UPLOADED` detail.
A timeline that filed a condition sheet under "document uploaded" would invite exactly the confusion
ADR-403's boundary exists to prevent.

**The service opens the round before anything reads it** — `status = PARSING`, `sheet_format =
GENERIC` — so the endpoint answers `202` immediately with a row the UI can poll (screen S1-02,
"Reading…"). Answering only when the parse finished would make a slow lender's PDF look like a broken
upload.

### Decisions worth arguing with

**PDF-only is checked on the sniffed type, not on the safety state.** ⚠️ `assess()` returns `SAFE`
for an **image** too — *"an image has no executable structure to strip and no pages to render — it IS
the raster"* — so a PNG passes the safety check cleanly. Keying only on the state would accept a
screenshot of a sheet and fail deep inside the reader, where the message means nothing. The three
refusals now read: a real PDF is accepted; a PNG gives *"The file says it is application/pdf but its
contents are image/png."*; rubbish gives *"The file type could not be identified."* Three distinct,
actionable messages, which is what §9.8 asks for.

**The storage path is server-controlled and never derived from the filename.** `save_at` refuses
traversal, but the deeper rule is that a real sheet's filename routinely carries the borrower's
surname and the loan number — building a path from it would write NPI into the storage layout itself.

**`round_date` is supplied explicitly.** It is NOT NULL with no default, and until the sheet is read
there is no printed date, so the round is dated by arrival with `date_printed` left null. Omitting it
fails the insert outright — the same shape as the `display_id` defect that hid LP-904's guards.

**The task is enqueued after the commit.** A worker that picked the round up before the transaction
landed would find no row.

## ⚠️ The constraint swap, and two ways I nearly got it wrong

Adding one `ActivityType` value means rewriting the whole CHECK (ADR-037: `str_enum` is VARCHAR +
CHECK). Each swap **drops** the constraint and recreates it from its own tuple, so whatever the tuple
omits is revoked — `tests/test_activity_type_migrations.py` exists because LP-UI-033 shipped a swap
that silently revoked four live values.

Two mistakes were made while writing it, both caught by measuring rather than by the guard:

| Mistake | What it would have produced |
|---|---|
| Listing values from `grep '^\s\+[A-Z_]\+ = "'` | **31 of 32** — it misses `document_replaced`, hidden in a line-number gap |
| Finding prior swaps by `grep ck_activity_logs_activity_type` | **0 files** — the real name has no underscore (`…activitytype`); by a helper-name grep, **3 of 13**, all mid-chain listing 21/22/24 values |

Copying one of those three would have revoked eight live values. The list came from
`[m.value for m in ActivityType]`, and the newest complete swap was identified with **the guard's own
parser**: `a7f42c8e91b6` (LP-819), the only one of thirteen listing all 32. The new swap lists **33**
and is now the only complete one.

Verified against a real database: `alembic upgrade head` applied `d1f4b8c25e93 → e5a2c7f31b84`
cleanly, single head, and the live constraint accepts `condition_sheet_received`.

## ⚠️ LP-904 shipped a schema module that could not be imported

`app/schemas/condition.py` raised `TypeError` on import — **always**:

```
date: date | None = None
TypeError: unsupported operand type(s) for |: 'NoneType' and 'NoneType'
```

`UnderwriterNotePublic` has a field *named* `date` annotated with `date`. In a class body CPython
binds the value first and evaluates the annotation second, so `date = None` enters the class
namespace and `date | None` then resolves to `None | None`. The field name is the API contract
(§LP-904: `underwriter_notes` is `[{date, text, first_seen_round_id}]`), so it could not simply be
renamed.

**Nothing had ever imported the module** until LP-905's router did. It shipped in LP-904, survived
two review rounds, and **7964 tests passed over it**. That is the fifth instance this stage of code
that looked correct because nothing executed it — after LP-904's six guards, §9.2's single branch,
the `264` projection pin, and §7.5's missing smoke test.

**The first fix did not work, and the reason matters.** `from __future__ import annotations` defers
annotations to strings — but Pydantic evaluates them with the **class namespace** as `localns`, which
still contains `date = None`. Deferral changed *when* the name resolved, not *which* namespace won. I
asserted it would work instead of testing it; the test said otherwise.

The fix is `from datetime import date as date_type`. All **five** annotations referencing the bare
name were rewritten — and four of them (`date_printed`, three `round_date`s) were only broken *by the
rename*, so a text-level edit would have missed them. They were found and spliced by AST position,
because `round_date: date` is a substring of two identical lines and on line 55 the field itself is
called `date`.

that one is now *buildable* — the row already carries `created_at` and `status`, so "PARSING for more

## Section 3 — the forward door

`POST …/inbound/attachments/{id}/condition-round` turns an emailed PDF into a round, and the
attachment is **kept as correspondence rather than becoming a document** — ADR-403's boundary at the
second door. Same `create_round_from_sheet`, differing only in `sources[0].kind = EMAIL` and the
`inbound_attachment_id` recorded alongside it.

**The action lives in `inbound_triage.py` by precedent, not taste.** That module already imports the
domain service owning what an attachment becomes — `from app.services.documents import
create_document` (line 44), called by `accept_attachment` at line 192 — so "a triage action reaches
into the domain service that owns the object it produces" is the established pattern in that exact
file. Building it in `condition_rounds` instead would invert a dependency the file has already
settled and would need `_attachment_bytes` promoted across a module boundary to do it.

**The three guards are copied from `accept_attachment`, deliberately not shared.** Cross-file check,
`safety_state is SAFE` (⚠️ PENDING is not a pass — the scan is asynchronous, so "nobody has looked
yet" genuinely persists), and a disposition that has not already been decided. A future divergence
between "may become a document" and "may become a condition sheet" should be *visible as a
difference here*, not hidden behind a helper both call. `CORRESPONDENCE` is allowed through, because
a processor may file an attachment first and decide to read it afterwards.

**⚠️ The path differs from the spec, and the code wins.** Spec §LP-905 writes
`POST /api/inbound/attachments/{id}/condition-round` with `loan_file_id` in the body when the
message is unrouted. This router is mounted at `/loan-files/{file_identifier}/inbound`, so the real
path carries the file — and that is the better shape, because `ScopedLoanFile` fetches it scoped to
the caller's company *before the handler runs*. A file id in the body would have to be scoped by
hand, which is the check everyone forgets. Recorded as a spec-vs-code difference per the survey's
rule.

**`attach_to_round_id` is accepted and refused.** The spec defines it as running "the LP-907 merge",
and LP-907 does not exist. Declaring the field keeps the endpoint's contract stable for the UI that
will send it; refusing with `501` is honest, where quietly creating a *second* round instead would be
the silent-wrong-answer shape this stage keeps finding. A test asserts the refusal leaves no round
behind.

Six tests, all passing: the round is created with `EMAIL` source, the attachment is kept as
correspondence with **no `Document` row**, `attach_to_round_id` is refused, a quarantined attachment
is refused, another company's attachment is a `404` (the same 404 as a missing one — distinguishing
them would confirm the id exists), and an unauthenticated call is `401`. The messages arrive through
`process_raw_message` with a real RFC-5322 body, so the attachment carries a genuine `safety_state`
rather than one a fixture asserted into existence.

## Review fixes (section 1)

Four recommendations, three taken as changes and one as a deliberate no-change.

**⚠️ The cross-tenant test was pulled forward rather than left to section 2.** The argument was cost,
not principle: the fixture, the pattern and a worked example already existed
(`tests/api/test_documents_endpoints.py`, "CRITICAL: cross-tenant isolation"), so it was a handful of
lines against machinery that works. Deferring it would have left this stage's signature failure in
place for one more commit — a believed property with nothing executing it — and the one time such a
property was finally checked here, **six of LP-904's guards failed on their first run**.

**Tenancy is stronger than section 1 originally claimed, and the ticket now says so in the right
terms.** It is not "checked after the lookup": `get_loan_file` builds from `_scoped(company_id)` and
returns `None` for another company's file, and the service takes **no `company_id` at all** — it
derives every one (storage path, round, event, activity) from `loan_file.company_id`. A mismatched
(company, file) pair is therefore **unconstructible**, not merely unchecked.

**Q1 — the declared content type now comes from the caller.** `assess`'s mismatch message is a claim
about the *sender*: "this is not what it said it was". Hardcoding `application/pdf` made that
sentence true for an upload and false for a forward — a real PDF attached as
`application/octet-stream` would have been told it "says it is application/pdf" when it said no such
thing. Changed while there is one caller; section 3 adds the second. Same bytes now produce three
honest messages depending on what was claimed, and a test pins both branches.

**Q3 — `now.astimezone(UTC).date()` removed.** `utcnow()` is `datetime.now(UTC)`, so it was a
provable no-op, and the kind that later persuades a reader the value might *not* be UTC and earns a
second conversion elsewhere. The intent is now a comment, where it cannot be mistaken for work.

**Q4 — the eager loads stay.** Three extra `selectinload`s on a single-row read followed by a file
upload and a commit are not measurable, and inventing a second scoped read is how two lookups drift
into disagreeing about what "this company's file" means.

### ⚠️ Three mistakes in my own tests, all silent

Worth recording together, because each looked like a code failure and was a *test* failure:

| Symptom | Actual cause |
|---|---|
| Five endpoint tests returned `401`; the only one passing was the one asserting `401` | The root `client` fixture overrides nothing, so the request resolved `get_db` to a **different session** and never saw the flushed user. **34** test files define a shadowing fixture for exactly this reason; there is no shared one to import. |
| The 413 test failed on `ModuleNotFoundError: app.tasks.conditions` | `monkeypatch: object` is an annotation, not a fixture request — so nothing was patched, the cap stayed at 20 MB and the upload ran to completion. My own `# type: ignore[attr-defined]` silenced the one complaint that named it. **0** other tests in the repo do this, against **736** correct uses. |
| The same test would still have passed vacuously | The fixture PDF is **843 bytes** and the cap under test was **1024** — never exceeded. The cap is now 100, lowered below the payload rather than the payload padded above the cap. |

The refusal-reason assertion was also wrong **twice**: first looking for a literal `"PDF"` the message
never contained, then for `"application/pdf"` — true only while the declared type was hardcoded, and
false the moment Q1 landed. It now asserts the durable property: the message names what the sender
actually sent.
