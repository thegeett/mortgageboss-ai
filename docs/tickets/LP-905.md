## The two STOP AND ASK points, resolved

Spec §LP-905 marks two. Both were already answered with evidence by the survey, and the product
owner confirmed both rather than changing them:

**Where the PDF is stored** — `storage.save_at()`, with **no `Document` row**. The spec's trigger is
conditional ("STOP AND ASK *if the only way* to store it would send it through classify → extract →
needs") and it does not fire: `save_at` exists precisely for bytes that are not a document and have
no derived path. A condition sheet satisfies no need and would be classified against a 166-type
*borrower* taxonomy, which is the same reasoning that produced
`AttachmentDisposition.CORRESPONDENCE`.

**Whether `CORRESPONDENCE` keeps the file retrievable** — yes, via `_attachment_bytes`, which
re-derives the bytes from the stored raw message rather than storing a second copy. Section 3 uses
it; nothing new is needed.

## Section 1 — the sheet arrives

**`condition_sheet_max_bytes`, default 20 MB.** Larger than the 10 MB MISMO cap because a two-page
UWM letter rasterised by the lender's own pipeline is routinely several megabytes, and a scan more
so. Enforced by a **chunked** read that aborts at the limit — reading the body and measuring it
afterwards means a 2 GB upload is already in memory by the time it is refused, which makes the cap a
formality rather than a defence.

**`ActivityType.CONDITION_SHEET_RECEIVED`,** its own type rather than a `DOCUMENT_UPLOADED` detail.
A timeline that filed a condition sheet under "document uploaded" would invite exactly the confusion
ADR-403's boundary exists to prevent.

**The service opens the round before anything reads it** — `status = PARSING`, `sheet_format =
GENERIC` — so the endpoint answers `202` immediately with a row the UI can poll (screen S1-02,
"Reading…"). Answering only when the parse finished would make a slow lender's PDF look like a broken
upload.

### Decisions worth arguing with

**PDF-only is checked on the sniffed type, not on the safety state.** ⚠️ `assess()` returns `SAFE`
for an **image** too — *"an image has no executable structure to strip and no pages to render — it IS
the raster"* — so a PNG passes the safety check cleanly. Keying only on the state would accept a
screenshot of a sheet and fail deep inside the reader, where the message means nothing. The three
refusals now read: a real PDF is accepted; a PNG gives *"The file says it is application/pdf but its
contents are image/png."*; rubbish gives *"The file type could not be identified."* Three distinct,
actionable messages, which is what §9.8 asks for.

**The storage path is server-controlled and never derived from the filename.** `save_at` refuses
traversal, but the deeper rule is that a real sheet's filename routinely carries the borrower's
surname and the loan number — building a path from it would write NPI into the storage layout itself.

**`round_date` is supplied explicitly.** It is NOT NULL with no default, and until the sheet is read
there is no printed date, so the round is dated by arrival with `date_printed` left null. Omitting it
fails the insert outright — the same shape as the `display_id` defect that hid LP-904's guards.

**The task is enqueued after the commit.** A worker that picked the round up before the transaction
landed would find no row.

## ⚠️ The constraint swap, and two ways I nearly got it wrong

Adding one `ActivityType` value means rewriting the whole CHECK (ADR-037: `str_enum` is VARCHAR +
CHECK). Each swap **drops** the constraint and recreates it from its own tuple, so whatever the tuple
omits is revoked — `tests/test_activity_type_migrations.py` exists because LP-UI-033 shipped a swap
that silently revoked four live values.

Two mistakes were made while writing it, both caught by measuring rather than by the guard:

| Mistake | What it would have produced |
|---|---|
| Listing values from `grep '^\s\+[A-Z_]\+ = "'` | **31 of 32** — it misses `document_replaced`, hidden in a line-number gap |
| Finding prior swaps by `grep ck_activity_logs_activity_type` | **0 files** — the real name has no underscore (`…activitytype`); by a helper-name grep, **3 of 13**, all mid-chain listing 21/22/24 values |

Copying one of those three would have revoked eight live values. The list came from
`[m.value for m in ActivityType]`, and the newest complete swap was identified with **the guard's own
parser**: `a7f42c8e91b6` (LP-819), the only one of thirteen listing all 32. The new swap lists **33**
and is now the only complete one.

Verified against a real database: `alembic upgrade head` applied `d1f4b8c25e93 → e5a2c7f31b84`
cleanly, single head, and the live constraint accepts `condition_sheet_received`.

## ⚠️ LP-904 shipped a schema module that could not be imported

`app/schemas/condition.py` raised `TypeError` on import — **always**:

```
date: date | None = None
TypeError: unsupported operand type(s) for |: 'NoneType' and 'NoneType'
```

`UnderwriterNotePublic` has a field *named* `date` annotated with `date`. In a class body CPython
binds the value first and evaluates the annotation second, so `date = None` enters the class
namespace and `date | None` then resolves to `None | None`. The field name is the API contract
(§LP-904: `underwriter_notes` is `[{date, text, first_seen_round_id}]`), so it could not simply be
renamed.

**Nothing had ever imported the module** until LP-905's router did. It shipped in LP-904, survived
two review rounds, and **7964 tests passed over it**. That is the fifth instance this stage of code
that looked correct because nothing executed it — after LP-904's six guards, §9.2's single branch,
the `264` projection pin, and §7.5's missing smoke test.

**The first fix did not work, and the reason matters.** `from __future__ import annotations` defers
annotations to strings — but Pydantic evaluates them with the **class namespace** as `localns`, which
still contains `date = None`. Deferral changed *when* the name resolved, not *which* namespace won. I
asserted it would work instead of testing it; the test said otherwise.

The fix is `from datetime import date as date_type`. All **five** annotations referencing the bare
name were rewritten — and four of them (`date_printed`, three `round_date`s) were only broken *by the
rename*, so a text-level edit would have missed them. They were found and spliced by AST position,
because `round_date: date` is a substring of two identical lines and on line 55 the field itself is
called `date`.
