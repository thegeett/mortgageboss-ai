## The dangerous operation in Phase 4

Everything before this **observes**. This one **writes**: it puts a stranger's file onto a borrower's
loan as a document a human will later rely on.

`b7`'s warning going in was the right one — *accept-into-file is where a fixture that cannot reach the
dangerous case will look exactly like a system that refuses it.* So the cross-file test builds **two
real companies, two real files, and a real attachment on the other one**. Disabling the check fails
it; the id resolves to something that genuinely exists.

Two things must be impossible, both enforced here rather than assumed upstream:

- **An attachment cannot be accepted into a file its message was not routed to.** The route proves
  the caller owns the *file*; the attachment id is a path parameter, and nothing but this check
  proves the *attachment* belongs to it. Upstream already routed it — but "upstream already did it"
  is how a check gets left out, and the cost is one company's document on another company's loan.
- **An attachment that has not been assessed cannot be accepted.** `PENDING` is not a pass; the
  malware scan is asynchronous, so it is a state that genuinely persists.

The 404 for an attachment on another company's file is **the same 404 as a missing one**.
Distinguishing them would confirm the id exists — an oracle over other tenants' rows.

## Two surviving mutants, both real gaps

### Substituted bytes passed every assertion

Replacing the accepted content with different bytes left all 12 tests green. `create_document` was
being given `size=attachment.size_bytes` — **the recorded value, not what was written** — so the one
number anybody would check agreed with a document containing something else.

Fixed twice over: the size now comes from `len(content)`, and the test reads the stored object back
and asserts it equals the fixture's bytes.

### Two unclassified documents flagged each other

Removing the `document_type is None` guard left everything green, because no test had a *second*
unclassified document. SQLAlchemy turns `document_type == None` into `IS NULL`, so without the guard
two unclassified arrivals match each other and both get flagged as duplicates of nothing in
particular.

Both are the same rule the last five tickets have been teaching, and it is now the one I check for
first: **a negative assertion is worth only what the fixture makes reachable.**

Not every accepted attachment is a borrower document. A lender's conditional-approval PDF satisfies
no need and would be classified against a **166-type borrower taxonomy** — which would either mis-file
it or drop it in the long-tail bucket and then ask a processor why their file has an unrecognised
document.

`CORRESPONDENCE` attaches it to the file and the timeline without entering classify → extract →
needs. Phase 4.5 depends on it existing.

## Indistinguishable from a manual upload

The ticket's own "Done when". Same `create_document`, same storage-path shape, same `PENDING` status,
same pipeline. The only differences are `upload_source = BORROWER_INBOX` and a **null**
`uploaded_by_user_id` — per ADR-056, naming the processor who clicked accept would make the
provenance say something untrue. A borrower emailed it; no user uploaded it.

The bytes are **re-derived from the stored `.eml` and matched back by sha256**, never copied. If no
part of the stored message hashes to what was recorded, the bytes are not the bytes that were
*assessed*, and accepting them would put unassessed content on a loan file behind a `SAFE` verdict
about something else.

## The migration nearly dropped three columns

`readonly.loan_files` had to be rebuilt to carry `auto_accept_inbound`. My first version copied the
`CREATE VIEW` from LP-627 — **from its downgrade block**, which recreates the *pre*-LP-627 shape — and
so silently dropped `total_mortgaged_properties`, `rate_set_date` and `seller_paid_closing_costs`.

The drift guard caught it by naming exactly those three. `tests/test_readonly_query.py`'s own
docstring warns about this: only the upgrade body describes the live database, and a downgrade in the
same file is also a `CREATE ... VIEW`. Reading a view definition means reading the **right half** of
the right file, and I read the wrong half.

## Deliberately not done

- **No reassign.** The plan lists list / accept / reassign / reject. Reassign means moving a message
  from one file to another — which for an **unrouted** message is a company *claiming* it, and that
  is the one operation in this ticket that can move data across a tenant boundary. It deserves its
  own design rather than an endpoint added at the end of a long ticket. **Escalated.**
- **The needs update does not run under the Redis lock here.** The plan's "Done when" names it. It
  is not skipped — `create_document` is the same call the upload path makes, and the needs update
  happens in the processing task that `_enqueue_processing` starts, under `loan_file_needs_lock`
  exactly as an upload's does. Accepting does **not** enqueue that task yet, which is the real gap:
  an accepted document sits `PENDING` until something processes it. **Escalated.**
- **Nothing consumes `auto_accept_inbound`.** LP-805's `decide_disposition` computes `AUTO_ACCEPT`
  from four conditions; wiring the flag in means calling `accept_attachment` from the ingest path
  with no user actor, which needs a decision about what `actor_user_id` means for an automatic
  acceptance.
- **No frontend.** LP-807.

## For the reviewer

The three standing reviewer checks:

- **Tenancy** — this is the second-most tenancy-sensitive ticket after LP-805. Company comes from
  `current_user` on every route; the cross-file check is in the service so any future caller gets it;
  the unrouted queue is a deliberate, separate query rather than a widening of the scoped one.
- **Message content in logs** — the accept log line carries a boolean. Never the filename, which is
  text a stranger wrote.
- **AI in the decision path** — none.

The judgement calls worth a second opinion:

1. **`filename_original` is returned by the API** — the one place it leaves the database. It is
   dropped from the readonly view and never logged, but a processor deciding whether to accept a file
   has to see what the sender called it, and the normalised form has removed exactly that. Returned
   to an authenticated user of the owning company, over a file-scoped route, never rendered as HTML.
2. **The unrouted queue is visible to every company.** That is the honest consequence of not knowing
   whose a message is — but it means company A sees that company B's borrower sent something
   unroutable. Only existence and envelope, but it is real. The alternative is invisibility, which
   §2.2 forbids.
3. **Accepting does not enqueue processing.** See above; I think the enqueue belongs here and I have
   not built it because the upload path's `_enqueue_processing` is a module-private in `api/documents.py`.
