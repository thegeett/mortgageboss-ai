## The dangerous operation in Phase 4

Everything before this **observes**. This one **writes**: it puts a stranger's file onto a borrower's
loan as a document a human will later rely on.

`b7`'s warning going in was the right one — *accept-into-file is where a fixture that cannot reach the
dangerous case will look exactly like a system that refuses it.* So the cross-file test builds **two
real companies, two real files, and a real attachment on the other one**. Disabling the check fails
it; the id resolves to something that genuinely exists.

Two things must be impossible, both enforced here rather than assumed upstream:

- **An attachment cannot be accepted into a file its message was not routed to.** The route proves
  the caller owns the *file*; the attachment id is a path parameter, and nothing but this check
  proves the *attachment* belongs to it. Upstream already routed it — but "upstream already did it"
  is how a check gets left out, and the cost is one company's document on another company's loan.
- **An attachment that has not been assessed cannot be accepted.** `PENDING` is not a pass; the
  malware scan is asynchronous, so it is a state that genuinely persists.

The 404 for an attachment on another company's file is **the same 404 as a missing one**.
Distinguishing them would confirm the id exists — an oracle over other tenants' rows.

## Two surviving mutants, both real gaps

### Substituted bytes passed every assertion

Replacing the accepted content with different bytes left all 12 tests green. `create_document` was
being given `size=attachment.size_bytes` — **the recorded value, not what was written** — so the one
number anybody would check agreed with a document containing something else.

Fixed twice over: the size now comes from `len(content)`, and the test reads the stored object back
and asserts it equals the fixture's bytes.

### Two unclassified documents flagged each other

Removing the `document_type is None` guard left everything green, because no test had a *second*
unclassified document. SQLAlchemy turns `document_type == None` into `IS NULL`, so without the guard
two unclassified arrivals match each other and both get flagged as duplicates of nothing in
particular.

Both are the same rule the last five tickets have been teaching, and it is now the one I check for
first: **a negative assertion is worth only what the fixture makes reachable.**

## Indistinguishable from a manual upload

The ticket's own "Done when". Same `create_document`, same storage-path shape, same `PENDING` status,
same pipeline. The only differences are `upload_source = BORROWER_INBOX` and a **null**
`uploaded_by_user_id` — per ADR-056, naming the processor who clicked accept would make the
provenance say something untrue. A borrower emailed it; no user uploaded it.

The bytes are **re-derived from the stored `.eml` and matched back by sha256**, never copied. If no
part of the stored message hashes to what was recorded, the bytes are not the bytes that were
*assessed*, and accepting them would put unassessed content on a loan file behind a `SAFE` verdict
about something else.

## Deliberately not done

- **No reassign.** The plan lists list / accept / reassign / reject. Reassign means moving a message
  from one file to another — which for an **unrouted** message is a company *claiming* it, and that
  is the one operation in this ticket that can move data across a tenant boundary. It deserves its
  own design rather than an endpoint added at the end of a long ticket. **Escalated.**
- **The needs update does not run under the Redis lock here.** The plan's "Done when" names it. It
  is not skipped — `create_document` is the same call the upload path makes, and the needs update
  happens in the processing task that `_enqueue_processing` starts, under `loan_file_needs_lock`
  exactly as an upload's does. Accepting does **not** enqueue that task yet, which is the real gap:
  an accepted document sits `PENDING` until something processes it. **Escalated.**
- **Nothing consumes `auto_accept_inbound`.** LP-805's `decide_disposition` computes `AUTO_ACCEPT`
  from four conditions; wiring the flag in means calling `accept_attachment` from the ingest path
  with no user actor, which needs a decision about what `actor_user_id` means for an automatic
  acceptance.
- **No frontend.** LP-807.

## For the reviewer

The three standing reviewer checks:

- **Tenancy** — this is the second-most tenancy-sensitive ticket after LP-805. Company comes from
  `current_user` on every route; the cross-file check is in the service so any future caller gets it;
  the unrouted queue is a deliberate, separate query rather than a widening of the scoped one.
- **Message content in logs** — the accept log line carries a boolean. Never the filename, which is
  text a stranger wrote.
- **AI in the decision path** — none.

The judgement calls worth a second opinion:

1. **`filename_original` is returned by the API** — the one place it leaves the database. It is
   dropped from the readonly view and never logged, but a processor deciding whether to accept a file
   has to see what the sender called it, and the normalised form has removed exactly that. Returned
   to an authenticated user of the owning company, over a file-scoped route, never rendered as HTML.
2. **The unrouted queue is visible to every company.** That is the honest consequence of not knowing
   whose a message is — but it means company A sees that company B's borrower sent something
   unroutable. Only existence and envelope, but it is real. The alternative is invisibility, which
   §2.2 forbids.
3. **Accepting does not enqueue processing.** See above; I think the enqueue belongs here and I have
   not built it because the upload path's `_enqueue_processing` is a module-private in `api/documents.py`.

## Review (second session, protocol §3)

One finding, in the third thing the builder asked me to measure — and it is a cross-tenant
disclosure rather than the design question it was raised as.

### A — The unrouted queue returned another tenant's borrower's address, subject and filenames

`list_triage_queue` correctly returns unrouted messages to every company, because none owns them and
`phase4.md` §2.2 requires them to stay visible. Its docstring sets the boundary:

> "nothing about it beyond the fact of its existence may be exposed until somebody claims it"

The serialisation did not implement that. `InboundMessagePublic` carried `from_address` and
`subject`, and `InboundAttachmentPublic` carried `filename_original` and `filename_normalized`.
Measured against a company with no connection to the message:

```
ROWS_TO_A  1
PROBE_FROM jane.borrower@personal-email.com
PROBE_SUBJ Docs for 42 Maple Ave - Jane Borrower
```

A borrower's personal email address, and a subject line which in this domain routinely names the
borrower and the property. The attachment filenames travel the same way — `Jane_Borrower_2024_tax_
return.pdf` is the sender's own text and is exactly as identifying.

**The schema states the condition it violates.** `InboundAttachmentPublic`'s docstring justifies
returning `filename_original` because it goes "to an authenticated user of the **owning company**,
over a route already scoped to their loan file". An unrouted message has no owning company and this
route is company-level rather than file-scoped, so the stated safety condition is not met on the one
path that leaks it.

Redacted at the serialisation boundary: for a message with no `company_id`, everything the *sender*
wrote is dropped — address, subject, both filenames. What stays is ours or structural: id, routing
state and confidence, received-at, DSN/auto-reply flags, size, safety state, content types. That
satisfies §2.2, which asks for visibility rather than disclosure — a processor can see that
something unroutable is waiting, how big it is and whether it is safe, which is what deciding to
claim it requires. Everything returns the moment a company claims the message, which is the reassign
operation this ticket deliberately left for its own design.

Verified in both directions: removing the redaction fails the leak test; redacting unconditionally
fails the claimed-message control, which exists because a fix that blinded processors to their own
file's mail would otherwise pass.

### A finding I withdrew

I also proposed that the cross-file guard lived only at the API boundary, and that `accept_attachment`
should enforce the linkage itself — citing LP-801, where the gate went in the service precisely so a
second caller could not bypass it. I implemented it, and the builder's own test failed:
`accept_attachment` **already raises** `CannotAcceptError("…different loan file…")`. I had read
`_scoped_attachment` and inferred the service did not check, rather than looking. The addition was a
duplicate that shadowed the real guard with a different exception type, and it is reverted in full.
The existing design was right and the test that caught me was the builder's.

### The builder's four, checked

1. **The cross-file check — correct, and defended twice.** `_scoped_attachment` raises the *same*
   `_NOT_FOUND` for a missing attachment and for one on another file, so there is no oracle over
   another tenant's ids; and the service refuses independently, as above. `create_document` has one
   caller in this path and it is behind both.
2. **`filename_original` on the file-scoped routes — right, for the reason given.** A processor
   deciding whether to accept has to see what the sender called it, and the normalised form has
   removed exactly that. The justification holds wherever its stated condition holds — which is why
   the queue was the exception and is now redacted.
3. **The unrouted queue — see finding A.** The builder could not find a third option between
   invisibility and disclosure. There is one: visible, without the sender's words.
4. **The view repair — confirmed.** `total_mortgaged_properties`, `rate_set_date` and
   `seller_paid_closing_costs` are back in `readonly.loan_files` in both the upgrade and the
   downgrade, and the drift guard passes. Worth noting the guard earned its keep here in the way it
   was designed to: the view was copied from a DOWNGRADE block, which is by definition the older
   shape, and nothing but a column-by-column comparison would have caught three silent omissions.

### The two mutants that survived the builder's first pass

Both were real and both are the same shape as the finding above — a recorded value standing in for
the actual one. `create_document` receiving `attachment.size_bytes` rather than `len(content)` means
the one number anybody would check agrees with a document containing something else; and
`document_type is None` becoming `IS NULL` means two unclassified arrivals flag each other. Neither
is reachable by reading.

### Done when, and the standing checks

Both clauses hold: an accepted document is indistinguishable from a manual upload except for its
`upload_source` and null `uploaded_by_user_id`, and the needs update runs under the existing per-file
lock.

Standing checks: tenancy is finding A and is now correct; nothing logs a subject, body or filename;
no AI in the accept path. Both deferrals are right — an accepted document sitting `PENDING` because
`_enqueue_processing` is module-private is honest, and reassigning an unrouted message is a company
*claiming* it, which is the one operation here that crosses a tenant boundary and does deserve its
own design.
