# LP-508 — wire the accuracy layer to the verdict layer

## What this ticket is

`gate.py` has four defences and **a confidently-wrong parsed value defeats all four**. This adds a fifth: a
declared list of extraction fields with a confirmed wrong value in the corpus, so a rule reading one degrades
to `needs_review` + ratification instead of auto-asserting.

The chosen option was **(d)** — a field-level distrust list degrading through `ratification_pending` — not
(a), wiring LP-474's per-extraction flag, because Phase A measured that **LP-474 covers 3 of 9 ledger items
and does not cover doc 104**, the case this ticket exists for.

No rule is added. `ACTIVE_RULE_IDS` stays **41**.

## Phase A — the trace

**1. The hole, confirmed in code.**

```python
confidences = [t.confidence for t in load_bearing.values() if t is not None and t.confidence is not None]
verdict_confidence = min(confidences) if confidences else None
if verdict_confidence is not None and verdict_confidence < confidence_floor:
```

`confidence is not None` filters parsed tags out of the minimum — and when **every** load-bearing tag is
parsed, `confidences` is empty, `verdict_confidence` is `None`, and the floor check is **skipped entirely**.
IH-1 had **no confidence defence at all**.

**2. `confidence=None` is deliberate.** `parsed.py:46` — *"a parsed passthrough — never a fabricated
confidence"*. The reasoning is right; nothing else covered the consequence.

**3. LP-474's flag stops at the database.** `run_consistency_checks` is called once
(`app/tasks/document_processing.py:462`) and writes a `DocumentFinding` of type `CONSISTENCY`. **Nothing in
`app/verification/snapshot/` reads document findings.** Option (a) needs a plumbing step that does not exist.

**4. ⚠️ Coverage — LP-474 catches 3 of 9**, from its own measured record: **088** (state tax == federal),
**049** (amount == running balance), **096** (Box 12 == Medicare), each with 0 false positives. **Not caught:
104, 146, 294, 244, 253, 293** (and 091). **Doc 104 — the IH-1 case — is not among them**, which is why (a)
alone is not the fix.

**5. ⚠️ Option (b) exists — and the recorded constraint was wrong.** `ships` is **metadata with no runtime
consumer** (it appears in `registry.py` / `engine.py` / `verification_run.py` only in comments). The real
mechanism is **`ratification_pending`**, a per-finding field on `RuleEvaluation` (`result.py:79`) that
`judgment.py:118` sets unconditionally and `deterministic.py` never set. **A deterministic rule can ratify
per finding with no `kind` change and no lie.** LP-485 and LP-486 both record the opposite; **both are
amended.**

**6/7. The options.** (a) 3/9, misses 104, needs plumbing. (b) exists but blunt — degrades everything,
always. (c) field-level list — covers 104, no plumbing, cruder. **(d) = (c)'s trigger + (b)'s mechanism,
chosen.**

## What was built

`distrusted_fields.yaml` (declared data, **every entry carries its document and the error**), a loader
(`rules/distrust.py`) that resolves entries to tag ids **through the production declarations** — so a field
distrusted on one document type does not catch a same-named field on another — and a fifth check in
`gate.py`, ordered **after** absent/`"unknown"` (a missing value gets the more specific message) and
**before** contradiction.

**⚠️ Distrusted is a fifth state.** Not absent (the value is there), not empty, not `"unknown"` (the extractor
was confident), not low-confidence (there is no confidence to read). Its own check, its own reason, pinned by
a test that all four remain distinguishable.

The degraded reason names the fact: *"the dwelling loss-settlement basis comes from a field the extractor has
read wrongly before, so this check was not decided automatically — a human should confirm the value."*

### The list as shipped — 5 fields + 1 explicit tag

`homeowners_insurance.replacement_cost_or_coinsurance_basis` (104) · `drivers_license.expiration_date` and
`.date_of_birth` (146/294) · `credit_report.report_date` and `appraisal.appraisal_effective_date` (the
single-source date class) · plus **`ins.dwelling_settlement_basis`** named explicitly, because it is
**derived** from the 104 field and field-name resolution cannot reach a recipe's inputs without guessing.

### ⚠️ `txn.amount` was in the seed and was removed — measured, not assumed

Listing it degraded **every deposit on every file — 39 tests moved** — because `txn.amount` is load-bearing
on **AS-1**, the flagship live rule. It was protecting doc 049, which **LP-474 already catches exactly, 0
false positives across 24 statements**.

**The rule that came out of it: LP-474 handles a wrong value with an INTERNAL SIGNATURE; this list handles one
with NONE.** Using the crude tool where the precise one works costs a whole lane and buys nothing. The three
LP-474-covered fields (088, 049, 096) are therefore deliberately **not** listed, with the reasoning recorded
in the file itself.

## ⚠️ The cost — larger than forecast

The sign-off anticipated *"at 46.7 % fill, IH-1 will rarely auto-assert."* **The reality is 100 %: IH-1 never
auto-asserts.** The guard keys on the *field*, not on whether the value filled, and
`ins.dwelling_settlement_basis` is IH-1's **only** gated tag — so every binder degrades, replacement-cost and
actual-cash-value alike.

That is the honest consequence of a field-level guard on a single-input rule. It is the right trade while
`auto` is the default for ~54 of 78 remaining rules with no ratify fallback — but it is **suspension, not
degradation**, and the entry must be pruned when the extractor improves. Every entry carries its evidence
precisely so it can be deleted with confidence.

separately as asked: snapshot unchanged ✅, verdict unchanged ⚠️ by design, not by accident.

## ⚠️ What remains uncovered

**Doc 253** — a gift read as **$224,307.94 instead of $24,307.94**. LP-474 recorded it as uncatchable by
self-consistency: one amount, **no sibling to contradict it**. A field-level list cannot help either without
distrusting every gift amount on every file. **It still passes, and a test says so by name.** Catching it
needs a **source-magnitude check** — a layer that does not exist.

Also uncovered: **244** (needs a Box-10 field that was never extracted) and **293** (a plausible-but-wrong
date, indistinguishable from a right one without the source).

## Assumptions and decisions

1. **Field-level, not per-extraction.** Cruder and broader, chosen because it covers 104 and needs no
   plumbing. (a) remains worth doing later as a **complement** — precise where it applies — once the
   findings→snapshot path exists.
2. **Derived tags are named explicitly**, never inferred. Guessing which fields a recipe reads is the same
   class of inference this layer exists to avoid.
3. **Every entry requires a reason** — the loader rejects a blank one. A bare field name cannot be pruned
   with confidence, and pruning is how this list stays small.
4. **Four IH-1 tests were updated, one rewritten.** The verdicts genuinely changed by design; the cause is
   named in each. The basis **normaliser** is still asserted, so pruning the entry restores the old
   behaviour. The reason-distinctness test now reads the spec's outcome text rather than a live verdict,
   preserving exactly what it protected. **No test was skipped, xfailed, deleted or weakened.**

## What this changes downstream

- **The `ships` constraint is lifted.** Any deterministic rule can be made to ratify per finding. LP-485 and
  LP-486 are amended; the constraint should not be carried forward.
- **The distrust list is the place to record a confirmed extraction error** — with its evidence, and with the
  expectation it will be deleted.
- **Two layers now exist with a division of labour.** LP-474 for internal signatures, this for their absence.
  Neither is a general accuracy solution, and 253 marks the boundary.

## ADR

**ADR-377** — records the hole (a parsed value carries no confidence, so four defences cannot see a
confidently-wrong one), the fifth defence, the division of labour with LP-474, the honest cost, and what
remains uncovered.

## ⚠️ CORRECTION (commit `0ec097b`, amended here at LP-487) — the guard reached 1 of the 5 rules it claimed

**The coverage table above was wrong when written.** The `fields:` section listed the PARSED fields —
`credit_report.report_date`, `appraisal.appraisal_effective_date`, `drivers_license.expiration_date` — but
**a rule almost never gates on the parsed tag.** It gates on a DERIVED tag computed from it:

| rule | what it actually gates on | was it protected? |
|---|---|---|
| IH-1 | `ins.dwelling_settlement_basis` | ✅ — only because its derived tag was named EXPLICITLY |
| ID-3 | the DOB compare | ✅ |
| **ID-5** | `id.borrower_id_expiration` | ❌ **not protected** |
| **CR-13** | `credit.report_age_months_at_closing` | ❌ **not protected** |
| **PR-6** | `property.appraisal_age_months_at_closing` | ❌ **not protected** |

Resolving `distrusted_tag_ids()` against every active spec's gated tags matched **IH-1 and ID-3 only**,
while the ticket claimed five. `distrust.py` documents why: field-name resolution covers `parsed`
declarations, and a derived tag's recipe inputs are deliberately never inferred.

**The rule that follows, and it is the one already applied to `ins.dwelling_settlement_basis`:** *every
derived consumer of a distrusted field must be named explicitly in the `tags:` section.* That discipline
was stated in the file and then applied to exactly one of the five entries.

**Why the tests did not catch it — the more important finding.** `test_the_other_seeded_rules_degrade_too`
passed because it called `evaluate_gate` **with the tag ids directly**. The mechanism worked; the WIRING
did not. A green test over a path no rule exercises is ADR-286/289 at the test layer.

**Fixed in `0ec097b`:** the three derived tags added to `tags:`, and
`test_every_distrusted_field_reaches_a_rule` now fails when a distrusted field has no rule-visible tag.
**Standing rule adopted at LP-487:** a guard test must exercise the guard **through a rule evaluation**,
never by calling the guard directly.
