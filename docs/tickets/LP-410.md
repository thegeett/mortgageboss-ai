# LP-410 — The derived-producer wave: build the three tags that unblock PC-7, AS-8, IN-6

## What this ticket is

Four Bucket 2 Phase 0s (LP-406-1/2/3/4) established that PC-7, AS-8, and IN-6 have their **inputs produced** but
their **checks are not expressible** in the rule DSL — PC-7 needs a `today` operand, AS-8 an ordered-pairwise
relation (ADR-322), IN-6 a set-coverage relation (ADR-323). Each is answered the same way: **derive the fact in
a small producer, and a trivial rule branches on it.** This builds all three producers together. **Producers
only — no rules** (PC-7/AS-8/IN-6 are their own follow-up tickets). Additive: no existing tag, producer, prompt,
or rule changed; `ACTIVE_RULE_IDS` stays **24**.

The discipline throughout (LP-400): **the tags DESCRIBE, the rules JUDGE.** No threshold or policy lives inside a
producer — PC-7's "realistic closing window" is the rule's (Priya-validated), never the tag's.

## D1 — The value set per tag (descriptive, not judgmental)

- **`contract.days_until_closing`** — a **signed integer string**: days from the file (snapshot) date to the
  closing date. **Positive** = the closing date is in the future; **negative** = it is in the **past** (a
  meaningful observation PC-7 will judge as stale — the tag emits it, it does not abstain the way a future-dated
  *pay stub* does). `unknown` when no parseable closing date is stated, or the file's documents disagree on it.
  It emits **only the number** — "too far out" / "stale" is PC-7's window, not the tag's.
- **`stmt.continuity`** — an enum describing the observed chaining state: `chained` (every account with ≥2
  statements carries each ending balance into the next opening balance) · `broken` (some account's consecutive
  balances do not carry — fire-if-any) · **`nothing_to_chain`** (no account has ≥2 statements — the
  `not_applicable`-enabler) · `unknown` (a needed balance/period is unreadable, or statements exist but cannot
  be grouped to an account). It names **what IS**, never "a problem."
- **`income.employer_coverage`** — a per-borrower enum: `covered` (both document types present and their
  normalized employer sets cover each other) · `uncovered` (a normalized employer on one side has no match on
  the other) · **`one_sided`** (the borrower lacks pay stubs OR W-2s, or has neither — the
  `not_applicable`-enabler) · `unknown` (an employer name on a relevant document is unreadable).

## D2 — The subject per tag, and the rule-subject match (anti-structural-death, done NOW)

| tag | produced at | the rule that will read it | match? |
|-----|-------------|-----------------------------|:---:|
| `contract.days_until_closing` | `loan` | PC-7 (loan-level) | ✅ |
| `stmt.continuity` | `loan` | AS-8 (loan-level) | ✅ |
| `income.employer_coverage` | `borrower` | IN-6 (per_borrower) | ✅ |

Asserted from `load_declarations()` in the tests, so none of the three rules can be born structurally dead (the
ID-5 class). **The subtle one — AS-8's multi-account representation:** `stmt.continuity` is **loan-level** but
computes **per-account** internally (via `resolve_accounts`), then aggregates with the precedence
**`broken > unknown > chained > nothing_to_chain`**. So among three accounts, **one broken** → `broken` (a real
break is never masked by a clean sibling — the `_stmt_min_account_months` fire-if-any discipline); an account we
**could not read** → `unknown` (never silently `chained`); only when every account either chains or has a single
statement is the value `chained` / `nothing_to_chain`. AS-8 then reads one loan-level value and needs no
per-account plumbing.

## D3 — The snapshot date (deterministic, not a wall-clock)

`contract.days_until_closing` computes `(closing_date − snapshot.created_at.date()).days`. `snapshot.created_at`
is the **file's fixed "as-of" datetime**, set when the snapshot is built — the same source `income.days_since_most_recent_pay`
uses. It is **never** `datetime.now()` at evaluation time, so the tag is **reproducible**: a test with a fixed
`created_at` gets the same number every run (asserted — `test_days_until_closing_is_deterministic_no_wall_clock`).

## D4 — `employer_coverage`'s normalization + the calibration-inheritance answer

**It reuses IN-5's exact-bookend normalizers** — `casefold` / `drop_punct` / `collapse_ws` / `strip` /
`drop_entity_suffix` (imported from `consistency.py`, the same chain IN-5's `normalization` declares) — to match
a pay-stub employer to a W-2 employer (so "Acme Corp" ↔ "Acme" match, the LP-340/ADR-281 convention). **This
introduces NO new unmeasured judgment:** it is the deterministic normalization already exercised by live IN-5,
and `income.employer_normalized` itself is measured **100%** (LP-379-D). **So IN-6 inherits IN-5's calibration —
it will NOT be held-on-calibration like OC-1.**

⚠️ **The documented limitation (describe-vs-judge boundary):** the producer does the **deterministic** half of
IN-5's comparison but **not** IN-5's AI fuzzy-residue judge. A legal-vs-common variance the normalizer cannot
reduce (e.g. a pay stub's "Acme" vs a W-2's "Acme Freight Co" — `drop_entity_suffix` yields "acme" vs "acme
freight", which differ) reports `uncovered` where IN-5's AI might forgive it. That residue is a **later
refinement** (a fuzzy-coverage pass), flagged in IN-6's stop-report (LP-406-3) — it is not resolved here, and the
tag never silently passes an unmatched name as covered (fail-closed). Reusing the measured normalizers over
inventing matching logic was the ticket's explicit preference.

## D5 — Fail-closed (per tag)

Each degrades to `unknown` (or, for a nothing-to-check state, a distinct `nothing_to_chain` / `one_sided`), never
a false `ok` / `covered` / `chained`:
- `days_until_closing` → `unknown` on no parseable closing date or a documents-disagree ambiguity.
- `stmt.continuity` → `unknown` on an unreadable balance/period, or statements that cannot be grouped to an
  account (present but ungroupable — surfaced, never guessed-merged, the LP-336 discipline); `broken` takes
  precedence so a real break is never hidden behind an unreadable sibling.
- `income.employer_coverage` → `unknown` when an employer name on a relevant document is unreadable, and only
  emits `covered` when both sides are fully readable and their sets cover.

## D6 — Cost + equivalence

All three are **derived** (pure functions over the snapshot — **no AI calls**), so there is **no per-run model
cost**. They are **purely additive**: three new recipes in the registry, three new vocabulary + `tag_production`
declarations, nothing existing touched. Proven by the full suite staying green (the 24 live rules and every
existing tag unchanged) and the additive materialization on LF-6T3N below.

## THE MATERIALIZATION PROOF (reported, not predicted)

**On the real fixtures** (materialized parsed+derived, no AI):

| tag | LF-6T3N (base, 5 real statements) | note |
|-----|-----------------------------------|------|
| `contract.days_until_closing` | **`"1"`** — "the closing date 2026-07-15 is 1 day(s) from the file date (future)" | a real number off the fixture's contract + snapshot date |
| `stmt.continuity` | **`"chained"`** — "every account's consecutive statements chain…" | LF-6T3N's 5 real bank statements **do** chain |
| `income.employer_coverage` | **`"unknown"`** (both borrowers) — "an employer name … could not be read" | HONEST: `income.employer_normalized` is AI, not produced in a no-AI run (like OC-1's fixture) |

`build_lf6t3n_plus` gives the same three values.

**The observed-state branches** (constructed snapshots, since the AI `employer_normalized` and specific
balance/date shapes aren't on the base fixture — reported from the passing tests):

- `days_until_closing`: future → `"10"`; **past → `"-10"`** (signed, emitted not abstained); no closing date →
  `unknown`; documents disagree → `unknown`; fixed snapshot date → deterministic `"30"`.
- `stmt.continuity`: two carrying statements → `chained`; a balance that doesn't carry → **`broken`**; **a single
  statement → `nothing_to_chain`** (the not_applicable-enabler, NOT `unknown`); an unreadable balance →
  `unknown`; **per-account isolation** — Chase Jan→Mar chaining with a Wells statement dated in between → still
  `chained` (a global date-chain would fabricate a break; per-account grouping prevents it); a break in one of
  two accounts → `broken` (fire-if-any).
- `income.employer_coverage`: matching employers (with suffix variance) → `covered`; **two employers each covered
  both ways → `covered`** (the exact case `ConsistencyEval` could not express — it would fire); an employer with
  no counterpart → `uncovered`; **only W-2s (or no income docs) → `one_sided`** (the not_applicable-enabler); an
  unreadable employer → `unknown`; **per-borrower isolation** — borrower A's pay stub does not cover borrower B's
  W-2 (both read `one_sided`, proving no cross-borrower pooling).

**The achievable n / coverage for the rule tickets:** `days_until_closing` and `stmt.continuity` resolve to real
values on the base LF-6T3N (so PC-7 and AS-8 can each prove a **satisfy/real** path on the existing fixture —
PC-7: a +1-day closing; AS-8: a `chained` file). To exercise the **fire** paths and `employer_coverage`, the
rule tickets need scenarios: a past/far-future closing date (PC-7), a balance-break statement series (AS-8), and
income docs with the AI `employer_normalized` produced (IN-6, via the income-scenario fixture with the income
group run). Those are each a fixture concern for the rule ticket, not this one.

## What each of PC-7 / AS-8 / IN-6 now needs (a trivial rule each)

- **PC-7** — a deterministic loan-level spec reading `contract.days_until_closing`, comparing to a **Priya
  closing window** (how many days past/future is acceptable). It ships **`validated=false`** flagged for her (a
  real threshold, the only one of the three). `past → fired`, in-window `→ satisfied`, `unknown → couldnt_check`.
- **AS-8** — a deterministic loan-level spec reading `stmt.continuity`: `broken → fired`, `chained → satisfied`,
  `unknown → couldnt_check`, **`nothing_to_chain → not_applicable`** (an applicability predicate). **No Priya
  threshold** (exact carryover) → activatable through the `no-ai-dependency` gate once its input resolves on the
  fixture (it does — `chained`).
- **IN-6** — a deterministic per_borrower spec reading `income.employer_coverage`: `uncovered → fired`,
  `covered → satisfied`, `unknown → couldnt_check`, **`one_sided → not_applicable`**. **Inherits IN-5's
  calibration** (no OC-1-style hold); the AI fuzzy-residue is a documented later refinement.

## Every assumption / decision

- **Reused templates, no new mechanism:** `days_until_closing` mirrors `income.days_since_most_recent_pay`
  (snapshot-date arithmetic) + `_loan_closing_date` (single-closing-date gather, disagreement → unknown);
  `stmt.continuity` mirrors `_stmt_min_account_months` (per-account grouping via `resolve_accounts`, fire-if-any,
  fail-closed) with `_income_max_employment_gap`'s consecutive-pairing; `employer_coverage` reuses
  `_borrower_attributed_documents` (the `belongs_to` per-borrower primitive) + `consistency._normalize`. Both
  cross-module reads (`resolve_accounts`, `_normalize`) are **lazy imports**, mirroring `_stmt_min_account_months`
  (the rule_engine ↔ tag_materialization init-order guard).
- **`stmt.continuity` owns the BALANCE chain only**; the missing-**period** dimension stays AS-10's
  (statement-recency completeness) — the scope boundary AS-8's stop-report drew (LP-406-2 D4). So AS-8 and AS-10
  do not double-fire on one missing month.
- **A past closing date is emitted (negative), not abstained** — unlike `days_since_most_recent_pay`, which
  abstains on a future pay date (a data error). For closing, "in the past" is a real state PC-7 must see.
- **`one_sided` covers both "only one document type" and "no income documents"** — both are "nothing to
  cross-check" → the same `not_applicable`-enabler.
- No rule written; no existing tag/producer/prompt changed; `ACTIVE_RULE_IDS` = 24.

## Any NEW gap

- **The AI fuzzy-residue for `employer_coverage`** (D4) — deterministic normalization can't resolve a
  word-level short-form ("Acme" vs "Acme Freight"); that residue reports `uncovered`. A later fuzzy-coverage
  refinement (or IN-6 shipping `uncovered` as `needs_review` rather than auto) is the follow-up. Not a blocker
  for IN-6's core (both-sides-present, normalized-set coverage).
- **PC-7's closing window is still Priya's** — this ticket deliberately left it out of the tag; PC-7 will
  surface it for sign-off.

## ADR

**ADR-324** (added to `decisions.md`): the derived-producer resolution to the relation taxonomy — ADR-322
(ordered-pairwise) and ADR-323 (set-coverage) established the DSL cannot express these relations natively; the
pattern is to **derive the fact and let a trivial rule branch on it**. Records the three tags' descriptive value
sets (tags describe, rules judge — LP-400), the **`not_applicable`-enabling design** (a nothing-to-check state
must be distinguishable from can't-check, so the rule reaches `not_applicable` not `couldnt_check`), and the
**calibration-inheritance finding** (`employer_coverage` reuses IN-5's *measured* normalizers → no new judgment,
so IN-6 is not held; the AI fuzzy-residue is a documented limitation). Cross-refs ADR-322/323, LP-406-1/2/3/4,
LP-400.
