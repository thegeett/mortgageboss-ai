# LP-1000 — the same document uploaded twice

- **Ticket:** LP-1000 · new feature, from bug-025's investigation
- **Status:** Built — awaiting review
- **Date:** 2026-09-12
- **Scope:** `models/document.py`, `services/documents.py`, `api/documents.py`,
  `services/inbound_triage.py`, `services/upload_links.py`
- **Migration:** `d5c1a8f3e720` — a content digest on every document

---

## What was asked

> *"For document dedup I would like you to create LP-1000 ticket as it looks like new feature. […]
> What if we give responsibility to identify duplicate document to document upload job, it creates
> checksum/hash internally to each document it uploads and if finds same duplicate (content) then it
> rejects? It should also show the reason why particular upload failed because of duplicate caught."*

That is the design this implements, and it is the right layer — it stops the duplicate existing
rather than compensating for it afterwards, and it tells the person at the one moment they can act.

## Measured first

**Nothing in the system could express "is this the same document?"** No hash, checksum or digest
existed on `documents`; `create_document` performed no duplicate check at all. The only duplicate
mechanism that existed — `Document.possible_duplicate` (LP-33) — runs **only** on the email-triage
path, tests by document **type** rather than content, and its own docstring records that nothing has
ever written `True` to it.

On staging, grouping active documents by `(loan_file, document_type, file_size_bytes)`:

| | |
|---|---:|
| groups holding more than one copy | **22** |
| document types affected | **8** |

Pay stubs (×3 on one file), bank statements, mortgage statements, lease agreements, a credit report,
purchase agreements, a USCIS notice, and an untyped pair. Three purchase-agreement pairs were
byte-identical at **3,037,074 bytes**, one of each named `… (1).pdf` — the rename a browser makes
when the same file is downloaded twice.

And one file (`10b6f5e4`) carries the same credit report twice — same filename, same 134,660 bytes —
where **each extraction lists the same 24 tradelines**, so every row-level gather over that file sees
48 rows where 24 exist. That is what turned this from tidiness into arithmetic, and it is bug-025's
subject.

## The design

**One check, in `create_document`.** Four routes create documents — bulk upload, replace,
email-triage accept, borrower upload link — and every one already holds the bytes and calls that
function. A check in any of them would have to be written four times and would be missed once; a
check there covers all four by construction, including whatever route is added next.

**SHA-256 of the raw bytes**, stored as `documents.content_sha256`, hex, `String(64)` — the shape
`InboundAttachment.sha256` has used since LP-806. One convention for the same fact, not two.

**Scoped to the loan file, never wider.** The same document legitimately appears on two loans (a
blank lender form, a borrower with two applications), and `Document` has no `company_id` of its own —
it is company-scoped transitively through its loan file (ADR-052). So scoping the lookup to the loan
file is *also* what makes it tenant-safe by construction rather than by a filter someone must
remember.

**Refused, not flagged.** Byte-identical content on one loan file carries no information the first
copy does not: accepting it only creates a second row for every per-document rule to answer and a
second set of extracted rows for every aggregate to gather.

**And the refusal names what it collided with** — filename and upload date. "Duplicate rejected" with
no referent is worse than accepting the duplicate: the processor can neither tell which of their files
was refused nor find the one already there.

### Per route

| route | behaviour |
|---|---|
| **Bulk upload** | Checked in **stage 1**, beside the size/type validations, so the endpoint keeps its all-or-nothing promise. `DuplicateDocumentError` subclasses `DocumentValidationError`, so the existing handler maps it — carrying its own **409** rather than a 413/415. Also detects **the same file selected twice in one request**, which only the batch can catch. |
| **Replace** | Refused — and refused against everything **except the target** (`exclude_id`), because `create_document` runs *before* `supersede_document`, so the document being replaced is still active when the check fires. See *Review* below: left to the backstop, an identical replace collided with its own target and advised the processor to replace the document they were replacing. Two distinct refusals now: "same as the one you are replacing" and "already on the loan as X". |
| **Email triage** | Re-raised as `CannotAcceptError`, which the endpoint already maps to a 409 carrying the message — so the processor triaging the mailbox is told which document it duplicates rather than handed a 500. |
| **Borrower upload link** | Re-raised as `UploadLinkError`, and deliberately **without naming the existing document**: that response goes to an unauthenticated stranger holding a link, and which documents a loan file holds is not theirs to learn. |

## Three decisions worth arguing with

**1. Nullable, and it stays nullable.** Every row predating the column has no digest and nothing can
backfill it without re-reading every blob out of object storage. So `NULL` means "uploaded before
LP-1000", never "this file has no content", and the check treats `NULL` as no-match — the **fail-open**
direction, on purpose. Refusing an upload because an old row happens to be unhashed is a worse error
than accepting a duplicate.

**2. An index, not a unique constraint.** Uniqueness is deliberately *not* enforced in the database:
the existing rows already hold the duplicates above, so `CREATE UNIQUE INDEX` would fail outright
until they are reconciled — and a constraint would turn the collision into a 500 where the service
raises a 409 naming the document already there. Worth revisiting once the existing duplicates are
cleaned up; the column and index are what make that cleanup writable at all.

**3. Exposed in `readonly.documents`.** A digest is not content — it is fixed-width hex that reveals
nothing about the bytes it covers, unlike `full_text` or `summary`, which C7 drops because a scrub
matching identifier *shapes* cannot redact prose. And it is the column that makes "are these two
documents the same?" answerable from the read-only layer at all: the investigation behind bug-025 had
to proxy that question with `file_size_bytes`, which cannot tell two different 3 MB scans from one
file uploaded twice.

## What this does NOT solve

**Near-duplicates.** Proven in the data: LF-XMB2's two purchase agreements are **485,001 vs 480,929
bytes** — different bytes, same contract (same price, parties, contract date, earnest money, even the
same typo, "kitchen friedge"), differing only in an extracted closing date. A checksum will never
catch that pair. It catches the other three, which are byte-identical.

**Everything already in the database.** The 22 groups are still there, and bug-025's arithmetic
exposure lives entirely in files already ingested. Upload-time rejection does nothing for them, which
is why bug-025 keeps a downstream guard rather than being closed by this ticket.

## Tests

`tests/services/test_document_dedup_lp1000.py`. The digest is the same hex SHA-256 anyone else would
compute, and it is stored. The same bytes on one loan file are refused with a 409 that names the
colliding document and carries the row itself. What must **still** be accepted, each a way this could
have been too strict: the same bytes on a different loan file; another company's identical document;
re-uploading a file whose twin was soft-deleted (without which a processor who deletes a bad upload
could never re-add it); different bytes under the same filename; and an upload colliding with a
pre-LP-1000 row whose digest is `NULL`. Plus `find_duplicate`'s `exclude_id`, which is the seam any
later reconciliation of the existing duplicates will need.

## A note on the migration, because it broke something first

The first cut hoisted the view SQL into module constants. `tests/test_readonly_query.py` scans each
later migration for `CREATE ... VIEW ... FROM public.<table>` **above the line `def downgrade(`** to
learn what the live database has — so the rollback definition landed in the slice read as live, the
drift guard began checking a definition the database does not hold, and that file went from 62 passed
to **24 failed**. Its own assertion names the cause exactly. The SQL now lives inside the function
that runs it, and the file is back to its 62-passed baseline.

## Review — REVIEWED

Peer review (second session). **The design is right and the layer is right** — one check in
`create_document` covering four routes, scoped to the loan file, refusing with the colliding document
named. One defect found on the route whose collision is with *itself*, one gap recorded, two claims
corrected, and one suspicion of mine that turned out to be wrong.

### Found: an identical replace collided with the document it was replacing

`replace` calls `create_document` **before** `supersede_document`, so when the check fires the target
is still `is_current=True` and `deleted_at IS NULL` — which is precisely what `find_duplicate` looks
for. An identical replace therefore matched its own target and refused with:

> This file is already on the loan as **'Appraisal v1.pdf'** (uploaded …). Upload a different file,
> or **replace the existing document if this one supersedes it.**

— advising the processor to do the thing they had just done, and naming the document they were
replacing as the obstacle to replacing it. The intent in the ticket (refuse a no-op replace) is right;
the sentence was not, and nothing caught it because the dedup suite never exercised replace.

The route now asks the question it actually has, which is "is anything OTHER than the target the
same?" — the `exclude_id` seam this ticket built and left unused. Two distinct refusals result:
*"this is the same file as the document you are replacing, so replacing it would change nothing"*,
and *"already on the loan as X — replace that one instead"*. Pinned by two tests at the seam.

### Recorded, not patched: two simultaneous uploads of the same bytes both pass

There is no unique constraint (deliberately — Q5) and no lock around document creation, so two
requests can both read "no duplicate" and both insert. The window is small and the outcome is the
state that existed *before* this ticket rather than a new failure, so it is noted in
`find_duplicate`'s docstring rather than fixed: an advisory lock per loan file would close it, and the
unique constraint closes it properly once the existing duplicates are reconciled. It matters because
the check reads like mutual exclusion and is not — it is a guard against the common case (a double
click, a browser re-send).

### The borrower-link 400 is correct, and I expected it not to be

My first reading was that returning **400** there while the other three routes return 409 is an
inconsistency. It is not. Every refusal on that route is a `UploadLinkError` → 400 — empty file,
inactive link, unsafe file, oversized — and its tests pin 400 three times. Giving a duplicate its own
status would hand an unauthenticated stranger a *distinguishable* signal for "you already sent this",
which is exactly the inference the deliberate non-naming exists to prevent. 400 with a borrower-facing
sentence is right; the reasoning just wasn't written down, and now is.

### Two claims corrected

- **"model + migration guards 17 passed"** does not reproduce: `tests/test_models.py` does not exist,
  and the nearest real grouping (`tests/models/` + the two alembic guards) gives **15 passed / 14
  errors** here, the errors being no-Postgres. Not wrong so much as unverifiable as written.
- **`tests/verification/` is 2,763, not 2,761** — bug-027's own guard added two after this commit was
  written. Worth fixing because a stale count is exactly what a baseline guard is for.

### One claim that is stronger than stated

"content_sha256 seen as exposed" reads as an observation; it is **enforced**.
`test_no_model_column_drifts` fails for any model column that is neither in its view nor in
`EXCLUDED`, and `documents`' `EXCLUDED` set is `{full_text, generic_analysis, summary, storage_path,
document_name}` — which does not contain the digest. So the exposure decision could not have been
skipped, and a future migration dropping the column from the view fails that guard.

### What I could not check

⚠️ **The same limit the commit message states, and it applies to my two new tests as well.** No local
Postgres and no Docker, so `tests/services/test_document_dedup_lp1000.py` COLLECTS (12 tests) and has
never executed — mine included. The replace fix is reasoned from the code paths, not observed passing.
CI or a database is required before this is believed. What did run here: ruff, ruff format and mypy
clean; `tests/test_readonly_query.py` at its 62-passed baseline (unchanged by these edits — they do not
touch the view); `tests/verification/` 2,763 passed, 0 failed.
