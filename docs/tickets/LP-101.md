# LP-101 — Refi MISMO fixtures + end-to-end refinance correctness sweep

- **Ticket:** LP-101 (third and FINAL ticket of the refinance epic, LP-99/100/101)
- **Epic:** Phase 3 — Refinance support
- **Status:** Completed
- **Date:** 2026-07-01

## Summary

The refi path (import → LTV → rules → findings → calculators) had never run end-to-end through a
real import — only unit tests constructed `loan_purpose=REFINANCE` directly, and the one real MISMO
fixture is a Conventional PURCHASE (Mahesh). This ticket creates two synthetic refi MISMO fixtures
and an end-to-end test that is a deliberate **correctness sweep** — its job is partly to FIND what's
still broken on the refi path (the project's recurring bug class: seams between the import/model and
the calculators). See **ADR-227**.

**The honest result:** refinance works end-to-end for what the fixtures exercise; the sweep surfaced
**two seams** (both conservative direction), one fixed inline and one documented + xfail'd as a
follow-up. The suite is NOT falsely green — the remaining gap is tracked, not hidden.

## The fixtures (synthetic / de-identified)

`scripts/generate_refi_fixtures.py` derives two fixtures from the purchase fixture, deterministically:

- **`tests/fixtures/mismo/refi_rate_term.xml`** — `NoCashOut` → `refinance_type=RATE_TERM`; loan
  1,104,000 / valuation 1,380,000 = **80% LTV** (passes the 97% purchase/rate-term cap).
- **`tests/fixtures/mismo/refi_cash_out.xml`** — `CashOut` (+ amount) → `refinance_type=CASH_OUT`;
  loan 1,173,000 / 1,380,000 = **85% LTV** (**over** the stricter 80% cash-out cap; would pass 97%).

The transform: **scrub all personal PII** to obviously-synthetic values (names, SSN, DOB, street
address, email, phone), flip `LoanPurposeType` → Refinance, **drop `SalesContractAmount`** (a refi
has none), and add the `REFINANCE` cash-out determination LP-99 parses. Bank/employer names,
city/state/zip, and account numbers are left as realistic parser input. Verified: the original
borrower name + SSN do not appear in either fixture.

**Grounded-starter test artifacts (validate-with-Priya):** a real refi LOS export may order/name
elements differently, carry FHA-specific refi sections, or mark the existing lien with a payoff
indicator we don't yet parse (see GAP-1). Re-run: `uv run python scripts/generate_refi_fixtures.py`.

## What the sweep ASSERTS (confirmed working)

- **Import (LP-99):** both fixtures import cleanly — `loan_purpose=REFINANCE`, `refinance_type`
  correct (CashOut→CASH_OUT, NoCashOut→RATE_TERM), Conventional, no purchase price (graceful).
- **LTV (LP-99):** appraised-value-only basis (no purchase price / no lesser-of degeneration); the
  cash-out fixture gets the **stricter** `conv.ltv.cash_out_max` (85% → `over`), the rate/term gets
  `conv.ltv.purchase_max` (80% → `pass`). The cash-out case is the epic's crux: it's flagged ONLY
  because the populated `refinance_type` made the stricter cap bind (it passes the 97% purchase cap).
- **Rules + needs (LP-100):** the purchase-agreement rule is **skipped on a refi even with the doc
  fact present** (while the DTI rule still evaluates — DTI isn't purpose-gated); a full
  `run_verification` produces findings with **no** purchase-agreement finding; the refi need-set
  (existing mortgage statement + payoff) seeds, and the purchase-agreement need does not.
- **MI:** computed on the refi (appraised-only) LTV, program-aware — cash-out at 85% → PMI required;
  rate/term at 80% → not required.
- **Max-loan:** uses the appraised value basis for a refi; constraints resolve (no purchase-shaped
  crash).

## Surfaced gaps (handled honestly — never assert-wrong-as-correct)

Both gaps are in the **conservative** direction — they over-state risk, never make a file look more
qualified than it is (the opposite of the earlier permissive binding bugs). Still real correctness
gaps worth flagging.

### GAP-2 (reserves) — FIXED inline

`build_reserves_view` defaulted the down payment to `value − loan` (the borrower's home equity) and
subtracted it from eligible reserves. A **refinance has no down payment**, so this wrongly gutted a
refi's reserves (conservative: understated → spurious "insufficient reserves"). Fixed:
`down_payment = 0` for a refinance (the purchase path is unchanged). Small, obvious, safe — the
textbook "clearly-wrong default". Asserted in the sweep. Direction of the fix (slightly more
reserves) is toward permissive, but `0` is the unambiguously correct value for a refi. Grounded-
starter — validate-with-Priya (esp. cash-out, where the borrower receives funds at closing).

### GAP-1 (DTI) — documented + `xfail(strict)`, follow-up **LP-102**

The back-end DTI counts the existing first mortgage being paid off by the refinance. `_auto_debt_lines`
includes ALL stated liabilities, and we don't parse the MISMO payoff indicator, so the **new PITI**
and the **old mortgage payment** are both counted (double-count). Direction: conservative (DTI
over-stated → possible spurious over-DTI finding); it also propagates to max-loan's DTI ceiling.

**Why not fixed inline:** it is NOT safe to simply drop all `MortgageLoan` liabilities — a borrower's
OTHER mortgages (rental/second homes) must still count. The correct fix needs (a) parsing the MISMO
payoff / "will be paid off" indicator and (b) purpose-aware exclusion of the subject's paid-off lien
from the refi back-end DTI. That is LP-102. The sweep marks the desired behavior
`@pytest.mark.xfail(strict=True)` so the gap is documented and will flip to a hard failure the moment
it's fixed — the bug is never asserted as "correct".
