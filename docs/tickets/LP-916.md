# LP-916 — Condition detail sheet (S2-03, with S2-04 and S2-05)

**Goal:** everything about one condition in one place, opened from any row.

Built in two parts, because the screen could not be built at all until the wire carried the facts its
sentences are made of.

## Part 1 — what a condition's history is allowed to say

**The events endpoint was thin, and its own docstring said so:** `ConditionEventPublic` projected only
ROUND-level keys (`rows`, `created`, `seen_again`, …), so a condition event reached the client as
`kind`, `occurred_at` and `actor_user_id` and nothing else. S2-03's five history lines need more than
that.

**Eight condition-level scalars now travel**, each an enum value, a date or a count — never open text:
`prep_status_from` / `prep_status_to`, `lender_status_from` / `lender_status_to`,
`verdict_source_kind`, `verdict_source_date`, `notes_added`, and `actor_name`.

### `email` is in both source vocabularies, and one key carried both

The defect this part is named for. `ConditionSourceKind` (how a round arrived: pdf_upload · email ·
paste · manual) and `VerdictSourceKind` (where the lender said it: portal · email · phone ·
round_comparison · underwriter_note) **both contain `email`**, and both are written by different
writers under the same `detail["source_kind"]` key.

Projecting that one key into two fields would have rendered **a lender's emailed answer as a condition
sheet arriving by email**. Nothing else in the suite could have caught it: both values are individually
valid members of their own enum, so every existing vocabulary test stays green.

So the projection is guarded by KIND, not by key name — `_VERDICT_SOURCE_KINDS` for the verdict side,
`_ROUND_SOURCE_KINDS` for the round side — and
`tests/api/test_condition_events_projection.py` pins it **in both directions**, because a guard that
only works one way is half a guard.

### `lender_code` is deliberately NOT projected

Every string on this schema is drawn from a closed vocabulary; a lender code is open text off the
sheet. The sheet already knows which condition it is showing, so carrying it would break the
invariant to decorate a sentence that does not need it.

### `actor_name` reuses the one resolver

`resolve_user_names` (shared with `overlay_admin.py`) rather than a second lookup, for the reason its
own docstring gives: *"two lookups would eventually give one actor two names."* `round_number` is
resolved from the event's `round_id` in the same pass — a query per history line would be a query per
line on a sheet that opens on every row click.

### A dead parameter that read as a feature

`from_model` took `round_number`, its docstring described the `detail` fallback, and **the body read
only `detail`**. So the route resolved a number, passed it in, and every condition event still came
back `round_number: null`. Nothing failed: the field was already nullable and round events were
unaffected. Same shape as the `_gate_map` entry LP-911's review proved was decoration, and only a
test asserting the RESOLVED value found either one.

## Part 2 — the sheet and its two dialogs

`condition-detail-sheet.tsx` (S2-03), `condition-answer-dialogs.tsx` (S2-04 and S2-05), wired through
`imported-view.tsx`, with rows in `imported-conditions.tsx` opening the sheet.

### Previous / Next follow the list because the list hands them over

A Done-when: *"Previous and Next follow the list's current filter and sort."* The sheet takes **the
array the list is already rendering, in that order**, and moves an index. It does not hold its own id
list and does not re-query — either would be a second source of order, and the two would disagree the
moment LP-913 adds the filter row. Today there is no filter state at all (`useConditions(fileId)` is
called with no params), so this is the shape that makes the Done-when true *later* without a change
here.

↑ and ↓ are bound while the sheet is open, and ignored while focus is in an input, textarea, select or
contenteditable — so the keys still move a caret inside the reason box.

### Two history vocabularies, and the duplication is only apparent

`round-details-sheet.tsx` already turns a `ConditionEvent` into a sentence. `lib/conditions/history.ts`
is not that function again: the two have different SUBJECTS. On S1-09 the reader is looking at a
round, so `condition_seen_again` reads "A condition was seen again" — one of thirty such lines. Here
the reader is looking at one condition, and the same event must read "Seen again in round 2".

**This one is exhaustive and that one is not**, which is the other real difference. `historyLine` ends
in a `default:` arm, correct there because a browser may run against a backend one deploy ahead.
LP-916's Done-when is stricter — *every* event kind has a plain sentence — so the switch is exhaustive
over the union with a `never` arm, and `history.test.ts` pins the same property from the other side
(`ALL_KINDS` is checked against the union with `Exclude`, so a kind the mirror adds fails `tsc` rather
than silently testing eighteen of nineteen).

### The owner override was invisible on the screen that changes it

`imported-conditions.tsx` rendered `owner_hint` / `owner_hint_source`. Harmless while nothing could
override them — and **LP-916 is what changes that**: the sheet's Owner select writes `owner_override`,
so a processor would reassign a condition to Title and the row behind the sheet would still show the
code map's guess. Now reads `effective_owner` / `effective_owner_source`, which the server already
coalesces in Python and in SQL so the row and the filter agree. *(Raised as an LP-913 item by LP-912's
review; it became LP-916's the moment the override was reachable.)*

### A row is a `<button>`, not a div with `role="button"`

The first version was the div, reasoning that the row IS a grid and a button would collapse its four
columns — true of the OUTER element, irrelevant once the grid moves inside it. Biome's
`useSemanticElements` was right: the button gets focus order, Enter/Space, disabled semantics and the
screen-reader role for free, where the div had me reimplementing three of them.

Three existing tests used `.closest("div.grid")` to find a row. Changed to `.closest(".grid")` — **the
assertions are untouched**, including "no row may say cleared, satisfied or done", which still holds
because a row that opens a sheet introduces none of those words. `round-review.test.tsx`'s three hits
are left alone: draft rows are still divs.

### The allow-list guard failed first, and it was right to

`tests/api/test_condition_events_endpoint.py::test_only_the_named_scalars_are_exposed` pins the
response's field set, and its docstring states the contract: *"A new key added to the response is a
decision somebody makes."* Eight new keys failed it by construction. Seven are trivially defensible
under rule 7 — four status enums, a verdict source enum, a date, a count.

**`actor_name` is not**, and that is worth stating rather than burying. It is the FIRST OPEN STRING on
this schema, so it breaks the invariant the sibling test enforces — that every exposed string comes
from a closed vocabulary, which is what stops `detail={"reader": "Alex Rivera"}` reaching a client
through a key that IS on the list.

Its defence is its SOURCE, not its shape: it is resolved from the `users` table by
`resolve_user_names` and never read from `detail`. **That justification was untested when it was
written**, which would have made updating the allow-list a quiet weakening of a safety guard. So the
fix ships with `test_an_actor_name_in_detail_is_ignored`, which stores a name under
`detail["actor_name"]` and asserts it does not travel — and asserts a caller-supplied name still does,
so the field is not merely always-null.

### What the first full-suite run cost, and what it did not

Two full runs were needed, and the second was not waste: the first measured the app code and found this
guard; the second measured the fix. The edits between them were test-only, so the resulting number was
predictable by arithmetic — **and reporting predicted arithmetic as a measurement is the thing this
ticket's own guards keep catching**, so it was measured instead. The reviewer relied on the last
ticket's number without re-running it.

The frontend was NOT re-run for the second pass, deliberately: it was green on this tree at 1985/1985,
and everything touched afterwards was two backend test files and two documents.
