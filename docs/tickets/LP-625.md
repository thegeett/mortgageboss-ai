# LP-625 — repairing what LP-623 could only prevent

## The report

The first verification after LP-623 deployed left LF-ABRS's Need List **unchanged**: still 20 rows,
still two needs titled "Government ID — Vidulasrri Muruganandam", one VERIFIED against the borrower's
green card and one REJECTED against their unreadable licence. The RECEIVED W-2 need still read "could
not be processed".

I had predicted the duplicate would "collapse to one verified row". It did not, and the reason is in
LP-623's own ticket: **all three passes ADD ONLY.** Preventing a defect does not undo it.

* `equivalent_need_type` stops the floor minting a second ID need under a new name — but neither
  `seed_floor_needs`, `rematch_needs_for_file` nor `seed_needs_from_findings` creates or removes a row,
  so a pair already there stays.
* `transition_need` now clears `reason` when a need leaves REJECTED — but a need that recovered BEFORE
  that shipped only re-transitions if a new document happens to arrive.

## What changed

**`repair_needs_for_file`, run last of the four passes** — after the three that add, because it exists
to fix what they leave behind. Idempotent; a clean file reports zero.

**1. Equivalent duplicates are merged.** Keyed exactly as `seed_floor_needs` now dedupes — normalised
type plus borrower — so a pair it would no longer create is a pair this collapses. The survivor is the
one furthest ALONG (`_PROGRESS_RANK`: verified > received > rejected > requested > pending), not the
oldest, so the outcome does not depend on which pass ran first. The redundant row is **waived, not
deleted**, carrying a reason naming what it merged into: the row and its history survive and a
processor can see what happened.

Per BORROWER, and a test pins it: collapsing two borrowers' ID needs would silently drop a
requirement — the failure the per-borrower key exists to prevent, arriving from the repair side.

**2. A reason that no longer describes the state is cleared.** `reason` belongs to REJECTED and WAIVED.
Anywhere else it is residue from a failure the need has recovered from. Tests pin both directions: a
genuinely rejected need keeps its sentence, and so does a processor's waiver reason.

**3. An AI need no document can close says so.** LF-ABRS carried two with `needs_type` null
("documentation for the 'Other' liability", "for the unspecified asset"). Matching keys on
`needs_type`, so no upload could ever advance them, and nothing on the row said so. The ask is real and
is KEPT — the reasoning now ends "No document type matches this request, so uploading a file cannot
clear it — close it by hand once the question is answered."

**4. Stale AI reasoning is refreshed rather than frozen.** Ingest skipped a proposal whose type already
existed, which froze the first explanation forever: LF-ABRS kept *"two years of personal tax returns,
because contract-basis income must be qualified from tax history"* — written when the model could not
see `self_employed: false` — long after LP-624 started carrying it. The need is right; the sentence
was not.

Refreshed only where the processor has NOT acted: origin `AI_REASONING`, disposition still `PROPOSED`,
status still open. A need someone confirmed, dismissed or adjusted carries their judgment, and a later
model run has no business editing the reason they acted on.

## Not done

**A need whose reason has gone away is still not retracted.** The purchase agreement on a file
corrected to a refinance, or an appraisal need whose MI-1 finding a processor overrode, stays on the
list. Deleting a line someone may already have requested or received is worse than a stale one, so the
answer is to SURFACE that the reason is gone and let them decide — which needs a UI affordance and a
column, not a repair pass. Recorded here rather than half-built.

## Verification

Ten tests, each written from the row that was actually wrong on staging rather than from a
hypothetical: the verified/rejected ID pair, progress-not-age ordering, two borrowers not collapsing,
the recovered W-2's failure text, a genuinely rejected need keeping its reason, a waiver keeping its
reason, a clean file reporting zero, two untyped needs not merging, and the unmatchable-note text in
both directions.
