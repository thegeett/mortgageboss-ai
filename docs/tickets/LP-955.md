# LP-955 — "I'll do it" actions

- **Ticket:** LP-955 · Phase 4.5 Stage 3 follow-ups, batch 4 (the staging trial)
- **Source:** [`phase4.5-staging-trial-2026-09-30.md`](../phases/phase4.5-staging-trial-2026-09-30.md)
  item 8; the owner: "Upload, and 'Ask someone for it' (turns it into an ask in that recipient's draft). For
  IV-01 at UWM, offer two routes: 'Pulled in UWM's system' -> ask the underwriter to clear; 'Our vendor' -> her
  task, upload the vendor invoice."

## Design

**Upload** is LP-953's "Upload here", already on every item (it links the upload to that item).

**"Ask someone for it"** — on an item whose step is "I'll do it", a select: The LO, The borrower, Title,
Someone else. Her choice goes through `update_item` (the existing item edit: `option` = `ask_borrower` for
the borrower, else `ask_third_party`, and `performers` = [who]), which re-syncs the drafts, so the item lands
in that person's email. Decisions:
- **In place, never replaced.** `update_item` changes the row; its id is what evidence, her unlinks
  (LP-953) and the draft link are keyed by, so nothing has to be carried. A test asserts the condition's only
  live item is still the original row.
- **Not offered:** herself (it is already her task) and the appraiser (appraiser asks go through the
  lender, LP-942); so the choice never silently routes back to her task or to a draft she did not expect.
- **Reversible** through the plan's existing step select ("I'll do it" again), which re-syncs the drafts
  and takes the item out of the email.
- "Becomes Waiting on …" (LP-947) follows from the same path as any ask, so it updates with the change.

**Routes** — when a lender has more than one way to get a condition done. `condition_plan.ROUTES` is data,
keyed by (canonical lender key, library type), each route a key, a label, a hint and the step it sets:
- `("uwm", "IV-01")`: **Pulled in UWM's system** (step: Ask the underwriter) and **Our vendor** (step:
  none; the item stays her task to upload the vendor's invoice).

The condition payload carries `routes` and `chosen_route` (the route whose step the condition has); every
caller of `_condition_public` must pass the file's lender keys (a required argument, so no door leaves the
choice off). `PUT /conditions/{id}/route {route}` chooses one through `set_next_step` (the one door for
steps, which re-syncs the underwriter's question); a route not offered for the condition is 409.

**The underwriter's question in the type's words.** The library gains an optional per-type `question`
(placeholders `{lender_short}` and `{code}`, filled by code). IV-01's: "The credit report for this loan was
pulled in {lender_short}'s system, so {lender_short} has the invoice. Could you clear {code}, or let me know
what else you need?" `render_question` uses it when the step is "Ask the underwriter"; otherwise the reading's
summary and the general request, as before.

**Frontend.** "How this gets done" (two buttons, the chosen one pressed, each with its hint) in the drawer
for a condition with routes; the "Ask someone for it…" select beside Link a document / Upload here on an
"I'll do it" item.

**For the domain expert:** whether other lenders' credit invoices need the same two routes, and whether
"Pulled in UWM's system" should also apply to other invoice types.

## Review (of `227faaf5`)

**Three findings, all fixed here. The backend decisions are right and tested at the layer they
matter — the in-place item edit especially — but the two new surfaces both offer less than the
model behind them supports, and each does so silently: a route she picks that cannot read as
chosen, a recipient list missing three of the emails an ask reaches, and a placeholder guard that
became the union of two disjoint sets.**

### Finding 1 — "Our vendor" can never read as chosen, so picking it looks like nothing happened

`chosen_route` returned only routes with a step:

```python
if route.step is not None and condition.next_step is route.step:
```

`our_vendor` is defined with `step=None` (its whole point: the items keep her task). So the
expression could never return it. Measured on 0006 before the fix:

```
chosen_route, default state                   -> None
chosen_route, after choosing lender_system    -> "lender_system"
chosen_route, after choosing our_vendor       -> None        <- her choice, invisible
chosen_route, after a step no route sets      -> None
```

The frontend presses on exactly that value (`condition-routes.tsx:28`, `aria-pressed={chosen}`), so
she clicks **Our vendor**, the request succeeds, the panel refetches, and both buttons are still
unpressed — the same picture as never having chosen. Rows 1 and 3 are indistinguishable.

Two statements promise otherwise, which is what makes this a defect rather than a trade-off: this
ticket's own Frontend section says *"two buttons, **the chosen one pressed**, each with its hint"*,
and the docstring said the task route *"reads as chosen only after a change"*. Neither was reachable.

**Fixed** by deleting the `route.step is not None` clause — the fix is a removal, not an addition.
`chosen_route` now answers with the route whose step the condition carries, `None` included, which
is what the panel's own heading asks: *How this gets done*. With `next_step` null the condition
genuinely is on the task route (its items carry their own steps and 0006's is hers to upload), so
pressing it states the current plan rather than inventing a decision.

The control matters as much as the fix: a condition whose step is one **no** route sets (she used
the step select for `ask_borrower`) still reads as `None`, so "pressed" means "on this route" and
not merely "has no other step". `test_our_vendor_reads_as_chosen_and_a_step_no_route_sets_reads_as_
neither` pins all four rows; restoring the clause fails it and
`test_iv01_at_uwm_offers_two_routes`, and nothing else.

That acceptance assertion changed from `chosen_route is None` to `== "our_vendor"`, which is the
behaviour change, stated: on arrival the panel now presses the task route instead of pressing
nothing. **What this fix does not do** is store her decision. The step is still a proxy, so
"has she decided?" remains unanswerable — if the product ever needs to nag her about an undecided
route, that needs a stored field and this derivation will not do. I considered adding one (a
`route_key` column, the `OwnerHintSource` shape LP-953 used for her unlinks) and rejected it: it
is a migration on a branch three sessions share, for a fact nothing reads yet.

`test_no_two_routes_in_a_pair_share_a_step` pins the premise the derivation now rests on, over the
whole table — two routes sharing a step (`None` counts) would make the answer arbitrary, and a new
ROUTES row that breaks it fails in a test rather than in a drawer. It asserts `ROUTES` is non-empty
first, so it cannot pass vacuously.

### Finding 2 — the placeholder allow-list became the union of two disjoint sets, and had no test

`EMAIL_PLACEHOLDERS` exists so that, in LP-922's words, *"a template cannot name a fact nothing
supplies"*. LP-955 added `lender_short` and `code` to it and added a sixth field (`question`) to the
same gate. But the two fillers are **disjoint**, which I checked rather than assumed:

- `condition_drafts._values` supplies `amount, amount_short, loan_number, required, verified,
  instruction` — and neither of the new two;
- `_type_question` supplies `lender_short, code` — and none of the six.

So after LP-955 every field validated against the union of names its own filler cannot supply, in
both directions. And `fill` answers a missing value with `None`, which no caller treats as an error:

- an item `email` naming `{code}` → that request **line disappears from the borrower's email**;
- a type `question` naming `{amount}` → `render_question`'s walrus falls through to the generic
  question, losing the type's words, with nothing logged.

Both are silent, which is precisely the failure the guard was built to make impossible. Neither is
live in `types.yaml` today (I checked every wording line that contains braces: two `email`, two
`why`, one `question`, all of them filled by their own caller), so this is the guard going wide
rather than a present bug — and the allow-list has **no test at all**, which is how the widening
passed unnoticed.

**Fixed** by splitting it per filler: `QUESTION_PLACEHOLDERS = {lender_short, code}` for `question`,
`EMAIL_PLACEHOLDERS` back to the six for the rest, and `_wording` taking the allowed set as an
argument. Three refusal rows in the existing parametrized harness, plus
`test_a_types_question_may_name_the_lender_and_the_code` as the positive control — the shipped
IV-01 question uses both names, so the narrowing cannot be green by refusing every placeholder.
Each half is pinned independently: re-widening `QUESTION_PLACEHOLDERS` fails only the `question`
row, and re-widening `EMAIL_PLACEHOLDERS` fails only the `email` row.

### Finding 3 — "Ask someone for it" reaches four of the seven emails an ask has

`ASK_WHO` listed `lo, borrower, title, other_party`. The backend's `_RECIPIENT` table
(`condition_plan.py:1218`) routes seven performers to their own drafts, three of which the select
never offered: `insurance` → the insurance email, `hoa` → the HOA's, `employer` → the employer's.
Each has its own heading ("Email to the insurance agent"), its own participant role (`INSURER`,
`EMPLOYER`) and its own place in `_RECIPIENT_ORDER`. The select is the only door that delegates an
"I'll do it" item, so those three lanes were unreachable from the UI.

The consequence is not only a vaguer label. `party_lines` (`condition_drafts.py:528`) appends the mortgagee
clause **gated on `item.performer is Performer.INSURANCE`, not on which draft it is building** ("THE INSURANCE EMAIL
CARRIES THE CLAUSE, exactly as the letter prints it (README S3-05)"). Delegating a hazard-insurance
item as "Someone else" sets the performer to `other_party`, so the ask lands in the other-party
draft **without the clause the README requires** — a domain-meaningful loss, not a cosmetic one.

The ticket says *"Not offered: herself … and the appraiser"*, naming two of the seven absences and
justifying only those two. The other five were unexplained, and three of them were wrong.

**Fixed**: the select now offers `lo, borrower, title, insurance, hoa, employer, other_party`, and
the comment enumerates why each remaining absence is absent — the **processor** is her own task;
the **attorney** shares Title's single `title_attorney` email, so offering both would be two labels
for one draft; the **lender** and the **appraiser** go to the lender's draft (LP-942, appraiser
independence), which is not a delegation she makes from here. No backend change was needed:
`update_item` already sets `item.performer = performers[0]`, which is the field the mortgagee clause
reads, so the fix delivers the clause and not just the label. The test asserts the full list in
order, asserts the four absences, and sends the insurance choice; dropping `insurance` fails it.

### Checked and not findings

- **The type question is escaped, one layer earlier than it looks.** `middle = f"<p>{asked}</p>"`
  interpolates with no `html.escape`, while the same function escapes `lender_code` at line 727 and
  the reading summary at 753 — the asymmetry a reviewer should chase. It is safe: `fill` escapes the
  template *and* every value (`loader`-side `html.escape` at `condition_drafts.py:283-285`, with
  LP-950's "a value is text, never markup" comment behind it). So `{lender_short}` filled with
  "M&T" lands as `M&amp;T`. Recorded because the next reader will make my mistake.
- **No literal placeholder can reach a reader through the three fields that use `fill`**, because
  `fill` returns `None` for a missing value rather than leaving the braces — the predicted defect
  I went looking for first. `render_question`'s walrus then falls through to the reading summary and
  the general request, so a route cannot produce an empty question; `test_a_question_without_a_type
  _question_keeps_the_reading` is that case, with 1582 as a real type that has no question.
- **A missing lender or an unmapped type gets no routes, not a crash.** `routes_for` returns `()`
  for a null lender key or a null type before the lookup, and `ROUTES.get(..., ())` covers the rest;
  the panel renders nothing for an empty list. `test_iv01_at_uwm_offers_two_routes` keeps 1582 as
  the positive control for the empty case.
- **`lender_keys` is a structural requirement, not a nominal one.** All four `_condition_public`
  callers pass a real value (three through `await _lender_keys(db, condition.loan_file_id)`), and
  because it is a required keyword a new door cannot omit routes by forgetting it. The one-query
  helper also carries the bug they found in the ticket (`dict()` over a SQLAlchemy result) as a
  comment at the line, which is where it belongs.
- **The new endpoint is gated without anyone having to remember it.** `PUT /conditions/{id}/route`
  sits on `conditions_by_id_router` with `ScopedCondition`, and `test_condition_route_gating.py`
  walks that router's routes by **dependency identity**, so the new route was covered the moment it
  was added — no list to update, which is exactly what that test's own comment was written for.
- **The in-place decision is tested at the layer the bug would appear.** `assert [i.id for i in
  await _items(...)] == [task.id]` names its reason (evidence, her unlinks and the draft link are
  keyed by the id), so it would fail if `update_item` ever replaced the row — which is the LP-953
  interaction worth protecting. This is the assertion they added after their runs; see below.
- **The derived `chosen_route` cannot claim a lender route she never picked — today.** It would, if
  anything set `ASK_UNDERWRITER` on an IV-01 at UWM automatically. Nothing does: the lender settings
  cover PA-03, IE-08, TI-01/02/05 and IN-01/02/04, and no IV type. A future ROUTES row whose step the
  plan also sets by itself would press a button she never touched, so the constraint belongs with
  the table; it is written into the `chosen_route` docstring.
- **A latent hole I measured and left alone, deliberately.** `label` and `short` are used raw
  (`condition_drafts.py:1241, 1658, 1670, 1677`) and never pass through `fill`, yet `_wording` lets
  them carry placeholders — so a `{code}` in either would print **literally** on her screen. No
  yaml value does it (checked: the only braces are in `email`, `why` and `question`), it pre-dates
  LP-955 by every name rather than the two it added, and fixing it means narrowing fields this
  ticket never touched. Logged as an open item instead; the per-field `allowed` argument this review
  added is the hook it needs.
- **Their disclosed gap is closed.** They said one assertion went in after their runs with only that
  file re-run, and named it. The full suite at `227faaf5` with nothing of mine added: **9105 passed,
  1 failed** (the named sonnet test), 8 skipped, 1 xfailed — their exact number, now measured after
  the assertion. "That file passes" and "the suite passes" are different claims; saying which one
  you have is what makes this a two-minute confirmation instead of a re-review.
