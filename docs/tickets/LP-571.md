# LP-571 — a processor can mark a liability paid off at closing

**Status:** control done; the detection rule is the next piece

## Why

LP-568 shipped the mechanism that keeps a retired obligation out of the back-end DTI, and nothing
could set it. The MISMO export carries `LiabilityPayoffStatusIndicator=false` on every liability
(deliberately stored as `NULL`, "not established"), and there was no human path — the schemas did
not carry the columns, so the POST/PATCH endpoints could neither read nor write them.

The result was a mechanism that was inert on exactly the file that motivated it. Deployed to
staging as `staging-ce8f04a`, LF-WCHG still read **58.59%**, because the flag on
`MortgageLoan — UNITED WHSLE MORT` was `NULL` and `None` keeps a debt counted by design.

## What shipped

`StatedLiabilityInput` accepts `paid_off_at_closing`; `StatedLiabilityPublic` returns it and
`payoff_source`. The liabilities editor gains a **"Paid off at closing?"** checkbox, alongside the
existing type / monthly / balance / holder fields.

Ticking it drops the payment out of the ratio: the DTI card recomputes **live** on the next read —
`build_dti_calculation` runs per request, so no verification run is involved — and the row renders
struck through as "not counted — paid off at closing".

**`payoff_source` is stamped server-side and never accepted from the client.** It distinguishes
"the 1003 said so" from "a processor said so", and the excluded line's wording is derived from it,
so a caller able to set it could label their own judgement as the export's. It is also **cleared**
when the flag is retracted, so stale provenance cannot outlive the claim it described.

**An untouched row writes nothing.** `_apply_update` uses `exclude_unset`, and `EditableRow` sends
only changed fields, so a liability nobody has judged keeps its honest `NULL` rather than being
recorded as "retained". The distinction matters: `NULL` is nobody having looked, `False` is somebody
having decided.

## What this does NOT do

It is a lever, not a detector. It fixes files where somebody notices. On every file where nobody
notices, the DTI stays wrong and nothing says so — that is the detection rule's job, and it is why
the rule is worth building even though this unblocks the immediate problem.

Deliberately not added: a control on the DTI card's debt rows. That is where the problem is
*noticed*, but a second write path would duplicate this one, and the rule's Apply button is the
right affordance at the point of notice.

**The findings and the frozen snapshot do not move without a re-run.** They are per-run artifacts,
so DT-6 keeps showing the old picture until verification runs again — and DT-6 will still *ask* the
retained-or-paid-off question, because the `not_applicable` scoping ships with the rule.

## Verified by removing the fix

| removed | result |
|---|---|
| the checkbox field | both editor tests fail |
| the server-side stamp | `test_marking_a_liability_paid_off_stamps_processor_provenance` fails |

`test_retracting_a_payoff_clears_the_provenance` passes with the stamp removed — with nothing ever
setting the source, "cleared" holds trivially. It guards the clearing in the real code, not the
stamping; noted so a future reader does not mistake it for a discriminating test.
