# LP-701 — arrow-key movement through the extracted fields feels random

- **Ticket:** LP-701
- **Status:** Open — two candidate causes from code reading; **not reproduced**
- **Date:** 2026-09-06
- **Reported by:** the user, from the running app
- **Scope:** Frontend — `components/file/documents/reviewer/{review-queue,use-review-keys}.ts`

## The report

> When we click arrow up and down button from keyboard, selection of extracted list goes
> randomly not in sequence.

## Not yet reproduced — read this first

The local dev servers were stopped at the user's request before this was investigated, so
what follows is **from reading the code**, not from watching it happen. Both causes below
are candidates. The first thing this ticket should do is reproduce the behaviour and say
which one it is — or neither.

That matters because the two want opposite fixes.

## Candidate 1 — it is skipping on purpose, and the purpose is invisible

`↓` and `↑` are bound to `nextField` / `previousField`, which call
`nextAttention()` in `review-queue.ts`. That function deliberately **skips every field
that does not need attention**:

```ts
export function needsAttention(field: QueueField): boolean {
  if (field.verdict) return false;          // already accepted / corrected / rejected
  return field.tier !== "confident";        // and anything the model was sure about
}
```

LP-UI-033 asked for exactly that — *"next field needing attention (skips confident ones)"* —
because the metric is flagged fields per minute. But nothing on screen says the arrows are
skipping. A confident field renders with **no chrome at all** (LP-UI-032's first acceptance
criterion), so from the reader's side the cursor jumps from row 2 to row 6 to row 9 past
rows that look no different from the ones it stops on.

It also varies per document: the skip pattern depends on which fields carry a confidence
and which have been decided, so the same keystroke behaves differently on the next
document. That is a good description of "random".

If this is the cause, the fix is **not** to remove the skipping. It is to make it legible —
and probably to separate the two motions: plain `↑`/`↓` walking every field, and a
distinct binding for "next one that needs me".

## Candidate 2 — the arrows sometimes belong to the page, not the list

LP-UI-043 gave the zoomed page view the arrow keys back, so a keyboard user can pan it:

```ts
if (isPanRegion(event.target) && SCROLL_KEYS.has(event.key)) return;
```

So `↓` moves the field selection when focus is anywhere else, and scrolls the document when
focus is inside the page canvas. Both are defensible; the pair is not, because **nothing
tells the reader which mode they are in**. Clicking a highlight box to select a field puts
focus inside the pan region — after which the arrows stop moving the selection, with no
visible cause.

If this is the cause, the fix is a visible focus treatment on the page view, or moving the
pan keys off the arrows.
