# LP-701 — arrow-key movement through the extracted fields feels random

- **Ticket:** LP-701
- **Status:** Done (2026-09-06). Reproduced in the running app; cause (a) confirmed, cause (b) ruled out as the trigger.
- **Date:** 2026-09-06
- **Reported by:** the user, from the running app
- **Scope:** Frontend — `components/file/documents/reviewer/{review-queue,use-review-keys}.ts`

## The report

> When we click arrow up and down button from keyboard, selection of extracted list goes
> randomly not in sequence.

## Not yet reproduced — read this first

The local dev servers were stopped at the user's request before this was investigated, so
what follows is **from reading the code**, not from watching it happen. Both causes below
are candidates. The first thing this ticket should do is reproduce the behaviour and say
which one it is — or neither.

That matters because the two want opposite fixes.

## Candidate 1 — it is skipping on purpose, and the purpose is invisible

`↓` and `↑` are bound to `nextField` / `previousField`, which call
`nextAttention()` in `review-queue.ts`. That function deliberately **skips every field
that does not need attention**:

```ts
export function needsAttention(field: QueueField): boolean {
  if (field.verdict) return false;          // already accepted / corrected / rejected
  return field.tier !== "confident";        // and anything the model was sure about
}
```

LP-UI-033 asked for exactly that — *"next field needing attention (skips confident ones)"* —
because the metric is flagged fields per minute. But nothing on screen says the arrows are
skipping. A confident field renders with **no chrome at all** (LP-UI-032's first acceptance
criterion), so from the reader's side the cursor jumps from row 2 to row 6 to row 9 past
rows that look no different from the ones it stops on.

It also varies per document: the skip pattern depends on which fields carry a confidence
and which have been decided, so the same keystroke behaves differently on the next
document. That is a good description of "random".

If this is the cause, the fix is **not** to remove the skipping. It is to make it legible —
and probably to separate the two motions: plain `↑`/`↓` walking every field, and a
distinct binding for "next one that needs me".

## Candidate 2 — the arrows sometimes belong to the page, not the list

LP-UI-043 gave the zoomed page view the arrow keys back, so a keyboard user can pan it:

```ts
if (isPanRegion(event.target) && SCROLL_KEYS.has(event.key)) return;
```

So `↓` moves the field selection when focus is anywhere else, and scrolls the document when
focus is inside the page canvas. Both are defensible; the pair is not, because **nothing
tells the reader which mode they are in**. Clicking a highlight box to select a field puts
focus inside the pan region — after which the arrows stop moving the selection, with no
visible cause.

If this is the cause, the fix is a visible focus treatment on the page view, or moving the
pan keys off the arrows.

## Reproduced — it was cause (a), and it was not random at all

Measured in the running app on a real pay stub with 19 extracted fields, pressing ↓ from a
fresh document:

```
rows 0..18 in list order
↓ →  5, 6, 7, 9, 10, 11, 12, 13, 15, 16, then wrapped to 5
```

Rows 0–4 were never reached. Row 8 (`Pay frequency`) and row 14 (`Position or title`) were
stepped over. Then it wrapped to the middle of the list.

Every one of those jumps was **exactly what the code was written to do**: `↓` and `Tab`
were both bound to `nextField`, which runs `nextAttention`, which skips any field that is
`confident` or already decided. LP-UI-033 chose that deliberately — "on a pay stub that is
the difference between three stops and thirteen".

The bug is not the skipping. It is that **a confident field draws no mark**, by an equally
deliberate LP-UI-032 decision, so nothing on the screen accounted for a single jump. A
correct behaviour that the interface refuses to explain is indistinguishable from a broken
one, and the report is what that looks like from the outside.

Cause (b) — LP-UI-043 giving the arrows to the page canvas — is real but was not this. The
keys were dispatched at the window, outside the pan region, and still skipped. It stays as
it is: a zoomed page has to be readable without a mouse, and the behaviour is tested.

## The fix: two motions, two keys

Rather than make the skip visible (a mark on every settled field, on every document, to
explain a key nobody would press again), the two motions are separated:

| key | motion |
|---|---|
| **↓ / ↑** | one row, in the order the list is drawn — `stepField` |
| **Tab / Shift+Tab** | the next field needing attention — `nextAttention`, unchanged |

`↓` now does the literal thing, which is what a processor reading a list expects, and the
flagged-fields-per-minute loop keeps its jump under the key whose sheet entry says so:
"Skip ahead to the next field needing attention".

`stepField` walks EVERY row, including the list-valued fields `buildQueue` drops (LP-702).
Those are rows on the screen, and `↓` has to reach what a processor can see.

## A guard that was green by construction

`shortcut-sheet.test.tsx` had a test called "documents every binding the table has". It
only checked that every row of the SHEET was real — it would have passed with a new action
bound to a key nobody wrote down, which is close to the shape of this bug. It now also
asserts every action in `ReviewKeyActions` is documented.

## Verification

- Re-measured in the app: `↓` from a fresh document walks 0, 1, 2, 3, 4, 5 — no skips.
  `Tab` from row 5 walks 6, 7, **9**, 10, 11, 12 — the attention jump intact, still
  stepping over the confident row 8. `↑` walks 11, 10, 9, **8**, 7, 6 — reaching the row
  `Tab` skips.
- Three isolated mutations, each reverted: re-aliasing the arrows to `nextField` failed 5

  failed 1.
- Full suite 1,263 passing. Shortcut sheet checked in light and dark.
