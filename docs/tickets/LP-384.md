# LP-384 — Extend the LF-6T3N fixture; verify and activate the stuck deterministic rules

## What this ticket is

Five no-AI deterministic rules (AS-9, IN-4, AS-3, AS-10, IN-3) resolved `unknown` **not because they're
broken** but because LF-6T3N lacked the documents they read (LP-381/382/383). This EXTENDS the fixture we
already trust with those documents — each built to a KNOWN, asserted answer — proves each rule's verdict, and
activates the ones that pass the eligibility gate. It does **not** build a new loan or a de-identifier.

## Acceptance criteria

- The fixture is extended ADDITIVELY (the base stays frozen for existing consumers); each added document
  carries the exact producer-read field names (the LP-333/369 trap) and a KNOWN answer.
- Each rule's REAL verdict is reported (fire AND satisfy proven), not predicted.
- The rules that truly resolve activate via the eligibility gate; the blocked ones stay held (fail-closed).
- The 14 previously-live rules are identical; full suite green.

## Phase 1 — the extension (a frozen base + a sibling)

`build_lf6t3n_snapshot` is consumed by many frozen tests, so LP-384 adds a SIBLING **`build_lf6t3n_plus()`** =
the base + exactly three appended documents:
- **two VOEs** with a deliberate 77-day gap (prior job ends 2024-06-30, current starts 2024-09-15) — the
  fields `start_date` / `end_date` (the exact names `income.employment_start` / `_end` read).
- **one bank statement** with `page_count_declared="5"`, `page_count_present="4"` — the exact names
  `stmt.page_count_declared` / `_present` read. It joins an EXISTING account + month (First Springfield
  `****5678`, May 2026), so **AS-10 is undisturbed**.

A test pins that the extension only appends — every existing document's tags are byte-identical, AS-10's input
is unchanged, and the ONLY loan-level tag that changes is the employment gap the VOEs are added to resolve
(`unknown` → `77`).
