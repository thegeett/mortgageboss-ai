# LP-109 — Show ALL documents matching a need (derive-on-read)

- **Ticket:** LP-109
- **Status:** Completed
- **Date:** 2026-07-03
- **Scope:** Backend (needs engine + API + schema) + frontend (needs card)

## The gap LP-108 left

LP-108 made a graded need honest — "documents attached — confirm coverage" instead of a false-green
"satisfied". But the data model stores a **single** `satisfied_by_document_id` (one FK per need), so
the card could only name **ONE** of several matching documents. For a graded need like "2 months of
bank statements" the processor was asked to *confirm coverage* while seeing only one of the statements
that actually matched — the evidence needed to confirm was mostly hidden. That undercut the whole
point of LP-108.

An earlier read-only investigation established WHY only one shows and, crucially, the mitigating fact:
the matcher's criteria is **trivial deterministic equality** (`document_type == needs_type`, or an
umbrella need's category == the document's category) over fields **already stored** on every document.
So the full matching set is a cheap display-time query — no traversal, no new joins, no new data.

## The fix (derive-on-read — no schema change, no matcher change, no migration)

`documents_matching_need(need, documents)` (in the needs engine) returns ALL of a file's completed
documents matching the need's criteria, reusing the matcher's own equality. At response-build time the
API computes this list and the response carries a `matching_documents: [{id, filename}]` array. The
single `satisfied_by_document_id` is **kept as the "trigger"** — the document that moved the need to
RECEIVED — and the full set is derived on read.

- **Backend.** `app/services/needs_engine.py` adds `documents_matching_need`. `app/schemas/needs_item.py`
  adds `MatchedDocument` + `matching_documents` (default empty) and `from_model(..., matching_documents=)`.
  `app/api/needs.py` loads the file's completed documents **once** for the list endpoint (no N+1) and
  attaches the matching set to graded needs; single-need endpoints derive via `_public_one`.
- **Frontend.** `need-card.tsx` renders the full list ("{N} matching documents" + each filename) when
  present, else falls back to LP-108's single "Satisfied by / Attached" line.

## The over-inclusiveness is intentional

For an umbrella need the derived set is **coarse** — the `asset_statement` need lists every
ASSETS-category document (even an earnest-money-deposit withdrawal). That coarseness IS the
"confirm coverage" honesty level: the system surfaces every candidate; the **processor curates** which
ones count. We deliberately do NOT narrow/refine — precise, per-account, per-month coverage
(N accounts × M months) is the V2 coverage grid, not this ticket. Showing a superset the processor
prunes is honest; hiding matches to look precise is not.

## Scope boundaries

- **Display/derivation only.** No schema change, no matcher change, no migration. Need generation and
  LP-108's honest STATUS logic are untouched and independent.
- **Live set, not a persisted decision (known limitation).** Derive-on-read shows the CURRENT matching
  set, not a persisted "the processor confirmed these specific documents" record. A persisted, curated,
  editable per-need document set (an explicit needs↔documents join + matcher accumulation) is the
  foundation for **V2 / Option A**, built when its shape is known — not now.

## LF-6T3N

The asset need (`needs_type = "asset_statement"`, umbrella) previously showed 1 attached document.
With derive-on-read it now shows all **9** matching ASSETS-category documents (including the
intentionally over-inclusive "EMD Withdrawal.pdf") — delivering LP-108's intent that the single-FK
model couldn't. Verified by smoke test against the real file; no data mutation required.

## Decision

See **ADR-233** in `decisions.md` — derive-on-read the full matching set; keep the single FK as
trigger; intentional over-inclusiveness; persisted one-to-many deferred to V2 / Option A.
