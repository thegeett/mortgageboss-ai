## Design

**The placeholders are named.** `condition_reading.GENERIC_NAME` ("What the lender asks for") and
`GENERIC_ACCEPTABLE` ("What the lender's words describe") replace the two literals (`_generic_item`, and
`condition_plan`'s copy of the name). They are internal words and may never reach an email.

**Masking** (`condition_drafts.mask_accounts`, code only). A run of digits (hyphen-joined groups count as
one run) that is not part of a word, a dollar figure or a decimal, and has five or more digits, becomes
`****` plus its last four. The lender's loan number is kept whole (the emails already print it). Five is
the line the existing privacy test draws ("no long digit run" outside the loan number). Known cost: a
five-digit ZIP or PO box inside the lender's words is masked too; that is the safe direction.

**The lender's words** (`lender_words`): the condition's verbatim text, "TC:" marker and closing full stop
dropped, masked. Used by:
- `_plain_line(condition, item, letter)`: a line with no library `email`. The item's own acceptable form
  when it has a real one; otherwise "**Name** — as the lender wrote it: “…”", or the bolded words alone when
  the item has only the generic name. Never a placeholder.
- `_values`' `{instruction}` (TI-04's line), which copied the verbatim text unmasked before.
- `render_question`'s summary line, now masked.
The mortgagee clause on an insurance line is NOT masked: the insurer must print it exactly, and it is
the letter's, not a borrower's.

**One line per wording** (`_one_line_per_wording`), found by running the LF-DH8V case: a condition read
without a type can split into several generic items, each quoting the whole condition, so 7086's paragraph
printed twice in one borrower email. Identical lines become one, carrying both codes. Applied in
`borrower_lines`, `party_lines` and `lender_lines`.

**The lender email** (`lender_lines` + `render_lender`, dispatched in `render` for
`DraftRecipient.LENDER`):
- each line is a request: "**Please order the** <item>" for an appraiser's item (routed to the lender,
  LP-942), "**Please provide the** <item>" otherwise; the detail is the library's acceptable form, else the
  lender's words in quotes;
- the opening is "For **SURNAME · loan**(property). Could you help with this?" and never "the lender
  needs";
- the subject names the request: "SURNAME LOAN — final inspection request" when there is one named
  request, else "— N request(s)".

**Reuses.** `_library_item`, `fill`, `_file_name`, `_signature`, `_ol`, `Line`.

## Review

Reviewer: a **fresh subagent** (the peer reviewer session was not sanctioned by its user), reading the
diff `de7df33c`, this file, the trial items 2 and 3, and the LP-934 reviewer brief cold. Every finding
below came from running something: `mask_accounts` on a list of shapes, the LF-DH8V drafts printed in
full, and a mutation of every guard on the path.

### Findings (7, all fixed)

1. **`mask_accounts` printed account numbers whole.** The pattern required a word boundary on both
   sides and refused a following comma (meant for "2,850"). Measured on the build:
   `account 123456789, statement`, `Account No.123456789`, `Acct123456789`, `acct x123456789`,
   `card 1234 5678 9012 3456`, `SSN 123 45 6789` all came back unchanged; the first is the commonest way
   a number sits in a sentence. **Fix:** one pattern with three named shapes: a `figure`
   (thousands-grouped or decimal, kept), a `spaced` number (groups of 2–5 digits joined by single spaces,
   masked whole at 8+ digits or when any group has 5, so `12345 67` cannot print its neighbours beside
   its last four), and a `run` (hyphen-joined, masked at 5+). Never mid-number, never after `$`. Controls
   kept: the loan number (also next to `12 months` and after a comma), `$38,210.40`, `12,345 units`,
   `123456.78`, `December 15 2025`, `09/30/2026`, `B3-4.2-02`. Not covered, and written in the docstring:
   dot-grouped digits (`123.456.789`), which read as a decimal.
2. **Only the lender's words were masked; the item's own name and acceptable form were not.** A generic
   item's name is the reading's or hers (S3-03), and either can copy an account number out of the
   condition. `_plain_line` and `lender_lines` printed both raw, and the lender subject printed the
   name raw. **Fix:** both masked in both builders; `render_lender` masks `request` itself, so the guard,
   which renders the template and not its caller, holds it.
3. **`fill` ate the mask.** It applied `**…**` bold AFTER substituting values, so TI-04's
   `**{instruction}**` with a masked `****7788` inside printed "account 7788" (the stars read as markup),
   and the lender's own `**8/28 Not in Upload` (LF-DH8V's text) splits the bold the same way. Found by
   writing the missing TI-04 test (finding 7). **Fix:** the template's bold first, then the values,
   escaped: a value is text, never markup.
4. **An acronym was lower-cased.** `lender_lines` and the subject used `name[:1].lower()`, so a
   confirmed name "CDA desk review" became "Please provide the cDA desk review" and "cDA desk review
   request". **Fix:** `in_sentence` (the house helper, already imported).
5. **One-line-per-wording dropped a reason.** Keyed on the body alone, a second line with the same
   words but its own Why (another condition's reason) was dropped with it. **Fix:** keyed on (body, Why);
   7086's case (generic, no Why) still collapses, which the LF-DH8V test holds.
6. **The lender subject named nothing in the trial's own case.** The owner: "Its subject names the
   request." With generic items (a file with no lender, LF-DH8V) the subject was "RIVERA 1226500417 —
   1 request". Separately, the `codes` a merged line "carries" had no reader anywhere. **Fix:** one
   unnamed request names its condition by the lender's code ("— request on condition 1228"), read from
   the line's `codes`; a line with no code is still counted ("— 1 request"), and two lines are never
   named by condition. The LF-DH8V test now pins the full subject.
7. **Three claims of this file had no test** (mutations survived): TI-04's `{instruction}` masked
   (reverting `_values` to the raw verbatim text passed every test), and one-line-per-wording in
   `party_lines` and `lender_lines` (removing either passed). The guard also checked bodies only, never
   a subject. **Fix:** a TI-04 test, a parametrised party/lender dedupe test, and the guard now renders
   subject + body, with an account number in the lender item's name and request.

### Checked and not changed

- **Polish (`propose_polish` / `use_polish`)** sends the draft's body only, which is already masked; it
  cannot see the lender's unmasked text. What she types is hers.
- **Other email builders** (`services/email_draft`, `api/party_requests`) render needs, not condition
  text. A generic item has `documents: []`, so it never creates a need (`_needs_for_items` asks only items
  with documents): the placeholder cannot reach a needs email that way.
- **`render_lender` is the one path for every lender draft**: `render` dispatches on
  `DraftRecipient.LENDER`, which both LP-942's lender asks and the appraiser's asks routed through the
  lender reach; LF-DH8V's lender draft (an appraiser item) reads "Please order". "Becomes Waiting on
  Lender" is true for a request to the lender.
- **Not fixed, for the builder:** the draft dialog's side column and "Other drafts" summary still label
  a generic condition by its item's name, i.e. "What the lender asks for". In-app words, not an email,
  so outside the owner's "any email"; worth a line in a later batch. Also the lender's own internal notes
  ("**8/28 Not in Upload") now reach the borrower verbatim, as the owner's "the lender's own words" asks.
- The mortgagee clause is unmasked by design (the insurer must print it exactly).
