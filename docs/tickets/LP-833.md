# LP-833 — Compose a request by picking documents

- **Ticket:** LP-833 · Phase 4 follow-up, from processor feedback
- **Status:** Built — awaiting review
- **Date:** 2026-09-07
- **Scope:** a document picker, `services/email_draft.py`, `api/communications.py`, `tasks/email_draft.py`
- **Migration:** none expected

---

## What was asked

> *"There should be a way to create new draft, where user selects documents from our all document
> list, multi selection and click on generate email, AI should generate that draft for the processor
> on the spot."*

Today a draft can only come from a **finding**. A processor who knows they need a document that no
rule asked for has no way to request it by email — they can add a needs item by hand, and nothing
drafts from it.

## Measured before designing

**166 document types** in LP-800's catalog. A flat multi-select of 166 rows is a list nobody reads;
the picker has to be searchable and grouped, and it should lead with what this file already needs
rather than with the alphabet.

**The AI drafter exists and does less than "generate the email".** `compose_open_draft_prose` fills
three framing slots — opening, bridge, closing — around a deterministic render. It does not write the
document list, the address line or the security notice, and it must not: those are LP-817's template
and LP-824's constant, and a model rewriting them is how a compliance sentence quietly changes.

**It runs on a worker and is off everywhere.** `email_draft_enabled` defaults False and is set in no
environment, and `compose_draft_prose` is a Celery task. "On the spot" therefore needs two things
that do not exist: a synchronous path, and the flag on.

## What "AI generates it" can honestly mean

The draft is a template render with three model-written sentences in it. So:

* **selecting documents** produces the needs items and the draft deterministically — that part is
  LP-809's machinery and involves no model;
* **the framing** is what the model writes, synchronously, while the processor waits;
* **if the model is unavailable, refuses, or the flag is off**, the draft is still a complete email —
  `plain_framing()` carries v1's exact sentences. The processor gets a draft, not an error.

That last point is the design. A compose flow that fails when a model is down is worse than one that
quietly produces the plain version, and the processor can read the difference on screen.

## Done when

- A processor can open a picker, search and multi-select document types, and get a draft.
- The picker leads with **this file's outstanding needs**, then the rest of the catalog. 166 types
  alphabetically is a worse answer than the eight this file is actually waiting on.
- Selecting a type that is **not the borrower's to send** (LP-800's responsible party) says so at the
  point of selection, not after the draft is made. LP-826 built the after-the-fact answer; this is the
  before-the-fact one, and it is cheaper for everybody.
- The draft is produced **on the request**, not enqueued. A processor who clicked "Generate" and got
  a spinner that resolves later is watching an animation for work that may never finish.
- With the flag off or the model unavailable, a **complete plain draft** is produced and the screen
  says which it is. A test asserts the plain path produces a sendable email.
- The model writes the framing and nothing else. A test pins that the address line, the document
  list and the security notice are byte-identical to the deterministic render.
- Selected types become real needs items, so the reminder clock and the needs list see them.

## For the reviewer

Two things.

**The synchronous model call is in a request handler.** Everything else in this codebase puts model
work on a worker, and the reason is timeouts. This one is a processor waiting on purpose, which is a
different case — but it needs a bound, and a failure has to fall back rather than 500.

**The flag.** `email_draft_enabled` is off in every environment. If this ships behind it, "AI
generates the draft" is a feature nobody has, and the plain path is what a processor actually gets.
Either the flag is turned on somewhere, or the ticket's own headline is untrue — and that is a
decision, not an implementation detail.

## Built, 2026-09-09

### What shipped, said in terms of what a processor gets

**"Pick documents, get a draft."** That is the honest description, and it is deliberate rather than
modest. `email_draft_enabled` is `False` by default and set in **no environment**, so the model
writes nothing today: a processor gets LP-817's deterministic template, which is a complete email
rather than a degraded one.

A done-when clause written about model output would be green on a path nobody can reach. So the
clauses here are about the draft, and the model is exercised separately with the flag **on** —
because a behaviour nobody can reach is not a behaviour anybody tested.

**The screen says which kind of email it made.** `composed_by_model` travels back with the result and
the toast reads *"using the standard wording"* or *"with wording drafted for this file"*. A message
claiming the model wrote one it did not would be the untrue half of this feature's own headline —
and a toast hardcoded to either sentence is a mutation both ways, so both are pinned.

### Until this, a draft could only come from a finding

A processor who knew they needed a document no rule had flagged could add a needs item by hand, and
**nothing drafted from it**. That is the gap.

### The selection becomes real needs items

Not a list of strings on an email. Needs items are what the needs list shows, what LP-811a's send
moves to `REQUESTED`, and what starts LP-814's reminder clock — a draft listing documents that are
not needs would ask a borrower for things nothing is tracking.

**Origin is `MANUAL`**, because that is what it is: a processor decided. `FINDING` would claim a rule
asked for it and put false provenance on the correction signal LP-70 reads.

### 166 types, and the eight this file is waiting on

The picker leads with the file's **outstanding** needs, then the rest of the catalog — ordered, not
filtered, because the rest is what the dialog is for. Served from the same `/documents/types/catalog`
endpoint LP-638 built, so a type added to the catalog is selectable the same day.

**An unknown type is refused with a 422 and nothing is created.** LP-638 found this exact defect on
the correction control: two of eight hardcoded options were not catalog types, so choosing them set a
document to a string with no tier, no category and no extractor. A partial compose that took the
valid half would leave a processor with a draft they did not ask for and no error they could act on.

**Already-requested types are marked at selection**, not after. LP-826 built the after-the-fact
answer; saying it before a processor picks is cheaper for everybody, and asking twice for one
document is the mistake it prevents.

### The model call is in a request handler, and that is a decision

Everything else in this codebase puts model work on a worker, and the reason is timeouts. This one is
a processor waiting on purpose, which is a different case — and `compose` **never raises**: every
failure mode returns `None`, so a model that is slow, refused or switched off leaves the
deterministic draft standing. `test_a_model_failure_still_produces_a_draft` runs that path with the
flag on and a stubbed-unavailable model, because it is the only way to reach it.

### Mutations

| mutation | result |
|---|---|
| already-outstanding types not skipped | 1 failed |
| origin claims a rule asked (`FINDING`) | 1 failed |
| `composed_by_model` asserted rather than measured | 2 failed |
| the toast always claims the model wrote it | 1 failed |
| outstanding needs not surfaced first | 1 failed |

### The decision this ticket does not make

**Whether to turn `email_draft_enabled` on anywhere.** Until somebody does, "AI generates the draft"
is a feature nobody has. That is a product and cost decision, it is stated on the screen rather than
implied, and the plain path is complete without it.

### The three standing checks

**Tenancy:** the endpoint is `ScopedLoanFile`-gated; every need and the draft are created against
that file. **Logging:** nothing added. **AI:** perception only, and only for the framing — the
document list, the address line and the security notice are LP-817's template and LP-824's constant,
which no model rewrites.

## Review — REVIEWED

One finding fixed, one question answered with numbers rather than a change, and one hypothesis of
mine disproved by measuring it.

**Finding: the compose asked for "this file's newest open draft" while holding the draft it meant.**
`compose_request` creates a draft and then called `compose_open_draft_prose(db,
loan_file=loan_file)`, which resolves the newest. Those are the same row today only because nothing
runs between the two statements — a property of the current code rather than of the function. It is
the shape LP-832's review already found once in `remove_need_from_draft`: a function resolving "the
draft" while its caller holds the one it means. The row lock covers a concurrent request; it does
not cover a future caller inside the same transaction, which is exactly what the build flagged.
`draft` is a parameter now; `tasks.email_draft` keeps the lookup, which is the case the default is
for.

**The test for it was wrong first, and the mutation is what said so.** Asserting the OUTCOME — that
each request's framing lands on its own draft — passes either way, because the draft a request
creates *is* the newest at the moment it composes. It survived the mutant that drops the parameter.
The divergence cannot be produced from outside, so the honest assertion is about the wiring: the
caller hands over the row it means. That one fails under the mutant.

### Ask 1 — the timeout is a real bound, and it is bigger than "the AI client's own" implies

Measured rather than assumed, and the answer changed what I was going to do. There **is** a bound:
`complete()` applies `ai_request_timeout_seconds = 60.0` itself. But `config.py:169` states the
total plainly: *"the total ceiling for a call is this value x ai_max_retries plus backoff and
pacing"* — `ai_max_retries = 3`, so **roughly three minutes** in a synchronous request handler. No
`idle_timeout` is set on the ALB in any environment, so AWS's default 60s applies: a compose that
retries even once does not reach the processor, who sees a gateway error while the server finishes
and commits.

**I was going to wrap the call in `asyncio.wait_for` and the codebase says not to.** The same comment
continues: *"callers must NOT wrap it in a second `asyncio.wait_for` — an outer wrapper also bills
rate-limiter queueing time to the call, which at a low RPM makes pacing look like a provider
timeout."* That is a decision from LP-313/B1 with a stated reason, so the fix is not available and
the property is worth recording instead: with the flag on, a slow compose degrades to "wait, get an
error, refresh, the draft is there".

### Disproved by measuring it

I expected that gateway error to leave a duplicate: the server commits, the processor clicks again,
and LP-832 makes every request a new draft. It does not. Run twice with the same selection:

```
after click 1: open drafts=1  needs rows=2
after click 2: open drafts=1  needs rows=2
```

The `outstanding` skip means the second click creates no fresh needs, so `add_needs_to_draft`
returns the existing draft without minting. The repeat is idempotent and the degradation is
cosmetic. Recorded rather than dropped, because the reasoning was sound and only the measurement
settled it.

### The build's other asks

3. **422 with nothing created is right.** A partial compose leaves a processor holding a draft they
   did not ask for and no error they can act on.
4. **`MANUAL` is correct, and it does carry a second meaning worth knowing.**
   `needs_engine.py:664` guards `keeper.origin is not NeedsItemOrigin.MANUAL` so the engine never
   re-titles a manual need — *"correcting their words underneath them"*. A compose-created need is
   titled from `document_label`, so there are no words of a processor's to protect, and the effect
   is that its title will not follow a future catalog rename. Harmless, and better than `FINDING`
   claiming a rule asked.
5. **Ordering rather than filtering is right**, and the missing test is honestly described: that a
   166-row list is usable is a question for somebody watching a processor use it, not for a test.
