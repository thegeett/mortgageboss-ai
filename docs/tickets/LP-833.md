# LP-833 — Compose a request by picking documents

- **Ticket:** LP-833 · Phase 4 follow-up, from processor feedback
- **Status:** Specified — not started
- **Date:** 2026-09-07
- **Scope:** a document picker, `services/email_draft.py`, `api/communications.py`, `tasks/email_draft.py`
- **Migration:** none expected

---

## What was asked

> *"There should be a way to create new draft, where user selects documents from our all document
> list, multi selection and click on generate email, AI should generate that draft for the processor
> on the spot."*

Today a draft can only come from a **finding**. A processor who knows they need a document that no
rule asked for has no way to request it by email — they can add a needs item by hand, and nothing
drafts from it.

## Measured before designing

**166 document types** in LP-800's catalog. A flat multi-select of 166 rows is a list nobody reads;
the picker has to be searchable and grouped, and it should lead with what this file already needs
rather than with the alphabet.

**The AI drafter exists and does less than "generate the email".** `compose_open_draft_prose` fills
three framing slots — opening, bridge, closing — around a deterministic render. It does not write the
document list, the address line or the security notice, and it must not: those are LP-817's template
and LP-824's constant, and a model rewriting them is how a compliance sentence quietly changes.

**It runs on a worker and is off everywhere.** `email_draft_enabled` defaults False and is set in no
environment, and `compose_draft_prose` is a Celery task. "On the spot" therefore needs two things
that do not exist: a synchronous path, and the flag on.

## What "AI generates it" can honestly mean

The draft is a template render with three model-written sentences in it. So:

* **selecting documents** produces the needs items and the draft deterministically — that part is
  LP-809's machinery and involves no model;
* **the framing** is what the model writes, synchronously, while the processor waits;
* **if the model is unavailable, refuses, or the flag is off**, the draft is still a complete email —
  `plain_framing()` carries v1's exact sentences. The processor gets a draft, not an error.

That last point is the design. A compose flow that fails when a model is down is worse than one that
quietly produces the plain version, and the processor can read the difference on screen.

## Done when

- A processor can open a picker, search and multi-select document types, and get a draft.
- The picker leads with **this file's outstanding needs**, then the rest of the catalog. 166 types
  alphabetically is a worse answer than the eight this file is actually waiting on.
- Selecting a type that is **not the borrower's to send** (LP-800's responsible party) says so at the
  point of selection, not after the draft is made. LP-826 built the after-the-fact answer; this is the
  before-the-fact one, and it is cheaper for everybody.
- The draft is produced **on the request**, not enqueued. A processor who clicked "Generate" and got
  a spinner that resolves later is watching an animation for work that may never finish.
- With the flag off or the model unavailable, a **complete plain draft** is produced and the screen
  says which it is. A test asserts the plain path produces a sendable email.
- The model writes the framing and nothing else. A test pins that the address line, the document
  list and the security notice are byte-identical to the deterministic render.
- Selected types become real needs items, so the reminder clock and the needs list see them.

## For the reviewer

Two things.

**The synchronous model call is in a request handler.** Everything else in this codebase puts model
work on a worker, and the reason is timeouts. This one is a processor waiting on purpose, which is a
different case — but it needs a bound, and a failure has to fall back rather than 500.

**The flag.** `email_draft_enabled` is off in every environment. If this ships behind it, "AI
generates the draft" is a feature nobody has, and the plain path is what a processor actually gets.
Either the flag is turned on somewhere, or the ticket's own headline is untrue — and that is a
decision, not an implementation detail.
