# LP-852 — a draft nobody knows about

Status: spec. **Blocked by LP-850.** Screen 1.

Epic: [`docs/domain/communication/v1-epic.md`](../domain/communication/v1-epic.md) · Screens: [`v1-screens.md`](../domain/communication/v1-screens.md) · Spec: [`comm-v1-draft-only-spec.md`](../domain/communication/comm-v1-draft-only-spec.md)

## The report

> "you are displaying draft and Not from the borrower-2, but in some instance Not from the borrower
> go bottom of the list and processor may not realize that draft has been created for non borrower.
> instead what if we make single list, containing some indication of new draft added recently. no
> bucket. Just user see the list with indication borrower non borrower."

And, on the request flow:

> "Always name the party draft."

## The failure this closes

A message the system wrote, addressed to somebody the processor did not expect, **sitting where they
will not look.** Two shapes of the same bug:

1. **The buckets.** Party tabs, or party group headings, put a title-company draft below the fold. A
   heading is a region that can be scrolled past. The processor never learns it exists, never sends
   it, and the title company is never asked.
2. **The toast.** `"Draft prepared"` — which draft, to whom? LP-835 already fixed one version of
   this: the panel used to say *"Send it from the document request above"*, and the draft above was
   the borrower's, so a processor following that instruction emailed the wrong person.

## Decisions

**1. The party is a column on every row, never a heading.**

One list, in one time order, with `Borrower` / `Title co.` / `Lender` in a fixed-width column on the
left of each row. A column cannot be scrolled past. This is the single change that closes shape 1.

**2. Every toast names the party and the count.**

`"Draft to the title company — 1 document"`, `"Draft to the borrower — 3 documents"`. Never
`"Draft prepared"`. The party is the part a processor cannot infer.

**3. The row says what is inside without being opened.**

Count *and* the first few document names. Four rows reading *"A document request is being
prepared"* is the screenshot that started this.

**4. A "since you last looked" dot, not an unread badge.**

Nothing is received in this version, so "unread" would be a claim about somebody else's behaviour.
The dot marks drafts created since this processor last opened the page, and clears on open.

**5. Status is a word and a colour, never a colour alone** — and the word is attributed.
`Draft` · `Sent by Priya · Mon 16:41`. Not `Sent`.

## What it must not break

- LP-831's list-leads layout and the modal it opens.
- LP-843's `party` column, which is where the column's value comes from — this ticket adds no new
  source of truth for who a draft is to.

## Acceptance

1. A title-company draft is visible **without scrolling past a heading** on a file with ten drafts.
2. Every creation path's toast names a party. Grep for `"Draft prepared"` returns nothing.
3. The dot appears on a draft created by another session and clears when the row is opened.
4. A screen reader reads the party before the subject on every row.

# What was built

Status: **done**.

## The shape

**Backend** — `TimelineEntry` gains four fields, each loaded once for the whole list rather than
once per row: `documents` (what the draft asks for), `actor_name` (who claimed the send),
`body_edited` (LP-853's `body_format`), and `created_at` — which is **not** `at`. `at` is
`sent_at or created_at` so the list orders by when the borrower heard from us; the dot is about when
the draft came into existence, and for a sent message those are different days.

**The party tab strip is gone.** In its place, `PartyCell` on every row: fixed 5.6rem, uppercase,
petrol for the borrower and muted for everybody else — which is what makes a title-company row catch
the eye in a column of borrower rows. A row with no party still gets a cell (`—`), or its subject
would slide into the party column and break the alignment the column exists for.

**The status pills stay.** They answer "what happened to it", which is a different question and one
a processor asks deliberately. What went is the axis that could *hide* a row.

## Acceptance 2 is written as a grep, and a grep is the weaker half

The reviewer's warning on this ticket was exact: *"'Draft prepared' grepping to nothing is a claim a
grep can verify but a SCREEN cannot."* Two things follow.

First, the plain grep the ticket asks for now matches the **comments that explain the removal**, so
taken literally the criterion fails forever for the wrong reason. The scan in
`draft-toast-title.test.ts` strips comments and matches string literals in product code only, with a
planted case proving the matcher matches.

Second, and more to the point, the replacement is asserted **where a processor reads it** — the
title actually handed to `notifySuccess`, per dialog. A grep cannot tell the difference between
"replaced with something that names the party" and "deleted".

## What the toasts say now

`draftToastTitle` and `requestToastTitle` live beside `requestConsequence` and share its
`PARTY_NOUN`, so one toast cannot call them "the title company" while the next says "Title co.".
Several parties are **joined, not summarised**: `"2 drafts prepared"` is `"Draft prepared"` with a
number on it and still does not say who. Nothing added says `"Nothing new to request"` rather than
claiming a draft that was not made — LP-826's review found exactly that in the consequence.

`POST /outbound/compose` returns `drafts: [{party, needs_added}]` because the toast needs a party and
`needs_added` alone could not name one.

## The dot, and what it honestly is

`localStorage`, per browser, which is **less than "per processor"** and is written down as such. A
server-side per-user timestamp is the real thing and is a schema change; this is right for the common
case — one person, one machine — and degrades to *nothing is new* on a second machine rather than to
a wrong claim. It is a dot rather than a count for that reason.

No stored timestamp means **nothing** is new. Ten dots on a first visit is true, useless, and it
teaches a processor that the dot means nothing.

**This project's jsdom provides `window.localStorage` as an object with no methods** — `getItem`
throws `TypeError`. That is why every access in `last-seen.ts` is guarded, and it means the other
tests in the suite exercise the unavailable path for free. The stub is installed in one describe
block rather than in `vitest.setup.ts`, deliberately: a global shim would quietly remove a condition
the product has to survive.

## Measured

- Communication route: **200 kB** first-load, from 199 kB at LP-851.
- Backend 7692 passed; frontend 1661 passed, run three times.

**One flake seen and not reproduced.** `lib/api/draft-broadcast.test.ts::a client from
makeQueryClient refreshes on another tab's announcement` failed once in a full run and passed alone
and in three subsequent full runs. It opens two real `BroadcastChannel`s on one name and does an
`await import()`, which is timing-sensitive under load. Nothing in this ticket touches broadcast or
the query client. Recorded rather than left out, because a flake nobody wrote down is a flake
somebody else re-investigates.

## What was not done

- **Screen 1's header buttons.** `Compose` is LP-856 and removing "Write to another party" is
  LP-857. This ticket is Screen 1's *list*.
- **The three-column CSS grid.** The row is a flex layout with a fixed-width party cell, which
  produces the same alignment. Appendix A specifies `auto 1fr auto`; the existing row already had a
  working flex structure carrying the reply box, the attachment manifest and the per-row actions, and
  converting it to a grid would have rewritten all of that to no visible effect.
- **A real second session.** Acceptance 3 says "created by another session"; the test approximates
  it with a stored timestamp older than the draft, which is what that condition looks like from this
  browser. A genuine two-session test would need the server-side timestamp this deliberately does
  not have.

# Review (second session)

Reviewed at `82c85bbe`. Findings measured; fixes mutation-checked.

## Fixed

**`statusLine` called a queued message a draft.** `draft` and `queued` shared a branch, so the one
thing that produces a queued row — `auto_reply.record_auto_reply`, an automated nudge carrying an
upload link — would have rendered as `Draft · 2 hours ago` under the compose pen: a message nobody
wrote, nobody can edit and nobody needs to act on, filed under the one word on this screen that
means "you still have to do something with this".

This is the answer to "is the fall-through swallowing a status the backend emits?" — it was not
swallowing `queued`, it was actively mislabelling it, which is worse. Before LP-852 the fall-through
said "Created": vague and true. Grouping it with `draft` made it specific and false.

**Reachability, stated precisely.** `record_auto_reply` has no caller, so nothing creates a queued
row today — the nudge is one of the things this epic's fence defers to the next phase, which is also
when it returns and this becomes live with nothing to catch it. Whether historical rows carry the
status is **unverified**: the staging SSO session was expired at review time and re-authenticating
was not mine to do. `queued` and `draft` are separate in both `statusLine` and `EntryIcon` now.

**`draft-broadcast.test.ts` was genuinely flaky, and the cause is in the helper.** Reproduced here —
failed in one full run, passed alone and in the three runs after — which makes it a second
observation rather than a mystery. `delivered()` was a single `setTimeout(…, 0)`, which assumes a
BroadcastChannel message arrives within exactly the NEXT macrotask; under a full parallel run it
sometimes does not, and the assertion then reads the state before delivery and reports the feature
broken. One test in the file had already grown a second `await delivered()`, which is the same fix
applied one tick at a time. Positive assertions wait for the CONDITION now, bounded; the negative
ones wait five tasks rather than one, so "nothing arrived" means it had a fair chance to. Three
consecutive full runs clean. **Out of this ticket** — nothing in LP-852 touches broadcast — but a
flake undermines every count this epic reports, so it is fixed rather than recorded.

## Checked and correct

- **`statusLine` is exhaustive over its producers.** All six `CommunicationStatus` values traced to
  what writes them: `draft`, `sent`, `failed` and `received` are produced and render correctly
  (`failed` and `received` fall through to LP-838's label, which handles both); `queued` is the one
  above; **`delivered` has no producer anywhere in `app/`**, which matches the epic putting it in
  the next phase.
- **`at` and `created_at` are the right way round.** `at` is `sent_at or created_at` — the event
  time — which is what a status line should show; `created_at` is composition time, which is what
  "appeared since you last looked" means. For a draft the two are equal anyway, so the dot's choice
  is only exercised where it is also correct.
- **The dot is honest enough to ship.** Per-browser is weaker than per-processor and is written down
  as such, and every failure mode points the safe way: a second machine says "nothing is new"
  instead of making a false claim, no stored value means nothing is new rather than everything, and
  `localStorage` is guarded at every access. `lastSeen` is read once into state on mount and the
  clock advanced immediately, so the dots describe this visit rather than clearing on the next
  keystroke. A dot rather than a count is the right weight for it.
- **The four new fields render nowhere they are meaningless.** `documents` is behind a
  `length > 0` guard, and `actor_name` is only read in the `sent`/`delivered` branch, which an
  inbound row cannot reach.
- **Both deliberate shortfalls are the right calls.** Flex with a fixed party cell reaches Appendix
  A's alignment without rewriting the reply box, the manifest and the per-row actions to no visible
  effect; and a stored timestamp older than the draft is exactly what "created by another session"
  looks like from this browser.
- **Acceptance 2 is asserted where a processor reads it**, not only by a grep — the title handed to
  `notifySuccess` is checked per dialog, which is what a scan cannot distinguish from a deletion.
