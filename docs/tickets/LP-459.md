# LP-459 — Prompt-divergence survey

Read-only survey. For each of the 109 document types: regenerate the prompt **in memory** (`emit_prompt`,
no model calls, never written over a shipped file), diff against the shipped
`app/ai/prompts/extraction/<type>.txt`, and classify. The goal LP-458 set: find spec fields the shipped
prompt never asks for — the "declared, plumbed, permanently null" shape.

## Headline

**No live rule is failing silently.** The apparent silent field gaps are **spec-vs-shipped naming
divergence**, not null fields — the concept is captured under a *different* name that the extractor,
snapshot, and rule all use. The real, systemic finding is that finding itself: **the specs and the
hand-maintained prompts are two different naming systems** (LP-446 re-normalized the specs; the shipped
prompts kept the original names), and **89 of 109 prompts are the untouched LP-434 "STARTER — REPLACE
WITH…" placeholder.**

## 2. ⚠️ The "silent field gap" table — and why it is NOT a silent gap

The primary deliverable was "spec fields the prompt never asks for." 62 such fields exist across 14 types
(all HAND-MAINTAINED + the 1099 mismatch). **But every one is a naming divergence** — the shipped prompt
asks for the same concept under a different name (§3 is the mirror image). Examples:

| type | spec name (not in prompt) | shipped prompt asks (§3) | same concept? |
|---|---|---|---|
| voe | `employment_start_date`, `present_position`, `current_gross_base_pay`, `average_hours_per_week` | `start_date`, `position_title`, `current_income_amount`, `hours` | ✅ yes |
| homeowners_insurance | `insured_property_address`, `dwelling_coverage_a`, `insurance_carrier` | `property_address`, `coverage_amount`, `carrier_name` | ✅ yes |
| retirement_account | `plan_type`, `plan_or_account_number_masked`, `plan_or_custodian_name` | `account_type`, `account_number_masked`, `institution_name` | ✅ yes |
| drivers_license | `full_name_raw`, `license_or_id_number_masked`, `residential_address`, `issuing_jurisdiction` | `full_name`, `id_number_masked`, `address`, `issuing_state` | ✅ yes |
| bank_statement | `institution_name`, `declared_page_count` | `bank_name`, `page_count_declared` | ✅ yes |
| profit_and_loss | `net_income_or_loss`, `total_operating_expenses`, `business_legal_name` | `net_profit`, `total_expenses`, `business_name` | ✅ yes |

**Live-rule cross-reference (verified individually):** 6 types had a silent-gap field whose spec `rules`
include an ACTIVE rule — `voe` (IN-4, IN-7), `drivers_license` (ID-1), `profit_and_loss` (IN-12),
`homeowners_insurance` (IH-1), `retirement_account` (AS-11), `bank_statement` (AS-8/9/10). In **every
case** the concept is asked under the shipped name (grep-confirmed: `property_address`, `coverage_amount`,
`bank_name`, `net profit`, `position`/`title`, `page` are all present in the prompts), and the rule reads
the **shipped/snapshot** name — so **the rule works today.** There is **no confirmed silent-null under a
live rule.** The alarm was the naming divergence, not a coverage gap.

## 5. `1099` — a `document_type`↔filename mismatch, not missing

The spec's `document_type` is `1099`; the shipped prompt is `form_1099.txt`. My survey saw `1099.txt`
absent (→ MISSING) and `form_1099.txt` with no spec (→ orphan). It's **one** naming mismatch, not a
missing prompt. Worth reconciling (the extractor registration name is the source of truth) so a future
spec-driven step doesn't generate a second `1099.txt`.

## 6. Bare-starter exposure

**89 of 109 types run on the untouched LP-434 starter prompt** — whose own header reads *"GENERATED
STARTER PROMPT (LP-434) — REPLACE WITH / MERGE INTO THE TUNED … accuracy is UNVALIDATED."* These have zero
spec-vs-prompt divergence (prompt == spec, by construction), so a spec edit + regenerate is faithful — but
they have never been tuned against real documents. Sizing each against the 889-doc bench corpus is a
worthwhile follow-up (the per-type classification counts live in `comparison-output/_INDEX*.csv`); the
count that matters now is **89/109 are placeholders.**

## ⚠️ Practical guidance for Phases 2 & 3 (the map)

| you are touching… | does a spec edit reach the prompt? | what to do |
|---|---|---|
| a **GENERATED** type (89) | No (generator is diff-mode; LP-458) — but the prompt uses the SPEC names | edit the `.txt` directly; spec names already match, so add the field under the spec name |
| a **HAND-MAINTAINED** type (19) | No, **and** the prompt uses DIFFERENT (original) names | edit the `.txt` directly, and **use the shipped/snapshot field name, not the spec name** — check §3 for the type's real names, and confirm the rule reads that name |
| `1099` | reconcile the `document_type`/filename first | — |

**In all cases a spec-only edit reaches no shipped prompt** (LP-458). A new field will silently return
null unless the `.txt` is edited to ask for it **under the name the extractor/snapshot/rule use.**

## ADR — systemic spec↔shipped naming drift

LP-446 re-normalized the specs (canonical field names, +232 fields). The 19 hand-maintained shipped
prompts predate that normalization and kept the **original** names; the 89 generated prompts are
`emit_prompt(spec)` and match the spec names. So there are **two naming systems**, and the spec is **not a
reliable description of what a hand-maintained extractor actually produces.**

The LP-446 dividend is **not inert** — the concepts are captured (under the original names) and the live
rules read those names, which is why the survey found **no** live-rule silent failure. But the spec is an
unreliable map for the 19 hand-maintained types: a Phase 2/3 change driven off the spec name would add a
field the extractor/rule never sees. **For those types, the shipped prompt + snapshot names are the
source of truth, not the spec.** Reconciling the two (or regenerating the 89 starters into tuned prompts)
is the larger cleanup this survey recommends — reported, not done.
