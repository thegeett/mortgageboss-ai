# LP-965 — No code map: every condition is typed by a fresh AI reading

- **Ticket:** LP-965 (the owner, 2026-10-07). **ADR-419.**
- **Source:** the owner: "I want to remove the concept of saving condition code per lender and remember
  what processor select. I want each time fresh AI resolution come at least for this version." The plan
  (AI-chosen type, table left in place, admin screen removed, long rounds in batches) was agreed before the
  build.

## Why

A condition got its library type only from its lender's shipped code map (`uwm.yaml`,
`champions.yaml`, seeded into `lender_condition_codes`), at import or when the file's lender was set.
The processor's "This is right" was saved per (lender, code) and reused on the next file without asking
the AI.

On LF-Y36E locally, the file had no lender and the local UWM lender had no key, so 1228 was never looked
up. The reading guessed, and the confirm screen said "the library has no type for this condition" although
PA-03 exists.

## The change

**The reading chooses the type** (`condition_reading.py`, prompt `read_v4`).
- Every condition goes to the model with the whole library, including each type's items (56 types, 52
  items).
- The model returns `library_type` and that type's items by key, or splits the condition itself when no
  type fits.
- `chosen_type` keeps only a real id. `read_round` writes it to `canonical_type_id`, and clears it when
  there is none, so no earlier type survives a fresh reading.
- Everything downstream of the type is unchanged: routes, `waits_on`, evidence matching, drafts and the
  package.

**Batches of eight.** `_BATCH_SIZE = 8` conditions per call. A failed batch sends only its own conditions
to the fallback. LP-962 had found one 21-condition call overrunning the 8,192-token answer, which sent
**every** condition to the fallback. Tokens and cost are summed across batches.

**The owner comes from the reading** (`OwnerHintSource.READING`, migration `0915cdf12565`). The code map
also filled `owner_hint`, which the list's Owner filter, owner grouping and the summary's owner counts read.
Without a replacement, nine of round 1's eleven conditions came back `unknown`.
- Where the sheet named nobody, the reading sets the owner: the lender if the lender does the work,
  else whoever the **first** item names.
- Performer to owner: borrower → borrower, title or attorney → title, insurance → insurance, lender →
  lender, LO → broker, processor → processor. Appraiser, HOA, employer and other party give none.
- The lender's own marker (`prefix`, `bucket`) and her choice (`manual`) are never replaced.
- The downgrade turns `reading` hints back to `unknown`/`none`.

**Nothing per lender code:**
- **Import** (`condition_import.py`) no longer applies a map's type, owner hint or info-only flag, and no
  longer records codes. `unmapped_codes` is gone from the import result, the API response and the frontend
  type.
- **Setting the file's lender** (`condition_lender.py`) types nothing. It moves the file's rounds and
  **all** live conditions to the lender. Before, only untyped conditions moved, because a typed one owed its
  type to its old lender's map.
- **The banner** no longer reports `has_code_map`; it shows only while the file has no lender.
- **"This is right"** confirms this condition only. The event detail no longer carries `saved_for_code`,
  and the dialog no longer says "Your answer is saved for this lender code".
- **The UWM reader** takes no owner hint from `uwm.yaml`. The unused `code` parameter is removed.
- **Removed outright:**
  - the admin "Lender codes to review" table;
  - `GET /lenders/{id}/codes-to-review`, `PUT /lenders/{id}/codes/{code}` and `GET /lenders/library-types`,
    with their schemas and hooks;
  - `lender_settings.codes_to_review` and `map_code`;
  - `condition_lender.record_proposals`, `type_conditions_for_code` and `_has_code_map`;
  - `app/scripts/seed_lender_codes.py`, and `lender_codes/status.py` with its test (only the seed used it).

**Kept:**
- the YAML files, for lender detection and the library review table;
- the `lender_condition_codes` table and its columns, unread and unwritten, so this is reversible without
  a migration;
- the `code_map` value in `OwnerHintSource`, because existing rows carry it;
- `condition.lender_code`, for display and for matching a condition across rounds by (lender, code).

## What changes for the processor

- **Typing is the model's now.** LP-962 measured it at 16 of 21 matching the map on the synthetic UWM sheet,
  with 4 untyped and 1 wrong. An untyped condition gets generic items and loses library features; the
  confirm flags and the plan are the checks.
- **With the AI off (or failing for a batch), nothing is typed.** No library items, and no figure only a
  type computes (7086's shortfall). Every reading in that batch asks her to confirm. Before, the code map
  still typed them.
- **0132's owner is now the borrower**, the first performer of its first item (re-signing the
  disclosure), where the code map said broker. So "Waiting on borrower" in round 1 is four conditions, not
  three. Choosing the first item's first performer is a simple rule; whether it is the right owner is a
  domain question for the expert.
- **Each reading sends the library** (a few thousand input tokens per batch).

## Review (of `ab5c940f`)

**Three findings, all fixed here. The deletion is clean and the batching is well pinned, but the two
mechanisms that replaced the code map — the reading's type and the reading's owner — each had a gap the
code map had been hiding: a hand-added condition is never read at all, and the owner rule drops a relay
the rest of the system applies. Two of the four guards you asked me to mutate survived.**

### Finding 1 — a condition added by hand is never typed

`create_manual_condition` says: *"NOTHING IS LOOKED UP BY ITS CODE (LP-965, ADR-419). **Its reading types
it, fresh, like any other.**"* Nothing delivered the second sentence. The code map used to type such a
condition as it was created; after this ticket a type comes only from a reading, and no door asked for
one — `add_condition_by_hand` commits and returns. So a hand-added condition kept **no library type at
all**: no library items, no checks, no LP-955 route, no type question, and `build_plan` fell to its
generic path. It stayed that way until some unrelated door (a lender change, "Read again") happened to
queue a reading.

**Fixed** in the route, after the commit: `await queue_unread_reading(db, loan_file_id=...)`, the same
helper the lender door uses. It reads only what nobody has read, so it types the new row and touches no
other, and `read_round` already reads every unread condition on the round's FILE rather than a sheet.
`test_adding_a_condition_by_hand_asks_for_a_reading` pins it through the route, with the broker pinned
because `queue_round_reading` marks the round FAILED ("not_queued") when the task cannot be sent, which
would have hidden the property. Removing the call fails exactly that test.

**A premise of mine that the test falsified, recorded because it nearly shipped.** I first fixed a second
half too: `unread_round_to_read` names an `IMPORTED` round only, and `_manual_round` does not set
`status`, whose model default is `parsing` — so on a file that never imported a sheet, I reasoned, no
round could ever be chosen. I wrote the test to assert that premise and it **failed**: the manual round's
status is `IMPORTED`, because `_manual_round` takes a number through `_assign_round_number`, which sets it
(`condition_import.py:540`). So `unread_round_to_read` finds it, that half was unnecessary, and I reverted
it. Reading the default and stopping there would have shipped a change on a false claim with a confident
paragraph attached.

### Finding 2 — the reading's owner drops the LO relay, which is why 0132 moved

You flagged 0132 changing from `broker` to `borrower` as a domain call. It is not a judgement about 0132:
it is a rule that exists elsewhere in this system being dropped in the new one.

`owner_from_reading` returns the first performer of the first item. 0132's first item names the borrower
**and** the LO, so it returns `borrower`. But everything else treats that pair as the LO's:
`condition_plan.recipient_for` is explicit — `if Performer.LO in performers: return _RECIPIENT[LO]`,
because "the LO relays to the borrower (0132's disclosure goes out in the LO email)" — and `WAITING_ON[LO]`
is `BROKER`, so once that email is marked sent the condition reads **"Waiting on LO"**. The Owner column
therefore said Borrower about a condition whose ask goes to the LO and which will wait on the LO. Two
server-derived facts about one condition disagreed, and `_PERFORMER_TO_OWNER` already maps `LO → BROKER`,
so only the precedence was missing. The retired code map's answer here was the one that matched.

**Fixed:** `owner_from_reading` applies the same relay — the LO among an item's performers wins over the
first named — with a comment naming `recipient_for` as the rule it mirrors and why it is mirrored rather
than imported (that one takes an item row, this takes the reading's dict).

**Two of your test updates revert, which is the part worth checking rather than accepting.**
`test_open_and_waiting_on_borrower_returns_exactly_the_four_borrower_conditions` is renamed back to
`..._the_three_asset_conditions`, and `by_owner["borrower"]` back to 3 — both with the reasoning in place,
and the first gains the half that makes it a relay rather than a drop: **0132 now appears under
`owner=broker`**, asserted, not merely absent from the borrower's list. Removing the relay fails both.

### Finding 3 — two of the four guards you asked about were unpinned, and both are comment-only claims

Measured, each mutation applied to a clean copy and the file restored byte-identical afterwards:

```
M1 chosen_type ignores the model's choice          -> 5 failed    (well pinned)
M2 _REPLACEABLE_SOURCES = frozenset(OwnerHintSource) -> 30 passed  SURVIVED
M3a _BATCH_SIZE = 100 (one call per round)         -> 2 failed    (pinned)
M3b _BATCH_SIZE = 1   (one call per condition)     -> 2 failed    (pinned)
M4 a stale canonical_type_id is left, not cleared  -> 30 passed  SURVIVED
```

- **M2.** `_REPLACEABLE_SOURCES`'s comment says "the lender's own marker (prefix, heading) and her choice
  (manual) are never replaced". Widening it to every source — so a reading overwrites her `manual` owner —
  passed every test. The code is right; nothing held it there. Her choice outranking every inference is
  ADR A2 (LP-912), the reason the hint and her override are separate fields at all, so a reading quietly
  rewriting it would undo that design rather than a detail.
  `test_a_reading_never_overwrites_her_owner_or_the_lenders_own_marker` pins `manual` and `prefix`, with a
  positive control that the reading DOES fill a hint where the sheet named nobody — so the two assertions
  cannot pass because the mechanism never ran.
- **M4.** `test_a_fresh_reading_replaces_an_earlier_type` pins type → type. Nothing pinned type → **none**,
  which is the direction a stale value survives in, and it is reachable through "Read again" (LP-952) on a
  condition an earlier reading typed. A stale type is worse than no type: it brings library items, checks
  and an LP-955 route the current reading does not support.
  `test_a_reading_that_chooses_no_type_clears_an_earlier_one` is the missing half, and asserts the model
  was actually asked so the clearing is an answer rather than a no-op.

Each new test fails its own mutation and nothing else.

### Checked and not findings

- **Moving EVERY condition on a lender change is right, and removes a latent break rather than causing
  one** (your focus area 3). `possible_match` requires `condition.lender_id is None or lender_id is None
  or condition.lender_id == lender_id`, and `on_file_lender_changed` moves the file's **rounds and live
  conditions together**, so the next imported round takes the same lender and both passes still match. The
  old behaviour — moving only the untyped — would have left a typed condition on the PREVIOUS lender,
  where "two different known lenders do not match" would have stopped it ever matching a new round. The
  module docstring already states this reason.
- **Nothing reads the retired fields** (your focus area 5). `saved_for_code` is gone from the tree
  entirely; `proposed_type_id` survives only as a column on `lender_condition_code`, the table you kept
  deliberately, with no reader in `app/`, `tests/`, or the frontend.
- **One genuinely stale doc, now fixed** (your focus area 4). `api/conditions.py`'s lender route said
  *"Untyped conditions take its code map; unread ones are read. A key her company has no lender for adds
  that lender, with its shipped code map"* — the typing half of which ADR-419 removed, while
  `set_file_lender`'s own docstring two files away already described the new behaviour correctly. A reader
  believes the route. Corrected in this commit. Everything else my grep flagged is accurate in context:
  `condition_lender.py`'s module docstring reads as stale line-by-line and is correct as a paragraph — its
  "used to" sits on the line above the clause my filter matched, which is a false positive of my own
  method rather than a defect of yours.
- **`chosen_type` is strict in both directions** and already tested for it
  (`test_only_a_real_library_type_is_taken`: a real id, an unreal one, `None`, and no payload at all).
- **The whole library, with items, goes to the model**, and `_BATCH_SIZE` is pinned from both sides — one
  call per round and one call per condition each fail two tests.
- **`lender_condition_codes` stays unwritten**, asserted end to end by
  `test_nothing_is_remembered_per_lender_code` across import, the lender door and the reading.
- **A stray untracked file appeared mid-review** (`app/ai/extraction/generated_sample_doc.py`) and was
  gone by the time I looked: `tests/ai/generator/test_generator.py` writes it into the source tree during
  a run. Not yours and not this ticket's, but worth knowing in a worktree three sessions share, since it
  shows up in `git status` as something unexplained.
