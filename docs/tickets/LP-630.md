# LP-630 — take staging off the clock overnight, and stop paying for a cache twice the size it needs

**Status: Phases A and D BUILT, not yet applied. Phases B and C unstarted.**

Phase D was pulled ahead of C deliberately: a manual `down`/`up` is the thing that
makes the schedule safe to automate, and it is what proves the sequencing before a
cron does it unattended at 22:00.

| Phase | What | State |
|---|---|---|
| A | `ignore_changes = [desired_count]` on all three services | **APPLIED** to staging 2026-08-25. `0 to add, 0 to change, 0 to destroy` plus two new outputs — a lifecycle block is state-only, so it changed no infrastructure |
| D | `./scripts/deploy <env> down` / `up`, plus guards on `deploy` and `migrate` | built |
| B | `redis_node_type = "cache.t4g.micro"` | unstarted |
| C | EventBridge Scheduler | unstarted — unblocked: timezone is `America/New_York` |

Also added, because `up`/`down` and Phase C's IAM scoping all need it: an
`rds_instance_identifier` and `rds_instance_arn` output on the data module and on
both environments. `down` falls back to the first label of `rds_address` when the
output is not in state yet, which is not a guess — an RDS endpoint hostname is
`<identifier>.<hash>.<region>.rds.amazonaws.com`.

`stage_status` now reports the RDS instance status and says `SHUT DOWN -- desired 0`
rather than `0/0 running`, so a deliberately-off environment does not read as a
broken one.

## The report

Staging runs 24 hours a day and nobody touches it between roughly 22:00 and 09:00. It costs
**~$161/month in fixed infrastructure** — before Bedrock, S3, ECR, KMS, CloudWatch or data
transfer — against a `budget_limit_usd = 300` alarm. Roughly 60% of those hours buy nothing.

Two changes recover **~$60/month (~$721/year), a 37% cut**, and neither of them risks data:

1. Scale the three ECS services to zero and stop RDS overnight and at weekends.
2. Halve the ElastiCache node, permanently, in one tfvars line.

A third change — recreating ElastiCache on the same schedule — is deliberately **out of scope**,
for reasons recorded below so nobody re-derives them.

## What can actually be stopped

**Clean stop, single AWS API call, no credential coupling:**

- **ECS services** — `ecs:UpdateService` with `DesiredCount: 0`. Instantaneous and fully
  reversible. Fargate bills per second of task runtime, so a task that is not running costs
  nothing.
- **RDS** — `rds:StopDBInstance`. Instance hours stop; provisioned storage and backup storage
  keep billing, which is why the $5.75 storage line stays in the floor.

**No stop API exists:**

- **ElastiCache** — there is no stop or pause operation on a replication group, only delete.
  See "Why ElastiCache is out of scope".

**Must stay up:**

- **ALB** — deleting and recreating it churns the ACM association, the Cognito authenticate
  action and the Route 53 alias. Not worth $16.43.
- **VPC interface endpoints** — the largest line item after Fargate, and only needed while
  tasks run, but a var-driven toggle is blocked: `infra/modules/network/main.tf:52` has a
  precondition that fails when `enable_nat_gateway` and `enable_vpc_endpoints` are both false,
  so `enable_vpc_endpoints = false` would break `terraform plan` outright. Tearing them down
  out of band creates drift the next apply would reverse. Left alone for now; noted as the
  next thing to look at if the floor needs to go below ~$101.

## The decision

**Schedule: down 22:00, up 09:00, every night, and stay down over the weekend
(Fri 22:00 → Mon 09:00).** That is 447.6 stoppable hours per month, 61.3% of the total.

| | Saved/month | Bill after |
|---|---|---|
| Nightly only, 7 nights (334.6 h off) | 36.22 | 124.84 |
| **Nightly + weekends (447.6 h off)** | **48.45** | 112.61 |
| **ElastiCache `small` → `micro`, always on** | **11.68** | — |
| **Both** | **60.13** | **100.93** |

The $48.45 is Fargate $34.13 + RDS instance hours $14.32.

Weekends are worth $11.42/month on their own — more than moving the stop time two hours
earlier would buy (~$6). The weekend is the cheap half of this change.

The remaining ~$101 floor: VPC endpoints $36.50, ALB $16.43, Fargate for 282.4 running hours
$21.53, RDS $14.79 including storage, ElastiCache micro $11.68.

## Why ElastiCache is out of scope

**Not because of data loss.** Redis holds nothing durable — see the next section. Deleting it
loses a queue, some expiring results and an auto-expiring lock. In staging that is genuinely
free.

It is out of scope because **recreating it breaks the environment every morning, and the
repair is a human procedure by design.**

`infra/modules/data/main.tf:230-247` deliberately does not manage the AUTH token:

```hcl
lifecycle { ignore_changes = [auth_token, auth_token_update_strategy] }
```

The token is applied out of band and hand-written into the `redis-url` secret. A recreated
replication group therefore comes up with **no token**, while Secrets Manager still holds
`rediss://:OLD_TOKEN@...`. Every API and worker container fails on connect. This is certain,
not a risk.

And the repair cannot be automated as it stands. `scripts/deploy:862-930` generates a token,
submits `modify-replication-group --auth-token-update-strategy ROTATE --apply-immediately`,
then polls for minutes until `Status=available AND AuthTokenEnabled=true`, and refuses to write
the URL if it cannot verify the result — the failure path warns that a timeout can leave "a
token nobody knows." On top of that, `REDIS_URL` reaches containers as an ECS task secret
(`infra/modules/compute/main.tf:72-75`, `valueFrom`), which ECS resolves **at task start**, so
the secret must be correct *before* the 09:00 ECS scale-up, not after.

The morning critical path would be: create an encrypted replication group (10–15 min) → apply
and verify a token (minutes) → rewrite the secret → only then start ECS. Roughly 25 minutes of
unattended, verification-gated steps, plus a Terraform destroy/create needing state-lock access
in a cron, plus a primary endpoint hostname that is assigned at creation and may not survive
the round trip.

**The payoff for all of that is $7.16/month** once the node is already a `micro`. Downsizing
captures $11.68 of the same $23.36 for one line and no risk. Scheduling the remainder is not a
trade worth making.

## What Redis is actually for

Recorded here so this does not have to be re-derived. Only four backend files touch it —
`app/main.py`, `app/core/config.py`, `app/core/redis.py`, `app/services/needs_engine.py`.

1. **Celery message broker** (`app/tasks/celery_app.py:34`) — the queue between the API and the
   worker. Without it, uploads reach S3 and Postgres and are never classified, extracted or
   verified. This is the load-bearing use.
2. **Celery result backend** (`celery_app.py:35`, with `task_track_started=True`) — task state
   and return values.
3. **Cross-process lock** (`app/services/needs_engine.py:970-993`) — `needs-lock:{loan_file_id}`
   with a `timeout` so a crashed worker cannot deadlock a file. Held at `app/tasks/needs.py:70`
   and `:83` and `app/services/verification_run.py:815`.
4. **Health-check dependency** (`app/main.py:169-215`) — `/health` and `/health/ready` both AND
   in `check_redis_connection()`. No Redis means the API reports not-ready, the ALB target group
   pulls it out of rotation, and the deployment circuit breaker can roll a deploy back. Redis
   going away does not merely pause background work; it takes the API offline.

Despite the service name, **nothing is cached**. No response cache, no session store (Cognito
owns auth), no rate-limit counters.

Point 3 is the only use a Postgres advisory lock could also serve. Points 1, 2 and 4 mean a
`micro` node still has to exist and stay reachable.

## Implementation

**Phase A — `ignore_changes` on `desired_count`. This must land before anything else. BUILT.**

The three services set `desired_count` from a per-service variable
(`var.api_desired_count`, `var.worker_desired_count`, `var.frontend_desired_count` — split by
LP-629, so the spec's single `var.desired_count` and its line numbers were already stale) with
no lifecycle block. Once anything else is setting the count to zero, the next `terraform apply`
— including every `./scripts/deploy staging deploy` — silently restores all three services to 1
in the middle of the night, and the bill stays high while every artifact says it should not.

Added to all three, at `infra/modules/compute/main.tf:423`, `:458` and `:499`:

```hcl
lifecycle { ignore_changes = [desired_count] }
```

This is the single highest-consequence line in the ticket. Without it the rest is theatre.

The consequence to keep in mind: tfvars now sets each count **once, at service creation**, and
is ignored by every apply after that. Changing a count for real means scaling the service —
`./scripts/deploy <env> up` reads the counts back out of tfvars, or `aws ecs update-service` by
hand. Recorded in `infra/modules/compute/README.md` and `infra/README.md`, both of which
previously told the reader to scale by editing tfvars and applying.

Terraform cannot take a variable in a `lifecycle` block, so this is module-wide: `envs/dev`
gets it too, and has no shutdown schedule to justify it. Acceptable — dev's counts are 1 and
nothing edits them — but it is the reason this is not conditional on the environment.

**Verified, not assumed.** `terraform plan -var api_desired_count=5 -var worker_desired_count=3`
against the applied state leaves `desired_count` out of the diff on all three services
(it sits in the hidden unchanged attributes), so the block does what it claims.

**That test also found a footgun this phase introduces.** The same plan was *not* empty — it
replaced three task definitions, because `envs/staging/main.tf:51-52` derives the Bedrock rate
limiter from the count:

```hcl
worker_slots            = var.worker_desired_count * var.worker_concurrency
bedrock_rpm_per_process = max(floor(var.bedrock_rpm_budget / local.worker_slots), 1)
```

`bedrock_rpm_per_process` reaches the container as `AI_REQUESTS_PER_MINUTE_BEDROCK`
(`main.tf:472`). So editing `worker_desired_count` from 1 to 3 and applying now **divides each
worker's pacing by three while the service stays at one task** — the single running worker
throttles to a third of its intended rate, silently. Before this phase the count and the
division moved together, which is exactly what made LP-629's derivation safe.

Changing a count is now two steps, in order: edit the tfvar and apply (which reprices the
limiter and rolls the task definitions), then `./scripts/deploy <env> up`, which reads the count
back out of that same tfvar and applies it to the services. Skipping the second leaves the
limiter and the task count disagreeing; skipping the first is the LP-629 failure the derivation
exists to prevent. Written up in `infra/modules/compute/README.md`.

**Phase B — `redis_node_type = "cache.t4g.micro"`.** One line in the tfvars. `apply_immediately`
is false on the replication group, so the change lands in the maintenance window; expect a brief
failover-style interruption. A single Celery worker (`desired_count = 1`, and see LP-629 on the
concurrency of that worker) does not need 1.37 GB of broker.

**Phase C — an EventBridge Scheduler module.** Pure Terraform, no Lambda, no application code.
Universal targets call the AWS SDK directly: `arn:aws:scheduler:::aws-sdk:ecs:updateService` and
`arn:aws:scheduler:::aws-sdk:rds:stopDBInstance` / `:startDBInstance`. It is free — 14M
invocations/month, and this uses about 250. Unlike classic EventBridge rules, Scheduler accepts
an IANA `schedule_expression_timezone`, so DST is handled without a second cron.

Eight schedules, ordered so the database is warm before any task can reach it:

| Time | Days | Target |
|---|---|---|
| 22:00 | Mon–Sun | `ecs:updateService` `DesiredCount=0` (api, worker, frontend) |
| 22:15 | Mon–Sun | `rds:stopDBInstance` |
| 08:45 | Mon–Fri | `rds:startDBInstance` |
| 09:00 | Mon–Fri | `ecs:updateService` `DesiredCount=1` (api, worker, frontend) |

The stop runs seven days a week while the start runs weekdays only. That is deliberate — see
gotcha 2.

Needs a scheduler IAM role with `ecs:UpdateService`, `rds:StopDBInstance`,
`rds:StartDBInstance` and `rds:DescribeDBInstances`, scoped to the two ARNs.

**Phase D — `scripts/deploy <env> up` / `down` stages. BUILT, and pulled ahead of Phase C.**

A manual override for "I need staging now" and "I am done for the day", following the existing
`stage_*` dispatch. Built before the scheduler on purpose: it is the same two sequences a cron
would run, with an operator watching, which is how the ordering gets proven before it runs
unattended at 22:00.

`down` scales the three services to 0, **waits for `runningCount` to actually reach 0**, and
only then stops RDS. The wait is not `wait_for_services_steady` — that one is satisfied by
`desired == running`, which `0 == 0` meets the instant the update lands, while tasks are still
shutting down. If they have not drained inside `DEPLOY_DOWN_DRAIN_TIMEOUT_SECONDS` (300) it
leaves the database running rather than cut a worker's connections mid-task, and says so; the
services are already at 0, so re-running `down` re-issues the scaling harmlessly and then stops
the database. An already-stopped instance is noted, not re-issued.

It also checks for one-off tasks before stopping the database. `update-service --desired-count 0`
does not touch a task started by `run-task`, so a `migrate` mid-Alembic or a `verify` inside its
1500s tail would otherwise keep its connection while the next step stopped the instance — a
half-applied migration, in the migrate case.

Every wait fails closed: a count that cannot be read is treated as "still running", never as
zero. Throttling, a transient 5xx and an expired SSO session all return nothing, and all three
look exactly like "fully drained" — the one reading that makes it safe to stop the database.

`up` is the reverse, database first, waiting for `available` before it scales anything: a task
that starts before Postgres answers fails its readiness check and the circuit breaker can roll
it back. If RDS does not come back inside `DEPLOY_RDS_START_TIMEOUT_SECONDS` (900) it scales
nothing, so nothing crash-loops against a database that is not there.

On the guard, the spec offered "call `up` first, or at minimum refuse": **refuse** was the
choice. Auto-starting an environment as a side effect of `deploy` hides a 5-minute wait inside
a command that looks like a code push, and it is the wrong default at 23:00.

The guard is two preconditions, because the stages need different ones. `require_db_up` covers
every stage that reaches Postgres or runs an apply — `deploy`, `migrate`, `query`, `query-setup`,
`add-user`, `bootstrap-admin`, `backfill-mismo`, `verify`, `phase1`, `phase2`. It refuses only
`stopped`, `stopping` and `starting`: `backing-up` and `modifying` are states of a *reachable*
instance, and staging snapshots after every start (`rds_backup_retention_days = 30`), so
refusing on them would tell the operator to run `up` immediately after `up` had just succeeded.
`require_services_up` is the second, for stages that wait on a rollout.

It checks **two** things, not just the one the spec named. RDS stopped is the obvious half.
The other: a service left at `desired 0` reaches steady state instantly, so `deploy` would push
an image, apply, wait, and report `deploy complete: <sha> is live` for an image that no task is
running anywhere. That is a worse failure than the obscure one, because it is silent.

## Gotchas

1. **`desired_count` drift** — Phase A. Repeated because it is the one that silently undoes the
   whole ticket.
2. **RDS force-restarts after seven days stopped.** AWS starts a stopped instance in its
   maintenance window so it does not miss updates. A nightly schedule never reaches seven days,
   but a holiday shutdown would, and the instance would then stay up. Running the 22:00 stop
   every day, weekends included, reaps any auto-restart within 24 hours.
3. **Do not `terraform apply` while RDS is stopped.** Modifications to a stopped instance can
   fail mid-apply. Infra changes belong in the running window.
4. **Celery warm shutdown.** `worker_stop_timeout_seconds = 120` gives the worker a SIGTERM
   window, but confirm that in-flight extraction and verification tasks are idempotent or
   re-queued before killing the worker nightly. LP-629 notes verification runs of 400+ seconds;
   a 22:00 scale-down can land in the middle of one.
5. **The site returns 503 overnight.** The ALB and Cognito stay up; the targets simply go away.
   Fine for staging, but anyone who might hit it needs to know.
6. **Nothing else fires at night.** Checked: there is no Celery beat schedule and no
   `aws_cloudwatch_metric_alarm` anywhere in `infra/modules/`, so no scheduled job is missed and
   no alarm flaps nightly. Re-check this if either is added.

## Rejected alternatives

- **Recreating ElastiCache on the schedule** — $7.16/month for a near-certain daily outage. See
  above.
- **`redis_auth_enabled = false`** to make that recreation tractable. The flag drives four things
  from one variable (`infra/envs/staging/main.tf:169`, `:501`, `:525`, and the
  `check "redis_auth_token_applied"` at `modules/data/main.tf:267`): it destroys the `redis-url`
  secret, moves `REDIS_URL` into plain `environment` as topology-only, drops it from
  `secret_arns`, and disarms the check. It does **not** remove the token from the cluster —
  `ignore_changes` sees to that — so flipping it on the current cluster yields `NOAUTH
  Authentication required` everywhere with the check that would have caught it now silent.
  Turning auth off for real is not one command: AWS supports it only as a migration through RBAC.
  You must create a user group, run `modify-replication-group --auth-token-update-strategy DELETE
  --user-group-ids-to-add <group>` (DELETE is rejected without it -- the strategy exists only for
  the RBAC transition), then `--user-group-ids-to-remove <group>` to drop access control entirely.
  Three steps, a new RBAC object, and a cluster modification between each. Beyond the mechanics,
  the module comment records that this cache carries real borrower NPI in staging. Not worth it
  for $7.16.
- **Running Redis as a fourth ECS container** (`redis:7-alpine`) so it scales to zero with
  everything else. This genuinely captures the full $23.36 and is defensible for a staging
  broker holding transient data. The cost is real: there is no service discovery in
  `infra/modules/compute` today (no Service Connect, no Cloud Map), the `redis-url` handling
  would need reworking, and staging's cache layer would stop mirroring what production will run.
  Roughly half a day. Worth revisiting only if the floor needs to drop below ~$101.
- **AWS's packaged "Instance Scheduler on AWS" solution** — does not handle ECS services
  natively and brings its own Lambda and DynamoDB. Built for hundreds of tagged resources; this
  environment has four.
- **Aurora Serverless v2 with min 0 ACU auto-pause** — would replace the RDS half of the
  scheduler with automatic pausing, but the 0.5-ACU floor costs $0.06/hour against $0.032, so it
  only wins when usage is sporadic rather than "some hours most weekdays". Not worth migrating
  off `aws_db_instance`.
- **Savings Plans and Reserved nodes** — a Fargate Compute Savings Plan directly conflicts with
  cutting Fargate hours by 61%; do not buy one. A one-year ElastiCache reserved node (−31%) is
  the only commitment that fits, since Redis is the unschedulable piece — but downsize to `micro`
  first, and only commit if this environment will exist for a year.

## Open questions

- **Which timezone. DECIDED: a US zone.** An earlier draft of this ticket recommended
  `Asia/Kolkata`. That was wrong and is corrected here so it is not re-derived: the environment
  runs on US hours. Nothing in the repo ever supported the other reading — there is no `TZ` or
  timezone setting anywhere in `infra/`, `backend/` or `frontend/` (the only hit is a comment in
  `app/core/jwt.py` noting timestamps are UTC), and `aws_region = "us-east-1"` says where the
  infrastructure runs, not where anyone works.

  **`America/New_York`**, confirmed 2026-08-25. Phase C sets
  `schedule_expression_timezone = "America/New_York"` and writes its crons in local time;
  EventBridge Scheduler handles DST, so the eight schedules need no seasonal variant. In UTC the
  down window is 02:00–13:00 in EDT and 03:00–14:00 in EST — worth knowing only for reasoning
  about the windows below, not for the configuration.

- **A US zone puts the RDS backup and maintenance windows inside the down window.** New, and not
  in the original analysis. Neither window is set in `infra/modules/data/main.tf`, so both are
  AWS-assigned; read off the live instance they are `PreferredBackupWindow 07:30-08:00` and
  `PreferredMaintenanceWindow fri:09:36-fri:10:06`, both UTC.

  | Zone | 22:00→09:00 local, in UTC | Backup 07:30 UTC | Maintenance Fri 09:36 UTC |
  |---|---|---|---|
  | `America/New_York` (EDT) | 02:00 → 13:00 | 03:30 EDT — down | 05:36 EDT Fri — down |
  | `America/New_York` (EST) | 03:00 → 14:00 | 02:30 EST — down | 04:36 EST Fri — down |
  | `America/Los_Angeles` | 05:00 → 16:00 | 00:30 PDT — down | 02:36 PDT Fri — down |
  | `Asia/Kolkata` | 16:30 → 03:30 | 13:00 IST — up | 15:06 IST Fri — up |

  It holds in both EST and EDT, so it is not a DST artifact. A stopped instance takes no
  automated backups, so staging would silently skip its daily snapshot on every night it is
  down, and the weekly maintenance window would fall while it is stopped. Tolerable in staging,
  but it should be a decision rather than a surprise.

  **Phase C sets both windows explicitly** so they land inside the running window. RDS takes
  these in UTC and does not accept a timezone, so they must clear the *later* of the two DST
  boundaries: the running window is 13:00–02:00 UTC in EDT and 14:00–03:00 in EST, and only
  14:00–02:00 UTC is inside both. AWS also requires the two not to overlap.

  ```hcl
  preferred_backup_window      = "14:30-15:00"       # 10:30 EDT / 09:30 EST
  preferred_maintenance_window = "wed:15:30-wed:16:00"  # 11:30 EDT / 10:30 EST
  ```

  Both arguments are currently absent from the `aws_db_instance` resource, so this adds them
  rather than changing anyone's decision. The tradeoff being made deliberately: a maintenance
  reboot now lands mid-morning on a Wednesday instead of overnight. That is disruptive on a
  running staging environment once a week, and it is still the right side of the trade — the
  alternative is that maintenance never applies and pending updates accumulate until the
  seven-day force-start applies them all at once, unattended. Related to gotcha 2 but distinct
  from it: that one is the seven-day rule, this one recurs weekly.
- **Whether 09:00 is early enough** given the 08:45 RDS start. `db.t4g.small` typically reaches
  `available` in 3–7 minutes, so 15 minutes should hold, but the first week is worth watching.
- **Interaction with LP-629.** If worker concurrency or `desired_count` rises to fix the
  single-slot queue, Fargate cost rises and the saving from this ticket grows proportionally.
  The percentages here hold; the absolute dollars would change.
