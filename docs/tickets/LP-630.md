# LP-630 — take staging off the clock overnight, and stop paying for a cache twice the size it needs

**Status: SPECIFIED. Not built, not deployed, not committed.**
Phases A–D below are all unstarted.

## The report

Staging runs 24 hours a day and nobody touches it between roughly 22:00 and 09:00. It costs
**~$156/month in fixed infrastructure** — before Bedrock, S3, ECR, KMS, CloudWatch or data
transfer — against a `budget_limit_usd = 300` alarm. Roughly 60% of those hours buy nothing.

Two changes recover **~$57/month (~$683/year), a 37% cut**, and neither of them risks data:

1. Scale the three ECS services to zero and stop RDS overnight and at weekends.
2. Halve the ElastiCache node, permanently, in one tfvars line.

A third change — recreating ElastiCache on the same schedule — is deliberately **out of scope**,
for reasons recorded below so nobody re-derives them.

## The baseline

Read from `infra/envs/staging/terraform.tfvars`, priced at us-east-1 list rates over a 730-hour
month (August 2026). Excludes Bedrock, S3, ECR, KMS, CloudWatch Logs, ALB LCUs, data transfer
and tax.

| Fargate ECS x3 | `api 512/1024`, `worker 1024/2048`, `frontend 256/512`, `desired_count = 1`, `cpu_architecture = "ARM64"` | $0.03238/vCPU-h + $0.00356/GB-h | **50.46** |
| VPC interface endpoints | 5 services x 1 AZ (`interface_endpoint_services`, `endpoint_availability_zones`) | $0.01/h each | **36.50** |
| RDS instance hours | `rds_instance_class = "db.t4g.small"` | $0.032/h | **23.36** |
| ElastiCache | `redis_node_type = "cache.t4g.small"` | $0.032/h | **23.36** |
| ALB | `enable_tls = true`, Cognito, ACM | $0.0225/h | **16.43** |
| RDS storage | `rds_allocated_storage = 50`, gp3 | $0.115/GB-mo | **5.75** |
| | | | **155.86** |

The three ECS services total **1.75 vCPU and 3.5 GB**, which is $0.069125/hour. RDS instance
hours are $0.032/hour. Together, **$0.1011 of every hour is stoppable.**

`enable_nat_gateway = false` already — there is no NAT gateway to find.

## What can actually be stopped

**Clean stop, single AWS API call, no credential coupling:**

- **ECS services** — `ecs:UpdateService` with `DesiredCount: 0`. Instantaneous and fully
  reversible. Fargate bills per second of task runtime, so a task that is not running costs
  nothing.
- **RDS** — `rds:StopDBInstance`. Instance hours stop; provisioned storage and backup storage
  keep billing, which is why the $5.75 storage line stays in the floor.

**No stop API exists:**

- **ElastiCache** — there is no stop or pause operation on a replication group, only delete.
  See "Why ElastiCache is out of scope".

**Must stay up:**

- **ALB** — deleting and recreating it churns the ACM association, the Cognito authenticate
  action and the Route 53 alias. Not worth $16.43.
- **VPC interface endpoints** — the largest line item after Fargate, and only needed while
  tasks run, but a var-driven toggle is blocked: `infra/modules/network/main.tf:52` has a
  precondition that fails when `enable_nat_gateway` and `enable_vpc_endpoints` are both false,
  so `enable_vpc_endpoints = false` would break `terraform plan` outright. Tearing them down
  out of band creates drift the next apply would reverse. Left alone for now; noted as the
  next thing to look at if the floor needs to go below ~$99.

## The decision

**Schedule: down 22:00, up 09:00, every night, and stay down over the weekend
(Fri 22:00 → Mon 09:00).** That is 447.6 stoppable hours per month, 61.3% of the total.

| | Saved/month | Bill after |
|---|---|---|
| Nightly only, 7 nights (334.6 h off) | 33.84 | 122.02 |
| **Nightly + weekends (447.6 h off)** | **45.26** | 110.60 |
| **ElastiCache `small` → `micro`, always on** | **11.68** | — |
| **Both** | **56.94** | **98.92** |

The $45.26 is Fargate $30.94 + RDS instance hours $14.32.

Weekends are worth $11.42/month on their own — more than moving the stop time two hours
earlier would buy (~$6). The weekend is the cheap half of this change.

The remaining ~$99 floor: VPC endpoints $36.50, ALB $16.43, Fargate for 261 running hours
$19.52, RDS $14.79 including storage, ElastiCache micro $11.68.

## Why ElastiCache is out of scope

**Not because of data loss.** Redis holds nothing durable — see the next section. Deleting it
loses a queue, some expiring results and an auto-expiring lock. In staging that is genuinely
free.

It is out of scope because **recreating it breaks the environment every morning, and the
repair is a human procedure by design.**

`infra/modules/data/main.tf:230-247` deliberately does not manage the AUTH token:

```hcl
lifecycle { ignore_changes = [auth_token, auth_token_update_strategy] }
```

The token is applied out of band and hand-written into the `redis-url` secret. A recreated
replication group therefore comes up with **no token**, while Secrets Manager still holds
`rediss://:OLD_TOKEN@...`. Every API and worker container fails on connect. This is certain,
not a risk.

And the repair cannot be automated as it stands. `scripts/deploy:862-930` generates a token,
submits `modify-replication-group --auth-token-update-strategy ROTATE --apply-immediately`,
then polls for minutes until `Status=available AND AuthTokenEnabled=true`, and refuses to write
the URL if it cannot verify the result — the failure path warns that a timeout can leave "a
token nobody knows." On top of that, `REDIS_URL` reaches containers as an ECS task secret
(`infra/modules/compute/main.tf:72-75`, `valueFrom`), which ECS resolves **at task start**, so
the secret must be correct *before* the 09:00 ECS scale-up, not after.

The morning critical path would be: create an encrypted replication group (10–15 min) → apply
and verify a token (minutes) → rewrite the secret → only then start ECS. Roughly 25 minutes of
unattended, verification-gated steps, plus a Terraform destroy/create needing state-lock access
in a cron, plus a primary endpoint hostname that is assigned at creation and may not survive
the round trip.

**The payoff for all of that is $7.16/month** once the node is already a `micro`. Downsizing
captures $11.68 of the same $23.36 for one line and no risk. Scheduling the remainder is not a
trade worth making.

## What Redis is actually for

Recorded here so this does not have to be re-derived. Only four backend files touch it —
`app/main.py`, `app/core/config.py`, `app/core/redis.py`, `app/services/needs_engine.py`.

1. **Celery message broker** (`app/tasks/celery_app.py:34`) — the queue between the API and the
   worker. Without it, uploads reach S3 and Postgres and are never classified, extracted or
   verified. This is the load-bearing use.
2. **Celery result backend** (`celery_app.py:35`, with `task_track_started=True`) — task state
   and return values.
3. **Cross-process lock** (`app/services/needs_engine.py:970-993`) — `needs-lock:{loan_file_id}`
   with a `timeout` so a crashed worker cannot deadlock a file. Held at `app/tasks/needs.py:70`
   and `:83` and `app/services/verification_run.py:815`.
4. **Health-check dependency** (`app/main.py:169-215`) — `/health` and `/health/ready` both AND
   in `check_redis_connection()`. No Redis means the API reports not-ready, the ALB target group
   pulls it out of rotation, and the deployment circuit breaker can roll a deploy back. Redis
   going away does not merely pause background work; it takes the API offline.

Despite the service name, **nothing is cached**. No response cache, no session store (Cognito
owns auth), no rate-limit counters.

Point 3 is the only use a Postgres advisory lock could also serve. Points 1, 2 and 4 mean a
`micro` node still has to exist and stay reachable.

## Implementation

**Phase A — `ignore_changes` on `desired_count`. This must land before anything else.**

`infra/modules/compute/main.tf:383`, `:420` and `:443` all set
`desired_count = var.desired_count` with no lifecycle block. Once a scheduler is setting the
count to zero, the next `terraform apply` — including every `./scripts/deploy staging deploy` —
silently restores all three services to 1 in the middle of the night, and the bill stays high
while every artifact says it should not. Add to all three services:

```hcl
lifecycle { ignore_changes = [desired_count] }
```

This is the single highest-consequence line in the ticket. Without it the rest is theatre.

**Phase B — `redis_node_type = "cache.t4g.micro"`.** One line in the tfvars. `apply_immediately`
is false on the replication group, so the change lands in the maintenance window; expect a brief
failover-style interruption. A single Celery worker (`desired_count = 1`, and see LP-629 on the
concurrency of that worker) does not need 1.37 GB of broker.

**Phase C — an EventBridge Scheduler module.** Pure Terraform, no Lambda, no application code.
Universal targets call the AWS SDK directly: `arn:aws:scheduler:::aws-sdk:ecs:updateService` and
`arn:aws:scheduler:::aws-sdk:rds:stopDBInstance` / `:startDBInstance`. It is free — 14M
invocations/month, and this uses about 250. Unlike classic EventBridge rules, Scheduler accepts
an IANA `schedule_expression_timezone`, so DST is handled without a second cron.

Eight schedules, ordered so the database is warm before any task can reach it:

| Time | Days | Target |
|---|---|---|
| 22:00 | Mon–Sun | `ecs:updateService` `DesiredCount=0` (api, worker, frontend) |
| 22:15 | Mon–Sun | `rds:stopDBInstance` |
| 08:45 | Mon–Fri | `rds:startDBInstance` |
| 09:00 | Mon–Fri | `ecs:updateService` `DesiredCount=1` (api, worker, frontend) |

The stop runs seven days a week while the start runs weekdays only. That is deliberate — see
gotcha 2.

Needs a scheduler IAM role with `ecs:UpdateService`, `rds:StopDBInstance`,
`rds:StartDBInstance` and `rds:DescribeDBInstances`, scoped to the two ARNs.

**Phase D — `scripts/deploy staging up` / `down` stages.** A manual override for "I need staging
now" and "I am done for the day", following the existing `stage_*` dispatch at
`scripts/deploy:3194-3212`. `stage_deploy` should call `up` first, or at minimum refuse to run
with a clear message when RDS is stopped — `stage_migrate` runs a one-off ECS task against the
database and will otherwise fail obscurely at 23:00.

## Gotchas

1. **`desired_count` drift** — Phase A. Repeated because it is the one that silently undoes the
   whole ticket.
2. **RDS force-restarts after seven days stopped.** AWS starts a stopped instance in its
   maintenance window so it does not miss updates. A nightly schedule never reaches seven days,
   but a holiday shutdown would, and the instance would then stay up. Running the 22:00 stop
   every day, weekends included, reaps any auto-restart within 24 hours.
3. **Do not `terraform apply` while RDS is stopped.** Modifications to a stopped instance can
   fail mid-apply. Infra changes belong in the running window.
4. **Celery warm shutdown.** `worker_stop_timeout_seconds = 120` gives the worker a SIGTERM
   window, but confirm that in-flight extraction and verification tasks are idempotent or
   re-queued before killing the worker nightly. LP-629 notes verification runs of 400+ seconds;
   a 22:00 scale-down can land in the middle of one.
5. **The site returns 503 overnight.** The ALB and Cognito stay up; the targets simply go away.
   Fine for staging, but anyone who might hit it needs to know.
6. **Nothing else fires at night.** Checked: there is no Celery beat schedule and no
   `aws_cloudwatch_metric_alarm` anywhere in `infra/modules/`, so no scheduled job is missed and
   no alarm flaps nightly. Re-check this if either is added.

## Rejected alternatives

- **Recreating ElastiCache on the schedule** — $7.16/month for a near-certain daily outage. See
  above.
- **`redis_auth_enabled = false`** to make that recreation tractable. The flag drives four things
  from one variable (`infra/envs/staging/main.tf:169`, `:501`, `:525`, and the
  `check "redis_auth_token_applied"` at `modules/data/main.tf:267`): it destroys the `redis-url`
  secret, moves `REDIS_URL` into plain `environment` as topology-only, drops it from
  `secret_arns`, and disarms the check. It does **not** remove the token from the cluster —
  `ignore_changes` sees to that — so flipping it on the current cluster yields `NOAUTH
  Authentication required` everywhere with the check that would have caught it now silent.
  Turning auth off for real needs an out-of-band
  `modify-replication-group --auth-token-update-strategy DELETE` first. Beyond the mechanics,
  the module comment records that this cache carries real borrower NPI in staging. Not worth it
  for $7.16.
- **Running Redis as a fourth ECS container** (`redis:7-alpine`) so it scales to zero with
  everything else. This genuinely captures the full $23.36 and is defensible for a staging
  broker holding transient data. The cost is real: there is no service discovery in
  `infra/modules/compute` today (no Service Connect, no Cloud Map), the `redis-url` handling
  would need reworking, and staging's cache layer would stop mirroring what production will run.
  Roughly half a day. Worth revisiting only if the floor needs to drop below ~$99.
- **AWS's packaged "Instance Scheduler on AWS" solution** — does not handle ECS services
  natively and brings its own Lambda and DynamoDB. Built for hundreds of tagged resources; this
  environment has four.
- **Aurora Serverless v2 with min 0 ACU auto-pause** — would replace the RDS half of the
  scheduler with automatic pausing, but the 0.5-ACU floor costs $0.06/hour against $0.032, so it
  only wins when usage is sporadic rather than "some hours most weekdays". Not worth migrating
  off `aws_db_instance`.
- **Savings Plans and Reserved nodes** — a Fargate Compute Savings Plan directly conflicts with
  cutting Fargate hours by 61%; do not buy one. A one-year ElastiCache reserved node (−31%) is
  the only commitment that fits, since Redis is the unschedulable piece — but downsize to `micro`
  first, and only commit if this environment will exist for a year.

## Open questions

- **Which timezone.** EventBridge Scheduler takes an IANA zone, and the choice decides who finds
  staging dark. `Asia/Kolkata` matches where the work happens; a US zone matches where the
  processors are. Recommend `Asia/Kolkata` and revisit if anyone US-side starts using staging.
  This is the one decision needed before Phase C is written.
- **Whether 09:00 is early enough** given the 08:45 RDS start. `db.t4g.small` typically reaches
  `available` in 3–7 minutes, so 15 minutes should hold, but the first week is worth watching.
- **Interaction with LP-629.** If worker concurrency or `desired_count` rises to fix the
  single-slot queue, Fargate cost rises and the saving from this ticket grows proportionally.
  The percentages here hold; the absolute dollars would change.
