# LP-643 — processor-added DTI rows, and a gate message that says the real reason

- **Status:** Done — backend and UI. §1 and §3 built on the recommendations below, confirmed by the user 2026-09-05.
- **Date:** 2026-09-05
- **Asked for by:** the user, 2026-09-05
- **Found via:** LF-ZE9N, whose gate banner sends the processor to the wrong document

Two changes to the DTI calculator, related only in that a processor meets both on the same screen.

---

## 1. Add and remove rows in each section

**The ask:** an add button in each DTI section (income, housing, debt) so a processor can add a row
with a description and an amount, and remove rows.

**What exists.** `DtiOverride` overrides the *value* of a line the calculator already produced, keyed
by `field_key` with one active override per field per file, a `note` for the reason, and soft-delete
so a cleared override revives in place. The API is `PUT` / `DELETE
/{identifier}/dti/overrides/{field_key}`.

That mechanism cannot express what is being asked. An override needs a `field_key` the calculator
emitted; a processor-added row has no such key, because the calculator never produced it. This is a
new kind of line, not a new override.

### Design questions — worth deciding before building, not during

**a. Does an added row clear a gate?** The established precedent says an override does: *"an
override on the line clears the gate (a processor-supplied figure is trusted)."* Extending that to
added rows means a processor could add "Rent — $2,000" to income and un-gate a file that
SEL-2026-08 says cannot be qualified without a Form 1007 (see LP-642). That is the fail-closed
discipline being routed around by the UI.

My recommendation: **an added row does not clear a gate.** A gate says a *required input is
unknown*; adding an unrelated row does not make it known. Overriding the gated line itself already
works and remains the way to clear it. But this is a policy call about how much a processor's
figure is trusted, and it is yours to make.

**b. Removing an engine row is a different act from removing your own.** Deleting a row you added is
housekeeping. Deleting a liability the credit report produced is an *exclusion* — a claim that a
real debt should not count — and the calculator already has machinery for it (`excluded_reason`,
which shows the line struck through with the reason, rather than vanishing it). Silently removing an
engine row would make the itemisation stop reconciling with the source data, and nothing would
record who decided that or why.

My recommendation: added rows are removable; engine rows are *excludable with a reason* through the
existing path, never deletable.

**c. Audit.** Every added row needs who / when / why, the way `DtiOverride.note` does. A DTI is the
number a loan qualifies on; a row nobody can attribute is a figure with no author.

**d. Does an added row survive re-computation?** Overrides do — they are stored per file and
re-applied. Added rows must behave the same, or a processor's work vanishes on the next document
upload.

### Shape this suggests

A sibling of `DtiOverride` — say `DtiCustomLine` — carrying `loan_file_id`, `section`
(income / housing / debt), `label`, `value`, `note`, soft-delete, and the same
created-by/timestamps. Surfaced through `_to_items` so a custom line is itemised, sums into its
section, and appears in the snapshot breakdown like any other. `POST` / `DELETE` alongside the
override endpoints.

The `_to_items` detail matters: LP-621 records that appending a figure to `*_lines` without routing
it through `_to_items` put it *"in the headline but not the breakdown, so the itemized list stopped
summing to the number beside it"*. A custom line must not repeat that.

## 2. The gate message names the wrong problem

**The banner already exists.** `GatedBanner` in `dti-calculator.tsx` renders `gate_reason` in a
warning box with `role="alert"`. This is not a missing feature — it is a wrong sentence, which is
worse, because it reads as authoritative.

**What LF-ZE9N shows a processor:**

> This is an investment property the borrower does not occupy, so the ratio is not the subject's
> payment against their income: the application states no GROSS monthly rent for the subject (a net
> figure cannot be run through the 75% vacancy factor).

Everything before the colon is right. The rest sends the processor to the 1003 to look for a number
that was never going to be there: MISMO does not repeat the subject in the owned-property schedule,
which is where we look. So the message describes our lookup, not the file's problem.

**What it should say** — the missing document, not the empty field:

> No document on this file states what the subject property will rent for. A comparable rent
> schedule (Form 1007) or a lease for the subject is needed.

With the form chosen by unit count — 1025 for two-to-four units (LP-642).

**The general form of the defect.** A gate reason is produced by whichever code could not proceed,
and it naturally describes *the lookup that failed*. What a processor needs is *the document to go
and get*. Those are different sentences, and the second is the useful one. Worth checking the other
gate reasons for the same shape rather than fixing this one and moving on — the housing gate's
`"<label> is unknown"` has the same property, though bug-001's unverified-inputs work already
softened it by naming what the file does state.

This is a strict prerequisite for LP-642's first step: the corrected wording and the Need List entry
are the same fix seen from two screens, and shipping one without the other leaves a processor told
what to get with no way to request it, or asked for a document with no explanation of why.

## 3. An "ungate" button, with a confirmation and an undo

**The ask (user, 2026-09-05):** a button that ungates the DTI calculator. On click, a popup carrying
a warning; on Apply, every value that was making the DTI gated is set to **0**, and the action can
be undone.

**What it is, said plainly:** a deliberate override of the fail-closed gate. That is not an argument
against it — a processor who knows a figure is genuinely zero, or who has the number in front of
them, is better placed than the engine, and the calculator already accepts that a
processor-supplied figure is trusted. But it should be built knowing what it is, because the gate
exists to stop a confident ratio resting on a value nobody established, and this is the control that
switches it off.

### What it interacts with

**Zeroing is not neutral, and the direction is not uniform.** A gated housing input set to 0
UNDERSTATES the housing payment and so understates the DTI — the over-qualifying direction. That is
exactly what `_extracted_monthly` refuses to do on its own: *"a $0 is implausible and — exactly like
an ABSENT figure (absent≠0) — must FAIL-CLOSED to unknown, never a confident too-low DTI resting on
a fabricated 0."* So this button hands a processor the fabricated zero the engine spent LP-375 and
LP-616 refusing to invent. Reasonable when they know it; the popup is what makes it a decision
rather than a slip.

**Some gates are not zero-shaped at all.** The LF-ZE9N gate is the subject's missing GROSS RENT — a
rental-treatment gate, not a housing-input one. Zeroing "the value making it gated" there means
asserting the property rents for $0, which would compute a net rental of −PITIA and carry the whole
payment as an obligation. That is not "ungated", it is a different wrong answer. Likewise the
occupancy gate ("we cannot tell what this subject is") has no numeric input to zero.

So the button cannot be "set every gating value to 0" uniformly. It needs to know, per gate, whether
a zero is even meaningful — and where it is not, either say so or offer the real remedy (the missing
figure, or the document that carries it).

**bug-012's exclusion must not be reachable this way.** The SEL-2026-08 restriction is applied
structurally *because* an amount override cannot establish 12 months of property-management
experience. An ungate that re-includes it would route around a guideline through the UI, which is
the same reasoning as §1(a) and the answer is the same: no.

### What the popup has to say

**The user's requirement (2026-09-05): the popup lists everything that will be set to 0, and Apply
is the agreement to all of it.** So it is an itemised consent, not a confirmation — "are you sure"
tells a processor nothing they can weigh, and a warning a reader skims is a warning that does
nothing (the LP-634 lesson, one screen over).

Concretely, five things:

**1. Every line, named, with what it becomes.** Not a count, not "3 values" — the labels, because a
processor recognises *Property taxes* and cannot act on *3 values*:

| Line | Now | After |
|---|---|---|
| Property taxes | unknown | **$0.00 / month** |
| Homeowners insurance | unknown | **$0.00 / month** |

**2. What each zero ASSERTS, in the processor's terms.** *"The DTI will be computed as if this
property has no tax liability."* The number is the mechanism; the assertion is the thing they are
being asked to agree with, and it is the half a processor can actually judge as true or false.

**3. The resulting ratio, before and after.** The point of ungating is to get a number, so the
number is what consent is really about — *"Front-end 8.43% → 12.10%; back-end 31.2% → 34.9%"*. This
means the popup COMPUTES A HYPOTHETICAL, which is a real design consequence: the calculator needs a
"what would this be with these overrides" path that does not persist. Worth building deliberately,
because a preview that silently diverges from what Apply produces is worse than no preview.

**4. What is NOT being zeroed, and why.** Where a gate has no meaningful zero (the missing gross
rent, the undetermined occupancy — see above), the popup says so rather than omitting it. A
processor who clicks Ungate and finds the file still gated, with nothing explaining which part did
not move, has been told less than before they clicked.

**5. That it is undoable, and how.** One line. It makes the decision cheaper to take and cheaper to
reverse, which is the whole reason to prefer per-line overrides over a file-level flag.

**What it must not do:** show a single aggregate ("this will set 3 values to $0") or a generic
warning ("this may affect the accuracy of the calculation"). Both are technically true and neither
lets a processor decide, which makes the popup a click-through — a consent screen that manufactures
consent rather than obtaining it.

### Undo

Straightforward if the zeroes are stored as ordinary overrides: undo is clearing them, which already
exists (`DELETE /{identifier}/dti/overrides/{field_key}`). That is the argument for implementing this
as "write an override of 0 to each gating line" rather than as a separate ungate flag — it reuses the
audit trail, the per-line display, and the existing undo, and it keeps one mechanism for "a processor
supplied this figure" instead of two.

The alternative — a file-level `ungated` boolean — is simpler to build and worse to live with: it
does not record WHICH values were asserted, it cannot be undone per line, and it makes the itemised
breakdown stop reconciling with the headline (the LP-621 failure this ticket already cites once).

**Recommendation:** build it as a batch of zero-value overrides with one confirmation, per-line
reasons in the popup, and no new undo mechanism. Refuse the two gates where zero is not a meaningful
answer (missing gross rent, undetermined occupancy) and say why in the popup instead of silently
doing nothing.

### Still the user's call

Whether to offer this at all on the housing gates, given it re-introduces the fabricated zero by
consent. My view is yes with the popup, because the alternative is a processor who cannot proceed on
a file they understand — but it is a policy decision about how much the system defers to a
processor, and it is the same decision as §1(a).

## §1 and §3 as built (2026-09-05)

The user confirmed the three recommendations, so each is now a pinned behaviour with its reasoning in
the test that holds it — a later reader loosening one should have to disagree with an argument rather
than delete an unexplained assertion.

**`DtiCustomLine`**, a sibling of `DtiOverride`: `loan_file_id`, `section`, `label`, `value`, `note`,
soft delete. No unique constraint, which is the opposite of an override's — a field has one value, but
two custom lines with the same label are two real additions (a borrower can have two side jobs), and
de-duplicating them would drop a processor's second entry.

Lines are shaped as `_AutoLine`s and merged **before** `_to_items`, so they are inside every
downstream behaviour: itemised, overridable, summed, in the snapshot breakdown, and inside the total
the rental treatment nets against. LP-621 records what happens to a figure that skips that path.

**An added row does not clear a gate** (§1a). Verified by mutation: forcing the gate off when any
custom line exists fails the test that pins it.

**An engine row has no delete endpoint** (§1b). `remove_dti_custom_line` scopes to
`dti_custom_lines`, so an engine key is simply not found, and removal is also scoped to the owning
file so a line id is not a cross-file handle.

**The ungate is a batch of ordinary zero-value overrides** (§3), which is what makes undo the existing
`DELETE .../overrides/{field_key}` rather than a second mechanism — and keeps the breakdown
reconciling with the headline. One audit entry, not N: the decision was a single decision about a set.

`GET /dti/ungate` returns the itemised consent — every line by name, what each zero **asserts** in a
processor's terms, the ratios before and after, and what will **not** move. The after-ratios are
computed by running the real calculator with the same overrides Apply would write, layered on top of
stored ones, because a preview computed a second way can diverge from what Apply delivers.

**The rental gate is reported, not zeroed.** Zeroing a missing gross rent asserts the property rents
for nothing, which computes a net of minus its whole PITIA — not "ungated", a different wrong answer,
and in the opposite direction from the housing case.

### Two of these tests were green and meaningless

Written, then mutation-tested, and two did not bite:

- the preview-agrees-with-apply test ran on a bare file where **both ratios are `None`**, so
  `None == None` passed with the preview computing its hypothetical from $99,999 instead of $0. It
  now has real income and asserts the value is not None before comparing.
- the first mutation aimed at §1a was a no-op against its own fixture, which said nothing about the
  test. Re-aimed, it fails correctly.

### The UI

Built, and deliberately thin. Every decision is enforced server-side, so the frontend cannot route
around one — the components render what the API returns and send what it accepts.

**Add a line**, one control per section, collapsed to a button until used. **Remove**, on custom
lines only — the trash control is rendered for a `custom.` key and nothing else, which mirrors the
API having no route to delete an engine line.

**The ungate** sits ON the gated banner, because that is where the problem is stated. Its dialog
renders `GET /dti/ungate` and derives nothing: every line by name, what each zero asserts, the ratio
before and after, and what will not move. The Apply button is DISABLED where there is nothing to
record, rather than applying an empty change and leaving a processor to wonder whether it worked.

The preview query uses `staleTime: 0, gcTime: 0` and is `enabled` only while the dialog is open. It
is a statement about what an action WOULD do to the file as it stands; serving a cached one would
show a consequence that has since changed, on the screen where it is accepted personally.

Five component tests assert what a processor is SHOWN — the named line, the assertion, the resulting
ratio, the unresolved reason, and that the reason they type reaches the request. Not that the dialog
renders.
