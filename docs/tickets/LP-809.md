## What was done

### One email, not four

A processor requests documents on Tuesday, three more findings land on Wednesday, and the borrower
should receive **one** message listing everything. So a draft holds a **set** of needs, and its body
is regenerated from that set on every add and every remove.

**Regenerated, never appended.** Appending cannot express a removal: the removed document would stay
in the email while the needs list said otherwise, and the email would look perfectly fine. That is
the failure mode `test_the_body_is_regenerated_not_appended` exists for.

Until LP-810's flag flips, the regeneration is LP-817's deterministic render — what that module
means by "the plain template". Nothing in this ticket calls a model.

### The join, and why the existing column was not enough

`Communication.needs_item_id` already exists and holds **one** need. That is the right shape for a
sent, single-purpose message and the wrong one for a draft still collecting. It is unchanged and
still answers "which need was this message about".

Both sides of the join **CASCADE**, deliberately differing from `needs_item_id`'s `SET NULL`. That
column preserves the historical fact that a *sent* message concerned a need that has since gone. A
draft has no history to preserve — it was never sent — and a need that no longer exists must not
still be listed in an email.

### What does not go into a borrower's email

LP-800 assigns every document type a responsible party, and this draft is addressed to the borrower.
A need for an appraisal, a title commitment or an employer's VOE is real work that is **not theirs
to do**, so it is not added.

It is **not lost**. The need stays on the needs list, which is where a processor tracks it, and
LP-820 owns the paths that chase the other parties. `DraftUpdate.skipped_not_borrower` returns which
ones, rather than swallowing them: a processor who requested five documents and sees three is owed
an answer, and the answer is not an error.

**An untyped need counts as borrower-facing**, which is the opposite of LP-800's default and
deliberate. LP-624 makes untyped needs routine — a request generated from a finding's own sentence
("One more source stating the date of birth") has no catalog type at all. Those needs were created
*by* a processor clicking "request documents", so the decision to ask the borrower was already made
by a person. LP-800's processor default protects against a document nobody classified; it should not
veto a request somebody made.

## Decisions

### Two columns the plan did not ask for

`communications.template_key` and `communications.template_version`.

`phase4.md` §6 requires the record to capture *template + version* beside the rendered body, because
that record is evidence. ADR-401 pins each version to a content hash so a version names exactly one
set of words — worth nothing if the version used is not stored. **No other M1 ticket has a migration
to add them**: LP-811 is explicitly migration-free and LP-810's is the prose cache. So they belong
with the ticket that first renders a template into a communication, which is this one.

The version is stamped **from the render itself**, not read from the registry separately. Read
separately, a template bumped between the render and the stamp files the new words under the old
version — the one thing the hash pin exists to make impossible. `render_draft_body` returns the
whole `RenderedTemplate` for that reason: subject, body, key and version travel together, so there
is no point at which they can come apart.

### A partial unique index, and the constraint LP-818 will have to revisit

`uq_communications_open_draft` on `(loan_file_id, template_key)` where `status = 'draft' AND
deleted_at IS NULL`.

The service looks before it creates, but look-then-create races: two near-simultaneous requests each
find no draft, each create one, and the file holds two half-populated drafts with no basis for
choosing between them — the same shape as the duplicate needs items LP-801's review found, reached
by another route. The index is what makes "the open draft" true under concurrency rather than merely
usual. It is declared on the model as well as in the migration, because the test database is built
by `create_all` and a constraint that exists only in the migration is one no test can violate.

**Scoped to `(file, template kind)` rather than to drafts in general**, because a file may
legitimately hold more than one kind of draft. LP-818 adds needs-less **reply** drafts, and one per
thread is the shape that will want. A reply draft has no template key to distinguish it by, and NULL
keys do not collide in a unique index — so LP-818 will pass *through* this constraint without being
governed by it. Recorded in the migration and here rather than discovered there.

### An emptied draft is kept

A processor removing the last line is editing, not abandoning. Deleting the row would discard
whatever else they had changed, and an empty draft is visibly empty where a missing one is not.

### The signer is not resolved

The body keeps the template's own `$processor_name` placeholder. A draft is not addressed to anyone
until it is sent, and LP-811 owns the send — resolving a signer now would bake in whoever happened
to click "request documents", who is not necessarily who sends it.

## Tests

`tests/services/test_email_draft_lp809.py`, 14 tests, plus one added to
`tests/test_readonly_query.py`.

Three of the behaviours here fail **silently** if wrong, which is what the tests are shaped around:

- **A second draft** is invisible until somebody opens the tab and finds two.
- **An appended body** reads perfectly while contradicting the needs list.
- **A stale `template_version`** is a correct-looking audit row pointing at the wrong words.

`test_two_files_get_two_drafts` is the control for every accumulation test: without it, "one open
draft" could be satisfied by one draft for the entire database and all of them would still pass.

### The views are executed, not only string-matched

`test_the_lp809_views_are_valid_sql` runs both views against the real test database — the gap LP-822's
review found, in the migration immediately after it. The **rebuild** of `readonly.communications` is
the more dangerous of the two: it drops a view that already exists and recreates it, so a mistake
does not merely fail to add a view, it leaves the deploy with none, and the text-matching checks pass
because the text is syntactically fine. The test also asserts `body`, `subject`, `sender` and
`recipient` are still absent — a rebuild is exactly where dropped content comes back by accident,
because the new view is written fresh rather than altered.

Verified by mutation, each confirmed applied before the run was believed:

| Mutation | Result |
|---|---|
| `template_version` stamped as a literal rather than from the render | 1 test fails |
| an untyped need treated as not borrower-facing | 2 tests fail |
| the borrower-facing filter removed | 1 test fails |
| draft ordered by title rather than by when each need was added | 1 test fails |
| `template_key` mistyped in the rebuilt view | 2 tests fail |

## Assumptions

- **One accumulating draft kind exists today.** Everything is scoped to
  `initial_documentation_request`. The reminder and condition-response templates render fine but
  nothing accumulates into them; LP-814 and LP-820 are where that question arrives.
- **`display_id` is the borrower-facing loan reference.** It is what the file is called everywhere
  else a person sees it.
- **A need's `title` is safe to put in front of a borrower.** It is written by
  `request_documents_in_bulk` from a document label or a finding's own request sentence, both of
  which are already borrower-facing prose. A hand-typed need title would also reach the draft, and
  that is the same trust the needs list already places in it.

---

## Deliberately not done

- **No API and no frontend.** The plan scopes this to the backend; LP-811 owns copy-and-send and
  LP-812 the timeline. There is currently no way for a processor to *see* the draft this ticket
  builds — which is fine for one ticket in a chain, and stated so nobody assumes otherwise.
- **No draft deletion or discard.** Nothing asks for it, and "discard this draft" interacts with the
  partial unique index in a way that wants a real decision rather than a guess.
- **No recipient.** `Communication.recipient` stays null. The borrower's email address is LP-811's
  to resolve, and putting a guess there now would look like an addressed message.
- **No activity-log entry for a draft change.** LP-812 merges communications with the activity log
  and is where "was this noisy?" gets answered with a screen in front of somebody.

## For the reviewer

The three standing reviewer checks:

- **Tenancy** — no `company_id` derivation. Every entry point takes an already-resolved `LoanFile`;
  the draft is a file-owned child (ADR-052) and scopes transitively. LP-805 remains the only
  resolver.
- **Message content in logs** — no logging added. Relevant here because this ticket is the first to
  put a rendered borrower-facing body into the database: it goes to `Communication.body` and
  nowhere else, and the readonly view still drops it.
- **AI in the decision path** — none. The body is a deterministic template render.

The judgement calls worth a second opinion, in the order I would attack them:

1. **The two provenance columns**, which the plan did not ask for. I argue §6 requires them and no
   later M1 ticket can add them. If you disagree, they are cheap to pull — but then §6's requirement
   has no home in M1 and that should be recorded as an escalation rather than left.
2. **An untyped need being treated as borrower-facing**, which inverts LP-800's default. My reason
   is that a person already decided; the counter-argument is that LP-800's default exists precisely
   because unclassified things should not reach a borrower, and consistency has value of its own.
3. **The partial unique index's scope.** I chose `(loan_file_id, template_key)` knowing LP-818 will
   slip through it. The alternative — a discriminator column now, sized for a draft kind LP-818 has
   not designed yet — seemed worse. It is a guess about a ticket I have not read.

**LP-809 does have a "Done when"?** No — it has none, the fourth after LP-802, LP-817 and LP-822.
Judged against the section's four sentences: the join exists, `request_documents_in_bulk` adds to the
open draft, and the body regenerates on add and on remove.
