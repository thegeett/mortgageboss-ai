# LP-616 — Decide "prior address" from the document's own date, not per-run AI

## The evidence

Two loan files, same borrower, same MISMO, same eight documents, created independently. Across 46
governed rules they agree on 45. The one disagreement:

| | the two 2023 W-2s' address | `id.current_address_type` | ID-4 |
|---|---|---|---|
| LF-3CVT | 298 Sewall Street, Boylston **MA** | `prior` | **satisfied** |
| LF-T9HD | 298 Apt A Sewall Street, Boylston **MA** | `residence` | **open (red)** |

ID-4 gathers only addresses tagged `residence`. On LF-3CVT the W-2 addresses are filtered out and
only Knightdale remains — consistent. On LF-T9HD they are kept, so Knightdale NC and Boylston MA sit
in one comparison set and the rule correctly reports a discrepancy in a set that should never have
held both.

**LF-3CVT is right.** ID-4 is not wrong on either file; its input is wrong on one.

`fact_tags.csv:52` names the producer: **AI**, over the enum
`residence | mailing | prior | unknown`. The tag cache is per-run and in-memory
(`caches = caches or TagCaches()`), so every verification re-asks. That is also why LF-3CVT's own
ID-4 flipped `open` → `satisfied` between its 14:07 and 16:20 runs while the W-2 extractions stayed
at version 1, created 00:17 and never re-run.

## What the file already knows

Every address-bearing document carries its own date:

| Document | its own date | address |
|---|---|---|
| W-2 | tax year **2023** | Boylston **MA** |
| W-2 | tax year **2023** | Boylston **MA** |
| W-2 | tax year **2024** | Knightdale **NC** |
| Driver's licence | issued 2024-08-30 | Knightdale NC |
| USCIS notice | 2024-09-16 | Knightdale NC |
| Property tax bill | tax year 2024 | Knightdale NC |
| Homeowners insurance | issued 2025-04-04 | Knightdale NC |
| Pay stubs | 2025-03-21, 2025-04-04 | Knightdale NC |
| Bank statements | periods ending 2025-02, 2025-03 | Knightdale NC |

The borrower moved from MA to NC between 2023 and 2024, and the documents say so — the 2024 W-2 from
the same employer already carries the new address. Nothing reads any of this.

## The rule

> Group a borrower's address-bearing documents. Where a document's year is **strictly earlier** than
> that of a document stating a **structurally different** address, the earlier document's address is
> `prior`.

**Demotion only.** It may move `residence` → `prior` and never the reverse. It therefore can only
ever shrink ID-4's gathered set, never inject a new "current" address — the failure mode of a
promotion rule (one bad document redefining the residence) is unreachable by construction.

The AI keeps every case this does not decide.

## Edge cases — each one changed the design

**Mixed date precision.** `tax_year` is a year; `pay_date` / `statement_period_end` / `issue_date`
are full dates. Comparing them needs a convention, and any convention about *when in the year* a W-2
speaks for is invented. Resolved by comparing at **year granularity only** and demoting on a strict
year difference. A W-2 for tax year 2025 issued in January 2026 needs no special case.

**Same year, different addresses.** A genuine mid-year move. No strict ordering → no demotion → the
AI decides, as today.

**The subject property is not the borrower's residence.** `mismo.facts` carries
`property.address_line` = 1013 Whispering Creek Court — tempting as the anchor, and correct on THIS
file only because it is a refinance of an owner-occupied home. On a **purchase** the borrower lives
elsewhere and every current-residence document would "disagree" with the subject property, inverting
the rule. There is no borrower-declared current address in `mismo.facts` (checked). So the design
anchors on nothing — it is purely relative between documents.

**A typo must not read as a move.** If "Whispering Crek Ct" demoted "Whispering Creek Court", a
spelling variance would silently shrink the set and HIDE a real discrepancy — a false negative,
worse than the false positive being fixed. So the difference must be **structural** — street number,
city, or state — under ID-4's existing normalization (`casefold`, `drop_punct`, `collapse_ws`).
Anything less structural is left to the judge, which exists for exactly that distinction.

**Mailing is a different axis.** `residence | mailing | prior` conflates two questions: *is this the
current one* and *is this where they live vs where post goes*. A recent PO Box is not a prior
address. The deterministic rule decides current-vs-prior **only**, and never overrides `mailing`.

**Undated documents.** No date → no demotion → the AI decides.

**Grouping needs a borrower.** The comparison is per borrower, but the tag is produced per document.
A document with no `belongs_to` link cannot be grouped — and LF-WCHG is the precedent, where 16 of 16
documents had zero borrower links and the five ID rules produced nothing at all. No link → no
demotion, never a cross-borrower comparison.

**Co-borrowers at different addresses** fall out of the grouping and need no special case.

## Blast radius

`id.current_address_type` is consumed by **ID-4 alone** (`rule_tags.csv:121`). `id.address_normalized`
is also read by **PR-7** (`rule_tags.csv:201`) — this ticket does not touch the value producer, only
the type. No backfill: tags re-materialize every run.

## Not in scope

The extractions themselves still differ per file — `Knightdale, NC 27545` vs `Knightdale NC 27545`,
one row missing `NC`, the unit reordered — because each file ran its own extraction. ID-4's fuzzy
compare absorbs that. Making extraction reproducible, and persisting the AI tag cache across runs by
the content fingerprint it already computes, are the broader reproducibility work and are separate.
