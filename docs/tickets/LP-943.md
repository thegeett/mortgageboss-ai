# LP-943 — Document display names

- **Ticket:** LP-943 · Phase 4.5 Stage 3 follow-ups, batch 2
- **Source:** the product owner, 2026-09-30: "Add a display name per document type for use in emails and
  notes (for example "Borrower's authorization for counseling"). Cover the five named, and add a test
  that fails for any type used by the library without a clean display name."
- **Closes:** the open items "Five document-type labels are not English where a re-ask now prints them"
  and "`document_label` now crosses a layer" (LP-938 reviews).

## Design

**`app/documents/display_names.py`**, beside the catalog and naming modules (the LP-938 review's
suggested home):
- `DISPLAY_NAMES` holds an explicit name wherever the underscore rule reads badly: possessives
  ("Borrower's authorization for counseling", "Driver's license"), hyphens ("Government-issued ID",
  "E-consent disclosure"), the classifier's discriminators ("Letter of explanation (assets)"), and form
  numbers ("Form 1040 tax transcripts", "W-2").
- Every other type gets a word-level rule: underscores become spaces, acronyms stay acronyms (`ACRONYMS`:
  HOA, ID, IRA, VOE, …), and the first letter is capitalised.
- `display_name(type)` is for a list or a heading. `in_sentence(name)` is for mid-sentence: it lowers the
  first letter unless the first word is an acronym or carries a number ("HOA statement", "W-2" stay).

**Where it is used:**
- the re-ask's document name ("A corrected borrower's authorization for counseling"), in
  `statement_from`;
- the package's row facts and its code-written note ("Service invoice attached"). The model wording the
  notes now sees the display name rather than the slug.

`document_label` (the rule engine's) is unchanged: its reasons are the engine's own wording. The
condition services no longer import it.

**The test** (`tests/documents/test_display_names.py`) runs over every document type the library uses
(41). A name is clean if it has:
- no underscore;
- no stray single letter;
- no acronym in any spelling but its own ("voe", and a sentence-initial "Hoa").

Also, a type whose slug extends another's (`letter_of_explanation_asset` extends `letter_of_explanation`)
must have an explicit name, because its suffix is usually a classifier tag. `appraisal_payment` is the
one where the suffix is a real word, and it is named on purpose.

## Review (of `8af848c6`)

**All 41 library types read cleanly — I rendered every one and checked. Two findings: two document types
share one display name and nothing notices, and `attention.py` still shows the processor the exact strings
this ticket exists to remove, from a helper whose docstring already promises otherwise.**

### Finding 1 — a display-name collision, invisible to the test

`letter_of_explanation_misc` is named "Letter of explanation"; the plain `letter_of_explanation` falls
through to the same string. Measured across all 41:

```
COLLISIONS: {'Letter of explanation': ['letter_of_explanation', 'letter_of_explanation_misc']}
```

Both are in live use on mapped sheets — CR-02 (UWM 5868, 7383) and CR-05 use `letter_of_explanation`,
CR-12 (Champions 245) uses `letter_of_explanation_misc`. So a file can carry two conditions asking for
"Letter of explanation", and in a package note or an email listing both, she cannot tell which document
answers which ask. The classifier distinguishes them; the display name does not.

**On your question (b), this is why I would change `_misc` rather than accept it.** Dropping "misc" is
right — it is a classifier tag, not a word anyone writes. But its two siblings are parenthesised
("(assets)", "(property)"), so leaving the third bare is both the odd one out *and* the collision.
**"Letter of explanation (other)"** matches the family, removes the collision, and costs one word.

**And the test should know.** Cleanliness says nothing about uniqueness, so this slipped through a test
written precisely to catch bad names. A set-equality guard in the shape you used for the discriminator
rule — display names are unique, with an explicit allow-list of any deliberate duplicate — would have
caught it, and would catch the next `letter_of_explanation_x`.

### Finding 2 — `attention.py` shows her the strings this ticket removes

`app/services/attention.py:200` — `_document_label`, whose docstring reads *"A processor's name for the
document, never the raw enum."* It is `document_type.replace("_", " ").capitalize()`:

| document type | her attention list says | `display_name` gives |
|---|---|---|
| `borrower_s_authorization_for_counseling` | **Borrower s authorization for counseling** | Borrower's authorization for counseling |
| `hoa_statement` | **Hoa statement** | HOA statement |
| `voe` | **Voe** | Verification of employment (VOE) |
| `ira_401k` | **Ira 401k** | IRA or 401(k) statement |
| `w2` | W2 | W-2 |
| `government_issued_id` | Government issued id | Government-issued ID |

Strictly this is outside the owner's words ("for use in emails and notes") — it is her screen, not a third
party's. I am reporting it because the function's own docstring promises exactly what `display_name` now
delivers, the substitution is one line, and leaving it means the app spells the same document two ways
depending on which panel she is looking at.

### (c) No slug reaches a third party — and two more reach her

Censused: every f-string interpolating a `document_type`, every `replace("_", " ")` in `app/`, and every
remaining `document_label` reader.

- **Nothing sends a document-type slug outward.** Email bodies are composed from the library's own words
  and item names, as you said. Leaving `verification/rule_engine/reasons.document_label` alone is right and
  now load-bearing for a second reason: `schemas/verification.py:334-338` builds a **label → type round
  trip** out of it, so switching that function would have broken the mapping, not just the wording.
- **Two item-key renderings reach her screen**, a different vocabulary from document types and so a
  separate note rather than part of this ticket: `condition_drafts.condition_label` (the draft dialog's
  side column) renders item keys with `replace("_", " ")`, and so does the "Other drafts this round"
  summary at line 1492. Generated re-ask keys are `reask_<8 hex>`, so those render as
  "6132 reask 3f2a9b1c".
- The rest of the `replace("_", " ")` hits are dev tooling (`eval/worksheet.py`, `generator/emitters.py`,
  the smoke scripts) or non-document values (loan purpose, occupancy).

### (a) Is "clean" tight enough? Tight for the class it targets; four measurable gaps

I fed adversarial names to `_problems` rather than reasoning about it. What passes:

| candidate | verdict |
|---|---|
| `"Letter of explanation"` (a duplicate) | **passes** — uniqueness is unchecked (Finding 1) |
| `"Bank  statement"`, `" Bank statement "`, `"Tax return  "` | **pass** — double, leading and trailing whitespace unchecked. Free to add: `name == name.strip()` and `"  " not in name` |
| `"Cpa letter"`, `"Fha case number assignment"` | **pass** — an acronym outside `ACRONYMS` is invisible |
| `"Bank statement misc"` | **passes** the cleanliness rule; caught only by the *separate* discriminator rule, and only because `bank_statement` is also a library type |

Two of those are inherent and worth stating rather than fixing:

- **The acronym gap cannot be closed by a rule.** You cannot enumerate unknown acronyms, so the test
  protects against *regression* on a known list, not against a new type arriving with an unrecognised one.
  That makes `ACRONYMS` the maintained artefact, and today's 41 contain none that are missing — I checked
  against a suspect list (cpa, fha, va, usda, pmi, ucdp, ein, tin, mers…) and found nothing.
- **The discriminator rule is conditional.** It fires when a type's slug extends *another library type's*.
  A tag-suffixed type whose base is not itself in the library (`verification_of_income_misc`, say) would
  pass. A good proxy, not a closed rule — worth one sentence in the test's docstring, which currently reads
  as though the rule is general.

### (b) The two choices

- **`letter_of_explanation_misc`** — see Finding 1: right to drop the tag, and "(other)" is the way to do
  it without the collision.
- **`voe` → "Verification of employment (VOE)"** — right. Expanding is necessary for a title company or a
  borrower, and keeping the acronym keeps it recognisable to her; `in_sentence` handles it correctly
  ("verification of employment (VOE)"). **But its sibling is now inconsistent:** `verbal_voe` stays
  "Verbal VOE", unexpanded. One of the pair expands and the other does not. "Verbal verification of
  employment" is the agency's own phrasing (B3-3.1-04 is about the verbal VOE), so the consistent choice
  is probably to expand both — but that is a domain-wording call, and CLAUDE.md says to flag a mortgage
  term rather than guess. **Worth putting to the resident expert with the pair side by side**, not decided
  by either of us.

## Review of the follow-up (`219ad4a6`)

**Both fixes verified on my own probes. One finding, and it is created by the `attention.py` change I asked
for: `display_name` now has a caller whose domain is all 166 catalogued types, while the test that

### The two fixes, verified independently

- **The collision is gone.** My own scan over the 41 now reports `COLLISIONS: none`, and restoring the bare
  name fails `test_no_two_library_types_share_a_name`. The empty `_SAME_ON_PURPOSE` allow-list is the right

- **Whitespace is rejected.** I re-ran my adversarial set against **your** `_problems`, imported, rather
  than the copy I had written for the last review — the copy would have told me nothing about your code:
  `"Bank  statement"`, `" Bank statement "` and `"Tax return  "` all now return `['stray whitespace']`.
- **`attention.py`** reads `display_name`, and reverting it fails
  `test_a_failed_document_is_named_by_its_display_name` with `+ Hoa statement failed extraction` — the
  before-and-after in the diff of a failing test, which is the clearest form that evidence takes.
- The docstring now says the discriminator rule is a proxy and that `ACRONYMS` is the maintained artefact.
  That is (a) recorded where the next person will read it.

### Finding — the guarantee covers 41 types; the new caller's domain is 166

`_document_label` is called on any document with `status is FAILED` or the stalest unresolved one
(`attention.py:160, 169`) — **no library gating**. The other two `display_name` callers are gated:
`condition_evidence.py:250` sits inside `statement_from`, reached through `check_document`, and `_takes`
admits only a document type the item lists; the package's `_row_facts` names documents that became
evidence the same way. So this commit gave the function its first ungated caller, and the cleanliness test
is parametrised over `_library_types()` — the 41.

Measured over all 166, the five that read badly:

| document type | the attention panel would say | should be |
|---|---|---|
| `social_security_administration_ssa_89` | "Social security administration **ssa** 89" | SSA-89 |
| `k_1_shareholder_profit_and_loss_transcripts` | "**K 1** shareholder profit and loss transcripts" | K-1 |
| `k1_statement` | "**K1** statement" | K-1 statement |
| `form_4506c` | "Form **4506c**" | Form 4506-C |
| `form_4506t_request_for_transcript` | "Form **4506t** request for transcript" | Form 4506-T |

Only the second is caught by your rule (the stray "K"); the other four pass cleanliness. **`ssa` is the
concrete member of the gap I could only describe last time** — an acronym outside `ACRONYMS` is invisible,
and here is one in the catalogue, on a form whose whole name is an acronym plus a number.

**Not a regression:** `replace("_", " ").capitalize()` produced the same or worse for all five. The point
is narrower and worth acting on — the commit routed a function with a 41-type guarantee to a 166-type
surface, and the guarantee does not hold for five of the rest.

**The fix is cheap and I have measured its whole blast radius:** parametrise the cleanliness test over
`CATALOG` rather than `_library_types()`, add `ssa` to `ACRONYMS`, and give those four an explicit name.
Exactly 5 of 166 fail today, so the test goes green after five one-line entries and then guards the surface
that actually calls the function. Collisions across all 166: **zero**, so the uniqueness test can widen for
free at the same time.
