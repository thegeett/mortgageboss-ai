# LP-425 — Record the OC-2 acceptance: a live rule running ratify-only on an unscored AI tag

## What this ticket is

LP-424's item 2 surfaced that **OC-2 is live (via `_BASE_ACTIVE`) and reads `occupancy.consistent_with_signals`
— an AI tag that is UNSCORED**. It predates the activation gate, so it never passed one. It is safe today only
because OC-2 is **judgmental → it RATIFIES every verdict** (a human signs each), so an unmeasured tag cannot ship
a trusted automated answer. **Geet's decision: ACCEPT it, deliberately and on the record**, rather than
deactivate. **This ticket is DOCUMENTATION + one guard — it changes no behaviour.**

## The acceptance as recorded (ADR-336 resolution)

- **Decision:** OC-2 stays LIVE, ratify-only, on the unscored tag — **accepted, deliberately** (not an
  oversight; it predates the gate — live by history, not a decision).
- **Reasoning:** ratification is real human review — every verdict is signed off, so the unmeasured tag cannot
  produce a trusted automated answer (the ships-mode already mitigates the exact risk). Deactivating trades real
  coverage for an already-contained risk. The problem LP-424 found was the *absence of a decision*, not the
  behaviour.
- **Exit condition:** when `occupancy.consistent_with_signals` is CALIBRATED (labels → accuracy → a Priya bar —
  which OC-1 needs anyway, and which requires REAL occupancy files, ADR-332), OC-2 can move OUT of `_BASE_ACTIVE`
  INTO the gate with a real bar, and the whole `_BASE_ACTIVE` set can be reconsidered (the LP-424 item-2
  re-architecture).
- **Scope:** OC-2 alone (per the sibling check).

**Why extend ADR-336 rather than a new ADR:** ADR-336 recorded the finding and framed it as "Geet's call." This
ticket IS that call; keeping the finding and its resolution in one ADR means a reader sees both together —
cleaner than a new ADR that only says "we accepted 336's finding."

## The pin test — the guard the acceptance depends on

`tests/.../test_lp425_oc2_acceptance.py` pins: OC-2 ∈ `_BASE_ACTIVE`, is judgmental (→ ratifies), the tag is
unscored (OC-1 held on it, no measured bar), OC-2 has no bar, and `ACTIVE_RULE_IDS` = 31. **The load-bearing one
is the ratify-mode:** the acceptance is valid *only while OC-2 ratifies*, so if a future change reclassified
OC-2 to a structural/calculative kind — making it auto-ship on the unscored tag — the test fails loud. That is
the real protection.

Provenance is also left at `_BASE_ACTIVE` in `registry.py` (a comment pointing to ADR-336) — the AS-5 lesson: a
value with no recorded reason gets mistaken for an oversight.

## Assumptions / decisions

- No behaviour change: OC-2 not deactivated, not given a bar, spec/ships-mode/tag untouched. `ACTIVE_RULE_IDS`
  stays 31; every live rule's verdict identical.
- Recorded the acceptance in ADR-336 (extension) + a `_BASE_ACTIVE` comment + a pin test.
- The sibling check is documented (ADR + this doc), not mechanically asserted for "genuinely unscored" (which
  depends on calibration-doc knowledge); the mechanical guard is the enforceable ratify-mode invariant.
