# LP-615 — An unquantized ÷ 12 cost a loan file its snapshot

## What happened

LF-3CVT took its homeowners binder and property-tax bill on 2026-08-21 at 14:05. The 14:07
verification run computed everything — the DTI gate cleared, every rule evaluated, the cross-check
scanned — and then stored **no snapshot at all**:

```
verification_persist_snapshot_failed error=RawPiiAtRestError detail="refusing to persist:
  unmasked account/SSN-shaped value(s) at
    calculations.dti.breakdown[3].amount                   (a 25-digit run),
    calculations.dti.value.housing_payment                 (a 24-digit run),
    calculations.dti.value.total_monthly_obligations       (a 24-digit run),
    tags.by_subject.loan.housing.insurance_monthly.reasoning (a 25-digit run),
    tags.by_subject.loan.housing.insurance_monthly.value     (a 25-digit run)"
```

None of that is PII. The binder states a $1,250 annual premium, and

```
Decimal(1250) / Decimal(12) == 104.1666666666666666666666667
```

The at-rest guard matches `\b\d{9,}\b(?!\.\d)`. The lookahead exempts the **integer** part of a
decimal — so a legitimate `123456789.00` passes — but nothing exempts the fraction: a 25-digit run
opened by `.` and closed by `"` is exactly the shape of an unmasked account number. The guard did
its job on a value that should never have existed.

The unrounded figure also propagated: into the DTI's insurance breakdown line, into
`housing_payment`, into `total_monthly_obligations`, and — because the producer interpolates the
value into its own explanation — into the tag's `reasoning` string as well. Fixing only `value`
would still have refused the write.

## The fix

Quantize every money division that reaches the snapshot to cents, `ROUND_HALF_UP` — the constant and
the rounding every calculator already uses (`verification/dti.py::_ratio`, `ltv`, `mi`, `reserves`).

| Site | What |
|---|---|
| `tag_materialization/derived.py` `_housing_insurance_monthly` | annual premium ÷ 12 — **the one that fired** |
| `tag_materialization/derived.py` `_housing_taxes_monthly` | annual tax ÷ 12 |
| `tag_materialization/derived.py` `_housing_hoa_monthly` | dues ÷ frequency months |
| `services/dti.py::_extracted_monthly` | annual → monthly (serves taxes **and** insurance) |
| `services/dti.py` HOA conversion | dues ÷ frequency months |

**Five sites, not one.** Property taxes escaped only by luck — `5282.58 / 12 = 440.215` terminates.
A $5,000 bill gives `416.666…` and refuses the write just as hard; every quarterly HOA (÷ 3) does
too. Fixing only the field named in the log would have left three loaded.

**Both halves of each pair, rounded identically.** Three of the five are the same number computed
twice: the tag producer and the DTI's own conversion. The tags are documented as agreeing-or-
abstaining and *never looser than* the calculation, and `dti.py` already carries a drift-guard
keeping the HOA frequency maps byte-identical. Rounding one side and not the other would break that
by a fraction of a cent, so both move together and a test pins them to one expected value.

## What this does NOT fix

The guard's other over-flag: a genuine ≥9-digit identifier in a plain `Field.value` — an insurance
policy number, an un-hyphenated ZIP+4 — still refuses the persist. That is deliberate, documented in
`persistence.py`, and pinned by `test_raw_account_number_run_is_rejected`. Deciding which ≥9-digit
identifiers are safe at rest is a per-field data decision, not a pattern one. Untouched here.

## Tests

Four existing assertions in `test_insurance_wiring.py` moved from `"100"` to `"100.00"`. One,
`test_non_whole_division_keeps_full_precision`, **pinned the defect** — it asserted the full
repeating expansion. Its stated intent was "never rounded to 0/108", i.e. never collapsed to a whole
number, and cents honour that intent exactly; it is renamed and now asserts `"108.33"` plus the
original never-a-whole-number property.

New, in `test_snapshot_persists_lp566.py` — the file that exists because "the snapshot must actually
persist, proven per field, not assumed". It covered identifier-shaped values arriving in *extracted
fields*; this is the second way to lose a snapshot, a value the snapshot **computes itself**:

- each of the five divisions, at the real LF-3CVT premiums, quantized → the guard accepts, asserted
  on the value **and** on a reasoning sentence containing it;
- the same divisions unquantized → the guard refuses, with property taxes skipping itself under the
  condition that names why it hid the bug for a day (no 9+ run even unrounded);
- the tag side and the DTI side of a $1,250 premium both landing on `104.17`.

Full suite: 5544 passed, mypy clean.

## Note

Staging ran with this defect from the moment LF-3CVT's binder landed. The findings are unaffected —
rules read the in-memory snapshot — but that run has no persisted record behind it, and re-running
after deploy is what produces one.
