# LP-103 — Right-size extraction token budgets for unbounded document types

- **Ticket:** LP-103 (follow-up to LP-102)
- **Status:** Completed
- **Date:** 2026-07-03

## Summary

LP-102 fixed pay-stub extraction truncating (budget too small for its verbose output) and added a
shared truncation guard. A budget **audit** across all ~18 extractors then found pay stub was not a
one-off: the same "unbounded catch-all output + 4096 scaffold budget" shape exists on other types —
including **`investment_account`, which was already truncating on LF-6T3N** (a silently-empty asset
document). This ticket right-sizes the flagged types and documents the sizing rule. See **ADR-229**.

## The audit (the tiers)

**Unbounded "capture every X" catch-all, still at 4096 — RAISED to 8192:**

| Type | Output shape | Note |
| --- | --- | --- |
| `investment_account` | itemized Holdings (each position: ticker, shares, value) | 🔴 **confirmed live failure** on LF-6T3N — a silently-empty ASSET doc |
| `retirement_account` | same "Holdings" shape (401k/IRA funds) | 🔴 same shape, same budget |
| `profit_and_loss` | revenue lines + each expense line item + COGS | 🟠 unbounded |
| `purchase_agreement` | contingencies / concessions / addenda / dates | 🟠 semi-unbounded |

**Correctly sized — LEFT UNCHANGED (no blanket raise):**

- Already generous for their density: `tax_return` (16384), `bank_statement` (8192), `pay_stub`
  (8192, LP-102), `divorce_decree` (6144).
- Bounded / semi-bounded fixed-form: `w2`, `voe`, `letter_of_explanation`, `homeowners_insurance`,
  `mortgage_statement`, `hoa_statement`, `property_tax_bill`, `form_1099` (4096), `drivers_license`
  (2048). The LP-102 guard is their backstop if one ever overflows.

## Why investment_account is a correctness bug, not cleanup

A brokerage statement truncating means its itemized holdings never populate → the extraction comes
back empty (`NEEDS_REVIEW`). Assets feed **reserves / down-payment verification**, so a silently-empty
brokerage statement **understates the borrower's assets** — a truncation that changes the answer.
That is why this is a live fix, not just prevention.

## The fix

- `investment_account._MAX_TOKENS` 4096 → **8192** (+ comment: unbounded holdings → long JSON; observed
  truncating on LF-6T3N).
- `retirement_account._MAX_TOKENS` 4096 → **8192** (same holdings shape).
- `profit_and_loss._MAX_TOKENS` 4096 → **8192** (unbounded expense-line output).
- `purchase_agreement._MAX_TOKENS` 4096 → **8192** (semi-unbounded contract terms).
- No other budget touched.

## Why not blanket-raise everything (the design decision)

A right-sized per-type budget encodes a size **expectation**, so a truncation against it is a
meaningful **anomaly signal** — that signal is how the pay-stub and investment-account bugs were
found. A uniform high ceiling would blind the system to output size and let a runaway output generate
expensively before anything stopped it. The LP-102 shared guard is the backstop that makes
right-sizing (not over-provisioning) safe: a mis-sized type still fails **honestly** (retry once at
16384 → honest truncated status), never silently.

## The documented sizing rule

Added to `app/ai/extraction/model_call.py` (where the guard + budget policy live), so the next
extractor is right-sized from the start:

- **Unbounded catch-all** ("capture every X" — a variable-length list of line items with snippets)
  → **generous** budget (8192, or 16384 for the densest like tax_return).
- **Bounded fixed-form** (a fixed field set, no unbounded list) → **small** budget (2048–4096) is
  correct and intentional.
- The LP-102 guard is the backstop for any mis-sizing — so right-size by shape, don't blanket-raise.
