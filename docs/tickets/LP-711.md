# LP-711 — editing was built, and unreachable with a mouse

- **Ticket:** LP-711
- **Status:** Done (2026-09-06)
- **Reported by:** the user, from the running app
- **Scope:** Frontend — `reviewer-fields.tsx`, `review/page.tsx`

## The report

> if we make row clickable then can we also select text and update value if we want. I hope
> previous few ticket we worked on editing part on extracted data plus soft delete and undo.

They remembered correctly. **All of it was built in LP-703** — correct a value, remove a
field (soft delete, undoable), add a field the model missed, and undo any of them, with the
corrections reaching the rule engine rather than only the screen.

**And there was no way to reach any of it with a mouse.** `setEditing` was called from
exactly two places, both key handlers: `E` to correct and `R` to reject. A processor working
with a mouse could select a field, see its box, read the quoted text, and change nothing. The
whole feature sat behind a shortcut discoverable only by opening the `?` sheet.

That is the LP-703 review's finding one layer out. That review found `useRevertFieldReview`
had existed since LP-UI-033 with **no component calling it** — undo built and unreachable.
This is the same shape: editing built, and reachable only if you already knew the keystroke.

## What was built

**An `Edit` control on the SELECTED row**, beside `Undo`, opening the same editor the `E` key
opens.

**Through the same rule.** `openEditor` now takes an optional field key and resolves it with
`editableFieldKey` — the function the LP-703 review extracted precisely so the mouse and the
keyboard cannot disagree about which fields are editable. That disagreement is the keyboard
lockout that review found: `setEditing` on a list field mounted no editor while
`shortcutsEnabled` had already switched the keyboard off, and nothing could clear it.

**Naming its own field rather than trusting the selection to settle.** The control passes
`field.key`; it does not rely on `selected` having updated within the same click.

**On the selected row only.** A control on forty rows at once is the chrome LP-UI-032 spent a
ticket removing.

## Text selection

Unaffected, and pinned by a test. Nothing calls `preventDefault` on the row click, so dragging
across a value to copy an account number still works — the click that ends the drag also
selects the row, which the user has confirmed is what they want. The test asserts
`defaultPrevented` is false, because a future `preventDefault` would break copying silently.

## The two consequences of a clickable row, accepted deliberately

Raised by the LP-710 review and put to the user, who took both:

- clicking `Undo` on a row that is not selected also selects it, and selection is not free —
  it moves the DOCUMENT to that field's page, mid-action;
- the pointer cursor now covers the value text.

## Verification

- 227 reviewer tests; the full frontend suite green, biome and tsc clean.
- Four mutations, all caught: no control (3 failures), a control on every row (4), naming the
  wrong field (1), showing while that row's editor is already open (1).
- End to end in the running app: clicking the value `$15,000.00` — not the label — selects the
  row and draws its boxes; `Edit` appears; clicking it opens the editor prefilled with
  `$15,000.00`, offering Save, "Can't verify" and "Not on this document".


## Review (2026-09-06)

### The mouse and the keyboard still disagreed, in the case the ticket was unsure about

The ticket's central claim is that routing both paths through `editableFieldKey` means they
"cannot disagree about which fields can be edited". They still did, and the ticket's own
item 2 found the symptom while mis-stating the cause: *"the keyboard has the same
restriction, so this is pre-existing rather than new."* It does not.

`editableFieldKey` asks only whether a field is **scalar**. The Edit control was placed
inside a block gated on `kind === "scalar" && value && value !== EMPTY_VALUE`, and the
verdict editor sits **outside** that block. So on a field the model returned empty:

- `E` opens the editor — measured, the editor renders,
- and no Edit control is drawn, so the mouse cannot.

It is also the field a processor most needs to reach. The model found nothing, so supplying
the value is the whole point — and `AddField` cannot offer it either, because the key is
already in the extraction and `addable_fields` excludes it.

**Undo went the same way.** It sits in the same block, so a verdict recorded on an empty
field by keystroke could not be withdrawn from the screen at all. That is the LP-703 finding
(`useRevertFieldReview` built and unreachable) reappearing through placement rather than
through omission.

The empty-value rule is now on the **mark alone**, which is what its comment always argued:
"a mark on a field with no value would be telling a processor to go and read a dash" is a
sentence about the mark. Edit and Undo are gated on `scalar`, matching the rule the keyboard
uses. A control asserts the mark still does not draw on an empty field, with a positive
control that it draws when there is a value.

### `openEditor` had two spellings of one rule

`requested ? editableFieldKey(fields, requested) : editableSelection()` — and
`editableSelection` is `editableFieldKey(fields, field.selected)`. The same function with a
different argument, written twice, which is the shape this ticket cites the LP-703 review for
catching. One call now: `editableFieldKey(fields, requested ?? field.selected)`.

### Nothing held the rule inside `openEditor`

Replacing `editableFieldKey(fields, ...)` with the bare key passed the entire suite. The
mouse test only asks whether a button was drawn, and `review-queue.test.ts` tests the rule in
isolation from the only caller that matters. What the rule prevents is documented on the page
and is severe: `E` on a list sets `editing` behind an editor that never mounts while
`shortcutsEnabled` has switched the keyboard off, and every callback that could clear it
belongs to that editor — the reviewer's keyboard is dead until reload. There is now a test
that presses `E` on a selected table and then asserts `?` still opens the sheet.

### The page layer, which is where the bug lived

LP-711's defect was **wiring**: a capability with no control, in `review/page.tsx`. Everything
holding the fix sat one layer below it — a component test that `onEdit` is called, and a unit
test of `editableFieldKey` — and both passed for the entire period the feature was
unreachable, because neither knows whether the page passes an `onEdit` at all.
`review-page.test.tsx` now renders the page and clicks a value, then Edit, then Save, and
asserts the mutation carries the corrected value. Removing `onEdit={openEditor}` fails three
tests.

### Text selection: the assertion is weaker than the claim, and here is the other half

`defaultPrevented === false` on a synthetic click is real but narrow. What actually breaks
copying an account number out of a row is `user-select: none` — the utility someone reaches
for when a row becomes clickable and text starts highlighting on double-click. A synthetic
click cannot see it and jsdom cannot perform a drag, so the class is pinned directly instead.
Both halves are now tested; neither is the gesture itself, and that limit is worth stating
rather than papering over.

### Confirmed rather than changed

The `busy` flag (item 4) is sound: it disables Edit, Undo and the editor's own buttons
together, and every handler that fires a mutation clears `editing` in the same call, so no
settled mutation leaves a control clickable into a stale editor.

### Mutations

Nine, eight caught: the page not passing `onEdit`, `openEditor` dropping the editable rule,
Edit back inside the empty-value gate, the mark drawn on an empty field, Edit on every row,
Edit shown while that row's editor is open, `select-none` added to the row, and the row's
click handler removed.

One survivor, recorded rather than papered over: `openEditor` ignoring `requested` and always
using `field.selected` passes. It is equivalent given the call sites — the Edit control only
renders on the selected row, so `requested` cannot differ from the selection today. The
parameter is defensive against a future control that names a row it does not sit on, and no
test can hold it while that is true.
