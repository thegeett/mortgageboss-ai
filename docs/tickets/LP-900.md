# LP-900 — The frontend tests never ran in CI

- **Ticket:** LP-900 · the first of three from the palette research (LP-900, LP-901, LP-902)
- **Status:** Built — awaiting review
- **Date:** 2026-09-11
- **Scope:** `.github/workflows/frontend-ci.yml`, `docs/development-workflow.md`, `docs/project-structure.md`
- **Migration:** none

---

## What was found

`frontend-ci.yml` ran `pnpm lint`, `pnpm typecheck` and `pnpm build`. It never ran `pnpm test`.

That mattered more than it sounds, because the suite is where the design system is enforced:

- `lib/design-tokens.test.ts` — no Tailwind palette-scale classes (`bg-gray-500`) and no
  `bg-`/`text-`/`border-white`;
- `tailwind.config.test.ts` — every colour token the config names exists in the stylesheet;
- `lib/a11y-contrast.test.ts` — no faded text tokens (`text-muted-foreground/80`);
- `ledger-assets.test.ts` — the design-doc reference copies have not drifted.

ADR-389 sets the rule — colour, weight and radius have exactly one source, the token layer — and
says a check has to enforce it; `design-tokens.test.ts` and `tailwind.config.test.ts` are that
check. The other two are neighbours, not ADR-389's: `a11y-contrast` is LP-UI-036, `ledger-assets`
the reference-copy drift guard. Enforcement that runs only when somebody remembers `pnpm test` on
their laptop is a convention. A PR could reintroduce `text-gray-400` and CI would stay green.

It was also a known gap: ADR-087, which adopted vitest, left wiring `pnpm test` into CI as "a small
follow-up". This is that follow-up.

## The change

One step, between typecheck and build:

```yaml
- name: Run tests (vitest)
  run: pnpm test
  env:
    TZ: UTC
```

`TZ` is pinned on purpose. GitHub's runners are UTC already, but pinning makes that a stated
property rather than an accident of the runner image — and it gives a developer the line to
reproduce CI locally, which `development-workflow.md` now says: `CI=true TZ=UTC pnpm test`. The
`CI=true` matters too — the runner sets it, and under it vitest fails a stray `.only` instead of
running just that test and passing.

## Would it have gone red?

**No — measured before the change.** Full suite on the unchanged tree:

| Run | Result |
| --- | --- |
| local TZ (EDT) | 127 files, **1503 passed** |
| `TZ=UTC` | all passing except two files mid-edit by LP-901 at the time; no timezone-dependent failure |
| `CI=true TZ=UTC` (review, full run) | 127 files, **1503 passed** |

Turning a check on over a red suite would have blocked every frontend PR on day one; it had to be
green first, and it was.

## Cost

About five minutes on the Raspberry Pi this was built on (`pnpm test`, 297s). GitHub's `ubuntu-latest` is several
times faster; expect well under two minutes. The step runs before `next build`, so a failing test
does not wait on the production build.

## Environment note

This machine (the Pi on `raspberrypi-work`) had no Node at all. Node 20.20.2 — the major CI pins —
was installed under `~/.local/lib/nodejs` with `node`/`npm`/`npx`/`corepack`/`pnpm` linked into
`~/.local/bin`, and pnpm pinned to 10 via corepack to match the lockfile. No system packages changed.

## For the reviewer

- The step is placed so lint and types fail fastest, tests next, build last.
- The path filters were widened in review — see below.

## Review — REVIEWED

The step itself is right: correct position, correct working directory (the job's default), and
`TZ` reaches the vitest workers because they inherit the environment. One finding in the workflow,
and the rest are claims that said more than was true.

### 1. The suite reads files the workflow does not watch

Four tests read files **outside `frontend/`**, and the `paths` filter only watched `frontend/**`:

| test | reads |
|---|---|
| `lib/loan-files/extraction-contracts.test.tsx` | `backend/app/ai/prompts/extraction/*.txt` |
| `components/file/documents/reviewer/page-budget.test.ts` | `backend/app/services/page_render.py` |
| `components/file/documents/reviewer/split-agreement.test.ts` | `backend/app/schemas/preferences.py` |
| `ledger-assets.test.ts` | `docs/design/ledger/assets/**` |

So a PR touching only one of those files could turn a frontend test red without Frontend CI
running at all. The red would then show up on the next, unrelated frontend PR. That includes the
drift check the ticket counts as enforced: an edit to a ledger asset alone never ran it. This is the
same "enforcement that only runs sometimes" this ticket exists to close, one level up. The build's
"path filters and triggers are as they were" was exactly the gap.

**Fix:** all four are added to both `push` and `pull_request` filters, with a comment at the top of
the workflow naming which test reads each and saying to extend the list. Found by searching every
test for `import.meta.url`-relative and `process.cwd()`-relative reads that leave `frontend/`. The
other whole-tree scans (`design-tokens`, `a11y-contrast`, `no-apology`, `layout`, …) root at
`frontend/`.

### 2. "CI and `TZ=UTC pnpm test` are the same run" — not quite

GitHub sets `CI=true`, and vitest 4.1.8 defaults `allowOnly` to `!isCI`. A stray `it.only` therefore
**passes locally**, running just that test, and **fails in CI**. The local command in the workflow
comment, `development-workflow.md` and this ticket is now `CI=true TZ=UTC pnpm test`. The workflow
comment also claimed pinning `TZ` stops a date test "passing here and failing on a laptop". It
doesn't: a laptop running plain `pnpm test` still uses its own zone. Reworded to say what the pin
actually buys.

### 3. Claims corrected in this ticket

- **ADR-389 was cited for something it does not say.** It does not name these tests, and two of the
  four (`a11y-contrast`, LP-UI-036; `ledger-assets`) are not about it. Reworded to show which tests
  guard which rule. **ADR-087**, which adopted vitest and left CI wiring as "a small follow-up", is
  the ADR this ticket actually closes. It was not cited; now it is.
- **The ADR-389 guard is partial, and nothing else closes it.** ADR-389 names its own blind spot:
  an arbitrary value (`bg-[…hsl(217_91%_60%)…]`, a hex) passes a `gray-*` scan while breaking the
  rule, "so the lint rule that enforces it must match arbitrary values too". `design-tokens.test.ts`
  matches palette scales and `bg`/`text`/`border-white` only. No tree-wide test matches arbitrary
  colour values: `toast.test.ts` bans hex, but only in the toaster's own class map. So CI now
  enforces the palette-scale half of "colour has one source", not the whole of it. Recorded, not
  fixed: it is a new guard, outside a ticket about running the existing ones.
- `design-tokens.test.ts` bans `bg`/`text`/`border-white`, not "`*-white`" (`ring-white` and
  `fill-white` pass it).
- "The step runs before the slowest step" — nobody measured `next build` against the suite, and on
  this Pi the suite is five minutes. The ordering argument doesn't need the claim, so it now says
  only that a failing test doesn't wait on the build.
- The `TZ=UTC` row in "Would it have gone red?" was a partial run. The full run is below.

### 4. Docs the build did not update

- `README.md` still described Frontend CI as "Biome lint/format, `tsc` type checking, and a
  production `next build`", and path filters as "each pipeline only runs when its area changes".
  Both were updated.
- `development-workflow.md` said `frontend-ci.yml` "runs on changes under `frontend/`". It now
  names the extra paths and the rule for adding one.
- Widening the filters moved `node-version` from line 38 to 54, and the Node pin is cited by line
  number. Updated in `frontend/Dockerfile` and `docs/worktree-setup.md`. **Left as written:** the
  `frontend-ci.yml:38` references in ADR-359 (`decisions.md`) and `docs/recon-run-commands.md`.
  Both are dated records that were true when written (the recon also still says there is no
  frontend Dockerfile).
- **Not changed, flagged:** `CLAUDE.md` still says CI is "biome/tsc/build". It is the project
  instruction file, so a peer review shouldn't edit it. It needs "biome/tsc/vitest/build" from
  whoever owns it.
- The job is still named "Lint, Type Check, and Build". Not renamed on purpose: a branch-protection
  required check matches the job name, and renaming it would leave a required check that never
  reports.
- The build commit's message repeats two of the claims above (ADR-389; "the same run"). A commit
  message can't be corrected without rewriting history, so this section is the correction.

### Verified

`CI=true TZ=UTC pnpm test` on the review tree: **127 files, 1503 passed**, 296s on the Pi. With
the build's EDT run, that is the same suite green in two zones. It also rules out a `.only`, since
`CI=true` would have failed one. `pnpm lint` and `pnpm typecheck` are clean. The widened workflow
parses, both filter lists are identical, and all four added paths exist.
