# LP-857 — take the next phase off the page

Status: spec. Net deletion. Screens 1 and 9.

Epic: [`docs/domain/communication/v1-epic.md`](../domain/communication/v1-epic.md) · Screens: [`v1-screens.md`](../domain/communication/v1-screens.md) · Spec: [`comm-v1-draft-only-spec.md`](../domain/communication/comm-v1-draft-only-spec.md)

## The report

> "In this version I want to limit to draft only, no reminder or nothing... No receiving, sending,
> secure upload link, reply email and all. We will do it in next phase."
>
> "No Write to another party in v1."

## The page must not offer what the version cannot do

Half the confusion in the current Communication page comes from controls that exist as an interface
with **nothing behind them**. `mail_transport` is the standing example — *"an interface with no
provider behind it, and that is the ticket"* — and a processor cannot tell the difference between a
feature that is broken and one that was never wired.

Three things come off.

### 1. `UploadLinkPanel` and `InboundMessagesPanel`

Both mounted in `app/(protected)/loan-files/[id]/communication/page.tsx`.

**Flag out, do not delete.** LP-815 and LP-807 are written and tested and return in the phase that
brings sending and receiving back. Deleting them buys nothing and costs the review that already
happened.

### 2. `PartyRequestButton` and most of `PartyRequestDialog`

The button goes. But **it was the only place a missing address could be added**, and LP-820 measured
the problem: of 166 document types, **13 across title, agent, CPA, insurer and employer had no
address anywhere in the schema.** The blocker was never "no way to compose" — it was "nobody to send
to".

So the address form is **lifted, not deleted**.

## The address moves to where it blocks something

A party draft with no address is **still created** — refusing would lose the record that the
document was asked for — and appears in the list marked *cannot be sent yet*. The draft itself
carries the form:

> **To** — No address on file for the title company
> *Who are they, and where do we write?*
> Name: `Acme Title` · Email: `closings@acmetitle.com` · `[Save address]`
> *Saved to the file — used for every future message to this party.*

This is the improvement hidden inside removing the button: **the address is asked of the person who
knows it, at the moment it blocks them**, instead of in a panel nobody visits. `add_party_address`
and its form both already exist inside `party-request-dialog`; this lifts them out and drops the
rest.

## Also gone, and worth saying out loud

- **No reminders.** LP-814's clock does not start. Marking a draft sent stamps `requested_at` and
  nothing else runs off it in this version.
- **No `delivered` / `failed`.** They remain valid enum values with no code path that can reach
  them. The furthest the UI goes is `Marked sent by Priya`.
- **No "Send".** Covered in LP-855; repeated here because the page is where the temptation lives.

## What it must not break

- LP-835's party drafts still build, still join the list, still open in the same modal. **Only the
  way in changes** — from a standalone dialog to the request flow plus an inline form.
- `add_party_address` keeps its endpoint and its semantics. The saved address is still a fact about
  the file, used for every future message to that party.
- Flagged-out panels stay compiled and their tests stay green. A flag that rots is a deletion with
  extra steps.

## Acceptance

1. The Communication page shows exactly two buttons: **Request documents** and **Compose**.
2. Requesting a title document with no address on file creates a draft, lists it as *cannot be sent
   yet*, and the draft shows the address form.
3. Saving the address makes the draft sendable without re-requesting the document.
4. `UploadLinkPanel` and `InboundMessagesPanel` are unreachable with the flag off and render
   unchanged with it on; their tests still pass.
5. The upload link is not mentioned anywhere in a generated body while the flag is off.

# What was built

Status: **done**. Commit message starts `LP-857 —`.

## The flag

**One setting, not two.** `receiving_enabled` (off) in `app/core/config.py`, served by a new
`GET /api/v1/capabilities` and read by the page through `useCapabilities`.

A `NEXT_PUBLIC_` twin on the frontend would have been smaller, and wrong. The same fact decides two
things a processor and a borrower see in different places: whether the page offers the upload and
inbound panels, and whether a generated request **promises a borrower an upload link** — and the
second is decided on the server when the body is rendered. Two flags with two names could hide the
panel and keep the promise, which is the failure this ticket removes rather than a new place to
introduce it.

`false` is the answer while loading and on error. The safe default is the restrictive one: a panel
that flashed in before the answer arrived would be a control a processor could click on a version
where the thing behind it does not exist.

## What came off the page

- `UploadLinkPanel` and `InboundMessagesPanel` — behind the capability. **Their tests still run**,
  which is what stops the flag being a deletion with extra steps.
- `PartyRequestButton` — deleted, along with `PartyRequestDialog`. The page is two buttons.
- **A third thing the ticket does not list**, found while reading: the *"Add a secure upload link"*
  button inside the message modal, whose own comment had been saying *"LP-857 takes it off the page
  with the rest of the next phase"* since LP-834. It is not cosmetic — it **mints a link and writes
  it into the body**, so leaving it would break acceptance 5 by a click rather than by a template.
  Gated on the client and **refused on the server**: a hidden button is a claim about the only
  caller we happen to know about.

## The address, lifted

`PartyAddressForm` (`components/file/communication/party-address-form.tsx`) is the unreachable-party
branch of `PartyRow`, moved. It renders **inside the draft that is blocked on it**.

Two server changes were needed for it, both narrow:

- **`party` on `MessageDetail`.** The modal has to know which party an address is being saved for,
  and `template_key` cannot answer — five parties share `document_request_third_party`, so a client
  deriving it would file a lender's address under the title company. Same rule as `_party_of`: the
  stored column first, the template key as the fallback for rows written before it existed.
- **`suggested_recipient` resolves a party address.** The old rule suggested nothing on a party
  draft, reasoning that such a draft *"carries the title company's address on the row"*. That holds
  only when there **was** one at creation — LP-841 deliberately creates the draft either way — so
  those drafts reached the modal with an empty box and no hint of why. Resolved through
  `_party_address`, the same function the draft's own creation uses. **The borrower is never
  suggested on a party draft**, which is what the old narrow rule was protecting, and there is a
  test with a borrower address in the fixture to leak.

The list says **`Draft · cannot be sent yet`** for an unaddressed outbound draft. A word, not only
a colour.

## What the tests caught

- **Two conditions on the address gate were untestable as written, and one was decoration.**
  `!counterparty && !suggested_recipient` looked redundant with "the box is empty" — at open time
  they agree, because an addressed draft seeds the box. They part company when a processor **clears**
  it, and "No address on file" would then be false for a file that has one and is offering it. Two
  tests now pin that. The `is_editable` condition really was redundant — the form renders inside the
  `is_editable` branch — so dropping it left every test green. Removed rather than kept: a guard no
  mutation can find is decoration. The sent-message case is asserted against the branch that
  actually enforces it, and a structural mutation that hoists the form out of that branch fails it.
- **`party !== null` let a payload with no `party` field through**, because `undefined !== null` —
  the form rendered with no role to save against, which is an address filed under nothing from a
  control that looked ordinary. Found by two existing fixtures that simply omit the key. Now
  `Boolean(data.party)`, with a test that deletes the key.
- **`parties[0]` is not the borrower**, and `bank_statements` routes to the PROCESSOR, which never
  becomes a draft. Both fixtures were asserting about a party that was not in the request. The
  helper names the party instead of indexing.
- **Four sibling suites broke on unmocked hooks** (`usePolishDraft` from LP-856, then
  `useCapabilities`) reaching for a QueryClient those trees do not have. Mocked at rest, except
  LP-834's own cases in `message-dialog.test.tsx`, which set `receiving: true` — they are testing
  the flagged feature, which returns.
- **LP-834's whole suite and one LP-853 case called the endpoint that now refuses.** Both turn the
  flag on, with the reason written down. The LP-853 one matters: it asserts the 409 *names editing*,
  and the new check runs first, so without the flag it would have passed on the wrong refusal.

## Claims in the ticket I checked rather than assumed

- **"No `delivered` / `failed`."** True. `DELIVERED` is set nowhere. `FAILED` is reachable only
  through a transport failure or `bounce_handling`, and `register()` — the only way a provider
  enters `_REGISTRY` — **has no caller**, so `transport_for` always returns None and `transmit`
  never sends. "No Send" holds for the same reason.
- **"No reminders. LP-814's clock does not start."** True of anything automatic: there is no Celery
  beat schedule and no reminder task. **But there is a live Reminders page** with a nav entry, and
  `/reminders` serves suggestions computed at read time. That is not an automated reminder and it is
  not on the Communication page, so it is outside this ticket — but "No reminders" reads as a
  stronger claim than the product supports, and somebody should decide about that screen.

## Not done

- **`usePartyRequests` and `useBuildPartyDraft` now have no callers.** Dead client hooks, not
  dangling references — the endpoints behind them exist and work, and LP-835's backend returns.
  Deleting them is scope this ticket does not claim. Named rather than swept.
- **The two `PARTY_LABEL` maps stayed two.** The lifted one says "Title company" and the timeline's
  says "Title co." because a fixed-width column has a different constraint from a sentence. That
  predates this ticket; merging them would need a decision about which words win.
- **LP-UI-047 (narrow widths) is untouched**, as instructed. The address form uses fixed `w-48` /
  `w-64` inputs inside `flex-wrap`, copied from the dialog it came out of — the same behaviour at
  the same widths, not new breakage.

## A pre-existing flake, unrelated to this ticket

`tests/verification/snapshot/test_e2e.py::test_stage1_end_to_end_build_persist_load` failed once in
a full run and passed 8/8 in isolation. Its at-rest sweep is
`re.search(r"\d{3}-\d{2}-\d{4}|\b\d{9,}\b", blob)`, and what matched was `721383570012` — **twelve
digits, which is the length of a UUID's last segment**, delimited by a hyphen and a quote. A
`uuid4()` whose final group happens to be all decimal digits trips it, at roughly (10/16)^12 ≈ 0.5%
per UUID per run. Not touched here; reported so it is not rediscovered as somebody's change.
