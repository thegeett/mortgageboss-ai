# LP-399 — The owner-match scenario worksheet for Priya's blind labeling

## What this ticket is

The labeling instrument for AS-6's two-directional measurement. LP-398 built the negative-case fixture (6
negatives + 2 positive controls) and probed it — N1 (a DIFFERENT middle initial) came back `yes`, the tolerance
possibly swallowing a relative. This generates the committable worksheet so Priya labels all 8 **blind**, giving
`stmt.owner_matches_borrower` a two-directional score (n=13 with the 5 existing positives) and the evidence for
the AS-6 ratify→auto revisit — or a prompt-fix if she rules the tolerance wrong.

## Acceptance criteria (met)

- 8 labelable rows for `stmt.owner_matches_borrower`, one per statement, committable (synthetic, no PII).
- Context shows BOTH the account holder AND the loan's borrower roster (judgeable); a neutral prompt that does
  NOT restate the AI's tolerance rules.
- NO prediction / expected answer / AI reasoning reaches the sheet (asserted against LP-398's published values
  and the clear-cut constants); N1/N5 blind.
- Row order does not group negatives-then-positives; deterministic + keyless; other worksheets byte-unchanged;
  `ACTIVE_RULE_IDS` unchanged (24); full suite green.

## Phase 0 — the report

- **The context column.** Each row shows the statement's own fields (`account_holder_name`, `bank_name`,
  `ending_balance`) PLUS the loan's borrower roster (`loan_borrowers: Jordan A Rivera; Robert Chen`), then the
  neutral question. The roster is essential: `build_worksheet`'s document context (`_doc_context`) is the
  statement's fields ONLY — without the roster injected she cannot compare, and would label `unknown` meaning
  *"I can't tell"* rather than a judgment (the LP-390-3 missing-field lesson). The roster is a snapshot fact
  (`loan_borrower_roster`), injected loan-level into every row.
- **The label prompt (quoted):**
  > Does the account holder on this statement match one of the loan's borrowers listed above? yes / no / unknown

  It asks ONLY the core question and deliberately does **NOT** say "be tolerant of middle initials / nicknames /
  maiden names" — restating the AI's tolerance clauses would hand her the answer key. `yes / no / unknown` are
  the tag's allowed values, not a prediction.
- **The row order — deterministic, non-grouping.** `build_worksheet`'s natural order is insertion order
  (N1…N6, P1, P2) — which groups all 6 negatives then the 2 positives, telegraphing which are which. The sheet
  uses a fixed permutation `(N3, P1, N1, N6, P2, N2, N5, N4)`: the two positive controls sit at positions 2 and
  5, splitting the negatives so no run of negatives is contiguous. Deterministic (reveals nothing) — not
  alphabetical or by case-number (both of which would re-group).
- **The anti-anchoring guard.** LP-398 published all 8 AI answers and the clear-cut expectations live in code
  (`CLEARCUT_EXPECTATIONS`). Neither can reach the sheet: the context is built by `build_worksheet` from the
  snapshot ONLY (no AI), the roster is a snapshot fact, `golden_label` is blank, and N1/N5 carry no encoded
  answer. Verified by grep (below).

## Assumptions, decisions & gaps

- **No ADR.** Instrument generation. The context is judgeable WITH the roster without hinting — showing the
  roster does not make the intended answer obvious for the negatives (N1 "Jordan M Rivera" vs "Jordan A Rivera"
  is a genuine judgment, not a giveaway), so no scenario is mis-designed. (An ADR would only follow if she rules
  the N1 tolerance wrong — then the prompt's middle-name clause is re-specified, its own ticket.)
- **Committable** — invented identities, no PII (unlike the gitignored DB worksheet, LP-392).
- **Reused `build_worksheet`** (predictions excluded by construction) + injected the roster loan-level; did not
  touch the LF-6T3N or income-scenario worksheets, the fixture, the prompt, or any tag/rule.
