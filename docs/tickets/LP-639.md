# LP-639 — a confident `unknown` cannot be explained

- **Ticket:** LP-639
- **Status:** In progress
- **Date:** 2026-09-01
- **Found on:** staging `LF-ZE9N` — a Closing Disclosure that classified as `unknown` at 0.85
- **Scope:** Backend — `documents/catalog.py`, `tasks/document_processing.py`

## The report

`CD - 7112 -1.pdf` is a text PDF of a Closing Disclosure, 79 KB, sent to the classifier complete —
no trimming, well inside the 15-page cap. The catalog has `closing_disclosure` as a Tier 1 type with
a good indicator. The classifier answered **`unknown` at 0.85 confidence**, and the document
completed with no flag.

**Nobody could say why**, and that is this ticket rather than the misclassification itself.

The only surviving evidence of what the model thought is `document_name` — its own free-text name for
the document, produced BEFORE the constrained pick, which LP-463 records as "a more reliable signal
than the constrained pick". It is deliberately never logged and never stored, because it is free text
that can quote a borrower's details.

So a confident `unknown` is an outcome with no account of itself, and diagnosing one means inferring.
The inference was wrong twice on this file:

* from `has_full_text=False`, which looked like "the PDF has no text layer" and is in fact
  meaningless — LP-463 stopped producing `full_text`, so it reads `False` for every document;
* from that, "a low-resolution scan", of a file the processor confirmed is a text PDF.

Two hypotheses, both confidently reasoned, both wrong, because the one fact that would have settled
it is unloggable.

## What this builds

`explain_catalog_match` — the same match as `match_catalog_type`, reported rather than decided:

| field | |
|---|---|
| `name_present` | did the model produce a name at all |
| `name_words` | how long it ran to — the coverage rule is a ratio against this |
| `matched` | the catalog type it matched, if any |
| `near_miss` | the type it ALMOST matched: words present, in order |
| `rejected_by` | which guard turned the near-miss away |

Logged as `classification_unknown_explained` at the confident-`unknown` branch.

**`near_miss` with `rejected_by=coverage` is the field that pays for the whole line.** It means the
model DID name a catalog type and this matcher turned it away — a different bug from the model not
recognising the document, needing the opposite fix. Today those two are indistinguishable after the
fact.

## Why it is safe to log

Every value is a count, a boolean, or a catalog SLUG — closed vocabularies. The name never appears,
in any form: not truncated, not hashed, not as a character length that could separate two candidate
documents. A test asserts the property over the whole object rather than over today's fields, so a
field added later that carries the name fails there rather than reaching a log.

## Why the explanation is a second pass, not a return value

`match_catalog_type` decides whether a processor sees a flag. Threading a diagnostic through it would
put observability on the path that makes that decision. The duplication is bounded — two guards — and
a test asserts the two functions agree on every catalog slug, in both a bare and a naturally-phrased
form, so they cannot drift into disagreeing about what matched.

## What this does not do

It does not fix the classifier, and it does not fix the matcher. It makes the next `unknown` answer
the question that this one could not, so the fix that follows is chosen from evidence rather than
from a flag that turned out to mean nothing.

## Review

### `rejected_by=coverage` could not tell the bug from the guard working

This was the field the whole line was justified by: "the model DID name a catalog type and the
matcher turned it away", meaning loosen the matcher. But `match_catalog_type`'s own docstring names
*"an email asking the borrower to send a bank statement"* as the case the coverage rule exists to
reject — and it produced a **byte-identical** explanation to LF-ZE9N's genuine Closing Disclosure:
`near_miss` set, `rejected_by=coverage`. The same docstring says a confident `unknown` "is very often
a cover letter, a transmittal, a fax sheet or an email printout — precisely the documents whose names
reference OTHER documents", so mentions are the *dominant* population producing that value. Acting on
the field as documented would have loosened the guard against exactly the names it was measured to
exclude.

The discriminator existed and was not reported. The matcher documents the populations — true names
0.5–0.67, mentions 0.18–0.25 — so `near_miss_coverage` is now on the explanation and in the log. On
the two cases above it reads 0.29 against 0.2, which is worth knowing on its own: the real phrasing
sits *between* the documented bands, which is the argument for logging the number rather than
guessing a threshold from it now.

### Three guards, two modelled

`match_catalog_type` applies three and the explanation modelled two, so the third was invisible:
`explain_catalog_match("Appraisal")` reported `rejected_by=order`, which reads as "the model named
nothing" about a name that named a catalog type **exactly**. `appraisal`, `passport`, `survey`, `w2`
and `1099` are all one-word slugs, so these are ordinary document names. That is the misdiagnosis
this ticket exists to prevent, reproduced inside it.

`order` was also a catch-all: "a receipt for the earnest money" — the matcher's own example of words
present but out of order — and "a photograph of a cat" gave the same answer, so the one guard that
could be loosened without touching coverage was unobservable. And `rejected_by=None` was shared
between a successful match and a name that normalised away to nothing, so a log query counting
matches silently included the degenerate case.

Five reasons now, one per outcome: `coverage`, `order`, `min_words`, `no_catalog_words`,
`unusable_name`.

### The diagnostic had become the decision

The design note said observability "must not sit on the path that decides whether a processor sees a
flag" — and by then `missed_catalog_type` was being read from `explain_catalog_match(...).matched`,
leaving `match_catalog_type` with no production caller at all. An edit to an early return in the
explainer would silently have changed who gets flagged. The decision comes from the matcher again;
the explanation is only logged.

### Two tests that could not fail

The **drift guard** — offered as what made the second-pass design safe — compared
`explain_catalog_match(name).matched` with `match_catalog_type(name)`, while the implementation
assigns `matched = match_catalog_type(free_text)`. It compared a value with itself: verified by
corrupting the matcher to return a constant, which left it green across the whole catalog. Replaced
with one that pins what is genuinely duplicated — the near-miss walk — against the matcher's own
constants, per reason, and it catches both drifts the old one could not.

The **word-count test** asserted `not re.search(r"[A-Za-z]{3,}", str(name_words))` on an int, whose
`str()` never contains letters. Its docstring claimed to pin against "a length in characters, a
hash"; both are ints and both would have passed. Replaced with a check that the numbers vary with the
name's *shape* and not its content, plus a bound on `name_words`.

### The PII claim: sound, and slightly overstated

**(a) is safe.** Every field is a count, a ratio, a boolean, or a value from a closed vocabulary —
164 catalog slugs and five reasons. The only open-vocabulary value is an integer of a few bits.
Combined with `document_id`, a reader learns "this document's model-supplied name was seven words and
ordered like `closing_disclosure`", which carries nothing about a borrower; and a reader who can join
on `document_id` already has the document. There is no channel through which the name's *content* can
pass.

Two corrections rather than objections. The guarantee as written — the name never appears "as a
length that could separate two candidate documents" — is false: `name_words` **is** a length of the
name. What is true is that it is a length in words, a handful of bits, and that is the claim now
made. And the property test only inspected `str` values, so a field added later as a list or dict of
free text — the natural shape for "the words that did match" — would have passed the test that exists
to stop exactly that. It is a type whitelist now.

**(d)** is fine: two distinct event names, one fires per confident `unknown` and the other only when
a flag is raised, so neither is double-counted.
