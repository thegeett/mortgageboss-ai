# LP-390-2 — Income-rule tag→consumer wiring audit (READ-ONLY)

## What this ticket is

Before Priya labels, confirm every income-wave rule's load-bearing tag actually REACHES it. The
structural-dead class — a rule reading a tag at the wrong subject, or a tag with no producer → couldnt_check
forever, silently — has appeared repeatedly this session (AS-1 calc-gate, ID-2/ID-3 field-mismatch, OC-2 /
IN-14 orphan, ID-5 / IN-10 / IN-11 / IN-12 subject-mismatch). **If a tag never reaches its rule, Priya labels a
tag the rule can't read and the calibration measures nothing.** This sweeps every inert income/asset rule for
it. **READ-ONLY — nothing is fixed; each finding is a fix ticket.**

## The method (spec → tag → producer subject → read subject → materializes?)

For each rule, traced with evidence at every hop:
1. **The rule's read subject** — `subject_enumeration` + the `required_inputs` `snapshot_path` in its spec
   (`app/verification/rules/specs/<RULE>.yaml`).
2. **The tag's producer + subject** — `app/verification/rules/tag_production.yaml` (the declared tag layer),
   PLUS the two non-declared producers the static trace must include: the **Stage-B correlation service**
   (`app/services/tag_correlation.py`, wired at `verification_run.py:434`) and the **derived recipes**
   (`app/verification/tag_materialization/derived.py`).
3. **Subjects match?** producer subject vs the subject the rule reads.
4. **A gate-of-record correction:** the declared tag layer (`tag_production.yaml`) is NOT the only producer —
   `txn.has_identified_source` / `txn.source_strength` are produced by the Stage-B service, not the declared
   layer. Trusting `tag_production.yaml` alone would have falsely flagged AS-2/AS-12 as orphans. (The code
   caught this.)

## Assumptions, decisions & the honest limit

- **Every "calibration-ready" call is evidenced above** (producer subject from `tag_production.yaml` line; read
  subject from the spec `snapshot_path`; both subjects the same class). The two Stage-B tags
  (`has_identified_source`, `source_strength`) are produced by `services/tag_correlation.py` (wired at
  `verification_run.py:434`), not the declared layer — a producer the naive trace would miss.
- **IN-12 and AS-5 are the sixth/seventh subject-mismatch instances** (IN-12 found in LP-390-1; **AS-5 is NEW
  this audit**). **AS-7 is a NEW orphan** (alongside the known IN-14). So this audit added two blocked rules the
  prior passes had not isolated.
- **The honest limit of a static trace:** it establishes that a tag's producer subject MATCHES the rule's read
  subject and that a producer EXISTS — it does NOT establish that the producer materializes the tag on a
  GIVEN file (a tag may materialize on LF-6T3N but not on a file without that document type; e.g. `voe_present`
  needs a VOE in the file). Those are DATA questions (the LP-384 pattern), settled only by running the group on
  a file that carries the document. What this audit rules out is the STRUCTURAL death (wrong subject / no
  producer) — the class that couldnt_checks on EVERY file regardless of data.
- **Two sub-findings (context-tag gaps, not blockers):** IN-13 reads `income.type` (document subject) from the
  borrower map where it isn't carried; AS-12's `txn.counterparty` has no producer. Both are `reasoned_over`
  judgment context, not gated load-bearing tags — the rules still reach a verdict on their load-bearing tag.
  Worth a look when IN-13 / AS-12 are wired for real, not blockers now.
