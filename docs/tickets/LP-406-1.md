# LP-406-1 — Write PC-7 (Contract), the first Bucket 2 rule — **STOPPED at Phase 0**

## What this ticket is

The first genuinely zero-dependency Bucket 2 rule, to be written from scratch on already-live inputs, as a
clean template for AS-8 / IN-6 / OC-1. LP-405's mini-census ranked PC-7 the **cheapest** of the four true
Bucket 2 rules on the grounds that every tag it reads (`contract.closing_date`) is already produced by the live
`purchase_agreement` extractor.

**Phase 0 refuted that ranking.** PC-7's check ("closing date vs **today**") is **not expressible** on the
currently-produced tags: the deterministic DSL has no notion of "today," and the only way to express a
date-vs-today comparison is a *derived recency tag* (the IN-2 pattern) that does not exist and whose
construction this ticket explicitly scopes OUT. Per the ticket's own guardrails ("FLAG anything inexpressible
in the spec DSL"; "a structurally-dead rule must not ship"; "the code beats my ticket text"), I **stopped
before writing the spec, changed no code, and report the finding.** No file was changed except this report.

This is the **LP-405 lesson, one level deeper**: the census verified *"is the read-tag produced?"* (yes) but not
*"can the rule be expressed on it?"* (no). That is the OC-1 trap the ticket warned about — reading the
producer's existence, not the rule's semantics.

## D1 — What does PC-7 actually check?

**Quoted from the source of truth:**
- `rule_kinds.csv`: `PC-7,Closing date realistic/current,Contract,structural,deterministic_only,false,true,…,"closing date vs today — date compare."`
- `docs/stage2-rule-classification.md` line 93: *"PC-7 | Closing date realistic/current | Contract | structural | deterministic_only | false | true | false | false"*.

**In one plain sentence:** *This rule verifies that the purchase contract's closing date is realistic relative
to the current (file) date — i.e. not already in the past and not implausibly far out.*

The description is **clear, not thin** — so the STOP is not "too thin to write." It is "clear, but the check
requires an input the DSL cannot supply" (D3).

## D2 — Its kind, and therefore its ending

**Structural / `deterministic_only`** (`rule_kinds.csv`; `priya_validated=false`, `threshold_needs_signoff=false`).
So *if* it were writable it would be a **deterministic** rule that could ship and activate via the eligibility
gate in this ticket. It is **not** judgmental — no AI, no calibration. The ending is blocked not by
calibration but by an **expressibility gap** (D3) and, secondarily, by a **Priya window threshold** (D6).

## D3 — The read-tags + their REAL semantics (the decisive finding)

PC-7 reads exactly one tag (`rule_tags.csv`):

| read-tag | producer | subject | real semantics (not the name) |
|----------|----------|---------|-------------------------------|
| `contract.closing_date` | `parsed` | **document** | The raw closing **date** parsed from the purchase-agreement PDF (`PurchaseAgreementExtraction.closing_date`). A bare date value — **no relation to "today" is encoded in it.** |

There is also a loan-level promotion, `contract.loan_closing_date` (`derived`, subject **loan**, producer
`_loan_closing_date` in `derived.py:684`) — the same raw date lifted to loan level, which **ID-5 (live) reads**.
Still a **bare date**.

**The gap.** PC-7's check is a date **vs today** comparison. In the deterministic DSL a comparison's operands
come only from `tag` / `loan_tag` / `reference` / `calc` / `product` (`schema.py` `Operand`; resolver
`deterministic.py:128–150`). Of these:
- a `reference` is **decimal-only** (a `reference_values.values` number) — it **cannot be a date**, so "today"
  cannot be a date reference;
- a `date`-typed operand is valid **only** on a `tag` / `loan_tag`; there is **no `today` / snapshot-date tag**
  in `tag_production.yaml`, and the evaluator injects **no** current-date operand (grep of `rule_engine/` for
  `today` / `now(` / `created_at` / `snapshot_date` → nothing; the only injected structural tag is
  `document.document_type`).

**How the codebase actually expresses "vs today" — and PC-7 can't reuse it as-is.** IN-2 ("Pay stub recency")
is the exact precedent. It does **not** compare a raw date to "today" in the spec; it reads a **derived** tag
`income.days_since_most_recent_pay` (`derived.py:343`) that computes `snapshot.created_at.date() − pay_date` and
compares that **integer** against a decimal `reference` window (`paystub_recency_days: "30"`). The snapshot
"as-of" date is available **only inside a derived producer**, never as a spec operand.

**Therefore:** to write PC-7 deterministically we would need a **new derived tag** — e.g.
`contract.days_until_closing` = `(closing_date − snapshot.created_at.date()).days` at loan level (mirroring
`income.days_since_most_recent_pay`) — compared against a window `reference`. **That derived producer does not
exist.** So `contract.closing_date` being "produced" (LP-405's test) is **necessary but not sufficient**: the
rule is still not writable, because the *shape* of its check needs a producer that isn't there.

## D4 — The subject match (the structural-death check)

Even setting D3 aside, the subject axis is a trap: `contract.closing_date` is produced at subject **document**,
while a realism check is inherently **loan-level** (one closing date per file). A spec that enumerated `loan`
but read the document-subject `contract.closing_date` would `couldnt_check` on every file — the classic
ID-5-class structural death. The *right* loan-level tag (`contract.loan_closing_date`) exists and is proven live
(ID-5), so the subject axis is solvable — **but it is still a bare date, so D3's expressibility gap stands.**
Net: writing PC-7 today = a rule reading a tag that cannot feed its comparison → **born structurally dead. Not
shipped.**

## D5 — Absent / empty / unknown (argued, though moot until PC-7 is writable)

Three distinct states, per the house rule — the correct handling *once the derived tag exists*:
- **Purchase agreement absent entirely** → the file has no contract. A purchase loan should have one, so this is
  a **gap → `couldnt_check`** (the `applicability_expected=true` on a document-type applicability, ID-7's
  false-green fix), **not** `not_applicable`. (For a refinance, PC-7 would be `not_applicable` via
  `PurposeScope.PURCHASE`.)
- **Present but the closing-date field missing** → the derived `days_until_closing` producer returns `unknown`
  (fail-closed, never 0) → `couldnt_check` with an honest reason.
- **Field genuinely unknown / unparseable** → same `unknown` → `couldnt_check`.

These are recorded for the eventual writer; none is reachable today (no rule).

## D6 — A Priya threshold?

**Yes.** "Realistic/current" needs a **window**: how many days in the **past** is a closing date allowed to be
(likely 0 — a past closing date fires), and how far in the **future** is "implausible" (e.g. > 90 / 180 days).
That window is a threshold that must ship `priya_validated=false` / flagged for her — exactly as IN-2's 30-day
recency window is an agency default pending Priya. So even after the derived tag lands, PC-7 activates only with
a defensible default window flagged for sign-off. `rule_kinds.csv` currently says `threshold_needs_signoff=false`
for PC-7 — that row will need revisiting when the window is encoded (a `values`-carried window makes it a
signoff item, like IN-2 tracks in the Priya list rather than the CSV).

## Why no spec was written (the decision)

Writing `specs/PC-7.yaml` now forces one of two bad outcomes, both forbidden by this ticket:
1. **Read a nonexistent derived tag** (`contract.days_until_closing`) → the rule `couldnt_check`s forever →
   a structurally-dead rule shipped. Forbidden ("a structurally-dead rule must not ship").
2. **Build the derived producer here** → "wiring any new tag" — explicitly **OUT** of scope ("LP-407's audit
   covers that").

Both are refused. The honest, in-scope action is to **report the blocker** and hand the producer to LP-407.

## The corrected picture — what this changes for LP-405 and for AS-8 / IN-6 / OC-1

**LP-405's verdict for PC-7 (`writable-now`) is wrong; PC-7 is `needs-producer`** — it needs a derived
closing-recency tag (LP-407) **plus** a Priya window (D6). The census's cheapness ranking should drop PC-7 out
of the "zero-dependency now" set.

**The method fix (the reusable lesson):** a rule is writable-now only if BOTH (a) every read-tag is produced AND
(b) its check is *expressible in the DSL on those tags*. LP-405 tested only (a). Any **date-vs-today** rule
fails (b) on a raw date tag — it needs a derived recency tag. Re-grade the census for expressibility, not just
producer existence.

**For the other three Bucket 2 candidates — a Phase-0 expressibility check each (do not assume):**
- **OC-1** — reads two **loan** tags, `occupancy.stated` (derived) + `occupancy.consistent_with_signals` (AI,
  already live via OC-2). The check is an **enum agreement** (no date, no "today", no threshold). This looks the
  **most clearly expressible** of the four (a deterministic `when_tags` equality) and is the strongest candidate
  to take PC-7's "go first" slot — pending its own D3/D4 pass and OC-1's LP-371 D3 scope caveat (the AI tag
  measures *declaration* consistency, not address signals — write the spec to that, not the name).
- **AS-8** — "statement chaining: ending == next beginning per account pair." Reads only already-produced
  `stmt.*` / `txn.*` tags and needs **no "today"** — so it clears PC-7's specific blocker. **But** it is a
  **cross-statement, per-account-pair** comparison, and the deterministic DSL compares operands **within one
  subject enumeration**; pairing consecutive statements per account may itself need a derived tag or a new
  enumerator. **Flag for its own Phase-0 expressibility check** — do not assume it is writable.
- **IN-6** — "employer set-match both ways" is a **cross-document set comparison** — plausibly the
  **consistency** rule shape (`ConsistencyEval`: gather `income.employer_normalized` across sources, compare),
  not a simple deterministic compare. Needs no "today." **Flag for a Phase-0 shape check** (deterministic vs
  consistency).

**Recommended next step:** re-point LP-406-1's "write first" at **OC-1** (subject to its own D3/D4 pass), and
open an LP-407 item for the `contract.days_until_closing` derived producer + Priya's closing-window before PC-7
is attempted.

## Assumptions & decisions

- **The gate is producer-existence × DSL-expressibility.** Producer existence read from `tag_production.yaml`;
  expressibility read from `schema.py` (`Operand`), `deterministic.py` (`_resolve_operand`), and the derived
  registry (`derived.py`). Every claim above is a read, not an inference — specifically, that no `today`/
  snapshot-date operand exists was checked by grepping the evaluator and confirming the resolver's five operand
  sources.
- **"vs today" ⇒ a derived recency tag** is asserted from the IN-2 precedent (`income.days_since_most_recent_pay`),
  the only date-vs-today rule that is actually live; PR-6 / CR-6 / CR-13 (also date-vs-window) are unwritten, so
  IN-2 is the sole shipped template.
- **CL-1 does not exist as a spec** (checked `specs/`), so the ticket's "mirror CL-1" instruction could not be
  followed; ID-5 / IN-2 were read instead.
- **I did not invent a different PC-7** (e.g. "closing date present" or "closing vs rate-lock") to force a
  writable rule — the ticket forbids writing to the name / inventing, and the rationale is unambiguously
  "vs today."
- No code, no spec, no `ACTIVE_RULE_IDS` change. `ACTIVE_RULE_IDS` remains **24**. This report is the only
  deliverable.

## The NEW gap (for LP-407 / the backlog)

**`contract.days_until_closing` (or `contract.closing_date_age_days`) — a derived, loan-level recency tag**:
`(contract.closing_date − snapshot.created_at.date()).days`, fail-closed to `unknown` (never 0), abstaining when
the closing date is absent — the direct analog of `income.days_since_most_recent_pay`. It unblocks **PC-7** and
is a prerequisite for the other date-vs-today Contract/Closing/Property rules (**PC-9** financing-contingency
dates, **CL-1** rate-lock vs closing, **PR-6** appraisal validity — all "date vs a reference date" shapes). Pair
it with a Priya-flagged closing-window default. This is LP-407 (producer wiring) work, not this ticket's.
