# LP-978 — The plan's confirm section sits at the top

- **Ticket:** LP-978 (the owner, 2026-10-10: "put Plan confirmation button section on top").
- **Status:** built (frontend only).

## What changed

The plan panel's confirm block moved from below the conditions to just under the heading, above "Your
first moves". The block holds "When you confirm, we will:", **Confirm the plan** with the line beside it,
and "Review one by one". She no longer scrolls past every condition to reach it. The same holds for the
"added after you confirmed" panel (LP-976), which shares the block.

**Unchanged on purpose:** the error line stays under the conditions. It mostly reports an edit to a step,
which is down there; Confirm itself rarely refuses, because the button is disabled while a reading blocks
it, and the line beside it says why.

## Review (peer session, 2026-10-10)

Reviewed at `860aba70`. The move is what the owner asked for and the document-order test is the right
way to hold it. One finding, which is the question the ticket asked itself.

### A refused Confirm rendered below every condition (fixed)

The panel has ONE refusal line, at the bottom, and that was right while Confirm was down there with it.
The button moved to the top; the line did not. `confirm.mutate` passes the shared `onError`, so a 409
from `confirm_round_plan` — the blocking codes this screen holds can be stale, and the server refuses
with "Confirm 0132's reading first" — now renders under the whole condition list, which is off the
screen on a file with more than a handful of rows. She presses a button at the top and the only
explanation appears somewhere she is not looking.

Fixed with a second slot rather than by moving the one line: the confirm's own refusal renders inside the
confirm block, directly under the button, and the existing line keeps the step-edit refusals, which
belong beside the rows they came from. "shows a refused Confirm where the button is, not under the conditions" asserts the
message precedes the first condition row; against the panel as committed it fails on that position, and
sending the confirm's error back to the shared line fails it again.

**THE FIRST VERSION OF THAT TEST WAS ABOUT ITS OWN FIXTURE.** I threw a bare `Error`, and
`errors/api-error.normalizeError` returns the GENERIC sentence for any non-axios throw — so nothing
matched, the test failed on absence, and I read that failure as the position assertion I had written.
The real path delivers an axios error whose body carries the server's sentence; with that shape the
message appears and the position is what fails. A fixture the producing code cannot emit makes a test
that is green, or red, for reasons that have nothing to do with the screen.

### The second question: did any panel test rely on the old order?

No. The file's other tests find their elements by role and text rather than by position, and all 58 of
them pass with the confirm block at the top. The one exception in my run is not about order: the
LP-971 "Describe it" test fails against another session's in-flight `plan-add-step.tsx`, which they
flagged and own.
