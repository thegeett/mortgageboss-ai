# LP-631 — a need the file already answers: the coverage flag

- **Ticket:** LP-631
- **Status:** Built — CI green, not yet deployed
- **Date:** 2026-08-26
- **Scope:** Backend (model + migration + service + API) + frontend (need card)

## The report

Staging file LF-AWBB carries a Need List row reading *"Lease agreement or documentation for the
lease payment liability"*. It is `origin=ai_reasoning`, `disposition=proposed`, `status=pending`,
and its cited trigger is the MISMO-imported stated liability `LeasePayment / ALLY FINANCIAL /
$438.00`.

The file's credit report — completed, extracted — lists `ALLY FINANCIAL / AUTO / 438`. Fannie Mae
B3-6-01 requires the lender to "verify any other liability **that is not shown on a credit report**
by obtaining documentation from the borrower or creditor." The liability is shown on the credit
report. The precondition for the need is false, and has been since three minutes after the need was
created.

The timing is the whole story. The need is stamped `22:34:58`; every document on the file lands at
`22:37:47` or later. LP-69 reasons at MISMO import, when `documents_present` is empty by
construction — so **every** AI-proposed need is provisional when it is written, and the system has
no way to represent a provisional claim being withdrawn.

## Why nothing retires it

Measured, not assumed. Across staging: **32 open AI-proposed needs** (`pending` + `proposed`) over
17 need types. For every single one, `own_doc_present = 0` — no open AI need has a completed
document of its own type sitting on the file. Ordinary satisfaction matching is not failing. All the
staleness is the **cross-document** kind: the need asks for document X while the evidence sits
inside document Y.

`apply_ai_needs` (`services/needs_ai.py:400`) loops over `proposals` and nothing else. Each proposal
either creates a row, refreshes an existing row's reasoning (LP-625), or is skipped. There is no
branch that considers existing needs the new proposal set **omitted**, and the JSON contract has one
key — `{"needs": [...]}` — so the model has no channel to withdraw anything even if it judged it
should. The two passes that do touch existing rows don't help: `consolidate_and_flag` only merges
duplicates, and `repair_needs_for_file` scopes itself to floor-origin rows.

Omission cannot be read as withdrawal, either. The prompt **orders** silence about anything in
`already_covered`, so a missing need type means "I was told not to restate it" — indistinguishable
from "it is no longer needed". Reading omission as retraction would delete every correct need on
every re-run.

## What this ticket builds

The **mechanism**, once — not any particular predicate. LP-632 is its first consumer and LP-633 its
second.

**Three columns on `needs_items`**, mirroring LP-111's duplicate-flag pair:

| column | meaning |
|---|---|
| `covered_by_document_id` | the document that appears to already answer this need (FK, `SET NULL`) |
| `coverage_note` | why, in the processor's words — "the credit report lists ALLY FINANCIAL at $438/mo, matching the stated lease payment" |
| `coverage_reviewed` | true once a processor disposed of the flag, so a pass never re-flags a judgement already made |

**`services/needs_coverage.py`** — `flag_covered_needs(loan_file_id)`, a registry of predicates plus
the eligibility gate and the flag write. A predicate answers one question: *is this need's
precondition now false, and which document proves it?* Adding one is adding a function to a list.

**The eligibility gate is `_refreshable`'s, exactly** (`needs_ai.py:511`): origin `AI_REASONING`,
disposition still `PROPOSED`, status `PENDING`/`REQUESTED`, plus not-already-flagged and not
`coverage_reviewed`. A need a processor confirmed, dismissed, or adjusted carries their judgement and
is out of scope no matter what a predicate concludes. That boundary is already written and tested;
this reuses it rather than restating it.

**It flags. It never closes.** See ADR-388. The processor disposes through the endpoint that already
exists (`POST /needs/{id}/dismiss`) or through a new `POST /needs/{id}/not-covered`, which clears the
flag and sets `coverage_reviewed` so the pass stays quiet — the mirror of `not-duplicate`.

**Runs where the other passes run:** in `_run_needs_update` and `_run_propose_ai_needs`
(`tasks/needs.py`), after `consolidate_and_flag`, under the same per-file lock.

**The drift guard caught a real defect in the first cut.** `test_no_model_column_drifts` reads every
`CREATE VIEW` above `def downgrade(` and lets the last win; the rollback view was a module-level
constant, so the scanner read the PRE-LP-631 shape as the live one and reported the three new columns
as unexposed. It is now defined inside `downgrade()`. The guard was right and the layout was wrong —
exactly the failure LP-509-B1 wrote it for, arriving from a direction it had not seen.

## Assumptions

- Reusing LP-111's flag-and-dispose shape rather than inventing a second one is deliberate: it means
  no new status, no state-machine change, and a UI affordance processors have already met.
- Three columns rather than two because the *why* is the entire value of the flag. A row saying only
  "possibly covered" asks the processor to redo the work.
- `coverage_reviewed` is a plain bool, not a timestamp: nothing needs to know *when* the judgement
  was made, only that it was.
