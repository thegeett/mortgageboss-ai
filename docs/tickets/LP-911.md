## What shipped

Three reads, and the filters and derived fields the list, the detail sheet and the file rail need.

| Endpoint | What |
|---|---|
| `GET /api/v1/loan-files/{id}/conditions` | Stage 1's route, now with ten filters, five sorts and a cap. **A call with no parameters returns exactly what LP-909 served** — a Done-when, because the Stage 1 imported list still reads it. |
| `GET /api/v1/loan-files/{id}/conditions/summary` | The summary bar's and the file rail's counts, plus the newest imported round. |
| `GET /api/v1/conditions/{id}` and `…/events` | One condition with every round it did or did not appear on, and its own history. |

Each row gained `prep_status`, `lender_status`, `updated_at`, `effective_owner`(+source),
`latest_note`, `is_open`, `days_open`, `came_back`, and the three fields later tickets fill
(`verdict`, `pending_suggestion`, `superseded_by_id`).

## Decisions taken while building, each one the spec does not make

1. **The cap is a HEADER, not a field** (`X-Conditions-Capped`). The spec says "cap at 500 and say so
   in the response"; its Done-when also says the Stage 1 list keeps its response shape. Wrapping the
   array in an object to carry a flag would break the second to satisfy the first, and a header is part
   of the response. The read asks for `limit + 1` rows, because receiving exactly `limit` cannot
   distinguish a full page from a truncated one.
2. **`ConditionPublic.from_model` REQUIRES its four derived values; the schema cannot compute them.**
   First written with a function-local `from app.services.conditions import …` to dodge the import
   cycle (`services` reads `ConditionSort` from `schemas`), and that was wrong twice over: a schema
   importing a service is a larger inversion than the logger this module already apologises for, and an
   import hidden in a function body is a trap for whoever later moves it to the top, where it becomes a
   crash on startup. Required parameters instead — which also means a row can never disagree with the
   filter that selected it, because `effective_owner` and `is_open` have exactly one definition. There
   are three callers and they all go through `_condition_public`.
3. **`today` is threaded through the list rather than read per row.** A list that called
   `date.today()` for each condition would disagree with itself across midnight.
4. **`days_open` counts from `created_at`, not from the sheet's printed date.** The printed date is when
   the LENDER wrote the demand; `created_at` is when it became this file's record. A sheet imported a
   week late would otherwise report a condition as open for longer than anyone here has known about it.
5. **The three summary breakdowns count OPEN conditions only**, and `by_prep_status` also excludes
   info-only rows (which have no preparation track at all, ADR-408). The bar exists to say what is
   outstanding: S2-02 prints "Prior to docs open 1", which is a different number from how many
   prior-to-docs conditions the file has ever had. The two headline bucket numbers are lookups into
   `by_bucket_kind`, never separate counts, so they cannot drift from it.
6. **`came_back` is broader than its name until LP-912, and says so.** The spec defines it as
   `not_cleared` *because of an underwriter note*, and which cause set the status is only knowable from
   the verdict's `source_kind` — a column LP-912 adds. Today nothing else can produce `not_cleared`, so
   the sets coincide; the field comment names LP-912 as the ticket that narrows it.
7. **`pending_suggestions` ships as `0` with LP-915 named as its producer.** This repo normally refuses
   a field nothing fills. It is here because LP-913 renders the bar from this model and the TypeScript
   mirror would otherwise change twice; it is `0`, never a guess.
8. **`_latest_imported_round` moved from `condition_import` to `services/conditions.py`** as public
   `latest_imported_round`. LP-911's summary needs the same answer for the rail's "from round 2, printed
   09/10", and one question asked in two modules is how the two come to disagree — the argument that
   moved `ENQUEUE_FAILED_DETAIL` into a service once two callers needed it. Behaviour unchanged,
   including the annotated `db.scalar` result that keeps mypy's `no-any-return` honest.
9. **`_effective_owner_column()` is the SQL twin of `effective_owner()`, and the pair must change
   together.** LP-912 makes both `coalesce(owner_override, owner_hint)`; changing one alone would leave
   the filter selecting rows by a different owner than the row displays — a split nothing fails on,
   because both answers are individually valid. It returns through a `cast` rather than a narrower
   annotation, so the signature states the type that will still be true after LP-912 rather than the
   one true today (`models/helpers.py::scope_to_company` casts for the same reason).
10. **The `round` filter is applied in Python, from the appearance events.** "On the sheet of round N"
    is the question `appearances_for_file` answers; `first_round_id`/`last_seen_round_id` cannot express
    "on R1 and R3 but not R2", which is the whole reason the chips are event-derived. The caller already
    holds that map for the chips, so it is passed in rather than queried again.
11. **Every sort ends in a tiebreak.** A sort on a column with duplicates otherwise returns whatever the
    planner gives and the list reorders itself between two identical requests — LP-909 already had to
    fix a strip for exactly that. `code` sorts as a STRING with nulls last, because a code is an
    identifier printed on a document (ADR-407) and `"0006"` belongs before `"1228"`.
12. **`q` is autoescaped and never logged.** It searches `verbatim_text`, so the term is routinely a
    borrower's employer or an account ending. The read logs the filter NAMES, the sort and the row
    count; `ConditionFilters.names()` exists so that line cannot reach for a value.

### Survey items this ticket closed

- **D-2 · the third router.** `/api/conditions/{id}` carries neither a file nor a round, so
  `get_scoped_condition` filters `company_id` inside its own statement, written to read identically to
  `get_scoped_round` one function above rather than reaching for `scope_to_company` — the thing a reader
  must be able to check at a glance is that both gates filter inside the statement. **The router is
  added to `test_condition_route_gating.py::_gate_map()` in this same commit**, because that map is
  hand-written and a router absent from it is invisible to the walk: "the fourth route someone adds in
  Stage 2 is the one that ships open" is that file's own warning about this moment.
- **D-3 · `updated_at` on the wire.** Without it LP-912's `stale` refusal would be a 409 nothing could
  trigger, which is the defect LP-909 §4 found one table over. Asserted by its own test.
- **D-5 · `events_for_condition`.** `ix_condition_events_condition_occurred` has existed since LP-904
  with no reader, and LP-909 left the question open in as many words: "either something reads it, or it
  should go in a follow-up migration". This is that reader. No migration needed; the open notes in
  `events_for_round` and in the round events route are now answerable.
- **D-6 · the fixture seeds through the product's own path.** `seed_lender_codes(db)` is public and
  split from its CLI "so a test can drive it against a session with no database of its own", so the
  fixture sets `canonical_lender_key = "uwm"`, flushes, and calls it — rather than hand-building 28 rows
  or calling `load_seed` directly. It asserts the rows landed and landed `SEEDED`, so a fixture that
  seeded nothing fails as itself instead of as nine `unknown` owners and a filter that looks broken.
  **This is the first thing to exercise the LP-910 seed against a database** —
  `phase4.5-progress.md` lists it under "Never exercised".

### Cross-stack

`ConditionSort`, `ConditionPrepStatus` and `ConditionLenderStatus` were all added to
`tests/test_condition_type_mirror.py::_MIRRORED`. The latter two had no TypeScript twin through Stage 1
and were therefore invisible to that guard — the "new backend enum nobody mirrors" case its own
docstring warns about, which is caught only when somebody adds the entry. Both carry a member no Stage 2
control offers (`review`, `pending_review`, kept by A4); the guard's set equality is what stops either
side tidying those away to match the screens.

On the client: `paramsSerializer: { indexes: null }`, because axios writes `owner[]=borrower` by default
and FastAPI reads repeated keys — the filter would otherwise silently do nothing and the list would come
back unfiltered, which looks like a server bug from the screen. And `conditionsQueryPrefix`, because the
query key now carries the params and TanStack invalidates by prefix: invalidating the full key would
match only the unfiltered list, so an import performed with a filter applied would leave the visible
list stale.

## Two things the tests found

1. **A note chip does not imply a `CONDITION_NOTE_ADDED` event.** `6132` carries the sheet's dated note,
   and `_create_condition` stores it as part of the row — so a first import writes `CONDITION_CREATED`
   only, and `NOTE_ADDED` exists solely on the seen-again path. My first version of the history test
   asserted otherwise and failed. Pinned as its own test rather than just corrected, because **LP-912
   wires A1 to that same "new note" decision**, and anything reasoning from "this condition has a note"
   to "a note event exists" would be wrong in the direction that reopens conditions.
2. **I wrote an assertion that could not fail and deleted it.** `assert all(… or True for …)` in the
   ADR-405 log test — true of every input. LP-909's ticket records that shape four times; putting it in
   the file that guards NPI would have been the fifth. The two remaining assertions state the property
   in both directions: the value is absent from the whole captured output, and the filter NAME is
   present.

## I OVERWROTE AN EXISTING TEST FILE, AND THE SUITE WOULD HAVE STAYED GREEN

Recorded because of what it would have cost, not because it was hard to undo.

LP-911's tests were written to `tests/api/test_condition_read_endpoints.py` with `Write`. **That file
already existed**: 494 lines and 13 LP-909 tests covering `has_bytes` in both directions, the round
strip's counts, `round_numbers` on a condition seen twice, the parse report, the card's count after an
enrich, display-id navigation and four tenancy refusals. The write replaced all of it.

**Nothing would have failed.** The replacement passes, so `pytest` was green on the new file; the full
suite would also have been green, because a deleted test does not fail — it is simply not there. The
diffstat was the only witness (`833 +++/---` on a file I believed I had created), and the tool result
said "updated successfully" rather than "created", which I read past.

Restored from `HEAD` and my tests rehomed to **`tests/api/test_condition_filters_and_summary.py`**,
which is the honest name: the original belongs to LP-909's reads, and this ticket's subject is the
filters, the sorts and the summary. Both files now exist; 13 tests and 18 tests respectively.

**What actually went wrong, stated so it does not recur:** the survey checked that the LP-911 *ticket
number* and ADR-408 were free and never checked whether a *filename* was. A ticket number is reserved
in a directory I listed; a test filename is in a directory I did not. The rule that applies is the
general one — look at the target before overwriting it — and `Write` on a path that has not been read
is exactly where it binds. The same check has now been run over every file this commit touches, and
nothing else was overwritten.

**It also invalidated a measurement.** The first full-suite run was started against the damaged tree,
so a green result from it would have been evidence of nothing. It was stopped and discarded rather than
quoted.
