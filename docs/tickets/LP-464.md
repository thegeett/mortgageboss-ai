# LP-464 — the extractor `ValueError` crash + extraction-side retry

10 documents had a correct classification and a correct schema but errored to a COMPLETELY EMPTY result. The
alarm: both loan applications (URLAs) failed — 100% of a type read by 28 rules. Phase 1 diagnoses before any
fix. **The length correlation is confounded, and it turned out to be more than one thing.**

### 1a — is the traceback captured? Partly — the TYPE, never the LOCATION.
`model_call._attempt` catches only `AIClientError` and logs `extraction_ai_failed` with the extractor + phase
— **not the cause**. `client.complete` logs `ai_call_failed` with `error_type=type(exc).__name__` (so the
CAUSE TYPE — `ValueError` — is recorded, which is how the bench tagged it), but **not the message or the
line**. So we had the *what* (`ValueError`) but never the *where*. Small hardening proposed below.

### 1b — the payload hypothesis (tested FIRST): RULED OUT.
Extraction sends the whole document, so a genuinely >100-page doc *would* hit the Bedrock document limit — but
**none of the 10 is over 38 pages**, and **257 (0.23 MB) and 261 (0.28 MB) are tiny**. The error does NOT
track input size. It tracks **output density**: every failing doc has a long text layer (175: 99k chars, 272:
88k, 257: 25k) → a long extraction → the model TRUNCATES at its first-attempt budget → the LP-102 guard
retries at `RETRY_MAX_TOKENS = 32768`. **This is not LP-462's problem.**

### 1c/1e — the root cause (confirmed by git + reproduction): the pre-LP-461 non-streaming-timeout ValueError, **already fixed**.
The anthropic SDK's non-streaming `.create()` raises `ValueError("Streaming is required …")` when
`max_tokens` could exceed a 10-minute worst case — i.e. **`max_tokens > 21,333`**. The truncation-retry asks
for **32,768** → over the threshold → `ValueError`, raised client-side BEFORE the call. That is exactly the
bug **`dcc2196` — "Stream completions to fix the truncation-retry ValueError (core AI path)"** fixed by
switching `complete()` to `messages.stream()`. Timeline:
- The 889-doc bench ran **2026-08-05 10:26**.
- `dcc2196` landed **2026-08-05 23:41** (~13 h later) and **is an ancestor of HEAD** — the fix is in this
  branch. There is no non-streaming `.create()` path left in `client.py`.

**Reproduction (live, streaming fix present) — the empty docs now extract fully:**

| doc | bench | re-extracted NOW |
|---|---|---|
| **257** investment_account | FAILED · ValueError · 0/27 positions | **SUCCEEDED · 19 typed · security_positions = 29** |
| **205** URLA | FAILED · ValueError · empty | **SUCCEEDED · 30 typed · 16 catch-all sections** |
| **175** lease_agreement | FAILED · ValueError · empty | **SUCCEEDED · 17 typed · 12 catch-all sections** |

So the primary bug — **8 of the 10** (174, 175, 176, 205, 206, 198, 257, 261) — is the truncation-retry
`ValueError`, **already fixed on this branch**. It is density-correlated (small dense docs fail), NOT
input-size. The length hypothesis was confounded exactly as suspected.

### 1d — 174 is a SEPARATE concern layered on the same error.
174 has **an empty text layer (image-only / scanned)**. It ALSO hit the truncation-retry `ValueError` (the AI
reads the *image* natively, produces a long transcription, truncates, retries at 32768 → ValueError). The
"scanned" note in the source report was about DETERMINISTIC pypdf text tools, which do not touch the AI path
— the model reads scans directly. So 174 should now extract like the others; if it does not, its scan (not a
parse bug) is the reason. **Reported separately; not bundled.**

### It is NOT one bug — it is (at least) three, plus two footnotes:
1. **Truncation-retry `ValueError` (8 docs) — ALREADY FIXED** by `dcc2196` (streaming), in-branch. Reproduced.
2. **`RateLimitError` (272) — Phase 3.** The backoff RETRY already exists in `complete()` (3 attempts,
   exp+jitter, covers throttle — LP-462 era). What extraction LACKS is the LP-462 **throttled-vs-failed
   surfacing**: a throttled extraction is recorded as a bare "AI call failed", indistinguishable from a
   content failure — the same corrosion LP-462 fixed for classification. That is the real Phase-3 work.
3. **103 — a genuinely EMPTY result, not a crash.** `ai_failed=false`, no error, a 1-page HOI/EOI: the model
   returned an all-null extraction (→ the `_all_null_core_is_failed` FAILED) or parsed to empty. NOT the
   `ValueError` bug. Re-extract to see if it is real (a thin EOI) or a fixable parse.
4. **261 — the `ValueError` (now fixed) PLUS a misclassification** (`miscellaneous_document` @ 0.75). Fixing
   the crash alone would extract it against the wrong schema. ⚠️ **Re-classify FIRST** — LP-463 (declining +
   the `type_matches_document` guard) may already resolve the forced 0.75 pick.

## Proposed Phase 2/3 (pending sign-off) — the primary bug is already fixed, so the build is small

- **The 1003 regression guard (mandated regardless).** 100% of URLAs failed silently on the document the most
  rules read. Add a test that a multi-section URLA extraction path does NOT return empty AND that the
  truncation-retry (a big response forcing the 32768 retry) does NOT raise — locking the streaming fix so
  this class cannot silently return. (A unit test with a mocked large/truncated-then-full response — no live
  call.)
- **1a hardening.** Log the underlying cause type in `_attempt` (`extraction_ai_failed` gains
  `error_type=infra_failure_kind(err)`-style info) so a future extraction `ValueError`/throttle has a
  location, not just a type buried in the client log.
- **Phase 3 — extraction throttled-vs-failed surfacing.** Mirror LP-462: `run_extraction_completion` /
  `ExtractionCall` distinguishes a throttle (`rate_limited`) from a content failure, and the pipeline records
  it distinctly (a throttled extraction is re-runnable, never a coverage gap). The retry itself is already
  shared, so this is the surfacing, not new backoff.
- **NOT:** a page cap on extraction (this bug is not the input limit — a >100-page extraction is a latent,
  separate gap for the splitter); no schema change; no classification cue for 261 before re-classifying it.

## PHASE 2 — the 1003 regression guard + the 1a hardening

- **1a hardening** (`model_call._attempt`): the failure log now records the underlying cause
  (`error_kind` = rate_limited/oversized/failed AND `cause_type` = the raw exception name, e.g.
  `ValueError`). We had the *what* (from the client log) but never the *where*; a future extraction crash now
  logs its location, not just an opaque "extraction_ai_failed".
- **The 1003 guard** (mandated regardless — the primary bug was fixed by accident, so the guard is the point):
  two tests lock the URLA extraction path so a silent-empty on the 28-rule document fails LOUD —
  (1) a full multi-section URLA extracts **≥ 20 populated fields**, never zero; (2) the exact fixed shape —
  first attempt truncates, the guard retries at 32768, the FULL result returns — **does not raise and does
  not silently empty**.

## PHASE 3 — extraction throttled-vs-failed surfacing

Mirrors LP-462, now on the extraction path. `_attempt` classifies an `AIClientError` by cause
(`infra_failure_kind`); `ExtractionCall` gains `infra_failure`; a **throttle** sets `failure_reason` to the
machine marker `INFRA_RATE_LIMITED`, which the 109 extractors already surface as `reasoning` (no per-extractor
change). The pipeline (`_extract_branch`) gates on it BEFORE persisting: a throttled extraction is recorded as
**re-runnable infrastructure** (`processing_error = "extraction throttled (rate_limited) — re-runnable"`, log
`reason=rate_limited, infra_failure=True`) and **no FAILED extraction version is written** — so a throttle
never reads as a content coverage gap (the corrosion LP-462 fixed for classification). The backoff retry
itself is the shared `complete()` one (unchanged); this is the surfacing.

## ADR
- **Root cause: the truncation-retry `ValueError`, already fixed by `dcc2196` (streaming).** LP-461 fixed it
  on the core AI path; the bench simply predates it by ~13 hours. The lesson worth recording is the mirror of
  LP-462's: **a limit/behaviour applied to one call path (there, the classification page cap; here, the
  streaming switch that removes the non-streaming ceiling) must be checked against every call path** — the
  streaming fix DID cover extraction (shared `complete()`), which is why re-extraction works, but the
  investigation had to prove that rather than assume it.
- **The 1003 regression guard.** 100% of URLAs returned empty silently, on the 28-rule document. A permanent
  test — not just the (already-shipped) repair — because a silent-empty on the highest-value document is the
  worst failure mode and must fail LOUD if it ever returns. A fix that arrived by accident deserves a guard,
  or the next regression is equally invisible.
- **Throttled ≠ failed, on the extraction path too.** A rate-limited extraction recorded as a content FAILED
  reads as a coverage gap and corrupts every downstream audit — the same reason four infrastructure losses
  appeared as classifier errors in the comparison report. The LP-462 distinction now covers extraction: a
  throttle is re-runnable infrastructure, never a content failure, and no FAILED extraction version is written
  for it.
