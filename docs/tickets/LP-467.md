Ticket 3 of the missing-types work, and the last of the set. Same four-piece mechanism
as LP-465/466: catalog entry · classifier indicator (CI-locked) · JSON spec · generate.

The load-bearing question is **A3**: is an ACORD 25 certificate genuinely a different type
from the existing `master_insurance_policy_for_condominium`, or would one absorb the

**Adjustments:**
- ⚠️ **DROP `amount_paid` + `payment_status`.** Neither is printed on either invoice — and
  they are *receipt* concepts. A `service_invoice` is a **BILL** (what is owed); the
  paid/receipt side is already covered by the existing `appraisal_payment` /
  `evidence_of_payment` types. Keeping them would blur the invoice/receipt line (see A2).
- `invoice_number`, `loan_number`, `property_address`, `borrower_name`, `due_date` →
  **optional** (each printed on some invoices, absent on others). `borrower_name` often
  coincides with `bill_to_name` (both samples) but can differ on a lender-billed invoice, so
  keep it.
- Extra fields on 064 (Loan Originator Name, Processor Name, vendor NMLS #) are
  processing-invoice-specific → **not added** (the generic-type discipline; catch-all).

### A2 — the two indicators (quoted)

**`certificate_of_liability_insurance`** (vs `master_insurance_policy_for_condominium` and
`homeowners_insurance`):
> *an ACORD 25 "Certificate of Liability Insurance" — a one-page standardized ACORD form
> SUMMARIZING the liability policies (Commercial General Liability, Automobile, Umbrella/
> Excess, Workers Compensation) an insurer has issued to an insured, furnished as evidence
> to a certificate holder. It states it "confers no rights" and "does not constitute a
> contract" — it is a CERTIFICATE, not a policy. NOT master_insurance_policy_for_condominium
> (the governing condo master POLICY with dwelling/property coverage, deductibles, and causes
> of loss) and NOT homeowners_insurance (a borrower's HO policy or dec page). A summary
> certificate of liability coverage.*

**`service_invoice`** (vs `general_correspondence`, and vs `appraisal_payment` /
`evidence_of_payment`, which exist):
> *a vendor service invoice — a BILL from a service provider (loan processor, surveyor,
> credit/title vendor, etc.) stating an amount OWED for a service: a vendor, an invoice date,
> a service description, and a total. NOT general_correspondence (it is a structured bill),
> and NOT appraisal_payment / evidence_of_payment (those are proof a payment was MADE — a
> receipt; an invoice is what is owed, before payment).*

### A3 — the certificate-vs-policy boundary (the decision that could cancel type 1)

**Decision: they are GENUINELY TWO TYPES. Keep `certificate_of_liability_insurance`; it is
NOT redundant with `master_insurance_policy_for_condominium`.** The argument, from the
document:

1. **Structure.** An ACORD 25 is a standardized one-page summary *certificate*; the master
   policy is the full multi-page governing *contract* (declarations, endorsements, terms).
   Different artifacts.
2. **Content — they do not overlap.** 073 is a **liability** certificate (CGL / Auto /
   Workers Comp). It has no dwelling replacement cost, no HO-6 walls-in coverage, no
   deductibles-per-peril, no causes-of-loss — the very fields the master-policy schema
   (`type_of_insurance, policy_number, limit, deductible, causes_of_loss`) exists to
   capture. Forcing 073 into `master_insurance_policy_for_condominium` would produce a row of
   nulls with the liability limits jammed into a property-coverage slot — garbage. The two
   schemas capture disjoint things.
3. **Purpose.** A certificate is evidence *issued to a holder* (here, the lender Paramount
   ISAOA); a policy is the contract between insurer and insured.

Because forcing one into the other mangles the data, this is the case where a **separate
type is correct** — the redundancy A3 guards against does not apply.

⚠️ **BUT the rule tie is weaker than the ticket claimed, and I want your call on it.** The
ticket ties the type to CO-3 (condo master policy + fidelity bond). CO-3's evidence is
master-*property* + *fidelity* coverage, which arrives as an **ACORD 27/28** (Evidence of
Property Insurance) + a crime/fidelity certificate — **not** an ACORD 25. 073 is a
builder's *liability* cert and does not contain what CO-3 reads. So the type earns its place
on **processor visibility** (an ACORD 25 is a real, standard, distinct document that shows up
in condo/new-construction files and currently dilutes `unknown`), per ADR-362/363 — **not**
on feeding CO-3. I recommend **keeping it** (it is distinct and real, and not adding it
leaves these in `unknown`), but with the honest rule tie recorded. If you would rather defer
a type whose only justification is visibility, that is a legitimate call — flagging it rather
than deciding for you.

### A4 — does `service_invoice` need `line_items[]`?

**No.** Both sampled invoices are **single-line**: 064 is one description + one total; 058's
"DESCRIPTION/AMOUNT" table has one real line ("Survey Fee $450") followed by **10 empty
template rows** — form furniture, not line items. A single `service_description` +
`total_amount` suffices. An unused list is plumbing for nothing (the ticket's own guidance).
If a genuine multi-line invoice surfaces later, add it then.

### A5 — categories and tiers

- `certificate_of_liability_insurance` → **Tier 1, PROPERTY.** There is **no INSURANCE
  category** in the enum; the insurance family (`homeowners_insurance`,
  `master_insurance_policy_for_condominium`) lives in PROPERTY, so this joins it. (Corrects
  the ticket's "INSURANCE?".)
- `service_invoice` → **Tier 1, MISC.**
- Both Tier 1 with specs — the LP-441 invariant (Tier-1 iff spec) holds. Confirmed.

### A6 — PII and the at-rest guard

The guard is `\b\d{9,}\b` (9+ **contiguous** digits, word-bounded). Against 073/064/058:
- **`loan_number`** (064: `1226375169`, 10 digits) → trips → masked via the **existing
  global `loan_number` registration** (reuse; no new entry).
- **`certificate_number`** (`W47440846`) → the "W" prefix means the 8-digit run has no word
  boundary before it → **does not trip.** No registration.
- **`policy_number`** (`MWZY 319668-26`), **`insurer_naic_number`** (`24147`), all
  **`limit_amount`s** (`5,000,000` → 7 digits) → no 9-contiguous run → **safe.**
- **`invoice_number`** (058: `1001`) → short → safe on samples. **Residual (flagged):** a
  9+-digit bare invoice number would trip; rare, and it is not semantically PII, so I leave
  it unmasked rather than register it (masking a vendor invoice id to last-4 would hurt a
  processor). Noted.
- ⚠️ **Free-text fields that can embed a bare loan/policy number** → add the digit-scrub
  backstop LP-466 introduced for wire memos (`_SCRUB_FREE_TEXT_FIELDS`):
  - `certificate_of_liability_insurance`: `description_of_operations` **and**
    `project_or_property_reference` — the ACORD 101 remarks on 073 literally print
    "Loan: 4256229242" (a bare 10-digit run that would trip).
  - `service_invoice`: `service_description` — a memo-style description could embed a bare
    loan number.

**Net: no new `_PII_FIELDS` entry** (loan_number reused; nothing else is a bare 9+-digit
run). **Three fields added to `_SCRUB_FREE_TEXT_FIELDS`** as backstops.

## Phase B — build

Two types, four pieces each. Cert has `coverage_lines` (flat_row); invoice is flat.

**1. Specs** — `115-certificate-of-liability-insurance.json` (10 scalars + `coverage_lines`),
`116-service-invoice.json` (11 scalars, no list; `amount_paid`/`payment_status`/`line_items` explicitly
rejected). Both `existing_extractor: null` → new-type mode.

**2. Generator** emitted real modules/prompts/tests; moved into place; registered in `EXTRACTORS` + imports.

**3. Catalog + indicators** (2 CI-locked pairs): `certificate_of_liability_insurance → (TIER_1, PROPERTY)`
(no INSURANCE category; joins the insurance family), `service_invoice → (TIER_1, MISC)`. Indicators from A2 —
the cert one excludes `master_insurance_policy_for_condominium`/`homeowners_insurance`; the invoice one
excludes `general_correspondence` and the `appraisal_payment`/`evidence_of_payment` receipt types. Catalog↔
indicator guard green (161 == 161).

**4. Snapshot wiring:** `coverage_lines` ListSpec (one row per section) + `_LIST_SPECS` entry (policy_number
redacted as a row-PII backstop). **No new `_PII_FIELDS`** (`loan_number` reused). Scrub backstop added to
`_SCRUB_FREE_TEXT_FIELDS`: cert `description_of_operations` + `project_or_property_reference`, invoice
`service_description`. **No nested-list-model change → `SNAPSHOT_VERSION` stays 4.**

**Post-generation prompt tuning (the LP-460 lesson):** the cert `coverage_lines` STARTER prompt was tuned to
enforce **ONE ROW PER COVERAGE SECTION** (not per sub-limit) — see Phase C for why (12 → 3 rows).
