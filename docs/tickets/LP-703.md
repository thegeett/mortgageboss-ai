# LP-703 — a processor can correct an extracted value, and the rules read the correction

- **Ticket:** LP-703
- **Status:** Done (2026-09-06). Corrections, removals and additions reach the rule engine. Carry-forward across re-extraction is designed and NOT built — see the last section.
- **Date:** 2026-09-06
- **Reported by:** the user, from the running app
- **Scope:** Backend — `models/field_review.py`, `services/field_reviews.py`,
  `verification/snapshot/documents_section.py`, a migration; Frontend — the reviewer fields pane
- **Related:** ADR-393, AMENDMENTS A28b, LP-UI-033

## The report

> I think we should allow to update any extracted value, delete (soft delete, undo to bring
> back), add value. And update should be available for snapshot for next time run.

## Where this starts: half of it exists and does nothing

LP-UI-033 built `FieldReview` — one row per `(extraction_id, field_key)` carrying a verdict
of `accepted` / `corrected` / `rejected`, a `corrected_value`, a note, the actor, a
soft-delete for undo, and an activity-log trail. A processor can already type a corrected
value and it is stored.

**Nothing reads it.** AMENDMENTS A28b records this plainly: the rule engine reads
`extracted_data`, which a correction deliberately does not touch, so a processor can fix a
wrong gross pay and the DTI is still computed from the model's figure. The screen shows the
correction; the verification does not. Today a correction is a note to the next human.

This ticket is the other half.

## The one place it has to land

`verification/snapshot/documents_section.py::build_document_fields()` is the **single choke
point** where `extracted_data` becomes `SnapshotField`s. Everything downstream — tags,
rules, findings — flows from there, and it has exactly one caller (the snapshot builder,
which reads `document.current_extraction.extracted_data`).

That makes the insertion point small and reviewable. It also means a mistake there is
invisible everywhere and wrong everywhere, so it wants care rather than confidence.

**Overlay, do not rewrite.** `extracted_data` must keep saying what the model read —
"what did the model actually say?" is the question every accuracy investigation starts
from, and the LP-508 distrust ledger is entirely that question. The correction is applied
as the snapshot is built, not written back into the extraction.

**A corrected field must carry a different `source`.** `SnapshotField` already has one
(`_EXTRACTED`). A human-supplied value is not an extracted value, and CLAUDE.md's own
principle — stated versus verified tracked separately — applies here more than anywhere. A
finding that cites a corrected figure should be able to say a person supplied it.

**PII routes exactly as before.** `build_document_fields` sends any `_PII_FIELDS` key
through `PiiField` so a raw SSN never lands as plaintext `Field.value`. A corrected SSN has
to take the same path. This is the single easiest thing to get wrong here.

## Three operations, not one

`FieldVerdict` has three values today and none of them is add or delete. The
`activity_type` CHECK-swap migration from LP-UI-033 is the pattern for extending it.

**Update** — the existing `corrected` verdict, now consumed.

**Delete (soft, undoable)** — "the model extracted something that is not on this document".
The effect on the snapshot is that the field is **absent**, which is meaningfully different
from null: rules that need it degrade to `couldnt_check` rather than evaluating against a
value nobody stands behind. Undo is the existing soft-delete restore.

**Add** — a field the model missed. **Constrained to the document type's declared schema
keys**, not free text: `app/schema_specs/*.json` declares 1,603 typed-core keys across 121
document types, and a key outside that set is data no rule can ever read. An add should
be a pick from the type's own field list.

## The hard part: what happens on re-extraction

ADR-393 keyed a verdict to `extraction_id` so that re-extracting retires it — a person's
confirmation must not vouch for a figure they never saw. The user asks for the opposite
direction: *the update should be available for the next run*.

Both are right, about different events:

- **A verification run** rebuilds the snapshot from the *current* extraction. A correction
  on the current extraction already survives every run. Applying it at
  `build_document_fields` satisfies the request as stated.
- **A re-extraction** creates a new version. Here the tension is real.

**The proposal: carry the correction forward, and re-confirm it only when the model changes
its mind.** That needs one column `FieldReview` does not have — the value the correction
*replaced*. Then on re-extraction:

| the new model value | what happens |
|---|---|
| same as the value the correction replaced | the correction still applies, silently — the model is still saying the same wrong thing |
| different | the correction is kept but marked **stale**, the row shows both, and it does not reach the snapshot until a person re-confirms |

That avoids both failure modes: retyping a correction after every re-extraction, and
silently overriding a genuinely new reading with an old human one.

## Consequences that must not be missed

**A correction makes the existing verification stale.** Findings cited the old value.
`services/verifications.py::mark_verification_stale` is the hook already used when a
document changes; a field correction is a change of the same kind and should call it.

**A distrusted field that a human corrected.** LP-508 lists fields with confirmed-wrong
extractor values, and a rule reading one degrades to `needs_review`. If a processor has
corrected that exact field, the reason for distrusting it is gone. Whether the degrade
should lift is a real question and probably a follow-up, but it should be decided rather
than discovered.

**`corrected_value` is already kept out of the readonly views** — LP-UI-033 dropped it and
`note` from `readonly.field_reviews`, because correcting an SSN field means the correction
*is* an SSN. Adding an "added value" column inherits that requirement.

## Acceptance

- [ ] A corrected value reaches the rule engine, proven **at the layer the bug was seen**:
      a file whose DTI changes because a processor corrected an income figure — not a unit
      test on the overlay function
- [ ] `extracted_data` is unchanged by any of the three operations; the model's reading stays
      answerable
- [ ] A corrected field is distinguishable from an extracted one in the snapshot, and a
      finding citing it can say so
- [ ] A corrected PII field is masked and match-hashed exactly as the extracted one is —
      with a test that fails if a raw value reaches `Field.value`
- [ ] Delete makes the field absent, not null, and the rules that need it say `couldnt_check`
- [ ] Add is constrained to the document type's declared keys
- [ ] Re-extraction behaviour matches the table above, with a test for **both** branches
- [ ] A correction marks the verification stale
- [ ] Undo restores in every case, and the audit trail shows the sequence rather than only
      the current state

## What was built

**The overlay, at the one place it had to land.** `build_document_fields` takes an
`overrides` mapping and substitutes the processor's value **before the routing**, not after
the fields are built. That ordering is the whole safety argument: a corrected SSN then
travels the identical `PiiField` path an extracted one does, and the LP-569 free-text scrub
applies to a hand-typed value as much as to a read one. Overlaying afterwards would mean a
second copy of both, and the second copy is where a raw identifier eventually reaches
`Field.value`.

`extracted_data` is never touched. The snapshot builder loads every live snapshot-changing
verdict for the file in **one** query, beside `_links_by_document`.

**Five verdicts, in two kinds.** `accepted` / `corrected` / `rejected` record an opinion
about a value the model produced. `corrected` / `removed` / `added` change what the rule
engine reads — `FieldVerdict.changes_the_snapshot` names the distinction once so that
several call sites cannot each derive their own list.

`rejected` is deliberately still not `removed`. "I could not verify this" leaves the model's
value in place for the next person; "this is not on the document" takes it out. Collapsing
them would make an illegible page delete data.

**A corrected field carries `FieldSource.CORRECTED` and no confidence.** The source is new,
because stated-versus-verified is the separation this codebase is built on and a finding
citing a corrected figure should be able to say a person supplied it. The confidence is
dropped because `confidence` is the *model's* self-rating; carrying 0.91 forward onto a
value the processor has just overruled would report the model as fairly sure about a figure
it never saw.

**Removal makes a field absent, not null.** A rule that needs it can then degrade rather
than evaluate against a value nobody stands behind.

**Addition is constrained to the document type's declared TYPED-CORE keys.** The API sends
`addable_fields` — declared minus already-extracted — so the screen offers a pick, never a
text box.

**Undo.** `useRevertFieldReview` had existed since LP-UI-033 and **no component called it**.
Every decision, including one made by a mis-key, was permanent from the screen. There is an
Undo on any field carrying a verdict now.

**A correction marks the verification stale**, and so does withdrawing one — the findings
were computed with it, so undoing it leaves them describing a file that no longer exists.

## Three things that were wrong and are not in the report

**The screen and the rules would have disagreed.** The reviewer's rows are built from
`extracted_data`, so a corrected `gross_pay` went on rendering **$15,000.00** with a
"Verified" mark beside it while the rule engine used the processor's 4,200. Found by looking
at the running app rather than by reading the code. The frontend now takes the same
substitute-before-formatting path the backend does, and the row shows the correction with
*The extraction read $15,000.00* beneath it.

**`addable_fields` offered nested-row columns.** The shared spec loader unioned typed core
with nested-list rows, because its first caller (`distrust`) needs both. `earning_type` is a
column *inside* a pay stub's `earnings_lines`, not a field of the pay stub — offered at the
top level it would have been stored, displayed and read by nothing. The two sets are
separate now, with a test that the nested column really is declared somewhere, so the
exclusion cannot pass for the wrong reason.

**An added field rendered "Not rated".** `tierInputFor` counted `accepted` and `corrected`
as human-confirmed and knew nothing of the two new verdicts, so the one value on the row a
person is actually answerable for had no mark at all. `added` is human-confirmed now — the
same act as correcting — and `removed` has its own tier, checked *before* confirmation so
that correcting a field and then removing it shows the removal.

## A guard the model claimed and the database did not have

`verdict` is declared `str_enum(FieldVerdict)`, which emits `ck_field_reviews_fieldverdict`
under `create_all` — so the test suite has always had a CHECK constraint that no migrated
database has (LP-UI-033's migration created a bare `String(50)`). A verdict value outside
the enum was rejected in tests and accepted in staging: the environment with real data was
the lenient one. The migration adds it, with `DROP CONSTRAINT IF EXISTS` because every
existing environment is one that never had it.

Left alone deliberately: the column is `VARCHAR(50)` in the migration and `VARCHAR(32)` in
the model. Narrowing risks truncation for no benefit — every permitted value is under 32
characters and the CHECK is what governs.

## Verification

- 20 integration tests in `test_field_reviews_reach_the_rules.py`, all through
  **`build_snapshot`** rather than the pure overlay function. The overlay's own unit tests
  would have passed while the builder never passed an override in — which is the original
  bug's exact shape, one layer up.
- A positive control: without a correction, the snapshot carries the model's value. Without
  it, every other assertion would pass against a builder that always used the correction.
- Five isolated mutations, each reverted: never passing overrides in failed 7 tests; a
  removal rendering as null failed 2; a corrected field keeping `EXTRACTED` failed 2;
  keeping the model's confidence failed 1; not walking added keys failed 1.
- Exercised against the running app end to end — a correction, a removal, an add refused for
  an already-extracted field, an undeclared key refused, `verification_stale` set — and read
  back on screen in light and dark.

## What is NOT built, and why it is not a quiet omission

**Carrying a correction across a re-extraction.** `replaced_value` is written — the column
that makes it possible, captured now because it can *only* be captured now: after the next
extraction lands, the value the processor overruled is gone from the current version and
nothing can reconstruct what they were looking at. Nothing reads it yet.

The design stands as written above: on re-extraction, a correction whose `replaced_value`
matches the new model value carries forward silently, and one where the model has changed
its mind is held back for a person. It is a separate change to the re-extraction path with
its own ADR-393 tension to argue, and putting it inside this ticket would have meant
shipping the interesting half untested.

The request as the user made it — *"update should be available for snapshot for next time
run"* — is satisfied without it: every verification run reads the current extraction, and a
correction on it now survives every one of them.
