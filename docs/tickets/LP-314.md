# LP-314 — Tag production: Stage B (cross-entity correlation) + candidate-then-judge

**Status:** Complete. **Branch:** `phase3_new_AI_arch_finding_stage2`.
**ADR:** [ADR-253](../../decisions.md). **Depends on:** LP-312 (content_ids + Tag +
tags layer), LP-313 (Stage A — consumed here), LP-310 (the cross-source clone).

## What it is

The first **cross-entity correlation** tag and the **candidate-then-judge** pattern.
It produces `txn.has_identified_source` — is a deposit sourced, or an unexplained
inflow (the AS-1 fraud signal)? — by splitting the work: deterministic code searches
the whole file for candidate sources; the AI judges only one deposit against its
small candidate set (never the whole file). This is the pattern every future
correlation tag will follow. **Stage B, the sourcing tag only.**

## Acceptance criteria

- [x] Deterministic candidate-search (pure code, no AI): for each money-in deposit,
  own-account transfer debits (exact amount, ±5-day window, across all accounts) +
  a payroll self-source. Extensible, deterministic order, content_id-referenced.
- [x] A bounded judge prompt: **one deposit + its candidates only**, never the whole
  file; returns `yes|no|unknown` + `source_index` + confidence + reasoning.
- [x] **No candidate → a real `"no"`, NOT `"unknown"`** (the unexplained-deposit signal
  AS-1 fires on). `"unknown"` reserved for genuine can't-determine.
- [x] **DAG-ordered after Stage A:** consumes `txn.is_money_in`; `in`→judge,
  `unknown`→`unknown` (derived, no AI call), `out`→not a subject; confidence capped at
  the input's.
- [x] `source_facts` cite the deposit **and** the matched source by `content_id`;
  content_ids never reach the AI (index-mapped, out-of-range fails closed).
- [x] Fail-closed: AI error / timeout / truncation / malformed → `unknown`-with-reason,
  never a defaulted `"yes"`. `complete()` reused with the timeout.
- [x] Cache by (deposit + candidate-set) content; AI calls scale with deposits, not
  transaction pairs.
- [x] All tests keyless (stub judge). ruff + mypy(`app/`) + full suite green (1861 passed).

## What was built

- **`app/ai/tag_correlation.py`** (the judge): `STAGE_B_SOURCING_SYSTEM_PROMPT`;
  `reason_stage_b_sourcing(context_json)` — Opus temp-0, timeout, truncation guard,
  defensive object parser; `SourcingJudgment` / `SourcingResult`.
- **`app/services/tag_correlation.py`** (candidate-search + orchestrator):
  `find_source_candidates(...)` (pure); `produce_stage_b_sourcing_tags(snapshot, *,
  reasoner=None, cache=None, date_window_days=5, amount_tolerance=0)` — gathers Stage-A
  tags, judges each money-in deposit against its candidate set, DAG-propagates,
  fails closed, caches, and extends the tags layer via `model_copy`.
- **Tests:** `tests/services/test_tag_correlation.py` (12 — sourced/unsourced,
  cross-account search, DAG, honesty, provenance, cache, scaling) and
  `tests/ai/test_tag_correlation.py` (9 — parser + timeout/truncation).

## Assumptions & decisions

- **Candidate-then-judge scales because the search is code, not AI.** Candidate search
  is O(deposits×transactions) pure iteration; the AI is called once per money-in
  deposit with only its few candidates. The AI never searches or sees the whole file.
- **Candidate-match criteria are Priya-confirmable parameters:** amount tolerance
  (default `$0.00` exact — transfers move exact amounts) and date window (default
  `±5 days`). Tight on purpose; the AI judges genuineness. Payroll is a self-source
  (the deposit's own category). Structure is extensible to gift/liquidation/etc.
- **`"no"` vs `"unknown"`** is the load-bearing distinction: `"no"` = looked, found no
  source (unsourced — AS-1's signal); `"unknown"` = genuinely can't determine (only via
  DAG propagation when `is_money_in` itself is unknown). The judge is instructed never to
  soften an unsourced deposit to `"unknown"`.
- **DAG / confidence propagation:** Stage B reads Stage A; a sourcing tag is never more
  confident than the `is_money_in` it depends on (`min`). The `is_money_in==unknown` case
  is `produced_by="derived"` (deterministic, no AI call).
- **content_ids never reach the AI** (LP-313 hardening reused): candidates are numbered;
  the model returns an index; the id is reattached; an out-of-range index on a `"yes"`
  fails closed to `unknown`.
- **How this generalizes:** any future correlation tag follows the same shape —
  deterministic candidate-search over the raw+tags layers → a bounded per-subject judge →
  honest, DAG-ordered, content-id-cited, cached tag. Only the candidate criteria + the
  judge prompt change.

## Deferred / out of scope

- AS-1 (and AS-2/AS-5) **rule evaluation / findings** (LP-315/316) — this produces the
  tag they read, not the finding.
- **Other correlation tags** (`is_retained_reo`, undisclosed liability, `is_recurring`,
  `source_reference`) — the pattern is established here; produce only sourcing.
- Other entities, the discovery lane, `from_tag` population. The AI is never given the
  whole file (candidates only); the stale `evaluators/` is not imported.

# LP-314a — Sourcing STRENGTH (matched paper-trail vs self-asserted claim)

**Status:** Complete. **ADR:** [ADR-255](../../decisions.md). Refines LP-314's judge + LP-315's AS-1 rule.

## What it is

The LF-6T3N trace showed the sourcing judge was too generous: it marked a deposit
`has_identified_source: yes` when the deposit's OWN DESCRIPTION claimed a source (e.g.
"ONLINE TRANSFER FROM PATEL A BROKERAGE") even with **no matching debit found**. A
description is the borrower's **claim**, not a verified paper trail — a fraudster can
label a deposit anything. LP-314a distinguishes them with a **source strength** and routes
large self-asserted deposits to `needs_review`.

## Strength vocabulary (companion tag `txn.source_strength`)

- **`verified`** — a matching debit/paper-trail candidate was found and cited (own-account
  transfer, same amount, within the directional window). Strong.
- **`intrinsic`** — sourced by nature: payroll / interest / dividend. No matching debit
  needed. Strong.
- **`self_asserted`** — the description claims an own-account/gift source but **no matching
  debit** was found. A claim, not proof. Weak.
- **`none`** — no source found. Unsourced.

`has_identified_source` stays `yes|no|unknown` (verified/intrinsic/self_asserted → `yes`;
none → `no`).

## Acceptance criteria

- [x] `verified` when a matching debit is cited → satisfied (the $20k case).
- [x] `self_asserted` (description claims a source, no matching debit) over threshold →
  **needs_review** with a how_to_fix naming the source account statement (the $12k/$2k case
  when large).
- [x] `intrinsic` for payroll / interest → satisfied (no debit match required).
- [x] Small `self_asserted` (under threshold) → satisfied, strength still recorded.
- [x] Third-party deposit with no trail (the $147 Zelle) → `none` → `has_identified_source=no`.
- [x] Reasoning states honestly which strength and why (matched debit for verified;
  "no matching debit, description-only claim" for self_asserted).
- [x] Backward-compatible: a snapshot with no strength tag falls back to sourced→satisfied.
  ruff + mypy(`app/`) + full suite green (1904 passed).

## What was built

- **`app/ai/tag_correlation.py`** — judge prompt updated: matched-paper-trail vs intrinsic
  vs description-only-claim, with the honesty requirement that a claim be reported as `yes`
  + `source_index` null + reasoning stating no debit was found.
- **`app/services/tag_correlation.py`** — `SourceStrength` enum; strength **derived
  deterministically** (`_derive_strength`: cited `own_account_transfer` → verified; income
  category → intrinsic; else → self_asserted; `no` → none) — not taken from the AI's word;
  produces the companion `txn.source_strength` tag (`produced_by=derived`).
- **`app/verification/rule_engine/as1.py`** — reads `txn.source_strength`; sourced + large
  (≥ threshold, `GE`) + `self_asserted` → `needs_review` with the "show me the debit"
  how_to_fix; else satisfied. `source_strength` added to the inline load-bearing provenance
  (not gated; absent-tolerant).
- **Tests** — Stage-B strength derivation (6) + AS-1 strength routing (6).

## Assumptions & decisions

- **Strength is code-derived, not AI-self-classified.** A matched own-account-transfer
  candidate is authoritative for `verified`; a `yes` without a matched debit and not
  intrinsic is conservatively `self_asserted`. The AI cannot upgrade a claim to verified.
- **The candidate-search is unchanged** — it already finds the debits, which is what makes
  `verified` verifiable. Only the judge honesty + the strength derivation + the AS-1 verdict
  changed.
- **`needs_review` uses `GE`** ("at or over" the threshold) per the ticket; the unsourced
  fire keeps strict `GT`.

## Deferred

- **Register `txn.source_strength` in the fact-tag vocabulary** (`docs/snapshot-fact-tags.xlsx`
  → `fact_tags.csv`). It is produced here but not yet in the vocabulary registry — a follow-up
  that touches the LP-311 xlsx→CSV pipeline (out of scope for this judge/rule refinement).
