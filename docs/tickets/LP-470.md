### A3 — `general_correspondence`: BUILD NOTHING (the decision)

All five (152, 153, 156, 159, 214, read in the LP-467 diagnostic) are **Gmail email threads** — borrower/
broker/lender correspondence delivering **explanations** (an employment history, an arms-length relationship,
two paystub/BOA address-discrepancy explanations, a Non-QM rationale). The **envelope is uniform** (from/to/
cc/date/subject/attachments); the **value is entirely in the body and varies per letter**.

**Recommendation: build no extractor. Leave `general_correspondence` at Tier 2 (recognized + summarized).**
- A thin envelope schema would capture the wrapper and **miss the content** — arguably worse than Tier 3.
- Since LP-463, **Tier 3 free extraction** lands the body in a marked-untyped snapshot section readable by AI
  cross-source verification — exactly right for per-letter-varying content (employment rows, disputed
  addresses, LOE questions). Do NOT build a "key facts" area (the ticket's own warning).
- ⚠️ **And it's partly a routing observation, not a missing extractor** — 152/153/156/214 are LOX/LOE by
  content; the existing **`letter_of_explanation` family** (7 types) already covers explanations. Where the
  classifier sends an explanation-email to `letter_of_explanation` (Tier 1) it gets structured; where it lands
  in `general_correspondence` it gets a Tier-2 summary + Tier-3 body. **Both are acceptable; neither needs a
  new extractor.** This is **the third time a "missing extractor" was really routing** (EAD→passport,
  compensation→commission, now correspondence→LOE/Tier-3).

**So this ticket builds nothing for `general_correspondence`** — recorded deliberately (ADR) so no one builds
a thin schema later.

## Closing summary — the whole missing-extractor workstream

The `_MISSING_EXTRACTORS.md` report headlined **~64 documents with no extractor**. That number was never 64
*missing types* — it was 64 documents, and most resolved without a new extractor. Where they went (reconstructed
from the ticket outcomes, LP-462 → LP-470):

- **Infrastructure, not missing types (LP-462):** ~8 documents were lost to classification/extraction infra
  failures (rate-limit / oversize / streaming crash), recovered by page caps + throttle surfacing — no schema.
- **Real new / promoted types (LP-465-467, 469, 470):** **11 types** absorbed the bulk —
  `temporary_buydown_agreement`, `uscis_notice_of_action` (LP-465); `home_value_estimate`, `wire_instructions`,
  `lender_dashboard_screenshot` (LP-466); `certificate_of_liability_insurance`, `service_invoice` (LP-467);
  `form_1098` (LP-469); `compensation_statement`, `closing_disclosure`, `loan_estimate` (LP-468/470) — roughly
  **40+ documents**.
- **Routing, not a missing extractor (3 findings):** EAD → `passport` (LP-468, an indicator fix +
  work_visa_ead_card already existed); compensation → `commission_income_statement` (LP-468, the real type is
  `compensation_statement`); correspondence → `letter_of_explanation` / Tier 3 (LP-470). The recurring lesson:
  a "missing extractor" is often a document already served by an existing type via a different route.
- **Deliberately built nothing (Tier 3):** `general_correspondence`'s 5 email threads (LP-470, ADR-367);
  Tier-3 free extraction serves per-letter-varying bodies better than a thin schema.
- **Splitter cases (not schema cases):** the multi-document packages — 066, 069, 167 (31pg), 204 (73pg), 271 —
  need a document splitter, not a type. Handed to the splitter backlog.
- **Image-quality gap (LP-468):** rotated/low-res ID-card photos (266, 453) misread as `passport` — a
  classifier preprocessing (auto-rotation/OCR) follow-up, not an extractor.

**So "64 missing extractors" was really ~11 new/promoted types plus a set of non-extractor resolutions**
(infra recovery, routing fixes, splitter cases, and one deliberate build-nothing). The genuine remaining work
is the **document splitter** (for the packages) and, if the pre-submission scope boundary moves, extending the
CD/LE headline to the cost tables (ADR-366).
