# LP-841 — Every requested document reaches the party who holds it

## The report

> "I clicked Request rate lock agreement, closing disclosure and Request credit report, closing
> disclosure button to request, though it said the document already been requested — nothing new was
> added."
>
> "so there are four receiver from processor borrower, Employer, Lender, Title company. All document
> should fall in correct bucket. there should be tab for each bucket."
>
> "if any party's contant is not there then keep it empty in draft. processor mostly worry about a
> meesgae."

## What was wrong

Three separate defects, all producing the same symptom: a click that reported success and reached
nobody.

**1. The duplicate check asked a question the draft does not.** `_already_asked` looked for a
PENDING needs item of the same type and refused if it found one. But a need can be pending and in no
draft — that is the ordinary state of anything the rule engine found and nobody has emailed about.
On LF-JR4T all three documents had been pending since the engine created them and none was in a
draft, so every click was refused to protect a request that had never happened. The file was
permanently stuck with no way to ask.

The two questions had drifted apart: this one asked "is there a pending need of this type?" and the
draft asks "is it carried by an open draft?". "Already asked" now means **in an unsent draft, or in
a draft that has been sent** — both are membership of a communication, which is what a request
actually is.

**2. A document that is not the borrower's produced a needs item and no message to anybody.** The
draft builder dropped any need whose responsible party was not the borrower, on the reasoning that
an appraisal is not the borrower's to send. True, and the conclusion did not follow: it is the
*lender's* to send, and nothing asked them. 53 of the catalog's 166 types are somebody else's.

**3. Party drafts existed but nothing could address one.** `party_addresses` raised when a
participant had no email, so a title company with no contact on file blocked the draft entirely —
when what a processor wants is the message written, ready to address.

## What changed

**Requests route by responsible party.** `add_needs_to_draft` groups the needs by
`party_for(need)` and builds one draft per party, each under its own template key. A single click
that names a borrower document and a lender document now produces two drafts.

**The processor is the one party that is not a recipient.** The catalog gives 24 of 166 types to the
processor — the condo questionnaire, the HOA certification, the 1003. "We order it ourselves" is not
a message, so these stay on the needs list and never become a draft. They are still **reported** in
the outcome, so the caller can say where the request went.

**An unreachable party still gets a draft, with an empty To.** `_party_address` returns None rather
than raising. The processor's concern is the message; the address is something they can supply when
they have it.

**The draft rule, per party.** An open draft for that party means the next request makes a new draft
carrying everything that party still has outstanding plus the new document. A draft marked sent ends
that chain, and the next request starts fresh. This is LP-832's model applied per-bucket rather than
per-file.

**Tabs, derived from the file rather than listed.** `TimelineEntry.party` is computed on the server —
from the template key for an outbound message, from the sender address matched against the file's
participants for an inbound one. The tabs read that value.

Deriving the buckets on the client was the obvious alternative and is the failure this ticket is
about wearing different clothes: the bucket a draft is *filed* under and the bucket it is *shown*
in would be two definitions of "the lender's messages" that nothing forces to agree, and when they
drift the draft exists behind an empty tab.

`party_for_draft_template` is the exact inverse of `draft_template_key`, and a test asserts the
round trip for every party. The borrower is what would break a cleverer implementation: their key is
`initial_documentation_request`, not the `document_request_borrower` the pattern implies, because
ADR-401's version pin resolves against the historical key.

## Decisions

**Seven tabs are possible, not four.** The report names borrower, employer, lender and title. The
catalog also routes to an accountant, an agent and an insurer. Building exactly four tabs would have
left an accountant draft with no tab that reaches it — invisible, which is worse than noisy, and the
same class of defect as the one being fixed. The tab set is derived from what the file has, ordered
with the four named first. Files with one correspondent get no tab strip at all.

**Null is a real party, not a fallback.** An inbound message from an address nobody on the file
recognises — a forward, a stray reply, a borrower writing from an address we were never given — has
no party. Filing it under the borrower because that is the common case would put a stranger's mail
in the borrower's thread. It shows on the unfiltered list, which is where something we cannot place
belongs.

## What the tests pin, and what it cost to pin it

Four backend claims and two frontend ones were each mutated to confirm the test fails without the
code. Three of the six first attempts were satisfied for a reason other than the one they named:

- **The dedupe mutation was invalid.** Removing the two joins left `Communication` referenced in the
  WHERE with no FROM, so SQLAlchemy cross-joined an empty table and the query returned nothing —
  which *passes*. It proved nothing until the mutation restored the actual prior predicate.
- **The processor-bucket test asserted the wrong shape.** It asserted the processor was absent from
  the result, which is also true of a build that silently discards it — the old behaviour under this
  ticket's name. It now asserts the processor is *reported* with no draft.
- **The empty-state test was satisfied by the status pill.** It clicked a party tab *and* a status
  pill, so it passed against a build with no party clause at all. The reachable case is a selected
  tab kept alive after its last entry goes; that is what it tests now.

## Not done

A party draft still renders the borrower's template body — "Hello there," then "your loan file" and
a secure-upload sentence, to a lender. The routing is correct and the copy is not. LP-835 already
records this; it is template work, not routing work, and is left there.

## The copy that quietly became false

Renaming the outcome field broke nothing and falsified two sentences, which is the more dangerous
half. `not_borrower_facing: int` became `routed_elsewhere: dict[str, int]` on the server; the
frontend type still declared the old name, so `tsc` passed, the branch silently never fired, and the
sentence it guarded — *"N are not the borrower's to send, so they are on the needs list only"* — was
by then a false account of a request that had in fact reached the lender.

The same was true one level down: `RuleFindingPublic.documents_not_borrower` was a list of labels
whose entire meaning was "these were left out", rendered on the row as *"requested — on the needs
list, not the borrower's to send."* It now carries `{label: party}` as `documents_other_party`, and
the row names the party: *"credit report requested — in a draft for the lender."*

Both were found by grepping the renamed column across `schemas/` and the frontend rather than by a
failing test, because neither had one that could fail.
