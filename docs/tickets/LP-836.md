## What was asked, and confirmed

| environment | domain |
|---|---|
| production | `imbox.mortgageboss.ai` |
| staging | `imboxstaging.mortgageboss.ai` |
| local | *this ticket's open question* |

Confirmed directly, with the reason: *"i dont want same name for both environment"*.

**Recorded once, plainly, because it is a domain and not a variable name:** the spelling is `imbox`,
with an **m**, in both values. It reads like `inbox` and is not. Both values were given deliberately
and the distinction asked for is between the environments, which the `imbox` / `imboxstaging` split
provides. It is one line of config in each environment and is reversible in a minute — but a wrong
mail domain is not something a test can catch, so it is written here rather than assumed.

## What is there today

| | value | set where |
|---|---|---|
| default | `inbox.mortgageboss.ai` | `core/config.py:278` — **production's domain, fails OPEN** |
| staging | `inbox.staging.mortgageboss.ai` | `infra/envs/staging/main.tf:472` |
| dev template | `inbox.dev.mortgageboss.ai` | `infra/envs/dev/main.tf` — never applied |

The default being production's domain is deliberate and documented: an environment that forgets to
set `INBOX_DOMAIN` advertises production's address, so the wiring in each environment is what keeps a
staging file from taking real borrower mail. **That reasoning survives this change**, and the default
moves with production's value.

## Localhost, which was asked about and has no answer today

There is no local value at all — a developer's app advertises **production's** inbox domain on every
file, because the default is production's and nothing overrides it locally. That is harmless while
nothing receives mail, and it is exactly the shape of the `UPLOAD_LINK_BASE_URL` defect: a plausible
value that is wrong and that nothing complains about.

Three options, and the third is what I would do:

1. **`imbox.localhost`** — obviously local, resolves nowhere, cannot be confused with a real domain.
2. **`imboxlocal.mortgageboss.ai`** — consistent with the others, but it is a real domain that could
   be made to resolve, which is the property we do not want locally.
3. **Refuse to start without it outside a test run**, the same treatment LP-827 gave the upload base
   URL. Then no environment can silently inherit another's mail domain, and the choice of local value
   stops mattering because it must be stated.

## What this does to existing files

`LoanFile.get_inbox_address()` composes the address from the **current** setting, so it is not stored
per file. Changing the domain therefore changes the address of **every existing file at once** —
including files whose address has already been given to a borrower in a sent email.

On staging that is nine files and no live mail, so it costs nothing. **It is stated because on
production it would not be**, and this ticket is where somebody should decide whether a file's inbox
address ought to be a stored value rather than a computed one before there is real mail to lose.

## Done when

- Production's default and staging's task definition carry the confirmed values.
- A local value exists and is not production's, by whichever of the three routes is chosen.
- `docs/` and `.env.example` say the same thing as the code. A grep for the old domain returns
  nothing but history.
- The DNS these names need does not exist yet, and neither does the SES receipt rule. **This ticket
  changes what the app advertises, not what receives it** — the address it produces will still reach
  nothing until the infrastructure is applied. That is a different ticket, on hold, and this one must
  not read as having fixed it.

## For the reviewer

The one-line check: grep the whole repository for `inbox.` and confirm every hit is either history, a
comment about history, or a test that pins the old value on purpose. A domain changed in the config
and left in a seed file, a fixture or a doc is the way half of an environment ends up on each.
