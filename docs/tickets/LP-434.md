# LP-434 — Build the extractor generator: JSON spec → working extractor

## What this ticket is

`docs/schema-specs/` holds JSON specs (108 today) describing each document type's
extraction schema; `_GENERATION_GUIDE.md` defines exactly how a spec becomes code,
verified against this codebase. This ticket builds the generator that reads a spec and
emits the artifacts — **validator first, refuse loudly, prove by round-trip before
trusting the templates**. It answers whether 108 schemas is a scripted job or 108
tickets.

The generator lives in `backend/app/ai/extraction/generator/`:
`spec.py` (loader) · `validator.py` (the five §0 stop conditions) · `emitters.py`
(module / prompt / registration / test / count-cross-check / diff-report) ·
`cli.py` (`validate` / `generate`). Tests: `backend/tests/ai/generator/`.

## D0 — the stop conditions (the most important feature)

The validator (`validator.py`) runs **before** any emitter and returns every refusal;
a spec is generatable only when the list is empty. The five conditions (guide §0):

1. an `open_questions` entry with `blocks_implementation: true`;
2. a field `type` with no coercer (only `str`/`Decimal`/`date`/`int` exist);
3. a `pii.kind` not in the live `PiiKind` enum — **DOB and ADDRESS do not exist today**;
4. **any** nested list (~5 bespoke files each, no generic mechanism);
5. a field with no `reason_class`.

The valid PII kinds are read from the live `PiiKind` enum (`{SSN, ACCOUNT}`), **not
hard-coded** — the day someone adds `ADDRESS` with a mask strategy, the validator
accepts it with no edit here.

## D1 — how much is actually identical? (diffed `property_tax_bill.py` vs `w2.py`)

The guide says "near-identical across 18 except the field list." **Diffing two shipping
flat modules, that is true for the *structure* but not the *prose*:**

- **Byte-identical (modulo substituted names):** the imports (only the `parsing` coercer
  line varies with the field types), the `…ExtractionResult` class, `.failed()`, the
  `_parse_*_json` body, the `extract_*` body, the logging, `_SUPPORTED_MEDIA_TYPES`. The
  control flow does not vary at all.
- **Deterministic from the spec:** the field declarations, the `_CORE_SPEC`, the coercer
  import set, every name (class prefix, function names, log labels, prompt path).
- **Genuinely bespoke prose (a generator cannot reproduce, and should not fake):** the
  module docstring, the class docstrings, and the inline field comments
  (`# Box 1`, `# assessed owner (LP-202)`, `# housing/DTI`). `_MAX_TOKENS` also carries a
  per-type comment.

**So the generator emits *neutral, honest* docstrings/comments** (a "GENERATED STARTER —
accuracy UNVALIDATED" banner) rather than imitating the hand-written prose. This is why
the round-trip diff is **all docstrings/comments and nothing else** — see the proof.
The guide's §12 "near-identical" is right about the code and slightly optimistic about
the prose; **the structure is scriptable, the prose is not** (recorded in ADR-341).

## D2 — template mechanism

**f-string templates, normalized through ruff itself.** The emitter writes readable
f-string templates; `emit_module`/`emit_test` then pipe the output through
`ruff check --fix --select I` (import order) and `ruff format` (line-wrapping) via
`--stdin-filename` set to the field's intended `app/` home (so ruff's first-party
detection places `app` correctly). This is the simplest mechanism that **guarantees**
byte-clean, import-sorted, ruff-and-mypy-passing output for any field set — instead of
hand-guessing where ruff would wrap a long `model_validate(...)` call for a long class
prefix. (Jinja/AST buy nothing here — the structure is fixed; only names and a field
list vary.) ruff is a dev dependency, always present in-repo.

| 002 bank_statement | REFUSE | 3 (ADDRESS) · 4 (transactions) |

**⚠️ The ticket predicted 008-w2 would pass ("14 fields, no nested lists, existing PII
kinds"). It does NOT.** `w2` has `employee_address` with `pii.kind: "ADDRESS"`, which is
not in `PiiKind` → condition 3. And `w2` has a shipping extractor, so it is **diff-mode**
anyway (a report, never a fresh module). Reported, not predicted (guide wins over the
ticket text). The two closest-to-passing:
- **009 condo_questionnaire** — no nested list, no bad PII, all coercible types; its
  *only* refusal is one blocking open question (whether IH-7 reads the master-policy
  document instead). Answer that and it generates.
- **008 w2** — its only *field-level* refusal is the single ADDRESS field; the other four
  additions are plain `str` and generate fine (see the diff report below).

**Consequence:** none of the ten produce a fresh full module today, so the full-module
generation proof rests on the **round-trip** (a spec I authored describing
`property_tax_bill` as it ships, `existing_extractor: null`) — which is exactly the
ticket's designated "proof that matters."

## D4 — `_MAX_TOKENS`

**Derived, not added to the spec.** A generatable spec is flat (nested lists refuse), so
its output is bounded fixed-form → the generator emits `_MAX_TOKENS = 4096` (guide §7,
matching every shipping flat 4096 type) with a comment pointing at the sizing rule and
the `test_extraction_budget_sizing` CI guard. The 8192/16384 budgets only ever attach to
nested/dense types, which are refused — so the generator never needs to choose them.
Adding `_MAX_TOKENS` to the spec format was considered and rejected: it would be a
constant `4096` on every generatable spec and dead weight everywhere else. A human tunes
it down (a tiny fixed-form doc → 2048) or up (when a nested list is later hand-added).

## D5 — the prompt's variable parts (confirmed from two real prompts)

Diffing `property_tax_bill.txt` vs `w2.txt`: the **PER-FIELD CONFIDENCE block and the
overall JSON-contract scaffold are byte-identical**. What varies: the document name, the
typed-core field block (names + type labels + `prompt_hint`s), the JSON-contract
`typed_core` keys, and the `reasoning` hint (SSN docs add "do NOT quote the full SSN").
The generator substitutes exactly those, adds a PII rule line when a PII field is present
and a "last-4 only" line when a field is `pre_masked`, and emits a "GENERATED STARTER —
refine with Priya" banner. The generated prompt is a scaffold, **not tuned** (guide §11).

## D6 — diff mode

**A report, never a patch (recommended, and adopted).** When `existing_extractor` is set
the generator emits a diff-mode **report** of the `exists_today: false` additions, each
annotated `ADD` (mechanical) or `BLOCKED` (needs a human — an absent PII kind or a nested
list). It never rewrites or patches the shipping module: a bad patch to a shipping
extractor is worse than a manual edit. `generate` writes only under `--out-dir`.

## What was built

- **`spec.py`** — tolerant loader + `Spec`/`SpecField`/`NestedList`; the four type→coercer
  / →annotation / →JSON / →prompt-label maps.
- **`validator.py`** — the five stop conditions → `list[Refusal]`; PII kinds from the
  live enum.
- **`emitters.py`** — `emit_module` / `emit_prompt` / `emit_registration` / `emit_test`;
  `count_crosscheck_pairs` + `emit_count_crosscheck` (guide §8, built ready);
  `emit_diff_report`; `_ruff_normalize`.
- **`cli.py`** — `validate <specs…>` (report only) and `generate <spec> --out-dir DIR`.
- **Tests** — `tests/ai/generator/test_generator.py` (19 tests) + the round-trip fixture.

## THE ROUND-TRIP PROOF (reported, not predicted)

`tests/ai/generator/fixtures/roundtrip_property_tax_bill.json` describes
`property_tax_bill` as it ships today (`existing_extractor: null`, the 6 shipping fields).
Generating from it and diffing against `app/ai/extraction/property_tax_bill.py`:

- **`_CORE_SPEC` — byte-identical:**
  `owner_name/coerce_str, property_address/coerce_str, assessed_value/coerce_decimal,
  annual_tax_amount/coerce_decimal, due_dates/coerce_str, taxing_authority/coerce_str`.
- **Field declarations — identical** (names + `TypedField[T]`), only the trailing
  hand-written comments removed.
- **Imports — identical** (`from …parsing import (CoreSpec, coerce_decimal, coerce_str,
  derive_status, parse_catch_all, parse_typed_core)`).
- **Every function body — identical.**
- **The ONLY differences are prose:** the module docstring, the class/function
  docstrings, the inline field comments, and the added `_MAX_TOKENS` guidance comment.

Two tests pin this behaviourally: `test_roundtrip_core_spec_identical_to_shipping`
(compares `_CORE_SPEC` name+coercer pairs against the live shipping module) and
`test_roundtrip_model_fields_identical_to_shipping` (model field names + typed
annotations). **No difference in behaviour, coercers, or `_CORE_SPEC` → the templates are
correct.**

## The generated W-2 artifacts (in full)

`008-w2` is **diff-mode** (shipping extractor) **and** ADDRESS-blocked, so the generator's
W-2 output is a **diff report**, not a module:

```
# Diff-mode report — w2 (existing: app/ai/extraction/w2.py)
#
# A shipping extractor exists. This is a REPORT of what the spec adds, NOT a patch
# (guide §6 / D6). Apply the ADD items by hand; each BLOCKED item is its own ticket.

## Typed-core additions (5)
- ADD      employer_address: TypedField[str] / coerce_str
- BLOCKED  employee_address: pii.kind 'ADDRESS' not in PiiKind ['ACCOUNT', 'SSN'] — needs a mask strategy (its own ticket)
- ADD      retirement_plan_checked: TypedField[str] / coerce_str
- ADD      statutory_employee_checked: TypedField[str] / coerce_str
- ADD      is_corrected_w2: TypedField[str] / coerce_str
```

Because no real spec produces a fresh module today, the concrete **full-module** example
is the round-trip `property_tax_bill` — module, prompt, and test all generated, ruff- and
mypy-clean, byte-equal to the shipping module modulo prose. The generated prompt scaffold
and test skeleton carry the identical framing every hand-written one uses, with a
GENERATED-STARTER banner.

## Assumptions / decisions

- **Location:** the generator lives under `app/ai/extraction/generator/` (not `scripts/`)
  so mypy-strict + ruff + the test suite cover it and it can import the extraction shape,
  the coercers, and the live `PiiKind`.
- **ruff-as-formatter (D2):** generation depends on ruff (a dev dep); absent → a clear
  `GenerationError`.
- **Full-module vs diff by `existing_extractor`:** null → validate then emit a module (or
  refuse); set → a diff report, never a module.
- **Leading-digit types** (`document_type` not a Python identifier, e.g. `1099`) are a
  known generator limitation → `GenerationError`, hand-write it. None of the ten hit it.
- **Count-cross-check is built but unreachable today** (every `*_count` field lives beside
  a nested list, and nested specs refuse) — unit-tested directly so it is ready.

## New gaps

- **DOB and ADDRESS PII kinds** block six of the ten (1003, credit report, bank statement,
  pay stub, w2). Each needs a `PiiKind` member **and a real mask strategy** (not last-4)
  — its own ticket, then these specs unblock at condition 3.
- **The nested-list majority.** The top ten carry 12 nested lists; each is a bespoke
  ~5-file ticket (guide §4). The generator refuses them by design.
- **Accuracy is unvalidated** for every generated extractor — same position as the 18
  hand-written ones (guide §11). Validation is Priya reviewing real extractions.

## What the ~98 remaining specs will need

Consistent with guide §12 (**not 108 tickets, not one script**):
- **Scripted generation** for the flat, all-coercible, PII-declared, no-blocking-question
  thin majority — the generator emits module + prompt + test + registration snippet, all
  clean, for each.
- **A bounded set of real tickets** (~15–20) for the nested / PII-heavy / new-coercer
  documents (the top ten alone carry 12 nested lists and the DOB/ADDRESS need).
- **Answer the blocking questions first** — several thin specs (e.g. condo) are one
  resolved `blocks_implementation` away from generating.
- **A Priya prompt-tuning + real-extraction pass** over all of them.

## ADR

**ADR-341** records the generator's contract (what it emits, what it refuses and why, the
round-trip result) and the D1 finding that the modules are less uniform in *prose* than
the guide's §12 implies — the structure is scriptable, the docstrings/comments are not,
so a generated extractor ships with neutral generated prose and a Priya validation pass,
never imitated hand-written prose.

## What this closes

The generator is proven correct by round-trip and refuses every non-generatable spec with
a clear reason. Running it across the thin ~98 (and the DOB/ADDRESS + nested-list tickets)
is the follow-on work, now that the templates are trusted.
