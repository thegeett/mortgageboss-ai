# LP-997 — Send button (Communication tab)

Step 2 of the email work (`loan-email.md` §15a). The Communication tab gets a real Send. Includes one
small migration (a per-company switch) and the backend fields the screen needed. No AWS changes.

**Scope changed after review (2026-10-31):** the condition page is left out for now and is exactly
as it was. See "Not done on purpose".

## What and why

The backend already sends (LP-994) and records what happened (LP-995), but no screen could ask it to.

- **Send in the message dialog** (Communication tab), From the file address with the processor in CC,
  in place of copy / "open in mail app" / "Mark as sent".
- **Only when the company is switched on for sending.** A new per-company switch,
  `company_mail_domains.sending_enabled`, **off by default**. Off: the old buttons. On: Send. It is
  turned on with a command once the company's domain is onboarded for email (below). The server
  refuses a Send while it is off, so the button and the API cannot disagree.
- **Status in plain words**, on the timeline row and in the open message: Queued, Sending, Sent,
  Delivered, "Failed: <reason>", "Not confirmed: check before sending again".
- **Checking for the result:** after Send, the screen re-checks every 30 seconds, three times
  (1.5 minutes). Still queued or sending after that → "Not confirmed: check before sending again", and
  the checking stops. Nothing changes on the server: if the worker finishes later, the next load shows
  the real status.
- **A refused Send** shows the server's own sentence in the dialog, which stays open.

## When does Send show?

`can_send` on the message, computed by `email_send.transmit_blocker`, the same function the Send
endpoint refuses with. Send shows only when all of these hold:

1. The file has an address: the company's domain is active and `FILE_ADDRESSES_ENABLED` is on.
2. The company is switched on for sending (`sending_enabled`).
3. This server has a mail sender (`MAIL_TRANSPORT`). This is why a file could have an address and
   still not send: the address and the sender were two separate settings. Now the button follows both.
4. It is not a condition draft. Those keep "Mark as sent" (on the Conditions page, it also moves the
   conditions to Waiting on …); a Send of one from the Communication tab is refused.

**Turning it on** (after `set_company_mail_domain`):

```bash
uv run python -m app.scripts.set_email_sending "<company id or exact name>" on    # or off
```

It refuses a company with no active domain. In staging it runs as a one-off ECS task, the same way as
`set_company_mail_domain` (`docs/tickets/LP-991.md`, "Link it"), with the command
`["uv","run","python","-m","app.scripts.set_email_sending",$id,"on"]`.

## Not done on purpose

- **Condition page**: no Send there; condition drafts on the Communication tab keep "Mark as sent", and
  the API refuses a Send of one. Its "counts as sent" reads (`_question_sent`, the draft tail) still
  read only `sent`, which is fine while a condition email can only be marked sent. Comes back as its own
  ticket (review findings 1, 5, 6, 7, 9).
- **Content-check screen**: deferred with LP-996.
- **"Send again"** for a failed email.
- **An admin switch** for sending: the command only, for now.
- **"Not confirmed" is screen-only.** The database row stays queued/sending; the worker's own
  re-enqueue (LP-994, every 5 minutes) may still send it, and the next load then shows Sent. The label
  is timed from the server's send time against the browser's clock; a badly wrong browser clock shifts
  it.
- **The Next.js dev overlay counts a refused Send as "1 error"**: the API client logs every failed
  request with `console.error`, as it does for a refused "Mark as sent". Dev only.
