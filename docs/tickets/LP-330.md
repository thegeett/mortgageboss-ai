# LP-330 — Declared absent-document resolution (ID-7 false-green fix)

## What it is

LP-329 resolved EVERY zero-in-scope per_document rule to `not_applicable`. That is correct for ID-9 (a
POA rule when no POA was used — genuinely irrelevant) but WRONG for **ID-7** (a purchase with NO title
commitment — title IS relevant to a purchase; the document is MISSING). ID-7 is **LIVE**, so a missing
title commitment sat in **Tab 4** (`not_applicable`, doesn't block) instead of **Tab 1** (`couldnt_check`,
blocks) — a **live false-green**. This makes the absent-document resolution DECLARED per rule.

## The live false-green it fixes

§8: `not_applicable` = irrelevant to the NATURE OF THE FILE (scope-false, never a finding, Tab 4);
`couldnt_check` = lost visibility — the rule applies, the thing might exist, we can't see it (Tab 1,
BLOCKS). A missing title commitment on a purchase is **lost visibility**, not scope-false. LP-329's
"it's visible in Tab 4 with a reason" is the exact reasoning §8 warns against — Tab 4 is the *doesn't-
block* tab, so a processor scanning Tab 1 for what needs attention never sees it. **Before LP-330** ID-7
on a title-less file → `not_applicable` (silent). **After** → `couldnt_check` ("no title_commitment in
file"), Tab 1, BLOCKS.

## Acceptance criteria

- [x] The absent-subject expectation is DECLARED per rule (`applicability_expected`); generic resolution.
- [x] Expected + confidently absent → `couldnt_check` naming the missing document (Tab 1). Not expected /

- [x] The three §8 cases stay distinct: present-but-unreadable → `couldnt_check` (distinct reason);
  confidently-absent-but-expected → `couldnt_check`; not-expected-absent → `not_applicable`.
- [x] ID-7 declares expected (false-green closed); ID-9 default confirmed (unchanged).
- [x] EQUIVALENCE: every spec without the declaration behaves exactly as LP-329. No rule-id branch.
  ruff + mypy + full suite green.

## Assumptions & decisions

- **"Should this document exist for this file?"** — the framing correction. LP-329 asked "did the filter
  match anything" (circular: scope vs DATA). Only the rule knows whether the document is expected → it is
  DECLARED. `applicability_expected: false` is the default (LP-329's behavior → equivalence).
- **Confidently absent** = every enumerated subject is clearly out of scope (all `not_applicable`; none in
  scope, none `couldnt_check`-from-unknown-type). If any subject is in scope, the document EXISTS. If any
  subject's type is `"unknown"`, we cannot claim absence (that subject already `couldnt_check`s). So the
  missing-document `couldnt_check` fires only when we are SURE the document is not there.
- **One `couldnt_check`, not a mix.** When expected-and-absent, the evaluator returns a SINGLE
  `missing:<type>` `couldnt_check` (the meaningful gap), not the per-doc `not_applicable`s (noise, dropped
  from findings anyway). Stable `missing:<type>` subject id so cross-run reconciliation carries it forward
  and retires it when the document appears.
- **ID-7 ≠ ID-9 from one mechanism.** ID-7 `applicability_expected: true` → title-less file blocks; ID-9
  default `false` → POA-less file `not_applicable`. The DECLARATION is the only difference.
- **Conditional-on-purchase — NOT supportable yet (reported, not invented).** The general form
  (`expected when loan.purpose == purchase`) needs a loan-purpose TAG; none exists (only the `LoanFile`
  DB field, not a snapshot tag). ID-7 is encoded **unconditionally** expected — defensible (a lender needs
  title insurance on a purchase AND a refinance; a rare title-less refinance → `couldnt_check` is safe,
  not a false-green). The conditional is a follow-on once a loan-purpose tag is materialized.

## PRIYA / DOMAIN question

- **Is a title commitment expected on a refinance at this stage of processing?** ID-7 currently expects it
  unconditionally. If Priya says a title commitment is NOT expected on (some) refinances, the fix becomes
  conditional (`expected when purchase`) — which needs a materialized loan-purpose tag first (a follow-on).

## New generalization gap surfaced (reported, NOT patched)

- **A materialized loan-purpose tag.** The conditional expectation (and other purpose-scoped rules) need
  `loan.purpose` (purchase / refinance / cash-out) as a snapshot tag; today it is only a `LoanFile` DB
  field. Materializing it (LP-326 declaration reading the loan file) is a small follow-on that unblocks
  the conditional here and purpose-scoped rules generally.

## What -C must cover for ID-7's absent-title case

A purchase with no title commitment → `couldnt_check` ("no title_commitment in file"), blocks; a title
present but unreadable → `couldnt_check` (distinct reason); a title present + consistent/inconsistent →
satisfied/fired; (once conditional) a refinance with no title → per the Priya decision.
