# LP-452 — Step D.1: the `property.type` parsed tag (gates five rules)

## What this ticket is

The cheapest high-leverage move in the LP-451 audit: **one parsed tag declaration** gating **five rules**
(CO-1, CO-3, CO-5, IH-7, PR-3), each of which must know condo vs SFR vs PUD before it can scope. IH-1's spec
(LP-447) explicitly noted this gap — it could not exclude condos because no reliable property-type signal
existed. **No model calls** (a parsed tag is deterministic; Geet had ~$0.95 of API credit — nothing here
re-extracts or reasons; the full suite uses mocked stubs).

## D1 — where it comes from: MISMO carries it (the key), authoritative for a loan-subject parsed tag

`mismo_section.build_mismo_section` emits it: **`put("property.type", property_.property_type)`** (line 156). So
the exact MISMO fact key is **`property.type`** — one of LP-450's 28 loan-level keys (the tag's reference is in
the guard's universe, D5). This is the authoritative loan-level fact and the natural home for a **loan-subject
parsed tag**, exactly like `program.type` reads `loan.program` and `property.purchase_price` reads
`property.purchase_price`.

Other sources exist (reported): the **appraisal** extractor carries `property_type`, and **purchase_agreement**
carries `property_type` — both document-level. MISMO is chosen because it is the loan-level authority and a
loan-subject parsed tag reads it directly; a document-sourced or cross-source tag would be a materially bigger
job (D3).

**A pre-existing vocabulary orphan, now fixed.** `property.type` was already in the vocabulary (`fact_tags.csv`),
declared `produced_by: AI` with an **aspirational normalised enum** `[sfr, condo, pud, 2-4unit, manufactured,
coop, unknown]` — but with **no producer** (an authored-ahead orphan, read only by the inert CO-*/PR-3 rules, so
non-fatal). This ticket gives it a producer. (Note: the vocabulary metadata still says `produced_by: AI` — it is
generated from the xlsx and can't be hand-edited here; the actual producer is the parsed declaration. A cosmetic
metadata drift to reconcile upstream, like the IH-3 rule_tags drift — it changes no behaviour, and no test
requires `produced_by:AI` ⟺ an AI declaration.)

## D2 — the value set: raw MISMO, NOT normalised — and it is null on every fixture

The MISMO `property_type` column is a `PropertyType` StrEnum: **`single_family / condo / townhouse /
multi_family / manufactured / other`**. `produce_parsed_tag` carries the value **verbatim** (it never re-types —
LP-313), so the tag produces one of those raw strings, or absent.

**⚠️ The declared vocabulary enum does NOT match the MISMO column** (`sfr/condo/pud/2-4unit/manufactured/coop`
vs `single_family/condo/townhouse/multi_family/manufactured/other`). The vocabulary enum was the aspirational
*AI-normalised* set; the parsed tag emits the *raw* MISMO value. **This is correct per the ticket** — "do NOT
normalise into a tidy vocabulary inside the tag; tags describe, rules judge." A rule needing "is this a condo"
branches on the raw `condo`; the finer PUD/co-op/2-4-unit distinctions (which MISMO folds into
`townhouse/multi_family/other`) are a rule's or a derived tag's problem, not a re-labelling here. The
`allowed_values` enum is used only for AI coercion, so it does not constrain this parsed tag.

**The real values from stored data:** MISMO `property_type` is **`None` on all three files** (LF-6T3N, LF-96SV,
LF-XU26) — the MISMO import did not populate it. So the tag is **null on every current fixture** — an honest
source-data gap, fail-closed, reported not predicted (D3 gap).

## D3 — source disagreement: this tag reads ONE source (MISMO); cross-source is a candidate rule

The 1003/MISMO, the appraisal, and the purchase_agreement can each state a property type and can DISAGREE (the
same class as the contract-vs-1003 price case, which has no comparing rule). **This tag reads MISMO only** — the
loan-level authority. A **cross-source property-type comparison is recorded as a CANDIDATE RULE**, not built
here. **New gap:** because MISMO property_type is null on the current files while the appraisal/purchase_agreement
extractors DO carry a type, a follow-up may need a document-sourced or derived tag that falls back to a document
when MISMO is empty — flagged, not forced into this ticket.

## D4 — what the five rules need (raw type vs "is condo"); the boolean is DEFERRED

| rule | quoted check (rule_kinds.csv) | needs |
|---|---|---|
| CO-1 | "Condo → questionnaire present — presence" | **is-condo** |
| CO-3 | "Master + fidelity adequacy vs requirements — judgment" | **is-condo** (+ master policy) |
| CO-5 | "Surface litigation/delinquency/concentration — judgment" | **is-condo** |
| IH-7 | "Condo → master policy present + adequate" | **is-condo** |
| PR-3 | "Classify property type vs allowed — AI-assist" | **the RAW type** (all types) |

Four of five want an "is condo" boolean; PR-3 wants the raw type. **The boolean is NOT built here**, deliberately:
(1) it is **untestable on the current fixtures** (property.type is null on all three); (2) MISMO has no PUD/co-op
enum (they fold into `other`), so "is condo" from MISMO alone may be insufficient for the real condo rules, which
also reference a separate `property.is_warrantable_condo` concept and the master-policy document — the
condo-detection semantics belong in the rule tickets, with that context, not a premature re-labelling here. Per
the ticket, the boolean belongs in this ticket "only if trivial"; the null data + the mapping ambiguity make it
not-trivially-correct yet. Recorded for the rule tickets. **One tag, one source, no judgment.**

## D5 — the guard

The LP-450 `_mismo_field_universe` guard validates parsed loan/borrower `data` references. `property.type` is a
real MISMO loan key, so the guard **accepts** it (asserted) — a typo'd reference would have failed loudly instead
of resolving silently to absent (the IH-1 trap this whole step closes).

## What was built

- `tag_production.yaml`: `property.type: {mode: parsed, subject: loan, data: property.type}` — the parsed
  loan-subject declaration, mirroring `program.type` / `property.purchase_price`.
- `tests/verification/tag_materialization/test_property_type_tag_lp452.py`: materialises verbatim from MISMO (a
  raw value is not re-typed); an absent source → an absent tag (fail closed); the declaration is parsed/loan
  reading the MISMO key; the LP-450 guard accepts it.
- **No rule written, no value normalised, no source compared, no existing tag touched.**

## Assumptions / decisions

- MISMO is the single source (D3); the appraisal/purchase_agreement document sources and any cross-source
  reconciliation are deferred (a candidate rule + a possible fallback tag).
- The raw MISMO value passes through unnormalised (the ticket's rule); the stale vocabulary enum
  (`sfr/pud/coop/…`) and `produced_by: AI` are cosmetic drift to reconcile in the xlsx upstream.
- The "is condo" boolean is deferred to the rule tickets (untestable on null data + the condo/PUD/coop-vs-MISMO
  mapping needs the rules' context).

## NEW gaps / what remains

- **MISMO property_type is null on all fixtures** — the tag is wired and guarded but produces nothing until a
  file carries the fact (or a document-sourced fallback is added). This is the honest state.
- **A document-sourced / cross-source property-type tag** (appraisal or purchase_agreement fallback) is a
  candidate if MISMO stays empty in practice.
- **A cross-source property-type comparison rule** is a candidate (the disagreement question).
