# LP-366-A — The `loan_tag` operand: read a loan-level tag from any rule, without a calculator

## WHAT THIS IS

The **engine half** split out of LP-366. LP-366 wanted to fix AS-1's false DTI dependency as a pure DATA
change — swap AS-1's income operand off the gated DTI calc onto a direct income read. Phase 0 proved that is
**impossible** with the operands that exist: a `tag` operand is subject-scoped, and a `per_deposit` rule (AS-1)
never has the loan's tags in its subject map. The only door to loan-level was `calc` — the very thing dragging
in the insurance gate. The blocker is a **missing operand kind**, so it becomes its own small, generic engine
ticket. LP-366 (still open) is now the trivial one-line data swap that consumes this.

## THE BLOCKER (Phase 0, proven)

- `_resolve_operand(operand, spec, snapshot, subject_tags)` resolves a `tag` operand from `subject_tags`.
- The `per_deposit` enumerator hands each transaction subject ONLY its own tag map
  (`by_subject[txn.content_id]`) — **never** the loan's (`enumerators.py::_per_deposit`).
- ∴ a per-deposit rule **cannot** read a loan-level fact through a `tag` operand. The only operand that
  reaches loan-level is `calc` (`snapshot.calculations`), which is exactly what fail-closes on
  `housing.insurance_monthly` (LP-367) — an input AS-1 never uses.

This is a structural gap in the operand vocabulary, not a data typo. Reported; the user chose "split into its
own ticket."

## WHAT WAS BUILT (engine, small, generic)

1. **`specs.py` — the `loan_tag` operand.** `Operand` gains `loan_tag: str | None`; it joins the
   exactly-one-source set (`tag / loan_tag / reference / calc / product`), and a non-decimal `type`
   (LP-328) is valid on `loan_tag` as it is on `tag`.
2. **`deterministic.py` — one resolution branch.** A `loan_tag` operand reads
   `snapshot.tags.by_subject[LOAN_SUBJECT]` directly (the same access `_per_loan` uses), coerced through the
   SAME `_COERCERS[type]` registry as `tag`. **Fail-closed:** absent loan subject / absent tag / unparseable
   value → `None` → `couldnt_check`. **Never `0`** (a `0` income would size AS-1's threshold to zero and fire
   on every deposit).
3. **`tag_production.yaml` + `derived.py` — the income tag it reads.** Declares
   `dti.qualifying_income_monthly` (mode `derived`, subject `loan`) — the tag already existed in
   `fact_tags.csv` but had no producer. The recipe sums the borrowers' MISMO **stated** income lines
   (`borrower.<n>.income.<m>.monthly_amount`), abstaining to `unknown` (never `0`) on no income or an
   unparseable line. Enumerates borrower indices from the facts (a gap must not truncate the sum).

**No rule-id branch. No live-rule change.** A rule opts into a loan-level read with a SPEC line only.

## WHY `loan_tag` BEATS `calc` (independent of AS-1)

A `calc` operand ignores the calculator's confidence (LP-318 Caveat A — `_calc_operand` never reads
`entry.confidence`). A `loan_tag` flows the tag's confidence through the **ordinary tag gate**, like every
other governed fact. Reading a loan-level number as a *governed tag* rather than an *opaque calculator output*
is strictly more honest — a general property, true regardless of AS-1.

## D1 — WHICH INCOME TAG (argued, not assumed)

AS-1's threshold is definitionally **"50% of total monthly qualifying income."** The right tag is the
**existing** `dti.qualifying_income_monthly`, NOT a newly-minted second income figure (LP-323-IN-A warns
against minting parallel income numbers). Its recipe sums the **MISMO STATED 1003 income** — the SAME income
the DTI qualifies on (the DTI's income lines are `source='stated'`). So AS-1 and the DTI qualify on one
figure, produced once. On the real file it materializes to **$28,168.80**, matching LP-365's reported
`gross_monthly_income` exactly.

## F2 — recorded prominently

AS-1's income is the **MISMO stated 1003 total** (`source='parsed'`), **NOT** the AI
`income.qualifying_monthly` tag. That AI tag **did not materialize** on the real run (one of the 95
degradations) and its continuity/averaging convention is underspecified (LP-343 F2). Reading the stated total
keeps F2 **entirely off AS-1's path** — AS-1 never depends on the AI qualifying-income judgment. (Whether the
AI qualifying tag *should* materialize is the 95-degradations ticket's question, below — orthogonal to this.)

## EQUIVALENCE (verified)

- AS-1 is **byte-identical**: its `threshold` operand is still `{product: [{reference: ...}, {calc: [dti,
  gross_monthly_income]}]}`. The AS-1→`loan_tag` swap is **LP-366**, a separate data change.
- The `calc` operand is **untouched** — AS-4 keeps it (its reserves→PITI→insurance dependency is legitimate).
- `ACTIVE_RULE_IDS` unchanged. Full backend `tests/verification tests/tasks` suite green (**855 passed**,
  `-p no:randomly`). `mypy app/` clean. Ruff clean.

## TESTS

- `tests/verification/rule_engine/test_loan_tag_operand.py` (13) — the mechanism (`_resolve_operand` reads the
  loan subject from a NON-loan subject, where a `tag` operand returns `None`); fail-closed (absent tag / absent
  loan subject / unparseable → `None`); the validator (exactly-one includes `loan_tag`; non-decimal `type`
  allowed on `loan_tag`, still rejected on `reference`); end-to-end (a synthetic **per_deposit** spec reading a
  `loan_tag` fires / satisfied / couldnt_check, from a SPEC only); equivalence (AS-1 still `calc`;
  `ACTIVE_RULE_IDS` unchanged).
- `tests/verification/tag_materialization/test_qualifying_income.py` (6) — the recipe sums stated income
  (matches the real $28,168.80), enumerates non-contiguous borrower indices, and abstains to `unknown`
  (never `0`) on MISMO-absent / no-income / unparseable-line.

## REPORTED, NOT FIXED (each its own ticket)

- **The 95 `tag_production` degradations** (LP-365) — NOT investigated here. Whether
  `income.qualifying_monthly` should materialize is orthogonal to AS-1 reading the stated total.
- **Pre-existing flaky test:** `test_no_raw_pii_in_stored_json` trips the `_LONG_DIGITS` at-rest guard
  (`\b\d{9,}\b`) ~0.6% per persisted `PiiField`, because a salted `match_hash` hex occasionally contains a
  quote-bounded 12-digit run (empirically 19/3000 salts over the exact snapshot shape). **Independent of
  LP-366-A** — that test hand-builds its snapshot; no recipe runs in it. Flagged for its own ticket (the guard
  should exclude the hex `match_hash` region, or the hash should be non-numeric-bounded). Run the suite with
  `-p no:randomly` or rerun to confirm green in the meantime.
