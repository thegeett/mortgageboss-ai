## 1. The name matcher fails when a given name is written with a space — FIXED HERE

**What happens.** `_score_one` takes the FIRST TOKEN of the borrower's given name and matches it
token-by-token against the document's name tokens. A name written as ONE word on the application and
TWO on the document can never match, however perfect the surname is.

**Evidence, both ends.** The MISMO carries `<FirstName>Vidulasrri</FirstName>`. The PDFs themselves
print `Vidula Srri Muruganandam` (pay stub) and `VIDULA SRRI MURUGANANDAM` (bank statement) — read
out of the PDF text, so our extraction is FAITHFUL and this is not an extractor bug. Run against the
real matcher:

```
VIDULASRRI MURUGANDAM     (surname missing a syllable)      -> fuzzy @ 0.95   LINKED
VIDULA SRRI MURUGANANDAM  (space in given name, surname OK) -> NO MATCH
```

It accepts a CORRUPTED SURNAME and rejects a SPACE — lenient about the riskier variance, strict
about the safer one.

**Impact.** 11 of 13 documents unlinked. Roughly fifteen rules degrade to couldn't-check with text
that misreads as a documentation gap: IN-5 "only **0** document(s) state the employer name",
IN-10/IN-11 "no income documents are currently attributed to this borrower", ID-2 "no documents
showing the borrower's SSN" — on a file carrying two W-2s. The file looks fully documented and
silently is not verified. Hits `Mary Ann`/`Maryann`, `De La Cruz`/`Delacruz`, and most South Asian
given names.

**The fix.** `_adjacent_joins` — concatenations of two or more ADJACENT tokens — applied in three
places, symmetrically, because the asymmetry runs in both directions and on both halves of a name:

- `_best_token_match` tries the borrower's token against the document's adjacent joins
  (`vidula` + `srri` → `vidulasrri`);
- `_score_one` tries the borrower's joined GIVEN name against the document's tokens (`Mary Ann` on
  the 1003 vs `MARYANN` on the pay stub — only `first_tokens[0]` was ever scored, so `Ann` was
  invisible);
- `_score_one` tries the borrower's joined SURNAME against the document's tokens. `last_tok` is the
  surname's LAST token, so `Van Der Berg` anchored on `berg` alone and a document printing
  `VANDERBERG` failed. Without this the fix was half a fix.

**Two restrictions, both precision rather than tidiness.** ADJACENT tokens only — splicing
non-adjacent tokens would invent a surname nobody wrote. And a join matches by EXACT membership
only, never fuzzily — a re-spacing stacked on top of an edit is two liberties at once on the
evidence that two people are the same person.

The result is labelled `normalized`, not `exact`: the same name, differently spaced.

**Verified against the real values, and against the cases that must still fail:**

```
VIDULA SRRI MURUGANANDAM  (the real document)     -> normalized @ 1.0   was NO MATCH
MARYANN SANCHEZ           vs app "Mary Ann"       -> normalized @ 1.0
PIET VANDERBERG           vs app "Van Der Berg"   -> normalized @ 1.0
JOSE DE LA CRUZ           vs app "Delacruz"       -> normalized @ 1.0

PRIYA MURUGANANDAM        (different given name)  -> NO MATCH
VIDULASRRI SUNDARAM       (different surname)     -> NO MATCH
VIDULA SRRI MURUGANANDAM  vs app "Raj Muruganandam" (a relative)     -> NO MATCH
JOHN SMITH SONIA          vs app "Ann Smithson"   -> NO MATCH   (substring, not a join)
```

**A matcher fix alone would not have reached this file.** Linking runs ONCE, in `process_document`,
at the moment the extraction succeeds; re-running verification never re-links. So
`app/scripts/relink_document_borrowers.py` re-runs `assign_document_borrower_links` over documents
already extracted — no re-extraction, no model call, it reads the extraction already on disk. Report
only by default; `RELINK_FILE=LF-ABRS` scopes it to one file. It CAN remove links (a link the old
matcher made wrongly should go) and it skips a FAILED extraction, because the linker DELETEs before
it looks for names and a failed extraction is an absence of data, not a determination that the
document names nobody (LP-569's guard, re-applied).

## 2. Snapshots never persist — the PII guard's known over-flag, landing — FIXED HERE

Both runs completed and stored ZERO snapshots:

```
mismo.facts.property.postal_code.value                    (a 9-digit run)
documents.entries[10].fields.project_or_job_number.value  (a 10-digit run)
```

**The refusal is all-or-nothing.** One unrouted field does not lose its own value — it rejects the
ENTIRE snapshot, so the file loses every tag value and every calculation too. That is what made two
ordinary reference numbers cost this file its whole audit trail on every run.

### The postal code — fixed at the parser, plus a migration

The MISMO carries `<PostalCode>341203361</PostalCode>`: a ZIP+4 with the hyphen dropped, which is
LITERALLY the example `persistence.py` names in its own comment. The same export writes `40290-1037`
WITH the hyphen elsewhere, so this is one field inconsistent with its own document, not a house
style to respect.

`_to_postal_code` in the MISMO parser hyphenates a value that is exactly nine digits and passes
everything else through untouched — a 5-digit ZIP, an already-hyphenated ZIP+4, and a non-US code
are left as written, so it cannot corrupt an address it does not understand.

**A parser fix alone would not have reached this file.** Import is ONE-SHOT and the snapshot reads
`properties.postal_code` from the TABLE, not from the XML. Migration `d2e5b83c61af` normalizes the
stored rows, matched on `^\d{9}$` so nothing else is touched. It is a pure column normalization with
no I/O — which is why it is a migration and not a script, unlike LP-596's backfill.

### The job number — fixed by routing

`project_or_job_number` (survey) now goes through `_PII_FIELDS`, the remedy the guard's own message
asks for. Not borrower PII and read by no rule (`"rules":[]` in its schema spec) — routed for the
reason LP-509-C1 already recorded for `state_employer_id` and `control_number`: masking keeps the
guard strong, where an exemption would trade a loud failure for a silent leak.

I also tried to route `aba_routing_number` on the reasoning that a US routing number is always
exactly nine digits — and the linter rejected it as a duplicate key. **It was already routed**, by
LP-466/467, on exactly that reasoning. Worth recording: I had read only the first screen of an
84-entry registry and assumed the rest.

### The exposure this leaves — worth its own ticket

A sweep of the extractor set found **142 identifier-shaped fields** (`*_number`, `*_id`, `*_tin`,
`account*`). **55 are routed; 87 are not.** Fifteen of the unrouted ones carry values that are
routinely nine digits or longer:

```
case_number                  certificate_number            check_reference_or_trace_number
commitment_number            counseling_certificate_number invoice_or_receipt_number
lender_id_or_loan_number     lender_loan_number            loan_number_property_or_invoice
master_policy_number         parcel_identification_number  parcel_or_tax_map_number
permit_number                va_file_or_loan_number        wire_or_ach_trace_number
```

`parcel_identification_number` is on the appraisal and the title commitment — two documents that
reach almost every file — and a Florida parcel id is routinely 12+ digits. Each of these is a latent
all-or-nothing snapshot refusal waiting for the first file that carries a long value in it.

Deciding which of the 142 to route is a per-field data decision, not a bulk edit — the same judgment
`persistence.py` already refuses to make in a pattern. Recorded here rather than guessed at.

## 3. DTI reports the property tax "missing" when the file states it twice — FIXED HERE

The gate reads "DTI calculation gated due to missing property tax amount". The file contains:

- UWM dashboard, p3 — "Annual Property taxes: **$5,579.00**"
- Property Explorer report — "Tax Amount (Year) — **$5,579 (2025)**"

**And we extracted it.** `home_value_estimate.annual_property_taxes = 5579` is in the database,
captured at upload. So this was never an extraction failure.

### Why it was missed

The calculator reads ONE document type and ONE field:

```python
taxes = await _extracted_monthly(db, loan_file.id, "property_tax_bill", "annual_tax_amount", annual=True)
```

The file has no `property_tax_bill`, so that returns `None`, the line is unknown, and the calculation
gates. The `home_value_estimate` carrying the figure was never consulted.

**That narrowness is CORRECT.** `_extracted_monthly` fails closed for the reason its own docstring
gives — "never a confident too-low DTI resting on a fabricated 0" — and an automated valuation's
assessor-sourced estimate is not verification for underwriting. A calculator that quietly read the
estimate would produce a confident DTI on a number no underwriter accepted. The defect was never
"use the estimate"; it was that the GATE had no idea the estimate existed.

### The fix

`_unverified_housing_inputs` reads OUR OWN stored extraction of the home value estimate and, when the
taxes line is the gated one, returns a sentence naming the figure and why it is not enough:

> The home value estimate states annual property taxes of $5,579.00. That is an automated valuation's
> estimate, not verification — upload the property tax bill.

It cannot ungate anything: it feeds no line, only the reason. A processor who disagrees can still
override the line explicitly, which is a decision on the record rather than an estimate promoted
quietly.

Carried STRUCTURALLY on `DtiCalculation.unverified_inputs` rather than folded into the text by each
producer, because there are TWO gate-reason producers — the /dti card's (`services/dti.py`, human
labels) and the snapshot's (`calculations_section`, tag ids, which is what the AI cross-check reads
and therefore what a processor actually saw) — and rebuilding the sentence in both would let them
drift.

Guarded on both sides: a file that genuinely states nothing reads exactly as it did before, a $0
estimate is not quoted (`absent != 0` — quoting it would invite an override to zero), a file gated
only on insurance is not told about a tax estimate it was not asked for, and naming the estimate
never clears the gate (`back_end_dti` stays None).

### One click to accept it

Decided and built: the gated DTI card offers **"Use the estimate ($464.92/mo)"**, with the reason in
a tooltip. Clicking it writes an ORDINARY OVERRIDE — the processor's id and a note reading
`Accepted the home value estimate's figure of $5,579.00/yr — not a verified tax bill.` The
difference between this and letting the calculator read the estimate is the whole point: one is a
decision on the record, the other is an assumption nobody made.

`UnverifiedInput` carries `field_key` + `monthly_amount` precisely because they are what
`DtiOverrideInput` needs, so the offer and the override cannot disagree about the figure.

### ⚠ WHAT THIS EXPOSED: nothing tracks the missing tax bill

Checked while building the button, and it changes what the button must say. `housing.taxes_monthly`
is read by **DT-1 and DT-4, and NEITHER HAS A SPEC FILE** — neither is a live rule. Nothing else asks
for a property tax bill: no Need List item, no rule, nothing.

**So the DTI gate is the only thing on the file that says the tax bill was never provided.** Accept
the estimate and that signal is the last one gone — the requirement disappears with the gate that
was standing in for it.

Which is why the tooltip says, in as many words, that the tax bill is still outstanding; and why
that is a plaster over a real gap rather than a fix for it. **A rule or Need List item for the
property tax bill belongs on its own ticket** — the file should not depend on a calculator's gate to
remember what it is missing.

## 4. DT-6 and RE-1 issue two different instructions about the same lien — FIXED HERE

Both fired on the unmatched Lake Michigan Credit Union mortgage statement:

- **RE-1** (needs_review): "...and if so, **add it to the application's liability list**."
- **DT-6** (couldnt_check): "Confirm whether the mortgage is **being paid off at closing or
  retained**."

One lien, two different instructions — from the rule whose own header promises it will not
"double-report the discrepancy RE-1 already surfaced".

### DT-6 was keeping that promise. The prose was not.

Its verdict WAS couldnt_check, exactly as designed. The cause is three steps back:

1. **The gate path short-circuits before any declared outcome** and reads `couldnt_check_fix`.
2. **DT-6 declared its careful guidance on the `couldnt_check` OUTCOME instead** — text that already
   deferred to the undisclosed-mortgage check. The gate never reaches an outcome, so it found none
   and the finding shipped with `how_to_fix` **NULL**.
3. **The composer must "make THE SAME REQUEST as `suggested_fix`"** — and with no request to make, it
   reasoned from the situation to a DIFFERENT question, which another rule already owned.

### The fix, in two parts

**DT-6 declares a `couldnt_check_fix`** saying what it actually needs (which liability the statement
belongs to, and a monthly payment on both sides) and handing the undisclosed-mortgage question back
to the rule that owns it.

**The composer gains the rule it never had for the empty case**: when `suggested_fix` is absent, ask
only for what `problem` says is missing and introduce NO new question — because another rule may own
that question and be asking it already, and two instructions about one fact is worse than one. The
real example is written into the prompt.

### Why this reaches the finding already on the file

The composer's cache is persistent and keyed on the FACTS (`sha256(to_json())`), **with no prompt
version in it** — so a prompt change ALONE would leave every already-composed finding exactly as it
is. Adding the `couldnt_check_fix` changes the facts, which changes the key, which turns the stored
invented action into a miss. Verified: the two keys differ.

### What this leaves — worth its own ticket

**45 rules can gate; only 15 declare a `couldnt_check_fix`.** DT-6 is now one of them; the other 44
still hand the composer an empty request on the gate path. The prompt rule reduces what it does with
that vacuum, but the prompt is not a mechanical guard — LP-601's self-healing re-check only drops
cached prose a `rejection_reason` can DETECT, and "invented a plausible action" is not detectable
that way. So for those 44, already-composed findings keep whatever was invented.

Writing 44 fix texts is real work with a domain judgment in each, which is why it is recorded rather
than bulk-guessed:


## 5. Cross-check findings resolve and reopen under new wording — FIXED HERE

All nine run-1 findings went `resolved`; nine opened in run 2, several the same issue reworded — and
**"Recurring Chase credit card payments not matched to stated liabilities" appeared in both lists
with a byte-identical title**. Nothing had resolved.

### It was not the index drift you would guess

`finding_key` is `sha256(kind + sorted paths)`, so identity is the snapshot ADDRESSES. Both rows had
the same kind and the same title, so the paths differed — and four documents had been added between
the runs, which makes positional shift the obvious suspect. The indices were IDENTICAL:

```
run 1   documents.entries.0.transactions.13.description
run 2   documents.entries.0.lists.transactions.13.fields.amount.value
```

Same statement, same row. Two things differ: the CHANNEL and the quoted FIELD.

`documents_section` publishes a bank statement's transactions **twice** — through
`entry.transactions` (typed, feeds AS-1) and through `entry.lists["transactions"]` (generic, LP-437)
— and says so in its own comment: *"the SAME extracted transactions rows populate BOTH"*. Both are
real addresses and the grounding check accepts both, correctly. Identity hashed them verbatim.

This is exactly the failure LP-613 fixed for leaf-vs-route, arriving through a second door — and its
docstring predicted it: *"accepting two spellings of ONE address meant a model that cited the leaf on
one run and the route on the next produced two different `finding_key`s... That is the failure this
whole module exists to prevent, arriving through the door left open for grounding."*

### The fix

A document row canonicalises to the ROW, through either channel, dropping the quoted field. Within
one transaction the field is the model's choice of what to quote about a single event — commentary,
in LP-604's sense, exactly like the title.

**Deliberately not applied to the flat sections.** `liability.3.unpaid_balance` and
`liability.3.monthly_payment` are genuinely different facts about one debt, and merging them would
hide one behind the other. **The row index is kept**, as LP-613 kept it: stripping it would collapse
two different transactions onto one key, the failure measurement rejected there.

Verified on the real strings: the two run-1/run-2 spellings become one identity, while a different
row, the same row number in a different document, two facts about one liability, and a document's own
field all stay distinct.

### What this does not fix

The already-stored rows keep the keys they were written with, so LF-ABRS's existing duplicate pair
stays until something re-keys them. This stops the NEXT run from minting a third.

Nor does it address drift in a flat-section path — the model citing `liability.3.unpaid_balance` one
run and `liability.3.monthly_payment` the next about one observation would still churn. LP-604
measured that case at 4-of-5 stability and left it; this ticket does not re-open that measurement.
