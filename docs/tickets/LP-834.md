# LP-834 — The secure link belongs in the draft

- **Ticket:** LP-834 · Phase 4 follow-up, from processor feedback
- **Status:** Specified — not started
- **Date:** 2026-09-07
- **Scope:** `services/upload_links.py`, `services/email_draft.py`, the draft modal
- **Migration:** none expected

---

## What was asked

> *"Secure upload link does not require borrower's email. While reading draft model, allow an option
> to add Secure upload link. [...] Each draft window has secure upload link, on clicking it expire
> previous one and make active new one and append it to email draft."*

## Measured

**The email is already optional.** `mint_upload_link(recipient_email: str | None = None)` and the
request schema agrees. So "does not require borrower's email" is true in the service today — the
thing to check is that no screen asks for it as though it were required, and the panel's field is
already labelled *"Who is it for (optional)"*.

**The link is on its own panel, not in the draft.** A processor mints it in one place and pastes it
into another, which is the gap this closes.

## Why "expire the previous one" is the right rule and needs saying

A live link is a bearer credential. Two live links on one file means two ways in, one of which is in
an email nobody is looking at any more. Expiring on mint keeps **one live link per file**, which is
also what makes "the link in this draft" a meaningful phrase — otherwise a borrower holding an older
email has a working link to a request that has moved on.

The cost is real and belongs in the ticket: **a borrower who was already sent a link loses it.** If a
processor adds a link to a second draft, the borrower reading the first email now has a dead link and
no explanation. That is the correct trade against two live credentials, and it is the reason the
action needs to say what it does before it does it.

## The plaintext token, which decides the shape

`MintedLink`'s docstring: the token *"exists HERE AND NOWHERE ELSE — the row holds a hash"*. So a URL
cannot be rebuilt later. Two consequences:

* the link must be written into the draft body **at the moment it is minted** — there is no reading
  it back;
* once written, that draft body holds a live credential. `communications.body` is already
  `NEVER_EXPOSED` in the readonly views, so it does not reach analytics — but it does mean a draft is
  now a thing with a secret in it, and that should be stated rather than discovered.

## Done when

- The draft modal offers "Add a secure upload link". Clicking it mints a link, **expires any other
  live link on the file**, and appends it to the draft body.
- The processor is told, before clicking, that any link already sent stops working. Not after.
- No borrower email is required at any point in that flow, and nothing on screen implies otherwise.
- Adding a link twice to the same draft replaces the line rather than appending a second one. Two
  links in one email is the state this ticket exists to prevent, arriving by the obvious route.
- The body still renders correctly with no link — this is an option, not a step, and a draft without
  one is a complete email (LP-824 names the route in words rather than carrying a URL).
- A test asserts the previously live link is dead after a new one is minted, by **redeeming it and
  being refused**, not by reading a column.

## For the reviewer

The interesting failure is a link minted and the draft save failing after it: the old link is dead,
the new one is in no email, and the file has a live credential nobody can see. Whether that is
possible depends on where the mint sits relative to the write, and it is worth checking rather than
assuming the transaction covers it.
