# LP-834 — The secure link belongs in the draft

- **Ticket:** LP-834 · Phase 4 follow-up, from processor feedback
- **Status:** Built — awaiting review
- **Date:** 2026-09-07
- **Scope:** `services/upload_links.py`, `services/email_draft.py`, the draft modal
- **Migration:** `c7d2e94f1a35` — the draft remembers its link

---

## What was asked

> *"Secure upload link does not require borrower's email. While reading draft model, allow an option
> to add Secure upload link. [...] Each draft window has secure upload link, on clicking it expire
> previous one and make active new one and append it to email draft."*

## Measured

**The email is already optional.** `mint_upload_link(recipient_email: str | None = None)` and the
request schema agrees. So "does not require borrower's email" is true in the service today — the
thing to check is that no screen asks for it as though it were required, and the panel's field is
already labelled *"Who is it for (optional)"*.

**The link is on its own panel, not in the draft.** A processor mints it in one place and pastes it
into another, which is the gap this closes.

## Why "expire the previous one" is the right rule and needs saying

A live link is a bearer credential. Two live links on one file means two ways in, one of which is in
an email nobody is looking at any more. Expiring on mint keeps **one live link per file**, which is
also what makes "the link in this draft" a meaningful phrase — otherwise a borrower holding an older
email has a working link to a request that has moved on.

The cost is real and belongs in the ticket: **a borrower who was already sent a link loses it.** If a
processor adds a link to a second draft, the borrower reading the first email now has a dead link and
no explanation. That is the correct trade against two live credentials, and it is the reason the
action needs to say what it does before it does it.

## The plaintext token, which decides the shape

`MintedLink`'s docstring: the token *"exists HERE AND NOWHERE ELSE — the row holds a hash"*. So a URL
cannot be rebuilt later. Two consequences:

* the link must be written into the draft body **at the moment it is minted** — there is no reading
  it back;
* once written, that draft body holds a live credential. `communications.body` is already
  `NEVER_EXPOSED` in the readonly views, so it does not reach analytics — but it does mean a draft is
  now a thing with a secret in it, and that should be stated rather than discovered.

## Done when

- The draft modal offers "Add a secure upload link". Clicking it mints a link, **expires any other
  live link on the file**, and appends it to the draft body.
- The processor is told, before clicking, that any link already sent stops working. Not after.
- No borrower email is required at any point in that flow, and nothing on screen implies otherwise.
- Adding a link twice to the same draft replaces the line rather than appending a second one. Two
  links in one email is the state this ticket exists to prevent, arriving by the obvious route.
- The body still renders correctly with no link — this is an option, not a step, and a draft without
  one is a complete email (LP-824 names the route in words rather than carrying a URL).
- A test asserts the previously live link is dead after a new one is minted, by **redeeming it and
  being refused**, not by reading a column.

## For the reviewer

The interesting failure is a link minted and the draft save failing after it: the old link is dead,
the new one is in no email, and the file has a live credential nobody can see. Whether that is
possible depends on where the mint sits relative to the write, and it is worth checking rather than
assuming the transaction covers it.

## Built, 2026-09-09

### The ticket missed that regeneration would wipe it

The ticket said the link must be written into the body at mint time, since the token cannot be read
back. True, and not sufficient: **`_regenerate` rewrites the body from the template on every add and
remove.** A link living only in the prose would be gone the first time a processor requested one more
document — and unrebuildable, because `upload_links` holds a hash.

So the draft **remembers** its link: `communications.upload_link_url`, nullable, and
`render_draft_body` is handed it. Regeneration is lossless because the renderer is given the URL
rather than parsing it back out of a sentence.

**That column holds a bearer credential, and it is stated rather than discovered.** It is the same
secret already in `body`, which is `NEVER_EXPOSED` in every readonly view; this column is excluded
there too, and the drift guard is what enforces that rather than this paragraph. The guard caught it
on the first run and made me say why.

### The template gained a slot, not a sentence

`initial_documentation_request.v4` replaces the fixed security sentence with `$secure_upload_block`.
`secure_upload_block(None)` renders **LP-824's exact wording**, so a draft with no link is unchanged
— the words a borrower reads are identical to v3's. With a link it renders the caution, the URL and
how long it lasts, derived from `DEFAULT_TTL_HOURS` rather than typed again.

`SECURITY_CAUTION` is in both branches. It is a fixed decision in the execution protocol and does not
become optional because a link exists.

### One live link per file, and the cost falls on somebody who cannot see it

Minting revokes every other usable link on the file. Two live links means two ways in, one of them in
an email nobody is looking at any more.

**A borrower already sent a link loses it** — they click and are refused, with no explanation on
their end. That is the correct trade and it is why the button says what it does **before** it is
clicked: *"Any link already sent to this borrower stops working."* Once a draft carries one the
control reads **Replace the secure link**, because a button still saying "Add" is how a processor
reaches two-links-in-one-email believing they are adding a second route.

### What proves the old link is dead

**Using it.** `revoked_at` being set proves a write happened; a borrower clicking the link they were
sent is what must be refused. So `test_minting_again_kills_the_first_link_for_a_borrower_holding_it`
mints, **asserts the first link works**, mints again, and then GETs and POSTs the first token through
the public endpoint a borrower would reach. Both are 404.

The control matters as much as the assertion: without "it worked first", a link that never worked
would satisfy the refusal and prove nothing.

### Mutations

| mutation | result |
|---|---|
| the previous link is not revoked | 1 failed — the redemption test |
| the URL is not stored on the draft | 4 failed |
| regeneration forgets the link | 4 failed |
| the warning replaced with a bare label | 1 failed |
| the button always says "Add" | 1 failed |

### One thing the ticket asked for that was already true

*"No borrower email is required at any point"* — `mint_upload_link(recipient_email=None)` was already
the default and the panel already labelled its field optional. `attach_upload_link` passes nothing:
the link is for whoever the draft is addressed to, which the processor may not have typed yet, and
the redemption path checks no address.

### The three standing checks

**Tenancy:** the endpoint is `ScopedLoanFile`-gated and resolves the draft through `message_detail`,
which checks `loan_file_id` on the row; the mint is scoped to that file. **Logging:** one line, and
it carries the loan file id — never the URL, which is the credential itself. **AI:** none.
