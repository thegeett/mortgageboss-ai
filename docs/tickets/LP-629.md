# LP-629 — one worker slot serialises the whole environment

**Status: PHASE A BUILT for staging and dev. Not deployed, not committed.**
Phase B (queue separation) and Phase C (production sizing) not started.

## The report

Staging processes **one background job at a time, for the entire environment**. Every document
extraction, every verification run and every needs update stands in the same single-file queue.

Three independent measurements, all from staging CloudWatch on 2026-08-23/24:

**1. The worker's own startup banner, on every restart:**

```
- *** --- * --- .> concurrency: 1 (prefork)
```

**2. Every task log line is `ForkPoolWorker-1`.** There is no second child. `mbai-staging-worker`
is `desiredCount: 1`, so one container x one child = one slot.

**3. Six documents from one upload, run strictly back to back:**

| Finished | Duration |
|---|---|
| 22:45:30 | 27.5s |
| 22:46:05 | 35.0s |
| 22:46:36 | 31.6s |
| 22:47:03 | 26.4s |
| 22:47:28 | 25.6s |
| 22:47:54 | 26.0s |

Each completion is spaced by exactly the previous task's duration. **2m53s of wall clock for a
critical path of ~35s.**

And seven `verification.run_rule_engine` runs: **404.8, 413.9, 425.2, 427.1, 431.2, 443.2, 445.4
seconds**. For those ~7 minutes the environment's only slot is held, so a document another
processor uploads mid-run waits behind it. This is not verification blocking verification — it is
one job blocking everything.

## Why it is 1, and why that is nobody's decision

No `--concurrency` flag exists anywhere: not in `backend/Dockerfile:59`, not in
`docker-compose.yml:78`, not in `infra/modules/compute/main.tf:85-86`. Celery therefore defaults to
`os.cpu_count()`. `worker_cpu = 1024` is one vCPU, the container sees one CPU, and you get one
child.

The `1` was never chosen. It is the residue of a sizing decision about CPU that silently became a
decision about throughput.

## What is NOT the cause

Worth stating, because it changes the size of the work. There is no code-level serialisation:

- **No queue routing.** No `task_routes`, no `task_queues` — every task shares the one default
  queue.
- **No global lock.** The only lock is `loan_file_needs_lock`, per-file and advisory, held briefly
  near the end of a run (`verification_run.py:815`).
- **No ordering between jobs.** `upload()` fires one independent `process_document.delay()` per
  file (`api/documents.py:184-185`) — no `chain`, no `group`.

The tasks are already written to run concurrently. They have simply never been given more than one
slot. **This is a capacity and configuration change, not a redesign.**

## Goal

1. Extraction runs in parallel across loan files.
2. Verification runs in parallel across loan files.
3. Neither blocks the other, and neither blocks a third processor.
4. Concurrency is **capped**, and work above the cap queues rather than being refused.
5. The cap is **configured per environment** — dev, staging and production hold different values.

## The two levers, and which one costs money

Total parallel jobs = **worker tasks x concurrency per task**.

| Lever | Mechanism | Cost |
|---|---|---|
| Concurrency inside a task | `--concurrency=N` on the worker command | **free** until memory forces a bigger task |
| More worker tasks | `desired_count` | **linear** — a full Fargate task each |

At ARM64 us-east-1 rates (~$0.032384/vCPU-hr, ~$0.003556/GB-hr, verified 2026-08-24) the current
worker — 1 vCPU, 2 GB — is **~$28.83/month**. A second identical task adds the same again. Going to
2 vCPU / 4 GB on one task costs **~$57.66/month**.

**So: raise concurrency inside the existing task first. Add tasks only when one task's memory is
genuinely the ceiling.** Measured, the worker peaks at **21.75% of 2048 MB (~445 MB)** with average
~20%. Prefork children share the interpreter copy-on-write and diverge from there, so N=4 on the
current 2 GB is plausible but not proven — Phase A measures it rather than assuming.

## Design

### 1. Split `desired_count` — it is currently shared by all three services

`infra/modules/compute/main.tf:383,420,443` use the **same** `var.desired_count` for the API, the
worker and the frontend. Scaling the worker today would scale the web tier with it, for no reason
and at triple the cost.

Split into `api_desired_count` / `worker_desired_count` / `frontend_desired_count`, each with no
module default so every environment states its own — the convention `worker_cpu` already follows.

### 2. Declare concurrency explicitly, per environment

Add `worker_concurrency` to the module and put `--concurrency=${var.worker_concurrency}` in
`worker_command`. Never inherit `os.cpu_count()` again: a change to `worker_cpu` must not silently
change throughput.

Keep the pool as **prefork**. `gevent` is the textbook answer for I/O-bound work and is the wrong
answer here: the tasks call `asyncio.run()` and gevent's monkey-patching does not coexist with
asyncio. `--pool=threads` is the plausible upgrade (each thread gets its own event loop, and both
`task_session` and `get_redis_client` are already per-loop by ADR-133/ADR-181) — but the
`@lru_cache`d Anthropic client would then be **shared across concurrent loops**, which ADR-361
tested only sequentially. Recorded as a follow-up with that specific risk named, not adopted here.

### 3. Separate the queues — this is the change that answers the complaint

Route by task name (`task_routes` in `celery_app.py`):

| Queue | Tasks | Shape |
|---|---|---|
| `extraction` | `documents.process_document`, `documents.reprocess_document` | many, ~30s, bursty on upload |
| `verification` | `verification.run_rule_engine`, `verification.run_cross_source` | few, ~7 min, one per Run click |
| `default` | `needs.*`, `health.*` | small, fast |

Then run **one worker container consuming all three queues with per-queue concurrency**, or two
containers if the environment wants hard isolation. A 7-minute verification can then never be the
reason a 30-second extraction has not started.

Without this, a single shared pool still lets one long verification occupy a large share of the
slots. The queue split is what makes the cap *per kind of work* rather than global.

### 4. Prefetch — the hidden second serialiser

`worker_prefetch_multiplier` is unset, so it is Celery's default of **4**. With minutes-long tasks
that is head-of-line blocking: one child reserves four tasks and holds them while a sibling idles.
Celery's own guidance is explicit — *"If you have many tasks with a long duration you want the
multiplier value to be one."*

Celery 5.6.3 is installed, which also offers **`worker_disable_prefetch`**: *"the worker fetches a
new task only when an execution slot is free, preventing tasks from waiting behind long running
ones on busy workers"*, and it is **Redis-broker only** — which is exactly our broker. That is a
better fit than `prefetch_multiplier=1` because it removes the reservation entirely.

Deliberately **not** turning on `task_acks_late`. It is the usual companion, but it changes
delivery to at-least-once: a hard-killed task is redelivered and re-run. `process_document` is
documented retry-safe; `run_rule_engine` at ~7 minutes and ~$0.30 of model spend is a different
proposition, and a redelivery that duplicates a run is the same collision as §7. Its own decision,
with its own evidence.

### 5. The AI rate limiter has to become environment-aware

`ai_requests_per_minute_bedrock` is enforced **per process** (`app/ai/rate_limit.py`), and the
tfvars comment says so: *"at N worker tasks the effective rate is N x this value. Raising the worker
count REQUIRES dividing this by the new count."* Prefork children multiply it too, not only tasks.

So the deployed value must become `quota_share / (worker_desired_count x worker_concurrency)`.
Either compute it in Terraform from the two knobs — so it cannot drift — or keep it manual and add a
`precondition` that fails the plan when the product exceeds the quota share. Terraform-computed is
preferred: the current arrangement depends on a human reading a comment.

**And the limiter is measuring the wrong thing.** Bedrock enforces **two** quotas — requests per
minute and **tokens per minute** — and AWS's guidance is that TPM binds first in most real
workloads, *"because a single request with a long document can carry thousands of tokens."* Verified
for this account (058190633983, us-east-1):

| Model | Cross-region RPM | Cross-region TPM |
|---|---|---|
| Claude Haiku 4.5 | 10,000 | **5,000,000** |
| Claude Sonnet 4.5 V1 | 10,000 | **5,000,000** |

One bank-statement extraction was 34,386 in + 16,384 out ≈ **51k tokens** (LP-628). At 5M TPM that
is ~98 such calls per minute — while the RPM limiter would happily allow 2,000. **RPM is nowhere
near binding; TPM is the real ceiling and nothing measures it.** Not fixed in this ticket; recorded
as the constraint that decides how far concurrency can ultimately go, and worth its own ticket
before any large increase.

### 6. The cap is the cost control, and it is the whole cost story

The user requirement — *cap it, queue the rest, configure per environment* — is satisfied by
`worker_concurrency` alone. Redis holds the backlog; nothing is refused; work drains at the capped
rate. Cost is bounded because **the container costs the same whether its slots are busy or idle**.

Model spend does not increase either. The same documents are processed and the same runs happen —
they finish sooner. The only new spend is a bigger task if memory demands one.

**Deliberately not doing autoscaling.** Queue-depth autoscaling on ECS is well-trodden (a Lambda
publishing depth to CloudWatch, a target-tracking policy on backlog-per-task) and it is the right
answer at production volume. It is the wrong answer now: it adds a Lambda, a custom metric, alarms
and scaling policies to an environment whose problem is that a single number is 1. Recorded as the
production follow-up, with `backlog per task` as the metric to target rather than absolute depth.

### 7. Prerequisite — guard a second run on the same file

`run_verification` (`api/verification.py:178-232`) checks the input-fingerprint cache but **does not
check for an in-flight RUNNING run**. Two quick clicks on one file create two runs. Today
concurrency=1 serialises them harmlessly.

At concurrency > 1 they would execute together and collide on `findings`' partial-unique index over
`(loan_file_id, rule_id, subject_key)` — and a finding-persistence collision is one of the two
failures `run_verification` deliberately **propagates** rather than degrades. Different files are
safe; the same file is not.

Fix either by refusing the enqueue while a run is RUNNING, or by taking a per-file lock around the
run (`loan_file_needs_lock` is the pattern, already in the file). **This must land in the same
change as the concurrency increase, not after it.**

## Risk register

Measured on staging 2026-08-24, not estimated. Ordered by how much they should change the plan.

### Real, and they size the change

**1. CPU contention — the constraint nobody expected.** The worker peaks at **32% of one vCPU**
(average ~2%) running a single document. Four children each peaking at 32% want **128% of a 1-vCPU
task**. They will not fail, but they will contend, and the base64 encoding of a 50 MB PDF is
genuinely CPU-bound rather than I/O-bound. Either raise `worker_cpu` to 2048 alongside concurrency,
or accept that 4 concurrent extractions run slower than 4x. **Phase A must measure this**, because
it is the difference between a 4x speedup and a 2.5x one.

**2. Memory, and the blast radius when it runs out.** Peak is **445 MB of 2048 MB (21.75%)**.
Prefork forks the process, so four children are not 4 x 445 MB (the interpreter is shared
copy-on-write) but they diverge as each loads a document. If the container is OOM-killed, ECS kills
**the whole task** — all four in-flight jobs die together, where today one dies. The blast radius of
every failure multiplies by the concurrency.

**3. A killed task is lost, not retried — and there is no watchdog for documents.** We deliberately
leave `task_acks_late` off (§4), so a hard-killed task is not redelivered. LP-628's own housekeeping
already records the consequence: *"Three LF-AWBB bank statements are stranded in `extracting` …
They will never advance and need a reset or re-upload."* Verification has a stuck-run watchdog
(`_reconcile_stuck_run`); **document processing has none**. At concurrency 4, one OOM strands four
documents instead of one. A stranded-document reconciler is the follow-up this argues for.

**4. Bedrock throttling, and the safety margin that disappears.** Four processes each pacing at
2,000 RPM is 8,000 against a 10,000 quota. The margin was chosen deliberately — the tfvars comment
explains that *"a REJECTED request still counts against the quota, so pacing at the ceiling turns
one burst of throttling into a self-sustaining one."* Dividing the limiter (§5) is not tidiness; it
is what keeps a throttle from becoming a throttle storm.

**5. Cost arrives four times faster.** Total model spend is unchanged — same documents, same runs.
But a runaway loop burns the budget at 4x the rate before anyone notices. The concurrency cap is
also the burn-rate cap, which is an argument for choosing it deliberately rather than maximally.

### Checked and NOT a risk

**Database connections.** Measured: `max_connections = 181`, currently **14 in use**. Each task
holds roughly one connection (`task_session` builds a per-task engine with `NullPool`), so four
concurrent tasks is four connections. Even a 7-minute verification holding one open is irrelevant at
this ratio. No pool tuning needed.

**Racing on the needs list.** Already solved. `needs.update_for_document` takes a per-loan-file Redis
lock (ADR-177), so two documents finishing together on the same file serialise on that file and run
in parallel across different files — which is exactly the desired behaviour.

**Racing on different loan files.** Nothing is shared. Documents, extractions, snapshots and findings
are all scoped to one file.

### Staging-specific

**Staging holds real borrower NPI.** That is the reason Bedrock exists in this project. It does not
make concurrency riskier, but it raises the bar on "just try it and see" — Phase A should be a
deliberate deploy with the memory and CPU readings taken, not a flag flipped and forgotten.

**One container is a single point of failure.** Four slots in one task means a deploy, an OOM or a
task replacement takes out all four. Two tasks at concurrency 2 gives the same throughput with half
the blast radius, for ~$29/month more. Worth weighing at production sizing (§Open decisions, 2).

**RDS is `db.t4g.small`, single-AZ, burstable.** t4g instances run on CPU credits. Load today is
trivial (14 connections, and the query above returned instantly), so this is a watch item rather
than a blocker — but four concurrent workers is the first time it will see sustained parallel
traffic.

**Interleaved logs.** Four children writing to one CloudWatch stream makes a single job's story
harder to follow. `ForkPoolWorker-N` is in every line, so it is greppable, but the days of reading
the log top to bottom end here.

**Priya's demo environment.** The project brief names domain-expert time as a binding constraint. A
change that makes staging flaky costs more than the throughput is worth, which is the argument for
Phase A being cautious and measured rather than going straight to production numbers.

## Phases

**Phase A — make it parallel, safely.** Split `desired_count`; add `worker_concurrency` and wire it
into `worker_command`; set `worker_disable_prefetch`; make the rate limiter a computed function of
the two knobs; add the same-file run guard (§7). Deploy to staging at concurrency 4. **Acceptance:**
re-run the six-document upload and see six completions inside ~40s rather than 2m53s, and start a
verification and an upload together and see both progress.

**Phase B — separate the queues.** Add `task_routes` and per-queue consumption. **Acceptance:** a
verification running on file A does not delay an upload on file B at all, measured the same way.

**Phase C — measure memory and TPM, then size production.** Read the worker's memory under real
concurrency; instrument tokens-per-minute against the 5M ceiling; only then choose production's
numbers. Autoscaling, if it is wanted, is designed here with real numbers rather than guessed ones.

## The production shape

Staging's answer (one container, more children) is not production's answer. Recorded here so Phase C
sizes against a target rather than inventing one.

### The unit of capacity: a slot-hour per loan file

From the measurements, one loan file costs roughly **one slot-hour** end to end:

| Work | Measured | Per file |
|---|---|---|
| Extraction | ~30s typical, 220s worst (LF-AWBB) | 30 documents x ~45s avg ≈ **23 slot-min** |
| Verification | 405-445s | 5 runs over the file's life ≈ **35 slot-min** |
| Needs / other | 2-18s | negligible |

That is an **estimate built on measured parts**, not a measurement — the 30-document count is
LF-6T3N's, and "5 runs per file" is a guess that Phase C should replace with the real re-run rate
from `verifications`. But it converts an unanswerable question ("how many containers?") into an
arithmetic one:

**slots needed ≈ (files per day x 1 slot-hour) / working hours x peak factor**

At 20 files/day over an 8-hour day that is 2.5 slots average; uploads cluster, so a peak factor of
3-4 gives **8-10 slots**. That is the number to design against, and it should be re-derived from
production's real file rate.

### Arranging the slots: containers x concurrency

Cost is a function of total vCPU and GB, **not of how they are packaged**. At ARM64 us-east-1 rates,
eight slots costs about the same either way:

| Shape | Task size | Monthly | Blast radius | Memory efficiency |
|---|---|---|---|---|
| 1 x concurrency 8 | 4 vCPU / 8 GB | ~$115 | all 8 jobs | best (one interpreter) |
| **2 x concurrency 4** | 2 vCPU / 4 GB | ~$115 | 4 jobs | good |
| 4 x concurrency 2 | 1 vCPU / 2 GB | ~$115 | 2 jobs | worst (4 interpreters) |

Sizing comes from the two staging measurements: **32% of a vCPU** and **445 MB** per concurrent job,
so a concurrency of 4 wants ~2 vCPU and ~4 GB.

**Recommended: 2-3 tasks at concurrency 3-4.** Since the cost is flat, containers are effectively
free to add and buy real resilience — multiple AZs, a deploy that does not empty the pool, an OOM
that takes a fraction rather than everything. The counterweight is that each container duplicates
the ~250 MB Python baseline, which is why the answer is not "many tiny containers".

### Two worker services, not one

Extraction and verification have opposite shapes — many short bursty jobs versus few long rare ones —
so in production they should be **separate ECS services** consuming the separate queues from §3:

| Service | Queue | Why |
|---|---|---|
| `worker-extraction` | `extraction`, `default` | bursty; scales with upload volume |
| `worker-verification` | `verification` | steady; sized by concurrent processors, not documents |

This is the production form of the guarantee the user asked for: verification work and extraction
work cannot compete for the same slots, because they no longer share a pool.

### Autoscaling — and the blocker that must be cleared first

**Autoscaling is the right end state and is currently unsafe to enable.**

The AI rate limiter is **process-local by design** (`app/ai/rate_limit.py`, and its own docstring says
so). The effective request rate is therefore `setting x tasks x concurrency`. Under autoscaling that
product changes on its own, which means **the effective rate limit rises exactly when load is
highest** — the moment throttling is most likely. The industry framing of this is blunt: *"a
per-process limit multiplies by the number of processes, so the effective rate changes every time the
fleet scales — including automatically, at exactly the moment load is highest."*

So the ordering is fixed:

1. **First**: replace the process-local limiter with a **Redis token bucket** (atomic via a Lua
   script, so two workers cannot both spend the last token). The existing docstring already names
   this as the deferred alternative — *"a distributed limiter needs Redis coordination on the hot path
   of every model call, which is a different (and much heavier) decision."* Autoscaling is what makes
   that decision worth taking. A shared reactive backoff belongs here too: the first worker to see a
   429 writes it to Redis and the whole pool backs off together, rather than each discovering the
   throttle independently.
2. **Then**: ECS target-tracking on **backlog per task** (queue depth / running tasks), not absolute
   queue depth — the AWS-documented pattern, and the one that stays correct as the fleet changes size.
   A small Lambda publishes Redis queue depth to CloudWatch; ECS high-resolution metrics make the
   response faster than the classic 1-minute path.
3. **Tuning**: scale **out** fast and **in** slowly. A 7-minute verification must not be interrupted
   by a scale-in, so the verification service needs a stop timeout above its hard limit (the module
   already has `worker_stop_timeout_seconds = 120`; verification's ceiling is 1200s).
4. **Never scale to zero in production** — a cold ECS task plus interpreter start is tens of seconds
   in front of a waiting processor. Scale-to-zero **out of hours is worth considering for staging and
   dev**, where the wait does not matter and the saving is most of the monthly cost.

Do **not** use Celery's own `--autoscale`: it varies child count inside a container, which multiplies
the per-process limiter in exactly the same uncontrolled way, and it does not save money because the
container is already paid for.

### Sequencing

| Stage | Shape | Autoscaling | Rate limiter |
|---|---|---|---|
| now (staging) | 1 task x 4 | no | per-process, divided by 4 |
| production v1 | 2-3 tasks x 3-4, two services | no — fixed size | per-process, divided by the fixed product |
| production v2 | same, min/max bounds | yes, backlog-per-task | **Redis token bucket** |

Production v1 is deliberately fixed-size. A known, hand-set number is safe with a per-process
limiter; an autoscaled one is not. The limiter work is the gate between v1 and v2, and it is its own
ticket.

## The decisions taken, and why

**Concurrency 4, and CPU deliberately left at 1024.** One job peaked at 32% of a vCPU, so four want
~128% and will contend. That is a slowdown, not a failure — whereas an OOM kills the whole task and
all four jobs with it. Since 1024 CPU already permits up to 8192 MB, buying off the OOM risk costs
**~$5/month** and the CPU question can wait for a real reading at concurrency 4. Spending $29/month
on CPU to remove contention nobody has measured yet would be guessing.

**The rate limit is computed, not hand-set.** `bedrock_rpm_budget` states what the *environment* may
spend and `main.tf` divides it by the slot count. The old arrangement stored the per-process value
and defended the multiplication with a comment saying "remember to divide this" — a defence that
fails the first time someone moves a knob without reading it, which is the whole failure mode this
ticket exists to close. Confirmed in the plan: **`2000` -> `500`**, so four slots spend exactly what
one slot spent before. **Raising concurrency does not raise the spend rate.**

**`worker_disable_prefetch` rather than `worker_prefetch_multiplier = 1`.** It removes the
reservation instead of shrinking it, and its Redis-broker-only restriction is satisfied. Verified it
is a real setting on the installed Celery 5.6.3 rather than silently ignored
(`celery_app.conf.worker_disable_prefetch` reads `True`).

**`task_acks_late` left OFF** — see §4. It is the usual companion and it changes delivery semantics;
that deserves its own evidence, not a side effect of this change.

**The in-flight guard returns the running run rather than a 409.** The client already polls the
returned run to completion, so a double-click lands on the run that is genuinely happening and the
contract is unchanged. `force` deliberately does not override it: `force` bypasses the input
fingerprint CACHE, not the one-run-per-file invariant. The two are easy to conflate — both read as
"run it anyway" — and only one is safe while a run is in flight, so a test pins the distinction.

predicts $50.46/month; Cost Explorer reports **$51.28**. A 1.6% error, which is rounding on the ARM
discount — so the $5.19 is arithmetic on a rate that demonstrably matches reality, not a guess.
(Even at the *x86* rate the delta is only $6.49, so the answer is robust either way.)

### Free, and why

* **Concurrency 1 -> 4: $0.** The container is already paid for and sits at **~2% CPU average**.
  Four children run inside the box already rented. This is the entire reason the ticket raises
  concurrency before adding tasks.
* **Prefetch, the desired_count split, the computed rate limit, the in-flight guard: $0.** Code and
  configuration.
* **Model spend: unchanged.** Same documents, same runs, same calls. The budget was DIVIDED across
  the slots, not raised — the plan shows `2000 -> 500` per process across 4 processes. Raising
  concurrency does not raise the spend rate.
* **VPC / CloudWatch / RDS / ElastiCache / S3: unchanged.** Same bytes, same log lines, same
  instances. Four DB connections against a measured `max_connections` of 181.
* **Marginally cheaper in one place:** the in-flight guard stops a double-click minting a second
  verification run, which is ~97 AI calls and roughly $0.30-0.47 each time it fires.

### The shape change that is not a cost change

Work finishes sooner, so the **same** spend lands in a **narrower window**. Six documents cost the
same whether they take 2m53s or 40s. On a daily Bedrock chart the peaks get sharper while the area
under the curve stays put — worth knowing before someone reads a spike as a regression.

### The cost NOT taken

Raising `worker_cpu` 1024 -> 2048 to remove the predicted CPU contention would add **~$23.64/month**
(4.6x this ticket's entire increase). Deliberately not done: contention is a slowdown, not a
failure, and there is no reading yet to justify it. Phase A's measurement decides it.

## Verification

* **Full suite: 5836 passed, 6 skipped, 1 xfailed.** ruff, ruff format and mypy clean across
  `app` and `tests`.
* **`terraform validate` passes for both staging and dev**; `terraform fmt -check -recursive` clean.
* **`terraform plan` against real staging** shows exactly the intended change and nothing else:
  `+ "--concurrency=4"` on the worker command, `memory "2048" -> "4096"`,
  `AI_REQUESTS_PER_MINUTE_BEDROCK "2000" -> "500"`, three task definitions replaced (a new revision
  each), API and worker services updated in place. `Plan: 3 to add, 2 to change, 3 to destroy.`
* **The guard tests were proven able to fail.** With the guard's condition disabled,
  `test_second_run_on_same_file_returns_the_in_flight_run` and
  `test_force_does_not_override_the_in_flight_guard` both go red. A test that cannot fail is worse
  than no test, and this repo has paid for that lesson more than once (LP-321a, LP-377).

## Not done

* **Not deployed and not committed.** The plan above is the evidence; `./scripts/deploy staging
  phase1` applies it.
* **Not measured under real concurrency.** The acceptance case is the six-document upload that took
  **2m53s**; it should finish in roughly **40s**. Memory and CPU at concurrency 4 must be read from
  CloudWatch after the first real burst — those readings, not this ticket, should size production.
* **Phase B (queue separation) not started.** With one shared pool a verification still occupies one
  of the four slots. That is a large improvement on occupying the only slot, but it is not the
  structural guarantee separate queues give.
* **The stranded-document gap is untouched.** Verification has a stuck-run watchdog; document
  processing has none, and LP-628 already recorded three statements stranded in `extracting`. At
  concurrency 4 one OOM strands four. Its own ticket, and it should follow soon.
* **TPM is still unmeasured** (risk register, §5). Nothing here changes it; it is the constraint that
  decides how far concurrency can ultimately go.

## Open decisions for the approver

1. **Staging concurrency: 4, or start at 2?** 4 is my recommendation — the memory reading supports
   it and the gain is what the ticket exists for. 2 is the cautious first deploy.
2. **One worker container consuming three queues, or two containers?** One is cheaper and simpler;
   two give hard isolation and let verification be sized independently. I lean one for staging, two
   for production.
3. **Compute the rate limit in Terraform, or keep it manual with a plan-time `precondition`?**
   Computed is safer; manual keeps the tfvars readable as a plain number.
4. **Does the TPM finding change the plan now, or become its own ticket?** My recommendation is its
   own ticket — the numbers above show large headroom at concurrency 4, and conflating the two
   delays the fix.
