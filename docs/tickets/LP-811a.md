## The split, and why

The plan gives LP-811 as **backend + frontend** in one ticket. Protocol rule 2.1 says a ticket that
turns out to contain two things gets split in the progress file, and §4 says a ticket that runs long
was too big. A send endpoint plus a draft panel plus its API client plus its tests is a diff nobody
reviews properly, and the frontend half additionally needs a **home in the file view** — a
navigation decision this branch's new UI stream should settle, not one I should guess at inside a
backend ticket.

So: **LP-811a** is this, and **LP-811b** is the panel, recorded as row 8b.

---

## What "send" means in M1

**Nothing transmits.** The plan's send path is *copy and send* — the processor puts the text into
their own mail client — plus an "open in mail client" link. LP-816 is the ticket that transmits
through a connected mailbox. So this module's job is to **record** that a draft went out, produce the
artefacts the message must carry, and start the clocks.

## What was done

### The clock, which is the point of the ticket

`request_needs_item` has existed since LP-19 at `services/needs_items.py` with **zero callers**. So
`requested_at` is NULL on every needs item that has ever existed, and LP-814's reminders — a Celery
beat over that column — are queries over an empty set. They cannot fail and cannot fire, and from
outside those look identical.

`send_draft` calls it for every need in the draft. That is the first write to that column in the
system's life.

The control matters as much as the assertion: `test_a_need_not_in_the_draft_keeps_its_clock_unstarted`
exists because stamping *every* need on the file would pass the positive test and would start
reminder clocks for documents nobody has asked the borrower for.

### The footer tag is an identifier, never a capability

`[LF-XXXX]` — the `display_id`. ADR-048 draws exactly this line: the display id is an **identifier**
whose predictability is low-risk; `inbox_token` is a **capability** whose possession lets anyone post
documents into the file.

A footer is quoted into every reply, forwarded, and pasted into other threads. Putting the token
there would hand it to everyone the borrower ever forwards the message to — which is the opposite of
what ADR-397 did when it narrowed ADR-094 rather than widening it. A mutation swapping one for the
other fails three tests.

The tag is a **fallback**: `Reply-To` routes a well-behaved reply, and this is what LP-805 can still
match on when a client strips or rewrites the header, which several do.

### The rate limit counts across files, not within one

One per address per five minutes, three per day. **Across the whole system**, and that direction is
the one that matters: a borrower with two loan files in progress is one mailbox, and a per-file limit
would let them be emailed twice in a minute while every individual limit read as respected. The test
uses a second loan file for exactly that reason.

Header-independent, as the plan requires. `Auto-Submitted` and friends *ask* a well-behaved
correspondent not to reply; a loop forms with one that is not. A count over what we have actually
recorded cannot be talked out of.

### `mailto:` is withheld rather than offered and hoped for

`mailto:` does not fail when it is too long — it opens a compose window containing **half an email**,
which a processor may not notice before sending. The threshold is 1,800 characters, set below the
lowest limit anybody documents rather than at it, because the real limit differs per client, per
browser and per OS handler.

`mailto_available` is computed **server-side**. Two places deciding the same thing is two places to
disagree, and the disagreement here ships a truncated email.

### No bulk send, by construction

`send_draft` takes one `draft_id`, and the id is a **path parameter** rather than inferred from the
file. Inferring it would let a draft that changed between the read and the click be sent unseen,
which for a borrower-facing email is the whole risk. A bulk path would either bypass the rate limit
or fail halfway through a list with no way to say which half went out.

## The columns I did not add

The plan says **Migration: no**, and also says to "store the model draft, the human edit and the sent
version separately" and that the endpoint requires `reviewed_by_user_id`. Those cannot all be true —
`Communication` has one `body` and no approver column.

I honoured **Migration: no**, because unlike LP-809's two provenance columns there **is** a later
ticket that owns this: LP-821 builds `phase4.md` §6's full evidence record, including "the
authenticated approver" and "the rendered body **as sent**". Adding a partial version here would mean
LP-821 inherits a half-shaped record it has to migrate again.

What that leaves today:

- **The composed draft** is in `email_draft_prose`, keyed by facts (LP-810), or reproducible from the
  template and version stored on the communication (LP-809).
- **The sent version** replaces `Communication.body`. The record of an outbound message must be what
  went out.
- **The human edit** is the sent version minus a deterministic footer, so it is recoverable but not
  stored distinctly.
- **The approver** is the `actor_user_id` on the `COMMUNICATION_SENT` activity-log entry.

Recorded rather than absorbed: the three-way record and the approver field are LP-821's, and this
ticket is only correct on the assumption LP-821 lands.

## Tests

`tests/services/test_email_send_lp811a.py` (16) and `tests/api/test_communications_lp811a.py` (6).

Every negative has a positive control, because the failure modes here are silent: a threshold that
refused every `mailto:` looks exactly like the feature not being built, and a matcher that resolved a
loan reference from any text would route a stranger's mail into somebody's file.

The API tests needed a **savepoint-joining session** rather than the plain rollback fixture, because
the endpoint commits — the same pattern `test_verification_endpoints.py` uses, and for the same
reason.

## Assumptions

- **`recipient` is not validated as an email address** beyond a length bound. Nothing transmits, so a
  malformed address fails in the processor's own client where they can see it. When LP-816 transmits,
  that stops being true and validation belongs there.
- **The rate limit reads `Communication.recipient`**, which is only populated on send. Inbound rows
  and drafts carry NULL and cannot collide with it.
- **A resent draft is impossible rather than idempotent.** The second attempt is a 409, not a silent
  success — a processor who clicks twice should be told the first one went, not left unsure.

## For the reviewer

The three standing reviewer checks:

- **Tenancy** — every route declares `ScopedLoanFile`, so the file is fetched and company-scoped
  before any code here runs. No `company_id` is derived anywhere; LP-805 remains the only resolver.
  `test_another_companys_file_is_not_reachable` asserts it on the route, because the draft id is a
  path parameter a caller could guess.
- **Message content in logs** — the one activity entry carries ids, the template key and the version.
  `test_the_send_is_logged_without_the_content` asserts the body and the recipient's address are
  absent from both the summary and the detail.
- **AI in the decision path** — none. Nothing in this ticket calls a model.

The judgement calls worth a second opinion, in the order I would attack them:

1. **The split itself.** I split a ticket the plan gave as one. If you think the frontend half was
   small enough to have come along, say so — but the panel has no home in the file view yet, and I did
   not want to invent one inside a backend ticket.
2. **Honouring "Migration: no" at the cost of the three-way record.** The opposite call — add the
   columns now, as I did in LP-809 — is defensible. The difference I relied on is that LP-821
   explicitly owns this record and LP-809's columns had no other home. If LP-821 slips, this ticket
   ships an evidence record that §6 would not accept.
3. **`AUTO_REPLY_SUPPRESSION_HEADERS` has no reader.** Nothing transmits, so nothing consumes them.
   That is the pattern I have twice declined to build — and I built it here because the plan places
   it in this ticket and the alternative is that no ticket owns it. A suppression header omitted from
   an auto-reply is how a mail loop starts, and the loop is with a borrower's mailbox. Overrule me if
   you think it belongs in LP-815 instead; that is where its first consumer is.
