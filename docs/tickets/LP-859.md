## §1 — Every unedited draft renders its HTML as literal text. CONFIRMED, with a cause.

> Reported: the Message editor shows `<p>hello, we just want these list of dcoument</p>`.

**Screenshots:** `01-edited-draft-shows-tags.png` (draft *"fdgdfgdfg"*, to geet.thaker@gmail.com,
created 13 Sep 2026 11:44) and `02-template-draft-shows-tags.png` (draft *"Documents we need for
your loan (LF-XMB2)"*, template `initial_documentation_request v4`, created 12 Sep 2026 09:58 —
a wall of `<p>`, `<ul>`, `<li>`, `<strong>` and `&#39;` entities shown as text).

### The cause: the body is escaped twice

`message-dialog.tsx:570`

```tsx
<MessageEditor
  value={data.body_format === "html" ? data.body : emailBodyToHtml(data.body)}   // ← conversion 1
  format={data.body_format}
  onChange={onEdit}
/>
```

`message-editor.tsx:146`

```tsx
content: format === "html" ? value : emailBodyToHtml(value),                     // ← conversion 2
```

On any draft whose `body_format` is `plain`, the caller converts the body to HTML and then hands the
editor **the converted HTML together with the flag saying it is not HTML.** The editor converts it
again, and `emailBodyToHtml` escapes before it wraps (`lib/markdown/email-body.ts:21` — `<` → `&lt;`,
`'` → `&#39;`), so the `<p>` tags produced by the first pass are escaped into text by the second.
The `&#39;` visible in screenshot 2 is the same double pass reaching the apostrophes.

**`body_format` is `plain` on every draft a person has not edited**, because LP-853 made that column
mean *"a person wrote this body"* (`message-dialog.tsx:290` — `const edited = data.body_format ===
"html"`). Every template-generated draft therefore takes the broken path. **This is not an edge case;
it is the default state of every draft on the screen.**

The read-only preview at `message-dialog.tsx:695` converts **once** and is correct — which is why
this never showed anywhere but the editor.

### Fix

`message-dialog.tsx:571` → `value={data.body}`. The editor's own prop contract already says so:
*"`value`: the body. `format` says which language the body arrived in."* The caller must not
pre-convert a value it is also labelling.

### Done when

Opening the `initial_documentation_request v4` draft on LF-XMB2 shows a formatted list — bold labels,
bullets, paragraphs — and no angle bracket anywhere in the editor.

### The test that was missing

Not text presence. **Assert the tags became elements:**

```ts
// The editor must hold a real <p>, not the four characters "<p>".
expect(container.querySelector(".ProseMirror p")).toBeTruthy();
expect(container.querySelector(".ProseMirror")?.textContent).not.toContain("<p>");
```

Add it for both `body_format` values. The second line is the one that fails today.

## §2 — The left rail's rows are unreadable at 300px. CONFIRMED.

> Every row's summary wraps one word per line — `document / request / is / being / prepared` — and
> the status line is clipped at the rail's edge.

**Screenshots:** all three. In `02-template-draft-shows-tags.png` the EMPLOYER row's status line
**overflows the rail and collides with the right pane's "Status" label** at the same y position.

### The cause: a four-column row built for a full-width list, never re-laid-out for 300px

`timeline-panel.tsx:498` — the row is `flex items-start gap-3` over four children, and **three of
them cannot shrink**:

| Child | Line | Width | Shrinks? |
|---|---|---|---|
| `EntryIcon` | `:504` | ~14px | `shrink-0` |
| `PartyCell` | `:71` | `w-[5.6rem]` = **89.6px** | `shrink-0` |
| summary / subject / documents | `:509` | `min-w-0 flex-1` | **the only one** |
| `statusLine` + `MessageActions` | `:600` | `whitespace-nowrap`, ~274px for *"Marked sent by Geet Thaker · 1 day ago"* at 12px mono | `shrink-0` |

Fixed width: 8 (`pl-2`) + 14 + 12 + 90 + 12 + 274 + 24 ≈ **438px inside a 300px rail.** The flexible
column is squeezed past zero to its min-content width — one word — and the nowrap status line runs
out of the rail entirely. Both symptoms follow from the one cause.

**This was correct before LP-858 and LP-858 did not break the row — it moved the container.** The
list used to span the tab. §2 of the design contract set the rail to 300px and specified what it must
hold (*"party, subject preview, document count and time"*) **without specifying that they stack**,
and the row was left alone. That unstated choice is the same gap §3 of the contract exists to close
for components; it now applies to layout.

### Fix — stack the row, do not shrink the rail

Three lines, full width of the rail, nothing horizontal but the first:

```
┌─ 300px ───────────────────────────────┐
│ ✎ BORROWER              1 day ago     │  ← party + relative time, time may truncate
│ Draft · edited                        │  ← state as a word, its own line
│ 3 documents · Insurance, Licence, …   │  ← what is inside, truncated
└───────────────────────────────────────┘
```

- **Nothing in the row may be `whitespace-nowrap` and `shrink-0` at once.** That pair is what put
  content outside the rail.
- The attribution (*"Marked sent by Geet Thaker"*) moves to line 2, where it has the width for it.
- Keep `PartyCell`'s `shrink-0`; it is 90px of a 300px line that now has the whole line.

### Done when

At 300px, on LF-XMB2, **no row's text wraps mid-phrase, no text crosses the rail's right edge, and no
row is taller than three lines.** Check the `Marked sent by Geet Thaker` row specifically — it is the
longest string the screen can produce.

## §3 — A blank compose draft describes itself as a document request. CONFIRMED.

**Screenshot:** `03-compose-row-wrong-summary.png`. The right pane reads **"New message · To nobody
yet · Created 13 Sep 2026, 19:50"** — correct. The row for that same draft, selected in the rail,
reads **`Draft · cannot be sent yet`** over **"A document request is being prepared"**.

The draft asks for nothing and says nothing. Both strings are wrong, and the contract names what they
should be — `lp858-draft-panel.md` §6 and §10: **`New message`** and **`Nothing written yet`**.

### The cause

`services/timeline.py:272` — `_summarise` returns `"A document request is being prepared"` for
**every** draft, with nothing distinguishing one that has no needs, no subject and no body:

```python
if message.status is CommunicationStatus.DRAFT:
    return "A document request is being prepared"
```

`timeline-panel.tsx:125` — `statusLine` returns `Draft · cannot be sent yet` whenever an outbound
draft has no counterparty. True of a blank compose draft, but §6 says that row reads `New message`,
and *"cannot be sent yet"* is the no-address warning, which means something else.

### Fix

- `_summarise`: a draft with no `template_key`, no linked needs, no subject and no body summarises as
  **`Nothing written yet`**. The distinction already exists server-side —
  `email_reply.py:270` `_is_untouched_compose_draft` computes exactly this predicate for the hard
  delete. **Use that, do not write a second one.**
- `statusLine`: an untouched compose draft reads `New message`. The `cannot be sent yet` branch keeps
  the case it was written for (LP-857: a *party* draft the file has no address for).

### Done when

Pressing **+ Compose** adds a row reading `New message` / `Nothing written yet`, and it changes the
moment anything is typed into it.

### Note for whoever builds this

`timeline-panel.tsx:556` carries the comment *"Four rows reading 'A document request is being
prepared', identical but for a timestamp, is the screenshot that started this ticket."* Screenshot 3
has **six.** The documents-and-counterparty sub-lines LP-852 added to fix that are real, but they are
collapsed by §2 above and a blank compose draft has neither. §2 and §3 fix the same complaint from
two ends; neither is sufficient alone.

## §4 — "No drafts on this file" over a rail showing four drafts. CONFIRMED.

**Screenshot:** `04-empty-state-over-a-full-rail.png`. The rail lists two BORROWER drafts, an
EMPLOYER draft, a LENDER draft and a sent message. The right pane says **"No drafts on this file —
Request documents from a finding, or write a message."** The screen contradicts itself, and the half
that is wrong is the half with the larger type.

### The cause: one empty state doing two jobs, and `closed` is the second one

`message-dialog.tsx:428` — `close()` ends **both** its branches with `onClose()`:

```tsx
if (untouched && data) { deleteDraft.mutate({ draftId, discard: true }, …); onClose(); return; }
flush();
onClose();
```

`page.tsx:188` — `onClose` sets `closed = true`, and `:104`:

```tsx
const autoSelected = narrow || closed ? null : (openDrafts.find(…)?.id ?? null);
```

So after any ✕, `autoSelected` is null for the rest of the mount — **which is correct and
deliberate** (`page.tsx:190` — *"CLOSING MEANS CLOSED, and the auto-selection must not immediately
undo it"*). What is wrong is what gets rendered in its place: `page.tsx:199` falls to §2.1 rule 4's
empty state, whose words are about a file with no drafts. Nothing distinguishes *"this file has
none"* from *"you closed the one you were reading"*.

**The path the reporter took** is visible across screenshots 3 and 4: **+ Compose** → a `New message`
pane → ✕. The untouched compose draft is discarded (correct, §8), `onClose()` fires immediately after
`onDeleted()`, `closed` becomes true, and the pane sits on the false sentence.

**A related inconsistency, and it is the reason the Delete button does not show this bug.**
`page.tsx:182` states the intent — *"`closed` stays false, because a delete is not a close"* — and
that holds for `removeDraft`, which calls `onDeleted` alone. It does **not** hold for the discard
path above, which calls both. The comment describes a guarantee the code keeps in one of the two
places it is claimed.

### Three states, not two

| Condition | Right pane |
|---|---|
| `entries` is empty | full-width **"No drafts on this file"** — unchanged, correct |
| open drafts is empty, `entries` is not (sent-only) | in-pane **"No drafts on this file"** — unchanged, **correct**: there really are none |
| **open drafts exist, the pane was closed** | **new** — see below. Today this wrongly borrows row 2's words |

### Fix

Keep the behaviour, give the third state its own words. `page.tsx:196` branches on whether any open
draft exists rather than rendering one empty state for everything:

```
No draft selected
Pick one from the list, or start a new message.
```

Do **not** re-select on close; that trades a false sentence for a pane that cannot be dismissed.

### Done when

Open a draft, press ✕, and the rail still shows four drafts while the pane reads **"No draft
selected"**. On a file with genuinely no drafts the old words are unchanged.

### Test

- `a closed pane says no draft is selected, not that the file has none` — asserts the rail still has
  rows **and** that the string "No drafts on this file" is absent.
- `a file with only sent messages still says the file has no drafts` — the case that must not change.

# §1 — built

`message-dialog.tsx` hands the editor `value={data.body}`. One line. The editor's own prop contract
already said so: *"`value`: the stored body; `format` says which language it arrived in."* The caller
was passing the **converted** body together with the flag saying it was not converted, and
`emailBodyToHtml` escapes before it wraps, so the first pass's own `<p>` came back as four
characters.

**Not `format="html"`.** That also stops the double escape and is the wrong fix: it makes
`body_format` mean *"what this string is"* here and *"whether a person wrote it"* everywhere else,
which is the root cause in different clothes. LP-853 spent a ticket making that column mean one
thing. **It is also not caught by the obvious test** — see below.

## The tests, and the mutant that survived the first pair

Two tests, one per `body_format`, asserting the tags became **elements**:

```ts
expect(document.querySelector(".ProseMirror p")).toBeTruthy();
expect(document.querySelector(".ProseMirror")?.textContent).not.toContain("<p>");
```

The second line fails on the shipped build — confirmed before the fix, `expected '<p>Hello Felicia,
</p><p>Please send t…' not to contain '<p>'`.

**Then `format="html"` passed both of them.** Mutated it in: a plain body handed to Tiptap as HTML
is wrapped in **one** paragraph, so "the tags became elements" and "no `<p>` in the text" are both
satisfied while every paragraph break the processor wrote is silently gone. The forbidden fix was
indistinguishable from the right one.

`expect(document.querySelectorAll(".ProseMirror p")).toHaveLength(2)` separates them. Both mutants
now die: restoring the double conversion fails one test, `format="html"` fails the same one.

## An existing test caught a real consequence

`does not save a draft typed in and then undone back to where it started` went red. The stub editor
called `onChange(value)` — echoing what it was handed — and that was HTML **only because the caller
was pre-converting**. The stub was accidentally correct, and correct *because of the bug*. With the
caller fixed it began reporting a plain body as an edit.

The stub now does what the real editor does (`format === "html" ? value : emailBodyToHtml(value)`),
which is what its `onChange` contract said all along: *"called with HTML, always"*. The polish
suite's seed-shape assertion moved the same way — the paragraph break it pinned as a `<p>` element
is the blank line it has always been in the stored body.

## §1 — found in review, and what it changes

Three findings from the review session, none of them a defect in the fix. Two go to **Still open**;
one changes how §2's browser pass must be read.

### 1. My commit message overclaimed, and the correction is committed (`686f421c`)

I wrote that the autosave stub *"now does what the real editor does"*. It does not. The stub calls
`emailBodyToHtml(value)`; the real editor hands back `editor.getHTML()`, ProseMirror's own
re-serialisation. The stub is faithful for the case it was written for — restoring §1's defect turns
the undo test red, measured — and not faithful in general.

### 2. `openedAs` never matches what the editor reports back — PRE-EXISTING, NOT §1's

I asked whether the two `emailBodyToHtml` calls could diverge. They cannot: same function, same
input. **The problem is the third string.** `openedAs` holds `emailBodyToHtml(data.body)`; `onEdit`
receives `editor.getHTML()`. Measured against the real extensions:

```
seed:    <p>Hi Sarah,</p>\n<p>Please send:</p>\n<ul><li>Bank statement</li>…
getHTML: <p>Hi Sarah,</p><p>Please send:</p><ul><li><p>Bank statement</p></li>…
```

Different by the newline joiner **and structurally** — `<li>text</li>` comes back as
`<li><p>text</p></li>`, so a whitespace-tolerant comparison does not close it either.

**The reachable case is not the mount case the code comment covers.** A processor types one
character and presses Ctrl+Z: the document is identical, the strings are not, the 800 ms debounce
flushes, and a draft nobody changed is stored as `body_format = html`. `_regenerate` then refuses it
and LP-851 warns about losing changes that do not exist. The same comparison drives `untouched` in
`close()`, so a compose draft typed-and-undone also stops being discardable.

It predates §1 — the old code had the same mismatch, worse. The honest fix is for the editor to
report its own normalised baseline once, which is `message-editor.tsx` and outside §1's scope.

### 3. Rows already corrupted by the old code stay corrupted — THIS CHANGES §2's CHECK

Under the broken build the editor held the double-escaped document, so **the first keystroke
autosaved it**:

```
<p>&lt;p&gt;Hi Sarah,&lt;/p&gt;<br>&lt;p&gt;Could you send the March statement.&lt;/p&gt;</p>
```

with `body_format = "html"`. After the fix those rows take the `html` branch in both the editor and
the preview and render as-is — **so they still show literal tags, and re-editing re-saves the same
escaped text. Stable, not self-healing.**

### I could not size the affected population

`body_format` (and not `body`), so the count is one query away for whoever has a session:

```sql
select body_format, status, count(*)
from readonly.communications
where direction = 'outbound' and deleted_at is null
group by 1, 2 order by 1, 2;
```

That gives the size. Naming *which* drafts are corrupt needs the body, which the readonly views drop
by design — so it is a `body_format = 'html'` count first, then a judgement about repair.
