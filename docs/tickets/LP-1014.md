# LP-1014 — Follow-ups on screen (+ three backend fixes from LP-1013)

Step 5 (Follow-ups), second ticket. LP-1013 built automatic follow-ups on the backend; this puts them
on the Communication tab, and makes three backend fixes the screen needs. Code, tests and a dev check
with screenshots. Nothing committed.

## What a processor sees

- **Sending:** above the draft pane's button bar, only where Send is, a box **Follow up if no reply**
  (unticked). Ticked: *Every [3] days, up to [2] reminders, at [time]*, the browser's time zone, and
  *First reminder: Tue, Nov 10 at 9:30 AM* (the interval from now; a weekend day moves to Monday).
  Send carries `follow_up {interval_days, max_auto, time, tz}` only when ticked.
- **A sent email** (an original, not a reminder) has a **Follow-up** bar under its header: a pill, the
  state in words, *Waiting for*, *Next* (in the follow-up's own zone), *Sent n of m*, and the buttons
  its state allows:

  | State | Says | Buttons |
  |---|---|---|
  | On, reminders left | On | Edit (the three fields inline, Save → PATCH), Send now, Stop |
  | Paused | Paused — they replied | Resume, Send now, Stop |
  | No reply (on, `auto_sent >= max_auto`) | No reply | Send now |
  | Finished | Everything arrived | — |
  | Stopped, sender deactivated | Stopped — <sender>'s account was deactivated | — |
  | Stopped (by a person) or Off | Stopped / Off | Start follow-ups (the three fields inline → start) |

- **The message list:** an automatic reminder's row reads *Automatic reminder (for Priya) · Sent*; an
  email with a follow-up carries a pill: *Follow-up · Tue* (success), *Paused* (warning), *No reply*
  (danger), *Stopped* / *Finished* (neutral). The pills come from the list endpoint; the timeline
  query is unchanged.
- **The Follow-ups list**, full width above the two panes, only when the file has one: Email (subject,
  *To <recipient> · by <sender>*), Waiting for, Status, Next / sent, Actions (the same rules as the
  bar). *No reply* rows first, in the danger colour; then the rest, newest first. Clicking a row (or
  its subject, the keyboard way in) opens that email in the right pane.

Every action refreshes the list, the email and the timeline. Buttons are `<button>`s, at least 36px
(`min-h-9`). No dialog; the two-pane layout is unchanged.

## Backend (Part A)

1. **`GET /api/v1/loan-files/{file}/follow-ups`** — the file's original outbound emails whose
   follow-up was ever started (`status != off`), newest first (`send_requested_at`). Same company
   scoping as the message endpoints (`ScopedLoanFile`: another company's file is a 404). Each row:

   ```json
   {
     "communication_id": "…",
     "subject": "Documents we need for your loan (LF-JD4T)",
     "recipient": "jane.borrower@example.test",
     "sender_name": "Priya Desai",
     "sender_active": true,
     "follow_up": { "status": "on", "interval_days": 3, "max_auto": 2, "auto_sent": 0,
                    "clock_at": "…", "paused_at": null, "next_reminder_at": "…",
                    "time": "09:30", "tz": "America/New_York", "waiting_for": ["W-2"] }
   }
   ```

   The sender is the approver on the original's evidence record (`original_sender`, as the job reads
   it); `sender_name` is null and `sender_active` false when nothing records one.
2. **Deactivated sender.** In the job, after the sender is found and before anything is sent: an
   inactive user → `follow_up_status = stopped`, outcome `stopped_sender_inactive`, log
   `follow_up_sender_inactive`. No column: the screen reads `sender_active`.
3. **Time zone in Python AND Postgres.** The schema checks `zoneinfo`; the endpoint then checks
   `pg_timezone_names` and answers 422 *"Unknown time zone: X. Use a name like America/New_York."*
   (the schema's message now reads the same). On **start** and **PATCH**, as the brief says, **and on
   the Send** with follow-up ticked: it is the third place that writes `follow_up_tz`, and one name
   Postgres does not know fails the job's SQL for every company. Measured on dev: the two lists are
   currently identical, so the tests make Python's check accept a made-up zone to reach Postgres's.
4. **The timeline entry** (needed for the reminder row) carries in `detail`: `follow_up_of_id`,
   `automatic_reminder` (a reminder nobody clicked) and `reminder_for` (the sender's first name, from
   each reminder's own evidence record, one query for the whole list).

## Decisions

- **"No reply" is derived in one function** (`followUpState`), read by the bar, the pill and the list.
- **Edit keeps the follow-up's zone**; Start and Send use the browser's. The fields show the zone they
  will be read in.
- **The reminder row keeps its send state** after the label (*Automatic reminder (for Priya) · Sent*),
  so a failed reminder still says *Failed*.
- **The bar shows only for an original** (`follow_up` non-null), so a draft, a reminder or inbound
  mail renders nothing new, and the existing pane tests (which mock every query) are untouched.

## Open

- **A Send-now reminder's row** reads *Sent · Re: …*, not "Reminder"; the brief names only the
  automatic one.
- **"Sent a document request for 0 item(s)"** is what the activity feed says for a Send of a compose
  draft (seen in `09`: Avery's email to the title company). It predates this ticket.
- **The first-reminder line** uses the browser's clock; the server counts from `send_requested_at`.
  They differ only if the click and the request straddle midnight.
- **Review findings left as they are** (the owner's call, 11-08), in the review section below: 1-4.

## Review (one round, 11-08)

Ten findings from `/code-review`; each was checked against the code before deciding (the zone check's
cost measured: 7.7 ms). The owner chose 5-10.

| # | Finding | Outcome |
|---|---|---|
| 1 | Start and Resume work for a deactivated sender; the screen shows a date the job then cancels | **Open** |
| 2 | "Stopped — X's account was deactivated" is inferred from the sender's state today, not why it stopped (no stop reason is recorded) | **Open** |
| 3 | `on` with a departed sender still shows a next date until the job stops it | **Open** |
| 4 | "No reply" stays red after every document arrives: an exhausted follow-up is never picked again, so it never finishes | **Open** |
| 5 | "Up to 0 reminders" was allowed and read "No reply" at once | **Fixed**: at least 1 on screen (`min=1`) and in the API (`FollowUpSettings`, `FollowUpPatch`, `FollowUp`: 1-10, was 0-10, LP-1013's range). The database CHECK stays 0-10 (a migration for no gain: the API is the gate). |
| 6 | The number fields corrected every keystroke: clearing 3 to type 7 gave 37, saved as 30 | **Fixed**: `NumberField` holds the text, passes up only an in-range number, and puts an empty or out-of-range value right when she leaves the field. |
| 7 | Start offered on a follow-up whose email failed; the server refuses it | **Fixed**: the row carries `email_status`; a stopped follow-up on a failed email reads "Stopped — the email failed" with no buttons. |
| 8 | The list asked per row for needs and sender (~3 queries a row) | **Fixed**: `needs_by_original` and `senders_of`, one query each; a test counts the statements for one row and four and finds them equal. |
| 9 | `pg_timezone_names` read on every Send / Start / Edit | **Fixed**: read once per process (`_POSTGRES_ZONES`); a test counts one read for two PATCHes. |
| 10 | "Who sent this" written twice (job and timeline) | **Fixed**: `follow_ups.senders_of` is the one definition; `original_sender` and the timeline's reminder label both use it. |
