# LP-557 — What "Apply" means, and which rules can offer it

Design, agreed 2026-08-19. Not built.

## The definition

**Apply writes the finding into the loan's structured data.** The target follows the nature of the
finding; the calculators recompute from there. One verb — not "Apply" for a correction and something
else for an addition.

Every other action changes only the FINDING's state. Apply changes the LOAN:

```
apply_finding()
  -> _incorporate_into_structured_data()   writes stated_liabilities / stated_income_items / ...
  -> mark_recompute_needed()               DTI and LTV recompute from the changed data
  -> the finding closes as APPLIED, carrying applied_record
```

The finding closing is a consequence, not the point. That is why Apply is the only action that can
move a ratio, and the only one where Undo has real work — it restores the pre-apply state exactly
from `applied_record`, so the change is reversible rather than merely forgettable.

## The target mapping

| The finding is about | Apply writes to | What actually moves |
|---|---|---|
| A debt not on the application | `stated_liabilities` (add) | **DTI up** |
| A debt understated | `stated_liabilities` (correct payment) | **DTI up** |
| Income overstated | `stated_income_items` (correct) | **DTI up** |
| Funds that cannot be used | `stated_assets` (exclude / reduce) | **reserves, cash-to-close** |
| Purchase price wrong | `property.purchase_price` | **LTV** |
| Appraised value wrong | `property.valuation_amount` | **LTV** |

**Assets do not touch LTV.** LTV is loan / value, so it moves only when the price or the appraised
value changes. Asset findings move reserves and cash-to-close. The recompute hook fires for both
calculators regardless; only the relevant one changes.

**Every Apply moves a ratio the conservative way.** The two existing actions already do — a liability
raises debt, a corrected income lowers income, both pushing DTI UP. An Apply that could LOWER a DTI is
a different risk class and must not share this path without a separate decision.

## Two actions exist; the rest are new

`_incorporate_into_structured_data` supports `add_liability` and `correct_income` today. Anything else
returns `{"action": ..., "applied": False}` — a button that looks right and does nothing, which is
worse than no button.

Needed: `correct_liability_payment`, `exclude_asset`, `correct_purchase_price`, `correct_valuation`.
Each mirrors `_correct_income`, which already does the tenant-checked lookup, money coercion and the
audit record.

## The blocker, and why it is smaller than it first looked

A rule can only Apply if it CARRIES the corrected value on the finding. Most carry only a verdict-shaped
enum — the engine is built so tags DESCRIBE and rules JUDGE, so `reo.statement_payment_coverage` is
`covered` / `uncovered` and DT-6's $4,148.28 lives only in the tag's prose.

Measured across the 18 candidates: **only PC-2, AS-12 and FR-5 carry a usable value today.**

**But the value tags mostly already EXIST and are already PRODUCED** — they are simply not on these
rules' `load_bearing_tags`:

| Tag | Produced? | Serves |
|---|---|---|
| `income.documented_monthly` / `income.stated_monthly` | yes | IN-1, IN-3 |
| `liab.monthly_payment` | yes | CR-1, CR-4, RE-1, DT-6 |
| `property.purchase_price` / `contract.sales_price` | yes | PC-2 |
| `property.appraised_value` | yes | PR-2 |
| `income.employer_normalized` | yes | IN-5 |
| `liab.balance` | **no producer** | the balance half of add_liability |
| `property.retained_pitia` | **no producer** | DT-6's billed total |

So the work is mostly the LP-555 move — add the value tag to `load_bearing_tags` as **provenance,
never `gated_tags`**. Gating on a value would make a subject missing it ABSTAIN instead of being
evaluated, trading a usable button for a lost verdict.

## Per rule

### Apply possible once the value tag is carried

| Rule | Apply writes | Value it needs | Moves |
|---|---|---|---|
| PC-2 | correct purchase price | `contract.sales_price` (carried) | LTV |
| IN-1 | correct income | `income.documented_monthly` | DTI |
| IN-3 | correct income | `income.documented_monthly` | DTI |
| CR-1 | add liability | `liab.monthly_payment` + `liab.balance` | DTI |
| CR-4 | add liability | same | DTI |
| RE-1 | add liability | same | DTI |
| DT-6 | correct liability payment | a billed-total tag (none produced) | DTI |
| PR-2 | correct valuation | `property.appraised_value` | LTV |
| IN-5 | correct employer | `income.employer_normalized` | none (data quality) |

### Apply with a choice the processor makes

**AS-12** and **FR-5** reach two different targets, and which one is right depends on what the
processor learns — not on anything the rule concluded:

* the funds were **borrowed** -> `add_liability` -> DTI up
* the funds cannot be **sourced** -> `exclude_asset` -> reserves and cash-to-close down

Both are legitimate under B3-4.2. The rule concluded "unsourced", never "borrowed", so Apply here asks
the processor for information the system does not have. It must not be a blind one-click.

**AS-6** is the asset case alone: the account holder is not a borrower, so the funds come out.

### No Apply, correctly (about 58 rules)

Nothing structured to write. The remedy is a document (Request docs — CL-1, CR-13, IN-8, ID-7, PR-6,
IH-*, AS-9/10, CO-1, LO-2, TI-1), a human judgment (Ratify / Override / Accept risk — CR-6, CR-8, OC-2,
DT-7, TI-6, FR-3, PR-3/5, ID-8/9), or the finding is computed from data that is already correct (MI-1,
MI-4, PE-1, PE-3, AS-4).

## One rule that fits the pattern and must be refused

**ID-2 (SSN consistency)** compares the application's SSN against a document's, so on paper it is a
clean Tier-1 correction. It must NOT get an Apply button. A one-click overwrite of an SSN from an OCR'd
field is the highest-cost silent error available, and the column is Fernet-encrypted precisely because
it is handled differently from every other field. Human-only, with a note.

## Safety properties to preserve

1. **Never without a click.** These are `ratification_pending` judgment rules; auto-applying is exactly
   what ADR-336 forbids. A human clicking Apply IS the ratification — which is sound only if the click
   is real.
2. **Reversible.** Undo restores the exact pre-apply state from `applied_record`. A new action must
   record enough to be reversed, or it must not ship.
3. **Conservative direction.** See above.
4. **An unknown action must not silently succeed.** Today it returns `applied: False` and the finding
   still closes as APPLIED. That is a finding marked resolved with nothing done — worth fixing before
   adding four new actions that could typo their way into it.
