## Design

**Tables and migrations:** none. `lender_condition_codes.canonical_type_id` and
`conditions.canonical_type_id` already exist (Stage 1) and were null.

**Data:** `backend/app/conditions/library/types.yaml`, version 1, **55 condition types** in 11 categories
(assets, credit, income, insurance, property, identity, title, closing, disclosure, invoice, lender). Each
type records:

| Field | What it holds |
|---|---|
| `id`, `name`, `category` | `AS-04`, "Earnest money", assets |
| `items` | what the condition usually asks for, each with `name`, `acceptable` (the acceptable form), `performer` (who provides it), `option` (the proposed next step), `documents` (the app's document types that satisfy it) and `checks` (what code verifies on arrival) |
| `default_option` | only for a type with no items: `lender_doing_it` or `information_only` |
| `rule` | an agency section the Stage 3 plan cites, or `lender_requirement` |
| `playbook` | one line for the processor |
| `waits_on_type` | a link to another type (0007's invoice waits on 1228's inspection) |

**Vocabulary:** `app/models/condition_vocabulary.py` — `Performer` (11), `PlanOption` (8, plan §5 LP-921's
table), `EvidenceCheck` (12). Enums only, under `app.models` because LP-920 and LP-923 store them.

**Loader:** `app/conditions/library/loader.py`, `load_library()` cached. It refuses: an id not shaped
`XX-00` or repeated; a performer, option or check outside the vocabularies; a document type no schema spec
declares; an agency citation the plan does not make; a type with no items and no itemless default, or with
items and a default; an unknown `waits_on_type`; empty text.

**Code maps:** every UWM (28) and Champions (28) row in `app/conditions/lender_codes/*.yaml` now carries
`canonical_type_id`. The 14 UWM ids spec §6 LP-910 named are kept exactly. `seed_lender_codes` already
updates the column on existing rows, and import already copies it onto the condition
(`_apply_code_defaults`), so no service changes.

**Review table:** `docs/phases/phase4.5-library-review.md`, generated from the library: the top 20 types
with items → who (option), documents, checks, rule, the codes they appear as, and a column for the
product owner's mark.

**Reuses:** the code-map loader and seed (LP-910), the schema specs' `document_type` vocabulary, the
import path's code defaults.

**Fixtures added:** none (tests build minimal libraries inline).

## Decisions

1. **The taxonomy is ours, built from the plan and the Stage 1 spec.** `phase4.5-appendix-C-condition-
   taxonomy` and `phase4.5-condition-research.md`, which the plan cites, are in no branch of this
   repository. The ids the Stage 1 spec gave 14 UWM codes are kept; the rest are assigned here in the same
   shape. Recorded rather than guessed at: if the appendix surfaces, reconcile ids against it.
2. **Citations only where the plan cites.** Six sources (ADR-409). Everything else — gifts, credit
   letters, title items — is "lender requirement". I did not cite sections I could not check against the
   plan's sources (for example Fannie Mae's gift section), because a processor would quote them.
3. **Lender behaviour is not in the library.** PA-03 (final inspection) proposes "I'll do it"; at UWM the
   lender orders it (decision 1), which is a lender setting applied by LP-920, not a UWM-specific type.
4. **About 40 became 55**, because every mapped code needs a type and Champions' lender-side codes
   (closer reviews, VOD, condo approval) are kinds UWM's sheets do not have. The test bounds the library
   at 40–60 so it cannot grow unreviewed.
5. **6378 is TI-04 "Instruction to title"** with option `ask_third_party`: plan §6 adds it to the title
   email as information to pass on; there is nothing to collect.
6. **0132 is DI-01 with three items** (disclosure → LO, approved attorney → LO, wire instructions →
   attorney). S3-03 draws the first item as "Borrower + LO"; the reading (LP-919) sets that per condition.

## Review (of `28ffc2f8`)

**One finding, fixed here.** The library, the loader and the code maps hold up: every claim in this
ticket was re-derived from the data rather than read, and the loader's refusals were made to fire.

### The finding

**F1 — five condition-type ids are already verification-rule ids, and nothing pinned that.**
`types.yaml`'s header says the two vocabularies "never meet" and closes with *"The loader refuses an
id outside the pattern below so a rule id cannot be pasted in unnoticed."* That last clause is not
true: the pattern is `XX-00`, which a two-digit rule id fits exactly — only the engine's single-digit
spellings (`AS-1`) are refused by shape. Measured against `rule_kinds.csv`, **five ids are in both
vocabularies today**, meaning different things in each:

| id | verification rule | condition type |
|---|---|---|
| `AS-10` | Statement recency completeness | Short funds to close or reserves |
| `AS-11` | Retirement/stock liquidation terms | Departing residence being sold |
| `CR-11` | Judgments / liens resolution | Contingent liability paid by others |
| `CR-12` | Disputed accounts | Residence history or mortgage verification |
| `CR-13` | Credit report validity at closing | Mortgage statement for another property |

Nothing joins the two vocabularies in code, so no data is wrong today; the cost is human, and it is
the cost this repo has paid before — someone reads `AS-14` in a ticket and opens the wrong document.
Both vocabularies are still growing, and a sixth would arrive silently. **Fixed:**
`backend/tests/conditions/test_library_ids_against_rule_ids.py` pins the five with both meanings, so
a new overlap fails and becomes a decision (rename the type, or record it having judged the overlap
harmless) — and a collision that *goes away* fails too, because a stale "known problem" list stops
describing anything. It carries a positive control, since the same assertion passes on two empty sets
if either file stops being read. Mutation-checked: dropping one id from the list fails it. The header
sentence is corrected to say what the pattern does and does not stop, and names the five.

### The citations, each checked against the plan

The reviewer brief names four sources; **the plan cites six**, and the loader's `AGENCY_CITATIONS`
is exactly those six, spelled as the plan spells them — including `Fannie Mae B7-3-07 / B7-3-08` as
the single combined string the plan uses (plan line 107) and `Reg Z 1026.36(c)(3)` (line 106), which
the brief's list omits. Every `rule:` in `types.yaml` is either one of the six or
`lender_requirement`: 48 lender requirements and 7 agency citations, all inside the allow-list.

The guard is real, not decorative. Feeding the loader a **plausible but uncited** section —
`Fannie Mae B3-5.1-01` — is refused just as an invented `B9-9-99` is, which is the property that
matters when a processor may quote it to an underwriter.

### Done when, the half that is this ticket's

"Every mapped lender code resolves to a type", re-derived through the real loaders rather than the
ticket's test: **56 mapped codes (28 UWM + 28 Champions), 0 without a type, 0 pointing at a type that
does not exist**, against 55 types, inside the 40–60 bound. Round 1's anchors are 6637 → `AS-04`,
7086 → `AS-10`, 1228 → `PA-03`, as the ticket says. The owner's sign-off on the top 20 is decision 6's
separate open item and correctly does not block this.

### The loader's refusals, made to fire

Nine mutations of the shipped library, each rejected with a message naming the type and the reason,
against a positive control that loads all 55: an invented citation; a plausible uncited one; an
unknown document type; a performer outside the vocabulary; a check outside it; a type with both items
and a `default_option`; an unknown `waits_on_type`; a duplicate id; a malformed id.

### The data decisions, checked against the data

Decision 5: 6378 → `TI-04` "Instruction to title", one item, option `ask_third_party`. Decision 6:
0132 → `DI-01` with three items — re-signed disclosure (LO), approved attorney (LO), wire instructions
(attorney). `waits_on_type`: 0007 → `IV-03` waits on `PA-03`, which is 1228's final inspection; no
`waits_on_type` anywhere is dangling. The items/`default_option` invariant holds for all 55 types with
no exceptions. The two code-map files are purely additive apart from header comments that had become
false (they said the column was null on every row).

**Plan fit:** the plan says "about **40**" types and this ships **55**. That is the plan's own two
requirements in tension — it also says every UWM and Champions code gets a type — resolved the way
decision 4 records, and bounded 40–60 by a test so the library cannot grow unreviewed. Accepted.
