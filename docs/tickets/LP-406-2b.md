# LP-406-2b — Write AS-8 (statement chaining), now that `stmt.continuity` exists — **and it goes LIVE (24 → 25)**

## What this ticket is

LP-406-2 stopped AS-8 at Phase 0: its check — statement N's ending balance == statement N+1's beginning
balance, per account — is an ordered-pairwise relation the deterministic DSL cannot express (ADR-322). LP-410
built the derived loan-level tag **`stmt.continuity`** that computes exactly that. **AS-8 is now a trivial
deterministic rule that branches on one enum** (the OC-1/AS-4 "deterministic rule reading an already-produced
tag" pattern, plus an applicability predicate for the `not_applicable` case).

**AS-8 is the first Bucket 2 rule to go LIVE.** It has **no AI dependency** (`stmt.continuity` is derived from
parsed statement balances) and **no Priya threshold** (exact carryover), so — unlike OC-1 (held on calibration)
and PC-7 (needs a Priya window) — it clears the no-AI-dependency gate and activates: **`ACTIVE_RULE_IDS` 24 →
25.**

## D1 — The subject match (anti-structural-death) — confirmed

`load_declarations()["stmt.continuity"].subject == "loan"`, and AS-8's `subject_enumeration == "loan"`. So AS-8
reads the tag exactly where LP-410 produces it — not born structurally dead (the ID-5 class). Asserted in the
tests and re-verified live.

## D2 — The `not_applicable` mechanism (new ground — OC-1 had no such case)

`not_applicable` is **not** a deterministic *outcome* verdict (the outcome verdicts are
`fired`/`satisfied`/`needs_review`/`couldnt_check`) — it is produced by the **applicability layer**
(`resolve_applicability`, §8 Tab 4). So AS-8 declares an applicability predicate:

```yaml
applicability: { tag: stmt.continuity, op: ne, value: nothing_to_chain }
```

Traced against `resolve_applicability` (read from the code):
- `stmt.continuity == "nothing_to_chain"` → the predicate (`ne nothing_to_chain`) is **false** →
  **`NOT_APPLICABLE`** (scope-false, no finding). ✅ the trap avoided.
- `stmt.continuity == "unknown"` → the resolver treats a predicate tag's `"unknown"` as **`couldnt_check`** (Tab
  1 — cannot tell / a data gap). ✅
- `stmt.continuity == "broken" / "chained"` → the predicate holds → the rule proceeds to the gate + outcomes.

This is the correct DSL mechanism (an applicability predicate, not a verdict branch) — no new machinery, so **no
ADR needed** (the pattern is the shared LP-329 applicability resolver, already used by ID-7/ID-9/AS-9).

## D3 — The outcome mapping + reason strings

| `stmt.continuity` | AS-8 verdict | reason (plain language, LP-376-C) |
|-------------------|--------------|-----------------------------------|
| `broken` | **fired** | "an account's bank statements do not chain — a statement's ending balance does not carry into the next statement's opening balance; reconcile the account's history before submission" (+ `how_to_fix`) |
| `chained` | **satisfied** | "every account's consecutive bank statements chain — each ending balance carries into the next statement's opening balance" |
| `nothing_to_chain` | **not_applicable** | (scope-false; no surfaced finding) |
| `unknown` | **couldnt_check** | "the statement balance continuity across the account could not be determined — this check needs it to tell whether the rule applies here" |

The `broken`/`satisfied`/`couldnt_check` reasons are static prose with **no dotted tag ids** (asserted). The
**specific** detail — which account breaks, at what balances — lives in the `stmt.continuity` provenance the
finding carries (its own reasoning names the break), not interpolated into the static reason (the deterministic
reasoning template interpolates only operands, and AS-8 has none — the OC-1/AS-6 convention). A plain-language
`fact_label` for `stmt.continuity` ("statement balance continuity across the account") was added to `reasons.py`
so the `couldnt_check` reason names the fact, not the tag id. *(The `not_applicable` reason is the shared
resolver's generic string — the same format every applicability-gated rule emits (`ID-7`/`ID-9`/`AS-9`); it is
scope-false and never a surfaced finding.)*

## D4 — Kind + ships; no AI dependency

`rule_kinds.csv`: AS-8 is **structural**, `deterministic_only`, `priya_validated=false`,
`threshold_needs_signoff=false`. A structural rule ships **auto** (LP-376-B). Its only load-bearing tag,
`stmt.continuity`, is **derived from parsed data** — no AI tag → **no calibration gate, no OC-1-style hold.** The
activation bar is `no-ai-dependency` with `load_bearing_ai_tags: []`.

## D5 — A Priya threshold? — none (re-confirmed)

The check is an **exact** balance carryover: statement N's ending balance *is* statement N+1's opening balance at
the same instant — there is no interval for interest/pending items to post between them, so **no tolerance** is
needed. `threshold_needs_signoff=false` (matches the CSV). LP-406-2 D6 said the same; re-confirmed against
`stmt.continuity`'s exact-equality design (LP-410).

**The four branches** (constructed snapshots):

**Activation:** `is_eligible(AS-8 bar) == True` (no-ai-dependency, `input_resolves`); `"AS-8" in
ACTIVE_RULE_IDS`; **`len(ACTIVE_RULE_IDS) == 25`** (was 24).

## The untested fire path (the caveat AS-8 ships with)

**LF-6T3N's 5 real statements chain cleanly, so AS-8's `fired` ("broken") path ships UNEXERCISED on real data.**
This is the **AS-2 one-sided-trigger shape**: AS-2 went live with its `loan_proceeds` trigger at n=0 on the
fixture; AS-8 goes live with its `broken` trigger unexercised on the fixture. Recorded in the bar rationale. The
`broken` path is proven on **constructed** snapshots (the tests), and the producer's own `broken` logic is
proven in LP-410's tests. **The scenario that would close it:** a bank-statement series with a deliberate balance
break (one statement's ending balance ≠ the next's opening) — a **fixture ticket** (the LP-393-1 scenario
pattern), NOT this one. AS-8 must not *falsely* fire on a clean file — verified (LF-6T3N → satisfied, not fired).

## The AS-10 scope boundary

`stmt.continuity` (and therefore AS-8) covers **only the balance carryover**. Whether an account has the required
number of recent consecutive **months** is **AS-10** (statement recency completeness, via
`stmt.min_account_months`). AS-8's reasons say *"balances don't carry"* and **never** *"a month is missing"*
(asserted — no `"month"` substring in the fired/satisfied reasons). So AS-8 and AS-10 do not double-fire on one
gap: AS-8 flags an unexplained balance break; AS-10 flags too few months. Clean, complementary.

## Every assumption / decision

- **`not_applicable` via applicability, not a verdict** — the DSL supports exactly this (the LP-329 resolver);
  AS-8 reuses it. A `nothing_to_chain` file is scope-false (nothing to chain), the same shape as AS-9's
  document-type applicability.
- **`rule_tags.csv` drift (noted, not fixed):** `rule_tags.csv` still lists AS-8 reading the raw
  `stmt.beginning_balance` / `stmt.ending_balance` / … (the pre-LP-410 plan). AS-8's **spec** reads the derived
  `stmt.continuity` (the tag that made the check expressible). Nothing enforces spec-vs-`rule_tags.csv`
  consistency (verified — no such test), so the drift is harmless; `rule_tags.csv` is the planning artifact,
  the spec's `load_bearing_tags` is authoritative for evaluation. Left as-is (out of this ticket's scope, like
  OC-1's census-drift note); a future `rule_tags.csv` regen should point AS-8 at `stmt.continuity`.
- **The `broken` reason is static** (no account-specific interpolation) — the detail is in the provenance tag,
  the OC-1/AS-6 convention.
- No existing tag, producer, prompt, or rule changed. The 24 previously-live rules are byte-identical; AS-8 is
  purely additive to the active set. `stmt.continuity` (LP-410) is unchanged.
