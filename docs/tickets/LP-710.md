# LP-710 — one field list, and selecting a field actually shows its box

- **Ticket:** LP-710
- **Status:** Done (2026-09-06)
- **Reported by:** the LP-703 review (the refactor) and the user, from the running app (the selection)
- **Scope:** Frontend — `review/page.tsx`, `reviewer-fields.tsx`, `box-overlay.tsx`, `vitest.setup.ts`

## Part 1 — the field list was derived twice

The review page and the fields pane each called `extractionFields` on the same data. Nothing
made the two agree, and they drifted **three times**. Each time the symptom was a field a
processor could **see but not reach**, or reach but not see:

- a backend-sensitive field rendered as a masked scalar on screen and arrived at the keyboard
  as a *list* — and lists are excluded from the queue, so it looked reviewable and was
  permanently unreachable;
- an **added** field was drawn with no row key, no queue entry and no label, and
  `editableFieldKey` could never name it — the one value a human is personally answerable for
  was the one row the keyboard could not touch.

Both were repaired by making the ARGUMENTS impossible to differ (`sensitiveKeysOf`,
`correctionsOf`). That is a fix that holds until the next argument someone adds.

**The page derives the list once and passes it down.** `ReviewerFields` renders what it is
given. Two call sites deriving one list is the defect; a test only reports it after they have
already drifted.

## Part 2 — selecting a field did not reliably show its box

Two separate gaps, both reported from the app.

**Only the field NAME was clickable.** The comment above the row has said *"the whole row is
the control rather than a small affordance inside it"* since LP-UI-030, while the click
handler sat on the label button alone. Clicking a value, a source snippet, or the space
beside them did nothing — a processor reading a row had to go back and hit the one word at
its left edge. The row is the control now; the label stays a real button because an `<li>`
serves no keyboard user, and the row cannot become one without nesting the buttons it
already contains.

**Nothing scrolled the document to the box.** Selecting a field jumped to the box's *page*
and stopped there. On a zoomed page — where the pan region scrolls — the box was highlighted
somewhere outside the visible area and the screen appeared not to respond. The fields pane
has had the mirror of this since LP-UI-030 (`selectedRow.scrollIntoView`); the document side
never did. Keyed on selection, never on hover: hover is how a processor skims, and scrolling
under a moving pointer would make the document unusable.

## Two tests that passed for the wrong reason

Found by mutation, not by reading:

**`scrollIntoView` is one function on `Element.prototype`.** Asserting `element.scrollIntoView`
*was called* proves nothing about *which* element — the spy is shared by every element in the
document. A ref attached to every box passed the whole suite. The recorder captures `this`
now, so the assertion compares elements.

**A "does not scroll on hover" test with nothing selected.** The ref is only attached to the
selected box, so with no selection no scroll can happen for any reason — the test passed with
the hover guard deleted. It keeps a field selected throughout now and asserts that moving the
pointer adds no scroll.

## Verification

- 1,306 frontend tests, biome and tsc clean.
- Four mutations, all caught after the two rewrites: no ref (3 failures), a ref on every box
  (1), scrolling on hover (1), the row not clickable (2).
- Checked in the running app: clicking the VALUE `$15,000.00` — not the label — selects the
  row and draws the boxes on the page.


## Review (2026-09-06)

### The scroll did not fire in the case it was reported for

Keyed on `selected`, the effect ran in the commit where the selection changed — and for a box
on ANOTHER page that is a commit where the box is not rendered and the ref is null. The page
moves from a separate effect in `review/page.tsx`, so it lands in a LATER commit, by which
time the selection has not changed and the effect does not run again.

So the fix worked only where the box was already on the page on screen, and the reported
symptom — "selection jumped to the box's page and stopped there" — survived it. Every scroll
test kept `page={1}` with the selected box on page 1, so nothing could see it.

The same shape hid a second case: the boxes come from a query, so selecting a field before it
resolves also ran the effect against a null ref and nothing ran it again.

Both are fixed by one change — the effect now depends on the identity of the box it is
scrolling to, which becomes non-null when the box APPEARS, however it appears. No ordering
assumption between the two commits, and hover is still not in the dependency.

### The fields pane, cited here as the working precedent, had the same gap

`ReviewerFields` has had `useEffect(..., [selected])` since LP-UI-030 and this ticket treats
it as the side that already worked. It has the identical latent bug in the identical shape:
selection arrives from the document as well as from the pane, the two sides load on separate
queries, and a processor who clicks a box while the pane is still a skeleton sets `selected`
in a commit with no rows in it. Fixed the same way, with a control asserting that a key this
document has no row for scrolls nothing.

### A field can have several boxes on one page

`ref={isSelected ? selectedBox : undefined}` gives the SAME ref object to every box of the
selected field, and the matcher returns up to `MAX_MATCHES` of them. `current` ended up
holding whichever React attached last, so the page scrolled to the bottom-most occurrence by
accident rather than to the first one a reader looks for. The ref now goes to the first box
alone, identified by the same `boxKey` helper React keys on — written out twice they drift,
and the drift is silent, because the ref would attach to a box the effect is not watching.

### The third test passing for the wrong reason

The ticket found two and asked for a third. It is the hover test, and it is still green by
construction after its rewrite: `hovered` is not a dependency of the effect, so no guard
inside the effect decides anything about hover and a mutation weakening one passes. What
distinguishes the code from a plausible regression is a target that falls back to the hovered
field — `selected ?? hovered` is how someone would naturally add "highlight what I am pointing
at" — and the existing test cannot see that, because something is selected throughout and
selection wins. The new case hovers with nothing selected, and fails against that mutation.

### One handler per activation

The row and the label button each carried an `onClick` calling `onSelect(field.key)`, so
activating the label fired it TWICE. Harmless only because selection happens to be idempotent
— and neither copy could be held by a test, because deleting either one leaves the other
selecting. The label's is removed: the browser delivers a button activation as a click, which
reaches the row's handler, so the keyboard path the a11y suppression names still holds and
there is now one rule rather than two copies of it.

### The a11y suppression is the right trade

`onClick` on an `<li>` with the label button as the keyboard path is sound: the row cannot
become a button without nesting the buttons it contains, and the stretched-link alternative
touches `ExtractionTable`, which is shared. No change asked for.

Two consequences worth stating rather than fixing, both judgement calls for whoever owns the
screen. Clicking Undo on a row that is not selected now also selects it, and selection is not
free — it moves the DOCUMENT to that field's page. And `cursor-pointer` now covers the value
text, so a processor dragging to copy an account number ends the drag with a click that
selects the row.

### Confirmed rather than changed

`ReviewerFields` calling `useDocumentDetail` alongside the page is the same query key against
the same cache, and `scrutiny[field.key]` is a raw lookup rather than a derivation — so this
is not the shape that drifted three times, which was two derivations from different arguments.
The `scrollIntoView` shim is installed only when absent and no test depended on the throw;
`searchable-select.tsx` already called it optionally.

### Verification

- 1,315 frontend tests, biome and tsc clean.
- Ten mutations, ten caught: both `[selected]` dependency reversions, the ref on every box,
  the target picking the last box, the target falling back to hovered, `boxKey` drifting from
  the ref comparison, the pane ignoring whether the row exists, the row's click handler
  removed, a second handler back on the label, and the row's hover handlers removed.
- The row's hover handlers had no test at all: LP-710 moved them from the label button to the
  row and nothing held them in either place, so pointing at a value to emphasise its box could
  have been deleted with the suite green.
