# LP-710 — one field list, and selecting a field actually shows its box

- **Ticket:** LP-710
- **Status:** Done (2026-09-06)
- **Reported by:** the LP-703 review (the refactor) and the user, from the running app (the selection)
- **Scope:** Frontend — `review/page.tsx`, `reviewer-fields.tsx`, `box-overlay.tsx`, `vitest.setup.ts`

## Part 1 — the field list was derived twice

The review page and the fields pane each called `extractionFields` on the same data. Nothing
made the two agree, and they drifted **three times**. Each time the symptom was a field a
processor could **see but not reach**, or reach but not see:

- a backend-sensitive field rendered as a masked scalar on screen and arrived at the keyboard
  as a *list* — and lists are excluded from the queue, so it looked reviewable and was
  permanently unreachable;
- an **added** field was drawn with no row key, no queue entry and no label, and
  `editableFieldKey` could never name it — the one value a human is personally answerable for
  was the one row the keyboard could not touch.

Both were repaired by making the ARGUMENTS impossible to differ (`sensitiveKeysOf`,
`correctionsOf`). That is a fix that holds until the next argument someone adds.

**The page derives the list once and passes it down.** `ReviewerFields` renders what it is
given. Two call sites deriving one list is the defect; a test only reports it after they have
already drifted.

## Part 2 — selecting a field did not reliably show its box

Two separate gaps, both reported from the app.

**Only the field NAME was clickable.** The comment above the row has said *"the whole row is
the control rather than a small affordance inside it"* since LP-UI-030, while the click
handler sat on the label button alone. Clicking a value, a source snippet, or the space
beside them did nothing — a processor reading a row had to go back and hit the one word at
its left edge. The row is the control now; the label stays a real button because an `<li>`
serves no keyboard user, and the row cannot become one without nesting the buttons it
already contains.

**Nothing scrolled the document to the box.** Selecting a field jumped to the box's *page*
and stopped there. On a zoomed page — where the pan region scrolls — the box was highlighted
somewhere outside the visible area and the screen appeared not to respond. The fields pane
has had the mirror of this since LP-UI-030 (`selectedRow.scrollIntoView`); the document side
never did. Keyed on selection, never on hover: hover is how a processor skims, and scrolling
under a moving pointer would make the document unusable.

## Two tests that passed for the wrong reason

Found by mutation, not by reading:

**`scrollIntoView` is one function on `Element.prototype`.** Asserting `element.scrollIntoView`
*was called* proves nothing about *which* element — the spy is shared by every element in the
document. A ref attached to every box passed the whole suite. The recorder captures `this`
now, so the assertion compares elements.

**A "does not scroll on hover" test with nothing selected.** The ref is only attached to the
selected box, so with no selection no scroll can happen for any reason — the test passed with
the hover guard deleted. It keeps a field selected throughout now and asserts that moving the
pointer adds no scroll.

## Verification

- 1,306 frontend tests, biome and tsc clean.
- Four mutations, all caught after the two rewrites: no ref (3 failures), a ref on every box
  (1), scrolling on hover (1), the row not clickable (2).
- Checked in the running app: clicking the VALUE `$15,000.00` — not the label — selects the
  row and draws the boxes on the page.
