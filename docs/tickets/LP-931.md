# LP-931 — the three CHECK constraints no migration created

- **Ticket:** LP-931 · Phase 4.5 follow-up · schema (one migration, one guard change)
- **Raised:** Stage 2's follow-ups in [`phase4.5-progress.md`](../phases/phase4.5-progress.md), first
  found by the LP-912 review's migrated-schema guard
- **Migration:** `backend/alembic/versions/20260928_1200_fb263dfd0473_lp931_missing_checks.py`
  (`a7c31e6d94b2` → `fb263dfd0473`)

## What was wrong

`communications.body_format`, `users.mail_client` and `validation_verdicts.kind` are `str_enum`
columns. `create_all` gives each a CHECK, so the test suite has always had them. A migrated database
had none, so each column accepted any string on staging:

| Column | How it reached the database without a CHECK |
|---|---|
| `validation_verdicts.kind` | LP-89 declared it `sa.Enum(..., native_enum=False)`. `create_constraint` defaults to False in SQLAlchemy 2, so no CHECK was emitted. |
| `communications.body_format` | LP-853 added it as a plain `String(16)` with a server default. |
| `users.mail_client` | LP-855 added it as a plain `String(32)`, nullable. |

`tests/test_migrated_checks_match_models.py` found them on its first run and held them in
`_KNOWN_MISSING`.

## Step 1 — the read-only check, run before the migration existed

This lists every row whose value is outside the permitted set. NULL is not a violation (a CHECK passes
on NULL, and `mail_client` is NULL until a processor picks a client); `body_format` and `kind` are
`NOT NULL`, so they cannot hold one. It runs against a database with `public` access (dev, or a scratch
database):

```sql
SELECT 'communications.body_format' AS col, body_format AS value, count(*) AS n
  FROM public.communications
 WHERE body_format IS NULL OR body_format NOT IN ('plain', 'html')
 GROUP BY body_format
UNION ALL
SELECT 'users.mail_client', mail_client, count(*)
  FROM public.users
 WHERE mail_client IS NOT NULL
   AND mail_client NOT IN ('gmail', 'outlook_work', 'outlook_personal', 'mailto')
 GROUP BY mail_client
UNION ALL
SELECT 'validation_verdicts.kind', kind, count(*)
  FROM public.validation_verdicts
 WHERE kind IS NULL OR kind NOT IN ('validated', 'corrected', 'flagged_remove', 'add_new')
 GROUP BY kind
ORDER BY 1, 2;
```

A healthy result is zero rows.

### What it found

- **Local dev (`mortgageboss_dev`): zero rows, but that is vacuous.** All three tables are empty there
  (0 communications, 0 users with a `mail_client`, 0 verdicts). A clean result on an empty table says
  nothing, so the query's positive control was run on a scratch database: at `a7c31e6d94b2`, with one
  `mail_client = 'thunderbird'` row and one `'gmail'` row inserted, it returned exactly
  `users.mail_client | thunderbird | 1`.
- **Staging: clean for the two columns the readonly role can see.** Run 2026-09-28 through
  `./scripts/deploy staging query` against `readonly.communications` and `readonly.validation_verdicts`,
  listing every value present rather than only the bad ones:
  `communications.body_format` holds `plain` (16) and `html` (3); `validation_verdicts` has no rows.
- **Staging `users.mail_client` could not be checked.** `readonly.users` does not expose the column
  (`column "mail_client" does not exist`), and the readonly role cannot read `public`. The migration's
  own pre-check covers it: if staging holds a bad value, the deploy's `migrate` stage fails with the
  offending value named, and nothing is changed. The only writer in `app/` is
  `PUT /users/me/preferences` (`app/api/preferences.py`), whose schema types the field as
  `MailClient | None`, so a bad value would need a write from outside the API.

## Step 2 — the migration

- **Raw `op.execute("ALTER TABLE ... ADD CONSTRAINT ...")`, never `op.create_check_constraint`**,
  which is how the naming convention doubled LP-904's names. The names are exactly what `create_all`
  emits: `ck_communications_bodyformat`, `ck_users_mailclient`, `ck_validation_verdicts_verdictkind`
  (read from `Base.metadata` compiled for PostgreSQL, not written from memory).
- **The value lists are literals, not read from the enums.** A migration records what it installed;
  importing the enum would make a replay install whatever the enum says that day. The migrated-vs-models
  guard keeps the two equal.
- **Bad rows stop it, loudly, and nothing is rewritten.** Before adding anything it runs the step 1
  check for all three columns, and if any row fails it raises one `RuntimeError` listing every
  offending value with its count, saying nothing was changed and pointing here. Which value a bad row
  should hold is a person's decision. Postgres would refuse the `ADD CONSTRAINT` anyway, but with a
  message naming only the constraint.
- **Downgrade** drops the three with `DROP CONSTRAINT IF EXISTS`.

## Step 3 — the guard now requires them

`_KNOWN_MISSING` is now empty. The comment above it records that LP-931 emptied it and keeps it as the
place to record the next gap as a decision. **Mutation-checked:** with the `users.mail_client` entry
deleted from the migration, `test_every_check_the_models_declare_is_what_migrating_installs` fails with
`[('users', ('mail_client',))]`; restored, it passes.

## Step 4 — upgrade, downgrade, upgrade on a scratch PostgreSQL 16

Local PostgreSQL 16.14, database `lp931_scratch` created and dropped by the run:

| Step | `alembic_version` | CHECKs present |
|---|---|---|
| `upgrade head` | `fb263dfd0473` | all three |
| `downgrade -1` | `a7c31e6d94b2` | none |
| `upgrade head` | `fb263dfd0473` | all three |

After the second upgrade, an `INSERT` with `mail_client = 'thunderbird'` was rejected by
`ck_users_mailclient`.

**The refusal, proved:** downgraded to `a7c31e6d94b2`, one `mail_client = 'thunderbird'` row inserted,
then `upgrade head`:

```
RuntimeError: LP-931 refused to add its CHECK constraints, and changed nothing: these rows hold a value outside the permitted set.
  users.mail_client = 'thunderbird': 1 row(s)
Decide what each should hold and correct it by hand, then run the migration again. The read-only query that lists them is in docs/tickets/LP-931.md.
```

Afterwards the version was still `a7c31e6d94b2`, the row was still there unchanged, and none of the
three constraints existed.

## Decisions

1. **No `IF NOT EXISTS` on the add.** No migrated database has these names, so the plain form succeeds
   everywhere this is expected to run. A database that somehow already has one fails loudly rather
   than being skipped silently, which is the direction this ticket prefers.
2. **Not added to `_CASES` in `test_activity_type_migrations.py`.** That guard reads migration text for
   enums likely to gain values by swap. The migrated-schema guard now compares these three column by
   column against the models, which catches a new enum member with no migration just the same.
