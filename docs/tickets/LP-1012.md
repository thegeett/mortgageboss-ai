# LP-1012 — Prove step 4 in staging

Step 4 (Receive), last ticket. One small code fix, a deploy, and a check with real email: the Yadees test
company (`mb-mail.yadees.com`), Geet's Gmail, and the Yadees login (`geet.thaker+yadees@gmail.com`). Nothing
committed.

## What and why

LP-1008 to LP-1011 built receiving and were only checked in dev. This ticket deploys them and proves the flow
end to end with real email: a reply with PDFs reaches its file, the processor gets a copy, Reply-all and a
reply from the copy don't make another copy, and unmatched mail can be moved or dismissed.

## Part 1 — Subjects stored decoded

LP-1011 Open 3: ingest stored `Subject` as written, so an accent or emoji showed on the card as
`=?utf-8?q?…?=`.

| File | Change |
|---|---|
| `services/inbound_mime.py` | `decoded_header` and `one_line` moved here from `processor_copy.py` (one helper, two users) |
| `services/processor_copy.py` | Imports them; its own copies removed |
| `services/inbound_ingest.py` | `subject` stored through `decoded_header`: RFC 2047 decoded, raw 8-bit bytes read as UTF-8, control characters (line breaks) as spaces. No subject stays None |
| `api/inbound.py` | The card's `subject` also goes through `decoded_header`, so rows stored before this read decoded too (a no-op on new rows). One line |

Existing rows are not rewritten.

**Tests:** `test_lp1012_the_subject_is_stored_decoded` (accent → "Documentos de José", emoji, plain unchanged,
an encoded line break → a space), `test_lp1012_no_subject_stays_none`, `test_lp1012_an_unencoded_8bit_subject_is_stored` (UTF-8, not UTF-8),
`test_lp1012_an_old_row_with_an_encoded_subject_shows_decoded`.

**Mutation checks** (restored from a copy):

| Mutation | Failed by |
|---|---|
| Ingest stores the subject as written | the accent, emoji and line-break cases (plain passes, as it should) |
| Raw 8-bit not read as UTF-8 | `test_lp1012_an_unencoded_8bit_subject_is_stored[utf-8]` |
| Card shows the stored subject as is | `test_lp1012_an_old_row_with_an_encoded_subject_shows_decoded` |

**Suite:** backend 9712 passed (9704 + 8), 12 skipped, 1 xfailed. `ruff`, `ruff format`, `mypy app` (590
files) clean.

**Review (one round):**

1. **A subject sent as raw UTF-8 bytes, not encoded, is stored as `Documentos de Jos��`.** Measured with
   `Subject: Documentos de Jos\xc3\xa9`. Before this ticket the same email **crashed ingest**
   (`asyncpg DataError: expected str, got Header`: compat32 returns a `Header` object for 8-bit bytes, which
   was handed to the database), so it retried and would reach the DLQ. Now it is stored, with the accent
   lost. **Fixed** (on instruction): `decoded_header` reads `unknown-8bit` parts as UTF-8; bytes that are
   not UTF-8 still store, with a replacement character, instead of crashing.

**Suite:** backend 9715 passed (9712 + 3), 12 skipped, 1 xfailed; `ruff`, `ruff format`, `mypy app` (590 files) clean. Frontend 2488 passed
(202 files); `biome`, `tsc` clean.

**Review (one round):**

1. **Acting on an attachment undid "Mark unread".** The first version refreshed every open message on the
   file. Fetching an unread message marks it read (`api/communications.py:581`), so open, Mark unread, then
   Accept left it read. Measured with a throwaway test (a second fetch after Accept). **Fixed:** only a
   message already read is refreshed.
2. **An open draft was fetched again for nothing.** No harm to edits (the editor seeds once per id,
   `message-dialog.tsx:178`). **Fixed** by 1: a draft is never read (`mark_read` refuses an outbound message).
3. **Nothing tested that the queueing comes after the commit.** **Fixed:** the commit-order test above.

**The two documents from step 3 are not queued by this fix**: it acts at Accept, and they were accepted
before it. Nothing on screen restarts them: the bulk "Re-read unidentified documents" skips a `pending`
document (`already_queued`), and the per-document "Re-read this document" is disabled while the status is
not final (`isTerminalStatus`; `pending` counts as in flight). The API's per-document reprocess does take
`pending`.

## Open

1. **Rows stored before this keep the encoded subject** in the table; only the card decodes them.
2. **Nothing reads the `scan-results` queue.** 3 messages wait there, one per new `inbound/` object. No code
   in `backend/app` reads it; GuardDuty tags the object, and the app checks attachments itself. They expire at the
   queue's retention. Not a failure, but it means the GuardDuty verdict reaches no screen.
3. **`mbai-staging-scheduler-dlq` holds 5 messages.** Not a mail queue, and outside this ticket; not looked into.
4. **After Accept, the open message's "What arrived" list still said "not yet accepted"** while the card below it
   said "Added to documents" (step 3 screenshot). Cause: no attachment action refreshed the open message's
   query. **Fixed in Part 1b.**
5. **An accepted email attachment is never processed.** Both documents from step 3 stayed `pending`, never
   updated after creation. Cause, from the code: `accept` (`api/inbound.py:299`) and `accept_attachment`
   (`services/inbound_triage.py:155`) create the document and commit, and nothing enqueues
   `process_document`. The other ways a document arrives do: upload (`api/documents.py:254`) and the upload
   link (`api/upload_links.py:223`). `accept_attachment`'s docstring says "same processing pipeline"; it is
   not. **Fixed in Part 1b** (on instruction). The two step-3 documents need a per-document re-read.
