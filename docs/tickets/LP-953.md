## Design

**The doors** (listed first, so every rule is checked at each):

| # | Door | Where | Matching rule | Her unlinks respected | 404 for another file |
|---|---|---|---|---|---|
| 1 | Arrival | `condition_evidence.check_document` | `document_answers` | yes | n/a (same file by construction) |
| 2 | Plan time ("Already in the file", found) | `condition_plan._find_document` | `document_answers` | n/a (a new item has none) | n/a |
| 3 | Link | `POST /conditions/{id}/items/{item}/links` | her choice | clears the fact for that pair | document and item |
| 4 | Change | same, with `replace_document_id` | her choice | old pair recorded, new pair cleared | both documents |
| 5 | Unlink | `DELETE /conditions/{id}/items/{item}/links/{doc}` | n/a | writes the fact | document and item |
| 6 | Upload here | documents upload with `condition_item_id` | her choice | n/a (a new document) | item (checked before anything is stored) |
| 7 | "Already in the file" by hand | `update_item`, `set_next_step` | refused unless linked | n/a | n/a |

**What is true** (ADR-418). The evidence row is the link; `condition_items.document_id` is a pointer that
follows it. A manual link is an evidence row with `origin = manual`, `linked_by_user_id`, `page`.

**Her choice is a stored fact.** Unlink deletes the evidence row (so none of the seven queries over evidence,
in `condition_evidence`, `condition_package` and `figures_check`, has to learn to skip it) and writes
`condition_item_unlinks (item, document)`. Doors 1 and 2 pass that set into `document_answers`. Linking the
pair again by hand deletes the fact. This follows the owner field's pattern: her decision is a separate fact,
never an overwrite of the inference, so clearing it restores the automatic match with nothing to rebuild.

**One matching rule** (`app/services/condition_matching.py`): `document_answers(wanted, match_words, document,
item_id, unlinked)`. The type must be one the item wants; when the library gives words, one must be in the
document's name; the pair must not be one she unlinked. What differs between the callers is passed in (the
plan matches a new item with no unlinks; arrival passes the file's unlinks). Arrival's month and account rules
stay in `_takes`, after this. `library_item_for` splits a part's key on the first dot; the premise "no library
key contains a dot" is now pinned by a test.

**The two tensions in the spec, decided:**
1. *"Marks the item done" vs "checks still run and stay visible".* A manual link runs the item's checks like
   any evidence. A document whose type the item does not ask for gets a failed **Right document type** check
   naming both types ("The linked document is a credit report; this item asks for a service invoice"). So the
   item is NOT done, `_settle` cannot move the condition to Ready, and the package cannot pick it up. She can
   **Accept anyway** with her reason (the existing step), which is her decision, recorded; the item is then
   done. A manual link to an item with no checks, of a type it accepts, is done (she chose it; nothing to
   run). A manual link made before the document has been read carries a not-run "Document read" check
   ("Waiting for the document to be read") until the evidence step checks it, so it is never done early.
2. *"More than one document per condition" vs one `document_id`.* Evidence rows are keyed by item and
   document, so an item can have several documents and a condition several items. No new link table; the
   pointer names the latest link.

**Unlink recomputes.** The item becomes done if another linked document still passes, received if one is
linked, else open (or requested if its ask went out). A Ready condition goes back to To do
(`condition_prep_moved`, `by: unlink`). Unlinking a plan-time "Already in the file" pointer makes the item her
task again (an "Already in the file" with no document is the state this ticket forbids).

**Events.** `condition_evidence_linked` (item key, document id, page, `replaced`) and
`condition_evidence_unlinked` (item key, document id). Migration `9a3e5c7b1f20`: the evidence columns, the
`condition_item_unlinks` table (ids only; a readonly view, re-granted) and the two kinds (36).

**Frontend.** Each item in the drawer offers **Link a document** (a document on the file, and a page) and
**Upload here**. Each evidence card says how it was linked ("linked by hand by Priya Raman, page 3", or "linked
to this condition automatically", which used to be said of every card) and offers **Change** and **Unlink**.
A manual link is never re-asked (nobody sent it). History lines for both events.

**Not built:** a document picker that filters by the item's wanted type (all the file's documents are
offered; a mismatch is allowed and flagged, by design).

## Tests

`backend/tests/conditions/test_lp953_linking.py`, 23 tests:
- the premise: no library item key contains a dot;
- every invoice pair, both directions (IV-01 credit, IV-02 processing, IV-03 inspection: 9 cases), only its
  own invoice answers;
- arrival: a processing invoice answers 1582 and not 0006; the positive control, a credit invoice answers
  0006;
- a link to a document still being read waits ("Document read") and is checked when it is read;
- a mismatched link fails "Right document type", the item is not done and the condition is not Ready; Accept
  anyway makes it done;
- unlink deletes the row, records her choice, the document processed again is not re-linked, and linking it
  by hand clears the fact; unlinking the document that made a condition Ready puts it back to To do; Change
  unlinks the old and links the new (`replaced` false then true);
- another file's document is not found (link and unlink), at the service and through the routes;
- "Already in the file" by hand is refused without a link (item and condition) and accepted with one;
  unlinking a plan-time pointer makes the item her task again;
- the routes: link, 409 when already linked, the response's evidence says `manual`, the page and who; unlink;
  409 when nothing is linked; upload here links the upload awaiting its read, and another file's item is
  refused.

Also observed and pinned rather than changed: IV-01's item has no checks, so a document ARRIVING for it leaves
the item "received", never done (LP-923 as built); only her link or her "done" finishes it.

1582 by hand with no document. They now give its items a document pointer first (`point_items_at_a_document`),
