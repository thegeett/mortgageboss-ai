# LP-709 — never draw a box we cannot verify

- **Ticket:** LP-709 (LP-700 series, 4 of 4)
- **Status:** Open. Ships WITH LP-706, not after it.
- **Scope:** Backend — `services/field_boxes.py`; Frontend — the reviewer's box overlay
- **Prompts changed:** none. **Extra AI calls:** none. **New dependencies:** none.

## The idea in one line

Every ticket in this series makes boxes appear where none did. The failure they all share is
a box that appears in the **wrong** place, and a confident wrong highlight is worse than no
highlight at all.

## Why this is a ticket and not a paragraph in the others

Today the box mechanism is exact string search: it either finds the text or it does not, so
a wrong box is close to impossible. Every improvement in this series trades that certainty
for coverage:

- **LP-706** matches loosely, so it can match the wrong thing — the same figure appearing
  twice, a normalised value that collides with another field.
- **LP-707** takes anchors from the model, which can name the wrong neighbours.
- **LP-708** adds OCR, whose rectangles are estimates and whose text can be misread.

Each is worth doing. Together they change the guarantee from "a box is right or absent" to
"a box is probably right", and nothing in the current design notices the difference.

## What changes

**Verify before drawing.** A box is only drawn when the text under it actually contains the
extracted value — check the matched words against the value, not merely against the snippet
that led us there. A match that fails this check becomes **no box**, not a box.

**Say which kind of certainty it is.** The reviewer already has honest no-box states
("Not locatable on the page", "the extraction cited a page this document does not have").
They should extend to say when a box came from OCR — an estimated position on a page nobody
proofread is a different claim from a position read out of the file.

**Measure the wrong ones, not just the missing ones.** The LP-UI-031 measurement counted how
many fields *have* a box. From here on that number can go up while accuracy goes down. The
metric has to become "boxes that contain their value", sampled and checked.

## Behaviour by document kind

| | what happens |
|---|---|
| **Text PDF** | Catches a loose match that landed on the wrong occurrence of a repeated value. |
| **Scanned PDF** | Catches an OCR misread — the box sits over words that do not contain the value. This is where it earns its keep, because OCR rectangles are estimates. |
| **Mixed PDF** | Per page, like everything else in this series. |
| **Image** | Same as a scanned page. |

## Acceptance

- [ ] A box whose words do not contain the extracted value is never drawn
- [ ] The metric changes from "fields with a box" to "fields with a box that contains the
      value", and both numbers are reported
- [ ] The reviewer distinguishes a position read from the file from one estimated by OCR
- [ ] A deliberately wrong match is a test, so the guard cannot pass by never running
