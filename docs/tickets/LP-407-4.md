# LP-407-4 — Write PC-3 (contract property address vs the loan file): the last blocker-free rule

## What this ticket is

LP-415/LP-416's re-plan puts **PC-3 alone in blocker class A** — the last rule with no Priya value, no
calibration round, no producer batch, no extractor extension, and no absent extractor. It needs one
address-normalize producer + a spec; its "file" operand is the MISMO subject-property address, already reachable.
PC-3 compares the **purchase contract's subject-property address** against the **loan file's (1003/MISMO)
subject-property address** — a mismatch means the contract and the application describe different properties.
**PC-3 activates: `ACTIVE_RULE_IDS` 29 → 30.**

**The key design finding (the gate of record beat the ticket's "trivial spec" premise):** the deterministic
operand path is decimal/date only — it **cannot string-compare** — so PC-3 is a *derive-then-branch* rule (the
OC-1/IN-6 shape), and the deterministic normalizers can't expand `St→Street`, so a mismatch **routes to
`needs_review`, not `fired`** (ADR-325, second instance).

## D0 — the redundancy check

No product surface (services/api/findings/calc) shows a contract-vs-file property-address mismatch — grepped,
empty. PC-3 duplicates nothing. **No STOP.**

## D1 — the mailing-address trap: AVOIDED

The file's **subject-property** address is independently reachable via distinct MISMO facts
`property.address_line` / `address_line_2` / `city` / `state` / `postal_code` (populated from the Property
model) — **separate** from the borrower `current_address_line` (which the MISMO parser can fill with a *mailing*
address). PC-3's producer reads `property.address_*` and requires the street line + city + state + postal to all
be present (else `unknown`) — **never a comparison against a partial or mailing address, and never against a
retained-property tax bill** (a different property; the recipe scopes to `purchase_agreement` docs only). **No
STOP.**

## D2 — normalization → `needs_review`, not `fired` (ADR-325 extended)

Two facts reshaped the plan:
1. **The deterministic operand path coerces to decimal/date only** (`KNOWN_OPERAND_TYPES = {decimal, date}`) — it
   **cannot compare two address strings**. So PC-3 cannot be an IH-3-style operand compare; it is a
   *derive-then-branch* rule (the OC-1/IN-6 shape): a derived `property.address_normalized_match` enum
   (yes/no/unknown) does the compare, PC-3 branches.
2. **The consistency normalizers** (`casefold` / `drop_punct` / `collapse_ws`) do **not** expand `St→Street` /
   `Apt↔#↔Unit` / ZIP+4 — so an exact-after-normalize mismatch carries a known false-positive residue.

**→ The mismatch branch routes to `needs_review`, never `fired` (ADR-325, the second instance after IN-6).** A
false "different property" *firing* on an abbreviation variant is noisy and alarming; surfacing it for a human to
confirm is safe (a genuine different-property still surfaces). **FP/FN:** the FP (an abbreviation read as a
mismatch) is exactly why it routes to `needs_review`; a missed genuine mismatch still surfaces (as
`needs_review`). **I reused the consistency normalizers — no new fuzzy matcher.** The AI-tolerant match
(`property.address_normalized_match`'s `fact_tags.csv` design) is the future refinement that reduces the
`needs_review` noise — a calibration ticket, deferred.

## D3 — the promotion + multi-contract abstain

`_property_address_match` is a **loan-level derived** recipe reading the contract's `property_address` field +
the MISMO subject address directly. Multiple purchase agreements that **disagree** on the property address →
`unknown` (abstain, never pick one) — the established discipline.

## D4 — the subject match (anti-structural-death)

PC-3 `subject_enumeration: loan`; `property.address_normalized_match` is loan-subject. Verified against
`load_declarations()`. Not born structurally dead.

## D5 — provability + the scenarios

**LF-6T3N has no MISMO subject-property address** (LP-414 added only `property.purchase_price`), so PC-3
**couldnt_checks on LF-6T3N** — an honest absence, not a bug. The branches are proven on **4 standalone address
scenarios** in `fire_path_scenarios.py` (own `95…` ids, NOT LF-6T3N): match → satisfied, mismatch →
needs_review, abbreviation (`Lane` vs `Ln`) → needs_review (the FP case), mailing-only → couldnt_check (the D1
trap).

## D6 — the overlap boundary

**ID-4** compares the **borrower's residence** address across sources; **PC-3** compares the **subject
property** address (contract vs 1003). Distinct facts — no double-fire.

## Every assumption / decision

- **Derive-then-branch, not an operand compare** — the operand path is decimal/date only; it cannot string-compare.
- **`needs_review`, not `fired`** — the deterministic normalizers cannot expand abbreviations (ADR-325 extended).
- **The MISMO SUBJECT address only** — never `current_address` (mailing) or a retained-property tax bill (D1).
- **Multi-contract disagreement → unknown** — abstain, never pick.
- **Scoped to `purchase_agreement`** — `property_address` also appears on tax bills / binders (the LP-417-review
  field-name-collision lesson, applied preemptively).
- **The AI-tolerant match is a future refinement** (a calibration ticket) — not built here (no fuzzy matcher).
