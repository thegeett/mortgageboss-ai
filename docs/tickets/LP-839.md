- **Ticket:** LP-839 · from processor feedback on the verification tab
- **Status:** Specified — not started

- **Scope:** `components/file/verification/*`, `services/email_draft.py`, `api/verification.py`
- **Migration:** none expected

## 1 — The request works. The sentence about it does not. And VOE is one of sixteen.

**VOE was an example, so the class was measured rather than the instance.** Of the **43** documents
any rule can put behind a Request button, **16 are not the borrower's to send** — 37%:

| document | whose | rules that ask for it |
|---|---|---|
| `credit_report` | lender | CR-1, CR-6, CR-10, CR-12, CR-13 |
| `appraisal` | lender | MI-1, PR-2, PR-3, PR-4 |
| `closing_disclosure` | lender | CL-1, CR-6, CR-13, DT-7 |
| `title_commitment`, `preliminary_title_report` | title | ID-7, TI-1, TI-2, TI-6 |
| `purchase_agreement` | agent | FR-3, PC-2, PC-3, PC-7 |
| `voe` | employer | IN-4, IN-7, IN-8, IN-15 |
| `master_insurance_policy_for_condominium` | insurer | CO-3, IH-7 |
| `aus_findings`, `loan_estimate`, `rate_lock_agreement` | lender | AU-3, IH-2, CL-1 |
| `condo_questionnaire`, `hoa_certification`, `verbal_voe`, `verification_of_rent`, `uniform_residential_loan_application` | processor | CO-1, CO-4, ID-6, IN-7, IN-14, OC-3 |

`add_needs_to_draft` deliberately leaves every one of them out of an email addressed to the borrower
— LP-800's rule. The need is created and is on the needs list; the draft is unchanged, correctly.

**So this is not a VOE bug and not an edge case.** Better than a third of the Request buttons in the
product produce a success toast and no draft change, including the ones a processor reaches most —
the credit report, the appraisal, the title commitment.

**So the defect is the confirmation, and it is mine.** LP-826 built `requestConsequence`, which reads
the server's `document_request` outcome and says *"1 is not the borrower's to send, so it is on the
needs list only"*. It was wired into `findings-list.tsx` — the LEGACY AI-sweep rows — and **not**
into `verification-panel.tsx:457`, which handles the governed §8 rule rows where the Request button
actually lives. Those still show the pre-LP-826 hedge:

> *"On the needs list, and whatever the borrower can send is in the file's email draft."*

True, unfalsifiable, and it reads as "it worked" whether the draft gained a line or not. Found one,
fixed one — the second place is where a processor clicks.

**The bulk route shares that handler**, so "Request all" is telling the same non-answer.

## 2 — The button has no idea a request happened

`rule-finding-actions.tsx:127` gates on `finding.missing_documents.length > 0` and renders
`Request {missing_documents}` — with **no reference to `docs_requested`**, the marker LP-801 writes
onto the finding at request time. So after requesting, the row offers the identical button, and a
processor cannot tell a fresh finding from one they have already acted on.

Under LP-832 a second click is already harmless — `add_needs_to_draft` returns the existing draft and
adds nothing when the need is already carried — but "harmless" is not "visible".

## 3 — Nothing says where the request goes

The whole effect of the button is on another page. A tooltip is the cheapest place to say so.

## 4 — The note is stored and never read

Measured end to end: the textarea's text reaches `create_needs_item(description=note)`, and
**`email_draft.py` never reads `description`** — `_document_line` renders the catalog's guidance or
the need's `title`. So a processor's note is written to a column and reaches nobody.

That is the decision this ticket has to make, not a bug to fix quietly. Two honest answers:

* **the note is for the file, not the borrower** — then the textarea should say so, because
  "Anything to add to the request?" reads as text going into the email;
* **the note is for the borrower** — then it belongs in the draft, and the request says AI compose
  should run when it lands there.

The second is what was asked for and is the larger change: the note has to survive `_regenerate`,
which rewrites the body from the template on every add — the same problem LP-834's link had, with the
same shape of answer.

## 5 — "Request all" fires with no confirmation

It requests every document across a group of findings in one click, and the only thing that follows
is a toast. A confirmation naming what is about to be asked for is cheap, and this is the one action
whose blast radius a processor cannot see beforehand.

## Done when

- The **governed rule rows** report what actually happened, from the server's outcome — including
  "this one is not the borrower's to send". One confirmation shared with the legacy rows, not a
  second copy: two sentences about one event is how they drift apart.
- A finding whose documents have been requested says so, and the action reads **Re-request**.
- A re-request of something already in the latest draft **adds nothing and says it added nothing** —
  the behaviour already holds; this makes it visible.
- The request control carries a tooltip naming where the request goes.
- **The note's destination is decided and the UI says which.** If it reaches the draft, it survives
  regeneration and triggers the compose path; if it does not, the field stops implying it does.
- "Request all" confirms first, naming the documents, with a way out.
- A **non-borrower** request is the fixture in every one of these, not an afterthought: it is the
  case that produced the report, and the one an obvious implementation gets wrong.

## For the reviewer

The trap is fixing the sentence in the second place and leaving the two copies. `requestConsequence`
exists; the governed handler should call it rather than grow its own — and if a third surface ever
requests documents, it should be unable to invent a third sentence.
