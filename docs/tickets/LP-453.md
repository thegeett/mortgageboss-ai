# LP-453 — Step D.2: the tradelines list consumer (observation tags for the credit rules)

## D3 — the value vocabulary (checked FIRST, the LP-448 lesson) — it is OPEN-ENDED

The actual values across LF-96SV's 18 stored rows:

| field | distinct values observed | verdict |
|---|---|---|
| `account_type` | **`AUTO` ×2, `INST` ×7, `REV` ×9** — terse bureau codes | **open-ended** (elsewhere MTG/EDU/COLL/CHG…) |
| `account_status` | `AS AGREED` ×9, `PAID` ×9 — bureau phrasing | open-ended |
| `payment_status` | `I1` ×9, `R1` ×9 — Metro-2 codes | open-ended |
| `is_disputed` | free-text: `"…PREVIOUSLY IN DISPUTE-NOW RESOLVED…"`, **but also `"ACCOUNT IN FORBEARANCE"`, `"CLOSED BY CREDIT GRANTOR"`** | **free-text, includes NON-disputes** |
| `worst_delinquency` | `None` on all 18 | (no delinquencies in this file) |

**So classifying "mortgage / student loan / collection" (CR-8/9/10) or interpreting a dispute (CR-12) is JUDGMENT,
not a lookup** — a Priya/AI question, deferred (ADR-353). Counting non-empty `is_disputed` would OVERCOUNT
(forbearance and closed-by-grantor are not disputes). This is the LP-448 earnings lesson repeating.

## D4 — `payment_history_24mo` is a variable-length string; a position parser is a trap

The real values are `0`/`-` strings of **wildly varying length (16 to 84 chars)** — e.g. `"0000000000000000"`
(16), `"000…000"` (84), `"----"` (4), `"-0-00…000-000"`. The `"24mo"` in the name is misleading — it is the full
available history, variable per row, with `-` = no-data. **This is NOT a fixed position-per-month encoding**, and
it varies by bureau/report. A parser that extracts "recent lates" from one report's format would break on the
next (the ticket's exact warning). CR-8's "recent lates" is therefore **not deterministic here** — deferred.

## D1 — enumerator vs recipe: a RECIPE (the enumerator is deferred with the per-row rules)

| rule | shape it wants | but it needs | so |
|---|---|---|---|
| CR-12, CR-8 | per-row (name the account) | dispute/late CLASSIFICATION (open vocab) | deferred to the rule ticket (needs AI/Priya) |
| CR-10 | count or per-row | collection CLASSIFICATION | deferred |
| CR-1 | aggregate | the tradeline payment TOTAL (numeric) | **served here** |

Because every per-row finding needs an open-vocabulary CLASSIFICATION (judgment), a per-row **enumerator would
emit raw bureau codes the rules can't deterministically act on** — so it is deferred with those rules. The only
thing emittable deterministically is a numeric AGGREGATE → a **derived recipe** (the IN-12 shape), loan-level.

## D2 — the tags (describe, don't judge) — justified against the line

Emitted (pure numeric observations, no classification, no threshold):

| tag | what | why it is an observation, not a conclusion |
|---|---|---|
| `credit.tradeline_count` | how many tradelines the file's report(s) list | a raw count; no open/closed classification |
| `credit.tradeline_monthly_payment_total` | Σ of the rows' `monthly_payment` | a sum of a coerced number; the CR-1 DTI cross-check |

**NOT emitted** (a threshold or a classification = a rule in disguise): `credit.has_unacceptable_lates`,
`credit.is_derogatory`, `credit.collections_exceed_threshold`, `credit.mortgage_late_count_24mo` (needs type
classification + the D4 parser), `credit.disputed_tradeline_count` (needs the D3 free-text interpretation).

## D5 — scope: a SMALL correct set

**This ticket emits the two aggregates above** — the clearest observations with zero classification ambiguity
(the count, and the payment total CR-1 needs). Everything requiring open-vocabulary classification or free-text
interpretation is **deferred to Priya / the rule tickets** (ADR-353). A smaller correct set beats a complete
guessy one — the five-rules-died lesson.

## Assumptions / decisions

- The row vocabulary is open-ended (D3) → only numeric aggregates are deterministic; classification is a Priya
  question (ADR-353), not forced into a recipe.
- Loan-level aggregate (`all_list_rows`), mirroring the income aggregates. **Limitation:** a file with MULTIPLE
  overlapping bureau reports could double-count — reported; multi-report dedup is a reconciliation rule's job
  (LF-96SV has one 18-row report + one empty, so no double-count).
- Fail-closed via the `unknown` abstain sentinel (the derived-recipe convention), never a fabricated 0.

## NEW gaps / what remains

- **The open bureau vocabulary is unresolved** — mortgage/student/collection classification, dispute
  interpretation, and the payment-history format are Priya/AI questions (ADR-353), the input to step E.
- **The per-row enumerator** (for the per-tradeline rules) is deferred with those rules.
- **Multi-report double-count** on a file with overlapping bureau pulls — a reconciliation rule candidate.

Every one still has further gates; this ticket delivers the one deterministic observation (the CR-1 payment
cross-check + a presence count) and names the rest as Priya/AI, honestly, rather than guessing a lookup.
