## PART 1 — AS-6: nothing to build (D1), and two ticket premises corrected

### D1 — the fields were ALREADY visible; a prompt change would DE-CALIBRATE an auto rule

`stmt_facts` (the AI group producing AS-6's three tags) uses `context_builder: document` → `_doc_context`, which
emits EVERY present document field (`subjects.py`):

```python
for name, field in raw.fields.items():
    if isinstance(field, PiiField):
        fields[name] = field.display if field.is_present else None
    elif field.is_present:
        fields[name] = field.value
```

`account_owner_name_2` / `account_owner_count` are plain (non-PII) fields → they flow through verbatim once
populated, with NO code change. And because `_doc_context` OMITS absent fields, a **single-holder statement's
context is byte-identical to pre-LP-446** — so AS-6's 11/11 calibration (it ships AUTO at 0.95) is preserved BY
CONSTRUCTION; only a JOINT account gains the second-holder line. Adding a prompt hint would have been a material
change to an auto-shipping rule → a re-scoring STOP. So **nothing was added** — "nothing to do" is the answer.

### The proof (on the REAL dev-DB documents; `claude-sonnet-4-5`)

- **The extraction gain is real:** the BofA joint savings statements extract `account_owner_count = 2` with the
  second holder populated (`AKASH V PATEL` + `BANSARI N PATEL`).
- **AS-6's FP-safety holds:** every genuine borrower match stays `satisfied` — ZERO false flags (the harm AS-6
  ships auto to avoid). The one non-`satisfied` real statement is an `EMD Withdrawal.pdf` receipt misclassified
  as a `bank_statement` with no extractable holder name → an honest `couldnt_check` (a missing holder name, NOT

## PART 2 — IH-1: the dwelling loss-settlement basis (ADR-340), built + activated

### D3 — the value vocabulary, matched FAIL-CLOSED (the thing most likely to break it)

The field is a **free-form STRING**. Real policies returned `"replacement cost"` AND `"Replacement Cost"` — and
the SAME policy returned different casing across two runs — so an exact `eq` cannot match. A DETERMINISTIC derived
tag `ins.dwelling_settlement_basis` normalises it against an **EXPLICIT allow-list** (casefold + collapse
whitespace, then exact membership — **NOT a fuzzy matcher**):

- replacement-cost family (→ `replacement_cost`, satisfied): `replacement cost`, `replacement cost value`,
  `replacement cost coverage`, `rcv`, `guaranteed replacement cost`, `extended replacement cost`,
  `full replacement cost`.
- actual-cash-value family (→ `actual_cash_value`, fired): `actual cash value`, `acv`.
- **anything else → `unknown` → the gate → `couldnt_check`** (fail closed — a novel carrier phrasing degrades to
  an honest abstention, NEVER a guessed `satisfied`). No fuzzy matcher was built.

### D4 — scope, boundaries, the anti-conflation

- **The anti-conflation is structural (ADR-351).** The recipe reads ONLY the typed dwelling field, NEVER the
  `forms_and_endorsements` list — so an ACV-ROOF or personal-property endorsement (a list row) cannot drive the
  dwelling basis. This is the same protection the Occidental policy tested in LP-446.
- **Priya's OTHER two adequacy conditions** (required hazards covered; deductible within agency limits) are NOT
  IH-1 — recorded as candidates (hazards → IH-6/IH-8/IH-2; the deductible needs a Priya threshold).
- **IH-7 (condo master policy ≥100% replacement cost)** is a different test on a different document — NOT bundled.
  IH-1 needs **no condo exclusion**: it never reads a master policy, and no reliable `property.type` signal exists
  to exclude on anyway (ADR-340).
- **The IH-3 boundary:** both read the binder, but IH-1 judges the settlement BASIS (adequacy) and IH-3 the
  effective DATE (a coverage gap in time). Different load-bearing tags (disjoint), different reasons — asserted.

### D5 — the bar (it ACTIVATES)

Deterministic, no AI tag, no Priya threshold (a boolean basis check) → `no-ai-dependency` → eligible on
`input_resolves` alone → **IH-1 activates (36 → 37)**. Its bar records the regulatory basis (ADR-340, effective
**2026-03-18**) so the ruling the rule's SHAPE rests on can be re-checked.

### A new derived-tag subject: DOCUMENT

IH-1 is PER-DOCUMENT (like AS-6) — which gives Priya's `not_applicable` for free (no binder → no in-scope
subject; DIFFERENT from IH-3's `couldnt_check`-on-missing-binder, deliberately). That needed the normalising tag
on the DOCUMENT subject. The declaration loader restricted derived tags to loan/borrower, but LP-332 had already
generalised the producer to enumerate any subject and key under its `subject_id`; a document recipe reads its OWN
`DocumentEntry` and keys under `content_id` — it does NOT mis-key (verified end-to-end). So `_DERIVED_SUBJECTS`
was widened to add `document` (`transaction` stays unsupported — no recipe reads a `TransactionRecord`).
