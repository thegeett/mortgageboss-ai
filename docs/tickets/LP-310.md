## Phase 0 — Pre-existing `verification_rules` table (STOP-AND-FLAG)

**Bottom line:** there is already a DB-backed rule registry (`verification_rules`
+ `rule_change_audits`) from **LP-118 / ADR-238**, built on a *different* branch
for the *pre-pivot* "code-evaluator" architecture. It overlaps the tag-arch rules
store on identity/gate/params but is shaped for the engine this branch is
replacing. **Do not create a parallel `rules` table until this is resolved.**

### Where it lives (branch vs local DB — they disagree)

- **Source of the table:** commit `95de1a8` — `feat(LP-118): rule registry storage
  — verification_rules + seed + rule_change_audit (hybrid)`.
- **On branch `phase3_5_1`** (local + `origin/phase3_5_1`). **NOT on this branch**
  (`git merge-base --is-ancestor 95de1a8 HEAD` → false). Nothing referencing
  `verification_rules` (the model, migration, `services/rule_registry.py`, or the
  seed) exists on `phase3_new_AI_arch_finding_stage2`.
- **BUT the local dev DB has both tables, populated:** `verification_rules` = **140
  rows**, `rule_change_audits` present. Meanwhile `alembic_version` =
  `c4e9a7f2b8d3` (this branch's LP-209 head, which does **not** include LP-118).
  → The local DB was migrated on `phase3_5_1` (which ran the LP-118 migration),
  then the working tree was switched to this branch. The tables **persisted as
  orphans**: they physically exist and hold data, but this branch's Alembic history
  neither created them nor tracks them. A fresh `alembic upgrade head` on this
  branch would **not** create them; a fresh DB would **not** have them.
- **Alembic fork:** LP-118 (`d4b8f1a63c27`) and this branch's LP-201
  (`a7c2e5f9d1b4`) **both declare `down_revision = e5a9c3f7b2d1`** (LP-114.1). The
  two branches forked at that revision. Merging them later produces **two Alembic
  heads** and will require a merge migration.

### What populated it

The version-controlled seed **`docs/rules/rule_seed.json`** (2528 lines, generated
from the playbook xlsx + live code rules, never hand-typed) via
`services/rule_registry.py::seed_verification_rules(bind)`, called from the LP-118
migration's `upgrade()`. Each insert is recorded in `rule_change_audits` with
`change_source="seed_migration"`. Local-DB tallies: **140 rows, 133 with a
`playbook_id`** (≈ the ~130-rule playbook), **19 `enabled=true`**, **4
`validated=true`**. The 18 live cross-source rules are seeded with real rule_ids
(e.g. `xsrc.asset.gift_without_letter`=AS-5); ~122 not-yet-built playbook rows carry
null `evaluator` + `enabled=false`.

### Overlap analysis vs. the tag-architecture rules store

There are now **three rule representations** across the two branches:

1. **`rule_kinds.csv`** (LP-301, this branch) — routing/classification, 133 rows, file.
2. **`specs/*.yaml` + `load_rule_spec`** (LP-303, this branch) — per-rule prose spec
   (criteria, required_inputs[snapshot_path], subject_enumeration,
   subject_key_fields, reference_values), file.
3. **`verification_rules`** (LP-118, `phase3_5_1`) — DB rule registry, 140 rows.

**Material overlaps** (why this is a stop-and-flag, not a coexist):

- **Identity + playbook + gate + params are duplicated.** Both LP-118 and LP-301/303
  carry rule_id, playbook_id, a Priya `validated`/`priya_validated` gate, and
  threshold params. AS-1 exists in **all three**.
- **Direct contradiction on AS-1's gate.** LP-118 seeds AS-1
  (`xsrc.asset.large_deposit_unsourced`, `params={"large_deposit_pct":50}`) as
  **`validated=TRUE`, `enabled=TRUE`**. LP-303's `specs/AS-1.yaml` sets
  **`priya_validated: false`, `threshold_needs_signoff: true`** and
  `rule_kinds.csv` agrees (false). The two branches disagree on whether AS-1's 50%
  threshold is Priya-signed-off. Whichever store wins must reconcile this.
- **Different rule_id vocabularies.** LP-118 keys by semantic ids
  (`xsrc.asset.large_deposit_unsourced`, playbook_id="AS-1"); LP-303 keys by the
  playbook id itself (`rule_id: AS-1`). A merged store needs ONE id scheme.

**Material divergences** (why it isn't a drop-in reuse either):

- `verification_rules` is shaped for the **pre-pivot code-evaluator engine**: its
  STRUCTURAL columns (`evaluator`, `applicability`, `canonical_type`,
  `message_template`) describe a *code evaluator per rule* — the "130 AI
  rule-evaluators" model this branch is explicitly **replacing** with the fact-tag
  approach. The tag arch's per-rule spec is instead prose `criteria` +
  `required_inputs[snapshot_path]` + `subject_key_fields` (LP-303), none of which
  `verification_rules` has columns for.
- It lives on a branch (`phase3_5_1`) whose downstream work (LP-119 applicability
  filter, LP-120 evaluators, LP-121 runner, LP-122 admin UI) is the evaluator-engine
  build — i.e. the architecture under replacement. **Whether that line of work is
  superseded by this pivot is the crux decision, and it is not mine to make.**

### The decision (reuse / rename / replace / coexist) — options, not a verdict

| Option | What it means | Pros | Cons / risks |
|---|---|---|---|
| **Reuse / extend** | Adopt `verification_rules` as the tag-arch rules store; add tag columns (`criteria`, `required_inputs`/`snapshot_path`, `subject_enumeration`, `subject_key_fields`); drop/ignore the evaluator-shaped columns | One table; audit log + validated gate + params + 130-row seeded playbook already built; `rule_change_audits` gives the append-only log for free | Must port LP-118 onto this branch (rebase + resolve the Alembic fork); dead evaluator columns; must unify rule_id vocab + resolve the AS-1 gate contradiction; imports phase3_5_1 design assumptions |
| **Replace** | Build the tag-arch rules table fresh; retire `verification_rules` + its seed | Clean model fit to the pivot; no dead columns | Discards a built, seeded, audited registry + the 2528-line seed; must drop the orphaned local-DB tables; abandons LP-118..122 work |
| **Coexist** | Two registries — `verification_rules` for any surviving evaluator rules, new table for tag rules | No rework of either branch | Two rule sources of truth = exactly the drift ADR-238 warns against; AS-1 gate contradiction becomes permanent; confusing for findings that reference rule_id |
| **Rename** | Keep both, rename one to avoid table-name collision | Trivial | Solves only the name clash, not the semantic overlap; weakest option |

**Recommendation (for your call, not executed):** the pivot away from
"130 code-evaluators" makes a *pure* reuse awkward — but `verification_rules`'
identity + `validated` gate + `params` + `rule_change_audits` are exactly the bones
the tag-arch store needs, and re-seeding 130 playbook rows is real work already
done. Lean toward **reuse-and-reshape** (extend the table with the tag-spec
columns, deprecate the evaluator-shaped ones) **only if** the team confirms
`phase3_5_1`'s evaluator-engine line is being folded into the tag arch rather than
run in parallel. If `phase3_5_1` is being abandoned wholesale, **replace**. Either
way, first resolve: (a) the Alembic fork, (b) the orphaned local-DB tables, (c) the
one rule_id vocabulary, (d) the AS-1 `validated` contradiction. **Blocking question
for the team before any tag-storage ticket starts.**

## Summary (the shape of what the tag layer builds on)

1. **Biggest reuse win — the calculator breakdown shape already exists.** The
   snapshot's `CalculationEntry {value, breakdown:[CalcBreakdownLine{key,label,
   amount,source,overridden}]}` (`snapshot/model.py:227-256`) is 90% of the
   `{value, breakdown[{label,value,source,from_tag}]}` the tag layer wants. Only
   `from_tag` is missing, and `source` is already a per-line lineage tag
   (`stated/computed/extracted/manual/override`).
2. **Biggest reuse win #2 — the AI-call + cross-source clone target is intact.**
   `complete()` still raises `AIClientError`, still has no timeout
   (`ai/client.py:183-213`); the two-file cross-source pattern (deterministic
   assembly, injected `Reasoner` seam, truncation guard, cost/fingerprint) is all
   present and is the right thing to clone for tag production.
3. **Biggest reuse win #3 — a persisted `Finding` model already exists** with a
   lifecycle enum, origin/provenance marker, identity+reconcile machinery, and
   migrations (`models/finding.py:116`). The finding work extends it, does not
   start from zero.
4. **Biggest build-new gap #1 (LOAD-BEARING) — there are NO stable content-ids on
   raw facts.** Transactions and documents are addressable *only by array
   position* or free-string dict key (`snapshot/model.py:118-171`). A tag that
   cites `source_facts` has nothing stable to anchor to today. This is the single
   gap the tag-model ticket MUST close first.
5. **Biggest build-new gap #2 — the four finding states don't exist as states.**
   `open` exists; `satisfied` / `no-longer-applies` / `couldnt-check` are today
   expressed as human resolutions, soft-delete, or a runtime `evaluated=False`
   with no persisted record (`models/finding.py:85-90`, `finding_reconcile.py:91`,
   `engine.py:38`). No append-only per-finding event log; no `subject_key` column;
   no `(loan_file, rule, subject)` uniqueness constraint.
6. **Surprise / correction #1 — there is no `cash-to-close` or standalone
   `CLTV/HCLTV` calculator.** The real set is 6 pure calculators (DTI, LTV [which
   emits CLTV/HCLTV as extra ratios], MI, reserves, max_loan, self_employed) — but
   **only 4 feed the snapshot** (DTI/LTV/MI/reserves). `max_loan` and
   `self_employed` are API-only.
7. **Surprise / correction #2 — the pure `verification/*.py` calculators carry NO
   source tags at all.** The `source` lineage lives one layer up, in the
   service/schema wrappers (`schemas/dti.py:25`, `schemas/calculators.py:28`), and
   only reaches the snapshot because `calculations_section.py` maps the *wrappers*,
   never the pure calculators. The tag layer must wrap at the snapshot/service
   layer, not the arithmetic layer.
8. **Contradicts the design docs — both known AS-1 bugs are still committed.** The
   `direction=="credit"` candidate filter (`AS-1.yaml:51`) and
   `subject_key_fields:[account, date, amount]` (`AS-1.yaml:91`) are unchanged,
   even though LP-302a removed `account` from `TransactionRecord`. The spec
   references a field that no longer exists on the fact it enumerates.
9. **Documentation gap.** The ticket cites `verification-architecture-v2.docx §3D`
   and `docs/snapshot-fact-tags.*`. **Neither exists.** The committed docx has
   sections 3A/3B/3C and stops there (its Stage-1/2 snapshot + lifecycle design is
   sections 3B, 8, 9); there is no §3D and no `snapshot-fact-tags` file in the
   repo. The reconcile below is against the committed v2 doc + the ticket's own
   description of the tag architecture. **This is itself a finding: the tag-layer
   tickets have no committed design spec to build to yet.**

## Per-area findings

### Area 1 — Rule spec + kinds infrastructure (LP-301, LP-303)

**Verdict: REUSE (loaders + CSV gate) / EXTEND (add DB projection later).**

- **`load_rule_spec`** — `verification/rules/specs.py:190-198`, `@cache`,
  `load_rule_spec(rule_id: str) -> RuleSpec`; delegates to `_load_spec_from`
  (`specs.py:154-187`). Specs live at `verification/rules/specs/<rule_id>.yaml`
  (`specs.py:36-37`), loaded with `yaml.safe_load`. Filename must equal the spec's
  own `rule_id` or it raises `RuleSpecInvalid` (`specs.py:178-179`).
- **`RuleSpec`** is a frozen Pydantic `BaseModel`, `extra="forbid"`
  (`specs.py:99-121`). Fields: `rule_id, name, category, kind (RuleKindName enum),
  numeric_check, criteria, applicability{scope,trigger}, required_inputs[]{name,
  snapshot_path,description}, reference_values{large_deposit_threshold,
  priya_validated, threshold_needs_signoff}, subject_enumeration,
  subject_key_fields[], evidence_required, guideline_reference, spec_version`.
  On load, `_check_consistency` (`specs.py:124-151`) asserts the spec's
  `kind/numeric_check/priya_validated/threshold_needs_signoff` match the
  `rule_kinds.csv` row — the CSV is the single gate of record.
- **`rule_kinds.csv`** header (`rule_kinds.csv:1`): `rule_id,name,category,kind,
  evaluation_path,numeric_check,exact_match,priya_validated,
  threshold_needs_signoff,rationale`. 133 data rows. Loader
  `load_rule_kinds()` (`kinds.py:162-204`, `@lru_cache`, returns read-only
  `MappingProxyType`), `csv.DictReader`, header validated against `_COLUMNS`
  (`kinds.py:43-54`), fail-loud. **Bools are strict**: `_to_bool`
  (`kinds.py:93-103`) accepts only `"true"`/`"false"`; `exact_match` is optional
  (`_to_opt_bool`, empty→`None`, `kinds.py:106-110`). Per-rule `RuleKind`
  dataclass (`kinds.py:77-90`): `kind, numeric_check, exact_match:bool|None,
  priya_validated, threshold_needs_signoff`.
- **Files vs DB:** pure static-file reads today, **no DB backing** (grep for
  SQLAlchemy models referencing specs/kinds is empty). Swappability is documented
  as intended-but-unbuilt: `specs.py:16-19` docstring — "a DB-backed source later
  is a drop-in"; LP-303.md:102 lists a DB spec store as out of scope.
- **Gotcha:** the loader `@cache`/`@lru_cache` means specs are read once per
  process — a files→DB projection must preserve read-once semantics or the cache
  will mask DB updates.

**AS-1 spec status (verbatim, both bugs still present):**
- (a) `direction=="credit"` filter — **STILL COMMITTED**, `AS-1.yaml:51`:
  `snapshot_path: 'documents.entries[document_type=="bank_statement"].transactions[direction=="credit"]'`
- (b) `account` in the subject key — **STILL COMMITTED**, `AS-1.yaml:91`:
  `subject_key_fields: [account, date, amount]` (with `subject_enumeration:
  per_deposit`, `AS-1.yaml:90`).
- LP-303.md:57-68 *acknowledges* the contradiction and claims `account` "resolves
  from the parent entry," and comments at `AS-1.yaml:86-89` describe that intent —
  but the field list itself was never changed. **The spec still enumerates
  deposits by a field (`account`) that LP-302a deliberately removed from
  `TransactionRecord`.** The tag layer / evaluator ticket must resolve this: either
  drop `account` from the key, or surface the parent statement's masked account as
  a stable, resolvable attribute (see Stable-id verdict).

### Area 2 — Snapshot model after LP-302a (the raw layer the tags sit on)

**Verdict: REUSE (snapshot shape) / BUILD-NEW (stable ids — see dedicated
verdict below).**

- **Top-level `Snapshot`** (`snapshot/model.py:327-346`): `loan_file_id, run_id,
  created_at, snapshot_version, mismo (MismoSection), documents (DocumentsSection),
  calculations (CalculationsSection)`. The three sections are deliberately
  un-linkable — no cross-section correlation by design (`model.py:15-28`).
- **`DocumentEntry`** (`model.py:150-171`): `document_type: str|None`,
  `belongs_to: tuple[BorrowerRef,...]|None`, `fields: dict[str, Field|PiiField]`,
  `transactions: tuple[TransactionRecord,...]|None` (None=absent, ()=present-empty
  — the LP-302a addition).
- **`TransactionRecord`** (`model.py:118-147`) — exactly **four** `Field`s, **no
  account**: `date` (extracted), `amount` (extracted), `direction` (DERIVED —
  credit/debit computed from `transaction_type`, absent when unclassifiable, never
  fabricated; `documents_section.py:287`), `description` (extracted, SSN/9+-digit
  redacted). **NB:** the LP-302a.md acceptance checklist (lines 16-20) still
  describes a 5-field record with `account: PiiField` — that was *reversed* by the
  review follow-up (LP-302a.md:129-144); the code is the 4-field version.
- **Account representation:** the masked account lives **once** on the parent
  `DocumentEntry.fields["account_number_masked"]` as a `PiiField`
  (`documents_section.py:142`), **not** per-transaction
  (`documents_section.py:277-278`). That `PiiField` is pre-masked with
  `match_hash=None` and is **non-matchable**: `PiiField.pre_masked(...)` sets
  `match_hash=None` (`pii.py:233`); `is_matchable` = `match_hash is not None`
  (`pii.py:246-253`); `matches()` returns True only if both sides carry the same
  real hash — two `None` hashes never match (`pii.py:255-269`). **Confirmed as
  the ticket describes.**
- **`snapshot_version = 2`** (`model.py:50`); a mismatched version is hard-rejected
  (`model.py:356-369`). Build: `async build_snapshot(db, *, loan_file_id, run_id,
  company_id) -> Snapshot` (`builder.py:114-116`), stateless, company-scoped, each
  section in its own SAVEPOINT (failure → absent-with-reason). Load:
  `async load_snapshot(db, run_id) -> Snapshot | None` (`persistence.py:93-98`),
  `Snapshot.model_validate` of stored `snapshot_json`; persist guards against raw
  PII at rest (`persistence.py:54-61`).
- **LF-6T3N:** surfaces transactions but there is **no committed persisted snapshot
  row and no deterministic fixture asserting the count**. LP-302a.md:36,81-83
  reports 5 bank statements → **50 transactions** (hand-verified via smoke script,
  not a checked-in assertion). `test_transactions.py` uses tiny synthetic 2/3-txn
  fixtures (`test_transactions.py:53,78`), not the 50. So: yes transactions
  surface, count is documented-not-tested.
- **Field shape** matches the v2 doc's intent (§3B): every `Field` carries
  `value/confidence/source` (`source ∈ parsed|extracted|derived`;
  `fields.py:44-59`), `PiiField` carries `display/match_hash/confidence/source`
  (`pii.py:153-171`).
- **Gotcha:** `direction` can legitimately be *absent* (unclassifiable
  transactions produce no direction). The AS-1 `direction=="credit"` filter
  (Area 1) therefore silently drops any deposit whose direction couldn't be
  derived — a correctness risk the tag/evaluator ticket must handle.

### Area 3 — The calculators

**Verdict: EXTEND (wrap the snapshot-layer breakdown; add `from_tag`).**

The confirmed set is **6 pure calculators** in `verification/*.py`, of which **only
4 feed the snapshot** (`calculations_section.py` maps DTI/LTV/MI/reserves;
`calculations_section.py:1,154-157`). See the dedicated calculator table below.
Key architectural fact: the pure calculators return **scalar dataclasses with no
lineage** — MI and reserves have no line-item list at all; DTI/LTV/max_loan/
self_employed have line structs but **no `source` field**. The per-line `source`

extracted / manual / override`). `calculations_section._line()`
(`calculations_section.py:64-70`) copies `item.source` **verbatim** into
`CalcBreakdownLine.source` ("never re-derived").

- **Gotcha #1:** wrap at the snapshot/service layer, NOT the pure arithmetic layer
  — the pure layer has no tags to carry.
- **Gotcha #2:** `CalcBreakdownLine` (`model.py:227-242`) is exactly
  `{key,label,amount,source,overridden}`. **No `from_tag` today** — adding it is a
  model change (snapshot_version bump territory).
- **Gotcha #3:** `source` is a free string (`model.py:230-233`) with a 5-value
  de-facto vocabulary. If tags need a closed enum, that's a tightening, not a
  reuse.

### Area 6 — Storage conventions (files → DB rules/tags projection)

**Verdict: REUSE (base/mixins/alembic conventions).** A rules/tags table would be
the *first* production static-file→DB loader.

- **Base/mixins** (`models/base.py`): single `Base(DeclarativeBase)` with a
  `NAMING_CONVENTION` metadata (`base.py:15-32`). Opt-in mixins via multiple
  inheritance: `UUIDMixin` (`base.py:82-92`, `id = mapped_column(primary_key,
  default=uuid4)` — **Python-side** default, renders `sa.Uuid()`),
  `TimestampMixin` (`base.py:40-58`, tz-aware, Python `default=utcnow`),
  `SoftDeleteMixin` (`base.py:61-79`, explicit filtering via
  `helpers.only_active`). Append-only tables omit timestamps/soft-delete
  deliberately (e.g. `snapshot_records`).
- **JSONB vs JSON:** `JSONB` (pg dialect) for queryable blobs
  (`snapshot_record.py:27,57`); plain `JSON` + `default=dict/list` for opaque
  config bags (`lender.py:72-73`). Use `JSONB` for structured rule/tag payloads.
- **Alembic** (`alembic/env.py`): `target_metadata = Base.metadata` (`:32`),
  async, `compare_type`/`compare_server_default` on (`:44-45,56-57`). Versions
  named `YYYYMMDD_HHMM_<rev>_<slug>.py`, explicit `op.create_table` (not
  reflected), `# pragma: allowlist secret` on revision ids. Extensions enabled in
  the first migration. **A new model must be imported in `models/__init__.py`** or
  autogenerate won't see it.
- **Reference-data pattern:** **none exists as a DB table** — rules are pure
  file reads (`rule_kinds.csv` + `specs/*.yaml`), which is exactly what a
  projection would change. The only "seed to DB" mechanism is the **dev-only,
  prod-guarded** `scripts/seed_dev_data.py` (companies/users/lenders/loan files) —
  not a production reference loader. `load_rule_spec` is already documented as a
  DB drop-in (`specs.py:17-19`).
- **Multi-tenancy:** two patterns. Direct `company_id` FK (indexed, per-company
  composite unique) for tenant-owned top-level entities (`lender.py:52-58`,
  `validation_verdict.py:51-57`); transitive scoping through `loan_file` for
  file-owned children (ADR-052/053; `finding.py:16`, etc.). Enforcement via
  `helpers.scope_to_company` (`helpers.py:58-78`). **Decision for rules/tags:**
  canonical rule reference data → **global, un-scoped** (like the CSV, no
  `company_id`); per-tenant tag/override data → direct-`company_id` pattern (like
  `ValidationVerdict`, which already scopes per-company decisions *about* rules).

## Stable-id verdict (load-bearing — from Area 2)

**Tags CANNOT cite raw facts by a stable content-id today. This is a gap the
tag-model ticket MUST close before Stage A/B production can safely emit
`source_facts`.**

- The complete set of id/UUID fields in `snapshot/model.py` is: `borrower_id`
  (on `BorrowerRef`, `:72`), `loan_file_id` and `run_id` (on `Snapshot`,
  `:339-340`). That is all.
- `TransactionRecord` (`:118-147`) has **no** `id/uuid/txn_id/fact_id/hash` — a
  transaction is identified only by its index in the `DocumentEntry.transactions`
  tuple.
- `DocumentEntry` (`:150-171`) has **no** document-level id — a document is
  identified only by its index in `DocumentsSection.entries`.
- `mismo.facts` / `DocumentEntry.fields` cells are keyed by free strings (e.g.
  `borrower.1.income.base_monthly`); individual `Field`/`PiiField` cells carry no
  id. `PiiField.match_hash` is a value-equality correlation key, **not** a stable
  per-fact identity, and it's `None` for pre-masked accounts anyway.

**Consequence:** any tag `source_facts` reference is positional
(`documents.entries[i].transactions[j]`) or dict-key based, and is invalidated if
extraction order or the entry list shifts on a re-run. Since the snapshot is
rebuilt from scratch each run, positional references are **not run-stable** — which
directly undermines subject_key stability for findings (Area 4). **The tag-model
ticket must add stable, run-independent content-ids to `TransactionRecord`,
`DocumentEntry`, and (ideally) field cells — a `snapshot_version` bump.** This is
a decision-to-be-made in that ticket (see ADR note), not decided here.

## Recommendations for the upcoming tickets

- **Tag storage (files → DB rules/tags):** follow `Lender`/`ValidationVerdict` for
  a per-company tag/override table (direct `company_id` FK, indexed, per-company
  composite unique, `scope_to_company` on all reads) OR keep canonical rule
  reference data **global/un-scoped** mirroring `rule_kinds.csv`. Use `JSONB` for
  structured payloads, a Python `uuid4` pk, the standard mixins, and register the
  model in `models/__init__.py`. Keep `load_rule_spec` as the swap seam
  (`specs.py:17-19`) — implement the DB read behind that signature and preserve
  read-once cache semantics.
- **Tag model:** **must add stable content-ids** to `TransactionRecord` and
  `DocumentEntry` (and ideally field cells) so tags can cite `source_facts`
  run-stably; this is a `snapshot_version` bump (2 → 3) and the load-bearing
  prerequisite for everything downstream. Add the `from_tag` field to
  `CalcBreakdownLine` here or in the calculator-tag ticket.
- **Stage A/B tag production:** clone the cross-source two-file pattern
  (`ai/cross_source.py` + `services/cross_source.py`) verbatim — deterministic
  context assembly, injected `Reasoner` seam, truncation guard,
  cost/`input_fingerprint`. Reuse `extract_json_object` (`ai/parsing.py:15`) and
  model the array parser on `_load_findings_list` (`ai/cross_source.py:208`). Give
  `complete()` a timeout if the tag pass is latency-sensitive (it has none today).
- **Rule engine (calculator-as-tag):** wrap at the **snapshot/service layer**
  (`calculations_section.py` + `schemas/*`), never the pure `verification/*.py`
  calculators. The `{value, breakdown[{label,value,source}]}` shape already exists;
  add `from_tag`. Remember only 4 of 6 calculators are in the snapshot — decide
  whether max_loan/self_employed need tagging too.
- **Findings (four-state + provenance):** extend the persisted `Finding`
  (`models/finding.py:116`) — do NOT create a parallel table. Reuse `FindingOrigin`
  for provenance and `finding_identity()`/`reconcile_findings()` as the substrate.
  Build: (a) the four lifecycle states as a new/extended enum (migration widening
  the CHECK, pattern at the LP-75 migration), (b) `subject_key` as a first-class
  column (today only in `details` JSON), (c) a `(loan_file, rule, subject)`
  uniqueness constraint, (d) an append-only per-finding event log (none exists;
  `ActivityLog` is per-file). Derive `subject_key` from **stable** tag values — but
  note this depends on the stable-id gap being closed first.

## Open questions / risks

1. **No committed tag design spec.** `verification-architecture-v2.docx §3D` and
   `docs/snapshot-fact-tags.*` do not exist in the repo (the docx has 3A/3B/3C
   only). The tag-layer tickets are building to a design that isn't written down
   yet — commit the tag vocabulary + §3D before/with the tag-model ticket.
2. **Stable-id closure is a prerequisite, not a nice-to-have.** Until
   `TransactionRecord`/`DocumentEntry` carry run-stable ids, `source_facts`
   citations and subject_key stability are both unsound. Sequencing risk if a
   Stage-A/B ticket lands before the tag-model ticket.
3. **AS-1's `account` subject key vs the fact model.** The committed spec
   enumerates deposits by `account`, which no longer exists on the transaction.
   Either the masked account must be resolvable as a stable per-transaction
   attribute (it currently lives once on the parent entry, non-matchable), or the
   subject key must change. This blocks a correct per-deposit subject_key.
4. **`direction` absence.** The AS-1 `direction=="credit"` filter drops
   unclassifiable deposits. Confirm with the domain expert whether a missing
   direction should be treated as a candidate (fail-open) or excluded.
5. **`match_hash=None` on accounts contradicts the v2 doc's matching story.** §3B
   describes PII carrying a `match_hash` so rules can prove "this deposit cleared
   the listed account." LP-302a made the account non-matchable (mask-only source).
   If any tag/rule needs account-to-asset matching, that capability does not exist
   for statement accounts today.
6. **Snapshot version churn.** Adding stable ids and `from_tag` both bump
   `snapshot_version`; coordinate so the schema moves once (2 → 3), not twice.
7. **Reconcile-model tension.** The four-state + append-only-log design partially
   reverses the current mutate-in-place/soft-delete reconcile
   (`finding_reconcile.py:8-10`). The findings ticket must explicitly reconcile the
   two, not layer on top.
