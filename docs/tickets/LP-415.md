# LP-415 — The five-gate audit of Bucket 3 (Title, Insurance, Condo, Program, MI) — READ-ONLY

## What this ticket is

§13 sizes Bucket 3's ~23–28 rules as a fast "deterministic wave." Every prior census over-counted: LP-405
asked ONE gate → over-counted 10×; LP-407-1 asked FOUR → over-counted 2×; the vacuity check (ADR-330) then
killed two more (DT-5, DT-2). This audits all **28 in-scope candidates** against **all five gates** — vacuity
first — so the downstream work is planned on facts. **No file was changed except this report.**

**Headline (three findings):**
1. **The true `write-now` count is 0.** Not a single Bucket 3 rule has both operands produced today.
2. **The self-source vacuity pattern is SYSTEMIC — now 4 confirmed instances** (DT-5, DT-2, **IH-4**, **CO-2**).
   IH-4 and CO-2 are each explicitly flagged in `rule_kinds.csv` as duplicating the two already-killed rules,
   and each compares an extracted figure to itself. This is the most important finding: the spec set
   repeatedly assumes a "stated / used in the calculation" figure the system does not independently carry.
3. **Bucket 3 is mostly Bucket 4 in disguise.** ~17 of 28 are blocked on an **absent extractor** (title, flood,
   condo questionnaire, MI certificate, appraisal — all Tier-2, none extracted). Only **Insurance** is partially
   reachable, via a derived-producer wave off the already-extracted `homeowners_insurance` binder.

**The five gates, in order:** (0) **vacuity** — are the two operands INDEPENDENT? (1) **inputs available** —
extractor running? typed-core vs catch-all? (2) **check expressible** — relation class (all-equal / presence /
enum / value-vs-threshold native; ordered-pairwise / set-coverage / date-vs-today need a producer); (3) **AI
measured** — a bar; (4) **Priya threshold**. Gate 0 kills fastest and is checked first (ADR-330).

## Phase 2 — the roll-up

### The true `write-now` count: **0** (§13 said ~28)

**Not one Bucket 3 rule has both operands produced today.** The only Bucket-3-relevant produced tags are
`program.type` (an applicability gate) and the `housing.*` monthlies (whose only Bucket-3 consumers, IH-4 /
CO-2, are vacuous). Every real rule needs a producer, an extractor, a definition, or calibration first.

### THE VACUITY COUNT — 2 here, **4 total → the pattern is SYSTEMIC**

| instance | rule | both operands trace to | status |
|----------|------|------------------------|--------|
| 1 | **DT-5** (LP-407-2) | binder `annual_premium` | killed |
| 2 | **DT-2** (LP-407-3) | `hoa_statement.dues_amount` | killed |
| 3 | **IH-4** (here) | binder `annual_premium` — `rule_kinds` literally says "(dup DT-5)" | **do not write** |
| 4 | **CO-2** (here) | `hoa_statement.dues_amount` — `rule_kinds` says "(overlaps DT-2)" | **do not write** |

Four instances confirm the systemic cause named in ADR-330: **the spec set repeatedly assumes a "stated / used
in the calculation" figure that the system does not carry independently of the source document.** The DTI
auto-derives its insurance and HOA lines from the very binder/statement the rule would "check them against," so
the compare is a value against itself. **Every remaining "X used vs the document" spec is a vacuity suspect** —
MI-2 and MI-5 looked like it but are NOT (the MI factor/structure is a starter rate / pricing, independent of
the absent certificate — they are needs-extractor, not vacuous). The distinguishing test: *does the "used"
value trace to the SAME extracted field as the "document" value?* (IH-4/CO-2: yes → vacuous. MI-2/MI-5: no →
blocked on the cert.)

## What this changes about §13

- **"Bucket 3 ≈ ~28 deterministic-wave rules" is wrong.** It is **0 write-now**, **2 vacuous** (IH-4, CO-2),
  **~17 blocked on an absent extractor** (title, flood, condo questionnaire, MI cert, appraisal — Bucket 4),
  **~4 needs-derived-producer** (IH-1, IH-3, MI-1/4, PE-1 — off already-extracted docs / the MI calc), **2
  needs-extractor-extension** (IH-2, IH-8), and the rest gated on Priya definitions + calibration rounds.
- **Bucket 3 is mostly Bucket 4.** The "fast deterministic wave" framing held only for the ONE already-extracted
  binder slice (Insurance), and even there IH-4 is vacuous and IH-2/IH-8 are catch-all.
- **The systemic vacuity finding (4 instances) should reshape the spec set**, not just Bucket 3: any rule phrased
  "X used in the calculation vs X from the document" must be vacuity-traced before it is scheduled — the DTI/MI
  calculators derive their lines from the same documents, so a naive "used-vs-document" check is a value against
  itself. This is the census lesson, sharpened: gate 1 ("inputs produced") over-counts; gate 0 ("operands
  independent") is what separates a real rule from permanent-satisfied noise.
- **The genuinely cheap next step is small and specific:** the `homeowners_insurance` derived-producer wave
  (`ins.effective_date` → IH-3, then `ins.dwelling_coverage` → IH-1) + surfacing the MI calculator (MI-1/4).
  Everything else waits on an extractor, a Priya value, or a labeling round — none of which is "deterministic
  wiring."
