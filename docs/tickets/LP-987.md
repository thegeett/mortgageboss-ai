- **Ticket:** LP-987, the seventh of the step-1 tickets in `loan-email.md` §15.
- **Status:** applied to staging (account `058190633983`, us-east-1) on 2026-10-20 (US Eastern). The
  subscription is confirmed, and a test alarm's ALARM and OK emails both arrived.

## What and why

When email health goes wrong, an email now goes to **contact@mortgageboss.ai**, through one SNS topic,
`mbai-staging-ops-alerts`. The topic is general-purpose; other alarms can use it later.

| Alarm | Watches | Fires when |
|---|---|---|
| `mbai-staging-ses-bounce-rate` | `AWS/SES` `Reputation.BounceRate`, hourly maximum | above 2.5% |
| `mbai-staging-ses-complaint-rate` | `AWS/SES` `Reputation.ComplaintRate`, hourly maximum | above 0.05% |
| `mbai-staging-outbound-mail-events-dlq-not-empty` | messages in the delivery-events dead-letter queue, 5-minute maximum | any message |
| `mbai-staging-inbound-mail-dlq-not-empty` (when receiving is on) | the inbound mail DLQ | any message |
| `mbai-staging-scan-results-dlq-not-empty` (when the scan is on) | the GuardDuty scan-results DLQ | any message |

**Why half of AWS's levels.** AWS puts an account under review at a 5% bounce rate or a 0.1% complaint
rate, and can pause sending at 10% or 0.5% ("Amazon SES Sending review process FAQs"). Alarming at
half of the review level gives time to act before AWS does.

The metrics are fractions, not percentages: 0.05 means 5% ("Creating reputation monitoring alarms using
CloudWatch"). So the thresholds are `0.025` and `0.0005`. They are account-level metrics with no
dimensions.

Every alarm also emails when it returns to OK (`ok_actions`), and treats missing data as not breaching.
Hours with no sending therefore do not alarm.

## Decisions

- **The ops topic is not KMS-encrypted.** CloudWatch publishing to an encrypted topic would need
  another key grant, and an alarm message holds no customer data: only the alarm's name, state and
  reason. The reason is written as a comment on the topic.
- **`count` uses a bool (`alarms_enabled`), not the topic ARN.** The brief first gated each alarm on
  `alarm_topic_arn == ""`. The plan failed with `Invalid count argument` (exit 1) on all three outbound
  alarms, and on all five in the receiving-on preview. The topic is created in the same apply, so its
  ARN is unknown at plan time, and Terraform cannot work out how many alarms to create from a value it
  does not have yet. With a separate bool:
  - the count is known at plan time;
  - the modules still receive the real `aws_sns_topic.ops_alerts.arn`, so Terraform sees that each
    alarm depends on the topic and always creates the topic first.

  The alternative, building the ARN from names as `sns_topic_arns` does, was rejected at the checkpoint.
  It would have hidden that ordering in a string. The `alarms_enabled` description records why.
- Each alarm lives in the module that owns the thing it watches, so a module without its queue never
  has a stray alarm.

## What to do when an alarm fires

**Bounce rate.** Too many sends are going to addresses that do not exist.

1. Look at recent sends and bounces. The delivery-events queue carries each bounce, and the SES
   console's reputation page shows the trend.
2. Find whether one tenant or one loan file's addresses are the cause.
3. If one tenant is, stop sending for that tenant until the addresses are fixed.

The account suppression list (LP-984) already stops repeat sends to addresses that hard-bounced.

**Complaint rate.** Recipients are marking our email as spam. Look at recent sends for the same
pattern: which tenant, which kind of message. Stop the tenant causing it, then find out why the
recipient did not expect the email.

**Any DLQ alarm** (delivery events, inbound mail, scan results). A message failed processing three
times (events) or five times (inbound) and was set aside.

1. Read it with `aws sqs receive-message` on the DLQ.
2. Fix the cause in the worker.
3. Then either redrive it to the main queue (`aws sqs start-message-move-task --source-arn <DLQ arn>`)
   or delete it if it is not worth reprocessing.

The alarm clears by itself once the DLQ is empty.
