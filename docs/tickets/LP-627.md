# LP-627 — lifting the load-bearing facts out of catch_all

## Why

LP-624's guard inventoried **41 load-bearing MISMO leaves sitting unreachable in `catch_all`** —
facts the export states that the rule engine cannot read, because the typed schema never lifted them
and the snapshot reads only typed sections. Nine had a named consumer that was abstaining, or deriving
what the file says outright.

This lifts seven of them. The rest stay pinned in the guard's baseline as recorded debt.

## The one with a dollar consequence

**The application states the property tax.** MISMO carries `HOUSING_EXPENSES` under the LOAN — the
proposed PITI breakdown:

| Type | Monthly |
|---|---|
| FirstMortgagePrincipalAndInterest | $4,347.79 |
| HomeownersInsurance | $100.00 |
| **RealEstateTax** | **$541.67** |

LF-ABRS's DTI card reads *"Property taxes / unknown — missing or unusable input (fail-closed, never
assumed $0)"*. The figure has been in the file all along. That ratio sits at **44.8% against a 45%
limit**, so the gap between a stated figure and an unusable one is the loan.

**STATED, NOT VERIFIED — and the gate is right.** `_extracted_monthly` reads the tax BILL on purpose;
an application's own figure is not verification and must not set a DTI. So this feeds
`_unverified_housing_inputs`, the structure bug-001 built to say what the file contains without
ungating anything. The card now offers **two** named sources where both exist — the AVM estimate
($5,579/yr) and the application ($6,500/yr) — because on this file they disagree, and a processor
choosing between two named figures is better served than one handed a single number with the other
hidden.

`timing` is kept, not filtered: "Proposed" is this loan's payment and "Present" is what the borrower
pays today — which is precisely the input a non-occupant borrower's ratio needs and currently has
nowhere to come from (LP-621).

## The other six

| Field | Lifted to | Consumer |
|---|---|---|
| `LiabilityPaymentIncludesTaxesInsuranceIndicator` | `stated_liabilities` | DT-6 asks exactly this |
| `TotalMortgagedPropertiesCount` | `loan_files` | LP-597 DERIVES it from the REO schedule |
| `CurrentRateSetDate` | `loan_files` | CL-1, which is waiting on a rate lock |
| `SellerPaidClosingCostsAmount` | `loan_files` | FR-3 (interested-party contributions) |
| `PropertyMixedUsageIndicator` | `properties` | PR-3 (programme-specific eligibility) |
| `SpecialBorrowerSellerRelationshipIndicator` | **borrower declarations** | the FR family |

**DT-6's is the sharpest.** It compares a mortgage statement's billed payment against the
application's stated payment. Whether the two are the same KIND of figure decides whether the
comparison means anything — a P&I-only stated payment and a servicer's PITIA differ by the escrow and
are not a discrepancy. On LF-ABRS the mortgage liability states **$5,703 with the indicator FALSE**:
the application says that figure is P&I only. DT-6 had one side of its own comparison.

## A mis-placement the guard caught

I first read `SpecialBorrowerSellerRelationshipIndicator` as loan-level and added a `loan_files`
column. It is not:

```
BORROWER/DECLARATION/DECLARATION_DETAIL/EXTENSION/OTHER/ULAD:DECLARATION_DETAIL_EXTENSION
```

A **per-borrower** declaration, in the `ULAD:` namespace, three levels below where the parser read
declarations — it iterated DIRECT CHILDREN of `DECLARATION_DETAIL`, so every ULAD-extension
declaration was skipped, not just this one. The loop now walks descendants and the borrower's
declaration count on the fixture goes from a subset to 18. The loan-level column was removed; a
borrower-level fact on a loan-level column would have been wrong on any two-borrower file.

## Tri-state throughout

Every field is nullable and None means "the export did not state it" — never 0 and never False.
Reading an absent indicator as False asserts a fact the file does not contain, which is the
fail-closed discipline LP-375 settled for the housing inputs.

## Backfill

`scripts/backfill_stated_housing_expenses.py`, report-only by default. Import is one-shot, so the six
files already on staging have no rows and their DTI cards keep saying the tax is missing until it runs.
Skips a file that already has rows — a partial breakdown is worse than none, because a card showing
taxes but not insurance reads as complete.

## The backlog

34 load-bearing shapes remain stranded, still pinned as an equality so a new one fails immediately and
a lifted one fails until removed. The nine QM/ATR loan features (`BalloonIndicator`,
`InterestOnlyIndicator`, `PrepaymentPenaltyIndicator`, …) are deliberately NOT lifted: no rule reads
them today, and adding columns for data nothing consumes is the opposite of this ticket's point. They
belong with whoever builds the ability-to-repay checks.
