# LP-379-D — DB-sourced calibration worksheet so real-file labels are scorable

## What this ticket is

The premise: Priya labeled the REAL DB file (Akash Patel, real BofA statements) while the harness scores the
de-identified FIXTURE (Jordan/Taylor); they share no `subject_id`s, so her 52 labels can't be scored. **The
gate of record refuted this** — her labels already join to the fixture she labeled. So this ticket (a) reports
that + **scores her stable-vocabulary labels now**, and (b) adds a **separate, deliberate DB-sourced worksheet
path** (PII-contained) for a future round that labels the real *documents*, without touching the fixture path.

## Acceptance criteria

- The fixture path (`worksheet.py`) is untouched and byte-identical for CI.
- A DB-sourced worksheet path exists, reusing `build_snapshot`, **never committed** (guarded, gitignored),
  never the CI/default path.
- Priya's labels join by an exact key; an unjoinable row is dropped + reported, never mis-scored.
- The stable tags are scored now; `apparent_category` / `has_identified_source` are **explicitly** held.
- `ACTIVE_RULE_IDS` unchanged; full suite green.

## Phase 0 — the argument (the premise refuted)

**Tested empirically: all 122 of Priya's filled goldens join to the fixture worksheet 100% (0 unjoined)** by
`(tag_id, subject_id)`. She labeled the **committed fixture worksheet** (`docs/calibration/*.csv`) — her
subject_ids **are** the fixture's, not the DB's. Two facts make them scorable against the fixture:

- **Transaction labels** (`is_money_in`, `apparent_category`) are on **verbatim transactions**. The fixture
  reuses the DB's real transactions unchanged (same content-ids, same date/amount/description — only
  statement-level fields were de-identified). Her notes name real people (Akash, Ravi, Anand) because she
  *recognized* them via the LP-379-C real filenames, but the transaction data is identical.
- **Document labels** (income/id) use the **fixture context** — `id.name_normalized="Jordan A Rivera"`,
  `income.documented_monthly=6500` (Jordan's data, not Akash's). She labeled from the row's context column.

### D1 — DB worksheet generation
LP-345's "live" path scores real *reasoners* against fixture/case snapshots — it does **not** build a DB
snapshot. So the reuse point is `build_snapshot(session, loan_file_id=…)` directly (as the LP-385/LP-379-B
probes did), plus the governed `document_filenames_by_content_id` (real `original_filename`s) and the existing
`write_worksheets`. The human invokes `db_worksheet.write_db_worksheets(session, "LF-6T3N", out_dir)` — a
deliberate call, never wired into CI or a normal run.

### D2 — the label join (fail-closed)
Her existing labels join to the **fixture** (100%) — no re-map needed to score them today. For a FUTURE DB
worksheet, transaction rows share subject_ids with her transaction labels (verbatim transactions → they
re-join), but her document labels are fixture-context values on synthetic docs — they do **not** correspond to
the DB's real documents, so they are **not** joined to a DB worksheet (a new document-labeling round replaces
them). The scorer joins strictly by `(tag_id, subject_id)`; a label whose subject is absent scores against no
prediction rather than being guessed onto the wrong row.

### D3 — PII containment (the serious one)
A DB worksheet carries real borrower NPI (names, addresses; accounts/SSNs are PiiField-**masked**). It MUST
NEVER be committed — the LP-210 posture (real-loan artifacts generated locally, `.gitignore`-d). Containment:
`guard_pii_safe_out_dir` refuses any `out_dir` inside the repo tree unless it is under a gitignored
`calibration-local/` segment — **outside-repo or gitignored only, fail-closed (raises, never writes)**;
`.gitignore` covers `calibration-local/`. The generator only writes to `out_dir`; `build_snapshot`'s own
logging is the app's existing behaviour (masked fields). No real PII lands in the repo or a test artifact.

### D4 — scorable now vs held
