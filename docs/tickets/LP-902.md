## What was asked

A palette picker, **dev-only**, on top of LP-901's split — so a palette can be judged on the real
screens rather than imagined from a CSS file.

## Where it lives: the account menu

Under **Row density**, a development build now shows:

```
 Palette                         Dev
 ● Petrol
   Blue
 ☐ Dark theme
```

In the account menu rather than on a `/dev/theme` page because the thing being judged is the app: a
loan file, the verification panel, a table at compact density. A swatch sheet would show that the
colours are the colours. Selecting keeps the menu open, so you can flip Petrol ↔ Blue and watch the
screen behind the menu change.

Dark theme rides along. The `.dark` palettes have existed since LP-UI-001 and nothing could turn them
on — no toggle, no cookie, not one `dark:` variant. Showing a palette in one theme only would be
half a comparison.

## How it works — the same shape as ⌘B and density

- `data-palette` and the `dark` class on `<html>` are the **single source of truth**; the palettes
  hang every colour off them.
- The **server stamps them from cookies** (`ledger-palette`, `ledger-theme`) in `app/layout.tsx`, so
  the first paint is already in the right colours — no flash, no hydration mismatch.
- The **cookie is only persistence** and the React state only a mirror, as in `use-nav-collapse.ts`.
- Only a non-default value is stamped, and the default **deletes** the cookie rather than writing a
  second spelling of "no cookie" (the rule density and ⌘B already follow).
- An **unknown palette** in the cookie (one since deleted, a hand-edited value) falls through to the
  default rather than stamping an attribute that matches nothing.

There is no database half, unlike density: this is a developer's tool, not a processor's preference,
so it follows the browser.

## Dev-only, and what that means precisely

`THEME_SWITCHING = process.env.NODE_ENV !== "production"` (`lib/theme.ts`). In a production build:

- the menu section is not rendered, and is **absent from the client bundles** — checked after
  `next build`: neither `ledger-palette` nor `Dark theme` appears anywhere under `.next/static`;
- the server **reads both cookies and discards them** — `stampedTheme`'s `enabled` compiles to
  `false`, so it returns before looking at either value — and a developer's cookie cannot recolour
  staging for them and make a staging screenshot disagree with what processors see. Staging runs a
  production build and behaves exactly like production here.

## The second palette: Blue

`app/palettes/blue.css` — LP-5's original accent (`#2563EB`) on slate neutrals, the look `CLAUDE.md`
described until LP-901. Chosen because it is a real alternative the project has history with, not a
random second colour. Values start from Tailwind's blue / slate / red / green / amber / violet and are
adjusted where a pair needed it.

Stock blue-600 (53.3%) **fails** as the accent here: 4.37:1 as text on the hover fill (`accent`).
The first cut sat at 48% (5.24:1 there) and passed every pair LP-901 shipped with. It then **failed
the translucent pairs LP-901's review added**: white on Badge's `hover:bg-primary/80` was 4.20:1
over a card. The accent is now `221.2 83.2% 44%` — the lightest that clears it, 4.59:1. That is the
review's point made on the first palette it met: a slightly lighter accent passed every older check.

The light status hues are darkened past their stock `-600`s for the same kind of reason: they are
read on the hover fill and inside their own `/10` chip, not only on white.

| Blue, tightest | Light | Dark |
| --- | --- | --- |
| text on any ground | 4.79 | 5.50 |
| `-foreground` on its fill | 5.18 | 6.03 |
| text on a translucent fill (chip, drop zone, hovers) | 4.59 | 4.99 |
| `input` / `ring` | 3.77 | 3.41 |

Nothing in LP-902 names a palette colour outside `globals.css` and `app/palettes/` (the guard LP-901's
review added): the switcher shows labels, not swatches, so it needs none.

## Adding a third palette

1. Copy `app/palettes/blue.css` to `app/palettes/<id>.css`; change the selectors to
   `:root[data-palette="<id>"]` and `:root[data-palette="<id>"].dark`, and the values.
2. `import "./palettes/<id>.css";` in `app/layout.tsx`.
3. Add `{ id: "<id>", label: "…" }` to `PALETTES` in `lib/theme.ts`.
4. `pnpm vitest run app/palettes` — it names every pair below its floor, with the ratio.

Forgetting step 2 or 3 fails the test ("imported by the root layout", "the switcher offers exactly
the palettes on disk"); so does a missing colour, or a block under a mistyped selector.

## Verified

- **Server stamping**, curl against `next dev` with each cookie combination:

  | Cookies | `<html>` |
  | --- | --- |
  | none | no class, no attribute |
  | `ledger-palette=blue` | `data-palette="blue"` |
  | `…blue; ledger-theme=dark` | `class="dark" data-palette="blue"` |
  | `ledger-palette=sepia; ledger-theme=dark` | `class="dark"`, no attribute |

- **In a browser** (headless Chromium, `/login` — the one page that renders without the backend),
  `getComputedStyle` per combination: petrol light `--primary 187.9 67.9% 22%`, petrol dark
  `186.9 47.3% 53.1%`, blue light `221.2 83.2% 44%`, blue dark `213.1 93.9% 67.8%`; screenshots of all
  four look right. Console: **no hydration warning** in any combination; the only error is the
  session refresh failing against the stopped backend, identical with and without the cookies.
- **Production build**: the blocks ship as `:root[data-palette=blue]` and
  `:root[data-palette=blue].dark` (the minifier drops the quotes); the switcher is absent.
- **Tests**: `stampedTheme` (including the production branch), `useTheme` (adopts the stamped state,
  default deletes the cookie, palette and theme independent), and the menu items rendered in a real
  Radix menu. Removing the `preventDefault` that keeps the menu open fails "stays open to compare".

## Not verified

## Limits

- Dark theme is **not product-ready by decision**, not by defect: LP-UI-004 audited it (zero AA
  failures), but whether processors get it is a product call. This ticket only makes it reachable in
  development.
- Palette and theme apply at `<html>` only (ADR-402), so there is no side-by-side light/dark preview.

## Review — REVIEWED

The switcher is right as built. It follows the ⌘B/density pattern faithfully, down to the cookie
format. It validates the cookie before stamping, reads the DOM only in an effect (so there is nothing
to mismatch at hydration), and the tests drive the real Radix items. The three claims to check:

- **(a) Production.** I ran an independent `next build` (exit 0) and searched the output. Under
  `static/`, `ledger-palette`, `ledger-theme`, `Dark theme` and `DevThemeItems` are absent, and the
  only `data-palette` is the CSS selector. The server chunk keeps `stampedTheme` with `enabled`
  compiled to `false` (`function(e,t=!1){…if(!t)return{palette:void 0,dark:!1}`), so the cookies
  are read and discarded. The ticket said the server "does not consult" them; it now says what the
  build does. Both Blue blocks ship as `:root[data-palette=blue]` and `…blue].dark`.
- **(b) Hydration.** This holds by construction. The attributes come from the same server render as
  the RSC payload, and `useTheme` reads `<html>` only in an effect. The component mounts only when
  the menu opens, so it is never server-rendered. I did not repeat the browser run.
- **(c) A logged-in click-through.** Still not done. There is no backend here either.

Every figure in "Blue, tightest" (4.79 / 5.18 / 4.59 / 3.77 light, 5.50 / 6.03 / 4.99 / 3.41 dark) and
the accent history (4.37 at 53.3%, 5.24 and 4.20 at 48%, 4.59 at 44%) matches my recomputation with a
separate HSL conversion. No `dark:` variant exists in the tree.

### 1. The dark theme drew native widgets light

This is the first ticket that lets `.dark` appear, and nothing set `color-scheme`. Scrollbars, the
option list of the 13 native `<select>`/typed inputs (the admin validation page, lender contacts,
mailbox connections, the reviewer's add-field…), and date and file pickers take their colours from
`color-scheme`, not the palette. So a developer judging the dark theme on real screens would see
white scrollbars and light dropdowns on a dark page, and misjudge it.

**Fix:** `.dark { color-scheme: dark; }` in `globals.css`, outside any `@layer` like the palettes, and
synced to the ledger asset copy. It has no production effect, since nothing stamps `.dark` there.
Compiling `globals.css` with the Tailwind CLI confirms the rule survives (`.dark{color-scheme:dark}`).
It is not a colour role, and ADR-402 now says so. Toasts were checked and are already fine: the
toast, its description, action and close button are all overridden with tokens (`TOASTER_CLASSNAMES`).

### 2. The Petrol-measured exemptions became a live claim about Blue

ADR-402 recorded that `MEASURED_SAFE` in `a11y-contrast.test.ts` "carr[ies] ratios measured against
Petrol and [is] not recomputed per palette". With one palette that was a caveat. With two it is an
unchecked claim. `text-primary/80` on a card is 5.10:1 in Petrol but **4.59:1 in Blue light**. It
passes, but it crosses the floor at the same lightness (44.9%) as the Badge hover this ticket tuned
for. The `blue.css` comment explained the Badge constraint and not this one, which a future "tweak
Blue's accent" would have met with no test to stop it.

**Fix:** `palettes.test.ts` reads `MEASURED_SAFE` from `a11y-contrast.test.ts` (parsing the
`"text-x/NN": "N:1 on bg-y …"` shape, so a new exemption is covered with nothing to remember). It
recomputes each entry for every palette and theme, with a control that fails if the parse finds
nothing. **Mutation:** changing the exemption to `/40` fails in all four palette × theme
combinations (1.99–2.17:1), and fails the control. `a11y-contrast.test.ts` gains a comment saying
its ratios are Petrol light's and naming the shape to keep. ADR-402's sentence is updated.

### 3. Claims corrected

- **`blue.css`**: "needs the accent at 44% or darker" is not the threshold. It is 44.9%, and 44.5%
  passes at 4.54:1. The comment now gives the threshold and names the second pair that shares it.
- **My own LP-901 comment** in `palettes.test.ts` gave Badge's unused `destructive` hover as 4.13:1.
  That was over a background; over a card it is **4.09:1** in Petrol light, and 4.42:1 in Blue.
- **ADR-402** said a production build does not "read" the cookies. It reads them and ignores them,
  so it now says "honours".

### Not changed

- `CLAUDE.md`, including the stale CI line, left for the user as asked. Its new dev-only sentence is
  accurate.
- The one-frame window where the menu opens showing Petrol and light before `useTheme`'s effect adopts
  the stamped state is `useDensity`'s pattern too. It is left alone for consistency rather than fixed
  in one hook.
