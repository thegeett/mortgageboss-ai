# LP-844 — Formatting that survives the copy

Status: spec. Build order: third of four. Shares a template version bump with LP-843.

## The report

> "Also use some text editor in message as having some bold text, bullet point will help, plus
> copying them should preserve the style."

## The fact that decides the design

`send_draft` (`services/email_send.py:218`) **records** that a message was sent. It does not
transmit. The processor delivers by copying the body into their own mail client, or by a `mailto:`
link.

So the clipboard is not a convenience on top of rich text — **the clipboard IS the send path**, and
it is the only place formatting can survive. This is also why almost none of HTML email's usual
difficulty applies: we never build MIME, never inline CSS for Outlook, never fight a client that
strips `<style>`. The processor's own Gmail or Outlook does all of that when they paste.

## Everything is plain text today

| Layer | Now |
|---|---|
| Storage | `Communication.body` — one `Text` column |
| Templates | `.txt` with `$placeholders` |
| Editor | `<textarea>` (`message-dialog.tsx:139`) |
| Reader | `<pre className="font-mono text-xs">` |
| Copy | `navigator.clipboard.writeText(body)` — plain only |

The monospace reader earns its own mention: part of why this email reads as machine-generated is
that the product renders it in a code font.

## The change

**Storage: Markdown in the existing `body` column.** Not a second `body_html`.

One source of truth is the point. The sent record must be *what went out*, and two columns that can
disagree give two answers to that. Existing rows stay valid — plain text is valid Markdown — so
nothing is migrated and no historical body changes meaning.

**Clipboard: `navigator.clipboard.write()` with a `ClipboardItem` carrying BOTH `text/html` and
`text/plain`.** Gmail, Outlook and Word take the HTML flavour and keep bold and bullets; a plain
target takes the text. Standard API, no library.

**Editor: Markdown in the textarea plus a live preview.** Decided over a WYSIWYG (Tiptap/ProseMirror)
because there is no editor and no HTML sanitiser in `package.json` today, and the processor is
editing a generated email rather than authoring a document. The existing reader panel becomes the
preview. Recorded as a decision the user did not get to make; revisit if processors ask for it.

**Reader: rendered Markdown, not `<pre>`, and not a code font.**

**Templates become Markdown**, at a new version under ADR-401. LP-843 bumps the same files — do them
together, not as three separate versions of the same text.

## The hard constraint, stated so nobody re-litigates it

**`mailto:` cannot carry HTML.** RFC 6068 defines the body as plain text and no client renders markup
there. The `mailto:` path stays plain whatever this ticket does. Formatting survives the COPY path
only, which means the UI should make copy the recommended route rather than leaving them looking
equivalent.

## Safety note for the build

Rendering Markdown to HTML and putting it on the clipboard is an injection surface: a body contains
a processor's free text, a finding's message (LP-842) and a borrower's own name. Either render
through a sanitiser, or use a renderer configured to emit no raw HTML. A test must prove that a body
containing `<script>` or an `onerror=` attribute reaches the clipboard's HTML flavour inert.

# Built

## No markdown library, and no template version bump

**The renderer is written here, ~70 lines, escape-first.** The spec assumed a library; reading the
constraint changed that. This is not a preview — the clipboard IS the send path, so the HTML this
produces is what reaches a borrower, and it carries a borrower's own words, a processor's free text
and a rule's sentence. Every general-purpose markdown renderer has a raw-HTML passthrough that must
be configured off or paired with a sanitiser, and neither `marked` nor `dompurify` is in this
project.

Escaping runs before a single tag is emitted, so injection is impossible **by construction** rather
than by configuration: there is no passthrough to leave on, and no sanitiser whose rules have to keep
up with the renderer's. The subset is matched to what the templates actually emit — paragraphs, `- `
bullets with their indented detail lines, `**bold**`. A body is a business letter; headings, links,
images, tables and code blocks are things we never write and therefore never parse.

**The templates did not change, so ADR-401 is untouched.** The spec planned a version bump shared
with LP-843. It turned out to be unnecessary: the document list already emits `- ` lines, which are
bullets. A bump would have been three new template files and three fingerprints to buy nothing.

One case the subset exists for: the catalog indents "Where to get it" under each document, and **four
spaces is a code block in ordinary Markdown** — a general renderer would put the instructions in a
monospace box detached from the document they describe. Here an indented line under a bullet is that
bullet's detail.

## What actually changed for a processor

- **The reader is a letter, not a dump.** It was a monospace `<pre>`, which is part of why these
  emails read as machine-generated: the product showed a business letter in a code font.
- **Copy writes both flavours.** `text/html` keeps bold and bullets in Gmail, Outlook and Word;
  `text/plain` is what a textarea or a terminal takes. Falling back to plain text when
  `ClipboardItem` is unavailable or refused, because a processor whose copy silently did nothing
  cannot send the message at all — and plain text is exactly what they had before this ticket.
- **A preview toggle**, because the editor is Markdown: `**this**` is bold in the recipient's inbox
  and not in the box being typed into, and a processor who cannot see the result is proof-reading the
  wrong artefact.
- **The UI says which route keeps the formatting.** `mailto:` bodies are plain text by RFC 6068 and
  no client renders markup in one, so the two buttons are not equivalent and a processor should not
  have to discover that.

## Two things the build got wrong first

**The styles went in `globals.css` and broke the design ledger.** `docs/design/ledger/assets/globals.css`
is a reference copy implementers drop in, and a test compares them. The failure was right and the fix
was not parity: these are FEATURE styles, not design tokens, and adding a message-body rule to the
ledger would ship this ticket's CSS to every new screen as though it were part of the system. They
are arbitrary variants on the container now. The rendered HTML still carries no classes at all — a
mail client keeps the semantic tags and discards our stylesheet.

**The first XSS mutation was invalid and reported a pass.** It prepended two no-op `.replace` calls
to `escapeHtml`'s chain rather than removing the chain, so the escaping still ran and 31 tests
"survived" a mutant that was never applied. Neutering the function properly kills five tests across
two files, including the one that renders through `dangerouslySetInnerHTML`. This is the third
invalid mutation in this run of tickets; the shape is always the same — an edit that looks like a
removal and is an addition.

## Scope note

`mailto:` stays plain whatever this ticket does. Formatting survives the COPY path only.
