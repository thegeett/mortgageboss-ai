# LP-844 — Formatting that survives the copy

Status: spec. Build order: third of four. Shares a template version bump with LP-843.

## The report

> "Also use some text editor in message as having some bold text, bullet point will help, plus
> copying them should preserve the style."

## The fact that decides the design

`send_draft` (`services/email_send.py:218`) **records** that a message was sent. It does not
transmit. The processor delivers by copying the body into their own mail client, or by a `mailto:`
link.

So the clipboard is not a convenience on top of rich text — **the clipboard IS the send path**, and
it is the only place formatting can survive. This is also why almost none of HTML email's usual
difficulty applies: we never build MIME, never inline CSS for Outlook, never fight a client that
strips `<style>`. The processor's own Gmail or Outlook does all of that when they paste.

## Everything is plain text today

| Layer | Now |
|---|---|
| Storage | `Communication.body` — one `Text` column |
| Templates | `.txt` with `$placeholders` |
| Editor | `<textarea>` (`message-dialog.tsx:139`) |
| Reader | `<pre className="font-mono text-xs">` |
| Copy | `navigator.clipboard.writeText(body)` — plain only |

The monospace reader earns its own mention: part of why this email reads as machine-generated is
that the product renders it in a code font.

## The change

**Storage: Markdown in the existing `body` column.** Not a second `body_html`.

One source of truth is the point. The sent record must be *what went out*, and two columns that can
disagree give two answers to that. Existing rows stay valid — plain text is valid Markdown — so
nothing is migrated and no historical body changes meaning.

**Clipboard: `navigator.clipboard.write()` with a `ClipboardItem` carrying BOTH `text/html` and
`text/plain`.** Gmail, Outlook and Word take the HTML flavour and keep bold and bullets; a plain
target takes the text. Standard API, no library.

**Editor: Markdown in the textarea plus a live preview.** Decided over a WYSIWYG (Tiptap/ProseMirror)
because there is no editor and no HTML sanitiser in `package.json` today, and the processor is
editing a generated email rather than authoring a document. The existing reader panel becomes the
preview. Recorded as a decision the user did not get to make; revisit if processors ask for it.

**Reader: rendered Markdown, not `<pre>`, and not a code font.**

**Templates become Markdown**, at a new version under ADR-401. LP-843 bumps the same files — do them
together, not as three separate versions of the same text.

## The hard constraint, stated so nobody re-litigates it

**`mailto:` cannot carry HTML.** RFC 6068 defines the body as plain text and no client renders markup
there. The `mailto:` path stays plain whatever this ticket does. Formatting survives the COPY path
only, which means the UI should make copy the recommended route rather than leaving them looking
equivalent.

## Safety note for the build

Rendering Markdown to HTML and putting it on the clipboard is an injection surface: a body contains
a processor's free text, a finding's message (LP-842) and a borrower's own name. Either render
through a sanitiser, or use a renderer configured to emit no raw HTML. A test must prove that a body
containing `<script>` or an `onerror=` attribute reaches the clipboard's HTML flavour inert.
