## What was asked

> *"Each draft list should show stime stamp when it was created on list like an email list and
> opening model should also show that timestamp (date rime)."*

## Why this is one ticket and not a line in three

Three surfaces show a message: the drafts list, the modal, and the popover. **The list and the modal
were named; the popover is the third and was not** — and adding it to two of three is how a processor
learns to trust a time that is sometimes there.

So the requirement is stated as a class: **anywhere a message is listed or opened, it says when.**
That is checkable across the surfaces rather than three times in three places, and a fourth surface
inherits it.

## Which time, because a draft has more than one

A message has up to four moments, and they are not interchangeable:

| | |
|---|---|
| `created_at` | when the draft was composed |
| `sent_at` | when it actually went to the borrower |
| `read_at` | when a processor opened an inbound message |
| the last change | not stored — see below |

**The rule LP-812 already settled**: a message belongs at `sent_at` when there is one, `created_at`
otherwise. *"A draft composed on Monday and sent on Thursday belongs at Thursday — that is when the
borrower heard from us."* The list should order and label by the same rule, or the mailbox and the
timeline will disagree about when the same message happened.

The request says "when it was created", which for a draft is exactly `created_at` — the two rules
agree everywhere a draft is concerned and differ only once a message is sent, where LP-812's answer
is the right one.

**"Last changed" is not available.** `Communication` has no `updated_at`, and a draft is regenerated
on every add and remove, so a processor reading "created 3 days ago" on a draft that changed an hour
ago is being told something true and not what they asked. Adding `updated_at` is a migration and a
decision; it is **not** in this ticket, and the label must therefore say *created*, not *updated*.

## Two clocks, and the list and the modal want different ones

* **The list** wants what an email client shows: relative and short. "2 hours ago", "Yesterday",
  "3 Sep". A column of full timestamps is unreadable at a glance and that is what the list is for.
* **The modal** wants the full date and time, as asked — a processor who has opened one message is
  looking at that message, and "yesterday" is not enough to put in a note or an audit conversation.

Both from the same value. The difference is presentation, and it belongs in one formatter rather than
two components each deciding.

## Done when

- The drafts list shows a time on every row, ordered by the same rule LP-812 uses.
- The modal shows the full date and time.
- The popover's rows show a time. This is the surface that was not named.
- The times are **the same instant** on all three, formatted differently. A test asserts that from
  one value, which is the only way the claim means anything.
- The label says what the time IS. "Created" on a draft; "Sent" once it has gone. A bare timestamp
  beside a message that was composed on Monday and sent on Thursday is ambiguous in exactly the way
  that matters.
- An unparseable or missing value renders as nothing rather than as "Invalid Date". Both the timeline
  panel and the activity feed already guard this, so the third surface should not learn it the hard
  way.

## For the reviewer

The check that is worth running rather than reading: compose a draft, wait, add a second document to
it, and confirm the list still says **created** and says so honestly. If it silently starts showing
the regeneration time, the label is wrong and nothing in the type system says so.

## Built, 2026-09-09

### The popover is NOT in this ticket, and that is a correction to it

This ticket said *"the popover's rows show a time. This is the surface that was not named."* **LP-837
has not been built.** There is no popover. Writing a formatter call for a component that does not
exist would be a function nothing runs — the exact shape this phase keeps producing, and the one it
has spent three tickets learning to refuse.

So the requirement moves to LP-837, which builds the surface. It is recorded in that ticket's
done-when rather than left in this one as a line nobody could satisfy.

The module it will use has two real callers today, so nothing here is dead.

### It had already produced three formats, on one page

The prediction in the ticket — *"'every surface' is exactly the sentence that produces four copies of
a date format and one of them wrong"* — was already true when it was written:

| surface | what it did |
|---|---|
| `timeline-panel.tsx` | a local `when()` → `formatDistanceToNow` |
| `message-dialog.tsx` | a local `when()`, **same name, different behaviour** → `d MMM yyyy, HH:mm` |
| `inbound-message-card.tsx` | `new Date(iso).toLocaleString()` — locale-dependent, absolute |

Three formats for the same kind of fact, on the same screen, **none of them wrong on its own**. The
third was found by grepping for the class rather than by working the ticket's list, which named only
two.

`lib/message-time.ts` is now the one place. The instant, the label and both presentations come from
it.

### The instant is the server's rule, not a second one

`messageInstant` applies `_message_at`'s rule — `sent_at` when there is one, `created_at` otherwise —
rather than restating it. The list is **ordered** by that value server-side, so a client that picked
a different instant to display would sort by one and label by another, and the disagreement would
surface as a list that looks mis-sorted rather than as a wrong date.

`inbound-message-card` keeps `received_at` and does **not** adopt the timeline's fallback.
`_message_at` falls back to `created_at` for inbound only to avoid joining `inbound_messages` to
order a list, and its own comment says `received_at` *"is the better answer"*. The card already holds
it.

### The label, and the one it would have got wrong

A bare timestamp beside a message is ambiguous in exactly the way that matters: a draft composed on
Monday and sent on Thursday shows **Thursday**, and "Thursday" alone does not say whether the
borrower has heard from us. So every time carries what it is — Created, Sent, Received.

**Failed is its own word.** A failed send's instant is `sent_at`, so the obvious implementation
labels it "Sent" — which is the one thing that did not happen. LP-819 gave delivery failure its own
activity type for the same reason.

**"Last changed" is not available and is not guessed at.** `Communication` has no `updated_at` and a
draft regenerates on every add, so a draft edited an hour ago says *created*, truthfully. Adding
`updated_at` is a migration and a decision; this does not make it, and the label says `created` so
nothing implies otherwise.

### The class is asserted, not described

`test_nothing_under_components_file_communication_formats_a_message_time_itself` reads the directory
and fails on `toLocaleString()`, `formatDistanceToNow` or `format(new Date`. A fourth surface
inherits the rule by failing that, rather than by somebody remembering.

It has one allowed exception, named with its reason: `upload-link-panel.tsx` formats an **expiry**,
which is a deadline rather than a thing that happened, and "Expires in 2 days" is not a sentence this
module should learn to say.

**The guard fired on its own comment first.** The scan matched the sentence explaining why
`toLocaleString()` had been removed, and reported the file it had just fixed. Comments are stripped
before scanning now — a guard that fires on prose about itself is a guard nobody keeps.

## Review — REVIEWED

Two findings, both in the guard rather than in the formatting, and both are about the guard being
narrower than the class it claims.

**1. The comment-stripping could hide real code, and it existed for one sentence.** The build
suspected this and could not prove it. Measured:

```
const a = "a /* b";
export function Thing() { return <span>{new Date(x).toLocaleString()}</span>; }
const c = "d */ e";
→ offender still visible after stripping: false
```

An unclosed `/*` in one string literal and a `*/` in a later one makes the strip swallow the code
between them, and a real offender in that span disappears. Then: exactly **one** comment in the
scanned directory contained a matching token — the inbound card's note about what it had replaced.
So a regex that can hide code was carried for one sentence. The sentence now names the formatter
instead of quoting it, the stripping is gone, and the guard is a plain substring scan that a string
literal cannot fool.

**2. The guard could not see the surface the requirement was moved to.** Moving the popover's
timestamp rule into LP-837's done-when was right — a formatter call in a component that does not
exist is a function nothing runs. But LP-837's scope names `components/file/file-header.tsx`, and
this guard scans `components/file/communication/` only. So the requirement landed as a sentence in a
document with nothing enforcing it, in the ticket whose whole point is that the class should be
asserted rather than described.

The header file is in the scanned set now, and planting a `toLocaleString()` in it fails the guard —
which it did not before. Two assertions were added with it: that the scan read more than three
files, and that the extra path exists. A scan over nothing reports no offenders, and a renamed
directory would otherwise read as a clean bill of health.

**3. A comment claimed a behaviour the function does not have.** `messageTimeLabel` said "An
unlabelled time is better than a wrong label" and then returns `"Created"` for a fully-null row.
Both cannot be true. The sentence is the part that goes, not the code: `Communication.direction` and
`.status` are both `nullable=False` and `build_timeline` reads `.value` off each, so a row reaching
that branch with both null cannot come from the server. Adding an unlabelled branch would be
machinery for an unreachable case plus two callers learning to trim a leading space. The comment now
says which line to revisit if a non-message kind is ever added.

### The build's other asks

2. **Two instants for one inbound message — endorsed, with the cost named.** `received_at` is the
   message's own arrival time and is the better answer; `_message_at` falls back to `created_at` for
   inbound only to avoid a join, and says so. So the card and the timeline can differ by the ingest
   lag. That is defensible per surface and it is worth being precise about what would close it: a
   join in `build_timeline` so the server's ordering instant and the card's are the same value. That
   is a server change and this ticket is frontend-only, so the decision stands — but it is a known
   cost rather than a footnote, and the short form's relative rendering hides it in the ordinary
   case while the dialog's absolute form does not.
3. **"Failed" as its own label is right**, for the reason given: its instant is `sent_at`, so the
   obvious implementation labels it with the one thing that did not happen.
