# LP-623 — the Need List did not know what the rules found

## The report

LF-ABRS's Need List carried thirteen items. Not one of them was the **appraisal**, the **title
commitment**, the **credit report**, the **rate lock** or the **Closing Disclosure** — while ten
findings on the same file said each was absent (MI-1, PR-6, ID-7, CR-4, CR-8, CR-10, CR-13, CL-1,
IH-3, ID-5).

A processor working that list to zero would have submitted a file with no appraisal, no title and no
credit report.

Four smaller defects sat alongside it, all visible in the same thirteen rows.

## Why the backbone was missing

Both halves of the system knew half the answer and neither told the other.

* The **floor** (`needs_engine.seed_floor_needs`) is six deterministic rules — a government ID per
  borrower, pay stubs + W-2 on employment income, purchase agreement or mortgage statement + payoff
  by purpose, bank statements on stated assets. None is property- or credit-related, and
  `_PER_FILE_UNIVERSAL` is an empty list.
* The **AI reasoner** (LP-69) is asked what is DISTINCTIVE about a file. Its own docstring is candid
  that reasoning quality is "the highest-value Priya input". It reliably proposes the situational
  documents — a brokerage statement for a stock asset, two years of 1040s for contract income, a VOE,
  statements for four revolving accounts — and reliably under-proposes what is true of every file.
* The **rules** already declare the documents they read (`requires_documents`, LP-541/620), and the
  read path already computes which of them nothing on the file satisfies. That answer only ever
  powered a button a processor pressed once per finding.

## What changed

**1. `services/needs_from_findings.py` — seed the list from unfinished findings.** One need per
DOCUMENT rather than per finding (four credit-report findings are one errand — the same grouping
LP-562 gave the bulk button), deduped against the whole list in any status, so re-running is a no-op
once settled. `disposition=CONFIRMED`, not PROPOSED: a rule declaring a document the file does not
hold is deterministic — the same standing as a floor need, and the click this exists to remove.

It decides nothing a rule did not already decide. A satisfied, retired, not-applicable or
processor-resolved finding contributes nothing, and a document type the catalog does not carry is
skipped rather than seeded under a name nothing can match.

**2. `rematch_needs_for_file` — replay matching over documents already on file.** Matching fired only
on arrival, so every change to WHAT MATCHES silently skipped everything already there. bug-001 added
`existing_mortgage_statement -> mortgage_statement`; LF-ABRS's mortgage statement had arrived before
it shipped, so the need sat PENDING beside the document that answers it and would have forever. This
calls the same matcher per document rather than reimplementing it, so aliases, umbrella types and
state changes are picked up by construction.

**3. `REJECTED` is an open state.** LF-ABRS carried two W-2s, one COMPLETED and one NEEDS_REVIEW.
Whichever was processed first claimed the need; the bad one landed on it, the need went REJECTED, and
REJECTED was absent from `_OPEN_STATES` — so the good W-2 that followed matched nothing. The list
reported "did not pass processing" beside a perfectly usable document, and a processor would re-ask
the borrower for what they already had. `_VALID_TRANSITIONS` had always permitted REJECTED → RECEIVED;
only the matcher's own query disagreed. A `_MATCH_PRIORITY` ordering prefers an unfilled need over a
rejected one, so a good document cannot be handed to the rejected need while a pending one waits.

**4. The rejected reason names the real errand.** "Rejected" reads as "the borrower sent the wrong
thing". The document is IN the file and unreadable; what is needed is a clean copy, not another
request. The stored enum is untouched — the sentence a processor reads is not.

**5. The floor is re-derivable instead of one-shot.** `seed_floor_needs` guarded on "does this file
have ANY floor need" and bailed, and it had exactly one call site — MISMO import. So the deterministic
half of the list froze at import and never moved again:

* a borrower added afterwards never got a Government ID — the per-borrower loop only ever saw the
  borrowers who existed at import;
* a loan purpose corrected from purchase to refinance kept the purchase agreement and never gained
  the mortgage statement or payoff statement;
* income or assets entered later never raised pay stubs, W-2s or bank statements.

The AI half re-reasons on every document arrival and partly compensates, but it is asked what is
DISTINCTIVE about a file and so is the least likely thing to propose a government ID for a borrower
who turned up late.

Idempotence moved from per FILE to per NEED: a need is skipped when the file already carries one of
that type — for a per-borrower universal, of that type FOR THAT BORROWER, because one unattributed ID
line must not silently cover two borrowers. Matched against every need in ANY status and ANY origin,
so a pass can neither duplicate what the AI or a finding already raised nor resurrect one a processor
waived. It now runs at verification alongside the other two passes, first, since it is the only one
that reflects a change to the file's own stated data.

**6. "Government ID" is not a driver's licence.** The floor's universal need was typed
`drivers_license` — the one slug it happened to name — while its title said "Government ID". LF-ABRS's
borrower holds a **permanent resident card**, an unexpired government-issued photo ID sitting in the
file, and the need was REJECTED beside it: the processor is told to chase an ID they already have.

Fixed with a named ALTERNATIVES set (`_NEED_ALTERNATIVES`) — driver's licence, passport,
government-issued ID, military ID, permanent resident card — deliberately the same membership as
ID-5's `requires_documents`, which asks the identity question on the rules side. The need is now
minted as `government_id`.

NOT an umbrella CATEGORY, which is the mechanism that already existed and is wrong here: BORROWER_INFO
also holds divorce decrees, marriage certificates, trust agreements and eight kinds of letter of
explanation, any of which would then "satisfy" an identity requirement. A test pins that a divorce
decree does not clear it.

The pre-LP-623 name keeps working and accepts the same alternatives — every ID need on every live file
is stored as `drivers_license`, and a stored row cannot be renamed retroactively, so without that the
fix would have STRANDED every ID need already raised. Both the matcher and the display path read the
alternatives, so the card cannot list a document set the matcher does not count.

**7. AI needs get a matchable type and a category.** Two needs on LF-ABRS had `needs_type = null`
("documentation for the 'Other' liability", "for the unspecified asset"); matching keys on
`needs_type`, so no upload could ever advance them. They are real asks and are KEPT, but the type is
now normalised against the document catalog (`canonical_need_type` — so a model answering
`verification_of_employment` is stored as `voe`, the name the documents use) and an unmatchable one is
logged rather than passing silently. Category is derived from the same catalog: every floor need
carried one and no AI need did, so more than half the list could not be grouped.

## A wrong ask removed: IN-13

IN-13 covers "other" income BROADLY — child support, alimony, capital gains, Social Security, a
pension, a housing allowance — and its own criteria says the requirement "differs by type and is not a
single three-year test". It declared `[social_security_award_letter, pension_statement,
disability_award_letter]`.

A `requires_documents` group names its FIRST member as the thing to ask for, so **every IN-13 finding
asked for a Social Security award letter** — including LF-ABRS's, which is about CONTRACT-BASIS income
on a file stating no Social Security income anywhere. That was already wrong on the existing request
button; seeding would have put it on the Need List.

A static group cannot express "the document for THIS income type", so it must not pretend to.
Declared `[]`, with the reason recorded in the spec. The per-finding `requested_documents` channel
(LP-620) keyed on `income.type` is where this belongs and is the follow-up.

## Where it runs

All three passes run at the end of a verification, after findings are persisted, best-effort and
idempotent: they touch the needs list and nothing a verdict rests on, so a failure degrades the run
rather than failing it. Order is floor → re-match → seed, so each dedupes against what the one before
it added or satisfied.

Everything else about the list stays live and needs no verification: a document arriving still
advances its need within seconds through `needs.update_for_document`, and the AI still re-reasons on
every arrival. Seeding from findings is the one pass that inherently CANNOT run earlier — findings do
not exist until the rules do.

## Expected effect on LF-ABRS

The next verification should add appraisal, title commitment, credit report, rate lock agreement,
Closing Disclosure and VOE to the list, clear `existing_mortgage_statement` against the mortgage
statement already on file, and move the W-2 need off REJECTED onto the completed W-2. IN-13 should
stop asking for a Social Security award letter.

## Adds only, in both directions

Neither the floor nor the finding-seeded pass REMOVES a need whose reason has gone away — a purchase
agreement on a file corrected to a refinance, or an appraisal need whose MI-1 finding a processor
overrode. Deleting a line a processor may already have requested or received is worse than leaving a
stale one, so the honest fix is to SURFACE that the reason is gone and let them decide. That is not
built here.

## Not done

The floor is still six rules. Nothing here makes it richer — the argument for seeding from the rules
rather than extending the floor is that the rules already carry the knowledge and stay current, so a
new rule brings its documents with it. Whether the universal backbone ALSO belongs in the floor (so a
file has its list before the first verification runs) is a real question and is not answered here.
