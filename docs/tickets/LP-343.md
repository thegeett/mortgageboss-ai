# LP-343 — The prompt-exemplar audit (the tag-does-the-rule's-job bug class)

**READ-ONLY.** This ticket audits and REPORTS; it fixes nothing. `git diff` is this file only. Each finding
becomes its own fix ticket (one principled change, measured once — LP-335's discipline).

## WHAT THIS IS

A downstream RULE's concern smuggled into a TAG's prompt. The tag then pre-judges FOR the rule and
**destroys the rule's input** — silently: no error, no flag, and the tests pass (they assert what the prompt
produces). Found TWICE, both by accident, both only by LIVE calibration against real content:

- **LP-335 / `id_address`:** the prompt defined `prior` as *"e.g. an old driver's-licence address"* → every
  DL address tagged `prior` → ID-4's residence filter EXCLUDED it → a real discrepancy could vanish
  (false-green). 50% on a LIVE tag.
- **LP-340 / `income_employer`:** *"drop 'Inc'/'LLC' noise where it aids matching"* — *"where it aids
  matching"* is IN-5's concern inside a tag. Split the model from the labeler → 25%.

**The principle (§3D):** a tag reports what the document STATES; deterministic code queries and judges. A tag
that does the rule's job removes the rule's evidence. Keyless calibration structurally CANNOT catch this
(the golden labels agree with the prompt that produced them) — so the field has never been read with this
question in mind. This audit reads it. **It does not clear it** (see The Honest Limit).

## ACCEPTANCE CRITERIA (met)

- Every fact-tag-producing prompt inventoried (incl. the ones OUTSIDE `tag_production.yaml`) and audited
  against a checklist; ordered by blast radius.
- Every prompt gets a verdict — finding / clean / unsure — no blanks, no audit fatigue.
- Each finding has a TRACED CONSEQUENCE (named rule + outcome), a severity, and a proposed fix ticket +
  the principle it should encode. Fix nothing.

## THE AUDIT METHOD (checklist, derived from the two known instances)

1. **A concrete EXEMPLAR encoding a downstream assumption** — *"e.g. an old driver's-licence address"*: the
   exemplar IS the instruction (LP-335).
2. **A PURPOSE HEDGE** — *"where it aids matching"*, *"so the rule can compare"*: a tag prompt naming what a
   rule does with the tag (LP-340).
3. **SPECULATION about reliability / currency / adequacy** — *"often stale"*, *"if it seems legitimate"*.
4. **PRE-FILTERING / PRE-JUDGING** — telling the model to omit / discard / normalize away something a rule
   needs to see.
5. **AN UNDERSPECIFIED TERM** — "normalized" / "qualifying" / "usable" with no definition (LP-340's root
   cause; both the model and a labeler pick a meaning).
6. **A MISSING `unknown`** — the prompt forces a choice where the document doesn't indicate one → fabrication.

Note (per the ticket): a JUDGMENT-rule prompt is SUPPOSED to reason about adequacy — that is its job, not a
violation. The bug is a rule's concern in a FACT-TAG's prompt.

## THE FINDINGS

### F1 — Stage-B sourcing forces `no` over `unknown`, citing the downstream rule (BLAST: LIVE AS-1)
**Quoted:** *"if you were given NO candidates and the deposit shows no payroll/income signal of its own, the
answer is 'no' — a real 'no' meaning 'unsourced', NOT 'unknown'. **An unsourced deposit is exactly the
signal downstream rules must catch, so do not soften it to 'unknown'.**"*
**Checklist:** 2 (purpose hedge — names what the downstream rule must catch), 4 (pre-judging absence as a
value), 6 (steers AWAY from `unknown`).
**Traced consequence:** the deterministic candidate search hands the model "the small set of candidates it
found." The prompt equates *"I was given no candidates"* with *"no source exists"* → forces
`has_identified_source = no`. If the search is INCOMPLETE (a source in an un-provided statement, a
mis-classified document), the truth is *"couldn't check"* but the tag says *"no"* → **AS-1 (LIVE,
auto-shipping) fires an unsourced-large-deposit finding that is actually unverifiable** — a FALSE-POSITIVE
on a live rule.
**Severity:** blast radius is the highest (AS-1, auto-shipping), but the direction is false-POSITIVE (noise),
not false-green, and there is a defensible fail-loud rationale (an unsourced deposit SHOULD surface). **So:
UNSURE / medium — the strongest candidate for a MEASURED check, not a confident bug.**
**Fix ticket (LP-344):** decide whether "no candidates found" may honestly resolve to `no`, or must be
`unknown` when file completeness is not established. Principle: a fact-tag distinguishes *"the document/file
shows no source"* from *"I was not shown the source"* — the second is `unknown`, not `no`. Encode the
completeness precondition, not the downstream rule's appetite.
**Measurable today?** Yes on LF-6T3N (16 money-in candidates, n=16 — a bias hunt); AS-1 is live.

### F2 — `income.qualifying_monthly` asks the tag to APPLY underwriting rules (underspecified) (BLAST: inert today; AS-1-earmarked)
**Quoted (prompt):** *"qualifying_monthly — the amount usable for qualifying **after continuity/averaging**
(often equals documented_monthly for stable base pay)."* **(vocabulary):** *"The amount usable for
qualifying **after AI applies continuity/averaging/history rules**."*
**Checklist:** 4 (the tag performs the underwriter's qualification), 5 (which continuity? which averaging?
whose overlays? — undefined, LP-340's root cause).
**Traced consequence:** qualification (continuity, averaging, declining-income haircuts, 2-yr history) is an
underwriting DETERMINATION — a rule's/underwriter's job. The tag applies it with no defined convention, so
the model picks one and a labeler picks another (the LP-340 split, pre-fix). `used_by` earmarks it for
**AS-1's large-deposit threshold** (50% of monthly qualifying income): an OVER-stated qualifying figure
raises the threshold → a genuinely large unsourced deposit slips UNDER it → **AS-1 false-green**. Today AS-1
reads MISMO income, not this tag (verified), and DT-1/AS-3 are inert — so the live risk is latent, not
active.
**Severity:** MEDIUM now (inert consumers), HIGH if wired to AS-1's threshold (false-green on auto-shipping).
**Fix ticket (LP-345):** either make `qualifying_monthly` a DOCUMENTED figure the RULE adjusts, or DEFINE the
qualification convention (the LP-340 pattern for `*_normalized`, but for "qualifying"). Principle: the tag
reports what the document supports; qualification rules live in the rule/underwriter, or in a named,
testable convention.
**Measurable today?** Yes — income tags are labelable on LF-6T3N (n=8, bias hunt, per LP-338's corrected
coverage). `documented_monthly` scored 100% (LP-337) and is CLEAN; only `qualifying_monthly` is at issue.

### F3 — `income.voe_present` has no `unknown` (BLAST: inert IN-8)
**Quoted:** *"voe_present — is this a written/verbal Verification of Employment? **"yes" | "no"**."* — while
the module header states *'"unknown" is always legal and never coerced away'* and its siblings offer
`unknown`/`n/a`.
**Checklist:** 6 (missing `unknown`).
**Traced consequence:** on a genuinely ambiguous document (a letter that half-reads as a VOE) the model must
fabricate `yes`/`no`. Feeds **IN-8 (inert)**. Low blast radius; a presence classification is usually
unambiguous.
**Severity:** LOW.
**Fix ticket (LP-346, or fold into an income-prompt pass):** add `unknown` to `voe_present` (and check
`offer_letter_present`, which offers `n/a` but not `unknown`). Principle: every fact tag can say "the
document doesn't indicate this."

### F6 — `stmt.is_reserve_eligible` asks the tag to judge RESERVE ELIGIBILITY (underspecified) (BLAST: inert AS-4)
**Quoted:** *"is_reserve_eligible — are the funds in this account **usable as reserves** as the statement
shows them (a normal checking/savings balance), vs restricted or a retirement/discounted account?"*
**Checklist:** 4 (reserve eligibility is an agency/underwriting determination), 5 ("usable as reserves" —
which account types count? what discount on retirement? — only a rough hint).
**Traced consequence:** AS-4 (inert) reads `is_reserve_eligible` into its reserves calc; a wrong AI
eligibility silently becomes AS-4's input when it activates. The retirement-discount factor is itself a
Priya-pending number (LP-323-AS-B) — the tag pre-empts it.
**Severity:** MEDIUM (inert).
**Fix ticket (LP-347):** report the account-TYPE fact (checking/savings/retirement/brokerage + any stated
restriction) and let AS-4 apply the eligibility/discount rule; or define the eligibility convention.
Principle: account type is a fact; reserve-eligibility is a rule.

## ⚠️ THE TWO-PROMPT DRIFT (a real, separate risk — not the bug class)

There are **two txn Stage-A prompts** producing the same tags: the standalone `STAGE_A_TRANSACTION_SYSTEM_PROMPT`
(what **LIVE AS-1** runs, via `produce_stage_a_transaction_tags`) and the generic `txn_stage_a` group (the
LP-326 re-implementation). **LP-337's 98%/n=50 measured the YAML group — NOT the prompt AS-1 actually uses.**
They already differ (the standalone defines `apparent_category`; the yaml doesn't). This is a maintenance/
measurement hazard: the audited-clean and the measured prompt for AS-1 are not guaranteed to be the same
text. **Recommend (LP-348): converge the two, or make the live path consume the generic group, so the
measured prompt IS the shipped prompt.**

## ASSUMPTIONS + DECISIONS

- **Judgment prompts not flagged for judging.** `id_poa` (ID-9) and the spec `judge.system_prompt`s reason
  about adequacy because that IS their rules' job — per the ticket, not a violation.
- **The "deterministic-over-enum" pattern is treated as sanctioned, not a bug.** `id_title`,
  `stmt.owner_matches_borrower` let the AI resolve a comparison the rule reads (the AS-6 decision, LP-323-AS-B
  D2). Flagged as design-notes with their blast radius, NOT as exemplar-bias findings.
- **Where I could not trace a consequence, I marked UNSURE** (`continuance_3yr`, `usable_value`, the
  `id_address`/`id_name` downstream-references) rather than manufacture a finding.

## THE HONEST LIMIT

**This is a READING. LP-335 and LP-340 were found by MEASUREMENT, not by reading** — a prompt can look clean
and still teach a bias the labels hide. This audit NARROWS the field and orders the risk; it does not clear
it. What still needs LIVE measurement, in blast-radius order: **`document_type`** (the classifier — highest
applicability-blast, 12 rules, cheaper Haiku model; a mis-classification silently flips applicability — added
by the review addendum); **Stage-B sourcing** (F1) and **apparent_category** (the standalone Stage-A's
unmeasured tag — its labels are unfilled) on AS-1; then **ID-7's** `title_vesting_consistent` (F4) and
**ID-1/ID-4** free-text (now scorable per LP-342). Per LP-338's corrected
coverage, LF-6T3N can support `id.*` (n=2), `income.*` (n=8), `asset.*` (n=3) labeling today — a bias hunt,
enough to test F1/F2/F6 against real content. The extraction-layer prompts (`app/ai/extraction/*`) were NOT
audited here — a separate layer, a separate ticket.

## LP-343 REVIEW ADDENDUM (corrections found reviewing this audit)

1. **The `document_classifier` prompt was MISSED (now inventoried, row 0).** The first pass claimed "every
   fact-tag-producing prompt inventoried" but omitted `render_classification_prompt`
   (`app/ai/classification_prompt.py` + `document_classifier.txt`), which produces `document.document_type`
   — read by **12 rules' APPLICABILITY** (AS-1/5/6/9/11, ID-7/9, IN-8/9/10/11/12), the highest
   applicability-blast fact in the system. It IS the bug class' natural home (a biased classification →
   wrong `document_type` → a rule silently `not_applicable` → the check skipped, the LP-335 false-green
   shape), and it is not extraction (its output is read directly by rules). **Audited against the checklist
   now → CLEAN:** it classifies by document IDENTITY from the catalog indicators (facts, not rule concerns),
   names no downstream rule, pre-judges nothing, and handles `unknown` EXEMPLARILY — three distinct cases
   (unsure-which-type → low-conf best guess; none-of-the-known → high-conf `unknown`; unreadable → low-conf
   `unknown`). RESIDUAL RISK is not the prompt but MEASUREMENT: it runs on a cheaper model (Haiku) at the
   highest applicability-blast, and a mis-classification silently changes applicability — so `document_type`
   accuracy is the top MEASURED-check candidate (added to The Honest Limit), alongside the two live
   `document_type` value-mismatch bugs this surface already produced (LP-333, LP-335).

2. **`id_address`'s consuming-rules cell was wrong.** It listed "ID-4, PR-7" but (a) **OC-2** (LIVE) also
   consumes `id.current_address_type` via its `reasoned_over`, so id_address's live blast radius was
   understated, and (b) **PR-7** exists only in `rule_kinds.csv` (Appraisal address matches) with NO spec
   authored — it is PLANNED, not a current consumer. Corrected inline to "ID-4, OC-2 (reasoned_over), PR-7
   (planned)".
