# LP-800 — Borrower instruction catalog

- **Ticket:** LP-800 · Phase 4, M1, ticket 3 of 26
- **Status:** Built — awaiting review. **Priya's pass is outstanding and is not a blocker** (the
  progress file's own note: "Priya reviews after — do not block on her").
- **Date:** 2026-09-06
- **Plan:** [`phase4-build-plan.md`](../phases/phase4-build-plan.md) LP-800 section
- **Design:** [`phase4.md`](../phases/phase4.md)
- **Scope:** `app/documents/catalog.py`, `decisions.md`
- **Migration:** none, by design — ADR-400.

The catalog answered "what IS this document". Phase 4 sends the ask, and that needs two things it
could not answer: whose document it is, and what to say to the person who has it.

---

## What was done

### A third axis on the same slugs

`ResponsibleParty` (borrower / processor / lender / title / employer / cpa / agent / insurer) and
`BorrowerGuidance`, both in `documents/catalog.py` beside tier and category. `GUIDANCE` covers all
**166** catalog types; `get_guidance()` never raises, matching the rest of the module.

The distinction the party field draws is not "who is accountable" — a processor chases all of these.
It is **whether the borrower can act on the ask at all**. An appraisal is ordered by the lender
through an AMC; a title commitment comes from the title company; a written VOE is completed by the
employer. A drafted request for any of them is a wasted round trip that also costs the borrower's
confidence in every other ask in the same email.

### Full instructions for 28 types

The plan scopes authoring by tier — "roughly 25 types are ever asked of a borrower" — and that is
what was written. Everything else carries its party and no prose.

Party distribution across the 166: borrower 113, processor 26, lender 14, title 5, agent 3, cpa 2,
insurer 2, employer 1.

The 28 with full entries: pay stubs, W-2s, 1099s, personal and business tax returns, P&L, K-1, SSA
award letter, 4506-C, bank / investment / retirement statements, gift letter, gift donor statement,
EMD withdrawal proof, homeowner's insurance, mortgage statement, property tax bill, HOA statement,
lease agreement, student loan statement, credit LOE, general LOE, divorce decree, driver's licence,
passport, permanent resident card, Social Security card.

### `common_rejects` is the field that earns its keep

It is also the one most easily skipped, and it is why these entries are long. Almost every re-request
in a processing file is a document that arrived, was looked at, and was sent back: page 1 of 5, a
screenshot of a balance, an expired licence, a state tax return instead of the federal one. Naming
the failure in the **first** ask is cheaper than a second round trip, and it is knowledge the
borrower has no way to have.

## Decisions

### `GUIDANCE` is derived, not written out 166 times

The plan shows `GUIDANCE: dict[str, BorrowerGuidance] = {...}` as one literal. It is built instead
from two private maps — `_RESPONSIBLE_PARTY` (all 166, explicit, grouped by category with the
reasoning for each group) and `_BORROWER_INSTRUCTIONS` (the 28). The public name, type and contract
are exactly as specified.

The reason is the sync guarantee rather than brevity. Written as one literal, ~120 entries would be
the identical `BorrowerGuidance(ResponsibleParty.BORROWER)`, and adding a catalog type would mean
editing two places with nothing to catch a missed one. Derived, the party map is the single home for
that fact, and a catalog type absent from it is absent from `GUIDANCE` — which is precisely what the
sync test reports.

### The default is `PROCESSOR`

An uncataloged type is one nobody has classified. Failing towards "someone on our side deals with
this" costs a processor one manual step; the other default generates a borrower-facing request for a
document that may not be theirs to send. ADR-400 records it.

### `template_url` is `None` everywhere

The field exists as specified — gift letters, LOEs and the 4506-C are the types that will have one.
LP-817 owns the template library, and a link that resolves to nothing is worse in an email than no
link, so nothing is set until there is something to point at. A test pins the absence so the first
entry to set one has to change that test deliberately.

## Tests

`tests/documents/test_borrower_guidance_lp800.py`, 13 tests. Shaped by what fails **silently** —
none of these raise:

- **A missing party** falls to a default and addresses the request to somebody. The sync test mirrors
  `test_indicators_exactly_cover_the_catalog` exactly, in both directions.
- **Prose containing a catalog slug** renders fine and reads as a system leak only to the borrower
  receiving it. `test_no_borrower_text_leaks_a_catalog_slug` asserts no underscore appears in any
  borrower-facing string across all 166 entries.
- **Instructions on a document the borrower cannot obtain.** Every entry carrying a `borrower_label`
  must have `responsible_party = BORROWER`.
- **A label with nothing behind it** — a full entry must have all of `how_to_obtain`,
  `completeness_rule` and a non-empty `common_rejects`.

The fallback tests are parametrised over `None`, `""`, an unknown slug, and `"Bank Statement"` — the
capitalised form is deliberately included, because `get_guidance` does not normalise, so a future
normalisation has to change that test on purpose rather than silently widen the lookup.

Two positive controls, because "returns the default" is also what a broken lookup returns:
`bank_statement` must return its real instructions, and `appraisal` must return `LENDER` with no
prose — the third state, cataloged but not instructed, has to be reachable or the other two assertions
prove less than they look like they do.

Verified by mutation, each killed:

| Mutation | Result |
|---|---|
| `pay_stub`'s party entry deleted | sync test fails |
| a slug leaked into `bank_statement`'s label | 2 tests fail, including the leak test |
| `appraisal` reassigned to `BORROWER` | non-borrower control fails |
| `get_guidance` always returns the default | 2 tests fail |

## Assumptions

- **The party assignments are an industry-standard first pass**, on the same footing as the catalog
  itself and labelled that way in the code. They are what a US residential mortgage file normally
  draws each type from. They are **not** validated against Priya's real workflow, and a processing
  company's own habits move some of them — a shop that orders payoffs through the borrower rather
  than the servicer, for one. The judgement calls I would put in front of her first are listed below.
- **`get_guidance` does not normalise its input.** It matches `CATALOG`'s existing behaviour, and the
  parametrised test pins it so a change is deliberate.

---

## Deliberately not done

- **No `is_borrower_facing()` helper.** `responsible_party is BORROWER` answers it, and an API with
  no reader is a claim nobody checks.
- **No per-company or per-file override.** ADR-400 records why, and what the extension would look
  like if it turns out to be needed.
- **No change to the classification prompt.** Guidance is read after classification; the prompt's
  type list is unaffected.
- **No template files.** LP-817.

## Review (second session, protocol §3)

Two findings. The structure, the never-raise discipline and the thirteen tests are sound — the sync
guarantee runs in both directions, `test_instructions_exist_only_where_the_borrower_can_act` already
closes the invariant I went looking for, and the no-slug-leak test is the right shape for the
failure it names. Both findings are about what the tests could *not* see.

### A — A misspelled instruction key is dropped in silence

`GUIDANCE` is a comprehension over `_RESPONSIBLE_PARTY.items()`, so an instruction keyed on a slug
that map does not carry never enters it. Nothing downstream notices: the coverage test sees no
orphan, because the key is not in `GUIDANCE` to be orphaned; and the floor is `>= 25`, so 28 entries
quietly becoming 27 still passes.

Measured, with the mutation confirmed applied before the run: renaming `pay_stub` to `pay_stubs` in
`_BORROWER_INSTRUCTIONS` left **all 170 tests green** while the borrower instructions for the single
most-requested document in a mortgage file stopped reaching anyone. The type would have fallen back
to party-only and the drafter would have named it with no how-to-obtain, no completeness rule and
none of the `common_rejects` that exist precisely to save a round trip.

Two guards added, both verified to fail against that mutation:

- every `_BORROWER_INSTRUCTIONS` key must exist in `_RESPONSIBLE_PARTY`;
- the eleven types the build plan names by hand must each have a full entry — a `>=` floor cannot
  say *which* types are covered, and 25 entries for the rarest types in the catalog would satisfy it.

### B — One appraiser's work product, split across two parties

`appraisal` is LENDER ("ordered through an AMC; never a borrower ask"), while
`comparable_rent_schedule` (Form 1007) and `small_residential_income_appraisal` (Form 1025) are
PROCESSOR. All three are the same appraiser's product arriving on the same AMC order, and the
evidence is already in this repo rather than in my judgement:
`ai/extraction/comparable_rent_schedule.py` opens by quoting the guide — *"The **lender** must
obtain the following: a Single-Family Comparable Rent Schedule (Form 1007) or Small Residential
Income Property Appraisal Report (Form 1025)"* — and its prompt states both forms are
appraiser-prepared. The catalog's own comment on the PROCESSOR line said "from the appraiser",
naming a source that was not the party assigned.

No borrower is mis-addressed either way, since both values are non-borrower. The cost lands in
LP-820, which builds per-party request paths and per-party clocks: as written, two documents that
arrive from one order would be chased down two paths. Both reassigned to LENDER.

### The party assignments, and Priya

I checked the other 164 rather than waving them through, grouped by party so a type could be
compared against its own class instead of read alone. The distinctions that could have been sloppy
are made correctly: `flood_certification` LENDER against `flood_insurance_policy` BORROWER;
`mortgage_statement` BORROWER against `verification_of_mortgage` PROCESSOR;
`prior_closing_disclosure...` BORROWER against `closing_disclosure` LENDER; `wire_instructions`
TITLE. I found nothing in the 113 BORROWER entries that a borrower cannot actually obtain, which is
the assignment class that would do real harm.

The builder's flagged uncertainties, ruled on rather than left open:

- **`form_4506c` / `form_4506t...` BORROWER** — right. The borrower signs; the signer is who a
  missing signature is chased from, and the same rule already governs
  `authorization_to_run_credit`, `borrower_authorization_and_certification` and
  `social_security_administration_ssa_89`. Consistent across all five.
- **`gift_letter` BORROWER although the donor signs** — right, and the important one to get right.
  The party is who we ASK, not who signs; a processor asks the borrower, who asks the donor.
  `gift_donor_bank_statement` is BORROWER on the same reasoning and agrees.
- **`earnest_money_receipt` AGENT against `emd_withdrawal_proof` BORROWER** — right, and not an
  inconsistency: the receipt is issued by the agent or escrow, and the withdrawal proof comes off
  the borrower's own bank statement. Two documents, two holders.
- **`homeowners_insurance` BORROWER against the two INSURER entries** — right under the rule "who
  buys it": the borrower buys their own policy, while the condo master policy and the liability
  certificate belong to an entity they are not party to.
- **The disclosures rule** — recording whoever a missing copy is chased from, rather than who
  issued it, is a defensible rule consistently applied. `notice_of_right_to_cancel` is the one
  entry where the opposite reading is about equally strong (the lender issues it; the borrower
  signs it; the closing agent usually holds the executed copy). Left as LENDER: it is not wrong,
  and churning a defensible call is worse than leaving it legible.

**On the "Done when" and rule 3.4.** The clause has four parts and three are met — party mapping
complete, the borrower-facing types have full entries, sync test passes. *"Priya has reviewed them"*
is outstanding. This does **not** go back to `PENDING`: the progress row's own note says "Priya
reviews after; do not block on her", §4 forbids idling on it, and the standing direction on this
project is to build from research rather than wait on expert validation. What I have substituted for
her review is the pass above — evidence from the repo and internal consistency across classes, which
is a different thing from domain sign-off and does not replace it. The party assignments remain the
part of this ticket most likely to need revision, and the ticket says so.

## Sourcing pass — Fannie Mae Selling Guide (2026-09-07)

At the user's direction, the responsible-party assignments were re-grounded on the Selling Guide
rather than left resting on recall. Sections read 2026-09-07; each citation now sits **inline beside
the assignment it governs**, so a reviewer reads the rule and the claim together.

### What the Guide actually settles

| Assignment | Section | What it says |
|---|---|---|
| `appraisal`, `comparable_rent_schedule` (1007), `small_residential_income_appraisal` (1025) | [B4-1.1-03](https://selling-guide.fanniemae.com/sel/b4-1.1-03/appraiser-selection-criteria) | Lenders "may not use appraisals ordered or received by borrowers or other parties with an interest in the transaction, such as the property seller or real estate agent." |
| `voe`, `verification_of_deposit`, `verification_of_assets`, `verification_of_mortgage`, `verification_of_rent` | [B3-4.2-01](https://selling-guide.fanniemae.com/sel/b3-4.2-01/verification-deposits-and-assets) | The form is "requested directly from the depository institution", and returned directly by it. |
| `form_4506c` vs `tax_transcript` | [B3-3.1-06](https://selling-guide.fanniemae.com/sel/b3-3.1-06/requirements-and-uses-irs-ives-request-transcript-tax-return-form-4506-c) | "The lender must have each borrower whose income is used in qualifying … complete and sign a separate IRS Form 4506-C", and the **lender** enters its own name as recipient of the transcripts. |
| `verbal_voe` | [B3-3.1-04](https://selling-guide.fanniemae.com/sel/b3-3.1-04/verbal-verification-employment) | The lender obtains it, by telephoning the employer. |
| `gift_letter`, `gift_donor_bank_statement` | [B3-4.3-04](https://selling-guide.fanniemae.com/sel/b3-4.3-04/personal-gifts) | The gift "must be evidenced by a letter signed by the donor"; evidence of transfer comes from the donor's account. |
| `earnest_money_receipt` vs `emd_withdrawal_proof` | [B3-4.3-09](https://selling-guide.fanniemae.com/sel/b3-4.3-09/earnest-money-deposit) | Receipt is verified by "a copy of the borrower's canceled check **or** a written statement from the holder of the deposit." |

**B4-1.1-03 is the one that changes the character of an assignment.** It is a prohibition, not a
convention: an appraisal a borrower sent us is not merely awkward to have asked for, it is
**unusable**, and the asking is what invites them to produce one. `render_document_block` already
refuses every non-`BORROWER` type, so this is enforced rather than advisory — but the tests are now
named after the rule, so anyone moving one of those types has to read what they are overriding.

**B3-3.1-06 splits an ask that looks like one thing.** The 4506-C is a borrower ask (a signature);
the transcripts it produces are not. Asserted as a pair, because either half alone reads as a
plausible whole answer.

### No assignment was wrong

Every sourced assignment already matched the Guide. The one error in this area — 1007/1025 assigned
to the processor beside an `appraisal` that was already the lender's — had been found and fixed in
LP-800's review, from a Selling Guide quotation already sitting in
`ai/extraction/comparable_rent_schedule.py`. This pass adds the citation and the test that pins it.

### What the pass did surface

**1. The party is recorded twice, and the wrong copy wins.** `GUIDANCE` preferred an entry from
`_BORROWER_INSTRUCTIONS` wholesale, and every one of those literals repeated the party as its first
argument. So for the 28 types with full instructions, **editing `_RESPONSIBLE_PARTY` did nothing** —
no effect, no error. It is the same "two spellings of one fact" ADR-399 refused, in the file that
argued for it.

Found by mutation, not by reading: flipping `form_4506c` to `PROCESSOR` left all 182 tests green
while four other flips failed. It could only ever disagree in the direction nothing looks at, because
`test_instructions_exist_only_where_the_borrower_can_act` pins every literal to `BORROWER`.

Fixed: `_Instructions` now carries the prose only, `_RESPONSIBLE_PARTY` is the single home for the
party, and `GUIDANCE` composes them. The mutant is killed.

**2. The vocabulary cannot name a depository or a servicer.** `verification_of_deposit`,
`verification_of_assets`, `verification_of_mortgage` and `verification_of_rent` are third-party forms
sent **out** — the same shape as `voe`, which can name its third party because `EMPLOYER` exists.
They are recorded as `PROCESSOR`, which is honest about "not a borrower ask" and **wrong about "no
outbound request at all"**. LP-820 owns the non-borrower request paths and will read these four as
having nowhere to go. Recorded in the code and in the progress file's escalations.

### What is still unsourced

The majority. The Guide says who must **obtain** a document for a loan to be saleable; it does not
say who a processor emails, and for most of the 166 types nothing says. Disclosures, identity
documents, letters of explanation, inspections and the long tail remain the industry-standard first
pass. Priya's review is still the thing that settles those — but she now has a much smaller pile,
because the types where a wrong answer is a compliance problem rather than an inconvenience are the
ones now carrying a citation.
