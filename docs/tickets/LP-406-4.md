# LP-406-4 — Write OC-1 (Occupancy consistency), the first Bucket 2 rule written from scratch

## What this ticket is

The first genuinely zero-dependency Bucket 2 rule, **written from scratch** on already-live inputs. It is the
pivot from LP-406-1 (PC-7), which Phase 0 found was *not* writable-now (it needs a derived "days-until-closing"
recency tag that does not exist — see `LP-406-1.md`). OC-1 reads two loan-level tags that are **already
produced** — `occupancy.stated` (derived from MISMO) and `occupancy.consistent_with_signals` (the same AI tag
LIVE OC-2 rides) — so no new producer, extractor, or AI call is needed to *write* it.

**Outcome:** OC-1 is **written and producing real verdicts**, but **HELD (not activated)** — its verdict rests
on an AI tag that is unscored, and OC-2 (which ratifies) never had to calibrate it. This is an explicit,
documented hold, which the epic's DoD permits ("live **or** explicitly held with a documented reason"). No live
rule changed; `ACTIVE_RULE_IDS` stays **24**.

## D1 — What does OC-1 actually check?

**Quoted from the source:** `rule_kinds.csv`: *"OC-1, Occupancy consistency, Occupancy, structural,
ai_fuzzy_match, …, Stated occupancy vs address signals — compare; inference → AI."* Classification doc line 77:
*"OC-1 | Occupancy consistency | Occupancy | structural | ai_fuzzy_match."*

**One plain sentence (written to what the tag MEASURES, not the name):** *OC-1 verifies that the borrower's
stated occupancy for the subject property is consistent with the borrower's other 1003 occupancy declarations —
intent-to-occupy, the FHA second-residence indicator, and the financed-unit count.*

⚠️ **The LP-405 / LP-371 D3 trap, confirmed in Phase 0.** The rationale says *"stated occupancy vs address
signals,"* but the produced tag `occupancy.consistent_with_signals` does **not** compare address signals — the
loan/MISMO context that produces it carries **no borrower residence address** (LP-371 D3), so it measures
whether the borrower's *other declarations* agree with the stated occupancy. The spec is therefore worded to
**declaration** consistency, and explicitly disclaims the address dimension (a separate follow-up needing a new
producer). A spec written to the name would have promised a check the tag cannot deliver.

## D2 — Its kind, and therefore its ending

**Structural** (`rule_kinds.csv`; `numeric_check=false`, `priya_validated=false`, `threshold_needs_signoff=false`).
A structural rule may carry a **deterministic** body (schema `_check_evaluation_body`), and OC-1's is purely
deterministic: `occupancy.consistent_with_signals` is *already* the structured `yes`/`no`/`unknown` answer, so
OC-1 just branches on the enum (the AS-4 pattern — a deterministic rule reading an AI-produced enum). **No AI
call happens at rule time**; the `ai_fuzzy_match` in the CSV describes how the *tag* is produced, not how OC-1
evaluates (the loader cross-checks `kind`, not `evaluation_path`).

**The ending — HELD, not 24→25.** Because OC-1 is deterministic it *would* auto-ship. But its verdict is only as
trustworthy as `occupancy.consistent_with_signals`, an **AI tag that has never been scored** (no measured
accuracy, no Priya bar — Phase 0 confirmed there is no bar for it anywhere). **LIVE OC-2 rides the same tag but
RATIFIES every verdict** (a human signs each), so OC-2 never needed the tag *calibrated*; an auto-shipping OC-1
does. Activating OC-1 now would ship a **trusted** verdict on an **unmeasured** AI tag — exactly the exposure the
activation gate exists to prevent. So OC-1 is `not-calibratable-yet` → `is_eligible=false` → **not activated**.
This is the same "written-but-inert pending calibration" state as IN-8/IN-9/IN-13.

## D3 — The read-tags + their REAL semantics

| read-tag | producer | subject | real semantics |
|----------|----------|---------|----------------|
| `occupancy.stated` | derived (`_occupancy_stated`) | **loan** | MISMO `property.occupancy` mapped to the shorthand enum `primary`/`second`/`investment`; `unknown` if MISMO states no occupancy. |
| `occupancy.consistent_with_signals` | **ai** (occupancy group) | **loan** | `yes`/`no`/`unknown`: do the borrower's *other 1003 declarations* (intent-to-occupy, FHA second-residence indicator, financed-unit count) agree with the stated occupancy — **not** address signals (LP-371 D3). Unscored (no bar). |

The verdict is written to those semantics: `no` → the declarations conflict → fire; `yes` → they agree →
satisfied; the reason names the concrete declarations (intent to occupy, second-home indicator, unit count).

## D4 — The subject match (anti-structural-death)

OC-1 enumerates `subject_enumeration: loan`. Both read-tags are **declared at subject `loan`**
(`load_declarations()["occupancy.stated"].subject == "loan"`, same for the consistency tag) and, verified on the
**real LF-6T3N fixture**, `occupancy.stated` **materializes under the `loan` subject** where OC-1 reads it. So
OC-1 is **not** born structurally dead — it reads where the producers write. (Its LF-6T3N value is `unknown` for
a *data* reason — the fixture states no occupancy — which is distinct from a subject mismatch; see the proof.)
This is the ID-5 class of bug (subject mismatch → silent couldnt_check forever) explicitly checked and cleared.

## D5 — Absent / empty / unknown (three distinct states, all handled by the fail-closed gate)

OC-1 declares both tags as `gated_tags`, so the LP-315 gate routes every degradation to `couldnt_check` before
any outcome runs — proven by real evaluation:

| state | what it means | verdict | reason (plain language) |
|-------|---------------|---------|--------------------------|
| **absent tag** | `occupancy.consistent_with_signals` never produced (e.g. a no-AI run) | `couldnt_check` | "…could not be found in the file — this check needs it" |
| **absent MISMO** | no 1003/tags at all | `couldnt_check` | "the stated occupancy could not be found in the file…" |
| **present-but-unknown** | occupancy stated but the AI/derived value is `"unknown"` | `couldnt_check` | "…could not be read from the documents (it is present but unclear)" |
| **shaky signal** | AI confidence < 0.5 floor | `needs_review` | "the automated read of this was low-confidence…" |

Occupancy applies to **every** loan, so there is **no `not_applicable` case** and no document-type
applicability gate (unlike PC-7's purchase-only / POA-scoped rules). Absent inputs are always a *gap*
(couldnt_check), never scope-false.

## D6 — A Priya threshold?

**None.** OC-1 is a pure enum-agreement branch — no window, tolerance, or numeric threshold — so
`threshold_needs_signoff=false` (matching the CSV) is honest. The Priya dependency is a *different* one: her
**calibration** of `occupancy.consistent_with_signals` (labels → measured accuracy → a signed-off bar) is what
would let OC-1 activate. That is out of this ticket's scope (calibration is its own path).

## The spec as written

`backend/app/verification/rules/specs/OC-1.yaml` — key points:
- `kind: structural`, `numeric_check: false`; `deterministic` body; `subject_enumeration: loan`.
- `load_bearing_tags` + `gated_tags` = `[occupancy.stated, occupancy.consistent_with_signals]` (both gated → the
  D5 states couldnt_check).
- `operands: {}` — the decision is an enum branch via `when_tags`, so there is nothing to resolve (an enum
  string is neither a decimal nor a date operand; keeping operands empty avoids a coercion-to-None couldnt_check).
- Outcomes: `fired` when `occupancy.consistent_with_signals == "no"`; `satisfied` default. Static, plain-language
  reasons (no dotted tag ids) — the stated occupancy rides on the finding as a load-bearing tag (provenance).
- Criteria/notes worded to **declaration** consistency with the LP-371 D3 caveat inline.

Its activation bar (`activation_bars.yaml`, required so the loader's exact-coverage check passes) is
`status: not-calibratable-yet`, `ships: auto`, `threshold: null`, `validated: false`,
`load_bearing_ai_tags: [occupancy.consistent_with_signals]` — the AS-4 shape.

## THE PROOF (reported, not predicted)

Run via `evaluate_deterministic_rule(load_rule_spec("OC-1"), snapshot)`:

**Both verdict paths + every D5 state (hand-built snapshots):**
```
consistent=yes           → satisfied   "the borrower's stated occupancy agrees with the file's other occupancy declarations"
consistent=no            → fired       "…does not agree with the other occupancy declarations in the file (intent to occupy, the second-home indicator, and the financed-unit count) — reconcile…"
consistent=unknown       → couldnt_check  "…could not be read from the documents (it is present but unclear)"
stated=unknown           → couldnt_check  "the stated occupancy could not be read from the documents…"
consistency tag absent   → couldnt_check  "the occupancy consistency… could not be found in the file — this check needs it"
all tags absent (no MISMO) → couldnt_check "the stated occupancy could not be found in the file…"
low confidence (0.2)     → needs_review   "the automated read of this was low-confidence (0.2)…"
```

**On the real LF-6T3N fixture** (materialized parsed+derived, no AI): OC-1 → **couldnt_check**. Root cause,
**named** (per the house rule that a uniform couldnt_check is a failure to explain, not a pass): the fixture's
MISMO **states no occupancy** (`occupancy.stated` materializes at the `loan` subject with value `"unknown"`),
**and** `occupancy.consistent_with_signals` is AI (not produced in a no-AI run). This is a **data/fixture gap**
— the same class as live IN-1's honest no-stated-income abstain on LF-6T3N — **not** a bug and **not** structural
death (the tags' subject matches, proven in D4). The satisfy/fire paths cannot be exercised on the base fixture
because it states no occupancy; the scenario that *would* exercise them is a fixture that adds
`property.occupancy` to the MISMO **and** produces the consistency signal (a stub or a live AI run) — a **fixture
ticket**, not this one (mirrors how `build_lf6t3n_plus` added documents for AS-9/IN-4).

**Activation:** `is_eligible(OC-1 bar) == False`; `"OC-1" not in ACTIVE_RULE_IDS`; `len(ACTIVE_RULE_IDS) == 24`
(unchanged). OC-1 is written + producing + **held**.

## Every assumption / decision

- **OC-1 is deterministic, not a consistency rule.** It reads a single pre-computed enum tag (not a cross-source
  gather), so a `deterministic` block (branch on the enum) is the right shape, not `ConsistencyEval`.
- **`operands: {}` is deliberate.** The evaluator's operand coercers are decimal/date only; an enum-string
  operand would coerce to None → couldnt_check. So the enum decision lives in `when_tags`, and the stated
  occupancy appears in the reason only as provenance (a load-bearing tag), never as a `{placeholder}`.
- **Held is the honest ending**, and it is a valid DoD outcome. The ticket's "activate iff deterministic and it
  clears the gate" is satisfied by *not* activating: it is deterministic but does **not** clear the gate (its AI
  tag is unmeasured). Auto-activating would trust an unscored AI tag — refused.
- **OC-2's liveness does not imply the tag is calibrated.** OC-2 is in `_BASE_ACTIVE` (pre-gate) and *ratifies*,
  so it rode the tag without a bar; that does not transfer to an auto-shipping OC-1. This corrects the epic
  plan's implicit "rides OC-2's live producer → no new calibration" for the *activation* step.
- **The LF-6T3N couldnt_check is a data gap, not a defect** — the fixture states no occupancy. Documented, not
  hidden.

## Any NEW gap

- **`occupancy.consistent_with_signals` is unscored** — no calibration, no Priya bar. This blocks OC-1's
  activation (and is the real remaining work). A calibration ticket (label the tag on occupancy scenarios →
  measure → Priya sets a bar) would flip OC-1 live. **This is a genuine correction to the epic:** the four
  Bucket 2 rules were framed as "no new calibration"; OC-1 needs calibration to *activate* (it needs none to be
  *written*).
- **The LF-6T3N fixture states no occupancy** → OC-1 (and any occupancy rule) couldnt_checks on it. A fixture
  that adds `property.occupancy` (+ produces the consistency signal) would exercise satisfy/fire end-to-end.
- **The address-signal dimension** (the rule's original name) is unbuilt — the produced tag only sees MISMO
  declarations. A future producer that feeds a residence address would extend OC-1's coverage.

## What this template means for AS-8 / IN-6 (LP-406-2/3)

OC-1 establishes the **deterministic-rule-reading-an-already-produced-tag** template and, more importantly, the
**two-gate lesson**: a rule is writable-now if its inputs are produced, but *activatable-now* only if any AI
input it trusts is **calibrated with a signed-off bar**. Apply that Phase-0 check to the next two:
- **AS-8** (statement chaining) reads only **parsed** stmt/txn tags (no AI to calibrate) — so it can plausibly
  **activate** if it clears the no-ai-dependency gate (`input_resolves`). **But** its check is a cross-statement,
  per-account-pair comparison; confirm the deterministic DSL can express that pairing within one subject
  enumeration, or it needs a derived tag/enumerator (its own Phase-0 expressibility check — the PC-7 lesson).
- **IN-6** (pay-stub ↔ W-2 coverage) rides `income.employer_normalized` (AI, **measured 100%** via live IN-5) —
  so unlike OC-1 its AI tag *is* calibrated, and it may activate. Confirm its shape: an employer **set-match
  across documents** is likely the `ConsistencyEval` shape, not a plain deterministic branch.

In short: OC-1's inputs exist and it produces correct verdicts, but it is **held on calibration**; AS-8 and IN-6
each need their own Phase-0 pass on (a) expressibility and (b) whether their trusted AI tag is already measured.

## ADR

No new ADR: OC-1 is a planned rule written on existing inputs with the established evaluator, and its held state
is the documented activation-gate behavior. The **finding** worth carrying forward — *"a ratifying judgment rule
(OC-2) riding an AI tag does not calibrate that tag for an auto-shipping sibling (OC-1); each auto rule needs its
own measured bar"* — is recorded here and folds into the LP-405/epic correction above; no architectural decision
is being made, so `decisions.md` is untouched.
