# LP-202 — Document→borrower name field + deterministic link

## Summary

Produce a **deterministic** (non-AI) link saying which borrower(s) a document is
about, as a prerequisite for the Stage-1 snapshot (LP-206 will consume it to
populate `belongsTo`). Where a document clearly asserts a borrower name but didn't
extract it, add that name field (carrying LP-201's per-field confidence). Then a
pure `normalize + score` matcher maps a document's asserted name(s) to the loan
file's borrowers, above a configurable threshold, into a new `document_borrower_links`
table that supports **one document → many borrowers** (joint docs). Nothing
consumes the link yet.

Architectural decisions recorded in **ADR-239** (`decisions.md`).

## Acceptance criteria

- [x] Name extraction added where a doc clearly asserts a borrower name but lacked it.
- [x] Deterministic matcher: normalize (case/whitespace/punctuation, nickname map,
      middle/initial tolerance) + similarity score. **No AI anywhere.**
- [x] Configurable no-match threshold (named constant); low similarity → no link,
      never a forced closest-match.
- [x] Per-(document, borrower) result: matched borrower, confidence, method tag
      (`exact` / `normalized` / `fuzzy`).
- [x] Joint documents link to more than one borrower (one-to-many).
- [x] New `document_borrower_links` table + Alembic migration; UNIQUE

- [x] Write path + read path; no-match → zero rows (no error, no null-borrower row).
- [x] Resolved link lives only in the table; the raw asserted name stays on the

- [x] Tests: single, joint, no-match, below-threshold near-miss, method tags,
      round-trip persistence, no-name → no links.
- [x] ADR added (ADR-239) and referenced here.
- [x] CI green: ruff, mypy, pytest (affected suites).

## Phase 0 findings

- **Borrower model:** `first_name` (req), `last_name` (req), `middle_name`
  (nullable), a `full_name` property; a loan file has 1+ borrowers
  (`LoanFile.borrowers`, ordered). **No existing name normalization.**
- **No link on this branch:** `Document` has no `borrower_id`; the
  `document_borrower_links` on `phase3_5_1` is not in use here. Built fresh.
- **Extraction storage:** `extractions.extracted_data` JSON (per LP-201, each
  field is `{value, source, confidence}`).
- **Name coverage:** 10 of 18 types already extract a usable borrower name
  (pay_stub/w2/voe `employee_name`; bank_statement `account_holder_name`;
  investment_account/retirement_account `account_holder`; drivers_license
  `full_name`; form_1099 `recipient_name`; gift_letter `recipient_name`;
  purchase_agreement `buyer_name`; tax_return `taxpayer_names`). 4 clearly assert a
  borrower name but didn't extract it (added in Phase 1). 3 have no clean single
  borrower-name slot and were left alone (`divorce_decree`, `letter_of_explanation`,
  `profit_and_loss`).

## What was built

**Phase 1 — name extraction (4 extractors)** — added a borrower-name typed field
(data model + `_CORE_SPEC` + prompt contract + TYPED CORE bullet), carrying LP-201
per-field confidence automatically:
- `homeowners_insurance` → `named_insured`
- `mortgage_statement` → `borrower_name`
- `property_tax_bill` → `owner_name`
- `hoa_statement` → `owner_name`

**Phase 2 — deterministic matcher** — `app/services/borrower_name_matching.py`
(pure, no DB, no AI):
- `normalize_name()` — accents, case, punctuation, `"Last, First"` reorder,
  suffix/connector removal, tokenization.
- Small high-precision **nickname map** (Robert↔Bob, William↔Bill, …), symmetric
  via a canonical form.
- `match_document(asserted_names, borrowers)` — **last-name anchor** (`_LAST_NAME_MIN
  = 0.85`) then first-name exact/nickname/initial/fuzzy (`difflib`), combined
  `0.5·last + 0.5·first`; a full-set token match tags `exact`. Returns one
  `MatchResult(borrower_id, confidence, method)` per borrower ≥ threshold — many for
  a joint document.
- **Threshold:** `NAME_MATCH_THRESHOLD = 0.80` (named constant). Below → no link.
- `BORROWER_NAME_FIELDS` registry mapping each document type → its borrower-name
  field(s), **excluding counterparties** (`donor_name`, `seller_name`);
  `asserted_names_for()` reads them from `extracted_data`.

**Phase 3 — storage** — `app/models/document_borrower_link.py`
(`DocumentBorrowerLink`) + migration `b3f8d2c6a941`: `{document_id, borrower_id,
confidence, method, created_at}`, `UNIQUE (document_id, borrower_id)`, `[0,1]`
CHECK on confidence, `ondelete=CASCADE`. `app/services/document_borrower_links.py`:
`assign_document_borrower_links(db, document)` (recompute + replace, flush-only,
zero rows on no-match) and `get_document_borrower_links(db, document_id)`.

**Phase 4 — tests** — `tests/services/test_borrower_name_matching.py` (pure:
single/joint/no-match/near-miss/method-tags/normalization/registry) +
`tests/services/test_document_borrower_links.py` (DB round-trip: single, joint→both,
no-name→zero, unmatched→zero, persist+read-back, idempotent re-match).

## Assumptions & decisions

- **Threshold 0.80** with a **0.85 last-name anchor**: exact/nickname/initial clear
  it; a surname typo (`Patek` vs `Patel`) and a same-surname different first name
  fall below → no link. Precision over recall — a no-match is a correct outcome.
- **Method tags:** `exact` (full normalized token-set equal), `normalized`
  (last + first both matched via exact/nickname/initial), `fuzzy` (any component
  relied on edit-distance). Stored as a free `String(64)` (small stable set; could
  become a `str_enum` CHECK later).
- **Raw-name-vs-resolved-link separation:** the asserted name is never rewritten
  onto the borrower or into a document fact; the correlation lives only in the link
  table, so the snapshot's document facts stay raw/uncorrelated (ADR-239).
- **Nickname/normalization rules:** a modest, high-precision nickname map (not
  exhaustive); suffixes (Jr/Sr/III) and joint connectors (`and`/`&`) dropped;
  compound/hyphenated surnames anchor on the last token (a simplification).
- **No-match handling:** `assign_...` deletes any prior links then inserts the new
  matches; a document with no asserted name or no match ≥ threshold ends with zero
  rows.
- **Counterparties excluded:** gift `donor_name` and purchase `seller_name` are not
  in the borrower-name registry, so they can't mislink.
- **Owner-name caveat:** `property_tax_bill` / `hoa_statement` name the current
  *owner*, who on a purchase is the seller; the threshold simply won't link a seller
  to a borrower — extracting the owner name is still honest.

## Post-review hardening (code review, 2026-07-09)

A review found the matcher produced **false links between same-surname family
members** — the common mortgage case, and a fabricated fact that would propagate
into `belongsTo`. Precision was fixed first. See the amendment in
[ADR-239](../../decisions.md).

- **[correctness] 1099 never linked.** `BORROWER_NAME_FIELDS` keyed the 1099
  mapping `"form_1099"`, but `Document.document_type` holds the slug `"1099"`, so
  every 1099 produced zero links. Fixed the key; added a test asserting
  `set(BORROWER_NAME_FIELDS) ⊆ set(EXTRACTORS)` so the drift can't recur.
- **[correctness] A non-matching name component now contributes zero.** A first
  name below the fuzzy bar previously still fed its raw ratio into the combined
  score; `John Smith` linked a document asserting `"Johnson Smith"`. Now a failed
  component scores `0.0` and cannot clear the anchor or pad the score.
- **[correctness] A bare initial confers no match.** A stray middle initial
  (`"Robert A. Smith"`) no longer links co-borrower `Andrew Smith`; an initial-only
  first name (`"A. Patel"`) no longer links `Akash Patel`.
- **[correctness] Short surnames must match exactly.** `Han` vs `Hahn` (and
  Lee/Li) no longer fuzzy-match — fuzzy requires both tokens ≥ 5 chars.
- **[recall] Shared nicknames now map to a set of canonicals.** `Stephen`↔`Steve`
  and `Catherine`↔`Kate` now link (previously the second canonical was dropped).
- **[integrity] Soft-deleted parents no longer leak links.**
  `get_document_borrower_links` joins the soft-delete-aware document + borrower via
  `only_active`, so a link to a removed borrower is never returned.
- **[convention] `method` is a CHECK-constrained `str_enum` (`MatchMethod`)** and
  `MatchResult.method` is `Literal["exact","normalized","fuzzy"]` — the value
  LP-206 branches on can't drift or typo silently (mirrors LP-201's
  `confidence_source`).

Tests were added from the **real** failure scenarios (same-surname co-borrowers,
short surnames, the `1099` slug, shared nicknames, soft-deleted borrower) — the
original tests missed these because they used unrealistic data.

## Deferred / follow-up

- **Compound / hyphenated surnames anchor only on the last token** (`Garcia Lopez`
  vs a doc saying `Maria Garcia`; `Smith-Jones` vs `Jane Smith`) → currently a
  `belongsTo: null` (a **safe miss**). Deferred deliberately: loosening the surname
  anchor fights the precision fixes above; revisit once precision is proven.
- **Three reimplemented helpers** → route through existing shared helpers as a
  follow-up: the typed-cell value accessor (`asserted_names_for` is a 5th copy of
  `entry.get("value")`), the current-extraction query (`_current_extracted_data`
  should call `documents.get_current_extraction`, which also applies
  `only_active(Extraction)` — the LP-202 copy omits it; latent today as nothing
  soft-deletes extractions), and the active-borrowers query (`_loan_file_borrowers`
  duplicates `borrowers.list_borrowers`).
- **Redundant per-borrower normalization** in `match_document`'s inner loop
  (each borrower's name is re-normalized once per asserted string) → hoist the
  per-borrower tokenization out of the loop as a follow-up.
- **No pipeline trigger.** `assign_document_borrower_links` is a library call;
  auto-invoking it on document processing is left to the consuming ticket (LP-206),
  per scope ("nothing consumes the link yet").
- **No backfill** of existing documents; links are produced on (re)match.
- The 3 no-clean-name types (`divorce_decree`, `letter_of_explanation`,
  `profit_and_loss`) were intentionally not given a name field.
- **Dev DB migration not applied** — same environment caveat as LP-201: the dev DB
  is stamped at a leftover `phase3_5_1` revision not on this branch, so
  `alembic upgrade` won't run cleanly there. The migration chains correctly on this
  branch (verified) and tests build the schema from metadata.
