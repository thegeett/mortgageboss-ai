# LP-830 — A document uploaded through the secure link is never processed

- **Ticket:** LP-830 · Phase 4 follow-up, from processor feedback on LF-JR4T
- **Status:** Specified — not started · **borrower-facing**
- **Date:** 2026-09-07
- **Scope:** `services/upload_links.py`, `services/inbound_triage.py`, `api/documents.py`
- **Migration:** none expected

---

## What was reported

> *"I uploaded file from special link for file LF-JR4T, but it shows processing only"*

## Measured, two ways, and they agree

**On staging.** The file's documents, newest first:

| status | source | type |
|---|---|---|
| **pending** | **secure_link** | *(none)* |
| completed | user_upload | w2 |
| needs_review | user_upload | *(none)* |
| completed | user_upload | pay_stub |
| *(eight more)* | user_upload | *(all typed)* |

Every document uploaded through the UI reached a terminal state. The one that arrived through the
secure link is `pending` with no type, and it is the only one.

**In the code.** `process_document.delay` is reached from exactly five places, and **all five are in
`api/documents.py`**. Four things create a document:

| creator | enqueues |
|---|---|
| `api/documents.py:359` — upload | yes, at :385 |
| `api/documents.py:856` — replace | yes, at :879 |
| `services/upload_links.py` — **the secure link** | **no** |
| `services/inbound_triage.py` — **accepted from email** | **no** |

So the document is not slow, and nothing is retrying. **No work was ever queued.** It will stay
`pending` forever.

## The class, and it is not one path

The two paths that enqueue are in the API module; the two that do not are in the service layer. That
is not a coincidence — `_enqueue_processing` is **module-private to `api/documents.py`**, so a
service cannot reach it without importing another module's private name.

Both non-enqueueing paths are the ones where the document comes from **outside**: a borrower's link
upload and a borrower's emailed attachment. Which is exactly where it matters most, and exactly
where a processor is least likely to be watching.

The inbound-triage half has been on the escalation list since LP-806, worded as *"accepting does not
enqueue processing"*, with the note that reaching into another module's private was outside that
ticket. It was filed as one gap. **It is two**, and the second is the one a borrower can reach.

## The screen is making a claim, and it is false

`lib/status.ts:78` maps `pending` to `{ label: "Processing", spin: true }`. A spinner means work is
in flight. Nothing is in flight. The animation is the product asserting something untrue, and it is
why the report reads "shows processing only" rather than "shows nothing" — a stuck document is
indistinguishable from a slow one, by design of the label.

## Done when

- A document uploaded through a secure link is processed: classified, extracted, and its need
  satisfied, the same as one uploaded through the UI.
- **The same is true of a document accepted from an inbound email.** Both members, or the fix is
  "found one, fixed one" on a class this ticket exists to name.
- The enqueue is reachable from the service layer without importing a private from `api/`. Wherever
  it lands, there is **one** enqueue that every creator uses — a second copy is how these two drifted
  apart in the first place.
- A test asserts, for **every** path that creates a document, that processing was enqueued. Written
  over the creators rather than as three separate cases, so a fifth creator inherits the requirement
  instead of quietly not having it.
- A broker failure still does not fail the upload. `_enqueue_processing` logs and moves on precisely
  so a borrower's bytes are never rejected because a queue was down; that property must survive.
- **The existing stuck document on LF-JR4T is processed**, or the user is told it must be
  re-uploaded. Fixing the path forward leaves a document sitting `pending` on a real file with a
  spinner next to it.

## For the reviewer

Two things to check that a green suite would not show.

**The count.** The fix must be verified by watching the document reach a terminal state, not by
asserting that a mock was called. A test that asserts `delay` was invoked passes against a Celery
app with no worker, which is the state this environment is usually in.

**The label.** If "Processing" with a spinner is kept for `pending`, then a document that is not
being processed still says it is. That is a smaller defect than this one and it is the reason this
one was invisible until somebody waited long enough to doubt it.
