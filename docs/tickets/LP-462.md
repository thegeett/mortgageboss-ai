# LP-462 — Classification Phase 1: recover the 8 infrastructure failures

Eight documents from the 889-doc bench never got a classification result — not because the model judged them
wrong, but because **the model call never completed**: four rejected by Bedrock for an oversized payload
(`BadRequestError`), four throttled in a consecutive burst (`RateLimitError`). All eight are types the
catalog handles when the call goes through. This ticket is **infrastructure only** — no judgment, prompt, or
indicator changes (that is Phase 2).

Method: read the shipped code paths and the bench's recorded outcomes; count the actual pages deterministically
(pymupdf). No model calls in Phase A.

---
## ⚠️ PHASE A — diagnosis (the code + the API's real limits are the gate)

### A1 — what is sent, the real limit, and the page cap

**What is sent today (quoted):** `classify_document` (`app/ai/classification.py:138,143`) sends the **entire
PDF**, base64-encoded, as one `document` content block — `build_document_block`
(`app/ai/client.py:101-125`) does `base64.standard_b64encode(content)` over the whole file; nothing is
sliced. Output is capped at `_MAX_TOKENS = 512` (a tiny JSON result — output is not the problem). The **input
payload is the whole document.**

**The real limit (evidence-backed, not guessed):** Anthropic's PDF `document` block is capped at **100 pages
and 32 MB per request** (the same limit on the direct API and on Bedrock). The four `BadRequestError` docs
(deterministic page counts):

| doc | source | pages | size |
|---|---|---|---|
| 060 | Prior Closing Disclosure / Final CD (closing package) | **141** | 3.32 MB |
| 066 | Daniel McKinnon final closing package | **148** | 6.28 MB |
| 069 | Closing package | **118** | 2.58 MB |
| 075 | CC&Rs / Bylaws (condo declaration) | **177** | 10.85 MB |

**All four exceed 100 pages; all four are under 32 MB** → the binding constraint is the **100-page** limit,
not bytes. (Cross-check: the four `RateLimitError` docs are 1–47 pages / ≤2.2 MB — well under both limits, so
their failure is purely throttling, a clean separation of the two modes.)

**Proposed page cap: classification reads the first `classification_max_pages` = 15 pages** (a new setting,
so it is tunable without a deploy). Justification:
- Classification needs to identify the **lead** document, not read the whole file. A Closing Disclosure, a
  condo declaration, an appraisal, a tax return, a bank statement are all identifiable in the first 1–3
  pages. 15 gives generous headroom for a cover page + the start of a second document.
- 15 pages of even the 177-page / 10.85 MB doc is ≈ 1 MB and 15 pages — an order of magnitude under both
  limits, so the `BadRequestError` cannot recur.

**⚠️ The trade-off of a cap that is too tight (stated, per the ADR):** 060/066/069 are **closing packages** —
multi-document bundles. If a package's *substantive* document begins after the cap, classification will label
it by its **lead** document (or as a generic closing package). That is the **correct behaviour for Phase 1**:
the type is recovered, and a genuinely multi-document package is a **splitter** problem (out of scope), not a
classification error — the known cases 167 and 271 (a package whose second document is the substantive one)
belong to the splitter work, and Phase C will flag any of the four that is really multi-document rather than
treat it as a miss. A cap far tighter than 15 (e.g. 1–2 pages) would raise the risk of missing an early
second document; 15 keeps that risk low while staying safe.

**⚠️ Extraction is NOT capped (and must not be).** Extraction goes through the **same** `build_document_message`
with the full PDF (`app/ai/extraction/*` → `run_extraction_completion` → `complete`), so a >100-page document
would hit the identical 100-page wall in extraction. **But extraction genuinely needs more pages than
classification** — extracting a Closing Disclosure or a tax return requires the substantive pages, not just
the lead. Did extraction run on the four oversized? **No** — classification routes extraction
(`document_processing.py`: a failed/`unknown` classification never reaches the extractor), so extraction never
executed on these four. The classification cap is therefore **classification-only**; extraction on a
>100-page document remains a **known open gap** whose real fix is the splitter (a per-document extraction
after splitting), NOT a page cap. This ticket does not touch extraction's page handling.

### A2 — the rate-limit path

**Current error handling (quoted).** `complete` (`app/ai/client.py:376-411`) **already** retries transient
failures: `_is_transient` (`:236`) returns True for HTTP 429 (`_RATE_LIMIT_STATUS`), 5xx, connection/timeout,
**and** the Bedrock throttle codes (`_BEDROCK_TRANSIENT_CODES` = throttling/modelnotready/serviceunavailable/
toomanyrequests, matched against the type name + message + response body — `:214`). The retry uses
`_backoff_delay` (`:292`): **exponential backoff with full jitter** — `base_delay * 2**(attempt-1) *
uniform[0.5,1.5)`. Bounds: `ai_max_retries = 3`, `ai_base_retry_delay_seconds = 1.0`. On exhaustion or a
non-transient error it raises `AIClientError(f"AI call failed: {type(exc).__name__}") from exc` — **preserving
the original exception as `__cause__`.**

**So a `RateLimitError` DOES reach a retry** — it is not failed immediately. It becomes `AI call failed` only
after 3 jittered attempts. **Why did four consecutive still fail?** Two compounding reasons:
1. **The limiter is per-process** (`app/ai/rate_limit.py:120-121`, "The process-local limiter"). The Bedrock
   account quota (~10 req/min) is **shared** across the FastAPI process AND every Celery worker, but each
   process has its **own** `RateLimiter` set to `ai_requests_per_minute_bedrock`. Two processes each pacing at
   8/min = 16/min against a 10/min quota → the account is breached even though no single process thinks it is
   over. A sustained bench burst then exhausts all 3 retries because the *aggregate* rate never drops.
2. **A burst is not a single spike.** Three jittered retries (≈1–7 s total) do not outlast a multi-second
   burst where every process is still calling; "four consecutive" is the signature of exactly that.

**⚠️ The real production gap — throttled is indistinguishable from failed.** `classify_document` catches
`AIClientError` and returns `ClassificationResult.unknown("AI call failed")` at **zero** confidence
(`classification.py:149-151`). The pipeline (`document_processing.py:148`) then routes any `unknown` /
low-confidence result to `NEEDS_REVIEW` with **reason `"low_confidence"`** — i.e. **a throttle is recorded as
a low-confidence *judgment***, which reads as a schema/coverage finding and corrupts every downstream audit.
The **bench already makes the distinction** it needs (`app/dev/bench/prompt.py:53-67`): it inspects
`AIClientError.__cause__` and, if `_is_transient(cause)`, tags the document `rate_limited` (vs a non-transient
auth failure, tagged failed-but-not-throttled). **Production classification does not** — it discards the
`__cause__`. This is the fix: classification must surface the infrastructure cause so a throttle/oversize is
recorded distinctly from a judgment.

**Proposed backoff / distinction (the retry mostly exists — the *surfacing* does not):**
- **Keep the existing backoff** (exp + full jitter, 3 attempts) — it already covers 429 + Bedrock throttle for
  all callers. I do **not** propose changing `ai_max_retries` or the limiter's steady-state rate (that would
  touch every caller's latency and the steady-state throughput — out of proportion, and cautioned by scope).
- **Surface the outcome in `ClassificationResult`.** Add an optional infrastructure-outcome field (e.g.
  `infra_failure: "rate_limited" | "oversized" | None`), set by inspecting `AIClientError.__cause__` with the
  same `_is_transient` logic the bench uses (throttle → `rate_limited`; `BadRequestError`/oversize →
  `oversized`; other → a plain failure). The pipeline records that distinct reason on the NEEDS_REVIEW
  activity (`"rate_limited"` / `"oversized"` instead of `"low_confidence"`), so a throttled document is
  **re-runnable and never reads as a schema gap.** Additive; a successful classification is unchanged.

### A3 — blast radius

Both concerns touch the shared client, so I scoped the fixes to avoid it:
- **`complete()` is called from 13 sites** (classification, extraction via `model_call`, and reasoning:
  `rule_judgment`, `tag_production`, `tag_correlation`, `tag_materialization/ai`, `observation`,
  `generic_analyzer`, `cross_source`, `summarization`, `finding_guidance`). **Neither LP-462 fix changes
  `complete()`** — the backoff already exists and is left as-is.
- **The page cap lives in `classify_document`**, before `build_document_message` — it slices the PDF only when
  `page_count > classification_max_pages`, and only for `application/pdf`. A ≤15-page document (every
  currently-succeeding classification) is byte-identical to today. **Zero effect on extraction/reasoning.**
- **The throttle-vs-failed surfacing lives in `classify_document`'s except block + the pipeline's reason
  string** — it changes only the METADATA on a failure path, never a success. **Zero effect on any other
  caller.**
- **Confirmed:** neither fix alters behaviour for calls that currently succeed.

## PHASE B — build (decisions: surface-only retry; result-field + pipeline-reason distinction)

1. **Page cap.** New `classification_max_pages = 15` setting (`config.py`). `pdf_utils.first_n_pages(content,
   n)` returns a PDF of the first `n` pages (pymupdf `insert_pdf`), the **original bytes unchanged** when the
   doc is already ≤ n pages (no re-encode), or `None` for a non-PDF/unreadable input. `classify_document`
   slices only `application/pdf` over the cap before `build_document_message`; a non-PDF/None sends the
   original. **Classification-only — extraction is untouched.**
2. **Throttle-vs-failed surfacing.** `client.infra_failure_kind(AIClientError)` classifies by `__cause__`
   (the same `_is_transient` the retry + bench use): `rate_limited` (429 / Bedrock throttle / 5xx /
   timeout), `oversized` (HTTP 400), else `failed`. `ClassificationResult` gains an optional
   `infra_failure` field; `classify_document`'s `except` sets it and logs `classification_ai_failed` with the
   kind. The pipeline (`document_processing.py`) adds an **infrastructure gate before the low-confidence
   gate**: an `infra_failure` result → `NEEDS_REVIEW` with reason `rate_limited`/`oversized`/`failed`
   (+`infra_failure=True`), **not** `low_confidence`. A throttle is now re-runnable, never a coverage gap.
3. **`complete()`, the backoff, the limiter rate, and extraction's page handling are unchanged** (surface-only
   decision).

## ADR
- **Classification page cap = first 15 pages.** Classification identifies the lead document; 15 pages is far
  under the 100-page/32 MB Bedrock limit and generous enough to catch an early second document. **Trade-off —
  a cap makes first-document lock-in MORE likely, not less:** a package whose substantive document begins
  after the cap is classified by its lead. **The counter-example is 271** — the classifier locked onto a small
  1099-INT at the front and dropped ~$173k of W-2 wages behind it; a page cap can only worsen that lock-in.
  This is acceptable for Phase 1 (the type is *recovered*, the call *completes*), but it is a concrete
  argument the **splitter** work will have to answer — the cap trades "no result at all" for "the lead
  document's result," and on a mixed package the lead is not always the substantive one. Not a bigger cap;
  a splitter.
- **Retry: surface-only (decision).** The existing backoff (exp + full jitter, 3 attempts, covers
  429 + Bedrock throttle) is left untouched. Raising the attempt count to survive a burst would add worst-case
  latency to all 13 `complete()` callers to treat a symptom in the wrong place; the throttle *tag* + re-run is
  the right recovery. `ai_max_retries` and the limiter rate are unchanged.
- **⚠️ DEFERRED TICKET (explicit, not a footnote): a shared/coordinated rate limiter.** The account's Bedrock
  quota (~10 req/min) is **shared**, but `RateLimiter` is **per-process** — so any concurrent Celery work can
  breach the quota regardless of how correctly each process paces. **This WILL recur and gets worse as the
  system scales out** (more workers = more uncoordinated pacers against one quota). The fix — a shared
  limiter (e.g. Redis-backed) or auto-lowered per-process rpm under concurrency — **touches the shared client
  that every extraction and reasoning call goes through, so it needs its own equivalence proof** and does not
  belong in a ticket scoped to recovering 8 documents. Filed as the follow-up below.

## What Phase 2 / follow-ups must now do
- **Judgment (Phase 2):** prompts / indicators / the taxonomy — **not** touched here. (Confidence does not
  predict correctness — 0.75–0.99 were all wrong on other docs — so no confidence threshold was added.)
- **Deferred ticket — shared/coordinated rate limiter** (see the ADR): the per-process limiter cannot honour
  a shared account quota under concurrent Celery load; a Redis-backed or concurrency-aware limiter, with its
  own equivalence proof over the shared client. This recurs and worsens with scale-out.
- **The splitter** for genuinely multi-document packages (060/066/069 candidates; 167, and 271 — where the
  lead document is NOT the substantive one). The classification page cap makes the lead-document lock-in more
  acute, so the splitter is the real answer, not a larger cap.
- **The extraction-on-large-documents gap** (a >100-page doc cannot be extracted whole) — splitter-dependent;
  the classification cap is deliberately NOT applied to extraction.
