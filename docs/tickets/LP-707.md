# LP-707 — ask the model for anchors, not for a retyped snippet

- **Ticket:** LP-707 (LP-700 series, 2 of 4)
- **Status:** Done (2026-09-06) — **but not as written.** Measuring first, which this ticket required, showed the 119-prompt rewrite is not needed. The goal was reached in the matcher. No prompt was changed.
- **Scope:** Backend — `ai/prompts/extraction/*.txt` (119 files), `ai/extraction/parsing.py`,
  `services/field_boxes.py`
- **Prompts changed:** all of them. **Extra AI calls:** none. **New dependencies:** none.

## The idea in one line

Retyping a value is a task the model can fail at silently. Naming the words *around* it is
easier and checkable.

## How it works today

Each field's provenance is `{"page": <int>, "snippet": <verbatim text>}`. Two things go
wrong with that contract, and they are different problems:

- The **page** is a number the model writes from memory. Measured: 4.3% of fields name a page
  the document does not have. Not one is an off-by-one; they are inventions.
- The **snippet** must be transcribed exactly for a literal search to find it. LP-706 makes
  that tolerant, but a snippet the model paraphrased or normalised is still unfindable.

## What changes

Replace the bare snippet with a **location hint**: the verbatim value plus 5–10 words of
surrounding context as anchors. This is what production grounding systems ask for, because
a run of neighbouring words is far more distinctive than a value alone and turns a
whole-page search into a targeted lookup.

The page number is then **derived from where the anchors were found**, not trusted from the
model. A page it invented cannot survive, because nothing looks there.

## Behaviour by document kind

| | what happens |
|---|---|
| **Text PDF** | Recovers the fields LP-706 still cannot place, and removes invented pages. |
| **Scanned PDF** | No box — still nothing to anchor against. **But the page number stops being invented**, which matters on its own: the reviewer navigates to the right page even when it cannot highlight anything on it. |
| **Mixed PDF** | Anchors resolve on the text pages; the scanned pages behave as above. |
| **Image** | One page, so a page number is trivially right. No box until LP-708. |

## Why this is second, not first

It touches 119 prompt files and the shared parser, and it interacts with the prompt-cache
breakpoint in `ai/client.py`, which is tuned against a 4,096-token minimum and fails
**silently** when disturbed. LP-706 must be measured first, so the gain from this one is
known rather than assumed — if fuzzy matching alone recovers most of the bucket, this may
not be worth the blast radius.

- [ ] Prompt-cache hit rate measured before and after, not assumed unchanged
- [ ] The old `snippet` shape still resolves, for every extraction already stored

## The rewrite was measured and rejected

This ticket said, in its own words: *"LP-706 must be measured first, so the gain from this
one is known rather than assumed — if fuzzy matching alone recovers most of the bucket, this
may not be worth the blast radius."* That measurement was done, and it disposed of the
premise.

**The snippet is not wrong. It is a SYNTHESIS.** Of the 72 fields the earlier tiers could not
place on typed documents:

```
  61  ALL of the snippet's words are on the page
  11  SOME of the snippet's words are on the page
   0  none of it is on the page
```

Not one field has a snippet the page does not contain. What the page does not contain is the
whole snippet **as one contiguous run** — because the model writes things like

> "Total Taxes $3,663.31 + Total Pre-Tax $1,410.00 + Total Post-Tax $335.00"

which is three figures from three places joined by its own arithmetic. Asking the model for
neighbouring words as anchors would not have improved that: the words were already there.
The matcher was demanding all of them together.

## What shipped instead: a fourth tier, in the matcher

`MatchKind.PARTIAL` — the longest run of the snippet's words the page actually has, and only
ever a run **containing the extracted value**.

**The anchor rule is what keeps it from being a licence to match anything.** Taking the
longest run that merely occurs recovers all 72 — at a median of half the snippet and a
minimum of **3% of it**, which is one word in thirty and no evidence at all. Requiring the
run to contain the value recovers 26, and each of those is a box over text that demonstrably
includes the figure being cited. The other 46 keep their honest no-box state.

## Coverage now, on typed documents

```
  562 fields
  516 placed (91.8%)
      486  exact       the model's quoted text, verbatim
       30  partial     the confirmable part of a synthesised snippet
       46  none
```

From 84.7% before LP-706 to **91.8%**, with no prompt changed, no extra AI call, no cache
risk, and nothing to re-extract — the whole series' gain on typed documents reaches every
document already stored.

## What LP-707 would still have bought, and why it is not worth it

Two things, and both are smaller than they looked:

**Invented page numbers.** 4 fields of 562. And they already cost almost nothing: the
matcher falls through to a whole-document walk and reports `cited_page_exists=False`, so the
screen already says the citation was wrong rather than hiding it.

**A location for genuinely derived values.** The 46 remaining are values the model computed —
`ytd_gross`, `hours`, `pay_frequency`, `total_deductions_current`. A prompt could ask the
model to anchor those to their INPUTS, which is a real idea and a different feature: it is
not "where did you read this", it is "what did you read to work this out". That deserves its
own ticket and its own argument, not a rewrite of 119 files justified by this one.

**The blast radius that is not being spent:** 119 prompt files, the shared parser, and the
prompt-cache breakpoint in `ai/client.py` which is tuned against a 4,096-token minimum and
fails *silently* when disturbed.
