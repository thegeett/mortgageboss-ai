# LP-707 — ask the model for anchors, not for a retyped snippet

- **Ticket:** LP-707 (LP-700 series, 2 of 4)
- **Status:** Done (2026-09-06) — **but not as written.** Measuring first, which this ticket required, showed the 119-prompt rewrite is not needed. The goal was reached in the matcher. No prompt was changed.
- **Scope:** Backend — `ai/prompts/extraction/*.txt` (119 files), `ai/extraction/parsing.py`,
  `services/field_boxes.py`
- **Prompts changed:** all of them. **Extra AI calls:** none. **New dependencies:** none.

## The idea in one line

Retyping a value is a task the model can fail at silently. Naming the words *around* it is
easier and checkable.

## How it works today

Each field's provenance is `{"page": <int>, "snippet": <verbatim text>}`. Two things go
wrong with that contract, and they are different problems:

- The **page** is a number the model writes from memory. Measured: 4.3% of fields name a page
  the document does not have. Not one is an off-by-one; they are inventions.
- The **snippet** must be transcribed exactly for a literal search to find it. LP-706 makes
  that tolerant, but a snippet the model paraphrased or normalised is still unfindable.

## What changes

Replace the bare snippet with a **location hint**: the verbatim value plus 5–10 words of
surrounding context as anchors. This is what production grounding systems ask for, because
a run of neighbouring words is far more distinctive than a value alone and turns a
whole-page search into a targeted lookup.

The page number is then **derived from where the anchors were found**, not trusted from the
model. A page it invented cannot survive, because nothing looks there.

## Behaviour by document kind

| | what happens |
|---|---|
| **Text PDF** | Recovers the fields LP-706 still cannot place, and removes invented pages. |
| **Scanned PDF** | No box — still nothing to anchor against. **But the page number stops being invented**, which matters on its own: the reviewer navigates to the right page even when it cannot highlight anything on it. |
| **Mixed PDF** | Anchors resolve on the text pages; the scanned pages behave as above. |
| **Image** | One page, so a page number is trivially right. No box until LP-708. |

## Why this is second, not first

It touches 119 prompt files and the shared parser, and it interacts with the prompt-cache
breakpoint in `ai/client.py`, which is tuned against a 4,096-token minimum and fails
**silently** when disturbed. LP-706 must be measured first, so the gain from this one is
known rather than assumed — if fuzzy matching alone recovers most of the bucket, this may
not be worth the blast radius.

- [ ] Prompt-cache hit rate measured before and after, not assumed unchanged
- [ ] The old `snippet` shape still resolves, for every extraction already stored

## The rewrite was measured and rejected

This ticket said, in its own words: *"LP-706 must be measured first, so the gain from this
one is known rather than assumed — if fuzzy matching alone recovers most of the bucket, this
may not be worth the blast radius."* That measurement was done, and it disposed of the
premise.

**The snippet is not wrong. It is a SYNTHESIS.** Of the 72 fields the earlier tiers could not
place on typed documents:

```
  61  ALL of the snippet's words are on the page
  11  SOME of the snippet's words are on the page
   0  none of it is on the page
```

Not one field has a snippet the page does not contain. What the page does not contain is the
whole snippet **as one contiguous run** — because the model writes things like

> "Total Taxes $3,663.31 + Total Pre-Tax $1,410.00 + Total Post-Tax $335.00"

which is three figures from three places joined by its own arithmetic. Asking the model for
neighbouring words as anchors would not have improved that: the words were already there.
The matcher was demanding all of them together.

## What shipped instead: a fourth tier, in the matcher

`MatchKind.PARTIAL` — the longest run of the snippet's words the page actually has, and only
ever a run **containing the extracted value**.

**The anchor rule is what keeps it from being a licence to match anything.** Taking the
longest run that merely occurs recovers all 72 — at a median of half the snippet and a
minimum of **3% of it**, which is one word in thirty and no evidence at all. Requiring the
run to contain the value recovers 26, and each of those is a box over text that demonstrably
includes the figure being cited. The other 46 keep their honest no-box state.

## Coverage now, on typed documents

**These figures did not survive review — see "The partial tier was the value tier" below.**
The gain they report was real arithmetic over a tier that was not doing what this section
says it was doing, so the corrected numbers are in that section, not here.

```
  562 fields
  516 placed (91.8%)
      486  exact       the model's quoted text, verbatim
       30  partial     the confirmable part of a synthesised snippet
       46  none
```

From 84.7% before LP-706 to **91.8%**, with no prompt changed, no extra AI call, no cache
risk, and nothing to re-extract — the whole series' gain on typed documents reaches every
document already stored.

## What LP-707 would still have bought, and why it is not worth it

Two things, and both are smaller than they looked:

**Invented page numbers.** 4 fields of 562. And they already cost almost nothing: the
matcher falls through to a whole-document walk and reports `cited_page_exists=False`, so the
screen already says the citation was wrong rather than hiding it.

**A location for genuinely derived values.** The 46 remaining are values the model computed —
`ytd_gross`, `hours`, `pay_frequency`, `total_deductions_current`. A prompt could ask the
model to anchor those to their INPUTS, which is a real idea and a different feature: it is
not "where did you read this", it is "what did you read to work this out". That deserves its
own ticket and its own argument, not a rewrite of 119 files justified by this one.

**The blast radius that is not being spent:** 119 prompt files, the shared parser, and the
prompt-cache breakpoint in `ai/client.py` which is tuned against a 4,096-token minimum and
fails *silently* when disturbed.

## Review (2026-09-06)

### The partial tier was the value tier, one tier earlier, with the guard removed

The tier is described as "the longest run of the snippet's words the page actually has".
Instrumented over the stored corpus, that is not what it did. Of the fields it placed:

```
  45  placed by the partial tier
  45  placed on a run whose fold IS the value's — no context at all
  44  of those had no run carrying any context anywhere on the page
  38  were figures the DOCUMENT REPEATS
```

The 38 are the finding. `MatchKind.VALUE` sits below this tier precisely so a repeated
figure can be counted across the whole document and refused — that rule was made
document-wide in the LP-706/709 review, for the case of the same amount on two pages.
Ranking a bare-value match above the tier that counts it does not make it a stronger claim;
it only skips the counting. Measured before the fix, the value tier fired **zero** times on
the whole corpus: the partial tier had absorbed every field it used to guard.

The fix is one rule — the run must carry **strictly more than the value**. A run that turns
out to be the value and nothing else is not a partial quotation, and falls through to the
value tier, where it is counted document-wide and labelled for what it is.

The hypothesis that reached for first was wrong and is worth recording: the obvious
explanation is that LP-706's `_visually_contiguous` guard rejects label-and-figure pairs
sitting in separate table cells. Measured with that guard disabled, it accounts for exactly
**1** of the 45. For the other 44 no run with context exists on the page at all.

### The anchor was checked on the snippet, not on the page

`folded_value not in needle` is an unaligned substring test against the model's own snippet
text — the exact failure `_runs` carries a word-boundary rule to prevent. `fold("1,500.00")`
is `"1500"`, which is a substring of `fold("Escrow balance 21,500.00")`; `fold("Smith")` is a
substring of `fold("Blacksmith Holdings LLC")`. Both pass, and neither page says the value.
The anchor is now resolved on the page with `_runs` and the boxed run is required to
**contain** one, which is the guarantee the ticket already claimed in prose.

Finding the value's runs first also bounds the cost. The candidate walk is quadratic in the
snippet's words — a forty-word snippet is 820 folds and 820 substring searches, per page,
per field, measured at **8 ms per page per field** — and it ran in full on every page,
including the great majority that do not hold the value at all. A page that cannot anchor
anything now costs one search: 8 ms to 0.0 ms on that measurement.

### Corrected coverage

Re-measured with one harness across both states, so the two lines are comparable to each
other rather than to the numbers above (this selection keeps 69 typed documents / 608 valued
fields; the original run's selection differed and is not reproducible from the repo):

```
  as committed   562 placed (92.4%)   515 exact,  2 normalised, 45 partial,  0 value, 46 none
  corrected      524 placed (86.2%)   515 exact,  2 normalised,  0 partial,  7 value, 84 none
```

**The corrected tier fires zero times on the TYPED selection above** — confirmed against a
control run with the tier deleted from the walk entirely, which places the identical 524. So
LP-707's measured gain on typed documents is nil, and the 38 boxes it removed are figures the
document repeats.

**Not zero over the whole corpus, though, and this section said so before it was measured.**
Re-run across all 79 documents rather than the 69 typed ones — scanned pages included, so
OCR supplies the word rectangles — the tier fires twice, and the folded tier that had fired
twice fires 27 times:

```
  691 fields, 79 documents   556 placed (80.5%)
      515 exact   27 normalised   2 partial   12 value   135 none
```

Both partial matches carry context, by the rule: a run that reduces to the value is no longer
this tier. So the honest statement is nearly inert rather than inert, and the tier is kept on
the same footing as `NORMALISED` — a demonstrated failure mode real documents almost never
present. If a later corpus shows it still dead, delete it.

### The OCR budget from LP-708 was never spent

Not LP-707's, but in the file it touches and introduced by the LP-708 **review**:
`_index_page` took a `budget` and called `_page_words(page)` without it, so `words_for`
always saw `None` and `MAX_OCR_PAGES_PER_REQUEST` bounded nothing. Measured: a 20-page
scan OCR'd 20 pages against a cap of 12. The budget's own test called `words_for` directly
and passed throughout — it tested the layer the rule was written at, not the layer a request
meets it at. There is now a test at the request layer, with a positive control.

### Mutations

Eight, seven caught: the budget dropped again, the context rule removed, the page-side
anchor filter removed, the value-first early return removed, `PARTIAL` dropped from the
walk, longest-run-first reversed, and `MAX_MATCHES` dropped from this tier.

Two of the eight survived the first sweep and both were tests of this review's own: the
early return and the containment filter each answered every illusion case, so either could
be deleted alone with everything green, and the cost test used a value absent from the
snippet, so the quadratic walk it was meant to bound never ran. Both now have a case that
isolates them.

One survivor stands, recorded rather than papered over: loosening containment to overlap
(`run[0] < v1 and v0 < run[1]`) passes. Reaching it needs an aligned occurrence of the value
straddling the matched run's edge *while* the run's own text separately contains the value's
characters at an unaligned offset; every construction attempted collapsed into containment.
It is treated as equivalent in practice, not as caught.
