# LP-420 — The combined labeling worksheet: one Priya session, the tags that survive D1

## What this ticket is

Six/seven AI tags each block a written rule (IN-8, IN-9, IN-12, IN-13, IN-14, AS-7, OC-1). Running a separate
calibration round per tag is the OC-1 economics mistake (a wave for one rule). This ticket generates **blind
worksheets** so ONE Priya session covers them — but only after a **D1 labelability census** decides which tags
are worth her time. **Worksheets only — no labeling, no scoring, no rules.**

The census is the real work: **four of the seven tags were EXCLUDED** (never spend her time on a thin or
one-sided tag — LP-395 / AS-6). Three passed and got worksheets.

## D1 — the labelability census (achievable n + value distribution)

| tag | rows | value distribution | verdict |
|---|---|---|---|
| `income.voe_present` | 12 | 6 VOE (yes-shaped) + 6 offer (no-shaped) — **2-sided** | ✅ include |
| `income.offer_letter_present` | 12 | 6 offer (yes) + 6 VOE (no/n/a) — **2-sided** | ✅ include |
| `income.continuance_3yr` | 6 | pension/alimony/child-support/disability/SS/note — **multi-sided** | ✅ include |
| `income.type` | 25 | **23 base + 2 bonus, 0 self-employment/rental** — one-sided | ❌ exclude |
| `txn.is_nsf_or_overdraft` | 0 | no fixture; per-transaction | ❌ exclude |
| `occupancy.rental_support` | 0 | no fixture; **loan-subject (1 row/loan)** | 🛑 stop |
| `occupancy.consistent_with_signals` | 0 | no fixture; **loan-subject** | 🛑 stop |

**The four exclusions (the census is this ticket's main value — it protects Priya's time):**

- **`income.type`** — the *priority* tag (it was to lead the session, unblocking IN-12 + IN-13) is the **least
  ready**. 25 rows but one-sided base wage, with an EMPTY positive class for `self_employment` (IN-12's gate) and
  `rental` (IN-13). Correction (LP-420 review): this is a **FIXTURE gap, not structural** — `income_amounts`
  reads `[pay_stub, w2, uniform_residential_loan_application]` and its `type` value space includes
  `self_employment`/`rental`, so a self-employed / rental **1003** (LP-419's `employment_type=self_employed`
  shape) WOULD produce them; no producer change is needed. **Excluded because authoring such a 1003 STAMPS the
  type (labeling our own invention) — the genuine unblock is a REAL self-employment/rental income file, out of
  scope.** This still corrects the ticket's premise that income.type just needs a labeling round.
- **`txn.is_nsf_or_overdraft`** — n=0. Building means inventing bank lines; "NSF FEE" pre-answers its own label,
  and the only ambiguous cases turn on the tag's *definition* (does an overdraft-protection transfer count?), a
  prompt question, not accuracy. **Needs real bank statements with genuine NSF activity.**
- **`occupancy.rental_support` + `occupancy.consistent_with_signals`** — loan-subject (one row per loan); n>=6
  means authoring 6+ whole loan files whose declaration-vs-signal (in)consistency / lease adequacy is the exact
  judgment — **labeling our own invention (STOP).** (OC-1's tag measures declaration consistency, LP-406-4.)

See **ADR-332** for the named rule: a tag whose correct label is determined by the fixture we invent is not
calibratable on synthetic data.

## D2 — anti-anchoring

The included tags' per-row AI answers were **not** published (LP-395/418 report counts and capacity, not
per-document answers), so there is nothing tag-specific to leak. Blindness is structural: `build_worksheet` is
**keyless** (context = snapshot facts + a neutral prompt, no AI), the header has no prediction/confidence/
reasoning column, and `golden_label`/`labeler_note` are blank on every row. Asserted by tests (header scan,
blank-label scan, prompt-rule scan).

## D3 — the session agenda (file split, counts, time)

Two committable files, **~30 rows, ~20 minutes** total (earlier rounds ran ~30–45 min for ~33 rows):

| order | file | tag(s) | rows | ~time | what this decides |
|---|---|---|---|---|---|
| 1 | `income-docs-voe-offer-labels.csv` | voe_present + offer_letter_present | 24 | ~15 min | whether the file's employment documents are told apart — a VOE vs an offer letter. Unblocks IN-8, IN-9. |
| 2 | `income-continuance-3yr-labels.csv` | continuance_3yr | 6 | ~5 min | whether each borrower's non-employment income will last long enough to count. Advances IN-13. |

(`income.type` was to lead — it is excluded, so voe/offer lead.) The one-line notes live in `SHEET_NOTES`
(combined_labeling_worksheet.py) and here — context, never a hint at any answer.

## D4 — the label prompts (quoted; values, not rules)

- **voe_present:** `Is this document a Verification of Employment (VOE)? yes / no`
- **offer_letter_present:** `Is this an employment offer letter stating a future start date? yes / no / n/a`
- **continuance_3yr:** `Is this income likely to continue for at least 3 years? yes / no / unknown`

Each shows the allowed VALUES so she can choose; none restates the model's rules for choosing (no "a VOE is
signed by the employer", no "income with a defined end date is 'no'"). (The two loan-subject occupancy prompts —
`occupancy.consistent_with_signals` especially, which had to ask about *declaration consistency* not the address
— were not written: their tags were excluded before a prompt was needed.)

## The verification (reported, not predicted)

- **Anti-anchoring:** header carries no prediction/confidence/reasoning/expected column; every `golden_label` and
  `labeler_note` is blank; the prompt scan finds none of the model's decision-rule phrases.
- **Sample row (voe/offer):**
  `income.voe_present, 95-offer-0, employment_offer_letter, ... , context: employer_name=Summit Robotics;
  candidate_name=Dana Brooks; position=Analyst; start_date=2026-09-01; annual_salary=95000.00 | Is this document
  a Verification of Employment (VOE)? yes / no`. Judgeable: the document's own fields tell her it is an offer
  letter, not a VOE — she does not need the file open.
- **Sample row (continuance):**
  `income.continuance_3yr, ...101, borrower, context: [uniform_residential_loan_application]
  other_income_type=pension; other_income_description=Retirement pension, $1,800/mo, no stated end | Is this
  income likely to continue for at least 3 years? yes / no / unknown`. The continuance horizon ("no stated end",
  "matures 2027", "through 2031") is a FACT on the 1003 she reads to judge — not an AI answer (judgeability, the
  LP-390-3 lesson).
- **Row order:** voe/offer interleaves the two source types (voe, offer, voe, offer…) within each tag block and
  groups by tag (a document's two rows sit 12 apart); continuance uses a fixed non-insertion permutation.
- **Byte-stable + keyless:** a fresh generation equals the committed files; regeneration is deterministic.
- **Equivalence:** no tag/rule/producer/prompt change; the other four worksheets + all fixtures byte-unchanged;
  `ACTIVE_RULE_IDS` = 30.

## Which rules each sheet unblocks + what happens after she labels

- voe_present → **IN-8**; offer_letter_present → **IN-9**; continuance_3yr → **advances IN-13** (IN-13 also needs
  `income.type`, which is excluded — so IN-13 stays blocked on income.type).
- **After labeling:** a scoring ticket per tag reads the filled CSV, scores the AI against her goldens, and — if
  the accuracy clears a Priya bar — sets the activation bar so the rule can go live. That scoring/bar work is a
  later ticket per tag (NOT this one).
- **Still blocked (reported):** IN-12 + IN-13 (income.type — producer/real-data), AS-7 (NSF — real statements),
  IN-14 + OC-1 (occupancy — real files). ADR-332 records why.

## Assumptions / decisions

- The D1 census is the gate of record over the ticket's "seven rules" premise (the ticket itself says the
  producers/fixtures/published docs beat its text). An honest census that includes 3 and excludes 4 is the
  intended output of a ticket whose first instruction is "never spend her time on a thin tag."
- No new scenario built: the tags that would need one are exactly the excluded ones, which cannot be built
  without inventing the label.
- The worksheet `consuming_rules` column shows the `_GROUPS` display metadata (voe/offer → IN-2, continuance →
  IN-4), left unchanged (changing it is a worksheet-metadata edit out of scope and not anchoring-relevant).

## New gap

- `income.type`'s producer reads only `pay_stub`/`w2`; `self_employment` (IN-12) and `rental` (IN-13) can never
  materialize from it. Until a producer reads the document types those values live on (tax returns / Schedule E),
  IN-12's self-employment gate and IN-13's other-income scope cannot be calibrated. Recorded in ADR-332.
