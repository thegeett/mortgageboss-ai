# LP-618 — One verification at a time, and a queue wait that fails the run

## The report

> "let's assume there are N files and people are working on them — even if one is running,
> all N-1 have to wait."

Correct, and observed live. Two files were verified together on 2026-08-21:

```
LF-3CVT  enqueued 19:27:41  picked up 19:27:41  completed 19:34:20   (6m40s)
LF-T9HD  enqueued 19:27:50  picked up 19:34:20  — waited the whole of the first run
```

Both rows read `RUNNING` in the database the entire time. Only LF-3CVT had a
`verification_progress` row, which is why the UI showed progress for one file and nothing for the
other. The second file was queued, not running, and nothing said so.

## Why only one runs

`worker_cpu = 1024` is ONE vCPU, and the worker command carries no `--concurrency`, so Celery
defaults to `os.cpu_count()` = **1**. `desired_count = 1`, and it is a single variable for every
service, so raising it scales the API and frontend too. The module states there is deliberately no
autoscaling.

## Bedrock is NOT the constraint, and this is measured

The obvious suspicion is the rate limiter. It is not. From the 19:27 LF-3CVT run:

| | |
|---|---|
| Model calls in one full verification | **271** |
| Run duration | 6 min 40 s |
| Average request rate for one run | **~40 RPM** |
| Time lost to the limiter across the whole run | **2.1 s** over 20 waits (longest 0.207 s) |
| Our self-imposed limit | 2000 RPM per process |
| Account quota | 10,000 RPM |

A verification needs about **40 RPM** against a 10,000 RPM account. On request rate alone the
account supports roughly **250 concurrent verifications**, or ~50 holding to the deliberate 20% of
quota. The limiter cost two seconds out of four hundred — it is a backstop, not a throttle.

The constraint is that we launch one process. Nothing else.

## Part 1 — size the worker for concurrent users

Concurrency is set by processes and memory; the per-process rate is then quota ÷ processes.

| Target simultaneous runs | worker_cpu | worker_memory | worker_concurrency | `ai_requests_per_minute_bedrock` |
|---|---|---|---|---|
| 2 | 1024 | 4096 | 2 | 1000 |
| 6 | 2048 | 8192 | 6 | 333 |
| 10 | 2048 | 16384 | 10 | 200 |

Even the last row leaves each process 200 RPM against the ~40 a run uses, and totals 2000 — the
same 20% of quota as today. Memory drives the cost: each prefork child is a full interpreter.

**Every row REQUIRES dividing `ai_requests_per_minute_bedrock` by the process count.** The limiter is
process-local by design (`app/ai/rate_limit.py`), so N processes at the current 2000 would pace at
N x 2000 — the silent rate multiplication the `desired_count` warning already describes.

A prototype of this (a `worker_concurrency` variable threaded through the compute module, wired into
the worker command, with the tfvars halved to match) was written and `terraform validate`d, then
reverted pending a decision on the target number. It is a small change.

## Part 2 — the watchdog fails a run for waiting

**This is a correctness bug, not a capacity one, and it should be fixed regardless of Part 1.**

`create_verification_run` stamps `started_at = utcnow()` at CREATION — enqueue time — and nothing
re-stamps it when the worker picks the task up. `_reconcile_stuck_run` then fails any `RUNNING` run
older than `_STUCK_RUN_TIMEOUT_SECONDS = 1500` (25 min). So **queue wait counts against a run's own
timeout.** At ~7 min per run and one slot:

| Queue position | Starts | Finishes | Age at completion |
|---|---|---|---|
| 1 | 0 | 7 | 7 |
| 2 | 7 | 14 | 14 |
| 3 | 14 | 21 | 21 |
| **4** | 21 | 28 | **28 — past the 25-minute watchdog** |

The 4th queued file is marked FAILED for waiting. Two aggravations:

- The watchdog fires on an **API read** (`api/verification.py:405`), so it triggers when a processor
  opens the file to check on it — they see "failed" on a run that is queued or running normally.
- Marking it FAILED does not stop the task. The worker later completes the same run, so a run can go
  FAILED then COMPLETED.

**The fix needs TWO timeouts, not one.** A *queue* timeout (nothing ever picked this up — a dead
worker, which is what LP-89 was built to catch) and a *run* timeout (picked up, then hung).
Collapsing them into one clock is what makes a busy queue indistinguishable from a crash. That means
recording a pickup time on the run and measuring the run timeout from it.

Worth fixing alongside: the run is `RUNNING` while it is really queued, and the UI has no way to say
"waiting to start" — which is the whole of what was confusing about LF-T9HD.

## Part 3 — production needs autoscaling, and that needs a shared limiter

A fixed process count is a staging answer. Real simultaneous users want workers autoscaled on queue
depth — and that is blocked by the per-process limiter, because a rate that must be divided by hand
by the process count cannot be correct when the process count changes by itself. Moving the limiter
to Redis is the prerequisite, and `rate_limit.py`'s own header names it: "a distributed limiter needs
Redis coordination on the hot path of every model call, which is a different (and much heavier)
decision."

## Order

Part 2 first — it produces wrong answers rather than slow ones, and it is contained. Then Part 1 with
a chosen target. Part 3 when sizing for real usage.
