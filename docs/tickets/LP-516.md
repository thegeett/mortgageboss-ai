# LP-516 — AS-12: scope by loan purpose, and give it the inputs its prompt asks for

**Status:** Phase A complete — stopped for decisions. Nothing implemented.

## Phase A findings

### A0 — Branch conflict (raised before any work)

The ticket says branch `phase3_bucket_2_fast`. **That branch does not contain LP-509** (it sits at
LP-498-era code, tip `6d6e295`). Consequences if LP-516 is built there:

- AS-12 has no `txn.is_money_in` applicability predicate, so it still evaluates all 57 transactions
  including ATM fees and utility bills. The ticket's premise — "10 findings remaining after
  LP-509-A1" — is not true on that branch.
- Phase C cannot be reproduced there: the ten deposits it names are a post-LP-509 measurement.
- Both tickets edit `AS-12.yaml`, so a later merge conflicts.

This also explains the ticket's `rule_kinds.csv 135`: correct on `phase3_bucket_2_fast`, **stale on
`bedrock_integration_with_rules_staging`, where it is 136** (LP-509-D1 added IH-9). `SNAPSHOT_VERSION`
is 4 ✓ and `activation_census.py` is present ✓.

**Recommendation:** build on `bedrock_integration_with_rules_staging`, which carries LP-509 and is what
staging runs.

### A1 — The abstain fallback: use the operand AS-1 actually uses

⚠️ **The ticket (and the decision brief before it) both name the wrong tag.** AS-1 does NOT read
`income.qualifying_monthly`. It reads **`dti.qualifying_income_monthly`**, and AS-1's own spec says why:

> ⚠️ STATED, NOT QUALIFYING (priya_validated:false — needs sign-off): `dti.qualifying_income_monthly`
> sums the MISMO STATED 1003 income, but the guideline below is 50% of QUALIFYING income. STATED >=
> QUALIFYING … so this threshold is LOOSER than the guideline … Accepted provisionally (the qualifying
> tag is underspecified — LP-343 F2 — and degraded live).

So `income.qualifying_monthly` is *known-degraded* and is not in live use for this purpose. Building
AS-12's threshold on it would build on the worse of the two inputs.

**Measured resolution of `dti.qualifying_income_monthly` across the local corpus (21 loan files):**

| | files | resolves |
|---|---|---|
| With a MISMO import + stated income | 12 | **12 / 12** |
| No MISMO import (manually created) | 9 | **0 / 9** |

The correlation is exact — every resolving file has `mismo_imports=1` and stated income items; every
`unknown` has neither. So the input does not fail on *real* files; it fails on files that have no 1003
at all, where there is genuinely no income baseline to be 50% of.

Corroboration on LF-WCHG: AS-1 returned `satisfied` (not `couldnt_check`) on all ten deposits, which it
can only do if the threshold operand resolved.

**Decision: abstain to `couldnt_check`, mirroring AS-1's documented "absent/unknown income → None →
couldnt_check (never 0 — a 0 threshold would fire on every deposit)".** Do NOT fall back to
`documented_monthly` or `stated_monthly`: a different denominator from AS-1 would make the two rules
disagree about what "large" means on the same deposit, which is worse than abstaining. Inherit AS-1's
known stated-vs-qualifying deviation rather than inventing a second, different one.

### A2 — "Verified accounts" is NOT checkable ⚠️

The guide's exemption is for a *transfer of funds between **verified** accounts*. Both sides of that
match are deliberately unavailable in the snapshot:

| | |
|---|---|
| `stmt.account_masked` | *"Masked account number (**display only, non-matchable** — no raw on branch)"* |
| transaction `description` | *"any 9+-digit identifier (incl. space/dash-grouped accounts/cards) … redacted so it is PII-safe at rest"* |

A weak heuristic remains possible (institution name + a surviving last-4 in the description against the
masked account's last-4), but it is fuzzy text matching against a field the vocabulary explicitly says is
not for matching, and last-4 collisions are real.

**Therefore: if the refinance exemption is implemented on `apparent_category == transfer_own` alone, it
rests on the AI's category judgement, NOT on the guide's condition.** That is weaker than the guideline
and must be recorded as such.

**This is not hypothetical on LF-WCHG.** The six own-transfers come from Digital Federal Credit Union
(4–5 of them) and a Wells Fargo Way2Save savings account (1–2). **There is no DCU statement anywhere in
the batch folder**, uploaded or not — so those accounts are not verified in any sense, and a faithful
reading of the guide would NOT exempt them.

### A3 — `loan.purpose` resolves

Verified end-to-end during LP-509-A5: `refinance` → `not_applicable`, `purchase` → the rule runs,
absent → `couldnt_check`. LF-WCHG's value is `refinance`, confirmed twice (the MISMO parse and the Final
CD's extracted `loan_purpose`). The applicability-predicate pattern already abstains on absent/unknown
and only treats a definitely-false value as scope-false.

### A4 — Adding the tags to `reasoned_over` IS sufficient

The ticket's concern (that `_txn_context` returns only four fields, per LP-498/FR-5) does not apply.
That is the tag-materialisation path. **AS-12 is a judgment rule**, and `judgment._build_context` builds
its context from the declared tags alone:

> *"The judgment context — ONLY the declared structural tags (never raw documents)."*

So adding `txn.amount` and `txn.date` to `reasoned_over` puts them in front of the model. No wider
context mechanism is needed.

⚠️ **But two of the prompt's three signals, not all three.** "Proximity to closing" needs the *closing*
date, which is loan-level (`contract.loan_closing_date`) and absent on LF-WCHG — it is exactly why IH-3
abstains there. Phase B closes "large" and "round-dollar"; it does not close "just before closing".

### A5 — AS-1 tests the GROSS deposit, not the unsourced portion

`observed: {tag: txn.amount}` — the whole deposit. There is no unsourced-portion logic, and the guide
says only the unsourced portion should count. AS-1 is therefore **stricter** than the guideline
(over-flags rather than under-flags — the safe direction).

**Not a one-line fix and not done here:** nothing in the data model splits a deposit into sourced and
unsourced parts, so this needs a new concept, not an edit. Reported per the ticket's instruction.

### A6 — Standard checks

- **No new parsed tag.** `txn.amount` and `txn.date` already exist in `fact_tags.csv`, parsed, and are
  load-bearing on AS-1 / AS-8 / AS-10 / DT-6. No `document_type` scoping question arises.
- **Distrust list:** `txn.amount` is deliberately absent, because LP-474 catches doc 049 (a row's amount
  equal to its running balance) structurally. The file states this explicitly; it still holds.
- **ADR-330 vacuity:** not vacuous. `txn.amount` comes from the bank statement, the income operand from
  the MISMO 1003 — independent sources. This is the same comparison AS-1 already makes.

### A7 — An added question the ticket did not ask

**What happens when a deposit is readily identifiable but the model answers `yes`?** The guide
anticipates exactly this:

> *"However, if the source of the deposit is printed on the statement, but the lender still has questions
> as to whether the funds may have been borrowed, the lender should obtain additional documentation."*

Phase C asserts "a deposit the model flags `yes` reaches a human regardless" — but if the exemption
scopes the subject out *before* the AI is asked, there is no `yes` to respect. The two cannot both hold.
**Decide which:** scope-before-asking (cheaper, but forfeits the guide's own escape hatch) or
ask-then-suppress-a-no (costs an AI call per deposit, but honours it).

## The design question Phase A raises

The ticket's table assigns the threshold to purchases and the readily-identifiable exemption to
refinances. Reading the guide's structure, the exemption is not refinance-specific — it is an exemption
from the large-deposit *documentation* duty, which is the purchase branch:

- **50% threshold** — definitionally about large-deposit *documentation* (AS-1/AS-2's duty)
- **Readily-identifiable list** — the guide's own statement of what needs no further explanation
- **Borrowed-funds duty** — stated unconditionally, outside the transaction-type table

Two consequences of the ticket's ordering: a large payroll deposit on a *purchase* would fire, though the
guide exempts it; and applying the 50% threshold to AS-12 is an *interpretation* (it is the
documentation test, not the borrowed-funds test) that should be labelled as such rather than presented
as sourced.

**Proposed reordering:** readily-identifiable first on BOTH purposes; the 50% materiality test second,
on purchases only, over whatever remains. This is more faithful, and it makes A1 far less load-bearing —
income is then needed only for deposits that are *not* readily identifiable, which on LF-WCHG is zero.

## Phase B — what was built

Decisions taken: **current branch** (`bedrock_integration_with_rules_staging`, which carries LP-509) and
**ask-then-suppress**.

**1. `txn.readily_identifiable_source`** — a new per-transaction derived tag (yes/no/unknown) encoding
B3-4.2-02's readily-identifiable list. Declared in `vocabulary_extra.yaml`, produced by
`derived._readily_identifiable_source`.

Of the guide's four sources, only **payroll** maps cleanly onto the category vocabulary. SSA and
IRS/state refunds have no category (`refund` is ambiguous — a merchant refund is not a tax refund, and
reading it as one would be inference, not a read). **`transfer_own` is deliberately NOT exempt** — see
A2: the guide conditions it on VERIFIED accounts and nothing in the snapshot can establish that.

**2. `transaction` added to `_DERIVED_SUBJECTS`.** The exclusion was never technical — the producer
enumerates the subject registry generically and `transaction` has always been a registered subject type.
The code comment recorded only that no recipe read one yet. Now one does.

**3. `exempt_when` / `exempt_unless_judgment_in` on `JudgmentEval`** — additive. A spec declaring
neither behaves exactly as before, and a test asserts AS-12 is the only rule that declares them.

⚠️ **This does touch the mechanism the ticket ring-fenced, and here is why it must.** Ask-then-suppress
cannot be expressed as an applicability predicate: a predicate short-circuits BEFORE the AI is asked, so
there would be no answer for the guide's escape hatch to respect. The suppression is therefore in the
judgment evaluator. What it is NOT is "auto-clearing a confident no": the clearing is done by a
deterministic predicate, and the model's answer can only ever ADD a review, never remove one.

**4. AS-12 gains `txn.amount` and `txn.date` in `reasoned_over`** — the inputs its prompt already asked
for. Two of the three signals; "proximity to closing" still needs the loan's closing date (A4).

## A test-infrastructure defect found and fixed

`test_derived_declaration_on_a_per_row_subject_fails_loud` pointed `_PRODUCTION_YAML` at a fake file and
restored the caches AFTER its `pytest.raises` block. When that assertion failed, the restore never ran
and the fake declarations stayed cached for the rest of the session — **one failure became 25**, none of
them in that file. The restore is now in a `finally`. The test's protective purpose is retained and
extended: it now covers both the unknown-subject guard and (by narrowing `_DERIVED_SUBJECTS`) the
derived-specific one.
