# LP-421 — Surface a tax return's nested Schedule C / Schedule E into the snapshot

## What this ticket is

The `tax_return` extractor already produces Schedule C / Schedule E as **typed core**
(`_SCHEDULE_C_SPEC` / `_SCHEDULE_E_SPEC` / `_SCHEDULE_E_PROPERTY_SPEC`), but
`documents_section.build_document_fields` **discards them**: `_scalar()` returns `None` for a nested structure
and the loop `continue`s, so a `tax_return` reaches the snapshot carrying only flat 1040 scalars. Every producer
reads the snapshot → the self-employment / rental signal was gone before any producer ran (`grep
schedule_c/schedule_e` in `app/verification/snapshot/` returned nothing). This ticket surfaces the schedules via
the **ADR-061 first-class typed path** (as `bank_statement` transactions got). **Schedules only — no producer,
no rule.**

| the 30 live rules identical; `ACTIVE_RULE_IDS` 30; suite green | ✅ |

## D1 — the ADR-061 reuse assessment (what transferred, what didn't)

**Read end to end:** a `bank_statement`'s transactions go extraction → `transaction_field_sets` (reshape gated on
`document_type`) → `build_transactions` (assigns per-row `content_id`) → `DocumentEntry.transactions:
tuple[TransactionRecord, ...] | None`; a per-transaction rule reads them off the entry it iterates.

**Transferred (the whole pattern):** a frozen Pydantic record model per structure, an optional `| None` field on
`DocumentEntry` (absent≠empty), a reshape gated on `document_type`, and the same per-field coercion the flat core
uses.

**Different shapes, same mechanism (no new mechanism, no STOP):**
- `schedule_c` is a **list of objects** → maps directly like `transactions` (`tuple[ScheduleCRecord, ...]`).
- `schedule_e` is a **single object containing a nested list** (two-level) → a `ScheduleERecord` with a
  `properties: tuple[ScheduleEPropertyRecord, ...]` field. Expressible as a typed record; no new machinery.
- schedule fields are `TypedField` (`{value, source, confidence}`), **not** flat scalars → reuse
  `build_document_fields`' own coercion (a `{value, confidence}` entry → a `Field`), not the transaction
  `_txn_field` path.

**Two deliberate simplifications vs transactions:** schedules carry **no `content_id`** (a schedule is
document-level, not a rule-enumerated subject) and are **not folded into the document content-id fingerprint**
(`_document_base` untouched) — which is precisely what keeps every existing `content_id` byte-identical (D6). A
schedule-only change therefore won't re-id a tax return; acceptable for plumbing, revisitable (the
transactions-fingerprint precedent exists) if a future consumer needs per-schedule reconciliation.

## D2 — the fields surfaced, per consumer

| surfaced | fields | consumer |
|---|---|---|
| `DocumentEntry.schedule_c: tuple[ScheduleCRecord, ...] \| None` | business_name, gross_receipts, total_expenses, **net_profit** | **IN-12** — self-employment presence + net profit |
| `DocumentEntry.schedule_e: ScheduleERecord \| None` | total_net_rental_income, depreciation, **properties**[address, **rents_received**, total_expenses, net_income] | **IN-13** — rental presence + rents + property list |

**`k1s` excluded** — no consumer today (the D2 default; surfacing unused structure is cost, and a separate
reshape wouldn't carry it "for free"). The record surfaces its consumer's full schedule (the transaction
precedent — a record is the natural unit), never the unrelated k1s / catch-all schedules.

## D3 — the STARTER-extractor caveat (the downstream inheritance)

`tax_return.txt` line 1 is literally `STARTER PROMPT — REPLACE WITH / MERGE INTO THE POC + PRIYA TAX-RETURN
PROMPT`; the module docstring calls a tax return "the most varied, multi-schedule … tested only against
constructed inputs is especially risky." **This plumbing makes the schedules REACHABLE; it does NOT make them
TRUSTWORTHY.** A rule gating on Schedule C presence would rest on an extractor never validated against a real
return. The honest ending: **reachable now; trustworthy after golden files** (a later ticket). The plumbing
validates nothing.

## D4 — typed, not free-form

Every surfaced value is a typed `Field` (nullable confidence carried faithfully; absent≠empty) inside a frozen
Pydantic record — typed-core-grade, coerced through the same path as the flat core. Nothing lands in the
free-form `additional_sections` blob (the LP-405 finding: no rule may depend on the catch-all).

## D5 — provability + the LP-419 stub

- **New fixture** `build_tax_return_with_schedules_snapshot()` (`fire_path_scenarios.py`, `95…`): a tax_return
  whose Schedule C (net_profit 82000) and Schedule E (2 properties, rents 18000 / 9600) reach the snapshot
  **through** `build_schedule_c` / `build_schedule_e` — the two-level structure proven end to end.
- **LP-419's stub left alone:** `build_self_employed_no_history_snapshot` baked FLAT fields and materializes
  `income.type` via a stub reasoner (no real schedules). It still builds; its tax_return carries
  `schedule_c=None` — **superseded, not broken** (a test pins this).
- **DB path proven:** an integration test seeds a real `tax_return` extraction and asserts
  `build_documents_section` surfaces `schedule_c` / `schedule_e`, while a `pay_stub` in the same file gets
  `schedule_c=None` (additive).

## D6 — the every-document equivalence (the gate that mattered most)

`build_document_fields` and `_document_base` are **untouched**. The schedules arrive via a **separate** path
(`build_schedule_c` / `build_schedule_e`), so:
- `build_document_fields` still drops nested structures — a test asserts its output for a tax return is the flat
  1040 core ONLY (no `schedule_c` / `schedule_e` / `k1s` keys).
- every content_id is byte-identical (`_document_base` unchanged).
- every non-tax-return `DocumentEntry` gains `schedule_c=None` / `schedule_e=None` — additive, exactly like the
  existing `transactions=None`.
- the full suite (every snapshot + rule test) stays green; the 30 live rules are identical on LF-6T3N.

## The proof (reported, not predicted)

**A tax return with schedules now lands in the snapshot as:**
```
DocumentEntry(document_type="tax_return", fields={tax_year=2025, filing_status=single},
  schedule_c=(ScheduleCRecord(business_name="Enterline Woodworks", net_profit=Field(82000.00, conf=0.9),
                              gross_receipts=Field(140000.00), total_expenses=Field(58000.00)),),
  schedule_e=ScheduleERecord(total_net_rental_income=Field(21000.00), depreciation=Field(6600.00),
    properties=(ScheduleEPropertyRecord(address="12 Oak St", rents_received=Field(18000.00), ...),
                ScheduleEPropertyRecord(address="9 Elm Ave", rents_received=Field(9600.00), ...))))
```
- **Absent≠empty:** a tax return with no Schedule C/E → `schedule_c=None`, `schedule_e=None` (never a fabricated
  empty record); a Schedule E with totals but no properties → `ScheduleERecord(properties=())`.
- **Equivalence:** `build_document_fields` output unchanged (flat core only, schedules dropped there); a
  `pay_stub` → `schedule_c=None` (additive); `ACTIVE_RULE_IDS` = 30; the 30 live rules identical.

## What a producer can now read (the next ticket's input)

Off any tax-return `DocumentEntry` in the snapshot: `entry.schedule_c` (a tuple of `ScheduleCRecord`, or `None`)
→ **presence + `net_profit`** for a self-employment signal (IN-12); `entry.schedule_e` (a `ScheduleERecord`, or
`None`) → **presence + `rents_received` per property** for a rental signal (IN-13). The next ticket maps these to
`income.type` / `income.is_self_employed`; this ticket surfaced the structure only.

## Assumptions / decisions

- Schedules deliberately excluded from the content-id fingerprint to preserve the byte-identical content_id
  equivalence (D6) — the one place a change would have rippled to every document.
- `k1s` excluded (no consumer). `schedule_c` full record (the natural unit, transaction precedent) — the
  "unused structure" D2 warns against is the unrelated k1s / catch-all, not a field within a consumer's schedule.
- `SNAPSHOT_VERSION` **not** bumped (kept at 4). The v2-transactions precedent bumped, but the change here is
  backward-compatible additive (both fields default `None`) AND a committed golden fixture
  (`lf6t3n_tagged_snapshot.json`, v4) must keep loading — the strict version validator rejects a v4 snapshot
  under a v5 reader (this was the initial regression: 74 failures, all from that fixture load). Not bumping is
  what keeps the D6 byte-identical equivalence; a bump would have broken it.

## New gap

- **The STARTER extractor** (ADR-333, D3): the schedules are now reachable but untrusted — golden-file validation
  of the tax-return extractor is a prerequisite before any rule gates on Schedule C/E. A later ticket.
