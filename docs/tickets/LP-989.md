## The scan-results gap

GuardDuty scans each object and tags it (row 7). The EventBridge rule `mbai-staging-inbound-scan-results`
matches the scan event and should deliver it to `mbai-staging-scan-results`. The delivery fails.
CloudWatch `AWS/Events` for the rule over the test window:

| Metric | Value |
|---|---|
| `MatchedEvents` | 1 |
| `Invocations` | 1 |
| **`FailedInvocations`** | **1** |

**Cause.** The scan-results queue and its DLQ are encrypted with the environment CMK
(`modules/inbound_mail/malware_scan.tf`, `kms_master_key_id = var.kms_key_arn`). The key policy grants
four principals:

- the account root;
- CloudWatch Logs;
- `ses.amazonaws.com` (LP-981);
- `sns.amazonaws.com` (LP-983).

`events.amazonaws.com` is not one of them, so EventBridge cannot generate a data key to send to the
queue.

**Why it matters.**
- **Nothing records the failure.** The rule's target has no dead-letter config, so the event is
  dropped. The scan-results DLQ alarm cannot fire because nothing reaches the DLQ, and no alarm watches
  `FailedInvocations`.
- **The health events are lost too.** The same rule carries GuardDuty's "Resource Status" plan-health
  events, which `malware_scan.tf` exists to surface ("SILENCE IS THE DANGEROUS STATE"). Those are being
  dropped as well.
- **The object tag still records each verdict.** Only the queue copy is missing.

**Not fixed here** (this ticket changes only the two flags). Follow-up:

1. Add `events.amazonaws.com` to the key policy for `kms:GenerateDataKey*` and `kms:Decrypt`, scoped
   with `aws:SourceArn` to the rule, the same pattern as the SNS grant.
2. Give the EventBridge target a dead-letter queue.
3. Add an alarm on the rule's `FailedInvocations`.
4. Re-run row 8 with one test email.

## Cleanup

- **Purged:** the inbound queue and the scan-results queue (exit 0).
- **Kept:** the S3 object, as the record of the test.
- **Self-inflicted DLQ message.** The events-queue check in row 23 used `receive-message
  --max-number-of-messages 10 --visibility-timeout 0`. With visibility 0, SQS returned the **same**
  Delivery event three times in that one call (one SQS message ID, `060f3de6-…`). The events queue's
  `maxReceiveCount` is **3**, so the message moved to `mbai-staging-outbound-mail-events-dlq` before the
  purge ran.
  - We confirmed the DLQ held exactly that message (same SQS and SES message IDs), then purged it.
  - `mbai-staging-outbound-mail-events-dlq-not-empty` had already gone to `ALARM` and notified
    `contact@mortgageboss.ai`. **That alert was caused by this test, not a real failure.** It
    incidentally shows the DLQ → alarm → ops-alerts path works.
  - **Lesson:** on these queues, receive with `--max-number-of-messages 1` and a non-zero visibility
    timeout. Visibility 0 with a batch size above 1 can spend the whole receive budget in one call.
    The inbound and scan-results queues allow 5 receives; the events queue allows only 3.

## Kill switch

Turns off receiving for the whole account, with no infra change:

```bash
aws ses set-active-receipt-rule-set --region us-east-1
```

With no rule-set name it deactivates. Use it if unexpected or abusive mail arrives, if the bucket or
queues misbehave, or before any change that could expose received mail. Reactivate with
`--rule-set-name mbai-inbound`.
