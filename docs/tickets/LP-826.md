# LP-826 — Requesting a document says nothing about the draft it just wrote

- **Ticket:** LP-826 · Phase 4 follow-up, from processor feedback on LF-JR4T
- **Status:** Specified — not started
- **Date:** 2026-09-07
- **Scope:** `components/file/verification/*`, the needs list, a shared draft-state indicator
- **Migration:** none expected

---

## What was reported

Clicking "Request" on a finding produces no sign that an email draft now exists. The processor's
concern, in their words: *"we should notify somehow to the user that draft is created."*

The mental model they reached for was a cart — not a shopping cart exactly, but the same idea: a
place where the things you have picked up accumulate, visible while you keep picking.

## Why this is the right instinct, and what it has to survive

LP-809's whole design is that requests **accumulate into one email**. That is invisible at the
moment of clicking, which is the only moment the processor is thinking about it. So the feature is
not a success toast — a toast says "that worked" and disappears, and the thing worth showing is a
running count that persists: *three documents are waiting in a draft on this file.*

Two constraints from what already exists:

- The draft is **per file**, not per finding. Requesting a second document must show "2", not a
  second indicator.
- Requesting a **non-borrower** document (title, appraisal, employer) deliberately does NOT enter
  the borrower draft — `_is_borrower_facing` filters it, and the need still lands on the needs list.
  An indicator that counts every request would claim the draft holds something it does not, which is
  worse than showing nothing. `add_needs_to_draft` already returns `skipped_not_borrower` for
  exactly this, and nothing reads it today.

## Done when

- After a successful request, the processor sees, without navigating away, that the item joined a
  draft and how many the draft now holds.
- The indicator is reachable — it takes the processor to the draft. A count nobody can act on is a
  decoration.
- A request that was NOT added to the borrower draft (non-borrower party) does not increment it, and
  says where that request went instead. This is the case the obvious implementation gets wrong.
- The count comes from the draft's actual contents, not from counting clicks. A processor who
  removes a line from the draft must see the count fall.
- It survives a reload, because it is derived state, not a transient notification.

## For the reviewer

Two failure modes to check, and neither shows on a happy-path screenshot: the count that counts
requests rather than draft rows (drifts the moment a line is removed), and the count that includes
a non-borrower request (claims an email contains something it does not). Both look correct on the
first click.
