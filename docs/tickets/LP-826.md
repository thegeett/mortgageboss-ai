# LP-826 — Requesting a document says nothing about the draft it just wrote

- **Ticket:** LP-826 · Phase 4 follow-up, from processor feedback on LF-JR4T
- **Status:** Built — awaiting review
- **Date:** 2026-09-07
- **Scope:** `components/file/verification/*`, the needs list, a shared draft-state indicator
- **Migration:** none expected

---

## What was reported

Clicking "Request" on a finding produces no sign that an email draft now exists. The processor's
concern, in their words: *"we should notify somehow to the user that draft is created."*

The mental model they reached for was a cart — not a shopping cart exactly, but the same idea: a
place where the things you have picked up accumulate, visible while you keep picking.

## Why this is the right instinct, and what it has to survive

LP-809's whole design is that requests **accumulate into one email**. That is invisible at the
moment of clicking, which is the only moment the processor is thinking about it. So the feature is
not a success toast — a toast says "that worked" and disappears, and the thing worth showing is a
running count that persists: *three documents are waiting in a draft on this file.*

Two constraints from what already exists:

- The draft is **per file**, not per finding. Requesting a second document must show "2", not a
  second indicator.
- Requesting a **non-borrower** document (title, appraisal, employer) deliberately does NOT enter
  the borrower draft — `_is_borrower_facing` filters it, and the need still lands on the needs list.
  An indicator that counts every request would claim the draft holds something it does not, which is
  worse than showing nothing. `add_needs_to_draft` already returns `skipped_not_borrower` for
  exactly this, and nothing reads it today.

## Done when

- After a successful request, the processor sees, without navigating away, that the item joined a
  draft and how many the draft now holds.
- The indicator is reachable — it takes the processor to the draft. A count nobody can act on is a
  decoration.
- A request that was NOT added to the borrower draft (non-borrower party) does not increment it, and
  says where that request went instead. This is the case the obvious implementation gets wrong.
- The count comes from the draft's actual contents, not from counting clicks. A processor who
  removes a line from the draft must see the count fall.
- It survives a reload, because it is derived state, not a transient notification.

## For the reviewer

Two failure modes to check, and neither shows on a happy-path screenshot: the count that counts
requests rather than draft rows (drifts the moment a line is removed), and the count that includes
a non-borrower request (claims an email contains something it does not). Both look correct on the
first click.

## Built, 2026-09-07

### Two halves, because one artefact cannot carry both facts

**A running count, derived from the draft.** `DraftBadge` reads `needs_item_count` off the file's
open draft and links to it. It survives a reload, it is the same for a colleague on the same file,
and **it falls when a line is removed from the email** — none of which a notification could be. It
renders **nothing** when there is no draft: `GET /outbound/draft` 404s, and "0 documents in the
draft" would be a claim about an email that does not exist, sitting on every file that has never
requested anything.

**The click's own answer, in the toast.** The count cannot say that *this* request was one of the
documents waiting, or that it was not. A processor who requests an appraisal and sees the count stay
at three cannot tell a request that went elsewhere from a click that did nothing. So
`document_request` carries `added_to_draft` and `not_borrower_facing`, and the toast says which.

`DraftUpdate.skipped_not_borrower` has existed since LP-809 **with nothing reading it**. This is what
reads it.

### The trap the ticket named, avoided by construction

Both numbers come from `add_needs_to_draft`'s own answer, never from what was asked for. A count of
requests would report "1 added" for an appraisal — telling a processor an email contains a request
it does not contain — and would drift the moment anybody edited the draft.

The toast's previous copy hedged: *"whatever the borrower can send is in the file's email draft"*.
That hedge was honest while nothing told the client what the draft had taken. It is now the fallback
for a version skew, not the answer.

### What changed shape

`request_docs_for_finding` and `request_documents_in_bulk` return `RequestOutcome` rather than
`list[NeedsItem]`. The draft's answer is decided inside `_create_document_needs` and was discarded
there; returning it is what lets the caller tell a processor anything at all. Seventeen test call
sites updated to read `.needs`.

`document_request` is **null on every response that is not a request** — twenty-three endpoints carry
this schema, and a field that was always present would have to mean something on an override, where
there is nothing true for it to say.

### Mutations

| mutation | result |
|---|---|
| count the ASK rather than what the draft took | 1 failed — the appraisal case, which is the one it exists for |
| the badge renders with no draft | 40 failed |

The first is the ticket's stated trap and it is caught by exactly one test, because it is the only
one whose fixture requests something that is not the borrower's to send. The others pass either way,
which is why that fixture had to be built deliberately rather than reached by accident.

`PR-3` was chosen over `PR-2` for it: PR-2 wants an appraisal **and** a purchase agreement, so the
count would have been 2 — right for the wrong reason, and it would not have shown that each skipped
need is counted once.

### One existing test file needed teaching

`verification-panel.test.tsx` mocks `@tanstack/react-query` with `useQueryClient` alone, and the
badge reads a query. Its mock now answers `useQuery` with **no draft**, which is the right default
there: those cases are about the findings panel, and a badge asserting itself into forty of them
would be noise. The badge has its own tests.

### Not done here

The badge is on the verification screen, where requests are made. It is not in the file rail, so a
processor on the Documents tab does not see it. That is a placement question rather than a
correctness one, and widening it is cheap once somebody decides where it belongs.

### The three standing checks

**Tenancy:** unchanged — the badge reads the draft through the same file-scoped endpoint the
communication page uses; no `company_id` derived anywhere new. **Logging:** nothing added. **AI:**
none.

## Review

Two findings. The first is mine — a defect LP-809's review claimed to fix and only half fixed — and
this ticket's outcome field is what made it visible.

**1. A finding that names no document could still be requested twice.** LP-809's review fixed "a
second click asks the borrower twice" in `_create_document_needs`, and proved it with `IN-1` — a
rule that *declares* a document, so the test never reached the other branch.
`_create_needs_item_from_message`, the branch for a finding that declares none, had no duplicate
check at all. Measured on **ID-3, the rule the original LF-JR4T report came from**:

```
ID-3 click -> 200  {'added_to_draft': 1, 'not_borrower_facing': 0}
ID-3 click -> 200  {'added_to_draft': 1, 'not_borrower_facing': 0}
  needs created: 2  ['Documents for: One more source…', 'Documents for: One more source…']
  lines naming the ask in the draft body: 2
```

Two identical needs items and two identical lines in the borrower's email. The fixture is what hid
it — with a rule that declares documents the case passes either way, which is exactly how a review
that ran the mutation still missed the branch. The duplicate lookup is now one function used by both
shapes, and an already-open ask is reused rather than refused: the finding still gets its marker,
draft membership is idempotent, and the caller sees an outcome with nothing added, which is the
truth.

**A surviving mutant found a second hole in the fix.** Dropping the `title ==` filter from the reuse
lookup left every test green — two findings that each name their own sentence (LP-624's channel:
ID-2 and ID-3) would collapse onto one needs item, the second finding's `docs_requested` pointing at
the first finding's need, and the thing it actually asked for never requested. The first version of
the test that was meant to catch this *also* passed under the mutant, because its fixture created
ID-3's need first and the lookup orders by `created_at` — so the wrong answer and the right answer
were the same row. Reversing the fixture order kills it. Recorded because the fixture, not the
assertion, was doing the work.

**2. The second-click sentence claimed the draft holds something that may not exist.** The
all-zeros branch of `requestConsequence` read "It was already on the needs list **and in the file's
email draft**". Measured on PR-3 — a rule whose only document is the lender's appraisal — the second
click returns `{added: 0, elsewhere: 0}` on a file with **no draft at all**. The sentence asserted
membership of an email that does not exist, in exactly the case this ticket exists to distinguish.
It now says only what the click did, and a test asserts it cannot mention the draft, with a control
so an empty string would not satisfy it.

### The build's four asks

1. **The 17-site rewrite is clean.** Checked mechanically rather than by eye: no `assert` line was
   added or removed in either rewritten file, and the test inventory is unchanged (14 → 14, 20 →
   20), with three genuinely new endpoint tests.
2. **The thinness is real and is now less thin.** The appraisal case was the only one that could
   kill the count-the-ask mutant. Three more tests now exercise the outcome from different angles —
   the documentless double-click, two documentless findings, and the consequence's zero branch.
3. **The shared mock change is additive and does not weaken anything.** It adds `useQuery` to the
   existing mock; no assertion changes, and no test in that file ever asserted anything about the
   badge. "No draft" is the right default for cases about the findings panel.
4. **`PR-3` over `PR-2` is right**, and for the stated reason: PR-2's count of 2 would have been
   right for the wrong reason and would not show that each skipped need is counted once.

### Endorsed

Counting from `add_needs_to_draft`'s own answer rather than from what was asked for; reading
`skipped_not_borrower`, which had existed since LP-809 with nothing reading it; rendering nothing
when there is no draft. The unaddressed placement note — the badge is on the verification screen and
not in the file rail — is placement, not correctness, and is correctly left recorded.
