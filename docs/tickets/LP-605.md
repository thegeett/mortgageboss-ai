# LP-605 — Eight findings about a borrower who was never removed

## What a processor saw

After the first pay stubs landed on LF-3CVT, eight findings said this:

> "Obtain a credit report for the **removed borrower**."
> "Obtain a W-2 or 1099 for the **borrower who is no longer on this file**."
> "Confirm that the **borrower who was removed from this application** had stable employment..."

CR-4, CR-10, ID-2, IN-1, IN-7, IN-10, IN-11, IN-16. The file has **exactly one borrower, not
deleted**, and the two pay stubs had just linked to them at confidence 1.0.

## It was not a hallucination

The model was told this. `resolve_subject_label`:

```python
if _is_uuid(subject_key):
    return borrower_names.get(subject_key) or "a borrower no longer on this file"
```

`borrower_names` defaulted to `{}`, so **"not supplied" and "supplied, and this id is not in it"
collapsed into one answer — and that answer asserts a fact.** The composition pass passes
`document_filenames` and never passed `borrower_names`, so every borrower-subject finding was handed
the subject string *"a borrower no longer on this file"* and wrote faithfully about a removal.

The read path passed both maps all along, so the same finding named the borrower in the list and
declared them gone in its own text. The composer's docstring had already named the requirement:

> "the composer just has to use the same resolver, **with the same maps**, so a finding cannot read
> one way in the list and another in its text."

It used the same resolver with half the maps.

## Fixed both ends

1. **The composer builds and passes `borrower_names`**, reusing `_active_borrower_names` — the helper
   that already existed for the snapshot's `belongs_to`.
2. **The fallback stops asserting removal it cannot know.** `borrower_names=None` (not supplied) now
   returns "this borrower"; a supplied map that lacks the id still returns "a borrower no longer on
   this file", because there the removal is real. Two different questions, two different answers.

The second half matters more than the first: without it, the next caller to forget the map
reintroduces the same false claim silently.

## Tests

Four — the composer naming the borrower it was given, and the three label cases the old test had
collapsed into one (map absent, map present without the id, map present with it). Mutation-checked:
removing the map from the composer, and re-collapsing the fallback, each fail.

Full suite green: **5464 passed**.

## The pattern, fifth time

A correct mechanism reached with incomplete inputs, degrading to something that reads as authoritative:
the cross-source parser was inert, DT-8's producer read the wrong field name, the composer's guards
ran only on cache misses, `PROMPT_VERSION` never moved, and now a resolver given half its maps. In
every case the code was right and the wiring was not, and in every case the failure was silent because
the fallback was written to sound reasonable.
