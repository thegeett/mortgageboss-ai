# LP-377-C — The fourth fail-open: the governed engine has never been allowed to finish

## WHAT THIS TICKET IS

LP-365 measured the governed rule pass at **~282s** on a 30-document file. `celery_app.py` set
`task_soft_time_limit=120`. **Nobody put 282 next to 120.** Every normal run: the AI sweep succeeds in ~65s and
marked the run COMPLETED; the rule pass is killed at 120s, retries, exhausts, and **its FAILED marker never
lands**. The result is a **COMPLETED run with no governed output, displaying stale findings from a prior FAILED
run as current.** The engine has **never once been allowed to finish** — and every governed count from LP-376
onward was read off run `96f55e9d`, killed mid-flight.

## WHY EVERY EXISTING GUARD WAS BLIND (the compounding)

| guard | why it missed |
|---|---|
| LP-377 BUG 1 (sweep won't overwrite FAILED) | **Nothing ever set FAILED** — the pass was killed before `_mark_failed` could commit. Moot. |
| LP-377 BUG 2 (enqueue failure → FAILED) | **`.delay()` SUCCEEDED.** The task was received and ran. The bool guards the enqueue, not a timeout. |
| `retry_or_terminal` → `_mark_failed` | Runs in **borrowed time after the soft limit fired**; the hard limit kills the child before its commit lands. |
| stuck-RUNNING watchdog (300s) | Fires only on **RUNNING** — the sweep already flipped it to **COMPLETED**. |
| the read path (`_build_status`) | Selects governed findings by `loan_file_id` + `evaluation_outcome` — **no run filter, no status filter.** |

**The failure mode is a TIMEOUT MID-EXECUTION. None of BUG 1/2/3 model it.**

## ACCEPTANCE CRITERIA

- The governed pass can **complete** on a real 30-document file (Fix 1).
- The sweep can **not** mark a run COMPLETED alone; a run whose governed pass never finished is not COMPLETED,
  and detection does not depend on the dying task (Fix 2).
- The read path **says so** when the latest run's governed pass did not complete, without breaking LP-322's
  carry-forward (Fix 3).
- The **first complete run** on LF-6T3N is reported (real counts, not predicted) + run #2's reconciler.
- Tests fail on the pre-fix code; no engine/rule/tag/spec change; `ACTIVE_RULE_IDS` unchanged; full suite green.

## PHASE 0 — THE ARGUMENT

### D1 — what dominates the ~282s (measured)
The runtime is **sequential AI-call latency.** `materialize_tags` awaits each of **6 AI groups**
(`txn_stage_a`, `id_address`, `id_name`, `id_poa`, `id_title`, `occupancy`) in a `for` loop; within a group
`produce_ai_group_tags` batches subjects and calls the model **sequentially**; the id.* groups run across
**every document**. Plus Stage A / Stage B. Nothing overlaps. (Confirmed in the run below — a single Stage-A
call was ~22s.) Reducing it (parallelize / gate groups to relevant doc-types, LP-368 rec 4) is an ENGINE
change — out of scope. **The lever is TIME.** Threading `TagCaches` across task runs was rejected: it dedupes
only *within* a run, so the first run pays full cost regardless — not the lever, and it touches engine behavior.

**Decision:** `run_rule_engine_pass` gets its OWN `soft_time_limit=900` / `time_limit=1200`; the 65s sweep keeps
the short global 120/180.

### D2 — the run's status must depend on the governed pass
**The rule pass is the completion authority.** The sweep records its findings/counts/fingerprint and **leaves
the run RUNNING** (it cannot know the governed half finished). The rule pass marks COMPLETED on its **success
path**, under LP-377's row lock (only if not already FAILED). A killed pass never reaches that line → the run
stays RUNNING → the **watchdog** (raised to **1500s**, above the pass's 1200s hard limit) fails it. **Detection
lives in the watchdog, not the dying task.** `PARTIAL` was rejected for blast radius; the run reads FAILED, the
sweep's findings stay readable, and D3 makes the surface honest. No schema migration.

### D3 — the read path couples findings to run success (without breaking LP-322)
A `verification_id` filter would gut carry-forward (a finding minted in run 1 and carried into run 5 belongs to
run 5). So all findings still show; one signal is added — `rule_findings_stale` = latest run not COMPLETED AND
governed findings exist — and the surface says *"these findings are from an earlier run; this run's rule engine
did not complete."* Forces a minimal frontend notice (built).

## WHAT WAS BUILT

- `app/tasks/verification_rules.py` — per-task `soft_time_limit=900`/`time_limit=1200` (Fix 1); on success the
  rule pass marks the run COMPLETED under a row-lock re-read (Fix 2 — the completion authority).
- `app/services/cross_source.py` — the sweep no longer marks COMPLETED (it leaves the run RUNNING); still marks
  FAILED on its own failure (Fix 2).
- `app/api/verification.py` — the stuck-run watchdog timeout raised 300s → 1500s (Fix 2 backstop);
  `rule_findings_stale` computed in `_build_status` (Fix 3).
- `app/schemas/verification.py` — `VerificationStatusPublic.rule_findings_stale`.
- Frontend — `VerificationStatus.rule_findings_stale`; a stale-findings notice above the tabs
  (`rule-findings-tabs.tsx`), wired from `verification-panel.tsx`.

## THE FIRST COMPLETE RUN (DB LF-6T3N — reported, not predicted)

Ran `run_verification` on LF-6T3N to completion, instrumented, **twice** (real `claude-sonnet-4-5`). **These
are the first complete governed runs on this file — ever.**

**Runtime + what dominates it (D1, measured).** RUN #1 **290.2s**, RUN #2 **284.2s** — squarely LP-365's ~282s,
and **2.4× the 120s soft limit that killed it.** Every stage is sequential AI latency:

| stage | RUN #1 | share |
|---|---|---|
| build_snapshot | 0.1s | 0.0% |
| Stage A (txn) | 82.6s | 28.5% |
| Stage B (sourcing) | 77.3s | 26.6% |
| **materialize (6 AI groups × docs)** | **114.3s** | **39.4%** |
| evaluate_rules | 15.8s | 5.5% |

Per-document AI materialization is the single biggest slice; nothing overlaps (a single Stage-A call was
~22–26s). Cost ≈ **$0.30/run** (Stage A $0.12 + Stage B $0.086 + materialization; ~$0.65 for both runs).

**The counts — the complete run vs the killed run everything since LP-376 was read off (`96f55e9d`):**

| outcome | failed run `96f55e9d` (partial) | **complete run** |
|---|---|---|
| couldnt_check | 30 | **13** |
| satisfied | 2 | **18** |
| needs_review | 4 | **5** |
| open | 2 | **2** |
| **total** | 38 | 38 |

**The `couldnt_check` pile more than halved (30 → 13) and `satisfied` went 2 → 18** — because the killed run
died mid-materialization, so most tags never materialized and their rules gated to `couldnt_check`. The
headline: **AS-1's 15 deposits flipped `couldnt_check` → `satisfied`** — the "15 couldnt_check" quoted in
LP-366/LP-368/LP-376 was an artifact of a run that never finished Stage-A/B/materialization. Per-rule
(complete run): AS-1 satisfied 15 + needs_review 2 · ID-1 satisfied 2 · ID-2 satisfied 1 / couldnt_check 1 ·
ID-3 couldnt_check 2 · ID-4 couldnt_check 2 · ID-6 **open** 1 · ID-7 couldnt_check 4 · ID-8 needs_review 2 ·
ID-9 couldnt_check 4 · IN-2 **open** 1 · OC-2 needs_review 1. (ID-7/ID-9's couldnt_check survive — LP-377-A:
the file genuinely has no title/POA document; the untyped docs are a red herring, correctly diagnosed.)

**LP-376-C's reason text finally renders** — the string that started this investigation. ID-9 now reads:
*"a document in the file could not be classified — it may be the power of attorney this check needs; classify
it so the check can run"* (and ID-7: *"…the title commitment…"*), not the old *"applicability tag
'document.document_type' is unknown."* The evaluator was always right; the pass had just never reached persist.

**RUN #2 — the reconciler's first real exercise on a COMPLETE run (LP-322).** `carried_forward=38, minted=0,
retired=0, resolved=0, revived=0` — every finding re-matched by `(rule_id, subject_key)` and carried forward
with its outcome **identical** to RUN #1. No duplicate mint, no false retirement, deterministic across runs.
(RUN #1 itself carried forward the 38 rows from the failed `96f55e9d` and **refreshed** their stale outcomes +
messages — which is how the old strings finally became LP-376-C's.)

## ASSUMPTIONS / DECISIONS + WHAT'S STILL OPEN

- **What this invalidates:** every governed count from LP-376 onward was partial-run output. The first complete
  run above is the real baseline. LP-377-A survives (it read documents + the classifier, not findings).
- **Capacity (reported, out of scope):** the limits (900s/1200s) cover the current realistic file sizes with
  margin; a file large enough to exceed 1200s of sequential AI calls needs the engine-level fix (parallelize /
  gate the per-document AI groups — LP-368 rec 4). Raising a number does not scale forever.
- **Retry-on-timeout waste (reported):** `retry_or_terminal` retries a `SoftTimeLimitExceeded` — pointless for a
  deterministic timeout. With the raised limit, timeouts should not occur for realistic files; not changed here.
- **The RUNNING window:** a run is now legitimately RUNNING from the sweep's finish (~65s) until the rule pass
  completes (~282s). This is honest (the governed pass IS running); the findings are visible throughout.
