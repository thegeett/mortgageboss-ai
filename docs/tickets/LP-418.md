# LP-418 — The producer batch: build the small producers that unblock written-but-inert rules

## What this ticket is

A **producer batch**, not a rule batch. Several rules are written-but-inert only because an input is not
produced. LP-418 builds those small producers (and the labeling fixtures they need) — **and writes / activates
NO rule.** The rules the producers unblock (IN-12 / AS-7 / IN-14) activate in their OWN later tickets. So
`ACTIVE_RULE_IDS` is **unchanged** (still `EXPECTED_ACTIVE_RULE_COUNT`); the only census move is **+1 vocabulary
tag** (`income.is_self_employed`).

## D0 — the redundancy check (done first)

The batch also weighed an **MI producer.** **STOPPED — redundant.** The loan product already surfaces mortgage
insurance: `calculations_section.map_mi` maps `compute_loan_mi`, and "MI always determines required," so
`housing.mi_monthly` / `mi.required` are already produced. A new MI producer would re-derive what the product
surfaces. This is the **third** redundancy-driven abandonment (after the DTI-component cluster and DT-5). The
standing discipline: before building a producer, check whether the fact is ALREADY produced (by the product, an
AI tag, or an existing derived recipe) and **promotable**, not just whether it is "missing" from the consuming
rule's subject.

## D1 — which are deterministic vs AI

- **#1 is deterministic.** IN-12's bar said the signal "does not exist — `income.type` is subject:document." The
  right build is not a new AI perceiver but a **promotion**: `income.is_self_employed` (subject:borrower) reads
  the borrower's own attributed income documents (`_borrower_attributed_documents`, LP-385) and promotes their
  `income.type`. Derived-last (LP-333) makes it legal — a derived recipe runs after the AI stage, so it sees the
  AI-produced `income.type`. **No calibration round.**
- **#2 / #3 are AI** (grouped for ONE labeling round each, when their rules are written). Their rules already
  HELD / ship ratify on calibration; they were producer-blocked, not calibration-blocked.

## Phase 2 — proof they produce (reported, not predicted)

- **#1 branches** (against real `income.type` values): borrower with a `self_employment` income doc → **`yes`**;
  borrower with a readable non-self-employment type → **`no`** (lets IN-12 reach `not_applicable` — an enum can,
  a number can't, ADR-330); borrower with no readable type → **`unknown`** (fail-closed). Wired per-borrower
  end-to-end: on the income calibration fixture it materializes **13 rows** (one per enumerated borrower); under
  the keyless stub each reads `unknown` (the stub assigns no real `income.type` — an honest reflection, the
  yes/no branches are proven against real values in the recipe test).
- **#5**: `income_docs` (subject:document, `applies_to:None`) judges every document → `income.voe_present` /
  `income.offer_letter_present` each get **12 rows**; the labelable positive class is 6 VOE + 6 offer docs.
- **#6**: `income_stability` (subject:borrower) produces `income.continuance_3yr` for **6 borrowers**.

## The subject-shape constraint (re-hit + recorded)

A transaction-subject AI group must NOT set `applies_to` (that key gates/gathers documents — meaningful only for
document/borrower-subject groups). `txn_nsf` first tripped the loader's `DeclarationError`; fixed to omit it
(`applies_to: all` semantics). Recorded in ADR-331 so the next transaction/loan-subject producer does not re-trip.
