# LP-102 — Fix pay-stub extraction empty-result (truncation) + shared truncation guard

- **Status:** Completed

> Note: an earlier reference in LP-101/ADR-227 used "LP-102" as a placeholder for the *refi DTI
> double-count* follow-up. That is a **separate** future ticket and needs a new number; this LP-102
> is the pay-stub extraction truncation fix.

## Summary

Documents classified "Pay stub" extracted EMPTY (all fields blank → "Needs review") while W-2 and
investment extractions in the same file succeeded. Root cause: pay-stub extraction **overflowed its
`max_tokens` budget** and the truncated response was **silently misreported** as a parse failure.
Fixed by right-sizing the pay-stub budget (**Fix A**) and adding a **shared truncation guard** across
all extractors (**Fix B**). See **ADR-228**.

## Confirmation (step 1 — done before fixing)

Queried LF-6T3N directly: all **4** pay-stub docs are `needs_review` with
`error_detail = "could not parse extraction"` and `tokens_used = None` — the truncation/parse-None
fingerprint (an all-null *read* would instead store the model's natural-language reasoning). Both
tiny (9,497 / 9,481 B) and large (209,080 / 209,089 B) stubs failed → output verbosity, not input
size. **`investment_account`** (also 4096) had one `needs_review` "could not parse extraction" on its
densest doc — the gap was already systemic. Working types that were bumped (bank_statement 8192)
completed. → **Truncation confirmed; proceeded.**

## Root cause

- A pay stub enumerates many earnings/deduction/tax line items (current + YTD), each emitted as
  `{value, page, verbatim snippet}` → the JSON response exceeds 4096 output tokens → the model
  **truncates** it mid-object (`stop_reason == "max_tokens"`).
- **No extractor checked `stop_reason`** (all ~18). The cut-off body flows into `extract_json_object`
  (which requires a *balanced* `{…}`) → `None` → `failed("could not parse extraction")` — a
  self-inflicted truncation **misreported** as an unreadable document → empty `NEEDS_REVIEW`.
- W-2 (fixed ~11-box form) fits in 4096; pay stub / dense investment don't. Opus 4.8's thorough
  transcription makes truncation more likely for any verbose type.

## Fix A — right-size the pay-stub budget

`pay_stub._MAX_TOKENS` 4096 → **8192** (matches `bank_statement`; same "capture every line item"
verbosity). The other verbose types were already generous (bank_statement 8192, tax_return 16384,
divorce_decree 6144); pay stub had been left at the LP-39 scaffold 4096.

## Fix B — the shared truncation guard (the primary, systemic fix)

New `app/ai/extraction/model_call.py :: run_extraction_completion` — the ONE shared model call every
extractor now uses instead of `complete()` directly:

1. Attempt 1 at the type's own budget.
2. If `stop_reason == "max_tokens"` → log **`extraction_truncated`** (distinct, not a parse failure)
   and retry **exactly once** at **16384** (one decisive jump, not incremental bumps).
3. If the retry still truncates → return the **honest** `TRUNCATED_REASON` =
   `"response truncated - document too dense to extract in full"` (never "could not parse"); the
   extractor surfaces it via `.failed(reason)` → the pipeline stores it as `error_detail`.
4. Retries fire **only** on truncation — never on other stop reasons, parse failures, or AI errors.
   At most **2 attempts**. A successful retry is **transparent** (fields populate, COMPLETED).

Covers all ~18 extractors via the single shared path — pay stub was just the first to hit it. Each
extractor's `try: resp = await complete(...) except AIClientError: ...` block was replaced by a call
to the runner (`if call.text is None: return X.failed(call.failure_reason or "AI call failed")`),
with the token lines reading from the runner's result.

## Rejected — Fix C (dropping snippets)

Not done: the per-field verbatim `snippet`s are **source provenance** for verification / the LP-43
drawer. We fixed the budget, not the provenance.

## Honest failure mode

A genuinely too-dense document (overflowing even 16384) now fails **honestly** — truncation is
labeled as truncation and lands in NEEDS_REVIEW with an accurate reason, instead of the misleading
"could not parse extraction". Same honest-failure-mode principle the project applies everywhere.

## Files

- `app/ai/extraction/model_call.py` (new) — the shared truncation-guarded runner + `TRUNCATED_REASON`
  + `RETRY_MAX_TOKENS = 16384`.
- `app/ai/extraction/pay_stub.py` — `_MAX_TOKENS` 4096 → 8192 (Fix A) + uses the runner.
- The other 17 extractors — mechanically switched from `complete()` to `run_extraction_completion`
  (shared guard; no other behavior change).
- `tests/ai/test_extraction_truncation_guard.py` (new) — 11 tests (runner logic + Fix A + Fix B
  through pay_stub and a second extractor).
- `tests/ai/test_*_extraction.py` — mocks repointed to `model_call.complete` + `stop_reason` added.

## Systemic note

`AIResponse.stop_reason` already existed "so callers can detect a truncated response instead of
silently parsing a cut-off body" — but no extractor used it. Fix B closes that gap for the whole
extraction fleet; this becomes more important under Opus 4.8's more thorough transcription.
