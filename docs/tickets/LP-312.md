# LP-312 — The tag object model + snapshot two-layer shape (+ stable content-ids)

**Status:** Complete. **Branch:** `phase3_new_AI_arch_finding_stage2`.
**ADR:** [ADR-251](../../decisions.md). **Depends on:** LP-204 (frozen snapshot),
LP-302a (transactions), LP-310 (recon — gap #1).

## What it is

The **load-bearing prerequisite** for the whole tag layer. It makes two coupled changes
to the frozen per-run snapshot in **one `snapshot_version` bump (2 → 3)**:

1. **Stable, run-independent content-ids** on raw facts (`TransactionRecord`,
   `DocumentEntry`), so tags (`source_facts`) and findings (`subject_key`) can reference a
   raw fact by an id that survives a rebuild — closing LP-310 gap #1 (facts were addressable
   only by array position, which is not stable because the snapshot is rebuilt each run).
2. **The tag object model** (§3D contract) + the **`tags` layer** added alongside the
   existing raw layer.

**MODEL + SHAPE ONLY** — no tag production, no AI call, no rule evaluation. The tags layer
ships **present-empty**; `from_tag` ships **null**.

## The content-id derivation (precise)

- **Transaction id** = `"txn" + sha256(canonical({doc: <parent document_content_id>, date,
  amount, direction, description}) + "#" + occurrence_index)[:16]`.
- **Document id** = `"doc" + sha256(canonical({document_type, belongs_to (ids+names),
  fields (sorted, JSON), transactions_fingerprint}) + "#" + occurrence_index)[:16]`, where
  `transactions_fingerprint` is an **order-independent** hash of the document's transaction
  contents (so two statements differing only in transactions get distinct ids
  deterministically, not by positional luck).
- **occurrence_index** is the count of byte-identical prior siblings (documents in the
  section; transactions in one statement). It is 0 for every distinct fact, so distinct
  facts are pure content hashes (fully position-independent). It only ever differs for
  genuine duplicates, where the assignment among indistinguishable siblings is immaterial.

## Assumptions & decisions

- **Additive two-layer, not a `raw` wrapper.** The raw sections stay at the top level
  (paths unchanged); a new sibling `tags` section is added. Nesting them under `raw.` would
  move every existing JSON path and ripple through every calculator/consumer — the ticket's
  "existing content UNCHANGED, additively" rules that out.
- **v2 superseded (clean bump).** Per LP-310 no production snapshot was ever persisted, so
  the reader supports only v3; a stray dev v2 blob is rejected on load and rebuilt.
- **`content_id` is required** (not defaulted). A raw fact must be addressable; the builder
  computes it. Direct constructors (tests/fixtures) pass a literal.
- **PII-safe id format.** Letter-prefixed hex, no internal separator → one `\w` run starting
  with letters → can never match the guard's `\b\d{9,}\b` (deterministically). Verified by a
  test that runs 50 ids through the real guard.
- **`Tag.value` = `pydantic.JsonValue`** (any JSON value; honors "any", permits `"unknown"`
  and null). Structured calculator values live in the calc breakdown path (`from_tag`), not
  generic `Tag.value`.
- **Loader/builder unchanged elsewhere.** `build_snapshot` and persistence round-trip the new
  fields automatically (`model_dump(mode="json")` / `model_validate`); no persistence change.
- **`build_transactions` API changed** — now `(field_sets, *, document_content_id)`; the
  reshape half is `transaction_field_sets`. Callers/tests updated.

## Deferred / out of scope

- **Field-cell content-ids** — deferred; scoped to `TransactionRecord` + `DocumentEntry`
  (the recon's priority). MISMO facts / `DocumentEntry.fields` cells remain keyed by their
  dict keys; add cell ids when a tag needs to cite a specific field cell.
- Tag **production** (Stage A/B, any AI call — LP-313/314); rule **evaluation**; populating
  the tags layer or `from_tag` (LP-318); findings / `subject_key` (LP-316).
