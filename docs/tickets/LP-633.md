# LP-633 — letting the reasoner withdraw a proposal

- **Ticket:** LP-633
- **Status:** Built + review-fixed — CI green, not yet deployed
- **Date:** 2026-08-26
- **Scope:** Backend (LP-69 prompt contract + context assembly + ingest)
- **Depends on:** LP-631 (the flag mechanism), whose columns it writes

## Why a predicate cannot cover this

LP-632 reaches six of staging's 32 open AI-proposed needs. Two more predicates are conceivable and
neither is close to free:

- **`stated_employers` × w2 / pay_stub** would reach the four open `verification_of_employment` /
  `voe` needs — but "a W-2 is present, so retire the VOE" is wrong. A W-2 documents *last year's*
  income; a VOE verifies *current* employment. They are not substitutes, and LP-624 already caught
  this reasoner misreading employment records once. The substitution rule is a domain question before
  it is a code one.
- **`stated_assets` × statement accounts** would reach three needs — and it is exactly the
  account-level coverage grid LP-108 named as "Option A" and **declined**, because account-level
  matching is where false-greens live.

That leaves roughly nineteen needs with nothing to join against: an `appraisal` and a `title_report`
triggered by a MISMO field, six needs with `needs_type=null` that no document can clear by any route,
and the various `letter_of_explanation` / `tax_return` rows whose moot-ness is a reading question,
not a lookup. For those the only thing that can judge the need stale is the thing that wrote it.

## The change

**A second key in the LP-69 contract.** Today it is `{"needs": [...]}` — one key, additive by
construction:

```json
{
  "needs":   [ ... unchanged ... ],
  "retract": [ {"needs_type": "...", "why": "..."} ]
}
```

**`existing_needs` grows to carry the argument.** `assemble_file_context`
(`services/needs_ai.py:208-210`) sends `{needs_type, title}` today. A model cannot sensibly judge
whether to withdraw a claim it cannot read, so it also sends each need's `reasoning`, `origin` and
`disposition`.

**One load-bearing sentence in the prompt:** *"Silence is not retraction. A need you do not name in
`retract` stays on the list."* This preserves today's semantics exactly for every need the model says
nothing about — which is nearly all of them — so the change is additive in behaviour as well as in
schema. Without that sentence the prompt's existing order to stay quiet about `already_covered` would
turn every correct need into a withdrawal.

**A retraction sets LP-631's flag.** It does not close the need. Same columns, same eligibility gate,
same disposal path as LP-632's predicate — the AI is simply another source of the same signal, and
`coverage_note` carries its `why`.

## Two things the build changed

**Keyed on the need's `id`, not its `needs_type`.** The spec above argued for type, on the grounds
that ids are opaque to the model. They are not: LP-110 already hands it finding ids and it refs them
correctly. And keying on type would have excluded exactly the population this exists for — the six
untyped needs on staging, the largest single bucket and the only ones no document can EVER clear.
`documents_present` now carries ids for the same reason, so a retraction can cite the document that
answers the need and the card can say *"checked against credit-report.pdf"* instead of asserting.

**The self-contradiction guard, and where it had to read from.** A model can argue for a need under
`needs` and against it under `retract` in one answer. Left alone the flag lands on a row the same run
argued for, telling the processor two opposite things at once. A need the response also proposes is
therefore not retracted — the ask wins, the direction that cannot lose a document.

Getting that right needed a second pass. The guard first matched against `ReasonedNeeds.proposals`
and never fired, because `reconcile` drops any proposal whose type the file already covers — which is
every re-proposal of a need that exists, i.e. the whole signal. `ReasonedNeeds` now also carries
`raw_proposals`, the model's answer before reconciliation, and the guard reads that. Matched on type
AND on description, since an untyped need collides only by wording.

`coverage_note` became the canonical "is flagged" marker: LP-632's predicate always has a document to
point at, but a retraction may rest on an argument ("the employment record states
`self_employed: false`"), and a flag with no note would be a row saying "possibly covered" with
nothing to check.

## Assumptions

- Retraction is confined to `AI_REASONING` + `PROPOSED` + open, like every other write in this area.
  A processor's judgement is not the model's to revisit, and `apply_retraction` re-checks that itself
  rather than trusting the caller.
- A retraction naming an unknown need id, or a document id from another file, is dropped silently —
  the model is answering about a list it was given, and neither is worth failing a needs update over.
  A foreign document id drops to null and the note stands alone: the claim stays visible, the false
  citation does not.
- The failure mode is deliberate. A model that ignores the new instruction emits no `retract` key, and
  the pass behaves exactly as it did before LP-633.

## Not covered

Nothing measures whether the model retracts *well*. The mechanism is pinned by tests; the judgement
quality is a real-file question, and the first evidence will come from watching it on staging — where
LP-632's predicate already handles the liability cases, so what LP-633 fires on will be the residue
that predicate cannot reach.


## Review fixes

**The self-contradiction guard compared canonical against raw.** The STORED type is canonical —
`apply_ai_needs` writes `canonical_need_type(p.need_type) or p.need_type` — while the guard built its
set from the model's raw strings. So every aliased pair slipped through: a response proposing
`verification_of_employment` while retracting the need it had created (stored as `voe`) read as no
contradiction, and the flag landed on the row that same response argued for — precisely what the guard
exists to prevent. `existing_mortgage_statement` -> `mortgage_statement` and `drivers_license` ->
`government_id` failed the same way. Both sides now normalise through `_comparable_need_type`
(`canonical_need_type`, then `equivalent_need_type`).

This is the guard's second correction. It was written against the reconciled proposals and never fired
at all; fixed to read `raw_proposals`; and now fixed again on the comparison itself. Worth recording
plainly: the mechanism it guards is a two-set comparison across a normalisation boundary, and both
defects were the boundary rather than the logic.

**The kill switch did not cover this path.** `flag_covered_needs` consults
`needs_coverage_flagging_enabled`; `apply_retraction` did not. An operator turning coverage flags off
would have silenced the deterministic source while the model kept writing the same columns, rendering
the same card, on every AI needs run — a switch that does not do what it says. Both paths are now
gated by it, and the config comment says the switch covers both.
