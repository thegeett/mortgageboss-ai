# LP-940 — Withdraw a condition entered in error

- **Ticket:** LP-940 · Phase 4.5 Stage 3 follow-up
- **Source:** the product owner, 2026-09-29:
  - only for conditions added by hand (`origin = manual`); sheet conditions keep ADR-404's rule;
  - "Withdraw" on the detail sheet asks for a short reason. It soft-deletes (`deleted_at`), writes a
    `condition_withdrawn` event with the reason, and removes the condition from the list, counts, plan,
    drafts and package;
  - it stays in the history, in a collapsed "Withdrawn (n)" section, with Undo;
  - it is refused, with a sentence saying why, if the condition has a recorded lender verdict or was in
    a submitted package;
  - recorded in `decisions.md` as an amendment to ADR-404.

## Design

**Service** (`app/services/condition_withdraw.py`):
- `withdraw(condition, reason, actor)`. It refuses, each with its own sentence:
  - a sheet condition: "Only a condition you added by hand can be withdrawn. One from the lender's sheet
    stays until the lender clears or waives it.";
  - a recorded lender verdict (any `condition_verdict_recorded` event): "The lender's answer is recorded
    on it, so it stays on the file.";
  - a submitted package holding it: "It went to the lender in the package submitted on 09/09/2026, so
    it stays on the file.";
  - an empty reason: "Say why — the reason is kept in the history.". The reason is at most 500 characters.

  Otherwise it sets `deleted_at`, writes `condition_withdrawn` with `{"reason": …}`, and takes it out of
  the drafts (below).
- `restore(condition, actor)`, which is Undo: clears `deleted_at` and writes `condition_restored`. It
  refuses a condition that is not withdrawn, and re-syncs the drafts so its asks return.
- `withdrawn_for_file(loan_file)`: the withdrawn hand-added conditions, newest first, each with its
  reason and when it was withdrawn (from its latest `condition_withdrawn` event).

**Taking it out.** Every reader already skips soft-deleted conditions, except these, which are fixed here
(census in the Verification section):
- **Drafts.** The round sync skips it, but its items stay linked to an unsent draft. `withdraw` unlinks
  its items from unsent drafts, discards an unsent question draft of its own, and re-syncs. Sent drafts
  are history and stay.
- **Package.** A built but unsubmitted package's stored rows can hold it. The view, the download and
  Mark submitted skip rows whose condition is withdrawn. The stored rows are not rewritten.
- **Figures check.** `_funds_evidence` loads the condition by id and now skips a withdrawn one.

**Routes:**
- `POST /conditions/{id}/withdraw {reason}`, behind `get_scoped_condition` (active only);
- `POST /loan-files/{id}/conditions/{condition_id}/restore`, behind the file's gate, because a withdrawn
  condition is not found by `get_scoped_condition` by design;
- `GET /loan-files/{id}/withdrawn-conditions`.

Refusals are 409 with the sentence.

**Migration:** the event-kind CHECK gains `condition_withdrawn` and `condition_restored`, 31 kinds, all
listed, in raw `op.execute`. The downgrade refuses while any such event exists, rather than deleting
history.

**Frontend:**
- **The sheet:** a "Withdraw" control only on a hand-added condition. It asks for the reason inline
  ("Why — for example, added twice by mistake") and confirms with the reason's button. A refusal shows
  its sentence.
- **The list view:** a collapsed "Withdrawn (n) · codes" section below the list. Each row shows the
  code, the words, "Withdrawn 09/29 — <reason>" and **Undo**.
- **History:** a line for each kind (as built: without the reason, see below). `ALL_KINDS` goes to 31.

**ADR-404 amended:** a hand-added condition is the processor's own entry, not the lender's demand, so
she may withdraw it with a reason, and nothing is deleted. Only conditions she typed qualify, and never
once the lender has answered on it or it has gone to the lender.

**Built as designed, with one change:** `restore` refuses only a condition that is not soft-deleted. A
first version also checked that the deletion came from a withdrawal. Measured: nothing else in the app
sets `conditions.deleted_at`, so that check could never fire, and a test for it would have had to invent
the state. It is replaced by `test_only_a_withdrawal_deletes_a_condition`, which fails the day a second
writer appears.

**History:** the lines read "Withdrawn as entered in error" and "Put back". Her reason is not in the
history's allow-list (LP-923's precedent for her free text); it shows on the Withdrawn section's row,
from its own endpoint.

## Review (of `faea58ad`)

**The owner's five asks are all built and the refusals are right. One finding, measured end to end: a
condition withdrawn while a package is BUILT stays in that package's stored rows when it is submitted,
which makes the submitted record overstate what was sent and turns the withdrawal into a one-way door on
a false premise. The census you asked me to check is complete for the readers it covers; I found one
class it does not name.**

### Finding — stale stored rows make a submitted package lie, and the second withdrawal is refused

`submit` sets `status` and `submitted_at` but never assigns `package.rows` — though its own docstring says
"the rows frozen as the record". `live_rows` is applied to what submit *iterates*, not to what it *keeps*.
Reproduced:

```
built rows:                                  ['7086', '6132', '6178', '0006', '9001']
withdraw 9001  -> live_rows:                 ['7086', '6132', '6178', '0006']
               -> stored rows:               ['7086', '6132', '6178', '0006', '9001']
submit moved:                                ['7086', '6132', '6178', '0006']      <- correct
status=submitted   STORED ROWS AFTER SUBMIT: ['7086', '6132', '6178', '0006', '9001']  <- 9001 kept
_submitted_on(9001) after submit:            2026-09-30 00:49:15+00:00
restore worked
withdrawing again: REFUSED -> 'It went to the lender in the package submitted on 09/30/2026, so it stays on the file.'
```

Three consequences, in order of seriousness:

1. **A sentence she reads is false.** 9001 never went to the lender — `live_rows` excluded it and `submit`
   did not move it — but the refusal says it did, and names a date.
2. **The Undo becomes a one-way door.** Restore works, and then withdrawing again is refused forever,
   because `_submitted_on` reads the stale row. She can put it back but never take it away again.
3. **The submitted package's stored rows are the record of what was sent, and they overstate it.**

`live_rows`'s own docstring asserts the invariant this breaks: *"A submitted package is the record of what
was sent: its rows are all live, because a condition in one cannot be withdrawn."* True of a condition
withdrawn **after** submission; false of one withdrawn while the package was merely built.

**The fix is to make `submit` do what its docstring already claims** — freeze `await live_rows(...)` into
`package.rows` at submission. Then the record matches what was sent, `_submitted_on` is true, and the
second withdrawal is allowed again. The withdrawal's own reason is already in the events, so nothing is
lost by pruning the row.

### The census — complete for Condition-row readers, and one class it does not name

I enumerated mechanically rather than checking your list: every `select(Condition…)` and
`db.get(Condition, …)` in `app/`, with its enclosing function and whether a deleted filter is in scope.
**40 sites load a Condition row.** The unfiltered ones, and what makes each safe:

| site | why it is safe |
|---|---|

| **13 sites in `condition_drafts.py`** (`render`, `mark_sent`, `_name_the_send`, `draft_view`, `drafts_for_file`, `set_due_date`, `use_polish`) | not filtered at all — made safe at the DATA level by `_leave_unsent_drafts`: items unlinked from unsent drafts, the condition's own unsent question draft discarded. A SENT draft keeps its items deliberately, so a sent email stays a true record |
| `condition_evidence.py:646 check_document` | `_open_condition` checks `deleted_at is None` — verified in the code, not taken on trust |

| `conditions.py:762, 784 condition_summary` | both id sets are intersected in `summarise_conditions` as `sum(1 for c in open_conditions if c.id in …)`, and `open_conditions` comes from the filtered `list_conditions` — verified, so neither `your_tasks` nor `failed_check` can count a withdrawn condition |
| `figures_check.py:156` | fixed here |
| `lender_settings.py:124` | example wording across companies |

Counting the drafts as one line is what makes "three" look small: it is thirteen readers held safe by one
data-level fix rather than by thirteen filters. That is the better design — but it means the guarantee
lives in `_leave_unsent_drafts`, so its one edge deserves saying: a draft whose `Communication` row is
missing reads as *sent* (`message is not None and …`), so its items would not be unlinked. Unreachable
today; the assumption is worth a sentence there.

**The class your census does not name: queries on CHILD tables that do not filter the parent.**
`_items_by_condition` filters `ConditionItem.deleted_at` but not the condition's, so
`items_public_for_file` returns a withdrawn condition's items. Every consumer happens to look them up **by
condition id** (`.get(condition.id)`), and the withdrawn condition is not in any list, so nothing renders
them. Safe today, but by the shape of the callers rather than by the query — and a future consumer that
iterates the map instead of keying into it would show them. One filter on the join would make it safe by
construction.

### (a) The history lines carrying no reason — defensible

The reason is **persisted**: `withdraw` writes `{"reason": text[:500]}` into the `condition_withdrawn`
event's detail, so it is durable in the audit trail and only the *rendered* line omits it. That matches
LP-923's accept-anyway precedent exactly, and keeping her free text out of the rendered allow-list is the
right default.

One thing to put to the owner rather than decide: **after an Undo the reason is on no screen at all** — the
Withdrawn row is gone and the history line never carried it. If "stays in the history" meant "I can see
later why it was withdrawn", a withdraw → undo leaves nothing visible. The data is there; only the
rendering is not. Your reading is reasonable; it is his sentence, so it is his call.

### (b) Undo treating any soft-deleted condition as withdrawn — the grep is weaker than the guard it replaced

**Your measured claim is true, and I checked it more widely than the test does:** no other
`*.deleted_at =` assignment in `app/` targets a condition (the others are stated financials, lender
contacts, saved views, field reviews); there is no `update(Condition)` bulk statement; no `setattr` on
`deleted_at`; and the `cascade="all, delete-orphan"` on the loan file is an ORM hard-delete cascade, not a
soft one, so a soft-deleted loan file leaves `conditions.deleted_at` untouched.

**But a source grep pins a spelling, not a property.** `test_only_a_withdrawal_deletes_a_condition` catches
`condition.deleted_at =` and would miss `cond.deleted_at =`, `row.deleted_at =`,
`update(Condition).values(deleted_at=…)` and `setattr`. The guard you removed — requiring a
`condition_withdrawn` event before restoring — cannot go stale, costs nothing, and states the correct rule
anyway: *do not resurrect something you did not withdraw.* "It could never fire" is an argument that it is
unnecessary today, which is not the same as an argument that it is worthless tomorrow. I would put it back
and keep the grep as documentation.

### (c) Two tests marking a sheet condition `origin=manual` — avoidable at no cost, and I can show it

The **property** you are testing is reachable, so the tests are not testing a fiction. But the
**intermediate state** — a sheet condition whose origin is manual — is not reachable, and it does not need
to be, because the real path is six lines. My own probe above did exactly that: `create_manual_condition`
(via your `_hand_added`), `move_prep_status(... READY)`, `build(...)` — and the hand-added condition
appeared in the package rows as `9001`. So both tests can use a genuinely hand-added condition instead of
flipping a sheet one's origin, which removes the invented state and the docstring that excuses it.

### The finding is fixed, measured independently

Re-running my own probe against the fix, not the test written from it:

```
built:               ['7086', '6132', '6178', '0006', '9001']
moved:               ['7086', '6132', '6178', '0006']
STORED AFTER SUBMIT: ['7086', '6132', '6178', '0006']        <- 9001 gone from the record
_submitted_on(9001): None                                     <- was a timestamp
withdraw -> submit -> restore -> withdraw again: ALLOWED       <- the one-way door is gone
```

All three consequences are closed at once, which is what computing `sent` once and storing exactly what
was iterated buys. Removing the freeze kills
`test_withdrawn_while_built_it_is_not_sent_and_can_be_withdrawn_again`.

Keeping the un-ticked rows in `sent` is right, incidentally: they are live conditions she chose not to
include, the package view distinguishes them, and `_submitted_on` already tests `included`, so they cannot
block a later withdrawal.

### The Undo guard — unpinned only where it cannot fire, and that is not the direction that matters

You reported honestly that nothing reaches the new clause and no test pretends otherwise. Confirmed, and
worth stating more precisely, because "unpinned" sounds worse than the truth:

| mutation | result |
|---|---|
| the clause removed from `restore` | **survives** — the refusal branch is unreachable today |
| `_was_withdrawn` always `True` (equivalent to no guard) | **survives** — same reason |
| `_was_withdrawn` always `False` | **4 tests fail** |

So the function is firmly pinned in the direction that would hurt: if it ever stopped recognising a real
withdrawal, Undo would refuse one and four tests say so immediately. Only the branch that cannot happen
until another deleter exists is unpinned — which is inherent, not an omission, and inventing a test that
fakes a condition soft-deleted by something else would be testing a fiction, the same trap as (c). Leaving
it unpinned and saying so is the correct handling.

**The ordering inside `_was_withdrawn` is also safe**, which was worth checking since it takes the latest
of two event kinds and a tie would pick arbitrarily: `ConditionEvent.occurred_at` defaults to a
Python-side `utcnow`, so each row gets its own value. Measured over three withdraw/restore cycles in one
transaction — five events, **five distinct timestamps**, about 30 ms apart — and `_was_withdrawn` answered
correctly at each step (False after each restore, True after each withdrawal).

### (c), and the two recorded items

Using a genuinely hand-added condition in the package tests is the right change, and keeping the sheet-flip
in the draft and figures tests is a fair call: those need a confirmed plan's asks or accepted statements,
which the manual path does not produce, and the docstring now says which tests do it and why. The
distinction that matters is the one you drew — the invented state is gone where the real path was cheap,
and declared where it is not.

Both items you recorded rather than changed are the right side of that line: the reason being on no screen
after an Undo is the owner's sentence to interpret, and the child-table class is a design note, not a
defect today.
