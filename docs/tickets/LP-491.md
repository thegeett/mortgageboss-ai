## TI-1 — and the direction argument

⚠️ **A mismatch is `needs_review`, never `fired`** — argued, as the ticket asked. A vesting difference is
frequently legitimate: a revocable trust whose trustee is the borrower, an estate selling, a name changed
on marriage or divorce, a deed not yet recorded. Each is a **correct file** that a firing rule would call
defective. The real failure this guards — wrong property, wrong party — is caught just as well by
surfacing it. IH-2's precedent, on the same reasoning. A test pins that no outcome can produce `fired`.

⚠️ **The purpose branch lives in the producer, not an applicability predicate** — a deliberate departure
from LP-487/LP-488, because TI-1 applies to **both** purposes and there is no single predicate value to
scope on. The abstain a predicate would have given is preserved exactly: an unstated purpose resolves to
`unknown` and the gate surfaces it. All three directions are proven — purchase, refinance, **and absent**.

It **reuses IH-2's normaliser** rather than cloning it, so a fix to either rule's name handling reaches
both, and matches against **either** vested owner (3 of 4 commitments carry a second).

## The derivation, and the run that was thrown away

**Method:** fresh-context re-derivation — call 1 through the normal path, call 2 in a fresh context never
shown the first answer, then compare. Not same-context grading.

⚠️ **The first run was discarded.** It returned **1.0000 with `judgment_ai_failed` on every subject** —
the AWS SSO token had expired, so two *failed* calls agreed with each other perfectly. Exactly LP-490a's
lesson repeating. No rate from it was recorded. Re-run after the token was renewed, the calls succeeded.

| rule | rate | cases | disagreements | verdict spread |
|---|---|---|---|---|
| TI-2 | 1.0000 | 4 | 0 | `{needs_review: 4}` |
| TI-6 | 1.0000 | 4 | 0 | `{needs_review: 3, couldnt_check: 1}` |

⚠️ **The rates compare VERDICTS, not the model's underlying answers** — the honest limit of how they were
measured, recorded on both bars. A judgment rule collapses every value into `needs_review`, so two
**different** answers on the same commitment would still agree at the verdict level. **TI-2 returned
`needs_review` on all four, so its rate carries the least information of any in the cohort: it shows the
pipeline is stable, not that the judgment is.** TI-6's spread did vary, so it at least distinguishes
answered from abstained.

**Model:** `us.anthropic.claude-sonnet-4-5-20250929-v1:0` via **AWS Bedrock**, 2026-08-13.
**Cost: ~$0.15**, against a $0.10–$0.20 estimate reported before the first call. The 303-document bench
was not re-run. **n=4 is the whole corpus** — this proves wiring and direction, not accuracy.

## ⚠️ A consequence worth deciding on

**Nine live judgment rules now emit `needs_review` on every finding, including clean ones** — AS-12,
CR-8, CR-10, ID-8, ID-9, IN-7, OC-2, and now TI-2 and TI-6. `judgment.py` has two exits, `needs_review`
and `couldnt_check`; there is no `satisfied` path. So a clean title chain consumes a sign-off identically
to a broken one, and TI-2 produces one per commitment on every file regardless of the answer.

That is the ratification armor working as designed (LP-376-B), and it is what makes activating on an
unmeasured tag safe. But it is a real load on the processor. Two ways out, different in kind: let a
judgment rule map a confident value to `satisfied` (removes the noise, **breaks the guarantee** — needs
the tag measured first), or leave the armor and fix the surfacing (a needs-list question, not a
rule-engine one). Raised for Geet.
