## Design

**The prompt** (`read_v3.txt`, `READING_VERSION = "read_v3"`):
- every condition's answer carries `clauses`: each clause of the lender's text copied exactly, with the key
  of the item that covers it or a `note` saying why it asks for nothing;
- for a condition WITH a library type, the type's items come first as before, and an item may be added after
  them, with a new key, for a clause they do not cover. The rule names the case: "possibly a Change of
  Circumstance" is an item for the LO.

**Code checks it** (`condition_reading.uncovered_conditionals`). For every conditional word in the lender's
text (`possibly`, `if applicable`, `and/or`: the owner's three, whole words, case-insensitive), the word is
covered when a clause the model quoted contains it, really is in the lender's text (a quote the lender never
wrote covers nothing), and names an item the reading has or carries a non-empty note. Anything else is
reported in the lender's own words.

**The reading.** An uncovered conditional caps the confidence just below the bar (`bar - 0.01`), so the
reading is `needs_confirmation` and nothing is drafted for it until she confirms (README rule 3). The words go
in `reading.uncovered`, which the reading box shows as "Not covered by an item yet: “…”". An added item never
replaces a library item (a key the type already has is ignored), and confirmed readings are left alone.

**The plan: the lender does the type's work, not every clause's.** UWM orders the final inspection (decision
1), so `build_plan` used to give EVERY item of 1228 "Lender is doing it". It now gives that only to the library
type's items. An added item keeps its own step: 1228's re-disclosure is an ask in the LO email. When the lender
is not doing all of a condition, its items carry their own steps (`next_step` is null) and the reason still says
"Ordered through the lender — confirm on your files". Two readers follow the items rather than the step:
- the package's "open prior-to-docs" sentence still says "the final inspection is ordered through the lender
  and not back yet" when the lender is doing any live item (it would otherwise have said "nothing has been
  asked for yet", which is false);
- the plan panel's "Lender is doing it" pill counts a condition the lender does part of.

**Draft side column order.** "Other drafts this round" is now listed by recipient (borrower, title/attorney,
LO, …) as S3-05 shows it, not by creation order. Which draft a plan creates first follows the sheet's order,
and LP-954 put 1228's LO ask ahead of the borrower's.

## Review (of `3253e4d5`)

**No defects. The hard part of this ticket — verifying a prompt change in a suite that stubs the model — is
answered the right way: the code checks the model's output rather than trusting the prompt. One finding,
small and actionable: the guard's floor is lower than the prose describes.**

### Finding — the clause guard verifies the quote is real, not that it is a clause

`uncovered_conditionals` is the whole ticket's load-bearing check, so I tested its boundary rather than its
happy path. Measured, with a control at each end:

```
True  uncovered  <- no clauses at all (the drop this guard exists to catch)
True  uncovered  <- a FABRICATED quote naming a real item
False uncovered  <- a one-word quote "possibly" naming a real item
False uncovered  <- a one-word quote with a junk note "x"
False uncovered  <- the real clause naming a real item
```

The two failures that matter are caught: a dropped clause, and a quote the lender never wrote
(`quoted not in plain_text` does its job). But the weakest input that satisfies the guard is **the
conditional word itself plus any existing item key** — or any non-empty note. So the ticket's "a clause the
AI quoted … names an item the reading has or a note saying why it asks for nothing" is stronger than the
code's test, which cannot tell a clause from an echo of the word, nor judge whether the named item really
covers it.

A judgement cannot be adjudicated in code, and the model is cooperative rather than adversarial — but a
reading that satisfies the guard this way is `READY` and nothing is flagged, so the floor matters.

**Fixed here**, per the brief, both halves: the quote must now say more than the word it contains
(`len(quoted) <= len(word)` is rejected), and the docstring states what the guard establishes and what it
cannot. After the fix, re-measured:

```
True  uncovered  <- no clauses (the drop it catches)
True  uncovered  <- fabricated quote, real item
True  uncovered  <- one-word echo, real item          (was False)
True  uncovered  <- one-word echo, junk note          (was False)
False uncovered  <- the real clause, real item
False uncovered  <- the real clause, real note
```

The trade is recorded in the docstring rather than left implicit: a clause that is nothing but the
conditional phrase ("Provide X. If applicable.") now reads as uncovered. That asks her to look at a
sentence no lender writes, which is the safe direction for a guard whose only cost is a confirmation.
`test_an_echo_of_the_conditional_word_does_not_cover_it` pins all six rows — the last two are its positive
control, so it cannot pass by reporting everything as uncovered — and removing the length check fails it.

### Checked and not findings

- **The §6 supersession is authorised, and I went looking for the opposite.** The acceptance test's new
  comment attributes it to the owner, which is exactly the kind of attribution worth verifying rather than
  accepting. The owner's quoted words at the top of the ticket do say it: *"Test with 1228: 'possibly a
  Change of Circumstance' becomes an item for the LO (re-disclosure)."* An item asked in the LO email
  cannot also be "Lender is doing it", so the §6 row had to give way, and the progress row records the
  supersession. The plan doc keeps its original row, which matches how this project has handled deviations
  since batch 1 — recorded in the progress file, not edited into the spec.
- **The acceptance test update is principled**, which is not what four changed test files usually mean. The
  deciding hunk is the last one: `assert _plan(...) == SECTION_6` was not relaxed, it was **split** — the
  no-AI path still asserts the old row ("WITHOUT THE AI NOBODY READS 1228'S CLAUSES: the library's PA-03
  alone, the lender's, as §6 had it") and only the AI path carries the added item. Keeping the old
  assertion alive for the case where it is still true is the difference between updating a test and
  blessing a regression.
- **No case false-positives in the guard.** `CONDITIONAL` is `IGNORECASE`, `word` is casefolded and
  `_plain` casefolds both sides, so a capitalised "Possibly" in a quote still matches. I checked because a
  normalisation mismatch here would cap confidence on readings that are fine — the too-wide-guard class
  this batch has already paid for twice.
- **`uncovered` has a reader, and stays on her screen.** Rendered at `reading-box.tsx:92` as "Not covered
  by an item yet:", with a test. It is not read by `condition_drafts` or `condition_package`, so the
  lender's own words — which is what the 40-character window holds — reach no borrower or third party.
  Both halves matter: a new field with no reader is a defect this batch has hit, and the LP-950 open item
  is precisely the lender's words travelling outward.
- **The surviving mutation is genuinely equivalent**, and the reasoning holds in every branch rather than
  the one they had in mind. `ready` requires `source is AI and confidence is not None and confidence >= bar
  and not uncovered`. Where `uncovered` is non-empty: if `confidence` is `None` or below the bar, `ready`
  already fails; if it is at or above, the cap has just set it to `bar - 0.01`, so it fails. The guard
  cannot change the answer today. Keeping it is defensive depth, and reporting it as equivalent rather than
  counting it as a kill is the right call — it is also why the pair, not the guard alone, is what a test
  can pin.
- **The prompt change is verified where it can be.** A prompt cannot be tested by a suite that stubs the
  model, so the honest move was not to trust it: `read_v3` asks for `clauses`, and
  `uncovered_conditionals` checks what comes back, capping confidence when a conditional is uncovered. That
  turns an unverifiable prompt edit into a verifiable code guard, which is the shape to reuse next time a
  prompt changes.
- **Their own gap is closed.** Their 9097 predated a one-line lint fix in an acceptance assertion, with
  only that file re-run — and they said so. The full suite after it: **9097 passed, 1 failed** (the named
  sonnet test), 8 skipped, 1 xfailed. Same number, now measured after the fix.
