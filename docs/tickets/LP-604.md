# LP-604 — Cross-check identity by snapshot address

## The problem, in one comparison

The same finding, two consecutive runs on staging:

| | run before | run after |
|---|---|---|
| label A | `liability.3.unpaid_balance (application)` | `liability.3.unpaid_balance (UNITED WHSLE MORT)` |
| label B | `owned_property.1.lien_upb (property schedule)` | `owned_property.1.lien_upb` |
| value | `451829.00` | `$451,829` |

Identical facts about the same mortgage. The model changed one parenthetical and dropped another;
identity was a hash over those labels, so the finding "resolved" and a duplicate opened beside it.

LP-598 had fixed the other half of the same key — the free-text `kind` — and left the labels alone.
Same disease, half treated.

## Measured, not assumed

Three Bedrock calls (Sonnet 4.5, temperature 0) against a faithful LF-3CVT snapshot, then three more
against the production payload shape:

| scheme | distinct identities | stable across all 3 runs |
|---|---|---|
| **address-based** | 5 | **4** |
| label + value | 8 | **1** |

And the case that matters, from the probe:

```
run 1  "Subject property lien balance does not match liability being paid off"
run 2  "Existing mortgage balance does not match subject property lien balance"
both   liability.3.unpaid_balance + owned_property.1.lien_upb   → ONE identity
```

**Path validity: 31 of 31 across both payload shapes.** The model cites real addresses, so the
grounding check rejects fabrications rather than ordinary output. A separate probe confirmed the
lower finding count under the production payload is the model producing fewer, **not** grounding
rejecting real ones — both findings it produced were kept.

## What was built

1. **Identity = `(kind, sorted snapshot paths)`.** No model prose.
2. **Grounding.** A finding citing an address absent from the snapshot is dropped. Nothing checked
   this before — a cited place was prose, so a fabricated pairing was indistinguishable from a real
   one.
3. **The original wording is kept** on a match. Rewriting on every match made a settled finding look
   changed; in three probe runs the same finding returned with two different titles. Now a wording
   change *means* something.
4. **`PROMPT_VERSION` 1 → 2.** It should have moved twice already: LP-598 replaced the category
   vocabulary and rewrote the prohibitions, LP-602 added the `calculation_blocked` clause, and
   neither bumped it — so every file whose snapshot had not otherwise changed was still being served
   answers from the *original* prompt. The fixes were live in the code and invisible on those files.

### Two exceptions on the retention, both load-bearing

- **A cited value moved.** Identity excludes the figures on purpose, so a finding stays itself when a
  balance changes — but its text quotes them. Frozen wording would state $451,829 as fact after the
  file says $412,000.
- **The stored text no longer passes.** LP-601 was this bug one layer over: the composer's guards ran
  only on a cache miss, so prose written before a guard existed outlived it. `text_rejection` is one
  function called from both `_parse` and the retention path, so retained wording is re-checked against
  the rules as they stand.

## Decisions worth recording

**The index is KEPT.** Stripping it (`liability.3.unpaid_balance` → `liability.unpaid_balance`) to
survive reordering was measured and rejected: identical stability, while collapsing `liability.1` and
`liability.4` onto one key so two findings about different debts would silently merge. The cost of
keeping it is that renumbering breaks identity — `build_mismo_section` orders by row UUID so existing
rows hold still, and MISMO re-import is deferred. Revisit when re-import ships.

**`snapshot_paths` is permissive about depth**, accepting both the full route
(`mismo.facts.liability.3.unpaid_balance`) and the leaf key. Vindicated by the probe: the model cited
`calculations.dti.value.gate_reason`, a deep nested route, which a mismo-leaf-only whitelist would
have wrongly rejected. The goal is catching fabrication, not making the model guess a house style.

**Semantic dedupe was considered and NOT built.** Every churn actually observed was rewording, which
addresses fix deterministically and auditably. An AI matcher would reintroduce run-to-run
non-determinism — the thing this feature exists to eliminate — and its dangerous direction is a wrong
"these are the same", which absorbs a new problem into a dismissed finding where nobody sees it. It
stays on the shelf until real granularity drift (one finding one run, four the next) appears.

## The migration deletes rather than re-keys

`c8d1a4e77b93` clears `snapshot_findings` and `snapshot_finding_scans`, which is the opposite of what
LP-600 did one migration earlier. The difference is what the new key needs: LP-600 could recompute
because every input was still on the row, and **no stored row has paths** — they were never asked
for. Inventing one from a label would be a guess written into an identity that then looks
authoritative.

The cost is stated plainly: a `signed_off` / `not_an_issue` row is a processor's decision and this
discards it. It is done only because the alternative — a fabricated path — mismatches silently
forever, losing the same dismissals *and* leaving a wrong key behind. The scan markers go too, or the
next run would be a cache hit over an empty table and the tab would sit empty until the file changed.

## Tests

11 new or rewritten, every part mutation-checked: reverting identity to prose, removing grounding,
always rewriting text, and never refreshing it each fail. Two existing tests were inverted with the
reasoning recorded — one asserted `# wording refreshes`, the other varied a model LABEL to prove two
findings differ, which was the bug rather than the contract.

LP-600's migration test was re-pinned to fixed values from its own code rather than to the app: a
migration is history and must keep meaning what it meant, whatever the app does next.

Full suite green: **5461 passed**.
