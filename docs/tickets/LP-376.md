# LP-376 — The five tabs + the provenance card

## WHAT THIS TICKET IS

The first time a human sees the rule engine's output. ~40 tickets of gates, five outcome states, and
provenance existed only in test assertions and JSON; LP-375 made the data reachable (`rule_findings`), this
renders it — the §8 five-tab model + the provenance card — **on the real verification page**
(`/loan-files/[id]/verification`), in its existing visual language. No new page. **Frontend only — zero
backend change.**

## ACCEPTANCE CRITERIA

- Five tabs with counts on the existing Verification panel; Tab 1 default; tabs 1-4 read `rule_findings`,
  Tab 5 reads `findings`; never merged/summed.
- The honesty contract enforced in the UI (couldnt_check → Tab 1; Tab 3 ≠ Tab 4; needs_review ≠ open).
- A row is identifiable without its raw content-id; Tab 1's three outcomes are visually distinct, `open`
  first; the provenance card shows the reasoning + the spec's guideline; no §10 actions on tabs 1-4.
- The DTI card renders its gate. Honest empty states. biome + tsc + vitest + the (untouched) backend green.

## PHASE 0 — THE DESIGN DECISIONS

**Decision 1 — the subject label.** `subject_key` is an opaque content-id and is **never** rendered as a
row's identity. The **message** (always present — the backend refuses to persist a reasonless finding) is the
row's identity as a subline; messages differ per subject, so rows are distinguishable. A compact **subject
chip** is derived from `load_bearing_tags` when a recognisable value exists (`ruleSubjectChip`):

| family | example | chip |
|---|---|---|
| AS-1 (per-deposit) | txn.amount `20000` + txn.date `2025-03-27` | **$20,000 · 2025-03-27** |
| ID-2 (per-borrower) | id.name_normalized present | **the name** |
| ID-6 (loan-level) | subject_key `"loan"` | **Loan-level** |
| ID-7 (per-document) | id.address_normalized present | **the address** |

When no chip derives (e.g. a couldnt_check with no address tag), the row relies on the rule id + category +
message — never the hash. **Gap found:** the rule NAME (`spec.name`, e.g. "Current address consistency") is
NOT in the payload — only `rule_id` ("ID-4"). Rows show the id + category; the guideline (in the card) gives
full context. Reported, not worked around (§ below).

**Decision 2 — Tab 4 is structurally empty.** `not_applicable` subjects are not persisted (AS-1's 33 money-out
transactions never became rows), so Tab 4 renders empty on **every** file. It is kept (with count 0) and shows
an **honest empty state explaining why** — "not-applicable subjects aren't recorded; this tab exists so 'not
applicable' can never quietly absorb a 'couldn't check'." Not dropped (§8 says it exists, and its visibility is
the honesty contract), not fabricated.

**Decision 3 — Tab 1's internal treatment.** Within Needs attention, three labelled groups in priority order —
**Violation** (`open`, first), **Couldn't check** (`couldnt_check`), **Needs review** (`needs_review`) — each
with its count + a one-line "what this means", each colour/dot-distinct. So the 2 `open` violations sit atop
the 30 `couldnt_check` and stay findable (LP-333's warning, one layer up).

**The DTI card** now renders its gate: the tile shows **"Gated"** (not a number), the detail shows a
gate banner naming the unknown input(s), and the insurance/taxes line reads **"Unknown"** (not $0.00). The
display agrees with the engine.

## HOW THE §8 HONESTY CONTRACT IS ENFORCED IN THE UI

- `couldnt_check` maps to Tab 1 only (`OUTCOME_TAB`); Tab 2/4 can never contain it (tested).
- Tab 3 and Tab 4 have distinct empty states, not merged (tested).
- `needs_review` sits in Tab 1 but under its own "Needs review — not a violation" group and carries a
  ratification-pending marker (tested).
- The two systems are two typed lists into two tab sets; counts are per-list, never summed (tested — 2 + 7
  reads as 2 and 7, "9" appears nowhere).

## WHAT THIS SURFACE CANNOT DO YET

- **No §10 actions on tabs 1-4** (Accept-risk / Request-docs / Override / Add-note) — LP-377, and whether you
  can "accept risk" on a `couldnt_check` is an undecided policy question. A button that does nothing is a lie,
  so there are none. Tab 5 keeps its existing actions.

## WHAT BUILDING IT REVEALED ABOUT THE FINDINGS MODEL

- **The four-tab split is right** — the five outcomes fell cleanly into it, and the honesty distinctions
  (couldnt_check ≠ pass, Tab 3 ≠ Tab 4, needs_review ≠ open) all had a natural home. No outcome was homeless.
- **A reason is ALWAYS present** — the backend refuses to persist a reasonless verdict (LP-375
  `_persistable`), so no row is a dead end. Confirmed, and relied on.
- **The provenance is legible and it is the product** — a `couldnt_check`'s load-bearing tag carries a real
  sentence ("the document states no address type"); a parsed tag carries a value with no reasoning (shown as
  value only — confidence is hidden without reasoning, so a number is never noise).
- **The subject is only half-legible** — the message identifies a row, but a compact per-subject *label* is
  uneven: it derives for AS-1 (txn tags) but not for a bare `couldnt_check`. **The rule NAME is missing from
  the payload** — a real gap: rows show "ID-4", not "Current address consistency". A small `RuleFindingPublic`
  addition (the spec's `name`) would close it — a finding for LP-377, not a backend reach here.
- **Tab 1 is usable at 34 rows — because of the grouping, not despite the count.** The 2 violations are found
  instantly under a red "Violation" header; the 30 `couldnt_check` are one labelled group below. But **30
  couldnt_check on one file is itself a signal**: most are genuinely-absent documents (no title, no POA, one
  DOB source). A future refinement worth considering: sub-group `couldnt_check` by *why* (missing document vs
  thin data) so the tab reads as a document-request worklist. Reported, not built.
- **Tab 4's structural emptiness is a model choice surfaced** — because `not_applicable` isn't persisted, the
  UI cannot show what a rule found irrelevant to the file. If that ever matters (an auditor asking "did you
  consider X?"), the backend would need to persist n/a subjects — a decision, not a bug.
