# LP-519 — loan-level transaction aggregation (scope)

Not built. This is the scoping document; the phasing at the end is the proposed order.

## The problem, stated once

Three separate gaps are the same architectural limitation:

1. **Split deposits (money in).** AS-12 gained a materiality floor in LP-518. A $20,000 gift split into
   five $4,000 transfers is now five sub-threshold deposits and produces **zero** findings. The floor
   traded visible noise for an invisible gap.
2. **Recurring undisclosed debits (money out).** FR-5 *"Recurring undisclosed debit"* exists in
   `rule_kinds.csv` and is **not active and has no spec file**. `activation_bars.yaml:2194` records why:
   *"FR-5's declared 'pattern across statements' is unanswerable from a context that shows one
   transaction."*
3. **`txn.apparent_category: debt_payment`** is a declared enum value that **no spec consumes**.

Every one of them is blocked by the same thing: a rule enumerating `per_deposit` (or any
per-transaction subject) gets one transaction's tags. It cannot see the others exist. Same wall LP-498
hit, same wall LP-518 recorded.

## No rule looks at money-out at all

Worth stating plainly, because it is easy to assume otherwise: `txn.is_money_in` appears in exactly
three specs — AS-1, AS-2, AS-12 — and all three are `op: eq, value: in`. **Nothing in the engine
examines an outgoing transaction.**

The two live undisclosed-debt rules approach it from the other side entirely:

| rule | active | reads |
|---|---|---|
| CR-1 — Undisclosed liability | yes | MISMO vs application |
| CR-4 — Undisclosed tradeline | yes | credit report vs stated liabilities |
| FR-5 — Recurring undisclosed debit | **no** | bank statements |

So a debt visible only as a recurring bank debit — a private or family loan, a rent-to-own, anything
not reported to the bureaus — is invisible today. That is the category most likely to be undisclosed.

## The precedent already exists

`derived._stmt_nsf_count` is the exact shape needed, and its abstention discipline should be copied
rather than reinvented:

- walks `snapshot.tags.by_subject.values()`, reads a per-transaction tag, returns a loan-level number;
- **absent ≠ zero** — if the per-transaction tag is on no transaction it returns `unknown`, because a
  concrete 0 would mean "detection ran and found none" when it actually means detection never ran;
- **any `unknown` → abstain**, because the count would be a lower bound and reporting it as exact would
  under-report just as a fabricated 0 would.

Declared as `stmt.nsf_count: {mode: derived, subject: loan, data: stmt_nsf_count}` in
`tag_production.yaml`, with a `vocabulary_extra.yaml` entry (`entity: loan`, `value_type: number`).
`subject: loan` is materialised by the generic pass, so this avoids the LP-516 trap that killed a
`transaction`-subject derived tag.

## The constraint that decides the phasing

**Perception for the interesting version does not exist.** Checked across `tag_production.yaml`,
`app/ai/tag_production.py` (the live Stage-A producer) and `app/ai/tag_correlation.py` (Stage B):

| tag | declared in `fact_tags.csv` | produced |
|---|---|---|
| `txn.amount`, `txn.date` | yes | yes (parsed) |
| `txn.is_money_in`, `txn.apparent_category` | yes | yes (Stage A, `txn_stage_a`) |
| `txn.has_identified_source` | yes | yes (Stage B) |
| `txn.is_nsf_or_overdraft` | yes | own group, held on calibration |
| **`txn.counterparty`** | yes | **no** — orphan (LP-390-6 dropped it from AS-12's load-bearing for this reason, though it remains in `reasoned_over`) |
| **`txn.is_recurring`** | yes | **no** |
| **`txn.implies_obligation`** | yes | **no** |

So: grouping deposits **by counterparty** is not buildable today, and FR-5 is not buildable today.
An **ungrouped** aggregate is buildable today from tags that already exist.

A second constraint: **there are no list-valued tags in the system** (`value_type` is
`number | date | string | enum | match_hash | object`, and no tag uses `object`;
`activation_bars.yaml` notes FR-6 "would be the first list-producing tag"). So an aggregate must
return a **scalar**, and the evidence for *which* transactions it covers lives in the tag's `reasoning`
string — exactly as `stmt.nsf_count` does.

## Proposed phasing

### Phase 1 — the ungrouped money-in aggregate (buildable now, no new perception)

A derived loan tag summing money-in deposits that AS-12's floor scoped out, plus a sibling rule that
fires when the total is itself material.

- Inputs: `txn.is_money_in`, `txn.amount`, `txn.apparent_category` — all produced.
- Excludes the guideline-exempt categories (`payroll`, `interest`), for the arithmetic reason LP-518
  recorded: two paychecks alone exceed a 50% floor, so including payroll fires on every W-2 borrower.
- Catches the five-way split; does **not** distinguish one source from five different ones.

**It must not be framed as a large-deposit finding.** Aggregation has no guideline basis — the research
found every agency text framed per-deposit ("a single deposit that exceeds 50%…"). It implements the
separate, un-thresholded duty: *"the lender must investigate any indications of borrowed funds"* and,
on a refinance, *"the lender remains responsible for ensuring that any borrowed funds, including any
related liability, are considered."* Cite that, not B3-4.2-02's definition.

**Window:** the documented period (~60 days). No agency text specifies one; this matches the evidence
boundary, needs no extra justification, and does not let a split straddle a statement edge.

**Do not use the word "structuring" in finding text.** It is a BSA/AML term (31 U.S.C. 5324) carrying
criminal connotation and has no mortgage-side definition. *"Multiple deposits totalling $X within the
documented period — confirm the source"* says the same thing without borrowing the vocabulary.

### Phase 2 — produce the missing perception

`txn.counterparty`, `txn.is_recurring`, `txn.implies_obligation`. These are AI tags on the transaction
subject, so they extend `txn_stage_a` or get their own group. **This costs a model call per
transaction on every file** — `txn_stage_a` is a required group, so widening it is not free. Its own
group, scoped to depository statements (the `txn_nsf` pattern), is likely the better shape.

Note `txn.is_nsf_or_overdraft`'s precedent: a new perception tag is **held on calibration** until a
labelling round scores it. Expect the same gate here rather than treating production as shipping.

### Phase 3 — counterparty grouping, and FR-5

With Phase 2 landed:

- the money-in aggregate can group by counterparty and return the **largest same-counterparty total**
  (a scalar), which distinguishes five transfers from one person from five unrelated deposits;
- **FR-5 becomes buildable** — a loan-level tag over `txn.is_recurring` + `txn.implies_obligation` +
  `txn.amount`, answering the "pattern across statements" question its spec was written for;
- `debt_payment` gets a consumer.

## Open questions

- **Does the money-in aggregate fire alongside the per-deposit findings, or instead of them?** On a
  file where deposits individually clear the floor, both would surface the same money. Suppressing the
  aggregate when any member already fired is probably right, but it is a real decision.
- **Should the aggregate use the same floor as the per-deposit test** (50% purchase / 10% refinance of
  qualifying income), or its own? Same is simpler and defensible; different would need its own basis.
- **FR-5's threshold.** A recurring $40 debit is a streaming subscription; a recurring $450 debit is a
  car payment. Where the line sits is a domain call, and unlike the deposit floor there is no agency
  number to anchor on.
