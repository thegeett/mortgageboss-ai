# LP-519 — loan-level transaction aggregation

**Phase 1 is built and INERT.** Phases 2–3 are scoped, not built — they need new AI perception, which
this codebase holds on a calibration round rather than shipping.

## What landed

| piece | state |
|---|---|
| `derived._stmt_repeated_money_in_max_total` + its vocabulary/production entries | built, materialising |
| `AS-13.yaml` — the rule reading it | built |
| `rule_kinds.csv` row, `activation_bars.yaml` bar | built |
| `ACTIVE_RULE_IDS` | **deliberately not added** |

**AS-13 is inert on purpose.** Its bar is `calibratable-now` with `validated: false`, so the eligibility
gate refuses it. Same-amount grouping is a heuristic that has **never run against a real snapshot**, and
`validated: true` would assert a sign-off on behaviour nobody has observed — which is exactly how LP-516
shipped a gate that did nothing on a real file. Every other rule in this repo was measured first and
activated second. `test_as13_is_deliberately_inert` pins the hold so it cannot be lost silently; flip
`validated` after a real run, updating that test in the same commit.

Predicted effect once activated, on LF-WCHG: **not computed, and the earlier number here was wrong.**

The figure previously stated ($8,000, from "its five surviving AS-12 deposits, four at $2,000 and one at
$3,000") was computed over the wrong population. The aggregate applies **no floor** — its input is every
non-exempt money-in deposit on the file, not the ones that survived AS-12's materiality floor — so a
group of sub-threshold deposits that AS-12 never reported could sum higher than any group among the
survivors. The prediction also predated the three discriminators the review added: `transfer_own` is now
exempt, deposits must cluster within 14 days to count, and duplicate statement lines are deduplicated.
Each of those can only lower the total.

The honest statement is that the effect on LF-WCHG is unknown until the aggregate is materialized against
that file's real snapshot, which is the same real run the `validated` flip already waits on. Reporting a
number derived from the wrong input set would make the activation decision look measured when it is not,
and this is the number that decision gets measured against.

## The problem, stated once

Three separate gaps are the same architectural limitation:

1. **Split deposits (money in).** AS-12 gained a materiality floor in LP-518. A $20,000 gift split into
   five $4,000 transfers is now five sub-threshold deposits and produces **zero** findings. The floor
   traded visible noise for an invisible gap.
2. **Recurring undisclosed debits (money out).** FR-5 *"Recurring undisclosed debit"* exists in
   `rule_kinds.csv` and is **not active and has no spec file**. `activation_bars.yaml:2194` records why:
   *"FR-5's declared 'pattern across statements' is unanswerable from a context that shows one
   transaction."*
3. **`txn.apparent_category: debt_payment`** is a declared enum value that **no spec consumes**.

Every one of them is blocked by the same thing: a rule enumerating `per_deposit` (or any
per-transaction subject) gets one transaction's tags. It cannot see the others exist. Same wall LP-498
hit, same wall LP-518 recorded.

## No rule looks at money-out at all

Worth stating plainly, because it is easy to assume otherwise: `txn.is_money_in` appears in exactly
three specs — AS-1, AS-2, AS-12 — and all three are `op: eq, value: in`. **Nothing in the engine
examines an outgoing transaction.**

The two live undisclosed-debt rules approach it from the other side entirely:

| rule | active | reads |
|---|---|---|
| CR-1 — Undisclosed liability | yes | MISMO vs application |
| CR-4 — Undisclosed tradeline | yes | credit report vs stated liabilities |
| FR-5 — Recurring undisclosed debit | **no** | bank statements |

So a debt visible only as a recurring bank debit — a private or family loan, a rent-to-own, anything
not reported to the bureaus — is invisible today. That is the category most likely to be undisclosed.

## The precedent already exists

`derived._stmt_nsf_count` is the exact shape needed, and its abstention discipline should be copied
rather than reinvented:

- walks `snapshot.tags.by_subject.values()`, reads a per-transaction tag, returns a loan-level number;
- **absent ≠ zero** — if the per-transaction tag is on no transaction it returns `unknown`, because a
  concrete 0 would mean "detection ran and found none" when it actually means detection never ran;
- **any `unknown` → abstain**, because the count would be a lower bound and reporting it as exact would
  under-report just as a fabricated 0 would.

Declared as `stmt.nsf_count: {mode: derived, subject: loan, data: stmt_nsf_count}` in
`tag_production.yaml`, with a `vocabulary_extra.yaml` entry (`entity: loan`, `value_type: number`).
`subject: loan` is materialised by the generic pass, so this avoids the LP-516 trap that killed a
`transaction`-subject derived tag.

## The constraint that decides the phasing

**Perception for the interesting version does not exist.** The complete produced set of `txn.*` tags,
established across every producer location — `tag_production.yaml` (parsed + AI group declarations),
`app/ai/tag_production.py` (the live Stage-A prompt) and **`app/services/tag_correlation.py`** (Stage B;
note this is the service layer, not `app/ai/tag_correlation.py`, which only holds the prompt):

| tag | declared in `fact_tags.csv` | produced |
|---|---|---|
| `txn.amount`, `txn.date` | yes | yes (parsed) |
| `txn.is_money_in`, `txn.apparent_category` | yes | yes (Stage A, `txn_stage_a`) |
| `txn.has_identified_source`, `txn.source_strength` | yes | yes (Stage B) |
| `txn.is_nsf_or_overdraft` | yes | own group, held on calibration |
| **`txn.counterparty`** | yes | **no** — orphan (LP-390-6 dropped it from AS-12's load-bearing for this reason, though it remains in `reasoned_over`) |
| **`txn.is_recurring`** | yes | **no** |
| **`txn.implies_obligation`** | yes | **no** |
| **`txn.source_reference`** | yes | **no** |

So: grouping deposits **by counterparty** is not buildable today, and FR-5 is not buildable today.
An aggregate over the produced tags is.

A second constraint: **no list-valued tag is produced.** `fact_tags.csv` *declares* five
(`title.open_liens`, `contract.contingency_dates`, `aus.conditions`, `fraud.novel_discrepancy`,
`loe.required_conditions`) and six `object`-typed `calc.*` tags, but **none of the five has a producer** —
which is what `activation_bars.yaml` means by FR-6 "would be the first list-producing tag in the
system". (Stated carefully on purpose: declared-vs-produced is the exact distinction the table above
turns on, and an earlier draft of this ticket got it wrong by checking only `vocabulary_extra.yaml`.)

So an aggregate must return a **scalar**, with the evidence for *which* transactions it covers carried
in the tag's `reasoning` string — exactly as `stmt.nsf_count` does.

## Proposed phasing

### Phase 1 — repeated same-amount deposits (buildable now, no new perception)

**The design this replaces, and why it does not work.** The obvious shape is "sum the deposits AS-12's
floor scoped out". It is not buildable: a derived tag is materialised **before** any rule runs and a
recipe receives only the snapshot — it has no access to a spec's `reference_values`, so it cannot know
what floor AS-12 applied. Reimplementing the floor inside the recipe would put a threshold in Python,
against the rules-as-data principle, and leave two copies free to drift. Summing *all* non-exempt
money-in instead avoids that but fires on essentially every file (LF-WCHG: ~$11,000 against a $1,317
floor), so it carries no signal.

**What works instead: group by repeated amount.** A split shows up as the *same amount, more than once*
— which needs no floor and no counterparty.

New derived loan tag `stmt.repeated_money_in_max_total` (number):

- walk every subject; take transactions with `txn.is_money_in = in` whose `txn.apparent_category` is
  not guideline-exempt (`payroll`, `interest`, `transfer_own` — for the arithmetic reason LP-518 records:
  two paychecks alone exceed a 50% floor, so including payroll fires on every W-2 borrower);
- group by exact `txn.amount`, keep groups of **2 or more**, return the largest group's **total**;
- `reasoning` names it: *"4 deposits of $2,000.00 within the documented period"*;
- abstention, per `_stmt_nsf_count`: tags absent → `unknown`; `txn.is_money_in` on no subject at all →
  `unknown` (detection never ran ≠ none found); any in-scope amount or date `unknown` → `unknown`
  (the total would be a lower bound). No repeats found, everything readable → a concrete **0**.

**Amount equality alone is a weak signal, and the review found three ways it is wrong.** All three are
answerable from facts already on the subject, so none of them adds a perception dependency:

- **the category.** `transfer_own` is Stage A's own label for "a transfer between the borrower's own
  accounts" — a standing savings-to-checking sweep of one round figure is the most common benign repeated
  credit there is, and the bar's `fp_fn` text names it as a false positive to avoid. Exempt, like payroll.
- **the cadence.** Grouping with no time window cannot tell a *split* (same amount, clustered over days)
  from *recurring income* (same amount, monthly). Six $1,800 rent or child-support credits sum to $10,800
  and clear a 50% floor on any income under $21.6k/mo — accusing an income stream documented elsewhere in
  the file of being borrowed funds. Members of a group now have to chain within **14 days** of each other
  (`_SPLIT_WINDOW_DAYS`), read from `txn.date`, which is parsed rather than perceived. A chain rather than
  a fixed span, so a split that dribbles out over three weeks is still one cluster.
- **the document.** Two uploads of one statement are two documents with two `content_id`s, and
  `assign_content_ids` deliberately gives byte-identical content distinct ids, so nothing upstream
  collapses them. A single $9,000 deposit present in both copies would become a 2-member group totalling
  $18,000. Deposits are now keyed on `(amount, date, description)` — the description comes from the raw
  `TransactionRecord`, PII-redacted at rest. AS-1 and AS-12 are immune to this (they would emit the same
  per-deposit finding twice); this rule would turn duplication into a *new claim about a pattern*.

**Abstention is bounded, not all-or-nothing.** A deposit whose direction or category is `unknown` forces
`unknown` only when its amount matches an in-scope amount or another undetermined one — i.e. only when it
could form or extend a repeat. Stage A is instructed to return `unknown` liberally and a real file carries
dozens of transactions, so the unbounded form made the tag *less* likely to be concrete the larger the
file got, leaving the rule silently useless on exactly the files it exists for.

New rule **AS-13** (AS-1…AS-12 are taken), `subject_enumeration: loan`, deterministic. **AS-7 is the
template** — it is the existing loan-subject rule reading an aggregated transaction tag
(`stmt.nsf_count`), and it shows the exact operand shape. Note a loan-subject rule uses a plain
`{tag: …}` for a loan tag; `loan_tag` is only needed by a per-subject rule.

```yaml
operands:
  repeated: {tag: stmt.repeated_money_in_max_total}
  threshold:
    product:
      - {reference: repeated_deposit_floor_pct}
      - {tag: dti.qualifying_income_monthly}
```

**One fraction, not two.** AS-12 varies its floor by loan purpose; AS-13 cannot, because a deterministic
outcome guard (`when_tags`) does not resolve a `loan_tag` — LP-518 added a load-time validator rejecting
exactly that, since such a predicate is absent on every subject. Threading the loan map into
`_tags_hold` would lift the restriction and is the natural follow-up (it is the unbuilt half of LP-518's
review finding 2), but it touches a shared evaluator path and does not belong in this ticket.

50% of qualifying income is the right single number: the aggregate's claim is *"these deposits together
are as significant as one large deposit"*, so the guideline's own figure is the honest anchor, and
unlike AS-12's refinance branch it needs no invented second value. On LF-WCHG that is a $6,583 floor
against a $8,000 repeated total (4 × $2,000) — **it would fire**, saying something the five per-deposit
findings do not.

**Limitation, stated rather than implied:** exact-amount grouping catches $4,000 × 5 and misses
$3,900 / $4,100 / $4,000. It is a heuristic that degrades gracefully, and counterparty grouping
(Phase 3) is the general answer.

**It must not be framed as a large-deposit finding.** Aggregation has no guideline basis — the research
found every agency text framed per-deposit ("a single deposit that exceeds 50%…"). It implements the
separate, un-thresholded duty: *"the lender must investigate any indications of borrowed funds"* and,
on a refinance, *"the lender remains responsible for ensuring that any borrowed funds, including any
related liability, are considered."* Cite that, not B3-4.2-02's definition.

**Window:** the documented period (~60 days). No agency text specifies one; this matches the evidence
boundary, needs no extra justification, and does not let a split straddle a statement edge.

**Do not use the word "structuring" in finding text.** It is a BSA/AML term (31 U.S.C. 5324) carrying
criminal connotation and has no mortgage-side definition. *"Multiple deposits totalling $X within the
documented period — confirm the source"* says the same thing without borrowing the vocabulary.

### Phase 2 — produce the missing perception

`txn.counterparty`, `txn.is_recurring`, `txn.implies_obligation`. These are AI tags on the transaction
subject, so they extend `txn_stage_a` or get their own group. **This costs a model call per
transaction on every file** — `txn_stage_a` is a required group, so widening it is not free. Its own
group, scoped to depository statements (the `txn_nsf` pattern), is likely the better shape.

Note `txn.is_nsf_or_overdraft`'s precedent: a new perception tag is **held on calibration** until a
labelling round scores it. Expect the same gate here rather than treating production as shipping.

### Phase 3 — counterparty grouping, and FR-5

With Phase 2 landed:

- the money-in aggregate can group by counterparty and return the **largest same-counterparty total**
  (a scalar), which distinguishes five transfers from one person from five unrelated deposits;
- **FR-5 becomes buildable** — a loan-level tag over `txn.is_recurring` + `txn.implies_obligation` +
  `txn.amount`, answering the "pattern across statements" question its spec was written for;
- `debt_payment` gets a consumer.

## Open questions

- **Does AS-13 fire alongside AS-12's per-deposit findings, or instead of them?** On LF-WCHG both would
  surface the same $8,000. Resolved for Phase 1 as **alongside**: AS-13's claim ("four deposits of the
  same amount") is genuinely different information from AS-12's ("is this one deposit borrowed?"), and
  suppression would need cross-rule state the engine does not have. Revisit if it reads as duplication
  on a real file.
- **FR-5's threshold.** A recurring $40 debit is a streaming subscription; a recurring $450 debit is a
  car payment. Where the line sits is a domain call, and unlike the deposit floor there is no agency
  number to anchor on.
