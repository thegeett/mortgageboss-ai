# LP-638 — a misclassified document cannot be corrected

- **Ticket:** LP-638
- **Status:** Done — the type picker offers the catalog and only the catalog (`4598388`, reviewed in `1209dde`). Searchable, keyboard-navigable, with the PATCH rejecting an unknown type 422.
- **Date:** 2026-09-01
- **Found on:** staging `LF-ZE9N`, reported by the processor: *"there is no way to confirm in drawer,
  there is no field to update and say it is this type"*
- **Scope:** Backend — `api/documents.py`, `schemas/document.py`; Frontend — document drawer, a new
  searchable picker

## The report

LP-637 shipped a way to re-read a document whose type the classifier got wrong. When that still came
back `unknown`, the documented remedy was "correct the type by hand in the drawer". **That remedy did
not work**, and the processor found it before anyone checked it.

Three defects, each worse than the last.

### 1. The picker offered 8 of 164 types

`OVERRIDE_TYPE_OPTIONS` was a hardcoded list written for LP-44, in Phase 1, when the catalog had
three document types:

```
pay_stub · w2 · bank_statement · tax_return_1040
drivers_license · credit_report · gift_letter · other
```

The catalog now has **164**. `closing_disclosure`, `purchase_agreement`, `mortgage_statement`,
`homeowners_insurance` and 150-odd others were not selectable at all — so the document that prompted
this, a Closing Disclosure, had no correct answer available.

### 2. Two of the eight were not catalog types

`tax_return_1040` and `other` do not exist in the catalog (the real slug is `tax_return`). The
override endpoint validated nothing, so choosing either set a document to a string with **no tier, no
category and no extractor**:

| | correct type | what the picker set |
|---|---|---|
| type | `tax_return` | `tax_return_1040` |
| tier | Tier 1 | Tier 3 |
| category | income & employment | misc |
| extractor | yes | none |

And satisfaction matches `needs_type == document_type` exactly, so **a document corrected to
`tax_return_1040` can never satisfy a `tax_return` need** — the same unmatchable-row defect as
bug-001 and bug-009, reached through the control that exists to fix misclassification. Correcting a
type made the file quietly worse.

### 3. The helper text was a stale claim

`EXTRACTABLE_TYPES` in the frontend listed three types while the backend registry holds **121**. So
correcting a document to `closing_disclosure` told the processor *"This type is recorded only — no
data is extracted"* while the pipeline extracted it. A sentence about what the system does, wrong.

## What this builds

**`GET /documents/types/catalog`** — the picker's options, served from `CATALOG`. A type added to the
catalog is selectable the same day, and a list that cannot drift cannot go stale again. It carries
`extracts` from the extractor registry, so the helper text is a served fact rather than a local
guess.

**Catalog validation on the override endpoint.** Rejecting an unknown type at the API, not only in
the picker: the list was one caller and the next would have had the same freedom.

**A searchable picker** (`components/ui/searchable-select.tsx`). A native `<select>` is right for the
short fixed lists it serves elsewhere and wrong for 164 options — it can only be searched by first
letter. Type-to-filter on label *or* slug, arrow/Enter/Escape keys, grouped by category, no new
dependency (the reason `select.tsx` gives for being native in the first place).

## The pattern

All three defects are one shape: **a list in the frontend duplicating a list in the backend, and
drifting.** The fix in every case is to serve the backend's, not to update the copy. This is the same
failure LP-635 found three times over one column name, and the same reason LP-637's bulk control
deliberately does not compute eligibility client-side.

## Review

### The processor still could not confirm

The report was two complaints: *"there is no way to confirm in drawer, there is no field to update
and say it is this type."* The commit fixed the second and left the first. `changed` gated the Apply
button on the selection differing from the current type — which is exactly the confirm case — while
the banner directly above it said "confirm or correct the type below". A `needs_review` document
whose AI type is already right, the common case, still had no action available.

Confirming matters because the PATCH is what performs it: it sets `classification_confidence = 1.0`
and clears the review state, which is what takes the document out of the queue. The button now reads
**Confirm** when nothing has changed and is enabled for a flagged document, gated on the selection
being a real catalog entry — which also closes the other half of it: the retired-slug fallback keeps
a non-catalog type visible, and the endpoint now rejects anything not in the catalog, so confirming
a document typed `unknown` would otherwise be a guaranteed 422.

### The picker opened itself on every document

`onFocus` was the only way to open the list. The drawer is a Radix Sheet, whose FocusScope focuses
the first tabbable node on mount — and everything above the picker is headings and divs, so the
picker is it. Opening any document popped a 164-option listbox over the drawer body. It looked
intermittent only because a cold types cache leaves the input disabled, and therefore untabbable, on
the first open. Opening is now an explicit act: click, type, or arrow.

That fixed a second bug with it. Choosing an option `preventDefault`s the mousedown so focus never
leaves the input — so clicking the field again fired no `focus` event and the control was dead until
the processor clicked elsewhere first.

### Escape closed the whole drawer, and the obvious fix does not work

Radix's `DismissableLayer` binds Escape on `document` in the **capture** phase, so it runs before any
handler inside the layer. A processor backing out of the type list lost the drawer and the correction
in progress.

Stopping the event in the component does not prevent this, and a draft of the fix assumed it would.
Measured with a capture listener registered before mount: it still runs, because it has already run
by the time the target's own handler is reached. Nothing a child does after the fact can un-run it.
So the component reports its open state and the drawer stands its Sheet down —
`onEscapeKeyDown` + `preventDefault` while the list is open. The component keeps its own Escape
handling, which is correct outside a dismissable ancestor.

### An abandoned search stranded the list

Closing on an outside click left `query` set. The input correctly reverted to the selected label, so
nothing looked wrong — and refocusing restored the abandoned search and its filtered list. On a
164-type catalog a processor came back to a picker that appeared to hold one option, with no visible
cause. Every exit resets now.

### The control had no accessible name

The two `useSemanticElements` suppressions are correct: ARIA 1.2's combobox pattern is right here and
a native `<select>` is precisely what cannot serve it. But defending the suppressions is not the same
as being accessible — the input had neither `aria-label` nor `aria-labelledby`, so a screen reader
announced an unnamed combobox. `label` is a required prop now, so the next caller cannot repeat it.
`id` was optional while `aria-controls`, `aria-activedescendant`, the option ids and the highlight
scroll all hung off it; it is generated when absent.

### The list keyed by catalog slug drifted on the commit that introduced it

Three of `_TYPE_LABEL_OVERRIDES`'s ten keys — `vod`, `hud1`, `form_1003` — are not catalog slugs, so
those entries were dead and the types they were written for fell through to the derived label. A
second hand-maintained list keyed by catalog slug is the exact shape this ticket exists to end.
Corrected, and a test now asserts every override names a real type.

The derived label was `capitalize()`, which lowercases everything after the first letter: a processor
picked from "Hoa statement", "Aus findings" and "E consent disclosure", and those strings are now
echoed back in the confirmation toast. Derived per word against an acronym set instead, which fixes a
dozen-plus labels without one override each.

### Two label vocabularies that must not be merged

`_TYPE_LABEL_OVERRIDES` and `naming.NAME_RULES[...].label` both map a slug to a human-ish string,
overlap on `w2` and already **disagree** on `voe` ("VOE" vs "Verification of employment (VOE)"). That
reads as drift and invites someone to make them agree — which would break filenames, because
`standard_name` joins its label into `{Type}_{Identifier}_{Date}` and cannot hold spaces or slashes.
They are different vocabularies. `tests/documents/test_label_vocabularies.py` pins the property that
keeps them apart, in both directions.

### Answered

**(c) Validation is safe against existing data.** Queried staging: no document carries
`tax_return_1040` or `other`. One type in use is outside the catalog — `unknown`, on 2 documents —
and the retired-slug fallback keeps it visible while `canApply` prevents submitting it.

**(d) `staleTime: Infinity` is right.** The list changes only on deploy. The residual is that a tab
open across a backend deploy keeps the old list until reload; if the catalog ever SHRINKS, a stale
client could offer a type the server now rejects, which surfaces as a clear 422 rather than a silent
wrong write.

**(e)** — see the two vocabularies above. Keep the map, and do not merge it.

### Known limitation

The dropdown is absolutely positioned inside the drawer's `overflow-y-auto` body, so it is clipped
when the section sits low in a scrolled drawer. The fix is a portal with measured coordinates;
deliberately not attempted in a review round, because hand-rolled positioning with scroll and resize
tracking is the same category of thing this review just spent its findings on.
