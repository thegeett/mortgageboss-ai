# LP-996 — Pre-send content check

Step 2 of the email work (`loan-email.md` §15a). Code, one small migration, tests, a measurement and
a dev check against MailHog. No AWS or Terraform changes. Backend only; the screen is LP-997.

## What and why

Rule 5 (`loan-email.md` §2): every outbound email gets a pre-send check, with no rates, APRs,
approval or denial wording, or account and routing numbers. A blocked email is refused with the
reason, and sending it anyway needs a note.

This ticket checks a **Send** (`send_draft(transmit=True)`): the email the app itself sends from the
file address. It reads the final subject and body, exactly what the worker will send, and blocks on
three grounds:

| Ground | What it catches | Reason shown |
|---|---|---|
| `rate` | a percentage, "APR", "annual percentage rate", "interest rate" | Mentions an interest rate or APR |
| `commitment` | approved, approval, pre-approved, denied, denial, declined, committed, commitment, guarantee(d/s), cleared to close, underwriting decision | Uses approval or denial wording (for example approved, denied, cleared to close) |
| `payment_routing` | any 9-digit number, "routing number", "account number", "wire instructions", "wire transfer" | Contains an account or routing number, or wire instructions |

**The patterns are the AI drafter's own** (`ai/email_draft.py`: `_RATE`, `_COMMITMENT`, `_ROUTING`),
imported through a new public helper, not copied. A test checks they are the same compiled objects.
No pattern was changed.

**Why the drafter's other five grounds are not used for a person's email.** `money_amount`,
`triggering_term`, `settlement_service`, `invented_instruction` and `identifier` exist to stop the
model inventing content. On a processor's own words or a catalog document list they block ordinary
text: "the $10,000 deposit", "your down payment", "all pages of each statement". `identifier` blocks
any email address or link, because its dotted pattern matches `summit.example` or `gmail.com`. (The
brief named the `[LF-XXXX]` footer as an example of what `identifier` would block. It does not, and
a test now checks that directly.)

**Not checked:** "I've sent it" (`transmit=False`). The processor already sent that email from her
own mail app; the app only records it. Rule 5 says every outbound, so templates sent automatically
(reminders, auto-replies) will need the same check when they start sending. Today nothing sends
automatically: the worker only sends rows a person pressed Send on (LP-994).

## How the override works

- Grounds found, no note: refused with `ContentCheckError` (a `CannotSendError`, so every existing
  handler still refuses). Nothing is recorded or queued: no evidence row, no activity entry, the
  draft stays `draft`, the needs are untouched.
- Grounds found, note shorter than 10 characters after trimming: the same refusal, with "Add a note of
  at least 10 characters to send anyway."
- Grounds found, valid note: sent as normal, and the override is recorded:
  - **Evidence row:** `content_check_grounds` (e.g. `rate,commitment`) and
    `content_check_override_note` (the trimmed note). Not `guardrail_fired`, which is the AI
    drafter's guard. Both are returned by the evidence API (`GET /loan-files/{id}/evidence`), so an
    override can be told apart from a clean send in the app.
  - **The send's own activity line**, not a second one: "Sent a document request for 1 item(s). Sent
    despite the content check: Mentions an interest rate or APR.", with the approver as actor and
    the grounds in `detail.content_check_grounds`. With all three reasons the line is 248 characters,
    inside the 256-character column (a test checks the worst case).
  - **The note is only on the evidence row.** It is not on the activity line, and never written to
    application logs (a test captures the logs and checks).
- No grounds: sent as normal; a note sent anyway is ignored and not recorded.

**The readonly views.** `readonly.communication_evidence` exposes `content_check_grounds` (a fixed
vocabulary, names nobody) and excludes the note (`EXCLUDED` and `NEVER_EXPOSED` in the drift test).
The note is kept off the activity line because `readonly.activity_logs` exposes `summary` and
`detail` with only identifier shapes scrubbed, so a name in a note would pass. The first version put
the note on the activity line; the review caught that this undid the evidence-view exclusion.

**Same problem, not changed here:** finding notes (`finding_resolution.py`, `detail.note`) and the
legal-hold reason (`evidence.py`, `detail.reason`) are processor free text that already reach
`readonly.activity_logs` that way, although `readonly.loan_files` hides the legal-hold reason. Worth a
ticket of its own.

## What changed

- **`ai/email_draft.py`:** `_SEND_CHECK_GROUNDS` (the three ground names with the module's own
  compiled patterns) and `send_check_grounds(text) -> set[str]`, with a comment saying why the other
  five grounds are drafter-only.
- **`services/content_check.py` (new):** `content_check_grounds(subject, body, *, html)`. An HTML
  body is read as text first with LP-993's `html_to_text`, so a tag cannot split a word
  (`<strong>appro</strong>ved` reads "approved"). A link's hidden address is left out: the borrower
  reads the link text, which is checked (a link whose text is the address is still checked), not a
  9-digit path segment she never sees. Subject and body are checked separately, so no match is made
  across the join. Grounds come back in a fixed order (`rate`, `commitment`, `payment_routing`).
  `CONTENT_CHECK_REASONS` holds the plain-words reasons in one place; `reasons_for` and
  `reason_items` read it for the activity line and the API. `OVERRIDE_NOTE_MIN_CHARS = 10`.
- **`services/outbound_mime.py`:** `html_to_text(..., keep_link_targets=True)`. The default is
  LP-993's behaviour for the plain part; the content check passes False.
- **`services/email_send.py`:** `ContentCheckError(CannotSendError)` with `grounds`,
  `note_too_short` and `message`. `send_draft(..., override_note=None)`: on `transmit=True`, after
  every existing guard and before anything is recorded, it checks the subject and the body **as
  stored for the worker** (after `finalise_draft_body`, `build_outbound` and, for an HTML draft,
  `sanitise_html`). Then the refusal or the override, as above.
- **`services/evidence.py`:** `record_sent` takes the grounds and the note.
- **`api/evidence.py`:** `EvidencePublic` gains `content_check_grounds: list[str]` and
  `content_check_override_note`.
- **Migration `7c1e5a9b3d48`** (hand-written, with downgrade): `communication_evidence.
  content_check_grounds` and `content_check_override_note` (text, null); `readonly.
  communication_evidence` rebuilt from LP-821's body plus the grounds. Applied, rolled back and
  re-applied on the dev database.
- **API:** `SendDraftRequest.override_note: str | None` (max 2,000 characters). `ContentCheckError`
  becomes a 409 with a structured body (below). Every other `CannotSendError` keeps its 409 shape.

## Measurement

**Dev database** (read-only: one transaction, rolled back). Every open draft finalised the way
`send_draft` would (greeting resolved, signature "Pat Processor", footer tag, sanitised), and every
outbound email that is not a draft. Measured before the dev check added rows.

| | Checked | Blocked | `rate` | `commitment` | `payment_routing` |
|---|---|---|---|---|---|
| Open drafts | 3 | 1 | 0 | 0 | 1 |
| Sent emails | 7 | 0 | 0 | 0 | 0 |
| **Total** | **10** | **1** | 0 | 0 | 1 |

| Kind | Checked | Blocked |
|---|---|---|
| `initial_documentation_request`, draft | 1 | 1 (`payment_routing`) |
| `initial_documentation_request`, sent | 7 | 0 |
| Condition email (`condition_request`), draft | 2 | 0. **Both were to the title attorney and the loan officer, not the borrower**: see the review finding below |
| Hand-written | 0 | — |

The one example: `payment_routing` on "…your name, the bank's name, the **account number** and the
statement period." No `rate` or `commitment` examples exist in dev.

Ten emails is too few to give a rate, so three sweeps of the text the templates fill in were added
(no database):

| What | Trips | Detail |
|---|---|---|
| Catalog guidance and labels, borrower-held types | **3 of 113** | `bank_statement`, `investment_account`, `retirement_account`: each says "…the **account number** and the statement period / vested balance" (`payment_routing`) |
| Catalog labels, other parties' types | 3 of 53 | `title_commitment` ("Title **commitment**", `commitment`), `underwriting_approval` ("Underwriting **approval**", `commitment`), `wire_instructions` ("**Wire instructions**", `payment_routing`) |
| Rule `outbound_ask` sentences | 1 of 17 | AS-1: "…the account holder's name, the **account number**, and every page…" (`payment_routing`) |
| Condition library email lines | 3 of 8 | DI-01: "an attorney on the lender's **approved** list" (twice, `commitment`); "**Wire instructions** that match the attorney…" (`payment_routing`) |
| Dev conditions' lender wording (account numbers masked, as emails do) | 0 of 6 | — |
| **Borrower condition email (S3-04), fixed text** (found in review) | **always** | `render_borrower`: "The lender **approved** your loan with a few conditions" (`commitment`) |

**Misfires: they block ordinary requests.**
- **Bank, investment and retirement statements (`payment_routing`).** The catalog's own guidance
  tells the borrower the statement must show the account number, and `_ROUTING` matches the phrase.
  Bank statements are on nearly every purchase file's first request, so **every
  `initial_documentation_request` that asks for them is blocked**: 1 of 1 open initial-request draft
  in dev, and confirmed live in the dev check (check 4 below). That is well above 1 in 5 for that
  email. The rule engine's AS-1 ask says the same thing.
- **Title-company requests.** Asking for the title commitment or the wire instructions trips
  `commitment` or `payment_routing`. The ground exists to stop *us* sending wire instructions; asking
  the title company for theirs is a normal request.
- **Every borrower condition email (`commitment`). The worst one, found in review, not by the
  measurement above.** `render_borrower` opens every borrower condition email with "The lender
  approved your loan with a few conditions", so a Send of one is always refused. The question email's
  "The approval shows…" (`render_question`) is the same. My measurement missed it: the only two
  condition drafts in dev were to other parties, so "2 checked, 0 blocked" never covered the borrower's.
  Today these are sent with Mark sent (record-only, not checked); the general Send can transmit one.
- **Condition DI-01:** "the lender's approved list" trips `commitment`.
- **A percentage that is not a rate (`rate`).** `_RATE` matches any `N%`, so a processor writing
  "100% of the gift funds" or "owners of 25% or more" is refused as "Mentions an interest rate or
  APR". Found in review; the same kind of misfire that kept `money_amount` drafter-only.
- **Not seen in dev but possible:** a 9-digit lender loan number. Condition emails keep the lender's
  loan number unmasked (`mask_accounts(..., keep=letter.loan_number)`), and `\b\d{9}\b` matches it
  (checked on a sample subject). None of the 6 dev conditions has one.

Not changed here, as asked. The strict-xfail tests below go red when any of these is fixed, so the
marker has to come off. Options for the follow-up: narrow `account number` / `wire instructions` for
a person's Send (e.g. block only alongside digits), or reword the catalog guidance ("the last four
digits of the account number" still trips; "which account it is" does not). A domain question for the
resident expert: whether "approved list" and "title commitment" belong on the list at all, and how the
borrower condition email should open instead of "The lender approved your loan…" (a template
wording change, which is a new version).

## For LP-997

A refused Send is a 409 in the app's error envelope. The structured part is `error.data`:

```json
{
  "error": {
    "type": "conflict",
    "message": "This email can't be sent as written.",
    "data": {
      "code": "content_check",
      "message": "This email can't be sent as written.",
      "reasons": [
        {"ground": "rate", "text": "Mentions an interest rate or APR"},
        {"ground": "commitment", "text": "Uses approval or denial wording (for example approved, denied, cleared to close)"}
      ],
      "override_allowed": true,
      "note_too_short": false,
      "min_note_length": 10
    }
  }
}
```

`note_too_short` is true when a note was sent but is under `min_note_length` once trimmed; `message`
then reads "This email can't be sent as written. Add a note of at least 10 characters to send
anyway." Every other refusal keeps its old shape (`error.message` only, no `data`), so branch on
`error.data.code == "content_check"`.

The screen must show: the message; each reason's `text` as a list; a note box ("Why send it
anyway?"), with Send anyway enabled only at 10 or more characters after trimming (the server checks
too); and re-post the same body and subject with `override_note`. Notes are capped at 2,000
characters. The evidence view can show `content_check_grounds` and `content_check_override_note`
from the evidence API. Because of the misfires above, a bank-statement request, and any borrower
condition email sent with Send, will hit this screen until the follow-up lands.
