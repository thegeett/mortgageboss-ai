# LP-824 — The request asks for an attachment and then warns against sending one

- **Ticket:** LP-824 · Phase 4 follow-up, from processor feedback
- **Status:** Specified — not started
- **Date:** 2026-09-07
- **Scope:** `app/communications/templates/initial_documentation_request.v*.txt`, ADR-401 version bump
- **Migration:** none expected

---

## What was reported

The draft contradicts itself. It says:

> You can reply to this message with them attached, or send them to:
>   $inbox_address

and then, four lines later:

> Email is not a fully secure channel. If you would rather not send something this way, reply and
> tell us and we will arrange another route.

A borrower reads: *send it by email — but email is not safe — but tell us if you would rather not,
and we will think of something.* The instruction and the caveat are both defensible on their own and
they cancel out.

## Measured

`initial_documentation_request.v2.txt`, lines as quoted. Both sentences are in the same template
version, so this is not a rendering accident.

The caveat is not decoration: outbound carries **no attachments by design** — LP-815 enforced GLBA
Safeguards 16 CFR 314.4(c)(3) structurally, and `OutboundEnvelope` (LP-816) has no attachments
field. The rule is about what WE send. It says nothing about what a borrower may send us, which is
why the template can ask for a reply-with-attachment at all.

**The alternative route the caveat gestures at already exists and the template does not mention it.**
LP-815 built the secure upload link. `initial_documentation_request.v2.txt` has no `$upload_link`
variable, so the one concrete answer to "I would rather not email this" is the one thing the email
does not offer. Instead it asks the borrower to reply and wait.

## The decision that has to be made

Three ways to resolve it, and they are genuinely different products:

1. **Drop the caveat.** Simplest. Loses a disclosure that a compliance reviewer may want present,
   and nobody in this repo has asked for it to be there.
2. **Keep the caveat and make it actionable** — replace "reply and tell us and we will arrange
   another route" with the secure link. The contradiction becomes a choice: email it, or use the
   link. This is the reading I would take, and it depends on **LP-827** (the link does not currently
   open).
3. **Lead with the link and make email the fallback.** Strongest privacy posture, biggest behaviour
   change, and it makes every request depend on a link being minted first.

This is a wording and disclosure decision on a borrower-facing message. It is not mine to settle
alone, and the five templates' wording is already on the list for the domain expert.

## Done when

- The template no longer instructs and dis-instructs the same action.
- Whichever option is taken, it ships as a **new template version** (ADR-401 — the version is a
  content hash and the record pairs words with version), not an edit to v2. Messages already sent
  under v2 must keep resolving to the words that went out.
- If option 2 or 3: the template carries the link, and there is a defined answer for what the body
  says when no link has been minted — an empty `$upload_link` must not render a bare sentence
  pointing nowhere.

## For the reviewer

The check that matters is not that the new words read well. It is that a message sent under v2 still
renders as v2 — a template edit in place would silently rewrite history in the evidence record.
