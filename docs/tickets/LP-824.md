# LP-824 — The request asks for an attachment and then warns against sending one

- **Ticket:** LP-824 · Phase 4 follow-up, from processor feedback
- **Status:** Built — awaiting review
- **Date:** 2026-09-07
- **Scope:** `app/communications/templates/initial_documentation_request.v*.txt`, ADR-401 version bump
- **Migration:** none expected

---

## What was reported

The draft contradicts itself. It says:

> You can reply to this message with them attached, or send them to:
>   $inbox_address

and then, four lines later:

> Email is not a fully secure channel. If you would rather not send something this way, reply and
> tell us and we will arrange another route.

A borrower reads: *send it by email — but email is not safe — but tell us if you would rather not,
and we will think of something.* The instruction and the caveat are both defensible on their own and
they cancel out.

## Measured

`initial_documentation_request.v2.txt`, lines as quoted. Both sentences are in the same template
version, so this is not a rendering accident.

The caveat is not decoration: outbound carries **no attachments by design** — LP-815 enforced GLBA
Safeguards 16 CFR 314.4(c)(3) structurally, and `OutboundEnvelope` (LP-816) has no attachments
field. The rule is about what WE send. It says nothing about what a borrower may send us, which is
why the template can ask for a reply-with-attachment at all.

**The alternative route the caveat gestures at already exists and the template does not mention it.**
LP-815 built the secure upload link. `initial_documentation_request.v2.txt` has no `$upload_link`
variable, so the one concrete answer to "I would rather not email this" is the one thing the email
does not offer. Instead it asks the borrower to reply and wait.

## The decision that has to be made

Three ways to resolve it, and they are genuinely different products:

1. **Drop the caveat.** Simplest. Loses a disclosure that a compliance reviewer may want present,
   and nobody in this repo has asked for it to be there.
2. **Keep the caveat and make it actionable** — replace "reply and tell us and we will arrange
   another route" with the secure link. The contradiction becomes a choice: email it, or use the
   link. This is the reading I would take, and it depends on **LP-827** (the link does not currently
   open).
3. **Lead with the link and make email the fallback.** Strongest privacy posture, biggest behaviour
   change, and it makes every request depend on a link being minted first.

This is a wording and disclosure decision on a borrower-facing message. It is not mine to settle
alone, and the five templates' wording is already on the list for the domain expert.

## Done when

- The template no longer instructs and dis-instructs the same action.
- Whichever option is taken, it ships as a **new template version** (ADR-401 — the version is a
  content hash and the record pairs words with version), not an edit to v2. Messages already sent
  under v2 must keep resolving to the words that went out.
- If option 2 or 3: the template carries the link, and there is a defined answer for what the body
  says when no link has been minted — an empty `$upload_link` must not render a bare sentence
  pointing nowhere.

## For the reviewer

The check that matters is not that the new words read well. It is that a message sent under v2 still
renders as v2 — a template edit in place would silently rewrite history in the evidence record.

## Built, 2026-09-07

### Two measurements changed the shape of the ticket

**The contradiction is in three templates, not one.** `initial_documentation_request.v2`,
`reminder_follow_up.v1` and `condition_response_request.v1` all say *"reply with them attached, or
send them to $inbox_address"* and all carry the same caveat verbatim. Only the first is rendered by
anything today — nothing in `app/` references the other four keys — so only the first was reported.
All three are bumped. An asymmetry is a class, and leaving two would ship this on the day somebody
wires them up, with nothing to say it was known. `status_update` and `custom` carry the caution and
ask for nothing, so there is nothing for it to contradict; they are unchanged, deliberately.

**The link cannot be carried, only named** — and this is what made the ticket small. The three
options in the specification assumed a `$upload_link` variable was possible. It is not:
`MintedLink`'s docstring says the plaintext token *"exists HERE AND NOWHERE ELSE — the row holds a
hash"*, so **no URL can be rebuilt for an email composed later**. A URL in a stored draft would have
to be a live credential sitting in `communications.body`, and minting one at read time would put a
side effect on a GET. So option 2 resolves to naming the route, not linking it — no plumbing, no
deferred placeholder, no dependency on LP-827 having been applied.

### The change

`SECURITY_NOTICE` was one constant doing two jobs. Split:

* **`SECURITY_CAUTION`** — *"Email is not a fully secure channel."* The fixed decision in the
  execution protocol, in every template, asking or not.
* **`SECURITY_NOTICE`** — the caution plus *"If you would rather not send documents this way, reply
  and ask — we will send you a secure upload link instead."* For the templates that ask.

The message now gives an instruction and a real choice rather than an instruction and an argument
against it. And the offer is one we can honour: LP-815 shipped the link and the panel that mints it.

Three new versions under ADR-401 — v2's file and fingerprint stay on disk, so an audit row naming v2
still resolves to the words it named.

### One existing test's premise was stale

`test_the_security_notice_does_not_promise_a_link_that_does_not_exist` asserted both `"http" not in`
and `"link" not in` the notice, reasoning that *"steering to an upload link is LP-815's, and a link
that resolves to nothing would be worse in an email than no link at all."*

The first half still holds and is now asserted for a sharper reason — the token cannot be rebuilt, so
a URL here could only be stale or a stored credential. The second half was true while LP-815 was
unbuilt and is not any more. Rewritten as `test_the_notice_names_the_route_but_never_a_url`, which
also pins the old phrase as a literal so a revert fails rather than reading as a rewording nobody
notices.

### Mutations

| mutation | result |
|---|---|
| notice reverted to the vague wording | 4 failed |
| **only the reported template fixed**, the other two left at v1 | 1 failed — `reminder_follow_up` |
| v3's file edited in place instead of bumped | 2 failed — the ADR-401 pin, and the wording |

The second is the one worth having. "Found one, fixed one" is the failure mode this ticket was most
likely to reach, and the class-level parametrisation over `_ADDRESS_BEARING` is what catches it — a
fourth asking template inherits the requirement rather than quietly not having it.

### Left undone, on purpose

The vague sentence survives in `status_update.v1` and `custom.v1`. It is vague there too, but it
contradicts nothing — neither template asks for a document — and bumping them would be two more
version bumps for a cosmetic reason, against a template whose notice placement `test_the_status_
update_does_not_ask_and_then_offer_a_route_out` shows was deliberate. Recorded rather than done.

Whether a security caution belongs in a message that asks for nothing at all is a disclosure
question for the domain expert, along with the five templates' wording. Unchanged by this ticket.

### The three standing checks

**Tenancy:** nothing touched. **Logging:** nothing added. **AI:** none — the notice is a constant,
and the drafting engine's three framing slots do not reach it.
