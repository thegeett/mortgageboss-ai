- **Ticket numbers:** LP-934 and LP-935 were free on both `phase4.5-conditions` and `raspberrypi-work`
  (`git ls-tree -r <branch> -- docs/tickets/`, local and `origin/`); LP-918 to LP-929 stay reserved for

## Design

Three parts, none of them product code.

1. **The screens against the plan** (below): every screen opened as PNG and HTML, compared with the plan's
   tickets, §4, §4a and §6, and with what Stage 2 and Phase 4 actually built; every number re-derived.
2. **The harness**, `scripts/visual-check/`:
   - `seed.py`: builds a screen's state on a **scratch** database (name must start with `mbai_visual_`;
     it refuses the dev database by name and by URL) from fictional fixtures only. It creates the file
     the screens draw (Alex Rivera, `LF-R7QK`, UWM, $242,199, 100 Example Ln), imports round 1 through
     the real services (the round-1 fixture rendered as a PDF, parsed by the task body, imported), and
     stamps the "Today" table's timestamps onto what it wrote. States a later ticket builds register
     themselves in the same file; until then asking for one says which ticket builds it.
   - `shoot.mjs`: Node's built-in `WebSocket` and `fetch` driving headless Google Chrome over the
     DevTools protocol, as LP-909 §5 did. **No new dependency:** no Playwright, no Puppeteer, no npm
     package. It logs in as the seeded processor through the real `/auth/login` (the refresh cookie
     then lets the app's silent refresh sign it in), sets 1600 px wide and the reference PNG's own
     height, forces the light theme and the `America/New_York` time zone, freezes the page's clock at
     the state's moment, and saves `docs/design/phase4.5-conditions/stage3/checks/<S3-xx>-actual.png`
     (or `-review.png` for the reviewer).
   - `run.sh`: one command. Creates and migrates the scratch database, seeds the state, starts an API on
     `:8011` and a `next dev` on `:3011` against it (with `NEXT_DIST_DIR=.next-visual`, so the dev
     server on `:3000` is not touched), shoots, and stops what it started.
   - `README.md`: how to run it.
3. **The state file**: the Stage 3 section of `phase4.5-progress.md`, its ticket table, the decisions
   pre-made, and an empty STOP AND ASK list.

Reuses: `render_uwm_pdf` (Stage 1's PDF fixture), `create_round_from_sheet`, the `parse_round` task body,
`import_round`, `seed_lender_codes`, `create_loan_file`. Adds no fixture data beyond the seed script's
constants, all fictional (ADR-405).

### The finding

**F1 — the "never the dev database" guard was enforced by code and pinned by no test.** This is the
harness's one safety property: `seed.py` writes a whole loan file and `run.sh` drops and re-creates
the database it is handed first, so pointed at `mortgageboss_dev` the result is not a bad screenshot
but the dev database gone. The guard is right and I verified it by running it three ways, but it was
checked by hand when it was written and by nothing afterwards — a later edit could have removed it in
silence, which is exactly what the "Done when … with a test that would fail if it weren't" clause is
for. **Fixed:** `backend/tests/scripts/test_visual_check_refuses_dev_db.py` imports the real module
(its guard runs at import only under `__main__`, so importing is safe) and pins both directions —
five names refused, including the near-miss `mbai_visual` without its underscore; the
named-in-`.env` branch with the dev name patched rather than read from the machine; and a positive
control that a genuine `mbai_visual_` database is *allowed*, without which a guard that refused
everything would pass. **Mutation-checked:** replacing the prefix test with `if False` fails 4 of the
7, and the positive control still passes. 7 passed; ruff, format and mypy clean.
