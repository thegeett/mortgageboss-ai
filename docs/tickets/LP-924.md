## Design

**A proposal, computed by code, applied only by her** (README rule 6: figures change only when she
applies them). `GET /loan-files/{id}/figures-check` works out what the file's accepted evidence changes.
`POST …/figures-check/apply` applies it through the existing edits. Nothing is stored for the proposal
itself: it is recomputed from the file each time.

**What it finds (`app/services/figures_check.py`).**
- **Verified assets.** From evidence that proves funds to close (an item that checks "enough for
  closing", such as 7086's statements) once the item is done: the latest ending balance per account,
  summed, as LP-923 computes it.
  - "In the file" is the file's stated depository assets for that borrower.
  - Applying updates the one stated checking or savings asset held in that name. If there is none, or
    more than one, it adds a stated asset for the statement's account. The stated-financials service
    does the write (`add_stated_asset` / `update_stated_asset`), with its own audit.
- **Monthly homeowners insurance.** From the homeowners insurance declarations the file holds
  (`homeowners_insurance`: `annual_premium` ÷ 12), chosen as the latest effective policy.
  - "In the file" is the insurance line the DTI calculator uses now.
  - The source names the condition whose policy it is: the condition whose push-back or text names that
    effective date, so 6178 in round 1 (LP-934 M2). Otherwise it names the document.
  - Applying sets the DTI calculator's insurance override (`set_dti_override`) with a note naming the
    document.
- **Housing ratio and DTI.** The existing DTI calculator run twice: as the file is, and with the proposed
  insurance as an in-memory override (`build_dti_calculation(extra_overrides=…)`, LP-643's preview path).
  The same code produces the ratio that applying produces. The DTI row shows the change in points.

**The DU tolerances (Fannie Mae B3-2-10), by code** (`du_rerun_reasons`, pure). DU must be re-run when:
- the DTI rises above 45% from 45% or under;
- the DTI rises 3 points or more;
- the verified income is lower than the income DU used;
- the verified reserves are short of what DU required and below 90% of it.

The guide's own examples: 44% → 46% needs a re-run (crosses 45%); 46% → 48% does not (already over 45%,
up 2 points). An input the file does not have is not checked, and the panel says so rather than claiming
it passed.

**Assets now cover closing.** Shown when the verified total is at least the funds the condition requires
(7086's $38,210.40, from its reading).

**Applying.**
- The client sends the rows it showed. The server recomputes and applies only if they are still the
  same; otherwise it refuses with 409 "The figures changed — look again before applying."
- Each change is written through its existing service, which keeps its own audit. One activity line
  names the conditions: "Applied 2 changes from accepted evidence (7086, 6178)".
- The loan figures and the lender's track are never changed by anything else here.

**"Not now"** hides the panel for this view only; the proposal is recomputed next time the tab opens.

**The panel** sits under the round strip while there is a change to propose. It shows "Figures check" and
"2 changes from accepted evidence", then a table with the columns Figure · In the file (struck through) ·
→ · From evidence · Source. Below that are the two callouts, the line explaining when it would say
"Re-run DU before submitting", and the buttons "Apply 2 changes to the file's figures" and "Not now".
The file rail keeps the old ratios until she applies.

**Tests.** The reading model's stub moves to `tests/conditions/conftest.py` (autouse). The LP-923 review
found that a new test file importing `_asked` without its own stub reached the real API.
