## Design

**A proposal, computed by code, applied only by her** (README rule 6: figures change only when she
applies them). `GET /loan-files/{id}/figures-check` works out what the file's accepted evidence changes.
`POST …/figures-check/apply` applies it through the existing edits. Nothing is stored for the proposal
itself: it is recomputed from the file each time.

**What it finds (`app/services/figures_check.py`).**
- **Verified assets.** From evidence that proves funds to close (an item that checks "enough for
  closing", such as 7086's statements) once the item is done: the latest ending balance per account,
  summed, as LP-923 computes it.
  - "In the file" is the file's stated depository assets for that borrower.
  - Applying updates the one stated checking or savings asset held in that name. If there is none, or
    more than one, it adds a stated asset for the statement's account. The stated-financials service
    does the write (`add_stated_asset` / `update_stated_asset`), with its own audit.
- **Monthly homeowners insurance.** From the homeowners insurance declarations the file holds
  (`homeowners_insurance`: `annual_premium` ÷ 12), chosen as the latest effective policy.
  - "In the file" is the insurance line the DTI calculator uses now.
  - The source names the condition whose policy it is: the condition whose push-back or text names that
    effective date, so 6178 in round 1 (LP-934 M2). Otherwise it names the document.
  - Applying sets the DTI calculator's insurance override (`set_dti_override`) with a note naming the
    document.
- **Housing ratio and DTI.** The existing DTI calculator run twice: as the file is, and with the proposed
  insurance as an in-memory override (`build_dti_calculation(extra_overrides=…)`, LP-643's preview path).
  The same code produces the ratio that applying produces. The DTI row shows the change in points.

**The DU tolerances (Fannie Mae B3-2-10), by code** (`du_rerun_reasons`, pure). DU must be re-run when:
- the DTI rises above 45% from 45% or under;
- the DTI rises 3 points or more;
- the verified income is lower than the income DU used;
- the verified reserves are short of what DU required and below 90% of it.

The guide's own examples: 44% → 46% needs a re-run (crosses 45%); 46% → 48% does not (already over 45%,
up 2 points). An input the file does not have is not checked, and the panel says so rather than claiming
it passed.

**Assets now cover closing.** Shown when the verified total is at least the funds the condition requires
(7086's $38,210.40, from its reading).

**Applying.**
- The client sends the rows it showed — each row's `key` and its `from_evidence` value. The server
  recomputes and applies only if that set is still the same; otherwise it refuses with 409 "The
  figures changed — look again before applying."
  **What this does NOT compare is the `In the file` column** (`in_file`), which the payload does not
  carry: a figure edited on the file between her reading the table and pressing Apply is overwritten
  without a 409. See the review's F1.
- Each change is written through its existing service, which keeps its own audit. One activity line
  names the conditions: "Applied 2 changes from accepted evidence (7086, 6178)".
- The loan figures and the lender's track are never changed by anything else here.

**"Not now"** hides the panel for this view only; the proposal is recomputed next time the tab opens.

**The panel** sits under the round strip while there is a change to propose. It shows "Figures check" and
"2 changes from accepted evidence", then a table with the columns Figure · In the file (struck through) ·
→ · From evidence · Source. Below that are the two callouts, the line explaining when it would say
"Re-run DU before submitting", and the buttons "Apply 2 changes to the file's figures" and "Not now".
The file rail keeps the old ratios until she applies.

**Tests.** The reading model's stub moves to `tests/conditions/conftest.py` (autouse). The LP-923 review
found that a new test file importing `_asked` without its own stub reached the real API.

## Review (of `2f848c5f`)

**One finding, reported rather than fixed, and one STOP AND ASK raised on the question this ticket
asked the review.** The arithmetic, the screen and the recompute-on-read design all hold.

### F1 — Apply does not compare the baseline she was shown

The client sends `key` and `from_evidence` per row; `FiguresApplyRow` has no `in_file`, so the "In the
file" column — the before she read — never reaches the server. A figure edited on the file between her
reading the table and pressing Apply therefore passes the guard.

**Demonstrated, not argued.** With the full row set sent exactly as the client sends it, a concurrent
edit of the stated asset from `11,062.18` to `20,000.00` was **overwritten by Apply with no 409**; the
asset ended at `41,914.42`. Bounded: the activity log records the edit with its `from` and `to`, so it
is visible afterwards, and only the one depository asset is affected.

It matters because the row she reads is *"$11,062.18 → $41,914.42"*, and the promise attached to the
button is that she applies what she saw. This ticket's own prose said the server "applies only if they
are still the same"; that sentence is now corrected above to say what the comparison actually covers.

**Not fixed here, deliberately.** The remedy changes the API contract and the UX — `in_file` into
`FiguresApplyRow`, into the comparison, and into what the client sends, producing refusals it does not
produce today. The repo already has the pattern for it: LP-916's `expected_updated_at` on the draft
update. That is a product decision about how often to stop her, not a reviewer's to take unilaterally.

**How I got there is worth recording.** My first probe "proved" the guard caught it — and it was my
probe that was wrong: I had sent only the rows with `applies=True`, so the set differed for an
unrelated reason. The guard compares all four rows, ratios included. Had I stopped at the first green,
I would have reported the opposite of the truth.

### STOP AND ASK — the 45% reading you asked me to check

**I cannot settle it from this repository, and it should not be settled by either of us.** What is
verifiable:

- The plan states the rule twice as a LEVEL: §2.3 "required if the recalculated DTI **exceeds 45%**,
  or rises by 3 points or more", and §5 "DTI now **over 45%** or up 3 points or more".
- The plan's own **Done when** requires `46% → 48%` **not** to be flagged. Under a level reading it
  would be, since 48% exceeds 45%.

Those two cannot both hold. Your implementation follows the Done-when — the crossing reading — and is
internally coherent: measured across the range, `44→46` flags, `46→48` does not, `46→49` flags on the
3-point limb, `45.0→45.1` flags, `50→51` does not. So a file already above 45% that rises by less than
3 points is never flagged, which is exactly where the two readings part.

`du_rerun_reasons`'s docstring calls these "the guide's own examples". They are also the plan's
Done-when examples, and B3-2-10 itself is not in this repository, so that attribution is not traceable
from here — the same class of citation issue LP-918 was reviewed for. **This is a domain question with
money attached** (a missed DU resubmission), and CLAUDE.md sends domain questions to the resident
expert rather than to a reading of a guide nobody here can open. Raised as STOP AND ASK 2; the build
stands meanwhile, since it satisfies the ticket's acceptance criterion and the 3-point limb still
catches large rises above 45%.

## Review of the follow-up (of `e7afa680`) — F1 verified

**No findings. The fix does what it says, and it does not over-refuse**, which is the failure mode a
guard like this invites.

**My own scenario, re-run against the new code:** with the full row set read from the check and the
stated asset then edited to `20,000.00` underneath, Apply is **refused** and the concurrent edit
**survives as 20,000.00**. Before the fix the same probe ended with the asset at `41,914.42` and no
409.

**The positive control matters more than the refusal here.** A comparison that refused everything
would pass the test above and break the feature. An untouched baseline still applies cleanly: asset →
`41,914.42`, exactly as before.

**Mutation, run independently.** Making the comparison vacuous — dropping the recomputed `in_file` so
the server compares the client's own value back — fails
`test_a_figure_changed_underneath_is_refused_not_overwritten`, and only that test. The server compares
what it recomputed, not what it was told.

**The contract's safe direction.** `in_file` is `str | None` with a default, so a stale client that
does not send it produces a mismatch and a 409 rather than a silent overwrite. Failing toward "look
again" is the right way round for this particular field.

**STOP AND ASK 2's attribution is corrected.** `du_rerun_reasons` now cites "the plan's Done-when
examples (§5 LP-924)" instead of "the guide's own examples", and points at the STOP AND ASK. The
implementation is unchanged and still follows the Done-when — which is right, because the question is
the owner's and the expert's, not the code's.

## Follow-up — F1 fixed (the builder's call)

The review's F1 was that Apply compared `from_evidence` only, so a figure edited between her reading the
table and pressing Apply was overwritten without a 409. I fixed it. The design already promised
"applies only if the file would still get exactly what she saw", and the row she reads is both sides:
"$11,062.18 → $41,914.42".

- `FiguresApplyRow` carries `in_file`, the client sends it, and `apply` compares every row as
  `(key, in_file, from_evidence)`.
- The refusal is the existing 409 "The figures changed — look again before applying."; she re-reads the
  panel and applies again. It fires only when a figure really moved underneath her, which is the case
  the promise is about.
- `test_a_figure_changed_underneath_is_refused_not_overwritten` is the reviewer's scenario: the stated
  asset is edited to $20,000.00 after the check is read, Apply is refused, and $20,000.00 stands. The
  mutant that echoes her `in_file` back instead of computing it fails that test.
- `du_rerun_reasons`'s docstring now calls 44→46 and 46→48 the plan's Done-when examples, not "the
  guide's own", and points at STOP AND ASK 2.

**Verification:** backend 8669 passed, 1 failed (the named sonnet test). Frontend vitest 2115 / 2116; the
