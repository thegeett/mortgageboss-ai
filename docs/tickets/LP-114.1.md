# LP-114.1 — Findings show ALL their source documents (multi-document provenance, honest by construction)

- **Ticket:** LP-114.1
- **Status:** Completed
- **Date:** 2026-07-04
- **Scope:** Backend (finding source-set capture + expose) + frontend (finding card)

## The flaw LP-114 left

LP-114 stored a single `source_document_id`. But a cross-source finding is derived from **multiple**
documents — an employer appears on a pay stub AND a W-2; a discrepancy compares stated data against
one-or-more documents. The single-FK shape is incomplete, and it's why most findings nulled out:
LP-114's "resolve to a unique document or null" refused to pick one among several. **Showing ALL the
source documents completes the provenance AND dissolves the ambiguity** — show every document that
genuinely contains the value; no wrong pick. This is the finding analog of LP-109 (which showed all
matching documents for a need).

## The fix — a SET, derived by value-matching, honest by construction

- **Storage (Option A):** a new `findings.source_document_ids` JSON array (mirrors needs' `source_facts`,
  no join table). `source_document_id` stays as the primary/trigger (back-compat).
- **Capture:** `populate_finding_source_documents` runs at the end of a verification run (engine +
  cross-source) and on the backfill — uniform across all three generators, no per-generator wiring.
  It value-matches each finding's cited value(s) to every document that contains them.
- **Expose:** `FindingPublic.source_documents: [{id, filename}]` names the whole set (the file's
  document names loaded once — no N+1); the frontend `VerificationFinding` mirrors it.
- **Display:** the finding card lists **all** source documents ("Sources: doc1, doc2" — "Source:" for
  one) on the card and in the Details "Source" section, each clickable to open via LP-114's
  `?doc=<id>` nav. Graceful when the set is empty (keeps page/snippet; no broken "Source:").

## Honest by construction (the precision discipline)

Two guards keep the set honest — a document is included only if it's genuinely a source:
1. **Distinctive value.** The match keys on the finding's SPECIFIC cited value (its `document_value`;
   an amount / address / account-fragment in the snippet), NOT generic tokens — a lone common word is
   dropped.
2. **Category compatibility.** A document is eligible only if its category fits the finding's — an
   INCOME/employer finding matches only INCOME_EMPLOYMENT documents, **not** a savings statement that
   merely repeats the bank name. Cross-cutting finding categories (cross-source / documentation /
   regulatory) are unconstrained. This is what stops "Bank of America" (employer) from over-including
   the BofA savings statement — the exact over-inclusion single-value matching risked.

The category compatibility is a **grounded starter — validate-with-Priya**.

## LF-6T3N

Named findings jumped from a handful to **16/19**: the employer-mismatch findings now show their
pay-stub + W-2 sources *precisely* (no coincidental savings statements, thanks to the category guard);
the balance/license findings show their one document. The 3 unnamed have no distinctive locatable
value (graceful null).

## No migration on the primary; V2 unchanged

Only the additive `source_document_ids` JSON column (migration up+down). `source_document_id` is kept.
The document VIEWER, PAGE deep-linking, and TRANSACTION HIGHLIGHTING remain **V2** (no viewer, no bbox
data — see `phase3.md §2.7`).
