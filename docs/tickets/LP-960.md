# LP-960 — add-company: a second tenant on a deployed environment

- **Ticket:** LP-960 (the owner, 2026-10-05)
- **Source:** the owner wanted to create a second company, `vemamortgage`, on staging and found no way to.

## What was missing

Staging had one company (MortgageBoss) with two admins. Nothing could make a second one:

- **`bootstrap-admin`** creates a company, but refuses once any user exists (`bootstrap_admin.py`, guard (a)).
- **`add-user`** refuses a company slug that does not exist, by design: a typo'd slug silently creating a
  tenant is the failure it exists to prevent.
- **No API route** creates a company. Outside the model, only `bootstrap_admin.py` and the dev/visual-check
  seed scripts construct a `Company`. The search covered every local and remote branch and the full git
  history (`add-company` / `add_company`: no matches).
- **`query`** connects as `mbai_readonly`, which cannot write.

## The change

**`backend/app/scripts/add_company.py`** creates the company and its first ADMIN in one transaction, built
like `add_user`. It takes a bcrypt hash, never a password, reads its inputs only from the environment with no
defaults, and puts every guard before the first write. It refuses:

| Input | Refused when | Why |
|---|---|---|
| environment | not in `ADD_COMPANY_ALLOWED_ENVIRONMENTS` (default `staging`) | same allowlist as the other two |
| slug | not `[a-z0-9]+(-[a-z0-9]+)*`, or over 64 chars | permanent; the operator should see the slug they get, so it is refused, not normalized |
| slug | held by ANY company, soft-deleted included | the unique index covers deleted rows; reusing one would make old links resolve to the new tenant |
| name | held by a LIVE company, ignoring case and surrounding space | the same tenant twice under two slugs. A soft-deleted company's name is allowed, so a tenant can be re-onboarded |
| name | blank | |
| admin email | malformed, or held by any user in any company, ignoring case | the existing `add_user` check |
| hash | not a well-formed bcrypt hash | the existing check |

**Company and admin are created together.** A company with no user is a tenant nobody can log in to, and
finishing it would rely on a second `add-user` run someone could forget.

**`assert_email_unused` moved to `_provisioning.py`.** `add_user` had it inline. Both scripts now share it, and
its message is unchanged, so the `add_user` tests matching it still apply. `add_user`'s unknown-slug refusal now
names the `add-company` stage.

**`./scripts/deploy <env> add-company`** follows `add-user` exactly: provisioning-environment allowlist,
Cognito required, database up, interactive prompts, password hashed locally, the request built from the
environment into a 0600 file, and the migrate task definition run as a one-off task. The slug is also checked in
the shell, so a bad one is refused before the password prompt. At the end the stage prints the matching Cognito
`admin-create-user` command, as `bootstrap-admin` does.

Docs: `infra-deploy-staging.md` §8 and the one-off-script list, `commands.md` and `deployment-runbook.md`
(the stages that refuse while the environment is down).

## Before it can run on staging

**The script is run from the deployed image.** The one-off task uses the migrate task definition, so
`app.scripts.add_company` exists on staging only after an image built from this tree is deployed. Until then
the stage starts a task that fails with `No module named app.scripts.add_company`. The stage cannot detect
this itself.

## Tests

`backend/tests/test_add_company.py`, 43 cases: the happy path on a populated and an empty database; the new
admin logging in through `authenticate_user` with a mixed-case email; every refusal, each asserting that the
company and user counts are unchanged; `config_from_env` reading every variable and refusing each missing one;
and no secret in the success line or a refusal.

Provisioning suite (`test_add_company`, `test_add_user`, `test_bootstrap_admin`): **104 passed**.

**Mutation pass:** 12 mutations of `add_company.py`, one per guard or behaviour, and all 12 were caught:

- the slug check ignoring soft-deleted companies, or removed;
- the name check made case-sensitive, counting deleted companies, or removed;
- the email check removed, or moved after the company write;
- role set to PROCESSOR;
- the environment allowlist removed;
- the slug pattern removed;
- the name not trimmed;
- the blank-name check removed.

The file was restored from a copy afterwards.

**Not exercised:** the deploy stage itself. `scripts/deploy` has no dry-run mode, and running the stage creates
a real tenant. `bash -n` passes, `--help` lists the stage, an unknown stage still lists it among the valid ones,
the shell slug pattern was run against the same accept/refuse cases as the Python one, and the jq request builder,
run with dummy values, emits the `add_company` command and all seven variables. Shellcheck is not installed
locally.
