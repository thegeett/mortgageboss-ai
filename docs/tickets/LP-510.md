# LP-510 — Backfill the MISMO property project indicators

**Status:** done (implemented; not yet run against staging)
**Follows:** LP-509-B1

## The problem

LP-509-B1 taught the parser to capture `PropertyInProjectIndicator` and `PUDIndicator`, which are what
decide `property.type` when a MISMO export states none — and every export seen so far states none.

**Import is one-shot.** A loan file imported before that change has both columns NULL, and re-running
verification never re-parses the XML. So the fix deployed and nothing happened: on LF-WCHG,
`property.type` stayed absent and CO-1 / CO-3 / CO-4 / IH-7 kept reporting *"the property type has not
been determined"* — four findings asking a processor for something the file already contains.

Measured after the LP-509 deploy:

```
in_project | is_pud | property_type | attachment_type | construction_method | financed_unit_count
-----------+--------+---------------+-----------------+---------------------+--------------------
           |        |               | Detached        | SiteBuilt           | 1
```

The three columns the ORIGINAL import knew about are populated; the two it did not are NULL.

**How this got missed:** B1 was verified end-to-end locally by importing the MISMO *fresh*, which
silently creates the one condition staging cannot have. A fresh import is not a regression test for an
existing row.

## Where the data is

| Source | Has it? |
|---|---|
| `properties.in_project` / `is_pud` | No — NULL, that is the bug |
| `mismo_imports.catch_all` | **No** — checked against the real export; the property section's leaves are not swept there |
| `mismo_imports.raw_file_path` | **Yes** — every import saves the raw content to object storage (`import_service.py`) |

So the values are recoverable only by re-parsing the retained file.

## The fix

`app/scripts/backfill_mismo_property_indicators.py`, run as a one-off ECS task via the new
`./scripts/deploy <env> backfill-mismo` stage.

**A task, not a migration.** It does object-storage I/O per row — network, credentials, partial failure —
which does not belong inside a DDL transaction. It follows the `bootstrap-admin` / `add-user` / `query`
shape already in the script.

**Report-only by default.** It prints exactly what it would change and writes nothing until
`BACKFILL_APPLY=1`, so looking is never the same action as changing.

**Only ever fills a NULL.** A value already in the column wins over the re-parse, so a re-run repairs a
partial run and never reverts a human's correction. It does not touch `property_type` — deriving a type
from the indicators is the tag layer's job (`derived._property_type`), and writing the conclusion into
the column would bake today's rule into the data.

**One unreadable file does not stop the batch.** A lost object is reported and skipped; the exit code is
non-zero so the gap is visible.

## Expected effect

On LF-WCHG: `in_project=false, is_pud=false, units=1` → `property.type = sfr` → **CO-1, CO-3, CO-4 and
IH-7 all become `not_applicable`**, removing 4 from Needs attention.

Wider than one file: `property_type` is null across the board, so the condo lane currently abstains on
**every** existing loan file. A report-only run against the local database found 16 files to fill, four
of them PUDs.

## Acceptance criteria

- [x] Re-parses from `raw_file_path`; fills only NULLs; never overwrites
- [x] Report-only by default; writes only under `BACKFILL_APPLY=1`
- [x] One unreadable file is reported and skipped, batch continues, exit code non-zero
- [x] `./scripts/deploy <env> backfill-mismo` stage + `--help` entry
- [x] Tests cover all six outcomes (report-only, apply, no-overwrite, already-set, unreadable, no raw file)
- [ ] Run against staging and confirm the four condo findings clear

## The general lesson

**Capturing a new MISMO field implies a backfill for existing imports.** Import is one-shot and re-import
is deferred, so a parser change alone only affects files imported afterwards. That should be part of any
such change, not discovered after deploying.
