# LP-398 — The negative-case scenario for owner_matches_borrower: test the direction AS-6 exists to catch

## What this ticket is

LP-390-8a made `stmt.owner_matches_borrower` produce, scoring 5/5 (100%) — but **all 5 goldens were `yes`**: the
tag had only ever seen statements that DO belong to a borrower. AS-6 exists to catch the opposite — a statement
that does NOT belong (the dangerous FN direction: someone else's assets accepted as the borrower's), and that
direction had never been tested (why AS-6 ships ratify-only, LP-397). This builds it: a standalone fixture of 6
negative statements (each resembling a borrower in one specific way) + 2 positive controls, and a live probe of
all 8. **This is the exit condition from ratify → auto.**

  byte-unchanged.

  ambiguous cases unanchored.

  one miss investigated. No tag/rule/producer/prompt change; `ACTIVE_RULE_IDS` unchanged (24); full suite green.

## Phase 0 — the argument

- **D1 — the minimum scenario.** A borrower roster (MISMO borrowers with names) + one `bank_statement` carrying
  an `account_holder_name`. Nothing else. Every case is built to exactly that.
- **D2 — the roster reaches the group (the LP-379-B trap avoided).** `loan_borrower_roster` reads MISMO
  `borrower.{n}.first/middle/last_name`, so the fixture wires two borrowers WITH NAMES — verified: the roster is
  `["Jordan A Rivera", "Robert Chen"]`, non-empty. An empty roster would abstain every case and the probe would
  measure nothing.
- **D3 — which clause each scenario probes** (LP-390-8a's tolerance rules): N1 middle-name (a DIFFERENT
  initial), N2 nickname/variant (Roberta≠Robert), N3/N6 entity (trust/LLC), N4 the sanity check (unrelated), N5
  joint-account, P1 benign middle-drop (control), P2 nickname working (control).
- **D4 — doc-type scope.** `stmt_facts` runs only on `bank_statement`/`money_market` (the LP-397 D5 gap), so
  every scenario is a `bank_statement` and actually materializes. The investment-account gap is NOT fixed here.

### The clear-cut results — 5 of 6 pass; 1 miss (in the SAFE direction)

- **N3, N4, N6 → `no` ✅** — the tag CAN reject a genuine negative (a trust, an unrelated name, an LLC). **The
  dangerous FN direction is exercised for the first time, and the tag is not stuck saying `yes`.** N4 (the
  sanity check) passing means the tolerance is not catastrophically broken.
- **P1, P2 → `yes` ✅** — the controls hold; the tolerance correctly accepts a benign middle-drop and a nickname
  (no over-strictness regression).
- **N2 → `unknown` (expected `no`) — the one miss.** The model abstained ("could potentially be Robert Chen")
  rather than rejecting. **It is the SAFE direction** (it did NOT falsely match — no FN), but it shows the tag
  hedges on a Roberta/Robert-style variant. Honest reading: "Roberta vs Robert" is more ambiguous than the
  clear-cut label assumed (a candidate to reclassify as ambiguous in a future round) — reported, **not fixed
  here** (the prompt is out of scope).

### The ambiguous outputs — reported without judging (Priya's labels decide)

- **N1 (Jordan **M** vs Jordan **A**) → `yes`.** ⚠️ **The headline finding:** the tolerance **swallowed a
  DIFFERENT middle initial** — it treated "M" and "A" as the same person. This is exactly the
  dangerous-tolerance concern LP-397 flagged. Whether that is right (a benign variant) or wrong (M is a
  relative, a different person) is **Priya's call** — but if her view is that a different middle initial is a
  different person, **the tag currently fails that**, and the middle-name clause needs re-specifying (its own
  prompt ticket).
- **N5 (joint, non-borrower co-holder) → `yes`.** The "match if EITHER holder is a borrower" rule fired. Whether
  a non-borrower co-holder should instead be FLAGGED is an open underwriting question — **Priya's call.**
