## How the reading is made

1. Her confirmed answer for (lender, code) wins, and that condition is not sent to the model.
2. A library type decides the items; the model fills specifics (amounts, bank, month, names) and may
   widen a performer the text names (0132: "signed by Borrower(s) and Loan Officer" → Borrower + LO).
3. Only an untyped condition takes its items from the model.
4. Code then: drops any amount not written in the text; reads the last four itself; computes 7086's
   shortfall and writes that summary; compares 6178's two dates; fills "Source of the {amount}" from the
   lender's amount; maps the underwriter's note.
5. Status: `ready` only for a model reading at or above the bar; `needs_confirmation` below it, and for
   every reading made without the model (the library fallback), so "nothing is drafted" holds there too.
6. A `lender_to_clear` heading, or a library type whose default is "lender doing it", marks the reading
   `lender_doing_it` (1760 and 0571 on the page-break sheet).

## Decisions

1. **The reading's specifics may come from the model; figures may not.** Months ("Jul 2026") and bank
   names are specifics the plan lets the AI fill; any dollar amount must be in the lender's text, and
   the last four is always code's.
2. **A library-only reading is `needs_confirmation`.** The plan says the fallback's readings are "marked
   for her to confirm"; treating them as ready would draft emails from a reading nobody checked.
3. **Tests never queue the reading.** An autouse fixture replaces `read_condition_round.delay`; before
   it, import tests pushed tasks into whatever Redis the machine runs, where a dev worker would take them.
4. **The detail sheet's header got `pr-8`.** At S3-01's width the sheet's × sat on top of ↓ (a Stage 2
   defect the S3-01 check found); the Must-match line names ↑ ↓ and ×.

## Review (of `65cb0617`)

**No findings.** The safety properties this ticket rests on were made to fail before being believed,
the screens were re-shot and walked against the README's own lists rather than this ticket's, and every
count matches.

### The property that matters most: the model never supplies a figure

`_checked_specifics` keeps an amount only when `facts.money_is_in(amount, text)`. The fixture's planted
`$27,148.22` is the figure the lender never wrote — and it is also the *correct* answer, which is what
makes it worth testing: had code trusted it, the screen would look identical. **Mutation:** removing
the filter so the model's amounts are trusted fails `test_round_one_reads_as_the_plan_says`. The guard
is pinned, not merely present. The last four is code's in every case, never the model's digits.

### Principle 7, read against what actually leaves the process

The payload is `{file: …, conditions: [{ref, code, text, notes, type}]}`, and the `file` summary is
borrower FIRST names (max 4), the lender's name, `must_not_close_before`, `earnest_money` and
`loan_purpose`. Principle 7 (plan line 165) explicitly allows "a short file summary (borrowers,
accounts by bank and last four, employers, earnest money, closing date, parties)", and the two money
and date facts are read from `round_.header`'s `loan_facts` — **the lender's own letter, not the app's
snapshot**. This is narrower than the principle permits: no accounts, no employers, no full names.

### The migration

Raw `op.execute` throughout — the one apparent `op.create_check_constraint` is a comment warning
against it (LP-932's lesson). `reading` JSONB; `reading_status` VARCHAR(32) NOT NULL DEFAULT `unread`
+ CHECK; `reading_source` VARCHAR(32) + CHECK; `reading_confidence` NUMERIC(3,2). The event-kind swap
is `_EVENT_KIND_BEFORE` (19) + `condition_read` + `condition_reading_confirmed` = **21**, dropped and
re-added under LP-932's single name. The migration-cases guard needs no edit and is not vacuous:
`_CASES` already carries `("ck_condition_events_conditioneventkind", ConditionEventKind)`, so the new
swap is read automatically and a missed value fails there.

flipped date comparison: the fixture's two dates are EQUAL (the policy starts 09/30/2026 and the letter

genuinely pinned by `test_condition_facts.py`, which uses non-equal dates. Worth knowing because it is
the same shape as the stranded-round follow-up: an assertion sitting exactly on a boundary answers the
boundary question by accident.
