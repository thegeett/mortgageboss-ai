# LP-944 — Flaky tests

- **Ticket:** LP-944 · Phase 4.5 Stage 3 follow-ups, batch 2
- **Source:** the product owner, 2026-09-30: "Find the shared cause of the three tests that fail now and
  then, fix it, and run the full suite three times to show it. The inbox-token test gets the fix already
  described in the progress file."
- **The three:**
  - `tests/services/test_loan_file_ids.py::test_inbox_token_is_independent_of_display_id`;
  - `tests/conditions/test_condition_evidence.py::test_the_reask_goes_into_a_new_borrower_email`;
  - `tests/services/test_timeline_lp812.py::test_the_timeline_never_carries_a_body`.

## The shared cause

**Each test asserted on something the test does not control.** There are two mechanisms of that one
cause, and each is now measured, not assumed.

**1. A short string that must not appear in text that also carries random values** (the inbox token and
the timeline).
- The inbox-token test asserted that a 4-character random display code never appeared in a 22-character
  random token. Chance alone does that about once in a thousand runs (the progress file's measurement:
  2 in 2000 simulated). `RAKSTDzq1DNBKVL5PyKWmQ` contains `AKST`.
- The timeline test asserted `"4821" not in repr(entry)`. The repr carries the entry's random UUID and
  two microsecond timestamps. **Measured: 2 failures in 3,000 repetitions** of the test's own scenario,
  each from "4821" in a UUID or a timestamp. That is the ~0.08% a simulation predicts.
- The reviewer saw this test fail once in about eight full runs, which is more often than 0.08% suggests.
  The mechanism is proved, and that frequency is put down to chance rather than claimed as explained.

**2. The row order of a query with no ORDER BY** (the re-ask test).
- The test's `_drafts` helper keys drafts by recipient, keeping whichever row comes last. After the
  re-ask a recipient has two drafts: the round's sent one and the new one.
- **Measured under forced join plans:** with the default, nested-loop and hash plans the new draft came
  last, and under a **merge join the SENT draft came last**, so the test failed.
- Postgres picks the plan from table statistics. Over a full run those change: rolled-back rows count as
  dead tuples, and autovacuum and autoanalyze catch up mid-run. So the test failed only in full runs and
  never alone, which fits the reviewer's "leaks per run, not per test".
- 150 repetitions inside one transaction never flipped: there the statistics do not move.

## The fixes

- **Inbox token:** independence is proved by construction, as the progress file described. The generator
  takes no arguments (nothing to derive from), and 200 tokens for one display id are all different. The
  whole 7-character display id is still asserted absent; at that length chance cannot supply it.
- **Timeline** (the service test and the API test, which had the same assertion against the whole JSON
  response): they assert the phrase "ending 4821", which is the body's and cannot be spelled by a UUID or
  a timestamp. "Dear Jane" stays as it was.
- **Re-ask:** `_drafts` orders by (unsent last, then creation time), so when a recipient has two drafts
  the unsent, newest one wins, deterministically. Verified: all four forced plans now pick the new draft.

**The sweep for the same shapes:**
- Every `assert "<digits>" not in …` in the suite was listed. Besides the two timeline tests, the others
  test list or set MEMBERSHIP ("9001" not in the codes), which is exact, not a substring.
- The three extraction tests assert against logs of a mocked model with fixed numbers, where there is no
  random value for the digits to collide with.
- `_drafts` is the one test helper that builds a recipient dict from an unordered query.

## Review (of `adf963aa`)

**The sweep holds for its class — I widened it to every spelling and checked each hit for a random
haystack. One finding: the *other* mechanism, row order without `ORDER BY`, has a live member in app code,
in this batch's own area — and this repo already wrote down the doctrine for it after the same bug bit
once before. Two smaller notes, and one number that still does not fit, which you flagged yourself.**

### The sweep — checked, and complete for its class

Your grep was `assert "<digits>" not in`. I widened it to the spellings that would have hidden a member:
`assertNotIn(`, `assert not any(... in ...)`, single-quoted literals, and short **alphabetic** literals
(the class is "a short string asserted absent", not "digits"). Then I judged each hit on the ingredient
that actually matters — whether the haystack carries **random** values:

| candidate | verdict |
|---|---|
| `"9999.99" not in blob`, `"4250.00" not in str(detail)`, `"1104000" not in blob` | 7 characters including a decimal point; needs that exact run in a UUID or timestamp. Not a practical member |
| `"Mahesh" / "Chhotala" not in blob`, `"broker" not in detail.lower()` | alphabetic words, no random source. Not members |
| `";" not in rendered`, `"$2" not in line` | haystacks are deterministic (migration SQL, a fixed log line) |
| **`"ssn" not in body`** (several leak tests) | **looked like the nearest member and is not**: `body` is `resp.json()[0]`, a **dict**, so this is key membership, not a substring search. No collision is possible |

So: no missed member. The three you fixed are the three that existed.

**One thing the mirror of your sweep found.** I also looked for the opposite shape — a short literal asserted
**present**, which can pass by accident:
`tests/verification/tag_materialization/test_insurance_wiring.py:63` asserts
`"1200" in reason and "12" in reason`. The second conjunct **cannot fail while the first holds**, because
"1200" contains "12". It is not flaky; it is vacuous — it reads as "the reason names the divisor" and
asserts nothing. Adjacent to your class rather than in it, and a one-line fix (assert the division, e.g.
`"÷ 12"`, not the digits).

### Finding — the ordering mechanism has a live member in app code

You scoped the second sweep to test helpers ("`_drafts` is the only helper building a recipient dict from
an unordered query"), which is true. But the mechanism is not test-specific, and in app code it is a
product bug rather than a flaky test. I censused `app/` for the three shapes that let row order decide an
answer — `.first()`, `[0]`/`[-1]` on a result, and `{row.key: row for row in …}` where the **last row
wins** — and found 42 order-sensitive sites, 28 without an `ORDER BY` in scope. Nearly all key on a
primary key, so last-wins is moot. One is not:

**`app/services/condition_enrich.py:185`** — `by_text = {c.text_fingerprint: c for c in existing}`, built
from a query with no `ORDER BY`. `text_fingerprint` is a **sha256 of the verbatim text** with only a
non-unique index (`ix_conditions_file_fingerprint` on `(loan_file_id, text_fingerprint)`), so two
conditions with identical text on one file share a key — and which one enrichment matches a sheet row to
is then the planner's choice, exactly as the draft dict was.

**And this repo has already written the answer.** `app/services/email_send.py:482`, after the same bug bit
with mailboxes:

> WHICH mailbox is "the" mailbox is a product answer and is escalated. That `.first()` had no ordering at
> all is not: two connected mailboxes made the choice undefined, so the same file could send as a
> different identity on two requests with nothing changed. Ordering does not decide the product question;
> it makes the answer reproducible while somebody decides.

That is the doctrine, applied once there and a second time in this ticket. `condition_enrich` is the third
site and has not had it. The fix is the same shape as yours: order the query, so the answer is
reproducible while somebody decides whether identical-text conditions should be matched at all.

### Verified

- **The fix's mechanism, against the database rather than by assumption.** The `_drafts` ordering relies on
  `False` sorting before `True`; Postgres confirms `select x from (values (true),(false)) t(x) order by x`
  returns `f, t`. So `order_by(status == DRAFT, created_at)` really does leave the newest **unsent** draft
  last, which is what the dict then keeps.
- **Counts:** 8929 passed, 1 failed (the sonnet test), 8 skipped, 1 xfailed — matching all three of your
  runs.

### The number that still does not fit — and you were right to say so

Your measurement gives ~0.067% per assertion. My own observation was the timeline test failing once in
about eight full runs; under your model the chance of seeing **any** failure in eight runs is about
**0.5%**. So my single observation is a 1-in-200 coincidence under the explanation, which is possible and
is not evidence of a second cause — but it is the kind of residual that deserves naming rather than
rounding away, and **you named it yourself** ("the ticket calls it chance and does not claim it
explained"). That sentence is why this ticket reads as honest work.

If anyone wants to close the gap rather than accept it, there is a cheap test: your 3,000 repetitions
rebuild the same scenario, so the repr is the same size each time. A full run might not be — if leftover
rows make the entry (or the API test's whole JSON response) carry **more** random material than it does in
isolation, `p` rises with it, and that would fit both your mechanism and my observation without needing a
third. Measuring the repr's length in both contexts settles it in one run.

### On the epistemics, which are the best part of this ticket

*"Three clean runs cannot prove a 0.1% failure gone; the evidence is the mechanism measured before and
after."* That is the correct standard and an uncommon one to hold yourself to — three green runs are what
most reports would have led with. The evidence here is the 3,000-repetition measurement, the forced-plan
probe, and the two mechanisms named; the runs are a sanity check on top, and the ticket says so.
