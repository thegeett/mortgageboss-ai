## What was reported

> *"Still requesting document does not work. Currently I have 3 rows in communication, two of them
> marked as sent, one is old draft. When I request any document new Draft is not getting created."*

## It was created. The screen kept its cached copy.

**Nothing is wrong on the server.** `add_needs_to_draft` creates the new draft, as LP-832 built it.

The Communication page reads `["timeline", fileId, filter]`. Both request mutations invalidated
`outboundDraftQueryKey` — **the key of `OutboundDraftPanel`, which LP-831 took off that page and
which nothing renders any more.** So a request refreshed a query with no reader and left the list the
processor was looking at untouched. The header badge (LP-837) reads the same timeline key, so it did
not move either.

Three rows before, three rows after, and a draft sitting in the database. Indistinguishable from a
button that does nothing.

## This is mine, and it is the lesson I keep writing down

LP-809's review added that invalidation **with the right reasoning** — *"the draft the communication
page reads is stale the moment this resolves"*. Then LP-831 changed **what that page reads** and did
not move the line. Check the reader, not just the writer — and then the reader moved.

**The test that existed to prevent this kept passing.** `verification-draft-invalidation.test.ts` was
written in LP-809 and asserts `outboundDraftQueryKey` is invalidated. That remained true and stopped
meaning anything the moment the page read something else: it pinned a **key** rather than *"the list
a processor is looking at refreshes"*. A guard naming an implementation survives the implementation
moving out from under it.

That file already carried one version of this lesson — its own docstring records that the first
version compared string literals and used `["needs", identifier]`, a key no query was ever registered
under, as its positive control. Same failure, one level up.

## The fix

`invalidateDraftViews(queryClient, fileId)` — one function listing what a change to a file's drafts
is visible in: the timeline (mailbox **and** header badge, every filter), the needs list, the activity
log. Every mutation that touches a draft calls it: both request routes, the send, the compose, the
link attach.

`needsQueryKey` is imported rather than spelled out, because LP-809's review found `["needs", id]`
matching nothing — the real key is `["loan-file-needs", id]`, and prefix matching is element by
element. `["timeline", fileId]` **does** match every filter's query, which is what lets one line
cover the pills.

## Deleted, because nothing rendered it

`OutboundDraftPanel` and its test, and `useOutboundDraft` / `outboundDraftQueryKey` with them.
LP-831 replaced the panel with the modal and left the component behind; its only remaining effect was
to make a stale invalidation look like a live one.

## Mutation

Removing the timeline line from the helper fails
`test_invalidates_the_needs_list_and_the_MAILBOX_and_nothing_else` — **which is the reported bug
exactly**: needs list refreshes, mailbox does not.

## For the reviewer

The negative control is the part worth checking: the test registers `["documents", fileId]` and
asserts it is **not** invalidated, so a blanket `invalidateQueries()` would fail rather than pass
everything. And the timeline query is registered **with a filter** so the prefix match is exercised
rather than assumed — that assumption is what made LP-809's original literal wrong.

## Review — REVIEWED

One finding, which is the build's own question 3 answered by measuring it: **two other modules kept
their own list, and both still invalidated the key this ticket deleted the query for.**

`invalidateDraftViews` was introduced to be the one place, and `outboundDraftQueryKey` was deleted
with `useOutboundDraft`. But the key was spelled as a **string literal** in two modules this commit
did not touch:

| module | invalidated | result |
|---|---|---|
| `lib/api/messages.ts` | `["timeline", …]` and the deleted draft key | reply / important / read |
| `lib/api/party-requests.ts` | `partyRequestsQueryKey`, `["timeline", …]`, the deleted draft key | Build request |

So the named constant went and two hand-spelled copies stayed — an invalidation of a query with no
reader, which is exactly what this ticket is about, surviving in the commit that fixes it. Both now
call the helper, keeping their own extra keys.

**My first hypothesis was wrong and the measurement said so.** I expected `useBuildPartyDraft` to be
the reported bug still live: `build_party_draft` creates a `Communication`, and `build_timeline` has
no template filter, so a party draft IS a row in the mailbox. But its hand-rolled list happens to
include `["timeline", fileId]`, so the mailbox does refresh there — correct today, by coincidence
rather than by construction, which is the thing the helper exists to remove.

### The guard is derivable after all (ask 2 and 3 together)

The build could not find a derivation for *"everything a draft is visible in"* and is right that it is
not computable. But the rule that matters is, and it is one level up: **refreshing the mailbox means
going through the one place that knows what else to refresh.** Anything invalidating a timeline key
directly has decided for itself what a draft change is visible in, which is the decision this module
owns. Three assertions, all over the source rather than over a list of callers:

1. No module under `lib/api` invalidates a timeline key except `draft-views.ts` (and the key factory).
2. No module invalidates the deleted draft key at all.
3. **`draft-views.ts` still names the timeline** — the positive half, because the first two are
   satisfied by a codebase that never mentions it, which is the reported bug with the line removed
   rather than moved.

A sixth mutation that hand-rolls its own list now fails (1) rather than shipping. Verified in three
directions: restoring a hand-rolled timeline key fails (1), restoring the dead key fails (2), and
removing the timeline line from the helper fails (3) and the build's own behavioural test.

**My own comment tripped the guard first**, exactly as the build's did in LP-838: prose quoting the
literal reported the file it had just fixed. Reworded to name the key rather than quote it, which is
the lesson from that review applied rather than re-learned.
