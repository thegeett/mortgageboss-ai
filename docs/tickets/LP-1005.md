# LP-1005 — Domain setup command

## What and why

Step 3 gives each customer their own mail subdomain (for example `mb-mail.abcmortgage.com`), so
their files get addresses like `lf-xxxx@mb-mail.abcmortgage.com` and email goes out from their own
domain. Per the 10-31 decision, we set this up with **a command, run during the customer's onboarding
call**. There is no settings screen.

```
uv run python -m app.scripts.set_up_mail_domain <company id or exact name> <subdomain>
```

It works in three stages. Each run gets as far as it can, then says where it is and what comes next:

1. **pending_ns.** The command creates a Route 53 hosted zone for the subdomain, saves it, and prints
   the one NS record (the name plus our four nameservers) for the customer to add at their DNS
   provider.
2. **verifying.** Once public DNS shows the subdomain pointing at our nameservers, the command:
   - creates the SES identity (Easy DKIM);
   - sets MAIL FROM to `bounce.<subdomain>`;
   - writes every record into the zone.

   AWS then checks DKIM.
3. **active.** Once SES says the domain is verified, the row becomes `active` and sending is switched
   on (decision 10-31: an active domain turns the company on). Files then get addresses through the
   existing `file_address`.

The stages wait on things outside our control (the customer's DNS change, AWS's check), so one run
rarely gets all the way. Run it again later, or let the hourly check (LP-1006) do it: both call the
same function, `advance_mail_domain`.

## The records written

They're written in one Route 53 call, all `UPSERT`, TTL 300 seconds. "Region" is the app's AWS
region (`settings.s3_region`, `us-east-1` in staging).

| Name | Type | Value | What it's for |
|---|---|---|---|
| `<token1>._domainkey.<subdomain>` | CNAME | `<token1>.dkim.amazonses.com` | DKIM signing (Easy DKIM), 1 of 3 |
| `<token2>._domainkey.<subdomain>` | CNAME | `<token2>.dkim.amazonses.com` | DKIM, 2 of 3 |
| `<token3>._domainkey.<subdomain>` | CNAME | `<token3>.dkim.amazonses.com` | DKIM, 3 of 3 |
| `<subdomain>` | MX | `10 inbound-smtp.<region>.amazonaws.com` | Receiving: replies reach SES |
| `bounce.<subdomain>` | MX | `10 feedback-smtp.<region>.amazonses.com` | MAIL FROM: bounces come back to SES |
| `bounce.<subdomain>` | TXT | `"v=spf1 include:amazonses.com ~all"` | SPF for the MAIL FROM domain |
| `_dmarc.<subdomain>` | TXT | `"v=DMARC1; p=reject"` | Reject forged email; no `rua` (no reports), decision 10-31 |

**That's 7 records, not 8.** The brief says "all 8 records" but lists these 7 (3 + 1 + 1 + 1 + 1),
and the tests check exactly these 7. If an eighth was intended (for example SPF on the subdomain
itself), it's a one-line addition. I didn't add one: SPF is checked against the MAIL FROM domain
(`bounce.`), and DMARC passes on DKIM.

The customer adds just one record at their own DNS: **NS** for the subdomain, pointing at the four
nameservers the command prints.

## Safe to re-run

- **The zone is created once.**
  - Each zone request carries a fixed `CallerReference`, `mb-<company id>-<subdomain>` (hashed if it would be longer than Route 53's 128 characters).
  - If the same request comes again, Route 53 answers `HostedZoneAlreadyExists`. The command then finds that zone, matching both the name and the `CallerReference`, and returns its id and nameservers. It never makes a second zone, which would have different nameservers from the ones the customer was given.
- **The identity is created once.** If SES says the identity already exists, the command reads its three DKIM tokens instead.
- **Records are UPSERTs.** Writing them again just writes the same values.
- **Each stage commits.** A crash between stages resumes at the next stage on the next run. The zone id and nameservers are saved before anything else is attempted.
- **Hand-linked domains are never touched.** A row with no zone was linked by hand (LP-991, like MortgageBoss on `mail.staging.mortgageboss.ai`, whose DNS and identity Terraform owns). `advance_mail_domain` returns it unchanged, whatever its status. It also never switches sending on for a domain that is already active, so the switch keeps working as the emergency off.

## What changed

- **Migration `5c8e1a7d3b92`** (hand-written, with downgrade):
  - The status CHECK gains `pending_ns`, `verifying` and `problem` (`problem` is used from LP-1006); `active` and `inactive` stay.
  - Two new nullable columns: `zone_id` (text) and `nameservers` (JSONB list).
  - Existing rows are untouched.
  - The readonly view exposes both new columns: they're DNS settings, not personal data.
  - Downgrade turns rows still mid-setup into `inactive` (no address) before restoring the old CHECK.
  - Round-tripped on the dev database: up, down, up.
- **Model** (`app/models/company_mail_domain.py`): the three new states, `zone_id` and `nameservers`.
- **Provider** (`app/services/domain_provider.py`): one small interface with two versions, chosen by the new `DOMAIN_PROVIDER` setting (`fake` by default; `.env.example` documents it).
  - `Route53DomainProvider`: Route 53 and SES v2. boto3 makes one attempt per call with short timeouts, like LP-993. An AWS error becomes `DomainSetupError` with AWS's code, and only the code and the domain are logged. It is `retryable` when AWS was busy or unreachable (throttling, a 5xx, a timeout or a dropped connection), and not when AWS refused (no permission, a bad name, missing credentials).
  - `FakeDomainProvider`: every stage succeeds at once. **It refuses to run outside `ENVIRONMENT=development`**, so a staging run without `DOMAIN_PROVIDER=route53` stops, before the database is opened, instead of marking a domain active that AWS has never heard of. It says so: `Refused: DOMAIN_PROVIDER is 'fake', which only runs in development (this is staging). Set DOMAIN_PROVIDER=route53.` Staging tasks run with `ENVIRONMENT=staging`.
- **Function** (`app/services/mail_domain.py`):
  - `advance_mail_domain(db, row, provider)` moves a domain one stage on.
  - `caller_reference(company_id, domain)` builds the zone request key.
  - LP-1006's hourly job will call `advance_mail_domain`.
- **Command** (`app/scripts/set_up_mail_domain.py`):
  - normalises the subdomain;
  - refuses anything equal to or under `mortgageboss.ai`, a subdomain another company has, and a company that already has a different domain;
  - refuses a new subdomain with fewer than 3 parts or without the `mb-mail.` prefix, because the NS record it prints moves that name's whole DNS to us. `--custom-subdomain` allows a prefix the customer chose;
  - `--replace` corrects a mistyped domain while it is at `pending_ns`, and prints the old zone id to delete by hand. Past that, changing a domain is manual;
  - creates the row (`pending_ns`, sending off) if there is none, and advances up to 3 times.
  - Exit codes: 0 done (at whatever stage), 1 refused (including the fake outside development), 2 AWS stopped it. On 2 it says either "Run the command again to resume." (retryable) or "AWS refused it, so running again fails the same way; this needs a fix first."
- **The LP-991 hand-link** (`set_company_mail_domain`) now refuses a row that this setup owns: one with a zone, or in `pending_ns` or `verifying`. It says "<domain> is managed by set_up_mail_domain; this command can't change it." It still links and switches off domains we manage ourselves (`mail.staging.mortgageboss.ai`, `mb-mail.localhost`).
- **Dependency:** `dnspython>=2.8` (it was already installed through another package; now it's declared).

## Staging command for LP-1007

This needs an image with this change deployed, and migration `5c8e1a7d3b92` applied
(`./scripts/deploy staging deploy`). Staging has no `DOMAIN_PROVIDER` in its task env until LP-1007
adds it, so the command below sets `DOMAIN_PROVIDER=route53` on the one-off task itself. Without it,
the fake provider refuses (staging is not `development`).

The task runs on the api role, which LP-1004 allows to create zones and identities, and is denied
any change to `staging.mortgageboss.ai` and `mail.staging.mortgageboss.ai`. Run `aws sso login
--sso-session mbai` first.

```bash
export AWS_PROFILE=mbai-staging-admin
COMPANY_ID=<company id>
SUBDOMAIN=<e.g. mb-mail.customer.com>
cd infra/envs/staging
CLUSTER=$(terraform output -raw ecs_cluster_name)
TASKDEF=$(terraform output -json ecs_task_definition_arns | jq -r .migrate)
API_SVC=$(terraform output -json ecs_service_names | jq -r .api)
cd -
CONTAINER=$(aws ecs describe-task-definition --task-definition "$TASKDEF" \
  --query 'taskDefinition.containerDefinitions[0].name' --output text)
read -r SUBNETS SGS < <(aws ecs describe-services --cluster "$CLUSTER" --services "$API_SVC" \
  --query 'services[0].networkConfiguration.awsvpcConfiguration.[join(`,`,subnets),join(`,`,securityGroups)]' \
  --output text)

aws ecs run-task --cluster "$CLUSTER" --task-definition "$TASKDEF" --launch-type FARGATE \
  --network-configuration "awsvpcConfiguration={subnets=[$SUBNETS],securityGroups=[$SGS],assignPublicIp=DISABLED}" \
  --overrides "$(jq -nc --arg c "$CONTAINER" --arg id "$COMPANY_ID" --arg sub "$SUBDOMAIN" \
    '{containerOverrides:[{name:$c,
      environment:[{name:"DOMAIN_PROVIDER",value:"route53"}],
      command:["uv","run","python","-m","app.scripts.set_up_mail_domain",$id,$sub]}]}')"
```

The output lands in log group `/ecs/mbai-staging/api`, stream `migrate/<container>/<task id>` (as in
LP-998). Then confirm, read-only:

```bash
./scripts/deploy staging query -c "select company_id, domain, status, zone_id, nameservers, sending_enabled from readonly.company_mail_domains"
```

Run the same task again after the customer adds the NS record, and again once AWS has verified, or
leave it to the hourly check once LP-1006 ships.

**Receiving needs no extra step.** The SES receipt rule has no recipient list: it takes mail for every
verified identity whose MX points at SES (`infra/modules/inbound_mail/main.tf`, LP-981). So once a
customer subdomain is verified, replies to it land in `inbound/` like staging's. Routing them to the
right file is step 4.

## Doc changes (for `docs/email-communication/loan-email.md`, not edited here)

- §15b LP-1005: done. The command is `set_up_mail_domain <company> <subdomain>`; the stages are
  pending_ns → verifying → active; the advancing function is `advance_mail_domain`.
- Record the 7 records and their values (the table above), with DMARC `p=reject` and no `rua`.
- Record "safe to re-run": `CallerReference` `mb-<company id>-<subdomain>`, an existing identity's
  tokens reused, UPSERT, a commit per stage.
- `DOMAIN_PROVIDER=fake|route53`. The fake refuses outside development, and says which setting to change. Staging needs `route53` in
  its task env (LP-1007); until then, the one-off command sets it.
- Hand-linked rows (no zone) are never touched by setup or the hourly check, and the hand-link command (`set_company_mail_domain`) refuses rows that setup owns. The hand-link is now only for domains we manage ourselves.
- A setup error says whether running again can help (AWS busy) or a fix is needed first (AWS refused).
- The command refuses a root domain: a new subdomain needs `mb-mail.`, or `--custom-subdomain` for a prefix the customer chose. `--replace` corrects a typo at `pending_ns`.
- **Gap to plan:** nothing can change a customer's domain past `pending_ns`, or take one fully out of use. `set_email_sending` stops sending, but files keep their addresses. LP-1006 doesn't cover this, so it needs a place in the plan, probably with offboarding. The sending switch
  stays an emergency off: only the move to active turns it on.
- Receiving: a verified customer subdomain is received by the existing receipt rule (no recipient
  list, LP-981); no change is needed per customer.
