# LP-586 — snapshot-based AI cross-source findings, and their tab

## Why a new pass rather than fixing the old one

There is already a cross-source AI layer — LP-78, with caching (LP-78.1) and stable identity
(LP-81). It is the **"Old findings"** tab. Its context comes from the **live database**:

```python
"stated": {"borrowers": await _stated_borrowers(db, …), …},
"verified_documents": await _verified_documents(db, …),
```

Reassembled from mutable tables on every run. Stabilising that required hashing the assembled
context **and `engine_fingerprint()`** — every version-controlled file under `app/verification/`.

**So its drifting counts were never a bug.** Six commits touching the engine on 2026-08-19, six
correct invalidations. That binding exists because serving findings from a retired engine version
once "cost a human an afternoon".

This pass reads the **snapshot**: one frozen, already-persisted artifact, identical byte-for-byte
across runs until the file really changes. That is what makes stability tractable, and it is why the
answer was a second pass rather than a repair.

## The stability contract

| | |
|---|---|
| unchanged snapshot | the model is **not asked**; stored findings returned as-is |
| changed snapshot | asked, then **reconciled** against what is stored |
| either way | the processor's disposition **survives** |

All three are load-bearing. A pass with only the first would look stable on an idle file and still
lose a dismissal the moment anything moved — which teaches a processor that dismissing is pointless,
and is worse than a count that drifts.

**The fingerprint excludes `run_id` and `created_at`, and that is the whole trick.** Both are fresh
every run *without the file differing*, so hashing the snapshot as-is would never hit the cache and
the feature would look implemented while being inert.

**It does not hash the engine**, unlike the older pass. Engine changes that matter arrive *through*
the snapshot — the tags and calculations it reads are the engine's own output. A recipe change that
moves a tag misses the cache; one that moves nothing a snapshot records is correctly not a reason to
re-ask about an unchanged file.

## Identity is content, not wording

`finding_key` hashes the **kind and the sources**, never the title or detail. An LLM rewords the same
observation between calls even at temperature 0; hashing the sentence would mint a new finding for a
reworded one and evaporate the disposition attached to the old key.

## The lifecycle

```
open ──(no longer observed)──> resolved ──(next change)──> gone
  ^                               │
  └───────(observed again)────────┘
```

Deleting outright is honest about the current file and tells a processor nothing: they upload the
appraisal, the finding vanishes, and that is indistinguishable from a bug. `resolved` carries the
current fingerprint, so it survives exactly as long as the snapshot that resolved it.

**A resolved finding that comes back reopens.** `resolved` is the *system's* label, not the
processor's — leaving it on a live finding would tell someone it was fixed while it sits in front of
them. A test fails when that reopen is removed.

`signed_off` and `not_an_issue` are the **processor's** and are retained indefinitely: their action
is a record, and deleting it would erase their work the first time the file moved (ADR-061).

## No apply, deliberately

No rule spec, no calibrated threshold, no guideline citation — so nothing here may write to the loan.
Sign off, dismiss, reopen. A test asserts no Apply button exists, because a regression that added one
would be a real one.

`resolved` is also excluded from the disposition endpoint's accepted values: it is the system's, and
letting a client claim it would make the tab lie about *why* something cleared.

## What it found on a real file

Run by hand against LF-WCHG's snapshot before building, to check the pass was worth having:

- the **property tax bill's assessed value (551,923)** beside a stated valuation of **578,000** with
  no appraisal in the file — LTV 78.20% on the stated figure, **81.9%** on the assessed one, which
  crosses the MI line
- the **tax bill naming two owners** beside an application with **one borrower** — while ID-7, the
  rule that asks about title vesting, was abstaining for want of a document one folder away
- the **"new" loan's terms identical to the existing mortgage's** to the cent
- three mortgage balances across dated documents that are **consistent with amortization** — a
  non-finding, and getting that right matters as much as the findings

## Two things the tests caught

- My own test helper minted a fresh `loan_file_id` per call, so it passed its own bug rather than
  exercising the per-run exclusion.
- The run wiring called the real AI client instead of the documented `Reasoners` seam, degrading
  every keyless test with an `AuthenticationError`.
