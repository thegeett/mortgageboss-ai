# LP-573 — DT-8: a refinanced lien still counted in the DTI

**Status:** live · **Rules:** 77 → 78

## Why

Debt-to-income is forward-looking — it measures what the borrower owes **after** this loan funds. On
a refinance the mortgage being replaced is paid off at closing, so counting its monthly payment
alongside the new housing payment charges the same property twice.

LF-WCHG, a rate/term refinance: income 13,166.67, new PITI 4,418.785, liabilities 3,186.00 (a
MortgageLoan held by the servicer named on the file's own mortgage statement) + 49 + 35 + 25. The
engine reported a back-end DTI of **58.59%**. Worked by hand with the resident domain expert, the
correct figure is **34.39%** — the difference between failing most conventional overlays and passing
comfortably.

LP-568 built the exclusion mechanism and LP-571 gave a processor a way to set it. Both are levers:
they fix files where somebody notices. DT-8 is the detector.

## The design decision, stated because it changes what the rule can be trusted to do

**The rule ASKS; it does not conclude.** It never proves which property secures a given mortgage.

Proving it was the alternative: match the liability to the subject property by address, or
corroborate through a 1098's tax figure — on LF-WCHG the DTI's `housing.taxes` of 440.215/month
annualises to 5,282.58 and the 1098 reads `Property Taxes 5,282.58`, which is conclusive *there* and
silent on any file without a 1098. That matcher would be a new source of error in the permissive
direction, and the verdict is `needs_review` either way, so it buys precision the workflow does not
need.

The asymmetry is the whole argument. A false negative (the refinanced lien stays in) **overstates**
the DTI — visible, and it fails a file that should pass. A false positive costs a processor one
glance, because the rule never fires and never excludes anything on its own. The dangerous direction
is the one an automatic exclusion would create: dropping a debt that is actually retained
**understates** the DTI and can pass a loan that should fail.

**What that costs, named rather than hidden:** on a refinance where the borrower owns mortgaged
rental property, DT-8 asks once per stated mortgage and the processor dismisses the retained ones.

## Shape

- **Subject:** `per_liability`, stated liabilities only — `liab.stated_is_mortgage` declines on a
  credit-report tradeline, whose bureau codes would need the open-vocabulary classification ADR-353
  defers. That is also the row the exclusion is written back to.
- **Scope is BOTH conditions** — refinance *and* mortgage. `not_applicable` means the rule is
  irrelevant to the subject's nature (§8), and it is irrelevant to a credit card for the same reason
  it is irrelevant to a purchase. The engine reserves `not_applicable` for the applicability
  predicate — an outcome cannot produce it — which is what forced the question and got it right.
- **It can never `fire`**, pinned by test, as DT-6 pins its own.
- **Apply:** `exclude_liability_paid_off`, targeting by holder name because a governed rule's
  subjects are content hashes, never DB primary keys. Exactly one match or nothing.

## Refinance-scoped, though the defect is not

A purchase reaches the same double count through a departing residence being sold, or a debt cleared
at closing to qualify. Detecting those needs different evidence, so a purchase is `not_applicable`
here and LP-571's control remains the path for them. That is also why LP-568 put the flag on the
liability rather than deriving it from loan purpose.

## Two traps the codebase caught

**`loan_tag`, not `tag`.** The subject is a liability, so the subject's own tag map has no
`loan.purpose`. A plain `tag:` loads cleanly and is then absent on every liability — the eq guard
never holds and every subject `couldnt_check`s. That is precisely what `reject_loan_tag` documents,
and it is what this spec did on its first run: all seven behaviour tests returned `couldnt_check`.

**Adding a projected field nearly re-keyed every liability.** Handled in LP-572 — the identity hash
and the gathered-field list are now separate.

## Verified by removing each fix

| removed | result |
|---|---|
| `loan_tag` → `tag` | 3 of 7 DT-8 tests fail — every subject `couldnt_check`s |
| the apply's exactly-one-match guard | the ambiguous-holder test fails |
