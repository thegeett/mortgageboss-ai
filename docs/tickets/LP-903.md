## What this is

Five decisions written down **before** LP-904 writes a migration, so the schema is designed once
rather than discovered. Everything here is a decision that would be expensive to reverse after tables
exist: whether a condition is its own row, what may close one, which columns are NPI, whether a
condition can become a finding, and how a lender's codes are keyed.

## Why it is its own ticket

Each of these is load-bearing on a column in LP-904, and three of them are only visible as a
*constraint* rather than a feature:

| ADR | The column it decides |
|---|---|
| 403 — a condition is its own entity | that `conditions` exists at all, rather than `needs_items` gaining an origin |
| 404 — only the lender clears | `prep_status` **and** `lender_status`, and `completeness` on the round |
| 405 — condition text is NPI | which columns the `readonly.*` views drop |
| 406 — a condition never becomes a finding | the absence of a column, and a Stage 3 link in the other direction |
| 407 — codes are lender-scoped | `(lender_id, code)` unique, `String(16)` keeping leading zeros, and `canonical_lender_key` |

## Decisions

**ADR-403 — a condition is its own entity.** A condition has a lender, a round, verbatim text owned by
the lender, a template code, a bucket and eventually a verdict; a need has none of those. They answer
different questions and come apart constantly — one condition asks for three documents, another asks
for no document at all. Conditions create needs (Stage 3); nothing creates a condition but a sheet or
a processor typing one.

**ADR-404 — only the lender clears, and a partial source never does.** Two tracks: our preparation and
the lender's answer. Absence is evidence only when the thing absent was in a list claiming to be
complete — which is the whole content of `completeness`, and why the paste dialog asks before it
accepts and defaults to *"just some"*.

**ADR-405 — condition text, headers and event details are NPI.** Ordinary queryable columns, protected
at rest and in transit, and **dropped from the `readonly.*` views** exactly as `documents.full_text`
is. No real condition sheet enters the repository.

⚠️ *Corrected in review.* The first draft justified "ordinary columns" by saying the text is "diffed,
searched and fingerprinted" and so must be comparable. **That inverts the design.** Matching runs on
`text_fingerprint` — a separate plain `String(64)` sha256 with its own index — which exists *precisely
so the text never has to be compared in SQL*; diffing happens in Python on retrieved rows. Encryption
would have cost the matching nothing. The decision is unchanged and its real support was verified:
`documents.full_text` is dropped by the C7 migration and additionally pinned in
`test_readonly_query.py`'s explicit exclusion list, so re-adding it later fails a test. The ADR now
rests on 314.4(c)(3) plus that exclusion, with the operational argument (a column nobody can index is
a trap for the next feature) in place of the false one.

**ADR-406 — a condition never becomes a finding.** Findings are rule-derived and the reconciler owns
their lifecycle; a row it must not retire has no business in the table it sweeps. A finding raised by a
condition's document links *back* to the condition.

**ADR-407 — lender codes are lender-scoped.** Always `(lender, code)`; leading zeros kept, because the
code is an identifier printed on a document and not a number.

### The one decision that came from a question, not the spec

The spec anticipated a STOP AND ASK at LP-910: *"match by lender name/slug; STOP AND ASK if there is no
reliable way to identify UWM and Champions."* The survey found there is none — `lenders` is
company-scoped with a slug unique only per company (ADR-045), chosen by each processing company, so a
seed keyed on a slug matches nothing on some tenants and the wrong row on others.

**Answered by the product owner, 2026-09-23: option 1.** `lenders` gains a nullable
**`canonical_lender_key`** (`"uwm"`, `"champions"`), admin-set, and the LP-910 seed matches on it. It
is recorded in ADR-407's consequences rather than as a sixth ADR, because it is the mechanism that
makes `(lender, code)` seedable across tenants rather than a separate decision.

⚠️ **Consequence for the build order:** `canonical_lender_key` is a `lenders` column, so it is added in
**LP-904's** migration beside `mortgagee_clause`, `condition_upload_cutoff` and
`condition_handling_notes` — not in LP-910, which only reads it. A lender with the key unset is not an
error: its codes arrive as `OBSERVED_UNMAPPED`, which is the same path any unknown code takes.

## Review — all four questions answered, two fixes applied

Peer review of `a19530d4`. I asked four specific questions rather than for a general read; all four
came back answered, two with changes.

**1. ADR-405's second reason did not hold — FIXED.** I suspected it and the review confirmed it with
the spec's own line numbers: `text_fingerprint` (spec :201, indexed at :209) exists *precisely so the
verbatim text never has to be compared in SQL*, and the matching at :601-606 runs on (code,
fingerprint) then fingerprint alone. Citing "it is fingerprinted" as a reason the text must be
comparable **inverts the mechanism's purpose**. The verdict was independently re-supported rather than
assumed: `documents.full_text` is dropped by C7 with the reasoning inline **and** pinned in
`test_readonly_query.py`'s explicit exclusion list, so a later migration re-adding it fails. ADR-405
now rests on 314.4(c)(3) + the readonly exclusion, with an operational argument replacing the false
one. The decision never moved; only its justification did.

**2. `canonical_lender_key` belongs in ADR-407 — NO CHANGE.** The reasoning I could not settle myself:
the key exists *only* because ADR-045 makes slugs per-company, which makes `(lender_id, code)`
per-company, which is what breaks seeding — and that chain starts inside ADR-407's own decision. So it
is a consequence of 407, not a peer of it. ADR-408 stays free.

**3. The glossary contradiction was real, and it was not the one I flagged — FIXED.** I worried about
**Round** beside **UW Round**; that pair reads cleanly ("the cycle is the event, the round is the sheet
it produced"). The actual contradiction was the **pre-existing `Condition` entry I left untouched** —
*"the file's to-do list coming out of underwriting"* — which is the **need** concept, i.e. the exact
thing ADR-403 spends its argument separating a condition from. Seven new terms sat under a heading
whose first definition contradicted the ticket's first ADR. Amended in place, keeping the original
sentence and adding what Phase 4.5 makes it mean.

**4. The four prohibited arrows are clear — NO CHANGE.** Verified structurally, not by reading:
no condition table among the 56 created across `alembic/versions/`; `Finding`'s FKs reach only
loan_files, verifications, documents and users; `NeedsItem`'s reach only loan_file, borrower,
`source_finding_id`, `satisfied_by_document_id`, `covered_by_document_id`, `duplicate_of_id`; and zero
repo-wide hits for `condition_id` / `lender_condition` / `condition_sheet` in `app/` or `alembic/`.
Every "condition" hit in the verification and needs code is "unconditionally", a PROPERTY category
comment, or "conditional rules". The prohibition describes nothing the codebase violates.

### One thing the review turned up that LP-904 needs

**`NeedsItemOrigin.CONDITION = "condition"` already exists** (`models/needs_item.py:91`), reserved for
this phase, with **zero branches on it** anywhere in `backend/app/`. It does not violate the Need →
Condition prohibition — it is the opposite direction, a need *originating from* a condition, which the
boundary diagram already carries as `Condition -->|Stage 3: creates| Need`. So it corroborates the
decision rather than contradicting it.

The reviewer flagged as **unverified** whether that value is in the stored constraint. **Checked here,
and it is:** `"condition"` appears in the original `create_needs_items` migration
(`20260611_1003_4db01a03523e:69`) and again in the LP-68 swap
(`20260619_1600_93a861456e2f:46`, `_ORIGIN_OLD = ("manual", "finding", "condition", "template")`). So
Stage 3 populates that origin with **no constraint-swap migration** — worth knowing because the
opposite case is precisely what `tests/test_activity_type_migrations.py` exists to catch.
