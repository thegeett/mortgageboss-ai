# LP-578 — a preview a processor approved must be the one that gets applied

## The window

The preview is computed at T; the processor reads it and confirms at T+30s. In between, another
processor can:

- edit the target liability's payment,
- **add a second liability from the same servicer** — which turns a clean Apply target into an
  ambiguous one the action refuses,
- soft-delete the row,
- change a DTI override.

Applying anyway writes something other than the before/after that was approved. Apply moves an
underwriting number — DT-8 swings the back-end DTI from 58.59% to 34.39% — so "close enough" isn't.

## The guard

The preview returns a **fingerprint** of the state it was computed against; the client hands it back
on confirm; the apply refuses with a 409 if it no longer matches.

**What it hashes, and why that material.** The calculators' LINE ITEMS *are* the apply-relevant rows:
a debt line's key is `debt.<liability id>`, its label carries the holder (`f"{kind} — {holder}"`),
its amount is the figure. Hashing the items catches a changed payment, a renamed holder, an added or
removed liability, and a new override — without enumerating tables here and going stale the moment
one is added. The finding's own resolution state is included because applying twice is the other way
the outcome diverges.

**Not a timestamp.** A file edited and edited back describes the same apply, and refusing it would
train processors to click past the warning — which is worse than not warning at all.

## What the tests caught

`str(Decimal("3000"))` and `str(Decimal("3000.00"))` are the same amount and different strings, so
the first version of the fingerprint changed on an edit-and-revert. That is a **false** staleness
refusal, the exact failure mode above. Money is now canonicalised to two places before hashing;
`test_an_edit_and_its_reversal_leave_it_unchanged` pins it.

The case worth keeping in mind is `test_a_second_liability_from_the_same_holder_changes_it`: a guard
watching only the target row's own fields would miss it entirely, because the *target* is unchanged —
what changed is that it is no longer unique. Watching the line items catches it, since a new debt
line appears.

And `test_renaming_the_holder_changes_it` is why the *items* are hashed rather than the headline
ratios: a rename moves no total at all, and it is precisely what breaks a holder-targeted Apply.

## Optional, deliberately

A caller that sends no fingerprint gets today's behaviour rather than a hard failure. The trade is
real — no fingerprint means no protection — and the UI always sends one, so the gap is a non-preview
caller (a script, a test), not the product path.

## Verified by removing the fix

| removed | result |
|---|---|
| handing the fingerprint back on confirm | `hands the fingerprint back so the apply can refuse a moved file` fails |
| canonicalising money | `test_an_edit_and_its_reversal_leave_it_unchanged` fails |
