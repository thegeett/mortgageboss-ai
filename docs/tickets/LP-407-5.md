# LP-407-5 — Settle the AS-2 / PC-5 boundary; PC-5 STOPS (the "not cleanly expressible today" rule)

## What this ticket is

PC-5 checks whether the purchase contract's earnest-money deposit (EMD) appears as a matching **withdrawal** in
the borrower's bank statements — a real fraud check (a missing/unsourced EMD may be someone else's funds, an
undisclosed loan, or an undocumented gift). LP-407-1 flagged that PC-5 **overlaps live AS-2**, whose own spec
calls the true cross-document match *"not cleanly expressible today."* So the **boundary decision comes first,
and it may change a live rule.**

**Outcome:** the boundary is **(b) COMPLEMENT** — AS-2 and PC-5 check **different transactions** (AS-2: a
suspicious *inflow*; PC-5: the EMD *outflow* match), so **AS-2 is UNCHANGED** (no live-rule change, no
equivalence risk). But **PC-5 does not survive as a clean, activatable rule today** — it is exactly the
multi-blocked cross-document match AS-2 defers. **PC-5 is NOT written.** The concrete build it needs is proposed
below for a dedicated future ticket. **No code was changed except this report.**

## D1 — the boundary (both rules quoted; the (a)/(b)/(c) argument)

**AS-2 (LIVE) — what it ACTUALLY checks** (`specs/AS-2.yaml`, verbatim):
> criteria: *"An earnest-money deposit paid from the borrower's funds must be sourced (traceable to a verified
> account)… NOTE (LP-323-AS-B): the true shape is a cross-document MATCH (contract EMD amount ↔ a debit) **which
> is not cleanly expressible today**; this approximates it via the AS-1 txn sourcing vocabulary and is reported
> for -C."*
> - `subject_enumeration: per_deposit`; reads `txn.apparent_category` + `txn.has_identified_source` (AI, reused
>   from AS-1); **fires when `txn.apparent_category == loan_proceeds` AND `txn.has_identified_source != "yes"`.**

So AS-2 is a **per-transaction sweep for a suspicious INFLOW** — a deposit that looks like *loan proceeds* and is
unsourced (borrowed money coming *in*). **It does NOT read `contract.emd_amount`** (the `rule_tags.csv` mapping
to `contract.emd_amount`/`contract.emd_sourced` is DRIFT — the live spec reads only `txn.*`). Its bar is
`calibratable-now`/validated/LIVE, but note its own caveat: the `loan_proceeds` fire path is **n=0 — never
measured** (it approximates and has never confirmed a fire).

**PC-5 — what it WOULD check** (`rule_kinds.csv`: *"EMD amount & source — EMD from contract + sourced debit
(ties AS-2)"*): does the contract's EMD amount appear as a matching **withdrawal (debit)** in the statements —
the actual cross-document match, money going *out* of a verified account.

**The argument:**
- **(a) PC-5 replaces AS-2 → NO.** They check **different transactions** — AS-2 an *inflow* (a loan-proceeds
  deposit), PC-5 an *outflow* (the EMD debit). A file can fail one and pass the other. Retiring AS-2 would drop
  the inflow check. So AS-2 does **not** narrow/retire. **No live-rule change, no equivalence proof needed.**
- **(b) COMPLEMENT → YES, in principle.** AS-2 catches undisclosed-borrowed-funds *inflows*; PC-5 catches the
  missing/unsourced EMD *outflow*. Distinct failure modes, distinct reasons. **This is the boundary: AS-2 stays,
  unchanged, as the inflow approximation; PC-5 would be the outflow match — IF it were cleanly buildable.**
- **(c) redundant → NO** (they're distinct) — but see the roll-up: PC-5 being *distinct* does not make it
  *buildable-and-valuable today*.

## D0 — the redundancy check (product surface)

No service/API surface shows an EMD-vs-bank-statement match (grepped — the `earnest`/`emd` hits are absent from
`services/`/`api/`). So PC-5 is not already delivered by a UI panel. **No STOP on D0** — the block is
expressibility, not product duplication.

## D2 — the relation class + the producer proposal

The EMD match is a **fuzzy cross-document SUBSET-SEARCH** (the ADR-323 shape) — "does *some* transaction (or
*combination* of transactions) match the contract EMD amount?" — carrying a heavy false-positive residue:
- the amount may be **split across two transfers** (no single matching debit);
- the withdrawal may be **EMD + a wire fee** (not the exact contract amount);
- it may **leave an account the file has no statement for** (the common case);
- the **date won't align** (the EMD is paid weeks before the file is assembled);
- the payee is an **escrow/title company** the statement names inconsistently.

**Proposed producer (for a future ticket — NOT built here):** a derived loan tag `contract.emd_sourced`
(`matched` / `unmatched` / `no_statements` / `unknown`) that promotes `contract.emd_amount` to loan level, then
searches the file's transactions for a **debit** (deterministic `direction == "debit"`, derived from
`transaction_type` — NOT the AI `txn.is_money_in`, so the search can be AI-free) whose amount matches within a
tolerance. Mirrors the LP-410 derived-search shape (`stmt.continuity` / `income.employer_coverage`), plus the
ADR-325 `needs_review` routing on `unmatched`.

## D3 — the operands (reachability)

| operand | source | reachable today? |
|---------|--------|------------------|
| the contract EMD amount | `purchase_agreement.earnest_money_amount` (**typed-core**) | producible, but needs a **loan promotion** (`contract.emd_amount` is a document tag; PC-5 is loan-enumerated) — the `contract.loan_sales_price` shape, **not built** |
| the transaction search | the file's transactions — amount (parsed) + `direction` (deterministic credit/debit, derived from `transaction_type`) | reachable, but needs the **match-search producer** (the fuzzy subset-search) — **not built** |

Both sides are *reachable in principle* but **neither the emd_amount promotion nor the match-search producer
exists** — so PC-5 is `needs-producer` (×2), not blocker-free.

## D4 — the subject match

PC-5 would be loan-enumerated; `contract.emd_sourced` would be loan-subject (the proposed producer). No
structural-death risk in the proposed shape.

## D5 — the DANGEROUS DIRECTION (the decisive hazard)

**Never fire "missing EMD" because a statement wasn't uploaded.** The EMD is routinely paid from a checking
account that is **not** in the uploaded document set (borrowers upload asset statements for the down
payment/reserves, not necessarily the EMD-paying account). So a "no matching debit" result is *most often*
benign (the paying account simply isn't in the file), not fraud. This forces a hard choice with no good answer
today:
- **non-match → `couldnt_check`** (we cannot confirm; the account may not be uploaded) → PC-5 then **NEVER fires
  or flags** — it only satisfies (match found) or couldnt_checks. **Near-vacuous** (positive confirmation only,
  never a finding).
- **non-match → `needs_review`** (ADR-325, "confirm the EMD source") → but the EMD account is *usually* not
  uploaded, so PC-5 would **needs_review on a large fraction of purchase files** — net **noise**, not signal.

**This is what distinguishes PC-5 from PC-3.** PC-3's `needs_review` fires on *rare* abbreviation variants;
PC-5's would fire on the *common* "EMD account not uploaded" case. And PC-5 uniquely carries the **fairness
hazard** of implying a phantom/undisclosed deposit because a document is missing. Neither branch is
clean-and-valuable today.

## D6 — the matching tolerance is Priya's

A match tolerance (exact? within $X? within N days? two transfers summing to the EMD?) is a **domain threshold
Priya sets** — the rule would ship `no-ai-threshold-pending`, `validated:false` (HELD). An exact-amount match
avoids the threshold but is **brittle** (misses EMD+fee and split deposits → more `needs_review` noise).

## D7 — provability

**LF-6T3N carries a contract EMD (`earnest_money_amount = 7300.00`, LP-414) but its committed transactions
contain NO matching ~$7,300 debit** (the "EMD Withdrawal.pdf" is a *statement filename*, not a matching
transaction). So even the satisfy path could not be proven on LF-6T3N — PC-5 would `needs_review`/`couldnt_check`
there. Every branch would need a constructed scenario (`fire_path_scenarios.py`, `95…`), NOT LF-6T3N.

## THE DECISION — STOP (do not write PC-5 now)

**PC-5 is the multi-blocked cross-document match AS-2's own spec defers as "not cleanly expressible today."** It
stacks:
- **needs-producer ×2** — the `contract.emd_amount` loan promotion + the fuzzy debit-match search;
- **needs-definition** — the matching tolerance (Priya) — or a brittle exact-match;
- **a delicate, low-value FP profile** — the *common* missing-EMD-account case forces either near-vacuous
  `couldnt_check` (never flags) or noisy `needs_review` (flags on most files), plus the fairness hazard of
  never accusing on a missing statement.

This is the OPPOSITE of the blocker-free rules this arc has been writing (PC-2/PC-3/IH-3). Forcing it would
repeat the census over-counting the whole arc has corrected, and would ship either noise or a near-vacuous rule.
**The honest call is (b)-and-stop: the boundary is settled (AS-2 stays, unchanged, as the inflow approximation;
PC-5 is the deferred outflow match), and PC-5 is not written today.**

## The concrete proposal (for a dedicated future ticket)

When PC-5 is scheduled, it needs, in order:
1. `contract.emd_amount` promoted to loan (`contract.loan_emd_amount`) — the `contract.loan_sales_price` shape.
2. A derived `contract.emd_sourced` producer (loan): search transactions for a `debit` (deterministic
   `direction`) whose amount matches `contract.loan_emd_amount` within Priya's tolerance (or exact + a
   split-aware pass); emit `matched` / `unmatched` / `no_statements` / `unknown`.
3. PC-5 spec: `matched → satisfied`; `unmatched (statements present) → needs_review` (ADR-325, the THIRD
   instance — which would confirm `needs_review` as the default for fuzzy cross-document rules); `no_statements
   / no contract → couldnt_check` (**never a "missing EMD" finding** — the D5 discipline); a **refinance** →
   `couldnt_check` (the `loan.purpose` gap PC-2/PC-7 share).
4. Priya's matching tolerance → the bar (`no-ai-threshold-pending`, `validated:false`, HELD until she signs off).
5. A "missing-EMD" scenario in `fire_path_scenarios.py` (`95…`), NOT LF-6T3N (which has no matching debit).

**Before scheduling, re-run D5:** confirm whether the common "EMD account not uploaded" case makes the
`needs_review` net-positive or net-noise — that is the true gate on whether PC-5 is worth building at all.

## Every assumption / decision

- **AS-2 does NOT read `contract.emd_amount`** — read from the LIVE spec (the `rule_tags.csv` mapping is drift).
- **The boundary is (b) complement** (inflow vs outflow), so **AS-2 is not changed** — no equivalence proof
  needed, no STOP-for-approval (that is only for (a)).
- **Direction is deterministic** (`direction` credit/debit from `transaction_type`), so a future producer can be
  AI-free — this is NOT the blocker; the producers + the tolerance + the FP profile are.
- **STOP, not build** — PC-5 is `needs-producer ×2 + needs-definition + a delicate FP profile`, the "not cleanly
  expressible today" rule; writing it now would ship noise or a near-vacuous rule.
- No file was modified. This report is the only deliverable.
