# LP-853 — the body becomes HTML the moment a person touches it

Status: spec. **Blocks LP-854. The one with real risk in it.**

Epic: [`docs/domain/communication/v1-epic.md`](../domain/communication/v1-epic.md) · Screens: [`v1-screens.md`](../domain/communication/v1-screens.md) · Spec: [`comm-v1-draft-only-spec.md`](../domain/communication/comm-v1-draft-only-spec.md)

## The report

> "I did not like current rich text area, It just has Bold and Bullet option. Check how many Gmail
> provide while compose, and make it like that."
>
> "Text area should be reach text... Make sure when user copy it and paste it it should preserve
> text formatting specially in email client, Outlook/gmail."

## This reverses LP-849's storage decision, with the benefit of having seen it

LP-849 decided: *"the body column stays one plain string; the editor converts on load and serialises
on save. Not HTML-in-the-column."* That was the right call **for the schema it shipped** —
paragraphs, bullets, bold — and it was chosen precisely so the editor could not produce something
the converter silently drops.

Underline, links, ordered lists, indent and block quotes **cannot round-trip through that string.**
So the toolbar request is a storage request, whether or not it was meant as one.

LP-849 listed four costs of storing HTML. **Three are avoidable and one is real:**

| LP-849's objection | Verdict |
|---|---|
| "every backend template would have to emit HTML (all of them, each a new ADR-401 version and fingerprint)" | **Avoided.** Templates keep emitting plain text. See the decision below. |
| "`finalise_draft_body`'s placeholder pass would run over markup" | **Avoided.** Placeholders resolve while the body is still plain. |
| "`mailto:` needs a generated plain-text downgrade" | **True, and cheap.** Derived on demand, never stored. |
| "the send record — which must be *what went out* — becomes a format no existing test reads" | **True.** This is what the format column is for. |

## The decision: a format column, and generated bodies stay plain

Add `Communication.body_format` — `plain` | `html`.

- **A generated draft is `plain`.** Templates, `finalise_draft_body`, ADR-401 fingerprints,
  `_regenerate` and LP-849's round-trip fixed point are all **untouched**. This is what kills
  objection 1: nothing on the backend learns to emit HTML.
- **The first processor edit stores HTML** and flips the column. From then on the body is authored
  content and the backend treats it as opaque.
- **`body_format == 'html'` IS LP-851's `body_edited` flag.** One fact, one place — **do not add a
  second column.** "A machine wrote this" and "it is still plain" are the same statement, and
  storing them twice is the pattern that has bitten this codebase seven times (A22).
- **`_regenerate` refuses on an `html` body.** LP-851's warning dialog is the user-facing half of
  the same rule; this is the half that cannot be clicked past.
- **Plain text is derived, never stored.** `plain` bodies are used as-is; `html` bodies are stripped
  on demand for `mailto:` and LP-855's compose links. Two stored copies of one message is the same
  anti-pattern again.

## Sanitisation is in this ticket, not a follow-up

`email-body.ts` is safe **by construction** today: it escapes every character that could begin
markup *before* emitting a single tag, so there is no passthrough to leave open and no sanitiser
whose rules have to keep up with a renderer. Its own comment says so, and it was right.

**Storing author HTML ends that property.** An allowlist on the way in replaces it — server-side,
matching the editor schema exactly, with the same tag set LP-854 enables and nothing else. A
sanitiser added later is a window in which every draft written is untrusted, so it ships here.

Attributes are the part to get wrong: `href` on `<a>` restricted to `http`, `https` and `mailto`
only. Nothing else survives — no `style`, no `class`, no `on*`.

## What it must not break

- **`emailBodyToHtml` stays the single renderer for the `plain` path.** The editor and the reader
  must not be able to disagree, which is LP-849's rule and still holds for every generated draft.
- **LP-844's clipboard pairing.** `text/html` + `text/plain` together in one `ClipboardItem`, with
  the `writeText` fallback. HTML alone fails silently in Chromium. Do not touch `copy-rich.ts`
  beyond feeding it the right source.
- **The mail-client-safe output.** Bare `<p>`, `<ul>`, nested `<ul>`, `<strong>` — **no classes, no
  stylesheet dependency**, because Outlook on the desktop renders with Word's engine and discards
  most CSS. Whatever LP-854 adds must hold to this.
- **LP-849's round-trip fixed point** still guards the `plain` path and must still pass.

## Acceptance

1. A generated draft stores `body_format = 'plain'` and a body byte-identical to today's.
2. Opening a generated draft and **not typing** leaves it `plain`. Focus is not an edit.
3. The first real edit flips it to `html` and `_regenerate` then refuses.
4. `mailto:` and the compose links carry correct plain text from both formats.
5. A body containing `<script>`, `onclick=`, `style=` or a `javascript:` href is stored stripped —
   tested server-side, with the request built by hand rather than through the editor.
6. Every LP-849 round-trip test still passes on the `plain` path.
7. Migration: every existing row is backfilled `plain`. No existing draft changes.

# What was built

Status: **done**.

## The decision LP-853 and LP-851 could not both have

**LP-853 says `_regenerate` refuses on an `html` body. LP-851's Screen 5 copy — literal, ships as
written — says "Adding a document rewrites the message from the template, and your changes … will be
lost."** Those cannot both be true of an unconditional refusal.

Resolved as: **`_regenerate` refuses by default, and the append path passes `force=True`.** The
rewrite is therefore reachable only behind LP-851's dialog, which is what "this is the half that
cannot be clicked past" has to mean for the sentence beside it to be true.

The alternative — refusing always — is worse in the direction this epic exists to close. The
membership would grow and the words would not, so the draft would ask for a document its own body
never names and the borrower would never be asked. Silently. And a Ledger rule applies directly:
*"Any copy that says what the system will do gets verified against the code that does it"* — an
unconditional refusal ships a false sentence.

`test_the_warned_append_does_rewrite_an_authored_body` pins it, and
`test_only_the_append_forces_a_rewrite` pins that the override has exactly one call site.

## The changes

**`app/communications/sanitise.py`** (new) — the allowlist that replaces "safe by construction".
Re-serialises from `html.parser`: nothing in the input reaches the output as markup, a tag off the
list contributes its text and nothing else, an attribute off the list does not exist, and
`script`/`style` lose their contents too. Stdlib rather than a dependency, because there is no
allowlist sanitiser in this project to reach for and a remove-what-is-bad design is the one that has
to keep up with an attacker. `ALLOWED` is the single place the tag set is written down.

**`Communication.body_format`** — `plain` | `html`, NOT NULL, server default `plain`. Migration
`b8d1f6e40c25`. It **is** LP-851's `body_edited`; `draft_body_edited()` reads it and there is no
second column.

**The three rewriters now refuse an authored body**, each before it changes anything:
`_regenerate` (unless forced), `refresh_if_stale` (a read path — there is no action to move it
behind), `attach_upload_link` (before minting or revoking, because the link's token is hashed and a
link that never reaches the body is unrecoverable), `remove_need_from_draft`, and
`party_requests.build_party_draft` (a `_regenerate` caller since LP-850's review, and nothing on
its path warns anybody).

**`_regenerate` resets the format to `plain` when it writes.** Found by a test: after a forced
rewrite the body is the template's again, so leaving the flag on `html` would refuse the *next*
request over words no person wrote and make LP-851 warn about changes that were already gone.

**`PUT /outbound/draft/{draft_id}/body`** — the save. Sanitises, stores, flips the column.

**Frontend** — the editor emits HTML and converts only on the `plain` path; the dialog autosaves
(debounced 800ms, flushed on close) and derives plain text for `mailto:`; `copy-rich.ts` is fed the
right source rather than changed; the reader shows an authored body as markup and a generated one
through `emailBodyToHtml`.

## Measured, not assumed

**The migration, against a real Postgres** (a scratch database, upgraded from empty to head):

- `body_format` is `NOT NULL DEFAULT 'plain'`;
- an INSERT that **omits** `body_format` — what code from before this column writes, which is what a
  rollback produces — succeeds and gets `plain`. The compatibility guarantee runs in both directions
  (AMENDMENTS, LP-UI-024 review) and this is the half that fails harder;
- the readonly view exposes `body_format` and still withholds `body`, `subject`, `recipient`,
  `sender` and `upload_link_url`;
- downgrade drops the column, rebuilds the view without it, and leaves the rows;
- and acceptance 7 directly: downgraded, inserted a row **before the column existed**, upgraded —
  it came back `plain`.

**The bundle.** The communication route is **197 kB** first-load, from 195 kB at LP-849. The +2 kB
is `htmlToEmailBody` joining the page bundle: the dialog and `copy-rich` now derive plain text on
the page, while the editor itself stays behind `next/dynamic`. LP-854 re-measures.

**Five guards mutated to prove they fail.** Each mutation was applied, run, and reverted:

| mutant | caught by |
|---|---|
| save route in a NEW module with no "draft" in its prefix | `test_no_draft_save_route` (derived scope) |
| `PATCH` reusing `SendDraftRequest` | same (route allow-list, not model) |
| handler with the payload as its SECOND parameter | same (full-signature matcher) |
| route on `message_router` rather than `router` | same (any router variable) |
| raw `data.body` into `dangerouslySetInnerHTML` | `email-body-templates` sink scan |
| editor serialising to plain text again | `message-editor::reports HTML … when the document changes` |
| editor reporting at mount time | `message-editor::reports nothing on mount, or on focus` |
| no flush on dialog close | `message-dialog-autosave::flushes the last edit` |
| send posting plain text on an authored draft | `message-dialog::sends the HTML once the draft is authored` |

## Three guards that were not guarding, found by mutating them

1. **`test_no_draft_save_route` read only the handler's FIRST parameter.** Every version matched
   `def NAME(FIRST: TYPE)`, so a handler written `(draft_id: UUID, payload: SaveDraftBodyRequest)` —
   which is how every FastAPI handler with a path parameter is written — reported its model as
   `UUID` and passed. **LP-853's own save route walked straight through it**, and `reply` has been
   invisible to that file since LP-818. It also matched only `@router.`, so half of
   `communications.py` (everything on `message_router`) was never scanned. And its scope was a
   literal set of two filenames — the third name-based narrowing in that file's history. The scope
   is now **derived from the import graph**: modules that assign a body onto a `Communication`, plus
   every api module that reaches one.

2. **The `dangerouslySetInnerHTML` scan matched `[^}]*`.** LP-853 made the one sink a ternary
   containing a `}`, so the regex stopped short and the scan matched **nothing** — zero offenders,
   zero sinks, reported as a clean tree. Only its own count control caught it. The matcher balances
   braces now and strips whole-line comments first (the sink's safety argument sits between the
   braces and the key), and two planted cases pin both shapes.

3. **The dialog's "does not save when the editor reports the body it was handed" test could not
   fail.** React bails out of a state update that sets an identical string, so the stub never
   reached the debounce — the assertion passed with the guard deleted. Removed, and the guarantee it
   was reaching for is asserted where it is real: Tiptap does not report without a document change,
   against the real editor.

Also: the autosave tests initially passed **vacuously** because `next/dynamic` resolves
asynchronously and the stubbed editor was not in the tree yet. Five `not.toHaveBeenCalled()`
assertions, all green against a tree with no button in it. The positive control is what caught it.

## What was decided that the ticket did not cover

- **A save route exists, and `test_no_draft_save_route.py` was narrowed rather than deleted.** That
  guard's own docstring named the condition: the heal "becomes destructive and must move behind an
  explicit action" the day a save exists. It is narrowed to permit exactly two routes, paired with
  the module and behavioural tests that the three refusals hold.
- **The allowlist is LP-849's tag set (`p`, `br`, `strong`, `ul`, `li`), not LP-854's.** The ticket
  says "the same tag set LP-854 enables"; shipping that here would allow tags the editor cannot
  produce, which is a hole nothing is watching. LP-854 extends the allowlist and the Tiptap
  extensions together, which is what "derive the list once" asks for.
- **The ticket's table claims italic already exists ("Bold · Italic | have them | LP-849"). It does
  not** — `EXTENSIONS` has no `Italic` and `emailBodyToHtml` emits no `<em>`. LP-854 adds it with
  the other seven. Recorded because the premise did not survive contact with the code.
- **No `html_to_plain` on the backend.** `from-html.ts` already derives it and is tested as a
  round-trip fixed point; a second implementation is A22. The one thing the backend reads the
  body's length for is the `mailto:` ceiling, and HTML is longer than the text it renders to, so
  that gate stays conservative rather than wrong.
- **A subject-only edit does not autosave.** It would flip `body_format` and record a body edit that
  never happened. The subject still rides along whenever a body save fires.

## What was not done

- **Acceptance 4's manual half.** "Paste into Gmail and Outlook on the web" is recorded in LP-854 as
  manual; nothing here has been pasted into a real mail client. The automated half (the clipboard
  carries both flavours, `mailto:` carries plain) is covered.
- **LP-855's button bar.** The dialog still has LP-849's buttons and the `mailto:` link. Screen 2's
  bar, the client picker and the removal of the length gate are LP-855.
- **Nothing on screen says "saving".** Screen 2 specifies no such indicator, and LP-852's list row
  (`Draft · edited · 2m`) is where the fact is meant to appear.

# Review (second session)

Reviewed at `a84bdf11`. Each finding below was measured — a test fails without its fix, and each
fix was mutation-checked in both directions.

## The one that matters

**The send could put unsanitised markup in the body column, and the modal renders that column with
`dangerouslySetInnerHTML`.** A stored XSS across a user boundary.

`sanitise.py` states the guarantee the rest of the system is built on — the column "never holds
anything that was not allowed", so "every reader of it inherits the guarantee without knowing the
rule" — and `message-dialog.tsx` cites it by name as the reason it may inject an `html` row
directly. `save_draft_body` holds that guarantee. `send_draft` did not: it takes `body` from the
client, assigned it to `draft.body` untouched, and never changed `body_format`. So a request that
posted `<img src=x onerror=…><script>…</script>` to the send of a draft already marked `html`
stored exactly that, and the next person in the company to open the sent message executed it.

Measured before the fix: the column held `<img src=x onerror="alert(1)"><script>alert(2)</script>`
with `body_format = html`. `send_draft` now sanitises when the row is authored; the plain path is
untouched, because a plain row is escaped at render by `emailBodyToHtml` and does not depend on
this. Guarded by `test_the_send_cannot_put_unsanitised_markup_in_the_column`, with
`test_a_plain_send_is_not_touched_by_the_allowlist` as the other half.

The root cause is worth keeping: the four rewrite mechanisms were each given a refusal and a
behavioural test, and the fifth writer of the same column — the send — was not on that list.

## Also fixed

**The loan tag was appended to an HTML body as plain text.** `build_outbound` appended
`\n\n[LF-XXXX]` unconditionally. In HTML a newline is whitespace, so the tag rendered inline,
running straight on from the processor's last sentence in the message the borrower reads. It takes
an `html` flag now and appends `<p>[LF-XXXX]</p>`; the tag's TEXT is unchanged, so
`inbound_routing`'s threading match is unaffected — asserted, because a change of spelling there
would silently orphan every reply.

**The dialog saved a draft that was typed in and then undone.** `dirtyRef` was only ever set true,
never cleared when the text returned to `openedAs`, so the flag set by a keystroke survived the
undo and the flush saved an unchanged body — flipping `body_format` to html for a draft nobody
changed, which freezes it against `_regenerate` and makes LP-851 warn about losing changes that do
not exist. That is acceptance 2 failing by a longer route than the one it was written for, and the
comment above it already claimed the case was covered. `onEdit` assigns rather than raises now.

## Checked and correct

- **The sanitiser holds.** 20 payloads beyond the 14 in the suite — mXSS through a `noscript`
  `title`, comment breakout, CDATA, a NUL inside a tag name, `svg/onload`, `iframe srcdoc`,
  double-decoded entities, unbalanced and malformed nesting — nothing reached the output as markup,
  with a positive control on the matcher. One cosmetic flaw, not worth a fix: `<ul><li>a<li>b</ul>`
  re-serialises as nested `</li></li>` rather than siblings.
- **The `force=True` decision is the right reading.** An unconditional refusal would let the
  membership grow while the words did not, so the draft would ask for a document its own body never
  names and the borrower would never be asked for it — silently, which is the failure this epic
  exists to close. Reachable only behind LP-851's warning is what makes both ticket texts true.
- **The guard rework closes the escape it was warned about.** Two mutants written and both die: a
  save route in `app/api/draft_body.py` with prefix `/compose` that imports `save_draft_body`, and
  a sneakier one in the same new module that assigns `draft.body` itself and imports no service.
- **The migration.** The readonly view omits `body`, `subject` and `recipient` in both directions,
  and the downgrade's column list matches LP-843's upgrade exactly, so a rollback restores the view
  that was there rather than a drifted one.
- **`renders_from_a_template` strands nothing.** The editor is seeded from a body that was already
  resolved for reading, so a saved HTML body has no placeholders left to lose.

## Reported, not fixed

**`GET /outbound/draft` runs `safe_substitute` over markup**, which is exactly what adding
`body_format is PLAIN` to `renders_from_a_template` prevents in `message_detail`. It calls
`draft_for_reading` unconditionally, so the protection covers one of the two read paths. No
frontend calls that route — it is a legacy panel surface and LP-857 is the ticket that removes it,
so a guard on a route nothing reaches would be speculative. Folding it into LP-857 is the cheaper
fix.

## Second review round — one defect in the fix, and one deferral verified

The LP-853 review (`3c803659`) found a **stored XSS**: `send_draft` writes the same column
`save_draft_body` does, and the allowlist was applied to one and not the other. That finding and its
fix are correct, and the shape of the miss is the part worth keeping — LP-853 enumerated the four
mechanisms that **rewrite** a body, gave each a refusal and a behavioural test, and never listed the
fifth writer. *The four that were enumerated are the ones that overwrite; the one that got through
is the one that writes.*

### The fix introduced a smaller defect of its own

`build_outbound` gained an `html` flag so an authored body gets `<p>[LF-XXXX]</p>` rather than a
newline HTML collapses. It was passed to the **sent** copy and not to the **composed** one, so the
two differed by the footer alone:

```
composed: <p>Please send the March statement.</p>\n\n[LF-DBFE]
as sent : <p>Please send the March statement.</p><p>[LF-DBFE]</p>
```

`EvidencePublic.was_edited` is `body_composed != body_as_sent`, so **every authored draft recorded
itself as edited** — including one where the processor opened the modal and pressed Mark as sent
without touching a character. Measured at exactly that, `True` where it should be `False`. The
composed copy also carried a plain-text newline inside an HTML body, which is the thing the flag was
added to stop, preserved in the copy an auditor reads.

This is the **third** time this comparison has been wrong in the same way: LP-823 resolved a
placeholder on one side and not the other, and this is a footer spelt one way on one side. The
pattern is that `body_composed` is built by a *second call* to the same function, and every
parameter that call does not mirror becomes a false edit.

Fixed by passing `html=authored` to both. Guarded by
`test_sending_an_authored_draft_unchanged_is_not_recorded_as_an_edit`, with
`test_an_authored_draft_the_processor_did_change_is_still_recorded_as_edited` as the control —
making both sides agree is otherwise trivially achievable by making `was_edited` always false, which
deletes the field's only purpose. Mutation-checked: reverting the flag fails the first and not the
second.

### The deferral, verified rather than accepted

The review reported `GET /outbound/draft` running `safe_substitute` over markup and deferred it to
LP-857 on the grounds that no frontend calls it. **Checked:** `fetchOutboundDraft` is defined in
`lib/api/communications.ts` and has no caller anywhere in `frontend/` — not a component, not a hook,
not a route. The route is unreachable from the UI, so the deferral stands and LP-857 deletes it.
Recorded here rather than left in a commit message, because an asymmetry outlives the reason for it.
