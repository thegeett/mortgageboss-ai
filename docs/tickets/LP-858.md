## §1 — The mail-client picker preempts the draft. CONFIRMED.

> *"on clicking draft, it suddenly asked me to choose what email client you want to open. Basically
> it should display the email first and later on clicking action button I should get that pop up."*

**Reproduced in code.** `message-dialog.tsx:376`:

```tsx
<Dialog open={open && !needsClient} onOpenChange={(next) => !next && close()}>
```

and `:191`:

```tsx
const needsClient =
  data?.is_editable === true &&
  preferences.data !== undefined &&
  preferences.data.mail_client === null &&
  !askedThisSession;
```

So on the **first editable draft of a session**, before any preference is saved, `needsClient` is
true and the message dialog is **suppressed entirely** — `open && !needsClient` is false — while
`MailClientDialog` renders. The processor asked to see a draft is asked instead which mail client
they use, about a message they have not read yet.

**Why it was built this way, and why that reason no longer holds.** The comment at `:755-762` is
about *z-order*: two modals were open at once, Radix marks everything outside the topmost one
`aria-hidden`, and the picker rendered first was unreachable to a screen reader. The fix chosen was
to render the picker last **and suppress the dialog underneath it**. That solves the accessibility
bug and creates this one. The right shape keeps both fixes: **do not open the picker on mount at
all.**

**What it should do.** Per spec §6, the draft's buttons are
`[Copy & open <client>]` · `[Copy message]` · `[Mark as sent]` · `[Delete]`. The client question
belongs to the **first button only**, and §8 says it is *"asked once, on the first draft"* — which
should be read as *the first time the button is pressed*, not the first time a draft is opened.
`Copy message`, `Mark as sent` and simply reading the draft need no client and must not trigger it.

**Done when:** opening a draft with no saved preference shows the draft. Pressing
**Copy & open mail app** with no saved preference shows the picker, and on answering it proceeds to
do what the button said in the same gesture — it does not ask and then make the processor press
again. `Copy message` and `Mark as sent` never raise it.

### The layout

**Do not build from this section — build from [`../design/lp858-draft-panel.md`](../design/lp858-draft-panel.md).**
That file is the contract: exact layout, the 300px rail, the three landing states, the literal

In one line: **list left, selected draft right, no modal**, compose is the right pane in create
mode, and `compose-draft-dialog.tsx` is deleted rather than adapted.

### Two things to preserve while swapping

1. **Do §1 first.** With the picker no longer opening on mount, the two-modal `aria-hidden`
   collision that `message-dialog.tsx:755-762` exists to work around is gone rather than re-solved.
2. **The editor loads once.** `compose-draft-dialog.tsx:96-99` deliberately uses a plain
   `<textarea>` so ProseMirror's ~55 kB is not paid on a three-field form. Folding compose into the
   right pane means the rich editor is now the *only* editor — that is correct and simpler, but it
   must not end up mounted twice.

### The empty-draft rule — needs one decision before building

*"if user do not add any detail it just delete the draft"* is right, and there are two ways to get
there. **They differ in what happens when the browser closes rather than the button being pressed**,
and that case is not rare.

| | **A — create on click, delete on close-if-empty** | **B — create on first keystroke** |
|---|---|---|
| Row appears | immediately, as asked | when they start typing |
| Close with nothing typed | row deleted | nothing was ever created |
| **Browser closed / tab navigated** | **an empty draft is left in the list** | nothing is created |
| Extra machinery | a sweep, or accept the litter | none |

**Recommendation: B.** It delivers the same thing a processor sees — a row for the draft they are
writing — and the "delete it if empty" problem stops existing rather than being handled. A is only
better if a row must appear the instant Compose is pressed, before any typing, and that has no
stated reason behind it.

**Whichever is chosen, "no detail" must be defined.** Recommendation: delete only when recipient,
subject **and** body are all empty. A processor who typed a recipient and stopped has done work;
destroying it silently is worse than leaving a row they can delete in one click.

### A correction to the decision document

`comm-v1-draft-only-spec.md` §2 says *"one open draft per party, enforced server-side"* and *"Create
a second draft does not exist."* **That is no longer true.** LP-832 dropped
`uq_communications_open_draft` — its migration is
`20260909_1200_b3f8d61a4c92_lp832_many_open_drafts.py`, and `models/communication.py:111-123`
records why: a request now creates a new draft each time, and *"several unsent drafts on one file is
the ordinary state."* The concurrency guarantee moved to a row lock in `add_needs_to_draft`.

That is convenient here — a composed draft cannot collide with an existing one — but the spec doc is
stale on the point and should be corrected, or the next person will design against a rule the
database stopped enforcing.

## §3 — Every draft deletable. NOT BUILT AT ALL. CONFIRMED.

> *"Each draft should be deleteable."*

**There is no delete route.** `api/communications.py` has exactly five:

```
GET   /draft
POST  /compose
PUT   /draft/{draft_id}/body
POST  /draft/{draft_id}/polish
POST  /draft/{draft_id}/send
```

No `DELETE`, and no `discard_draft` / `delete_draft` anywhere in `backend/app/`.

**And it was specified.** `comm-v1-draft-only-spec.md` §6 lists `[Delete]` as the quiet fourth
button, and `message-dialog.tsx:629` carries a comment describing that exact button row —
``Copy & open <client>` · `Copy message` · `Mark as sent` — spacer — `Delete``. The comment shipped;
the button never did. So this is not a regression, it is a gap between a comment and the code, and
§2's flow depends on it: without delete, an unwanted draft is permanent.

### What delete has to decide — this is the real question, not the endpoint

A generated draft is not just text. LP-809 links it to needs items through
`communication_needs_items`, and LP-801 writes `details.docs_requested` on the originating finding,
which `finding-card.tsx` reads to render the request button as **"Requested" and disable it**.

**So: does deleting a draft un-request the documents it was asking for?**

- **If no** — the finding still shows "Requested", greyed out, for a request that no longer exists
  anywhere. That is the exact defect LP-819's review found for bounced mail and fixed with
  `_clear_finding_markers`.
- **If yes** — deleting a draft reopens the needs and re-enables the buttons, and the processor can
  ask again. This is almost certainly right, and **`_clear_finding_markers` already exists and can
  be reused** — it was written for the bounce path and matches via `requested_needs_item_id`.

**Recommendation: yes, and reuse `_clear_finding_markers`.** A draft is unsent by definition, so
nothing was ever asked of anybody; leaving the file claiming otherwise is the worse failure.

Soft delete, per house convention — `deleted_at`, not a row removal. No confirmation dialog on an
unsent draft with no edits; **confirm only when `body_edited` is true**, because that is the one
case where a processor's own words are lost.

## §4 — HTML tags visible in a message. NOT REPRODUCED — needs one example.

> *"Also in message it shows html tag."*

**I could not pin this from the code, and the ticket should not pretend otherwise.** The rendering
path that most obviously could do it is, in fact, correct. `message-dialog.tsx:565-573`:

```tsx
dangerouslySetInnerHTML={{
  __html: data.body_format === "html" ? data.body : emailBodyToHtml(data.body),
}}
```

That is the right branch, and `emailBodyToHtml` escapes every tag-opening character before emitting
its own, so a plain body cannot leak markup through it.

**Two candidate mechanisms, both worth checking against a real row before writing any code:**

1. **A body whose stored `body_format` disagrees with its content.** `body_format` is written in
   exactly two places — `email_draft.py:1111` forces `PLAIN` on regenerate, and `:1746` sets `HTML`
   on save. A body containing real HTML but stamped `PLAIN` would be escaped by `emailBodyToHtml`
   and the tags would appear on screen, which is precisely the reported symptom. The regenerate path
   at `:1111` is the one that rewrites a body and stamps the column in the same statement, so it is
   the first place to look.
2. **A surface that renders a body as text rather than through the branch above.** The detail
   surface is correct; the timeline row, the polish proposal block (`:510`) and any preview are the
   ones to re-check.

**Before building:** get from the reporter **which screen, which draft, and one line of the text as
it appeared**. Then query that row's `body_format` and the first 200 characters of `body` on
staging. That single row answers which of the two it is, and they need different fixes.

**Done when:** the mechanism is named with a row id, and no surface on this tab renders a stored
body as anything other than the branch at `message-dialog.tsx:565`.

## §5 — "Polish is not available on this environment" is NOT a bug.

> *"After clicking polish it says Polish is not available on this environment — your message is
> unchanged."*

**Working as designed and as documented.** `core/config.py:275`:

```python
email_draft_enabled: bool = False
```

`ai/polish.py:149`:

```python
if not settings.email_draft_enabled:
    return PolishOutcome(text=None, refusal="unavailable")
```

and the module's own docstring, verbatim:

> *"IT FAILS VISIBLY OR NOT AT ALL. `email_draft_enabled` is off in every environment today, so the
> ordinary outcome is a refusal a processor can read. It never returns something subtly different
> and calls it polish: a silent degradation is worse than an error here."*

This follows the house convention — `need_prose_enabled` and `finding_prose_enabled` also default
to `False`, because a bad prompt degrades a whole queue rather than one row.

**So the question is not "fix the bug", it is "turn the flag on, deliberately, somewhere."** That
needs a decision this ticket does not make:

- Turning it on spends Bedrock tokens on every polish press and puts model-written prose in front of
  a borrower — the reason the flag exists.
- The guards are already built: `refusal_for` blocks an invented date, amount or document, and the
  regulatory floor is imported from `email_draft` rather than restated.
- **Recommendation:** enable it in **staging only**, leave production off, and have Priya press it on
  ten real drafts before it goes further. That is what the flag is for.

**A genuine defect adjacent to it, worth fixing in this ticket:** the refusal reads *"not available
on this environment"*, which tells a processor nothing they can act on and sounds like breakage. If
the answer is "this is switched off deliberately", say that — and if a processor cannot switch it
on, do not show them a button that can only refuse. **Either hide ✦ polish when
`email_draft_enabled` is false, or word the refusal as a state rather than a failure.** Hiding is
the more honest of the two and matches the page's own stated principle at
`communication/page.tsx:20-24` — *"a processor cannot tell a feature that is broken from one that
was never wired."* That principle was applied to the receiving panels and not to this button.

## Decided 2026-09-13 — all three answered

2. **"No detail" means no modification at all** — To, Subject and body all as the pane opened. A

3. **Delete does NOT un-request.** *"Keep it simple."* Needs items and `details.docs_requested` are

**Two deletes, not one:** a processor deleting any draft is a **soft** delete (`deleted_at`, row
kept). A composed draft closed without a single modification is a **hard** delete — the row is
removed, because it never held anything.

# Commit 1 — §1, the mail-client picker

## What was wrong

`message-dialog.tsx:376` read `open={open && !needsClient}`. On the first editable draft of a
session, before any preference was saved, `needsClient` was true — so the picker opened **and the
draft was suppressed entirely**, not merely covered. A processor who clicked a draft was asked which
mail client they use about a message they had not read.

## What changed

- **`needsClient` is a capability question now, not a trigger.** It is read by `copyAndOpen` and by
  nothing else. The `data?.is_editable === true` condition came off it: the only caller is the
  handler behind a button that renders inside the editable branch, so a condition for it there is
  one no mutation could find — the same decoration LP-857 removed from `needsAnAddress`.
- **`askedThisSession` is gone**, replaced by `pickerOpen`. The old flag existed to stop a
  mount-driven picker reappearing; a button-driven one has nothing to suppress. A processor who
  reaches the question and answers it has answered it (the dialog cannot be dismissed — "Not now"
  stores `mailto`), and one who never presses the button is never asked.
- **Answering completes the original action in the same gesture.** `onChoose` calls
  `copyAndOpen(client)` with the answer **passed in**, not read back from state — `setChosenClient`
  has not re-rendered when the callback runs, so reading state there would open `mailto:` for a
  processor who just said Gmail. That is the same defect the LP-855 review fixed one layer up.
- **§10's literal strings** applied to the picker: *"Which mail app should this open?"* and
  *"Asked once. You can change it in preferences."*

## Tests

Both names §9 requires, plus one the contract implies and nothing covered:

- `opening a draft does not ask which mail client` — asserts the question is absent **and** the
  draft is on screen. The absence alone also passes on a dialog that rendered nothing.
- `Copy & open asks once, then completes the action` — no window before the press; the question on
  the press; the window on the answer, at `mail.google.com` rather than `mailto:`.
- `Copy message and Mark as sent never raise it` — §5 names four things that must not trigger it.
  Mount and open are covered above; these are the two buttons sharing the row with the one that
  does, which is where a broad trigger would hide.

## Mutation results

| Mutant | Caught by |
|---|---|
| picker reopened on mount (`open={pickerOpen \|\| needsClient}`) | 6 tests |
| `void copyAndOpen(client)` removed from `onChoose` | 2 tests |
| `chosen ?? activeClient` → `activeClient` (stale read) | 2 tests |
| draft suppressed behind the picker again | **initially survived** |

The last one is the finding. §5 says *"the draft stays visible behind the dialog"*, and nothing
asserted it — every test passed with the message unmounted. It is asserted by **text** rather than
by role, deliberately: Radix marks the pane behind the topmost modal `aria-hidden`, which is correct
for something that cannot be interacted with, and a role query would fail on a draft that is on
screen and perfectly readable.

## Noted, and resolved by commit 3

While the picker is up, **two Radix modals are open at once** — the transient state LP-855's
z-order comment is about. The picker renders last, so it is topmost and reachable, which is the
half that matters; the draft behind it is `aria-hidden`, which is ordinary modal behaviour. This
disappears entirely in commit 3, when the draft stops being a `Dialog` and becomes a pane. It is
not re-solved here, because commit 3 removes the second modal rather than ordering it.
