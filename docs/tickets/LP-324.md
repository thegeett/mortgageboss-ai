# LP-324 — Generalize the rule engine: rules become SPECS run by GENERIC evaluators

## Why

LP-323-ID-A's gate found the wave BLOCKED. AS-1 and OC-2 were per-rule Python
modules (`as1.py` decision tree, `oc2.py` judgment flow) dispatched by two
hardcoded calls in the orchestrator, and `RuleSpec`/`ReferenceValues` were
AS-1-shaped — a `large_deposit_threshold` field and a PROSE `subject_enumeration`.
A spec literally could not express a second rule. This is the deferred LP-308 debt
coming due: authoring the remaining ~130 rules on that base would fork
`as1.py`/`oc2.py` across the family and defeat the fact-tag architecture's whole
point (§3D). This ticket generalizes the engine so a rule is a SPEC, not code.

## The safety property (the acceptance test)

**AS-1 and OC-2 must produce EXACTLY the same results after the refactor as before**
— same verdicts, confidences, gate routing, provenance, `threshold_used` — but now
driven by their SPECS through generic evaluators, with ZERO per-rule Python. The
equivalence is proven by the existing AS-1/OC-2 suites + the frozen LF-6T3N trace
passing unchanged:

- `tests/verification/rule_engine/test_engine.py` — 8 pass (AS-1 through the generic path)
- `tests/verification/rule_engine/test_as1.py` — 18 pass
- `tests/verification/rule_engine/test_oc2.py` — 15 pass
- eval harness + orchestrator + reconcile suites — pass unchanged
- **Full suite: 1975 passed, 1 xfailed.** ruff clean, mypy clean (271 files).

## What shipped

### 1. A machine-readable spec schema (`app/verification/rules/specs.py`)

- `RuleSpec` gains an evaluation body: `deterministic: DeterministicEval | None`
  (calculative/structural) or `judgment: JudgmentEval | None` (judgmental). A
  `model_validator` forbids both at once; `_check_evaluation_body` (called after the
  CSV consistency check, so a kind↔CSV mismatch still raises `RuleSpecInconsistent`)
  requires the block matching the rule's kind. `out_of_scope` carries neither.
- `subject_enumeration` is now an EXECUTABLE key (`per_deposit` / `loan`), resolved
  by the enumerator registry — no longer prose.
- `ReferenceValues` gains a generically-keyed `values: dict[str, str]` mapping and a
  `guideline_text` authority slot; the old `large_deposit_threshold` prose is kept
  but optional (nothing reads it in the evaluators).
- `DeterministicEval`: `load_bearing_tags`, `gated_tags`, an optional tag
  `applicability` (`TagCondition`), `operands: dict[str, Operand]`, ordered
  `outcomes`, `confidence_floor`. `Operand` is a tagged union (tag / reference /
  calc `(section, key)` / product) with an `_exactly_one_source` validator.
  `OutcomeRule` = a verdict + a guard (`when_tags` predicates + an optional declared
  `Comparison`) or `default`, plus `reasoning`/`how_to_fix`.
- `JudgmentEval`: `subject`, `load_bearing_tags`, `reasoned_over`, `output_tag`,
  `value_domain`, `system_prompt`, `confidence_floor`.

### 2. The generic deterministic evaluator (`rule_engine/deterministic.py`)

`evaluate_deterministic_rule(spec, snapshot, *, confidence_floor=None)` runs ANY
deterministic rule. Per subject: applicability (absent/unknown → couldnt_check;
mismatch → not_applicable) → the **reused** `evaluate_gate` over `gated_tags` →
resolve operands (any None → couldnt_check, never a fabricated number) → the ordered
outcomes, first match wins, the fire condition run through the **reused** `satisfies`.
`threshold_used` = the resolved `threshold` operand. No `direction ==` anywhere.

### 3. The generic judgment evaluator (`rule_engine/judgment.py`)

`evaluate_judgment_rule(spec, snapshot, *, reasoner=None, confidence_floor=None)`
runs ANY judgment rule. Fail-closed gate over `load_bearing_tags` BEFORE any AI call
(couldnt_check / needs_review short-circuit, no AI, no tag) → reason over the declared
TAGS (never raw docs) → AI transport/truncation failures → couldnt_check → resolve
(malformed/off-domain → honest `unknown`, drop confidence) → emit the `rule_judgment`
tag → ALWAYS needs_review + `ratification_pending` (LP-319 armor, reused). The AI
machinery is `app/ai/rule_judgment.py` — LP-313/314's OC-2 judge generalized to
`reason_rule_judgment(system_prompt, context_json)`.

### 4. The rule registry + generic dispatch (`rule_engine/registry.py`)

`ACTIVE_RULE_IDS = ("AS-1", "OC-2")`; `evaluate_rules(snapshot, *, judgment_reasoners,
confidence_floor, rule_ids)` dispatches the set BY KIND (deterministic /
judgmental / out_of_scope) and returns `(list[RuleEvaluation], dict[str, Tag])`. The
orchestrator's two hardcoded calls in `services/verification_run.py` are replaced by
this one loop. Adding a rule is a spec + a registry line + its tags — never new
evaluation Python.

### 5. AS-1 + OC-2 re-expressed as DATA

- `specs/AS-1.yaml` — the `deterministic` block; `reference_values.values`
  (`large_deposit_threshold_pct: "50%"`) + `guideline_text`; `spec_version: 2`.
- `specs/OC-2.yaml` (new) — the `judgment` block; the OC-2 underwriter prompt copied
  verbatim; `value_domain: ["yes", "no", "unknown"]` (quoted — bare `yes`/`no` parse
  as booleans in YAML); `spec_version: 1`.
- `as1.py` / `oc2.py` keep ONLY spec-derived identifiers + thin
  `evaluate_as1_rule` / `evaluate_oc2` wrappers (same signatures, so the eval harness
  and orchestrator are untouched). Their former decision-tree / flow code is deleted.
- `ai/occupancy_judgment.py` is now a thin shim over `rule_judgment.py`
  (`OccupancyJudgment = RuleJudgment`, etc.) for backward compat.

## Assumptions & decisions

- **Prose → executable subject_enumeration.** The old prose string became a key into
  an enumerator registry (`enumerators.py`): `per_deposit` (all transactions),
  `loan` (the single LOAN_SUBJECT). Adding a subject shape is one registry entry.
- **AS-1's threshold as data.** `threshold = multiplier × qualifying_income` became a
  `product` operand of a `reference` (the multiplier) and a `calc`
  (`(calculations_section, qualifying_income)`). The calc operand HONORS the LP-318
  gated flag — a gated calculator resolves to None → couldnt_check, never a stale
  number.
- **LP-314a generalized — NO schema gap.** AS-1's self_asserted → needs_review nudge,
  including its GE-vs-GT boundary vs the plain fired outcome, is expressible as DATA:
  an earlier ordered `OutcomeRule` whose guard is
  `has_source == yes ∧ source_strength == self_asserted ∧ observed ≥ threshold` with
  its own `when_compare`. First-match-wins ordering does the rest. No
  `if rule_id == "AS-1"` was needed anywhere — the escape-hatch that would have been a
  schema gap does not exist.
- **Equivalence via wrappers + aliases.** `evaluate_as1_rule`/`evaluate_oc2` keep
  their signatures; `OccupancyJudgment`/`Oc2Evaluation` are type aliases. This kept
  test churn to two touched assertions (the judgment context key generalized
  `occupancy_tags` → `tags`; the projection count `1 → 2` specs).
- **Schema gaps found:** none. Both rules re-expressed cleanly as data.

## Tests

`test_generic_evaluators.py` (new) proves the GENERALIZATION beyond equivalence:
`test_a_new_deterministic_rule_runs_from_a_spec_only` validates a synthetic SYNTH-1
structural rule (a shape AS-1 lacks — pure tag-compare, no operands, loan subject)
and asserts fired / satisfied / couldnt_check with ZERO new Python;
`test_registry_dispatches_the_active_rule_set_by_kind` proves the registry runs the
set by kind from specs.
