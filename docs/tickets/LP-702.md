# LP-702 — list-valued extracted fields render as `[object Object]`

- **Ticket:** LP-702
- **Status:** Done (2026-09-06). Root cause found on staging, blast radius re-measured against the extraction contracts and found to be four times larger.
- **Date:** 2026-09-06
- **Reported by:** the user, from staging (`LF-JR4T`)
- **Scope:** Frontend — `lib/loan-files/documents.ts`, the reviewer fields pane, the document drawer

## The report

> Some of the extracted values show `[object Object],[object Object],…`. Look at LF-JR4T in
> staging — paystub and HOA statement extraction. Make sure we display a value on the
> extraction field **for all documents in general**.

## The cause

**The typed core contains nested LIST fields, and the display layer stringifies them.**

`extractionFields()` reads each entry through `readTypedField()`, which is deliberately
tolerant of a bare value:

```ts
if (entry && typeof entry === "object" && "value" in entry) { … }
return { value: entry ?? null, source: null, confidence: null };   // tolerant: a bare value
```

A list field is stored as a plain array — `earnings_lines: [ {...}, {...} ]` — with no
`value` key, so it takes that second branch. `displayValue()` then does `String(value)`,
and an array of objects becomes `[object Object],[object Object],…`.

`extractionFields` skips exactly two keys — `additional_sections` and `transactions` — and
every other list field falls straight through.

## It is not a data problem

Checked on staging before assuming:

- **No typed-core field anywhere** has an `{value: <array|object>}` shape — 0 rows.
- **No catch-all field value** is anything but a string or null — 651 strings on lease
  agreements, 288 on bank statements, and so on.
- **The literal `[object Object]` is nowhere in `extracted_data`** — the corruption does not
  exist in the database.

It is produced at render time, every time, from correct data.

## Blast radius — 17 document types, not two

Distinct list-valued keys in current extractions on staging:

| document type | keys |
|---|---|
| bank_statement | `transactions`*, `additional_accounts` |
| mortgage_statement | `transaction_activity` |
| w2 | `box_12_items` |
| pay_stub | `earnings_lines`, `deduction_lines` |
| homeowners_insurance | `coverage_lines`, `forms_and_endorsements` |
| property_tax_bill | `installments_and_due_dates`, `jurisdiction_breakdown` |
| **hoa_statement** | **`payment_ledger`, `special_assessment_items`** |
| purchase_agreement | `contingencies`, `addenda` |
| tax_return | `schedule_c`, `schedule_e`, `w2_forms`, `k1s`, `capital_gains_transactions` |

| survey | `encroachments_or_overlaps` |

\* the one key already special-cased.

Both keys the user named are here: `hoa_statement.payment_ledger` and the pay stub's
`earnings_lines` / `deduction_lines`.

## The fix, and the shape of it

**Detect the shape, do not extend the exclusion list.** Two hardcoded key names is how this
bug exists; a third would be the same bug with one more name in it. `readTypedField` should
recognise a list-valued entry as its own kind, and the field row should render it as rows —
the way `transactions` already is — with the count visible and the rows reachable.

Non-negotiable, from the report: **a field must never display `[object Object]`.** If a
shape is not one this build understands, the row says so honestly rather than
stringifying it.

Note `tax_return.schedule_e` arrives as JSON `null` on 4 documents — the renderer has to
handle an absent list as well as an empty one.

## The blast radius was four times larger than staging showed

The 17 types above are the types with a document ON STAGING. The question the table
answers is "where has this been seen", not "where can it happen". The second question is
answered by the extraction contracts themselves — the JSON shape at the end of each
`app/ai/prompts/extraction/*.txt`, which is what the model is told to return:

| | types | list keys |
|---|---|---|
| seen on staging | 17 | 21 |
| **declared in the contracts** | **67** | **78** |

Fifty types could produce the bug and had no document to prove it. That is the reason the
test reads the contracts rather than a fixture: a list key added to a prompt is covered the
day it is written.

## What was built

**`readTypedField` no longer decides alone.** A new `shapeOf` classifies the unwrapped
value as `scalar`, `list` or `record`, and `ExtractionField` carries `kind`, `columns` and
`rows` alongside `value`. The kind is derived from the value; no key names are consulted.

**`leafDisplay` is the single guarantee.** It never returns `[object Object]` — an array
becomes a count, a nested object becomes its own first few entries on one line
(`Charge: 450 · Paid: 0`), and anything deeper degrades to a count rather than being handed
to `String()`.

**`extractionTransactions` and its private `TransactionsTable` are gone.** One
`ExtractionTable` renders every list, transactions included. Keeping the private one would
have been the same bug with better manners.

**Columns are the union of the rows' keys**, not the first row's: an HOA ledger whose first
row has no `paid` would otherwise drop the payment half of the ledger for every row after
it. `page`, `snippet` and `source` sort to the end — every contract carries them, and they
say where a value was read, not what it is.

**Nested cells mask through `catchAllDisplay`.** A `tradelines[].account_number` is keyed by
a name the MODEL chose, so `field_scrutiny` never reports on it and the backend's identity
list cannot reach it. The label+value test can, and it excludes money first so a running
balance is not hidden for having digits in it.

**A field the backend calls an identifier is never expanded**, whatever shape it arrives in
— a masked list would leak through its rows. It renders as bullets.

**List fields are out of the keyboard review queue.** Accept, correct and reject each name
one value; a table has none. Editing rows is LP-703's subject.

### Two deliberate losses

- **The transactions table's green/neutral direction tint is gone.** It keyed off
  `transaction_type`, which only bank statements have. A generic renderer that special-cased
  one type's column would be the thing this ticket removed.
- **Table cells are shown as extracted — no currency formatting.** `1234.56` renders as
  `1234.56`, not `$1,234.56`. The panel's claim is "here is what the model read", and a
  figure the component reformatted is one a processor cannot compare against the page.
  Scalars keep their existing `MONEY_KEYS` formatting.

## Verification

- 137 tests in `lib/loan-files/extraction-contracts.test.tsx` render one document of every
  contract type through `ExtractionView` and assert on the DOM text — the helper could be
  right and a component could still hand an object to React.
- A positive control asserts the contract parser found at least 60 types and 70 keys. Without
  it a parser that matched nothing would make every other assertion pass over an empty list.
- Three isolated mutations, each reverted after: stringifying nested objects failed 68 tests,
  stringifying list fields failed 135, reading columns off the first row alone failed 1.
- Checked in the running app against real local extractions — a pay stub (11 deduction
  lines), a credit report (18 tradelines), a bank statement (35 transactions) — in light and
  dark. No `[object Object]` on any of them.

Unrelated finding while verifying: the local dev database was nine migrations behind, which
made every `/documents` request 500. `alembic upgrade head` fixed it. Nothing to do with
this change, but it is why the first screenshots showed an empty file.

## Acceptance

- [x] No field in any document type renders `[object Object]`, enforced by a test that scans
      rendered output rather than checking the two known keys
- [x] List fields render as rows with their count, `transactions` included — one code path,

- [x] A shape the build does not recognise degrades to an honest sentence, never a stringified
