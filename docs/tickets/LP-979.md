# LP-979 — Five ways the plan screen now matches the mock

- **Ticket:** LP-979 (the owner, 2026-10-10: "keep option 1, go ahead with LP-979"), after comparing the
  mock with the built screen on 1228.
- **Status:** built.
- **Out of scope:** the route choices and condition-specific step wording (LP-970).
- **Kept as is** (the owner's option 1): the edit links stay once per task, on its first step. The app
  keeps them per task, not per step, so on every step they would all do the same thing.

## What changed

1. **"Next:" is a person's step, not the app's** (`plan-path.nextOf`). The mock says "Next: Review and
   send the email to UWM". The built row said "Next: We check what you upload" because a document was
   already linked and its check came first.
   - The app's own steps are now passed over for the first step someone takes: hers, or the person or
     lender she is waiting on. "Title / escrow sends it back" is the honest next thing while an ask is
     out.
   - Only when every step ahead is the app's does one show.
   - On 1228 this gives "Review the email, and send it once the plan is confirmed".
2. **The app's steps say what kind of step they are:**
   - "We prepare it" for what it drafts or puts in the package;
   - "We check it" for a check;
   - "We found it" for what it found on the file;
   - "Nothing to do" for an information line. They all said "We" before; the mock and the legend say
     "We prepare or check it".
3. **The ending names the lender and the condition:** "…goes in the package for UWM", then "UWM clears
   1228", with UWM as the step's label. The panel reads the file's lender (`useFileLender`) and passes it
   through `PathContext.lenderName`. With no lender on the file, the words stay "the lender" and "it".
4. **"Or describe what you want to do" is always there** under "Add a step", as in the mock. It hides only
   while one block's own form is open, so two ways to add are never half-filled at once.
   **This also fixes an LP-971 bug the peer found.** The LP-971 review kept her words when "Describe
   it" turned them into a question, because the note holds them nowhere. But the box sat inside the
   opened menu, and adding closed the menu, so the box unmounted and the words went with it. The review's
   test rendered the box on its own, which never unmounts, so it could not see this. Now the box stays
   mounted after adding, and the words with it. A test through `AddStep` pins it: it opens the menu as
   she would, adds a question, and checks the words are still there. With the box nested back inside the
   menu, it fails on that last check.
5. **"Changed by you · Go back to the suggested plan" shows only once she has changed the plan.** It was
   always shown, with nothing to undo on a plan as suggested.
   - **The flag:** `ConditionPublic.plan_changed`, from `condition_plan.plans_changed_for_file`, one
     history query per file.
   - **The rule:** a `condition_plan_changed` of hers after the condition's latest reset. The resets are
     "Go back to the suggested plan" (`reverted`) and Read again (`read_again`).
   - **The wiring:** `_condition_public` takes `plans_changed` as a REQUIRED keyword, as it does
     `lender_keys`, so no door can answer "never" by leaving it off.
   - **After a revert:** steps she added herself survive (`revert_to_suggested` leaves them), so the link
     correctly hides; there is nothing more for it to put back.

### "Changed by you" appeared on a plan the CODE carried (fixed)

`plans_changed_for_file` counts every `condition_plan_changed` except `reverted` and `read_again`. A
census of the writers — nine of them — found one more value that is not hers and one that is:

- **`carried`** (`carry_plan`, from `condition_compare` when she accepts a rewording) copies a replaced
  condition's whole plan to its successor. Measured: the successor, which she has never edited, came
  back from `plans_changed_for_file` as changed, so the row offered "Changed by you · Go back to the
  suggested plan" — a link to undo an edit that does not exist, on a plan whose own `plan_reason` says
  "Carried from the condition it replaced". A revert there replays the first recorded `from` of each
  field, of which there is none.
- **`item_added` with `why: "evidence"`** (`condition_evidence._add_ask`) stays hers on purpose: it is
  written while SHE answers a finding, so the plan does differ from the suggestion because of something
  she did.

So `carried` joins `_BASELINE_CHANGES`: the carried plan IS the suggestion for that condition, exactly as
a revert or a fresh reading is. Pinned both ways — removing `carried` from the set fails the new test, and
making every change a baseline fails two of the ticket's own.

### The other three questions

1. **A reset and a change tied in one transaction.** Unreachable today, checked writer by writer: the
   three baseline writers each write ONE event and nothing else of this kind in their transaction —
   `revert_to_suggested` writes only its `reverted` summary (its per-item work writes no events),
   `clear_for_reading` writes one `read_again` per condition, and `carry_plan` writes one `carried`
   whose caller (`condition_compare`) writes no plan changes of its own. `own_way`'s several events are
   all departures, so their order among themselves cannot matter. If a door ever writes both, `(occurred_at,
   id)` with uuid ids would decide it arbitrarily — the ticket is the right place for that to be written
   down, which it now is.
2. **Which `change` values are hers.** The finding above.
3. **Can "The lender clears it" be Next while she still has something to do?** No. `nextOf` scans in
   order and takes the first step whose `who` is not `we`, and every task's own steps precede the ending
   in `conditionPath`, so a `you`/`them` step that is still ahead always wins. The ticket's own test
   holds both halves: a `requested` item ahead gives "Title / escrow sends it back", and with every task
   finished the ending's lender step is what comes next. The only case where the lender's step wins over
   OUR work is when the sole remaining step is a `we` one — which is this ticket's stated intent, that the
   app's own work is not someone's next move.
4. **Anything else reading `whoLabel === "We"`.** Nothing reads it as a value at all: outside
   `plan-path.ts` the only consumer is `round-plan-panel.tsx`'s `{dropped ? "You" : step.whoLabel}`,
   which renders it. Code that branches uses `who`, not the label, so the four new labels are
   display-only and cannot change a decision.
