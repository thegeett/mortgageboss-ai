# LP-831 — The Communication page becomes a mailbox

- **Ticket:** LP-831 · Phase 4 follow-up, from processor feedback
- **Status:** Built — awaiting review
- **Date:** 2026-09-07
- **Scope:** `app/(protected)/loan-files/[id]/communication/page.tsx`, a drafts list, a draft modal,
  `api/communications.py`
- **Migration:** none expected

---

## What was asked

> *"Communication page should show list of draft, it should not show email draft on page, on clicking
> on the draft new model opens where it should show document request section, with send to, subject,
> message buttons. User should able to edit message draft there. Basically, communication page should
> look like and email webpage, like gmail page."*

## Why this is more than a rearrangement

The page renders five stacked panels, and one of them — `OutboundDraftPanel` — is a full compose form
sitting open at all times. That works while a file has exactly one draft. **It stops working the
moment it has two**, which LP-832 makes the ordinary case.

It has already stopped working once. LP-829's review found that `build_timeline` selects every
`Communication` on the file, so a **party draft** (title, agent, lender, CPA, insurer, employer —
LP-820) is on the timeline and clickable, while `get_open_draft` filters on the borrower template and
therefore never returns it. The party panel's own success message says *"Send it from the document
request above"*, and the draft above is the **borrower's**. A processor who follows that instruction
mails the borrower believing they contacted the title company.

**A list of drafts is what fixes that**, not as a side effect: every draft becomes reachable and
sendable because the list has no template filter to be wrong about.

## The shape

A mailbox, in the sense a processor already understands: **a list, and one thing open at a time.**

- The page leads with the drafts list — subject, who it is for, how many documents, when it was last
  changed. Sent messages join the same list once there are any, which is what makes it a mailbox
  rather than a drafts screen with a list in it.
- Clicking a row opens a modal: **Send to**, **Subject**, **Message**, editable, with the actions on
  it. That is the document request section, and it is the only editor.
- `OutboundDraftPanel` stops being a page-level panel. Its content becomes the modal's body.

**LP-829's read-only dialog and this editor are the same surface for different rows.** A sent message
cannot be edited (LP-821's evidence record must not change) and an inbound one is not ours to
rewrite; a draft can. The modal decides from the row, and there must be exactly one component
deciding it — two dialogs that look alike is how a sent message acquires a save button.

## Done when

- The Communication page shows a list of the file's drafts and no open compose form.
- A **party draft is in that list and can be sent from it.** This is the escalated LP-820 defect, and
  it closes here or the list is decoration.
- Clicking a draft opens one modal carrying Send to, Subject and Message, all editable, with the
  send action. Clicking a **sent or received** message opens the same modal read-only.
- The modal is the only place a draft is edited. A test asserts a sent message has no editable field
  and no save control, because "it does not today" and "it must not" are different claims.
- LP-823's resolution applies: no `$borrower_first_name` or `$processor_name` in anything rendered.
  Three tickets have now put that defect back in a new place; this is a fourth surface.
- The empty state is honest. A file with no drafts says so, and does not render a compose form for a
  draft that does not exist.
- Keyboard: the row opens on Enter, the modal traps focus, Escape closes it, focus returns to the row.

## For the reviewer

The trap is building a second dialog. LP-829 already has one, and a draft-shaped copy of it beside a
message-shaped one will drift — the day someone adds a field to the read-only view and not to the
editor is the day a processor cannot see what they are about to send.

## Built, 2026-09-09

### The list already existed

The page carried five panels, one of which — `TimelinePanel` — is already every message on the file,
with filter pills including **Drafts**, and since LP-829 every row opens a modal. LP-825 made it
messages-only. **That is the mailbox**, and building a second list beside it would have been two
lists disagreeing about what a file contains.

So this ticket is three moves, not a rewrite:

* the list leads the page;
* `OutboundDraftPanel` — a compose form open at all times — is **off the page**. It works while a
  file has one draft, and LP-832 makes several the ordinary state;
* LP-829's dialog becomes the editor.

### The read-only argument was right and its premise is gone

LP-829 made the dialog a reader because `OutboundDraftPanel` already owned editing on the same page,
and two components holding separate local state for one body means whichever saves last wins with
nothing on screen to say so. **The rule stands and its application moves**: exactly one editor, and
it is now the dialog, because the panel it was deferring to no longer exists.

What stays read-only is not a limitation: a **sent** message because LP-821's evidence record must
not change, an **inbound** one because a borrower's words are not ours to rewrite.

### `is_editable` is not `is_open_draft`, and that is the escalated defect closing

`is_open_draft` requires the **borrower's** template key. A party request is a draft under its own
key, `get_open_draft` filters on the borrower's, and the party panel's success message says *"Send it
from the document request above"* — where the draft above is the borrower's. **A processor following
that instruction mailed the borrower believing they had contacted the title company.**

`send_draft` takes a draft id and has never cared which template rendered it. The missing piece was
always a screen. So `is_editable` is the wider predicate — outbound and DRAFT — computed on the
server, so the screen and the send path cannot disagree about what may be edited.

A party draft also keeps **its own address**: suggesting the borrower's there would put a title
company's document request in the borrower's inbox, which is the same wrong mailbox by a shorter
route.

### The subject became sendable, with the asymmetry stated

The modal offers Send to, Subject and Message; the send endpoint took recipient and body. `subject`
is now optional on the request, and `body` is still required — **the asymmetry is deliberate.** A
defaulted body would let a stale draft be recorded as sent while the processor had edited it, which
is a false evidence row. A subject has no such gap: omitting it means "the one already on the draft",
which is a complete and true answer, and a test asserts that is what gets recorded.

### The deep link, built now rather than retrofitted

`?draft=<id>` opens the modal on arrival. LP-837's header popover navigates here and expects it open;
landing on the list with it shut looks exactly like a mis-click, which is how that feature would fail
quietly. Building it here also makes a draft something a processor can link a colleague to.

Two details that are not obvious: the parameter is tracked separately from the dialog's open state,
or **closing the linked message would re-open it on the next render** and the dialog could not be
dismissed. And `useSearchParams()` is read optionally, because it is null outside a router context —
not only in tests, but during a static render.

### A test of mine passed alone and failed in the suite

`mockSend` accumulated across cases, so the party-draft test read the call the borrower-draft test
had made a moment earlier. It passed in isolation and failed in the run — **the wrong way round for
a test to be wrong**, and the only reason it surfaced is that the full suite ran. `beforeEach`
clears them now.

### Mutations

### Not done here, and stated so it stays a decision

The secure-link and party panels are still separate panels below the list. **LP-834 and LP-835 fold
them in.** Until then the page is a mailbox with two attachments to it rather than one surface, which
is honest about what is built rather than a half-finished Gmail.

### The three standing checks

**Tenancy:** the modal reads through `GET /messages/{id}`, which is `ScopedLoanFile`-gated and checks
`loan_file_id` on the row; the send is unchanged and still resolves the draft against the file.
**Logging:** nothing added — no subject, body or address reaches a log line. **AI:** none.
