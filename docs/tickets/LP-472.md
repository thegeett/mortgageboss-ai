# LP-472 — One shared identity schema for passport / permanent_resident_card / work_visa_ead_card / government_issued_id

**Principle (Geet):** *classify precisely, extract in common* — the four stay distinct
in the catalog + classifier (ID-8 needs citizenship vs. work-auth-with-expiry), but they
should share ONE identity field set so a within-family misread still yields the same
name / DOB / number / expiry. `drivers_license` is NOT in scope (keeps spec 014 + its tuned extractor).

---

## Phase A — findings (STOP-and-report)

### A0. The ticket premise is wrong — only ONE of the four lacks an extractor

The ticket says all four "classify correctly and have NO extractor." The code says otherwise:

| type | tier | extractor today | spec today |
|---|---|---|---|
| `passport` | **Tier-2** | **none** ← the only genuine gap | none |
| `permanent_resident_card` | Tier-1 | `extract_permanent_resident_card` | 038-resident-alien-card |
| `work_visa_ead_card` | Tier-1 | `extract_work_visa_ead_card` | 108-work-visa-ead-card |
| `government_issued_id` | Tier-1 | `extract_government_issued_id` | 071-government-issued-id |

So three of the four already have **separate generated extractors with drifting field names** for the
same facts — the exact drift this ticket wants to prevent, already present:

| fact | 038 (PRC) | 071 (gov_id) | 108 (EAD) |
|---|---|---|---|
| name | `full_name` | `full_legal_name` | `full_name` |
| number | `card_number` / `uscis_number_or_a_number` | `document_number` | `document_or_card_number` / `uscis_or_a_number` |
| expiry | `card_expiration_date` | `expiration_date` | `expiration_or_admit_until_date` |
| issue | `card_issue_or_revision_date` | `issue_date` | *(valid_from_date)* |
| birth | `country_of_birth` | `place_of_birth` + `nationality_or_citizenship` | `country_of_birth_or_citizenship` |
| category | *(n/a)* | *(n/a)* | `visa_or_ead_category` |

**Consequence:** "one shared identity schema for all four" is not "add 4 extractors" — it is **add passport +
consolidate the 3 existing drifting ones onto the shared core.** That is bigger than the ticket assumed, so
the scope decision is Geet's (see A2). A verdict-safety check clears the risk: **no active rule reads any of
these field names** (grep of `app/verification/rules/` for the four types + their fields = empty; ID-1/ID-3/ID-8
are visibility-only today, ADR-362/363). Renaming/consolidating the family **cannot move a verdict.**

### A1. Real documents — the printed field set (ground truth)

Read: **264** Indian passport (Jagadeesan), **265** EAD (Poojitha Ale — *readable*), **266** EAD (rotated
CamScanner scan — the LP-468 unreadable case), **219** green card (Sabbineni), **221** green card (Gupta —
filename `GC_Sivaji` is mislabelled). **No plain state-ID sample exists in this batch** — both "GC" files are
PRCs — so `government_issued_id` keeps its generic superset (071) as the source for its extras.

Common core present on **every** identity doc:

- `document_type_as_printed`, `full_name` (+ `surname` / `given_names` where split), `date_of_birth`,
  `document_number`, `expiry_date`, `sex`, `issuing_country_or_state`, `issuing_authority`,
  `place_or_country_of_birth`, `nationality_or_citizenship`, `issue_date`, `residential_address`
  (present on passport back / gov-id; null on PRC/EAD).

Type-specific extras (one-of-four → typed nullable extras, **not** core):

- **passport (264):** place_of_issue (Coimbatore), file_number, prior_passport_number. MRZ present.
- **EAD (265):** `uscis_number` (201-764-302), `category_code` (C26), `valid_from_date` (11/10/23),
  employment terms ("NOT VALID FOR REENTRY"), `receipt_number`, status/class, employer — the rich ID-8 set from 108.
- **PRC (219/221):** `uscis_number` (208-384-911 / 203-552-041), `category_code` (E26 / E18),
  `resident_since_date`. No issue_date, no nationality on the card front.
- **gov_id:** `government_id_type` (state ID vs national ID), residential_address.

Note EAD **and** PRC share `uscis_number` + `category_code`. PRC/EAD/passport all carry an MRZ; a state gov-id does not.

### A2. Sharing mechanism + drift guard — **recommend option (c)**

The invariant `test_tier_1_iff_the_type_has_a_schema_spec` (LP-441) means each of the four **must** have its own
spec file (document_type = its slug) to stay Tier-1. So the spec layer is necessarily four files; the question is
where the single source of truth lives at **runtime**.

- **(a) four generated modules, one canonical core, CI-locked identical** — drift *caught* by a test, ×4 boilerplate.
- **(c) ONE shared runtime module `extract_identity_document`; all four `EXTRACTORS` entries point at it; four thin
  specs (satisfy Tier-1-iff-spec) whose core block is CI-locked identical.** ← **recommended.** Runtime drift is
  **structurally impossible** — the thing that extracts is a single function with a single prompt and a single
  superset model. The four specs exist only to satisfy the invariant + document the field set; a CI test asserts
  their core blocks match so the *documentation* can't drift either. This is the literal realization of
  "classify precisely (4 catalog types + 4 indicators + 4 specs), extract in common (1 module)."

The shared model is a **superset**: common core (~12) + all type extras as typed-nullable (~12). The prompt says
"fill only what is printed on this document; leave the rest null." `drivers_license` is untouched.

### A3. Does `government_issued_id` route here? **Yes.**

It is one of the four; already Tier-1 with an extractor. It joins the shared function; its 071 extras
(`government_id_type`, residential_address) become the gov-id extras block.

### A4. PII — mostly already registered; reuse the registered names

`_PII_FIELDS` already masks `document_number`, `card_number`, `document_or_card_number`, `passport_number`,
`uscis_or_a_number` / `uscis_number_or_a_number`, `receipt_number`, `i94_admission_number`. **Design the shared
core to reuse the already-registered names** (`document_number` for the primary number; `uscis_or_a_number` for
the USCIS#/A-number) → near-zero new PII wiring. `date_of_birth` + `full_name` stay **unmasked** (ID-1/ID-3
match on them; `drivers_license.full_name_raw` precedent).

**MRZ — recommend DROP from the typed core.** It re-encodes name / DOB / number / expiry already captured as
typed fields (redundant), and its contiguous digit run (e.g. `IAUSA2017643029EAC2325250751`) trips the
`_LONG_DIGITS` at-rest guard in `persistence.py` — capturing it would force a `_SCRUB_FREE_TEXT_FIELDS`
registration for zero informational gain. If present it lands in the catch-all, not a typed field.

### A5. 265/266 "swap" — **no swap; nothing to fix.**

Both 265 and 266 are EADs (265 Poojitha = readable; 266 H4EAD = the rotated CamScanner scan LP-468 hallucinated
as a UK passport). There is no passport↔EAD mislabel. 266 remains the **image-preprocessing gap** (ADR-365),
independent of this ticket. Report, don't fix.

### A6. LP-471 interaction

Passport gains a typed extractor → it no longer falls to the Tier-3 free-extraction path (LP-471). For the
**unreadable 266**: a typed identity extractor can *confidently misread* a rotated scan (the confident-coherent
limit, ADR-365); LP-471 only falls back on `FAILED`, not on confident-wrong — so consolidation **does not fix
266**, and a confident-garbage typed read is arguably worse than an honest Tier-3 summary. This is a known,
unfixable-here limit; flagged, not addressed.

### Verdict safety

`ACTIVE_RULE_IDS` unchanged (37). No active rule reads any family field (verified). No verdict may move.

### Phase C cost

Live re-extraction of the 5 family docs (264/265/266/219/221) through the shared extractor ≈ **$0.15–0.30**.
No 303-doc bench run.

## Phase B — build (Geet: full consolidation, option (c) one module, drop MRZ)

**One shared module.** `app/ai/extraction/identity_document.py` — hand-written (no "GENERATED" marker),
mirrors the flat-extractor shape (`property_tax_bill` reference). A **20-field superset** typed core + the
grouped catch-all; `_MAX_TOKENS = 4096` (0 nested lists). Prompt
`app/ai/prompts/extraction/identity_document.txt` — tuned for all four kinds, "fill only what's printed,"
MRZ + passport kin routed to the catch-all.

**Shared field set (20).** `document_type_as_printed, surname, given_names, full_name, date_of_birth,
document_number, uscis_or_a_number, issue_date, expiry_date, valid_from_date, resident_since_date,
category_code, employment_terms_or_restriction, issuing_country_or_state, issuing_authority,
place_or_country_of_birth, nationality_or_citizenship, place_of_issue, government_id_type, residential_address.`
Dropped vs. the old specs: `sex` (108's protected-class rejection wins in a shared schema), MRZ (A4), and the
EAD's I-797/visa-foil fields (not printed on the card). `document_number` + `uscis_or_a_number` reuse the
already-registered `_PII_FIELDS` slots → **zero new PII wiring**.

**Wiring.** `EXTRACTORS`: all four keys (`passport`, `permanent_resident_card`, `work_visa_ead_card`,
`government_issued_id`) → `extract_identity_document`. `passport` promoted Tier-2 → Tier-1 in `catalog.py`.
Deleted: the three old modules (`work_visa_ead_card.py`, `permanent_resident_card.py`,
`government_issued_id.py`) + their prompts + their three unit tests. `drivers_license` untouched.

**Four specs, identical core.** Rewrote `038-resident-alien-card` / `071-government-issued-id` /
`108-work-visa-ead-card` onto the shared core (document_type unchanged); added `121-passport.json`. A generator
script authored all four cores from one constant → byte-identical. Net spec count 120 → 121 (passport added;
the other three rewritten, not added).

**Drift lock (the LP-472 guarantee).** `tests/ai/test_identity_document_extraction.py`:
`test_the_four_specs_share_a_byte_identical_core_matching_the_module` asserts the four specs' typed cores are
identical to each other AND to the module's `_CORE_SPEC`; `test_all_four_types_share_one_extractor` asserts the
four keys resolve to the single function and `drivers_license` does not. Plus the shape/mechanism unit tests.

**Guards updated.** `test_catalog.py` (passport out of the Tier-2 list; spec count 121),
`test_lp439_spec_decisions.py` (`len(_ALL) == 121`). The LP-443 sizing guard skips the family automatically
(no per-type `{dt}.py` module exists after deletion). `emit_pii_registration(108)` still emits `PiiKind.ACCOUNT`
only (verified). `decisions.md` → **ADR-369** (classify-precisely/extract-in-common + the A6 typed-vs-fallback
limit, prominent alongside ADR-368).

Targeted run (identity + catalog + generator + budget suites): **200 passed**. Full suite: see Phase C.

## Phase C — proved live (Bedrock, mbai-dev; ~$0.30 incl. A/B + re-verify)

All five family docs extracted through the ONE shared `extract_identity_document`. `AWS_PROFILE=mbai-dev`
had to be set on the process (the `.env` value isn't exported to boto3; the first run failed with "could not
resolve credentials from session" until set).

**Wins — the goal is met.**
- **264 passport (the one gap):** 12/20, conf 0.92, all correct — full_name THANGAVEL JAGADEESAN, DOB
  1978-11-06, no. Z8043711, issued/expiry 2024→2034, nationality INDIAN, back-page address + MRZ + kin in the
  catch-all. Passport is now typed and reads cleanly.
- **219 / 221 green cards:** correct — GUPTA AMOL (E18, resident-since 2021) and SABBINENI SIVAJI (E26,
  resident-since 2022), DOBs/dates/categories right, conf 0.94 / 0.97. The shared schema nulls the passport/EAD
  extras appropriately (classify precisely, extract in common — confirmed live).
- One module, four kinds, identical fields — consolidation works end to end.

**⚠️ A REGRESSION found and mitigated — the EAD read (A6 made concrete).** On the readable EAD (265) the
first shared-prompt run **hallucinated a name** ("SAMEMMEH SORDITHA") and **mistyped** it PERMANENT RESIDENT /
E26, at conf 0.92. A 1-call A/B against the OLD EAD-specific prompt on the same doc read
`immigration_document_type = EAD (Form I-766)`, `category = C26`, and **`full_name = null`** (honest) — proving
the generic shared prompt caused the regression, not the scan. 266 (the rotated scan) was worse:
`JOHN SMITH, US PASSPORT, Dept of State` — a fully fabricated identity at conf 0.87. This is exactly ADR-369's
A6 limit: a typed extractor returns confident garbage on a bad scan, and LP-471's FAILED-only fallback never
fires.

**Prompt tuning fixed the DANGEROUS half.** Added (a) title-anchoring (EAD I-766/C-code vs. green-card
I-551/E-code) and (b) a hard honest-null rule for illegible names ("never emit John Smith / a guessed
spelling; a null name is correct, a confident wrong name is a serious error"). Re-run: 265 name → **null**
(conf 0.65); 266 → name **null**, "JOHN SMITH" gone (conf 0.72). The fabricated-identity failure mode is
closed; confidence is now honest.

**Residual gap (recorded, not a blocker).** Both Poojitha EAD scans (265 and 266 are two scans of the SAME
card — the A5 "265/266" pairing = same doc, not a swap) still mis-read the **title** (EAD→PERMANENT RESIDENT)
and **category** (C26→E26) under hologram glare on the title band. The shared prompt cannot *pre-declare* the
type (it serves four); the old per-type prompt read it right precisely because it hard-coded "this IS an EAD."
**The real fix is to thread the already-decided CLASSIFIED type into the shared extractor** so it anchors on
what classification determined — but that changes the uniform `(content, media_type)` extractor signature, so
it is a follow-up, not this ticket. No rule reads these fields today, so no verdict is affected. I have no
clean (non-hologram) EAD sample to show the shared prompt reading C26 correctly — only these two obscured
scans; flagged for Priya + a real clean EAD.

Full backend suite: **green** (the two stale `passport`-as-Tier-2 fixtures fixed → `warranty_deed`).
