## The row exists before anyone knows whose it is

`phase4.md` describes `inbound_messages` as **company-owned**. It cannot be, at ingest.

The standing tenancy rule says `company_id` is derived from a resolved loan file in exactly one
place — LP-805's resolver. Ingest would have to become a second one to fill the column, so
**`company_id` and `loan_file_id` are both nullable** and both are filled by routing.

That is a departure from the plan, forced by a rule the plan itself sets. Recorded rather than
resolved quietly.

### Which makes the dedup index the interesting part

`UNIQUE (company_id, ingest_key)` **`NULLS NOT DISTINCT`**.

Postgres treats NULLs as distinct in a unique index by default. Since every message starts with
`company_id` NULL, a plain unique index would never collide two unrouted messages — and the ticket's
acceptance criterion is *"the same message delivered twice produces exactly one row"*. The default
behaviour fails it in precisely the state every message is in.

`NULLS NOT DISTINCT` is declared on the model too (SQLAlchemy 2.0.50 supports
`postgresql_nulls_not_distinct` on `Index`, though not on `UniqueConstraint`), so `create_all` builds
it and a test can violate it. Reverting the flag fails three tests.

**Why the scope is `(company_id, ingest_key)` and not `ingest_key` alone.** The key falls back to the
`Message-ID` header, which the **sender** writes. Globally unique, anyone could suppress another
company's message by forging a collision. Scoped per company, they cannot. The window where that is
not yet closed is the unrouted set, and it is narrow: the key prefers the SES message id, which SES
assigns, so the header fallback is reached only when there is no SES id — which today means the dev
injector.

## Verdicts come from the receipt and nowhere else

`extract_receipt_verdicts` takes the SES **receipt**, never the parsed message. An
`Authentication-Results` header inside a message is written by whoever sent it and can assert its own
DKIM pass.

Every value is copied **verbatim**, including ones this code has never seen. `dmarcVerdict: GRAY`
stays GRAY — the ticket's second criterion. GRAY means SES could not decide, and a routing rule that
reads it as PASS treats "we do not know" as "authenticated".

A message with no receipt stores `{}`, not defaults. A later rule asking "did this pass DMARC?" must
find *nothing* rather than find something that reads as a pass.

## Two message kinds, because getting either wrong files it as a document

`is_dsn` — a bounce is an email, addressed to the file's inbox, usually carrying the original message
as an attachment. Detected on `multipart/report; report-type=delivery-status` **or** an empty
`Return-Path: <>`, which RFC 5321 requires of a notification so it cannot itself bounce. Real bounces
carry one, the other, or both.

`is_auto_reply` — `Auto-Submitted` with any value but `no` (RFC 3834), plus the two `X-` conventions
that predate it and are still what most autoresponders send.

**A test caught a real bug here.** The first version checked the empty `Return-Path` by reusing
`normalise_message_id`. That function strips angle brackets around *content*, and `<>` has none — so
it returned the literal `"<>"`, which is truthy, and **every bounce was missed**. Two headers are not
the same shape just because both are usually bracketed. Now checked explicitly.

## The injector, which is the part to protect (§H1)

`POST /dev/inbound/inject` takes an `.eml` and runs it through the same `ingest_raw_message` the SQS
consumer calls. Everything downstream is testable on a laptop with no AWS at all — without it, LP-804
and LP-805 are written blind and debugged in staging.

`ses_message_id` and `dmarc_verdict` are **form fields**, not derived from the message. That is the
point: the injector must not offer a shortcut the real path does not have. Passing `GRAY` here is how
the GRAY-stays-GRAY behaviour is exercised by hand without waiting for a real message to be graded.

`raw_storage_path` is None — nothing came from S3, so recording a path to an object that does not
exist would be worse than recording none.

Mounted only when `not settings.is_production`, and still auth'd.

## The consumer

`inbound.poll_queue` — a **beat task, not a second daemon**, per the plan. A long-running consumer
would be a new deployable with its own health check, restart policy and scaling story, for work that
is already idempotent and already retried.

**It is not on the beat schedule.** `inbound_queue_url` is None in every environment (INFRA-1 is
written and unapplied), so it would tick and no-op forever — a green tick that means nothing.
Scheduling belongs with the apply that gives it a queue.

`app.tasks.inbound` **is** in `_TASK_MODULES`. A module left out is never imported, the task is never
registered, and every enqueued message is discarded silently — the LP-78 worker-seam bug, which this
module would otherwise have reproduced exactly.

## Tests

`tests/services/test_inbound_ingest_lp803.py`, 20 tests, over four committed `.eml` fixtures (a
plain reply, an out-of-office, a bounce, and one with no `Message-ID`). The first four of §H2's
corpus; LP-804 needs the rest.

Every detector has a control, because a detector that fired on everything would satisfy its positive
test and send every borrower reply down the wrong path. `test_a_normal_return_path_does_not` is the
one that matters most — `Return-Path` is present on nearly every delivered message, and treating its
*presence* rather than its *emptiness* as the signal would flag all of them.

Verified by mutation, each confirmed applied:

| Mutation | Result |
|---|---|
| `NULLS NOT DISTINCT` turned off | 3 fail |
| ingest key stops preferring the SES id | 1 fails |
| every verdict coerced to `PASS` | 2 fail |
| the empty-`Return-Path` check removed | 1 fails |
| the `Auto-Submitted` check removed | 1 fails |
| conflict target narrowed to `ingest_key` alone | 11 fail |

### A guard I disabled with ordinary SQL

The readonly view first counted recipients with `cardinality(ARRAY(SELECT ...))`. Valid SQL, and it
**silently defeated the drift guard**: that check finds a view's select list by taking the last
`SELECT` before the first `FROM`, so a nested one truncated the list and *every* column in the table
read as unexposed. `jsonb_array_length` says the same thing with no subquery.

Worth knowing about beyond this ticket: a guard that ordinary SQL can switch off is one that will be
switched off again. Recorded in the migration rather than worked around quietly.

The view also has **no `has_subject` boolean** — `(subject IS NOT NULL) AS has_subject` *names* the
column, which the never-exposed check matches on text. The boolean goes rather than the guarantee,
the same call as LP-822's dropped exemplar count.

## Deliberately not done

- **No MIME parsing.** LP-804. Nothing here reads a body or an attachment; the raw bytes are stored
  and the headers are read for envelope, threading and kind.
- **No routing.** LP-805, and it is the only place allowed to derive `company_id`.
- **No beat schedule.** See above.
- **No per-company ingestion flag.** §H5 asks for one; it gates *routing and acceptance*, which is
  LP-805/LP-806's, and a flag here would only stop rows being written for mail that has already been
  accepted and stored by SES.
- **No seed data.** §H3, and it wants attachments and routing states that LP-804 and LP-805 define.

## For the reviewer

The three standing reviewer checks:

- **Tenancy** — `company_id` is **not derived anywhere in this diff**. It is left NULL for LP-805.
  This is the ticket where that rule bit hardest, and the nullable columns are the consequence.
- **Message content in logs** — actively load-bearing: this is the first code in Phase 4 to handle a
  real borrower's message. Two log lines, both metadata only — a 12-character key prefix and a byte
  count. No subject, no body, no address, and the S3 key is not logged either, because an SES message
  id identifies one person's mail.
- **AI in the decision path** — none.

The judgement calls worth a second opinion:

1. **Nullable `company_id`**, against the plan's "company-owned". The alternative is ingest resolving
   the inbox token itself, which is a second tenancy derivation and a blocking finding. I think the
   rule wins; if you read the plan as intending ingest to resolve, LP-805's scope changes.
2. **`InboundRoutingState.PENDING`**, which `phase4.md` does not list. Its four values are the
   *outcomes* of routing; a message that has been ingested and not yet routed is in none of them, and
   reusing `UNROUTED` would make "routing could not place this" and "routing has not looked" the same
   value — which is exactly what the triage queue distinguishes.
3. **`ingest_key` preferring the `Message-ID` header over the content hash.** A forged header is a
   suppression vector within the unrouted set. I preferred it because a legitimately redelivered
   message keeps its header and may not keep its bytes. The opposite order is defensible and would
   close the window at the cost of duplicate rows on ordinary relaying.
