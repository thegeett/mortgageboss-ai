# LP-849 — a message box, not a notepad

Status: spec. Fourth of four, and the largest.

## The report

> "We need reach textarea component for message, not like old scholl ***bold***. The message field
> looks like simple notepad version. Think like how message box in gmail."
>
> "For user it should text with all reach editor option, user should not see html tag or markdown.
> Plus when they copy it should be text, like what we generally do copy pasting the text in email."

This reverses LP-844's editor decision, with the benefit of having seen it. Markdown-in-a-textarea
was chosen there to avoid a dependency; the user has now used it and it reads as a notepad.

## What the requirements actually pin down

1. **A real toolbar** — bold, bullets, the usual — applied to a selection.
2. **No markup visible anywhere.** Not in the editor, not in a preview. A `**` is a failure.
3. **Copy pastes as ordinary formatted text**, the way copying out of Gmail does — which is what
   LP-844's `text/html` + `text/plain` clipboard already produces. That requirement is already met
   and must not regress.

## Storage: keep the plain source of truth

**Decided: the body column stays one plain string; the editor converts on load and serialises on
save.** Not HTML-in-the-column.

The alternative is storing HTML, which is truer to Gmail and costs more than it looks: every backend
template would have to emit HTML (all of them, each a new ADR-401 version and fingerprint),
`mailto:` needs a generated plain-text downgrade, `finalise_draft_body`'s placeholder pass would run
over markup, and the send record — which must be *what went out* — becomes a format no existing test
reads.

Keeping the plain string means the templates, the placeholder resolution, the `mailto:` path, the
audit record and LP-844's clipboard all keep working untouched. The user's requirements are about
what they SEE, and none of them is a statement about storage.

**The risk this accepts** is the round trip: visual edit → plain text → visual edit must not
degrade. The subset is small (paragraphs, bullets, bold, and LP-846's document blocks), which is
what makes a serialiser tractable — and the round trip is the thing to test hardest, in both
directions, because a lossy one silently eats a processor's formatting.

## Dependency

There is no editor in the project. Either a real one (Tiptap/ProseMirror — a substantial dependency
that brings a schema, which is how "no markup visible" stays true) or a hand-rolled
`contenteditable` with `document.execCommand`, which is deprecated and reimplements selection
handling badly.

**Leaning Tiptap**, constrained to the same subset the renderer supports — a schema that cannot
produce a heading is how the editor and `emailBodyToHtml` stay in agreement. To be confirmed at
build time against bundle size and the CSP.

## What it must not break

- `emailBodyToHtml` stays the single renderer, so the editor and the reader cannot disagree.
- The escape-first property is not weakened. A WYSIWYG produces markup by design, which makes the
  boundary between "structure the editor created" and "text a person typed" the thing to get right.
- `mailto:` stays plain text (RFC 6068).
