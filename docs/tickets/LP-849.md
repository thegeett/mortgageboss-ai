# LP-849 — a message box, not a notepad

Status: spec. Fourth of four, and the largest.

## The report

> "We need reach textarea component for message, not like old scholl ***bold***. The message field
> looks like simple notepad version. Think like how message box in gmail."
>
> "For user it should text with all reach editor option, user should not see html tag or markdown.
> Plus when they copy it should be text, like what we generally do copy pasting the text in email."

This reverses LP-844's editor decision, with the benefit of having seen it. Markdown-in-a-textarea
was chosen there to avoid a dependency; the user has now used it and it reads as a notepad.

## What the requirements actually pin down

1. **A real toolbar** — bold, bullets, the usual — applied to a selection.
2. **No markup visible anywhere.** Not in the editor, not in a preview. A `**` is a failure.
3. **Copy pastes as ordinary formatted text**, the way copying out of Gmail does — which is what
   LP-844's `text/html` + `text/plain` clipboard already produces. That requirement is already met
   and must not regress.

## Storage: keep the plain source of truth

**Decided: the body column stays one plain string; the editor converts on load and serialises on
save.** Not HTML-in-the-column.

The alternative is storing HTML, which is truer to Gmail and costs more than it looks: every backend
template would have to emit HTML (all of them, each a new ADR-401 version and fingerprint),
`mailto:` needs a generated plain-text downgrade, `finalise_draft_body`'s placeholder pass would run
over markup, and the send record — which must be *what went out* — becomes a format no existing test
reads.

Keeping the plain string means the templates, the placeholder resolution, the `mailto:` path, the
audit record and LP-844's clipboard all keep working untouched. The user's requirements are about
what they SEE, and none of them is a statement about storage.

**The risk this accepts** is the round trip: visual edit → plain text → visual edit must not
degrade. The subset is small (paragraphs, bullets, bold, and LP-846's document blocks), which is
what makes a serialiser tractable — and the round trip is the thing to test hardest, in both
directions, because a lossy one silently eats a processor's formatting.

## Dependency

There is no editor in the project. Either a real one (Tiptap/ProseMirror — a substantial dependency
that brings a schema, which is how "no markup visible" stays true) or a hand-rolled
`contenteditable` with `document.execCommand`, which is deprecated and reimplements selection
handling badly.

**Leaning Tiptap**, constrained to the same subset the renderer supports — a schema that cannot
produce a heading is how the editor and `emailBodyToHtml` stay in agreement. To be confirmed at
build time against bundle size and the CSP.

## What it must not break

- `emailBodyToHtml` stays the single renderer, so the editor and the reader cannot disagree.
- The escape-first property is not weakened. A WYSIWYG produces markup by design, which makes the
  boundary between "structure the editor created" and "text a person typed" the thing to get right.
- `mailto:` stays plain text (RFC 6068).

# Built — part one of two

**Stopped deliberately short of `message-dialog.tsx`.** The reviewer session is working in the same
worktree and has `email_draft.py`, `mail_transport.py` and `email-body.test.ts` open; the dialog is
the one file this ticket and that review would both touch. Everything below is new files, which
cannot collide.

## Tiptap, constrained to the renderer's subset

`Document`, `Paragraph`, `Text`, `Bold`, `BulletList`, `ListItem`, `HardBreak`. Nothing else.

**The schema is the contract.** An editor that could produce a heading would produce one
`emailBodyToHtml` silently drops on save — a processor watching their formatting vanish. Constraining
the extension set is how the editor and the renderer stay in agreement structurally, rather than by
somebody remembering.

Bundle cost, measured: the communication route is **195 kB** first-load. Not free, and paid only on
the route that has an editor.

## The round trip is the whole risk, and it is a fixed point

`Communication.body` stays one plain string, so every keystroke goes text → HTML → editor → HTML →
text. A lossy inverse eats formatting *gradually* — surviving one reopen and degrading on the fourth
— so it is tested as `render(parse(render(x))) === render(x)` across 13 shapes rather than against
hand-written expectations. That catches drift no guess of mine would, because it does not depend on
my picking the shapes that matter.

## The one asymmetry, which is where this design could have failed quietly

`emailBodyToHtml` renders a catalog line `Where to get it: …` as `<strong>Where to get it:</strong> …`
**and** a processor's `**bold**` as `<strong>bold</strong>`. Same HTML, two different plain forms.

The inverse uses the renderer's own rule: a `<strong>` that opens a nested detail item and ends in a
colon is a label and loses its asterisks; anything else is emphasis and keeps them. Get it wrong in
one direction and every template body gains `**` on every edit — invisible in the editor and visible
in the plain-text clipboard flavour and the `mailto:` body. Get it wrong in the other and a
processor's own formatting is silently deleted, which is worse because they chose it. **Both
directions are mutation-verified.**

## A defect the fixed-point test caught immediately

The first block splitter was `/<(p|ul)>([\s\S]*?)<\/\1>/g`, and a non-greedy match stops at the
FIRST `</ul>` — which, for a document with nested guidance, is the inner one. Every catalog body came
back empty or inside out: the one shape that actually matters. Replaced with a depth-aware scan.

# Built — part two, and the save decision

## The reviewer's point settled the design, and the answer was already the safe one

LP-848's heal re-renders a stale draft **on read**, and `_regenerate` re-renders on every
add/remove. Both are safe for exactly one reason: before a send the stored body is always
template-generated, so there is no human edit to destroy. LP-849 is plausibly the endpoint that
breaks that — the moment an edited body can be saved without sending, the next GET rewrites the
processor's work and so does the next document they request. **A rich editor whose output survives
until the next page load is worse than no editor.**

So the editor holds the edit **in memory until "Mark as sent"**, which is what was already built —
`MessageEditor` is `value`/`onChange` and the dialog's local state, with no route behind it.

**And that is now a guard rather than a property nobody re-checks.**
`test_no_draft_save_route.py` fails the build if any draft route accepts body text except the send.

Its first version keyed on the route NAME and flagged `POST /draft` —
`party_requests.draft_for_party`, which takes only a `party` and renders from the template exactly
as `_regenerate` does. A name allow-list turns every new legitimate route into a false failure. The
real property is **whether the client supplies the words**, so it scans for request models carrying
a `body` field.

**Then the mutant survived**: a `PATCH /draft/{id}` convenience route passed, because it reused
`SendDraftRequest` — of course it did, the obvious way to write a save is to take the payload the
send already takes. I had allow-listed the MODEL. The permission belongs to the endpoint that earned
it, so it is scoped to the route now, and the mutant fails.

## Bundle cost, measured twice

A static import took the communication route from 195 kB to **299 kB** of first-load JS. ProseMirror
is not small, and nobody needs it to READ a timeline, which is what this page is for most of the
time. Behind `next/dynamic` with `ssr: false` it is **196 kB** and the editor loads on the click
that needs one.

## Two tests that would have lied after this change

`fireEvent.change` does nothing to a contenteditable. Both dialog tests that drove the message field
that way would have kept passing while asserting that the **unedited** body was sent — green, and
testing nothing they claimed.

Simulating ProseMirror keystrokes in jsdom tests the simulation, so they now assert what is both
reachable and actually at risk: **HTML must not leak into the record of what went out**, and copy
and `mailto:` must carry the same body the send would. The conversion itself is a fixed point over
13 shapes; the editor's own suite covers the toolbar and what is displayed.

## The wiring, for the FIFTH time

Every other test in the dialog file reads `body` from the seeded detail, so **all of them pass
whether the editor mounts or not** — and `next/dynamic` with `ssr: false` is exactly the thing that
silently renders a placeholder forever. I probed the DOM to confirm it mounts, then added the
assertion, because confirming it once by hand is not a guard. Mutation-verified: putting the
textarea back fails.

## One of the reviewer's controls had to move

Their LP-844 sink guard asserted at least **two** `dangerouslySetInnerHTML` sinks. This ticket
removed one — the WYSIWYG is the preview, so that sink went with it. The count is a control against
a scan that read nothing, not a claim about how many sinks there should be, so it tracks the real
number and their guard is unchanged.

## Review (second session)

Reviewed `fa53d432`. Three defects found, all in the seam the ticket names, plus one gap in the guard
that protects the whole design.

### The sweep the ticket asked for, and the defect it found

`toHtml(fromHtml(toHtml(b))) === toHtml(b)` over all 1024 five-line sequences and over every real
template: **no divergence.** But the sweep starts from a stored body, so it only ever feeds
`htmlToEmailBody` the renderer's own output — which cannot contain a second nesting level, because the
plain form has no way to say one. The schema can: `ListItem` admits a `BulletList`, which is what makes
the catalog's guidance expressible in the first place, and nothing bounds the depth.

So the second sweep starts from the HTML instead, over fifteen shapes the editor can produce and the
renderer never would. Everything converged — and two levels of nesting serialised `detail` and `deeper`
as **`detaildeeper`**, one word, no separator. Three levels gave `bcd`.

Fixed in the serialiser rather than the keymap, because Tab can be rebound and **pasting** a nested
list out of Word or Gmail cannot: `detailLines` collapses any depth to the one detail level the plain
body has, each item its own line. Empty items are dropped rather than emitted as an indented blank,
which the renderer would read as the blank that ENDS a detail run.

The sweep as first written could not have caught this: `expect(once).toContain("detail")` passes for
`detaildeeper`. It compares TOKENS now, so the mutation fails three tests rather than the one named
example.

### The label rule was two rules, and five of seven cases lost the bold

The ticket calls the label/emphasis split the load-bearing judgement, and says a processor who types
bold ending in a colon loses their asterisks — judged acceptable. That is true of `**Note:**`: it
stores as `Note:` and comes back `<strong>Note:</strong>`, so nothing a processor can see changed.

It was not true elsewhere. `htmlToEmailBody` stripped the markers from any `<strong>` ending in a colon;
`emailBodyToHtml` re-bolds only `^[A-Z][^:]{2,40}:`. Measured across seven cases:

| bold inside a detail line | bold survived, before |
|---|---|
| `Note:` | yes |
| `note:` | **no** |
| `A:` | **no** |
| `Ab:` | **no** |
| a label longer than 41 chars | **no** |
| `2 things:` | **no** |
| `Note: really:` | partly — only `Note` re-bolded |

So a processor's formatting vanished on save, which is the exact failure the editor's own docstring says
the schema restriction exists to prevent. `isCatalogLabel` is now exported from `email-body.ts` and
derived from `LABELLED` rather than restating it, so the two directions are one rule and cannot drift.
All seven keep their bold; the genuine catalog label still stores unadorned, so the templates do not
inflate. Mutated: the old rule fails six tests.

### StarterKit was an installed dependency

The schema guard the ticket asked for — enumerating extensions against what the renderer handles rather
than asserting no `h1` renders — failed on first run, on the manifest rather than the component:
`@tiptap/starter-kit` was a declared dependency that nothing imported. It brings headings, italic, code,
blockquote, ordered lists and strike, none of which survive a round trip, and the obvious future edit is
"why import seven extensions when StarterKit exists". Removed. The guard asserts its absence from the
component AND from `package.json`, because a dependency nobody imports today is one somebody imports
tomorrow.

### The third escape path had nothing running it

The entity question is answered for the two functions the ticket owns. But the real sequence is stored
text → HTML → **Tiptap parses it** → **Tiptap re-serialises it** → HTML → stored text, and those middle
two steps are somebody else's parser normalising entities, whitespace and attributes. Nothing exercised
them: `round-trip.test.ts` calls the two pure functions, and the editor tests assert what renders.

`EXTENSIONS` is now exported so a test can drive the real schema. Eight bodies — a catalog body, bold,
a label, `&lt;name&gt;`, a bare ampersand, quotes and apostrophes, two lines in one paragraph — go in as
content and come back byte-identical through `getHTML()`. The path is faithful; it simply had not been
run. Mutated: decoding `&` first instead of last fails two of them.

### The save-route guard had a gap

It is the right property and it is well controlled, and it missed one shape. It decides a route is
draft-related by looking for "draft" in the decorator's path, so a `PATCH /{identifier}` on a router
declared `APIRouter(prefix="/draft")` was skipped before the check was applied. Two earlier mutants were
caught only because they happened to name the path parameter `{draft_id}` — the word appearing by luck
rather than by the route being read. The prefix now counts as part of the path; 26 of the api modules
declare one. Mutant confirmed failing.

### D — the editor does mount, and the split is real

Verified in a production build rather than in jsdom: the communication route is **196 kB**, matching the
ticket's figure for the dynamic form against 299 kB static. Three emitted chunks contain ProseMirror
(332 kB together) and **none of them is among the route's 16 initial chunks**, so the code exists to be
loaded and is genuinely deferred. The dialog is `"use client"`, so `ssr: false` is valid there.

What this does not prove is a mount in a real browser — that needs a browser. What is asserted is one
step better than the ticket's probe: `message-dialog.test.tsx` waits for `.ProseMirror` to appear
through the `next/dynamic` wrapper, so the import resolving is now a test rather than an observation.

### The fifth instance, and a ratchet for the component half

The ticket is right that this is a pattern rather than an accident, and right that the service-level walk
cannot see a component. `frontend/lib/unwired-components.test.ts` is the component half: an exported
component under `components/` that no production file references, its own module included.

The census is **one**: `LoadingRegion`, an `aria-busy` wrapper from LP-47 that no screen ever used. Left
alone rather than deleted, for the same reason as the three no-caller service functions.

Getting to one took two corrections, both of which would have made the check noise instead of signal:
Next's route files are wired by FILENAME, so including `app/` reported twenty false orphans; and a
sub-component rendered by the exported one beside it is wired, so counting only cross-file imports
reported seven more. The positive control pins the case that matters — `MessageEditor` is reached only
through `next/dynamic`'s import callback, which is the shape most likely to read as unwired, and the
control asserts it does not.

### Standing three

Frontend-only except one test file. No tenancy surface, no logging of message content, no model call.
The editor never sends HTML anywhere: `onChange` is handed `htmlToEmailBody(...)` on every keystroke, and
the backend guard fails the build if any draft route starts accepting body text except the send.

### Gate

Backend: ruff + `mypy --strict` clean, **7572 passed / 6 skipped / 1 xfailed** (the full suite, which the
ticket did not re-run). Frontend: biome clean across 382 files, `tsc` exit 0, **1602 tests in 135 files**,
`next build` succeeded at 196 kB for the communication route.
