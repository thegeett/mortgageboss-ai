# LP-825 — The communication page shows activity that has nothing to do with communication

- **Ticket:** LP-825 · Phase 4 follow-up, from processor feedback on LF-JR4T
- **Status:** Built — awaiting review
- **Date:** 2026-09-07
- **Scope:** `services/timeline.py`, `api/timeline.py`,
  `components/file/communication/timeline-panel.tsx`, the Recent activity surface
- **Migration:** none expected

---

## What was reported

The timeline at the bottom of the Communication page is useful, but it carries the whole file's
activity — document classifications, DTI overrides, field reviews. On LF-JR4T the ten most recent
rows were: one document request, two field-review entries, three DTI entries, and seven document
classifications. One of eleven was about communication.

The ask: the communication page shows communication only; everything else belongs in **Recent
activity**, with an overflow and a "see more" link.

## Measured

LP-812 built this deliberately, and the reasoning is sound for the problem it was solving. One
arrival writes three rows in three tables, so `MESSAGE_ACTIVITY_TYPES` derives every
`COMMUNICATION_*` activity from the enum and **excludes** it, letting the `Communication` row be the
timeline's single entry for that event.

The consequence nobody stated: excluding the communication activities means **including everything
else**. The filter was written as "drop the duplicates" and its effect is "keep all non-message
activity", which is the opposite of what the panel is for. This is the subtraction trap — a set
defined as "the rest" absorbs members nobody placed there.

## Done when

- The Communication page's timeline contains only communication events: messages sent, messages
  received, drafts, delivery failures, party requests, secure-link activity. Defined as an explicit
  **allow-list**, not as "everything except the message duplicates" — the current bug is exactly
  what a deny-list produces when a new activity type is added.
- The dedup property LP-812 exists for still holds: one arrival still appears once. A test drives a
  real message through the real chain, as LP-812's does, rather than asserting over a hand-built
  fixture that would give a one-row timeline either way.
- Non-communication activity appears on **Recent activity** with a bounded initial render and a "see
  more" affordance. The existing 200-row cap and its `truncated` flag are the precedent — a list
  that silently stops is the failure LP-812's review already fixed once.
- A positive control: a file whose only history is document classifications shows an EMPTY
  communication timeline and a populated Recent activity. Without it, a filter that dropped
  everything would pass every other assertion here.

Clicking one of those rows opens it — [LP-829](LP-829.md), which depends on this one.

## For the reviewer

The allow-list is the whole ticket. A fix that adds three more types to the exclusion list is green
today and wrong on the next activity type anybody adds, and nothing in the suite would say so.

## Built, 2026-09-07

### The fix is not an allow-list, and the ticket asked for the wrong thing

This ticket specified an explicit allow-list to replace the deny-list. **That would have been the
third enumeration standing in for a definition in as many tickets** — LP-827's `_LOOPBACK_HOSTS`,
LP-824's `_ADDRESS_BEARING`, and this. An allow-list goes stale the moment somebody adds an
`ActivityType`, in the same way the deny-list did.

The derivation was already in the file. Measured over the live enum: **32 activity types, 3 of them
`COMMUNICATION_*`.** An activity belongs on a communication timeline only if it is about a message;
`MESSAGE_ACTIVITY_TYPES` is exactly the set of types about messages, derived from the enum rather
than listed; and every one of them is already excluded because the `Communication` row carries that
event. **Nothing is left.** So `build_timeline` does not query the activity log at all, and a
thirty-third type inherits that by construction.

That is the whole backend change. There is no list to maintain and no list to go stale.

### Three things followed from it, and none could be left

* **`TimelineFilter.ACTIVITY` is gone.** It could only match an activity row and there are none, so
  it would answer "Nothing in activity" on every file forever. A control that always says nothing is
  broken, not empty. The pill is off the panel with it.
* **`TimelineKind` has one member.** Kept as an enum rather than collapsed to a literal — it is what
  a client branches on, and LP-829 is the next thing to add to it.
* **`MESSAGE_ACTIVITY_TYPES` is now a claim, not a filter.** Kept and exported because
  `test_every_communication_activity_type_is_excluded` asserts it against the live enum: if a
  thirty-third type ever describes a message without being named for one, that is where it surfaces.

### The other half: Recent activity had to be able to carry it

The Communication page was where a processor could scroll the file's history. It no longer is, so
the feed that always described it had to stop being a dead end — it was capped at 20 with nothing on
screen saying so, which is the same silent truncation LP-812's review already fixed once on the
other panel.

`GET /activity` takes `limit`, bounded at 200. **A refusal, not a silent clamp**: a client asking for
5000 gets a 422 rather than 200 rows and the belief it has the whole history.

The hook asks for **one row more than it shows**. There is no total and no cursor, so the extra row's
existence is the only honest answer to "is there more"; it is dropped before rendering, or every
"see more" would reveal a row already on screen. `limit` is part of the query key, so a page is a
new query and the previous one stays visible while the larger loads.

**No cursor, deliberately.** The feed is newest-first and grows at the top, so an offset skips
entries when something is written between two requests — the ordinary case here, not the rare one.
Re-reading rows is cheap at these sizes and cannot lose one.

### Tests: two inverted, four fixtures corrected, none weakened

`test_a_non_message_activity_still_appears` **was** the control against a timeline that dropped
everything. It is now `..._does_not_appear`, which is the reported defect. The control it provided
did not go away — it moved to `test_a_message_still_appears_on_an_otherwise_busy_file`, and that is
the assertion standing between this change and a Communication page showing silence on a file with a
live conversation.

Four fixtures counted rows that included an activity entry (5 → 4, 3 → 2). Each now states what the
timeline carries rather than counting off the fixture, so a change to that fails the test instead of
agreeing with it. `test_a_truncated_timeline_says_so` built its four entries **out of activity
rows** — since this change that produces an empty timeline, and the truncation test would have
passed on nothing being capped at all. Rebuilt from messages.

### Mutations

| mutation | result |
|---|---|
| the deny-list restored | **6 failed** |
| the timeline always empty | **15 failed** |
| "See more" never rendered | 1 failed |

The second is the one that matters. It is the failure this ticket could most easily have introduced,
and it is worse than the noise it replaced — a processor reads silence as "nothing has happened".

### The boundary decision, stated because it is arguable

"Requested docs from finding ID-3" is a `NEEDS_ITEM_CREATED` activity and does **not** appear on the
Communication timeline. The draft that request produces does. A document was added to a to-do list;
the email is the communication. If that reads wrong to a processor, the change is to give the event
its own communication-shaped row, not to reinstate the activity query.

### The three standing checks

**Tenancy:** unchanged — both queries are scoped by `loan_file.id` on a file the route resolved under
the caller's company; the activity endpoint keeps its `ScopedLoanFile` gate. **Logging:** nothing
added. **AI:** none.
