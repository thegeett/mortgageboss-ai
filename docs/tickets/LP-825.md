# LP-825 — The communication page shows activity that has nothing to do with communication

- **Ticket:** LP-825 · Phase 4 follow-up, from processor feedback on LF-JR4T
- **Status:** Specified — not started
- **Date:** 2026-09-07
- **Scope:** `services/timeline.py`, `api/timeline.py`,
  `components/file/communication/timeline-panel.tsx`, the Recent activity surface
- **Migration:** none expected

---

## What was reported

The timeline at the bottom of the Communication page is useful, but it carries the whole file's
activity — document classifications, DTI overrides, field reviews. On LF-JR4T the ten most recent
rows were: one document request, two field-review entries, three DTI entries, and seven document
classifications. One of eleven was about communication.

The ask: the communication page shows communication only; everything else belongs in **Recent
activity**, with an overflow and a "see more" link.

## Measured

LP-812 built this deliberately, and the reasoning is sound for the problem it was solving. One
arrival writes three rows in three tables, so `MESSAGE_ACTIVITY_TYPES` derives every
`COMMUNICATION_*` activity from the enum and **excludes** it, letting the `Communication` row be the
timeline's single entry for that event.

The consequence nobody stated: excluding the communication activities means **including everything
else**. The filter was written as "drop the duplicates" and its effect is "keep all non-message
activity", which is the opposite of what the panel is for. This is the subtraction trap — a set
defined as "the rest" absorbs members nobody placed there.

## Done when

- The Communication page's timeline contains only communication events: messages sent, messages
  received, drafts, delivery failures, party requests, secure-link activity. Defined as an explicit
  **allow-list**, not as "everything except the message duplicates" — the current bug is exactly
  what a deny-list produces when a new activity type is added.
- The dedup property LP-812 exists for still holds: one arrival still appears once. A test drives a
  real message through the real chain, as LP-812's does, rather than asserting over a hand-built
  fixture that would give a one-row timeline either way.
- Non-communication activity appears on **Recent activity** with a bounded initial render and a "see
  more" affordance. The existing 200-row cap and its `truncated` flag are the precedent — a list
  that silently stops is the failure LP-812's review already fixed once.
- A positive control: a file whose only history is document classifications shows an EMPTY
  communication timeline and a populated Recent activity. Without it, a filter that dropped
  everything would pass every other assertion here.

## For the reviewer

The allow-list is the whole ticket. A fix that adds three more types to the exclusion list is green
today and wrong on the next activity type anybody adds, and nothing in the suite would say so.
