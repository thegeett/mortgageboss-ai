# LP-807 — Triage queue UI, and the pipeline it needed to exist

- **Ticket:** LP-807 · Phase 4, M3, ticket 17 of 28
- **Status:** Built — awaiting review
- **Date:** 2026-09-08
- **Scope:** frontend triage UI, a file-scoped read and a preview endpoint, the ingest chain,
  seed data (§H3)
- **Migration:** `e4a7c15d92b0`

---

## The chain had no caller

`apply_safety_to_message` (LP-804b) and `apply_routing` (LP-805) were built, tested, exported — and
**nothing outside their own test modules ever called them.** The Celery task and the dev injector
both called `ingest_raw_message` and stopped.

So every message in the system would have sat at `routing_state=PENDING` with every attachment at
`safety_state=PENDING`, forever: never routed to a file, never assessed, and never acceptable, since
`accept_attachment` requires `SAFE`. Both suites were green throughout, because each called its own
function directly.

LP-807 is the ticket that noticed, because it is the first one that has to **show a processor what
arrived**. `process_raw_message` is now the chain — store, assess, route — and both callers use it.

The test for it is a **positive control with a negative twin**. On its own, "the message came out
routed" would pass just as happily if the fixture were doing the routing; the second test runs the
same message through the row-writer alone and pins what that looks like — `PENDING` and `PENDING`,
from a call that reads like a complete ingest.

## A key a later step rewrites is not a key

Wiring routing in immediately broke redelivery, and the failure is worth writing down.

The dedup index was `(company_id, ingest_key) NULLS NOT DISTINCT`. That is correct for exactly as
long as nothing fills `company_id` — and routing fills it. So a redelivery no longer collided with
the first copy, which had moved from `(NULL, key)` to `(company, key)`; it inserted a second row, and
then raised a `UniqueViolation` when routing tried to move **that** one to the same place.

**A redelivered message either duplicated or crashed the task**, and SQS delivery is at-least-once by
design. LP-803's "the same message delivered twice produces exactly one row" passed the whole time,
because the test ran in the state where the flaw is invisible.

The index is now on `ingest_key` alone. The company is not part of a message's identity — it is a
conclusion drawn about the message afterwards. `ingest_key` is `ses_message_id` whenever SES gave
one, which it always does on the real path, and which is globally unique per delivery: one message
delivered to two of our addresses is **one** SES receipt and one bucket object, so it is genuinely
one row.

The existing-row lookup was scoped to `company_id IS NULL` for the same lost reason, so it answered
`None` for exactly the row it was looking for once routing had claimed it — returning
`message_id="None"` to a caller treating the redelivery as handled.

**The limit, stated:** without an SES id the key falls back to the `Message-ID` header, which two
companies could share if the same forwarded thread were mailed to both. One would then be suppressed.
Not reachable on the SES path; **escalated** rather than papered over.

## The preview is the one thing here that renders a stranger's file

`derived_storage_path` has never been written — LP-804b produces the rasterised pages and throws
them away — so there was no stored artefact to show. The preview re-derives instead: bytes from the
stored `.eml` (matched back by sha256, so a preview cannot show content that is not the content that
was **assessed**), sanitised, first page rasterised.

**Nothing the sender wrote reaches the browser.** The response body is always a PNG this server
rendered; an image is decoded and re-encoded rather than passed through. That is stronger than
serving the original under a sniffed `Content-Type`, because a re-encode cannot carry a trailing
payload a content sniffer might reach for. `rasterise_pdf` grew a `limit` so a thumbnail renders one
page rather than two hundred; the page-count guard still runs first.

`SAFE` only, and `PENDING` is not a pass — the scan is asynchronous. A file the renderer cannot open
(a HEIC, a TIFF) returns **None, not a refusal**: those are different answers and the card shows
different things for them, and collapsing them would put a safety warning on an ordinary iPhone
photo.

### And no preview for a message nobody owns

The unrouted queue is shown to **every** company. LP-806's review had to strip the sender, the
subject and both filenames out of it after measuring one tenant receiving another tenant's
borrower's personal address. A thumbnail is that same disclosure in its most legible form.

The defence is not a flag on the route — it is that the **only** preview route is file-scoped, and an
unrouted message has no file. Every file a caller could name gives the same 404 as a missing
attachment. There is a test whose job is to stop a later convenience endpoint undoing that.

## What the UI says, and what it must not

The card renders the redaction as **a state, not as missing data**: "Sender hidden until claimed"
rather than a blank line, with a sentence explaining that the message matched no file and everything
appears once somebody claims it. It offers no Accept button there, because there is no file to accept
into.

`unclaimed()` reads `loan_file_id`, not a null `from_address` — a message genuinely can arrive with
no `From` header, and calling that "redacted for your protection" would be a confident explanation of
the wrong thing.

`GRAY` is not `PASS`. The badge compares for equality, so an unrecognised verdict reads as
unverified.

`filename_original` is rendered as text. React escapes by default and nothing here bypasses it —
no `dangerouslySetInnerHTML`, no `title`, no `href` built from it, and the `alt` text says what the
image is rather than what the sender called it.

### The signal labels were wrong before they were tested

The first draft of `SIGNAL_LABEL` had five entries — copy for ladder rungs 3 to 6, which LP-805 never
built and no message can carry — and spelled rung 2 `references` rather than `thread_reference`. The
map looked complete while the one real rung-2 message fell through to the generic fallback. It now
holds exactly the two rungs that exist, with a test asserting that.

## Seed data (§H3)

Seeded **by sending mail**, not by writing rows: `_seed_inbound_mail` goes through
`process_raw_message`, so routing, safety and dedup decide for themselves and the seeded queue is one
the running system could have produced. Hand-written rows would have let the states be whatever the
seed said — including combinations the pipeline cannot reach, which is worse than no seed, because a
frontend built against them looks finished and breaks on the first real message.

Three shapes: routed with a readable PDF, quarantined (a zip renamed `.pdf`), and unrouted.

`--reset` deletes them **by ingest key**. Deleting the company cascades the routed ones, but the
unrouted message has no company and no loan file and would survive — and because the seed is
idempotent, the survivor means a re-seed silently creates nothing for that case. The developer who
reset to get the queue back would be missing the one message the queue exists to demonstrate. The
keys are named once and a test asserts the two lists agree.

The dev injector now stores the raw bytes (`store_raw=True`). It passed `raw_storage_path=None` on
the reasoning that nothing came from S3 — true, and the consequence was that everything downstream
was dead locally: accept and preview both re-derive from the stored message, so every injected
message was listable and unopenable.

### The survivor was a test that could not fail for its stated reason

`test_an_unassessed_attachment_has_no_preview` built its attachment with `ingest_raw_message` alone,
so `raw_storage_path` was NULL — and the `CannotAcceptError` it caught was *"the original message is
no longer available"*, never the safety gate it was named after. Widening the gate to let `PENDING`
through changed nothing it observed.

It now builds through the full pipeline, **asserts the preview renders before flipping the state**,
and matches on the gate's own message. `UNSUPPORTED` is covered alongside — that is what LP-804b
marks the attachment on a bounce, which is the borrower's own message coming back, and rendering it
would show a processor their own request as though the borrower had sent it.

## Deliberately not done

- **No "suggested document type" or "suggested need" on the card.** The plan asks for them.
  Classification happens *after* accept, in the existing pipeline, and ladder rung 6 (the AI
  suggestion) was never built — LP-805 stopped at rung 2. What the card shows instead is real: the
  **signal** the message routed on, which is what a processor about to accept a document actually
  wants to know. Inventing the rest would have been five labels for states nothing produces, which
  is the mistake `SIGNAL_LABEL` already made once in this ticket. **Escalated.**
- **No claim/reassign from the unrouted queue.** LP-806 left it for its own design and that has not
  changed: claiming an unrouted message is the one operation here that moves data across a tenant
  boundary. The redaction now makes that boundary the moment the data appears rather than something
  to retrofit.
- **Accepting still does not enqueue processing** (LP-806's escalation, unchanged).

## For the reviewer

- **Tenancy** — `company_id` is still derived from an address in exactly one place. The two new
  endpoints take their company from `current_user`; the new service query scopes on `loan_file_id`,
  and is a separate query rather than a narrowing of the company-wide one.
- **Message content in logs** — the new log lines carry counts and a `kind`. The preview's failure
  path logs `kind="pdf"` / `kind="image"` and nothing else.
- **AI in the decision path** — none. The card proposes nothing.

The judgement calls worth a second measurement:

1. **The index change** is the one with reach beyond this ticket. It fixes a crash on every
   redelivery, and it makes `ingest_key` globally unique — see the stated limit above.
2. **The preview re-derives on every request**, uncached beyond TanStack's five minutes. A queue of
   five messages with three attachments each is fifteen rasterisations. The alternative is storing
   the raster, which is a second durable copy of a borrower's document.
3. **`save_at` is a new method on the storage ABC.** Raw inbound mail has no tenant at the moment it
   is stored, so it cannot use `save`'s path shape. Both S3 writers go through one `_put` so neither
   can lose the encryption args, and there is a test asserting that outcome rather than the refactor.

## Review (second session, protocol §3)

One finding, and it is in the builder's item 1 — but it makes the risk that was escalated as
*unreachable* reachable on every message.

### A — `ses_message_id` was read off the wrong object, so the dedup key was the sender's

`tasks/inbound.py` passed `receipt=notification.get("receipt")` and then read
`receipt.get("messageId")`. AWS documents `messageId` on the **`mail`** object; the `receipt` object
carries `action`, the five verdicts, `recipients`, `processingTimeMillis` and `timestamp`, and no id
at all ("Contents of notifications for Amazon SES email receiving", read 2026-09-07).

So `ses_message_id` was `None` for every real message, and `compute_ingest_key` fell through to its
next source — **the sender-written `Message-ID` header** — as the dedup key. After this ticket's own
index change that key is unique across every tenant.

That is exactly the escalation in the ticket doc, which reads *"not reachable on the SES path"*. It
was reachable on all of it: two companies receiving the same forwarded thread would have had the
second silently suppressed, and the key deciding it is a header the sender writes.

Fixed by reading `mail.messageId`, with the S3 object key as an explicit fallback — AWS says of
`objectKey` that "this is the same as the messageId in the mail object", so the fallback is sound,
and it is a fallback rather than the source so nothing silently depends on the delivery action being
S3.

**Nothing tested this file.** `rg` found no test anywhere referencing `app.tasks.inbound`, which is
why a mis-read field survived: everything downstream behaved correctly on whatever it was handed.
`tests/tasks/test_inbound_task_lp807.py` is new and builds its notification from the documented
field layout rather than from what makes the code pass.

**And my first version of that test was the thing I have been finding all session.** It re-derived
the extraction inline and asserted the result — so when I reverted the production code to read
`receipt`, it still passed. A test that reimplements what it checks is asserting its own copy.
`_ses_message_id` now exists as a named function precisely so the test can call the production path,
and the same mutation now fails two tests.

### The builder's four, checked

1. **The index change — right, and the reasoning about one receipt holds.** `receipt.recipients` is
   documented as a **list** — "the recipients … that were matched by the active receipt rule" — and
   `mail.destination` as "a complete list of all recipient addresses". One email to two of our
   addresses is one receipt, one `messageId`, one S3 object, one row. So the SES id is genuinely
   unique per delivery and `ingest_key` on it alone is correct. Removing `company_id` from the
   conflict target is also right on its own terms: the company is a conclusion drawn after routing,
   not part of a message's identity, and an index that dedups only while a column stays NULL dedups
   only until the system works.
   Worth carrying forward: because one message to two of our addresses is **one row**, a message
   addressed to two loan files routes to one of them and the other never sees it. Not this ticket's
   to solve, and not a regression — but it is the other half of the same fact.
2. **The preview endpoint — no path found where original bytes escape.** It re-derives from the
   stored `.eml` under a sha256 match, sanitises, rasterises page one through the server's own
   renderer and returns that PNG; images are decoded and re-encoded rather than passed through, and
   the gate is `SAFE` only. `nosniff` with `private, no-store` is right for one borrower's document
   on a per-user-authorised route: `no-store` keeps it out of shared caches and browser disk cache,
   and `nosniff` is what stops a rendered PNG being re-interpreted as anything else.
3. **No preview for an unrouted message — the shape holds.** The only preview route is file-scoped
   and an unrouted message has no file, so this is structural rather than a flag someone can flip.
   The test guarding it is the right kind: it pins the property a later convenience endpoint would
   break, not the absence of that endpoint.
4. **`save_at` — right, and for the reason given.** Raw inbound mail has no tenant when it is
   stored, so it cannot use `save`'s `{company}/{file}/{doc}` path. Routing both writers through one
   `_put` so neither can lose the encryption arguments is the correct shape, and asserting the
   outcome rather than the refactor is what makes it a test rather than a description.

### The ingest chain that had no caller

This is the most valuable thing in the ticket and it deserves recording as a class. `apply_safety_to_
message` and `apply_routing` were built, tested, exported — and invoked by nothing outside their own
test modules. Every message would have sat `PENDING` forever, unroutable and unacceptable, with both
suites green, because each called its own function directly. Two reviewed tickets shipped that way.

The general form: **a unit test proves a function works, and nothing proves it runs.** The only
thing that found it was the first ticket that had to show a processor what arrived — which is to say,
the first reader. That is the same lesson as the finding above, where nothing tested the task, and
the same as LP-819's, where a value was written correctly to a record nobody had unwound.

The redelivery failure it exposed on wiring is the sharper half: the dedup index worked for exactly
as long as nothing filled `company_id`, and LP-803's "the same message twice produces exactly one
row" passed throughout because the test ran in the state where the flaw is invisible.

### Done when, and the standing checks

The queue renders, the card carries sender, auth badge, subject and attachments, one click accepts,
and the company-level view holds unrouted messages — now as a state rather than as missing data,
which is what the LP-806 redaction requires of a reader.

Standing checks: no `company_id` derived anywhere in the UI or the endpoints added here; nothing
logs a subject, body or filename; no AI. The three deferrals are all correctly escalated — in
particular, showing the routing *signal* instead of a suggested type is the honest thing to do when
ladder rung 6 was never built and there is no source for a suggestion.
