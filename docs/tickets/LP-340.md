# LP-340 — the `*_normalized` tag convention: strip entity suffixes (in the RULE, not the tag)

## WHAT THIS IS

LP-337's first real live calibration (against real data) measured **`income.employer_normalized` at 25%
(6/8)** and **`id.name_normalized` at 50%**. **The model was NOT wrong.** It stripped the entity suffix
(`Acme Logistics` vs the golden `Acme Logistics Inc`) and chose the fuller `asserted_name` over `full_name`
— both consistent, reasoned behaviours. **It was a SPEC GAP:** the vocabulary never said what "normalized"
means, so the model chose one convention and the human labeler another. (Same run: `txn.is_money_in` 98%,
`income.documented_monthly` 100% — the structuring layer is accurate; these two tags were *underspecified*,
not inaccurate.) This ticket defines the convention once, for every `*_normalized` tag, present and future.

## THE DECISION (D1, Geet) + WHERE IT LIVES (the fork, resolved)

**D1 (Geet): the corporate entity suffix (`Inc`/`LLC`/`Corp`/`Co`/`Ltd`) is STRIPPED** — a suffix change is
a restructuring, not an employer change.

**Where the strip lives — Geet chose the RULE REGISTRY (Option 1), not the tag prompt:**
- The **TAG reports what the document states** (`Acme Logistics Inc`, in full) — LP-335's principle intact.
- The **RULE declares how it compares**: a new declared normalizer **`drop_entity_suffix`** on **IN-5's**
  `normalization` chain. This is the LP-325 registry's **sanctioned extension point** (a registry entry, like
  the LP-328 date coercer), **not** evaluator logic — so it stays within the "data, not per-rule Python"
  design. The Inc≡LLC decision is now **visible in IN-5's spec, deterministically testable, and reversible
  by deleting one line.**
- **Scoped to IN-5 (INERT) only. ID-1 and ID-4 (LIVE) chains were NOT touched** (asserted).

Why not the tag prompt: baking "strip Inc/LLC" into the tag is FINDING-1's exact class (a downstream
matching concern in a tag exemplar — which is what split the model from the labeler), and it makes the
Inc≡LLC consequence a non-deterministic model behaviour rather than a testable rule fact.

## THE ACCEPTED TRADE-OFF (named, not buried) — the PRIYA item

IN-5's exact bookend now treats **`Acme Logistics Inc` and `Acme Logistics LLC` as identical** → they match,
and the fuzzy leg never runs. Those are different legal entities; a real Inc→LLC change passes silently.
**Accepted** because a suffix change on the same base name is a restructuring, not an employer change. The
countervailing benefit: no AI call + no ratification-pending finding on the COMMON benign `Inc`-vs-no-suffix
formatting difference.

> **PRIYA:** *"Across a pay-stub and a W-2, is `Acme Inc` vs `Acme LLC` worth flagging as an employer
> change?"* **If yes, D1 reverses — delete the one `drop_entity_suffix` line from IN-5's chain** (vocabulary
> + spec only, cheap). The findable anchor is the test `test_in5_inc_vs_llc_matches_THE_ACCEPTED_TRADEOFF`,
> named so it is obvious which assertion must flip.

## D2 / D3 / D4 (argued — only D1 was decided)

- **D2 — which field wins (`id.name_normalized`):** report the document's **PRIMARY printed name of record**
  (`full_name`), not a fuller `asserted_name`. Rationale: the tag reports what the document states; ID-1's
  fuzzy leg exists precisely to reconcile a fuller/nickname/maiden variant. A defensible default,
  Priya-confirmable. Encoded in the `id_name` prompt.
- **D3 — what "normalized" means, generally:** **normalize FORMAT, not CONTENT** — casing, whitespace,
  punctuation, abbreviation expansion (St→Street) are IN; anything that changes the CONTENT a document
  states is OUT (content differences are the SIGNAL the consistency rules exist to catch). **D1 is a
  deliberate, recorded EXCEPTION** — an underwriting judgment that a corporate suffix is format, not content.
  Recorded so a future author knows it was chosen, not overlooked.
- **D4 — convention vs scoring (FINDING-2):** with D1 decided, a scoring problem REMAINS — genuine content
  variance (`Robert` vs `Bob`, maiden vs married) still can't be string-equality scored. That is FINDING-2's
  fuzzy-scoring method (its own ticket), and it is exactly what ID-1's fuzzy JUDGE handles at rule time.

## WHAT CHANGED

- **Engine (the declared-normalizer registry — the sanctioned extension):** `drop_entity_suffix` added to
  `_NORMALIZERS` (`consistency.py`) + `KNOWN_NORMALIZERS` (`specs.py`). A pure function stripping trailing
  entity-suffix tokens after `casefold`/`drop_punct`; never strips to empty. Drift-guard intact.
- **Spec (IN-5 only, INERT):** `drop_entity_suffix` appended to IN-5's `normalization` chain, with the
  trade-off + reversal recorded inline.
- **Prompts (data):**
  - `income_employer`: **removed the hedge** *"drop 'Inc'/'LLC' noise where it aids matching"* (FINDING-1's
    class). Now states the FORMAT convention and says nothing about matching — the tag reports
    `Acme Logistics Inc` in full.
  - `id_name`: D2 — report the primary printed name of record; do not substitute an asserted/alternate form.
  - `id_address`: **unchanged** — already format-only and correct (ID-4 is LIVE; not touched).
- **Vocabulary:** the convention (D3 general rule + D1 exception + D2 + D4) written into the header of
  `vocabulary_extra.yaml` — the hand-editable vocabulary source every wave author touches when minting a tag.
  (`fact_tags.csv` is generated from the xlsx and cannot be hand-edited per-tag; the overlay header is the
  durable data-only home for a convention binding all present + future `*_normalized` tags.)

## THE TESTS

`tests/verification/rule_engine/test_normalized_convention.py`:
- **the normalizer both directions:** a suffix is stripped; a name with NO suffix is not "corrected" into
  one; case/whitespace/punctuation normalize; `inc` alone never strips to empty.
- **IN-5 end-to-end:** identical employer → satisfied, **NO AI call**; `Acme Logistics Inc` vs `Acme
  Logistics` → **now equal, satisfied, no AI** (the case the decision optimises for); **`Acme Logistics Inc`
  vs `Acme Logistics LLC` → equal, satisfied — NAMED as `THE_ACCEPTED_TRADEOFF`** (findable if Priya
  reverses); a genuinely different employer → differs → the **fuzzy leg judges** (the real signal survives).
- **ID-1's fuzzy leg still reconciles** genuine naming variance (assert the AI is consulted, not
  short-circuited).
- **Equivalence:** ID-1 & ID-4 (LIVE) chains have **no** `drop_entity_suffix`; `ACTIVE_RULE_IDS` unchanged;
  IN-5 still inert; the drift-guard `set(_NORMALIZERS) == KNOWN_NORMALIZERS` holds.

The existing IN-C test `test_in5_full` was **updated** (not a regression): `Acme Corporation` vs `Acme` now
correctly collapses at the exact bookend (Corporation is a suffix → no AI) — the intended behaviour change;
a genuine DBA pair (`Acme Corporation` vs `Acme Trucking`) was added to keep the fuzzy-leg case covered.

## NO RE-MEASURE HERE — and a better number later ≠ a better model

Per LP-335's discipline (one principled change, measure ONCE), **the live calibration was NOT re-run.** The
re-run happens once Priya's judgment rows are filled (LP-337's judgment CSV) so the whole picture is measured
at once. **Read the eventual improvement correctly:** the tag now reports the full stated form (`Acme
Logistics Inc`), which is what Geet's golden labels already said — so a better `employer_normalized` number
means **the golden now matches the convention, NOT that the model got smarter.** The model's behaviour was
already correct; the spec moved to meet it (and the suffix strip moved to the rule).

## LABELER-SIDE NOTES (not code fixes)

- The 2 `id.address_normalized` golden cells hold the borrower's NAME, not the address (a column slip) — the
  model predicted the addresses correctly. Fix the two cells; not a code change.
- The 1 `txn.is_money_in` "miss" was a *transfer-to-own-account* debit where the model said `out` (defensible)
  vs golden `in` — a 1-row label/perspective judgment, not a model error.

## NEW GAP (reported, not patched)

`property.address_normalized_match` is an enum VERDICT tag (not a value `*_normalized` tag), so the
convention informs its underlying comparison but it has no suffix concern. If a future value-style
`*_normalized` property tag is minted, it inherits D3 from the overlay header.
