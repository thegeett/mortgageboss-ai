# LP-988 — Task environment wiring for email

- **Ticket:** LP-988, the eighth of the step-1 tickets in `loan-email.md` §15.
- **Status:** applied to staging (account `058190633983`, us-east-1) on 2026-10-21 (US Eastern, just
  after midnight). The outbound values are live; the inbound values appear when receiving is switched on.

## What and why

The api and worker containers need the names of the email resources (bucket, queues, configuration
set) to use them. Setting them now, as task environment variables, means step 2 is app code only: no
infra change has to ship alongside it.

| Env var | Value | Read by the app today? |
|---|---|---|
| `INBOUND_BUCKET` | `mbai-staging-mail` (when receiving is on) | **declared, not read.** `settings.inbound_bucket` exists in `config.py:374`, but nothing reads it: ingest takes the bucket from each SES notification (`tasks/inbound.py`, `S3StorageBackend(bucket=bucket, …)`) |
| `INBOUND_QUEUE_URL` | the inbound queue's URL (when receiving is on) | yes: `settings.inbound_queue_url`, read by `inbound.poll_queue` (`tasks/inbound.py:103`), which is not on any beat schedule |
| `EVENTS_QUEUE_URL` | `https://sqs.us-east-1.amazonaws.com/058190633983/mbai-staging-outbound-mail-events` | no, step 2 |
| `SES_CONFIGURATION_SET` | `mbai-staging-outbound` | no, step 2 |
| `MAIL_TRANSPORT` | `ses` | no, step 2 |

`Settings` ignores unknown variables (`model_config`, `extra="ignore"`), so the three not read yet are
harmless.

**Which containers get them.** `environment_variables` becomes `merged_api_env` → `local.api_env` in
the compute module, which three task definitions use:

- **api**;
- **worker**;
- **migrate**, the one-off migration and read-only query task. This is wider than the brief, which
  expected only api and worker. It is harmless: migrate ignores them too.

The **frontend** renders its own `frontend_environment_variables` and gets none of them. Confirmed on
its current revision.

## What changed

- `infra/envs/staging/main.tf`: two conditional maps added to `module "compute"`'s
  `environment_variables = merge(...)`, with a comment:
  - the inbound map behind `var.inbound_mail_enabled`;
  - the outbound map behind `var.outbound_mail_enabled`.

  A disabled stack contributes `{}`, so it sets nothing and the settings stay `None`. No module changes:
  every value is an existing output.

## What was deliberately not set

- **`INBOUND_KMS_KEY_ARN`.** `settings.inbound_kms_key_arn` (`config.py:376`) is declared and **read
  nowhere**: no match in `backend`, `frontend`, `infra` or `scripts` beyond the declaration. So
  setting it would trigger no client-side decryption or other KMS path. It stays unset anyway, because
  LP-981 moved to bucket-default SSE-KMS and the variable would describe a mode we do not use. The
  declaration is dead and could be removed with the step-2 settings work.
- **`DOMAIN_PROVIDER`**: step 3, with tenant onboarding.
- **`MAIL_BUCKET`**: renaming `INBOUND_BUCKET` happens in step 2, together with the code that reads it.
- `INBOX_DOMAIN` and every other existing variable are unchanged.

## Why setting `INBOUND_QUEUE_URL` is safe

Only `inbound.poll_queue` reads it, and **nothing schedules that task**: there is no `beat_schedule`
anywhere in `backend/app`, `infra` or the compose files. That matches its own docstring ("NOT ON THE
BEAT SCHEDULE YET"). So when LP-989 switches receiving on and sends a test message, the message stays
in the queue to be inspected rather than being drained and ingested.
