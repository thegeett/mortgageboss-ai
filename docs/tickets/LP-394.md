# LP-394 — The rule census: what actually exists, per category, and what each rule needs (READ-ONLY)

## What this ticket is

A read-only census that replaces the planning estimates with the real numbers from the code. It reads every
rule spec, the registry, the activation bars, and the rule vocabulary, and reports the true per-category counts
and each rule's actual state — so sequencing the remaining waves rests on facts, not on "~130". **No file was
changed except this report.**

## Findings

**1. No live rule is currently trusting an unmeasured AI tag — but the 11 base rules are not gate-tracked.**
The 13 gated-in rules are eligible only if `measured ≥ threshold`, so each has a recorded measurement. The 11
`_BASE_ACTIVE` rules predate the gate and carry **no bar / no `measured_accuracy`**. Of those 11, the AI
**auto-ship** rules are AS-1, ID-1, ID-4, ID-7 — and each one's AI tag **is** measured elsewhere: AS-1's
`txn.has_identified_source` at 93.8% (LP-390-5, the same tag that validated AS-2/AS-12), and ID-1/ID-4/ID-7's
`id.*` tags in the LP-379 calibration set. The judgmental base rules (OC-2, ID-8, ID-9) **ratify** and never
auto-ship, so an unmeasured tag cannot leak a trusted verdict. **So there is no AS-1-style exposure today** —
but the base rules' measurements live outside the activation-bar machinery, so a future tag/prompt change to one
of their tags would **not** trip the gate. A cheap follow-up: give the 11 base rules recorded bars so every live
rule is gate-tracked (not built here — a candidate ticket).

**2. IN-12's bar rationale is STALE.** It reads *"has_2yr_history PRODUCED but UNSCORED — blocked on
calibration."* That tag is now **measured 100%** (LP-393-6). IN-12's real blocker is the **wiring** mismatch
LP-393-1 found: IN-12 enumerates `per_document` (tax_return) while `has_2yr_history` is produced `per_borrower`,
so the rule couldn't consume it even though it is calibrated (and the self-employment/tax-return context is a
different measurement than the W-2 scenario anyway). Classified `wiring`; the bar text should be corrected (not
here).

**3. The generated classification doc's "priya_validated: 0/133" is stale.** That column comes from
`rule_kinds.csv` (always false); the live sign-off state is in `activation_bars.yaml`, where **9** bars are now
validated. The `rule_kinds.csv` census is authoritative for *what exists*, not for *validation state*.

**4. Category naming (correcting/confirming the ticket's list).** The real category list from `rule_kinds.csv`
is **19**: Identity, Income, Assets, Occupancy, Credit, Contract, Property, Insurance, DTI, Compliance, Closing,
Title, Fraud, Condo, MI, Program, AUS, REO, LOE. The ticket named "Title, Insurance/Hazard, Condo, Credit,
Property/Appraisal" — all real. Categories the ticket did **not** name but that exist: **Contract (9),
Compliance/TRID (7, all out-of-scope), MI (5), Program/Conv-FHA (5), AUS (4), REO (2), Fraud (6), LOE (2),
Closing (7).** "The small families" resolve to those.

## What this changes about the plan

- **Replace "~130" with the four denominators.** 133 planned / 118 in-scope / 34 written / 24 live. Progress is
  **~20% live of in-scope**, and **84 in-scope rules remain to be written** (plus 10 written-inert to unblock).
- **Extractors unblock the most — by a wide margin.** ~58 of the 84 in-scope unwritten rules sit behind a
  blocker-document extractor (credit report, AUS findings, appraisal, title, insurance, condo, MI cert, FHA).
  This **refines** the plan's framing: `phase3_new_order.md` calls the extractor phase *"the smallest rule
  count"* — the census shows the opposite: **the extractor-gated categories are the largest block of remaining
  rules** (they are still the biggest engineering, but not the smallest count). Sequencing should treat the
  first extractor (likely Credit — 13 rules, the largest single category) as the highest-leverage unlock.
- **One income-calibration wave is the cheapest written-rule win** — IN-8, IN-9, IN-13 (and AS-7) are all
  `needs-calibration`, no new producer or extractor required.
- **Identity is done; Income/Assets are ~half.** Don't re-plan Identity. Income/Assets finish with a small
  mix of calibration + one producer + one calculator + one design call + one wiring fix (all itemized above).
- **Two structural fixes are quick and isolated:** IN-12's wiring re-scope and AS-6's producer-context fix.

## Assumptions & what was inferred (not read)

- **The 84-rule "needs-extractor vs needs-spec" split is INFERRED** from each category's source-document type,
  not from an exhaustive check that each extractor is absent — I verified the extractors that the 34 written
  rules rely on exist (income docs, bank statements, IDs, MISMO), and that no spec exists for the unwritten
  categories, but did not open every extraction schema. The direction (extractors gate the majority) is robust;
  the exact per-category count of "needs-extractor" is approximate (±a few, e.g. how much of Contract reads
  MISMO vs the contract PDF).
- **Blocker classes for the 10 written-inert rules are READ** from `activation_bars.yaml` rationales + specs —
  none guessed. IN-12 is the only one where I overrode the bar's own text (stale), justified in finding 2.
- **"Live" = `ACTIVE_RULE_IDS`** (the registry), the single source of truth; I did not treat a validated-but-
  unlisted bar as live (none exist — the gate invariant holds).
- **Out-of-scope = `kind == out_of_scope`** in `rule_kinds.csv` (15 rules); these are counted as planned but
  excluded from the in-scope denominator.
- No file was modified. This is the only deliverable.
