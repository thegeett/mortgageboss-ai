# LP-969 — Add a step, and "I'll handle it my own way"

- **Ticket:** LP-969 (the owner, 2026-10-08). Series LP-967 to LP-973; the overview is in `LP-967.md`.
- **Source:** the owner: "we have to provide a free way to processor, because what if it require upload
  thing, write draft, or something else." Agreed design: the "Plan screen explained" artifact, board "The
  plan as a path".
- **Status:** built; see "What was built" below.

## What it adds

- **"Add a step"** on every path, with these building blocks:
  - write an email (to anyone; a blank or suggested draft);
  - ask someone to upload (an upload link);
  - upload it myself;
  - check a document;
  - ask the underwriter;
  - something else (a to-do in her words, with Mark done).
- **"I'll handle it my own way"** as the last route on every condition: the path starts empty, and the app
  still sends the emails, watches for replies and checks documents for each step she adds.

## It also closes the push-back gap

After LP-966's review a task cannot carry push back or ask the underwriter, because the server reads those
only from the condition. The whole-condition select appears only where the app proposed one. "Ask the
underwriter" and "push back" become steps she can add to any condition.

## What exists underneath

- **Exist:** drafts to any recipient (`email_draft`); upload links (`upload_links`); evidence checks;
  underwriter drafts.
- **New:** an item created by her with a free-text task, and a step order.

## Done when

- Each building block creates a real step that does what it says.
- "My own way" starts empty.
- Every addition is recorded in the condition's history.
- Peer review.

## What was built

**Almost nothing here is a new kind of step.** Every building block adds a task through `add_item`, or
sets the condition's own step through `set_next_step`. That is why each block does what it says: the
server already drafts, links and checks those. The only new server behaviour is "my own way".

| Block | What it does on the server | Why the promise holds |
|---|---|---|
| Email someone | A task asking that person (`ask_borrower` / `ask_third_party`), in her words | `sync_round_drafts` puts every OPEN ask in its recipient's draft, so it joins the email to them this round. Tested: the added ask gets a `draft_id` |
| Ask the borrower to upload | The same, to the borrower | The borrower's email carries a secure upload link, minted once the plan is confirmed (LP-968 review). No one else gets a link, so this block is borrower-only |
| Upload it myself; Something else | Her own task (`i_will_do_it`, performer: processor) | Its first step now offers Add document: upload, or link from the file (`ItemLinkActions`, LP-953 and LP-958); the checks run on either |
| Check a document on the file | Her task "Check {her words}", then the link dialog opens on it | A linked document's checks run (`check_link`, LP-953) |
| Ask the underwriter; Push back | The condition's own step | `_QUESTIONS` reads them from the condition only, so this closes the LP-966 gap: any condition can now be given one. The block says when it replaces the condition's current step |

**Who she can email** is derived from the performers, minus herself and the appraiser. The appraiser's asks
already go to the lender, which is on the list.

**"I'll handle it my own way"** (`POST /conditions/{id}/plan/own-way`, `condition_plan.handle_own_way`):
- **What it does:** marks every OPEN task not needed, with the reason "You chose to handle this condition
  your own way.", and clears the condition's own step.
- **How it can be undone:** it goes through `update_item` and `set_next_step`. They write the
  `condition_plan_changed` events that `revert_to_suggested` replays, so "Go back to the suggested plan"
  restores the suggestion exactly. Tested: options, statuses, step, notes, and the asks back in their
  drafts.
- **What it leaves alone:** a task asked, answered or done keeps its record.
- **Split parts go first.** An edit to a parent re-splits it, soft-deleting and re-making every OPEN part.
  If the parent were dropped first, its parts would come back as fresh OPEN parts, still in their drafts.
  Mutation-tested.
- **Going back restores the parts too, measured.** The LP-968 review's limitation is that revert finds no
  part, because it matches on the live key and LP-946 gives a part `<base>.<performer>`. That applies to an
  edit recorded against the base key. Own way edits each part itself, so each part's event carries the
  part's own key, and the replay finds it. The split test reverts afterwards and asserts every part is
  OPEN and back in its draft.
- **It is recorded once in the history** as `{"change": "own_way", "count": n}`. Each task's own event is
  recorded too.
- **Where it appears:** in "How it gets done", only while there is something to clear. Once nothing is
  live, the timeline shows "Build your own path".

**"Add a step" is under every condition's timeline, a failed or unread reading included.** That is the
first time such a condition has a way forward on the plan screen.

**"Remove step"** appears on a step she added (origin `manual`, still open), through the existing soft
delete. A step the reading suggested still has only Not needed, as LP-968 decided.

**Found on the way, a sentence that was not true.** The push-back path (LP-967) said "We draft a note …
explaining why it should not apply". `render_question` argues one case itself: the HOI policy start
against Must Not Close Before. Every other push back is drafted as the general question. The step now
says "Review the note, say why it shouldn't apply, and send it", and the Add-a-step hints say the same
for both questions.

**Not done here:**
- The mockup's free-address email ("or any address"): recipients are the performers, and the address is
  set on the draft as before.
- The other routes (LP-970).
- "Describe it" (LP-971).

**Also fixed, measured:** `ownStepPath`'s two questions said the draft is made "when you confirm".
`sync_round_drafts` has made the underwriter draft at plan-ready since LP-968, in the same pass as every
other draft, unless the reading still needs her. Both now say "It is drafted once the plan is ready…".
The send step says "once the plan is confirmed", because only sending waits (`unconfirmed_rounds_for`).

## Review (of `978462fd`)

**Three findings, all fixed here, plus the LP-968 docstring correction this ticket's own probe earned.
The two things that worried me most before reading — a second upload-link minting site, and the
push-back gap being "closed" in the UI while the server still ignored it — are both clean, and the
second is clean in the way that matters: the question blocks go through `set_next_step`, which is the
only place the server reads them from.**

### Finding 1 — Attorney and Title are two labels for one email

`EMAIL_WHO` is derived from `PERFORMER_LABEL` minus two exclusions, which is the right shape: a new
performer is offered without anyone remembering this list. But `condition_plan._RECIPIENT` maps **both**
`title` and `attorney` to the single `title_attorney` email ("Title and attorney share one email",
S3-05). So the To select offered two entries that produce the same draft, with nothing on screen saying
so — pick Attorney, and the ask lands in the title/attorney email exactly as Title would.

`item-links.tsx`'s `ASK_WHO` already excludes it for this reason (LP-955 review). Two lists answering
"who can I ask?" differently is what invites the next divergence, and this is the third time in this
series that one question has had two answers.

**Fixed:** `attorney` joins the exclusions, with the `_RECIPIENT` reason in the docstring. **The lender
stays**, and that remains a deliberate difference from `ASK_WHO`: a free email to the lender is
something she sends, while delegating a TASK to the lender is not — LP-942 routes a lender's or
appraiser's ask into the lender's own draft rather than making it hers. Both halves are asserted, so
the difference is now recorded rather than incidental.

### Finding 2 — a hint that tells her to do what she may have done an hour ago

"Ask the borrower to upload" read *"It goes in the borrower's email, with a secure upload link once you
confirm the plan."* Adding a step to an **already-confirmed** round is a normal flow since LP-968, and
the link then exists at once — so the hint instructs her to confirm something already confirmed.

**Fixed:** "…with a secure upload link." The path's own send step still carries the confirm nuance
("Review the email, and send it once the plan is confirmed"), so the hint does not need to, and a hint
that describes one state is wrong in the other. This is the same lesson as the LP-974 review's "the
tasks below": copy reused across states cannot describe one of them. The test asserts the property
rather than the wording — no block's hint mentions confirming — with the upload block's link promise as
its control.

### Finding 3 — the new component had no test, and "Check a document" rests on an unstated premise

`plan-add-step.tsx` maps seven labels to `(name, performers, option)`, which is what decides what the
server does, and it had no test file: the panel tests drive it but never pin the mapping.

The premise worth pinning is the one behind "Check a document". The panel finds the item it just created
as **the one whose id was not there before**, which it must, because the route returns `ConditionPublic`
and discards `add_item`'s return value. That works only while the block asks exactly one person:
`add_item` calls `split_item`, so a link step with two performers would create a base item **and** its
parts, and the panel would open the picker on whichever the response listed first — a document linked to
the wrong step. It is single-performer today (`["processor"]`), so the heuristic is sound; nothing said
it had to stay that way.

**Fixed** with `plan-add-step.test.tsx`: a link step asks exactly one person; the email block maps the
borrower to `ask_borrower` and anyone else to `ask_third_party`, which is what `recipient_for` reads;
and the two `EMAIL_WHO` properties above. Each fails its own mutation — the attorney restored, the hint
restored, and the link step given two performers.

**The residual, named rather than fixed:** `before` comes from the component's cached items, so two
rapid adds where the second is "Check a document" could still diff against a stale snapshot. The exact
fix is for the route to return the created item's id, which is an API change rather than a review's.

### Also fixed: the LP-968 docstring this ticket's probe corrected

`revert_to_suggested`'s "WHAT IT LEAVES ALONE" list said a split part is left alone "because the `from`
recorded against the base key finds no part to restore". That is true of a base-key edit and reads as
though parts are never restored. The builder probed it instead of accepting either answer — 1947 split
to title and insurance, then own way, then revert, both rows back to OPEN with their draft — and parts
**are** restored when the edit was recorded against the part's own key, which is what `handle_own_way`
does by editing each part. The docstring now distinguishes the two cases and says the split itself is
never undone either way. My sentence was over-broad; the correction is theirs.

### Checked and not findings

- **Every one of the four roots reaches `mint_upload_link`, and the LP-968 gate holds anyway.** This was
  my open item, and the direct-grep answer was not enough: a closure over `add_item`, `set_next_step`,
  `update_item`, `remove_item` and `handle_own_way` finds the path in all five —
  `→ _resync_drafts → resync_file → sync_round_drafts → render → mint_upload_link` (the closure was
  sanity-checked by confirming it finds the known path from `render` itself, so a "no" would have meant
  something). It is safe because of the gate the LP-968 review added: before confirm `render` does not
  mint at all, and after confirm the url already exists, so no second clock starts. The one new window
  is a borrower draft created for the first time AFTER confirm — she adds a borrower ask to a confirmed
  round — where the link is minted as she adds the step rather than as she sends. That is minutes, not
  the days the LP-968 finding was about, and it is the same timing the original design had.
- **The push-back gap is genuinely closed, at the layer the server reads.** The two question blocks emit
  `kind: "own_step"` and go through `set_next_step`, never `add_item` — so they set the CONDITION's step,
  which is the only thing `_QUESTIONS` reads (`condition_drafts.py:739, :747, :818, :1116`). That is the
  gap my LP-966 narrowing created, and it is closed by giving her the condition-level door rather than
  by loosening the item-level one, which is the right direction.
- **"My own way" does not read as unworked, and my challenge to that was wrong.** `handle_own_way`
  deletes nothing: it marks every OPEN task NOT_NEEDED through `update_item` and clears `next_step`, so
  the items remain on the condition, `items.length === 0` is false, and the dropped-task counting
  LP-974 introduced is exactly what keeps it out of "We couldn't work out what this one needs". I had
  read "the path starts empty" as "zero items" when it describes the live path, and told the builder
  their explanation could not be the mechanism. It was.
- **A step she writes keeps the dotted-key premise safe.** `add_item` mints `manual_{n}`, with no dot,
  so `library_item_for`'s split on the first dot is untouched and LP-953's "no library key contains a
  dot" test still describes the world.
- **`EMAIL_WHO` being derived is the right shape** and worth saying so: it is the opposite of the
  hand-written `ASK_WHO` the LP-955 review had to correct for being three recipients short.
