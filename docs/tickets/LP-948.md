## (a) Labels, never item keys

`condition_drafts.item_words(condition, item)` names an item for a sentence, via `in_sentence`, and never
uses the key:
- a library item by the LIBRARY's wording: its `label`, else its library `name`;
- a part (LP-946, key `<library key>.<performer>`) as its library item, matched on the key before the
  dot (no library key has a dot: 0 of 52);
- any other item (a re-ask, one she added) by its own name.

**Why the library's wording and not the item's name, found by the full run.** The first version used
the item's own name, and the full suite caught 6637 reading "Earnest money: source of the $2,850.00
and clearance": an item's name carries its figure once the reading names the amount. A side-column
label does not repeat a figure, so a library item is named by the library. Two places spelled a key:
- `condition_label`'s partial form, "Short: part and part", did `key.replace("_", " ")`;
- the "Other drafts this round" summary did the same on the first item.
A re-ask's key (`reask_3f2a9b1c`) and, since LP-946, a part's key (`source.employer`) were therefore
printed to her. The frontend dialog renders only these server strings; it has no key of its own to
leak (checked).

## (b) Round matching: the code first, then the wording, and a tie is a question

`condition_enrich._choose` is one rule for both paths (a draft round's JSON rows, and an imported
round's conditions):
1. **The lender code.** A code the PDF prints that exactly one remaining row carries decides it,
   whatever the wording.
2. **The wording** (the text fingerprint): among the rows with that code when several carry it,
   otherwise among all remaining rows.
3. **A tie** (more than one row left) is NOT picked. Nothing is filled and nothing is added. The PDF
   row becomes a question in `EnrichResult.questions`, and the S1-09 callout shows it: "Which pasted
   condition is the PDF's 5868? Conditions 3 and 5 read the same. Nothing was filled for it; set the
   code on the right one." It uses codes and row numbers only, never the lender's wording (ADR-405).

**Tied rows stay candidates.** Two identical pasted rows and two identical PDF rows are the ordinary
duplicate case, and each PDF row is asked about in turn; neither is added as "new". Tied rows are not
reported as "not on the PDF" either.

This replaces the dict-by-fingerprint that the LP-944 review found: last row wins, from an unordered
query, so which condition was filled was the planner's choice. The LP-944 doctrine ("ordering makes
the answer reproducible while somebody decides") is met by not deciding at all. The owner decided
that she does.

## (c) A withdrawn condition's items

`condition_plan._items_by_condition` joins the parent and requires `Condition.deleted_at IS NULL`.
Withdrawing (LP-940) soft-deletes the condition and leaves its items as they were, so Undo restores it
whole; the join makes every reader of the map agree with the lists.

## (d) The assertion that could not fail

`test_insurance_wiring.py::test_binder_materializes_annual_over_twelve` asserted
`"1200" in reason and "12" in reason`. The second half cannot fail while the first holds. It now
asserts the whole division: `reason.endswith("(annual premium 1200 ÷ 12)")`.

**The reading taken for (a) (STOP AND ASK 5).** The S3-04 mock prints "Earnest money: source and
clearance", and "source" and "clearance" are library item KEYS. The owner's words are "labels, never
internal item keys", so an item is named by its library label, else its own name, and that line now
reads "Earnest money: source of the earnest money and clearance". If the mock's shorter words are
wanted, `item_words` can use a library key for a library item and a name only for generated keys
(re-asks, parts): one line.

**How the tie reaches her (b).** `EnrichResult.questions` is carried to `ConditionEnrichResult.questions`
(a new field) and rendered under S1-09's success callout. `warnings` has no reader on screen, so a
question put there would never have been seen.
