## Part 1 — Code

### 1. The test command

```
python -m app.scripts.follow_up_clock <communication_id> --days N
```

It moves ONE email's conversation back N days, as if N days had passed:

- the original's follow-up clock, and `paused_at` if it is set;
- the send times (`send_requested_at`, `sent_at`) of the original and of each of its reminders:
  what the rate limit counts;
- the replies from the original's recipient on that file (`InboundMessage.created_at`, and that
  reply's row on the file), so "a reply since the clock" keeps its order.

Nothing else moves. **Other emails to the same address keep their times**, so the 5-minute and
3-a-day limits still count them.

It refuses outside dev and staging (before touching the database), a reminder's id (it names the
original to use instead), anything that is not an email sent from the app, and `--days` below 1. It
prints every timestamp it moved, before and after, the follow-up's status and the new
`next_reminder_at` (as the screen shows it: none unless `on` with reminders left). A real run in dev,
on LP-1014's test file LF-JD4T (its follow-up has spent both reminders):

```

original         0f1b1958-… follow_up_paused_at  2026-11-08T01:35:51.743193+00:00 -> 2026-11-07T01:35:51.743193+00:00
```

The same command with a reminder's id: `Refused: This is a reminder; pass the email it follows up
(0f1b1958-d910-48f6-a8fa-4154109eec0e).` The first version printed a next date for this spent

### 2. A blocked address stops it

**Found while reading the code:** the job already stopped a follow-up on a `suppressed` refusal
(since LP-1013: `stopped_suppressed`, test `test_a_suppressed_recipient_stops_it`). §15d's "retried
every 15 minutes forever" describes the rate limit, not this. What was missing, now added:

- its own log line, `follow_up_recipient_suppressed` (a rate-limit refusal keeps `follow_up_refused`
  and is still retried);
- `recipient_suppressed` on each Follow-ups list row (one query for the whole list, normalised as
  `is_suppressed` does);
- the bar and the list say **"Stopped — address blocked (bounce or complaint)"**, no buttons.

A bounce both fails the email and blocks the address; the screen then says "Stopped — the email
failed" (the failure is named first).

### 3. Closed or withdrawn file

The job's candidate query skips a file whose status is `closed` or `withdrawn`, as it skips a
deleted one (`DONE_FILE_STATUSES`). The follow-up stays `on`; set the file back and it goes again.

### 4. No reply gets Stop

"No reply" offers **Send now** and **Stop**, in the bar and the list.

## Open

- **Row lock during Stop has no test.** Stop takes no lock of its own: if the job holds the row
  (`FOR UPDATE SKIP LOCKED`), Stop's update waits for the job to commit and then sets `stopped`
  (the reminder that run sent stays sent); if Stop holds it first, the job skips the row. A test of
  that needs two database connections that both see the row, so the row must be committed, which
  the test suite forbids (`tests/conftest.py`: tests never commit). Options: a test that commits
  and cleans up after itself (a first in this suite), or scenario 22's style of check in staging.
- **The 3-a-day limit may bite in Session A.** Every new email to your Gmail counts for 24 hours
  until the command moves it. If a Send is refused "already emailed 3 times today", move the
  scenario's earlier email (or wait); it is the limit working, not a fault.
