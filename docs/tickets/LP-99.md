# LP-99 — Parse `refinance_type` (cash-out vs. rate/term) from MISMO

- **Ticket:** LP-99 (first ticket of the refinance epic, LP-99..101)
- **Epic:** Phase 3 — Refinance support
- **Status:** Completed
- **Date:** 2026-07-01

## Summary

`refinance_type` (`RefinanceType`: `rate_term` | `cash_out`) exists on `LoanFile` and the LTV
engine already consumes it correctly — **but nothing ever populated it.** A cash-out refi imported
from MISMO landed with `refinance_type = NULL`, and the LTV service treats a null refi as rate/term
→ the **looser** LTV limit. That is the dangerous, permissive direction: a cash-out refi (stricter
max) was silently getting the rate/term max.

The fix parses the MISMO cash-out determination at import and populates `refinance_type`, so the
LTV's **existing correct** cash-out path auto-triggers. An **undetermined** refi is never guessed to
the looser limit — it is **surfaced** (a needs item + a parse warning) and made correctable on the
Overview. Purchases are unaffected. The LTV engine itself is unchanged. See **ADR-224**.

## The MISMO representation (investigated first)

MISMO 3.4 expresses the cash-out kind under the loan's `REFINANCE` container:

- `LOAN/REFINANCE/RefinanceCashOutDeterminationType` — `CashOut` / `LimitedCashOut` / `NoCashOut`.
- `LOAN/REFINANCE/RefinanceCashOutAmount` — a corroborating dollar amount.

The one real fixture (`MISMO16940192.xml`, Mahesh) is a **purchase** — it has no `REFINANCE`
element — so the refi path is exercised with a **constructed** refi variant
(`tests/mismo/synthetic.py::refinance_variant`), not a real refi export. A real refi MISMO file (and
an e2e over it) is **LP-101**, deferred.

## The mapping (grounded starter — pending expert review)

`app/mismo/import_service.py::_CASH_OUT_DETERMINATION`:

| MISMO `RefinanceCashOutDeterminationType` | `RefinanceType` | LTV limit |
| --- | --- | --- |
| `CashOut` | `CASH_OUT` | **stricter** `conv.ltv.cash_out_max` |
| `NoCashOut` | `RATE_TERM` | shared purchase/rate-term `conv.ltv.purchase_max` |
| `LimitedCashOut` | `RATE_TERM` | shared purchase/rate-term max |

`LimitedCashOut → RATE_TERM` is a **grounded starter, pending expert review**: MISMO's
"limited cash-out" is the agency limited-cash-out refinance (Fannie LCOR), which carries the *same*
(higher) LTV limits as a rate/term refi — but the agency framing should be confirmed. (The LTV-max
thresholds themselves are LP-74 starter rules already flagged for review.)

**Fallback when the type is absent:** a positive `RefinanceCashOutAmount` ⇒ `CASH_OUT`; an explicit
zero ⇒ `RATE_TERM`. Keys are lower-cased/stripped for tolerance.

## Undetermined refi — surfaced, never silently looser

A refinance whose cash-out kind can't be determined (no determination type, no amount) keeps
`refinance_type = NULL` and is surfaced two ways at import:

- **A parse warning** on the `MismoImport` record ("Refinance type … could not be determined …").
- **A FLOOR needs item** — "Confirm refinance type: cash-out vs. rate/term" — directing the
  processor to set it on the Overview.

It is **never** silently defaulted to the looser limit. (The LTV still reads null-as-rate/term for a
not-yet-corrected file, but the ambiguity is now visible and actionable rather than hidden.)

## The correction path (made real)

The needs item says "set it on the Overview," but `refinance_type` was **not** exposed for editing —
it was listed in `_VERIFICATION_BASELINE_FIELDS` (editing it marks verification stale) but absent
from `LoanFileUpdate`, so there was no way to set it. LP-99 wires the path end-to-end:

- **Backend:** `refinance_type` added to `LoanFileUpdate` (PATCH input) and to `LoanFileDetail`
  (read). Editing it marks the cross-source verification stale (it changes the LTV limit) — the
  baseline set already anticipated this.
- **Frontend:** the Overview loan editor shows a **Refinance type** select **only for refinances**;
  correcting an undetermined refi PATCHes `refinance_type` and refreshes the coupled LTV/verification
  reads.

## Scope boundaries

- **The LTV engine is unchanged** — it already consumed `refinance_type` correctly. LP-99 only fills
  the field and surfaces the gap. Purchases are entirely unaffected (`refinance_type` stays null, no
  needs item, no warning).
- **Not in scope (later epic):** purpose-gating rules (LP-100); a real refi MISMO fixture + e2e
  (LP-101).

## Assumptions & decisions

- `LimitedCashOut → RATE_TERM` mapping is a grounded starter (agency LCOR framing) — flagged for
  expert review, same as the LP-74 LTV thresholds it feeds.
- The cash-out **amount** is used only as a fallback signal when the determination type is absent.
- The Overview refinance-type control is shown by the file's current purpose; switching a purchase to
  refinance and saving surfaces the control on the refreshed view.
- The not-yet-corrected undetermined refi still reads null-as-rate/term in the LTV (we don't block the
  calculator), but the ambiguity is now visible (needs item + warning) — the deliberate choice over a
  hard-fail or a silent stricter default.
