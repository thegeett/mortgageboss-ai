# LP-975 — A carried condition's plan is in force only if she confirmed it

- **Ticket:** LP-975 (the owner, 2026-10-09: "yes, write LP-975").
- **Source:** the LP-973 review, finding 3 ("confirming round 2 can put an unreviewed plan in force"),
  reported rather than fixed; the builder's focus area 5 asked the same question.
- **Status:** built and tested. The full backend suite and the staging backfill measurement are still open; see "Open".

## The problem

LP-973 made round 2's plan show only what is new on the sheet. A condition seen again keeps its plan
(`build_plan`'s carry-over, `carry_plan`) and is counted in one line, "N conditions from earlier rounds
keep their plan".

That is right when she confirmed that plan on its own round. It is wrong when she did not, which happens
if round 2 is imported while round 1's plan is still waiting:

- **The line says "keeps their plan"** about a plan she never approved.
- **The plan's in-force rule reads the wrong round.** `_plan_in_force` asks whether the condition's
  `last_seen_round_id` has a confirmed plan. For a condition seen again, that is the new round. So
  confirming round 2 puts the carried plan in force for a condition she was never shown: drafts resync,
  and `apply_step_status` can move it to Ready.
- **Nothing on the screen catches it.** `blocking_codes` lists readings that need her, not plans she has
  not confirmed, so the carried condition is neither shown nor blocking.

**Evidence, stated honestly:** the review traced this in the code (the panel's row filter,
`_plan_in_force`, `round_plan_blockers`) but did not reproduce it with two rounds. The first step of this
ticket is to reproduce it.

## A second question the same rule raises (measure it, do not assume it)

The same rule may also misfire in the other direction. When round 2 is imported, a carried condition's
`last_seen_round_id` moves to round 2, whose plan is not yet confirmed. So a plan she DID confirm on round
1 may read as "not in force" until she confirms round 2. Check what this does to:
- `apply_step_status`;
- the send guard (`unconfirmed_rounds_for`, LP-968);
- draft resync (`_resync_drafts` and `_plan_drafted`).

## Proposed fix

**The plan's approval belongs to the condition, not to whichever round last listed it.**

1. **Server:** a `plan_confirmed_at` timestamp on the condition (migration). `confirm_round_plan` stamps
   every condition on the plan she confirmed. `_plan_in_force` reads the condition's own stamp. A
   condition seen again keeps its stamp; a new one starts without one.
2. **Payload:** `ConditionPublic.plan_confirmed_at`, so the screen knows.
3. **The plan screen** shows a condition when it is new on this round, OR its plan was never confirmed,
   OR it blocks Confirm. The carried line counts only conditions whose plan she did confirm, so "keeps
   their plan" is true of every one it counts.
4. **Backfill** for existing rows: stamp each condition whose `last_seen_round_id` round has
   `plan_confirmed_at`. That is exactly what today's rule already treats as in force, so no condition
   changes state on deploy.

**Interim, if wanted before this:** `round_plan_blockers` could list a carried condition whose earlier
plan was never confirmed. That keeps it on screen through the rule LP-973 already uses for blocking
conditions. It is cheap, but it blocks Confirm instead of letting her confirm the carried plan along with
the new ones, so this ticket replaces it.

## What was built

**The rule** (`condition_plan.plan_confirmed`, read by `_plan_in_force` and by the send guard
`unconfirmed_rounds_for`): a condition's plan is confirmed if it carries a stamp, OR if its last-seen
round's plan is confirmed.

- **Why the round stays as a fallback.** A condition added by hand to a confirmed round is never stamped:
  `confirm_round_plan` returns early on a confirmed round. A stamp-only rule would hold its steps, and its
  emails, for ever. This was found while building; the proposal above did not have it.
- **Stamped:**
  - `confirm_round_plan` stamps every condition on the round that has no stamp yet. An earlier stamp is
    kept, because that plan was already hers.
  - `ConditionPublic.plan_confirmed_at` carries the stamp to the screen.
- **The second question, answered from the code: yes, and it was worse than "early".** The send guard
  asked the last-seen round, so once round 2 was imported, round 1's email for a condition seen again
  was refused with "Confirm the plan for round 2 first". `_plan_in_force` had the same blind spot.
  - The guard now skips a stamped condition.
  - Covered by `test_a_plan_she_confirmed_stays_in_force_when_round_two_lists_it_again`.
- **The backfill (migration `40f6b9efb93c`)** stamps each condition with the latest confirm of any round
  it appeared on (its `condition_created` / `condition_seen_again` events), or of its last-seen round.
  - The second half is today's rule, so nothing in force today stops being in force.
  - The first half stamps conditions seen again after a confirmed round, which is the case this ticket
    fixes.
  - This is wider than the "today's rule" the proposal named, deliberately: today's rule alone would
    leave exactly those conditions unstamped.
- **The screen:**
  - **Round 2's plan** also shows a condition seen again whose plan she never confirmed (no stamp). Its
    "keep their plan" line counts only stamped ones.
  - **The list's "Plan not confirmed yet" marking** covers the same case, limited to conditions on the
    newest round.
- **`readonly.conditions`:** the column stays out of the view (it is in the drift guard's EXCLUDED list).
  It is a timestamp that names nobody.

## The blocker that cleared itself

The first backend run failed with "column conditions.plan_confirmed_at does not exist". The shared test
database held tables from an earlier run killed before its `drop_all`, and `create_all` never adds a
column to an existing table.
- Dropping them by hand was refused by the session's permission system.
- The failed run's own teardown then ran `drop_all`. The peer session measured 0 tables in both
  `mortgageboss_dev_test` databases (ports 5432 and 5433), and the next run built the schema fresh.
- **This will recur.** Any run killed between `create_all` and `drop_all` leaves the old schema, and host
  memory pressure has killed several today.

## Open

- **The full backend suite.** Not run: swap was about 25 of 25.6 GB used, which is what has been killing
  full runs. Covered instead by the conditions folder, the readonly guard and the migration tests above.
- **The backfill on real data.** The query is ready (read-only, against the `readonly` views), but staging
  was shut down when it was tried. It should show `lose_force = 0`, which the fallback guarantees by
  construction, and a count of `gain_force`: conditions seen again after a confirmed round, which today's
  rule wrongly treats as unconfirmed.
- **Peer review.**

The backfill query, for `./scripts/deploy staging query <file>` once staging is up:

```sql
WITH stamp AS (
  SELECT condition_id, max(at) AS at FROM (
    SELECT e.condition_id, r.plan_confirmed_at AS at
      FROM readonly.condition_events e JOIN readonly.condition_rounds r ON r.id = e.round_id
     WHERE e.kind IN ('condition_created','condition_seen_again') AND e.condition_id IS NOT NULL AND r.plan_confirmed_at IS NOT NULL
    UNION ALL
    SELECT c2.id, r2.plan_confirmed_at
      FROM readonly.conditions c2 JOIN readonly.condition_rounds r2 ON r2.id = c2.last_seen_round_id
     WHERE r2.plan_confirmed_at IS NOT NULL
  ) x GROUP BY condition_id)
SELECT
  count(*) AS conditions,
  count(*) FILTER (WHERE r.plan_confirmed_at IS NOT NULL) AS in_force_today,
  count(*) FILTER (WHERE s.at IS NOT NULL OR r.plan_confirmed_at IS NOT NULL) AS in_force_after,
  count(*) FILTER (WHERE r.plan_confirmed_at IS NOT NULL AND s.at IS NULL) AS lose_force,
  count(*) FILTER (WHERE r.plan_confirmed_at IS NULL AND s.at IS NOT NULL) AS gain_force
FROM readonly.conditions c
JOIN readonly.condition_rounds r ON r.id = c.last_seen_round_id
LEFT JOIN stamp s ON s.condition_id = c.id
WHERE c.deleted_at IS NULL
```
