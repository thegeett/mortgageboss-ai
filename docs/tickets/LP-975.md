# LP-975 — A carried condition's plan is in force only if she confirmed it

- **Ticket:** LP-975 (the owner, 2026-10-09: "yes, write LP-975").
- **Source:** the LP-973 review, finding 3 ("confirming round 2 can put an unreviewed plan in force"),
  reported rather than fixed; the builder's focus area 5 asked the same question.
- **Status:** built and tested. The full backend suite and the staging backfill measurement are still open; see "Open".

## The problem

LP-973 made round 2's plan show only what is new on the sheet. A condition seen again keeps its plan
(`build_plan`'s carry-over, `carry_plan`) and is counted in one line, "N conditions from earlier rounds
keep their plan".

That is right when she confirmed that plan on its own round. It is wrong when she did not, which happens
if round 2 is imported while round 1's plan is still waiting:

- **The line says "keeps their plan"** about a plan she never approved.
- **The plan's in-force rule reads the wrong round.** `_plan_in_force` asks whether the condition's
  `last_seen_round_id` has a confirmed plan. For a condition seen again, that is the new round. So
  confirming round 2 puts the carried plan in force for a condition she was never shown: drafts resync,
  and `apply_step_status` can move it to Ready.
- **Nothing on the screen catches it.** `blocking_codes` lists readings that need her, not plans she has
  not confirmed, so the carried condition is neither shown nor blocking.

**Evidence, stated honestly:** the review traced this in the code (the panel's row filter,
`_plan_in_force`, `round_plan_blockers`) but did not reproduce it with two rounds. The first step of this
ticket is to reproduce it.

## A second question the same rule raises (measure it, do not assume it)

The same rule may also misfire in the other direction. When round 2 is imported, a carried condition's
`last_seen_round_id` moves to round 2, whose plan is not yet confirmed. So a plan she DID confirm on round
1 may read as "not in force" until she confirms round 2. Check what this does to:
- `apply_step_status`;
- the send guard (`unconfirmed_rounds_for`, LP-968);
- draft resync (`_resync_drafts` and `_plan_drafted`).

## Proposed fix

**The plan's approval belongs to the condition, not to whichever round last listed it.**

1. **Server:** a `plan_confirmed_at` timestamp on the condition (migration). `confirm_round_plan` stamps
   every condition on the plan she confirmed. `_plan_in_force` reads the condition's own stamp. A
   condition seen again keeps its stamp; a new one starts without one.
2. **Payload:** `ConditionPublic.plan_confirmed_at`, so the screen knows.
3. **The plan screen** shows a condition when it is new on this round, OR its plan was never confirmed,
   OR it blocks Confirm. The carried line counts only conditions whose plan she did confirm, so "keeps
   their plan" is true of every one it counts.
4. **Backfill** for existing rows: stamp each condition whose `last_seen_round_id` round has
   `plan_confirmed_at`. That is exactly what today's rule already treats as in force, so no condition
   changes state on deploy.

**Interim, if wanted before this:** `round_plan_blockers` could list a carried condition whose earlier
plan was never confirmed. That keeps it on screen through the rule LP-973 already uses for blocking
conditions. It is cheap, but it blocks Confirm instead of letting her confirm the carried plan along with
the new ones, so this ticket replaces it.

## What was built

**The rule** (`condition_plan.plan_confirmed`, read by `_plan_in_force` and by the send guard
`unconfirmed_rounds_for`): a condition's plan is confirmed if it carries a stamp, OR if its last-seen
round's plan is confirmed.

- **Why the round stays as a fallback.** A condition added by hand to a confirmed round is never stamped:
  `confirm_round_plan` returns early on a confirmed round. A stamp-only rule would hold its steps, and its
  emails, for ever. This was found while building; the proposal above did not have it.
- **Stamped:**
  - `confirm_round_plan` stamps every condition on the round that has no stamp yet. An earlier stamp is
    kept, because that plan was already hers.
  - `ConditionPublic.plan_confirmed_at` carries the stamp to the screen.
- **The second question, answered from the code: yes, and it was worse than "early".** The send guard
  asked the last-seen round, so once round 2 was imported, round 1's email for a condition seen again
  was refused with "Confirm the plan for round 2 first". `_plan_in_force` had the same blind spot.
  - The guard now skips a stamped condition.
  - Covered by `test_a_plan_she_confirmed_stays_in_force_when_round_two_lists_it_again`.
- **The backfill (migration `40f6b9efb93c`)** stamps each condition with the earliest confirm of any round
  it appeared on (its `condition_created` / `condition_seen_again` events), or of its last-seen round.
  - The second half is today's rule, so nothing in force today stops being in force.
  - The first half stamps conditions seen again after a confirmed round, which is the case this ticket
    fixes.
  - This is wider than the "today's rule" the proposal named, deliberately: today's rule alone would
    leave exactly those conditions unstamped.
- **The screen:**
  - **Round 2's plan** also shows a condition seen again whose plan she never confirmed (no stamp). Its
    "keep their plan" line counts only stamped ones.
  - **The list's "Plan not confirmed yet" marking** covers the same case, limited to conditions on the
    newest round.
- **`readonly.conditions`:** the column stays out of the view (it is in the drift guard's EXCLUDED list).
  It is a timestamp that names nobody.

  - There is no `lose_force` column, because the stamp contains the last-seen half by definition.

The backfill query, for `./scripts/deploy staging query <file>` once staging is up (corrected after the
review; the stamp is built from the events alone, so the last-seen half can be seen doing its work):

```sql
WITH event_stamp AS (
  SELECT e.condition_id, min(r.plan_confirmed_at) AS at
    FROM readonly.condition_events e JOIN readonly.condition_rounds r ON r.id = e.round_id
   WHERE e.kind IN ('condition_created','condition_seen_again')
     AND e.condition_id IS NOT NULL AND r.plan_confirmed_at IS NOT NULL
   GROUP BY e.condition_id)
SELECT
  count(*) AS conditions,
  count(*) FILTER (WHERE r.plan_confirmed_at IS NOT NULL) AS in_force_today,
  count(*) FILTER (WHERE r.plan_confirmed_at IS NOT NULL OR s.at IS NOT NULL) AS stamped_after,
  count(*) FILTER (WHERE r.plan_confirmed_at IS NOT NULL AND s.at IS NULL) AS kept_only_by_last_seen,
  count(*) FILTER (WHERE r.plan_confirmed_at IS NULL AND s.at IS NOT NULL) AS gain_force
FROM readonly.conditions c
JOIN readonly.condition_rounds r ON r.id = c.last_seen_round_id
LEFT JOIN event_stamp s ON s.condition_id = c.id
WHERE c.deleted_at IS NULL
```

## Review (peer session, 2026-10-09)

Reviewed at `31346197`. Three findings, two of them fixed here; the third predates this ticket and is
recorded for its own. Every claim below was run, not read: the reproductions are named, and each fix was
mutated to prove the new test is about it.

### 1. The send went condition-level and the borrower's upload link stayed round-level (fixed)

`_plan_confirmed_for` asked the DRAFT'S ROUND whether the plan was confirmed, and this ticket made the
send ask each CONDITION. The call site says why that gate exists, in its own words: "Nothing is sent
before confirm (`unconfirmed_rounds_for`), so there is no reason for the link to exist before it either."
That justification lives in another function, and this ticket changed it — so the two stopped agreeing.

Reproduced: round 1 confirmed and its borrower email sent, round 2 imported, a new ask added to a
condition round 2 carried. Round 2's borrower draft then holds only conditions she has confirmed, so
`unconfirmed_rounds_for` returns `[]` and the email can be sent — while `_plan_confirmed_for` returned
False, because round 2 itself is unconfirmed, and `render_borrower` omits the upload paragraph silently.
The borrower is asked to upload documents with no link to upload to.

Fix: `_plan_confirmed_for` asks the send's own question instead of keeping a second copy of the rule.
Test `test_the_upload_link_follows_the_send_not_the_round`, with the positive control that round 1's sent
email carried a link, and a negative control that takes the stamp away again and watches both the send
and the link refuse together. Mutations: the old round-level rule fails it; a gate that always allows
fails it on the negative control.

### 2. A task she cancelled stayed in an earlier round's unsent email, and that email can now be sent (fixed)

`sync_round_drafts` maintains the items of the conditions ITS round lists. A condition seen again moves
to the newer round, and a round that re-lists conditions without adding anything new never has a ready
plan (`build_plan` sets `plan_ready_at` only `if outcome.planned`), so it gets no drafts of its own. Its
asks stay in the earlier round's unsent drafts, which that round's sync no longer iterates.

Reproduced on round 1's "lo" draft, which asks for 1228's Change-of-Circumstance re-disclosure, with
round 2 re-listing 1228: "Not needed" with a reason moved the task to `not_needed` and **left it in the
email**, against `update_item`'s own docstring ("The task leaves the plan … and its draft"). Before this
ticket that email could not be sent (round 2 unconfirmed held it); with the stamp it can, so a cancelled
task goes out in a real email.

Two causes, both needed, each mutated separately:
- `sync_round_drafts` now also maintains the items that already sit in THIS round's drafts, whatever
  round their condition has moved to. Placement is unchanged: `_open_draft` has always looked a draft up
  by file and recipient, never by round.
- `_plan_drafted` asked the condition's own round whether drafts exist, while what it gates (`resync_file`)
  is file-wide by design. It now asks the file, which is the question the call makes.

Test `test_a_task_she_cancelled_leaves_an_earlier_rounds_draft`, with a control that the rest of the
email is untouched (and an assertion that there IS a rest, so the control is not vacuous).

### 3. The round fallback admits more than the condition she adds by hand (reported, not fixed)

`plan_confirmed`'s fallback is documented as being for "a condition that joined a round after its plan was
confirmed (one she adds by hand)". Measured: it admits a second class that is not hers. `condition_enrich.
_merge_conditions` creates conditions on an IMPORTED round — `ENRICHABLE` keys on `status`, and confirming
a plan does not change it — so attaching a lender PDF to a round whose plan she confirmed created four
conditions with `plan_confirmed_at = None` and `plan_confirmed() == True`: in force at once, with the plan
the reading proposed, never on a plan screen. `merge_attachment_into_round` is a second door onto the same
path — **and the builder's correction of this sentence is right: it is her action, not the letter's.** It
has one caller, `POST …/inbound/attachments/{id}/condition-round` with `attach_to_round_id` and a
`current_user`, so she picks the round for the attachment. What she is never shown is the plan of the
conditions the merge then adds. The original wording, "a forwarded letter reaches it with no click at
all", overstated the door and is withdrawn.

Not fixed here, and not a regression: the old round-level rule answered the same way. Making those
conditions wait would need a screen on which she could confirm them, and `RoundPlanPanel` returns null once
`confirmed_at` is set (and also when `planned === 0`). That is a ticket, not a line. `plan_confirmed`'s
docstring now states the real scope so the next reader does not take the fallback for the manual door.

### 4. `lose_force` in the staging query cannot be non-zero

The measurement query above reports `lose_force` as `r.plan_confirmed_at IS NOT NULL AND s.at IS NULL`.
The `stamp` CTE's second branch is `conditions JOIN their last-seen round WHERE r2.plan_confirmed_at IS NOT
NULL` — unconditional — so every row with a confirmed last-seen round has a stamp by construction, and that
column is 0 whatever the data says. Read as evidence it would mean "nothing loses force", which is true but
not because the query found it.

The number worth measuring is how much the last-seen half is carrying: build a stamp from the EVENT branch
alone and count `r.plan_confirmed_at IS NOT NULL AND event_stamp.at IS NULL` — conditions that are in force
today only by today's rule. `gain_force` is sound as written.

### The five questions asked, answered

1. **Does the round fallback reopen direction 2 anywhere?** Yes — finding 3, measured.
2. **Writers of conditions on a round with no appearance event?** No gap that loses force, and the reason is
   that the backfill's second half is unconditional: anything in force today keeps it. `condition_enrich`
   emits `CONDITION_CREATED` (its own comment records that an earlier version did not), so the only rows
   missing an earlier round's event are pre-LP-907-fix enrich rows, which cannot regain force and do not
   have it today either. One inconsistency: the backfill takes `max(at)`, the LATEST confirm, while the code
   keeps the EARLIEST (`if condition.plan_confirmed_at is None`). Only truthiness is read today, so nothing
   on screen is wrong, but the two halves disagree about what the timestamp MEANS.
3. **Other readers of round-level confirmation.** `_plan_confirmed_for` was a condition question in disguise
   (finding 1) and `_plan_drafted` was a file question in disguise (finding 2); `resync_file` is genuinely
   round-level and is left alone.
4. **`clear_for_reading` leaves the stamp.** Consistent with what a confirmed round already does, and the
   re-read is her own action on drafts she reviews before sending. What this ticket changes is that a
   carried condition on an UNCONFIRMED round now gets its re-read plan in force at once, where the round
   gate used to hold it. I did not reproduce a harm from that and am not claiming one.
5. **Does Confirm stamp the unstamped carried conditions the panel shows?** Yes, and by construction:
   `confirm_round_plan` stamps `last_seen_round_id == round_.id`, which is exactly the panel's `onRound`
   set. The wrinkle is the other direction — the panel is hidden entirely when `planned === 0`, so a round
   that re-lists conditions and plans nothing new offers no Confirm button, which is the state finding 2's
   stranded drafts live in.

### Verified rather than taken on trust

- The frontend's two new clauses, mutated independently: removing `!condition.plan_confirmed_at` from the
  panel's `shown`, and removing the list view's new disjunct, each fail exactly the LP-975 test that claims
  them (3/3 as reported).
- `unplannedIds`' first disjunct has no stamp check, which would mark a confirmed condition first seen on
  the newest round — unreachable, because `planGatePhase` returns "list" as soon as `plan.confirmed_at` is
  set, and `unplannedIds` is then undefined.
- `plan_confirmed_at?: string | null` is optional on the wire type while the server always sends it. The
  optional reading is the safe direction (absent reads as "not confirmed", so a condition is shown rather
  than hidden), so it is left as it is.

### 5. The branch the ticket is FOR was the one no test held (fixed)

The captured-statement test closes "a second statement" — `(sql,) = captured` raises on two — but not a
NARROWER one. Dropping `'condition_seen_again'` from the backfill's `kind` filter passes both of the
tests that existed, because in each fixture every condition was CREATED on a round that ends up
confirmed, and the unconditional last-seen half catches whatever is left.

Isolating that branch needs three rounds, because the condition must have appeared on a confirmed round
that is neither where it was created nor where it was last seen: created on round 1 (left unconfirmed),
seen again on round 2 (confirmed), seen again on round 3 (left unconfirmed). Only the seen-again branch
can stamp it. `test_the_backfill_needs_its_seen_again_half_and_nothing_else_covers_it` does that.

Measured, in that order: removing `'condition_seen_again'` from the `kind` filter now gives **1 failed,
10 passed** — the one failure is the new test, and the two backfill tests that existed before it are
among the ten that still pass. That is the finding and its fix in one line of output.

### 6. `min()` agrees with the code in one confirm order and not in the other (test added, SQL left alone)

The builder's own second question, and the answer is that it can differ. Reverse the fixture's order —
round 2 imported FIRST, so the conditions have already moved, then round 1 confirmed, then round 2 — and
`confirm_round_plan` stamps a carried condition with ROUND 2's time, because round 1's confirm no longer
matched it (`last_seen_round_id == round_.id`), while the backfill sees an appearance event on round 1 and
takes round 1's earlier time. Measured: all six carried conditions, round 1's confirm 144 ms before round
2's. Reachable through the confirm route on an older round — the sheet for round 2 can be imported while
she is on round 1's screen.

So the migration's "EARLIEST, AS THE CODE WRITES IT" holds in one order only. The SQL is left as it is:
the code's stamp is "the first confirm that covered this condition" and the backfill's is "the earliest
confirm of a round it appeared on", only whether the stamp is SET is read today, and reproducing the
code's rule from history would need a correlated `NOT EXISTS` over later appearance events for a date
nothing reads. What is asserted instead is the invariant that holds in both orders —
`test_the_backfill_is_never_later_than_the_code_in_either_confirm_order`: the backfill stamps every
condition the code stamped, and never later, so nothing can lose force or gain it late. The strict case
is deliberately not asserted, so making the two agree exactly stays an improvement rather than a failure.
The docstring claim is narrowed to match.

### The corrected staging query

Sound, and it can now report. Three things measured about it rather than assumed:

- `readonly.condition_events` exposes `occurred_at`, not `created_at` — worth knowing before the first
  run, since a query written from the model's names fails at the view.
- `readonly.condition_rounds` does expose `plan_ready_at` and `plan_confirmed_at`, so both halves resolve.
- `conditions.last_seen_round_id` is `nullable=False`, so the inner join drops nothing and `conditions`
  really is the denominator. (`plan_confirmed`'s `if condition.last_seen_round_id is None` is therefore
  defensive only.)

One caveat on reading the result: `kept_only_by_last_seen` counts conditions whose last-seen round is
confirmed and which have NO appearance event on any confirmed round. Every writer of a `Condition` emits

coverage is complete", not as "the last-seen half does nothing".
