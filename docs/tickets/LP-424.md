## Item 1 — `rule_tags.csv` regen → STOP (report the drift)

**Verdict: STOP.** The drift is **structural, not the 7-8 listed.** `rule_tags.csv` is a **data-lineage** map
(rule → its raw INPUT tags) while the live spec's `load_bearing_tags` is the **direct-read** set. They differ for
nearly every rule *by design*:

| rule | CSV says (raw inputs) | spec reads (direct) |
|---|---|---|
| PC-7 | `contract.closing_date` | `contract.days_until_closing` (derived from it) |
| AS-8 | `stmt.beginning/ending_balance`, `txn.*` | `stmt.continuity` (derived) |
| PC-2 | `contract.sales_price` | `contract.loan_sales_price` (the loan promotion) |
| IH-3 | `ins.effective_date` | `ins.loan_effective_date` (the loan promotion) |
| IN-6 | `income.employer_normalized` | `income.employer_coverage` (derived) |
| IN-2 | `income.pay_date` | `income.days_since_most_recent_pay` (derived) |
| IN-12 | `income.type` (STALE — pre-LP-419 scope) | `income.has_2yr_history`, `income.is_self_employed` |
| …(≈every live rule) | raw inputs | derived/final tags |

A spec-driven regeneration would change the artifact's **semantics** (lineage → direct-read), **fight the
existing xlsx-driven generator** (`generate_fact_tags`, which regenerates `rule_tags` from the authoring xlsx),
and change the projection edge count. That is a **CSV-contract decision** (which abstraction should `rule_tags`
encode, and which generator owns it), not a hardening fix — deferred to its own ticket. **Nothing reads
`rule_tags.csv` at evaluation** (the evaluator reads each spec's `load_bearing_tags`; confirmed by grep + a pin
test), so the drift is planning-only. IN-12's edge is the one genuinely stale entry (a scope change, not
lineage). See **ADR-336**.

## Item 2 — backfill base-rule bars → STOP (the OC-2 finding)

**Verdict: STOP + report + ADR.** Two walls:
1. **Structural:** `load_activation_bars()` fail-louds unless the bars file covers *exactly* the non-base
   candidates, and the invariant is `ACTIVE = _BASE_ACTIVE ⊎ eligible_candidates` (disjoint). Base rules can't
   get bars without **re-architecting** the base/gated split — not a bookkeeping fill.
2. **The finding:** moving base rules into the gate would DEACTIVATE any whose tag is unmeasured — and **OC-2**
   is exactly that. OC-2 is live via `_BASE_ACTIVE`, reads `occupancy.consistent_with_signals` (AI, **UNSCORED**
   — the OC-1 tag), and predates the gate. Safe today only because OC-2 is **judgmental → RATIFIES** every
   verdict (a human signs each; documented in OC-1's bar). Giving it a bar → `not-calibratable-yet` → ineligible
   → deactivated. **Geet's call** (deactivate pending calibration, or accept ratify-on-unscored) — not a silent
   change.

The 11 base rules, for the record (AI load-bearing tag, and eligibility if moved to the gate):

| rule | kind | AI load-bearing | if gated |
|---|---|---|---|
| AS-1 | calculative | `txn.is_money_in` (+ Stage-B `has_identified_source`, 93.8% LP-390-5) | eligible |
| OC-2 | judgmental | `occupancy.consistent_with_signals` **UNSCORED** | **ineligible → the STOP** |
| ID-7 | structural | `id.title_vesting_consistent` | (needs its measurement checked) |
| ID-9 | judgmental | `id.poa_present_and_acceptable` | ratify |
| ID-1/2/3/4/6, ID-8, IN-2 | structural/judgmental | none (deterministic/parsed) | no-ai-dependency |

Because ONE (OC-2) would deactivate, the whole item stops (the ticket's "all 11 must stay live → STOP" gate).
**No measurement was invented** (the AS-5 discipline). See **ADR-336**.

## Item 3 — loader cross-check → IMPLEMENTED

**Verdict: GO.** A bar declaring `ships: auto` for a **judgmental** rule is now a **load error** — a judgment
rule never auto-ships (the runtime ratifies regardless, LP-376-B), so such a bar lies. Added to `parse_bar` via
`rule_kinds.csv` (`kind_for()`; no import cycle — kinds.py depends only on stdlib). **The loader CAN see the
kind** — this is *not* the calc-only limit LP-411 hit (`threshold_needs_signoff`), so the guarantee is
enforceable at the bar layer. **No current bar violates it** (all four judgmental bars — AS-12, IN-7, IN-13,
IN-14 — correctly ratify), so startup is unaffected. Verified: the guard fires on a constructed judgmental+auto
bar; every committed bar still loads; a structural/calculative `ships: auto` is still accepted.

## Item 4 — `loan.purpose` → tag BUILT, predicate DEFERRED

**Verdict: build the tag; defer the predicate.**
- **Reachable + typed-core:** `loan.purpose` is a MISMO fact (`mismo_section.py`, from `loan_file.loan_purpose`
  = LoanPurpose enum), **not** a catch-all field. Built the tag as a **parsed** loan-subject promotion — the
  exact `program.type` precedent (`{mode: parsed, subject: loan, data: loan.purpose}`). Materializes:
  purchase→`purchase`, refinance→`refinance`, absent→absent (fail-closed). Enum `[purchase, refinance]`; +1 vocab
  tag (167→168), no rule_tags edge (no consumer yet).
- **Predicate DEFERRED (the equivalence is not clean):** applying `applicability: {loan.purpose, op: ne, value:
  refinance}` to PC-2/PC-7 would, on **LF-6T3N** (which carries **no** `loan.purpose`), make the predicate tag
  absent → `couldnt_check` → **regressing PC-2 (satisfied→couldnt_check) and PC-7 (satisfied→couldnt_check).**
  And **no refinance fixture exists in the snapshot verification path** (the only refi test uses the *legacy*
  facts engine, `evaluate(facts, rules, loan_purpose=…)`, not the snapshot/tag engine) — so the intended
  improvement (`couldnt_check → not_applicable` on a refi) is **unexercised**. The predicate is a follow-up,
  blocked on: (a) LF-6T3N (+ purchase fixtures) carrying `loan.purpose=purchase` so the predicate doesn't
  regress them, and (b) a refinance scenario in the snapshot path.
