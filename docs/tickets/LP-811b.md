## What was done

The Communication tab now shows the accumulating document request: who it goes to, the subject, the
editable body, the Reply-To and Bcc addresses, and three actions — **copy**, **open in mail client**,
**mark as sent**.

Nothing transmits. The processor takes the text to their own client; "mark as sent" records that it
went out, which is what moves every requested document to `REQUESTED` and starts LP-814's clock.

### `mailto:` is withheld with a reason, not just disabled

The server decides whether a message fits (`mailto_available`), and `mailtoUrl` returns `null`
rather than a truncated link. A `mailto:` over the client's limit **does not fail** — it opens a
compose window containing part of the message, which a processor may send without noticing.

A disabled button with no explanation gets worked around. The panel says why, and names the limit,
because a processor who is not told will assume the feature is broken and paste the message anyway —
which is the same outcome by a different route.

### The textarea is seeded by draft identity, not by content

LP-809 **regenerates** the draft on every add and every remove, so the query returns a new object
often. Re-seeding the textarea from it would throw away a processor's edits mid-sentence.

Seeding is keyed on the draft's `id`, tracked in explicit state rather than through an effect
dependency list. The obvious version — a `useEffect` keyed on `[draftId]` that reads `draftBody` —
requires lying to the linter about its dependencies, and **a lint suppression is something somebody
later "fixes"**. Here the fix would be the data loss. Render-phase state comparison says the same
thing without a suppression to remove.

### The empty state is ordinary, not an error

A file with nothing outstanding has no draft. The API client turns that 404 into `null` rather than
throwing, and the panel says so — an empty textarea with a Send button under it would read as a
broken page on a file in good order.

## Tests

`components/file/communication/outbound-draft-panel.test.tsx`, 10 tests.

`mailtoUrl` is deliberately **not** mocked. It is the function under test in two cases, and mocking
it would leave them asserting that a mock returns what it was told to.

Two are about work being lost, which nothing reports:

- `does not overwrite an edit when the same draft re-renders` — the regeneration case.
- `does seed from a different draft` — its control. A component that never seeded would satisfy the
  first and would show an empty box for every draft.

Verified by mutation, each confirmed applied:

| Mutation | Result |
|---|---|
| the `mailto_available` gate removed | 1 fails |
| seeding keyed on presence rather than identity | 9 fail |
| the composed body sent instead of the edited one | 1 fails |
| the send button enabled without a recipient | 1 fails |

## Assumptions

- **The recipient is typed each time.** There is no borrower-email lookup: `Borrower` has the field,
  but choosing *which* borrower on a multi-borrower file is a real decision nobody has made, and
  pre-filling the wrong one is worse than typing it. Recorded rather than guessed.
- **`navigator.clipboard` is available.** It requires a secure context, which the app is. A failure
  rejects the promise and the button simply does not flip to "Copied".

---

## Deliberately not done

- **No timeline.** LP-812 merges communications with the activity log; this tab shows the outbound
  draft only, and the placeholder's own description promised the rest of it.
- **No draft editing of the document list.** Removing a document is a needs-list action (LP-809's
  `remove_need_from_draft`), and duplicating it here would be a second way to do one thing.
- **No optimistic update on send.** The mutation invalidates and refetches. A send that is refused —
  already sent, or rate-limited — must not have looked like it worked first.

## For the reviewer

The three standing reviewer checks:

- **Tenancy** — no `company_id` anywhere; the client calls file-scoped routes and the server gates
  them.
- **Message content in logs** — nothing is logged. The body is rendered and copied, never sent
  anywhere but the API.
- **AI in the decision path** — none.

The judgement calls worth a second opinion:

1. **Render-phase `setState` instead of a `useEffect` with a suppressed lint rule.** It is the
   pattern React documents for deriving state from props, but it is unusual in this codebase — check
   whether it is the right local convention, and if not, whether the alternative is genuinely safe
   from the "someone fixes the suppression" failure.
2. **No borrower-email lookup.** Typing an address every time is friction on the most common action
   in the tab. The counter is that pre-filling the wrong borrower on a multi-borrower file sends a
   real person somebody else's document list.
3. **The panel is the whole tab.** LP-812 will want the timeline above or beside it, and I have not
   left a layout seam for that. Cheaper to shape now if you can see what it should be.
