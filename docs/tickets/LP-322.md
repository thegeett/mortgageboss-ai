# LP-322 — Finding reconciliation across runs

**Status:** Complete. **Branch:** `phase3_new_AI_arch_finding_stage2`.
**ADR:** [ADR-263](../../decisions.md). **Depends on:** LP-312 (stable content-ids), LP-316 (finding
+ event log), LP-320 (observation boundary), LP-321 (the orchestrator), §8/§9.

## What it is

When a verification runs AGAIN on the same loan file, match this run's findings against the prior
run's by the STABLE identity `(rule_id, subject_key)` and reconcile — completing the finding
lifecycle (§8 across runs) and immortality/reconciliation (§9):

- **carry-forward** — still detected → keep the same finding (id + history), refresh its state.
- **mint** — newly detected → a new finding.
- **retire** — no longer detected → `no_longer_applies` (visible, labeled, reasoned) — **never a
  silent delete**.
- **resolve** — open → satisfied when a resolving sourcing tag flips (the gift-letter loop).
- **revive** — a retired finding's subject reappears (exact subject_key) → the same finding, back.

## Acceptance criteria

- [x] `subject_key` stability verified (same raw facts → same content_id; a changed amount → a new
  subject) — reconciliation rests on this.
- [x] Carry-forward: the same subject open in run 1 + run 2 → ONE finding (same id), history kept,
  not duplicated.
- [x] Mint: a subject new in run 2 → a new finding.
- [x] Retire: a subject present in run 1, gone in run 2 → `no_longer_applies` (visible, reason +
  run_id + timestamp), `deleted_at` NULL (not deleted); a `retired` event logged.
- [x] Resolve (gift-letter loop): AS-1 fires run 1 (open); run 2 the sourcing tag flips no→yes → the
  SAME finding → satisfied, a `resolved` event citing the flipped tag. **Satisfied, not retired.**
- [x] Resolve ≠ retire: distinct states (`satisfied` vs `no_longer_applies`) + events
  (`resolved` vs `retired`).
- [x] Revive: a retired subject reappears (exact subject_key) → revived (same id), a `revived` event;
  a DIFFERENT subject → a new finding, not a revive.
- [x] Retire ≠ suppress: retiring subject X does not stop the rule minting for a new subject Y.
- [x] Immortality: no path deletes a finding; the event log is append-only across runs.
- [x] Re-running the same file no longer errors on the uniqueness index (reconcile replaces the
  collide).
- [x] Observation boundary: a still-firing rule stays open — only a TAG flip resolves (reconcile
  never reads observations). Migration up/down; new event types registered. ruff + mypy + full
  suite green (1973 passed).

## Assumptions & decisions

- **subject_key stability is the load-bearing assumption.** Identity is `(rule_id, subject_key)` and
  subject_key is the LP-312 content-id; a re-run of an unchanged transaction reconciles to the same
  finding, a changed one is a new subject. Verified before building.
- **resolve ≠ retire.** Resolve = subject present, rule now passes (`satisfied`, driven by a tag
  flip); retire = subject gone (`no_longer_applies`). Different outcomes + events — deliberately not
  collapsed.
- **Immortality — never silent-delete.** Retire moves the finding to `no_longer_applies` and keeps
  `deleted_at` NULL, so it stays on the surface (labeled). Retired stays retired until an exact
  subject_key revives it; a human-resolved finding is RETAINED (not retired), preserving the
  Undo/audit record. The append-only event log is never rewritten.
- **The gift-letter loop is a TAG flip, not an observation.** A resolve happens because
  `has_identified_source` flips no→yes (a formal tag / matched source), so the rule returns
  satisfied. An observation (LP-320) only surfaces to a human — reconcile never reads observations,
  so an observation alone can never flip a finding's state (the boundary that keeps extensibility
  from becoming a false-green vector). A still-firing rule stays open.
- **Two new event types, via a CHECK-widening migration.** `str_enum` is VARCHAR+CHECK, so adding
  `carried_forward`/`revived` is a CHECK replace (no `ALTER TYPE`). The migration drops both the
  single and a stale double-prefixed constraint name IF EXISTS, so it applies on drifted DBs and
  converges with `create_all` on the single name.
- **Coexists with LP-94.** The old `finding_reconcile.py` (normalized-substance identity,
  soft-deletes) serves the pre-fact-tag pipeline and is untouched; this reconcile is subject_key-keyed
  and retire-not-delete for LP-316 fact-tag findings.

## Deferred

- The **four-tab UI** that DISPLAYS the lifecycle (frontend). Emitting `carried_forward` events every
  re-run is deliberate (a "re-confirmed in run N" audit trail); a future prune/rollup is possible if
  the log grows. No new rule/tag logic, no resolving via observations, no run-trigger UX.
