# LP-405 — Bucket 2 mini-census: what's genuinely writable now (READ-ONLY)

## What this ticket is

A read-only zoom-in census that refines LP-394. LP-394 confirmed IN-6 / AS-8 / OC-1 / OC-3 exist as
planned-but-unwritten and inferred that Bucket 2 ("unwritten rules whose inputs already exist") is ~10–15
rules. **This ticket reads the wiring and reports which candidate rules are genuinely writable now** — i.e.
every tag they read is already produced from an already-extracted document — versus which secretly need a new
producer or a blocker-document extractor. **No file was changed except this report.**

**The decision rule (applied, not guessed).** A candidate is **`writable-now`** only if EVERY tag it reads has a
producer entry in `tag_production.yaml` AND that producer's source document is in the `EXTRACTORS` registry. If a
read-tag has no producer I split on WHY:

- **`needs-producer`** — the read-tag has no producer, but its **source document already has an extractor**
  (a cheap wiring job: declare a producer that reads the extracted field). *This is not Bucket 4.*
- **`needs-extractor`** — the read-tag needs a **blocker document that has no extractor** (credit report, title,
  appraisal, AUS, MI cert). *This is Bucket 4.*
- **`needs-definition`** — a Priya threshold/definition (and a rule-id + tag) must exist first.
- **`unclear`** — the code doesn't say; flagged, not guessed.

**The single most important thing Phase 0 surfaced** (and the reason LP-394's inference was imprecise): the
`EXTRACTORS` registry already contains **purchase_agreement, homeowners_insurance, property_tax_bill,
hoa_statement, 1099, gift_letter, mortgage_statement, divorce_decree, tax_return** (plus the pay-stub / W-2 / VOE
/ bank-statement / ID core). So the **purchase contract, hazard binder, HOA statement and property-tax bill are
already extracted** — their rules are `needs-producer` (wire the tag), **not** `needs-extractor`. The documents
with **no extractor at all** — the real Bucket 4 gate — are exactly: **credit report, title, appraisal, AUS/DU
findings, MI certificate.**

### What OC-1 / OC-3 actually check (I was asked not to guess)

- **OC-1 — Occupancy consistency (structural).** Reads `occupancy.stated` (the MISMO-derived stated occupancy
  enum) and `occupancy.consistent_with_signals` (the loan-subject AI tag: do the borrower's *other* 1003
  declarations — intent-to-occupy, FHA-second-residence indicator, unit count — agree with the stated
  occupancy). Both are **already produced and already live** (OC-2 consumes `consistent_with_signals`). ⚠️
  **Scope caveat (LP-371 D3, read from `tag_production.yaml`):** the AI group's context is the loan's MISMO
  facts and carries **no borrower residence address**, so the produced tag measures **declaration** consistency,
  **not** the "stated vs *address* signals" the rationale implies. OC-1 is writable-now against the produced tag,
  but the true address-signal dimension is a follow-up, not available today.
- **OC-3 — Investment rental support (judgmental).** Reads `occupancy.rental_support`
  (`adequate | inadequate | n/a | unknown` — "rental support docs for investment occupancy"). That tag has **no
  producer**, and its plausible source documents (leases / a Form-1007 rent schedule) have **no extractor**. So
  OC-3 is not writable now; it is `needs-producer` and, realistically, `needs-extractor` + calibration.

### Priya's 2 candidate rules (structural, inputs exist, but a definition is missing)

Both are **pure document-presence** structural rules and their source documents are already extracted, but
neither exists yet as a rule-id + tag, and each hides a threshold that needs Priya's sign-off:

- **Priya-A (pay-stub-only → W-2/1099):** how recent must the pay stub be, and does a 1099 satisfy it for a
  contractor? Needs the trigger definition + a presence tag.
- **Priya-B (terminated-VOE → offer letter + pay stub):** what counts as "terminated" (a VOE end-date present?
  a status field?). `income.employment_end`, `income.voe_present`, `income.offer_letter_present` are all
  produced, so the *inputs* exist — the **definition of "terminated"** is the gap.

### The DTI-obligations finding (highest-value)

**Yes — DTI needs the credit report.** DT-1 (the back-end DTI ratio, the core of the whole DTI category) reads
`liab.account_type`, `liab.monthly_payment`, `liab.dti_payment`, and `debt.counts_in_dti`. `fact_tags.csv`
describes these as the monthly liability payments that "drive DTI treatment," and **none has a producer**; their
source is the **credit report**, which has **no extractor** in the registry. There is also no `housing.pi`
producer (a P&I calc) and no `housing.taxes_monthly` producer (a property_tax_bill wiring). **Consequence:** the
DTI *number* cannot be computed until the credit report is extracted. **DTI is Bucket 4-gated, not a cheap
deterministic wave.** The plan's ~28-rule deterministic wave (Bucket 3) counted DTI's 7 as "fast, low-risk" —
that is wrong for DT-1 at minimum, and for the category's headline output entirely.

### The writable-now rules ranked by cheapness

All four ride **already-produced, already-live** producers, so **none needs a new producer and none needs new
calibration** (every AI tag they read was already measured for a sibling live rule). None needs a Priya
threshold. Ranked cheapest-first:

1. **PC-7** — `deterministic_only`, a single **parsed** tag (`contract.closing_date`), pure date compare. No AI
   at all. Cheapest, and it lands the Contract category's first rule.
2. **AS-8** — `deterministic_only`, an equality check on parsed balances; its one AI tag (`txn.is_money_in`) is
   already live (AS-1/AS-9/AS-10). Completes the bank-statement structural family.
3. **IN-6** — structural set-match; `income.employer_normalized` is already live via **IN-5**. No new
   calibration.
4. **OC-1** — structural; `occupancy.consistent_with_signals` is already live via **OC-2**. No new calibration —
   but carries the LP-371 D3 scope caveat (declaration- not address-consistency), so word the spec to that.

### Shared read-tags (build once, unblock several)

The notable fact is the *inverse* of "build once": **there is no new tag to build for the writable-now four** —
that is precisely *why* they are writable now. Each rides a producer already built and validated for a live
sibling:

- `income.employer_normalized` → IN-6 + **IN-5 (live)**
- `occupancy.consistent_with_signals` → OC-1 + **OC-2 (live)**
- `stmt.*` / `txn.*` → AS-8 + **AS-1 / AS-9 / AS-10 (live)**
- `contract.closing_date` → PC-7 + **CL-1** (already produced from the purchase_agreement extractor; CL-1 still
  needs `rate_lock.expiration` separately)

The real "build once, unblock several" leverage is in **Bucket 2.5**: one **purchase_agreement producer wave**
(`sales_price`, `earnest_money_amount`, `property_address`, seller-credit/addenda/contingency catch-all) unblocks
**PC-2, PC-3, PC-4, PC-5, PC-6, PC-9** (and feeds DT-* nothing, but PC-8). Separately, `housing.taxes_monthly`
(property_tax_bill) and `ins.premium_annual` (homeowners_insurance) and `housing.hoa_monthly` (hoa_statement) are
one-tag producer jobs each, unblocking DT-4 / DT-5 / DT-2 respectively.

### Suggested build order (genuine Bucket 2 only)

1. **PC-7** — Contract closing-date realism (cheapest; opens the Contract category).
2. **AS-8** — statement chaining (finishes Assets' deterministic statement family with AS-9/AS-10).
3. **IN-6** — pay-stub ↔ W-2 coverage (Income; rides IN-5's employer tag).
4. **OC-1** — occupancy consistency (Occupancy → 2/3; word the spec to the declaration-signal scope).

## What this changes about the plan (§13's Bucket 2/3/4 counts)

- **Bucket 2 is 4 rules / ~4 tickets, not ~10–15 / ~5–7.** The genuine members are IN-6, AS-8, OC-1, PC-7.
- **A new cheap wave the plan mis-filed into Bucket 4 exists — call it "Bucket 2.5" (producer wiring).** Because
  the **purchase_agreement, homeowners_insurance, hoa_statement, and property_tax_bill extractors already exist
  and run**, seven Contract rules (PC-2/3/4/5/6/8/9) and three DTI rules (DT-2/4/5) are `needs-producer` — a
  tag-wiring job — **not** the "build a new extractor" Bucket 4 work the plan assumed. This is materially
  cheaper than the plan's framing and should be sequenced right after Bucket 2.
- **DTI is not a deterministic wave.** DT-1 needs the credit report; the category's number is Bucket 4-gated.
  Remove DTI's 7 from the "~28 fast/low-risk" Bucket 3 estimate (some DTI sub-rules are cheap producer jobs, but
  the headline ratio is not).
- **The real Bucket 4 extractor gate narrows.** The documents with **no extractor** are **credit report, title,
  appraisal, AUS/DU findings, MI certificate** — that is the true blocker set. LP-394's ~58 `needs-extractor`
  estimate is too high: insurance, HOA, property-tax, and the purchase contract are **already extracted** (their
  tags are merely unwired). The extractor mountain is real but smaller than "~58 rules behind unbuilt
  extractors"; a chunk of that count is cheap producer wiring against extractors that already exist.

## Assumptions & what was inferred (not read)

- **The gate is `tag_production.yaml` (producer present?) × `EXTRACTORS` (source doc extracted?)** — both read
  directly. `writable-now` requires both; every verdict above is derived from these two, not from the ticket's
  assumptions.
- **`needs-producer` vs `needs-extractor` was decided by the `EXTRACTORS` registry**, read verbatim. Where an
  extractor exists but the tag is unwired I said `needs-producer`; where the source document has no extractor I
  said `needs-extractor`. This is a read, not a guess — but I did **not** open every existing extractor's schema
  to confirm it emits a field that cleanly maps to each unwired tag (e.g. that the purchase_agreement catch-all
  reliably yields `contract.contingency_dates`). The typed-core fields (`sales_price`, `closing_date`,
  `earnest_money_amount`, `property_address`, buyer/seller) are confirmed present in
  `PurchaseAgreementExtraction`; the catch-all-sourced tags (seller credit, addenda, personal property,
  contingency dates) are **inferred** to be reachable from the extractor's `additional_sections` and may need a
  small extractor extension — flagged, not asserted.
- **OC-3 / PC-3 wiring** was recovered from `fact_tags.csv` `used_by_rules` because both are absent from
  `rule_tags.csv`. The verdict does not depend on that recovery (their tags have no producer either way).
- **`contract.closing_date` is produced from the purchase_agreement extractor** — read from `tag_production.yaml`
  (`data: closing_date`) matched to `PurchaseAgreementExtraction.closing_date`; corroborated by ID-5 (live)

- **"terminated" (Priya-B) and "how recent" (Priya-A)** are thresholds I did not find defined in the code —
  flagged for her sign-off, not invented.
