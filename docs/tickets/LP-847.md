# LP-847 — a message can be marked sent with no recipient

Status: spec. Second of four.

## The report

> "Bug: when I clicked Mark as sent in borrower tab, all tab's draft Mark as sent button became gray
> out."

Diagnosed differently from how it was reported, and the difference matters: nothing about clicking
in the borrower tab disables anything. `useSendDraft` holds no shared state between dialogs. Those
buttons were **always** grey, and opening the other tabs is when they were noticed.

## Two of my own decisions contradicting each other

LP-843 creates a non-borrower draft with **no recipient**, because that was the explicit ask: "if
any party's contact is not there then keep it empty in draft. processor mostly worry about a
message."

`canSend` requires `recipient.trim().length > 0`, and `SendDraftRequest.recipient` is
`Field(min_length=3)` on the server. So the ticket that made an empty To legitimate never looked at
the control that refuses one. A processor can compose the message and can never record that they
sent it.

This is the failure my own note names — check the reader, not just the writer — one ticket after
writing it down.

## Decided: allow it

The user's call, and it follows from how sending actually works: nothing in this product transmits.
A processor copies the body into their own mail client and sends it to an address they may know
perfectly well and have never typed into our system. "Mark as sent" records **that they did it**, so
refusing the record because our row has no address is us insisting on bookkeeping the processor does
not owe us.

## THE TRAP THIS WALKS INTO, found before building rather than after

`recipient` is not only stored. It keys two guards in `email_send`:

- `is_suppressed(address=recipient)` — harmless on empty, matches no bounce.
- **`_refuse_if_rate_limited(recipient=recipient)`** — `Communication.recipient == recipient`, one
  send per window and N per day. **Every empty-recipient send shares the key `""`**, so the second
  one — a title company after a lender, entirely unrelated — is refused with "was emailed less than
  N minutes ago" about a mailbox that does not exist.

Two blanks are not the same mailbox. Both guards are about A SPECIFIC ADDRESS and neither has
anything to say when there is none, so both are skipped rather than fed an empty string. That has to
be asserted: a rate limiter that silently groups unrelated parties is exactly the kind of
green-looking defect this run keeps turning up.

## The change

- `SendDraftRequest.recipient` accepts empty.
- `canSend` drops the recipient requirement.
- Suppression and rate limiting apply only when there is an address to apply them to.
- The record stores what it has, which may be nothing, and says so rather than implying a send to
  an unknown party.

**Not in scope, and recorded because it is real:** `min_length=3` accepted `"abc"` as an email, so
there has never been a format check here (found in the LP-841 review). Relaxing the bound does not
make that worse, and fixing it properly is its own decision about whether a processor may record a
send to something we cannot parse.

# Built

Three changes, and the third is the one that mattered:

- `SendDraftRequest.recipient` is `default=""` with no minimum. The bound was never a format check —
  it accepted `"abc"` — so removing it removes something that protected nothing.
- `canSend` drops the recipient requirement and keeps the body one. There is no message to have sent
  without a body, and the server refuses that too.
- **Suppression and rate limiting are scoped to `if recipient:`**, which is the defect this ticket
  nearly created rather than fixed.

## The trap, found before building

The rate limiter matches `Communication.recipient == recipient`. Every empty-recipient send shares
the key `""`, so the second one — a title company after a lender, entirely unrelated — would be
refused with **"was emailed less than five minutes ago"** about a mailbox that does not exist. A
plausible, specific, entirely false message about a send the processor never made, on a feature
where nothing transmits.

Two blanks are not the same mailbox. Both guards ask a question about a specific address and neither
has anything to say when there is none.

## The guard is scoped to what it is FOR, and that is asserted in both directions

Mutating `if recipient:` → `if True:` (the trap) fails the new test. Mutating it → `if False:`
(over-wide, skipping the guards for everybody) fails five tests across the send and bounce suites.
An over-wide guard is green by construction and no mutation of the narrow direction finds it, which
is why both were run.

The control inside the new test does the same work at a smaller scale: after proving two blank
recipients do not collide, it proves the limit still bites on a real address twice. Without it,
`if recipient:` could have been `if False:` and the file would still have been green.

## What this says about the two decisions

LP-843 made an empty To legitimate and never looked at the control that refuses one — my own note
says check the reader, not just the writer, and this was one ticket after writing it down. The
reported symptom ("all tabs greyed out after I clicked") was not what happened: nothing about
clicking disables anything, and `useSendDraft` holds no state across dialogs. Those buttons had
always been grey. A disabled control with no explanation is indistinguishable from a broken one,
which is why the report described a cause that did not exist.

## Review (second session)

Reviewed as part of `13d36cf4`. The scoping decision is right and the question asked about it — whether
skipping the guards for an empty recipient can be used to get past a bounce suppression — is **no**,
now measured rather than reasoned.

### Why it cannot bypass a suppression

A suppression is keyed on an address, so the only way an empty recipient could bypass one is if
something downstream substituted an address. Nothing does. Traced every consumer of the recipient on
the send path: `draft.recipient = recipient` stores it, and the single reader is
`OutboundEnvelope(to=draft.recipient or "", …)` in `_transmit_if_possible`. There is no fallback to
the borrower's address, no default, and no second source — so an empty recipient stays empty all the
way to the transport rather than becoming somebody else's mailbox.

### One thing the scoping did weaken, and it is now closed

`transmit` promises in its own docstring that because every guard sits above it, "a provider
implementation inherits them by construction rather than by remembering". After LP-847 that is no
longer true of one message: a no-contact send reaches the transport line having passed neither the
suppression check nor the rate limit. Harmless today — `transport_for` returns None for every
connection, so nothing is transmitted at all — and a live provider would make it a real gap, found
only when somebody implemented one.

`transmit` now returns None for an envelope with no recipient, which is the answer its docstring
already defines (nothing transmitted, the caller stays on copy-and-send) and is what a draft with no
mailbox has always meant in practice. `test_a_draft_with_no_recipient_reaches_no_transport` registers
a real recording transport so the question is actually asked rather than answered by the absence of a
provider, and it carries a positive control: the same transport must still send when there IS an
address. Mutated — with the guard removed the test fails and the log shows `mail_transmitted`.

The record is still written either way, which is the point of the button.
