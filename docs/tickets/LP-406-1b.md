# LP-406-1b — Write PC-7 (closing-date realism), now that `contract.days_until_closing` exists

## What this ticket is

LP-406-1 stopped PC-7 at Phase 0: its "closing date vs today" check needed a `today` operand the deterministic
resolver has no source for. LP-410 built the derived loan-level tag `contract.days_until_closing` (a **signed**
integer: positive = future, negative = the closing date has **passed**, `unknown` = no parseable/agreed date).
PC-7 is now a deterministic rule — and **unlike AS-8/IN-6, it compares a NUMBER to a THRESHOLD** (the IN-2
operand path, not an enum branch), with a **two-sided window** that is Priya's to set. It ships **held**
(`ACTIVE_RULE_IDS` stays 25). This is the last of the four Bucket 2 rules.

## D1 — The subject match (anti-structural-death) — confirmed

`load_declarations()["contract.days_until_closing"].subject == "loan"`, PC-7's `subject_enumeration == "loan"`.
Asserted + verified live.

## D2 — The window shape (the substance): TWO asymmetric sides

A signed day-count is **two different problems**, so **two thresholds, two outcomes, two reasons** (ADR-326):
- **PAST (negative):** the closing date is behind the file date — a purchase cannot close in the past (the date
  moved and the contract wasn't updated, or it expired). **A finding at (almost) any magnitude.** Default
  `past_grace_days = 0` (any strictly-past date fires).
- **FAR FUTURE (large positive):** premature/unrealistic for a file in pre-submission processing. **A genuine
  threshold.** Default `far_future_days = 90`.

**What Priya must decide (in plain language, not parameter names):**
1. *"Is a closing date that's already 1–2 days in the past acceptable (a timing lag between when the file was
   pulled and the closing), or should ANY past closing date be flagged?"* → sets the past grace (default: any
   past date flags).
2. *"How many days ahead is 'unrealistically far' for a file we're still processing — 90 days? 120?"* → sets
   the far-future window (default: 90).

Both ship as **defaults** (`validated: false`); the window lives in the **rule**, never the tag (LP-410 left it
out — tags describe, rules judge).

## D3 — The operand path + negative coercion (the risk) — clears

PC-7 uses the operand path (`days = {tag: contract.days_until_closing}`, compared via `when_compare`), unlike
AS-8/IN-6's `operands: {}`. Verified the signed-integer string coerces cleanly: `coerce_decimal("-10") =
Decimal("-10")`, `coerce_decimal("1") = Decimal("1")`, `coerce_decimal("unknown") = None`. So a **past date
fires** (does not silently couldnt_check), and `unknown`/absent → couldnt_check. Proven end-to-end below.

## D4 — Applicability / scope: PC-7 is LOAN-WIDE (a reported gap)

PC-7 is **not** applicability-scoped purchase-only, because **there is no loan-purpose / transaction-type tag**
to scope it (confirmed — no such tag in `tag_production.yaml` / `vocabulary_extra.yaml`). A **refinance** has no
purchase agreement → no `contract.closing_date` → `contract.days_until_closing == "unknown"` →
**couldnt_check**. That is honest (it genuinely cannot check without a contract closing date) but not ideal — a
refi is *out of scope*, which would be better expressed as `not_applicable`. **The gap:** a `loan.purpose` tag
would let PC-7 scope a refi to `not_applicable` (the AS-8 applicability-predicate pattern). Reported; the
couldnt_check fallback is not a false finding, so it is safe in the interim. (LP-406-4's passing note "PC-7's
purchase-only" was an assumption; the classification row carries no purpose scope, and no purpose tag exists.)

## D5 — The outcomes

| `contract.days_until_closing` | verdict | reason (plain, interpolated) |
|-------------------------------|---------|-------------------------------|
| `< 0` (past) | **fired** | "the loan's closing date has already passed — it is {days} day(s) from the file date; a purchase cannot close in the past…" |
| `> 90` (far future) | **fired** | "the loan's closing date is {days} day(s) out — unusually far ahead for a file in processing…" |
| `0 … 90` (in window) | **satisfied** | "…within a realistic window of the file date (not passed, not implausibly far ahead)" |
| `unknown` / absent | **couldnt_check** | "the days from the file date to the closing date could not be read/found…" |
| (refi / no contract) | couldnt_check | (D4 — no purpose tag to make it not_applicable) |

Past and far-future get **distinct** reasons (asserted) — they are different problems a processor acts on
differently.

## D6 — Reason strings (interpolated)

PC-7 has a **real operand**, so — unlike AS-8/IN-6's static reasons — it **interpolates the day count** (the
IN-2 pattern, verified): "…it is **-10** day(s) from the file date", "…is **200** day(s) out". Far more
actionable than a static string. No dotted tag ids (asserted); a `fact_label` for `contract.days_until_closing`
was added for the couldnt_check reason.

## D7 — The bar: no-AI, but held on a Priya window (a model gap)

`contract.days_until_closing` is derived from a **parsed** closing date — **no AI tag** — so PC-7 is
`no-ai-dependency`, not the transitive-AI `calibratable-now` IN-6 needed. **But** PC-7 carries a **Priya
threshold** (the window), and the activation model has **no clean hold for a no-AI rule with a threshold
sign-off**: `no-ai` eligibility is `input_resolves` (no threshold step), and `validated: false` does nothing on
a no-AI bar. PC-7's input *does* resolve (`days == "1"` on LF-6T3N → SATISFIED), so `input_resolves: true` would
**activate it auto-shipping fired verdicts on an unvalidated window**. So PC-7 is held by leaving
`input_resolves: false`, with a rationale making the true reason explicit ("the window is a default", not "the
input doesn't resolve"). **Reported as a NEW gap** (ADR-326): a real fix gates no-AI eligibility on
`threshold_needs_signoff` (or adds a `no-ai-threshold-pending` status). `ACTIVE_RULE_IDS` stays 25.

## The spec as written

`specs/PC-7.yaml` — `kind: structural`, `subject_enumeration: loan`, `operands: {days: {tag}, past_grace:
{reference}, far_future: {reference}}`, two `fired` outcomes (`days < past_grace`; `days > far_future`) + a
`satisfied` default, `reference_values.values = {past_grace_days: "0", far_future_days: "90"}`. Plus its
`activation_bars.yaml` bar (`no-ai-dependency`, `input_resolves: false`, held) and the `reasons.py` label.

## Every assumption / decision

- **Two-sided asymmetric window** (past-fires vs a future-threshold), two outcomes, two reasons (ADR-326).
- **Held despite being no-AI** — the window is an unvalidated Priya default; held via `input_resolves: false`
  with the model-gap documented (a native hold is a follow-up).
- **Loan-wide, not purchase-scoped** — no purpose tag exists; a refi couldnt_checks (safe, not a false
  finding); a `loan.purpose` tag would make it not_applicable (gap).
- **Defaults, not decisions** — `past_grace_days=0`, `far_future_days=90` are proposals; Priya's two questions
  are stated plainly in the spec + bar.
- **`rule_tags.csv` drift** (mirrors AS-8/IN-6): maps PC-7 → `contract.closing_date`, not the derived tag;
  harmless, reconcile on the next xlsx regen.
- No existing rule changed; the 25 live rules are identical; PC-7 is additive (held). No new tag.

## Any NEW gap

- **No loan-purpose tag** → a refinance couldnt_checks instead of not_applicable (D4). A `loan.purpose` tag
  (from MISMO) would fix it.
- **The activation model has no native hold for a no-AI rule with a Priya threshold** (D7/ADR-326) — held via
  the `input_resolves: false` stand-in; a follow-up should gate no-AI eligibility on `threshold_needs_signoff`.
- **Both fired paths untested on real data** — a past-date and a far-out-date fixture would close them.
