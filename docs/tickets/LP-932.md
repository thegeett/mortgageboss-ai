# LP-932 — rename the 24 misnamed CHECK constraints

- **Ticket:** LP-932 · Phase 4.5 follow-up · schema (one migration, two guard changes)
- **Raised:** Stage 2's follow-ups in [`phase4.5-progress.md`](../phases/phase4.5-progress.md), first
  measured by the LP-912 review (R1)
- **Migration:** `backend/alembic/versions/20260928_1400_bac8810abe90_lp932_rename_checks.py`
  (`fb263dfd0473` → `bac8810abe90`)

## Why rename when the values already match

A write fails on what a CHECK permits, not on its name, and since LP-912 the migrated-schema guard
compares values column by column. But every swap is written against a NAME. A swap that drops the
model's name on a migrated database drops nothing, and its new CHECK lands beside the old one. Postgres
ANDs the two, which is exactly how LP-909 made `round_reparse_requested` unwritable. After this ticket
the name in the models is the name in every migrated database, and the guard checks names too.

## The 24, measured

column by column with one built by `create_all`: 76 constrained columns, one CHECK each on both sides,
**24 named differently.**

## The migration

`ALTER TABLE ... RENAME CONSTRAINT` has no `IF EXISTS`, so each rename is a `DO` block that reads
`pg_constraint` for the table first (constraint names are unique per table, so the lookup filters on
`conrelid`):

| Old name | New name | Action |
|---|---|---|
| present | absent | rename |
| absent | present | nothing: already renamed, or built another way |
| present | present | **refuse.** Two CHECKs on one column is the LP-909 shape; which is right is a decision, and dropping either is destructive. |
| absent | absent | **refuse.** The column has lost its CHECK, and renaming nothing would hide it. |

A refusal raises, so the migration's transaction rolls back every rename before it and nothing is
left half-done. The downgrade runs the same blocks with the names reversed. That is needed: earlier
migrations' downgrades (LP-521's, LP-912's) name the old spellings, and they must still find them when
a database is rolled back past this one.

No function in the file has `swap` in its name, because `test_activity_type_migrations.py` reads any
such function as a constraint swap and its `ck_` literals as definitions. With none, that guard reads
this file as naming, not defining, the `_CASES` constraints (`_NOT_DEFINED_HERE`).

## The guards

1. **`tests/test_migrated_checks_match_models.py` checks names now.** New test
   `test_every_check_carries_the_name_the_models_give_it`: for every column constrained on both sides,
   the migrated CHECK's name must equal `create_all`'s. It reports table, column and both names. The
   module docstring records that the comparison was keyed on the column because names differed, and
   that LP-932 made the third check possible.
2. **`tests/models/test_pending_automation_outcome_lp521.py` had to change, and would have failed
   otherwise.** It took "the newest migration whose text contains the constraint name" as that
   constraint's live definition. This migration names both `finding_events` constraints and defines no
   values, so it would have become their "definition" and `_declared_values` would have found no
   `_OUTCOMES` tuple to read. Now each constraint lists every name it has held (a future outcome swap
   will use the new name; LP-521's, the live definition, used the old one), and a migration counts as
   defining it only if it names it by one of those AND declares an `_OUTCOMES` tuple.

## What a later migration must now do

Use the model's name, which is now the only name. Every migration after `bac8810abe90` that swaps one
of these 24 CHECKs names it as in the right-hand column above: exactly what `create_all` emits, and
what `_CASES` in `test_activity_type_migrations.py` already lists.

## Review (of `45f722d8`)

**No defects in the migration.** Everything below was re-measured on a scratch PostgreSQL 16 rather
than read, including one fix applied to the LP-521 guard (question 3).

### The five questions

1. **The 24 are exactly right.** A database built to `fb263dfd0473` and one built by `create_all`,
   compared column by column: 76 constrained columns on each side, 24 names differing, and those 24
   match `_RENAMES` entry for entry — nothing measured that the table omits, nothing declared that
   the databases do not show, no duplicate `(table, old)` pair and no duplicate new name.
2. **All four `DO`-block cases hold, and the rollback claim is the one worth having proved.** With a
   second CHECK added beside `ck_conditions_ck_conditions_bucketkind`, `upgrade head` refused with
   the documented message; afterwards the version was still `fb263dfd0473` **and
   `communication_evidence` — which renames first, before `conditions` — still carried its OLD
   name**, so the earlier rename in the same run was rolled back. The neither-present case refused
   with its own message and changed nothing; the already-renamed case (new present, old absent)
   upgraded cleanly; the ordinary case round-trips (`upgrade head` → 0 names differing,
   `downgrade -1` → 24 again).
3. **The "defines" rule was too tight in a way this ticket pair makes likely, and is fixed here.**
   The pattern recognised only a BARE `_OUTCOMES = (`. An ANNOTATED declaration —
   `_OUTCOMES: tuple[str, ...] = (`, which is exactly how LP-931's `_CHECKS` and LP-932's `_RENAMES`
   are written — was missed. The next outcome swap written in this pair's own house style would
   therefore define nothing, `_defining_migration` would fall back to LP-521's older file, and the
   failure would name the wrong migration. The same pattern was also written twice, once in each
   reader; a pattern they do not share can drift into a file the detector accepts and the extractor
   cannot read, which fails as *"defines no `_OUTCOMES` tuple this guard can read"* — the symptom
   this ticket just hit, one layer down. **Fixed:** one shared `_OUTCOMES_DECL`, with an optional
   annotation that cannot span a newline, plus a test. The naive widening (`[^=]*`) was tried first
   and rejected by measurement: it reads prose mentioning `_OUTCOMES:` above an unrelated tuple as a
   declaration. **A no-op today** — all three constraints still resolve to
   `20260817_1820_b7f1a4c93e08_lp521_pending_automation_outcome.py` with 6 values each.
   **Still loose, recorded not fixed:** "names it" is a substring test over the whole file, prose
   included, so a migration that only MENTIONS one of these names in its docstring while declaring an
   `_OUTCOMES` tuple for a different constraint would still be taken as the definition. Tightening
   that needs real parsing rather than a wider regex.
4. **Skipping one-sided columns is the right division, with one consequence worth knowing.** The
   value test already reports them as missing or extra. But it subtracts `_KNOWN_MISSING` from
   `missing`, and the name test skips any column absent on either side — so a column parked in
   `_KNOWN_MISSING` is invisible to BOTH tests, name check included. It is empty today (LP-931
   emptied it), so nothing is hidden now; the next entry added there silently loses its name check
   as well, which is worth a line in that set's comment when it happens.
5. **Earlier downgrades still work: confirmed.** `downgrade b6d1e93f57ac` from head ran 4 downgrade
   steps (LP-932's, LP-931's, LP-915's, LP-912's — the last naming the doubled spellings) and
   `upgrade head` ran 4 back to `bac8810abe90`.

### Also measured

- **The new name test is not vacuous and catches what the value test cannot.** Renaming one
  constraint back by hand (`ck_reminder_snoozes_reminderkind` → its doubled spelling) makes the name
  comparison report that column with both names; the VALUE comparison over the same database stays
  completely clean (`missing=[]`, `differ=[]`). That is the argument for the new test, demonstrated
  rather than asserted.
- **Nothing outside the migrations and tests references any of the 24 old names** (`app/`,
  `frontend/`, `scripts/`). The one code path that matches an error by constraint name,
  `condition_import.py`'s `_is_duplicate_round_number`, keys on `uq_condition_rounds_file_number` —
  a UNIQUE index, and this migration filters on `contype = 'c'`, so it is untouched.
- **140 passed** across the five files: the ticket's 139 plus the test added here.

### A note on method

The first cross-check of `_RENAMES` against the measured 24 used a regex over the migration's text
and found 21 entries, because three are written on a single line and the pattern expected a trailing
comma before the closing paren. It would have reported three renames as undeclared. Parsing the file
with `ast.literal_eval` instead gave 24 and an exact match. A text pattern over source is a
measurement like any other, and it needs its own positive control.
