## A2 — `dti.atr_factors_documented` is a two-value enum, confirmed. But that is not what blocks DT-7.

`fact_tags.csv:66`:

```
dti.atr_factors_documented,loan,enum,"[""complete"", ""incomplete""]",Are all ATR factors documented.,AI,DT-7,AI-at-rule-time
```

**No abstain value, as the ticket suspected.** Two corrections to what follows from that:

**1. The runtime CAN abstain, and there is a working precedent.** `ai.py::_build_tag` coerces any
off-vocabulary answer — including a literal `"unknown"` — to an unknown-valued tag that keeps the model's
reasoning, and the gate routes it to `couldnt_check`. `txn.is_nsf_or_overdraft` is declared
`["yes","no"]` and its prompt explicitly offers `unknown` with instructions on when to use it; LP-418
recorded the gap as **value-space drift** to reconcile at the next `docs/snapshot-fact-tags.xlsx` pass,
because the generated `fact_tags.csv` cannot be hand-edited. DT-7's enum is the same shape.

The honest caveat: this makes the abstain path work **by coercion rather than by declaration**. The
prompt must sanction `unknown` explicitly, or the model is offered only two answers and will pick one.
That is a prompt-shape requirement, not a blocker — and it must not be met by mapping a low-confidence
answer onto `incomplete`.

**2. The actual blocker is that DT-7 has NO PRODUCER.** `dti.atr_factors_documented` appears in
`fact_tags.csv` and `rule_tags.csv` and has **no `tag_production.yaml` entry and no AI group** — the
ADR-289 vocabulary-orphan shape. LP-405 already recorded it as *"needs-producer → needs-extractor (spans
the credit report)"*. There is also no DT-7 spec and no activation bar.

**Is ATR completeness a processor's judgment at all?** The ticket asks the right question and the answer
shapes the rule:

- ATR is a **creditor obligation** under Reg Z, assessed at underwriting. A processor assembling a file
  is not the party making the determination, and a rule that asserted it would put a compliance
  conclusion in a processor's queue.
- The buildable rule is the **presence** question: for each of the eight factors, does the file carry a
  document that would support it? That is checkable from the document set, needs no ATR determination,
  and is genuinely a processor's job.
- **Recommendation: if DT-7 is built at all, build it as document-presence per factor, and rename the
  intent in the spec so it cannot be read as the determination.** The catalog rationale ("All ATR
  factors documented — completeness judgment") already reads as presence; the tag name
  (`atr_factors_documented`) does too. It is the *rule name* ("ATR documentation completeness") that
  invites the stronger reading.

# What survives, and the recommendation

**No rule is dropped.** Three are buildable and blocked on data; one is blocked on a producer and a
scope decision.

- **IN-13 — keep, and the per-type table is the real work.** Its spec exists, both tags produce, and its
  verdict tag already scored 5/6 against Priya's labels (LP-427). Two things hold it: `income.type` is
  unscored, and the corpus contains **no** other-income document to exercise the trigger. Building the
  per-type continuance table (rather than one blanket three-year test) is correct and is what the ticket
  asks for, but it would be built against zero instances, and its two sharpest types cannot be classified
  at all. Recommend building the table with per-type abstain, and recording `input_resolves: false`.
- **IN-14 — keep, and correct the stale bar.** `needs-producer` is factually wrong; the tag has produced
  since LP-418. The honest status is `not-calibratable-yet` with `input_resolves: false`: zero rental
  documents reach any loan file.
- **OC-3 — build, hold.** Not a missing-producer drop. Its blocker is that no investment-occupancy file
  exists, so the tag resolves `n/a` everywhere.
- **DT-7 — hold, and the scope question needs answering first.** No producer, no spec, no bar, and the
  enum needs `unknown` sanctioned in the prompt (the `txn.is_nsf_or_overdraft` pattern) even though the
  runtime can coerce one. Before any of that: **is it the presence question or the determination?** Only
  the presence reading belongs to a processor, and I recommend that reading explicitly.

**The honest summary: all four rules are limited by the same thing — the corpus contains no instance of
any of their triggers.** That is a corpus finding, not four rule findings, and it is why every one of
them would ship `input_resolves: false` on today's data.
