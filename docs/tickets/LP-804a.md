## The split

LP-804 is **4–5 days** and brings four new dependencies (`pikepdf`, `pypdfium2`, `puremagic`,
`mail-parser`). Rule 2.1 splits a ticket that contains two things; §4 says a ticket that runs long
was too big.

The seam is clean because the "Done when" is already two clauses:

- *"a forwarded message with a nested PDF yields the PDF"* — parsing. **LP-804a**, stdlib only.
- *"a `.pdf` that sniffs as ZIP is quarantined; the extraction path reads only the rasterized
  derivative"* — safety. **LP-804b**, and it carries every new dependency.

`pymupdf` is **already** a dependency and rasterises, so `pypdfium2` may turn out to be unnecessary —
recorded for LP-804b rather than decided here.

## The two things the plan names, as named tests

### `Content-Disposition` is not how you find an attachment

The plan calls it out and it is the trap: the header is advisory, frequently absent, and **a photo
taken on a phone arrives `inline`**. Filtering on `attachment` loses the single most common thing a
borrower sends, silently, and the borrower is told their document never arrived.

The rule is *has a filename, **or** is not text*. `inline_photo_no_disposition.eml` has neither a
disposition nor a filename, and is found.

### `message/rfc822` is recursed into

Borrowers forward. A parser that stops at the outer message finds an attachment that is itself an
email and reports success. Depth-capped at 5, and **exceeding the cap is reported** — a message whose
parts were not fully enumerated must be distinguishable from one that had nothing deeper, or a
hostile sender hides a payload past the cap and the file looks clean.

**The fixture for this was wrong in its first version.** `attach()` inlines a message rather than
wrapping it, so there was no `message/rfc822` part at all and the recursion test would have passed
**without recursing** — `nesting_depth` came back 0 for what should have been 1. Regenerated with
`add_attachment()`, and `test_the_forwarded_fixture_really_is_nested` now asserts the *shape of the
fixture* rather than trusting it.

That is the second time this session a fixture has claimed something it did not contain. The lesson
generalises past this ticket: when a test's meaning depends on the fixture's structure, assert the
structure.

## Stdlib only

`email` with `policy=default` and `BytesParser` handles RFC 2231 continuations and the RFC 2047
fallback correctly and is maintained alongside the language. `mail-parser` buys convenience over a
module that is already right, and the two alternatives the plan rejects — dead since 2016, abandoned
— are the argument for depending lightly here.

Recorded as a deviation: the plan lists `mail-parser` as a new dependency and this does not take it.

## Filenames are text a stranger wrote

Decoded, then normalised **separately**, with the original kept because it is what a processor will
recognise and because destroying the evidence of an attempt is worse than storing it.

`test_filenames_are_normalised` covers the case worth naming: `photo‮gnp.exe` contains a
right-to-left override and **renders as `photo_exe.png`** in most mail clients — a file that looks
like an image and is not.

Nothing builds a path from either form.

## The inventory, and what it deliberately does not decide

One row per file-like part, written **only on a first insert** — a redelivery reaches the duplicate
branch and never gets here, so the same message twice cannot double the inventory and show a
processor one document twice.

The bytes are **not copied**. The raw `.eml` already holds them, and a second copy of a borrower's
document is a second thing to secure, retain and destroy.

Every row lands `safety_state = PENDING`, which is **neither safe nor unsafe**. LP-804b sniffs and
sanitises; INFRA-2's scan is asynchronous, so PENDING is a state that genuinely persists rather than
a momentary one, and nothing downstream may read it as a pass. The safety columns are created here so
LP-804b is a service plus a backfill rather than a migration against a table with live rows.

`UNIQUE (inbound_message_id, sha256)` — content-addressed, not keyed on the filename. A forwarded
thread carries `statement.pdf`, `statement (1).pdf` and `ATT00001.pdf`; that is one document, and the
filenames are exactly what differs.

## A config change, flagged rather than slipped in

`.pre-commit-config.yaml` now excludes `*.eml` from the `mixed-line-ending` hook.

**Email is CRLF on the wire.** RFC 5322 says so and SES stores what it received. The hook rewrote one
fixture to LF on its way into the repo — and every other fixture had been generated LF too, because
Python's `policy.default` uses `\n`. So the whole corpus was in a line ending **no real message
has**, and the MIME parser was tested only against a form it will never see in production.

All ten fixtures are now CRLF and the tests pass unchanged, which is the honest outcome to report:
the gap was real, and it happened not to have been hiding a bug. Had it been, this is the ticket
where it would have shipped.

This is a shared config file rather than something inside the ticket's blast radius, so it is called
out here rather than left in the diff. The exclusion is narrow — one extension, and these files are
test **data**, not source.

## Deliberately not done

- **No sniffing, sanitising or rasterising.** LP-804b, with the dependencies.
- **No TNEF / `winmail.dat`.** It needs a dependency, so it goes with the others.
- **No `mail-parser`, and possibly no `pypdfium2`.** See above.
- **No document creation.** An attachment becomes a `Document` when a processor accepts it, which is
  LP-806's; `document_id` is here and null.

## For the reviewer

The three standing reviewer checks:

- **Tenancy** — no `company_id` anywhere. `inbound_attachments` is a file-owned child in ADR-052's
  sense, reached only through its message, and scopes transitively through whatever routing assigns.
- **Message content in logs** — the log line records a **count and a max depth**. Not the filename,
  which is text a stranger wrote, and not the content type, which would leak what a borrower sent.
- **AI in the decision path** — none.

The judgement calls worth a second opinion:

1. **Not taking `mail-parser`.** The plan lists it. I think stdlib is right and less to trust, but it
   is a plan deviation and the convenience it buys is real if LP-804b finds edge cases I have not.
2. **Deduplicating attachments within a message on sha256, first-occurrence-wins.** The shallowest
   copy keeps its name, which is usually the sender's own rather than a client-generated `ATT00001`.
   A borrower who genuinely attached the same file twice on purpose sees it once — I think that is
   right and it is a choice.
3. **`_looks_like_a_file` excluding `multipart/alternative` explicitly.** Every other multipart is
   recursed into before the test is reached; that one is named because it is the body's own
   container and would otherwise be the one non-text part that reaches the check.
