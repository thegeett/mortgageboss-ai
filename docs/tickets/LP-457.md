# LP-457 — Centralise LLM model selection; switch extraction to Haiku 4.5

## What this ticket is

Model names were effectively centralised through `config.py` settings, but with **two** settings where three
purposes exist — extraction and reasoning shared one knob (`anthropic_model_extraction`). This splits them into
**three tiers, one per purpose**, adds a guard so no caller can hard-code a model, then switches **extraction**
to Haiku 4.5 while **reasoning stays on Sonnet** (the live rules were calibrated on Sonnet reasoning). One model
call per document in Phase D; two documents.

## Phase A — the full table of every model reference (the most useful output)

Every caller already reads `settings.anthropic_model_*` — **no caller hard-coded a model**. But there were only
TWO settings, and **extraction + reasoning shared `anthropic_model_extraction`** (the config comment said so).

| purpose | callers | read | value (before) |
|---|---|---|---|
| **classification** | `ai/classification.py`, `ai/summarization.py`, `services/needs_dedup.py` | `…_classification` | haiku-4-5 |
| **extraction** (true) | `ai/extraction/model_call.py`, `tasks/document_processing.py` | `…_extraction` | sonnet-4-5 |
| **reasoning** (12) | `tag_materialization/ai.py`, `ai/{tag_production,rule_judgment,tag_correlation,cross_source,generic_analyzer,observation}.py`, `verification/finding_guidance.py`, `services/{verification_run,tag_production,tag_correlation,needs_ai}.py` | **`…_extraction`** (conflated) | sonnet-4-5 |
| home | `core/config.py` | — | the settings |
| env (wins) | `backend/.env`, `.env.example` | override | agreed with code |
| literal, NOT a selection | `ai/cost.py` (PRICING table), `scripts/seed_dev_data.py` (`model_used` placeholder), tests | — | — |

**Which override wins:** `backend/.env` (pydantic env > code default); it agreed with the code (both Sonnet), so
no live conflict — but this was the Phase-C trap (a stale `.env` would defeat the switch). **Stale default:** none
active (the prior Opus-4-8 incident was reverted); stale *prose* remained (`needs_ai.py` "Opus", `pay_stub.py`
"Opus-class", `staging-recon.md`) — the two code comments were fixed here. Frontend: no model references.

## The design: one PER PURPOSE (three settings), home = `config.py`

A single constant would drag the 12 reasoning callers onto whatever extraction uses — exactly today's problem.
So:

```python
anthropic_model_classification = "claude-haiku-4-5"
anthropic_model_extraction     = "claude-haiku-4-5"   # LP-457 switch (was Sonnet)
anthropic_model_reasoning      = "claude-sonnet-4-5"   # STAYS Sonnet — the live bars are calibrated on it
anthropic_model_analysis       = "claude-sonnet-4-5"   # LP-457 review — the Tier-3 generic analyzer, its OWN knob
```

**Review addendum — a FOURTH tier, `analysis`.** The Tier-3 generic analyzer (`ai/generic_analyzer.py`,
unrecognised documents) is a PERCEPTION task, not calibrated reasoning — so it was given its own knob
(`anthropic_model_analysis`, Sonnet by default) rather than sharing `reasoning`. That way a future re-point of
the reasoning model for calibration never drags this understanding task along. Behaviour is unchanged (both are
Sonnet today); it is only decoupled. So there are **four** tiers: classification · extraction · reasoning ·
analysis — the analyzer moved off `reasoning` onto `analysis`, leaving 11 callers on the reasoning tier.

All three env-overridable (`ANTHROPIC_MODEL_CLASSIFICATION / _EXTRACTION / _REASONING`) from the one home. A
**guard test** (`tests/ai/test_model_selection_lp457.py`) fails CI on any literal `claude-*` in `app/` outside the
config home (exempting the pricing table + the seed placeholder) — so a future hard-coded model is caught.

## What changed

- **Phase B (behaviour-neutral):** added `anthropic_model_reasoning` (default Sonnet); moved the 12 reasoning
  callers from `…_extraction` → `…_reasoning` (same value, Sonnet — reasoning behaviour UNCHANGED); fixed the
  stale "Opus" / "Sonnet by default" comments; added `ANTHROPIC_MODEL_REASONING` to `.env` / `.env.example`; added
  the guard test.
- **Phase C (the switch):** `anthropic_model_extraction` → `claude-haiku-4-5` in `config.py` **and** `backend/.env`
  **and** `.env.example` (all three, so the env override doesn't defeat it). The 2 true-extraction callers now
  use Haiku; the 12 reasoning callers are untouched (Sonnet).
- **Token ceiling:** `RETRY_MAX_TOKENS = 32768` holds — Haiku 4.5 caps at 64K output (same as Sonnet 4.5), so
  32768 (half) stays reachable, not stranded. The per-type first-attempt tiers (4096/8192/16384) are unchanged.
  The comment was updated to name both models.

## Phase D — the two-document diff (Haiku vs the stored Sonnet extraction; reported, not predicted)

Two real documents re-extracted on Haiku 4.5, diffed field-by-field against the stored `claude-sonnet-4-5`
extraction.

### Credit report — LF-96SV (the dense nested case, 18 tradelines)
- **Status: succeeded.** **Tradelines: 18 (Sonnet) → 18 (Haiku) — MATCH.** The nested list the ticket flagged
  came through complete; no dropped rows.
- Typed-core: 17 same, 12 different, 1 newly-null. **Most "differences" are Haiku populating fields the STORED
  Sonnet extraction left null** — because that stored extraction predates LP-445/LP-446, which ADDED those fields
  (ssn_alert_status, address_usage_alert, credit_report_current_employer/occupation/previous_employer,
  address_tenure). So Haiku is MORE complete on those, not worse — a schema-vintage artifact of the baseline, not
  a model gap. `tradeline_count`/`open_tradeline_count` is a field-name difference (both captured 9).
- **Genuine minor deltas (real, reported):** `score_model` 6 entries → 3 (Haiku dropped the VantageScore rows on
  a verbose field); `security_freeze_or_fraud_alert` 4 → 1 (partly restructured — the SSN alert moved to the typed
  `ssn_alert_status`); `total_monthly_debt_payment` 1432 → 1426 (a $6 sum difference); `borrower_former_address`
  dropped the ZIP+4. None drop a row or corrupt a load-bearing value.
- **Tokens: 32,902 in / 8,191 out → $0.0739** on Haiku (the same call on Sonnet ≈ $0.222 — ~3× cheaper).

### Pay stub — LF-6T3N (the density selector mis-picked; honest caveat)
- **Status: succeeded.** Earnings lines: **0 (stored) → 3 (Haiku).** ⚠️ **This is NOT a regression** — the stored
  extraction predates LP-446 (which added `earnings_lines`), so the baseline has 0; Haiku extracted the 3 real
  lines on this stub correctly.
- ⚠️ **Selection caveat:** the script picked the densest by STORED row count, but every stored pay stub has 0
  earnings_lines (pre-LP-446), so it grabbed Akash's **3-line** stub, not Bansari's **9-line** one. The denser
  9-line pay stub was NOT tested (respecting the two-document limit). The credit report's 18-tradeline list is the
  harder nested-density case, and it passed.
- Typed-core: 12 same, 4 different, 1 newly-null — again mostly Haiku populating LP-446-added fields
  (`employee_address`, `employer_address`, `total_deductions_current`) the stored baseline lacked; `employer_name`
  differs only by punctuation (`N. A.` vs `N.A.`); `pay_frequency` newly-null is the one genuine miss.
- **Tokens: 4,624 in / 3,221 out → $0.0207.**

## The verdict: is Haiku 4.5 safe for dense nested documents?

**Yes, on this evidence — with two minor caveats to watch.** The credit report's **18 tradelines came through
18/18**, status succeeded — the exact dense-nested stress case, passed. Typed-core is equivalent-or-better (Haiku
filled fields the pre-LP-445/446 baseline lacked). The **only genuine regressions** are on **verbose
free-text/enumerated fields** — `score_model` (6→3) and `security_freeze_or_fraud_alert` (4→1) — plus a $6
payment-sum difference and a dropped ZIP+4. None drop a list row or corrupt a load-bearing typed value. At ~3×
lower cost, the switch is safe for the extraction tier. Reasoning stays on Sonnet, untouched.

## Assumptions / decisions

- Three settings, one per purpose — extraction and reasoning MUST be separable (the ticket changes one, not the
  other). Reasoning stays Sonnet: the 37 live rules' bars were calibrated on it.
- The Phase-D baseline is the STORED Sonnet extraction, which predates LP-445/LP-446 — so many field-level
  "differences" are the baseline's missing fields, not Haiku regressions. The **row counts** (18 tradelines) are
  the cleanest, vintage-independent signal, and they matched.
- The guard exempts `cost.py` (a pricing table keyed by model) and `seed_dev_data.py` (a stored-value
  placeholder) — data, not selection.

## NEW gaps / what remains

- **The 9-line pay stub was not tested** (the density selector mis-picked on the pre-LP-446 zero-row baseline). A
  denser pay-stub check is a cheap follow-up if wanted — the 18-tradeline credit report is the harder case and it
  passed.
- **A corpus re-extraction on Haiku is its own ticket** (out of scope here) — the switch changes future
  extractions only; stored extractions are unchanged.
- **Verbose-field completeness** (`score_model`, alert strings) is slightly lower on Haiku — worth a glance if a
  rule ever depends on the full multi-entry string (none does today).
- `docs/deploy/staging-recon.md` still carries stale "Opus 4.8" drift notes (a historical recon snapshot) — left
  as-is (out of scope).
