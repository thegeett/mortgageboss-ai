# LP-390-5 — Calibrate the income tags against Priya's labels

## What this ticket is

The first measurement of the income tag layer against a domain expert. For each tag Priya labeled, the REAL AI
reasoner was run on the same subjects (the committed LF-6T3N sample fixture — invented test identities, no real
PII; keyless) and scored against her golden by the stable `(tag_id, subject_id)` key — reporting accuracy, n,
and every disagreement WITH the AI's reasoning (LP-334: the reasoning is where a prompt bug shows).

**These scores are a point-in-time LIVE run** (claude-sonnet-4-5, 2026-07-22) — the model is non-deterministic,
so the numbers are indicative of behaviour, not a byte-reproducible artifact. The scoring MECHANISM
(`score_snapshot_against_golden` + `test_income_calibration_lp390_5`) is reproducible and keyless.

## Phase 0 — the setup (confirmed)

- **Real reasoner, not a stub.** `materialize_tags(…, ai_reasoners=None)` runs the real model over the AI
  groups; `produce_stage_b_sourcing_tags(…, reasoner=None)` runs the real Stage-B for `has_identified_source`.

### The three findings (the disagreements + reasoning are the deliverable)

**1. `has_identified_source` — 93.8% (15/16), calibration-passed.** The priority tag, its first real
measurement — and the reframing worked: it scores high. The one miss is the redacted-memo class:
> golden `yes`, predicted `no` on `INBOUND PAYMENT RECEIVED` — AI: *"No candidates were provided and the
> deposit description is generic with no payroll/employer/interest intrinsic signal."* The AI is defensible
> (a generic memo is genuinely un-sourceable from the description alone); Priya knew the counterparty from
> outside the memo. This is the memo-richness limit (LP-379-F), not a prompt bug. **Ready for a bar (n=16
> adequate).**

**2. `owner_matches_borrower` — 100% unknown: a real producer/context bug.** Every one of the 5 abstained,
with the SAME reasoning:
> *"Account holder is 'Jordan A Rivera' but NO BORROWER NAMES were provided in the loan file to compare
> against."*
The `stmt_facts` group receives only the statement document's fields, never the borrower names (MISMO/1003), so
it structurally cannot answer "does the account holder match the borrower?" — it correctly abstains, on EVERY
file. Priya labeled `yes` (she can see the borrower). **This is a context gap the calibration surfaced: AS-6's
tag is un-producible until the group sees the borrower names.** → its own fix ticket (LP-390-8: feed the
sourcing/statement group the borrower identity context), NOT a bar.

**3. `is_reserve_eligible` — 0% (0/5): a systematic prompt/domain disagreement.** All 5 predicted `yes` where
Priya labeled `no`, with reasoning like:
> *"Standard checking/savings account, normal balances, no restrictions/retirement discount → reserve-
> eligible."*
The AI treats any liquid deposit account as reserve-eligible; Priya's `no` reflects a stricter underwriting
call (these specific accounts are not counted as reserves — likely because they hold the down-payment / EMD, or
another agency nuance). The AI's reasoning is plausible, so this needs a DOMAIN clarification with Priya AND a
prompt alignment, not just a prompt tweak. → its own ticket (a Priya-confirmed definition, then a prompt fix).

**4. `apparent_category` — 24.5% is an ARTIFACT, not a real accuracy.** Priya's golden here is FREE TEXT
(`"transfer to some one"`, `"Credit card payment"`, `"fee"`, `"big paymrny out"`, `"trasfer"`), not the enum —
so a byte-compare against the AI's enum output (`transfer_own`, `debt_payment`, `vendor`) scores most as wrong
EVEN WHEN THE AI IS RIGHT: e.g. golden `"transfer to own account"` vs predicted `transfer_own` (conf 1.0,
reasoning *"ONLINE TRANSFER FROM OWN ACCOUNT"*) is a semantic MATCH scored wrong. The clean measurement needs
LP-379-F's free-text→enum relabel applied to the golden first. On the CARD-PURCHASE memos (30+ of the 50), the
memo is genuinely ambiguous (`CARD PURCHASE / PAYMENT`) and Priya's own free-text is inconsistent
(`fee`/`debt_payment`/`transfer`), so those stay the redacted-memo class. → **data-blocked on the relabel**;
do not read 24.5% as the AI's accuracy.

### Unmatched labels (reported, not dropped)
6 labels had no prediction: `stmt.owner_matches_borrower` and `stmt.is_reserve_eligible` on `inv1`/`inv2`/`inv3`
(the investment-account documents). The `stmt_facts` group did not materialize a tag there — those are
`investment_account` docs (the `asset_facts` group's territory), so the stmt tags never produce on them. A
labeled subject the producer doesn't cover is a finding, surfaced here rather than silently scored.

## What each result unblocks / holds for LP-390-6/7

- **`has_identified_source` → LP-390-6 can set a bar** (n=16, 93.8%). The one miss is memo-data, not a prompt
  bug — a moderate bar with the memo-richness caveat.
- **`owner_matches_borrower` → HELD** on a context fix (LP-390-8): the group needs the borrower names. No bar
  until it can produce a real value.
- **`is_reserve_eligible` → HELD** on a Priya definition + prompt alignment (its own ticket). No bar.
- **`apparent_category` → HELD** on the LP-379-F relabel; re-score after mapping the free-text golden to the
  enum (the AI is often semantically correct, so the true accuracy is much higher than 24.5%).
- **`liquidation_terms` / `has_2yr_history` / `current_address_type` → indicative only** (n<5): gather more
  labels before any confident bar.

## Phase 3 — tests + what changed

- **`live_calibration.score_snapshot_against_golden`** (new): joins a whole materialized snapshot's predicted
  tags to the golden by `(tag_id, subject_id)`, scoring transaction / borrower / Stage-B / document tags
  together (unlike `calibrate`, which is one AI-group per single-document snapshot). Reports unmatched.
- **`test_income_calibration_lp390_5`** (new, keyless): the join scores matches by the declared method, reports
  a labeled subject with no prediction as unmatched (never a silent pass), and handles correct abstention.
- **No tag/rule/producer change; `ACTIVE_RULE_IDS` unchanged (17); full suite green.** The committed artifacts
  are the sample fixture worksheet + aggregate scores (the LF-6T3N identities are invented test data, confirmed
  — no real PII); the separately-generated DB worksheet stays gitignored under `calibration-local/`.
- **Priya's golden (89 labels) is committed** with this ticket (she labeled +11 since LP-390-3a), so the
  measurement is reproducible against the committed golden.

## Assumptions, decisions & gaps

- **The scores are a point-in-time LIVE run** — non-deterministic; re-running will shift the numbers slightly.
  The verdicts (which tag passes / needs a fix / is thin) are robust to that noise.
- **No ADR** (a measurement). The three findings each become their own follow-up (LP-390-8: owner_matches_
  borrower context; the is_reserve_eligible definition; the apparent_category relabel re-score).
- **A reported gap:** the `stmt_facts` group not covering investment-account docs (the 6 unmatched) — either
  the labels are on the wrong subject for those docs, or the group's applicability needs widening; for
  LP-390-8 to disposition.
