## Section 1 — the splitter

### It splits; it does not interpret — and that is enforced, not requested

The rules read a layout we know and give the lender's words exactly, every time, for nothing. This
runs only when `needs_ai` is set: the rules could not find where one condition ends and the next
begins. Even then the model's only job is to draw those boundaries.

**A prompt cannot enforce that.** What enforces it is that every `verbatim` the model returns must
claim a stretch of the input, and anything that cannot is dropped with a warning. A model that
paraphrases, summarises, tidies or invents cannot get its text into `verbatim_text` — the field
ADR-405 says carries the lender's own words.

### ⚠️ Why the check is a span claim and not `"..." in text`

Substring-ness is a property of each row **alone**. It says nothing about the relationships between
rows, and three failure modes live in that gap — the first of which a membership test cannot even
see:

1. **A row assembled from two distant fragments.** Every word is present somewhere, so `in` returns
   true while the row is a sentence the lender never wrote.
2. **The same span returned twice.** Both copies are genuinely in the input and both pass a per-row
   check. Nothing downstream would remove them either: rule 6's duplicate dedup lives in the
   **reader**, and this path never touches it — two identical conditions would reach the review
   screen at confidence 0.6 with no way to tell they came from one demand.
3. **A span crossing a real boundary.** The tail of one condition plus the head of the next is a
   perfectly valid contiguous substring, reads as plausible prose, and is the AI's most natural
   error on exactly the unstructured input this module exists for.

So `_Coverage` claims **positions**: every character of the input is assigned to at most one
condition, heading or `ignored` entry. A duplicate cannot claim a taken span. A stitched row can
claim nothing. And a boundary-crossing row is admitted — it *is* real text — but the genuine
conditions either side can then no longer claim their own spans, so what is left over is reported as
`unassigned_lines` instead of vanishing.

**Line-based coverage would not have caught the third**, because both lines are covered, just cut in
the wrong place. That distinction is why the partition was built first rather than retrofitted: a
line-based check and a span-based one need different data structures, and tests written against one
do not transfer.

### ⚠️ What the partition does NOT check: where the cuts fell

Review asked the question I put to them — can a response where every row claims a legitimate span,
with nothing unclaimed, still be a wrong split? **Yes, two ways**, both measured through this
module:

```
one condition cut in two:
  in  'TC: Title company to include lender loan number on all checks sent to lender.'
  out ['TC: Title company to include lender loan number', 'on all checks sent to lender.']
  -> 2 rows, 0 rejected, nothing unassigned, no warning

two conditions merged into one:
  in  two real conditions, one per line
  out ['Provide copy of invoice for credit report. Provide copy of invoice for final ...']
  -> 1 row, 0 rejected, nothing unassigned, no warning
```

**The reason is structural.** A partition constrains **coverage**, not **boundary placement**.
`claim` asks only whether a span is unclaimed; `unclaimed` reports only gaps. Neither asks where a
cut landed — so any set of non-overlapping spans that tiles the input passes, and the correct split
is only one of the many tilings that do.

Boundary errors *are* caught whenever they leave a remnant, which is most of them — an arbitrary
wrong cut usually strands something, and that is what the crossing-boundary test exercises. A clean
tiling leaves none.

So the claim **"AI only splits, enforced by code rather than by instruction" holds for
verbatim-ness and for coverage, and does not hold for boundaries.** Those rest on the prompt, which
addresses them explicitly and states the asymmetry — a condition carrying an extra sentence is a
small fix on the review screen; a condition split in half is two half-conditions, both wrong.

**A shape heuristic would catch both cases and is deliberately not implemented.** A row whose span
does not begin at a line start or end at a line or sentence end is suspicious, and both cases above
violate that. It is not built because this stage has **three failed gap rules** behind it, and a
fourth heuristic makes wrong answers rarer and more believable rather than fewer. The limitation is
named — here and in `_Coverage`'s docstring — instead.

**⚠️ The consequence reaches LP-909, so it is recorded rather than left implicit.** Case 1 is this
feature's duplication failure arriving by a fourth route: two rows fingerprint separately, so the PDF
path yields one condition where the AI path yields two, and §8 step 2's "6 seen again, 0 new" breaks
again. Case 2 is worse in kind — the second demand is not duplicated but **gone**, folded inside
another condition's text, with nothing unassigned and no warning, so a processor reading the review
screen has no signal that anything was lost.

The sharpest statement of the limitation is not "some wrong splits survive" but this: **the correct
split of two conditions and the wrong merge of two conditions are the same shape to every check that
exists.** The control run proves it — identical `rejected`, `unassigned` and `warnings` for both.

### ⚠️ A constraint LP-909 should meet as an input, not discover afterwards

Since the code cannot catch a boundary error, **the boundary limitation is discharged at review
time** — and the review screen as specified does not discharge it evenly:

- **Case 1 is findable.** Two adjacent rows reading as halves of one sentence look wrong, and a
  processor who notices can fix it.
- **Case 2 is invisible.** One plausible, correctly-worded condition with a second demand inside it.
  Nothing flagged, nothing unassigned. A processor cannot detect an absence they were never shown,
  and the only clue would be a count they have nothing to compare against.

§LP-909 describes the screen as rows grouped by heading — code, category, editable wording, notes,
owner hint, confidence, low-confidence first — plus warnings for duplicates, unassigned lines and
unknown codes. **The input text surfaces nowhere except unassigned lines**, so there is no view in
which the boundaries are visible against the text they were drawn on.

**The data for one already exists**: `ParsedRow.source_line_numbers` is populated (and was kept
correct through LP-907 precisely because "those numbers are what the review screen points at"), and
`_Coverage` knows each row's claimed span. Rendering the pasted text once with each row's span
delimited — for AI-split rounds only — turns case 2 from invisible into obvious, because a demand
sitting inside another row's highlight is what a person spots and code does not. That is LP-909's
call and its screens have a Must-match list; it is recorded here so the constraint arrives before the
layout is fixed rather than after.

### Details worth stating

- **Whitespace collapses on both sides; case does not fold.** A sheet prints a condition across
  several lines and the model returns it as one — a literal comparison would reject the correct
  answer. But the lender's capitalisation is part of the wording, so folding case would admit a
  model that "improved" a sentence.
- **`bucket_kind` is always `UNKNOWN`.** The heading is carried through exactly as printed; reading
  it as a bucket is interpretation, and LP-906's mapping applies only to layouts we recognise.
- **Codes keep their leading zeros** (ADR-407).
- **Confidence 0.6** (`AI_SPLIT_CONFIDENCE`), below the review screen's 0.8 threshold so every AI row
  is flagged. It is not a claim that the *wording* is uncertain — that is exact, or the row does not
  exist.
- **A dropped row's text is never logged or surfaced.** It is a string the model produced: the one
  thing here most likely to be wrong, and it could contain anything (spec §9.5).
- **`temperature=0.0`**, so the same sheet splits the same way twice — without which a re-parse could
  not be compared with the parse it replaced (spec §9.6).
- **Failure is typed.** "The model could not be reached" and "this page had no conditions on it" lead
  a processor to different actions; returning `[]` for both makes the first indistinguishable from
  the second (spec §9.8).

### ⚠️ Deviations, each with its reason

1. **The prompt is `conditions/split_v1.txt`, where the spec writes `split_v1.md`.** All 125 prompts
   in the tree are `.txt` and `load_prompt` takes whatever relative path it is given, so the
   extension carries no meaning — consistency with the repo is the only thing at stake.
2. **The splitter lives in `app/services/`, not `app/conditions/`.** That package is pure: no
   database, no network, no model call. This calls a model, so it sits beside `needs_ai.py`, which is
   the same shape.
3. **`app/ai/prompts/conditions/` has no `__init__.py`.** Neither do `needs/`, `analysis/` or
   `summarization/`, and `needs/needs_reasoning.txt` loads in production — the file is decorative
   here, and `hatchling` ships the directory either way.

### Recorded gap — the OCR branch is untested on this machine

Spec §LP-908 says the AI's input is the paste **or OCR of the rasterized pages**, never the PDF's raw
text layer. `ocr_available()` returns **False** here and `tesseract` is not on PATH, which is also
why two `test_page_ocr` tests are among the four pre-existing suite failures.

So the paste branch — the one §8 step 6 actually exercises — is fully tested, and the PDF-via-OCR
branch is **recorded as unverified rather than claimed**. It is the same honest position LP-907 took
on a real portal paste.

### The sentence this whole stage reduces to

> **A test that fails because the assertion was too broad is cheap; one that passes because it was
> too narrow is not.**

Every one of this stage's green-but-meaningless checks was an assertion narrower than the property
it claimed: `cost_estimate > 0`, the `or True` tautology, the monkeypatch detached from its target,

### ⚠️ A correction that propagated through four files

The NPI reasoning attached to `failure_detail` was wrong in three files and in a comment written for
this ticket. All four said it "reaches the readonly layer, which scrubs identifier SHAPES only".

Checked: `parse_report` is in the **EXCLUDED** set (`tests/test_readonly_query.py`), and migration
`d1f4b8c25e93` drops it whole — the view projects `reader`, `reader_version`, `ai_used`,
`duplicates_dropped`, `warning_count`, `unassigned_count`, every one derived. `failure_detail` never
reaches the readonly layer, so it is never scrubbed, and the scrub-shapes argument belongs to columns
that *are* exposed.

**⚠️ And the obvious account of how it happened is also wrong.** I first wrote that
`models/condition_round.py` "always said it correctly" — it does not say it at all. That line is
about **`header`**, a different column:

```
header:        "dropped whole rather than scrubbed: a scrub matches identifier SHAPES, and a
                name is not digit-shaped"                                            (:134)
parse_report:  "NPI AS A WHOLE, because `unassigned_lines` holds lines lifted from the sheet
                verbatim"                                                            (:145)
```

Both were correct at LP-904 and both still are. The repo never carried two contradictory statements
about one field, which would have been the more alarming finding.

**What actually happened is more ordinary and more useful.** The `header` comment states a true rule
in language general enough to sound like it governs the whole readonly layer. The service-layer
version borrowed that framing and applied it to a field where the *conclusion* holds (do not put a
name there) but the *mechanism* does not (this field is never scrubbed because it is never exposed).
Then it propagated.

So the failure is not "copies drifted apart" — copying was not the problem, and making the two
statements agree would fix nothing, because they already agree. It is **a correct sentence about one
field reused as a general rule.**

That sharpens the habit this stage has been leaning on. "Put the fact at the code" has worked every
time — `uwm_block_start`'s residual, `_Coverage`'s limitation, the `KNOWN_UNWIRED` entry, the two
enqueue comments — and this case shows its limit: the fact **was** at the code, correctly, twice.
What travelled was a rationale lifted from a neighbouring field, and putting facts at the code does
not stop a true sentence being carried somewhere it is false. The narrower rule:
**state the reason in terms of the specific field, not the mechanism class.** "Dropped whole rather
than scrubbed" is about scrubbing in general and travels; "`parse_report` is excluded, so nothing in
it is ever exposed or scrubbed" names the field and does not.

**A second inaccuracy found while checking this**, and fixed: `parse_report`'s own comment claimed
"the typed failure reason … is exactly what a staging query needs, so the readonly view exposes
those as separate scalars". The view exposes `reader`, `reader_version`, `ai_used`,
`duplicates_dropped`, `warning_count` and `unassigned_count` — **not** the failure reason. A false
statement at the code, of exactly the class this section is about.

**The reason that does hold is stronger**, and it is the one LP-904's review established: the value
is stored in a column whose NPI status is already decided. `parse_report` is excluded *because*
`unassigned_lines` inside it holds verbatim sheet text — so quoting a name into `failure_detail` puts
NPI at rest in a field nobody can inspect to find it. Identical to the loan-information warning fixed
earlier in this stage, where nothing escaped the view and it was still wrong to store.

## Section 2 — wiring

### ⚠️ Reverting to `PARSING` moved LP-905's stranded-round gap onto the interactive door

LP-905 recorded this gap and deliberately left it: the enqueue happens **after** the commit —
correctly, since a worker that picked the round up first would find no row — but if `.delay()` raises
or the broker is down, *"the row is committed in `PARSING` and nothing moves it. The processor sits on
screen S1-02 ('Reading…') indefinitely."*

Verified that the paste door has the same shape: `api/conditions.py` commits, refreshes, and only
then calls `.delay()`.

**Asserting the enqueue does not close this.** The endpoint test proves the code path calls
`.delay()`; it passes just as happily when the call was made and never arrived. The failure mode is
not "we forgot to enqueue".

**And this ticket widens the exposure.** Before, only the upload and forward doors could open a
`PARSING` round — both kicked off by a processor who then goes away. The paste door is the one a
person *watches*: they paste, sit on S1-02, and expect rows in seconds. So the most-watched door
became a door that can strand.

### The mitigation, and why it is not scope creep

A failed enqueue now marks the round `PARSE_FAILED` with `failure_kind = "enqueue_failed"` and a
sentence the processor can act on, instead of leaving a spinner with no end.

**This repo already has both shapes and a rule for choosing between them**, and the rule picks this
one. `documents.py`'s `_enqueue_reprocess` logs and moves on, because the document is fine either
way. Its `_enqueue_full_reprocess` *reports* the outcome, and the LP-637 review says exactly why:
its callers set a blocking state first, and *"a swallowed failure made that permanent: a FAILED
document became a PENDING one with a type and no error, which reads as healthy, is invisible in the
UI."* A round stuck in `PARSING` is that same shape — healthy-looking, and invisible.

`kombu.exceptions.OperationalError` is caught specifically, never a bare `except Exception`
(spec §9.8): that is the broker refusing the message, which is the failure the round must survive.
Anything else is a bug and should reach the error handler rather than be filed as a parse failure.

**The upload and forward doors share the shape and are deliberately left**, with the mitigation
recorded as available to them. They are LP-905's, already committed, with their own test surface —
and changing two shipped doors inside an AI-split ticket is how a ticket becomes a refactor, which
is this repo's own stated reason for leaving `_is_borrower_facing` and friends alone.

**⚠️ The window is narrowed, not closed, and the reaper's priority must not be downgraded on the
strength of it.** The round is committed in `PARSING` *before* `.delay()` is reached, so the
`PARSE_FAILED` write is a **second transaction**. If that write itself fails, or the process dies
between the two, the round is stranded exactly as before. What changed is the size of the window —
from "every broker outage" to "a broker outage plus a second failure" — which is a large improvement
and not a fix.

**A reaper is still the real fix and still unbuilt.** What changed is the priority: LP-905 recorded
the gap when it affected two background doors, and it now affects the one a person waits at.

**The record lives at the code, not only here.** `api/conditions.py`'s upload door and
`api/inbound.py`'s forward door each carry a comment saying they share this exposure and are
deliberately unmitigated. Without them a reader arriving at the upload enqueue sees a *guarded
sibling 125 lines above it in the same file* and cannot tell a decision from a gap — which is the
reading error this stage has produced repeatedly, and which putting the fact at the code has fixed
every time.

### What section 2 does

LP-907 deliberately returned `DRAFT` instead of the spec's `PARSING` when `needs_ai` was set, and the
reason recorded there was explicit: *"LP-908 does not exist, so that branch would enqueue nothing and
leave the round in `PARSING` with no worker and no exit."*

**That reason has now expired**, so the deviation gets reverted rather than left standing: a paste the
rules cannot split becomes `PARSING` with a queued split task, which settles it to `DRAFT` with the
AI's rows — or to `PARSE_FAILED` with the typed reason. The task needs registering in `_TASK_MODULES`
(the guard in `tests/tasks/test_task_registration.py` enforces it), and `parse_report` gains the
splitter's version beside the reader's.
