# LP-622 — every judgment finding tells a processor what to do, and OC-3 states the amount

## The report

OC-3's card on LF-ABRS read, in full:

> the AI judged 'no' — an AI verdict a human must ratify (it never auto-ships)

No rental income, no property, no amount, no fix. The substance was all present in the provenance
panel — the model's own paragraph names the $3,000 and the missing lease — and none of it in the
sentence a processor reads.

## Cause

OC-3 declared **no `guidance:` block and no `verdict_labels`**, so it fell to `_verdict_message`
(`rule_engine/judgment.py`), whose docstring already predicted both halves of this:

> Without it the text states a bare domain value ("the AI judged 'yes'") and never the QUESTION, which
> on a rule whose "yes" is the BAD answer is worse than uninformative.

and, on `how_to_fix`:

> the finding model already has a field for it, **which judgment rules previously hard-coded to None —
> the reason no judgment finding has ever told anyone what to do.**

The mechanism to fix this shipped in LP-520 / LP-522. **Five of nineteen judgment rules had adopted
it.** The other fourteen — CR-10, FR-3, ID-8, ID-9, IN-7, IN-13, IN-14, OC-3, PC-8, PR-3, PR-4, PR-5,
TI-2, TI-6 — each rendered the same wordless card with a NULL fix.

LP-522 left them deliberately: *"inventing a fix for a rule nobody has read is worse than vague
wording, because it sends a processor for the wrong document with confidence."* That caution is
honoured by READING each rule, not by leaving the text unwritten — so each block below was written
against that spec's own criteria, its guideline citation, and the enum its explanatory tag actually
carries.

## What changed

**1. Guidance for all fourteen.** `action` keyed on the verdict; `why` + `how_to_fix` keyed on an
explanatory TAG rather than the verdict, because the reason varies with the evidence and not the
answer — PR-5 separates a C6 rating from an unreadable one, CR-10 separates FHA's aggregate test from
Fannie's occupancy-and-property-type rules, IN-13 keys on the income TYPE because the continuance
requirement is per-type and one sentence would be wrong for most of them.

**2. OC-3 states the amount.** A new derived loan tag,
`property.subject_rental_income_monthly`, read from the MISMO real-estate-owned schedule's
`is_subject` row (LP-596). The card now opens:

> **Document the $3,000.00 monthly rent claimed on this investment property** — obtain a current lease,
> Schedule E from the tax return, or an appraisal rent schedule (Form 1007 / 1025).
>
> The application claims $3,000.00 a month in rent on this investment property, and the file carries no
> lease, Schedule E or appraisal rent schedule establishing it. The figure rests on what the
> application says about itself.

The tag is on `reasoned_over`, so it is also evidence for the judgment: $3,000 a month unsupported and
$150 a month unsupported are not the same file.

**The amount appears on every OC-3 finding on every file**, not only this one — OC-3 is scoped to
investment occupancy (a primary residence resolves `occupancy.rental_support` to "n/a" and is
not_applicable, producing no finding at all), so it shows wherever the rule fires.

Which surfaced a defect in review, before it shipped. The generic placeholder loop renders an
unresolved tag as its raw value or "not established" — fine on a chip, wrong inside prose. Every OC-3
sentence read **"The application claims unknown a month in rent"** the moment the REO schedule named no
amount, and that is reachable rather than theoretical: an investment file stating occupancy but no
rent, or any file with no REO schedule. An unresolved money tag now renders as the noun phrase "an
unstated amount", every template is worded to hold it, and the action headline carries no figure at all
because no wording of "Document the ... monthly rent" survives both branches. The six-way matrix
(three support values x amount-unknown / tag-absent) is pinned in
`test_oc3_reads_correctly_however_the_amount_lands`.

Its discipline:

* **the SUBJECT row, not the first row** — a borrower with three rentals has three, and one is this
  loan's. No subject row, or more than one, abstains rather than picking.
* **gross preferred over net, and which one is recorded** — Fannie qualifies on 75% of GROSS (IN-14's
  cited primary), so running a net figure through the factor would haircut an already-hair-cut number.
* **absent is not $0** — a zero or missing amount abstains, the fail-closed shape LP-375 settled for
  the housing inputs.

**3. Money renders as money.** `_guidance_fields` special-cased `txn.amount` and rendered every other
money tag as its raw `str(value)`, so the rent would have printed `3000.00` in a sentence asking a
processor to go and document it. An explicit `_MONEY_TAGS` set rather than "anything that parses as a
Decimal" — a count, a percentage and a number of days all parse, and none takes a dollar sign.

**4. Two allow-lists inverted into invariants.** `test_the_other_judgment_rules_are_untouched` and
`test_a_rule_without_guidance_is_untouched` both pinned the un-migrated set. An allow-list grows
quietly and says nothing when a NEW judgment rule ships wordless; the replacements fail the moment one
does — `test_every_active_judgment_rule_has_guidance`, plus a check that every verdict in a rule's
`value_domain` has an action (a missing one is a KeyError at message time, on whichever answer is
rarest and least likely to be seen before a processor sees it). The fallback branch is now unreachable
from any shipped spec but is still live code, so it keeps its own tests.

## Checked and NOT a defect

**The missing document reference on OC-3.** I reported this in-session as "judgment.py never sets
`source_content_ids`, so no judgment finding on any file carries document links". That was wrong.
`_attach_document_provenance` (`services/verification_run.py:741`) runs over ALL results, backfilling
each subject's document through LP-619's resolver, so the eight `per_document` judgment rules do carry
links. OC-3 gets none because its subject is `loan` — and that is LP-619's deliberate "empty is
honest": the finding rests on the ABSENCE of documents, so there is nothing to point at. Recorded here
so it is not re-opened.

## Scope

`priya_validated` is unchanged everywhere — this writes what a processor reads, not what a rule
decides. No verdict, gate, threshold or tag value moves.

The wording of fourteen rules' guidance is worth the domain expert's eye, in particular CR-10's split
between FHA's aggregate test and Fannie's occupancy rules, and IN-13's per-type continuance. None of it
can change an outcome if wrong — it can only send a processor after the wrong document, which is why
each was written from the rule's own cited guideline rather than from the rule's name.
