# LP-380 — Priya's activation bars: the decision surface for which rules may go live

## What this ticket is

An **activation bar** is the accuracy a rule's load-bearing AI tags must reach before the rule ships a TRUSTED
(auto, non-ratified) verdict. It **cannot be computed** — its height is the cost of error for that rule, a
domain judgment (Priya's). This builds the per-rule decision surface — every inert rule with its MEASURED tag
accuracy (LP-379), its auto-ship-vs-ratify status, its FP-vs-FN cost, and a **proposed default bar** — so Priya
can set each one. It sets no bar (`validated: false`) and activates nothing (LP-389).

## Acceptance criteria

- Every inert rule has a row: load-bearing AI tags, each tag's measured accuracy (or UNMEASURED), auto/ratify,
  FP/FN cost, a proposed default + rationale, and a calibratable status. None blank.
- `not-calibratable-yet` ≠ bar-unmet — an unmeasured rule is blocked-on-calibration, distinct and never "just
  a higher score away".
- Every bar `validated: false`; declared, resolved by registry, no per-rule branch; below-bar → `needs_review`
  (reconciled with LP-376-B).
- `ACTIVE_RULE_IDS` unchanged; nothing activated; full suite green.

### The counts — the honest activation state

| status | count | meaning |
|---|---|---|
| **calibratable-now** | **2** | IN-1, IN-5 — a bar can be set and met today |
| **not-calibratable-yet** | 14 | a load-bearing AI tag is produced but UNSCORED, or measured only in another context — **blocked on calibration** |
| **needs-producer** | 1 | IN-14 — `occupancy.rental_support` doesn't materialize |
| **no-ai-dependency** | 6 | parsed/deterministic — no AI gate; activation is a wiring decision (cf. active IN-2/ID-8) |

**Only 2 of 23 inert rules are calibratable-now.** Priya can set a bar for those two; the rest are blocked on
calibration / a producer / a wiring decision — reported so a rule never ships on a tag nobody measured.

### The apparent_category subtlety (LP-379-F, load-bearing)

`apparent_category` reads "100%" in the headline, but that is only for payroll/interest/transfer_own on this
file's generic memos. The categories AS-2/AS-5/AS-12 actually read — `gift`, `loan_proceeds`, third-party —
are UNMEASURED (LP-379-F: unmeasurable on redacted memos). So those rules are **not-calibratable-yet**, not
calibratable — the headline number does not transfer to the category a rule consumes.

## Phase 1 — the bar mechanism

- `app/verification/rules/activation_bars.yaml` — one entry per inert rule: `status`, `ships`, `threshold`
  (null unless calibratable-now), `validated: false`, `load_bearing_ai_tags`, `fp_fn`, `rationale`.
- `app/verification/rule_engine/activation_bars.py` — `load_activation_bars()` (validates: covers exactly the
  inert set; validated=false; a threshold only when calibratable-now; known status/ships; non-blank rationale)
  and `activation_mode(bar, accuracy)` — the pure reconciliation with LP-376-B.
- **Declared, no per-rule branch** — `activation_mode` depends only on the bar's data (a test pins two rules
  with identical bars get identical modes).
- **One safety with LP-376-B** — `activation_mode` returns `blocked` (not calibratable), `ratify` (a judgment
  rule — never auto-ships), `auto` (calibratable, at/above bar), or `needs_review` (calibratable, below bar).
- **Nothing activated** — `ACTIVE_RULE_IDS` untouched; the bars are set, the activation pass is LP-389.

## What LP-389 (activation) now has to work with

A per-rule bar with `validated: false` and a status. LP-389 activates a rule only when its bar is `validated`
(Priya-confirmed) AND its `activation_mode` at the measured accuracy is `auto` (or `ratify` for judgment
rules). **Today that is 0 rules** — the 2 calibratable-now bars are unvalidated (Priya hasn't set them), and
the 21 others are blocked. The gating surface is honest: activation is blocked on calibration + Priya's bars,
not on engineering.

## Findings (reported)

- **A rule that may never auto-ship:** the judgmental rules (AS-12, IN-7, IN-13, IN-14) NEVER auto-ship
  (LP-376-B) — their bar is "ratify-only"; a human ratifies every verdict. That is by design, not a gap.
- **IN-1 fraud-adjacency:** IN-1 feeds a deterministic income-variance/fraud verdict; even at 100% on one
  file, ratify-only may be the right call until measured on more files — flagged for Priya.
- **The IN-10/IN-11 per-document gap (LP-385):** they read `is_declining`/`has_2yr_history` per-DOCUMENT while
  the producer is per-BORROWER — a producer/consumer mismatch to resolve before calibrating those two.
- **`occupancy.rental_support` has no producer** — IN-14 is blocked on a producer, before any bar.

## Assumptions & decisions

- **Every FP/FN call and every threshold is a PROPOSED default flagged for Priya** (`validated: false`). This
  ticket decides none.
- **Unmeasured ≠ low bar** — encoded as a distinct status with a null threshold; the loader rejects a
  threshold on a non-calibratable rule.
- **Derived/transitive AI dependencies** (IN-1 via the shortfall, AS-4 via the reserves calc, AS-7 via
  nsf_count) are noted per rule; the chain should be verified when that rule is calibrated.
- **No ADR-worthy prompt/rule change** — this is a declared decision surface; recorded as ADR-305 because it
  defines what an activation bar is and the calibratable/blocked split LP-389 depends on.
