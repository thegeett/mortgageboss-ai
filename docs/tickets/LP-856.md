 # LP-856 — a draft about nothing, and a button that makes it presentable

Status: spec. **Blocked by LP-853.** Screen 8.

Epic: [`docs/domain/communication/v1-epic.md`](../domain/communication/v1-epic.md) · Screens: [`v1-screens.md`](../domain/communication/v1-screens.md) · Spec: [`comm-v1-draft-only-spec.md`](../domain/communication/comm-v1-draft-only-spec.md)

## The report

> "Also let's give option for processor to compose new free email, where they just write email and
> there will be AI button clicking on it, AI make the message more professional."
>
> "Also simple create email draft button for new free draft with AI composition."

## The free draft

A third button on the Communication page — **Compose** — producing an ordinary draft with **no needs
attached**. Same list row, same modal, same buttons, an empty "What it asks for" block.

`custom.v1` already exists as a template key. **This is not a second kind of object**, and it must
not become one: a free draft that needed its own list, its own modal or its own send path would
double every future change to drafts.

**The recipient is typed, not derived.** There is no party to look up an address for. Editable,
defaulting to the borrower, and **nothing written back to the file's party addresses from here** —
an address typed for one message is not a fact about the file.

## The AI button

One control in LP-854's toolbar: **✦ polish**. Violet, because violet in the Ledger means
**provenance — a model touched this** — and never status. Available on any draft, not only a free
one; a generated request a processor has rewritten by hand is exactly where it is wanted.

### It proposes; it does not replace

The rewrite is shown as a **proposal**, with the original held, and two actions: **Keep this** and
**Undo — put mine back**.

A rewrite that lands silently on save is a message going out in words nobody read — and the
processor is the one who will be asked about those words later. One click to accept, one to discard,
and the original recoverable until they choose.

### It fails visibly or not at all

`email_draft_enabled` is off in every environment today. LP-833's compose toast is already careful
about this — it says *"using the standard wording"* rather than claiming a model wrote something it
did not — and this button follows the same rule.

**When the model is unavailable the button says so and leaves the text alone.** It never returns
something subtly different and calls it polish. A silent degradation here is worse than an error,
because the processor cannot tell which version they are looking at.

### What it is allowed to change

Tone, grammar, structure, greeting and sign-off. **Not facts.** The prompt is constrained to
rewriting what is there — it does not add a deadline, a document, an amount or a date that the
processor did not write. A polish that invents "by Friday" is a commitment the file did not make.

## What it must not break

- The draft list, the modal and LP-855's buttons are shared. No branch on "is this a free draft"
  beyond the empty needs block.
- LP-853's format rule: a polished body is authored content, so it stores `html` and
  `_regenerate` refuses it — which is correct, because there is nothing to regenerate.

## Acceptance

1. Compose creates a draft with zero needs that appears in the list and opens in the same modal.
2. Polish with the flag off returns an error the processor can read, and the text is unchanged.
3. Polish with the flag on shows a proposal; **Undo** restores the original exactly, including
   formatting.
4. Accepting stores `body_format = 'html'`.
5. A typed recipient does **not** appear in `party_requests` afterwards.
6. A polish prompt given a body with no dates returns a body with no dates. Checked, not assumed.

# What was built

Status: **done**. Commit message starts `LP-856 —`.

## The free draft

`create_compose_draft` and `POST /messages` already existed — LP-818 built them for spec 4.3's
"compose", and the service tests have been green since. What LP-856 adds is the way in, and the
proof that the draft it makes goes down the same path as every other one.

- `components/file/communication/compose-draft-dialog.tsx` — three fields and a button. Mounted
  only while open, like the catalog dialog.
- `ComposeDraftButton` on the communication page, outline to "Request documents"' primary.
- `useComposeDraft` in `lib/api/messages.ts`.

**`template_key` stays null — and `custom.v1` is real.** The ticket says `custom.v1` "already
exists as a template key", and it does: `app/communications/templates/custom.v1.txt`, a
`TemplateSpec` taking `subject_line` and `message_body`, with a pinned content fingerprint. A first
grep over file *contents* found nothing and I wrote that it did not exist; the string is a
**filename**, which is why. The template carries the secure-channel notice every other outbound
message gets.

`create_compose_draft` has stored the processor's body raw, with `template_key=None`, since LP-818.
This ticket **leaves that as it is** — see "Not done" — and asserts it rather than assuming it.

**The recipient is seeded from `/borrowers`, not from the loan file.** The first attempt read
`file.data.borrowers`, which is `BorrowerPublic` — the *"safe borrower view — masked_ssn only"* its
own docstring describes, carrying no email. Widening it would have put a borrower's address into a
payload every file screen loads in order to supply a default value. `useLoanFileBorrowers` returns
`BorrowerDetail`, which has `email` and `is_primary`, and it runs only while the dialog is mounted.

## ✦ polish

**Backend.** `app/ai/polish.py` — `polish(text)` returning a `PolishOutcome`, and the guards that
decide whether a rewrite may be shown at all:

- `invented_date_words` — the date vocabulary is *derived* from `calendar`, not typed out, and a
  word that merely contains a day name is not a date.
- `unsupported_numbers_in` — a number in the rewrite that was not in the original.
- `regulatory_grounds(text)` in `app/ai/email_draft.py`, new alongside the existing
  `regulatory_refusal`. The guard compares the grounds the rewrite **introduced**
  (`grounds(after) - grounds(before)`), which is what lets a processor's own `$10,000` through while
  refusing an amount the model added. Comparing only the *first* ground would have let a message
  that already mentioned a figure quietly acquire a commitment; that is why it returns a set.

`POST /outbound/draft/{draft_id}/polish` returns `{polished, refusal}` and **writes nothing** —
verified by instrumenting the call: *assignments to the draft inside polish: none; commits: False*.
The route is allow-listed in `test_no_draft_save_route.py`, with its field deliberately named `body`
so that guard can still see it.

**Frontend.** The ✦ control sits below the editor in the compose window, in the `ai` token —
violet, which in the Ledger marks **provenance** and never status. It is offered on **any** draft,
not only a free one.

The rewrite is held as a proposal and replaces the editor in place under an *"After ✦ polish — not
saved yet"* header, with **Undo — put mine back** and **Keep this**. Accepting saves HTML, which
makes it authored content under LP-853's rule and puts it out of `_regenerate`'s reach — correct,
because there is nothing to regenerate on a message somebody chose.

## What the tests caught

- **`is_open_draft` is `false` on a composed draft, and that is correct.** It has meant one thing
  since LP-829 — the *borrower's* document-request draft, under `DRAFT_TEMPLATE` — and a free draft
  has no template. `is_editable` is the wider flag LP-831 added because the narrow one was being
  asked a question it does not answer, and it is the one the modal reads: measured, `is_open_draft`
  appears nowhere in the frontend outside the type declaration. Asserted as `False` so that
  widening it, or gating the modal on it, fails.
- **The proposal could have replaced the working body invisibly.** A mutant that wrote the rewrite
  into `bodyHtml` at proposal time passed every assertion — the visible editor is seeded from
  `data.body`, so it looked untouched, and the polished words would have gone out on the next
  "Mark as sent". The fix is `bodyThatWouldGoOut()`, which clicks the send button and reads the
  body it carries. Both "unchanged" cases now assert through the door that matters.
- **`emailBodyToHtml(proposal)` tripped the `dangerouslySetInnerHTML` guard** in
  `email-body-templates.test.ts`, which is the guard working. It is allow-listed on the
  *escape-first renderer* argument, not on provenance: model output is the least-trusted string on
  this screen, having been nowhere near the server's allowlist, because polish writes nothing. A
  test plants `<script>` in a rewrite and asserts it renders as visible text; a mutant that injects
  the proposal raw fails it.
- **Three sibling suites broke on an unmocked `usePolishDraft`** reaching for a QueryClient they do
  not have. Mocked in each, at rest.
- A stale docstring claimed `BorrowerPublic` carries `email`. Corrected.

## Not done

- **The free draft does not render `custom.v1`.** The template exists, is fingerprinted, and carries
  the *"Email is not a fully secure channel"* notice that every other outbound message carries; a
  composed draft gets the processor's raw text and no notice. Routing compose through the renderer
  would change the output of an endpoint LP-818 shipped and covered, which this ticket does not ask
  for — so it is asserted as it stands (`test_a_composed_draft_appears_in_the_list_and_opens_in_the
  _same_modal` pins `template_key is None` and the absent notice) and named here. **It is the one
  thing in this ticket I think should change and did not.**
- **`was_edited` still deserves its own ticket.** It is a string comparison of two separately
  assembled messages and has produced a false-edit bug in three consecutive tickets. Untouched here.
- **Nothing records that a body was polished.** A processor who accepts a rewrite leaves a draft
  indistinguishable from one they typed. The ticket does not ask for provenance on the row and
  adding a column would widen the scope; it is the obvious next question.
- **The prompt is not the guard.** `polish` refuses a rewrite that invented a date or a number, but
  with `email_draft_enabled` off in every environment the *model* half has never run against a real
  response. What is checked is the refusal logic, exhaustively; what is not is the prompt's own
  tendency.
