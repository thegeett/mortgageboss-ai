## What was built

**B1 — the `liability` subject family.** A fourth materialization subject alongside `document` / `loan` /
`borrower`. Its subjects come from `liability_rows` (`rule_engine/enumerators.py`) — **the same derivation
the `per_liability` rule enumerator uses**, so a tag can never materialize under an id no rule reads.
`test_subject_ids_match_the_rule_engine_enumerator_exactly` pins that contract.

**B2 — `liab.monthly_payment`,** the first produced `liab.*` tag. Parsed from whichever source the subject
came from, resolved through the family's alias map.

### The alias map — names only

The two sources name the same fact differently, so a declaration's canonical name maps to each source's
own column (`account_type` ← `type`, `balance` ← `unpaid_balance`, `creditor_name` ← `holder_name` on the
MISMO leg). ⚠️ **It normalises NAMES, never VALUES.** Mapping a bureau's `REV` to the vocabulary's
`revolving` is the open-vocabulary classification **ADR-353 defers to Priya** — which is why
**`liab.account_type` has no parsed producer**: a parsed tag is not validated against `allowed_values`, so
declaring it would ship out-of-domain values silently.

## Review findings, and what changed

Five of the seven touched this ticket's code. All are fixed; the reasoning matters more than the diff.

### 1. ⚠️ The tag never materialized in production — the headline claim was false

`materialize_tags` is called with `only_subjects=_MATERIALIZED_SUBJECTS` at both live sites in
`services/verification_run.py`. That set was `{document, loan, borrower}` — **`liability` was never
added** — so `in_scope("liability")` was False on every real run.

**Measured, not argued.** Running this ticket's own fixture through both call shapes:

| call shape | tags produced |
|---|---|
| as the TESTS call it (`only_subjects` omitted ⇒ everything) | **2** — `['4263', '914']` |
| as the LIVE run calls it (`only_subjects=_MATERIALIZED_SUBJECTS`) | **0** |

The tests passed because they omit the scope argument. **The second-order problem is worse:** the LP-373
orphan guard builds its "produced" set from `load_declarations()`, so *declaring* the tag made it look
produced regardless of live scope. Declaring it **disarmed the guard that exists to catch exactly this** —
a tag whose consumer couldnt_checks on every file, structurally, silently, forever.

**Fixed:** `liability` added to `_MATERIALIZED_SUBJECTS`, plus a new guard,
`test_declared_subjects_are_all_materialized`, asserting every declared subject is in that scope (or in an
explicit `_SUBJECTS_MATERIALIZED_ELSEWHERE` set for `transaction`, which Stage A/B produces). Verified by
reverting the fix: the guard fails with `declared subject(s) ['liability'] are never materialized`.

### 2. The context documented an opt-in it did not implement and could not receive

`_liability_context`'s docstring promised the app's stated liabilities "(opt-in)" via
`include_stated_liabilities`, "the SAME opt-in the borrower context uses". The body never read `opts`, and
`load_ai_groups` **raises `DeclarationError`** for any non-borrower group that sets that flag. So the first
liability AI group written against that docstring would either get no comparison set or fail at load.

**Fixed:** paragraph removed, replaced with why there is no such opt-in. Whether a liability-subject group
should see the stated set is a real design question — this family already carries **both sources as sibling
subjects** — not a flag to smuggle in.

### 3. The AI context bypassed the universal PII backstop

Every other list-derived context runs values through `_scrub_list_value`, whose own docstring calls it
*"THE UNIVERSAL backstop at the context boundary — the last gate before an AI reasoner"*. The liability
context used `_field_value` alone. A `ListRow.fields` value is a plain `Field`, never a `PiiField`, and
`ListSpec.redact` covers only the fields a spec **named** (`account_number_masked` on `_TRADELINES_LIST`)
— so a full account number a bureau prints inside `creditor_name` (`CHASE CARD 4111111111111111`) would
have reached the model unscrubbed. Dormant only because no AI group declares `subject: liability` yet.

⚠️ **Same class as the LP-479 review finding** (commit `704247b`): a declared per-field redact is not a
substitute for the universal backstop.

**Fixed:** values now go through `_scrub_list_value`.

### 4. The context emitted source-dependent key names

`read_field` normalised through the alias map, but `build_context` splatted `raw.fields` verbatim — so a
MISMO subject's context carried `type` / `unpaid_balance` / `holder_name` while a tradeline's carried
`account_type` / `balance` / `creditor_name`. Both arrive under **one** subject family, so a single group's
prompt saw two schemas and would silently under-read one leg.

**Fixed:** the alias map is applied inverted in the context. A column with no canonical name is still passed
through under its own name rather than dropped — nothing is hidden from a reasoner.

### 5. `heloc_credit_limit` was a value-semantics claim wearing a name mapping

The alias mapped the vocabulary's HELOC-specific limit onto `credit_limit_or_high_credit`, which **every
revolving tradeline populates**. It was **unconditional**, so the mapping is true only when the account
*is* a HELOC — precisely the classification the block four lines above says it refuses to make.

The consequence was live in the guard: `test_parsed_declaration_fields.py` treats the alias-map keys as the
legal universe, so declaring `liab.heloc_credit_limit: {mode: parsed, subject: liability}` would have
**passed every check and fed HCLTV a credit card's limit as a HELOC limit**.

**Fixed:** alias removed, with a comment saying what would have to exist (an account-type classifier) before
it comes back.

### 6. The D5 error message degraded for this subject

`_resolves` gained a `liability` branch; `_legal_universe` did not, so a typo'd liability declaration failed
with an empty universe and *"no close reference match"* instead of the nearest-legal-name hint the module's
D5 section explicitly promises. **Fixed:** matching branch added.

## Assumptions and decisions

1. **The alias map is the legal universe for liability declarations** (the guard's existing choice, kept).
   Removing `heloc_credit_limit` therefore also removes it from what a declaration may name — deliberate.
2. **No `include_stated_liabilities` for this family.** Deleting the false promise beats implementing it,
   because the loader guard that forbids it encodes a real constraint and relaxing it is a design call.
3. **Unaliased columns pass through under their raw name** rather than being dropped from the AI context —
   fail-open on *visibility*, fail-closed on *interpretation*: a reasoner may see an extra field, but only
   canonical names are comparable across the two legs.
4. **The ticket-id collision is reported, not resolved** — renumbering another session's staged backlog
   unilaterally is not this ticket's call.
