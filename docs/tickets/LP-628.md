# LP-628 — page-range extraction, so output size stops depending on document size

**Status: PHASE A COMPLETE.** Mechanism built and opted in for `bank_statement` only.
Phase B (extend by measurement) not started.

## The report

LF-AWBB, staging, 2026-08-24 02:28 UTC. A bank statement uploaded onto the LP-625 fix
(600s soft limit, already deployed as `staging-b5da562`) failed — but not on time:

| Step | Model | In | Out | Time | Stop reason |
|---|---|---|---|---|---|
| Classify | Haiku 4.5 | 40,746 | 152 | 8s | `end_turn` — bank_statement @ 0.95 |
| Extract | Haiku 4.5 | 34,386 | **16,384** | 68s | `max_tokens` — truncated |
| Retry | Haiku 4.5 | 34,386 | **32,768** | 126s | `max_tokens` — truncated again |
| Tier 3 | Sonnet 4.5 | 32,346 | 984 | 18s | `end_turn` — 5 findings |

Total 3m41s against a 600s budget. **Time was never the constraint.** The run produced
`extraction_truncated_after_retry` — the log line LP-625 could not find evidence of, and the
proof that `RETRY_MAX_TOKENS = 32768` is not a sufficient ceiling.

LP-625 is vindicated on its own terms: no retry loop, no stranded row, an honest terminal
state, and Tier 3 salvaging five findings. The remaining defect is a different one.

## The actual defect

A bank statement's extracted output is dominated by its transaction list. Output tokens
therefore scale with **transaction count**, which is a property of the document, not of our
configuration. Note the shape above: 34,386 tokens in, >32,768 out. The extractor is emitting
nearly as much as it reads, because it transcribes every transaction into JSON.

No fixed ceiling can bound a quantity that scales with input. Raising 32,768 → 64,000 buys
headroom for this statement and fails on one with twice the transactions. That is why this
ticket exists rather than a one-line constant bump.

This is not bank-statement-specific. Any extractor whose schema contains an unbounded list has
the same failure mode; bank statements are merely where it bites first and hardest.

## What already exists

More of this is built than expected:

- `app/services/pdf_utils.py::_first_n_pages_sync` slices a PDF with pymupdf
  `insert_pdf(src, from_page=0, to_page=n-1)`. **It already takes a start page** — generalizing
  to an arbitrary range is a parameter, not a rewrite.
- `cap_pdf_pages(content, media_type, max_pages)` is the shared "trim if over-cap PDF, pass
  everything else through untouched, never raise" wrapper. Two callers today: classification
  (LP-462) and Tier 3 (LP-463).
- `run_extraction_completion(...)` in `app/ai/extraction/model_call.py` is the single choke
  point every per-type extractor calls, and it **already detects truncation**
  (`stop_reason == "max_tokens"`) and owns the retry policy.

## Design

### 1. Trigger chunking reactively, not by threshold

The natural instinct is a page-count threshold ("chunk anything over N pages"). Reject it: it
needs per-type tuning, it penalises short-but-dense documents, and it chunks long-but-sparse
ones for nothing.

Instead, reuse the truncation signal we already have. `run_extraction_completion` currently
does: first call → truncated? → retry the **whole document** at a higher ceiling. Replace that
second step with: truncated? → **split into page ranges and extract each**. The document has
told us it is too dense; that is a better trigger than any threshold we could guess.

Cost for the overwhelming majority of documents is zero — they never truncate, so they never
take the chunked path, and their code path is byte-for-byte what it is today.

### 2. Chunking is per-extractor and declarative, defaulting to off

An extractor opts in by declaring a chunk policy: chunk-safe or not, page window, and how
results merge. Anything that does not declare one keeps today's behaviour exactly, including
the current high-ceiling retry as its fallback.

Not every document survives being cut. A bank statement is a linear transaction ledger and
splits cleanly. A credit report has sections that span pages and cross-reference each other; a
tax return's schedules interlock. Those need thought per type, and this ticket does not
pre-judge them.

### 3. The merge contract

Merging two partial extractions is the substance of the work. Three field categories, and they
must be handled differently:

- **Singleton/header** fields (account number, statement period, borrower name) — take from the
  first chunk that supplies one. Later chunks are **cross-checked, not overwritten**: a
  disagreement lowers confidence and is recorded, because two different account numbers across
  page ranges means the "statement" is actually two documents.
- **List** fields (transactions) — concatenate in page order.
- **Derived/aggregate** fields (totals, counts, `page_count_present`) — **recomputed after the
  merge, never taken from a chunk.** A chunk sees part of the document, so any total it reports
  is wrong by construction. `page_count_present` is already computed deterministically from the
  PDF rather than read by the model (LP-381/AS-9) and that precedent is exactly right here.

### 4. Boundary safety

A table row or a section heading can straddle a page break. Two options:

- **Accept the boundary.** Each chunk gets whole pages, so a row is never cut mid-render — only
  its surrounding context is lost. Simple, no dedupe.
- **One-page overlap plus dedupe.** Safer against a transaction printed across a page break,
  but needs a stable dedupe key (date + amount + description is not reliably unique — two
  identical $4.50 coffee charges on one day are a real thing, not a duplicate).

Recommendation: start with **accept the boundary**, and only add overlap if a real statement
demonstrates a loss. The dedupe key problem is worse than the boundary problem, and inventing a
key that silently drops a genuine repeat transaction is a data-integrity bug in a loan file.

### 5. Partial failure is total failure

If any chunk fails or truncates, the whole extraction is `failed` with an honest reason and
falls through to Tier 3 — exactly as today. **Never store a silently-partial list.** A missing
transaction in a stored extraction is invisible to a processor and to every downstream rule; a
failed extraction is visible. This follows the existing "abstain, never guess" principle
(LP-375, LP-622).

### 6. Non-PDF documents

JPEG/PNG cannot be page-sliced. They keep the current path unchanged. `cap_pdf_pages` already
establishes the "only `application/pdf` is touched, everything else passes through" convention
to follow.

## Phases

**Phase A — mechanism, proven on one type.**
Generalize the slicer to an arbitrary page range; add the chunk-policy declaration and the
merge contract; rewire the truncation branch of `run_extraction_completion` to chunk when the
extractor declares a policy. Opt in `bank_statement` only. Success criterion: the LF-AWBB
statement that produced `extraction_truncated_after_retry` extracts completely, with the
transaction list intact and totals recomputed.

**Phase B — extend by measurement.**
Confirm the at-risk list from `output_tokens` in the worker logs (not the combined
`tokens_used` above), then opt types in one at a time, each with its own merge policy and its
own judgement about whether it is chunk-safe at all.

## Companion, not in scope

Prompt caching is not used anywhere in `app/ai/` (`cache_control` appears in zero files).
Chunking re-sends the system prompt per chunk, so caching turns a real cost increase into a
negligible one. Worth its own ticket, and worth doing near this one.

## Open decisions for the approver

1. **Phase A scope** — bank_statement only, or bank_statement plus one more to prove the
   mechanism generalizes before committing to the abstraction? Recommendation: one type. A
   second type proves less than it costs, and Phase B is cheap once the contract exists.
2. **Interim ceiling bump** — raise `RETRY_MAX_TOKENS` 32,768 → 64,000 now as a stopgap so
   testing is unblocked while Phase A is built? It fits the time budget (observed ~260 tok/s →
   64K in ~250s, inside 600s) and helps the current statement, but it is a temporary measure
   that this ticket exists to make unnecessary. Recommendation: yes, if testing needs to
   continue this week; skip it otherwise, since it changes behaviour that Phase A then changes
   again.
3. **Boundary strategy** — accept-the-boundary (recommended) versus overlap-and-dedupe.

# Technical research (2026-08-24)

## Prompt caching on Bedrock — what is actually available to us

Verified against the AWS Bedrock user guide (`prompt-caching.html`), not inferred:

| Fact | Value | Consequence for us |
|---|---|---|
| Haiku 4.5 caching on Bedrock | **Supported**, GA | Not a blocker — extraction can cache |
| Minimum tokens per cache checkpoint | **4,096** | See the trap below |
| Max checkpoints per request | 4 | Ample |
| TTL | 5 min (default) and 1 h | 5 min covers a chunked run; 1 h unnecessary |
| Cacheable fields | `system`, `messages`, `tools` | A document block lives in `messages` — cacheable |
| Request form | `"cache_control": {"type":"ephemeral"}` per block, via InvokeModel | This is what `AsyncAnthropicBedrock` sends |
| Cache reads vs rate limit | **Not deducted** from the quota | Relevant to the per-process RPM limiter |

**Use explicit per-block `cache_control`. Do NOT use top-level auto-placement** — that convenience
field is exposed only on the newest Bedrock models (Sonnet 5, Opus 4.8) and is rejected on
Haiku 4.5.

### The trap that would have made caching a silent no-op

AWS: *"The minimum cache size is evaluated against the cumulative tokens across all three
sections combined, not each section individually."* Order is `tools` → `system` → `messages`.

Our `extraction/bank_statement.txt` system prompt is **11,235 chars ≈ 3,120 tokens** — **below
the 4,096 minimum.** A `cache_control` marker on the system block alone would silently cache
nothing: no error, `cache_creation_input_tokens: 0`, and a 1.25× premium bought for no reads.

Put the breakpoint on the **document block** instead. System (~3,120) + document (~31,000)
≈ 37,500 cumulative, comfortably over the minimum, and it caches both together.

### Where caching can and cannot pay — the complete map

1. **Across documents — impossible.** Documents differ; only the system prompt is shared, and at
   3,120 tokens it is under the minimum. Padding a prompt past 4,096 to make it cacheable would
   save ~3,120 tokens ≈ $0.003/document. Not worth engineering for.
2. **Classification → extraction — structurally impossible.** The cache is a prefix match and
   `system` renders before `messages`. The two calls use different system prompts
   (`document_classifier.txt` vs the per-type extraction prompt), so the prefix diverges before
   the document block is ever reached. No amount of marker placement fixes this. Do not try it.
3. **The truncation retry — cacheable, but conditional.** Identical system + document sent twice
   within seconds. Break-even is **P(retry) > 27.8%** (no cache: 1.0× / 2.0× with retry; cached:
   1.25× / 1.35×). Net on a retrying document **+$0.022**; on a non-retrying one **−$0.009**.
   Only worth enabling per-extractor where truncation is measured to be common.
4. **Across chunks — the one place it clearly earns its keep.** See below.

## What caching does to the chunking design

The chunk design has a fork that caching decides:

- **Option A — send only the page range.** Each page is sent once. Cheapest, but each chunk sees
  a slice with no document context (no header, no running balance, no "page 4 of 12").
- **Option B — send the whole document to every chunk** with an instruction naming the pages to
  extract. Every chunk gets full context. Naively 3× the input cost.

With a cache breakpoint on the document block, Option B's document is written once and read by
every subsequent chunk. Measured for this statement at N=3: Option A ≈ 43,700 input tokens,
Option B ≈ 59,200 effective. **Option B costs about $0.016 more per document** — small enough
that the choice can be made on accuracy rather than cost.

**This is the real reason to implement caching in this ticket**, and it is a genuine finding:
caching removes the main objection to the more accurate chunking strategy.

Concurrency caveat from the docs: a cache entry is readable only after the first response
**begins streaming**. Chunks must not all fire in parallel from cold — run chunk 1 first, then
the rest, or they each pay the write premium.

## The economics, measured on the actual failed document

Haiku 4.5 at $1.00/1M in, $5.00/1M out; Tier 3 on Sonnet 4.5 at $3.00/$15.00.

| Call | Cost | |
|---|---:|---|
| Classification | $0.0415 | |
| Extraction (16,384 out) | $0.1163 | **discarded** |
| Retry (32,768 out) | $0.1982 | **discarded** |
| Tier 3 fallback | $0.1118 | |
| **Total** | **$0.4678** | and no usable extraction |

**67% of the spend ($0.3145) bought nothing.** The 49,152 discarded output tokens alone are
$0.246 — 53% of the total.

Chunked, producing a usable result: **≈ $0.24** at N=2, N=3 or N=4. Chunk count is nearly
cost-neutral (pages are sent once either way; only the repeated system prompt scales), so **N
can be chosen for accuracy, not cost.**

**Output is 56% of the cost of a failed extraction.** Caching discounts input only. Chunking is
therefore worth roughly twice what caching is worth here, and the two interact: once chunking
removes the truncation retry, opportunity 3 above largely disappears with it. **Chunking is the
cost fix; caching is what makes the accurate chunking strategy affordable.**

## On the external best-practice literature

Searched for multi-page extraction practice. Most of it (LlamaIndex, Unstract, pdfplumber
threads, PyMuPDF4LLM) addresses **text-pipeline RAG chunking** — extract text, split on semantic
boundaries, embed, retrieve. That is a different problem: we send native PDF pages to a vision
model and never build a retrieval index, so the token-window and semantic-boundary advice does
not transfer.

The one transferable finding is the **continuation problem**, independently confirmed across
several pdfplumber discussions and a TurboLens write-up: a table row split across a page break
is the standard failure of page-wise extraction, and the standard remedy is a buffer — carry the
partial row forward and merge it with the first row of the next page, detecting incompleteness
by a heuristic.

This suggests a **third boundary option** better than both in the plan above: rather than
overlapping pages and deduping (which needs an unreliable dedupe key), have each chunk report
whether its last item looked cut off, and merge the tail forward. The model already sees the
page boundary; asking it is cheaper and safer than inferring it. **Recommendation updated: ask
the model, do not overlap.**

Sources: AWS Bedrock prompt caching user guide; pdfplumber discussions #768/#1019/#1188;
TurboLens multi-page table extraction (2026-05).

# Phase A — what changed

Approved decisions: full-document context per chunk (not page slices), `bank_statement` only,
no interim ceiling bump.

## Files

* **`backend/app/ai/extraction/chunked.py`** (new) — the shared mechanism. `plan_page_ranges`
  tiles a document into inclusive 1-based ranges; `run_chunked_extraction` sends the WHOLE
  document once per range with a cache breakpoint, sequentially, and returns one
  `ExtractionCall` per range. Generic: it holds no bank-statement knowledge, and an extractor
  opts in with an instruction builder plus a merge function.
* **`backend/app/ai/client.py`** — `build_document_block(..., cache=True)` attaches
  `cache_control: {"type": "ephemeral"}` to the document block, and `build_document_message`
  passes it through. `ai_call_succeeded` now logs `cache_read_tokens` / `cache_write_tokens`.
* **`backend/app/ai/extraction/bank_statement.py`** — `_chunk_instruction`, `_first_stated`,
  `_merge_chunk_results`, `_extract_in_chunks`; `extract_bank_statement` routes to the chunked
  path when `call.truncated`.
* **`backend/tests/ai/test_chunked_extraction_lp628.py`** (new) — 24 tests.

## Decisions that differ from the plan above

**Totals are NOT recomputed after the merge.** The plan said aggregate fields must be recomputed
because a chunk sees only part of the document. Reading `extraction/bank_statement.txt` showed
that is wrong for this schema: `total_deposits` and friends are the statement's OWN PRINTED
figures ("total deposits/credits for the period", each carrying a `page` and `snippet`), not sums
the model computes. Every chunk sees the whole document and reads the same box, so a printed
total is a whole-document read like the account number — first-non-null, cross-checked. Summing
them would have DOUBLED deposits on a two-chunk statement and inflated every reserves figure
downstream. Pinned by `test_a_printed_total_is_taken_once_and_never_summed`.

**Boundary handling is `BEGINS`, not a continuation flag.** The research recommended asking the
model whether its last row looked cut off, then merging the fragment forward. Telling each chunk
to claim a row by where it BEGINS achieves the same thing with no merge step and no flag to
mis-read: a row straddling a page break belongs to exactly one chunk by construction.

## Two defects the tests caught

* **Merged token counts were clobbered** by the truncated call's counts, under-reporting cost on
  every chunked document. Now the truncated attempts are ADDED — they were genuinely spent.
* **A document shorter than `pages_per_chunk` planned a SINGLE range** covering everything: the
  same request that had just truncated twice, for one more call's cost. The range now tightens
  whenever the plan would not otherwise split, and a single-page document is refused outright
  (`SINGLE_PAGE_REASON`) rather than re-asked.

## Not done

* **Phase B.** No other extractor is opted in; all ~119 others run today's path unchanged.
  Which types to add must come from `output_tokens` in the worker logs, NOT the combined
  `tokens_used` column measured above.
* **Chunking still starts after BOTH guarded attempts** (16,384 then 32,768). On LF-AWBB that
  retry cost $0.198 and 126s before chunking began. Chunking after the FIRST truncation would
  reclaim it, at the cost of the retries that do succeed on their own. Left as a tuning decision
  pending evidence of how often the 32,768 retry actually rescues a statement.
* **No cross-run memory.** A re-uploaded statement repeats the discovery (try, truncate, chunk).
* **Chunks run sequentially**, not in parallel. Required for the first chunk (a cache entry is
  only readable once the first response begins streaming) but chunks 2..N could overlap.
* **Not verified against a real statement.** Every test uses mocked completions. The LF-AWBB
  statement that produced `extraction_truncated_after_retry` is the acceptance case and needs a
  deploy to exercise.
