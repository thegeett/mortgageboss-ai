# LP-411 — Close the no-AI-threshold hold gap: `no-ai-threshold-pending`, and hold PC-7 honestly

## What this ticket is

LP-406-1b (PC-7) found the activation model has **no clean hold for a rule with no AI to calibrate but a Priya
threshold to sign off**. To hold PC-7 anyway, its bar was set `input_resolves: false` — **a value that same
ticket's own proof shows is FALSE** (PC-7's input resolves: `contract.days_until_closing == "1"` → SATISFIED).
A false value in the gate of record (`activation_bars.yaml`) is trusted by whoever reads the file rather than the
rationale — the **AS-5 stray-flag class** (LP-390-7) / the **IN-7 "a bar that lies" refusal** (LP-393-6).

This adds the missing eligibility case — a **third status `no-ai-threshold-pending`**
(`eligible = input_resolves AND validated`) — and restores PC-7's bar to the truth: `input_resolves: true`
(honest), held by `validated: false` (Priya's window, the real reason). No live rule changed; `ACTIVE_RULE_IDS`
stays **25**.

## D1 — The authoritative threshold flag

The runtime has **no** access to a "this rule's threshold needs sign-off" flag usable for PC-7:
- **`rule_kinds.csv` / the spec `reference_values.threshold_needs_signoff`** is **calculative-only** — `kinds.py`
  (`if rk.threshold_needs_signoff and rk.kind is not CALCULATIVE: raise`) rejects it on a **structural** rule,
  and **PC-7 is structural**. So PC-7 literally cannot declare a threshold sign-off there (its value is `false`,
  and can't be `true`).
- **`activation_bars.py`** imports neither specs nor kinds — `is_eligible(bar)` sees **only the bar**.

**Conclusion:** the signal must live on the **bar**. And it can't reuse the `validated` field on a plain
`no-ai-dependency` bar, because `parse_bar` **forbids `validated: true` on any non-`calibratable-now` status**
("a blocked rule cannot be signed off as live-able"). So the clean expression is a **new status** where
`validated` is meaningful and permitted.

## D2 — The eligibility change (flag vs status; the exact predicate)

**Chosen: a new status `no-ai-threshold-pending`** (the ticket preferred a flag "unless the code says
otherwise" — it did, per D1). A bar flag would (a) name-collide with the calc-only spec
`threshold_needs_signoff`, and (b) still need to relax the `validated`-only-for-calibratable invariant. The
status is self-documenting and scopes the relaxation cleanly.

**Before → after (`is_eligible`):**
- `calibratable-now`: `validated AND threshold != None AND measured_accuracy >= threshold` — **UNCHANGED**.
- `no-ai-dependency`: `input_resolves` — **UNCHANGED**.
- `no-ai-threshold-pending` (**new**): `input_resolves AND validated`.

`activation_mode` is **unchanged** — a no-AI status (incl. the new one) returns `blocked` there (it is the
AI-accuracy reconciliation; no-AI rules gate via `is_eligible`, not it). `parse_bar` gains: the new status in
`_STATUSES`; `validated` permitted for it; `input_resolves` permitted for it; and the D4 guard.

## D3 — The blast radius (the risk): ZERO

The change is purely **additive** — a new `if bar.status == "no-ai-threshold-pending"` branch; the
`calibratable-now` and `no-ai-dependency` branches are byte-identical. So **no existing bar's eligibility
moves.** Verified:

| bar(s) | status | eligible before | eligible after |
|--------|--------|:---:|:---:|
| IN-1, IN-5, IN-3, AS-2, AS-12, IN-7, IN-10, IN-11, AS-11 | calibratable-now (validated) | ✅ | ✅ |
| **AS-8**, AS-9, AS-10, IN-4, ID-5 | no-ai-dependency (input_resolves) | ✅ | ✅ (**the rule most at risk — a no-op for it**) |
| AS-3, AS-4, AS-5, AS-6, AS-7, IN-8/9/12/13/14, OC-1, IN-6 | held (various) | ❌ | ❌ |
| **PC-7** | no-ai-dependency → **no-ai-threshold-pending** | ❌ (`input_resolves: false`) | ❌ (`validated: false`) |

`eligible_rule_ids()` is byte-identical (the same **14**): `AS-2/8/9/10/11/12, ID-5, IN-1/3/4/5/7/10/11`. PC-7
was held, stays held — **no live rule deactivated**; nothing to STOP-and-report. The only change is PC-7's
status + `input_resolves` value, both making the bar **honest**.

## D4 — The loader guard (the LP-390-7 pattern)

**Added** a narrow, cheap guard: a `no-ai-threshold-pending` bar that is `validated: true` **must** have
`input_resolves: true` — you cannot sign off a threshold to activate a rule whose parsed input does not resolve.
This fails loud at LOAD (the AS-5 pattern) rather than being silently held by `is_eligible`. It does not
over-reject: a *held* bar (`validated: false`) is unaffected. *(A general "input_resolves matches reality" guard
is not cheaply checkable — the loader can't run the rule — and would over-reject; the specific false value this
ticket set is now removed at the source.)*

## THE PROOF (reported, not predicted)

- **PC-7 honest AND held:** `status == "no-ai-threshold-pending"`, `input_resolves == True` (was a false
  `False`), `validated == False`, `is_eligible(PC-7) == False`, `"PC-7" not in ACTIVE_RULE_IDS`.
- **`ACTIVE_RULE_IDS` unchanged — 25.** `eligible_rule_ids()` byte-identical (the same 14, listed in D3).
- **AS-8 (the live no-AI rule) unaffected:** `status == "no-ai-dependency"`, `is_eligible == True` (still live).
- **The new path both ways (constructed bars):** `input_resolves + validated → eligible`; `input_resolves +
  unvalidated → held`; `validated + not input_resolves → loader rejects` ("must have input_resolves").
- **`calibratable-now` unchanged:** IN-6/IN-3/the income wave behave identically (their tests pass untouched).
- **The LP-389 gate invariant holds:** `ACTIVE − BASE == eligible_rule_ids() == _ACTIVATED`.

- **No spec/tag/producer/prompt changed; the 25 live rules are byte-identical.**
