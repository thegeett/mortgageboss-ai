## The defect (confirmed)

`app/verification/ltv.py:103`:

```python
def _ratio(numerator: Decimal, basis: Decimal | None) -> Decimal | None:
    if basis is None or basis <= 0:
        return None
    return (numerator / basis * Decimal(100)).quantize(_CENTS, rounding=ROUND_HALF_UP)
```

⚠️ **`_ratio` is shared by ALL THREE ratios** — `ltv_pct`, `cltv_pct` and `hcltv_pct` all route through
it, so any rounding change touches all three at once. That is the first blast-radius fact.

## A0 — ⚠️ THE TICKET'S WORKED EXAMPLE IS WRONG, and so are two of its Phase C cases

Re-verified against the live guide, **B2-1.2-01, page dated 06/01/2022** (fetched 2026-08-13, tier **P**;
`robots.txt` respected, the page is public). The guide states the rule **and gives two worked examples**:

> "The result of these calculations must be **truncated (shortened) to two decimal places, then rounded
> up to the nearest whole percent**."
> "**94.01% will be delivered as 95%, and 80.001% will be delivered as 80%.**"

⚠️ **`80.001% → 80%`, per the guide itself.** Truncation to two decimals discards the `.001`, leaving
exactly `80.00`, which is *already* a whole percent — so the round-up moves nothing.

**The ticket says:** *"a computed ratio of 80.004%. Guideline — truncate to 80.00, round up to **81%**.
… the guideline requires MI and the current code clears the file."* **That is backwards.** 80.004
truncates to 80.00 → **80** — exactly what the current code produces. **There is no divergence on that
example at all**, and the motivating scenario for the ticket does not occur.

Checked against an implementation of the guideline rule:

| input | ticket's Phase C says | guideline actually gives | |
|---|---|---|---|
| 80.00 | 80 | **80** | ✅ |
| 80.001 | 81 | **80** | ⚠️ **ticket wrong** |
| 80.004 | 81 | **80** | ⚠️ **ticket wrong** |
| 80.499 | 81 | **81** | ✅ |
| 79.999 | 80 | **80** | ✅ |
| *94.01 (guide's own)* | — | **95** | ✅ matches the guide |
| *80.001 (guide's own)* | — | **80** | ✅ matches the guide |

**Where the divergence actually is.** Two places, and the first runs *opposite* to the ticket's claim:

1. ⚠️ **MI-1 (`> 80`): the CURRENT code is MORE conservative, in one narrow band.**
   Current fires iff `round_half_up(r,2) > 80` ⟺ `r ≥ 80.005`. Guideline fires iff
   `ceil(trunc(r,2)) > 80` ⟺ `r ≥ 80.01`. **For `r ∈ [80.005, 80.01)` the current code requires MI and
   the guideline does not.** Fixing this *relaxes* MI-1 in that band. (The guide's own
   *"rounding methodology that results in the same or a higher LTV ratio"* permits the current behaviour
   here — it is higher, not lower.)
2. **Everywhere else: the returned VALUE changes shape**, from a two-decimal figure to a whole percent —
   `80.95 → 81`, `96.50 → 97`. That is the real, broad change, and it is a *display* change on every file
   as much as a threshold one.

## A3 — ⚠️ THE FINDING: a whole-percent LTV cannot be compared against FHA's FRACTIONAL 96.5% cap

`_resolve_limit` compares `ltv_pct <= cap`. The caps:

| rule | cap |
|---|---|
| `conv.ltv.purchase_max` | 97 |
| `conv.ltv.cash_out_max` | 80 |
| `fha.ltv.cash_out_max` | 80 |
| Sun-West overlay (conv purchase) | 95 |
| ⚠️ **`fha.ltv.purchase_max`** | **96.5** |

Rounding **up to a whole percent** and then comparing against **96.5** is a category error:

```
raw 96.00  current 96.00 -> pass   guideline 96 -> pass
raw 96.01  current 96.01 -> pass   guideline 97 -> over    <== FLIPS
raw 96.25  current 96.25 -> pass   guideline 97 -> over    <== FLIPS
raw 96.50  current 96.50 -> pass   guideline 97 -> over    <== FLIPS
```

**Every FHA purchase loan with an LTV in (96.00, 96.50] flips from `pass` to `over`.** That band is not
exotic — **96.5% is FHA's actual maximum**, so real FHA purchase files cluster in exactly it. No file in
the current corpus sits there, so this is **latent, not live** — but it is the "verdict that moves and
nobody predicted" the ticket asks to surface.

The underlying reason: Fannie's whole-percent rounding governs **the ratio delivered to Fannie**. HUD's
96.5% cap is a different authority with an inherently fractional limit. One rounded value cannot serve
both.

## ⛔ THE SCOPE DECISION — and it is not the one-liner the ticket assumed

The ticket says *"a single-line arithmetic correction does not need [an ADR]"* and asks whether every
consumer should see the guideline value or only the threshold comparisons. **A3 answers it: a single
rounding cannot serve every consumer, because one live cap (FHA 96.5%) is fractional.**

**Recommendation: return BOTH, which is the shape the ticket itself anticipates.**

`_ratio` keeps producing the exact two-decimal figure; `LtvResult` gains a whole-percent
*delivered* value per ratio (`ltv_pct_whole` / `cltv_pct_whole` / `hcltv_pct_whole`), computed once in
`ltv.py` — never re-rounded at a call site. Then:

- **`loan.ltv_percent` (MI-1's input) → the WHOLE percent.** MI-1's 80% is a Fannie eligibility
  threshold and B2-1.2-01 governs it. The finding's evidence text cites **both** (`80.95% → 81%`) so a
  processor can still tell 80.01 from 80.99.
- **`_resolve_limit` → keeps the EXACT value.** Its caps are program limits from mixed authorities, one
  of them fractional; comparing a Fannie-rounded whole percent against HUD's 96.5% would fail 3 of the
  4 caps' intent. ⚠️ This is a deliberate, recorded divergence, not an oversight.
- **`mortgage_insurance.py` (`> 80`, `> 90`) → the WHOLE percent.** Both are whole-percent Fannie/FHA
  eligibility thresholds of the same kind as MI-1's.
- **Display (`calculations_section`, the API) → shows the exact value, with the delivered percent
  alongside.** Losing 80.95 in favour of a bare 81 makes a finding less checkable, not more.

**The alternative — change `_ratio` in place** — is genuinely one line and is what the ticket describes.
It is rejected because it silently breaks the FHA 96.5% comparison (A3) and degrades every display
figure. If that trade is acceptable, the one-liner is available and I will do it instead; the FHA flip
must then be recorded as accepted rather than discovered later.

⚠️ **This makes the fix non-local, so it warrants an ADR** — the ticket's own condition ("if consumers

# PHASE B / C — the fix, and the proof

## What changed

`ltv.py` now computes **both** figures from the **same raw quotient**, once:

| field | rounding | who reads it |
|---|---|---|
| `ltv_pct` / `cltv_pct` / `hcltv_pct` | half-up to 2 dp (**unchanged**) | display, and the **fractional** FHA cap |
| `ltv_pct_delivered` / … | truncate 2 dp → **ceil to whole percent** (B2-1.2-01) | `loan.ltv_percent` → MI-1, and `mortgage_insurance.py`'s 80% / 90% |

| consumer | takes | why |
|---|---|---|
| `loan.ltv_percent` (→ **MI-1**) | **delivered** | MI-1 asks a whole-percent Fannie eligibility question |
| `services/mi.py` → `mortgage_insurance.py` | **delivered** | PMI above 80%, FHA MIP duration at 90% — same kind of threshold |
| `services/ltv.py::_resolve_limit` | **exact** | its caps are mixed-authority and one is **fractional (FHA 96.5%)** |
| `calculations_section::map_ltv`, the API | **both** | a bare `81` hides whether the ratio was 80.01 or 80.99 |

`_ratio` is deliberately untouched — the defect was never that the exact figure existed, it was that it
was the **only** figure and so got used where the guideline's whole percent was required.

**MI-1's evidence text now carries both:** `"the loan-to-value is 94.44% (delivered as 95%) (340000.00
over the lesser of …)"`, so `80.95% → 81%` stays checkable on a finding.

## A bug this ticket's own tests caught, in this ticket's own first implementation

`delivered_percent` initially took the **already half-up-rounded** two-decimal figure. For a raw
**80.005** that is 80.01 → ceil → **81**; truncating the **raw quotient** gives 80.00 → **80**.
B2-1.2-01 says to truncate *"the result of these calculations"* — the quotient — so half-up must not run
first. Fixed by taking both roundings from a shared `_raw_ratio`, and pinned by
`test_delivered_truncates_the_RAW_quotient_not_the_half_up_figure`.

## The FHA band, proven on constructed values

No corpus file sits in the band, so it is proven **directly** rather than left hypothetical
(`test_fha_purchase_cap_must_use_the_exact_ratio_not_the_delivered_one`):

| raw | delivered | cap | with **exact** (shipped) | with **delivered** (rejected) |
|---|---|---|---|---|
| 96.00 | 96 | 96.5 | pass | pass |
| **96.01** | **97** | 96.5 | **pass** | **over** ← flips |
| **96.25** | **97** | 96.5 | **pass** | **over** ← flips |
| **96.50** | **97** | 96.5 | **pass** | **over** ← flips |

The test asserts the rejected direction explicitly, so if the delivered value is ever wired into the cap
comparison it fails with a message naming the band. Three of the four caps are whole percents
(`conv.purchase` 97, `conv.cash_out` 80, `fha.cash_out` 80); **FHA purchase 96.5 is the single
exception**, pinned so it is known to be one rather than assumed.
