## Design

**What moves our status, and when.** The option table's third column, read literally:

| Option | Our status | When (this ticket) |
|---|---|---|
| Ask the borrower / a third party | Waiting on *party* | when the email is marked sent — LP-922 writes that move; this ticket shows the "Becomes …" line |
| I'll do it | stays To do, then Ready | Ready once every live item on the condition is done ("Mark done" on the item) |
| Already in the file | Ready | at once |
| Ask the underwriter / Push back | Waiting on Lender | when the question is marked sent — LP-922 |
| Lender is doing it / Information only | no status | display only, never moves (§4a change 12) |

"At once" means **once the step is in force**: when the round's plan is confirmed, and for any choice
made after that. Before confirming, every step is a proposal (S3-02's own words), so choosing one moves
nothing. Automatic moves are **forward only, from To do**: the plan never moves a condition backwards and
never touches one she has moved herself past To do. Each move writes `condition_prep_moved` with
`by: "plan"` and the option that caused it, beside the `condition_plan_changed` the choice already
writes (LP-920). One function, `condition_plan.apply_step_status`, decides; `confirm_round_plan`,
`set_next_step` and `update_item` call it.

**Item done.** `PATCH /conditions/{id}/items/{item_id}` accepts `status: done | open` for an "I'll do it"
item only (an ask's item is done when its evidence passes — LP-923). Marking one done can move the
condition to Ready through the same function.

**Summary numbers (S3-12).** `ConditionSummary` gains `waiting_on_others` (open, our status Waiting),
`your_tasks` (open, with a live "I'll do it" step), `ready_to_send` (open, our status Ready) and
`has_plan` (any round of the file has a plan). Each is a filter: Waiting → our status Waiting; Ready →
our status Ready; Your tasks → a new `next_step` filter (`?step=i_will_do_it`; server side: the
condition's own step or a live item's option). The count and the filter are the same predicate over the
same rows. **Failed a check** has no data until LP-923 (evidence checks); its cell is added there.

**The bar is Stage 3's only on a file with a plan.** A file with no plan keeps Stage 2's seven cells
(S2-01, S2-02 unchanged); a file with a plan shows S3-12's: Open · Waiting on others · Your tasks ·
Ready to send · (Failed a check, LP-923) · Prior to docs open · Prior to funding open.

**Next step column (M3).** Replaces Owner in the list; the owner stays in the filter and on the sheet.
One token per condition from `nextStepToken` (pure, `lib/conditions/next-step.ts`):
"Lender is doing it", "Information only", "Question to UW" (push back / ask the underwriter),
"Your task · upload the invoice" (the library item's new `task` wording), "Waits on 1228",
"Already in the file · p.1", "In title email" / "Borrower + title emails" / "LO + attorney emails" (the
recipients of the condition's asks). LP-922 appends "· draft" / "· sent 08/28"; LP-923 puts "Evidence
failed a check — page 6" first.

**Display-only rows (M4).** A condition whose own step is "Lender is doing it" or "Information only"
stays in its heading group with a neutral token in place of the status select.

**"Waiting on LO" (M5).** The list's status select names who we wait on ("Waiting on Borrower"), from
`waiting_on`, which `ConditionPublic` now carries; `broker` reads "LO" there. The owner chip keeps
"Broker".

**Sheet (S3-01).** Next-step chips: every live step selected, plus "Already in the file" and "Ask the
underwriter" offered. A chip that is the condition's own step toggles it; an item's step is changed on
the item. Under the status: "Becomes **Waiting on Borrower** when the borrower email is marked sent."
(first ask), "Becomes **Waiting on Lender** when the question is marked sent." (push back / ask UW),
"Becomes **Ready to send** when your task is done." (I'll do it).

## Decisions

1. **Steps come into force at confirm.** The option table says "Already in the file → Ready", and S3-02
   says every step is a proposal until confirmed. Both hold only if the move waits for the confirm, so
   it does, and later choices move at once.
2. **Forward only, from To do.** The plan never moves a condition backwards and never overrides a move
   she made herself (a backward move needs her reason, ADR-408).
3. **"Mark done" is for her tasks only.** An ask's item is done when its evidence passes (LP-923); the
   server refuses "done" on it with "Only your own tasks are marked done here — an item you asked for is
   done when it arrives."
4. **Stage 2's bar on a file with no plan.** S2-01/S2-02 are files without a plan and stay as drawn;
   S3-12 is a file with one.
5. **Failed a check waits for LP-923.** It has no data before evidence checks exist; a cell that could
   only read 0 would claim a check ran.
6. **The library says what her task is** (`task` on an "I'll do it" item; required there, refused on an
   ask) — "upload the invoice", "log the verbal VOE call", "order the written VOE", "order the final
   inspection", "upload the documents".
7. **The sheet refreshes after a plan change.** `invalidatePlan` now also refreshes the open sheet and its
   history (it did not, since LP-920: an item added from the sheet appeared only after reopening it).
