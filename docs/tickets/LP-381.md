# LP-381 — Extract statement page counts (unblock AS-9) + map the 6 no-AI rules

## What this ticket is

LP-380 found **6 inert rules with NO AI dependency** — blocked only because a parsed field isn't extracted.
They need no calibration and no Priya bar (the cheapest, safest activations, the path IN-2/ID-8 took). This
extracts page counts (AS-9's blocker) AND maps all 6 to their parsed field + current state — so the extraction
work is scoped by evidence, and LP-382/383 are scoped by fact. It **activates nothing** (LP-389).

## Acceptance criteria

- A map: every no-AI rule → its parsed field → materializes today? → blocker → which ticket.
- Page counts extract for AS-9's doc-type; the emitted field names match AS-9's declared tags (the LP-333/369
  trap closed); AS-9 resolves to a real verdict when the fields are present.
- `ACTIVE_RULE_IDS` unchanged; no live rule's verdict changes; full suite green.

### The findings (the gate of record reshaped the ticket)

1. **ID-5 is activatable RIGHT NOW.** Its two parsed fields resolve with real values today — no extraction
   needed, just the name-match this map verifies. The cheapest, safest activation, ready for LP-389.
2. **The derived-4 (AS-3/AS-10/IN-3/IN-4) are NOT blocked on a missing extractor.** Their derived producers
   exist and run, but resolve `unknown` because their *inputs* are absent on LF-6T3N. They need a file that
   carries the inputs (or verification), not new extraction. (IN-4's employment dates → LP-382.)
3. **AS-9's blocker was bigger than framed:** `stmt.page_count_present` (the deterministic actual page count)
   was captured **nowhere** — `pdf_utils.page_count` existed but was called only from a dev endpoint, never in
   the ingestion pipeline. And `stmt.page_count_declared` (the printed "Page X of Y") had no extractor field
   (the code flagged this at `tag_production.yaml:102`, LP-369-exempted). AS-9 needs **both**.

## Phase 1 — page-count extraction

AS-9 fires when the declared page count exceeds the present one (a page is missing), both gated. Two fields,
two sources — per the "'page 3 of 5' vs '5 pages total'" distinction the ticket flagged:

- **`page_count_declared`** — the printed "of N", a MODEL read. Added to `BankStatementExtraction` (a
  `TypedField[int]`, `coerce_int`) + the prompt ("the TOTAL page count the statement PRINTS … null if no such
  'of N' is printed"). It parses to null when the statement doesn't print it → AS-9 honestly couldnt_checks.
- **`page_count_present`** — the DETERMINISTIC actual page total. A new `pdf_utils.pdf_page_count(content)`
  (lightweight PyMuPDF, never raises) is called in the extractor AFTER the model pass; the extractor already
  receives the PDF bytes, so this is computed from the file, **never a model read** (a model can miscount, and
  completeness must not be fabricated). Absent for non-PDF statements → AS-9 honestly couldnt_checks.

`stmt.page_count_present` is now declared in `tag_production.yaml` (parsed); the emitted field names match the
tags' `data` (`page_count_declared`/`page_count_present`) — the LP-333/369 silent-death trap closed for this
field, and the LP-369 exemption is removed (the exemption test enforces it: a now-resolvable declaration can't
stay exempted). **No rule spec was renamed** — AS-9's declared names were correct; the extraction was missing.

## Phase 2 — AS-9's resolution (reported, not predicted)

- **The field now extracts** — `pdf_page_count` returns the real page total (3-page PDF → 3), the extractor
  sets `page_count_present` deterministically and `page_count_declared` from the model, and given both tags
  AS-9 reaches a REAL verdict: `declared 5 > present 3` → **fired** ("a page is missing"); `5 == 5` →
  **satisfied**; only the deterministic present (no printed "of N") → **couldnt_check** (the honest
  completeness gap — there is no reference to check against).
- **On LF-6T3N: AS-9 does NOT yet resolve** — its stored extractions **predate** this field, so the
  page-count tags don't materialize (the probe showed `not_applicable` / `couldnt_check`, not a page-count
  verdict). **A re-extraction of the bank statements** would populate `page_count_present` (always,
  deterministic) and `page_count_declared` (if the statement prints "of N"). Reported, not worked around: the
  field is wired; the existing snapshot is stale.
- **AS-9 is NOT activated** — `ACTIVE_RULE_IDS` unchanged. Whether AS-9 is *activatable* depends on a
  re-extraction; the wiring is done.

## Assumptions & decisions

- **`page_count_present` is deterministic (PyMuPDF), not a model read** — the ticket's explicit preference;
  correctness (a model miscount can't fabricate completeness).
- **No ADR** — the map forced no decision: no rule's declared name was wrong, and page count means the PDF's
  actual page total (matching AS-9's completeness intent). Both fields were simply un-extracted.
- **The 5 other no-AI rules are NOT done here** — the map scopes them: ID-5 is activatable now (LP-389); the
  derived-4 need inputs/verification (IN-4 → LP-382); none needs a new extractor except AS-9.
- **AS-9's full resolution on LF-6T3N needs a re-extraction** — the field is wired; the stored snapshot is
  stale. Reported.
