## What S1-11 asks for, and why the screen cannot give it

The design's Must-match for S1-11 is a warnings card listing **each** warning, as
"2 × *Duplicate dropped* (code plus the start of the wording, and where it happened)" and
"1 × *Letter header not found*".

What the readers actually emit is a flat `list[str]` of diagnostic fragments, composed with
f-strings at the point of failure:

```
"header not found"
"no CONDITIONS marker; nothing could be read"
f"dropped page-overlap duplicate of code {row.code}"
f"unrecognised bucket heading: {heading!r}"
f"unrecognised loan-information line at line {int(line.y)}"
f"expiry date {token.text} is {distance:.0f} from the nearest column ({nearest[1]}); not assigned"
f"unparseable Date Printed: {value!r}"
f"centre rule disagreed with itself in {segment.heading!r} on page {segment.page}"
```

**The start of the wording is not in the string, and neither is a stable "where".** So the screen
cannot render the design's row by reformatting what it receives — the data is not there.

⚠️ **AND A CLIENT-SIDE PARSER OF THESE IS THE WRONG FIX.** Recognising `"dropped page-overlap
duplicate of code …"` with a regex would build a vocabulary in the client that goes stale the first
time a reader adds or rewords a warning, failing silently into "unrecognised" — the same shape as
`_READERS` in `schemas/condition.py`, and as `BUCKET_KIND_LABEL` being compared against a lender's
heading. The producer has to say what it means.

## Scope

1. **A structured warning.** At minimum `{kind, code, wording_start, where}`, with `kind` a closed
   vocabulary the client can map to the design's titles ("Duplicate dropped", "Letter header not
   found"). `wording_start` is a prefix of the lender's own text, which makes it **NPI** — see below.
2. **The four readers** (`uwm`, `champions`, `generic`, `paste`) emit it instead of strings.
3. **`ParseReportPublic.warnings`** carries the new shape, and the review screen renders each
   warning as the design draws it.
4. **The readonly views.** `parse_report` is dropped whole today; a warning carrying a slice of the
   lender's wording must stay dropped, and the migration and view definitions have to be checked
   rather than assumed.
5. **The dateless note chip**, which is the same defect one layer along: with no header there is no
   `date_printed`, and rule 4 resolves a note's year against exactly that — so the chip shows
   month/day because that is all the reader can honestly produce. Making it say so needs the reader
   to carry the fact structurally, which is this ticket's shape.

## Why it was not done in LP-909 §5

§5 is a Visual-check and polish pass. This changes a producer contract across four readers, a public
schema and the readonly layer — and `parse_report` is NPI-classified, so it touches the boundary
ADR-405 draws. Doing it inside a UI pass would have been the refactor this stage has twice declined
to start inside another ticket (LP-908 §2 on the shipped doors, LP-909 on `paste_conditions`'s
`condition_count`).

The Visual-check rows stay **"missing"** in the meantime: that table records what the screen shows
against Must-match, not whether the fix is in scope. Agreed with the review peer.
