## Section 1 — the foundations every reader stands on

**`Line` / `Token`** (`readers/lines.py`). A reader never sees a PDF or a paste; it sees positioned
lines. That is not ceremony — the Champions centre rule and the UWM expiry table are both
**positional**, and a reader written against raw text cannot ask where a column begins.

**The two coordinate systems are different units, deliberately.** From a PDF, `y` is points from the
top and `x0` points from the left; from text, `y` is the line index and `x0` the character offset.
Nothing compares the two, and every rule that uses them is relative — "nearest column", "the line
above", "2 * number.y - bottom" — so both work unchanged. It is why the spec's Champions layout
sample parses as text at all.

**Normalisation is three substitutions and nothing else**: soft hyphen → `-`, non-breaking space →
space, trailing whitespace stripped. Spec §9.1 is what constrains it — the lender's words are stored
verbatim, so a normaliser that "tidied" anything would put a paraphrase into `verbatim_text` with no
way back to what was printed. **`rstrip` only**: leading spaces are load-bearing, because indentation
is what separates a bucket heading (≤ 3 spaces) from a continuation line (≥ 20).

## Decisions worth arguing with

**The readers import `ConditionSheetFormat`, not the spec's `SheetFormat`.** The spec's `ParsedSheet`
sketch names `SheetFormat` — a name appearing exactly once in the spec and nowhere in the code, while
LP-904 already defined `ConditionSheetFormat` with the four values the readers produce. Two names for
one fact is the drift this codebase warns about repeatedly (`_ROW_RULE`, `str_enum`, both
`activity_type` swaps). Recorded as a spec-vs-code difference; the survey's rule applies and the code
wins.

**`lines_from_pdf` goes through `page_ocr.words_for`, not `page.get_text("words")`.** That function
already answers "where are this page's words" for both a text layer and a scan, returns the same
`(x0, y0, x1, y1, word)` shape either way, and decides **per page** — six of the corpus's documents
are mixed. Calling the raw API here would be a second answer to one question, and would silently
return nothing for a scanned sheet.

**Words group into lines by vertical centre, not by pymupdf's block/line indices.** UWM's header is
two columns: `Contact Name:` on the left and `Senior UW:` on the right, at the same height and in
different blocks. Grouping by block would split one visual line in two and the header parser would
never pair a label with its value.

**Blank lines are kept, not filtered.** The Champions segmenter reasons about "the line above a row's
top"; a reader that never saw the blanks would compute a different line and mis-slice every row in
the segment.

## ⚠️ The fixtures are extracted mechanically, not transcribed

`tests/conditions/fixtures/*.txt` are copies of the fenced blocks in the spec, cut with `sed` from
lines 663–748, 769–833 and 848–920, and verified with `diff` against their source ranges. Three
files, 86 / 65 / 73 lines.

**They are identical to the spec except for trailing whitespace on one line**, and an earlier draft
of this ticket wrongly called them byte-for-byte. The repo's `trailing-whitespace` pre-commit hook
stripped the expiry header's padding after `Rate Lock Exp` in round 1, and **the strip stands** — no
hook exclusion was added. `normalise` rstrips every line, so no reader can observe the difference,
and only column *starts* carry meaning. The `.eml` corpus is excluded from that same hook because
DKIM signs those bytes; borrowing that reason here would claim a significance these files do not
have. Provenance stays checkable with trailing whitespace stripped from both sides.

This is LP-910's lesson applied *before* the mistake rather than after. That ticket's review had to
diff 56 hand-copied rows to find three slips; these are ~220 lines of column-aligned text where the
spec says *"keep the spacing exactly as below — the readers depend on columns"*. The UWM expiry table
is matched by **column position**, so one shifted space puts a date under the wrong header and
produces a plausible-looking wrong answer rather than an error. Copying mechanically removes the
failure mode instead of guarding it.

**`{SHY}` stays a placeholder in the committed file.** A real U+00AD is invisible in an editor and in
a diff, so a fixture containing them could be corrupted by any tool that strips them with nobody
seeing. The loader substitutes on read, which also makes the count assertable — and it is asserted:
6 / 3 / 6.

## ⚠️ Two invisible characters that got into the source, and how they are written now

`SOFT_HYPHEN` and `NON_BREAKING_SPACE` were typed as `"\u00ad"` / `"\u00a0"` escapes and **arrived on
disk as the literal characters** — `od -c` showed `302 240` where the escape had been. Ruff's RUF001
caught the non-breaking one; the soft hyphen is not in its ambiguous set and would have stayed
invisible indefinitely.

Both are now `chr(0x00AD)` and `chr(0x00A0)`. An escape is legible but can be normalised back into
the character by a tool that rewrites the file; `chr()` survives that, names its codepoint without
needing a comment, and cannot be mistaken for whitespace by a reader or a linter. A scan confirms
**zero literal soft hyphens or non-breaking spaces** remain anywhere in the new source.

### Decisions worth arguing with

**Dedup is on `(code, note-stripped text, notes)` — never on code alone.** UWM lists `0571` once per
change of circumstance, and the page-break fixture carries three of them with three different amounts
(815000 → 805000). Deduplicating by code would silently delete two genuine conditions, which is the
class of bug nobody finds because the output still looks plausible. Notes are stripped before
comparison so a page-overlap copy is still caught when the underwriter annotated one of them.

**The note regex is "asterisks THEN a date", not "asterisks".** `***NOTE***` (three asterisks, no
date) is *lender* text and appears twice inside `0132`. Matching on asterisks alone would attribute
the lender's own aside to the underwriter. The same rule is what will stop Champions' `**AM to pull
SSN Verification.` (§7.4) being read as a note in section 3.

**Expiry dates are assigned by nearest column, never by order.** Six of the twelve columns are blank
on every real sheet — 6 dates, 12 headers — so the Nth date is not the Nth header. Order-matching
would file insurance under `other` and nothing would look wrong. Over `8` from any header, the date
is reported in a warning rather than assigned.

**A missing header is a warning, not a failure.** The page-break fixture has no letterhead at all.
Refusing the sheet would discard all 16 conditions on it, so the reader warns `header not found` and
reads the conditions block anyway — which is what §7.3 expects.

**`coerce_date` is reused from `app/ai/extraction/parsing.py`** rather than writing a third
`MM/DD/YYYY` parser. It already accepts ISO and six US formats and never raises.

**The category regex is non-greedy so `TC:` is not swallowed.** Row `6378  TC  TC: Title company…`
has the category `TC` and a text *beginning* `TC:`. It appears in all three fixtures.

**A malformed shipped code map does not take the reader down.** `load_seed` raising
`LenderCodeSeedError` costs every row its code-map owner hint and nothing else; the seed step is
where that error is fatal.

## Section 3 — the Champions reader and the generic fallback

`app/conditions/readers/champions.py` (§6 rules 1–5) and `generic.py`, against an authored §7.4 PDF.
**22 tests — 16 Champions, 6 generic — all passing.**

### The centre rule, and why this reader exists at all

Champions prints each condition's number **vertically centred on its row**, so it lands on the first
line, a middle line, or a line of its own depending only on how many lines the text wrapped to. There
is no marker saying where a row starts; the only thing that says so is the geometry. If a number sits
at a row's centre then `top = 2 × number.y − bottom`, and walking the numbers **bottom-up** makes
every row's bottom known before its top is needed. A top-down reader cannot do this — it would not
know where the first row ends until it knew where the second began.

This is what the positional line model from section 1 was built for, and the first place it earns its
cost.

### ⚠️ The fixture is authored, not extracted — and that changes what the tests are worth

§7.1–7.3 were cut from the spec with `sed` and `diff`-verified, so transcription error was
impossible. §7.4 instead gives a **table** of 28 section/number pairs plus a structural note each,
and full prose for only rows **71 and 268** (they appear in the §6 centre-rule example and are copied
exactly). The other 26 texts are authored in `champions_fixture.py` on the product owner's decision.

So an assertion comparing a row's text to the fixture's text **compares authored prose with itself**
and proves only that the centre rule reassembled *something*. The assertions that carry weight are
structural, and `all_rows()` exposes the §7.4 table mapping so a reviewer can diff the table against
the fixture without reading reader code.

### Two defects, both found by running against the spec's contract before writing a single test

**⚠️ Rows `133` and `286` were silently deleted.** Both are the only row in their section *and* wrap
to one line — so the number's centre falls on that line's own baseline and the two **merge into one
line**. The body-text column was measured as the median first-token `x0` *within the segment*, so in
a one-line segment that median **was the merged line**: the number failed its own "left of the body
text" test, the whole segment fell through to `unassigned_lines`, and the sheet reported **no
warnings**. 26 rows where 28 were required, looking clean. The column is now measured across the
whole sheet, where wrapped text dominates and the body column is unambiguous.

**⚠️ Every expiry date parsed as `None`, and contact names swallowed the next column.** `Credit Exp
Date` came back as `'01/07/2027 Appraisal Exp Date: 12/27/2026'` and `Name` as `'Omar Example Phone:
(555) 010-0144'`. The cause is one section 1 should have predicted: **PDF text has no double
spaces** — `Line.text` is `" ".join(tokens)` — so a pair regex ending a value at `\s{2,}` never
fires. Anchoring on a closed set of known labels bounds each value instead. Same repair as the UWM
reader's loan-fact defect, same underlying cause.

Both were invisible to any test written after the fact, because a test written from the reader's
output would have asserted 26 rows and no expiry dates and called it correct.

### Decisions worth arguing with

**The furniture rule matches `Date: … Loan #:` together, never `Date:` alone.** Rule 2's wrapped
label puts a bare `Date: 12/15/2026` in the *header* — the continuation of `Title Commitment Exp` —
and a furniture rule keyed on `Date:` would silently eat it, losing an expiry date with nothing to
show for it. The fixture deliberately contains both so the distinction is exercised.

**This reader never touches `Line.indent`.** It is `None` for PDF input, which is the only input
carrying the geometry the algorithm needs. Everything keys on `x0` and `y` order, both real on a PDF
and on text alike — which is also why the spec's layout sample parses as text.

**Line pitch is measured, not assumed.** Every tolerance is expressed in multiples of the sheet's own
median line gap, so no font size or fixture geometry is baked into a constant.

**`needs_ai` is set only when the rules found no structure at all** — not merely when a read was
imperfect. A sheet with warnings is still a rule-read sheet. In the generic reader, paragraphs split
on blank lines still set `needs_ai` when no row carries a number or code: splitting on whitespace is
a guess, and presenting a guess as a rule-read result is what the flag exists to prevent.

**A failed segment downgrades confidence rather than dropping rows.** If the geometry disagrees with
itself the rows are still returned at `0.5`, with a warning naming the heading and page; only a sheet
where *every* segment fails sets `needs_ai`.

scalars (`reader`, `reader_version`, `ai_used`, `duplicates_dropped`, and
`jsonb_array_length(parse_report -> 'warnings') AS warning_count`). **Warning bodies never cross the
view**, so nothing escaped that way — but the value was still being stored in a field LP-904 declares
clean, which is the part worth fixing.

The smoke test additionally truncates every warning at its first colon before printing, so a future
warning that embeds content cannot leak through that path either. The reader no longer produces the
NPI, and the test would not print it if it did.

## Follow-up — the UWM reader reads PDFs

Section 1 made `indent` return `None` for PDF-built lines, section 2 made `read_uwm` **refuse** PDF
input rather than answer plausibly, and section 3 authored the first PDF fixture. This closes it:
LP-905's own done-when is *"uploading a PDF built from `uwm_round1` produces a DRAFT round with 11
draft rows"*, which is unreachable while the refusal stands.

**The fixture renders the existing text fixtures rather than authoring new sheets.** One source of
truth: every expected value in `test_reader_uwm.py` was transcribed from the spec, so a PDF built
from the same text must produce the same rows. A separately-authored PDF could drift and nothing
would notice. Monospaced, because fixed pitch maps a character column linearly onto an x position —
measured, `x0 = 54.0 + indent × 4.8` exactly.

**The threshold is derived from the sheet, never hardcoded.** A UWM conditions block has two
first-token columns — headings and row codes at the margin, continuations in the text column — so
the split is the largest gap between consecutive first-token positions, with a minimum-separation
guard returning `None` when no gap deserves the name (a block of one-line rows has no continuations,
and inventing a threshold there would make the first slightly-indented line a continuation of
nothing). Measured:

| Fixture | first-token columns | derived threshold |
|---|---|---|
| `uwm_round1` | `{58.8, 265.2}` | 162.0 |
| `uwm_master_pagebreak` | `{58.8, 135.6, 265.2}` — the mortgagee clause adds a third | 200.4 |

The three-column case is handled correctly: 200.4 separates `{58.8, 135.6}` from `265.2`.

### ⚠️ Three defects, and the first is the third instance of one cause

**1. Every row fell through to `unassigned_lines`, so a PDF sheet read as EMPTY.** `_ROW_START`
requires `\s{2,}` between the code, category and text — and a PDF line is `" ".join(tokens)`, which
contains no run of two spaces anywhere. The same row, both ways:

```
text:  ' 0006         Invoice                       Provide copy of invoice for credit report.'
pdf :  '0006 Invoice Provide copy of invoice for credit report.'
```

The first matches; the second does not. This is the **third** defect from this one cause — the
Champions header pairs and the UWM loan-fact scan were the others — so it is worth stating once,
plainly: **on PDF input whitespace carries no information; only positions do.** The replacement
splits code / category / text by the derived threshold, inventing no characters.

**2. ⚠️ I weakened §9.2 while extending it.** The spec classifies three ways — heading at `≤ 3`,
continuation at `≥ 20`, and the band between them is *neither*, landing in `unassigned_lines`. My
first version answered both questions with one predicate (`not _is_shallow`), collapsing that band,
so a line at indent 10 was swallowed as a continuation and
`test_unassigned_lines_are_collected_never_dropped` lost one of its two expected lines. A refactor
meant to extend the invariant quietly removed part of it. `_is_continuation` is now a **positive**
test, never "whatever is left".

**3. A year was read as a row code.** `4235`'s continuation begins `2026 and 2025 for Jordan
Ellis…`, and `2026` is four digits. On text `_ROW_START` anchors at `^\s{0,3}`, so a number deep
inside a wrapped line can never open a row — translating to positions lost that anchor. The
page-break sheet returned **17 rows instead of 16** with `4235` truncated to its first line. The
margin test (`_is_shallow` on the code itself) is what `^\s{0,3}` means in a world of columns.

### Tests

`test_reader_uwm_pdf.py`, 20 tests. **The property asserted is equivalence, not a second set of
expectations**: the PDF reading is compared against the text reading of the same fixture, so a drift
in either direction fails and neither can quietly become the reference. Codes, order, bucket
headings, bucket kinds and full condition text are all compared, plus §9.2 on the PDF path and the
threshold landing strictly between the observed clusters.

Bucket headings are compared **explicitly**, because the defect this replaced kept the row *count*
correct while filing every row under a stale bucket — invisible to any assertion that counts rows.

`test_a_pdf_sheet_is_refused_loudly_rather_than_misread` is gone, its refusal being deliberately
removed; a degenerate PDF with no `CONDITIONS` marker is now pinned as a warning plus `needs_ai`
rather than a crash.

### ⚠️ Follow-up 2 — the header on a PDF, and three failed attempts at one rule

Widening the equivalence tests to `date_printed`, `header` and `warnings` — the fields the first
version did not compare — immediately exposed what that omission had been hiding: the PDF path
produced `date_printed=None` and **16 warnings** against the text path's **0**, while 20 tests
passed. *A guard that compares four fields says nothing about the fifth.*

**The fourth instance of one cause.** `_split_header`'s pair regex needed `:\s{2,}` and
`_LOAN_LABEL_SCAN` needed `\s{2,}` around its labels; PDF text is `" ".join(tokens)`. After the
Champions header pairs, the UWM loan-fact scan and UWM row starts, this is the fourth defect from
the same assumption — and the consequence chained: rule 4 resolves a note's year against
`date_printed`, so **every underwriter note on every uploaded PDF came back dateless.**

**Then I broke the text path fixing it.** Relaxing the scan to `\s+` brought back the exact defect
the section-2 review had found: `Property  118 Status Road` parsed as `{'Property': '118',
'Status': 'Road'}`. My justification — "the closed set bounds the value, not the width of the gap" —
was wrong. The gap width *was* doing work: distinguishing a label in the label **column** from a
label-shaped word inside a value.

**Three attempts at a gap rule, each wrong differently:**

| Attempt | Result |
|---|---|
| constant `24.0` points | every word became its own cell — `AUS: Desktop` |
| `median × 1.6` per line | merged column pairs — `AUS: Desktop Underwriter Submission Date 07/17/2026` |
| largest-gap bimodal split | same merge; **18 of 26** loan-information lines wrong |

The premise was the error, not the arithmetic. A PDF's gaps form a **hierarchy** — measured on round
1: words 9.6–52.8 points, label→value ~77–100, column-pair ~130–158 — so any single threshold picks
one level and merges the rest. I iterated on the derivation three times before questioning that, and
the measurement that settled it was available before the first attempt.

**The fix needs no gap rule at all.** A cell that *opens* with a known label has its value bounded by
the next known label (`_pairs_in_cell`). It cannot resurrect the street-name defect, because a cell
is only scanned when it starts with a label — `118 Status Road` never does. The same closed-set
technique that fixed the Champions header and the UWM loan facts, applied one level down.

`_NEAREST_COLUMN_TOLERANCE` had the same units bug and is now `_NEAREST_COLUMN_FRACTION`, derived
from the expiry headers' own spacing: the spec's "8" means eight *characters* on text and eight
*points* on a PDF — under two characters at 8pt — which rejected three of round 1's six dates as
"19 from the nearest column".

**Result:** `header` equal on both paths, warnings 0 on both, and the equivalence tests now cover
`date_printed`, `header`, `warnings` and resolved note dates.
