### The migration was wrong twice, and the database is what said so

**This is the part worth reading.** The first version used `op.create_check_constraint` and
`op.drop_constraint`, ran green, and installed **none of the four constraints under the names it
claimed**. `alembic upgrade head` reported success throughout.

`Base.metadata` carries a naming convention (`app/models/base.py`) whose `ck` template is
`ck_%(table_name)s_%(constraint_name)s`, so those helpers **re-prefix a name that already carries the
prefix**: `ck_conditions_ownerhintsource` became
`ck_conditions_ck_conditions_ownerhintsource`. Every other migration in that directory — about twenty
— uses raw `op.execute("ALTER TABLE … ADD CONSTRAINT …")` for exactly this reason, and **LP-815's
migration already documents the trap in a comment**, naming `ck_documents_ck_documents_uploadsource`
and observing that there "the DROP that preceded it failed loudly, which is the good outcome". Mine
did not fail loudly, because my DROP was re-prefixed to match.

Rewritten to raw SQL throughout, and verified against a scratch PostgreSQL 16 by listing every check
constraint on both tables by `conrelid` rather than querying the names I expected — which is the step
that found it, after an earlier inspection had told me the constraints were simply "MISSING".

### It exposed a live bug in a shipped migration, which this one repairs

**`round_reparse_requested` has been unwritable on every migrated database since LP-909 shipped.**

`b6d1e93f57ac` added the event kind with raw SQL, creating `ck_condition_events_conditioneventkind`
with 11 values — while LP-904's **doubled** name with 10 values was still there, because LP-904 had
declared its CHECKs as `sa.CheckConstraint(name="ck_condition_events_…")` inside `create_table` and the
convention doubled them. Its own `DROP … IF EXISTS <single>` was a no-op: the single name did not exist
yet. A column's effective constraint is the **AND** of all of them, so the 10-value copy has been
rejecting `round_reparse_requested` the whole time.

**Nothing could have caught it.** `conftest` builds the schema with `Base.metadata.create_all`, where
`str_enum` passes only the enum's own name — so the TEST database has the single-prefixed name and no
duplicate, while production has both. The suite and production disagree about what these constraints
are *called*, which is why two reviews and a full green suite never noticed.

This migration drops both spellings before adding the canonical single one, so `condition_events` ends
with exactly one constraint listing all 19 values. Verified: `'round_reparse_requested' in eventkind:
True`.

**Left alone, deliberately:** LP-904's five other doubled condition CHECKs (`bucketkind`, `ownerhint`,
`conditionprepstatus`, `conditionlenderstatus`, `conditionorigin`). Each exists exactly once, so each
is functionally correct and merely misnamed. **Follow-up:** normalise them, because the next migration
that swaps one by its single name recreates this bug exactly. Not done here — renaming five
constraints is not this ticket's job, and doing it inside a ticket about statuses would bury it.

**No new guard was written for the trap, and that is a decision.** LP-815's comment already records
it, no live migration does the harmful thing (the seven that use `op.drop_constraint` all target
foreign keys or unique indexes, most wrapped in `op.f()` to suppress re-prefixing), and a guard
generalised from my own mistake would be inventing coverage rather than closing a gap.

### Decisions taken while building

1. **`condition_came_back` is THE one event for a came-back**, carrying both from→to pairs — the
   lender's status to `not_cleared` and ours back to `to_do`. §6 rule 4 says "exactly one", and the
   review asked the ADR to settle which. `CONDITION_SEEN_AGAIN` is not a second record of that change
   but the **appearance** record, and it cannot be dropped: `round_numbers` — the `R1 R2` chips —
   derives from it. `CONDITION_NOTE_ADDED` **folds into** `condition_came_back` when the note is what
   reopened the condition, and stands alone only for a note that reopens nothing.
2. **Three `OwnerHint` columns on one table need three constraint names.** `str_enum` derives the name
   from the ENUM, so `waiting_on` and `owner_override` would both have collided with
   `ck_conditions_ownerhint`. Both are named explicitly and both are in `_CASES`, or a later `OwnerHint`
   member would be accepted by one column and rejected by two.
3. **`prep_note` gets the strong guard and `verdict` cannot.** `prep_note` appears in no view's text,
   so it is in `EXCLUDED` **and** `NEVER_EXPOSED`. `verdict` must be named by the view to project
   `source_kind` and `source_date` — the provenance that makes "cleared on the 12th" auditable — and
   `NEVER_EXPOSED` is a `\bverdict\b` search of the select list. So it is `EXCLUDED` only, plus
   `test_the_conditions_view_touches_verdict_only_for_its_provenance`, which asserts the SHAPE of every
   reference. **Mutation-checked both ways:** exposing `verdict` whole fails it, and adding
   `verdict ->> 'note'` fails it — and that second one passes `EXCLUDED`, `NEVER_EXPOSED` and
   `test_no_model_column_drifts` alike, which is the whole reason it exists.
4. **`effective_owner` is computed in the view** as `COALESCE(owner_override, owner_hint)` — the third
   statement of that rule, beside the service function and the filter column. They change together.
5. **Two `*_changed_at` columns rather than one `updated_at`.** "How long has this sat with the
   borrower" is a question about our track, and it must not be reset by the lender answering or by any
   other edit to the row.
6. **The downgrade is not an exact inverse, and says so.** It restores one constraint per column under
   the canonical name rather than reinstating LP-904's duplicate — returning the schema to what that
   migration *meant*, not to the state that made `round_reparse_requested` unwritable.

## Part 2 — the endpoints *(this section's commit)*

Shipped: `POST /conditions/{id}/prep-status`, `/verdict`, `/reopen`, `PUT /owner` and
`POST /loan-files/{id}/conditions/bulk`, all five on `services/condition_status.py`; the A1 came-back
hook in `condition_import` carrying §5.2's two guards; eight typed refusals, four of them the spec's
sentences character for character; optimistic concurrency on `updated_at` throughout; and on the
client, five request types and five mutation hooks.

**The rule the module exists to enforce is that only a recorded verdict may say the lender cleared
anything.** `cleared` and `waived` are unreachable without a `source_kind` and a `source_date`, and the
date has no default — a verdict dated by our clock is a verdict about us.

### The endpoint tests found that `effective_owner` had never been edited

The single most useful thing part 2 did. `PUT /owner` answered **200**, logged
`condition_owner_changed to=title`, wrote `owner_override`, and returned a body saying
`effective_owner: processor`.

`services/conditions.py::effective_owner` still returned `condition.owner_hint`, and its own docstring
said *"this function is what LP-912 edits rather than every caller"*. The docstring was the plan; the
edit never happened. Saying where a change belongs is not the same as making it, and **only a test that
read the response body could tell the two apart** — the service wrote correctly, the log was truthful,
and the row was right in the database.

Worse in combination: `set_owner` *did* set `owner_hint_source = manual`, so the chip would have
claimed a person chose the owner **while naming the wrong person**.

**And the same rule is written twice.** `_effective_owner_column` is the SQL twin, for filtering and
ordering, and it read the bare hint too — so a condition reassigned to Title *displayed* as Title and
did **not** come back under `owner=title`. Nothing fails on that, because both answers are individually
valid; the processor's symptom is a row vanishing from the group they just moved it to. Both are now
`coalesce(owner_override, owner_hint)`, and
`test_the_owner_filter_returns_what_the_row_displays` asserts the row and the filter agree — in both
directions, since appearing under the new owner without leaving the old group would also pass a filter
that ignored the override entirely.

### `_inferred_source` is gone, and the effective source is derived instead

`set_owner` overwrote `owner_hint_source` with `manual`, which destroyed the true fact that the code map
said `processor`, and then rebuilt a plausible value from the hint when the override was cleared — a
lossy reconstruction whose own docstring conceded it "cannot be recovered exactly".

`effective_owner_source` now derives `manual` from `owner_override is not None`. `owner_hint_source`
stays what it claims to be, provenance for the **hint**; clearing an override has nothing to
reconstruct; and a column of schema is not spent remembering a chip's subtitle.

### Decisions taken without the product owner

| # | Question | Choice, and why it is the safe one |
|---|---|---|
| 1 | The spec names `updated_at` in all five request bodies; `ConditionDraftUpdate` has shipped `expected_updated_at` since LP-909. | **The existing name.** Two names for one concept inside one feature is the drift this repo keeps correcting, and this one says the truer thing — the value the caller *read*, not the value it is setting. |
| 2 | The spec gives four refusal sentences "for example". Four more cases have none. | **Four authored codes**, each marked as mine in the source: `waiting_needs_owner`, `nothing_to_reopen`, `verdict_needs_round`, `status_not_offered`. The alternative is a 422 with a field path, which tells a processor which key was wrong rather than what to do. |
| 3 | The spec's backward-move sentence names *To do*, but a move to *Waiting on someone* is also backward. | **The target is interpolated.** Naming "To do" on a move to *Waiting* would simply be wrong. The To-do instance is what the test pins, byte for byte. |
| 4 | Does a bulk call fail or partly succeed? | **200 with refusals as data.** A 409 throws away the rows that worked; a body listing only successes leaves a processor to work out which row did not move. |
| 5 | Does a verdict tidy up our track? | **No.** A condition that was *Sent to lender* and is now cleared **was still sent**. Rewriting our status would erase what we did; the history says it instead. |
| 6 | Does a reopen reset our track? | **Yes, to `to_do`.** Unlike a verdict: the condition needs working again, and leaving it at *Sent to lender* hides it from the list that would make somebody pick it up. |
| 7 | Does a came-back reset our track? | **Only from `ready` or `with_underwriter`** — the two that became untrue when the lender refused it. A condition still `waiting` was already being worked, and resetting it would wipe an owner somebody chose. |
| 8 | A note we cannot date. | **Records the note, moves nothing.** A verdict needs a date, and a note we cannot date is not the lender answering on a day. Dating it by the round would invent the one fact that makes a verdict checkable. Stage 1's behaviour, kept. |
| 9 | `review` / `pending_review`, kept in the database by A4 and offered nowhere. | **Refused by `status_not_offered`** rather than silently treated as forward, because `_PREP_RANK` gives them no rank. |

### Carried forward from LP-911's review — both honoured

- **`came_back` narrowed** to `verdict.source_kind == underwriter_note`, so a manual *Came back*
  recorded from a phone call is `not_cleared` and is **not** a came-back.
- **`verdict` is on `ConditionPublic` typed**, with its producer, built leniently from JSONB so a list

### The came-back event's provenance, which the part 1 review required (R5)

R5: *"Part 2 must assert that the `condition_came_back` event's detail carries `source_kind:
underwriter_note` and the note's date, or `came_back` becomes the bare claim this test forbids."*

`tests/conditions/test_came_back.py` asserts exactly that, plus the date being the **note's** and not the
import's — an event stamped with when we read the sheet says when *we* found out, where S2-08's line is
"set by the lender's 9/8 note", the only version a processor can check against the letter.

This is the one place in Stage 2 where the app moves a status with nobody clicking, so the file also
pins what it does **not** do: no `condition_note_added` beside it (one event per change; the note *is*
the reopening), the appearance still recorded separately because the `R1 R2` chips derive from it, our
track left alone when the work had not moved on, and **the same note arriving on a third sheet reopening
nothing** — a full sheet reprints every note it still carries, so "a note is present" cannot mean "the
lender just wrote one".

The rows there are synthetic and the notes invented: `uwm_round2_2026-09-10.txt` carries no underwriter
notes at all, so no fixture drives this path, and real borrower data may not enter the repo.

### `ConditionRefusalCode` is mirrored, because the UI branches on it

The refusal codes are now a TypeScript union registered in `_MIRRORED`. It is the enum with the least
else watching it — neither a column nor a request field, so no CHECK and no schema guards it — and the
UI groups refused rows by it ("1 skipped: information only"). A code the server grows that the client
cannot type is a row the UI cannot group; a code the client branches on that the server never sends is a
branch that silently never runs. The **sentences** stay pinned separately, against the tickets file's own
bytes.

### A census, so a ninth refusal cannot ship untested

`test_every_refusal_code_the_service_can_raise_has_been_exercised` asserts that the eight `RefusalCode`
members are exactly the six covered by these tests plus the two reachable only elsewhere
(`verdict_needs_source` through bulk, since a single-row verdict missing its source is a 422 from the
request model; `status_not_offered` for the two A4 statuses no client offers). Adding a code now forces a
decision rather than sliding in with no test at all.

### One thing `errors.py` already provides that part 2 should use

`error_body` takes an optional **structured `data`** payload alongside the plain sentence, and
`http_exception_handler` passes a dict `detail` through as `error.data` while a string `detail` behaves
exactly as before. LP-850 added it for the open-draft conflict, on the grounds that "'Request failed' is
not something a processor can answer".

That is the envelope LP-912's bulk endpoint needs — `{applied: [...], refused: [{id, code, message}]}`
— so the typed refusal codes travel as `data` with the plain sentence as `message`, and **no second
error shape is invented**. Worth naming here because the obvious alternative (a 200 carrying a
per-row result list) would have been a different contract from every other refusal in the app.

Its review also recorded the trap that makes this worth reading: every assertion about that payload was
originally written against the exception object at the service layer, so nothing noticed the client was
receiving `{"type": "conflict", "message": "Request failed"}` and none of the contents. Part 2's bulk
tests assert on the RESPONSE BODY for that reason.
