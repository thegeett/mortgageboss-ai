### The migration was wrong twice, and the database is what said so

**This is the part worth reading.** The first version used `op.create_check_constraint` and
`op.drop_constraint`, ran green, and installed **none of the four constraints under the names it
claimed**. `alembic upgrade head` reported success throughout.

`Base.metadata` carries a naming convention (`app/models/base.py`) whose `ck` template is
`ck_%(table_name)s_%(constraint_name)s`, so those helpers **re-prefix a name that already carries the
prefix**: `ck_conditions_ownerhintsource` became
`ck_conditions_ck_conditions_ownerhintsource`. Every other migration in that directory — about twenty
— uses raw `op.execute("ALTER TABLE … ADD CONSTRAINT …")` for exactly this reason, and **LP-815's
migration already documents the trap in a comment**, naming `ck_documents_ck_documents_uploadsource`
and observing that there "the DROP that preceded it failed loudly, which is the good outcome". Mine
did not fail loudly, because my DROP was re-prefixed to match.

Rewritten to raw SQL throughout, and verified against a scratch PostgreSQL 16 by listing every check
constraint on both tables by `conrelid` rather than querying the names I expected — which is the step
that found it, after an earlier inspection had told me the constraints were simply "MISSING".

### It exposed a live bug in a shipped migration, which this one repairs

**`round_reparse_requested` has been unwritable on every migrated database since LP-909 shipped.**

`b6d1e93f57ac` added the event kind with raw SQL, creating `ck_condition_events_conditioneventkind`
with 11 values — while LP-904's **doubled** name with 10 values was still there, because LP-904 had
declared its CHECKs as `sa.CheckConstraint(name="ck_condition_events_…")` inside `create_table` and the
convention doubled them. Its own `DROP … IF EXISTS <single>` was a no-op: the single name did not exist
yet. A column's effective constraint is the **AND** of all of them, so the 10-value copy has been
rejecting `round_reparse_requested` the whole time.

**Nothing could have caught it.** `conftest` builds the schema with `Base.metadata.create_all`, where
`str_enum` passes only the enum's own name — so the TEST database has the single-prefixed name and no
duplicate, while production has both. The suite and production disagree about what these constraints
are *called*, which is why two reviews and a full green suite never noticed.

This migration drops both spellings before adding the canonical single one, so `condition_events` ends
with exactly one constraint listing all 19 values. Verified: `'round_reparse_requested' in eventkind:
True`.

**Left alone, deliberately:** LP-904's five other doubled condition CHECKs (`bucketkind`, `ownerhint`,
`conditionprepstatus`, `conditionlenderstatus`, `conditionorigin`). Each exists exactly once, so each
is functionally correct and merely misnamed. **Follow-up:** normalise them, because the next migration
that swaps one by its single name recreates this bug exactly. Not done here — renaming five
constraints is not this ticket's job, and doing it inside a ticket about statuses would bury it.

**No new guard was written for the trap, and that is a decision.** LP-815's comment already records
it, no live migration does the harmful thing (the seven that use `op.drop_constraint` all target
foreign keys or unique indexes, most wrapped in `op.f()` to suppress re-prefixing), and a guard
generalised from my own mistake would be inventing coverage rather than closing a gap.

### Decisions taken while building

1. **`condition_came_back` is THE one event for a came-back**, carrying both from→to pairs — the
   lender's status to `not_cleared` and ours back to `to_do`. §6 rule 4 says "exactly one", and the
   review asked the ADR to settle which. `CONDITION_SEEN_AGAIN` is not a second record of that change
   but the **appearance** record, and it cannot be dropped: `round_numbers` — the `R1 R2` chips —
   derives from it. `CONDITION_NOTE_ADDED` **folds into** `condition_came_back` when the note is what
   reopened the condition, and stands alone only for a note that reopens nothing.
2. **Three `OwnerHint` columns on one table need three constraint names.** `str_enum` derives the name
   from the ENUM, so `waiting_on` and `owner_override` would both have collided with
   `ck_conditions_ownerhint`. Both are named explicitly and both are in `_CASES`, or a later `OwnerHint`
   member would be accepted by one column and rejected by two.
3. **`prep_note` gets the strong guard and `verdict` cannot.** `prep_note` appears in no view's text,
   so it is in `EXCLUDED` **and** `NEVER_EXPOSED`. `verdict` must be named by the view to project
   `source_kind` and `source_date` — the provenance that makes "cleared on the 12th" auditable — and
   `NEVER_EXPOSED` is a `\bverdict\b` search of the select list. So it is `EXCLUDED` only, plus
   `test_the_conditions_view_touches_verdict_only_for_its_provenance`, which asserts the SHAPE of every
   reference. **Mutation-checked both ways:** exposing `verdict` whole fails it, and adding
   `verdict ->> 'note'` fails it — and that second one passes `EXCLUDED`, `NEVER_EXPOSED` and
   `test_no_model_column_drifts` alike, which is the whole reason it exists.
4. **`effective_owner` is computed in the view** as `COALESCE(owner_override, owner_hint)` — the third
   statement of that rule, beside the service function and the filter column. They change together.
5. **Two `*_changed_at` columns rather than one `updated_at`.** "How long has this sat with the
   borrower" is a question about our track, and it must not be reset by the lender answering or by any
   other edit to the row.
6. **The downgrade is not an exact inverse, and says so.** It restores one constraint per column under
   the canonical name rather than reinstating LP-904's duplicate — returning the schema to what that
   migration *meant*, not to the state that made `round_reparse_requested` unwritable.

### One thing `errors.py` already provides that part 2 should use

`error_body` takes an optional **structured `data`** payload alongside the plain sentence, and
`http_exception_handler` passes a dict `detail` through as `error.data` while a string `detail` behaves
exactly as before. LP-850 added it for the open-draft conflict, on the grounds that "'Request failed' is
not something a processor can answer".

That is the envelope LP-912's bulk endpoint needs — `{applied: [...], refused: [{id, code, message}]}`
— so the typed refusal codes travel as `data` with the plain sentence as `message`, and **no second
error shape is invented**. Worth naming here because the obvious alternative (a 200 carrying a
per-row result list) would have been a different contract from every other refusal in the app.

Its review also recorded the trap that makes this worth reading: every assertion about that payload was
originally written against the exception object at the service layer, so nothing noticed the client was
receiving `{"type": "conflict", "message": "Request failed"}` and none of the contents. Part 2's bulk
tests assert on the RESPONSE BODY for that reason.

### Three commands reported success today while doing nothing, and that shaped how this was measured

Recorded because the lesson is about method, not about this ticket. A `psql` invocation that was not
installed, a `sed` against a path that did not exist because the shell had changed directory, and a
backgrounded `pytest` that failed to spawn — each printed something that could be read as a pass, and
one of them (`3 failed, 8372 passed`) was quoted in a ticket before being caught. Two habits came out of
it and are worth keeping:

* **The suite run asserts its own preconditions** — it prints `pwd`, checks `pyproject.toml` is present
  and confirms `pytest --version` answers, before running anything. A spawn failure can then no longer
  masquerade as a green run.
* **Constraints were verified by ENUMERATING them per table**, not by querying the names expected. That
  is the step that found the doubled names; an earlier inspection querying by name had reported them
  simply "MISSING", which is a true statement that points at entirely the wrong bug.
