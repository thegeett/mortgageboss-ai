# LP-855 — copy and open, in one click

Status: spec. **Blocked by LP-853.** Screens 2 and 10.

Epic: [`docs/domain/communication/v1-epic.md`](../domain/communication/v1-epic.md) · Screens: [`v1-screens.md`](../domain/communication/v1-screens.md) · Spec: [`comm-v1-draft-only-spec.md`](../domain/communication/comm-v1-draft-only-spec.md)

## The report

> "On draft how many action button? On Send through your Email client, can we open Gmail or outlook
> compose page? How we should know whether to open gmail or outlook?"

## Yes to the first. No to the thing it implies.

Every web compose route exists and takes `to`, `subject` and `body`:

| Route | URL |
|---|---|
| Gmail | `https://mail.google.com/mail/?view=cm&fs=1&to=…&su=…&body=…` |
| Outlook — work | `https://outlook.office.com/mail/deeplink/compose?to=…&subject=…&body=…` |
| Outlook — personal | `https://outlook.live.com/mail/0/deeplink/compose?to=…&subject=…&body=…` |
| Desktop default | `mailto:…?subject=…&body=…` |

**Every one of them takes the body as plain text.** `mailto:` is plain by RFC 6068 and the three web
routes are no better. There is no route that carries the formatting LP-854 just built.

## So the button does both things

**Copy the rich body to the clipboard, and open the compose window with To and Subject filled and
the body left empty**, then say so: *"Paste into the message — ⌘V"*.

Filling the body with the stripped plain-text version instead would hand the processor a message
that **looks finished** and has quietly lost its structure — worse than an empty one, because
nothing prompts them to notice.

Leaving it empty also retires the length problem: `mailto_max_chars` exists because a long body
overflows the URL, and there is no longer a body in the URL. Keep the ceiling as a guard on subject
plus address; stop hiding the button because a message is long.

## Which client — it is a setting, because nothing can detect it

No browser API reports this. So: a **per-user preference** (`preferences` already exists — one
string), asked once on the first draft.

- **Seed the default from their own sign-in domain.** `@gmail.com` or a Workspace domain
  pre-selects Gmail; `@outlook.com` or a Microsoft 365 tenant pre-selects Outlook. It is a guess, so
  **it moves a radio button and says why** — it never decides.
- **"Whatever this computer opens" (`mailto:`) is the safe answer** and the fallback for anyone on
  Apple Mail, Thunderbird or a locally installed Outlook. It is what "Not now" selects.
- Until they choose, the draft button reads **Copy & open mail app**.

## The buttons on a draft — the answer to "how many"

`[Copy & open Gmail]` · `[Copy message]` · `[Mark as sent]` … `[Delete]`

Three and a quiet fourth.

1. **Copy & open <client>** is primary and is the whole send path. The label carries the chosen
   client, so the button says what will happen before it happens.
2. **Copy message** stays for anyone doing it their own way — and is the fallback when the popup
   blocker eats the compose window.
3. **Mark as sent** is the claim, attributed: `Marked sent by Priya · Tue 16:41`. In this version it
   starts no clock, because there are no reminders.
4. **Delete** is quiet and on the far side. It destroys the record LP-821 wants.

**There is no Send button, not even disabled.** `mail_transport` is an interface with no provider
behind it. A greyed-out Send is a promise this version cannot keep and the first thing a processor
will click.

## What it must not break

- LP-844's clipboard pairing, which is what makes the copy half work at all.
- The `mailto:` route stays, and stays honest about being plain text.
- Nothing here marks anything sent. Opening a compose window is not evidence.

## Acceptance

1. Each of the four routes opens with To and Subject correct and the body **empty**.
2. The clipboard holds `text/html` and `text/plain` after the click, verified by pasting into Gmail
   and Outlook web — bold, lists and links intact.
3. A blocked popup leaves the clipboard populated and tells the processor the copy succeeded.
4. Preference persists across sessions and is changeable.
5. A processor who never answers the picker gets `mailto:` and a button reading
   **Copy & open mail app**.
6. Subject and address are URL-encoded correctly, including `+`, `&` and non-ASCII names.

# What was built

Status: **done**, except acceptance 2's manual half, which is **not claimed**.

## The button does both things

`Copy & open <client>` copies the **rich** body to the clipboard and opens the compose window with
To and Subject filled and **the body empty**, then says *"Paste into the message — ⌘V."*

**The clipboard is written first, and the order is load-bearing.** `window.open` can be refused by a
popup blocker; if it went first, a refusal would leave the processor with neither a window nor a
copy. Copying first makes the worst case *"the message is on your clipboard, open your mail app and
paste it"* — which is exactly what the sentence under the buttons then says.

Filling the body with stripped plain text was the alternative and is worse than leaving it empty: it
hands the processor a message that **looks finished** and has quietly lost its structure, and
nothing prompts them to notice. An empty body is obviously unfinished.

## The preference

`User.mail_client`, **nullable, with no default** — unlike every other preference on that table. The
others default to the value the product would use anyway, because "never chosen" and "chose the
default" are the same thing for them. They are not the same thing here: `mailto` is both the safe
answer **and** what "Not now" selects, so a default would make "nobody has been asked"
indistinguishable from "they picked the desktop default", and the picker would then either never
appear or appear forever.

`suggest_mail_client` seeds the radio from the caller's own sign-in domain and is served **beside**
the stored value, never applied. **Exact domains, not substrings** — an `"outlook" in domain` test
matches `outlook-consulting.com`, which is a brokerage rather than a Microsoft tenant, and the
suggestion would be wrong in a way that looks authoritative. A domain that says nothing suggests the
safe answer and gives **no reason**: "suggested because we could not tell" is not a sentence anybody
benefits from reading.

Kept out of the readonly views, following LP-UI-030's decision for `reviewer_pane_split` — the
readonly surface answers questions about loan data, and which mail client a processor prefers
answers none of them.

## The defect my own test found: two modals hide each other

The picker was first rendered alongside the open message dialog. **Two open Radix modals mark each
other `aria-hidden`, so with both open nothing is in the accessibility tree** — measured at *zero*
reachable buttons and *zero* reachable dialogs, while the picker's heading was still findable by
`getByText`. A screen reader would have announced neither and a keyboard user could have reached
neither.

Reordering them did not help, because the problem is that there are two. There is one at a time now:
the message waits while the picker is up, and the draft opens behind it the moment it is answered.
Found by the picker's own test failing to find its own primary button.

## Acceptance

| # | Criterion | Test |
|---|---|---|
| 1 | each of the four routes opens with To and Subject correct and the body **empty** | `compose-routes.test.ts::every route` — parametrised over all four |
| 2 | the clipboard holds `text/html` and `text/plain` after the click | the copy is asserted (`copies AND opens`); **the paste into real Gmail and Outlook is not done — see below** |
| 3 | a blocked popup leaves the clipboard populated and says the copy succeeded | `a blocked popup still leaves the message on the clipboard, and says so` |
| 4 | the preference persists and is changeable | `test_the_answer_persists_and_is_changeable`, `ACCEPTANCE 4 — the answer is saved as a preference` |
| 5 | never answering gives `mailto:` and a button reading "Copy & open mail app" | `ACCEPTANCE 5` in both `compose-routes.test.ts` and `message-dialog.test.tsx` |
| 6 | subject and address URL-encoded correctly, including `+`, `&` and non-ASCII | `ACCEPTANCE 6 — encoding` — 8 awkward subjects × 4 routes, plus the ampersand and non-ASCII address cases |

**`&` gets its own case** because it is the one that fails silently: unencoded, "Smith & Sons"
truncates the subject and invents a header called " Sons". The test asserts the header **set**, not
just the value.

## No Send button, not even disabled

`mail_transport` is an interface with no provider behind it, so a greyed-out Send is a promise this
version cannot keep and the first thing a processor would click. Asserted as an absence over four
spellings — **with a positive control naming the three buttons that are there**, because a
not-assertion over a whole screen passes on a screen that failed to render, which is what a broken
import or a thrown hook produces.

## The length gate is retired, and the claim is measured

`mailto_max_chars` exists because a long **body** overflows the URL. There is no longer a body in
the URL, so the ceiling has nothing to measure: what remains is the subject and the address, capped
by `SendDraftRequest` at **256 each against a ceiling of 1,800** — read from the schema, not
assumed. The test that asserted the control was *disabled* on a long message is inverted, because
hiding the only way to send a message because the message is long is the behaviour being removed.

## Measured

- Migration run against a real Postgres: nullable with no default, `readonly.users` withholds
  `mail_client` and still withholds `email`, downgrade drops the column and leaves the view alone.
- Communication route: **201 kB** first-load, from 200 kB at LP-854.
- Backend 7731 passed. Frontend 1727 passed.

## What was not done

- **Acceptance 2's manual half.** *"Verified by pasting into Gmail and Outlook web — bold, lists and
  links intact."* Nothing has been pasted into a real mail client. `AT_RISK_IN_WORD` (LP-854) names
  what to look at.
- **A settings screen.** The picker says *"you can change this any time in settings"*, and the API
  supports it, but no settings control exists yet. The sentence is true of the system and not yet
  reachable by a processor — flagged rather than quietly left.
- **`Delete`, the quiet fourth button.** Screen 2 puts it on the far side of a spacer. Not built:
  there is no delete endpoint for a draft, and adding one is beyond what this ticket describes.
