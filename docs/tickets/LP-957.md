# LP-957 — The lender-package panel follows the conditions

- **Ticket:** LP-957 · Phase 4.5 Stage 3 follow-ups, batch 4 follow-ups (the owner, 2026-10-03)
- **Source:** the owner, testing LF-DH8V after batch 4: "I set all condition to Ready to Send … there is no
  sign for what next?"

## What was wrong

The next step after Ready to send exists: the lender package (S3-10, LP-925). `ConditionPackagePanel` shows
"6 conditions ready to send · Build package" above the summary bar. It was not there because its query,
`conditionPackageQueryKey = ["condition-package", fileId]`, was refreshed only by the package's own mutations.
A status move refreshes `conditionsQueryPrefix(fileId)`, so the list updated and the panel kept its earlier
"nothing ready" until a reload.

## The fix

`conditionPackageQueryKey` is now `[...conditionsQueryPrefix(fileId), "package"]`. Every door that refreshes the
file's conditions also refreshes the package: status moves, verdicts, bulk, links, the lender change, the
reading, and any door added later. The list's own keys are `["conditions", fileId, <params object>]`, so the
string `"package"` cannot collide with one. Nothing walks the cache by prefix and expects list data (the two
cache subscribers clean up image URLs under other keys). The server already counted the six as ready
(`_goes_in`: Ready, open with the lender, not information-only), so nothing changed there.

## Tests

`frontend/lib/api/package-refresh.test.tsx` (2):
- at the layer she hit it: `usePrepStatus` moving a condition to Ready marks the package stale;
- any refresh of the file's conditions covers the package, and another file's does not.

Mutation: the key put back to `["condition-package", fileId]` fails both.

**Runs:** frontend **2192 / 2192**, 184 files; biome, tsc and `pnpm build` clean. Backend untouched.

**Not in this ticket** (the owner asked for mockups first): a "Next: build the lender package" line in the

## Review (of `f1ce70d4`)

**No defects. A one-line key change that fixes the class rather than the instance, and the three
properties it depends on are all real — I checked each rather than taking them from the ticket. The
reason to prefer it over seven invalidations is already written in the file next door: withdrawal had
remembered to refresh the package and the status move had not, which is what a nested key makes
impossible.**

### What I verified, and how

- **The cascade is real.** Seven call sites invalidate `conditionsQueryPrefix(fileId)`, and none of
  them — nor anything else in the app — passes `exact: true` (grepped the whole frontend; zero hits).
  So all seven match the longer package key by prefix. The owner's own door is among them:
  `usePrepStatus` → `invalidateCondition` → the prefix.
- **The reader is what was broken, and it is fixed at the right end.** The panel's gate is
  `if (data.status === null && data.ready_count === 0) return null`, and `ready_count` comes from the
  package response, not from the conditions list. So a cached `ready_count: 0` hid the panel while the
  list beside it showed six Ready rows — the owner's "no sign for what next", reproduced exactly from
  the code. Refreshing the list could never have fixed it.
- **It refetches when it matters and not when it doesn't.** `ConditionPackagePanel` is mounted in
  `conditions-list-view.tsx:368`, the same screen as the status select, so the query is active and an
  invalidation refetches at once. On screens where the panel is not mounted the query is inactive, so
  invalidation only marks it stale — the nesting costs no extra request there. `makeQueryClient`'s
  `staleTime: 60_000` does not change this: invalidation refetches active queries regardless.
- **No collision.** The list key is `["conditions", fileId, params ?? {}]` — a third element that is
  always an object, never the string `"package"`.
- **Nothing walks the cache by prefix.** No `getQueriesData` or `setQueriesData` anywhere in the
  frontend, so no code can receive the package payload where it expects a condition list. The two
  `getQueryCache().subscribe` listeners both bail on `key[0] !== PAGE_IMAGE_KEY` / `!== PREVIEW_KEY`,
  so a `["conditions", …]` entry is ignored by both.
- **"Every door" holds, measured over all 45 mutations in `conditions.ts`.** A transitive closure
  through the invalidation helpers: **40 reach `conditionsQueryPrefix`**. The five that do not are each
  correct — `useBuildPackage` and `useUpdatePackageRow` refresh the package themselves,
  `useMarkDuRerunDone` writes the fresh package straight into the cache with `setQueryData`,
  `usePolishConditionDraft` changes draft wording only, and `useDeclineFileLender` touches no
  condition, which I confirmed on the server rather than inferring: `decline_suggestion` is documented
  and written as "Recorded on the round; nothing else changes."
- **The mutation kills both tests.** Key reverted to `["condition-package", fileId]`: both cases in
  `package-refresh.test.tsx` fail, and the file passes again on restore (`cmp`-verified). The first
  test also asserts `isInvalidated` is `false` **before** the move as well as `true` after, so it
  cannot pass on a key that was already invalid; the second has another file as its negative control,
  so the prefix is not merely matching everything.
- **Runs.** Frontend **2192 passed, 184 files** (their number, re-measured), tsc clean, biome clean on
  both changed files. Their commit touches four files, none under `backend/`, so "backend untouched" is
  checkable and true; no pytest was needed and none was run for this ticket.

### Checked and not findings

- **The redundant invalidations left behind are worth leaving.** `invalidateWithdrawal` still
  invalidates `conditionPackageQueryKey` explicitly (`conditions.ts:1239`), and `invalidatePackage`
  does too; after this change both are covered by the prefix. They are harmless, and removing them
  would be a second edit for no behaviour. More usefully, that line is the evidence for the chosen
  approach: the withdrawal door had remembered the package and the status move had not, which is the
  asymmetry a nested key removes by construction instead of relying on the next author to notice.
- **The tests build a bare `new QueryClient()` rather than `makeQueryClient()`**, and this repo has a
  precedent comment insisting on the factory (`page-image.test.tsx:110`). It does not apply here: that
  precedent exists because the revoke subscription is installed by the factory, so a hand-built client
  would test "a client the app never constructs". Nothing in this claim depends on factory config —
  `isInvalidated` is set by `invalidateQueries` irrespective of `staleTime` — so the bare client proves
  the same thing. I read the factory's defaults to confirm that rather than assuming it.
- **The server side was already right**, which is why this is a one-line fix: `_goes_in` counts Ready,
  open-with-the-lender, non-information-only conditions, and the panel was asking the right endpoint —
  just not often enough.

### A correction to my own method

My first pass at "every door" reported **14** mutations as missing the prefix, including
`useMarkConditionDraftSent`, `useAcceptEvidence` and `useWithdrawCondition` — all three of which would
have been real findings, since marking a draft sent moves a condition to Waiting and accepting evidence
can settle one to Ready. That number was an artifact: I had matched against four hard-coded helper
names and missed that `invalidateDrafts` and `invalidateWithdrawal` **delegate** to `invalidatePlan`,
which invalidates the prefix. The honest figure needed a transitive closure, which is the 40 of 45
above. A one-level search over a call graph answers a different question than the one being asked, and
the wrong answer here looked like three findings rather than like a broken method.
