# LP-460 — Schema-gap remediation, Phase 2: the six missing repeating-row lists

Phase 1 (LP-458) fixed fields that existed and returned null. The 268-doc comparison also flagged a
second pattern: **document types whose substance is a table with nowhere to land** — the rows fall into
the catch-all or are dropped entirely. LP-437's generic flat-row list mechanism makes each a *declaration*
(a `ListSpec` + a prompt block) rather than a bespoke feature. This ticket adds the six confirmed lists +
one column.

**Method held to LP-458's lesson:** 6 of 10 Phase-1 findings were the free reader over-recalling, so every
table here was checked against the actual PDF before being declared. **Unlike Phase 1, all seven items
verified as REAL** — expected, because this list was curated specifically for "the document *is* a table."

### ⚠️ Corrections the documents forced on the ticket text
- **Item 6 — "per-line deductibles" does not match the document.** On 116 the deductibles are a **separate
  policy-level table** (All Other Perils $1,000 / Wind-Hail $1,000), NOT a column on each A–F coverage line.
  `coverage_lines[]` will carry **`coverage_name`, `limit`, `premium`** — no per-line deductible (the doc
  doesn't structure it that way; the existing `wind_hail_deductible` scalar already holds the wind/hail one).
- **Item 5 — coverage *lines*, not policies.** They share one policy number, so a `coverage_lines[]` (with an
  optional per-row `policy_number`/`insurer_letter` for the multi-insurer ACORD case) is the right shape, not
  a `policies[]`.
- **PII / `redact`: none of the six row shapes carry per-row account numbers.** Ledger rows are
  date/description/charge/paid/balance; holdings rows are symbol/qty/value; jurisdiction rows are
  unit/rate/amount. Account/loan numbers live in the **masked typed-core scalars** already
  (`owner_account_number_masked`, `account_number_masked`, `loan_number_masked`), not repeated per row. →
  **No `redact` needed on any of the six**, with one watch-item: master `coverage_lines.policy_number` (238's
  `Q61-0134432`) — the master prompt already masks the scalar `policy_number`; the row will mirror that.

### ⚠️ `_MAX_TOKENS` — richer than the ticket assumed (the sizing rule drives it)
The guard's rule is `max_tokens_for`: **0 lists → 4096, 1 → 8192, ≥2 → 16384**, and
`test_every_wired_generated_extractor_matches_the_sizing_rule` enforces it for every *generated* module.
Adding a list changes the list count, hence the tier:

| type | lists now → after | `_MAX_TOKENS` now → required | note |
|---|---|---|---|
| mortgage_statement | 0 → 1 | **4096 → 8192** | as the ticket called out |
| retirement_account | 0 → 1 | 8192 → 8192 (no change) | already at 8192 (LP-103 raised it for the holdings catch-all); the rule now *agrees* |
| hoa_statement | 1 → **2** | **8192 → 16384** | ⚠️ crosses a tier — a 2nd list. 135's 36-row ledger genuinely needs the headroom |
| property_tax_bill | 1 → **2** | **8192 → 16384** | ⚠️ crosses a tier |
| homeowners_insurance | 1 → **2** | **8192 → 16384** | ⚠️ crosses a tier (forms_and_endorsements + coverage_lines) |
| master_insurance_condo | 1 → **2** | **8192 → 16384** | ⚠️ generated — regeneration sets this automatically from the spec |

**This is the sizing guard *working*, not being weakened.** Four types move to 16384 because they genuinely
gain a second list; the ledger/holdings tables are large enough to need it. Phase B updates the guard's
explicit assertions to the new true sizes (pull `mortgage_statement` out of the 4096 group → 8192; change
`hoa_statement`/`property_tax_bill`/`homeowners_insurance` 8192 → 16384). Never a blanket raise.

### The build mechanism (confirmed by reading the code)
- **Spec (`docs/schema-specs/NNN-*.json`):** the `ListSpec` (`name`, `shape: flat_row`, `shape_reason`,
  `expected_item_count`, `rules: []`, `exists_today: false`, `plumbing_sites`, `fields[{name,type,why}]`).
- **Hand-maintained modules (5):** lists are **hand-plumbed** at 5 sites — the `special_assessment_items`
  pattern in `hoa_statement.py`: Pydantic field (`list[dict[str,Any]] = Field(default_factory=list)`) + a
  row `CoreSpec` tuple + `_parse_rows(payload.get(<list>), <ROW_SPEC>)` + inclusion in the result dict +
  the `derive_status` count. The spec ListSpec documents it; the code is written by hand.
- **Generated module (master_insurance):** regeneration emits the field, parser, snapshot, and `_MAX_TOKENS`
  from the spec.
- **Prompt (`.txt`):** the row block is **hand-edited into all six** (the generator is diff-mode and never
  overwrites a shipped prompt — LP-458). `flat_row` JSON contract line, matching the existing list blocks.
- `SNAPSHOT_VERSION` stays **4** (additive with a default — LP-421). No consumer written (no rule reads
  these yet). Legacy attributes (`transactions`, `schedule_c`, `schedule_e`) untouched.

## PHASE B — build

Every list is a `flat_row` (LP-437) — no per-field provenance (no rule enumerates a row as a subject yet).
Row values are coerced to **strings** for the 5 hand-maintained lists (lossless — preserves "INCL", a
credit "($300)", and "$1,402" verbatim; matches the existing `special_assessment_items` precedent) and to
Decimal for the generated master's numeric limits (mirrors `building_limits`). **No `redact`** (no per-row
account number — those stay in the masked typed-core scalars) and **no `derived`** (nothing consumes these).

Per type, five sites: the **spec `ListSpec`** (`docs/schema-specs/NNN.json`), the **module** (Pydantic
field + row `CoreSpec` + `_parse_rows` + result dict + `derive_status` count), the **prompt `.txt`** (a
prose bucket + the JSON-contract array line, under each prompt's own naming — LP-459), and the **snapshot**
(a `ListSpec` constant + a `_LIST_SPECS` entry). `mortgage_statement`/`retirement_account` gained a new
`_LIST_SPECS` entry; the other four appended to their existing tuple. Legacy attributes untouched;
`SNAPSHOT_VERSION` stays **4**; no consumer written.

**Declared:**

### ⚠️ 238 Boiler & Machinery — a REAL finding, then a prompt fix (reported, not papered over)
The **first** Phase-C run captured only 3 of 4 coverage lines on 238 and **dropped Boiler & Machinery** —
the one line the ticket named. On the ACORD 24 cert that line's limit/deductible cells are **blank**, and
Haiku omitted it despite the "capture a blank-limit line" instruction. This is exactly the LP-458 shape
(a real gap under a confusable structure), so the prompt was the lever:
1. A blunt "emit EVERY labeled type, blank or not" over-corrected → **11 rows**, fragmenting the PROPERTY
   section into its 7 coverage sub-limits (Building / Personal Property / Business Income / …). Precision
   lost — the LP-458 recall-vs-precision swing, live.
2. Refined to **one row per TYPE-OF-INSURANCE SECTION, blank sections included, sub-limits NOT split** →
   **5 clean rows**: PROPERTY / INLAND MARINE / CRIME / **BOILER & MACHINERY** / GENERAL LIABILITY. Correct
   granularity, B&M present. 237 (a full coverage-pages doc, not an ACORD cert) still captures its 17
   detailed rows — no regression.

Only the master prompt's `coverage_lines` block was tuned (Phase C); no test depends on prompt content
there, and the master extraction + sizing suites stay green.

## ADR
Unlike LP-458 (6 of 10 findings were over-recall), **all seven LP-460 list items were real on the
documents** — the list was curated for "the document *is* a table", and the PDFs bore it out. The one
place the comparison-vs-reality tension reappeared was *within* a confirmed table: 238's blank-limit
Boiler & Machinery line, where pushing recall re-introduced sub-limit noise before the section-level
framing settled it. **The LP-458 precision/recall lesson is not just for scalars — it recurs at row
granularity, and the fix is the same: frame the unit of capture precisely rather than maximise recall.**

## What Phase 3 must now do
- **Consumers, not capture.** These six lists are captured but read by no rule. A per-rule enumerator/recipe
  (e.g. an HOA-delinquency rule over `payment_ledger`, a reserves-composition rule over `holdings`) is
  Phase-3/per-rule work — each needs its own `stable_row_id` decision and, if it maps a row enum, a
  fail-closed `derived`.
- **Document-check every scalar too.** Apply the same "open the PDF first" discipline to Phase 3's scalar
  additions — and frame any confusable field at the right granularity up front (the 238 lesson).
