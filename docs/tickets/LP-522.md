# LP-522 — a judgment finding must tell a processor what to do

**Phase 1 (AS-12) is built.** The other 17 judgment rules are unchanged and keep their LP-520 wording
until each gets domain-accurate text. Raised by a processor reading AS-12 on LF-WCHG: the findings explain our engine, not their
loan.

## What a processor reads today

> the AI judged that this deposit **does not appear to come from a borrowed source** — an AI verdict a
> human must ratify (**it never auto-ships**); $2,000.00 is above the $1,316.67 (10% of $13,166.67
> qualifying income) **materiality floor**

Then: an outcome chip repeating "a judgment awaiting human ratification", the same sentence again, a
guideline citation, and ~400 words of **Provenance — the tags this verdict rested on**.

Four failures, in order of severity.

### 1. No judgment rule can say how to fix anything

`judgment.py` hard-codes it:

```python
how_to_fix=None,
```

A DETERMINISTIC rule declares `how_to_fix` per outcome in its spec and the evaluator passes it through
(`deterministic.py:357`). A JUDGMENT rule has no way to carry one. **All 18 active judgment rules** are
affected — AS-12, CR-8, CR-10, DT-7, FR-3, ID-8, ID-9, IN-7, IN-13, IN-14, OC-2, OC-3, PC-8, PR-3,
PR-4, PR-5, TI-2, TI-6 — so no judgment finding has ever told anyone what to do.

This is a missing capability, not bad wording. It is the whole ticket.

### 2. The message contradicts its own placement

It says the deposit looks fine, and sits in Needs Attention. A processor reasonably asks *"if it is not
borrowed, why is it on my list?"* — and the sentence never answers. The answer is that the **sourcing is
unproven**, which appears nowhere in the message.

### 3. The reason is buried in the section users do not read

The decisive fact is the fifth provenance entry:

> NO matching debit of $2,000.00 was found … this is a DESCRIPTION-ONLY CLAIM, not a proven paper trail.

That is *why the finding exists*, sitting 400 words below the fold.

### 4. The verdict is stated four times

Message, outcome blurb, repeated message, and a bare `as.borrowed_funds: no` chip.

## The format

Action first. Agreed with the product owner, and it **reverses LP-376-B** ("the message states the
VERDICT") knowingly: for a processor the verdict is the least useful part, especially when it reads
"no" and the item is still in their queue. The verdict becomes supporting context; the action becomes
the identity.

> **Document the source of the $2,000.00 deposit on 3/3.**
>
> The statement describes it as a transfer from the borrower's own savings (Way2Save …3627), but no
> matching $2,000.00 withdrawal appears in any document on file — so the source rests on what the
> deposit says about itself. Deposits above $1,316.67 (10% of monthly qualifying income) need a
> traceable source.
>
> **To clear it:** obtain the statement for Way2Save …3627 showing the matching withdrawal on or before
> 3/3. If the funds came from elsewhere, get a signed explanation with supporting documents.

Three parts: **what to do**, **why it is on the list**, **how to clear it**. Nothing about AI,
ratification, or floors-as-mechanism.

## The "why" does not need to quote the model

LP-376-B keeps raw AI prose out of a finding's identity, for a good reason — engine-internal text leaks
to users. That looked like it conflicted with promoting the "no matching debit" sentence. It does not:
**`txn.source_strength` already carries that fact as a structured value**, derived deterministically
from the matched candidate (`services/tag_correlation.py`), with the prose written:

| value | prose |
|---|---|
| `verified` | a matching own-account debit was found — a verified paper trail |
| `intrinsic` | sourced by its own nature (payroll / interest / dividend) — no matching debit needed |
| `self_asserted` | the description claims a source but NO matching debit was found — a claim, not a paper trail |
| `none` | no source found |

This deposit is `self_asserted`. The model's 400-word paragraph was restating what a deterministic tag
already knew. So the message can state the reason **without quoting the AI**, and LP-376-B's principle
survives intact.

⚠️ `txn.source_strength` is produced (Stage B) and is load-bearing on AS-1, but is **not** in AS-12's
`load_bearing_tags` or `reasoned_over`. Adding it is cheap and required for this.

## Proposed mechanism

The three parts vary by verdict AND by situation — the "why" for `self_asserted` differs from `none`.
A flat per-verdict string is not enough. Two options:

**A. Verdict-keyed guidance with interpolation.** The spec declares, per `value_domain` entry, an
`action` / `why` / `how_to_fix` template interpolated over the subject's tags. The deterministic
evaluator already does exactly this — `str.format` over resolved operands, with placeholders validated
at LOAD so a typo fails there rather than mid-run (`specs.py` `_template_fields`). Reusing that
machinery is the main argument for this option.

**B. Verdict-keyed guidance, plus a composed "why".** As above, but the `why` sentence is assembled by
the engine from designated explanatory tags (`txn.source_strength` here), so a rule does not restate
prose that already exists beside the tag.

B is less spec-authoring and keeps one source of truth for "what self_asserted means"; A is more
explicit per rule. Not decided.

Either way `verdict_labels` (LP-520) folds in — it is the same idea one field earlier, and should
probably become one `verdict_guidance` block rather than two adjacent maps.

## Phasing

1. **AS-12 only.** Prove the shape on the rule the complaint came from, on a real file.
2. **The other 17 active judgment rules.** Mechanical once the shape is settled, but each needs
   domain-accurate wording — this is where the work actually is, and it should not be rushed by
   inventing fixes for rules nobody has looked at.

## UI — findings as a scrollable list, not a card to open

Requested alongside: show a rule's findings as bullets, visible at once, instead of a collapsed card
that must be expanded.

Today `CollapsedFindings` renders a header and hides every member behind a click. Proposed: the header
plus an inline list, one line per finding — `subject_label` + the **action** sentence — inside a
`max-height` + `overflow-y: auto` container, with full detail on demand per row.

⚠️ **This only works because of the message reframe, and is worth building in that order.** A one-line
bullet is useful when the first sentence is *"Document the source of the $2,000.00 deposit on 3/3"* and
useless when it is *"the AI judged that…"*. Doing the UI first would produce a list of identical
non-sentences.

Sizing: AS-2 carries 57 findings on LF-WCHG and AS-12 carries 48 in `no_longer_applies`, so the
container needs a real scroll boundary and a sensible cap, not an unbounded list.

## Decisions taken

- **Action first**, reversing LP-376-B's "the message states the verdict" — product owner's call,
  recorded here so the reversal is deliberate rather than drift.
- **AS-12 first**, then the remaining 17.
- **Provenance stays**, collapsed by default — it is the ratifier's audit trail, not the processor's
  reading.
- **The materiality arithmetic stays**, demoted from the headline to the "why this deposit" line. It is
  the auditability requirement from LP-518 and should not be lost while shortening.

## Closed — the two open questions

**1. Mechanism: BOTH, split by what varies.** `action` keys on the VERDICT; `why` and `how_to_fix` key
on an explanatory TAG (`explain_by`, AS-12: `txn.source_strength`). A single verdict-keyed template has
to assume a situation and is then false in the others — "the statement line reads X, but no matching
withdrawal appears" is simply wrong for a deposit whose source was verified. Keying the explanation on
the evidence gives one correct sentence per situation. A `default` case is REQUIRED at load: the tag can
be absent, and a finding with no explanation is the wordless card this ticket exists to remove.

**2. The yes/no chips go.** The verdict is not hidden — it SELECTS the action, so `yes` and `no` differ
in the first six words and in the fix. What it stops being is a bare chip a processor has to decode.
The decisive case: on this file the model answered `yes` on one deposit, and a skimmed `yes` reads as
"yes, fine" when it means "yes, this may be borrowed funds" — the worst finding on the file, read as its
opposite. `txn.has_identified_source: yes` goes for the same reason: it is an input whose meaning is
already inside the why sentence.

⚠️ This touches ADR-378, where ratification is the safety substitute for unmeasured accuracy. Recorded
as deliberate: the safety is that a human does real work on a real item, and a wrong verdict still costs
them attention. Hiding the label does not weaken that — a skimmed `yes` read as "fine" is a silent
mis-ratification, so removing it arguably strengthens the guarantee.

## The statement line — quoted, not summarised

The approved wording named "Way2Save …3627". `txn.source_reference` — the vocabulary's tag for exactly
that — is declared and produced by NOTHING, so the first plan was to drop the account name.

It turned out unnecessary: the description is on the `TransactionRecord` in the snapshot, and the
evaluator simply never passed it down. `{statement_line}` now quotes it verbatim. That is better than a
summary would have been — no model call, no calibration hold, and the processor can string-match
`Online Transfer From Talluri A Way2Save Savings xxxxxx3627` against the actual document.

## What it renders now

```
Document the source of the $2,000.00 deposit on 3/3.

The statement line reads "Online Transfer From Talluri A Way2Save Savings xxxxxx3627", but no matching
withdrawal appears in any document on file — so the source rests on what the deposit says about itself.
($2,000.00 is above the $1,316.67 (10% of $13,166.67 qualifying income) materiality floor)

To clear it: Obtain the statement for the sending account showing the matching withdrawal. If the funds
came from elsewhere, get a signed explanation with supporting documents. If they were borrowed, the loan
must be disclosed and its payment counted in the DTI.
```
