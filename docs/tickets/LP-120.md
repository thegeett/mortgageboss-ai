# LP-120 — Evaluator framework + first evaluator (thin slice; rule #1 = AS-5 gift-letter)

**Type:** Story · **Epic:** Phase 3.5 / Epic B · **Depends:** LP-118.6 (snapshot), LP-119 (ready-to-run), ADR-239
**Status:** complete · **Date:** 2026-07-08

## What this ticket is

The EVALUATOR layer: the code that runs a rule's actual check on the **ready-to-run** rules (LP-119's
output) and produces **FINDING** or **SATISFIED**. Where LP-119 answers "should this rule run?",
LP-120 answers "what's the verdict?".

The real deliverable is the **evaluator framework** — the shared contract every one of the ~125 rule
evaluators follows — **proven with ONE evaluator, AS-5 (gift-letter)**. **Scope held:** no
applicability filtering (consumes LP-119's ready-to-run), no runner wiring (LP-121), no other rules'
evaluators, and it never produces couldn't-check/doesn't-apply. Live path unchanged.

## Assumptions and decisions

- **Result shape:** `EvaluationResult` carries verdict + message + confidence + confidence_mode +
  provenance (+ optional `apply_spec` for future APPLY→recompute rules). **Severity/category are NOT
  on the result** — they come from the `verification_rules` row; the runner (LP-121) maps the result
  + the row onto a `Finding`. This keeps the evaluator focused on the *check*.
- **Confidence reuse:** deterministic evaluators use the existing `DETERMINISTIC_CONFIDENCE` (1.0),
  not a parallel constant. The computed path is capped at 0.99 so a fuzzy match is never a false 100%
  (the LP-115 employer-`_norm` gap this framework must eventually fix, in IN-5).
- **Registry dispatch:** a module-level dict keyed by `rule_id`; evaluators self-register in the
  package `__init__`. Adding a rule = add its evaluator module + one `register(...)` line — no
  framework edit. An unknown rule_id → `None` (graceful).
- **Provenance** records the snapshot paths read (`assets[].is_gift`, `documents[].document_type`) +
  what was observed — the trust-surface audit trail (LP-140).
- **AS-5 reproduces the live rule exactly:** same gift predicate (`is_gift` = "gift" in the asset
  type, frozen at fact-build), same gift-letter document types (`gift_letter` / `gift_funds`), same
  verified-document semantics (`present` + non-empty `fields`). The gift LETTER is the check-target —
  its absence is the FINDING produced here (LP-119 only gated "a gift exists").
- **Determinism by construction:** `evaluate(snapshot, params)` has no `db` and is sync, so it
  structurally cannot hit the DB, calculators, or AI — reinforced by the monkeypatch test.

## THE PATTERN — how to add a rule evaluator (the reusable template)

1. **Write an evaluator module** (`app/verification/evaluators/<rule>.py`) with a class exposing
   `rule_id` + `evaluate(self, snapshot, params) -> EvaluationResult`.
2. **Read the FROZEN snapshot only** — the already-computed/canonicalized facts (`computed.ltv`,
   `assets[].asset_type_canonical`, …). Never recompute, re-canonicalize, hit the DB, or call AI. If
   a value you need isn't in the snapshot, that's an applicability/couldn't-check concern (author it
   into the rule's `required_inputs`, LP-119), not the evaluator's.
3. **Return finding/satisfied via the builders:** `deterministic_finding/‑satisfied` for exact
   checks (full confidence); `computed_result(..., quality=...)` for fuzzy/matching checks (confidence
   < 1.0, "possible variation — verify" below `COMPUTED_VERIFY_THRESHOLD`). Read thresholds from
   `params`.
4. **Record provenance** — the snapshot paths you read + what you observed.
5. **Register it** — add `register(<Evaluator>())` in `evaluators/__init__.py`. Done; no framework
   change.

## Review fixes (hardening before LP-121)

**Guiding principle: fail toward couldn't-check or a loud error — never a silent pass/over-apply.**

- **FIX 2 — the AS-5 evaluator gates on the gift TOTAL, matching the live rule exactly.** An
  `is_gift` asset with a None/0 value is no longer a nonsense "gift of 0, no letter" FINDING — it is
  SATISFIED (nothing of value to document), mirroring the live `_gift_facts` (returns `(None,None)`
  when the total ≤ 0) + `_check_gift_without_letter`. Re-verified: the new verdict == the live rule
  on a normal gift AND on a gift-with-value-None fixture (both → correct verdict).
- **FIX 9 — one shared gift-document-types constant.** `GIFT_LETTER_DOCUMENT_TYPES` lives in
  `fact_namespace/projection.py` and is imported by the evaluator, so the live-parity list can't
  silently diverge into two literals.
- **FIX 10 — explicit, idempotent registration.** `registry.ensure_registered()` populates the
  built-in evaluators on every registry read, so a consumer that reaches the registry by any import
  path (or before the package `__init__` side effect) still finds AS-5 registered. Tested against an
  emptied registry.
