# LP-390-8a — Feed stmt_facts the borrower roster so owner_matches_borrower can compare (unblock AS-6)

## What this ticket is

The producer fix that AS-6 waited on — written before, **never landed** (LP-396 verified: no commit, no doc,
`_doc_context` still sent only the statement's own fields, tag still abstained 5/5). This is the real
implementation: give the `stmt_facts` group the loan's borrower roster so `stmt.owner_matches_borrower` has
names to compare the statement's account holder against. It makes the tag PRODUCE; correctness is the score.
**AS-6 is not activated.**

## Acceptance criteria (met)

- The roster comes from the existing LP-332 borrower resolution (no second identity path); injected via a
  DECLARED flag (no per-group code branch).
- `owner_matches_borrower` now produces a real comparison; the live re-score is reported (before/after +
  accuracy vs the 8 goldens).
- `is_reserve_eligible` and every other group are unaffected (additive context); AS-6 not activated
  (`ACTIVE_RULE_IDS` = 24); full suite green.

## Phase 0 — the argument (D1–D5)

- **D1 — roster source + injection.** The MISMO borrower names (LP-332). `_doc_context` gets only the
  DocumentEntry (no snapshot), so the roster is computed in `produce_ai_group_tags` (which HAS the snapshot),
  gated by a **declared** `AiGroup.include_borrower_roster` flag, and merged as `loan_borrowers` into each
  subject's context (part of the fingerprint). Reuses `subjects.loan_borrower_roster` →
  `_borrower_enumerate` + `_borrower_read_field` — no new resolution. **No per-group branch** (only `stmt_facts`
  sets the flag; every other group is byte-unchanged).
- **D2 — comparison shape.** `yes` / `no` / `unknown`, TOLERANT: middle-initial vs full/absent middle, nickname
  (Bob/Robert), maiden vs married surname, and a JOINT account (match if EITHER holder is a borrower).
  Over-strict is the DANGEROUS direction (a false "not the borrower's account" on a borrower's own statement),
  so the default leans tolerant; **the strictness is flagged for Priya**, not fixed. (LF-6T3N's statements are
  single-holder "Jordan A Rivera" — the middle-initial variant; the ticket's joint "AKASH…BANSARI" example is
  from the pre-LP-107 fixture. The prompt handles joint accounts regardless.)
- **D3 — abstention after.** The structural "no names given" abstain becomes a REAL judgment: a compare, or a
  reasoned `unknown` (ambiguous holder, or an empty/absent roster — the prompt is told to answer `unknown` when
  `loan_borrowers` is empty). Verified: the empty-roster path sends `loan_borrowers: []` and the tag abstains
  with a reason.
- **D4 — `is_reserve_eligible` must not move.** It shares `stmt_facts`' context, so it now also sees
  `loan_borrowers` — but the roster is additive and the prompt explicitly tells tag 2 to ignore it (it is about
  the account type/balance). Verified in the live re-run: `is_reserve_eligible` = `yes` on all 5, unaffected.
- **D5 — the scope mismatch (report only).** The worksheet labels `owner_matches_borrower` on
  `investment_account` docs (inv1–3), but `stmt_facts` runs only on `bank_statement`/`money_market` — so those 3
  goldens are `unmatched`. The right fix is likely **widening `stmt_facts`' applicability** to the
  investment/brokerage statement types (they have a holder too), NOT narrowing the worksheet — but that is its
  own doc-type-scope ticket, **not done here**.

## Phase 1 — what changed

- **`declarations.py`:** `AiGroup` gains `include_borrower_roster: bool = False`, parsed + guarded (only a
  document-subject group may set it; a non-bool or a non-document group fails loud).
- **`subjects.py`:** new `loan_borrower_roster(snapshot)` — the loan's borrower display names, reusing the
  LP-332 resolution + PII-safe reads (a masked name degrades to less-to-match-on, never a leak).
- **`ai.py` (`produce_ai_group_tags`):** if the group declares the flag, compute the roster once and merge
  `loan_borrowers` into each subject's context (fingerprint + batch).
- **`tag_production.yaml` (`stmt_facts` only):** `include_borrower_roster: true` + the `owner_matches_borrower`
  prompt rewritten to compare the holder against `loan_borrowers` per the tolerant shape (D2). The
  `is_reserve_eligible` half is unchanged except a one-line "ignore loan_borrowers" note.

### The prompt change (quoted)

> owner_matches_borrower — COMPARE the account holder named on the statement against the loan's borrowers, given
> to you as "loan_borrowers" (a list of names). Does the holder resolve to one of them? Be TOLERANT of harmless
> variation: a middle initial vs a full/absent middle name ("Jordan A Rivera" = "Jordan Rivera"), a common
> nickname ("Bob" = "Robert"), a maiden vs married surname, and a JOINT account that lists two holders (a MATCH
> if EITHER holder is a borrower). Answer: "yes" … / "no" (a DIFFERENT party — an unrelated name, or a
> trust/LLC/estate not a borrower) / "unknown" (ambiguous, or "loan_borrowers" empty/absent) — ALWAYS give a
> reason. NEVER guess an identity that is not in "loan_borrowers".
