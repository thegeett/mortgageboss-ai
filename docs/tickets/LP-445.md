# LP-445 — Fix the four credit-report findings from the real-file test

**Step A1 of the finish-the-rule-engine plan.** The first real credit report (LF-96SV,
18 tradelines) extracted correctly but surfaced four issues: a **false PARTIAL on every
credit report**, a retry with **zero headroom**, an **uncross-checked list**, and
**fraud/employer data stranded in the catch-all** (the third IH-1 instance).

## Acceptance criteria

- The false PARTIAL is gone: `open_tradeline_count` (open/active) is no longer cross-checked
  against the (all-tradelines) list.
- `total_tradeline_count` is cross-checked instead; null when the report states no total →
  the check does not fire (fail-closed).
- `inquiry_count` is cross-checked.
- The ID-risk + employer fields are promoted to typed core (spec + code + prompt), optional and
  null-tolerant, named for the fact, no judgment field.
- The truncation retry has real headroom above the top first-attempt tier.
- Re-extraction of the real report proves it (reported, not predicted).
- Equivalence: `ACTIVE_RULE_IDS` = 36; the 18 shipping extractors byte-unchanged; suite green;
  ruff + mypy clean.

## Phase 0 — the argument (D1–D5)

**D1 — false PARTIAL.** Guard at `credit_report.py` (`derive_status` → `declared != len(list)` →
PARTIAL), emitted by the generator's `count_crosscheck_pairs` (name heuristic `<stem>_count` ↔
`<stem>s`). The bug: `tradeline_count` is the **open/active** count (9); the `tradelines` list
holds **all** tradelines (18). Σ(monthly_payment) over 18 rows = the declared
`total_monthly_debt_payment` (1432) → no rows dropped → the 9≠18 downgrade was a **false positive**
(two different populations). Excluding `open_tradeline_count` while cross-checking a new
`total_tradeline_count` is **not expressible** via the name heuristic → an explicit `count_field`
spec declaration (below). **Does a real report state a total?** The LF-96SV report did not state an
all-in total up front (it quoted the open count) — so `total_tradeline_count` will **often be null →
the check rarely fires** (honest, fail-closed). Acceptable: today's check never protected
completeness, it flagged a population mismatch.

**D2 — retry ceiling.** Model = `claude-sonnet-4-5`, **max output 64K** (API spec; no codebase cap).
First-attempt tiers 4096/8192/16384 (by nested-list count); `RETRY_MAX_TOKENS` = 16384. The ≥2-list
tier (credit_report, tax_return) == the retry ceiling → **zero headroom**. Chosen: raise
`RETRY_MAX_TOKENS` → **32768** (a decisive 2× jump above the top tier, half of 64K). First-attempt
tiers UNCHANGED → the sizing guard stays meaningful; only the retry-ceiling assertion moves
(16384 → 32768: tracking the ceiling, not weakening the rule).

**D3 — the `<list>_count` audit (all specs).**

| spec | `*_count` fields | nested lists | cross-checked? |
|---|---|---|---|
| **credit_report** | open_tradeline_count, **total_tradeline_count**, public_record_count, inquiry_count | tradelines, public_records, inquiries | **total_tradeline_count ↔ tradelines**, public_record_count ↔ public_records, **inquiry_count ↔ inquiries**; `open_tradeline_count` **excluded** (different population) |
| appraisal | comparable_count | comparable_sales | comparable_count ↔ comparable_sales (unchanged) |
| aus_findings | condition_count | aus_required_conditions | condition_count ↔ aus_required_conditions (unchanged) |
| verification_of_mortgage | late_30/60/90/120_plus_count | payment_history_months | **none** — late counts are a sub-population of the months list |
| verification_of_rent | late_payment_count, returned_payment_count | rent_payment_history | **none** — sub-populations |
| boarder_rental_payments | returned_payment_count | payment_history | **none** — sub-population |
| trust_agreement / trust_documents / VOA / VOD / property_profile_* / survey / statement_of_account / … | grantor/trustee/beneficiary/borrower/owner/client/customer/party/… _count | (various or none) | **none** — a party/entity count, never a list length |

**The only same-population miss in the entire spec set was `inquiry_count` ↔ `inquiries`** (an
irregular plural: `inquiry` is not a substring of `inquiries`). Every other unpaired `*_count`
counts a different population and is correctly excluded. **SUCCEEDED-gating:** the check only
downgrades SUCCEEDED, so a coercion-driven PARTIAL masks the count signal — **safe** for the status
(PARTIAL is PARTIAL; nothing downstream reads a per-reason field); the only cost is diagnostic.
Kept as-is (collecting all reasons is a bigger refactor, out of scope); documented.

**D4 — naming + null-tolerance.** 7 promoted fields, named for the fact:

| field | type | source fact | PII |
|---|---|---|---|
| `ssn_alert_status` | str | SSN verification/alert status ("Requires Investigation", issuance alert) | none (status text, never the SSN) |
| `ssn_first_reported_date` | date | date the SSN was first reported | none (a date, not the SSN) |
| `address_usage_alert` | str | address-velocity alert text | none (alert text, never the address) |
| `address_tenure_months` | int | tenure at the current address, months | none |
| `credit_report_current_employer` | str | bureau-reported current employer (IN-5 corroboration) | none |
| `credit_report_previous_employer` | str | bureau-reported prior employer (IN-5 disambiguator) | none |
| `credit_report_occupation` | str | bureau-reported occupation (IN-7) | none |

The `credit_report_` prefix mirrors the `aus_*` precedent — a source-tag so no rule mistakes a
bureau-reported employer for the documented one. All optional TypedFields (default null): a null
field doesn't increment `non_null` and isn't a coercion loss → **absence keeps SUCCEEDED** (asserted).
No `pii` entry needed (none carry raw SSN digits or account numbers). **No judgment field** — text
only; a rule judges. Reverses the spec's prior `rejected: employment_history` for this subset
(annotated in the spec).

**D5 — regeneration safety.** Confirmed: `emit_module(spec)`/`emit_prompt(spec)` were byte-identical
to the shipped `credit_report.py`/`.txt`. So editing the **spec** (fields + `count_field`) + the
**generator** (honor `count_field`) and **regenerating** reproduces the module + prompt exactly — the
code edits are provably spec-derived. Only `model_call.py` (RETRY_MAX_TOKENS) is a non-generated infra
edit. `count_crosscheck_pairs` honours an explicit `count_field` first, name-heuristic as fallback, so
every spec that does not opt in emits byte-identical cross-checks (appraisal, aus_findings verified).
The validator refuses a `count_field` that names no typed-core field.

## The four fixes as applied (spec + code + prompt)

**FIX 1 — false PARTIAL.**
- *Spec:* rename `tradeline_count` → `open_tradeline_count` (+ prompt_hint); add `total_tradeline_count`;
  `tradelines.count_field = "total_tradeline_count"`.
- *Generator:* `NestedList.count_field` (spec.py, parsed in `_nested`); `count_crosscheck_pairs` honours
  it (emitters.py); validator refuses a bogus one.
- *Code:* regenerated — `open_tradeline_count`/`total_tradeline_count` fields + `_CORE_SPEC`; the
  cross-check now reads `total_tradeline_count != len(tradelines)`.
- *Prompt:* regenerated — the two fields with hints ("OPEN/active … the list contains ALL"; "TOTAL … null
  if only an open count is given").

**FIX 2 — retry headroom.** `model_call.py`: `RETRY_MAX_TOKENS` 16384 → 32768 (+ rationale comment);
guard tests updated (16384 → 32768).

**FIX 3 — inquiry cross-check.** `inquiries.count_field = "inquiry_count"` in the spec → regenerated
cross-check. Audit reported above.

**FIX 4 — promote stranded fields.** 7 fields added to the spec `typed_core` + regenerated into the
module (`_CORE_SPEC` + BaseModel) and the prompt; `rejected: employment_history` annotated.

  This is the guard working as designed, not the population-confusion false positive.

## Assumptions / decisions

- Explicit `count_field` on the nested list (not a smarter heuristic) — the spec is the source of truth
  and the mapping is self-documenting; the heuristic remains the fallback so no other spec changes.
- Global `RETRY_MAX_TOKENS` raise (not a per-type ceiling) — the zero-headroom problem is the whole
  ≥2-list class (tax_return too), so one decisive raise fixes the class.
- The 7 promoted fields are optional; a report without an ID-risk/employer section stays SUCCEEDED.

## NEW gap

- **`total_tradeline_count` reliability.** The live re-extraction had the model populate
  `total_tradeline_count` = 20 vs 18 captured rows → PARTIAL. Whether bureaus state an all-in total
  reliably, and whether the model over-populates the field when only an open count is printed, needs
  real-sample tuning (the honest D1 tradeoff: a stated-but-wrong total will PARTIAL — fail-closed toward
  a human look). The prompt hint ("Null if only an open/active count is given") is the first mitigation;
  Priya's pass on real samples is the follow-up.
- **UI list rendering** (out of scope, worth its own ticket): the frontend renders captured lists as
  `[object Object],[object Object],…`. Not touched here.
