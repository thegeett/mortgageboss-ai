# LP-121 — Runner: snapshot → filter → evaluator → result (thin slice, end-to-end on AS-5)

**Type:** Story · **Epic:** Phase 3.5 / Epic B · **Depends:** LP-118.6, LP-119, LP-120 (+ the LP-119/120 fix-up)
**Status:** complete · **Date:** 2026-07-08

## What this ticket is

The RUNNER: the orchestrator that ties the data-driven engine together and makes one rule run **END
TO END** on a real loan file for the first time. It builds the fact snapshot once, classifies every
rule via the applicability filter, dispatches evaluators only for ready-to-run rules, and returns the
**four-bucket** result (finding / couldn't-check / satisfied / doesn't-apply).

**A thin slice:** the runner is GENERAL (orchestrates any rules read from `verification_rules`), proven
end-to-end on ONE rule — **AS-5** (gift-letter). After this, the engine exists — adding a rule = author
applicability + register an evaluator, **no runner change**. **Scope held:** no trust-surface UI
(LP-162), no other rules, and the runner runs **alongside** the live cross-source path (unchanged;
retirement is LP-161).

## What was built

- **`app/verification/runner.py`** — `run_rule_engine(db, loan_file)`:
  1. `ensure_registered()` (fix #10) → 2. `assemble_fact_namespace` **once** (LP-118.6, reads the
  existing borrower↔document links) → 3. load enabled `verification_rules` → `classify_rules` (LP-119)
  → 4. for each ready-to-run rule, `evaluate_rule` (LP-120) → finding / satisfied / couldn't-check → 5.
  assemble the four-bucket `VerificationRunResult`. **Genuinely read-only** (post-review FIX 4 — see
  below): no writes, no link-refresh side effect.
- **`VerificationRunResult` / `RuleOutcome`** — the four buckets + per-rule detail.
- **Tests** (`tests/verification/test_runner.py`) — the four buckets, the live-rule correctness
  match, evaluator gating, snapshot-once, runner-ensured registration, a no-evaluator rule handled
  gracefully, plus the post-review fixes (malformed-row survival, read-only, provisional flag,
  confidence-mode vocab).

## Assumptions and decisions

- **Entry name `run_rule_engine`** — deliberately distinct from the live `run_verification` (API route)
  / `run_cross_source` (service), so the two run side by side. (The dormant-path rename is LP-161.)
- **Result shape** — a frozen Pydantic `VerificationRunResult` with four `list[RuleOutcome]` buckets;
  `RuleOutcome` carries `rule_id`, `bucket`, `message`, `reasons`, `missing_inputs`, `confidence`,
  `confidence_mode`, `provenance`. Serializable → a later API/UI (LP-162) consumes it directly.
- **The fifth case — ready-to-run but NO evaluator** — folds into **couldn't-check** with the reason
  `"no evaluator registered (rule not yet built)"`. This is honest (an applicable rule we couldn't run
  is surfaced, never a silent pass) and keeps the four buckets; it also means the runner never crashes
  on the ~17 enabled-but-unbuilt rules. `severity`/`category` mapping onto a persisted `Finding` is
  deferred (see below).
- **Snapshot built once** — one `assemble_fact_namespace` per run; every rule reads that frozen object
  (correctness + performance).
- **Result persistence is out of scope** — the runner computes + returns the result in memory. Where
  it lands (a run row + the `fact_snapshot`, mapping outcomes → `Finding`s with the rule row's
  severity/category, dedup/reconcile) is LP-140/162 + the eventual live-path swap.
- **Genuinely read-only** — the runner persists no findings, mutates no stated data, and writes NO
  borrower↔document links. It READS the existing links via the snapshot. Refreshing those links
  (`assign_documents_to_borrowers`, LP-118.8) is a **separate explicit, committed operation** run when
  documents change — not a verification side effect (post-review FIX 4). Verifying must never mutate
  the thing it verifies.

## Post-review fixes (honesty contract)

A read-only review of the LP-121 runner + the LP-119/120 hardening pass surfaced **10 findings**. The
hardening pass had fixed its original 10, but **two overshot into new honesty-contract inversions**, and
the runner had correctness gaps. The unifying principle they all serve:

> **UNMAPPED / malformed / mistyped / undeterminable all belong on the COULDN'T-CHECK side** — never
> "known", never a silent doesn't-apply, never a batch-abort. A failure in ONE rule must never take
> down the whole run.

**The two overshoots corrected (honesty-contract inversions):**

1. **FIX 2 — UNMAPPED treated as a known value.** The hardening's "present-None-with-a-source → known"
   rule (so a computed `mi_monthly=None` = "MI not required" reads as a real answer) wrongly swept in
   `UNMAPPED` / `ABSENT_*` sources too, silently passing a canonicalization *miss* as decided.
   `_known_value` now distinguishes three cases: absent → unknown; **non-determination source
   (`UNMAPPED`, `ABSENT_NO_SCHEMA`, `ABSENT_NOT_PERSISTED`, `ABSENT_UNCOMPUTABLE`) → unknown**;
   determined-value-or-genuinely-computed-None → known. (Tests: `test_fix6_present_none_computed_is_known`
   stays ready; `test_fix2_present_none_unmapped_is_not_known` → couldn't-check.)
2. **FIX 8 — a gift with no extracted amount asserted SATISFIED.** The hardening correctly killed the
   nonsense "$0 gift, no letter" FINDING (FIX 2 of the prior pass), but overshot to `SATISFIED` — a
   verdict the live rule never made (its gift facts are `(None, None)` → no check). Added
   `Verdict.COULDNT_CHECK` + `deterministic_couldnt_check`; the evaluator now returns couldn't-check,
   which the runner buckets accordingly. (Test: `test_fix8_gift_with_no_value_is_couldnt_check`.)

**Runner corrections:**

- **FIX 4 — genuinely read-only.** Removed the `assign_documents_to_borrowers` call: verifying must not
  mutate the thing it verifies. Link refresh is a separate explicit operation. (Test:
  `test_fix4_run_is_read_only` — zero commits, no new/deleted rows.)
- **FIX 1 — a malformed applicability row must not abort the batch.** `classify_rules` catches
  `ValidationError` **per rule** → that rule becomes couldn't-check with a compact reason; the rest keep
  classifying. (Test: `test_fix1_malformed_applicability_row_does_not_crash_run` — AS-5 still fires, the
  bad row is surfaced.)
- **FIX 5 — unvalidated rules run but are PROVISIONAL.** `RuleOutcome.provisional` is set from
  `VerificationRule.validated`: an un-Priya-validated threshold produces a verdict, but marked
  provisional / pending validation, never asserted authoritative. (Tests:
  `test_fix5_unvalidated_rule_outcome_is_provisional` / `…_is_not_provisional`.)
- **FIX 6 — one confidence-mode vocabulary end-to-end.** `RuleOutcome.confidence_mode` is the
  `ConfidenceMode` enum ({deterministic, computed}) — the SAME values the seed writes to
  `verification_rules.confidence_mode`, so a trust surface joins the rule row and the run outcome with no
  translation. The seed generator emits the same two values (was the stray "certain"). (Test:
  `test_fix6_confidence_mode_is_enum_matching_seed_vocab`.)
- **FIX 3 — scope dimensions are a categorical whitelist.** `_SCOPE_DIMENSIONS` maps only the five
  categorical dims (program, loan_purpose, refinance_type, occupancy, property_type); any other dim →
  couldn't-check, never a silent "no constraint → applies everywhere". (Test:
  `test_fix4_unknown_scope_dimension_fails_closed`.)
- **FIX 7 — nested required-inputs use `any`, not `all`.** A co-borrower missing a field must not sink a
  rule that a relevant borrower satisfies. (Test: `test_fix7_ragged_multi_borrower_any_present_is_ready`.)
- **FIX 10 — refi-type scope handled by the generic path.** The seed emits BOTH dims for a refi-type
  rule (`loan_purpose=[refinance]` + `refinance_type=[…]`); on a purchase the loan_purpose mismatch →
  doesn't-apply via generic FALSE-precedence, with **no** refinance-type-on-purchase special case in the
  engine. (Test: `test_fix10_refi_scoped_rule_on_purchase_doesnt_apply_via_generic_path`.)

**Two decisions locked in:** (a) unvalidated rules **do** run, but their output is provisional /
reduced-confidence (never suppressed, never full-confidence); (b) the runner is **genuinely read-only** —
borrower↔document linking is a separate explicit operation, not a verification side effect.

**Scope held:** the runner is still NOT wired to the live path; AS-5 remains the only evaluator; no
live-path behavior changed. Seed regenerated (140 rows, `confidence_mode ∈ {deterministic, computed}`,
all applicabilities parse under `extra="forbid"`). Verification suite green (225), ruff + mypy clean.

## THE MILESTONE

**One rule runs end-to-end.** For the first time, the pipeline — build the frozen fact snapshot →
classify by applicability → evaluate the ready-to-run rules → bucket the results — runs together on a
real loan file, and its verdict matches the live rule. **The engine can now run any rule: adding a
rule = author its applicability + register its evaluator, with no runner change.**
