# LP-495c — DT-7 activation, and the AI-enum abstain reconciliation it forced

**Branch:** `phase3_bucket_2_fast`. **Baseline verified this session** (not taken from the
ticket): `ACTIVE_RULE_IDS` 70 · `rule_kinds.csv` 135 rows · vocabulary 243 declared tags /
143 CSV rows · tree clean at `4b69316`.

## What this ticket does

Activates DT-7, which LP-495b built, measured and then held. The hold had one cause, and it
was upstream of the rule: `dti.atr_factors_documented` was declared with no abstain value, so
DT-7's legitimate "I cannot determine ATR" answer was indistinguishable from a broken pipeline.

Fixing that meant editing the vocabulary xlsx, and auditing the xlsx surfaced a **live**
instance of the same defect in shipped code.

---

## Part 1 — the defect, stated mechanically

Three facts compose into the bug.

1. `_build_tag` (`tag_materialization/ai.py:364`) coerces any model value outside the tag's
   declared `allowed_values` to `_unknown_tag(...)`, which sets **`confidence=None`**.
   A genuine in-vocabulary `"unknown"` instead keeps the model's own confidence.

2. `_scan_tag_degradations` (`services/verification_run.py`) matches the fail-closed marker
   **structurally**: `value == "unknown"` and `produced_by == AI` and `confidence is None`.

3. `VerificationRun.degraded` is `bool(self.degradations)`.

So for any AI tag whose **prompt sanctions `"unknown"` but whose declaration omits it**, every
run in which the model honestly abstains is reported as a degraded run. Degradation is meant to
signal a broken pipeline — a transport outage or a code defect, logged at ERROR. A legitimate
abstain is neither.

The fix is one-word and upstream: the declaration must permit the value the prompt already asks
for. Then leg 1 stops firing, the tag keeps its real confidence, and the abstain flows through
as the honest judgment it is.

## Part 2 — the audit: which tags actually have this defect

The declaration alone is not the test. A tag whose enum lacks `"unknown"` is only defective if
its **producer prompt offers `"unknown"`** and its group is actually **materialized**. I audited
all 143 vocabulary rows against `tag_production.yaml` on both conditions rather than reading the
declarations alone.

Of 59 AI-produced enum tags, 15 lack an abstain value. Only **three** meet both conditions:

| Tag | Declared | Prompt offers | Group | Read by | Status |
|---|---|---|---|---|---|
| `dti.atr_factors_documented` | `complete\|incomplete` | `complete\|incomplete\|unknown` | `atr_documentation` | DT-7 | inert (DT-7 not yet active) |
| `txn.is_nsf_or_overdraft` | `yes\|no` | `yes\|no\|unknown` | `txn_nsf` | AS-7 | inert (AS-7 not active) |
| `liab.in_application` | `yes\|no` | `yes\|no\|unknown` | `credit_profile` | **CR-1, CR-4** | **LIVE — both rules active** |

The other 12 are not defects and are deliberately left alone:

- **Seven are not materialized at all** — `liab.account_type`, `liab.is_disputed`,
  `liab.excluded_paid_off`, `liab.has_open_judgment_lien`, `property.appraisal_complete`,
  `mi.certificate_present`, `aus.data_matches_docs`, `loe.present_and_complete`,
  `contract.unusual_credits` have no AI group, so no prompt can contradict the declaration.
  Three of these (`property.appraisal_complete`, `aus.data_matches_docs`,
  `contract.unusual_credits`) additionally carry a malformed declaration —
  `enum: yes | no + missing[]` parses to the literal value `"no + missing[]"`. Recorded, not
  fixed here: unmaterialized, so nothing reads them, and inventing a shape for them is a
  separate decision.
- **Five have prompts that do not offer an abstain**, so declaration and prompt agree:
  `stmt.is_reserve_eligible`, `income.type`, `liab.derogatory_type`, `income.voe_present`,
  `income.offer_letter_present`.

`income.type` deserves a specific note, because widening it would be the tempting mistake.
Its stub abstains to `"unknown"` and is deliberately coerced — `stubs.py:141` records that
IN-12's self-employment gate *relies* on that honest-unknown being fail-closed. Its prompt
offers no `"unknown"`, so there is no prompt/declaration contradiction to fix, and adding one
would change a live rule's gating behaviour on no evidence. Left as-is.

### The live one

`liab.in_application` is the find that justifies the audit. Its prompt does not merely permit
`"unknown"` — it *mandates* it:

> "unknown" is a correct, expected answer — NEVER guess.
> TRUNCATION DISCIPLINE: … If the stated liabilities are truncated … you MUST answer "unknown"
> — NEVER a confident "no" over an unseen row.

CR-1 and CR-4 are both in `ACTIVE_RULE_IDS`. So on any real file where the stated-liability
list is truncated, or where there are no stated liabilities to compare against, the model
follows its instructions, the value is coerced to null confidence, and the run is flagged
degraded. This is shipped behaviour today, and it was not logged anywhere before this audit.

This is also why the AS-7 precedent could not be relied on. LP-495b took `txn.is_nsf_or_overdraft`
as a written-down precedent for the same pattern without checking it had ever been exercised —
AS-7 is inert, so it never ran through the orchestrator. `liab.in_application` is the case that
*has* been running, and it confirms the defect empirically rather than by analogy.

## Part 3 — the change

`docs/snapshot-fact-tags.xlsx`, `Fact-Tag Vocabulary` sheet, column C, three cells:

| Tag | Before | After |
|---|---|---|
| `txn.is_nsf_or_overdraft` | `enum: yes \| no` | `enum: yes \| no \| unknown` |
| `liab.in_application` | `enum: yes \| no` | `enum: yes \| no \| unknown` |
| `dti.atr_factors_documented` | `enum: complete \| incomplete` | `enum: complete \| incomplete \| unknown` |

then `uv run python -m app.scripts.generate_fact_tags`, committing the regenerated
`fact_tags.csv` with the xlsx.

The xlsx is a binary a reviewer cannot diff, which is the one reason to hesitate. Three things
mitigate it: the edit is a surgical rewrite of three cells' inline text with every other byte
of the sheet XML preserved (verified by diffing the extracted XML before and after); the exact
before/after strings are tabulated above; and the *reviewable* artifact — the regenerated
`fact_tags.csv` — carries the whole semantic change in three one-word diffs.

Not done by hand-editing `fact_tags.csv`: the xlsx is upstream and the next regeneration would
silently revert it, with no test to catch the loss. Not done via `vocabulary_extra.yaml`:
`projection.py` raises `ProjectionError` on a tag duplicating a CSV tag, by design.
