## Bounces are events, not mail

The plan says *"ingest the `bounces.` subdomain"*. **That is not possible**, and INFRA-3's review
confirmed it at the source: a custom MAIL FROM domain must carry **exactly one** MX pointing at SES's
feedback endpoint, and AWS says outright that a MAIL FROM domain *"shouldn't be a subdomain that you
use to receive email"*. So a bounce never arrives as a message anyone can read.

INFRA-3 built the real path — an SES configuration set publishing delivery events to SNS. This reads
them. The escalation was raised there and this is the ticket that depends on it.

---

## RFC 3463, quoted rather than recalled

From *Enhanced Mail System Status Codes*, read 2026-09-07:

> **4.XXX.XXX** Persistent Transient Failure — *"the message as sent is valid, but persistence of
> some temporary condition has caused abandonment or delay … sending in the future may be
> successful."*
>
> **5.XXX.XXX** Permanent Failure — *"not likely to be resolved by resending the message in the
> current form."*

So `5.x.x` suppresses and `4.x.x` does not. Getting it backwards either abandons a borrower over a
full mailbox or hammers a dead one forever — a mutation that swaps the two fails **11 tests**.

**UNKNOWN is not treated as permanent.** A report we cannot parse is one we do not understand, and
suppressing on it would abandon a borrower because a provider phrased something unexpectedly. On a
decision that stops someone being contacted about their mortgage, the conservative direction is to
leave it for a person.

The status pattern is anchored on word boundaries and a leading 2/4/5, because a diagnostic quotes
the recipient's address back and an address can contain digits and dots.

## The suppression reaches the reminder clock

This is the failure the plan names and the reason it is not enough to block the send path:

> **LP-814 keeps counting "no reply > 5 days" against a dead mailbox and escalates forever.**

LP-814 reads `requested_at`. A hard bounce means the borrower **never received the request** — so
`record_delivery_failure` unwinds it: `requested_at` cleared, the need back to `PENDING`. **A request
that bounced was never made.**

Only needs still in `REQUESTED` are touched, so one satisfied by a document that arrived another way
is not dragged backwards. A soft bounce unwinds nothing: a full mailbox will accept mail later, and
clearing the clock would make the system ask again immediately and forget it had ever asked.

## The column that has never had a writer

`Communication.error_detail` has existed since LP-20 with nothing writing it. This is the writer. It
carries the provider's own words — which quote the recipient's address — so it is stored, never
logged, and the readonly view already drops it.

## A bounce is not a document

The shape that most looks like one: a DSN is an email, addressed to the file's inbox, and it
**carries the original message back as an attachment**. Assessed on its bytes alone that attachment
is a well-formed PDF and comes back `SAFE` — so the borrower's own request would be filed onto their
file as though they had sent it, and a processor would see a document they are still waiting for.

`apply_safety_to_message` now marks every attachment on a DSN or auto-reply `UNSUPPORTED` with a
reason, before any assessment.

### The fixture was empty, and my own assertion caught it

`test_a_bounces_attachments_are_never_filed_as_documents` opens with
`assert rows, "the bounce fixture must carry an attachment for this test to mean anything"`. It
fired: `bounce_dsn.eml` had report parts and **no attachment at all**, so the test would have passed
while proving nothing.

That is exactly the class `b7` found in LP-804b — a deny-list assertion that is vacuous for what the
fixture lacks — and it is the first time the habit caught something before review rather than after.
The fixture is rebuilt as a realistic DSN: report parts **plus** the original message as a
`message/rfc822` part carrying a PDF at depth 1.

## Suppression is scoped per company

"This mailbox does not exist" is a fact about the world, not about a tenant. It is scoped anyway, for
the reason `b7` corrected me on in LP-811a:

* one company's bounce must not block another's send — a borrower shopping two brokers is ordinary;
* a shared table would **leak**: "that address is suppressed" tells company B that somebody else has
  been emailing their borrower.

The cost is one company learning the same fact the hard way, once. Addresses are stored and matched
**lowercase** — the local part is case-sensitive per RFC 5321 and case-insensitive at every provider
anyone uses, and matching case-sensitively lets one capitalisation typo walk past a suppression.

## The CHECK constraint

`ActivityType.COMMUNICATION_FAILED` is new, and `activity_type` is a VARCHAR + CHECK (ADR-037). A
swap **drops** the constraint and recreates it from its own tuple, so what the database accepts is
the set of the swap applied **last**, not the union of every swap. The migration therefore carries
the complete **32-value** list in model order, and `tests/test_activity_type_migrations.py` — which
reads migrations as text, because `create_all` regenerates the CHECK from the current enum and would
pass whatever the migrations said — is the guard.

The downgrade deliberately leaves the constraint carrying `communication_failed`: removing it would
reject rows already written with that value.

## Deliberately not done

- **No retry for a soft bounce.** The plan says "retry then alert". Retrying means a scheduler and a
  backoff, and nothing transmits yet — LP-816 is the ticket that sends. The classification and the
  record are here so that ticket has something to retry *from*; building the retry now would be a
  scheduler with nothing to schedule.
- **No SNS subscription or consumer task.** `record_delivery_failure` takes a parsed event.
  INFRA-3's topic is unapplied, so a poller would be a task that ticks and no-ops — the same call as
  LP-803's queue poller.
- **No un-suppression endpoint.** A person deciding an address is good again is a real flow with a
  real audit question, and nothing surfaces suppressions yet. The model supports a plain DELETE.
- **No complaint handling.** `SuppressionReason.COMPLAINT` exists because a complaint is the other
  thing that must stop sending, but SES publishes complaints on a different event shape and nothing
  parses it yet.

## For the reviewer

The three standing reviewer checks:

- **Tenancy** — `company_id` comes from `communication.loan_file_id` → `LoanFile.company_id`, which
  is a resolved loan file. That is a *read* of an existing column on a file we already have, not a
  derivation from an address; LP-805's resolver remains the only place that turns an address into a
  company. Worth checking I have that line in the right place.
- **Message content in logs** — the suppression log line carries a reason and a status code, never
  the address. The activity detail carries the class and the code; a test asserts the borrower's
  address appears in neither.
- **AI in the decision path** — none.

The judgement calls worth a second opinion:

1. **Unwinding `requested_at` on a hard bounce.** It is the cleanest way to stop LP-814 escalating
   against a dead mailbox, but it *loses* the fact that a request was attempted. The communication
   and the activity log both record it, so nothing is truly lost — but a query that only reads
   `NeedsItem` can no longer tell "never asked" from "asked and it bounced".
2. **UNKNOWN not suppressing.** A provider that reports failures in a shape I have not anticipated
   will bounce forever with nothing suppressed. I think leaving it for a person is right; the
   opposite reading is that silence is worse than over-suppression.
3. **Scoping suppression per company** when the underlying fact is global. Stated above; the leak
   argument is what decides it for me.

## Review (second session, protocol §3)

One finding, and it is the builder's own flagged concern arriving from the other side: the request
is written down in **two** places, and only one was unwound.

### A — The finding still said "Requested", with the button disabled

`_unwind_requests` correctly returns the need to `PENDING` and clears `requested_at`, on the sound
principle that a request which bounced was never made. But LP-801 marks the **originating finding**
with `details["docs_requested"]`, and `finding-card.tsx` does two things with that marker:

```tsx
disabled={busy || docsRequested}
… {docsRequested ? "Requested" : "Request docs"}
```

It is not a badge. It renders the request button as **"Requested"** and **disables it**.

So after a hard bounce the processor saw a finding claiming the documents had been asked for, with
the one control that would let them ask again greyed out — for a request this very function had just
decided never happened. The two records disagreed, and the one the processor could act on was the
wrong one.

`_clear_finding_markers` now unwinds the finding side too, matched through
`requested_needs_item_id` — the tolerant reader added in the LP-801 review, which handles the
pre-LP-801 bare `True`. Those rows carry no needs-item id, so they cannot be matched and are left
alone; that is correct rather than convenient, since a marker with no link cannot be shown to belong
to this bounce.

Verified in both directions, with two controls: removing the unwind fails the hard-bounce test;
clearing markers unconditionally fails the other-need control; and a soft bounce leaves both records
untouched, so a briefly-full mailbox does not erase the request record.

**This is the builder's item 1, and the answer to it.** The concern was that unwinding loses, from
the `NeedsItem` row, the fact that a request was attempted. The sharper version is that the *other*
record was never unwound to match — and the distinction the builder worried about losing is
recoverable exactly where it matters: the processor re-requests, and `send_draft` refuses with
*"this address is suppressed — an earlier message to it bounced permanently. Confirm the address
with the borrower before sending again."* That is the right place to learn it, and I checked the
suppression really does reach the send path rather than only the reminder clock.

### The builder's three, ruled on

1. **Unwinding `requested_at` — right, and now consistent across both records.** See above.
2. **`UNKNOWN` not suppressing — right, and it is the conservative direction on the correct axis.**
   The cost of not suppressing is more bounces; the cost of suppressing wrongly is a borrower
   silently uncontactable about their mortgage because a provider phrased a report unexpectedly.
   Those are not symmetric, and the reversible one is the right default.
3. **Tenancy — checked, and it is a read rather than a derivation.** `record_delivery_failure`
   resolves `communication.loan_file_id` → `LoanFile.company_id`. It starts from a communication row
   we already hold, whose loan file is already known; nothing here turns an address into a company.
   LP-805's resolver remains the only thing that inverts the invariant. The suppression table is
   scoped per company for the same reason my LP-811a finding scoped the rate limit — a shared table
   would tell one tenant that another has been emailing the same person.

### The habit catching something before review

Worth recording, because it is the first time in this loop that a discipline caught a defect before
the reviewer did rather than after. The DSN test opened with
`assert rows, "the bounce fixture must carry an attachment for this test to mean anything"` — and it
fired: `bounce_dsn.eml` had report parts and no attachment, so the test would have passed while
proving nothing. That is precisely the shape of the LP-804b `DANGEROUS_KEYS` finding, written as a
guard line rather than learned again.

### Done when, and the standing checks

RFC 3463 is quoted rather than recalled and the classification is right: 4.x.x persistent transient,
5.x.x not resolvable by resending. The plan's named trap is closed — the suppression reaches the
reminder clock and not merely the send path, which is what stops LP-814 escalating against a dead
mailbox.

Standing checks: tenancy as above; `error_detail` carries the provider's words, which quote the
recipient's address, and is stored but never logged and dropped from the readonly view; no AI. A
DSN's attachments are never filed as documents, which is the right call on the shape that most looks
like one — a bounce carries the borrower's own request back, and on its bytes alone that is a valid
PDF.
