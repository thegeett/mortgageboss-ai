# LP-438 — Spec format + generator for generic lists; apply DOB and blocking-question decisions

## What this ticket is

Step 3 of the schemas-for-all-105 plan. LP-437 built the generic list mechanism but shipped `_LIST_SPECS`

## D1–D5

- **D1 — decision scope, measured.** **11 DOB fields across 9 specs** (001×2, 005, 014, 038, 048×2, 052, 071,
  093, 108). **139 blocking questions across 85 specs**: 115 fall under a theme and were flipped (NL 73, PII 36,
  SIG 4, CHILD 2); **24 stay blocking** (outside all four themes). After the flips + DOB null + condition-4
  retirement, **70 specs pass** (was 14).
- **D2 — `_LIST_SPECS` registration.** A shared file every generated module edits is a merge-conflict factory.
  **The generator emits the registration as a SNIPPET** (`"<type>": (_<LIST>_LIST,)`), exactly like the
  `EXTRACTORS` snippet — never a patch. Actual wiring is a later step (step 7). **ADR-344** records that the
  `ListSpec` type lives in the snapshot layer (`documents_section`), so an extraction module cannot import it
  without a layering inversion — the reason wiring is a deliberate, separate step rather than an auto-patch.
- **D3 — the flat-row prompt block.** `bank_statement`'s transactions section is the template: one bare row
  per item + a per-field page/snippet, `transaction_type` driving the derived `direction`. The generator emits
  this shape (`3. NESTED LISTS — one FLAT ROW per repeating item`).
- **D4 — the count cross-check.** Four specs have a `<list>_count` field beside a matching list:
  `005` tradeline_count↔tradelines, `005` public_record_count↔public_records, `006` comparable_count↔
  comparable_sales, `010` condition_count↔aus_required_conditions. Each now emits the comparison (count ≠ rows
  → PARTIAL).
- **D5 — `plumbing_sites`.** Deprecated. Dropped from the reference (`002`) list entry and marked deprecated in
  `_FORMAT.md`; the cost is now ≈ one declaration + the per-rule consumer.

## The format extension (`_FORMAT.md`)

Added the three optional LP-437 helper declarations to `NestedList`:
```jsonc
"derived": [{"field":"direction","from":"transaction_type","map":{"deposit":"credit","withdrawal":"debit"}}],
"redact": ["description"],
"stable_row_id": true
```
`derived` is stated **fail-closed**: an unmapped value → an ABSENT field, never fabricated (the forged-deposit
discipline). Guide §4 rewritten: nested lists are GENERIC (a declaration → a `ListSpec`), no longer refused;
the CONSUMER (a rule enumerator or a derived recipe) stays per-list as the rule's own logic.

## The generated bank-statement output (002, diff mode)

The `transactions` list is now an **ADD** (was BLOCKED), with the emitted `ListSpec`:
```python
_TRANSACTIONS_LIST = ListSpec(
    name="transactions",
    fields=("date", "description", "amount", "transaction_type", "running_balance",),
    derived=(
        DerivedSpec(field="direction", from_field="transaction_type",
                    mapping={"deposit": "credit", "withdrawal": "debit"}),
    ),
    redact=frozenset({"description"}),
    stable_row_id=True,
)
# Register in app/verification/snapshot/documents_section.py::_LIST_SPECS (a snippet, never a patch — D2):
    "bank_statement": (_TRANSACTIONS_LIST,),
```
This executes into a real LP-437 `ListSpec` identical to LP-437's demo (asserted in tests). It COEXISTS with
the shipping bank_statement's legacy `transactions` attribute — the ListSpec is not wired (don't migrate a live
rule).

## Assumptions / decisions

- A blanket answer covers only the questions it fits; 24 were left blocking, not stretched.
- The generator emits list registration as a **snippet**, never a shared-file patch (D2 / ADR-344).
- Consumers are NOT emitted (per-rule logic); reported as follow-up per list.

## NEW GAP — custom PII kinds (cond 3 = 23)

The specs invented **~17 PII kinds beyond `PiiKind`'s {SSN, ACCOUNT}**: NAME (7), TIN (5), EIN (4), POLICY (3),
CARD (3), LOAN/ID/A_NUMBER/FILE_NUMBER/PHONE (2 each), CLAIM/EMAIL/DOCUMENT_NUMBER/RECEIPT_NUMBER/PASSPORT/
VISA/I94 (1 each). These refuse on condition 3. The ticket decided only **DOB** among PII kinds; Geet's "mask
account-like → ACCOUNT; addresses + case numbers plain" policy is now RECORDED in the flipped questions, but
**applying it to the fields (remap POLICY/LOAN/TIN/… → ACCOUNT; NAME/PHONE/EMAIL → their own decision) is a
field-level follow-up** — NAME/PHONE/EMAIL do not cleanly fit the account-like/address blanket, so remapping is
not stretched here. This is the largest remaining refusal bucket and the next cheapest unblock.
