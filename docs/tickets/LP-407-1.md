# LP-407-1 — The four-gate audit of Bucket 2.5 (READ-ONLY)

## What this ticket is

LP-405's census named ~10 rules (7 Contract, 3 DTI) whose source documents are **already extracted**
(`purchase_agreement`, `homeowners_insurance`, `hoa_statement`, `property_tax_bill`), so it called them "wire the
tag, not build an extractor" — **Bucket 2.5.** But LP-405 asked only **one** question ("are the inputs
produced?"), and Bucket 2 proved that insufficient: of 4 rules it called writable-now, **3 were non-expressible**
and needed derived producers first (ADR-322/323/324). This audits all 12 candidates (the 10 + the two assumed
blocked, PC-1 and DT-1) against **all four gates**, so the downstream work is planned on facts. **No file was
changed except this report.**

**Headline:** the true `wire-and-write` count is **~2 (PC-2, DT-5), not ~10.** The rest split into a small
derived-producer wave, four rules blocked on an extractor **extension** (a catch-all field), Priya thresholds,
and calibration. LP-405 over-counted Bucket 2.5 exactly as it over-counted Bucket 2 — by asking only gate 1.

⚠️ **`rule_tags.csv` is a PLANNING artifact that has DRIFTED and is NOT authoritative.** Confirmed here: it maps
**AS-2** → `contract.emd_amount` / `contract.emd_sourced`, but AS-2's **live spec** reads
`txn.apparent_category` / `txn.has_identified_source` (the loan-proceeds sweep). It also mis-wires
AS-8/IN-6/PC-7 (noted in their specs). So where `rule_tags.csv` disagrees with an extractor schema or a spec,
**the schema/spec wins.**

**The four gates.** A rule is genuinely `wire-and-write` only if all four pass: (1) every field is in a running
extractor **AND typed-core** (not catch-all); (2) the **relation** is natively expressible; (3) any AI tag it
trusts is measured; (4) no Priya threshold. **Gate 2 killed 3 of 4 Bucket 2 rules — it gets the most care.**

## Phase 2 — the roll-up

### The true `wire-and-write` count: ~2, not ~10

Only **PC-2** is cleanly `wire-and-write` (two parsed tags + a deterministic `==`), and **DT-5** with a caveat.
LP-405's ~10 counted the whole 2.5 set on gate 1 alone; the four-gate audit reclassifies them:

| verdict | rules | count |
|---------|-------|:---:|
| **wire-and-write** | PC-2, (DT-5 — with a redundancy caveat) | **~2** |
| **needs-derived-producer** (cheap, LP-410-style) | DT-2, DT-4, PC-3, PC-5 | 4 |
| **needs-extractor-extension** (a catch-all field) | PC-4, PC-6, PC-8, PC-9 | 4 |
| **+ needs-definition** (Priya threshold) | PC-4 (IPC cap), DT-1 (DTI limit) | 2 |
| **+ needs-calibration** (unmeasured AI) | PC-6 (signature), DT-4 (new-construction leg) | 2 |
| **needs-extractor** (absent document — Bucket 4) | PC-1 (title), DT-1 (credit report) | 2 |
| **unclear** (relation not determinable from the description) | PC-9 (which date the "flag" is against) | 1 |

*(Rules carry multiple blockers — the columns above sum past 12.)*

| tag | subject | computes | mirrors | for | size |
|-----|---------|----------|---------|-----|:---:|

Plus **parsed wires** (simple passthroughs from the typed-core fields): `contract.sales_price` +
`property.purchase_price` (PC-2), `ins.premium_annual` (DT-5), `contract.emd_amount` (PC-5).

**`housing.hoa_monthly` and `housing.taxes_monthly` share the `housing.insurance_monthly` monthly-conversion
shape — build the pattern once, get both.** The `purchase_agreement` typed-core fields (sales_price,
property_address, earnest_money_amount) are shared across PC-2 / PC-3 / PC-5, so one producer-wiring pass over
that extractor unblocks several.

### The extractor extension (the four catch-all rules)

**PC-4, PC-6, PC-8, PC-9** each need a field that lives in `purchase_agreement.additional_sections`, not
typed-core: **seller_credit, addenda/signature, personal_property, contingency_dates.** These need the
`purchase_agreement` extractor **extended** (promote the field to typed-core, or a producer that reads the
catch-all section). This is more than "wire a tag" but less than "build a new extractor" — it is a real, bounded
extractor change, and it gates **4 of the 7 Contract rules**. Note two of these are ALSO blocked elsewhere (PC-4
on the IPC threshold, PC-6 on the signature AI, PC-8 is judgmental), so the extension alone does not make them
`wire-and-write`.

### PC-1 / DT-1 — confirmed blocked (with one partial surprise)

- **DT-1 — confirmed Bucket 4.** Its `liab.*` / `debt.counts_in_dti` inputs come from the **credit report**
  (no extractor), plus `housing.pi` (an unbuilt P&I calc) and a Priya DTI limit. Multiply blocked; the census's
  credit-report gating holds. **No surprise.**
- **PC-1 — confirmed blocked on TITLE, but PARTIALLY reachable.** `title.parties_match` needs the title-commitment
  extractor (absent → Bucket 4). **However**, PC-1's *contract-vs-file* party leg (contract buyer/seller — both
  typed-core — vs the 1003/MISMO parties) is a plain all-equal fuzzy match, **reachable without title.** So a
  **reduced PC-1** (parties agree across the contract and the file) is wire-and-write; only the title
  reconciliation waits for Bucket 4. A boundary worth drawing.

### Overlap boundaries to draw (the AS-8/AS-10, IN-5/IN-6 precedent)

- **PC-5 ↔ AS-2 (live).** AS-2's own spec docstring says its true shape is "a cross-document MATCH (contract EMD
  amount ↔ a debit) which is not cleanly expressible today; this **approximates** it via the AS-1 txn sourcing
  vocabulary." So **PC-5 is the real EMD match that AS-2 approximates.** Decide: does PC-5 supersede AS-2's
  approximation, or complement it? Do not ship both firing on one EMD.
- **DT-2 / DT-4 / DT-5 ↔ DT-1.** These three verify the individual housing-expense **lines** (HOA, taxes,
  insurance); DT-1 verifies the back-end **ratio** that sums them. Complementary — but DT-1 needs all three lines
  produced, so the DT-2/4/5 producers are prerequisites for a complete DT-1 (whenever the credit report lands).
- **PC-3 ↔ ID-4 — NO overlap** (checked): ID-4 is the borrower's **residence** address; PC-3 is the **subject
  property** address. Distinct facts; both can be fuzzy-consistency rules without colliding.

### The build order (cheapest-first, with dependencies)

1. **PC-2** — wire `contract.sales_price` + `property.purchase_price` (parsed), write the deterministic `==`. The
   one true wire-and-write. Opens the Contract category with the least work.
2. **The monthly-conversion producers** — `housing.hoa_monthly` + `housing.taxes_monthly` (one shape, mirrors
   `housing.insurance_monthly`), then DT-2 + DT-4 (minus DT-4's new-construction AI leg).
3. **DT-5** — wire `ins.premium_annual`; **first resolve** whether "premium used vs binder" is a real check or
   trivially equal (housing.insurance_monthly already derives from the binder — see the caveat).
4. **PC-3** — the `property.address_normalized` AI tag (mirrors `id.address_normalized`), ConsistencyEval fuzzy,
   ships ratify (no calibration gate on a ratifying rule).
5. **The extractor-extension wave** — extend `purchase_agreement` for the four catch-all fields, then PC-4
   (+ Priya's IPC cap), PC-6 (+ signature AI), PC-8 (judgmental), PC-9 (+ its date relation, once clarified).
6. **PC-5** — the `contract.emd_sourced` cross-document match; **first resolve the AS-2 overlap.**
7. **Bucket 4** — PC-1's title leg (title extractor) and DT-1 (credit report). PC-1's contract-vs-file leg can
   ship earlier as a reduced rule.

## The caveats / assumptions (especially what was INFERRED)

- **Catch-all fields: READ, not inferred** — LP-405 flagged seller_credit/addenda/personal_property/
  contingency_dates as inferred; the extractor schemas confirm all four are **not typed-core** (catch-all).
- **DT-5's redundancy is a FLAG, not a conclusion** — "premium used vs binder" may be trivially equal because
  `housing.insurance_monthly` (the DTI's insurance line) already derives from the binder's `annual_premium`. If
  "premium used" means the DTI's insurance input, DT-5 compares the binder to itself. Its real target (a stated
  loan-terms premium vs the binder?) needs clarification; classified `wire-and-write` **provisionally**.
- **PC-9's relation is UNCLEAR** — "flag contingency dates" does not say against what (a passed deadline → date-
  vs-today → a recency tag; or vs the closing date → an operand compare). Flagged `unclear`, not guessed.
- **PC-3 as ConsistencyEval-fuzzy is INFERRED from the ID-4 precedent** — the planned tag
  `property.address_normalized_match` is an AI-at-rule-time enum (`fact_tags.csv`), which could instead be a
  pre-computed AI match tag (the OC-1 shape) needing calibration. Either way it needs an AI address tag from the
  contract; the ratify-vs-auto choice is a design call.
- **rule_tags.csv drift is confirmed** (AS-2 + AS-8/IN-6/PC-7) — do not trust it for wiring; the specs/schemas
  are authoritative.
- No file was modified. This report is the only deliverable.

## What this changes about the plan (§13's Bucket 2.5 sizing)

- **"Bucket 2.5 ≈ 10 wiring-only rules" is wrong.** It is **~2 truly wire-and-write** (PC-2, DT-5) + **~4 cheap
  derived producers** (DT-2, DT-4, PC-3, PC-5) + **~4 blocked on a purchase_agreement extractor EXTENSION**
  (PC-4/6/8/9) — with Priya thresholds (PC-4) and calibration (PC-6) on top. The "just wire the tag" framing
  held for the census's gate-1 view but not the four-gate reality.
- **The genuinely cheap sub-wave** (a real Bucket 2.5): PC-2 + the two monthly-conversion DTI producers (DT-2,
  DT-4) + DT-5 — **~4 rules, all mirroring existing patterns, no extractor change, no Priya threshold.** Ticket
  these first.
- **A distinct "extractor-extension" wave** (PC-4/6/8/9) should be split OUT of Bucket 2.5 — it needs a bounded
  `purchase_agreement` change, not just tag wiring, and carries thresholds/calibration/judgment.
- **PC-1 is partially reachable** (contract-vs-file parties) — a reduced rule can ship before the title
  extractor; only the title leg is Bucket 4.
- **The census's method lesson repeats:** gate 1 ("inputs produced") over-counts; the relation gate (2) and the
  typed-core/catch-all distinction (1b) are what separate cheap from not. This audit applied all four so the
  producer wave and the extractor-extension wave can each be ticketed on facts, not on "~10".
