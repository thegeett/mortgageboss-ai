# LP-635 — a 44-document file cannot finish a verification

- **Ticket:** LP-635
- **Status:** In progress — the ceiling and the grinding outage are fixed; the call count and a resumable pass are not
- **Date:** 2026-08-30
- **Found on:** staging `LF-ZE9N` (`staging-48d2f20`), two consecutive runs

## The report

`LF-ZE9N` cannot be verified. Two runs, both killed at exactly fifteen minutes:

```
00:44:42 → 00:59:42   failed   Rule-engine pass failed after retries
01:04:47 → 01:19:47   failed   Rule-engine pass failed after retries
```

Neither is an error. Both hit Celery's soft time limit while still working:

```
00:59:42  Soft time limit (900s) exceeded for verification.run_rule_engine
00:59:42  rule_engine_pass_exhausted terminal=True
          billiard.exceptions.SoftTimeLimitExceeded
```

At the moment it was killed the second run had logged 26 `ai_group_reasoning_done` and 12
`stage_a_reasoning_done` — still inside rule evaluation, nowhere near the composition passes that run
at the end. There is nothing to fix in the failure path: **the work does not fit in the window.**

Re-running does not help and should not be attempted as a remedy. It will fail identically every time.

## Why this file and not the others

| file | documents | outcome |
|---|---|---|
| **LF-ZE9N** | **44** | times out, twice |
| LF-AWBB | 21 | completes in 12m27s |
| LF-BVFU | 0 | n/a |

The rule engine's AI work scales with documents, and LF-ZE9N is more than twice LF-AWBB.

**The limit was sized against an assumption that no longer holds.** Its own comment states it:

```python
RULE_ENGINE_SOFT_LIMIT_SECONDS = 900  # 15 min — a 30-doc run (~282s) finishes with wide headroom
```

That is 9.4 seconds per document. LF-AWBB's completed run is 747 seconds over 21 documents — **35.6
seconds per document, near four times the assumption** — and at that rate a 30-document file needs
about 1,070 seconds, already past the limit the comment calls "wide headroom". The constant did not
drift; the cost per document grew underneath it, and nothing re-measured.

44 documents is not an unusual real loan file. This is a ceiling on file size, not an edge case.

## Where the time goes

Measured over the failed run's window: **591 AI calls, 2,542 seconds of cumulative model latency,
mean 4.3 seconds.** Concurrency keeps wall-clock below that sum, but the call COUNT is the cost, and
it is a function of documents and subjects.

**Every one of those 591 calls read zero cached tokens.**

```
cache_read_tokens: 0 across 591 calls   (nonzero: 0)
```

`build_document_block` does set a cache breakpoint, but only on a DOCUMENT block — that path serves
extraction, where the same PDF is sent repeatedly. The rule engine's reasoning calls send text and
share no cached prefix, so each pays full input price. Whether their system prompts are stable enough
to cache is not established here and is the first thing worth measuring: 591 calls sharing a large
prefix is the cheapest lever visible, and it is worth knowing before the limit is simply raised.

## Two adjacent defects, found in the same logs

**1. A connection failure is reported as rate limiting.** From 00:29 to 00:44 Bedrock was unreachable
from the worker — dozens of `APIConnectionError` at `latency_ms=1` to `52`. A request that fails in one
millisecond never left the host: that is DNS or connection-refused, not throttling, and it hit
`claude-haiku-4-5` and `claude-sonnet-4-5` alike. The retry layer nonetheless recorded:

```
classification_ai_failed  infra_failure=rate_limited
```

Anyone reading that goes looking for quota. The misclassification sends an operator after the wrong
subsystem during exactly the minutes they can least afford it.

**2. Retry exhaustion did not end the task.** The AI retries gave up within about fifteen SECONDS. The
task then sat until the soft limit killed it fifteen MINUTES later. A brief infrastructure blip cost a
full task slot and a failed run, and the first LF-ZE9N failure is that shape rather than the
size-related one the second failure is. Worth understanding separately from the ceiling: a run whose
calls have exhausted their retries has no reason to hold the slot.

This also revises two earlier diagnoses. The stalls at 2026-08-28 01:38 and 2026-08-29 01:22 were both
put down to the deploy rolling the worker mid-run. One of them was — the ECS events line up. The other
has this shape instead, and the connection-failure mode is the likelier explanation for both silences.

## Nothing on the needs path is prompt-cached (measured 2026-08-31)

Recorded here because it belongs to this ticket's subject — what the AI calls on a big file
actually cost — and was found while reviewing an unrelated need-list fix (bug-009).

`cache=True` reaches `build_document_block` from exactly three places: `app/ai/client.py`,
`app/ai/extraction/model_call.py` and `app/ai/extraction/chunked.py`. The needs reasoner is not one
of them, so **no call on the needs path sets a cache breakpoint**. This is consistent with the zero
prompt-cache reads measured for LF-ZE9N above, and it is the explanation for part of it.

What makes it worth costing now: bug-009 renders the valid need types into the reasoning system
prompt from the catalog, which took it to **11,746 characters, roughly 2,936 tokens, 175 types**. And
the reasoner is **not** once per file — `app/tasks/needs.py:78` re-reasons on every document arrival.
On a 44-document file that is ~44 calls on the reasoning tier (Sonnet by default), each carrying that
same unchanging prefix. The prefix is byte-identical across all of them, which is the ideal shape for
a cache breakpoint.

Two things to settle before changing anything, neither answerable from the repo:

  * **The Sonnet cache minimum on Bedrock.** `client.py` documents Haiku 4.5's as 4,096 tokens,
    evaluated against the cumulative `tools` -> `system` -> `messages` prefix. A 2,936-token system
    prompt is UNDER that, so a breakpoint on the system block alone would cache nothing and report
    `cache_creation_input_tokens: 0` — the silent no-op that file already warns about. Sonnet's
    minimum is not recorded anywhere in the repo and needs to be confirmed against the model in use,
    not assumed from Haiku's.
  * **Whether the user context defeats it anyway.** The system prompt is identical per call, but the
    file context in the user message changes as documents arrive. A breakpoint after the system block
    is what caches the prefix; that placement needs to be deliberate, for the reason the chunked path
    documents.

Not changed as part of bug-009: enabling caching is a cost decision that needs live measurement
against Bedrock, and it should be verified by reading `cache_read_input_tokens` back, not by
assuming a flag worked. The measurement above is the input to that decision.

## Not the cause: LP-634's need composer

Worth recording, because the timing invited the inference. The need-prose pass is the newest thing in
the run and it is not implicated:

* LF-ZE9N never reached it — the run died mid-evaluation, and neither `need_prose_pass_done` nor
  `finding_prose_pass_done` appears in its logs;
* on LF-AWBB it ran in about **five seconds** for 13 needs (`need_prose_pass_done composed=13
  needs=13` at 00:42:55, run complete 00:42:56).

LF-AWBB's 12m27s against roughly 10 minutes on earlier runs is document growth and variance, not this.

## What has been fixed (2026-08-31)

**1. The limit is a function of the file** (`rule_engine_limits`). A fixed 900s was never wrong about
the clock — it was wrong about the assumption underneath it, and a constant cannot report that. The
budget is now `documents x 35.6 s/doc x 1.7`, floored at the old 900s so small files are unchanged
and capped at 3600s. LF-ZE9N's 44 documents earn 2,662s against the ~1,566s the measurement says it
needs. The measured constant is named and dated in the code, so the next person to find it stale is
looking at a number that says what it was measured against.

The stuck-run watchdog and `scripts/deploy staging verify` derive their bound from the SAME function.
A fixed watchdog would have been the new bug: it would have failed a healthy 44-document run at 25
minutes and told the processor it "timed out", on exactly the files this change exists to make work.

**2. A pass whose AI backend has gone away now stops** (`AiInfraBreaker`). LF-ZE9N's FIRST failure was
not the size problem — it was the Bedrock outage, ground through for fifteen minutes because nothing
asked whether the next call could land. Five consecutive INFRASTRUCTURE failures (each already having
exhausted its own retries) end the pass. It is deliberately transient: the slot is released in
seconds and Celery retries later, where before an outage borrowed the soft limit's terminality by
arriving dressed as a timeout. Content failures do not count and reset the counter, so a hard file
still completes with honest `couldn't check` findings.

**3. The mislabelled connection failure** was fixed separately under LP-636 defect 2 —
`infra_failure_kind` now returns `connection` / `server_error` distinctly from `rate_limited`, and
routing keys off `RERUNNABLE_INFRA_KINDS` rather than any single label.

**Still open, and they are the interesting half:** the call COUNT (591 on one file) is untouched, and
the pass is still not resumable, which is what makes the ceiling hard rather than soft. Raising the
limit buys those files the ability to finish; it does not make finishing cheap. Prompt caching is
measured above and not enabled.

## What a fix has to decide

Raising the limit is the obvious move and the least informative one — it buys time without knowing
what the time is for. In rough order of what would be learned:

1. **Is the reasoning prefix cacheable?** 591 calls at zero cache reads is the largest single number
   here. If the AI groups share a stable system prompt, this is input tokens and latency for a
   breakpoint.
2. **Does the call COUNT have to scale this way?** 26 AI-group calls and 12 stage-A calls on one file
   is the shape to question before the clock is.
3. **Should the pass be splittable?** A rule run that cannot be resumed must fit in one window, which
   is what makes the ceiling hard rather than soft.
4. **Then raise the limit**, with a re-measured number and a comment that says what it was measured
   against — the failure here is as much the stale comment as the value.

## Impact

`LF-ZE9N` is unverifiable today. Any file above roughly 30 documents is at risk, and the risk is
invisible until a run has burned fifteen minutes and failed. The failure is safe — the run is marked
`failed` with a reason, nothing is half-written, and a re-run supersedes it — but it is not
recoverable by retrying, which is the natural thing for a processor to try.
