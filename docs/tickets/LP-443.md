# LP-443 — Step 7: bridge the list capture, prove it on one document, then wire in batches

## What this ticket is

**The last step of the schemas-for-all-105 plan.** LP-442 made every schema'd type reachable (109/109 resolve
to a catalog entry). ~90 generated extractors and ~50 `ListSpec`s existed — **and none of them ran.** Two things
stood in the way: the registrations were unapplied snippets, and **the list capture had a hole in the middle.**
This bridges the capture, proves it end to end on `bank_statement`, then wires the extractors (a batch, then the
remainder).

## THE HOLE (LP-440's recorded gap)

| layer | before LP-443 |
|---|---|
| **The prompt** | asks for the list as **bare rows** (`{"date": <scalar>, …, "page": …, "snippet": …}`) |
| **The extractor** | ❌ generated modules had **no field** to store them (typed-core + catch-all only) |
| **The snapshot** | `build_list_rows`→`_typed_field` expected **`{value}`-wrapped** rows |

Three layers, two mismatches, never run end to end. LP-437's own test proved nothing — it fed the reader
`{value}`-wrapped rows that no extractor produces.

## D1–D5

- **D1 — the bridge decision: read BARE in the snapshot (option b).** Two independent reasons converge:
  (1) **shape-match** — `bank_statement.transactions` already stores bare rows, so wrap-at-extraction would give
  the generated lists a SECOND stored shape (the divergence LP-441/442 repaired); (2) **forced by the proof** —
  bank_statement's transactions are bare and immutable (AS-1), so the reader MUST read bare for the generic
  mechanism to read them at all. Fixed in one place (`_list_field`); `_typed_field` (schedules, `{value}`-wrapped)
  untouched. The generator emits the extractor-side capture (`list[dict]` field + `_parse_<list>`).
- **D2 — what shape does `bank_statement.transactions` store today?** **BARE rows** — `_parse_transactions`
  stores coerced scalars + one `source` per row, NOT `{value}`-wrapped. The generated prompts ask for the same.
- **D3 — coexistence.** Registering `_TRANSACTIONS_LIST` makes `build_list_rows` read the SAME
  `extracted["transactions"]` the legacy path reads → the same rows populate BOTH `entry.transactions` (legacy,
  AS-1's input, byte-unchanged) AND `entry.lists["transactions"]` (generic, read by no rule yet). Additive,
  belt-and-braces, no migration. Caveat: the generic `direction` uses the minimal ListSpec mapping
  (deposit/withdrawal); legacy `_direction` maps a richer vocabulary — a future per-rule consumer must not treat
  the generic `direction` as AS-1's.
- **D4 — confidence on row fields.** A bare-row prompt supplies one `page`/`snippet` per row and NO per-field
  confidence → each list-row Field carries `confidence=None`, honest, never fabricated.
- **D5 — the Phase B batch (9):** `credit_report` (3 lists), `appraisal`, `title_commitment`,
  `condo_questionnaire` (flat), `aus_findings`, `business_license` (flat), `certificate_of_eligibility`,
  `verification_of_mortgage`, `homeowner_s_insurance_quote`.

## PHASE A — the bridge, proven on one document (the end-to-end proof)

A realistic bank statement, run through the REAL `_parse_bank_statement_json` → `build_documents_section`:

```
entry.lists['transactions'] — 3 rows landed (was 0 before the bridge):
  row_id=lst3058a3fbc9d…  date=2026-05-02  amount=5000.00  direction='credit'  desc='PAYROLL ACCT [redacted] DEP'  conf=None  src=extracted
  row_id=lst98e579a577d…  date=2026-05-11  amount=1800.00  direction='debit'   desc='RENT CHECK 1042'              conf=None  src=extracted
  row_id=lsteddd8c901ee…  date=2026-05-20  amount=2000.00  direction=None      desc='WIRE TRANSFER'               conf=None  src=extracted
```
Values coerced, description **redacted** (account# scrubbed), `direction` derived (deposit→credit,
withdrawal→debit, "wire"→**None** fail-closed), confidence honestly `None`, source `extracted`, stable
`lst…` row_ids. **Coexistence:** the legacy `entry.transactions` still populated identically (3 rows, same
directions), feeding AS-1 unchanged. **Count cross-check** (proven on the regenerated `appraisal`):
`comparable_count=3` vs 2 rows → **PARTIAL**; `count=2` → SUCCEEDED. *(Reported at the Phase-A STOP; both open
questions — coexistence caveat, bare-row `confidence=None` — confirmed by Geet before Phase B.)*

**⚠️ `credit_report` token ceiling (LP-439's flag):** 3 lists (tradelines 14 fields, public_records 6, inquiries
3) at the 16,384 ceiling. **No real tri-merge fixture exists** (extraction is always mocked in tests; there is no

truncation is detected, never silent. **A real tri-merge sample is the remaining validation (a gap).**

- `test_extraction_budget_sizing.py` — **extended** with the generated-fleet sizing check.
- `test_appraisal_extraction.py` + 51 other generated tests — regenerated (the generator now emits list-capture
  sample rows so the happy path stays SUCCEEDED past the count cross-check).
- New: `test_lp443_list_capture_bridge.py` (the bridge proof + coexistence + count cross-check).
- **No rule/extraction-logic test changed.**

## Assumptions / decisions

- Bare stored shape, one place fixed, `confidence=None` — all confirmed by Geet at the Phase-A STOP.
- The legacy `transactions`/`schedule_c`/`schedule_e` paths were NOT migrated (a STOP) — coexistence only.
- All 91 generated extractors are UNVALIDATED STARTERS; wiring makes them run, tuning is separate.
- A declared `source` list field wins over the reserved provenance key (collision handled in the generator).

## NEW gaps / what remains

- **List-row PII is not `_PII_FIELDS`-routed** — a PII value inside a captured list row (e.g. a tradeline's
  `account_number_masked`) relies on the prompt masking it; a per-list redact/route step is a follow-up.
- **`credit_report` token ceiling** needs a real tri-merge sample to confirm actual behaviour (guarded, not
  silent, today).
- **No per-rule consumer** reads any generic list yet (an enumerator / derived recipe is rule logic — its own
  step). The lists are additive facts.
- **The 18 diff reports** (typed-core additions for shipping extractors) are NOT applied — each is its own ticket.
- **AI visibility of list data** (step 8) remains.
- **Accuracy tuning** of all 91 generated starters with Priya + real documents.
