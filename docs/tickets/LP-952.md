# LP-952 — Reading state and Read again

- **Ticket:** LP-952 · Phase 4.5 Stage 3 follow-ups, batch 4 (the staging trial)
- **Source:** [`phase4.5-staging-trial-2026-09-30.md`](../phases/phase4.5-staging-trial-2026-09-30.md)
  items 4 and 5; the owner: "Add the queued/reading/done/failed state and an unread count. The panel
  polls until done. Add the Read conditions / Read again route and button, refused while a reading runs,
  and never re-reading a read or confirmed condition."

## Design

**Why.** The reading was queued only at import and recorded only when it ended
(`condition_rounds.reading_run`). After Import nothing on screen moved, and a round that was never read
(LF-DH8V's round 1, imported before LP-919) looked the same as one being read: "Not read yet" for ever.

**State** (`app/services/condition_reading_state.py`), kept in the existing `reading_run` JSONB, so no
migration:
- `queued` (set by every door before the task is sent), `reading` (the task, in its own commit before
  the model call), `done` (the end-of-run record, `RoundReading.as_run`, now carries `state: done`),
  `failed` (the task's final failure, error = the exception's TYPE name, never its text; or
  `not_queued` when the broker refused the task).
- `not_queued`, reported, not stored: conditions are unread and nothing is queued or running.
- A `queued` or `reading` record older than 15 minutes is reported `failed` with error `stalled`, so a
  lost task offers Read again instead of a spinner for ever.
- A `reading_run` written before LP-952 (no `state`) reads as `done`.
- `unread` counts the FILE's unread conditions, because `read_round` reads all of them.

**One door for queueing.** `api/conditions.queue_round_reading(db, round_)` marks `queued`, COMMITS, then
sends the task (so the worker's `reading` mark can never be overwritten by a late `queued`); a refusing
broker leaves it `failed / not_queued`. Import and LP-949's `queue_unread_reading` (lender set, code mapped,
PATCH) all go through it. `_enqueue_reading` now returns False when the broker refused.

**Routes** (round-scoped, tenant 404 like every round route):
- `GET /condition-rounds/{id}/reading` → `ReadingStatePublic {state, unread, error}`;
- `POST /condition-rounds/{id}/read`: reads the file's newest imported round. Refused 409 with a code:
  `reading_running` while one is queued or running (and not stale), `nothing_unread` when every condition
  is read, `not_imported` with no imported round. Never re-reads: `read_round` takes only `unread`
  conditions.

**Frontend.**
- `useReadingState(roundId, fileId)` polls every 3 s while `queued`/`reading`, and when a running reading
  ends it refetches the plan and the conditions, so the plan replaces the panel without a refresh.
- `ReadingStatus` above the plan panel: "Reading 6 conditions… The plan appears here when it is done."
  with a spinner; "6 conditions have not been read. Reading them builds the plan and the email drafts."
  with **Read conditions**; "The conditions could not be read. The reading stopped before it finished. 1
  condition still unread." with **Read again**. Nothing once every condition is read.
- The drawer's "Not read yet" no longer promises "The app reads each condition shortly after the sheet is
  imported" (false for LF-DH8V): it points to the panel above the list.

### Findings (6, all fixed)

1. **Only one door refused a second reading; the others started one beside a running one.** The
   "refused while a reading runs" check lived in the POST route alone. Import, setting the lender, the
   loan-file PATCH and a mapped code all went through `queue_round_reading`, which marked `queued` over a
   `reading` record and sent a second task. Two tasks running at once read the same unread conditions twice:
   two model calls and two `condition_read` events per condition. This is LP-951's "other doors skipped the
   check" again. **Fix:** `queue_round_reading` now takes the file's row lock (`SELECT … FOR UPDATE` on
   `loan_files`, the pattern `email_draft` uses) and skips when any round on the file has a reading queued
   or running that is not stale. It returns whether it sent one. A condition that arrives after the running
   reading took its list stays unread, and the panel then offers Read conditions. The POST takes the same
   lock, so two clicks cannot both see "nothing running". Test:
   `test_no_door_queues_a_second_reading_beside_a_running_one`, with the positive control that the same
   door queues once the reading is done.
2. **The state was recorded on one round and read from another.** The import door marked the round it
   imported. The panel asks about the newest imported round (by `created_at`), and the POST and
   `unread_round_to_read` act on it too. When an older draft is imported after a newer one, those are
   different rounds. The panel then said "6 conditions have not been read" beside a running reading, its
   button queued a second reading, and the plan was built under a round the panel does not show. A GET on
   an older round also reported that round's own old record. **Fix:** every door queues on the file's newest
   imported round. `reading_state` reports the file's reading: a running round anywhere on the file, else
   the newest imported round's record. The POST's running check covers the whole file (`running_round`).
   Tests: `test_the_reading_is_queued_on_the_newest_round_and_reported_on_every_round` and
   `test_a_reading_running_on_another_round_refuses_read_again`.
3. **A failure with nothing left unread showed false copy and a button the server refuses.** A `failed`
   record stays after another door has read every condition. The panel then said "The conditions could not
   be read. … 0 conditions still unread." and offered Read again, which the server refuses with
   `nothing_unread`. **Fix:** a failure with `unread == 0` reports `done`, so the panel shows nothing. Test:
   `test_a_failure_with_nothing_left_unread_offers_nothing`.
4. **A cached reading state hid readings started by other doors.** `["condition-reading-state", id]` is
   polled only while `queued` or `reading`, and its staleTime is the default minute. Setting the lender (the
   conditions tab and the overview PATCH) queues a reading, and an attached PDF can add unread conditions,
   but neither refetched the state. The panel kept "not read" with a button that is refused while the
   reading runs, or showed nothing, and the plan never arrived without a refresh. This repeats LP-951's
   cached value and LP-949's stale screen. **Fix:** `afterLenderChange`, `invalidateRound` (import and
   attach) and `useUpdateLoanFile`'s lender branch now invalidate `["condition-reading-state"]`. Tests:
   the lender and attach-PDF cases in `lib/api/reading-state.test.tsx`.
5. **A refused Read again left the stale panel up.** On a 409 (`reading_running` or `nothing_unread`) the
   panel showed the error and kept the button. **Fix:** `useReadAgain`'s `onError` refetches the reading
   state, so the panel shows the running reading or goes away. Test: "refetches the reading state when Read
   again is refused".
6. **Three stated behaviours had no test.**
   - Read again restarting the polling: setting the cache to `queued` must re-arm `refetchInterval` from
     `not_queued`, which does not poll.
   - The task marking `reading` before it reads: the builder's test called `mark` by hand rather than
     going through `_run_read`.
   - `_mark_read_failed` writing the error's type.
   **Fix:** tests for all three: the polling test has a positive control that `not_queued` does not poll,
   and `test_the_task_marks_reading_before_it_reads_and_failed_after_it_gives_up` runs `_run_read` with
   `task_session` patched.

### Checked, no finding

- **Every door that queues a reading:** `read_condition_round.delay` appears once, in `_enqueue_reading`.
  Its only caller is `queue_round_reading`, which import, the POST and `queue_unread_reading` (lender PUT,
  loan-file PATCH, code map) all call. The paste, split and reparse paths never import, so they never read.
- **The early return in `read_round`** with nothing unread writes `as_run()`, which carries `state: done`.
- **The task's two sessions:** a round deleted between them makes `read_round` and `build_plan` return
  early, and nothing is written.
- **The stale cutoff against the hard limit:** each attempt marks `reading` again with a fresh `at`. One
  attempt is at most 360 s (`PARSE_HARD_LIMIT_SECONDS`), plus at most 60 s of backoff, against 15 minutes.
  A live attempt cannot be called stalled. A hard-limit kill skips `on_exhausted`, so the spinner can run
  up to 15 minutes before Read again is offered. Accepted.
- **The unread count** uses the same filter as `read_round`: not superseded, not soft-deleted, any lender
  status, including withdrawn and information-only conditions. The count therefore equals what a reading
  would read.
- **NPI in `reading_run`:** the error field holds only `stalled`, `not_queued` or an exception's type name,
  capped at 200 characters. The log events carry ids and type names only.
- **The plan panel together with the reading panel:** `RoundPlanPanel` renders nothing at `planned == 0`.
  "6 not read" therefore never sits above an empty plan; it can sit above a plan for the conditions that
  were already read, which is accurate.
- **The drawer copy** ("The panel above the list shows …") holds in every state where a condition is
  unread, because the panel renders whenever `unread > 0`. `ImportedView`, the other host of the detail
  sheet, is no longer mounted.

### Rejected or recorded, not built

- **The `FOR UPDATE` lock has no test.** It needs two concurrent sessions, and the suite isolates each
  test in one. Mutating it fails no test. Recorded rather than faked.
- **Attaching a PDF to an imported round adds unread conditions but queues no reading.** This was true
  before LP-952. Import reads automatically; attach and forward do not. After finding 4, the panel shows
  "N conditions have not been read" with Read conditions, which is accurate. Whether attach should read
  automatically is a decision for the owner, so it is not built here.
- **The code-map mutation on the lender settings page** does not invalidate any of the file's condition
  queries, including the new one. This predates LP-952, and the file page is a different route that
  refetches once a minute has passed.
