# LP-596 — The real-estate-owned schedule, parsed and made visible

## What was wrong

MISMO has always carried `OWNED_PROPERTY` — the 1003's real-estate-owned schedule — and the parser
has always retained it. In `catch_all`, which is swept for display and **never reaches the snapshot**.
So the facts were parsed, stored, shown to a human, and invisible to every decision the system makes.

The cost was not theoretical. On the one real export, five `OWNED_PROPERTY` blocks sat unread while
three live rules reported they could not determine things the application states outright:

- **DT-6 / DT-8** ask whether a mortgage is the lien being refinanced or one on property the borrower
  keeps. `OwnedPropertyDispositionStatusType` (Retain / Sell / PendingSale) *is* DT-6's question, and
  `OwnedPropertySubjectIndicator` is DT-8's. DT-8 was deciding from the LO's payoff checkbox alone.
- **AS-4** waives minimum reserves for a one-unit principal residence, but only when the borrower has
  no *other financed properties* (B3-4.1-01: 2% of aggregate UPB for 1–4, 4% for 5–6, 6% for 7–10).
  It was returning `satisfied` without testing that precondition. On the real file — five retained
  liens totalling $2,190,383 — the correct answer is emphatically not zero.

This is the same failure as LP-510, which exists because "four findings asked a processor for
something the file already contains." This is that at ten times the scale: an audit of the real
export found **95 stated leaf elements the parser never reads**, of which this schedule is the
highest-value block.

## What was built

The full path, because parsing alone would have changed nothing:

1. `ParsedOwnedProperty` (`app/mismo/schema.py`) and `_parse_owned_properties` (`parser.py`).
2. `StatedOwnedProperty` (`app/models/stated_financials.py`) — named for the `Stated*` family
   deliberately: a lien balance here is corroborated by a payoff statement and a value by an
   appraisal, and this table claims neither.
3. Migration `a3f7c21b9e05` — table, index, and a `readonly.stated_owned_properties` view.
4. Persistence in `import_service`.
5. **Projection into the snapshot** (`mismo_section.py`) — the step `catch_all` never had, and the
   only reason any of the above matters.
6. `backfill_mismo_owned_properties` — a one-off task, LP-510's shape, re-parsing the retained raw
   file for already-imported loan files.

## Decisions worth recording

**`is_subject` is tri-state, and its `false` is nearly worthless.** The real export marks
`OwnedPropertySubjectIndicator=false` on all five blocks — the subject property is described in its
own section, not repeated in the schedule. So "no block is marked subject" means "the schedule lists
other properties", **not** "this loan has no subject property". Only a `True` identifies the subject.
This is the same trap LP-568 hardened `paid_off_at_closing` against, and it is pinned by a test that a
future change would have to argue with.

**The nested address is deliberately not parsed.** Each block carries a full `PROPERTY/ADDRESS` — the
borrower's other home. No rule asks for it, so pulling it into a typed column would add PII that the
snapshot, the readonly views and every log line would then have to scrub, for no evaluative gain. The
catch-all still retains it for display, which is the right home for something only a human reads.

**The backfill skips a file with any existing rows rather than topping it up.** A partial schedule is
worse than none: a rule counting financed properties would count a subset and report a confident wrong
number.

**No `SNAPSHOT_VERSION` bump.** Additive snapshot fields do not bump it — LP-421's precedent, and
`test_snapshot_version_unchanged` enforces it.

## Tests

`tests/mismo/test_owned_property_lp596.py` (7) and
`tests/scripts/test_backfill_mismo_owned_properties_lp596.py` (6), all against the real export where
one exists. Every guard mutation-checked:

- blinding the parser, and — separately — **parsing but not projecting**, which is precisely the
  `catch_all` bug this ticket fixes, and is caught by exactly the one test written for it
- report-only committing anyway, and existing rows being topped up rather than skipped

The lien-UPB join is asserted rather than assumed: the schedule's five balances equal the five stated
`MortgageLoan` balances exactly, which is what will let DT-8 learn which property secures which debt.

Full backend suite green (5381 passed).

## What this unblocks

AS-4 (task #15) and DT-8's corroboration branch (task #14) can now be built on the stated fact rather
than inferred from liability counts. **The backfill must run on staging before either lands**, or both
will evaluate against an empty schedule on every existing file.

## Still on the floor

The audit found 94 other unread elements. The ones that would close currently-open findings:
`CurrentRateSetDate` (CL-1 asks for the rate-lock date), `EmploymentStartDate` and
`EmploymentBorrowerSelfEmployedIndicator` (IN-4 asks for employment dates; self-employment changes the
whole document set), `CashFromBorrowerAtClosingAmount`, `LiabilityAccountIdentifier` (CR-6), the
`PROPOSED_HOUSING_EXPENSE` block (the gated DTI), and the full 1003 declarations — including
`UndisclosedBorrowedFundsIndicator`, which is literally AS-12's question.
