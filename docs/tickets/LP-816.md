## An interface with no provider, and that is the ticket

The execution protocol's §5 settles it: *"Which mail provider is the pilot customer on? **Unknown —
build Route B (forwarding) only.** Do not build Gmail API or Graph. LP-816 stays scoped to a mailbox
connection interface with no provider implementation."*

That is not a shortcut, and `phase4.md` §3 prices the alternative. Google's *read* scopes are
**restricted** — brand verification, scope justification, a demo video and an App Defense Alliance
**CASA assessment**, realistically 6 to 12 weeks for a first-timer with annual re-assessment forever.
On Microsoft, Graph is a clean ~1-week build. **Which of those we are looking at is decided by an
answer nobody has given**, and writing the wrong one costs more than writing neither.

So what exists is the seam the answer plugs into — and, far more importantly, the proof that plugging
one in cannot skip anything.

---

## The guards a transport cannot skip

`b7`'s warning going in was the one that shaped the tests: *"a send that bypasses the suppression
list, the rate limit or the reviewed_by requirement because it goes out through a different transport
is the same message with none of the checks."*

**Transmission happens inside `send_draft`, after every guard, and nowhere else.** There is no second
send function and no route that reaches a transport directly. A provider implementation therefore
inherits the suppression check, the rate limit and the approver requirement **by construction rather
than by remembering** — the way to make a bypass impossible is not to remember, it is to have nowhere
else to call from.

And the tests assert that in the shape that can actually fail. A transport is registered that
**records what it was handed**, and each guard case asserts it was handed *nothing*. Asserting only
that the guard refused would pass on a build where the transport ran first and the guard refused
afterwards — which is a message sent and then reported as blocked.

## The scopes are a closed set

`gmail.send` is **sensitive**, not restricted: a scope review, no security assessment. The read scopes
are restricted and would pull the customer into CASA — which is exactly why inbound is forwarding
(Route B) and only outbound is an API. §3 calls that pairing *"the cheapest full-duplex
configuration"*. Graph's `Mail.Send` is delegated, needs no admin consent, and has no CASA
equivalent.

`register()` **refuses a scope outside the allowlist**. This is the one place a future Gmail or Graph
build declares what it asks the customer's admin for, and a scope creeping past `gmail.send` is the
change that turns a scope review into a CASA assessment — for *them*, not for us. Refused here so it
is a failing import rather than a support conversation six weeks in.

---

## Three ways to reach "no transport", and all of them mean copy-and-send

- **No connection** — most files.
- **A forwarded alias** — Route B forwards *inbound* mail. §3 names send-as among "what forwarding
  cannot give", and a transport that tried would send from **our** domain with her name on it, which
  §3's Route C analysis rules out explicitly: the borrower sees an unfamiliar sender on a mortgage
  file, the exact shape of the phishing they have been warned about.
- **No provider registered** — every kind today, per §5.

`NoTransport` **raises rather than pretending**. Reporting a send that did not happen would tell a
processor a borrower had been written to and start a reminder clock against silence nobody caused.

---

## What sending this way would buy

A transmitted message has a `Message-ID` **we** generated, and `external_message_id` — which LP-818
separated from the id a reply *answers* — is filled with it. That is what LP-805's rung 2 matches a
borrower's `References` against, so their reply routes with **certain** confidence instead of falling
to the footer tag, which §2.2 grades "high" and which Gmail and Outlook mobile routinely trim out of
a quoted body.

On copy-and-send there is no such id, because the message left from her own client and we never saw
it. A test asserts that too, because it is the state of the product today.

## Tests

`tests/services/test_mail_transport_lp816.py` (16).

Verified by mutation, each confirmed applied:

| Mutation | Result |
|---|---|
| a forwarded alias allowed to send | **survived → fixture fixed → now fails** |
| a revoked connection allowed to send | 1 fails |
| the scope allowlist removed | 1 fails |
| a transport failure left silent | 1 fails |
| the provider's id not recorded | 1 fails |
| the connection looked up across tenants | 1 fails |

**The survivor was the fixture, again, and in the cleanest form yet.** Removing the
`FORWARDED_ALIAS` guard changed nothing — because the registry is empty, so the lookup returned None
anyway and the test could not reach the case it was named after. It now **registers a transport for
that kind**, which is exactly the mistake the guard exists to survive.

The suppression and rate-limit tests each carry a positive control: the rate-limit one asserts the
*first* send did reach the transport before asserting the second did not, because "nothing was
transmitted" is what a broken registry looks like too.

## Deliberately not done

- **No Gmail or Graph implementation**, per §5. **Escalated** — it is the open question, and the
  answer changes a 1-week build into a 6–12-week one.
- **No `reviewed_by_user_id` column.** The plan's LP-811 line names it; `send_draft` already
  requires `approver_user_id` and LP-821 stores it on the evidence record, which is the same
  guarantee under a different name. Adding a second field for it would be two places to look for one
  fact. **Recorded rather than resolved by adding a column.**
- **No token storage, refresh, or OAuth flow.** `MailboxConnection.encrypted_refresh_token` exists
  unused from LP-808, deliberately, so the provider that needs it is a service rather than a
  migration.
- **No UI.** Nothing to configure until there is a provider.
- **The ADR §3 asks for** — *"Email ingestion source is pluggable — forwarded SMTP for pilot,
  provider API for GA"* — is **not written**. This module is that decision in code; the ADR belongs
  with the provider choice rather than ahead of it. **Escalated.**

## For the reviewer

- **Tenancy** — the connection is looked up by the **file's** company. A lookup that found any
  connected mailbox would send one tenant's borrower mail out through another tenant's account;
  tested.
- **Message content in logs** — the two new lines carry a connection kind and a boolean. Never the
  recipient, the subject or the body.
- **AI in the decision path** — none.

Worth a second measurement:

1. **A transport failure does not undo the record.** `record_sent` has already run, and rolling back
   would lose the evidence row and the needs transition for a message that may well have gone out —
   a provider that timed out after accepting it is the ordinary failure. The status moves to
   `FAILED` instead. That is a judgement call about a partial failure and worth disagreeing with.
2. **The connection is picked with `.first()`** on the company's active connections. One company
   with two connected mailboxes is undefined today; LP-808's own review made "first wins" total by
   adding an id tiebreaker for participants, and this has no such ordering.
3. **`AUTO_REPLY_HEADERS_NONE` is an empty dict with a name.** A human-approved send carries no
   suppression headers — they ask a correspondent not to answer, and a document request is the one
   message we most want answered. Named so the absence reads as a decision.
