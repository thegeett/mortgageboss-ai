# LP-901 — A palette you can swap: raw colours and roles, split

- **Ticket:** LP-901 · second of three (LP-900, LP-901, LP-902)
- **Status:** Built — awaiting review
- **Date:** 2026-09-11
- **Scope:** `app/palettes/petrol.css` (new), `app/globals.css`, `app/layout.tsx`,
  `app/palettes/palettes.test.ts` (new), `tailwind.config.ts` (comment), `tailwind.config.test.ts`,
  `ledger-assets.test.ts`, `docs/design/ledger/assets/*`
- **Decision:** ADR-402 (extends ADR-389)
- **Migration:** none
- **Visible change:** none — every colour in the app is identical, verified below

---

## What was asked

Make the UI palette flexible enough that recolouring the app is a matter of changing the palette, and
the colour combination (which colour is used where) is just as easy to change.

## Where it stood

The components were already clean: after LP-UI-004 nothing names a colour except through a role
(`bg-primary`, `text-warning`) — zero palette-scale classes, zero hex, zero inline style colours.
What stood in the way was underneath them. Every role in `globals.css` held a literal HSL triple, and
a `.dark` block restated all thirty:

| Value (light) | Restated as |
| --- | --- |
| `187.9 67.9% 22.0%` (petrol) | `--primary`, `--info`, `--ring` |
| `188.6 17.9% 7.6%` (near-black) | `--foreground`, `--card-`, `--popover-`, `--secondary-`, `--accent-foreground` |
| `0 0% 100%` (white) | eight roles |

There was no "palette" to swap. There were sixty values, some of which had to move together.

## The split

**Palette** — `app/palettes/petrol.css`. Raw colours only, for light (`:root`) and dark (`.dark`):

```
--neutral-1 … --neutral-12   a ramp numbered by JOB, not lightness
--brand, --brand-contrast    the one accent, and what sits on it
--red / --green / --amber / --violet (+ -contrast each)
```

**Roles** — `app/globals.css`, written **once**, no dark block:

```css
--primary: var(--brand);
--muted-foreground: var(--neutral-10);
--warning: var(--amber);
```

So the two things you might want to change live in two places:

- **Recolour the app** → edit a palette (a second palette and a switcher follow in LP-902).
- **Change which colour plays which part** (headings in brand, cards the same as the page) → edit a role.

### Why the neutral ramp is numbered by job

| Step | Job | Light | Dark |
| --- | --- | --- | --- |
| 1 | app background | 98.6% | 5.7% |
| 2 | raised surface (card) | 100% | 8.2% |
| 3 | overlay (popover) | 100% | 9.6% |
| 4 | subtle fill (muted, secondary) | 95.7% | 11.0% |
| 5 | hover fill (shadcn `accent`) | 93.1% | 13.7% |
| 6 | hairline (`border`) | 89.8% | 15.1% |
| 7 | loading placeholder | 89.6% | 17.8% |
| 8 | strong hairline | 81.6% | 20.0% |
| 9 | control border (≥3:1) | 54.5% | 39.8% |
| 10 | quiet text (≥4.5:1) | 41.0% | 56.5% |
| 11 | secondary text | 29.8% | 72.5% |
| 12 | primary text | 7.6% | 92.4% |

(Lightness shown; each step also has its own hue and saturation.)

Step 10 *is* quiet text in both themes, so `--muted-foreground: var(--neutral-10)` is right in both,
and the role layer needs no `.dark` block. A lightness scale (`gray-500`) means the opposite thing in
dark and would have forced a second role block — the duplication this ticket exists to remove.

This is the same shape as Radix Colors' 12-step scales, arrived at from the other end: the twelve
roles the app already had turned out to be twelve distinct jobs in a consistent order in both themes.

## Verified identical

Nothing on screen may change, so this was checked numerically rather than by eye. A script parsed the
**old** `globals.css` (from `HEAD`) and resolved every **new** role through `petrol.css`:

```
60 colour roles compared across both themes, 0 differ
```

Then in a real browser (headless Chromium against `next dev`), `getComputedStyle` on `<html>`: petrol
light `--primary` = `187.9 67.9% 22%`, body `rgb(251, 252, 252)` = `hsl(180 14.3% 98.6%)`. And in the
production build the palette blocks are all present — the palettes sit outside any `@layer`, where
Tailwind tree-shakes nothing (the failure AMENDMENTS A4 recorded for the old `.dark` block).

## Contrast is computed now, not claimed

`globals.css` used to say *"every text tone clears 4.5:1 against its own ground in BOTH themes …
Verified, not assumed."* It was true — and it was a sentence, true of one set of values, that would
have stayed on screen after the next palette arrived.

`app/palettes/palettes.test.ts` resolves every role through every palette, in both themes, and
computes WCAG 2.x ratios for the pairs the UI actually draws:

| Pair | Floor | Petrol, tightest |
| --- | --- | --- |
| `foreground` / `foreground-2` / `muted-foreground` and every status/accent text, on each of background, card, popover, muted, secondary, accent | 4.5:1 | 4.60 (light `muted-foreground` on `accent`) |
| each `X-foreground` on `bg-X`, for 11 fills | 4.5:1 | 4.86 (light, on `muted`) |
| `text-X` on its own `bg-X/10` chip tint, over background and card | 4.5:1 | 4.77 (light `warning`, over background) |
| `input` and `ring` on background and card | 3:1 | 3.20 (light `input` on background) |

`/10` because it is the chip tint — `status-token.tsx` `CHIP`, and 62 of the app's 108 status-fill
opacities.

It also fails a palette that is **missing a colour** (which would otherwise render that colour from
the default and look like it worked), a block under any other selector, a non-HSL value, `border` equal
to `input` *after* resolution, and any colour role holding a literal instead of `var(--…)`.

### Mutations — each one fails the test

| Mutation | Fails |
| --- | --- |
| delete `--amber` from petrol's dark block | vocabulary (dark) and contrast (dark) |
| lighten light `--neutral-10` to 60% | contrast (light) |
| `--warning: 37.8 89.4% 29.6%` in globals.css | role-is-a-reference, contrast, and the control |

## What moved out of `tailwind.config.test.ts`

Its "`%s` is defined in `.dark`" and "`border` ≠ `input`" checks compared raw strings in
`globals.css`. There is no `.dark` block there now, and comparing `var(--neutral-6)` with
`var(--neutral-9)` can never fail even if a palette gives them the same value. Both now live in
`palettes.test.ts`, against resolved colours, per palette, per theme. The "every referenced var is
defined in `:root`" check stays where it was.

## The ledger assets

`docs/design/ledger/assets/globals.css` and `tailwind.config.ts` must match the shipped files
(`ledger-assets.test.ts`). They were byte-identical before the change, so they are copied, and
`assets/palettes/petrol.css` is added with its own pair: the asset `globals.css` is roles only now,
and not a drop-in without the colours it points at. Whether those reference copies should exist at
all now that the Ledger redesign has shipped is a separate question, not answered here.

## Assumptions and limits

- **Palette and theme apply to `<html>` only.** Roles are declared on `:root` and inherited as
  resolved values, so a `.dark` on an inner element would not re-theme that subtree. Nothing does
  that today; it is written into `globals.css` and ADR-402.
- **`MEASURED_SAFE` in `a11y-contrast.test.ts`** (`text-primary/80` "5.10:1 on bg-card") is still a
  hand-measured Petrol number. Faded text is a different question from palette contrast and is left
  as it was.
- **Shadows** still use Tailwind's built-in black; out of scope (research step 5).
- Values were rewritten without trailing zeros (`22.0%` → `22%`) — the same number.
