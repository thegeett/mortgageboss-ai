# bug-016 — IN-7 asked a borrower who never changed jobs for an offer letter

- **Status:** Fixed
- **Date:** 2026-09-11
- **Found on:** staging `LF-XMB2`, reported by the processor reading the finding against its own evidence
- **Scope:** Backend — `tag_materialization/derived.py` (a new recipe),
  `rules/tag_production.yaml`, `rules/vocabulary_extra.yaml`, `rules/specs/IN-7.yaml`

## The report

IN-7 surfaced this for borrower 2 on LF-XMB2:

> **Obtain an offer letter, contract, and pay stubs from the new position to document the start date and
> confirm income in the role.** The file shows Dare Odubote remains employed as Workforce Development
> Analyst 2 with Commonwealth of Pennsylvania, but documentation of the new position itself is needed…

There is no new position. That borrower has held one job since 2021-01-25, and the finding's own
evidence says so — the tag behind it reads *"All documents show employment with Commonwealth of
Pennsylvania … in the same position title 'Wrkfrc Dvpt Anl 2'. No employer or occupational change is
evidenced."* The message asks for a document that cannot exist.

## The cause

Two halves, and the second is why the first was invisible.

**IN-7 declared a scope it never tested for.** `applicability.scope` reads *"every borrower on the loan
with a job change"*, but the `judgment:` block carried no `applicability` condition, so the rule ran for
every borrower on every file.

**The tag it reasons over cannot scope it.** `income.same_line_of_work`'s own production prompt says to
answer **"yes"** when there is a single employer throughout. So "this borrower never changed jobs" and
"this borrower moved within the same field" arrive at the rule as the same answer, and no amount of
judgment downstream can separate them.

**And "yes" had no wording of its own.** `guidance.explain` covered `"no"` and `default`, so a "yes"
fell to the default — *"Document the new position — offer letter or contract, start date, and pay stubs
from it"* — which is the text written for a borrower who changed field.

## The fix

1. **A new derived per-borrower tag, `income.has_job_change`** (yes / no / unknown), read from the
   application's own employment records (`borrower.{n}.employer.{m}`): "yes" when the borrower has BOTH
   an ended and a current employer, "no" when every record is current (no move) or every record has
   ended with nothing current (a termination — IN-15's question), "unknown" when the application states
   no employment for this borrower.

   Deliberately **not** derived from documents: a pay stub says who pays the borrower now, and only the
   application says what came before, which is the whole of IN-7's question.

2. **IN-7's judgment block gains `applicability: {tag: income.has_job_change, op: eq, value: "yes"}`.**
   Resolved before the gate and before any AI call, so a borrower who has not changed jobs is
   `not_applicable` and costs nothing.

3. **`guidance.explain."yes"`** now asks for what a same-line move actually needs — the income evidenced
   in the new role (a pay stub from the current employer, or a VOE) — rather than an explanation of a
   change of field.

## Behaviour change to know about

A borrower whose employment the application does not state moves from an AI `needs_review` to
`couldnt_check`. That is the honest reading — the rule cannot judge a job change it cannot see — but it
is a change, and it is why the tag fails closed to "unknown" rather than to "no".

On LF-XMB2 this leaves IN-7 on borrower 1 (PNC ended 2026-03-03, FNB started 2026-03-09 — a real change,
correctly surfaced) and removes it from borrower 2.

## Tests

- The recipe: both flags for "ended" (an end date, and `is_current: false`), a single current employer,
  every record ended, no records at all, and a non-borrower subject.
- The rule: a no-change borrower reaches `not_applicable` **with the reasoner never called**; a changed
  borrower is judged; an absent tag is `couldnt_check`.
- Fixtures at `test_income_family.py:412` and `test_income_family_eval.py` gain
  `income.has_job_change: yes`, deliberately, so they still exercise the armor they are about.

## Review — REVIEWED

Peer review of `b09c67ad` (second session). **The diagnosis and the design are right** — the scope
belongs in a tag read from the application, and the three judgement calls hold up under evidence. But
**the commit left CI red**: three tests failed, one of them on text a processor would have read. All
three are fixed here, along with one latent false negative in the recipe.

### CI was red on this commit

The narrower selection run for the ticket passed; the full `tests/verification/` tree did not. All three
are attributable to this commit — `tests/verification/rule_engine/` and `tests/verification/rules/` were
both green at `cf6c4da3` one commit earlier (1,316 passed, during the bug-015 review).

1. **`test_every_live_rule_reason_tag_has_a_curated_fact_label`** — the one that would have reached a
   processor. An applicability predicate IS a reason tag: when it is absent or "unknown" the rule
   abstains and `applicability.py` builds the sentence from `fact_phrase(tag_id)`. With no `_FACT_LABELS`
   entry, `fact_label` degrades to the humanized stem and IN-7's couldnt_check read *"the file does not
   clearly establish **the has job change**"*. That is precisely the drift this guard exists to catch,
   and it is the same defect class as bug-015's. Added as a question phrase, so `fact_phrase` drops the
   article: *"…does not clearly establish whether the borrower has changed jobs, so it is not known
   whether this requirement applies here."*
2. **`test_desired_state_shape`** — the pinned vocabulary count (264) against the new overlay tag (265).
   Bumped, annotated in the file's own convention.
3. **`test_lf6t3n_full_verdict_distribution_is_stable`** — exactly 2 rows moved `couldnt_check` →
   `not_applicable`, which is IN-7's new scoping working: LF-6T3N's two borrowers publish employer NAMES
   ONLY, so the recipe reads "no job change". satisfied/fired/needs_review are unchanged, so the ±2 is
   the whole movement. Pin updated with that reasoning recorded.

### Found and fixed: a silent false negative in the recipe

The row count was `if ended … elif is_current`, so a record stating **neither** flag counted as neither
current nor ended and vanished from both totals. A borrower with one ENDED employer beside one flagless
employer therefore read **"no"**, and IN-7 skipped a real job change in silence — this rule's own failure
mode, inverted. Now `else: current += 1`: every employment record on a 1003 is either former or current,
and "not stated as ended" is the honest reading of one that does not say. Ended-only still reads "no"
(nothing current), and LF-6T3N still reads "no" (nothing ended), so no verdict moves.

Not a hypothetical shape: `stated_employers.is_current` is nullable and its own column comment records
that every employer imported before LP-624 carried NULL, while `put()` omits a NULL — so those rows
reach the snapshot stating only a name, exactly as LF-6T3N's fixture still does. Two tests added.

### The four questions, answered against evidence

- **Ended-only → "no" (the judgement call): endorsed.** A termination with nothing current is IN-15's
  question, and calling it a job change would send IN-7 after an offer letter for a role the borrower
  does not have. The `else` repair above does not disturb it.
- **Fail-closed breadth: not a problem, measured.** Staging carries 13 borrowers and **all 13 have
  employer records**, so the `unknown → couldnt_check` path affects zero live borrowers today. For
  scale, IN-7 currently has 9 findings, all `needs_review`, across 8 files — this change moves real rows,
  but no file loses IN-7 for want of employment data.
- **The `is_current` parsing: correct for what the importer actually writes.** `parser.py` sets it from
  `EmploymentStatusType` ("Current" → True, "Previous" → False, anything else → None rather than
  guessing), and `mismo_section.put()` writes the bool, so the snapshot carries `"True"`/`"False"` —
  which the truthy set reads correctly, and a present-but-not-truthy value as ended. Staging confirms the
  population: 18 employer rows, **0 with a NULL `is_current`**, 5 with an end date, 13 flagged current.
  The only real gap was the flagless row, fixed above.
- **Application-only, never documents: endorsed, with one caveat worth recording.** IN-7's question is
  before-and-after and only the 1003 states the "before". The cost is that a job change evidenced by a
  VOE but omitted from the 1003 now reads "no" and IN-7 goes `not_applicable` — silently, not as an
  abstention. Acceptable (the application is the borrower's own declaration and the rule is about what it
  declares), but if a real file ever shows it, that is the shape to revisit.
- **The fixture edits do not weaken what those tests prove.** The eval fixture deliberately keeps the
  scope tag on the fail-closed half so the GATE is still what abstains — without it the assertion would
  pass for the wrong reason, one step earlier at applicability. That is the right call and the comment
  says so; `test_income_family.py` is the same shape.

Checks: `tests/verification/` — **2,688 passed, 0 failed** (before these fixes: 3 failed). The 41 errors
are the DB-backed suites erroring on connect; this machine has no Postgres and CI runs them. Ruff, ruff
format and mypy clean.
