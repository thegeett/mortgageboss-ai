# bug-017 — IN-6's finding named no document, and would not say which side was missing

- **Status:** Fixed
- **Date:** 2026-09-11
- **Found on:** staging `LF-XMB2`, reported by the processor: *"IN-6 why document reference is not
  present, as it is derived from some document only"*
- **Scope:** Backend — `tag_materialization/derived.py` (`_income_employer_coverage`)

## The report

IN-6 surfaced on LF-XMB2 with no source document:

> Confirm whether the Commonwealth Of Pennsylvania employer on the pay stub and W-2 is the same entity
> named differently, or obtain the missing document so both employers appear in both document types.

The processor's objection is exactly right: this rule's whole input is a comparison of the borrower's
**pay stubs** against their **W-2s**, so the documents are not merely knowable — they are the finding.
AS-8, on the same file and the same run, named its two bank statements.

## The cause

`produce_derived_tags` puts a recipe's **third** return element onto the tag's `source_facts`, which is
what eventually carries a finding's document links. A recipe returning two elements falls back to
`(subject_id,)` — and IN-6's subject is a borrower id, which resolves to no document at all.

`_income_employer_coverage` read the borrower's pay stubs and W-2s, matched their employer names, and
returned only `(value, reason)`. It knew the documents and dropped them. `_stmt_continuity` (AS-8) had
already established the opposite pattern: it returns the pair of statements that disagree.

## The fix

The recipe now tracks the documents behind each normalized employer name and returns them:

- **uncovered** — the documents stating the uncovered employer **first**, then the others it was
  compared against. The order matters: the first id becomes the finding's `source_document_id`, the one
  document the UI opens (established in bug-013's review), and that must be the document carrying the
  employer the sentence names.
- **covered** — every pay stub and W-2 whose employer was read.
- **one_sided / unknown** — nothing, deliberately: there was no comparison to point at, and empty is
  honest.

**The reason now names the side.** *"appears on one of the borrower's pay stubs / W-2s but not the
other"* left the processor to work out which was missing before they could act. On LF-XMB2 that is the
whole finding: `Commonwealth Of Pennsylvania` is on the W-2 while the pay stubs say `COPA Exec Off` — a
naming variance the normalizer cannot reduce, not a missing document.

## Not fixed here

The variance itself. IN-6 inherits IN-5's deterministic normalizers (casefold, punctuation, entity
suffixes) and deliberately does **not** invoke IN-5's AI fuzzy-residue judge; the recipe's own docstring
records that as a known limitation (LP-406-3). So `COPA Exec Off` vs `Commonwealth Of Pennsylvania`
still reads "uncovered" and still asks a human. Naming the side is what makes that answerable in one
glance; reusing the residue judge is a larger change — a recipe is synchronous and deterministic, and
one rule cannot read another rule's verdict.

## Tests

In `test_lp410_producers.py`, beside the existing coverage tests and modelled on AS-8's pair:

- uncovered names the documents it compared, with the uncovered employer's own document leading, and
  the reason names the side;
- covered names every document it read;
- one_sided names nothing (still a 2-tuple);
- **end to end through the real evaluator** — `materialize_tags` → `evaluate_rules(rule_ids=("IN-6",))`
  → `source_content_ids`, which is the only version that proves a processor sees it (LP-487's standing
  rule; the unit tests are a supplement, never a substitute).

Four existing call sites that unpacked two values now index instead.
