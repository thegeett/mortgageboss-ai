# bug-017 — IN-6's finding named no document, and would not say which side was missing

- **Status:** Fixed
- **Date:** 2026-09-11
- **Found on:** staging `LF-XMB2`, reported by the processor: *"IN-6 why document reference is not
  present, as it is derived from some document only"*
- **Scope:** Backend — `tag_materialization/derived.py` (`_income_employer_coverage`)

## The report

IN-6 surfaced on LF-XMB2 with no source document:

> Confirm whether the Commonwealth Of Pennsylvania employer on the pay stub and W-2 is the same entity
> named differently, or obtain the missing document so both employers appear in both document types.

The processor's objection is exactly right: this rule's whole input is a comparison of the borrower's
**pay stubs** against their **W-2s**, so the documents are not merely knowable — they are the finding.
AS-8, on the same file and the same run, named its two bank statements.

## The cause

`produce_derived_tags` puts a recipe's **third** return element onto the tag's `source_facts`, which is
what eventually carries a finding's document links. A recipe returning two elements falls back to
`(subject_id,)` — and IN-6's subject is a borrower id, which resolves to no document at all.

`_income_employer_coverage` read the borrower's pay stubs and W-2s, matched their employer names, and
returned only `(value, reason)`. It knew the documents and dropped them. `_stmt_continuity` (AS-8) had
already established the opposite pattern: it returns the pair of statements that disagree.

## The fix

The recipe now tracks the documents behind each normalized employer name and returns them:

- **uncovered** — the documents stating the uncovered employer **first**, then the others it was
  compared against. The order matters: the first id becomes the finding's `source_document_id`, the one
  document the UI opens (established in bug-013's review), and that must be the document carrying the
  employer the sentence names.
- **covered** — every pay stub and W-2 whose employer was read.
- **one_sided / unknown** — nothing, deliberately: there was no comparison to point at, and empty is
  honest.

**The reason now names the side.** *"appears on one of the borrower's pay stubs / W-2s but not the
other"* left the processor to work out which was missing before they could act. On LF-XMB2 that is the
whole finding: `Commonwealth Of Pennsylvania` is on the W-2 while the pay stubs say `COPA Exec Off` — a
naming variance the normalizer cannot reduce, not a missing document.

## Not fixed here

The variance itself. IN-6 inherits IN-5's deterministic normalizers (casefold, punctuation, entity
suffixes) and deliberately does **not** invoke IN-5's AI fuzzy-residue judge; the recipe's own docstring
records that as a known limitation (LP-406-3). So `COPA Exec Off` vs `Commonwealth Of Pennsylvania`
still reads "uncovered" and still asks a human. Naming the side is what makes that answerable in one
glance; reusing the residue judge is a larger change — a recipe is synchronous and deterministic, and
one rule cannot read another rule's verdict.

## Tests

In `test_lp410_producers.py`, beside the existing coverage tests and modelled on AS-8's pair:

- uncovered names the documents it compared, with the uncovered employer's own document leading, and
  the reason names the side;
- covered names every document it read;
- one_sided names nothing (still a 2-tuple);
- **end to end through the real evaluator** — `materialize_tags` → `evaluate_rules(rule_ids=("IN-6",))`
  → `source_content_ids`, which is the only version that proves a processor sees it (LP-487's standing
  rule; the unit tests are a supplement, never a substitute).

Four existing call sites that unpacked two values now index instead.

## Review — REVIEWED

Peer review of `9ac78f5d` (second session). **The fix is correct and the ordering claim holds.** CI is
green on this commit — the full `tests/verification/` tree passes here as well (the 49-vs-41 error count
is only `test_projection_db.py`, which one run ignored and the other did not; all of them are DB-backed
suites erroring on connect). One branch was wrongly excluded, and it is the branch where the missing link
mattered most; fixed here with two tests.

**Verified independently:**

- **The bridge reaches the finding because IN-6 is DETERMINISTIC.** This was worth checking before
  anything else: a recipe's third element becomes `tag.source_facts`, and only
  `deterministic._named_documents` lifts those into `source_content_ids` — `judgment.py` never sets that
  field at all (established in bug-013's review). IN-6 declares a `deterministic:` block with
  `income.employer_coverage` in `load_bearing_tags`, so the ids travel. Had it been a judgment rule this
  fix could not have reached a processor, end-to-end test or not.
- **The ordering invariant is sound, and the sentence and the link cannot disagree** (the first
  question). `uncovered` is a symmetric difference, so an uncovered key exists in exactly ONE side's
  dict; `stated_by[key]` therefore holds only that side's documents, and `shown`, `side` and
  `counterpart` are all derived from that same key. `stated_by[key]` cannot `KeyError` — it is populated
  in the same loop that fills the buckets. Unreadable documents are excluded from `compared`, so "every
  document it read" is literally true.
- **Nothing else unpacks the recipe** (the fifth): only the tests call it, all four now index, and
  `produce_derived_tags` handles both arities by length. The annotation matches `_stmt_continuity`.
- **The new text passes the guards it should** (the fourth): `derived.py` IS in LP-530's
  `_REASON_MODULES`, so the machinery scan covers this sentence, and the satisfied-as-absence guard is
  untouched because the covered text did not change.
- **"covered" naming documents is fine** (the second): IN-6 declares no `collapse_uniform`, so there is
  no loan-level row that would union them, and links on a satisfied finding are additive — a processor
  who opens a pass sees what it was concluded from.

**Found and fixed: the `unknown` branch named nothing, and it is the one that most needed a name.**

The third question splits in two, and the answer is right for one half only. `one_sided` never reaches a
finding at all — IN-6's applicability makes it `not_applicable` — so naming nothing there is correct.
But `unknown` DOES reach a processor, as a `couldnt_check` (§8 Tab 1, via the same applicability
predicate), and that branch is reached ONLY when an employer name could not be read: with both sides
present and every name readable, both buckets are non-empty. So the recipe knew exactly which document
defeated it and dropped it, leaving the finding to say *"an employer name on ONE of this borrower's
income documents could not be read"* with no way to tell which — the processor's original complaint on
this very ticket, surviving in the branch where the link is the whole answer.

The unreadable document now leads, then what was read. Two tests: the recipe directly, and end-to-end
through `evaluate_rules`, because a `couldnt_check` takes a DIFFERENT path to the finding than the
uncovered case (it terminates at applicability rather than at an outcome) — that path builds its result
with the subject's load-bearing tags too, which is what carries the ids.

**Observations, deliberately not changed:**

- When BOTH sides carry uncovered employers, the sentence still names only `uncovered[0]` while the links
  name everything. The prose under-reports; it did before this commit too, and widening it is a wording
  decision for the domain expert rather than a review fix.
- `bucket[key] = original` keeps the LAST rendering read when two documents normalize equal, so the
  displayed spelling is arbitrary between them. Harmless — they are the same employer by construction.

failed** (41 errors, all DB-backed suites with no Postgres on this machine; CI runs them). Ruff, ruff
format and mypy clean.
