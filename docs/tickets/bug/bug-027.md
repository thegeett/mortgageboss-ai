# bug-027 — the rule→tag edge table disagrees with 67 of the 84 specs

- **Status:** Analysed — the fix needs a decision about what the file is *for* (the backlog already
  says so; see *Open decision*)
- **Date:** 2026-09-11
- **Found on:** the repo — no staging needed, and none was used
- **Scope:** `verification/rules/rule_tags.csv` + `fact_tags.csv` (both GENERATED from
  `docs/snapshot-fact-tags.xlsx`), their projection into the DB, and `rules/accessors.py`

## The report, and what measuring it turned it into

Reported as: *`fact_tags.csv` lists AS-5 as a reader of `txn.has_identified_source`, which cannot be
true.* It is true that it cannot be true. AS-5 is `per_document` over `gift_letter` and its spec
references exactly one fact tag:

```
rule_tags.csv          AS-5 -> txn.apparent_category   ✓ real
                       AS-5 -> txn.counterparty        ✗ the spec never mentions it
                       AS-5 -> txn.has_identified_source ✗
                       AS-5 -> txn.source_reference    ✗
```

But AS-5 is not a bad row; it is one instance of a systematic drift. Comparing **every** spec's
referenced tags (`load_bearing_tags`, `gated_tags`, `reasoned_over`, and applicability predicates) with
the table's edges:

| | |
|---|---:|
| specs on disk | 84 |
| specs whose tag set disagrees with `rule_tags.csv` | **63** |
| edges a spec needs that the table does **not** record | **101** |
| edges the table records that the spec does **not** reference | **68** |
| edges that are the rule's own OUTPUT tag (a different relation, not an error) | **1** |
| total edges in the table | 214, across 109 rules |

That 214 is exactly the figure published in `docs/rule-engine.md` ("Rule → tag edges | 214"), measured
2026-08-21. The documentation counts the file correctly; the file describes the rules incorrectly.

**The definition, stated because the numbers depend on it more than on the arithmetic.** An edge is a
tag the rule **reads as an input**: collected from `load_bearing_tags`, `gated_tags`, `reasoned_over`,
and every predicate naming one (`tag:`, `loan_tag:`, `gather_tag:`). Excluded: `output_tag` (written,
not read), `explain_by` (guidance rendering rather than an evaluation input), and
`document.document_type` (dispatch, not a fact tag). A tag id must be dotted, so an enum value cannot
masquerade as one.

**Two witnesses on the arithmetic.** These figures were derived twice, by two independently written
implementations. The first pass disagreed — 67/98/75 — because it missed `gather_tag:` (5 uses, the
consistency rules) and `loan_tag:` (1 use). That single `loan_tag` omission mattered on the flagship
rule: AS-1 references `dti.qualifying_income_monthly` through `{loan_tag: …}`, so the first pass
reported a real edge as spurious. Under-collecting spec tags deflates "missing" and inflates "spurious"
by the same tags, which is exactly the shape the two results differed by. Hand-checked on AS-5 both
times: four edges recorded, one real, three spurious.

**One witness on the definition, which is the weaker point and worth stating.** Once the second
implementation adopted the first's definition, the arithmetic had two witnesses and the *definition*
had one — and a shared definition is precisely what made bug-013's exact agreement worthless. Two
attacks were run on it rather than a third re-derivation:

- **`output_tag` is a different relation, and the table holds exactly one of them.** 19 specs declare an
  output tag; exactly one such pair appears in the CSV — `(OC-2, occupancy.reasonable)`, OC-2's own
  judgment output. Excluding output tags is right for a *dependency* relation, but it means that row is
  reported as "spurious" when it is really a fact of a different kind. Hence 68 genuinely unreferenced
  plus 1 output edge. It is not a convention — it is a single hand-authored row encoding a different
  relation from the other 213, which is its own argument for generating the table: a generated relation
  would have to declare which direction it means.
- **A key-agnostic sweep for a missed construct.** Every string in every spec that equals a known tag id
  was collected with the key path it sits under, and diffed against what the collector finds. The only
  key it misses is `output_tag`. So there is no fifth construct naming a tag — under the caveat that
  this matches against *known* tag ids, and the separate check below covers what that caveat hides.

**One guard worth copying, because it is the only check here a stranger could run.** An early pass at
the vocabulary comparison reported 73 spec tags as missing from the vocabulary — including the two AS-6
gates on. It was wrong: `vocabulary_extra.yaml` is `{tags: {…}}`, one top-level key, so the reference
set had been built with a single member (`"tags"`) and everything failed membership against it. The
counts above (143 / 122 / 265) are stated for the same reason, and this ticket's own "144" survived one
revision before the independent count caught it. **Assert the SIZE of a reference set before testing
membership against it** — `assert len(vocab) > 200` fires instantly on a set of one, needs no domain
knowledge, and does not depend on a second reader noticing the answer is implausible. It is the same
idea as "say what one row represents", one level up.

## What is and is not broken today

**Nothing in evaluation.** This is pinned, deliberately, by
`test_eval_path_does_not_read_rule_tags_csv`: it reads the source of `deterministic`, `judgment` and
`registry` and asserts the string `rule_tags` appears in none of them, with the note *"The drift in
`rule_tags.csv` is planning-only: the evaluator reads each spec's `load_bearing_tags`, never the CSV."*
So no verdict, gate or finding is wrong because of any of this, and the 67 disagreements cost a
processor nothing today.

**But the table is not inert:**

1. **It is projected into the database.** `projection.py` mirrors it faithfully into the `rule_tags`
   table — inserting, updating and deleting to match — so every wrong edge becomes a wrong row of
   production reference data.
2. **It is exposed as the future runtime seam.** `accessors.py` provides `tags_for_rule` and
   `rules_using_tag` over that table and describes itself as *"the runtime read seam the engine will use
   later"*. Today only a test calls them. The drift is safe exactly until something does.
3. **It is quoted as a statistic**, in the docs above.

**The failure mode is the one that hurts most**, and a colleague put it exactly right while reviewing an
unrelated metric: if you compute "which tags does this rule gate on" from the projection rather than
from the spec, the answer is silently wrong and *looks identical* to the right one.

### The direction that is unambiguous

The 68 "spurious" edges are not all errors. Some are deliberate — FR-5's `txn.implies_obligation` row is
kept knowingly, and FR-5's spec says why in its own header: the tag's question *is* the rule's question,
so consuming it would be two AI layers asking the same thing, and *"the row stays because
`rule_tags.csv` is generated from the vocabulary spreadsheet and is the domain expert's artifact to
change."* Others may be forward-looking plans.

**The 101 MISSING edges have no such defence.** A rule that gates on a tag the table does not record
breaks the table's own stated purpose — planning which rules unblock when a tag lands. FR-5 is the
clearest case: the table records `counterparty`, `implies_obligation` and `is_recurring`, while the
rule actually gates on `is_money_in`, `apparent_category`, `is_recurring` and `stated_liability_match`.
Three of its four real dependencies are invisible, and one recorded dependency is disavowed in the
spec. Anyone asking "what does FR-5 need?" from this table gets the wrong answer in both directions.

**AS-1 is the case that should decide this**, because it is the flagship rule, it is live, and it fails
in both directions at once:

| | |
|---|---|
| the table records | `income.qualifying_monthly`, `txn.apparent_category`, `txn.source_reference` — none of which AS-1's spec names |
| the table omits | `txn.source_strength`, which AS-1 genuinely gates on |

And `income.qualifying_monthly` is not merely unused by AS-1 — it is a tag this repo has already
recorded as dead for this purpose. LP-516 §28-35 says AS-1 reads `dti.qualifying_income_monthly` and
that *"`income.qualifying_monthly` is known-degraded and is not in live use for this purpose"*; LP-343
records it as underspecified; and `derived.py:487` flags its own vocabulary row STALE. So the table
points the flagship live rule at vocabulary the codebase knows is degraded, while hiding a tag it
actually depends on. Two prior reviews (LP-490, LP-491) each corrected one instance of this shape.
Nobody measured the population.

### Seven of the 101 cannot be authored at all

Not every missing edge is an oversight. Seven name a tag that is **absent from the vocabulary** — 143
rows in `fact_tags.csv` plus 122 in the `vocabulary_extra.yaml` overlay, 265 in all — and
`check_consistency` rejects any edge whose tag is not in that set (`load_desired_tags` builds it from
both). Adding these rows would fail the projection outright:

| edges | why the tag is absent from the vocabulary |
|---|---|
| `AS-1 → txn.source_strength`<br>`AS-12 → txn.source_strength` | A **known vocabulary orphan**: produced by Stage B (`services/tag_correlation.py`), consumed by live AS-1 (`rule_engine/as1.py`, `services/rule_findings.py`), never given a `fact_tags.csv` row. Already recorded — `test_vocabulary_orphans.py`'s D4 seam map lists it as a case that guard deliberately *cannot* see, "because this guard scans the vocabulary". |
| `CR-1`, `CR-6`, `CR-8`, `CR-12`, `DT-8` `→ liability.source` | **Not a vocabulary tag at all, by design**: a synthetic marker attached at enumeration time (`LIABILITY_SOURCE_TAG`, `rule_engine/enumerators.py`) so a summing rule can filter by source (ADR-374). |

So for these seven the table cannot record the truth *even in principle*. That is a different failure from
the other 94 — not "nobody updated the sheet" but "the sheet has no way to say this".

⚠️ **They are one bucket with two different right answers, and conflating them would cause a wrong fix.**
The two groups fail the same check for unrelated reasons:

- **`txn.source_strength` SHOULD have a vocabulary row.** It is a genuine orphan — Stage B produces it,
  live AS-1 consumes it, and nothing declares it. The fix is to give it its row, after which both edges
  become ordinary authorable ones.
- **`liability.source` should almost certainly NOT be in the vocabulary.** It is synthetic by
  construction: attached to subjects at enumeration time so a summing rule can filter by source
  (ADR-374). Adding it to `fact_tags.csv` to silence the check would put a marker that no producer
  materialises into the domain expert's tag vocabulary — the wrong fix, and one this note exists to
  prevent. The open question for these five is whether a synthetic marker belongs in a rule→tag relation
  at all, which is a question about the relation, not about the vocabulary.

Either way it sharpens the recommendation rather than weakening it: generating the edges would emit all
seven and `check_consistency` would reject all seven, forcing both questions into the open instead of
leaving them as silent absences.

## What now stops it getting worse

`tests/verification/rules/test_fact_tags_files.py` — the file that already guards these generated
CSVs — gains two checks:

- **`test_rule_tags_csv_drift_from_the_specs_does_not_grow`** pins the disagreement as a baseline
  that fails in *either* direction: a new spec drifting from the table is what it exists to catch,
  and a correction that shrinks the gap must lower the baseline in the same commit, so nobody can
  quietly widen it back.
- **`test_the_flagship_rules_dependency_is_recorded_wrongly`** pins AS-1's two specific wrong facts,
  because it is the row most likely to mislead anyone reading dependencies out of the projection.

**Its baselines are 96 and 69, which are the figures above counted differently — reconciled here so
the two never read as a contradiction:**

| | ticket | guard | why |
|---|---:|---:|---|
| missing | 101 | **96** | the guard drops the five `liability.source` edges: they are unauthorable, so demanding them would be asking for an impossible edit |
| spurious | 68 (+1 output) | **69** | the guard counts raw rather than special-casing the one output edge, so it would still notice if a second appeared |

This is a baseline, not an approval. It makes the drift visible and bounded; it does not decide what
the file is for, which is still the open question below.

### A third instance, found while working an unrelated ticket

`rule_tags.csv` lists **CR-1 → `txn.is_recurring`**, and no CR-1 spec references that tag. FR-5 is the
only spec that reads it.

Worth recording because of *how* it surfaced: bug-026 needed to know the blast radius of changing the
recurrence tag, took the answer from this table, and would have reported "FR-5 and CR-1" — overstating
it by one rule and making a change look twice as risky as it is. That is the failure mode this ticket
describes, caught in the act, on the third ticket in a row:

| ticket | what the table told it | the truth |
|---|---|---|
| bug-026 (draft) | the Stage-A prompt gates **AS-1** | AS-1's spec never references `txn.apparent_category` |
| bug-026 (again) | `txn.is_recurring` is read by FR-5 and **CR-1** | FR-5 only |
| bug-025 / this ticket | AS-5 reads `txn.has_identified_source` | AS-5 reads one tag, and it is not that one |

None of these was a *verdict* being wrong — the evaluator reads the specs. Each was a **scope estimate**
being wrong, which is exactly what the table is used for and exactly what it cannot be trusted for.

CR-1 carries a second spurious `txn.*` row while we are here: `CR-1 → txn.implies_obligation`. That tag
is attributed to **both** CR-1 and FR-5, and neither reads it — FR-5's spec header disavows it in as
many words ("`txn.implies_obligation` IS DELIBERATELY NOT READ, though rule_tags.csv still lists it
against FR-5"), and `CR-1.yaml` does not mention it at all. So one tag has two wrong consumers, one of
which documented its own wrongness rather than correcting it, because the row lives in the domain
expert's spreadsheet. That is the clearest single illustration of why generating the edges is the fix:
the spec author knew, wrote it down, and still could not change the table.

## Why nothing in the repo catches it

Two guards look like they would and neither can:

- **`test_projection_counts_match_files` asserts `len(rule_tags) == 214`** — a ROW COUNT. It pins how
  many edges exist, never whether any of them is right. It passes identically whether the 214 edges
  describe the specs or contradict them.
- **`check_consistency` validates each edge against the vocabulary** — that the `rule_id` is in
  `rule_kinds.csv` and the `tag_id` is in `fact_tags.csv`. Existence only. A spurious edge pointing at a
  real tag satisfies it completely.

So a wrong edge passes every check in the repo, which is how 63 specs drifted in silence. It is also the
strongest argument for generating the edges: a generated relation makes the count assertion *meaningful*
rather than tautological, because the number would then be derived from the same source it is checked
against.

## A second staleness in the same artifact

`fact_tags.csv` carries per-tag metadata that has drifted the same way. `txn.is_recurring` is recorded
as `produced_by=AI`, `AI-at-rule-time` — but LP-546 replaced that with a **deterministic** producer
(`txn_is_recurring` in `derived.py`, run as a stage in `services/tag_correlation.py`), whose whole point
was that recurrence is "a COUNT — no model, no calibration round". The vocabulary still describes a
model call that no longer happens.

Its row also carries a **readers column** — `"FR-5, CR-1"` — which is the rule→tag relation again, hand
authored in a second place in the same file, and drifting for the same reason (`fact_tags.csv` names
AS-5 as a reader of `txn.has_identified_source`, which is where this ticket started). If the edges are
generated, that column should go with them rather than survive as a third copy of the same claim.

### And `produced_by` is wrong on 12 rows, not one

`txn.is_recurring` is not an isolated case. Comparing `fact_tags.csv`'s `produced_by` against the mode
each tag is actually declared with in `tag_production.yaml`, **12 of the 82 tags present in both files
contradict each other**:

| tag | the vocabulary says | the producer is |
|---|---|---|
| `property.type` | ai | derived |
| `property.appraised_value` | ai | parsed |
| `property.address_normalized_match` | ai | derived |
| `occupancy.stated` | parsed | derived |
| `housing.hoa_monthly` | ai | derived |
| `housing.insurance_monthly` | ai | derived |
| `housing.taxes_monthly` | parsed/ai | derived |
| `liab.is_disputed` | ai | derived |
| `liab.monthly_payment` | parsed/ai | parsed |
| `condo.reserve_pct` | ai | parsed |
| `aus.recommendation` | parsed | derived |
| `stmt.page_count_present` | derived | parsed |

**The method matters, because the obvious version of this count is wrong by roughly tenfold.** Only the
**82 tags named in both files** are comparable. A tag in `tag_production.yaml` and absent from
`fact_tags.csv` is not a contradiction — the CSV is the *domain* vocabulary and most derived tags were
never in the spreadsheet at all. Scoring absence as mismatch turns 12 into ~80 and reads as a
catastrophe rather than a drift. *(That trap was hit and discarded during review; recording it so the
number is not "corrected" upward later by someone repeating it.)*

**And 12 is the STRICT count — the rule belongs beside the number.** Two rows in the comparable set
carry a hybrid `"parsed/AI"` in the vocabulary, so the comparison needs a stated convention:

| rule | count | |
|---|---:|---|
| **strict** — `produced_by` must equal the declared mode exactly | **12** | the figure above |
| union — a hybrid is satisfied by *either* half | 11 | `liab.monthly_payment` (`parsed/AI` vs declared `parsed`) drops out |

`housing.taxes_monthly` (`parsed/AI` vs `derived`) contradicts under **both** rules, so it stays either
way. Strict is the right convention here — a vocabulary that says a tag is "parsed *or* AI" when the
producer is unambiguously one of them is still misdescribing it — but the point is to state the rule, not
to win it: a bare "12" invites someone to reach 11 for a perfectly defensible reason, which is the
absence-is-not-contradiction trap one level down.

**Why the two columns are comparable at all**, since this is the first objection a reader will raise:
`produced_by` could plausibly name *where a value comes from* while `mode` names *the mechanism* — two
axes, in which case both counts would measure the adjacent question. They are the same axis.
`generate_fact_tags.py` only copies the column out of the xlsx, and `declarations.py:203` uses
`produced_by` as the overlay's own **mode** slot, defaulting to `"derived"`. So the 12 is a real
disagreement rather than a category error.

**It is inert at runtime, and that bounds the severity honestly.** Nothing branches on the CSV column:
`generate_fact_tags.py` writes it, and every consumer that cares reads the **runtime**
`Tag.produced_by` that the producer stamps — `gate.py:48` is the clearest case, gating explanation
reuse on `tag.produced_by is not TagProducedBy.DERIVED`, which the recurrence stage sets correctly to
`DERIVED`. So no verdict, gate or finding is wrong because of these 12 rows.

What it costs is the same thing the edges cost: **anyone reasoning about the system from this file gets
the wrong answer.** "Is `property.type` an AI perception or derived code?" decides whether it needs a
calibration round, and the vocabulary answers it wrongly. Which widens the conclusion below — this is
not one stale column to patch, it is **every derived column in a hand-authored artifact**, and the same
generation fixes all of them at once.

## Why it cannot simply be corrected

`rule_tags.csv` and `fact_tags.csv` are **generated** from `docs/snapshot-fact-tags.xlsx` by
`app/scripts/generate_fact_tags.py`, and `test_generated_csvs_are_committed_and_current` asserts the
committed CSVs match what the xlsx generates (it passes today). So a hand-edit to either CSV is
reverted by the next regeneration and fails that test. `vocabulary_extra.yaml` cannot help either —
`declarations.py` raises `DeclarationError` if an overlay tag duplicates a `fact_tags.csv` tag,
deliberately, so the two readers can never disagree about a tag's domain.

**The correction therefore lives in a binary spreadsheet the domain expert authors**, which is not
something to edit quietly — the same call as not restarting staging: the artefact has an owner, and it
is not us.

## Open decision — what is this file for?

The backlog already asks this, in as many words, and independently distrusts the table:

> ⚠️ **Lineage under-states judgmental rules** — PE-4's lineage lists only `program.type` while the
> rule is an `ai_judgment`. **Do not size these from `rule_tags.csv`.** *(LP-494)*

> ⚠️ The header is the wrong relation anyway … "which rules unblock together" is rule→tag, already in
> `rule_tags.csv`. **Decide what the file is *for* first.** *(LP-496)*

So this ticket is not reporting an unnoticed bug; it is measuring one the repo already suspected, and
the measurement says the drift is not marginal. The options:

1. **Derive the edges from the specs instead of authoring them.** A spec's `load_bearing_tags` is the
   rule→tag relation in executable, tested form; the xlsx sheet is a planning artifact that has drifted
   from it. This splits the two artifacts along their real ownership: the **vocabulary** (what a tag
   means, its allowed values, how it is produced) is genuine domain knowledge and stays hers; the
   **edges** are a fact about code. "AS-1 reads `txn.amount`" is discoverable by parsing the repo and is
   already authored in executable, tested form — it is not something a human should be maintaining by
   hand in a spreadsheet at all. Framed correctly, this **removes** an artifact the domain expert should
   never have had to maintain rather than taking one away from her. Recommended.
2. **Add a consistency check** comparing spec-referenced tags to the table, as `check_consistency`
   already does for unknown rules and tags. It would fail on 67 rules today, so it needs a baseline or
   a correction first — but it is what would have caught this at the point of drift.
3. **Retire the table**, if the specs carry the truth and nothing is to read it.
4. **Keep it as planning and say so loudly** — rename it, or document at the top that it is
   aspirational, so nobody computes a dependency from it.

Whichever is chosen, the `accessors.py` seam should not be wired to the table until it agrees with the
specs, because that is the moment the drift stops being free.
