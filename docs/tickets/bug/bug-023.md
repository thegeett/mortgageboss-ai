# bug-023 — ID-3 and ID-8 asked for documents the file was already holding

- **Status:** Fixed
- **Date:** 2026-09-11
- **Found on:** staging `LF-XMB2`
- **Scope:** Backend — `snapshot/traversal.py` (one shared predicate),
  `rule_engine/consistency.py` (ID-3's abstention), `rules/specs/ID-8.yaml` (its fix wording),
  `tag_materialization/derived.py` (ID-5 moved onto the shared predicate)

## The report

The other half of bug-020. LF-XMB2 carries four documents the classifier could not identify — including
a **driver's licence** and an **EAD card** — and two more rules spoke as though they were not there:

> **ID-3:** *"Obtain a second document stating Dare Odubote's date of birth. Only one document in the
> file shows the date of birth."* — the licence would have been the second.
>
> **ID-8:** *"Obtain Dare Odubote's identity document — permanent resident card, unexpired visa with
> work authorization, or EAD…"* — the EAD card is in the file.

bug-020 fixed exactly this for ID-5 and deferred these two, because each lives in a different layer.

## The cause

The same one in both places: a rule that looks for a document **type** skips an unclassified file
exactly as if it were absent. ID-3's gather filters to sources that state the fact, so an untyped
licence never joins the comparison and `len(gathered) < 2` reports one source — true of what could be
**read**, not of what the file **holds**. ID-8 never sees documents at all; its fix text is fixed
wording in the spec.

## The fix

1. **One shared predicate.** `traversal.unclassified_documents(snapshot)` returns the ids of documents
   nobody has identified. `_UNKNOWN_DOC_TYPE` was already declared in three modules (`ai.py`,
   `subjects.py`, `derived.py`) and bug-020 added a fourth copy inline; ID-3 would have made five. ID-5
   now calls the shared one, so the count that reaches a processor has a single definition.
2. **ID-3 says whether the second source may already be in the file** — *"; 4 document(s) in the file
   are not identified yet and may state it — identify those first"*, appended to the message.
3. **ID-8's fix text** ends *"…and check the file's unidentified documents first: one of them may
   already be it."*

## The line this does not cross

The clause goes in the **message** only, never in `requested_documents`. That string is borrower-facing
— its own comment records that Phase 4 shows it verbatim, and it deliberately names no document type,
because the borrower has no way to know which of their papers carries a date of birth. *"Identify the
untyped files"* is an instruction to the **processor**; asking a borrower to do it would be asking them
to do our filing.

## Tests

- the predicate: an untyped document and a `None`-typed one both count, a classified one does not, and
  an absent documents section returns nothing rather than claiming there are no untyped files;
- ID-3: the clause appears when the file holds unidentified documents, is absent when it does not, and
  `requested_documents` is unchanged in both cases — the borrower-facing string stays clean;
- ID-5 still produces the same sentence it did after bug-020, now via the shared predicate.

## Review — REVIEWED

Peer review of `d33200e7` (second session). **The predicate, its placement and the borrower-facing line
all hold.** CI is green (2,748 passed, 0 failed here too). One live defect found and fixed — in the half
this ticket flagged as "check it reads well", where staging says it does not.

### Found: ID-8's sentence is wrong on 4 of its 9 live findings

The clause was appended unconditionally: *"…and check the file's unidentified documents first: one of
them may already be it."* Spec text for a judgment rule cannot read the snapshot, so it says that on
every file — including the ones holding nothing unidentified. Measured:

| rule | outcome | findings | files | on files WITH untyped documents |
|---|---|---:|---:|---:|
| **ID-8** | needs_review | 9 | 8 | **5** |
| ID-3 | couldnt_check | 9 | 8 | **5** |
| ID-2 | couldnt_check | 1 | 1 | 0 |
| ID-1 / ID-4 / IN-5 | *(no couldnt_check rows at all)* | — | — | — |

> ⚠️ **"4 of 9" is rows-across-runs, not findings.** `readonly.findings` accumulates per verification
> run and the query above filtered on none of it. What survives the correction is the part that matters:
> the split is by FILE — 5 of the 8 files carry an untyped document and 3 do not — so an unconditional
> sentence is wrong on whole files regardless of how many runs each has. The defect and the fix stand;
> the ratio is pending a recount on a latest-run basis.

So on **4 of 9** ID-8 findings a processor is told to go and check documents that do not exist — the
same species as the sentences bug-015 and bug-020 removed, arriving through the one path that cannot
count. Fixed grammatically rather than with a count, since the guidance layer only interpolates
`reasoned_over` tags: *"If the file holds documents that have not been identified yet, check those
first — one of them may already be it."* True on both kinds of file, and pinned with a note in the test
module so it cannot quietly revert to the imperative.

### The wider behaviour change, measured rather than estimated

The clause sits in the generic `len(gathered) < 2` branch, so it is available to every consistency rule
— right, and the table above shows what that means today: **ID-3 is the only rule with live abstentions
of this shape** (5 of its 9 gain the clause), ID-2 has one on a file with no untyped documents, and
ID-1, ID-4 and IN-5 currently produce none at all. So the live blast radius is 5 findings on 5 files,
and the generality is latent rather than speculative. It is also correct in principle: the sentence says
"may state it" about whatever fact the rule gathered, which reads as well for IN-5's employer names as
for ID-3's date of birth. Stating the number is what makes the scope claim checkable, which is the only
thing the ticket was short of.

### The other questions

- **Q1: the line is not crossed, and the branch is clean.** `requested_documents` in that branch is
  built solely from `fact_label(con.gather_tag)` plus the enum label — the clause is appended to the
  MESSAGE argument only, and nothing else there carries processor vocabulary. On whether *"identify
  those first"* suits a processor who may not classify documents themselves: it is the same instruction
  bug-020 shipped for ID-5 and the same one the consolidated UNIDENTIFIED-DOCUMENTS finding already
  gives ("set the document type, or re-upload a clearer copy"), so the vocabulary is consistent with
  what this product already asks of that reader. If it is wrong it is wrong in three places, which is a
  wording decision for the domain expert rather than a defect here.
- **Q3: leave the three local sentinels.** Unifying them touches `ai.py`, `subjects.py` and `derived.py`
  for zero behaviour change, and the shared predicate already covers both callers that put a COUNT in
  front of a processor — which is where drift would be visible. Worth naming the trigger rather than the
  preference: unify when a third such caller appears, or the moment the classifier's sentinel stops
  being the literal string `"unknown"`, because that is the change four definitions would survive
  unevenly.
- **Q4: file-wide is right for ID-3 too, and for the same reason re-derived rather than inherited.** An
  untyped document usually carries no `belongs_to`, so a borrower-scoped count is 0 in exactly the case
  the clause exists for. The per-borrower consequence is that on a two-borrower file both findings cite
  the same untyped documents, one of which may be the other borrower's licence — acceptable only because
  the wording is conditional ("may state it") rather than an assertion of ownership. That conditionality
  is doing real work in both halves of this ticket.
