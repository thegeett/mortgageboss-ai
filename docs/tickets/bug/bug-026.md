# bug-026 — a cash withdrawal has no category, and `unknown` means three different things

- **Status:** Analysed — **no code change can name the missing category.** That much is closed: the
  floor has no value to resolve to, and the scope shortcut is forbidden by contract. Two things remain
  open and neither is "nothing": a vocabulary value, which lives in the domain expert's spreadsheet,
  and a larger design question of our own about where an honest abstention surfaces — which *is* code,
  just not code that belongs to this ticket.
- **Date:** 2026-09-11
- **Found on:** staging `LF-XMB2`, reported as "FR-5's category enum has no cash/card-purchase value"
- **Scope:** Backend — the tag vocabulary (`fact_tags.csv`, generated), the Stage-A prompt
  (`tag_production.yaml`), or a deterministic floor in code. **Not** `FR-5.yaml`, which needs no change.

## The report, half-corrected

`txn.apparent_category`'s twelve values are: `payroll`, `transfer_own`, `transfer_third_party_in`,
`transfer_third_party_out`, `debt_payment`, `gift`, `loan_proceeds`, `refund`, `interest`, `fee`,
`vendor`, `unknown`.

**The card half of the report is wrong.** The Stage-A prompt defines `vendor` as "a purchase or a
payment for goods or services — INCLUDING a recurring one: insurance premiums, utilities,
phone/internet, subscriptions, memberships, tuition". A debit-card purchase has a home.

**The cash half is right.** An ATM withdrawal is not a payment to anyone: no payroll, no counterparty,
no goods or services, not a transfer to a named party. It fits none of the eleven real values, so it can
only be recorded as `unknown`.

The prompt itself shows the gap is known on one side and not the other — when telling the model to
return a null counterparty it names "a fee, **a cash withdrawal**, an interest credit". The case is
contemplated for `counterparty` and homeless in `apparent_category`.

### ⚠️ And the live abstentions are mostly NOT about cash

FR-5 produces **30 `couldnt_check` rows across 5 files** on the latest run per file. Reading their
load-bearing tags, they split exactly in half:

| what abstained | rows |
|---|---:|
| `txn.apparent_category = unknown` — this ticket | **15** |
| `txn.stated_liability_match = unknown`, with a good `debt_payment` category | **15** |

So this ticket's mechanism accounts for half the abstentions, not all of them; the other half is a
different missing fact and is not addressed here.

**And within those 15, cash is one case in seven — measured, not estimated.** Reading the `txn.amount`
and `txn.date` off each abstention's own load-bearing tags, the 15 findings come from only **7 distinct
transactions**:

| what the transaction is | distinct transactions | findings |
|---|---:|---:|
| a payment to an **unnamed account** (`ACCT# 0586`, `CRD 2060`) | 4 | 11 |
| a **generic** "does not clearly establish the … category" message | 2 | 2 |
| an **ATM withdrawal** ($500, 2026-03-16) | **1** | 2 |

Two things fall out of that table, neither of which was the reported defect:

**The 15-from-7 ratio is duplicate-document noise wearing category noise's clothes.** One transaction
produces three findings because the statement it sits on is on the file three times. So part of what
looks like a vocabulary problem is a document problem.

⚠️ *This sentence used to say "bug-025 showing through", and that attribution was wrong — corrected
when LP-1001 tried to lean on it.* bug-025's guard is in `all_list_rows`, which gathers **list rows**;
a transaction subject comes through `all_transactions` (`traversal.py:29`) and never touches it. The
pass that governs these findings is **bug-021**'s `_collapse_duplicate_transactions`
(`verification_run.py:846`), which runs unconditionally at `:1427` and was therefore already live when
these 15 were measured. It deliberately does **not** merge rows whose verdict or load-bearing tag values
differ (`:902`, `:904`) — so the multiplicity that survives here is the signal that pass exists to
preserve, not a defect awaiting a fix. The cause is right; only the ticket number was wrong.

**And one of the two generic rows is the transaction that started all of this**: `$24.34` on
2025-12-26, whose message still reads *"the file does not clearly establish the **deposit** category"* —
for a withdrawal. That wording was fixed in bug-015; staging still shows the old text because nothing
from this series is deployed. Worth knowing before anyone reads that message as a live defect.

That distinction matters, because **for an unnamed payee `unknown` is the honest answer**, not a defect.
The description genuinely does not say what the payment is, and the finding that results reads as real
work rather than noise: *"Identify the payee and purpose of the $289 'Online Scheduled Payment to ACCT#
0586' that recurs across three months."* Inventing a category for those lines would be a fabrication.

So the enum gap bites on a **small** subset — recurring ATM withdrawals — while the larger group is
behaving correctly, if filed under a heading that undersells it.

## `unknown` is doing three jobs

| # | state | how it is recorded |
|---|---|---|
| (a) | production failed / truncated / off-vocabulary | `unknown`, `confidence=None`, reason names why |
| (b) | the model read the line and could not tell | `unknown`, **with** the model's confidence |
| (c) | the model read the line and no category fits | `unknown`, **with** the model's confidence |

`_scan_tag_degradations` (`services/verification_run.py:453`) already separates (a) structurally —
`value=="unknown"` + `produced_by==AI` + `confidence is None` — deliberately, so the orchestrator does
not match on reason wording. **It cannot separate (b) from (c)**, and that is exactly this ticket's
conflation. Worth citing as precedent rather than inventing a principle: the codebase already accepts
that `unknown` needs a companion signal to be interpretable.

**The off-vocabulary coercion compounds it.** `_ai_tag` (`services/tag_production.py:482`) records that
"an off-vocabulary value → coerced to `unknown` (never accepted verbatim)". So a model that confidently
answers `cash_withdrawal` produces the same tag as one that could not read the line at all. The
reasoning text survives as the absent reason, so the evidence is not lost — only the value is.

## What it costs, measured against the engine rather than assumed

`unknown` on a predicate tag resolves to `couldnt_check` (`rule_engine/applicability.py:63`), so the
first read of this is "every uncategorisable withdrawal becomes an abstention". **That is wrong, and the
conjunction rule is why.** `resolve_applicabilities` states the precedence: *"any predicate DEFINITELY
FALSE → not_applicable. Scope-false beats data-missing."*

FR-5's scope is a three-tag conjunction — `is_money_in eq out`, `apparent_category eq debt_payment`,
`is_recurring eq yes` — and `txn_is_recurring` returns a definite `"no"` for a payee appearing in only
one month (`derived.py:5921`). So a **one-off** cash withdrawal is cleanly `not_applicable` whatever its
category, and the enum gap costs nothing there.

The residue is precise: **money-out, recurring across two or more distinct months, and uncategorisable.**
That set is not empty — `_payee_key` strips digits, so "ATM WITHDRAWAL 1234" and "ATM WITHDRAWAL 5678"
collapse to one payee and a monthly cash habit reads as `is_recurring=yes`. Those become `couldnt_check`
on a transaction that is plainly out of scope.

**FR-5 is live** (`_LP551_ACTIVATED`), so this reaches processors rather than sitting behind an
activation bar.

**Not claimed: how many.** Counting the live rows needs the category value and confidence per
abstaining transaction, and staging is down. The query when it returns: FR-5 rows with
`evaluation_outcome='couldnt_check'` on the latest run per file, joined to their transactions'
`txn.apparent_category` — separating (b) from (c) by hand on the descriptions, since the data cannot.

## Three ways to fix it — and two of them are now ruled OUT in code

1. **Add an enum value** (`cash_withdrawal`, and/or an explicit `other` meaning "none of these").
   `fact_tags.csv` is GENERATED from `docs/snapshot-fact-tags.xlsx`, and `vocabulary_extra.yaml` cannot
   help — `declarations.py` raises `DeclarationError` if an overlay tag duplicates a `fact_tags.csv`
   tag, deliberately, so the two readers can never disagree about a domain. **So this is an edit to a
   binary spreadsheet the domain expert authors.** Not something to do quietly.

   ⚠️ **AND ON ITS OWN IT WOULD MAKE THINGS WORSE — the user's answer inverted this recommendation.**

   The mechanical reasoning was right and is worth keeping: the §8 contract forbids *absorbing* a
   data-missing into `not_applicable`, but says nothing against a predicate that is **definitely
   false**, which resolves `not_applicable` legitimately. An `unknown` category can never be definitely
   false ("we could not tell" might yet be a debt payment); an explicit `cash_withdrawal` **can** —
   it makes `apparent_category eq debt_payment` false on its face.

   *(The precedence above is quoted from a comment on the deterministic path, so the step a skeptical
   reader stops at is whether a JUDGMENTAL rule's applicability list obeys it. It does, and there is no
   second path: `judgment.py:614` and `deterministic.py:472` call the **same**
   `resolve_applicabilities`. The mechanism is in `resolve_applicability` — for `eq` it computes
   `matches = (tag.value == applic.value)` and returns `NOT_APPLICABLE` on `if not matches`
   (`applicability.py:65-71`), so ANY present, non-`unknown` value other than `debt_payment` is
   definitely-false. `unknown` abstains only because of the explicit `tag.value == _UNKNOWN` branch two
   lines above it, at `:63`.)*

   **But that means FR-5 falls silent, and silence is the wrong outcome.** Asked directly, the user's
   answer was *"recurring cash withdrawal need to be take care"*. Today the absence of a category is the
   only reason the withdrawal is visible at all — it abstains, and the abstention carries real text:
   *"Confirm the source and purpose of the $500 ATM withdrawal on 3/16. This withdrawal recurs across
   multiple months."* Add the value and that finding disappears, by exactly the mechanism argued for
   above. The fix would have deleted the thing it was meant to serve.

   **And FR-5's scope cannot simply be widened to cover it.** `TagCondition.op` is
   `PydField(pattern="^(eq|ne)$")` — eq or ne only — with its own warning that a third operator "added
   here without also giving those sites a shared comparator would be silently evaluated as `ne` —
   wrong, and invisible". There is no `debt_payment OR cash_withdrawal`, and `ne vendor` would be far
   too broad.

   So the value remains a **prerequisite** and stops being a fix: recurring cash activity is a
   different question from undisclosed debt — cash intensity rather than DTI — and needs its own rule,
   criteria and wording. **Tracked as LP-1001**, which carries the sequencing warning that matters
   here: the value must not ship *before* the rule, or FR-5 falls silent on the withdrawal while
   nothing else covers it. This ticket no longer recommends the enum change on its own.
2. **Change the Stage-A prompt** so the model has somewhere to put it. Not a cheap tweak:
   `_stage_a_version` keys the Stage-A cache (`tag_cache_store.py:124`), so editing the prompt re-runs
   the model over every transaction in the corpus and invalidates the calibration of a measured tag.
   Its live readers are **AS-2, AS-12 and FR-5** — *not* AS-1, which an earlier draft of this ticket
   claimed: AS-1's spec does not reference `txn.apparent_category` at all, and the `rule_tags.csv` row
   saying it does is one of the spurious edges bug-027 measured. AS-5 and PC-5 read it but are held.
3. ~~**A deterministic floor beneath the enum**~~ — **NOT POSSIBLE, and this is the finding.** The
   bug-022 shape needs a value to resolve *to*, and the vocabulary has none that fits a cash
   withdrawal: `fee` is wrong (staging carries `Non-Wells Fargo ATM Transaction Fee` as its own
   separate transaction), `vendor` means goods or services, and `transfer_third_party_out` requires a
   named party the description does not have. `_AI_TAG_ALLOWED` coerces anything off-vocabulary to
   `unknown`, so a floor could only force an ATM withdrawal into a category that misdescribes it —
   worse than the honest abstention.

**And the other tempting shortcut is forbidden by contract.** Since the uncategorisable lines are
plainly not debt payments, it is tempting to let FR-5's `apparent_category eq debt_payment` predicate
read `unknown` as scope-false and resolve `not_applicable` instead of `couldnt_check`. The
applicability module refuses exactly that, in its own words:

> **THE §8 HONESTY CONTRACT** — `not_applicable` (scope-false) must NEVER absorb `couldnt_check`
> (data-missing). […] the predicate tag is ABSENT / `"unknown"` → `couldnt_check` […] It IS a gap and
> it blocks. […] conflating them would hide a real gap behind a false "not applicable".

So there is **no code fix available**: the floor cannot name the value, the scope shortcut is
forbidden, and the prompt path spends a calibration. The missing concept genuinely lives in the
spreadsheet, which is the one place this repo cannot reach on its own.

## What is actually worth fixing — and it is not the cash category

The measurement above reframes this ticket. The enum gap is real but small; the larger half of the
`unknown` abstentions are recurring payments whose description names no payee, and **that group is the
textbook undisclosed-debt signal.** Industry underwriting guidance describes exactly it — recurring
payments to individuals or obscure entities that could indicate debts absent from the application —
and it is the question FR-5 was built to ask.

Those findings land in **`couldnt_check`**, which the UI shows under *"Couldn't check"* — a tab that
reads as *we failed to look*. The content is there and is well worded, but the shape says "gap" when
the honest statement is closer to *"we looked, we cannot name the payee, and that is itself the thing
worth reviewing."*

**And this cannot be fixed by reclassifying the predicate.** The tempting move — let FR-5 treat an
`unknown` category as scope-false — is forbidden by the §8 contract quoted above, and rightly: it would
let a genuinely missing fact hide behind "not applicable". So the fix, if there is one, is about where
an *honest* abstention surfaces, not about pretending it is not one. That is a design question about the
outcome vocabulary rather than the tag vocabulary, it touches every rule rather than FR-5, and it is
deliberately **not** decided here.

It is also the sibling of the abstention-layer finding under review on CR-10: a rule that cannot say
*which layer* abstained, beside a tag that cannot say *why* it is empty. Both are one value standing for
several states.

## The questions for the domain expert

**1. Is a recurring cash withdrawal something you want surfaced at all?** This is the question that
decides whether the first one below is worth your time.

> A borrower takes $500 out of the ATM in three different months. Fannie's asset guidance is about
> sourcing money coming IN and investigating borrowed funds — it says nothing we can find about cash
> going OUT. Does a recurring cash withdrawal tell an underwriter anything, or is it simply none of our
> business? If it is none of our business, we would rather the rule stayed silent on it than invent a
> category for it.

**2. Only if (1) is yes — should cash withdrawals get their own category?**

> Today an ATM withdrawal has no category. The list is payroll, transfers, debt payments, gifts, loan
> proceeds, refunds, interest, fees and vendor payments, and a cash withdrawal is none of them, so it is
> recorded as "unknown". Adding a value means editing `docs/snapshot-fact-tags.xlsx`, which is yours.

**3. Independent of both — would you want an explicit "none of these" value?**

> "Unknown" currently means three different things: our reading failed, the model read the line and
> could not tell, and the model read the line and none of the categories fit. The last two need opposite
> handling and we cannot tell them apart. A separate value for "read it, and it is none of these" would
> let a rule stop treating a definite answer as a gap.

**Not a question, but worth her seeing:** the recurring payments that name only an account number
(`Online Scheduled Payment to ACCT# 0586`) are being surfaced today, correctly, and the wording asks
the processor to identify the payee. That half needs no vocabulary change — only, perhaps, a better
heading than "Couldn't check".
