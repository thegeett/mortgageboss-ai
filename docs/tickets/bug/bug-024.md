# bug-024 — AS-6 asks about an account and answers once per statement

- **Status:** Fixed
- **Date:** 2026-09-11
- **Found on:** staging `LF-XMB2`
- **Scope:** Backend — `services/verification_run.py` (a second emission-time collapse),
  `rules/specs.py` + `rules/specs/AS-6.yaml` (the per-rule opt-in that makes it safe)

## The report

LF-XMB2 carries three statements of PNC ****1943, and AS-6 produced **three** needs_review findings
that say the same thing about the same account:

> Confirm the relationship between the non-borrower co-holders and the borrower, or document how the
> account satisfies program rules for joint ownership.

One account, one question, three rows. AS-6 produces **36 findings across 10 files** on staging
(8, 5, 5, 5, 4, 2, 2, 2, 2, 1 — latest verification per file, excluding soft-deleted rows).

The live reach of the collapse, measured on the latest verification per file:

- grouped on this collapse's own `(rule, verdict, facts)` key — the `(tag_id, value)` pairs, not the
  whole tag blob — AS-6 has ten groups of more than one row (5, 4, 4, 4, 4, 3, 2, 2, 2, 2), so
  **22 duplicate rows over 9 files**;
- grouped on the **account** as well, which is what the code actually does: ten `(file, bank, masked)`
  groups of 4, 3, 3, 2, 2, 2, 2, 2, 2, 2 → a ceiling of **14 rows**.

14 is the honest figure and 22 the upper bound; they differ because the fact-set key alone ignores
account boundaries. One caveat travels with the 14: masked account numbers are **not normalised**, so
two files show `****4679` and `3850 0679 4679` as separate groups where a human sees one account, and
`[REDACTED-ID]` appears on three files. `resolve_accounts` normalises the institution but not the masked
format, so the code would also treat those as two accounts — 14 bounds what the code merges, not what a
person would call duplicate.

## The cause

AS-6's question is *whose account is this*, and its answer is a property of the **account**: "a joint
account with an additional holder who is not a borrower" is true of the account, not of one statement
of it. The rule enumerates `per_document`, so it answers once per statement and the reconciler keys each
answer to that statement's content id.

## Why not `collapse_uniform`

That mechanism exists for "N subjects, one sentence" and two specs already use it — but it groups per
RULE per FILE and abandons the collapse at the first dissenting verdict. Measured before choosing:

- on **LF-XMB2** (five satisfied, three needs_review) it does **nothing at all** — the dissent stops it;
- across staging it would remove **3 rows** in total, on three files whose AS-6 rows happen to be
  uniformly satisfied (counted on the same rows-across-runs basis corrected below, so treat the
  magnitude as soft; the *shape* of the argument — dissent stops it — does not depend on the count);
- and on a file with co-holders on **two** accounts it would produce one row naming neither.

The grouping has to be the account, because the account is what the sentence is about.

## The key, and why every part of it is load-bearing

`(rule, account, verdict, facts)`:

- **account** — two accounts are two answers, whatever they say;
- **verdict** — a satisfied statement and a needs_review statement of one account disagree about
  something real;
- **facts** — the decisive part, and the data proves it rather than the argument. **LF-AYK4** has five
  rows under a single outcome but **two** fact sets: four about co-holder *Ila Patel*
  (`non_borrower_co_holder=yes`), and one about a misspelled holder — *"Divyeshkuamr Patel"* —
  carrying `owner_matches_borrower=unknown`, which is a different question with a different remedy. A
  collapse keyed on the account alone folds that row away silently.

Unchanged from bug-021: a rule a processor has already applied or overridden on that file is left
alone entirely, because re-keying retires their answer into fresh OPEN work; and every statement the
surviving answer covers stays named in `source_content_ids`, so the row still lists them.

## Why it is opt-in per rule (`answers_per_account`) — the correction this ticket needed

The first cut of the collapse applied to **any** rule whose subject is a statement. That was wrong, and
measuring it is what showed why.

Exactly **two** rules take a bank statement as their subject:

| rule | its sentence is about | findings | files |
|---|---|---:|---:|
| **AS-6** Account ownership | the **account** — whose it is, who else is on it | 36 | 10 |
| **AS-9** Missing pages | the **statement** — "declares 3 pages, 2 present" | 36 | 10 |

AS-9's distribution is **identical to AS-6's, file for file** (8, 5, 5, 5, 4, 2, 2, 2, 2, 1), and an
ungated collapse folds **10 AS-9 rows today** — nine groups of more than one row (3, 2, 2, 2, 2, 2, 2,
2, 2) — on the rule where doing so hides real problems.

⚠️ **The first version of this argument had the reason wrong, and the correction matters more than the
number.** It claimed AS-9's page counts were not extracted, so every row was a `couldnt_check` with an
identically empty fact set. That is false on current data: AS-9's rows are **`satisfied`** and carry
real counts (`stmt.page_count_declared=2`, `stmt.page_count_present=…`). The collapse happens for the
reason that was listed second — statements of one account genuinely agreeing on both values — and the
"when the extraction lands it gets worse" caveat describes something that has already happened. Three
statements that each declare 2 pages with 2 present are three answers about three documents; merging
them puts one row where three checks were.

So the spec declares it, because nothing in the code can derive it — the subject is a bank statement
either way, and only the author knows what the sentence is **about**. Same shape and same reasoning as
`collapse_uniform.unresolved`: declare it where the sentence summarises the set, leave it off
everywhere else, default safe. AS-6 declares it; AS-9 does not.

## What it does to the two motivating files

| File | Before | After |
|---|---|---|
| LF-XMB2 | 3 needs_review (one account, one fact set) | **1**, naming all three statements |
| LF-AYK4 | 5 needs_review (one outcome, two fact sets) | **2** — the co-holder answer once, the misspelled holder still its own row |

## Tests

Three statements of one account with one fact set collapse to one row naming all three, and the
survivor is the first row with only `source_content_ids` replaced (kept whole, never rebuilt — the
defect class `_collapse_uniform_passes` recorded twice). What must not merge: two accounts; differing
facts (the LF-AYK4 shape); differing verdicts; a statement whose account cannot be identified; a rule a
processor has answered; and non-statement subjects, which pass through in order.

The opt-in has its own two: **AS-9's three identical couldnt_checks stay three rows**, and an unknown
rule id never merges. Both read the real specs, so deleting `answers_per_account: true` from AS-6 — or
adding it to AS-9 — fails in CI rather than in staging.

## Review — REVIEWED

Peer review of `968588e9` (second session). **The collapse, the key and the opt-in are all right, and
the two corrections the measurement forced were both the correct call.** CI is green (2,759 passed, 0
failed here too). One real defect found — the one this ticket asked about first — and it is a correction
to *my own* review of bug-021.

### Q1: the reconciler exposure is real, and it was mine to catch in bug-021

The survivor was `keep, *rest = members` — whichever row sorts first in `results`. The survivor keeps its
own `subject_id`, and that IS the finding's `subject_key`, so if a later run picks a different member the
reconciler meets a subject it has never seen: it mints a fresh finding and retires the old one, taking
its history and any disposition short of `resolved` with it. (`humanly_resolved_rule_ids` protects a rule
someone has ANSWERED; the retire loop also retains a row whose `resolution_status.is_resolved` — but a
row merely seen, or noted, or assigned, is not protected.)

**And `results` order is not stable for this purpose.** Documents load with
`.order_by(Document.document_type, Document.created_at, Document.id)` — `document_type` leads. So
classifying a previously untyped statement, or a re-extraction that changes a type, moves a row within
its group and silently re-keys the finding. That is not a hypothetical on this codebase: bug-020 and
bug-023 exist because LF-XMB2 is carrying four unclassified documents right now, and typing one is the
expected next action.

Both collapses now choose the survivor by the lowest `subject_id`. A content id is stable per document by
construction (LP-312; a transaction's hashes `{"doc": …, **content}`), so it is the same choice on every
run over the same set. It does **not** survive a *new* statement whose id happens to sort lower — no
local rule can, short of consulting the prior findings — but it removes the reordering class entirely,
which is the reachable one. Pinned in both test files by feeding the same rows in several orders.

**So bug-021 was passed with this exposure standing, and that was wrong of me.** Its transaction collapse
had the identical `keep, *rest` and no order-independence test; both are fixed here, in the same commit,
because a stable-survivor rule that applies to one of two sibling collapses is not a rule.

### Q2: the bool is right, and the alternative has a cost the ticket did not name

`answers_per_account: bool` next to `collapse_uniform` is the right weight. A nested block earns its
keep when it carries configuration — `CollapseUniform` holds summary wording because the collapse
*writes a sentence*. This one writes nothing: it keeps a row whole and unions its sources, so there is
nothing for a block to hold. And the cost of the heavier form is not neutral: `CollapseUniform`'s own
`unresolved` field is exactly the kind of option that invites a second, subtler behaviour into a flag
that reads as a boolean. If this ever needs summary wording it will need `collapse_uniform`'s machinery
anyway, at which point it should *be* that, not a parallel block.

### Q3: confirmed rather than assumed

The pass runs after the transaction collapse and before `_collapse_uniform_passes`, and RE-1 and CR-12
traverse it untouched: `answers_per_account` defaults `False`, so the grouping loop `continue`s on their
rows before any key is built. They cannot interact — and the ordering is right for the reason given, each
pass seeing a set already free of the duplication the previous one understands. `compose_findings` runs
after both, so composed prose cannot defeat the fact-set key.

### Q4: a better number is not obtainable through the read-only path

I tried the account-aware query and it cannot be written usefully. `extractions.extracted_data` stores
each field as a typed object (`{"value": …, "source": {…}, "confidence": …}`) rather than a scalar, so
`->>'bank_name'` returns the whole JSON blob; and on the one multi-statement file that matters the masked
number comes back `[REDACTED-ID]`, because the scrub matches its shape. Grouping on it would merge
distinct accounts at one bank. What the query does establish: only **3** files hold more than one
statement of the same `(bank, masked)` pair — 3, 2 and 2 statements — so the collapse's live reach is
small and the 22 figure is a genuine upper bound, not an estimate to be taken literally. Left as an upper
bound in the ticket, with this reason recorded so the next person does not re-attempt it.

### The AS-9 correction was the important one

Worth stating plainly because it is the kind of thing that ships: the first cut would have folded ~22
AS-9 rows *today*, on the rule whose sentence is about the statement, and it would have done so
invisibly — every AS-9 row is a `couldnt_check` with an identically empty fact set, so the key could not
tell three statements apart. Catching that before commit is exactly what the count-it discipline is for,
and the ticket records it in the right place: as the reason the default is off rather than as a list of
rules to exclude.

Checks: the bug-024 file — 12 passed (11 + the order-independence case); the bug-021 file — 13 passed
(12 + its own); full `tests/verification/` tree — **2,761 passed, 0 failed** (41 errors, the DB-backed
suites; no Postgres here). Ruff, ruff format and mypy clean.

## Measurement correction (first session, after the review)

**Every staging count in the first draft of this ticket was inflated, and the review's Q4 reasoning
inherited it.** `readonly.findings` accumulates rows across verification RUNS, and I filtered on none of
it: the view holds **2,122 rows over 64 distinct `verification_id`s on 10 files**, 170 of them
soft-deleted. Per file the run count runs 34, 10, 7, 4, 3, 2, 1, 1, 1, 1. So `82ca98ed`'s "15 AS-6
findings" were 7 + 5 + 3 rows from three separate runs, and the headline "53 findings" counted rows
across runs rather than findings.

Corrected, latest verification per file and `deleted_at is null`: **AS-6 = 36 rows, AS-9 = 36 rows,
identical file for file.** The collapsible counts were then re-derived properly on the latest run, by
extracting `(tag_id, value)` pairs out of `load_bearing_tags` with `jsonb_array_elements` rather than
comparing whole blobs — see the reach figures at the top: 22 on the fact key, 14 with the account.

**What does not change:** AS-9 still mirrors AS-6 exactly, so the opt-in still prevents this collapse
landing on the rule whose sentence is about the statement — the reason the default is off is unaffected.
LF-XMB2 and LF-AYK4 both have `runs = 1`, so the three-PNC-statements report, the 8-row and 5-row shapes
and the two-fact-set case are all real as written. The survivor fix stands on its own reasoning.

**The question this section left open is now answered, and the answer was not the one the failed query
implied.** Counting distinct `load_bearing_tags` jsonb blobs returned `rows == fact_sets` on every file,
which would have meant the collapse never fires; that query over-distinguished on each document's own
`reasoning` text and confidence. Grouped on the real `(tag_id, value)` key it is **22 rows for AS-6 and
10 for AS-9**. Two lessons, both about the same reflex: a near-miss query that returns a clean,
plausible answer ("nothing collapses") is more dangerous than one that errors, and the first draft's 22
turned out to be right by accident — which is not the same as being right, and is why it had to be
re-derived rather than reinstated.

The lesson is narrower than "check the numbers": a view that is append-only per run looks exactly like a
view of current state until you group by `verification_id`, and every count taken from it before that
point silently multiplies by how often a file happened to be re-verified.
