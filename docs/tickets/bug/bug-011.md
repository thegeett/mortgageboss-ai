# bug-011 — a rule that produces findings but is not ACTIVE collides on its second run

- **Status:** Fixed (load/retire split) — one item deferred, one limitation open
- **Date:** 2026-09-02
- **Found on:** staging `LF-ZE9N`, reported by the processor: *"the verification I ran did not finish.
  It keeps going for step 3 to 2 backwards."*
- **Scope:** Backend — `services/verification_run.py` (the `evaluated_rule_ids` argument),
  `services/rule_findings.py` (the contract it feeds), `tasks/verification_rules.py` (the retry class)

## The report

A verification run started 2026-09-02 12:53:37 and never finished. The progress indicator kept moving
from step 3 back to step 2. At 50.9 minutes — past its own 44-minute soft limit — the worker log
carried **four** `stage_a_production_done` and **four** `stage_b_production_done`, events that fire
once per pass. The pass had restarted four times.

Each restart re-ran every model call. 418 `ai_call_succeeded` for what should have been ~110.

## The cause

The pass completes, then fails at the persist step:

```
IntegrityError: duplicate key value violates unique constraint
  "uq_findings_loan_file_rule_subject"
DETAIL: Key (loan_file_id, rule_id, subject_key) = (…, PC-5, loan) already exists.
```

`retry_or_terminal` treats that as transient, so Celery retries the whole pass — from stage A, which
is the step the processor watched it fall back to. Backoff 5s, 10s, 20s; four attempts; then FAILED.

**Why the row collides.** `reconcile_evaluation_findings` matches this run's results to prior findings
by `(rule_id, subject_key)`, and loads those priors with:

```python
prior = await _load_prior_findings(db, loan_file_id, evaluated_rule_ids)
```

The caller passes `evaluated_rule_ids=frozenset(ACTIVE_RULE_IDS)` — the 78 live rules. **PC-5 is not
one of them.** It is BUILT AND HELD (registry.py: its derivation returned a uniform abstain), and it
still reaches the findings table through the LP-391 pending-checks path, which emits a
`PENDING_AUTOMATION` flag for blocked candidates.

So its prior row is never loaded, the reconciler sees no match, mints a new finding, and the unique
index refuses it.

The mechanism is already written down — in a comment LP-640 added about its own synthetic rule id:

> *"`evaluated_rule_ids` gates `_load_prior_findings` — omitted, the prior row is never loaded, so
> every run MINTS a new one and the second collides on `uq_findings_loan_file_rule_subject`."*

That comment fixed the case its author was looking at. The same trap applies to every rule that
produces a finding without being in `ACTIVE_RULE_IDS`, and nothing covers those.

**Why it did not bite until now.** The 2026-09-01 13:37 run was the one that CREATED
`PC-5 / loan / pending_automation` — there was nothing to collide with. Every run since has collided
with the row that one left behind. Confirmed: PC-5 has exactly one finding in the entire staging
database, `pending_automation`, created 2026-09-01 13:50:50. It has never produced a verdict.

## What has to be fixed

**1. The lookup must cover every rule that can produce a finding**, not the active list. Any rule
reaching the findings table through a non-active path has the same latent collision — today the
pending-checks path, tomorrow any rule activated, held, or re-held. A rule moving between active and
held must not be able to corrupt the persist step.

**2. Retirement must NOT widen with it, and this is the part to get right.** `evaluated_rule_ids`
gates two things: which priors are LOADED, and (by default) which are RETIRE-ELIGIBLE. Widening both
would make a run that surfaced no pending flag retire the existing one — and the pending-checks path
is best-effort and isolated (`_evaluate_pending_checks` swallows every exception and returns `[]`),
so a path that failed for its own reasons would silently turn a real flag green. That is the
false-closed the whole `retire_eligible_rule_ids` mechanism exists to prevent.

The two gates have to be separated: load broadly, retire narrowly.

**3. An `IntegrityError` should not be retried.** It is deterministic — the same collision recurs on
every attempt — so retrying an expensive pass against it can only burn the model bill again and delay
the failure. Four attempts here cost roughly four times the AI spend of one run and 51 minutes of a
worker slot, to reach the answer the first attempt already had.

## Impact

Any loan file that has ever surfaced a pending-automation flag cannot be re-verified: every
subsequent run collides, retries four times, and fails. LF-ZE9N is the first file to hit it because
it is the first to have had one written.

The failure is safe — the run is marked FAILED with a reason and nothing is half-written — but it is
not recoverable by re-running, which is the natural thing for a processor to try, and each attempt is
expensive.

## Review

### The fix is right, and its population is six rules rather than one

`load_rule_ids` covers exactly the mint domain — mints come only from `persistable` — and
`_load_prior_findings`'s filters match `uq_findings_loan_file_rule_subject` exactly, so the load set
is now a superset of the collision set. The asymmetry holds: `_retire_eligible_rules` starts from
`ACTIVE_RULE_IDS` and cannot widen.

The ticket speaks of "the pending-checks path" as one thing. It carries **six** held rules — `AS-3`,
`AS-5`, `AS-7`, `CO-5`, `CR-5`, `PC-5` — any of which could have produced this outage; PC-5 is simply
the one that fired. They are disjoint from the active set, which is what the load/retire split
assumes, and a test now pins that so a seventh is covered rather than assumed to be.

### The "must not retire" test could not catch the mutation it named

It records, correctly, that widening `retire_eligible` with the run's own result ids "cannot reach a
rule that produced no result". True, and one step short: retirement is gated per RULE and applied per
IDENTITY `(rule_id, subject_key)`, so widening reaches every OTHER SUBJECT of a rule that produced a
result for any one of them. A held rule flagging two subjects, re-detected for one, would have the
other retired — a real pending flag turning green because a sibling was re-detected.
`test_widening_retirement_to_the_load_set_would_retire_a_live_subject` fails on that mutation; the
original passes through it.

### Every held rule was filed under the wrong category

`category_by_rule` was built over `ACTIVE_RULE_IDS`, so all six blocked rules fell through to the
ASSETS default and tripped LP-595's own `finding_category_unresolved` warning — PC-5 and CO-5 are
property, CR-5 is credit. Harmless only while the second run crashed; now that the row carries
forward it is filed wrong permanently, and LP-598's category refresh cannot correct it because
`category_by_rule.get("PC-5")` is `None`. The map is built over active ∪ blocked now.

### Two comments that had stopped being true

The LP-640 bullet still said `evaluated_rule_ids` gates `_load_prior_findings`; `load_rule_ids` does.
Its unconditional widening is still load-bearing — the run that must RETIRE the consolidated row is
the one that consolidates nothing, so its id is absent from `persistable` — and the comment now says
why, because as written the next reader deletes it as redundant.

And `registry.py` withheld AS-13 on the grounds that this very defect was "UNFIXED", gating
reinstatement on "that fix landing with its own tests". It has landed. AS-13 is deliberately not
reinstated here — that is an activation decision still needing a real run for its bar — but the hold
now names the reason that remains rather than one already dealt with.

### Open: a pending flag can never be retired

The asymmetry has a cost the fix does not pay. A held rule's row enters the load set only when this
run produced a result for it, and it is never retire-eligible — so when the rule stops applying,
`evaluate_pending_checks` drops it, it is absent from the results, never loaded, and the retire loop
never sees it. `PENDING_AUTOMATION` is in `_ATTENTION_OUTCOMES`, so the processor keeps seeing
"manual review needed" for something out of scope, with a stale message and verification_id. Turning
`settings.pending_checks_enabled` off strands every flag the feature ever raised.

Not fixed here because it changes what `_evaluate_pending_checks` promises: it is best-effort and
collapses "ran and found nothing" into "threw and returned `[]`", and the retire half can only widen
safely on the first. The durable shape is the one LP-640 already uses for `UNIDENTIFIED-DOCUMENTS` —
widen both sets, gate the retire half on domain health — which needs that function to report success.
Its own ticket.

### Deferred: the IntegrityError retry, and the reason to defer is not the stated one

The ticket defers making `IntegrityError` terminal because it "touches the shared `retry_or_terminal`
policy used by needs, cross_source and document_processing". It does not: `terminal_on` is a per-call
argument defaulting to `()`, and this task already passes
`terminal_on=(SoftTimeLimitExceeded, AiBackendUnavailable)`. Adding one exception type there touches
nothing else, and `retry.py`'s own justification for time limits — "a retry re-runs the same expensive
work and will time out again" — covers a deterministic constraint violation word for word.

The real reason to keep it separate is a case neither of us named: LP-629 refuses a second concurrent
run per file, but the stuck-run watchdog can declare a LIVE run dead and let a second start — and this
bug produced a 51-minute run against a 44-minute budget, so that path is reachable rather than
theoretical. In that overlap a retry could legitimately succeed, and making the error terminal would
convert a recoverable race into a hard failure. Worth deciding on evidence, in its own ticket.
