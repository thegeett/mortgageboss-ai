# bug-018 — IN-4 asked for employment dates the application already carried

- **Status:** Fixed
- **Date:** 2026-09-11
- **Found on:** staging `LF-XMB2`
- **Scope:** Backend — `tag_materialization/derived.py` (`_income_max_employment_gap`)

## The report

IN-4 abstained on LF-XMB2 with:

> **Upload employment documentation with start and end dates for each position covering the two-year
> history…** The file has fewer than two dated employment records, so employment continuity cannot be
> verified.

The application on that file states, for one borrower, PNC ending **2026-03-03** and First National Bank
starting **2026-03-09** — two dated positions and a six-day gap, sitting in plain sight. The processor
was asked to upload dates the file already had.

## The cause

`income.max_employment_gap_days` is built from the document tags `income.employment_start` and
`income.employment_end`, and those are read from **VOE fields only** (`tag_production.yaml`). A file with
no VOE therefore has zero dated records, whatever the 1003 says.

The 1003's employment records have been in the snapshot since LP-624 —
`borrower.{n}.employer.{m}.start_date` / `.end_date`, beside the `is_current` flag bug-016 now reads —
and nothing consumed them.

## The fix

The recipe now merges the application's employer records into the **same per-borrower groups** the
document records use (`frozenset({borrower_id})` is exactly the key a `belongs_to`-attributed document
produces), so a VOE end can pair with a stated start rather than the two sources forming rival
timelines. Three properties are kept deliberately:

- **Never across borrowers.** A stated record whose borrower the application does not link to an id is
  skipped rather than grouped under the unattributed bucket — pooling it there could manufacture a gap
  between two different people, which is the one thing this recipe has always forbidden.
- **Only documents are named.** A date read from the application has no document behind it, so a gap
  measured from stated dates alone names nothing rather than pointing at a file that does not evidence
  it.
- **It runs with no documents at all.** The early return that skipped everything when the tags or
  documents section was absent now skips only the document half.

**And the abstention no longer says the wrong thing.** One sentence served two different absences:
genuinely fewer than two dated records, and records that exist but never pair (a single position, or
every start before every end). The second now says so.

## What it does to LF-XMB2

IN-4 moves from `couldnt_check` to **satisfied**: the borrower's gap is 6 days against IN-4's 30-day
window, so this removes a queue item rather than adding one. A gap beyond the window on some other file
would now fire where it previously abstained — which is the point.

## For the domain expert

**Is a gap computed from stated 1003 dates alone actionable?** IN-4's remedy is a letter of explanation,
and the guideline (B3-3.1-01/02) is about the borrower's actual history rather than about which document
evidences it — so acting on stated dates looks right. But a stated gap is unverified, and the rule will
now fire on one. If she wants a documented gap only, the fix is to require at least one document-backed
date in the pairing rather than to revert the merge.

## Tests

`test_employment_gap_mismo_bug018.py` — a stated prior position and a stated current one produce the
gap; a stated record merges with a document record for the same borrower; two borrowers' stated records
never pair with each other; a stated record with no borrower link is skipped; a gap from stated dates
alone names no document while a document-backed one still names its two; and the two abstentions now

### Found: "read from VOE fields only" is false, and the merge makes that dangerous

`income.employment_start` is declared `{mode: parsed, subject: document, data: start_date}` with **no
`document_type` filter** — though `declarations.py` supports one for exactly this reason ("a field-name
is not unique"). Four extraction schemas declare a core field named precisely `start_date`: `voe`,
`employment_offer_letter`, **`alimony_income`** and **`child_support_income`**. So a child-support order
produces an `income.employment_start` tag carrying the date the SUPPORT began.

Only `voe` declares `end_date` (the `start_date`/`end_date` in `court_order_documents` belong to a
nested support-awards ROW, which a `subject: document` tag does not read), so a spurious END cannot
occur and no phantom gap can be manufactured. A spurious START can, and it is worse than it sounds:
each end pairs with the **earliest** start after it, so a support date falling inside a real gap
**shrinks** it. A VOE ending 2026-01-31 against a job starting 2026-06-01 is a 121-day gap IN-4 must
fire on; a child-support start of 2026-02-10 makes it read 10 days and IN-4 reports satisfied.

The mis-scoping predates this ticket (LP-382 / LP-454). **This ticket is what makes it reachable:**
before the merge a file with no VOE had no pair at all and abstained; now the application supplies the
other half, so the masking path is live on exactly the files this change was written to serve.

The recipe now reads employment dates only off an employment document
(`_EMPLOYMENT_DATE_DOC_TYPES = {voe, employment_offer_letter}`). Fixed there rather than in
`tag_production.yaml` because the declaration takes a SINGLE document_type, an offer letter's start date
is a legitimate employment start, and IN-7 reads the same tag for its own purposes — so the arithmetic
that can be silently wrong is corrected where it is done. Unclassified (`None` / "unknown") is excluded
too: including a date that may not be employment can only mask a gap, and masking is the one failure
this recipe must not have.

One existing fixture moved with it: the only test using these tags typed its documents `"paystub"`,
which cannot produce them in production (a pay stub's own field is `employment_start_date`). Retyped to
`voe`; what it proves — consecutive pairing rather than spanning, and naming the ended-then-resumed
pair — is unchanged. That the fixture was written that way is itself evidence the scoping was never
considered.

### The five questions

1. **The joint-document hole: endorsed, leave it.** With the allowlist, only a VOE or an offer letter
   contributes dates, and both name a single employee — a joint VOE is not a real shape. Splitting a
   joint document's dates into each borrower's group would pair one borrower's stated end against a date
   that may be the other's, which is the one property this recipe has always forbidden. Incomplete and
   safe beats complete and wrong here.
2. **Measured on staging (after the SSO login): this lands quietly, and nothing newly fires.** Every gap
   computable from the application's own dates — each ended employer against the earliest later start,
   per borrower — falls well inside IN-4's 30-day window.

   > ✅ **Unaffected by the rows-across-runs error found in bug-024.** Both measurements in this ticket
   > read `readonly.stated_employers` — one row per stated employer, not per verification run — so the
   > gap table and the 13-borrowers/13-with-employer-records figures carry no run multiplier. The error
   > applies to counts taken from `readonly.findings`, which this ticket does not use. Recorded because
   > this section feeds a question for the domain expert and she should know which numbers are solid.

   | borrower | ended | next start | gap |
   |---|---|---|---:|
   | b8d8a94c… | 2026-03-03 | 2026-03-09 | **6 days** |
   | 3a136d6d… | 2026-02-28 | 2026-03-02 | 2 days |
   | 3a136d6d… | 2025-04-27 | 2025-04-28 | 1 day |

   Three pairs in the whole corpus, so the change converts abstentions into **satisfied** verdicts and
   produces no new fired finding anywhere. The 6-day row is LF-XMB2's borrower (PNC → First National
   Bank), the file this ticket was written from.

   `readonly.stated_employers` does expose `start_date` and `end_date`, so the gaps themselves are
   obtainable rather than merely bounded — worth recording, because the natural fallback is to count
   borrowers holding both an ended and a current employer (3 here) and call that the answer. It is only
   an upper bound, and comparing the two is informative: **two** borrowers produce a positive gap, so the
   third holds an ended and a current employer whose dates OVERLAP — concurrent employment, which IN-4
   is silent on either way. The query:

   ```sql
   select s.borrower_id, s.end_date, min(t.start_date) as next_start,
          (min(t.start_date) - s.end_date) as gap_days
   from readonly.stated_employers s
   join readonly.stated_employers t
     on t.borrower_id = s.borrower_id and t.start_date > s.end_date
   where s.end_date is not null
   group by s.borrower_id, s.end_date
   order by gap_days desc
   ```

   Two limits on the reassurance: it measures pairs formed from STATED dates only, so a VOE end pairing
   with a stated start — the case the merge exists for — is invisible here; and it cannot show the
   duplicate-job artifact in §5 below, where two sources disagree about one job's end date.
3. **The unlinked stated record is unreachable, so the silent skip is fine.** `mismo_section` publishes
   `borrower.{n}.borrower_id` unconditionally for every borrower whose employer rows it publishes, so a
   row with no link cannot occur. The test for it guards an impossible shape, which is harmless.
4. **The two-message split is right.** One nuance: `dated` counts DATES, not records, so a single
   position stating both a start and an end (dated = 2) reads "no employment record starts after another
   one ends". That is the better sentence for such a file anyway — the behaviour is correct even though
   the variable name suggests records.
5. **A second question for the domain expert, beside the one already recorded.** A VOE and the 1003 may
   both state the SAME job with different end dates. Both ends enter the list, and `max` then turns the
   earlier one into a phantom gap: VOE end 2026-02-01, stated end 2026-03-03, stated start 2026-03-09
   gives 36 days and IN-4 fires on a disagreement between two sources about one job rather than on a gap
   in employment. Not fixable without employer identity; the path, if she wants it, is to dedupe by
   normalized employer name — both sides have one (`borrower.{n}.employer.{m}.name` and
   `income.employer_normalized`).
