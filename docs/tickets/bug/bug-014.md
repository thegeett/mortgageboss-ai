# bug-014 — the fix text a processor reads kept its placeholders

- **Status:** Fixed
- **Date:** 2026-09-11
- **Found on:** staging `LF-XMB2` — MI-1's needs_review row
- **Scope:** Backend — `verification/rule_engine/deterministic.py`, `verification/rule_engine/consistency.py`,
  `verification/rules/specs.py` (two load-time validators)

## The report

MI-1 fired on LF-XMB2 (96.5% LTV, conventional) and its fix read:

> Check that an MI certificate is in the file and that the monthly premium is in the qualifying housing
> payment. If the borrower is putting more down, confirm the final loan amount — at or below
> **{mi_threshold}%** the requirement falls away.

The one number the sentence exists to give was the literal name of an operand.

## The cause

`reasoning` and `how_to_fix` are written side by side in the same outcome and render a few pixels apart
in the same card, but only one was formatted:

```python
reasoning = outcome.reasoning.format(**_reason_fields(operands))   # deterministic.py
...
how_to_fix=outcome.how_to_fix,                                     # passed through raw
```

The same asymmetry exists in `consistency.py`, which formats `reasoning` over
`{values}` / `{sources}` / `{count}` and passes `how_to_fix` through untouched.

Because the field was never formatted, it was never validated either: the loader checks every
placeholder in `reasoning` against the declared operands (LP-511) and said nothing about `how_to_fix`.

**Not only MI-1.** A scan of every spec finds the same defect in two rules that have simply never
fired: MI-4 (`{required}`, twice — the recomputed UFMIP percentage) and IN-15 (`{end_date}` — the date a
pay stub must post after). Both would have reached a processor the first time they did.

## The fix

1. Both evaluators format `how_to_fix` over the same fields they already format `reasoning` over.
2. The loader now holds `how_to_fix` to the same standard as `reasoning` — deterministic outcomes
   against the declared operands (plus LP-511's `_percent` companions), consistency outcomes against
   `{values}` / `{sources}` / `{count}`. A typo now fails at load, not mid-run inside a Celery task.

## Tests

`tests/verification/rules/test_rendered_fix_text_bug014.py` — five guards, each catching what the
others cannot:

- **the evaluator renders it:** a real MI-1 evaluation (materialize → `evaluate_rules`, the LP-487
  standing rule) whose `how_to_fix` carries the threshold and no `{placeholder}`;
- **the other evaluator renders it too** (added in review): a consistency outcome whose fix carries
  `{count}` / `{sources}`, driven through `_outcome_result` and asserted on the rendered sentence;
- **every spec, statically:** no outcome's `reasoning` or `how_to_fix` may reference something it
  cannot resolve — deterministic outcomes against their declared operands (this is what covers MI-4 and
  IN-15, which no test fires), consistency outcomes against `{values}`/`{sources}`/`{count}` (extended
  in review; the original scan read only the deterministic half);
- **the loader refuses an unknown placeholder:** it raises at load;
- **the loader refuses a `_percent` companion the evaluator will not supply** (added in review): the
  companion exists only for a DECIMAL operand, so `{end_date_percent}` on a date operand is rejected.

## Review — REVIEWED

Peer review of `292e38e5` (second session). **The fix is correct in both evaluators.** I found one hole
inside the new load-time check itself, two coverage gaps, and one small duplication — all fixed here.

**Verified independently, all standing:**

- **MI-4 and IN-15 do not break.** This was the sharpest risk in the change: the new validator rejects a
  `how_to_fix` placeholder that is not a declared operand, so if MI-4's `{required}` or IN-15's
  `{end_date}` had been undeclared, both specs would now fail to LOAD — turning cosmetic text into two
  dead rules. Both are declared operands (`required: {reference: fha_ufmip_percent}`,
  `end_date: {tag: …, type: date}`), so they load and now render.
- **Formatting cannot raise at runtime on the deterministic path.** The operand loop breaks to
  `couldnt_check` on the FIRST unresolvable operand, so reaching the outcome loop means every declared
  operand is present in `_reason_fields` — the check the loader performs is exactly the one the
  evaluator needs. On the consistency path `{values}`/`{sources}`/`{count}` are built unconditionally.
- **No spec escapes validation.** `test_user_facing_text_lp530.py` loads every `*.yaml` stem in the
  specs directory through `load_rule_spec`, so the loader guard covers all specs — including inactive
  ones and the consistency half — and a malformed template or literal brace cannot ship silently.
- **The judgment evaluator was never part of this gap.** It formats `case.how_to_fix` too, but
  `_guidance_is_total_and_its_templates_resolve` has always validated `explain[k].how_to_fix` beside
  `why`. With this ticket the class is closed across all three evaluators.
- **The MI-1 test's `"80%"` is pinned to something stable** (the third question the ticket asked):
  `mi_required_above_ltv_percent: "80"` has no trailing `%`, so `parse_reference_fraction` yields a
  plain `Decimal("80")`. Written as `"80%"` it would parse to the fraction `0.8` and the assertion would
  fail loudly rather than drift — which is the behaviour you want from that assertion.

**Found and fixed:**

1. **A hole inside the new check.** `_reason_fields` supplies `{name}_percent` only where the operand's
   value is a `Decimal`, but the validator accepted the companion for ANY declared operand by stripping
   the suffix before the membership test. So `{end_date_percent}` on IN-15's date operand would load
   clean and raise `KeyError` mid-run — the precise failure this load-time check exists to prevent,
   surviving inside it. Now `_unknown_operand_fields` accepts the companion only for a decimal operand,
   for `reasoning` and `how_to_fix` alike. The same helper fixes a second-order bug in the old
   strip-first form: an operand genuinely NAMED `foo_percent` was read as the companion of a `foo` that
   need not exist; a direct hit now wins over the suffix.
2. **The static guard covered one rule shape while claiming both.** It scanned only `deterministic`
   outcomes, but its docstring and this ticket said "every spec". Extended to consistency outcomes
   against `{values}`/`{sources}`/`{count}`.
3. **The consistency half had no behavioural test** (the second question the ticket asked). Worth
   correcting the premise: it is not that no consistency spec references a placeholder in a fix — five
   specs define a consistency `how_to_fix` today (ID-1…ID-4 and IN-5, all on `on_disagree`), so the new
   `.format` call is live code on real specs, a no-op only for as long as none of them contains a brace.
   Added a test that drives `_outcome_result` with `{count}`/`{sources}` in a fix and asserts the
   rendered sentence.
4. **`_reason_fields(operands)` was computed twice** per matched outcome, once per template. Hoisted to
   a single call feeding both — they render the same operands into the same card.

**Answering the first question the ticket asked** — a path where formatting can now raise that the
loader does not cover: I found none for spec-driven text. Every spec loads through the validator in CI,
malformed templates raise there, and both evaluators guarantee their field maps are complete by the time
they format. The one genuine instance was finding 1 above, which was inside the new check rather than
outside it.

Checks: 1,307 tests pass across `tests/verification/rules/` and `tests/verification/rule_engine/`; ruff,
ruff format and mypy clean. `tests/verification/rules/test_projection_db.py` is excluded — it is
DB-backed and this machine has no Postgres; CI runs it.
