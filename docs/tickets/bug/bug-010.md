# bug-010 — the ACH originator id refuses every snapshot on staging

- **Status:** Fixed and committed (`e8ba972`, reviewed in `a789802`) — **not deployed**. Staging still runs pre-fix code and is still refusing every snapshot.
- **Date:** 2026-09-01
- **Found on:** staging, while asking why DTI is gated on `LF-ZE9N`
- **Introduced by:** `2d78cb8` bug-001 — *capture the ACH originator id, so one payee can be two creditors* (2026-08-22)
- **Blast radius:** every loan file with a bank statement carrying a PPD ID. **No snapshot has
  persisted on staging since 2026-08-25 23:56 UTC.**

## What happens

`persist_snapshot` runs the LP-209 at-rest PII guard over the serialized snapshot before the insert.
Since bug-001 added `originator_id` to the transaction rows, that guard finds the ACH PPD ID —
a bare 10-digit run — and refuses the write. The refusal is per-snapshot and total: one match
anywhere and the whole row is discarded.

From the worker log for `LF-ZE9N`'s completed run of 2026-09-01 13:53 UTC:

```
verification_persist_snapshot_failed error=RawPiiAtRestError
detail="refusing to persist: unmasked account/SSN-shaped value(s) at
  documents.entries[1].lists.transactions[0].fields.originator_id.value (a 10-digit run),
  …[9 more paths, all originator_id]…, and 162 more.
  Route the field through the documents section's PII map (_PII_FIELDS) so it is
  masked + hashed, rather than relaxing this guard."
```

172 offending values on that one file, all the same field.

## Why it happens

Three things compose, and each is individually defensible.

**The guard matches on shape, deliberately.** `_LONG_DIGITS = re.compile(r"\b\d{9,}\b(?!\.\d)")` —
nine or more digits as a standalone token. Its own comment calls the over-flag deliberate: *"A raw
account is only distinguishable from a legit identifier by which field carries it, not by pattern."*
A PPD ID (`"PPD ID: 4760039224"`) is ten digits. The guard cannot tell it from an account number,
and it is not supposed to try.

**The field was reasoned into the masked class and then not routed there.** `documents_section.py:559`:

> Not redacted — `_redact_description` scrubs free text, and this is a company id printed beside the
> payee, **the same class as the tax ids routed through `_PII_FIELDS`** rather than dropped.

The line below it is `"originator_id": _txn_field(txn.get("originator_id"))` — a plain `Field`. The
comment names the right home for the value and the code does not put it there.

**`_PII_FIELDS` could not have caught it anyway.** `build_document_fields` consults the registry
only for top-level keys of `extracted_data`; a value inside a captured list row never reaches it.
This is a known, recorded gap — `documents_section.py:846`:

> LP-443 review — a row-PII backstop: list-row PII is NOT `_PII_FIELDS`-routed, so if the
> (unvalidated, starter) prompt fails to mask, the `_DESC_REDACT` 9+-digit scrub redacts a leaked
> full account number. **Not a full PiiField route — the deterministic per-list route is the
> deferred step.**

That deferred step is what this ticket needs. The C7 read-only-query migration documents the same
gap from the other side, as its reason for scrubbing by shape rather than by key name.

## The pattern worth naming

Four distinct fields have now cost a snapshot for the same reason: a legitimate value whose
serialized form is 9+ consecutive digits. Two were identifiers we chose to store (ZIP+4, job
number), one was arithmetic (an unrounded decimal), one is a company id. Each was fixed at its own
site. The fifth will arrive the same way.

The class-level question is whether the guard should be narrowed where it is provably safe, rather
than fixed once per field:

- A run appearing **after a decimal point** is never an account number. The existing `(?!\.\d)`
  lookahead already exempts the *integer* half of a decimal (`123456789.00`, a $123M loan amount);
  it does nothing for the fractional half, because there the point precedes the digits. That
  asymmetry is what cost LP-615 and LP-616 two tickets. Narrowing it closes that class outright.
- Nothing similar is available for the identifier cases. Deciding which ≥9-digit identifiers are
  safe at rest is, as `persistence.py` says, "a per-field data decision, not a pattern one" — and
  LP-509-C1 explicitly declined to narrow on that basis. That judgement should stand.

So: one narrowing that is safe by construction, and no others. Worth deciding as part of this
ticket, not smuggled into the field fix.

## Open questions for implementation

Not decided here — these need a call before code is written.

1. **Type change vs. compatibility.** The sanctioned fix (the guard's own error message) is to route
   the value through `PiiField.from_raw`, which changes `TransactionRecord.originator_id` from
   `Field | None` to `PiiField | None`. The model comment records the field as *"ADDITIVE with a
   default, the LP-421 precedent, so SNAPSHOT_VERSION is not bumped"* — a type change is not
   additive. `load_snapshot` validates stored rows strictly against the current model, so any
   persisted snapshot carrying a `Field`-shaped `originator_id` would fail to load after the change.
   **Measure before deciding:** whether any of the 36 stored rows carries a non-absent
   `originator_id` (only a value under 9 digits could have survived the guard). If none do, the
   change is safe without a version bump; if any do, this needs `SNAPSHOT_VERSION = 5` or a
   tolerant reader.

2. **Does masking preserve what bug-001 wanted?** The field exists to tell two debts owed to one
   institution apart — *"all four Chase payments carry the SAME PPD ID, so what looked like two
   accounts is one autopay charged twice a month"*. `match_hash` is salted per loan file, so equal
   originators hash equal within a file, which appears to preserve grouping exactly. Confirm against
   the intended consumer — **nothing reads `originator_id` today**, so this is a claim about future
   use, not a behaviour that can be observed now.

3. **Per-field or per-list route?** LP-443 calls the deterministic per-list PII route the deferred
   step. Building it properly serves `account_number_masked` on tradelines (today covered only by
   the `_DESC_REDACT` backstop) as well as this field. Doing it narrowly for `originator_id` is
   cheaper and leaves the general gap open. This is the main scoping decision.

4. **The content-id invariant.** `originator_id` is deliberately excluded from a transaction's
   identity (`_IDENTITY_EXCLUDED_TXN_FIELDS`) because folding a field into the content id re-keys
   every per-deposit finding on every file — *"they retire as `no_longer_applies` and mint again,
   stranding any sign-off a processor had made"*. Whatever the fix, it must not change the content
   id. Worth a test rather than a comment.

## Observability

This is the second time the at-rest guard has silently cost staging every snapshot for a week.
LP-565 records the first: *"the at-rest guard refused every write on staging for six days (22
completed runs, 0 snapshots) while the only trace was `error=RawPiiAtRestError`, which says nothing
anyone can act on."* That fix made the message name the field, which is why this diagnosis took
minutes — but nothing alerts.

`persist_snapshot` is best-effort by design: the failure appends a `Degradation("persist_snapshot")`
and the run still reports COMPLETED and green. So the only signals are a log line nobody reads and a
degradation on a successful-looking run. A week of total snapshot loss should be visible somewhere a
person actually looks. Out of scope for the fix; in scope for the discussion.

## What the loss actually costs

A missing snapshot is not cosmetic. It is the persisted record of every tag value the rules ran on,
so for the affected week there is no way to answer "what did the engine see when it decided this"
for any file. `readonly.snapshot_records` is the table the staging query path reads for that
question; it currently answers as of 2026-08-25. That is how this was found — a DTI investigation on
`LF-ZE9N` had no snapshot to read.

## Fix as built (2026-09-01)

`originator_id` is routed through `PiiField.from_raw` — masked display plus the per-file match hash
— on BOTH paths that build a transaction row (the legacy `entry.transactions` and the generic
`entry.lists["transactions"]`), from one shared `_TXN_PII_FIELDS` declaration so the two cannot
drift and mask on one path while shipping raw on the other. `ListSpec` gains a `pii` mapping: the
per-list route LP-443 deferred. `loan_file_id` becomes a required keyword on
`transaction_field_sets` / `build_list_rows` / `_list_row_fields` — deliberately with no default,
since a fallback would silently put the raw value back at rest on whichever caller forgot it.

Masking costs nothing the field was captured for. `match_hash` is deterministic per value within a
file, so equal originators still compare equal (bug-001's actual finding: four Chase payments, one
autopay) and different ones still differ. It is salted per loan file, so a stored hash is not a
cross-file join key.

### The four open questions, answered

**1. Type change vs. compatibility → WIDENED, not narrowed.** `TransactionRecord.originator_id` and
`ListRow.fields` take `SnapshotField` (`Field | PiiField`). Measured: six persisted staging
snapshots carry the old `Field` shape, and **all six are ABSENT** —
`{"value": null, …, "absent": true}` — because a PRESENT one could never have persisted; the guard
refused every snapshot that held one. That shape is still incompatible with a `PiiField`-only type
(`extra="forbid"` rejects `value`, verified), and `load_snapshot` validates strictly, so narrowing
would make six rows unloadable for the sake of a value none of them holds. `SNAPSHOT_VERSION` is
not bumped: a bump is for a shape old readers cannot read, and this is the reverse.

**2. Per-field or per-list route → PER LIST.** Not added to the global `_PII_FIELDS`, which is
consulted only for a document's flat keys and would route in every list.

**3. The content-id invariant → HELD, and the reason is narrower than first written.** Transaction
and document ids are unchanged: `_txn_content` excludes `originator_id` via
`_IDENTITY_EXCLUDED_TXN_FIELDS`, now pinned by a test that asserts the exclusion survives the type
change.

The generic list's `row_id` DOES move, because it is derived from the whole row. The first
write-up called that safe because "nothing reads `lists['transactions']` yet". **That reason is
false** — `source_document_by_subject` walks every list on every run and puts each `row_id` into the
parents map that attaches source documents to findings. The correct reason is narrower: nothing
ENUMERATES transactions, so no finding's `subject_id` is a transactions row id and the changed keys
are inert. `all_list_rows` is called with `tradelines` at all four production sites
(`enumerators.py` 355 / 538, `derived.py` 2977 / 2990), verified by a scan.

The distinction is load-bearing, because `_TRANSACTIONS_LIST` declares `stable_row_id=True` — which
`model.py` documents as being for "a list whose rows a rule enumerates as finding subjects". The
declaration anticipates exactly the enumerator that would break this. Written as "nothing reads it",
whoever adds that enumerator gets no warning; written as "nothing enumerates it, and adding one
re-keys every finding on it once", they do. A test now scans for `all_list_rows` call sites and
fails on an unrecognised list name, saying what it will cost.

**4. The `type: ignore` → REMOVED.** `TransactionFieldSet` is a `TypedDict` with per-key types
(`originator_id: SnapshotField`, the rest `Field`), so `TransactionRecord(content_id=cid, **fs)`
checks without suppression and the one widened attribute is declared at the type level rather than
described in a comment. One `cast` remains in `_txn_content`, where `.items()` on a TypedDict is
typed `ItemsView[str, object]`; the loop is kept over `_IDENTITY_EXCLUDED_TXN_FIELDS` rather than
four hardcoded keys, so that constant, its comment and its test stay load-bearing.

### Review round 2 (the same commit, re-reviewed)

A second review of `e8ba972` found eight more, including one where the JUSTIFICATION in round 1 was
false. All eight fixed in the follow-up:

- **The stated reason for "per list, not global" was wrong.** The comment claimed a name in
  `_PII_FIELDS` "would route it in every list too, moving the row_ids of tradelines". `_PII_FIELDS`
  is read at exactly one site — `build_document_fields`, over a document's FLAT keys — so a name
  added there would not route in any list and would not move a single tradeline row_id. Both this
  session and the reviewing session asserted the false version. The true reason is the reverse:
  `_PII_FIELDS` CANNOT reach a row, which is the gap LP-443 recorded. Corrected in three places.
- **`redact` ran before `pii`**, so a field declared in both hashed the string `"[redacted]"` —
  giving every leaked account on a file the same `match_hash` and making two unrelated accounts
  compare equal. Latent, but on exactly the combination this route exists to create:
  `_TRADELINES_LIST` already declares `redact={"account_number_masked"}`. Masking now runs from the
  raw value and skips the scrub, which the mask strictly dominates.
- **`ListSpec.pii` dropped the `pre_masked` half** that `_PII_FIELDS` carries, so it could not
  express the pre-masked fields it was built for: through `from_raw` a stored `"****1111"` masks to
  `"****"` (destroying the last four) and still hashes (so every account ending 1111 compares
  equal). Now the same `(kind, pre_masked)` tuple.
- **A `pii` name that is not a field of the list was a silent no-op.** `_LIST_SPECS` is generated
  from `schema_specs/*.json`, so a rename would stop the masking and reintroduce this exact bug with
  no signal. `ListSpec.__post_init__` now refuses it at import.
- **"Nothing writes the `Field` arm any more" was false** — `_txn_pii_field` returns
  `Field.missing()` for every row without an ACH originator, the common case. A later cleanup
  narrowing the union on that comment would have made `load_snapshot` reject nearly every snapshot.
- **A row's `row_id` now depends on the encryption key**, since a masked field serializes its HMAC
  `match_hash`. It moves on a key rotation (ADR-051) and a `_HASH_VERSION` bump, and differs across
  differently-keyed environments — which was not previously possible. Documented, not just implied
  by "once, at the deploy that adds an enumerator".
- The second stale "never a `PiiField`" comment (`_liability_context`), and a repo-scanning test
  anchored on the process CWD rather than `__file__`.

### Still deferred

The class-level narrowing of `_LONG_DIGITS` for a fractional run, and the observability gap (a week
of total snapshot loss visible only in a log line, twice now). Neither is part of this change.
