# bug-015 — a withdrawal called a deposit, and seven couldn't-check rows that read identically

- **Status:** Fixed
- **Date:** 2026-09-11
- **Found on:** staging `LF-XMB2`, reported by the processor: *"AS-12 text looks duplicate, only value
  and date are different, it should display proper text"* and *"FR-5 24.34 is withdrawal, why it says
  deposit"*
- **Scope:** Backend — `verification/rule_engine/reasons.py` (the fact vocabulary),
  `services/rule_findings.py` (`_persistable` / `_named_subject`)

## The report

Two complaints about the same tab, with the same root: a finding's fallback text knows the tag that
blocked it and nothing else about the subject.

**1. A withdrawal was called a deposit.** FR-5 abstained on a $24.34 BetRivers card purchase and three
ATM withdrawals, each reading *"the file does not clearly establish the deposit category"*. FR-5 reads
money **out** only (`txn.is_money_in eq out`). AS-1 did the same to an outgoing *"Zel To …"* Zelle
payment, calling it a *"$70 deposit"*.

**2. Seven rows a processor cannot tell apart.** Four AS-12 findings read exactly *"the deposit category
could not be read from the documents (it is present but unclear)"*; three more (AS-1, AS-2) read *"the
file does not clearly establish the deposit direction …"*. They concerned seven different transactions —
$19,039.08, $31,000, $8,000, a $70 Zelle payment and two $30 transfers.

## The cause

**The vocabulary was written when only money-IN rules used it.** `_FACT_LABELS` maps `txn.amount`,
`txn.date`, `txn.is_money_in` and `txn.apparent_category` to "deposit …" phrases. That was true while
AS-1, AS-2 and AS-12 were the only readers (all scope `txn.is_money_in eq in`); FR-5 reads withdrawals.
The subject-label layer made exactly this correction for exactly this reason (LP-551,
`_deposit_label`'s "DIRECTION-AWARE, AND IT WAS NOT"), and the reason vocabulary did not follow.

**A couldnt_check reason names the missing fact, not the subject.** `gate.py` and `applicability.py`
build it from the blocking tag alone, so it is true of the whole class of subject and identifies no
member of it. Every subject of a rule gets one sentence. The composer (`services/finding_prose.py`)
normally rewrites these into specific prose — and did for the $70 Zelle row — but when it rejects its
own draft the raw template ships, which is what a processor saw seven times.

## The fix

1. **The four transaction tags are named neutrally**: "transaction amount / date / direction (money in
   or out) / category". `txn.has_identified_source` and `txn.source_strength` keep "deposit's": they
   exist only for money in.
2. **A couldnt_check about a transaction is prefixed with its subject** — *"Deposit of $19,039.08 on
   2/25 — the transaction category could not be read …"* — from `resolve_subject_label`, the same
   resolver the list view and the composer use, so a finding cannot name its subject one way in one
   place and another way in another. Deliberately narrow: only `couldnt_check` (every other outcome
   interpolates its own operands), only a transaction subject, never when the label carries no amount,
   and never when the message already contains it.

This is a **fallback**. When the composer succeeds, the prefix is redundant and harmless; when it
fails, the row is still identifiable. Existing findings recompose once, because the composer's cache
keys on the message text.

## Tests

`tests/verification/rule_engine/test_couldnt_check_subject_bug015.py` — seven cases: the LF-XMB2
deposit; a withdrawal not called a deposit; an unknown direction dropping the noun but keeping the
amount and date; two transactions no longer reading identically; an unidentifiable subject left alone;
a loan subject left alone; and only `couldnt_check` being prefixed.

`tests/verification/rule_engine/test_human_reasons.py` — the two assertions pinning "deposit
direction" now pin "transaction direction".

## Not in scope

Why those transactions could not be read at all — a blank direction on a line whose description says
"To", and a category enum with no value for cash or a card purchase — is bug-022. This ticket makes the
abstentions legible; it does not remove them.
