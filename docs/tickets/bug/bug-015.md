# bug-015 — a withdrawal called a deposit, and seven couldn't-check rows that read identically

- **Status:** Fixed
- **Date:** 2026-09-11
- **Found on:** staging `LF-XMB2`, reported by the processor: *"AS-12 text looks duplicate, only value
  and date are different, it should display proper text"* and *"FR-5 24.34 is withdrawal, why it says
  deposit"*
- **Scope:** Backend — `verification/rule_engine/reasons.py` (the fact vocabulary),
  `services/rule_findings.py` (`_persistable` / `_named_subject`)

## The report

Two complaints about the same tab, with the same root: a finding's fallback text knows the tag that
blocked it and nothing else about the subject.

**1. A withdrawal was called a deposit.** FR-5 abstained on a $24.34 BetRivers card purchase and three
ATM withdrawals, each reading *"the file does not clearly establish the deposit category"*. FR-5 reads
money **out** only (`txn.is_money_in eq out`). AS-1 did the same to an outgoing *"Zel To …"* Zelle
payment, calling it a *"$70 deposit"*.

**2. Seven rows a processor cannot tell apart.** Four AS-12 findings read exactly *"the deposit category
could not be read from the documents (it is present but unclear)"*; three more (AS-1, AS-2) read *"the
file does not clearly establish the deposit direction …"*. They concerned seven different transactions —
$19,039.08, $31,000, $8,000, a $70 Zelle payment and two $30 transfers.

## The cause

**The vocabulary was written when only money-IN rules used it.** `_FACT_LABELS` maps `txn.amount`,
`txn.date`, `txn.is_money_in` and `txn.apparent_category` to "deposit …" phrases. That was true while
AS-1, AS-2 and AS-12 were the only readers (all scope `txn.is_money_in eq in`); FR-5 reads withdrawals.
The subject-label layer made exactly this correction for exactly this reason (LP-551,
`_deposit_label`'s "DIRECTION-AWARE, AND IT WAS NOT"), and the reason vocabulary did not follow.

**A couldnt_check reason names the missing fact, not the subject.** `gate.py` and `applicability.py`
build it from the blocking tag alone, so it is true of the whole class of subject and identifies no
member of it. Every subject of a rule gets one sentence. The composer (`services/finding_prose.py`)
normally rewrites these into specific prose — and did for the $70 Zelle row — but when it rejects its
own draft the raw template ships, which is what a processor saw seven times.

## The fix

1. **The four transaction tags are named neutrally**: "transaction amount / date / direction (money in
   or out) / category". `txn.has_identified_source` and `txn.source_strength` keep "deposit's": they
   exist only for money in.
2. **A couldnt_check about a transaction is prefixed with its subject** — *"Deposit of $19,039.08 on
   2/25 — the transaction category could not be read …"* — from `resolve_subject_label`, the same
   resolver the list view and the composer use, so a finding cannot name its subject one way in one
   place and another way in another. Deliberately narrow: only `couldnt_check` (every other outcome
   interpolates its own operands), only a transaction subject, never when the label carries no amount,
   and never when the message already contains it.

This is a **fallback**. When the composer succeeds, the prefix is redundant and harmless; when it
fails, the row is still identifiable. Existing findings recompose once, because the composer's cache
keys on the message text.

## Tests

`tests/verification/rule_engine/test_couldnt_check_subject_bug015.py` — nine cases: the LF-XMB2
deposit; a withdrawal not called a deposit; an unknown direction dropping the noun but keeping the
amount and date; two transactions no longer reading identically; an unidentifiable subject left alone;
a loan subject left alone; only `couldnt_check` being prefixed; and, added in review, the direction
reason rendering as one sentence (the gate template's parenthesis counted, not just the label read on
its own) and the anonymity guard tracking the label layer across every direction it can see.

`tests/verification/rule_engine/test_human_reasons.py` — the two assertions pinning "deposit
direction" now pin "transaction direction".

## Not in scope

Why those transactions could not be read at all — a blank direction on a line whose description says
"To", and a category enum with no value for cash or a card purchase — is bug-022. This ticket makes the
abstentions legible; it does not remove them.

## Review — REVIEWED

Peer review of `ae735ca8` (second session). **Both halves are correct and the narrow scoping is right.**
I found one prose regression introduced by the rename and one guard that duplicated a constant it should
have asked for; both fixed here, with a test each.

**Verified independently, all standing:**

- **No import cycle.** Imported `app.main` and then every module under `app.tasks.` and `app.api.`
  (`pkgutil.walk_packages`, not by reading import lines): no failures. `rule_subject_label` pulls in
  `rule_engine.enumerators` and `reasons`, neither of which reaches back into `services`.
- **Nothing that keys on identity keys on the message.** The reconciler matches on
  `(rule_id, subject_key)` — `prior_by_identity` is built from exactly those two — so a reworded message
  cannot mint, retire or duplicate a finding.
- **The composition cache does hash the message, and once.** `FactSummary.problem` is `finding.message`
  and `to_json` includes it, so each affected finding recomposes a single time and then re-hits cache.
- **"deposit's source" / "deposit's source strength" were right to keep** (the second opinion asked
  for). The readers are AS-1, AS-2 and AS-12, and all three are `per_deposit` with
  `applicability: {tag: txn.is_money_in, op: eq, value: in}`, so neither tag can reach a withdrawal.
  Two near-misses worth recording: `PC-5` matches `txn.has_identified_source` on a grep but only inside
  a comment about AS-2, and is `per_borrower`; and `fact_tags.csv` lists **AS-5** as a reader, which
  cannot be true as written — AS-5 is `per_document` and never references the tag. Left alone (AS-5 is
  designed-but-gated, so the column may be forward-looking), but it is worth a look.
- **The assertion style is right** (the fourth question). A full-string assertion on the flagship
  LF-XMB2 case is what should break loudly if the label format moves; the other six already use
  `startswith` / substring, and `test_human_reasons` asserts a substring, so the renames needed no
  churn there. I would not loosen it.

**Found and fixed:**

1. **The new label reads badly in the sentence it is built for.** `txn.is_money_in` became "transaction
   direction (money in or out)", and every label here is interpolated — `gate.py` renders "… could not
   be read from the documents (it is present but unclear)", so a processor got *"the transaction
   direction (money in or out) could not be read from the documents (it is present but unclear)"*: two
   asides in one sentence. The tell is in this ticket's own test fixture, which wrote the reason as
   "the file does not clearly establish the transaction direction" — without the gloss — so production
   emitted prose no test read back. Now simply "transaction direction", pinned by a test that renders
   the gate sentence and counts the parentheses. Nothing anywhere pinned the glossed form.
2. **The anonymity guard kept its own copy of the label layer's strings.** `_ANONYMOUS_TXN_LABELS` in
   `rule_findings.py` restated the three values `_deposit_label` degrades to. Correct today and stale
   the moment a direction is added or a generic reworded — the prefix would then read "a credit — the
   transaction category could not be read", a label identifying nothing in front of a sentence that
   already says it. The set now lives beside `_deposit_label`, built from the same literals it returns
   and exported as `ANONYMOUS_TXN_LABELS`; a test walks every direction the resolver can see (including
   an unknown one) and asserts each amount-less label is in the set and is never prefixed.

Checks: 1,314 tests pass across `tests/verification/rule_engine/` and `tests/verification/rules/`
before these changes and after (plus the two added here); ruff, ruff format and mypy clean.
`test_projection_db.py` is excluded — DB-backed, and this machine has no Postgres; CI runs it.
