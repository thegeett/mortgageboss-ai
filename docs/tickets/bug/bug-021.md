# bug-021 — one statement uploaded twice, and every deposit on it judged twice

- **Status:** Fixed
- **Date:** 2026-09-11
- **Found on:** staging `LF-XMB2`, reported by the processor: *"AS-12 text looks duplicate, only value
  and date are different"* — bug-015 made those rows legible, and legible is how this became visible
- **Scope:** Backend — `services/verification_run.py` (a new emission-time collapse beside
  `_collapse_uniform_passes`, and one line in the pipeline)

## The report

LF-XMB2 shows the same deposit twice under AS-1 and again under AS-12:

- a **$19,039.08** deposit dated 2026-02-25, as `txna10e7b49c4112404` **and** `txne02cf38cf8f4e19e`;
- a **$30** transfer dated 2026-02-20, as `txn59248d5b675ba74d` **and** `txnf60b26459740d71a`.

It is not two statements that overlap. It is **one statement uploaded twice**, confirmed on staging:

| File | Bytes | Bank | Account | Period | Rows extracted |
|---|---:|---|---|---|---:|
| `Bank Statements Statement-2026-03-04.pdf` | 226,597 | PNC Bank | XX-XXXX-1943 | 2026-02-06 → 03-05 | 20 |
| `Bank Statements Felicia Statement 4.pdf` | 226,597 | PNC Bank | XX-XXXX-1943 | 2026-02-06 → 03-05 | 21 |

Same bytes, same account, same period — extracted once as 20 rows and once as 21.

## The cause

A transaction's content id is scoped to its document: `build_transactions` hashes
`{"doc": document_content_id, **content}`, deliberately, so ids are stable per document and the
duplicate tiebreak works within one. Two uploads of one statement therefore mint two different ids for
the same line, and `_per_deposit` enumerates every transaction with no notion of a duplicate. The
reconciler keys findings on `(rule_id, subject_key)`, so two ids are two findings, for ever.

Nothing upstream catches it either: `possible_duplicate` is only ever set by the **email** triage path
(`inbound_triage`), never for a user upload, and nothing under `verification/` reads it.

## The decision: collapse at emission, not in the enumerator

The tempting place is `_per_deposit`. It is the wrong place: `Subject = tuple[str, Mapping[str, Tag]]`
is the entire contract an enumerator can return, so a merged subject has **no channel to carry the
twin's id onward** — and the second statement's link would vanish. That is precisely the loss bug-013
and bug-017 existed to repair, so fixing duplication that way would reintroduce it.

At emission a `RuleEvaluation` already carries `source_content_ids`, so the surviving row can name
**both** uploads. The collapse therefore runs in the results pipeline, next to LP-640's
`consolidate_unidentified_documents`, after `_attach_document_provenance` and before `_persist`.

**Subject identity changes, and this codebase already decided what that costs.** Raised in bug-020's
review, and `_collapse_uniform_passes` (bug-005 / bug-007) had answered it: reconciliation keys a finding
on `(rule_id, subject_id)` and never re-keys one it carries forward, so a collapse that changes grouping
*"would retire those resolved rows and mint one loan-level row of fresh OPEN work — discarding the
human's answer"*. Its guard is `_rules_with_resolved_subjects`, and its closing principle is the one this
ticket adopts rather than re-deriving: **the safe direction is showing more rows, not fewer.**

So this collapse takes the same guard. Once a processor has APPLIED or OVERRIDDEN any per-subject
finding for a rule on a file, that rule stays per subject on that file — the duplicate row is the
smaller harm, and it is visible; a silently retired answer is neither.

Measured on staging as supporting evidence, not as the justification: every affected finding is `open`
with **zero** resolved rows (AS-1 368, AS-2 362, FR-5 168, AS-12 116, AS-6 53, FR-3 18, PC-8 18), so
nothing anyone has acted on is at stake on the first run of this change. The guard is what keeps that
true on every later one.

## What merges, and what deliberately does not

Identity is **(account, date, amount, description)** — the account resolved through the statement, so
two accounts at the same bank never collide.

- **Only across different documents.** Two identical lines *within* one statement are two real
  transactions and stay two subjects.
- **Only when the rows agree.** If the twins' verdicts or load-bearing tag values differ, both stay —
  the 20-vs-21 extraction proves the copies are not identical, and a disagreement is a signal to a human
  rather than something to average away.
- **Never an unresolvable statement.** No bank name or no masked number means no account identity, so
  no merge.
- **Both uploads stay named.** The surviving row's `source_content_ids` carries both statements, so the
  processor can see it appears twice — which is also what makes the duplicate visible at all.

## Deliberately not in this ticket

- **AS-6 fires once per statement** rather than once per account (three statements of PNC ****1943 →
  three identical findings). That is a different mechanism — `per_document` enumeration — and wants its
  own ticket.
- **The two purchase agreements** drive PC-8 and FR-3 twice. They are *not* byte-identical (485,001 vs
  480,929), so no content hash catches them; deciding which document types may legitimately appear twice
  is a domain question.

Both are recorded so they are not lost.

## Review — REVIEWED

Peer review of `67ad9d05` + `712ee1e3` (second session). **The fix is correct and it does fire on the
file it was written for** — measured, not argued. CI was green (2,728 passed, 0 failed here too). Two
small changes made; the identity is left alone, for a reason the measurement supplies.

### The headline question, measured: it fires on 16 of the 20 lines

> ✅ **Unaffected by the rows-across-runs error found in bug-024.** This comparison reads
> `extractions.extracted_data` with `is_current` — one row per transaction per DOCUMENT — so
> re-verifying a file does not multiply it. Which is the distinction this ticket is about: a second
> UPLOAD of the same statement does duplicate these rows, and that is the defect being fixed, whereas a
> re-RUN duplicates findings, which is what inflated the counts elsewhere.

The worry was that the two uploads were extracted differently, so the description-bearing identity might
never match. Comparing both statements' transactions through the read-only views (`extractions
.extracted_data -> 'transactions'`, filtered on `file_size_bytes = 226597`), **both pairs this ticket
names have byte-identical `(date, amount, description)`** and merge:

| date | amount | description (both copies) |
|---|---:|---|
| 2026-02-25 | 19039.08 | `Instpmntin Intuit Payments Inc. Fb 02/25 39073` |
| 2026-02-20 | 30.0 | `Online Transfer To XXXXX8307` |

16 of the 20 lines match exactly. **Four do not, and all four differ in the DESCRIPTION only**, in two
shapes:

| date | amount | one copy | the other |
|---|---:|---|---|
| 2026-02-11 | 120.0 | `1827 Debit Card Purchase Giv*Rccg Living Spring` | `Debit Card Purchase Giv*Rccg Living Spring` |
| 2026-02-26 | 120.0 | `1827 Debit Card Purchase Giv*Rccg Living Spring` | `Debit Card Purchase Giv*Rccg Living Spring` |
| 2026-02-11 | 150.0 | `Web Pmt- Facts Covenant Christi <id>` | `Web Pmt- Facts Covenant Christi` |
| 2026-02-25 | 631.92 | `Web Pmt Recur- Facts Covenant Christi <id>` | `Web Pmt Recur- Facts Covenant Christi` |

The 21st row is also explained: `Trnsfr Fr Interest Checking` (2026-03-02, 73.34) exists in one copy
only — the other carries just the matching `Trnsfr To Standard Checking`. It has no twin, so it stays.

**Keep the description in the identity.** The obvious loosening — strip leading/trailing digit runs — is
actively unsafe: `Check 1827` and `Check 1828` on one day for one amount would then share an identity
and a real second cheque would disappear, which is the failure this ticket calls the worse one. Pinned in
a test so nobody tries it. If the last four are ever worth merging, the safe route is not a looser
string comparison but deciding duplication at the DOCUMENT level (same account + period + byte size) and
then pairing by `(date, amount)` **1:1 within the confirmed pair**, preserving multiplicity so two real
$30 lines stay two. That is a design change, not a tweak.

### It interacts with bug-022, in the right direction

`transaction_type` disagrees between the copies on four rows (`transfer` vs `withdrawal`), and
`_direction` classifies by that field alone — bare `transfer` is DELIBERATELY absent from both sets
(ambiguous), while `withdrawal` is a debit. So one copy of those lines gets no direction and the other
gets "debit", their load-bearing tag values can differ, and the fingerprint guard refuses the merge —
correctly. They are the `Zel To …` lines bug-022 is about: **resolving direction there will raise this
collapse's merge rate**, because the twins will then agree.

### The other questions

- **The identity's reasoning holds** (question 1). Two statements of one account can both carry a line
  dated D only if their periods overlap — and if the same account, day, amount and description appear on
  both, it IS the same line whether the cause is a duplicate upload or an overlapping period. Merging is
  right in both cases; the same-document refusal is what protects two genuinely identical lines.
- **The ordering is right** (question 2): duplicates first, so a uniform-pass collapse counts each
  transaction once rather than reading N/2 lines counted twice as "N subjects agreeing".
- **Dropping rows does reduce the counts, and there is a consequence worth stating** (question 3).
  `_persist` receives the collapsed list and `ReconcileRunResult.detected` excludes what it never saw, so
  the run's counts follow. Verified further in the retire loop: the dropped twin's PRIOR finding is not
  detected this run, so on a retire-eligible run it retires to `no_longer_applies` — visible and
  labeled, with its message rewritten (bug-004) so it stops reading as an open concern, and skipped
  entirely if a human had resolved it. That is how the existing duplicate findings on LF-XMB2 get cleaned
  up rather than silently vanishing, and it is worth knowing before the first run after deploy.
- **The no-op is gone** (question 4). `parents.get(entry.content_id, entry.content_id)` always returned
  its argument — `source_document_by_subject` maps a document to itself — so it read as though `entry`
  might be nested in something. Now a direct lookup, and the traversal it needed is no longer computed
  in that function; the txn → statement direction is still used below, where it is not a no-op.
- **The logger matches the convention** (question 5): counts only, no content ids, like
  `rule_uniform_outcome_collapsed` beside it.
