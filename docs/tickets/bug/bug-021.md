# bug-021 — one statement uploaded twice, and every deposit on it judged twice

- **Status:** Fixed
- **Date:** 2026-09-11
- **Found on:** staging `LF-XMB2`, reported by the processor: *"AS-12 text looks duplicate, only value
  and date are different"* — bug-015 made those rows legible, and legible is how this became visible
- **Scope:** Backend — `services/rule_findings.py` (a new emission-time collapse),
  `services/verification_run.py` (one line in the pipeline)

## The report

LF-XMB2 shows the same deposit twice under AS-1 and again under AS-12:

- a **$19,039.08** deposit dated 2026-02-25, as `txna10e7b49c4112404` **and** `txne02cf38cf8f4e19e`;
- a **$30** transfer dated 2026-02-20, as `txn59248d5b675ba74d` **and** `txnf60b26459740d71a`.

It is not two statements that overlap. It is **one statement uploaded twice**, confirmed on staging:

| File | Bytes | Bank | Account | Period | Rows extracted |
|---|---:|---|---|---|---:|
| `Bank Statements Statement-2026-03-04.pdf` | 226,597 | PNC Bank | XX-XXXX-1943 | 2026-02-06 → 03-05 | 20 |
| `Bank Statements Felicia Statement 4.pdf` | 226,597 | PNC Bank | XX-XXXX-1943 | 2026-02-06 → 03-05 | 21 |

Same bytes, same account, same period — extracted once as 20 rows and once as 21.

## The cause

A transaction's content id is scoped to its document: `build_transactions` hashes
`{"doc": document_content_id, **content}`, deliberately, so ids are stable per document and the
duplicate tiebreak works within one. Two uploads of one statement therefore mint two different ids for
the same line, and `_per_deposit` enumerates every transaction with no notion of a duplicate. The
reconciler keys findings on `(rule_id, subject_key)`, so two ids are two findings, for ever.

Nothing upstream catches it either: `possible_duplicate` is only ever set by the **email** triage path
(`inbound_triage`), never for a user upload, and nothing under `verification/` reads it.

## The decision: collapse at emission, not in the enumerator

The tempting place is `_per_deposit`. It is the wrong place: `Subject = tuple[str, Mapping[str, Tag]]`
is the entire contract an enumerator can return, so a merged subject has **no channel to carry the
twin's id onward** — and the second statement's link would vanish. That is precisely the loss bug-013
and bug-017 existed to repair, so fixing duplication that way would reintroduce it.

At emission a `RuleEvaluation` already carries `source_content_ids`, so the surviving row can name
**both** uploads. The collapse therefore runs in the results pipeline, next to LP-640's
`consolidate_unidentified_documents`, after `_attach_document_provenance` and before `_persist`.

**Subject identity changes, and this codebase already decided what that costs.** Raised in bug-020's
review, and `_collapse_uniform_passes` (bug-005 / bug-007) had answered it: reconciliation keys a finding
on `(rule_id, subject_id)` and never re-keys one it carries forward, so a collapse that changes grouping
*"would retire those resolved rows and mint one loan-level row of fresh OPEN work — discarding the
human's answer"*. Its guard is `_rules_with_resolved_subjects`, and its closing principle is the one this
ticket adopts rather than re-deriving: **the safe direction is showing more rows, not fewer.**

So this collapse takes the same guard. Once a processor has APPLIED or OVERRIDDEN any per-subject
finding for a rule on a file, that rule stays per subject on that file — the duplicate row is the
smaller harm, and it is visible; a silently retired answer is neither.

Measured on staging as supporting evidence, not as the justification: every affected finding is `open`
with **zero** resolved rows (AS-1 368, AS-2 362, FR-5 168, AS-12 116, AS-6 53, FR-3 18, PC-8 18), so
nothing anyone has acted on is at stake on the first run of this change. The guard is what keeps that
true on every later one.

## What merges, and what deliberately does not

Identity is **(account, date, amount, description)** — the account resolved through the statement, so
two accounts at the same bank never collide.

- **Only across different documents.** Two identical lines *within* one statement are two real
  transactions and stay two subjects.
- **Only when the rows agree.** If the twins' verdicts or load-bearing tag values differ, both stay —
  the 20-vs-21 extraction proves the copies are not identical, and a disagreement is a signal to a human
  rather than something to average away.
- **Never an unresolvable statement.** No bank name or no masked number means no account identity, so
  no merge.
- **Both uploads stay named.** The surviving row's `source_content_ids` carries both statements, so the
  processor can see it appears twice — which is also what makes the duplicate visible at all.

## Deliberately not in this ticket

- **AS-6 fires once per statement** rather than once per account (three statements of PNC ****1943 →
  three identical findings). That is a different mechanism — `per_document` enumeration — and wants its
  own ticket.
- **The two purchase agreements** drive PC-8 and FR-3 twice. They are *not* byte-identical (485,001 vs
  480,929), so no content hash catches them; deciding which document types may legitimately appear twice
  is a domain question.

Both are recorded so they are not lost.
