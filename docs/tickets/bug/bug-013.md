# bug-013 — AS-1 and AS-2 findings name no bank statement

- **Status:** Fixed
- **Date:** 2026-09-11
- **Found on:** staging `LF-XMB2`, reported by the processor: *"why AS-1 does not show any document
  where these finding came from"*
- **Scope:** Backend — `services/verification_run.py` (`_attach_document_provenance`); a corrected
  docstring in `verification/rule_engine/deterministic.py` (`_named_documents`)

## The report

On LF-XMB2 every AS-1 finding — the three open large deposits, the three it could not check, and the
187 satisfied — showed no source document. AS-12 and FR-5 findings about the *same* transactions did
name their statement (the $19,039.08 deposit: *Statement-2026-03-04.pdf*; the $31,000 deposit: the Chase
statement), so the processor had to find the page through a different rule.

Through the read-only views, all three open AS-1 findings carried `source_document_ids` = JSON `null`,
and every load-bearing tag's `source_facts` was the finding's own transaction id (`txn…`).

## The cause

Three steps, each correct alone:

1. LP-647 §1 made the deterministic evaluator carry the ids its tags NAMED
   (`deterministic.py` `_named_documents` → `RuleEvaluation.source_content_ids`).
2. An AI or parsed per-transaction tag names its own subject: `source_facts=(subject_id,)`
   (`tag_materialization/ai.py`, `parsed.py`). For a deposit that is the transaction id.
3. `_attach_document_provenance` treats a non-empty `source_content_ids` as the rule's own answer and
   skips the subject → parent-statement lookup (LP-619) that exists for exactly this case. Then
   `_source_document_ids` drops the transaction id, because it is not a document.

So the finding was written with no document. AS-12 and FR-5 are judgment rules; their results carry no
ids, so they took the subject path and were linked correctly — which is why the same transaction was
linked under one rule and not under another.

`_update_finding` keeps prior links when a run resolves none (LP-620), so a finding minted *before*
LP-647 kept its link and only newer ones went blank.

## The fix

`_attach_document_provenance` now translates each carried id through the same parent map the subject
path uses: a transaction (or list row) becomes the document it is nested in; a document maps to itself;
an id the map does not know passes through unchanged. So:

- AS-1's `("txn1",)` becomes `("stmt_jan",)`;
- a rule that named the deposit AND a matching withdrawal on another statement would become both
  statements, in the order the spec's `load_bearing_tags` name them — the first is the finding's
  primary `source_document_id`. Nothing produces that shape today (see Review below);
- a consistency rule's carried documents — including what it excluded — are untouched, and an
  unchanged result is returned as the same object.

Existing findings pick the link up on their next run: `_update_finding` refreshes links whenever the run
resolves any.

## Tests

`tests/verification/snapshot/test_source_document_by_subject_lp619.py` — six new cases: the LF-XMB2
shape (a carried transaction resolves to its statement), a matched debit on a second statement, two
transactions on one statement named once, a carried document id returned untouched, an AS-1 finding
end-to-end through the real evaluator (`evaluate_as1_rule` → `_attach_document_provenance`, asserting
the precondition that the rule carried a TRANSACTION), and — added in review — that the carried order
decides the primary link. The existing "what the rule carried is never overwritten" case still passes
unchanged.

## Review — REVIEWED

Peer review of `6473335a` (second session). **The fix is correct and I found no defect in it.** What I
changed is a set of claims that were stated as current fact and are not.

**Verified independently, all standing:**

- ⚠️ **The scale table below is inflated — see the measurement correction at the end of this ticket.**
  The confirmation was real but it checked the wrong thing: both counts were computed the same wrong way.
- The scale table, re-queried against staging through the read-only views: AS-1 368/203, AS-2 362/250,
  AS-12 116/57, FR-5 168/7 — an exact match, and every one of those findings has a `txn…` subject key.
- AS-2 really is fixed by this, which was worth checking because AS-12 (same `per_deposit`
  enumeration, same `load_bearing_tags` shape) is NOT: `AS-2.yaml` carries a `deterministic:` block, so
  it runs the evaluator that carries ids, while AS-12 and FR-5 are `judgment:` and carry none — which
  is exactly the ticket's account of why the same transaction was linked under one rule and not another.
- A consistency rule's carried ids are untouched by the translation, as claimed: `consistency._result`
  builds them from `inst.source_id`, and a gathered instance's `source_id` is a document `content_id`
  (`entry.content_id`), which maps to itself.
- The LP-620 claims: `_update_finding` refreshes links only `if source_ids`, so prior links survive a
  run that resolves none, and existing findings do pick this up on their next run.
- `replace(...)` returning the same object when nothing changed, order-preserving dedupe, and
  pass-through of an id the map does not know (an already-covered case).

**Found and fixed — three claims that were not true as written:**

1. **The matched-withdrawal case was documented as something the system does.** Both the test docstring
   ("A verified source names the deposit AND its matching withdrawal") and the ticket's fix bullet read
   as current behaviour. Nothing produces that shape: every load-bearing tag on all four `per_deposit`
   rules is AI or parsed, and both producers set `source_facts=(subject_id,)`; `_per_deposit` merges no
   loan-level tags into a transaction's tag map; and the only two recipes that name their own sources
   (`condo_questionnaire_present`, `stmt_continuity`) are loan-subject. The test is a legitimate forward
   guard for the translation and the dedupe — it is now labelled as one, with the reasoning, so nobody
   concludes AS-1 links matched withdrawals today.
2. **"The deposit's own statement stays first — it is the finding's primary link" asserted a guarantee
   the code does not make.** Order comes from the carried order, i.e. the spec's `load_bearing_tags`
   order; the subject plays no part in it. It holds today only because every `per_deposit` spec happens
   to list a tag on the subject first (AS-1 opens with `txn.is_money_in`). Since `_update_finding`
   writes `source_ids[0]` to `source_document_id` — the single document the UI opens — a future spec
   that led with a tag naming another document would quietly send a processor to the wrong file. Pinned
   in a new test (`test_the_carried_order_decides_the_primary_link`) and stated in
   `_attach_document_provenance`'s docstring as the real invariant.
3. **`_named_documents` left a now-false sentence standing as live truth.** "Content ids are prefixed
   (`doc` / `txn`), so a transaction id can never resolve as a document" was the safety argument for the
   unfiltered union, and bug-013 is precisely that argument failing; the commit appended a correction
   below it but left the original reading as current. Corrected in place: safe from a WRONG link, never
   from NO link.

Also fixed: this ticket said "four new cases" while the commit added five — the omitted one was the
end-to-end `evaluate_as1_rule` test, the only one that proves the precondition through the real
evaluator. The Scope line named only `verification_run.py` though `deterministic.py` changed too.

**Considered and deliberately not changed:** making the code *guarantee* that a nested subject's own
document leads (by prepending the subject's parent). It would fix finding 2 by construction, but it
cannot be done without taking a position on the consistency case, where the subject's own document may
be one the rule deliberately EXCLUDED from its gather — prepending it there would assert the opposite of
the verdict. No rule reaches the bad shape today, so this stays a documented-and-tested invariant rather
than speculative behaviour. It becomes real work the moment a `per_deposit` spec lists a tag that names
a document other than the subject's own, or a recipe starts naming matched withdrawals.

Checks: the file's 15 tests pass, plus 62 in the related provenance suites (`test_finding_provenance_lp617`,
`test_provenance_degradation_lp620`, `test_unidentified_document_consolidation_lp640`,

## Measurement correction (2026-09-11, found while reviewing bug-024)

**The scale table is rows-across-runs, not findings.** `readonly.findings` accumulates one set of rows
per verification RUN — 64 `verification_id`s across 10 files, one file at 34 runs, 170 soft-deleted rows
— and neither the original query nor the review's "independent confirmation" filtered on any of it. So
AS-1 368/203, AS-2 362/250, AS-12 116/57 and FR-5 168/7 are sums over every re-verification a file has
ever had, and the per-file figures they imply are inflated by however many times that file was re-run.

**Why the confirmation did not catch it:** both counts were computed the same wrong way, so they agreed
exactly. A check that inherits its input's method is not a check — the agreement was evidence about the
query, not about the defect.

**What stands unchanged.** The defect was established from the code, not the counts: a per-transaction
tag's `source_facts` carries the transaction id, `_attach_document_provenance` took that as the rule's
own answer, and `_source_document_ids` then dropped it as not-a-document. LF-XMB2's AS-1 findings naming
no statement was read directly off the file, and the fix is verified by tests. What the table was ever
for was ordering the queue, and the RATIO it implies (AS-1 and AS-2 losing roughly half their links,
AS-12 and FR-5 far less) is not disturbed by a uniform run multiplier — but the absolute numbers should
not be quoted. A recount on a latest-run basis is pending; staging was shut down when this was found.
