# bug-025 — the same document uploaded twice is two facts everywhere downstream

- **Status:** **Fixed** — the downstream guard is built (below). Prevention moved to **LP-1000**, which
  the user raised as its own feature: a content digest at upload, refusing a byte-identical file on the
  same loan file. This ticket is the other half — what protects the files *already* carrying duplicates,
  which upload-time rejection can never reach. One domain question remains open (which document types
  may legitimately repeat); the ADR-183 scoping question was answered by the user authorising LP-1000.
- **Date:** 2026-09-11
- **Found on:** staging `LF-XMB2`, reported as "two purchase agreements drive PC-8 and FR-3 twice"
- **Scope:** Backend — the cause is at ingestion (`services/documents.py`), the visible damage is at
  snapshot build (`snapshot/documents_section.py`, `snapshot/content_id.py`)

## The report, and why it is bigger than it looked

PC-8 and FR-3 each answered twice on four files. Measured on the latest verification per file, they
produce 16 rows across those 4 files, of which **8 are duplicate answers** — one per rule per file.

But purchase agreements are not the problem; they are one symptom of it. Grouping every active document
by `(loan_file, document_type, file_size_bytes)`, **22 groups hold more than one copy, across 8
document types**:

| type | copies | note |
|---|---|---|
| `pay_stub` | 3 | LF-XMB2, all at 40,571 bytes |
| `purchase_agreement` | 2 × 3 files | all at 3,037,074 bytes |
| `mortgage_statement` | 2, on 4 files | several sizes |
| `lease_agreement` | 2, on 3 files | 506,110; plus a second pair at 8,342,505 |
| `bank_statement` | 2 | 226,597 — the pair bug-021 already collapses at transaction level |
| `credit_report` | 2 | 134,660 |
| `uscis_notice_of_action` | 2 | 3,539,116 |
| `unknown` | 2 | 14,724,118 |

**23 of 84 rule specs enumerate `per_document`.** So one duplicated upload can double the findings of up
to 23 rules, and the two collapses already shipped (bug-021, bug-024) address only the transaction and
account levels.

### It is not noise — it is arithmetic, and the path is demonstrable without staging

A doubled finding is noise a processor dismisses. A doubled **sum** is a wrong number that reaches a
threshold. The whole path is in the repo:

```
_collection_aggregate_balance            (derived.py:4761)   sum(rows, Decimal(0))
  → _non_medical_collection_balances     (derived.py:4668)   iterates liability_rows(snapshot)
    → liability_rows                     (enumerators.py:346)
      → all_list_rows(snapshot, "tradelines", document_type="credit_report")
        → traversal.py:74                a flat comprehension over every matching document. NO DEDUP.
```

`all_list_rows` gathers rows from **every** credit report on the file. Two copies of one report
contribute their tradelines twice, so every row-level sum over them doubles.

`credit.collection_aggregate_balance` is not an observation nobody reads: it is a **load-bearing tag on
CR-10**, which is live (`_LP490A_ACTIVATED` in `rule_engine/registry.py`). CR-10 compares that total
against Fannie's $250 / $1,000 / $2,000 / $5,000 payoff thresholds.

**And it fails in the dangerous direction.** The recipe's own docstring explains why it abstains rather
than under-state:

> ⚠️ ABSTAINS IF ANY CONTRIBUTING BALANCE IS UNREADABLE. A partial sum understates the aggregate and
> could clear a $1,000 or $2,000 threshold the file does not actually clear — **the one direction that
> turns a missing number into a pass.**

A duplicate does the opposite: it **over**-states, pushing a file over a payoff threshold it does not
actually cross, so CR-10 can answer `payoff_required` for debt that does not exist. The careful guard
against one direction sits beside an unguarded path to the other.

**Which aggregates are affected is decided by the operator, not the rule.** A `sum` or a `count` doubles;
a `max` is idempotent under duplication and survives. So:

| tag | shape | duplicated report |
|---|---|---|
| `credit.collection_aggregate_balance` | `sum` | **doubles** — and gates live CR-10 |
| `credit.tradeline_count` | `len(rows)` | **doubles** (its own preamble already admits the limitation) |
| `credit.tradeline_monthly_payment_total` | `sum` | **doubles** — CR-1 cross-checks it against the DTI |
| `credit.largest_single_collection_balance` | `max` | unaffected |

Three summing tags, one of them gating an active rule. Sums and counts are what to audit.

**What is claimed and what is not.** The code path above is verified by reading it. Whether any live
total is *currently* wrong depends on whether `10b6f5e4`'s duplicate credit-report pair carries
non-medical collections, which needs staging and is **not** claimed here. That is the difference between
"this rule can produce a wrong number" and "this rule has produced one".

## The cause

Nothing detects a duplicate upload, at any layer:

1. **No content identity is stored.** There is no hash, checksum or digest column on `Document`, and
   none in the storage layer. `create_document` records filename, mime type, size and storage path, and
   performs no duplicate check. The storage `save()` already receives `content: bytes`, so hashing at
   upload would be nearly free — it is the column and its migration that make it a real change.
2. **The one duplicate check that exists never runs here.** `_flag_possible_duplicate` lives in
   `inbound_triage.py`, on the accept-attachment path, so it only ever sees documents arriving by
   **email**; UI uploads never call it. Its own docstring notes the column has existed since LP-33 and
   "NOTHING HAS EVER WRITTEN True TO IT". Consistent with the data: `possible_duplicate` is `False` on
   all eight purchase agreements.
3. **The snapshot detects duplicates and then deliberately discards the signal.** This is the
   interesting one. `assign_content_ids` hashes each document's canonical content (type + resolved
   borrowers + fields + an order-independent fingerprint of its transactions) and, when two payloads are
   byte-identical, folds an occurrence index (`#0`, `#1`) into the hash **so that duplicates receive
   DISTINCT ids**.

That tiebreak is correct for what it was written for and wrong for documents. Its own justification —
"Genuinely-duplicated content (two identical $50 purchases, same day + description) would otherwise
collide… which physical record receives `#0` vs `#1` is immaterial" — holds for **transactions**, where
two identical lines are two real payments. For a **document**, an identical canonical payload means one
document recorded twice: not two facts, one fact counted twice. The collision is the signal, and it is
computed and thrown away on every run.

## The fix this points to

Detect the duplicate where the evidence already exists — the equality of canonical document payloads in
`_reshape_and_assign_ids` — rather than by any `(type, size, filename)` heuristic, which would carry
exactly the hiding risk AS-9 forced bug-024 to refuse.

Two constraints the implementation must respect:

- **Do not key anything on the occurrence index.** `enumerators.py` refuses it explicitly — it is
  order-dependent, "making the id depend on projection order — the very thing this shape refuses". Use
  payload equality (order-independent) to detect, and bug-024's rule — lowest `content_id` — to choose
  which copy survives, so the survivor is stable across runs.
- **Borrower links are part of the payload, and that is a stated NON-GOAL rather than a gap.** Two
  copies linked to different borrowers (or one linked and one not) hash differently and must never be
  seen as duplicates: on a joint file a **per-borrower credit report legitimately is two documents** —
  the very case `enumerators.py` names in the same breath as the duplicate. Detection must not merge
  them, so the payload including borrower refs is the behaviour we want, not a limitation to fix.

Surface the duplication **once, as its own finding** ("this document is in the file twice — remove one"),
and let the per-document rules answer against the surviving copy.

**That is not a presentation preference — a collapse cannot do this job.** The aggregates above are
computed in TAG MATERIALISATION, upstream of findings entirely. Collapsing duplicate rows at emission
would tidy the visible output and leave `credit.collection_aggregate_balance` doubled underneath, still
feeding CR-10's threshold comparison. An emission-time collapse cannot reach the damage, so **bug-021's
and bug-024's approach cannot substitute for fixing this at ingestion** — the duplicate has to stop
existing, or be marked so the materialiser can skip it.

The two shipped collapses remain necessary anyway: catching duplicates at upload does nothing for the
files already carrying them. The ordering was simply backwards — this was the cause, and it should have
come first.

## The guard, as built

`all_list_rows` (`snapshot/traversal.py`) now collapses documents that contribute **identical rows** for
the list being gathered, so a document filed twice contributes once.

**Why there, and not anywhere else.** Four consumers gather through that one function, and every one of
them was wrong by the same factor:

| consumer | was | now |
|---|---|---|
| `credit.tradeline_count` | counted 48 | counts 24 |
| `credit.tradeline_monthly_payment_total` | summed 48 payments | sums 24 |
| `credit.collection_aggregate_balance` (gates **live CR-10**) | summed over 48 rows | over 24 |
| `liability_rows` | two subjects per debt | one |

**Why not at emission.** These rows feed **tag materialisation**, upstream of findings entirely, so no
collapse of duplicate *findings* could ever have reached the doubled number — the mistake bug-021's and
bug-024's shape would have invited. Verified end to end rather than reasoned: `liability_rows` now
returns **one** subject (`cr1-row0`) for two identical reports, and the same subject when the documents
arrive in reverse order.

**The identity is `document_type` + resolved borrowers + every row's `(field, value)` pairs.** Three
things about that are load-bearing:

- **`row_id` is excluded.** A row's id is derived from its content *scoped by the parent document's
  content id*, so two byte-identical documents produce rows whose ids differ by construction. Comparing
  ids would find no duplicates, ever.
- **`belongs_to` is included**, and it is what keeps the legitimate case safe: a joint file may carry
  one credit report per borrower — two documents about two people, not one filed twice. `enumerators.py`
  names that case in the same breath as the duplicate.
- **A `PiiField` has no value at all.** A tradeline's `account_number_masked` is declared sensitive, so
  every real credit report hits that branch; the comparison uses the masked display plus the match hash,
  which two copies share and two different accounts do not.

**The survivor is the lowest `content_id`, never the first in document order** — bug-024's review lesson
applied before it could bite. `liability_rows` uses a row's `row_id` as a finding's subject key, and
documents load ordered by `(document_type, created_at, id)`, so classifying one of LF-XMB2's untyped
documents would reorder them; a moving survivor would re-key the finding and discard its history.

### An existing test asserted the doubling, and it was a tripwire

`test_two_credit_reports_double_list_the_same_debt` (LP-480) asserted **two** subjects under
*"⚠️ RECORDED LIMITATION: no dedup WITHIN a source"*. Its sibling in the same file explains what such
pins are for — *"Pinned so the day someone changes the identity fields, this test tells them what it
fixes"* — so this was that day. It is rewritten to assert the fix, keeping the limitation's history in
the docstring rather than deleting the record, and naming what must still **not** be deduplicated.

### What the guard does not fix

**Near-duplicates.** LF-XMB2's two purchase agreements are 485,001 vs 480,929 bytes — same contract,
same typo, one differing extracted closing date. Their rows differ, so they are two documents here, as
they are to LP-1000's digest. Neither half of this work catches that pair, and the domain question below
is the only thing that can.

## Review — REVIEWED

Peer review (second session). **The guard is correct, in the right place, and its survivor rule is
right.** All five claimed numbers reproduce exactly — `tests/verification/` 2,773 passed / 0 failed (was
2,763), the new dedup file 10 passed, the rewritten LP-480 file 25 passed, ruff and format clean, and the
7 mypy errors in the LP-480 test file are genuinely pre-existing: the commit's only hunk there is
`@@ -375,12 +375,32 @@` and every error sits at lines 100–263, above it.

Four questions were asked. Three hold as built; the fourth found a fifth aggregate.

### Q1 — the distinction exists, and this ticket had already written it down

The question was whether de-duplicating in the traversal for lists while bug-021 collapses transactions
at emission leaves two layers for one problem, with no principled line between them. There is a line, and
it is **this ticket's own sentence**: *"Which aggregates are affected is decided by the operator, not the
rule. A `sum` or a `count` doubles; a `max` is idempotent under duplication and survives. Sums and counts
are what to audit."*

So the layer is not the principle — **the aggregate is**. Value-identity de-duplication belongs wherever
a count or a sum is computed over per-copy subjects, and this codebase already does exactly that in three
places: `_stmt_repeated_money_in_max_total` keys on `(amount, date, description)` and skips
*"the same deposit, seen again in a duplicate or overlapping statement"*; `_documents_stating` and
`_documents_dated` guard the same way; and now `all_list_rows`. bug-021's emission collapse is not a rival
layer — it fixes duplicate **findings**, which is a different defect from a doubled **number**.

**And the audit stopped one layer short.** The table above audits four aggregates, all fed by
`all_list_rows`. `stmt.nsf_count` is a fifth of the identical shape, fed by **tags** instead of rows:

```
_stmt_nsf_count (derived.py:1617)   count += 1 per subject tagged "yes"
  → iterates snapshot.tags.by_subject          NO value-identity guard
    → txn.is_nsf_or_overdraft  {mode: ai, subject: transaction}   one tag per transaction SUBJECT
      → assign_content_ids folds an occurrence index, so duplicate copies get DISTINCT subject ids
        → AS-7:  when_compare {op: ">", left: count, right: nsf_tolerance "3"}
```

A statement filed twice therefore doubles the count, and neither guard reaches it: the traversal fix is
for list rows, and an emission collapse cannot reach a tag. Fixed here, in the same shape as its
neighbour one recipe up.

**Severity, stated precisely, because it is much weaker than the CR-10 exposure above.** This is *"can
produce a wrong number"*, and not even reachably so today. AS-7 is **inert** — `registry.py`: "AS-7 is
BUILT AND HELD"; `activation_bars.yaml`: `status: not-calibratable-yet`, held for two reasons, one being
*"NO TRIGGER EXISTS IN ANY AVAILABLE DATA, measured rather than assumed"* (2,557 PDFs scanned, 223 files
carrying an NSF signal, 886 occurrences, **not one an actual event**; all 55 "Total Overdraft/NSF Fees"
lines at $0.00). The defect needs three coincidences: AS-7 activated, a real NSF line existing, and its
statement filed twice. It is fixed because the guard is ten lines and because it closes the **class** the
question asked about — not because anything is wrong in production today. Recorded on AS-7's activation
bar so whoever activates it inherits the knowledge rather than the bug.

**⚠️ ONLY A FULLY-DETERMINED IDENTITY DEDUPLICATES, and the asymmetry is load-bearing.** The recipe's
whole discipline is never to undercount — an `unknown` status abstains rather than report a lower bound —
so two NSF lines with no amount and no date must **both** count. Collapsing those would be precisely the
undercount the abstention exists to refuse. Pinned by a test.

### Q2 — unconditional is right today, and latent-only is why

`all_list_rows` is generic over 66 lists, so an unconditional collapse could in principle drop a list
where two documents legitimately carry identical rows — two different bank statements each showing one
identical `fees` row, say, where the count would silently halve in the data-hiding direction.

**It cannot fire today**, and that is measured rather than assumed: all four call sites pass
`document_type="credit_report"` with the `tradelines` list (`derived.py:3231`, `3244`,
`enumerators.py:355`, `538`). So the exposure is latent, and unconditional is the right trade now —
opt-in would add a parameter every caller sets the same way. It becomes a real question the first time a
caller gathers a list where two documents may legitimately agree, and the honest place for that is a
comment at the seam rather than an unused parameter.

### Q3 — the rewrite is right, and ADR-374 is not touched

Challenged as asked, and the challenge fails on the ADR's own scope. **ADR-374 governs the union
*between* sources**: "Every row from either source becomes its own subject… A debt appearing in both
sources is deliberately present twice, once per source", because *"an undisclosed tradeline is precisely
a debt present in one source and absent from the other. CR-4 exists to detect exactly that."*

De-duplicating two copies of **one document inside one source** leaves that comparison completely intact:
every distinct tradeline still appears, the `mismo_stated` side is untouched, and CR-4's difference is
unchanged. What the old test pinned was explicitly *"⚠️ RECORDED LIMITATION: no dedup **WITHIN** a
source"*, adding that *"`liability.source` does not protect a summing rule here"* — the language of a
defect being recorded, not a contract being asserted. Reading it as a tripwire was correct.

### Q4 — no harmful shape for the live caller, and the risky one is out of reach

For credit-report tradelines the answer is stronger than "no": two reports from **different bureaus**
listing an identical tradeline set have identical rows and identical borrowers, so they collapse — and
collapsing is the *correct* arithmetic, since 24 distinct debts are 24 whether two bureaus report them or
one. A refreshed report differs (balances move); a per-borrower report differs (`belongs_to`); a
near-duplicate differs (rows). The shape that would hurt is the generic one in Q2, and it is unreachable
from today's call sites.

One limitation worth recording rather than fixing: the signature compares a document's **entire row set**,
so two byte-identical uploads whose *extractions* differ by a single field — plausible, since extraction
is a model call — produce different signatures and neither is collapsed. That fails in the pre-existing
direction (both kept), so it is a narrowing of the guard's reach, not a new defect. LP-1000's digest is
what catches that pair at the door.

### What I could not check

Staging was queryable during this review only because the peer session ran `terraform init`, which
re-dirties `infra/envs/staging/.terraform.lock.hcl` — a file the user deliberately reverted. So the open
staging question from the section above stands unanswered by choice, not by obstacle: whether
`10b6f5e4`'s duplicate credit report actually carries non-medical collections, which is the difference
between CR-10 *can* produce a wrong number and *has*. `_stmt_nsf_count`'s own exposure needs no query —
the corpus measurement on AS-7's activation bar already establishes there is no NSF event to double.

## Open decisions — not mine to make

1. **DOMAIN: which document types may legitimately appear more than once?** A file holds 8 bank
   statements and 8 mortgage statements legitimately; two pay stubs may be two periods or one stub
   twice. This matters beyond this ticket, because `_flag_possible_duplicate`'s existing test is
   **type-level** — any second document of the same type — so extending it to the UI path as-is would
   flag every one of those as a duplicate. The question is really about that check, not about this fix.

2. **PRODUCT: ADR-183 already scoped this, and not in this direction.** `docs/document-model.md` records
   "gentle duplicate surfacing (informational, client-side) + the email-ingest `possible_duplicate` flag
   concept" — deliberately informational and email-only.

   **The argument against that scoping is the CR-10 path, not the 22 groups.** "Gentle, informational,
   client-side" is a defensible answer to duplicate rows a processor can dismiss. It is not a defensible
   answer to a duplicate that silently doubles a tag feeding a payoff threshold on a live rule, where
   the failure is invisible in the UI and lands as a wrong requirement on a borrower. The scoping was
   written against noise; the evidence here is arithmetic. That is a real decision to re-open, and it is
   the user's, not mine.

## The one genuine content question — LF-XMB2's pair

Three of the four purchase-agreement pairs are byte-identical (3,037,074 bytes), with filenames differing
only by a browser download-collision rename (`… (1).pdf`). Those need no domain ruling.

LF-XMB2's pair is the exception — 485,001 vs 480,929 bytes, different filenames. Their extracted terms:

| field | copy A (485,001) | copy B (480,929) |
|---|---|---|
| sales price | 480000 | 480000 |
| contract date | 2026-06-08 | 2026-06-08 |
| earnest money | 2500 | 2500 |
| included items | washer, dryer, kitchen friedge, microwave | *identical, same typo* |
| **closing date** | **2026-06-08** | **2026-07-22** |
| extraction confidence | 0.95 | 0.98 |

Everything matches, including the misspelling, except the closing date — and copy A's closing date equals
its own contract date, which is implausible for a purchase and looks like a misread rather than a term.
So this is most likely **one contract extracted twice**, which would mean the domain question shrinks to
almost nothing. Worth confirming with the expert as a precise question rather than assuming:

> Two copies of one purchase contract, identical in price, parties, contract date, earnest money and
> included items, differ only in closing date (2026-06-08 vs 2026-07-22). Is that an amended closing
> date, or one contract read twice? And does a purchase agreement ever legitimately appear twice on a
> file?
