## Review (of `37f5aa9f`)

**Both of the owner's asks are satisfied, and the generator is right rather than merely self-consistent
— I re-derived the whole table from the raw sources. One finding, pre-existing but squarely inside this

### Finding — the receipt item's only check can never pass

`receipt` now names `earnest_money_receipt` (right) and checks `amount_matches` (unchanged). Measured,
by putting a real earnest money receipt through `check_document` on 6637:

```
6637 items:
  key='receipt'   status=open  documents=['earnest_money_receipt']  checks=['amount_matches']

after the receipt arrives:
  item='receipt'  item_status=received
  checks={'amount_matches': ('not_run', 'no transactions could be read')}
```

`amount_matches` reads `Statement.movements`, and `statement_from()` builds a Statement out of
**bank-statement** fields (`transactions`, `account_number_masked`, `statement_period_*`). An earnest
money receipt extraction has none of them, so `movements` is empty and the check returns NOT_RUN.
`_item_passes` needs `all(r == PASSED)`, so the item stops at **Received** and can only be completed by
her accepting the document by hand — for every earnest money receipt, forever.

The data is there and unread: the extractor captures `earnest_money_amount` (and `check_number`), which
is exactly what the check wants. So the gap is that `amount_matches` looks in the wrong place for this
document type, not that the amount is unavailable.

**This is not a regression** — the check and the item's old document list had the same problem, so
LP-938 neither caused nor worsened it. I am reporting it because the owner's ask was to make this item
name the right document, and the honest answer is that the right document now arrives, is recognised,
and still verifies nothing.

Two things worth fixing together: teach `amount_matches` to read a receipt's own amount when the
document is one; and the NOT_RUN reason, *"no transactions could be read"*, is false here — the amount
was read perfectly, it just was not looked at. A sentence that will appear on her sheet should not
describe a failure that did not happen.

### (a) A backend test reading a `docs/` file

**Fine here, and there is precedent** (`tests/ai/generator/test_lp438_generic_lists.py` reads
`_GENERATION_GUIDE.md` and `_FORMAT.md`), plus `parents[4]` repo-root paths already in `app/`
(`verification/eval/db_worksheet.py`, `ai/extraction/generator/emitters.py`). CI checks out the whole
repo, and `read_text()` raises if the file is missing — a loud failure.

But the path expression deserves a comment, because **this exact one has a scar on it**.
`app/verification/rules/distrust.py:18-31` records what it cost: `parents[4] / "docs" / "schema-specs"`
counted on a `backend/` directory that exists in the repo and not in the image, where the package root
is `/app`; the walk landed on `/docs/schema-specs`, the spec set came back **empty**, and every
containerised rule-engine run raised on the first entry "for the whole life of the image" — a packaging
problem reported as a renamed field.

`review_table.py` is safe from that because nothing reads `REVIEW_TABLE` at request time — only
`__main__` and the test — and an empty read is impossible where a missing file raises. A line saying so
would stop the next person wiring this module into anything that runs in the container.

### (b) `TOP_20` as a constant

**Right as it is.** It is the owner's review order, not a fact about the library, and deriving it from
code-map frequency would let a document he is marking up silently reorder itself when a code map
changes — the worst property a review artefact can have. Keeping it explicit alongside a generated body
is the correct split, and `test_twenty_distinct_types_in_the_library` catches the failure that matters
(an id that no longer exists).

The one gap is the mirror image and is not testable: nothing notices when the library gains a type that
*should* be in the top 20, so the curation can go stale in the direction the tests cannot see. That is a
judgement for the sign-off conversation, not a guard — worth one line in the docstring naming who
revisits it and when.

## Follow-up — the review's finding fixed (the builder's call)

**The finding (pre-existing):** AS-04's receipt item checks "Amount matches", which reads a statement's
transactions. An earnest money receipt has none, so the check was not run ("no transactions could be
read", which was untrue: the receipt's `earnest_money_amount` had been read, just not used). Every real
receipt stopped at Received and needed her manual accept.

**The fix, where a document becomes the checks' facts (`statement_from`):** when an extraction has no
transactions but carries `earnest_money_amount`, that amount is its one movement, dated by
`funds_received_date` (or `receipt_date`), and the document is a "receipt".
- The failure says "no $2,850.00 on this receipt"; a statement still says "statement".
- The not-run reason is now "no amount could be read on this document", true for both.
- A purchase agreement also extracts `earnest_money_amount`, but no item that checks amounts takes that
  type (`_takes` filters by document type), so its stated deposit cannot pass anything.

**Tests** (`test_condition_evidence.py`, with a new `add_receipt` fixture built from the real
`EarnestMoneyReceiptExtraction`):
- `test_an_earnest_money_receipt_is_checked_against_its_own_amount`: "$2,850.00 on 08/03/2026" passed;
  the receipt item is done; with the statements, 6637 is Ready by evidence alone.
- `test_a_receipt_for_another_amount_fails_and_says_receipt`.

**Mutations**, each restored from a copy and killed:
- the receipt branch off (2 fail);
- its date dropped (1 fails);
- the failure saying "statement" again (1 fails).

**Also from the review:**

- the S3-10 harness docstring no longer says evidence checks cannot check a title receipt.
