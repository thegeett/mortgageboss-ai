### Finding — the receipt item's only check can never pass

`receipt` now names `earnest_money_receipt` (right) and checks `amount_matches` (unchanged). Measured,
by putting a real earnest money receipt through `check_document` on 6637:

```
6637 items:
  key='receipt'   status=open  documents=['earnest_money_receipt']  checks=['amount_matches']

after the receipt arrives:
  item='receipt'  item_status=received
  checks={'amount_matches': ('not_run', 'no transactions could be read')}
```

`amount_matches` reads `Statement.movements`, and `statement_from()` builds a Statement out of
**bank-statement** fields (`transactions`, `account_number_masked`, `statement_period_*`). An earnest
money receipt extraction has none of them, so `movements` is empty and the check returns NOT_RUN.
`_item_passes` needs `all(r == PASSED)`, so the item stops at **Received** and can only be completed by
her accepting the document by hand — for every earnest money receipt, forever.

The data is there and unread: the extractor captures `earnest_money_amount` (and `check_number`), which
is exactly what the check wants. So the gap is that `amount_matches` looks in the wrong place for this
document type, not that the amount is unavailable.

**This is not a regression** — the check and the item's old document list had the same problem, so
LP-938 neither caused nor worsened it. I am reporting it because the owner's ask was to make this item
name the right document, and the honest answer is that the right document now arrives, is recognised,
and still verifies nothing.

Two things worth fixing together: teach `amount_matches` to read a receipt's own amount when the
document is one; and the NOT_RUN reason, *"no transactions could be read"*, is false here — the amount
was read perfectly, it just was not looked at. A sentence that will appear on her sheet should not
describe a failure that did not happen.

### (a) A backend test reading a `docs/` file

**Fine here, and there is precedent** (`tests/ai/generator/test_lp438_generic_lists.py` reads
`_GENERATION_GUIDE.md` and `_FORMAT.md`), plus `parents[4]` repo-root paths already in `app/`
(`verification/eval/db_worksheet.py`, `ai/extraction/generator/emitters.py`). CI checks out the whole
repo, and `read_text()` raises if the file is missing — a loud failure.

But the path expression deserves a comment, because **this exact one has a scar on it**.
`app/verification/rules/distrust.py:18-31` records what it cost: `parents[4] / "docs" / "schema-specs"`
counted on a `backend/` directory that exists in the repo and not in the image, where the package root
is `/app`; the walk landed on `/docs/schema-specs`, the spec set came back **empty**, and every
containerised rule-engine run raised on the first entry "for the whole life of the image" — a packaging
problem reported as a renamed field.

`review_table.py` is safe from that because nothing reads `REVIEW_TABLE` at request time — only
`__main__` and the test — and an empty read is impossible where a missing file raises. A line saying so
would stop the next person wiring this module into anything that runs in the container.

### (b) `TOP_20` as a constant

**Right as it is.** It is the owner's review order, not a fact about the library, and deriving it from
code-map frequency would let a document he is marking up silently reorder itself when a code map
changes — the worst property a review artefact can have. Keeping it explicit alongside a generated body
is the correct split, and `test_twenty_distinct_types_in_the_library` catches the failure that matters
(an id that no longer exists).

The one gap is the mirror image and is not testable: nothing notices when the library gains a type that
*should* be in the top 20, so the curation can go stale in the direction the tests cannot see. That is a
judgement for the sign-off conversation, not a guard — worth one line in the docstring naming who
revisits it and when.

## Second follow-up — the rest of the class, and the guard made structural

**The review's finding:** the class is "an item that checks `amount_matches` against a document type with
no transactions". Two latent members remained:
- AS-06's gift letter: `gift_amount` was unread, so it could never pass;
- AS-05's deposit slip: `deposit_total` was unread.

The review also asked for a tripwire so a library edit cannot let a purchase agreement's STATED deposit
satisfy a check that confirms receipt.

**The fix is a typed allow-list, not a field lookup.** `OWN_AMOUNT` in `condition_evidence.py` maps each
document type whose own stated amount is the money it evidences to `(amount field, date fields, the word
the failure uses)`:
- `earnest_money_receipt` → "receipt";
- `gift_letter` → "gift letter";
- `bank_deposit_slip` → "deposit slip".

`statement_from` reads it only when told the document's type, which only `check_document` does; every
other caller wants statement facts.

A purchase agreement is deliberately absent, and it is keyed by TYPE. So no pairing in `types.yaml` can
make a contract's figure pass: the guard does not depend on the library, which a tripwire on the library
would. That is why this is structural rather than the census test the review sketched.

**Tests** (`test_condition_evidence.py`, built from the real extraction models):

  naming its document;

## Review of the second follow-up (`c9425f67`)

**The structural guard is the right call, and better than the tripwire I suggested. One finding, on a
path this commit opens: the re-ask names every one of these documents "A corrected the statement".**

### The judgement you asked for: structural, not a tripwire — yes, and for three reasons

1. **It makes the unsafe pairing unrepresentable, not merely noticed.** A tripwire on `types.yaml` fires
   *after* someone writes the pairing, and then the argument is about the test. Keyed by document type,
   a contract's stated deposit reads no movement whatever any library item says. That is the difference
   between a guard and an alarm.
2. **It puts the fact where the semantics live.** "Whose stated amount *is* the money" is a property of
   a document type, not of which lender condition happens to ask for it. My suggestion would have
   encoded it in the wrong place and made every future library edit carry the question.
3. **It takes `_takes` off the correctness path.** `_takes` is about which item a document *links* to;
   it was never meant to carry evidence semantics, and resting stated-versus-verified on it coupled two
   unrelated concerns. Now `_takes` can change freely without touching this.

The comment naming stated-versus-verified as the reason is the part that will still be true in a year.

**Two residuals worth naming, neither a defect:**

- **The allow-list's own keyset is not pinned.** The risk has moved, correctly, from "a bad YAML pairing"
  to "a bad `OWN_AMOUNT` entry" — and `test_a_contracts_stated_deposit_never_satisfies_an_amount_check`
  pins exactly one adversary by name. Add a future stated-amount type (a settlement statement, a
  contract variant) to `OWN_AMOUNT` and every test still passes. This is where the tripwire *does*
  belong now: assert the exact keyset, as `test_deposit_findings_stay_on_one_item.py` does for
  `_COVERS_ITEMS`, so any addition is a moment where somebody looks at stated-versus-verified again. You
  moved the guard from the YAML to the code, which was right; the code's list now wants what the YAML no
  longer does.
- **`document_type` defaults to `None`,** so a future caller that *should* pass it silently will not. The
  mutation covers today's caller; it cannot cover tomorrow's. Keyword-only and required would be
  stronger, at the cost of churning eight call sites that legitimately want statement facts. Acceptable
  as it stands — but the default is the quiet direction, and the comment is what carries it.

### Finding — the re-ask calls a receipt, a gift letter and a deposit slip "the statement"

`reask` is **newly reachable** for these three types. Before this commit `amount_matches` was NOT_RUN for
them and `reask` refuses when nothing failed ("Nothing failed on this document."). Now a wrong amount
FAILS, the sheet offers the re-ask callout, and `reask_name` produces the item's name — which goes into
the borrower or third-party email. Measured, with the bank statement as the positive control:

```
earnest_money_receipt  amount_matches   -> 'A corrected the statement'
gift_letter            amount_matches   -> 'A corrected the statement'
bank_deposit_slip      amount_matches   -> 'A corrected the statement'
purchase_agreement     signed_and_dated -> 'A corrected the statement'
bank_statement         all_pages        -> 'Page 6 of the Capital One ··9912 August 2026 statement'
```

Two things are wrong with it. It calls a receipt a statement — the exact error this commit fixed one
function away, in the FAILED reason — and **"A corrected the statement" is not a sentence**: `what`
collapses to `"the"` when there is no bank and last4, so the article doubles. She is being offered an
ask whose name is broken English, and it is the name the third party reads.

`reask_name`'s fallback is `f"A corrected {what}{month} statement"`, and the fix is nearly free because
**this commit already computed the right word**: `Statement.source` holds "receipt", "gift letter",
"deposit slip". Using it there gives "A corrected the receipt" and leaves the statement case untouched.
The `all_pages` branch can stay as it is — only a paginated statement reaches it.

**Pre-existing, and widened here.** `purchase_agreement` + `signed_and_dated` already produced the same
string, so the defect did not start with this commit; but the commit adds three document types to the set
that can reach it, and it is the commit that created the field which fixes it.
