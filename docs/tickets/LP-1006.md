# LP-1006 — Hourly check

## What and why

After LP-1005, a customer's domain setup only moved when someone re-ran the command, and nothing noticed if a working setup later broke. A worker job now runs every hour and does three things:

- **Finishes setup on its own**, so nobody has to wait by the keyboard while DNS spreads.
- **Catches a broken setup**, for example a customer deleting their NS record, and pauses that company's email.
- **Never pauses on a hiccup.** A timeout, a DNS error, or AWS being busy changes nothing. Only a clear failure counts.

## The states table

`check_mail_domain` (`app/services/mail_domain.py`) returns what happened, for the log.

| Row | What the check does | Returns |
|---|---|---|
| No `zone_id` (linked by hand) | Nothing, in any state | `skipped` |
| `inactive` | Nothing | `skipped` |
| `pending_ns` | `advance_mail_domain`: once the NS record is live, writes the identity and records | `verifying`, or `pending_ns` if not live yet |
| `verifying` | `advance_mail_domain`: once SES has verified, goes active and switches sending on | `active`, or `verifying` if not yet |
| `active`, NS `wrong` or DKIM `failed` | Goes to `problem` | `problem` |
| `active`, otherwise (including any `unknown`) | Nothing | `unchanged` |
| `problem`, NS `ok` and DKIM `ok` | Goes back to `active`; `sending_enabled` stays as it is | `active` |
| `problem`, otherwise | Nothing | `unchanged` |
| An AWS error while advancing | Rolls back, logs the code | `error` |
| Someone else holds the row | Nothing | `locked` |

## What changed

**Provider (`app/services/domain_provider.py`).** Two new answers, which separate a clear answer from a hiccup:

- `delegation_state`: `ok` when the NS answer equals our four; `wrong` for a clear different answer, NXDOMAIN or no NS records; `unknown` for a timeout, SERVFAIL or any other DNS error. `is_delegated` now calls it.
- `dkim_state`: `ok` for DKIM `SUCCESS` and verified for sending; `failed` for DKIM `FAILED`; `unknown` for anything else, including an AWS error.
- The fake says `ok` to both.

**The lock (`lock_mail_domain`).** `SELECT … FOR UPDATE SKIP LOCKED`, which also reads the row fresh. The check and the command both use it, so they can't work on one row at once. The lock ends at the next commit, so each stage locks again.

**Send side.**
- `file_address_and_sending`: a `problem` domain keeps its file address.
- `transmit_blocker`: a `problem` domain gives "Email for this company is paused: its DNS setup changed. Contact support." So `can_send` is false, and the API refuses with that sentence (409).
- `tasks/outbound.py`, **not in the brief, needed for it to hold:** the worker re-checks just before sending, and that check only looked at the address. Once a `problem` domain keeps its address, an email queued before the problem would have gone out anyway. It now fails with the paused reason (error code `domain_problem`).

**Job (`app/tasks/mail_domains.py`).** `mail_domains.check_all`, every 3600 seconds, `expires: 3600`, registered in `celery_app.py`. It covers rows with a zone that are not `inactive`, and logs one summary line (`mail_domains_checked`: a total and counts per outcome). If the provider isn't allowed here (the fake outside development), it logs once and returns. One domain crashing doesn't stop the others.

**Terraform.**
- The three domain-setup statements moved out of the api role's policy into one document, `domain_setup`, in `infra/modules/compute/iam.tf`. Both roles use it through `source_policy_documents`, so there is nothing to copy. The api role's permissions didn't change, and it isn't in the plan.
- The worker gets that document and loses `DomainCheckRead`, which `DomainSetup` now covers. Why: the hourly check finishes setup, so it has to create identities and write records with nobody at a keyboard. Still no delete, and our own zone and identity stay denied.
- Staging sets `DOMAIN_PROVIDER = "route53"`, in the same conditional block as the other outbound mail settings.

**Review fixes.**
1. **`--replace` could collide with the job.** Forced on the dev database, in this order: the command reads `pending_ns`, the job moves it to `verifying`, the command replaces. Result: `mb-mail.right-review.example verifying zone=None`. The job then skipped that row forever, and both commands refused it. The brief's lock covered only the advance step, so `--replace` now takes the same lock first, which also re-reads the status.
2. **The emergency off was refused during a problem**, with the false message "no active mail domain; link one first". So sending resumed by itself on recovery, even if someone wanted it off. `set_email_sending` now allows off during `problem`. On is refused with the paused sentence. This was the user's decision, as an addition to the brief.

## Open

Found, not built, as the brief asks.

1. **A removed NS record may take up to 2 days to notice. This affects LP-1007.** Our Route 53 zone's NS records have a TTL of 172800 seconds (measured on `staging.mortgageboss.ai`), and new zones are expected to get the same default, not confirmed. LP-1007 expects "Remove the NS record → next check marks `problem`". It should measure the real delay. A possible fix is a short TTL on each customer zone's NS record.
2. **Setup takes at least two runs.** The job moves one stage per run, so after the NS record goes live it writes the records, and marks the domain active on the next run an hour later, even if AWS verified in minutes. Running the command by hand is still immediate, because it loops. A possible fix is for the job to advance until nothing changes, as the command does.
3. **Some permanent failures stay `unknown` forever, and nothing says so.** A deleted SES identity (`NotFoundException`) and a permissions error (`AccessDeniedException`) both measured `unknown`, as the brief specifies. From the code, a customer's NS pointing at dead servers gives SERVFAIL, also `unknown`. The domain stays `active` and Send stays on while SES may be rejecting the mail. The summary counts these as `unchanged`, and a DNS `unknown` logs nothing. A possible fix is to count `unknown` separately, and for a real alert, track how long it has lasted.
4. **The reason doesn't reach the screen.** The API refuses with the sentence, but the screen gets only `can_send: false`, so a processor sees "Mark as sent" with no explanation, and can still mark a message sent from their own mail. Showing it needs a new API field and a frontend change; the brief says no screen.
5. **The job can hit the worker's time limits in an outage.** The limits are 120 seconds (soft) and 180 seconds (hard). A domain can take up to about 25 seconds if AWS hangs (DNS 5, SES connect 5, read 15), so only about 7 would finish. Nothing is damaged, since a hiccup changes nothing and the next hour tries again, but the summary line isn't logged, and the domains later in the list aren't checked that hour. This won't come up with a few customers.
6. **The first run is an hour after the worker starts** (measured: a fresh schedule isn't due for 3600 seconds, and the schedule file in `/tmp` is lost on restart). Staging starts at 09:00, so the first check is about 10:00, and each deploy resets the hour. LP-1007 should expect this wait.
7. **A `verifying` domain whose DKIM has failed stays `verifying`.** The brief only checks DKIM on `active` and `problem`, so a setup that never verifies has no signal beyond its status.
8. **The worker's wider permissions are a trade-off, chosen in the brief.** The worker reads untrusted emails and documents, and can now change the records of any customer zone. If it were compromised, it could redirect a customer's mail subdomain. Our own zone and identity stay protected by the Deny.
9. **Carried from LP-1005:** nothing changes a customer's domain past `pending_ns`, or takes one fully out of use.
10. **The NS check can't see what the customer typed. LP-1007 must test this.** `delegation_state` asks a normal resolver, and the answer comes from our own zone, not from the customer's record. Measured on `staging.mortgageboss.ai`: the parent zone's record has a TTL of 1799; the resolver's answer and our zone's own answer both have 172800.
    - **Fewer names:** a customer who enters only 1 to 3 of the 4 names should still read as `ok`, because our zone answers with all 4. Worked out from the measurement, not tried with a real domain. Email would work, with less backup if servers go down, and nothing warns us. The "3 of 4" tests use a mocked answer, so they don't prove otherwise.
    - **Later edits:** missed too, as long as one of our names remains.
    - **Deleted record:** this is the cause of Open 1's delay.
    - **LP-1007 must:** enter only 3 names on the test domain and record what the check says; delete the record and record how long `problem` takes.
    - **Possible fixes, to choose from those results:** a short TTL on each customer zone's NS record (small; shortens the removal delay only), or asking the parent zone directly (more code; solves both).
11. **The job doesn't stop neatly at the soft time limit.** `SoftTimeLimitExceeded` is an `Exception` (measured), and the job's loop catches those per domain, so it counts as one failed domain and carries on until the hard stop at 180 seconds. That is why the summary line in Open 5 is lost. A fix is to catch it separately, stop the loop and log the summary (about 3 lines).
12. **One test depends on the shared test database being clean.** `test_the_job_checks_only_rows_with_a_zone_and_logs_one_summary` expects exactly 3 domains, and the job counts every row. A killed run that leaves a `Lock Co …` row makes tests fail until it is deleted. This happened once during this ticket.
13. **SERVFAIL has only been tested with a mock.** The real test name tried in the review (`dnssec-failed.org`) answered `NOERROR` from this resolver, so it proved nothing. The real SES answers (`ok`, and `unknown` for a missing identity) and the other real DNS answers matched.

## Doc changes (for `docs/email-communication/loan-email.md`, not edited here)

- §15b LP-1006: done. The job is `mail_domains.check_all`, hourly; the function is `check_mail_domain`; the states are in the table above.
- §15b LP-1004's result says the worker "may only read". That's replaced: the worker now has the same domain-setup permissions as the api role, because the hourly check finishes setup. Still no delete anywhere, and the Deny on our own zone and identity applies to both roles.
- `DOMAIN_PROVIDER=route53` is now in staging's task env. The LP-1005 one-off command's override is no longer needed, and does no harm.
- A hiccup never moves a domain: only a clear failure leads to `problem`.
- A `problem` domain keeps its file addresses, but doesn't send: the screen hides Send, the API refuses, and the worker fails a queued email.
- `set_email_sending`: off works during `problem`, and stays off after recovery; on is refused until the domain recovers.
- LP-1007: expect the first check about an hour after the worker starts, at least two runs to finish setup, and possibly a long delay before a removed NS record is noticed (Open 1, 2, 6).
