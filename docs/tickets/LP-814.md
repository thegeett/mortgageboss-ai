## The clock is `requested_at`, and the trap has two mouths

§1.4: *"A reminder keyed on `created_at` would nag about documents nobody has asked for yet."*
`request_needs_item` had existed since LP-19 with zero callers until LP-811a, so `requested_at` was
NULL on every row that had ever existed — every rule here would have been a query over an empty set.

And LP-819 **unwinds** `requested_at` on a hard bounce: the borrower never received the request, the
need goes back to `PENDING`, the stamp is cleared. That is correct, and it means a bounced request
correctly has **no clock**.

So the trap runs both ways. A rule reading `created_at` nags about a need nobody asked for; a rule
*falling back* to `created_at` when the stamp is NULL — which looks like tolerance — nags **hardest
about exactly the requests that bounced**, against a mailbox that does not exist, and every nudge
bounces too.

### The two tests named after the trap were passing on something else

`test_a_need_nobody_has_asked_for_is_not_suggested` and `test_a_bounced_request_produces_no_clock`
both build needs at status `PENDING` — which the status filter excludes anyway. Measured: swapping
`requested_at` for `created_at` in the query failed **one** test, and neither of those two.

`test_the_stamp_decides_and_not_the_creation_date` is the case only the clock can decide —
`REQUESTED`, created a month ago, requested yesterday. It was missing, and it is what actually pins
the claim the module is named after.

The `requested_at IS NOT NULL` clause turns out to be **redundant and is kept anyway**: SQL's
three-valued logic already makes `NULL < timestamp` unknown, so removing it changes no test. The
comment now says that rather than letting it read as load-bearing.

## Why there is no Celery beat

The plan says "Celery beat over `requested_at`". A beat that computes suggestions and writes them
changes nothing a read cannot do — it **suggests only**, so it has no side effect worth scheduling —
and it would be a table going stale the moment a document arrives, nudging about something that
turned up an hour ago.

What a beat *would* serve is reaching a processor who is not looking, and that is a notification
channel this product does not have. **Escalated** rather than built as a task nothing drains — which
is the shape this loop has now found five times.

The cross-file read is what makes rule 3 possible at all: *"this file has gone quiet"* is by
definition about a file nobody is opening, so a per-file endpoint could never surface it. A processor
would have to visit the file to be told they have not visited the file.

## What is stored, and what is not

**Suggestions are computed on every read.** The rules are a function of `requested_at`, the needs
list and the activity log; materialising them means a second copy that goes stale, and a processor
nudged about something already resolved is how a list teaches its reader to ignore it.

**What is stored is the decision** — the only fact a query cannot derive, because a person chose it.
Snooze and dismiss share one row: *"come back on Thursday"* and *"stop telling me"* are the same
decision at different distances, and two tables would make "is this suppressed?" two questions, the
second of which is the one somebody forgets.

The unique index carries **`NULLS NOT DISTINCT`**, because `subject_id` is NULL for a rule about the
file itself. Without it every "file untouched" snooze is a fresh row and none of them suppresses
anything — Postgres's default biting in the direction that makes a feature silently do nothing.
Tested by snoozing twice.

## The three rules, and the judgement in each

- **Pending > 3 days.** `status == REQUESTED` as well as the stamp: a need satisfied by a document
  arriving another way keeps its `requested_at` and is not waiting for anything.
- **No reply > 5 days.** *One suggestion per file, not per message* — a processor who sent three
  requests and heard nothing has one problem, and three cards for it is a list they stop reading.
  And "nothing since" means **nothing inbound after the send**, not "no inbound at all": a borrower
  who replied last month and has gone quiet since Tuesday is exactly what this is for.
- **File untouched > 7 days.** The **activity log** is the clock, not `loan_files.updated_at` —
  that column moves when a background job writes a status, so a file nobody has touched in a
  fortnight can look fresh. A file with no activity at all falls back to its creation, because it is
  genuinely untouched and skipping it would hide the newest files, which are the likeliest to have
  been forgotten.

Submitted and withdrawn files are never nagged about: a finished file is not a forgotten one, and
nudging about it teaches a processor to ignore the list.

**Days, not business days.** A borrower's weekend is not a working day for them either — the clock
is about how long somebody has been waiting — and a business-day count needs a per-jurisdiction
holiday calendar for a threshold nobody has calibrated.

## Deliberately not done

- **No Celery beat.** See above. **Escalated.**
- **No cross-file snooze.** A snooze is per (file, kind, subject). "Stop telling me about quiet
  files" as a company-wide preference is a different feature and would hide rule 3 entirely, which
  is the rule most worth keeping.
- **Thresholds are not configurable.** 3, 5 and 7 come from spec 4.5. Named constants rather than
  settings, because a per-company threshold is a decision nobody has made and a settings row nobody
  reads is worse than a constant somebody can find.
- **A suggestion offers no "send" action.** Spec 4.5 says suggests only. The card's actions are
  "put it off" and "stop telling me"; a test asserts nothing on it reads as having sent.

## For the reviewer

- **Tenancy** — every rule is company-scoped, and a named file is re-checked against the caller's
  company even though a scoped route resolved it. Snoozes are written through `ScopedLoanFile`.
  Tested both directions, including same-company-two-files for the file-level path.
- **Message content in logs** — this module logs nothing. A suggestion's summary is built from the
  need's **title**, which comes from a template or a processor, never from a borrower's message.
- **AI in the decision path** — none. Nothing here proposes what to say.

Worth a second measurement:

1. **The "one suggestion per file" collapse in rule 2.** It picks the newest qualifying send and
   asks whether anything inbound followed it. Please check the case of a send that bounced —
   `FAILED` is excluded from the query, so a bounced send does not produce a "no reply" card, which
   I believe is right and is the kind of thing worth disagreeing with.
2. **`_untouched` falls back to `created_at` for a file with no activity.** That is the opposite
   fallback to the one rule 1 refuses, and for a different reason — worth checking I have not
   reasoned myself into an inconsistency.
3. **The absence of a beat.** If you think the plan's "Celery beat" is load-bearing rather than
   descriptive, that is the finding.
