# LP-850 — outstanding means outstanding, and one draft per party

Status: spec. First of eight. **Blocks LP-851 and LP-852.**

Epic: [`docs/domain/communication/v1-epic.md`](../domain/communication/v1-epic.md) · Screens: [`v1-screens.md`](../domain/communication/v1-screens.md) · Spec: [`comm-v1-draft-only-spec.md`](../domain/communication/comm-v1-draft-only-spec.md)

## The report

> "Le's think about the flow of communication page. I think current flow is buggy. When processor
> click on individual document request button it check if there is any draft open, if so it adds
> requested document ask on that draft. If no draft is open it creates new draft."
>
> "How we would know whether previous draft is satisfied by receiving documents or not? Because we
> are not going to build or make it live receiving an email with document by email from borrower or
> other parties."
>
> "No two open draft for same party. Keep it simple."

## Two defects, one root cause

**Draft membership is being used as the source of truth for what is outstanding.** The needs list
already knows — it is literally the `needs_action` group — and the draft query re-derives the same
fact from a different table. The two disagree.

### D1 — a new draft supersedes nothing

LP-832 removed the `uq_communications_open_draft` partial unique index, so each request creates a
**new** draft carrying `outstanding + fresh`. Nothing retires the one it replaces. N clicks leave N
live, valid, sendable drafts with overlapping contents. Send Draft 1 and then Draft 3 and the
borrower is asked for the same bank statement twice.

The screenshot this produces is four rows reading *"A document request is being prepared"*, same
subject, same recipient, differing only by a timestamp — and **nothing marks 1 and 2 obsolete,
because nothing knows they are.**

### D2 — the outstanding set never looks at whether the document arrived

`_outstanding_needs` (`email_draft.py:866`) selects needs joined to a `Communication` where:

```python
Communication.loan_file_id == loan_file_id,
Communication.status == CommunicationStatus.DRAFT,
Communication.template_key == draft_template_key(party),
Communication.deleted_at.is_(None),
NeedsItem.deleted_at.is_(None),
```

**There is no filter on `NeedsItem.status`.** A need that is `received`, or `verified`, stays in the
outstanding set for as long as some unsent draft carries it — and is therefore carried into the next
draft and asked for again.

It only *looks* correct because marking a draft sent also clears the set: the needs drop out because
of **the send**, not because the document arrived. The two causes coincide often enough to pass a
demo and diverge in real use.

**This bites hardest in exactly our situation.** With no live inbound email, documents arrive by
manual upload or by the secure link — paths this query never looks at. And borrowers send things
unprompted, or after a phone call, so a document arriving *before* its request went out is ordinary
rather than rare.

## Decisions

**1. The outstanding set comes from need status, not draft membership.**

`_outstanding_needs` gains a filter: carry a need only while its status is `pending`, `requested` or
`rejected`. Anything `received` or `verified` drops out the moment the document lands — by upload,
by the secure link, or by a processor marking it — because the need's own status is what moved, and
the need's own status is now what is read.

The outstanding set becomes **identical to the `needs_action` group the screen already shows**. One
fact, one place.

**2. One open draft per party, enforced in the service.**

Not in the UI. LP-832's index could not express this because it keyed on the file, and a title
company's draft and a borrower's draft are both legitimately open at once. The constraint is
`(loan_file_id, party, status=DRAFT, deleted_at IS NULL)`.

**3. A request against an open draft has exactly two outcomes.**

Append to it, or mark it sent and create a fresh one. There is no "create a second open draft",
which is what removes D1 by construction rather than by asking a processor to be careful.

## The endpoint

The UI must not have to ask twice. A request returns either the draft it created, or a
**decision-required** response naming the open draft, its contents and its age — enough for
LP-851's dialog to render without a second round trip.

```
POST /loan-files/{id}/communications/requests
  { needs_type[], on_conflict: null | "append" | "mark_sent_and_new" }

201 { drafts: [{party, draft_id, needs_added[]}] }
409 { decisions_required: [{party, open_draft: {id, created_at, needs[], body_edited}}],
      would_create: [{party, address, needs[]}] }
```

`would_create` carries the parties that need no decision, so LP-852 can name them in the same
dialog. A 409 writes nothing.

## What it must not break

- **LP-832's composing rule stands.** A new draft still carries everything outstanding plus the new
  items. What changes is *what counts as outstanding*, and what happens to the draft being replaced.
- **LP-821's evidence record.** A superseded or marked-sent draft is never deleted. `mark_sent` is
  the existing transition, not a new one.
- **`party_requests.PARTY_ROLE` still excludes `PROCESSOR`**, deliberately — mapping it to anything
  would turn "we fetch this" into "we email somebody about it".
- **LP-835's party drafts stay reachable** from the same list and the same modal.

## Acceptance

1. **The test that fails today:** request a document, mark the need `verified` while the draft is
   still unsent, request a second document. The second draft contains **only** the second document.
2. Two requests in a row for the same party produce **one** draft, not two.
3. `on_conflict: null` with an open draft writes nothing and returns 409 with the draft's contents.
4. `mark_sent_and_new` leaves the old draft `sent` with its `requested_at` stamped and its needs
   intact, and the new draft carries only what is still outstanding.
5. A request spanning the borrower and the title company returns one 409 listing the borrower's open
   draft and the title company under `would_create`.
6. Marking a draft sent does **not** move any need to `received`. Sending is not receiving.

# What was built

Status: **done**. Backend only — LP-851 is the dialog that renders the refusal this ticket produces.

## The failing test, first

`tests/services/test_draft_lifecycle_lp850.py::test_a_need_verified_while_its_draft_is_unsent_is_not_asked_for_again`
was written and run against `phase4-with-ui` before any code changed. It failed, and for the stated
reason:

```
E       AssertionError: a need that is already VERIFIED was carried into the next draft
E       assert 'Bank statements' not in 'Hello $borr...ocessor_name'
E         'Bank statements' is contained here:
E           - Bank statements — the two most recent months
```

The fixture marks the need `verified` **without a send**, which is what separates the defect from
the coincidence that hid it — marking a draft sent also clears the outstanding set, so a fixture
that sent anything would pass either way.

## The changes

**`app/services/needs_items.py`** — `AWAITING_COLLECTION` (`pending` | `requested` | `rejected`).
One definition of "somebody still has to collect this", because it now has three readers.
`attention._AWAITING_NEEDS` imports it instead of restating it.

**`app/services/email_draft.py`**

- `_outstanding_needs` gains `NeedsItem.status.in_(AWAITING_COLLECTION)`. The draft join stays: the
  draft says what was *asked*, the status says what is still *outstanding*, and either alone is
  wrong. Reading status alone would return every pending need on the file, and after a send every
  need is `requested` — which is in the set — so a just-sent document would go straight back into
  the next email.
- `_addressed_to(party)` lifted out of `_open_drafts_stmt` and reused by `_outstanding_needs`. See
  "beyond the ticket" below.
- `OnConflict` (`append` | `mark_sent_and_new`), `NeedSummary`, `OpenDraftConflict`, `PlannedDraft`,
  `DraftDecisionRequired`, `draft_body_edited`.
- `add_needs_to_draft` gains `on_conflict`. It now **plans every party before it writes any of
  them**, so a refusal leaves the database exactly as it was and one refusal can describe the whole
  request.
- `_add_to_party_draft` became `_apply_party_plan`, with the three shapes: create, append, or
  mark-sent-and-create.
- `_mark_sent` calls the existing `send_draft` rather than assigning `status = SENT` — that is what
  stamps `sent_at` and `requested_at`, writes the activity row and writes LP-821's evidence record.

**`app/services/email_send.py`** — `send_draft` only calls `request_needs_item` for needs still in
`AWAITING_COLLECTION`. See "beyond the ticket".

**API** — `on_conflict` on `ComposeRequestPayload`, `RequestDocsRequest` and
`BulkRequestDocsRequest`; `DraftConflictPublic` in `app/schemas/communication.py`; all three routes
answer `409` with it.

## Acceptance

| # | Criterion | Test |
|---|---|---|
| 1 | verified while unsent → absent from the next draft | `test_a_need_verified_while_its_draft_is_unsent_is_not_asked_for_again` |
| 2 | two requests → one draft | `test_two_requests_in_a_row_for_one_party_produce_one_draft` |
| 3 | `on_conflict: null` writes nothing, 409 carries the contents | `test_an_open_draft_refuses_and_names_its_contents`, `test_a_refusal_writes_nothing` |
| 4 | `mark_sent_and_new` — old draft sent, needs intact, new one carries what is outstanding | `test_mark_sent_and_new_leaves_the_old_draft_sent_with_its_needs_intact` |
| 5 | borrower + title company → one 409, two rows | `test_a_request_spanning_two_parties_refuses_once_and_names_both` |
| 6 | marking sent moves nothing to `received` | `test_marking_a_draft_sent_does_not_move_a_need_to_received` |

Plus the direction the filter must not break: `pending`, `requested` and `rejected` all stay
outstanding (`rejected` especially — a document arrived and failed, and the borrower has not been
told), and `waived` drops out.

## Two things beyond what the ticket asked for, and why

**1. `_outstanding_needs` was matching on `template_key`, not on the party.** The ticket quotes that
`WHERE` clause and names only the missing status filter. But since LP-843 five parties share
`document_request_third_party`, so "the title company's outstanding documents" also returned the
lender's, the agent's, the CPA's and the insurer's — while `_open_drafts_stmt`, which decides
whether a draft is open for this party at all, reads the `party` column. Two definitions of one
audience, inside the function this ticket exists to correct, and LP-850 makes them answer in the
same breath: one decides whether to refuse, the other decides what the replacement draft carries.
They are one expression now (`_addressed_to`). Guarded by
`test_one_partys_outstanding_documents_stay_out_of_anothers_draft`.

**2. `send_draft` pushed an arrived need back to `requested`.** `request_needs_item` sets the status
unconditionally, so a need that was `verified` when its draft was marked sent was downgraded — and
`requested` is outstanding, so the document already in the file re-entered the next email by a
second route, defeating decision 1 through a door the ticket does not mention. Guarded by
`test_marking_sent_does_not_un_arrive_a_document_that_has_landed`.

Both are corrections inside the mechanism the ticket is about. Neither adds a feature.

## What was decided that the ticket did not cover

- **`body_edited` is `False` for now.** `draft_body_edited()` exists and returns `False` with the
  reason written into it: LP-853 adds `Communication.body_format`, and the decision there is that
  `body_format == 'html'` **is** this flag. Deriving one here by re-rendering and comparing would be
  worse than nothing — a template bump would report as a processor's edit, and LP-851's warning
  quotes the processor's own sentence back at them.
- **No new `POST /communications/requests` route.** The ticket sketches one. The contract it
  describes — one call returns the drafts or a decision-required refusal — is applied to the three
  routes that already make requests, because those are the three doors LP-851 wires up and a fourth
  route duplicating `compose` would be a second definition of the same act.
- **Deleting the only open draft drops its documents from the next request.** That is LP-832's own
  rule (`deleted_at IS NULL` in the outstanding-set query) applied to a model with one draft per
  party. The needs stay on the needs list. `test_a_deleted_draft_does_not_take_its_documents_into_the_next_one`.
- **The row lock is unchanged** and still the concurrency guarantee; LP-850 narrows what two
  concurrent requests can produce rather than replacing it.

## What was not done

- No UI. Every 409 above is currently unhandled by the frontend — that is LP-851, and until it lands
  the three request buttons will surface the conflict as an error rather than a dialog.
- `mark_sent_and_new` inherits `send_draft`'s rate limit (three sends per address per day). A
  processor cycling through it quickly will be refused with the rate-limit message. Left alone
  deliberately: it is the existing transition, and weakening the limit is not this ticket's call.

# Review (second session)

Reviewed at `10982bce` by a second session, against the six points the author raised plus the
tests. Everything below was **measured** — each finding has a test that fails without its fix.

## What was wrong

**1. The 409's payload never reached the client.** `app/core/errors.py` built the envelope with
`message = exc.detail if isinstance(exc.detail, str) else "Request failed"`, so the dict detail the
three routes pass — the whole `DraftConflictPublic` — was discarded. The client received
`{"error": {"type": "conflict", "message": "Request failed"}}` and none of the contents.

This is the ticket's headline contract ("enough for LP-851's dialog to render without a second
round trip") and LP-851 could not have been built on it. It survived review because every
assertion about the refusal reads the EXCEPTION OBJECT at the service layer; nothing asserted the
HTTP response. Fixed by giving the envelope an `error.data` for structured refusals (a string
detail behaves exactly as before), and `DraftConflictPublic` now carries a `message` so the
fallback sentence is answerable. Guarded by `test_the_409_body_is_what_the_dialog_will_render`.

**2. `party_requests.build_party_draft` created a second open draft for a party.** It looked its
existing draft up by `template_key == template_key_for(party)` — LP-841's legacy key — while
`email_draft` has written LP-843's key since that ticket. Measured across all eight parties, only
`employer` matched. So a title company with a draft from the request flow got a second one here:
decision 2 broken, through a module LP-850 did not touch.

It is the third instance of one defect. `_legacy_draft_keys` records it for LP-843's compatibility
arm ("only `employer` matched"), `_outstanding_needs` records it for LP-850 itself, and this was
the one nobody looked at. The lookup is now `get_open_draft`, the same one the other two use.
Guarded by `test_a_party_draft_joins_the_one_email_draft_made_rather_than_forking_it`.

**3. That fix exposed three defects in `build_party_draft`'s own renderer**, which had to be fixed
with it rather than after: it rendered from `request.needs` (`PENDING|REJECTED`) instead of the
draft's membership, so a carried-forward `REQUESTED` need stayed joined to the draft and vanished
from its words while `send_draft` still marked it; it dropped `upload_link_url`, which is LP-834's
unrecoverable-link defect; and it stamped `template_version` without `template_key`, which is the
ADR-401 pair LP-848 put back together. All three go away by calling `_regenerate`. The draft is
also now CREATED with `draft_template_key(party)` rather than written with the legacy name and
corrected by the next rewrite.

## What was already right

- `_outstanding_needs` intersects draft membership with `AWAITING_COLLECTION` correctly, and the
  join genuinely is load-bearing in both directions. All six `NeedsItemStatus` values are
  accounted for: `received`, `verified` and `waived` are out, and nothing is left over.
- `mark_sent_and_new` does compute the carry-forward before the send.
- `send_draft` no longer downgrading an arrived need is right, and the skipped statuses are exactly
  the three that should be skipped.
- `_addressed_to` is a correct unification of the two predicates it replaced.
- **A 409 really does write nothing**, including the needs rows `compose_request` creates before
  the draft — verified against the database. The guarantee rests entirely on `get_db`'s
  `except Exception: await session.rollback()`, which nothing in the suite exercised, because every
  API test overrides `get_db` with a bare `yield db` that never rolls back. Now pinned by
  `tests/api/test_get_db_rollback_contract.py`, with a positive control.
- `body_edited` returning a hardcoded `False` is honest, not a placeholder standing in for
  something broken: nothing can edit a draft body today (the only body writes happen at send, and
  a sent draft is no longer a draft), so `False` is the true answer until LP-853's column exists.
- The four tests changed to pass `on_conflict` all kept the assertion they were written for — the
  membership count of 2 and "one list containing both documents" survive in each.

## Left alone deliberately

**`mark_sent_and_new` carries the old draft's documents into the new one; marking sent and then
requesting does not.** Measured on the same two acts:

| | new draft carries |
|---|---|
| mark sent, then request | `Pay stubs` |
| `mark_sent_and_new` | `Bank statements`, `Pay stubs` |

Both readings are defensible — one is a follow-up restating what is still missing, the other is
this epic's own rule that "the set resets at a send" (LP-832, confirmed with the user) — and the
divergence is a product decision rather than a defect a reviewer should settle. Flagged to the
author; not changed.

### Settled: the carry-forward stays, and the asymmetry is correct

The reviewer was right to refuse to settle this in a review. The answer is that the two acts are
different acts, and the epic decides it — twice.

**The deciding argument is that the reset makes acceptance 1 vacuous.** Move the `_outstanding_needs`
call to after `_mark_sent` and there are no open drafts left to read, so the carry-forward is
*always* empty and the new draft *always* contains only the new document. Acceptance 1 would then
pass with `NeedsItem.status.in_(AWAITING_COLLECTION)` deleted from the query — verified by removing
it. The ticket says of exactly this: *"It only looks correct because marking a draft sent also
clears the set... **Do not 'fix' it by also clearing drafts on send; that is the coincidence that
hides it.**"* Reading the set after the send is that coincidence, reintroduced as the design.

Measured, by mutating the code rather than by reasoning about it:

| mutant | `test_a_need_verified_while_its_draft_is_unsent_is_not_asked_for_again` |
|---|---|
| `NeedsItem.status.in_(AWAITING_COLLECTION)` deleted, read before the send | **fails** |
| the same deletion, with the read moved to after `_mark_sent` | **passes** |

So the filter is load-bearing where the call is, and stops being load-bearing under the reset. That
is the whole ticket.

**And the product reading agrees.** LP-832's "the set resets at a send" describes a request made
*later*, as its own act: time has passed, the borrower has had the email, and the next request is a
new conversation. `mark_sent_and_new` is not that. It happens *inside* one request — the processor
is part-way through asking for a document, is told a draft is open, and says "I already sent that
one". The replacement draft is the continuation of the act they are performing, and what it carries
forward is what the borrower has been asked for and has **not sent**. Anything they did send has
already dropped out, because that is this ticket.

That is `email_draft.py`'s founding principle applied, not contradicted: ONE EMAIL, NOT FOUR. A
borrower who ignored the first message gets one message listing everything outstanding, rather than
one about `A, B` and a second about `C` alone.

No code change. `test_mark_sent_and_new_leaves_the_old_draft_sent_with_its_needs_intact` already
pins the carry-forward as non-empty, which is what stops the reset being reintroduced quietly.
