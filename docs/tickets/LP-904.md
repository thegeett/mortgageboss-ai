## Decisions worth arguing with

**`round_number` is assigned on IMPORT, not on arrival.** Two drafts can exist at once — an upload
and a paste — and numbering on arrival would either renumber on import or leave gaps where a draft
was discarded. It is null until imported, with a **partial** unique index over
`(loan_file_id, round_number)` restricted to `round_number IS NOT NULL AND deleted_at IS NULL`.

⚠️ *Corrected in review, and the first version was wrong in the expensive place.* The predicate also
carried `status = 'imported'`. **`DISCARDED` is a live status, not a deletion** — so an imported
round later discarded keeps its number but leaves the index, freeing that number for reuse. Because
`condition_events` is append-only, the discarded round's `ROUND_IMPORTED` event survives forever, and
two different sheets end up recorded as "round 2" in an immutable history with nothing able to
separate them. The clause also bought nothing: the case it was written for is a discarded **draft**,
whose `round_number` is NULL and which never conflicts anyway. Nothing constrains the import →
discard transition — no state machine, no service layer yet — so the predicate *is* the rule, and
the rule was wrong as written. `deleted_at IS NULL` stays: a soft delete is a deliberate act by a
person, so releasing the number there is a visible consequence rather than a side effect.

**`sources` is a list, not a field.** A pasted round whose PDF arrives later *merges into that round*
(LP-907) rather than starting a second one, so the round carries every way it arrived.

**`company_id` is on `condition_rounds` and `conditions`, and deliberately NOT on
`lender_condition_codes`.** Most file-owned children scope transitively (ADR-052) because they are
only ever reached through their parent. A round and a condition are reached by id from
`/api/condition-rounds/{id}` — there is no parent in the request to scope against, so the column is
what `scope_to_company` filters on. A code row is only ever reached through its lender, which carries
one. That asymmetry is stated in each model rather than left to be inferred.

**`lender_code` is `String(16)`, never an integer.** UWM prints `0006`. The leading zeros are part of
an identifier printed on a document; normalising to `6` is a silent loss that resurfaces months later
as a failed match (ADR-407).

**`verbatim_text` keeps the underwriter's notes; `text_fingerprint` excludes them.** The lender wrote
one string, so the text keeps it whole. The fingerprint is taken with the note spans removed, which
is what lets a condition that *came back* still match as the same condition. It is also why the text
never has to be compared in SQL — a fact that corrected ADR-405's reasoning in LP-903's review.

**Both status fields exist now and nothing moves them.** `prep_status` and `lender_status` are
created with defaults here because this is where the schema is designed; leaving them for Stage 2
would mean a second migration over a table that by then has rows. Stage 1 writes them once (ADR-404).

**The CHECK constraints are spelled out by hand.** `str_enum` sets `create_constraint=True`, but that
only materialises through `Base.metadata.create_all` — which is what the suite builds from, and
precisely why an enum/database mismatch is invisible to it. `tests/test_activity_type_migrations.py`
exists because of exactly that class of bug.

## The readonly views, and two things the guard taught me

All four tables are exposed (`EXCLUDED_TABLES` is empty by design — every application table gets a
view), with the NPI columns dropped rather than scrubbed: `readonly.scrub()` matches identifier
*shapes*, and a condition quoting an employer or a street is not digit-shaped, so it would cross a
scrubbed view intact.

**⚠️ The drift guard caught a real defect in my first view.** `condition_rounds.sources` was written
as `jsonb_array_length(sources) AS source_count`, and `test_no_model_column_drifts` failed — correctly.
`_output_columns` reduces each select item to the name it comes *out* as, precisely so a column
"mentioned in a predicate about itself" is not counted as exposed. The guard was right and the honest
fix was to expose `sources` whole: it holds arrival kinds, timestamps and internal ids, with no
borrower or lender content, and "how did rounds arrive, pasted or uploaded?" is a real question.

**⚠️ `NEVER_EXPOSED` is a text check over every view, which forces a choice per column.** Adding all
six NPI columns to it turned 1 failure into 6. The check searches the select-list *text*, so any
derived scalar over a column trips it — and `condition_events.detail` can never be listed at all,
because `activity_logs.detail` is a different table's column legitimately exposed in its own view.
The repo had already recorded this trade twice, in both directions:

| Precedent | Choice |
|---|---|
| `style_profiles.exemplars` — *"`cardinality(exemplars)` would trip the NEVER_EXPOSED text check, so the migration chose the guarantee over the metric"* | guarantee |
| `communication_evidence.attachment_manifest` — `EXCLUDED` and counted in the view, not in `NEVER_EXPOSED` | metric |

So: **`conditions.verbatim_text` takes the guarantee** (no `length()` of it anywhere; it is the
lender's prose, the class `findings.source_snippet` is in). **`raw_text`, `header`, `draft_rows` and
`underwriter_notes` take the metric** — "did the parse find a header", "how many rows await review",
"how often do conditions come back" are the questions these views exist to answer, and each needs its
column named in a predicate to produce the count. All five remain in `EXCLUDED`, so
`test_no_model_column_drifts` still forces a decision on each.

### Why `ROUND_ENRICHED` may exist unwritten when `condition_cleared` may not

The append-only test asserts that `ConditionEventKind` contains no `condition_cleared`,
`condition_removed` or `round_compared` — an enum member nothing writes is an invitation. But
`ROUND_ENRICHED` **is** in the enum and nothing in Stage 1 writes it either: LP-907's attach-PDF
merge is what produces it. Raised in review, and the distinction is worth stating rather than leaving
as an inconsistency.

**The test to apply is: could a reader of this row infer that the lender answered?**

That question separates the four items. The first draft of this section said the forbidden kinds were
"verdicts about a condition's fate", and ⚠️ *that rule fails on its own list* — `round_compared` is
not a verdict about any condition's fate; it is a round-level operational fact, **the same category
used to justify keeping `ROUND_ENRICHED`**. A rule that does not separate the items it is offered to
separate is the version a later reader stretches, and `round_compared` is precisely what would have
slipped in under it.

| Kind | Could a reader infer a lender answer? |
|---|---|
| `condition_cleared`, `condition_removed` | **Yes — it states one.** ADR-404's reserved claim, and the one a processor acts on. |
| `round_compared` | **Yes — it manufactures one.** Comparison is the mechanism that produces "this one is gone, so it probably cleared". A row in the history is evidence the inference ran, which the boundaries doc says Stage 1 never does. |
| `ROUND_ENRICHED` | **No.** It says a second arrival merged into a round. Merging provenance cannot be read as the lender speaking, by anyone, later. |

So `ROUND_ENRICHED` stays and the assertion stays at four kinds — but the reason is the question
above, not the category. Anyone adding an event kind should answer it before adding the member, not
after.

⚠️ **There was no append-only test to copy.** The spec says to copy `finding_event.py` "and its
tests". The model exists; the tests do not — every suite touching `FindingEvent` only *reads* event
rows to assert a lifecycle. This guard was written from scratch, and it says in its own docstring what
it does **not** check: LP-904 ships no service layer, so "cannot be updated through the service layer"
has no service yet. The assertions are about the mechanism that makes a mutating service
inexpressible. The service-level test belongs beside LP-909's import.

## NOT verified, and it is the same limit as LP-1000

**`alembic upgrade head` and `downgrade` have never run.** No local Postgres, and nothing in the suite
exercises migrations — `tests/conftest.py` builds its schema with `Base.metadata.create_all`, which is
exactly why an enum/CHECK mismatch is invisible here. So the DDL in `d1f4b8c25e93` is **unexecuted**:
the `CREATE TABLE`s, the partial unique index, the five views and the whole downgrade path are
reasoned from the pattern in `a6c3e8d47f21`, not observed working.

The DB-backed tests (`tests/models/test_condition_*`) **collect but do not run** here for the same
reason. CI runs a real Postgres service, so the PR is the first execution — and the first line to read
in that job is whether the migration applies at all.
