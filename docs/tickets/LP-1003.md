# LP-1003 — One shared extractor implementation, tested once

**Status: not started.** Planned from the test-suite review that produced LP-1002.

## Problem

The extractors under `app/ai/extraction/` are 118 copies of one template: 100 emitted by the LP-434
generator (they carry its `GENERATED` marker) and 18 hand-written, 27.7k lines in all. Each module
repeats the same mechanism: check the media type, load the prompt, call `run_extraction_completion`,
parse JSON into a typed core plus a catch-all, mark an all-null core `FAILED`, never raise, and log
metadata only. Only the schema (field list and types), the prompt path, `max_tokens` and the log label
differ.

Because the code is copied, the tests are copied too. After LP-1002, the 118 test files still hold
five template tests each, about 575 tests that check the same mechanism once per copy:

| Template test | Copies |
|---|---|
| `test_extract_ai_failure_returns_failed` | 118 |
| `test_parse_unparseable_returns_none` | 117 |
| `test_extract_success` | 117 |
| `test_all_null_core_is_failed` | 114 |
| `test_typed_core_coerced_with_source` | 100 |

The copies can't simply be deleted: while each extractor is its own code, each copy of a test is that
extractor's only check. The code has to be shared first.

## Proposal

1. **A generic extractor.** One `extract(spec, content, media_type)` (or an `Extractor` built from a
   per-type config: extraction model, core field spec, prompt path, `max_tokens`, log label) that owns
   the mechanism above. Each type's module keeps only its Pydantic model and config.
2. **Move the generated extractors first.** They are mechanically identical by construction, so moving
   them is low-risk. Then change the generator to emit a config rather than a module.
3. **Hand-written extractors one at a time.** Several have real special cases: `bank_statement`
   (chunked), `w2` and nested lists with count cross-checks (LP-443/445), the four identity documents
   consolidated by LP-472, and `pay_stub`/`tax_return` field logic. Each moves only if its special
   case fits a hook. Otherwise it stays hand-written, along with its own tests.
4. **Tests.**
   - Test the generic mechanism once, thoroughly. That includes `.failed()` confidence/empty data,
     which LP-1002 left unchecked.
   - Add one parametrized test over `EXTRACTORS` that checks each type is wired up: its config loads,
     its prompt file exists, and a full sample payload parses to `SUCCEEDED`.
   - Delete the per-type copies of the five template tests. Keep every test that isn't one of those
     five: the per-type logging, nested-list and field-specific tests.

## Expected effect

About 575 fewer test cases, minus the roughly 120 that the wiring test adds back (one per type), and
roughly 20k fewer lines across app and tests. Re-measure both before starting; these are counts from
2026-10-29.

## Risks and checks

- **Behaviour must not change.** Before moving anything, record each extractor's output on the
  fixture payloads, then confirm the output is identical after the move. A green test run alone is not
  enough, because the tests being deleted are the ones that would have noticed.
- **Prompts and `max_tokens` are per type.** A config typo would silently send the wrong prompt. The
  wiring test must check each type's prompt path and limit against the current values.
- **PII logging.** The "never log values" guarantee becomes shared code. Keep the per-type
  `test_does_not_log_*` tests until the shared version is proven on a type with PII (DOB, SSN, account
  number).
- **Other readers.** Check what reads these modules besides `EXTRACTORS`: the generator's diff mode,
  the LP-440 marker test (`tests/ai/generator/test_lp440_generation.py` reads modules by the
  `GENERATED` marker), and the dev extraction bench.
