# LP-801 — Requestable-finding filter, one `docs_requested` shape, one activity type

- **Ticket:** LP-801 · Phase 4, M1, ticket 2 of 26
- **Status:** Built — awaiting review
- **Date:** 2026-09-06
- **Plan:** [`phase4-build-plan.md`](../phases/phase4-build-plan.md) LP-801 section
- **Design:** [`phase4.md`](../phases/phase4.md)
- **Scope:** `services/finding_requests.py` (new), `services/finding_resolution.py`,
  `api/verification.py`, `verification/rule_engine/result.py`,
  `verification/rule_engine/consistency.py`, `services/rule_findings.py`, `decisions.md`
- **Migration:** none — see "Why no migration" below. The plan allowed for one.

Three defects that share one cause: nothing downstream of a document request could tell what had been
requested, or from what, or whether it should have been requested at all. Phase 4 drafts an email from
exactly that information, so all three become load-bearing at LP-810.

---

## What was done

### A `requestable` predicate, and where the gate lives

`services/finding_requests.requestable(finding)` — false for the consolidated unidentified-document
finding, true otherwise.

That row (LP-640) is real work, but it is the **processor's** work. "Identify these files" is answered
by setting document types on files already in the loan file; a request generated from it asks the
borrower to re-send documents they have already sent, in words naming nothing they could act on.

The gate is in the **service**, not the endpoint. Both request routes go through
`services/finding_resolution`, and Phase 4's drafting engine will be a third caller that never touches
an endpoint. The two routes refuse differently, and deliberately:

- `request_docs_for_finding` **raises** `NotRequestable`; the endpoint returns **409**. That route has
  a processor standing in front of one specific finding, and a quiet 200 that created nothing looks
  on screen exactly like a request that was made.
- `request_documents_in_bulk` **drops** the finding and honours the rest. "Request all N" is a bulk
  verb; failing the whole action over one ineligible member would be worse than the thing it prevents.

### The `docs_requested` shape, unified

`docs_requested_marker(actor_user_id=..., needs_item_id=...)` produces the one value both paths write:
`{by, at, needs_item_id}`.

The bulk path wrote a bare `True`. This never looked wrong: the frontend reads
`Boolean(details.docs_requested)`, which is true for either, and its declared TypeScript type already
said `{ needs_item_id?: string } | null` — so the type was a description of one path and a fiction
about the other. What was lost is the forward link from the finding to the thing the borrower was
actually asked for, which is what a draft follows.

### The activity type, fixed

The bulk path logged `ActivityType.FINDING_RESOLVED` for an action its own docstring says does not
resolve the finding. The Phase 4.3 timeline is built on this log, so every bulk request read there as
a resolution of findings that are still open. It now logs `NEEDS_ITEM_CREATED`, matching the
per-finding path, and its `detail` carries `needs_item_ids` so the timeline can link rather than
re-derive from titles.

### ID-2 / ID-3 / ID-4 ask for "one more source"

`consistency.py`'s single-source abstention recorded `"Another document stating the <fact>"`. Now
`"One more source stating the <fact>"`, and `"A source ..."` where the file has none.

The count distinction stays — with one source you need one more, with none you need a first — and the
change is the noun. What that branch is short of is a second *statement* of the fact, and the borrower
has no way to know which of their papers carries it: a payslip, a bank statement and a utility bill
can each state an address. Naming a document type would be the engine guessing on their behalf, and
LP-810 puts this string in front of the borrower verbatim.

## Why no migration

The build plan says "Migration: possibly one", and prefers persisting the cause on the finding. It is
not needed, and ADR-399 records why: the per-rule abstentions carrying `unidentified_document` never
become findings. `consolidate_unidentified_documents` replaces all of them with one loan-level
evaluation under `UNIDENTIFIED-DOCUMENTS` **before** any write, on both persistence paths
(`persist_evaluation_findings` and `reconcile_evaluation_findings` — checked, not assumed). A new
column would be `True` on exactly one row per file: the row that rule id already names, on an identity
LP-640 made stable precisely so the reconciler could carry it across runs.

The plan explicitly delegates this ("decide in the ticket and write the ADR"), so this is the plan
being followed rather than departed from.

The constant moved from `services/rule_findings` to `verification/rule_engine/result`, beside the
in-run flag it is the persisted form of — so the two cannot drift apart in separate files, and the
read layer can reach it without a schema importing a service. `rule_findings` re-exports it.

## What was already right, and why it still needed writing down

Before this ticket, no request was in fact generated from the unidentified-document row. That outcome
came from two accidents:

1. the synthetic rule id carries no spec file, so `_missing_documents` returns `[]` for it; and
2. `rule-finding-row.tsx` hides the request affordance on any `couldnt_check` finding.

Neither is a statement that this finding must not be requested from, and neither survives someone
giving the synthetic id a spec. The predicate is the statement. This is also why the frontend needed
no change: it was already correct, for reasons that were not about this rule.

## Tests

`tests/services/test_finding_requests_lp801.py`, plus one API-level test in
`tests/api/test_verification_endpoints.py` — the refusal is asserted at the layer a processor clicks,
not only in the service.

Every negative assertion is paired with a positive control, because "no request was created" is also
what a broken fixture produces:

- `requestable` is false for the consolidated id **and** true for `CR-6` — without the second, a
  predicate that returned `False` for everything would satisfy every other test here.
- The bulk drop test passes two documents and asserts the *other* one was created.
- The activity-type test asserts `NEEDS_ITEM_CREATED` is present as well as `FINDING_RESOLVED` absent
  — an absence assertion alone would pass if the function stopped logging entirely — and then asserts
  the needs item is actually on the file.
- The two paths' markers are compared to **each other**, not each to a literal; two parallel literal
  assertions can drift together and both keep passing.

Verified by mutation, each one killed:

| Mutation | Result |
|---|---|
| `requestable` returns `True` unconditionally | 4 tests fail |
| bulk logs `FINDING_RESOLVED` again | 1 test fails |
| bulk writes a bare `True` again | 3 tests fail |
| phrasing reverted to "Another document" | 2 tests fail |

## Assumptions

- **A finding contributing to two documents links the first item.** `needs_item_id` is singular
  because the per-finding path is 1:1 and the frontend's declared type is singular. The bulk path can
  produce two items for one finding (`CR-6` with two unsatisfied document groups); it marks the
  finding once, for the first. The other link exists in the other direction — every needs item's
  `reasoning` names the rule ids waiting on it. If LP-810 turns out to need all of them forward, that
  is a shape change and a frontend change together, and it should be made once rather than half-made
  here.
- **Dropping a bulk member silently is right.** The endpoint returns the whole verification status, so
  the processor sees which findings are now marked; there is no per-member error channel in the
  response shape and inventing one is outside this ticket.

---

## Deliberately not done

- **No frontend change.** See above — the UI was already correct.
- **No new schema field.** `RuleFindingPublic` does not gain `requestable`. Nothing would read it: the
  card already hides the affordance for these findings, and adding an API field with no reader is the
  failure mode this repo has hit before.
- **No change to the bulk dedupe.** A finding whose document was already requested by an earlier click
  still gets no marker (`slug in existing` skips before the marking loop). That is a real gap — the
  finding stays unmarked while the borrower has in fact been asked — but it predates this ticket, is
  about the dedupe rather than the shape, and fixing it changes what "requested" means for a
  second-click case. Recorded here rather than absorbed.
- **No revisit of `FINDING_RESOLVED` elsewhere.** Only the bulk request path was mislabelled.

## For the reviewer

The three standing reviewer checks:

- **Tenancy** — no `company_id` derivation in this diff. Both service paths take an already-resolved
  `loan_file` / `finding`; LP-805 remains the only resolver.
- **Message content in logs** — no logging added. The one activity `detail` that changed carries needs
  item titles (internal document labels from the catalog) and needs item ids. No body, no subject, no
  external filename.
- **AI in the decision path** — none. `requestable` is a string comparison on a rule id.

The judgement calls worth a second opinion, in the order I would attack them:

1. **ADR-399's "no column" decision**, which is the one place this ticket departs from the plan's
   stated preference. It rests on a claim that is checkable: that no `unidentified_document` result
   ever reaches a write without being consolidated first. If a third persistence path exists, or one
   is added later, the predicate silently under-covers.
2. **The first-item link** for a finding spanning two documents. The alternative is a list, which
   means changing the per-finding shape and the frontend type in the same breath.
3. **Whether the bulk path should refuse loudly** rather than dropping. I think not, but the argument
   is not one-sided: a processor who selects five findings and gets four items has no way to learn
   which one was ineligible.
