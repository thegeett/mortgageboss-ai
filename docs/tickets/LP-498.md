## Phase A — findings

### A1 — FR-1: **outcome 1. The tag cannot see what it is asked about.**

`fraud.altered_appearance` is declared *"Document shows alteration/formatting anomalies"* — font
inconsistency, misaligned text, a pasted figure, an inconsistent typeface.

`_doc_context` (`tag_materialization/subjects.py:169`) is what a document-subject AI group receives:

```python
fields = {"document_type": raw.document_type}
for name, field in raw.fields.items():        # extracted typed values
    ...                                        # PiiField -> masked display only
if opts.include_lists:   fields["lists"] = ...            # nested tables
if opts.include_untyped: fields["untyped_extraction"] = ...  # Tier-3 free extraction
```

Extracted **values**. No page image, no layout, no coordinates, no typeface, no rendering. **None of
the anomalies the tag names survives extraction**, so the tag cannot answer its own question. This is
AS-4's shape (LP-497) a second time: a tag scoped where its subject is not visible.

**But the pipeline CAN see a rendering, and the answer should be precise about that.** Two shipped
paths take document **bytes** and send them to the model:

- `app/ai/classification.py::classify_document(content, media_type)`
- `app/ai/generic_analyzer.py::analyze_document(content, media_type)` — Tier-3, capped by
  `cap_pdf_pages(content, media_type, settings.tier3_max_pages)`

Both accept `application/pdf`, `image/png`, `image/jpeg`. So alteration detection is **architecturally
possible** — at the **document-analysis layer**, not as a snapshot AI-group tag. The cost is another
full-document model call per document, on top of classification and extraction.

**And reshaping FR-1 to "internal consistency from extracted fields" (outcome 2) would duplicate a
shipped mechanism, exactly as the ticket warned.** `app/ai/extraction/consistency.py` (LP-474) already
does it: declaration-driven `MustDiffer` pairs — two extracted values a document's structure says must
differ, coming out equal → a `CONSISTENCY` finding. **Deterministic, no model call**, and *"proven on
the stored v2 corpus at ZERO false positives"*. Adding a check is one line in `CHECKS`, not a rule.

**Recommendation: do not build FR-1.** A judgmental, model-driven version of a check that already
exists deterministically at zero false positives would be strictly worse on the axis this cohort cares
about most — accusing on thin evidence.

### A2 — FR-6: the declaration shape exists; the production path has never run

| | |
|---|---|

does not apply. Nothing distinguishes a real discovery from a fabricated one at the point of
production.

**Recommendation: hold, and scope the mechanism in its own ticket with an ADR.** Do not build it
inside a build phase — the ticket says so and the shape confirms it.

### A6 — the systemic finding: the tag→rule metadata does not match the specs

The ticket warns that four tags are read by live rules and that any producer change is a change to
live behaviour. **All four warnings are void**, and the reason is a defect worth more attention than
the rules themselves.

`fact_tags.csv`'s `used_by_rules` column and `rule_tags.csv` are both **generated from the xlsx** —
authoring metadata. The authoritative statement of what a rule reads is its **spec's**
`load_bearing_tags` / `judgment.tags`. They disagree:

| tag | metadata claims | the specs actually say | live reader? |
|---|---|---|---|
| `title.rapid_transfer` | TI-6, FR-2 | TI-6 reads `title.chain_has_gap`, `chain_shortest_interval_days`, `chain_transfer_count` | **none** |
| `txn.implies_obligation` | CR-1, FR-4, FR-5 | CR-1's spec reads **only** `liab.in_application` | **none** |
| `txn.is_recurring` | CR-1, FR-5 | as above | **none** |
| `txn.counterparty` | AS-2, AS-5, AS-12, FR-5 | AS-12's judgment reads `txn.apparent_category`, `txn.has_identified_source` | **none** |

None of the four has a producer either. **The blast radius for all four is zero.**

This is the **third instance this session** of generated metadata contradicting the specs — LP-497
found it for AS-4 / `stmt.is_reserve_eligible` (a bar naming a load-bearing tag that fed nothing), and
LP-498 finds four more. It has now caused a rule to be held for three tickets (AS-4) and would have
caused four spurious blast-radius investigations here. **Recommend a drift test** asserting
`rule_tags.csv` agrees with the specs' declared tags, so the two cannot diverge silently.

### A4 — FR-4 and FR-5 both read the wrong surface

`_txn_context` (`subjects.py:143`) is the entire transaction context:

```python
return {"date": ..., "amount": ..., "direction": ..., "description": ...}
```

Four fields, for **one** transaction. No account, no statement period, and **no other transactions**.

- **FR-5 is unanswerable at this scope.** `txn.is_recurring` is declared *"Does this appear to be a
  recurring debit/credit (**pattern across statements**)?"* — and recurrence is by definition a
  property of a set over time. A context showing one date, amount and description cannot establish
  that anything recurs. Third instance of the AS-4 class in this ticket alone.
- **FR-4 reads the wrong document entirely.** A garnishment on a **pay stub** is a deduction line —
  the corpus carries these as `pay_stub:deduction_lines` (LP-497 measured that list). But
  `txn.implies_obligation` is a **transaction** tag, and transactions come from bank statements. FR-4
  as specified asks a bank-statement tag about a pay-stub fact.

Every figure in the ticket is confirmed:

> "If the re-sale date is **90 days or less** following the date of acquisition by the seller, the
> property is **not eligible** for a mortgage to be insured by FHA."

91–180 days: eligible, but where the resale price exceeds the purchase price by **100 percent or

**This is FHA only.** Conventional has no codified 90-day rule. Recorded for TI-6's owner: its

## Phases B–E — what was built

**FR-3 activated. FR-1, FR-2, FR-4, FR-5 and FR-6 held.** `ACTIVE_RULE_IDS` 74 → **75**.
**Total model spend: 16 calls ≈ $0.06** (two derivations of 4 cases, run twice — see below).

### The malformed declaration, fixed first

`contract.unusual_credits` was declared `enum: yes | no + detail`, which parses to the **literal value
`"no + detail"`** — a value no model would return and no rule could match. LP-495c catalogued it and
left it because the tag was unmaterialized; materializing it required fixing it. One cell in
`docs/snapshot-fact-tags.xlsx` (C139) → `enum: yes | no | unknown`, `fact_tags.csv` regenerated,
verified as a 1-byte sheet change with all 13 other zip entries byte-identical.

### The verdict direction, argued

FR-3 asks **"should a human look at these terms?"**, never "was there fraud?". Three things enforce it:
the producer prompt is told a seller credit is ordinary and forbidden to speculate about intent or use
the word fraud; the rule is judgmental, so LP-376-B routes every verdict to `needs_review` — there is
no `fired` and no `satisfied` path, and a test asserts `is not FIRED`; and an unreadable contract
abstains at the gate rather than being surfaced.

### The derivation — and the defect it exposed

**First run: 0.7500 over 4 cases, one disagreement.** On the ordinary $3,000 closing-cost credit,
call 1 said `no` (*"routine closing-cost credit, clearly stated purpose"*) and call 2 said `yes`
(*"routine credit type **but** should be reviewed to verify terms align with loan guidelines"*).

Both described the same facts correctly. They differed on **which question they were answering** —
call 2 answered *compliance*, which is PC-4's question, not *unusualness*, which is FR-3's. On the
commonest real contract that flips the tag to `yes` half the time: the false-positive direction this
cohort exists to avoid, demonstrated concretely.

That is a **prompt defect, not model noise**, and only reading the reasoning surfaces it — the
LP-495b/DT-7 lesson applied. The prompt now states that the tag is not asked whether a credit
complies, that "should be verified" is true of every credit and would make the tag say `yes` on every
contract, and lists the three things that actually qualify.

**After the fix: 1.0000 over 4 cases, 0 disagreements**, full three-value spread — `no` (ordinary
credit), `yes` twice by two *different* routes (a referenced side agreement; a $45,000 credit whose
purpose is only "per addendum"), `unknown` (fields absent). Two `yes` routes deliberately, so the
branch does not rest on the side-agreement field alone. Call 2 re-derives from the same source data
with the document's field dict **reversed**, so at temperature 0 the prompt is not byte-identical.

All four pre-rate checks ran: the context was printed and confirmed to carry real content per case;
8 of 8 calls succeeded; the spread is three-valued, not uniform; and the reasoning was read, which is
what caught the defect.

**What the rate does not show.** It establishes that the plumbing works and every branch is reachable.
It establishes **nothing about detecting a real unusual credit** — the fixtures' author knows the
intended answer, so scoring self-authored cases against self-authored logic measures self-consistency,
not correctness (ADR-332, LP-487's amendment). Recorded on the bar in those words.

### A scoping defect found by running it

FR-3 enumerates `per_document`. With the applicability predicate on the **tag**, it produced a
`couldnt_check` row on **every document** — 8 on LF-6T3N, none of them a purchase contract. A
fraud-adjacent rule reporting "could not check your contract" against a pay stub is noise, and on this
cohort's axis it is worse than noise. The predicate is now `document.document_type eq
purchase_agreement`, so a non-contract document is `not_applicable`, which is what it is.

The unreadable-contract case is still covered — by the **gate** rather than the predicate. The tag is
load-bearing, so an absent or `"unknown"` value short-circuits to `couldnt_check` *before* any
rule-time model call. A test supplies a judgment reasoner that **raises if invoked**, proving an
unreadable contract accuses nobody and costs nothing.
