# LP-705 — one stated liability in ~270 refuses its whole loan file's snapshot

- **Ticket:** LP-705
- **Status:** Done (2026-09-06). Fixed by unanchoring the uuid skip and collapsing the two copies of the decision into one.
- **Date:** 2026-09-06
- **Found by:** the reviewer session, in a full-suite run
- **Scope:** Backend — `verification/snapshot/persistence.py`, `services/dti.py`
- **Related:** LP-509-C1, LP-565 / bug-001, ADR on PII-at-rest

## The failure

A verification run aborts with:

```
RawPiiAtRestError: refusing to persist: unmasked account/SSN-shaped value(s) at
calculations.dti.breakdown[0].key (a 12-digit run)
```

Nothing is written — not the snapshot, not the tag values, not the findings. The run
completes and persists nothing.

## Why, and how often

A DTI line built from a stated liability is keyed `f"debt.{liab.id}"` (`services/dti.py:201`),
and the income equivalent is `f"income.{item.id}"` (line 162). Both are a **prefix plus a
uuid**, not a bare uuid.

The at-rest guard skips canonical uuids, and the skip is anchored:

```python
_UUID = re.compile(
    r"\A[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}\Z", re.IGNORECASE
)
```

`\A…\Z` means `debt.23a4e051-…` does not match, so the string is scanned — and a uuid's
final group is twelve hex characters, which is a 9+ digit run whenever it happens to be all
digits.

**Measured: 0.354% of random uuid4s contain a 9+ digit run — one stated liability in ~283.**
Its whole loan file's snapshot is then unpersistable, and stays that way for every subsequent
run until that liability is edited or deleted.

Two independent runs of 2,000,000 samples each: 0.3539% (95% CI [0.3457%, 0.3622%]) and
0.3545% ([0.3463%, 0.3627%]). An earlier pair of 200,000-sample runs gave 0.369% and 0.342%
— both within their own error bars and neither reliable, because 200,000 samples of a 0.35%
event carries about ±0.08%. The figure is recorded to four significant figures with its
interval so that whoever fixes this is not choosing between two numbers.

The guard's own docstring names this symptom: LP-509-C1 was written because "a refusal that
said only 'a long bare digit run is present' left a loan file with no snapshot, no persisted
tag values and no way to tell which field was responsible". LP-565 / bug-001 records "22
completed runs, 0 persisted". **This may be the cause of a production symptom someone has
already seen** — a file whose verification never sticks, with no pattern to it, because the
trigger is which uuid a row happened to be assigned.

## Why it was not fixed in LP-703

Relaxing a PII-at-rest check is not a change to make inside someone else's review, and the
guard's own error message says what to do instead: *"Route the field through the documents
section's PII map so it is masked + hashed, rather than relaxing this guard."* That advice
does not fit a synthetic key, which is why this needs its own argument rather than a quick
edit.

## What was built

**Option 1, unanchored.** `_UUID` matched `\A…\Z`; it is now `_UUID_ANYWHERE`, and
`_without_uuids` removes every canonical uuid from a value **before** the two patterns are
applied. That covers `debt.{id}`, `income.{id}`, and any future `<prefix>.<uuid>` at once,
without exempting a path or a key name.

**The replacement is a space, not nothing**, and that detail is load-bearing: substitution can
then only ever *create* a word boundary, never close one, so a leak written flush against an
id is still caught. `debt<uuid>123456789` is the case that separates the two — with an empty
replacement `debt` joins the digits, `\b` never opens, and the leak walks through.

**One decision, not two copies of it.** `_assert_no_raw_pii` now calls `refuses_at_rest`
rather than restating the same two patterns. They had already drifted — the guard skipped
uuids and the door did not — in the harmless direction this time. `refuses_at_rest` was
exported in the LP-703 review precisely so a value could be refused where a person types it,
with a docstring saying the two must not disagree; sharing the code is the only form of that
promise which cannot rot.

**Why widening the skip is not turning the guard down.** Removal deletes exactly 36 characters
of canonical uuid, and neither pattern can be hidden that way: an SSN carries hyphens at
positions 3 and 6 and a bare account number carries none, so neither can be contained by an
8-4-4-4-12 hex-with-hyphens run. Asserted rather than reasoned, in
`test_removing_a_uuid_is_not_a_hiding_place`.

### One mutation escaped first, and the test was the weak part

The space-versus-nothing argument above was in the code comment before it was in a test. The
first version of that test used `"<uuid>123456789"` — where the uuid sits at the *start* of
the value, so the string edge is already a word boundary and the case passes with the uuid
replaced by nothing at all. Substituting `""` for `" "` broke nothing, which is how it was
found. The distinguishing case is a word character immediately before the uuid, and the test
now leads with it.

## The shape of a fix, as considered

The value is **not PII**. It is a row identifier the application minted, and the guard is
matching it by accident of digit distribution. Three candidates, in rough order of how much
they narrow rather than loosen:

1. **Skip a uuid wherever it appears in a key**, not only when it is the whole string —
   scan with the uuid runs removed rather than anchoring the skip to the whole value. Narrow,
   and it fixes `income.` and any future `<prefix>.<uuid>` at once.
2. **Exempt the `key` path**, since a DTI line key is structural by construction. Path-based
   exemptions are the kind that grow, and one that covers a whole field name would also
   cover a future value that is not structural.
3. **Change the key shape** so no digit run can appear — the cheapest edit and the one that
   fixes nothing else: the same accident is waiting for any other synthetic key that embeds
   an id.

The first was taken. The test needs a uuid that HAS the run — a random one passes 99.6% of
the time whether the bug is fixed or not.

**Construct it; do not search for it.** An earlier draft of this ticket said "generate uuids
until one contains a 9+ digit run". That shape is right and the loop is worse than it looks:
median 202 iterations, p95 852, p99 1402, and 2,291 observed in 2,000 trials. Unbounded, it
will occasionally look like a hang; bounded at anything comfortable-sounding like 500 it
fails spuriously about one run in twenty — which is worse than the bug, because a flaky test
gets deleted rather than read.

`uuid.UUID("12345678-9012-4345-8678-901234567890")` has the run by construction (`901234567890`)
and is a valid RFC 4122 version-4 uuid. The test then states what it is testing instead of
hunting for it. If a search is used anyway, bound it at 10,000 — about one chance in 10^15 of
missing — and assert the loop actually found one before asserting anything about persistence,
or a search that quietly found nothing makes the whole test vacuous.

## Verification

- Four new tests in `test_persistence.py`, all on the constructed uuid.
- Four isolated mutations, each reverted: re-anchoring the uuid match failed 2; substituting
  `""` for `" "` failed 1; scanning nothing failed 10; editing the constructed uuid to one
  with no digit run failed 1 — the positive control that stops the whole block going green by
  construction.
- The pre-existing guard tests are untouched and still pass: a dashed SSN, a bare account
  number, a large decimal money amount, the content-id and match-hash prefixes.

## Acceptance

- [x] The test CONSTRUCTS that uuid rather than searching for one
- [x] The guard still refuses a genuine raw SSN and a genuine raw account number — asserted
      in the same test file, so the narrowing cannot be mistaken for a relaxation
- [x] `income.{id}` is covered by the same fix, and asserted alongside `debt.{id}`
