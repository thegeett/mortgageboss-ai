# LP-389 — Activate the three ready rules (the first activation pass)

## What this ticket is

The FIRST activation pass — deliberately SMALL. Take the inert rules LP-379/380/381 measured and prepared, and
turn on **only** the ones that are genuinely ready, via a **declared eligibility gate** (not a blind list edit).
Fail closed: when in doubt, do NOT activate. The ticket proposed three (IN-1, IN-5, ID-5); **the gate of record
reshaped it to two** — ID-5 was held on a producer/consumer subject mismatch the gate caught.

## Acceptance criteria

- Activation is a DECLARED, testable gate (`activation_bars.is_eligible`), so a rule cannot go live without
  meeting it and `ACTIVE_RULE_IDS` cannot silently drift from the evidence.
- Only genuinely-ready rules activate; every held rule fails the gate for a named reason.
- A real run on LF-6T3N reports each activated rule's ACTUAL verdict (reported, not predicted), naming the root
  of any couldnt_check.
- The original 11 base-active rules are intact; full suite (ruff + mypy + pytest) green.

## Phase 0 — the eligibility gate (declared, not a hand-list)

A rule goes live ONLY by passing `activation_bars.is_eligible(bar)`, fail-closed:

- **AI rule** (`calibratable-now`): eligible iff the bar is Priya-`validated` AND `measured_accuracy >=
  threshold` (which is exactly `activation_mode == auto/ratify`).
- **no-AI rule** (`no-ai-dependency`): eligible iff its parsed `input_resolves` — VERIFIED to resolve to real
  values on a real file **at the subject the rule reads**.
- Everything else (unmeasured tag / unvalidated bar / missing accuracy / unresolved input / needs-producer) is
  HELD.

Two new bar fields carry the evidence, both fail-closed defaults: `measured_accuracy` (float in [0,1] | null,
the LP-379 number) and `input_resolves` (bool, default false). `ACTIVE_RULE_IDS` stays an explicit list —
the foundational registry must not import the bar loader (a circular edge) — but `_BASE_ACTIVE` (the 11) +
`_LP389_ACTIVATED` are separated, and `test_activation_gate_lp389` pins `set(ACTIVE_RULE_IDS) - _BASE_ACTIVE ==
eligible_rule_ids()`. So the list can never drift from the declared evidence.

### The finding that reshaped the ticket — ID-5's subject mismatch

LP-381 reported ID-5's parsed inputs (`id.id_expiration`, `contract.closing_date`) "resolve on LF-6T3N" — but
at the **document** subject. Both are declared `subject: document` (tag_production.yaml) and materialize on the
ID/contract documents (`dl1`/`dl2`/`pa1`). **ID-5 reads them at `tags.by_subject["loan"]`** (its spec's
`snapshot_path` + `subject_enumeration: loan`), so they never reach it and ID-5 couldnt_checks on **every**
file. Its existing tests (`test_typed_operands`, `test_identity_family_eval`) only pass because they hand-place
the tags at `loan`. So `input_resolves` is honestly **false**, the gate holds ID-5, and its subject model is a
flagged follow-up — with two borrowers, "which ID is the loan-level expiration" is a domain (Priya) call, out
of scope for this small pass. **The declared gate earned its keep: a blind list edit would have shipped a rule
that never checks anything.**

## Phase 1 — the activation

- `_LP389_ACTIVATED = ("IN-1", "IN-5")`; `ACTIVE_RULE_IDS = (*_BASE_ACTIVE, *_LP389_ACTIVATED)` → **11 → 13**.
  IN-1 SUPERSEDES the LP-333 deferral (documented_monthly is now calibrated 100% and the derived per-borrower
  producer is fixed).
- **A derived load-bearing tag pulls its upstream AI group.** IN-1's load-bearing tag is the DERIVED
  `income.documented_income_shortfall_pct`, which rests on the AI `income.documented_monthly` (group
  `income_amounts`). `_required_ai_groups` previously pulled a group only when the DIRECT load-bearing tag was
  AI — so IN-1 would have couldnt_checked forever (its AI input group never ran). Fix: an active rule's
  activation-bar `load_bearing_ai_tags` (which name exactly the upstream AI — IN-1's bar declares
  `income.documented_monthly`) are folded into the required set. `income_amounts` + `income_employer` move from
  dormant to live; the dormant probe's set shrinks 6 → 4.
- Each newly-live rule's couldnt_check reason tag got a curated mortgage phrase (`reasons.py`):
  `income.documented_income_shortfall_pct` → "documented-vs-stated income shortfall";
  `income.employer_normalized` → "employer name". (ID-5's `contract.closing_date` is deliberately NOT added —
  ID-5 is held; it's added when it goes live.)

## Assumptions & decisions

- **ID-5 HELD, fail-closed** (Geet's call, presented with the evidence) — the subject-mismatch fix needs a
  domain decision (per-borrower vs a loan-level promotion; which ID) and is a flagged follow-up ticket, not
  this small pass. ADR-306.
- **IN-1 activated despite its LF-6T3N couldnt_check** — its gate is AI accuracy (met, 100% ≥ 0.98,
  Priya-validated); the couldnt_check is honest data-absence (no stated income in the fixture MISMO), which the
  ticket anticipates naming, not a wiring defect. This is distinct from ID-5, whose gate (input resolves at its
  subject) is genuinely unmet.
- **No change to `activation_mode` or the bar semantics** — the gate reuses the existing declared surface; it
  adds only the two evidence fields.
- **Follow-up reported:** ID-5's subject model (document-subject inputs vs a loan-subject read); and, separately,
  IN-1's stated-income input needs a real file (or a fixture with borrower MISMO income) to demonstrate a fired
  verdict.
