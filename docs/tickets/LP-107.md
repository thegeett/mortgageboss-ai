# LP-107 — Unknown/unclassified documents display the original filename, not "Unknown_{date}"

- **Ticket:** LP-107
- **Status:** Completed
- **Date:** 2026-07-03
- **Scope:** Backend naming (the frontend already shows the type — no component change)

> Ticket-number note: LP-106 flagged its recency-facts follow-up as "LP-107"; since LP-107 is now
> this naming fix, that follow-up needs a fresh number (e.g. LP-108). See LP-106.md / ADR-231.

## The bug

Documents the classifier couldn't confidently type land as `document_type = "unknown"`, and
`standard_name` (LP-72) produced `Unknown_{upload_date}` — **discarding the original uploaded
filename**, the best identifier an unknown document has. On LF-6T3N, four unknown documents all
displayed as `Unknown_2026-07-02`, indistinguishable and **strictly worse** than the real filenames:

- `Akash W2 Wells 2024.pdf`, `EMD wire receipt.pdf`, `Home Value estimate- Property tax.pdf`,
  `Home Value estimate- Property tax (1).pdf`.

## The fix

`app/documents/naming.py::standard_name` — when the type is unclassified (`"unknown"`, or `None`
before/without classification), fall back to the **original uploaded filename** instead of
`Unknown_{upload_date}`. The name recovers the best identifier; multiple unknown docs are now
distinguishable by their real filenames.

- **The "Unknown" type signal is kept.** Only the *name* changes. The card renders the type
  **separately** (`humanize(document_type)` → "Unknown"), so the unclassified state is still shown
  honestly — the processor still sees it needs attention. So **no frontend component change** was
  needed; the card reads `{original_filename}` · **Unknown** · size · time.
- **Non-destructive:** this is the derived/display name; `original_filename` is the source and is
  preserved (nothing is renamed on disk).
- **Defensive last resort:** if there's genuinely no filename, it still returns `Document_{date}`.

## Composition with LP-105 (same function, different fallback case)

The two fallbacks are disjoint and don't conflict:

| Case | Result | Owner |
| --- | --- | --- |
| Known type + period extracted | `Pay-Stub_ACME_2026-06-20` | LP-72/105 |
| Known type, period **not** extracted | `Pay-Stub_2026-07-02` (`{Type}_{upload_date}`) | LP-105 |
| Classified type with **no** naming rule | `Credit-Report_2026-07-02` (meaningful — states the type) | LP-72 |
| **Unclassified** (`unknown` / `None`) | **`{original_filename}`** | **LP-107** |

Verified: LP-105's period names and the classified-no-rule path are unchanged.

## Secondary — the Tier-2/3 question (reported, NOT fixed here)

The four unknown docs are `tier_3` — i.e. they ARE routed to the generic long-tail analyzer, which is
the expected architecture for a genuinely novel document. So this is **not a tiering bug**. However,
at least one — `Akash W2 Wells 2024.pdf` — is obviously a **W-2** by its filename/content, so it
landing as `unknown` is a **classification-confidence gap** (a typeable doc classified as unknown),
not a tiering problem. That is a separate classification-quality concern (out of scope here); the
naming fix stands regardless and, notably, now makes such misclassifications *visible* (the real
filename shows) instead of hiding them behind `Unknown_{date}`. Flagged for a decision — not fixed.
