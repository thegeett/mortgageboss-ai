# LP-992 — Worker scheduler and mail bucket

Step 2 of the email work (`loan-email.md` §15a). Code, tests, dev check, and one small staging
apply (task definitions only).

## What and why

**Nothing in the app ran on a schedule.** There was no Celery beat anywhere: not in the worker, not
in infra, not in compose. Step 2 needs periodic jobs (LP-995 drains SES delivery events; step 4 puts
the inbound poller on a timer), so this ticket turns on Celery's built-in scheduler with one job: a
heartbeat log line every 5 minutes, which shows the scheduler is alive.

**Beat runs inside the worker** (`celery worker -B`), not as its own ECS service. That keeps it to
one flag. The cost is a rule: **the worker must run exactly one task.** With two, both run beat and
every scheduled job runs twice. If more workers are ever needed, beat moves to its own one-task
service first.

**One helper for raw email files.** LP-994 will save a copy of every sent email to
`outbound/<communication_id>.eml` in the mail bucket (`mbai-staging-mail`); step 4 reads `inbound/`
from the same bucket. `get_mail_storage()` gives both a storage backend: S3 on the mail bucket in
staging, a local folder in dev.

**The setting is renamed** `inbound_bucket` → `mail_bucket` (env `INBOUND_BUCKET` → `MAIL_BUCKET`),
because the bucket holds both directions. Nothing read the old name (LP-988).

## What changed

**Worker command** (all three places it is defined) gains `-B --schedule=/tmp/celerybeat-schedule`:

| Where | |
|---|---|
| `infra/modules/compute/main.tf` (`worker_command`) | ECS worker task definition, staging and dev |
| `docker-compose.yml` | local worker |
| `docker-compose.images.yml` | the image rehearsal |

`--schedule` puts beat's small state file in `/tmp`. Checked first that it is writable: the worker
task definition sets no `readonlyRootFilesystem`, and the image has no `USER` (runs as root). The
Dockerfile's own `CMD` was not changed (that would change the image); ECS and both compose files
override it.

**Schedule** (`app/tasks/celery_app.py`): `beat_schedule = {"heartbeat": {"task":
"health.heartbeat", "schedule": 300.0}}`, with the one-worker rule in the comment above it.

**Heartbeat** (`app/tasks/health.py`): task `health.heartbeat` logs one structured line,
`beat_heartbeat`. No database, no network.

**Guards on the worker count** (0 or 1; 0 is the overnight stop):

- A `validation` on the compute module's `worker_desired_count`, next to `worker_command`, so it
  covers staging and dev alike. (First added on staging's variable only; moved after review.)
- `scripts/deploy`: `service_desired_from_tfvars worker` refuses any other value, and `stage_up`
  calls it directly before starting RDS, so `up` stops before anything is started.
- The worker service stops the old task before starting the new one on a deploy
  (`deployment_maximum_percent = 100`, `deployment_minimum_healthy_percent = 0`). ECS's defaults
  (200% / 100%) started the new task first, so every deploy ran two schedulers for a minute. The
  cost: a short gap with no worker; queued tasks wait in Redis, and a beat tick in the gap is skipped.
- `infra/README.md` states the rule next to "scale the services up".

| Path that sets the count | Bounded? |
|---|---|
| Terraform (create) | Yes: the module validation |
| Overnight start schedule (`modules/scheduler`, `start_service`) | Yes: it scales to the validated variable |
| `./scripts/deploy staging up` | Yes: the script's own check on the tfvar it reads |
| ECS deploy | Yes: no overlap (above) |
| Autoscaling | None configured (no `aws_appautoscaling_*` anywhere) |
| `aws ecs update-service --desired-count N` by hand | **No.** Nothing can stop that; the README says why not to |

**Mail storage** (`app/storage/__init__.py`, `get_mail_storage()`), reusing the existing backends:

- `storage_backend == "s3"` → `S3StorageBackend` on `settings.mail_bucket` with
  `settings.mail_kms_key_id`; raises `ValueError` when either is unset or blank. The S3 constructor
  call is shared with `get_storage_backend` (`_s3_backend`), so a new argument reaches both.
- Cached per configuration (`_mail_storage`, keyed on backend, bucket, key and local path): the local
  backend resolves and creates its root in `__init__`, which should not run once per message.
- `"local"` → `LocalStorageBackend` rooted at `<storage_local_path>/mail`.
- Same keys in both: `outbound/<id>.eml`, `inbound/<id>`, through `save_at` / `read` / `delete`.
- `.eml` now maps to `message/rfc822` in the S3 backend's content types.
- `loan-email.md` §15a sketched this as `services/mail_store.py` with `put_raw` / `get_raw`; the
  brief asked for one function next to `get_storage_backend()`, which is what was built.

**Encryption: the mail bucket's own key, in its own setting.** In staging the documents key and the
mail bucket's default key are the same CMK today (`module.secrets.kms_key_arn`, `alias/mbai-staging`,
the key LP-989's `head-object` showed), so the first version reused `s3_kms_key_id`. Review pointed
out that this works only by that coincidence: give the mail bucket its own key and KMS refuses every
write. So:

- New setting `mail_kms_key_id` (`MAIL_KMS_KEY_ID`), required with `mail_bucket` in s3 mode; the
  documents key is not a fallback.
- Staging sets it from a new `inbound_mail` module output, `kms_key_arn`, read from the bucket's own
  default-encryption rule. So the app sends the bucket's key by construction.
- "Leave out `SSEKMSKeyId` and use the bucket default" was not possible without changing the S3
  backend: with no key id it sends `ServerSideEncryption: AES256`, which would store mail as SSE-S3,
  not under the bucket's CMK.
- The bucket policy requires no SSE header (its only deny is insecure transport). The worker's
  `MailKey` statement (LP-986) allows `kms:GenerateDataKey` and `kms:Decrypt` on
  `module.secrets.kms_key_arn`, the same key. No IAM change. If the mail bucket is ever given its own
  key, that statement's input (`mail_kms_key_arn` in `envs/staging/main.tf`) must follow it.

**What the worker may do with it in staging** (LP-986 IAM, unchanged): `s3:PutObject` on
`outbound/*` and `s3:GetObject` on `inbound/*`. Reading back or deleting an `outbound/` object is
AccessDenied there. LP-994 only writes, so that is enough; a staging round trip like the dev one
below would fail at the read, by design.

**Env rename**: `infra/envs/staging/main.tf` sets `MAIL_BUCKET` (same value, same
`inbound_mail_enabled` condition) instead of `INBOUND_BUCKET`, and `MAIL_KMS_KEY_ID` beside it, with
the comment updated. `.env.example` has `MAIL_BUCKET=` and `MAIL_KMS_KEY_ID=` (empty locally); a
blank value reads as None, like the other S3 strings. Dev infra and compose had no
`INBOUND_BUCKET`. Settings use `extra="ignore"`, so an old `.env` with `INBOUND_BUCKET` still starts.

**Default command** (after review): the image's `CMD` (`backend/Dockerfile`) and the host commands
in `docker-compose.yml`'s comment, `README.md` and `docs/development-workflow.md` gain `-B
--schedule=/tmp/celerybeat-schedule`, so nothing that runs the worker without overriding the command
gets one that never schedules. The host instructions say to stop the Compose worker first. The CMD
change reaches staging with the next image build (LP-998); ECS overrides it anyway.

**Heartbeat expiry** (after review): the entry has `"options": {"expires": 300}`. It shares the
default queue with verification runs of up to 20 minutes; a heartbeat that waited a whole interval
is dropped rather than logged late in a burst, which could look like a live scheduler after it died.

## Rule going forward

**One worker task while beat runs inside it.** Before scaling the worker beyond one task: create a
separate beat service (one task, `celery beat`), remove `-B` from `worker_command` and both compose
files, then raise the count and relax the module validation and the `scripts/deploy` check. Deploys
no longer overlap, but a hand-run `update-service` still could, so a job that must never run twice
should also be safe to repeat.

## Checked in LP-998

The new code (the heartbeat task, `beat_schedule`, `get_mail_storage`) is not deployed by this
ticket: the apply only changes task definitions, on the image already running
(`staging-9b0c5b29`). Until LP-998 deploys this tree, staging's worker runs beat with the old
code's empty schedule, so beat starts and sends nothing. That is harmless. The old code read neither
`INBOUND_BUCKET` nor `MAIL_BUCKET`, so the rename changes nothing at runtime either.

After LP-998's deploy, check the worker log group `/ecs/mbai-staging/worker` for `beat: Starting...` and a `beat_heartbeat` line every 5 minutes.
