## Section 1 — the paste door

### The question the spec leaves open, and the measurement that answered it

Spec §LP-907 says `sheet_format = PASTED_TEXT` **"unless the text itself is recognisably UWM or
Champions"**, and screen S1-07 says the format line "says the UWM layout was recognised in the pasted
text". Neither says *how*, and the obvious answer does not work: `detect_format` keys on the first
content line, and **a processor pasting from the portal copies the headings and the rows, not the
title above them** — nor the `CONDITIONS` marker that `read_uwm` bounds its block with.

So the excerpt was run through both readers before any code was written. On the round-2 fixture's own
conditions block, with the marker stripped the way a portal copy strips it:

```
read_uwm     on the marker-less paste ->  0 rows, needs_ai, "no CONDITIONS marker; nothing could be read"
read_generic on the same paste        ->  7 rows, needs_ai FALSE
```

Seven, not six. The bucket heading `UW - Prior To Final Approval (PTD)` became a **row of its own**,
and every real row kept its category glued to the front of its text:

```
'Invoice                       Provide copy of invoice for credit report.'   <- generic
'Provide copy of invoice for credit report.'                                 <- the same row, read as UWM
```

**⚠️ THE COST IS NOT ONE SPURIOUS ROW, IT IS SEVEN WRONG FINGERPRINTS.** Conditions are matched
across rounds on a fingerprint of `verbatim_text`, so not one of those six would match the condition
already on the file. Spec §8 step 2 — *"6 seen again, 0 new, still 11 conditions"* — becomes **7 new
and 18 conditions**.

And note the shape of that failure: not an error, not a warning, not an empty result. Six
near-duplicates that look correct on the review screen, each one a copy of a condition already there,
and the processor's only clue is that the list doubled. **Recognising the layout is the difference
between a merge and a duplication**, which is why S1-07's sentence is load-bearing rather than
decorative.

### What was built

`uwm_block_start(lines)` (in `readers/uwm.py`) answers "do these lines carry UWM rows, and where do
they start" using **the reader's own `_row_start` rule** rather than a looser "looks like a code"
regex — so a paste can never be recognised as UWM and then read as nothing, because the two decisions
are the same decision. `read_uwm` gained `conditions_from`, which supplies the block start when the
marker is absent and is ignored when it is present.

`readers/paste.py` → `read_pasted_text(raw) -> (format, reader_name, ParsedSheet)` puts them in
order: whole letter → excerpt → fallback.

**⚠️ THE BLOCK START IS PASSED IN RATHER THAN A `CONDITIONS` LINE PREPENDED.** Both work — measured,
the rows are identical — so the tie is broken by a property nothing currently tests: a synthetic line
shifts every row's `source_line_numbers` by one against the text the processor pasted, and those
numbers are what the review screen points at. Invisible until someone clicks a warning and lands on
the wrong line.

Result on the excerpt: **6 rows**, and `verbatim_text`, `lender_category`, `bucket_kind` and
`bucket_heading` all **identical to the same sheet read whole**. 0 unassigned, no warnings.

### Champions is recognised and deliberately not read

Spec §LP-907 names Champions beside UWM. It is **not** claimed here, and the reason is measured
rather than assumed. Copied out of our own Champions fixture PDF — a clipboard copy is what a paste
*is*:

```
detect_format  -> champions_certificate      (the title survives a copy)
read_champions ->  0 rows, 97 unassigned lines
read_generic   ->  4 rows, needs_ai FALSE    (for a 28-condition certificate)
```

The reader is built on the row number sitting **vertically centred** beside its text; a copy
linearises the two-column table so the number lands on a line of its own, and the geometry the whole
algorithm needs is gone. Generic's four is the worse answer of the two because **it reports
success**: three are the same repeated page-footer line and the fourth starts mid-sentence.

So a pasted certificate gets `PASTED_TEXT` with `needs_ai` and a warning that names the reason. That
is a deviation from the spec's literal wording, taken because the alternative is a format label
asserting a read that did not happen.

**Order matters for the same reason.** `read_generic` returned `needs_ai=False` for *both* bad cases,
so it can never be used to decide whether a better reader should have run. The UWM test goes first;
generic is only ever the fallback.

### The round

`create_round_from_paste` opens a **`DRAFT`** round with rows already in it — the opposite of every
other door, because the work is different: an upload has bytes to fetch and pages to rasterise, a
paste is text already in memory. `POST /loan-files/{id}/condition-rounds/paste` answers **201**, not
the upload's 202, and the round it returns is finished. A client polling it for `DRAFT` would be
polling a round that was already there.

- `raw_text` stores the paste **verbatim** — NPI (ADR-405), and kept because for a pasted round it
  *is* the source: LP-908 splits that text, never a reconstruction from rows the rules may have
  misread, and §9.3 checks every AI row is a substring of it.
- `sources` carries no `storage_path`. Nothing was stored, and claiming a path would make the parse
  task fetch a file that does not exist instead of refusing cleanly.
- `round_date` prefers the processor's date, then the sheet's printed date (a paste of the whole
  letter has one), then today.
- **Both** `ROUND_RECEIVED` and `ROUND_PARSED` events are written. An uploaded sheet arrives and is
  read later, in two events; a paste does both inside one request, and emitting only one would make
  the round-details history (S1-09) read differently for rounds that are otherwise identical.
- `completeness` is **required, with no default at the boundary** (ADR-404). The UI defaults the
  control to "just some"; the API refusing to guess is what makes that a decision rather than a
  fallback.

### ⚠️ Deliberate deviations from the spec, each with its reason

1. **`DRAFT`, not `PARSING`, when the rules cannot split the text.** Spec §LP-907 says to answer
   `PARSING` and queue the AI split. **LP-908 does not exist**, so that branch would enqueue nothing
   and leave the round in `PARSING` with no worker and no exit — the processor sits on screen S1-02
   forever. LP-905 recorded a stranded `PARSING` round as the one gap it left open; manufacturing
   that state on purpose would be worse than a DRAFT holding what the rules did find. `needs_ai` is
   recorded in `parse_report` so LP-908 can find exactly these rounds and finish the job.
2. **Champions pastes route to `PASTED_TEXT`** — see above; the specialised reader returns nothing on
   this input.
3. **201 rather than an unspecified code.** The spec does not give one; 201 is what a synchronous
   creation is.

### Changes to existing code, and why

- **`parse_report` gained `needs_ai`**, with `ParseReportPublic` gaining the field. It is not the
  same fact as `ai_used`: `needs_ai` is the reader's verdict that the rules could not split the text,
  `ai_used` is whether a split actually ran. The pair is what makes "waiting for LP-908" a findable
  state rather than something only visible in a warning string.
- **`_parse_report` and `_draft_rows` moved from `tasks/conditions.py` into `services/condition_rounds.py`**
  as `parse_report_for` and `draft_rows_json`. Both doors write these now, and a second copy would
  drift the moment one gained a key — which is the argument `draft_rows_json`'s own docstring makes
  about `DraftRowPublic`, one level up. `tasks → services` is this repo's normal direction.
- **A stale comment removed from `read_uwm`.** It claimed the function "REFUSED LOUDLY ON PDF INPUT"
  and that "section 3 authors the first PDF fixture" — a refusal that was deliberately removed when
  the derived column threshold replaced `indent`, as `test_a_pdf_sheet_with_no_conditions_block_is_not_an_error`'s
  own docstring says. It described behaviour the code no longer had.
- **"header not found" is no longer warned for an excerpt.** There the absence is the input's shape
  rather than a finding, and a warning present on every pasted round is one a processor learns to
  skip — including on the sheet where it means something. A sheet that *has* a `CONDITIONS` marker
  and no `LOAN INFORMATION` still warns, so the page-break fixture's warning is unchanged.

### Recorded gaps

- **A paste from an HTML portal is not measured**, and cannot be from here. What was measured is a
  clipboard copy of a fixed-pitch PDF, where the columns survive intact (the whole-letter paste reads
  6 rows, header and printed date, with no warnings). If a real portal copies as single-spaced HTML,
  `_ROW_START`'s `\s{2,}` will not match and the paste falls to `PASTED_TEXT` + `needs_ai` — the safe
  direction, and LP-908's job. §7.5's real-sheet smoke test on the product owner's machine is where
  that meets reality.
- **`needs_ai` is not exposed in the `readonly.*` view**, though the view projects `ai_used` beside
  it (migration `d1f4b8c25e93`). Deferred to LP-908, which adds the consumer: a view column nothing
  reads is the unexercised addition this stage keeps finding green.
- **Champions pasted text has no fixture of its own.** What exists is the measurement above, pinned
  in `test_a_pasted_champions_certificate_never_reaches_the_champions_reader`, which asserts both
  halves — that the specialised reader returns nothing, and that the paste path therefore does not
  call it.

### ⚠️ Review fix — five non-UWM tables were claimed as UWM sheets

The first version recognised a paste by **counting row starts**, with this reasoning in the code:
"ONE four-digit number followed by two columns occurs in ordinary prose … Two of them on separate
lines is a list." **The premise was right and the conclusion did not follow.** Two of them on
separate lines is a *table*, and a fixed-pitch table whose first column is four digits is what a
processor pastes constantly. Reproduced locally, every one came back `uwm_approval_letter` with
`needs_ai=False` and **not one warning**:

```
tax years      -> 2 rows, codes 2026 / 2025,        categories 'Tax Return'
amortisation   -> 3 rows, codes 1000 / 1001 / 1002, categories Principal / Interest / Escrow
invoice list   -> 3 rows, codes 4417 / 4418 / 4419, categories 'Appraisal Inc' / 'Title Co'
account digits -> 2 rows, codes 8821 / 8822,        categories Checking / Savings
```

**This was worse than the Champions case beside it.** Champions fails *visibly* — wrong rows, a
warning, `needs_ai` set — so a processor sees something went wrong. These are plausible rows with
confident lender codes and nothing asking for a second opinion, and their fingerprints then feed the
import matcher: **the same duplication failure this recognition exists to prevent, arriving through
the door opened to fix it.** One of the five was my own `test_two_coded_lines_are_a_list`, which
asserted the defect as intended behaviour.

**The discriminator is the bucket heading, and it is not the codes.** Rejecting year-shaped codes is
the obvious fix and is wrong — the round-2 block's own codes include `1947`. What separates a
conditions block from a table is that its rows are grouped under headings, and a processor copying
the portal copies those headings too — which is exactly why the generic reader turned the heading
into a spurious seventh row.

A heading-*shaped* line is not enough either: `_HEADING` matches any short title-cased line, so
`Tax Returns` passes it. The rule requires a heading whose bucket the reader **knows**. Measured
across every fixture, that costs nothing on real input:

| Fixture | headings | known bucket |
|---|---|---|
| `uwm_round1` | 3 | **3** |
| `uwm_round2` | 2 | **2** |
| `uwm_master_pagebreak` | 5 | **5** |

Not one real conditions block carries an unknown-kind heading; all four tables carry none at all.

**The false negative is deliberate.** A processor copying one bucket's rows without its heading gets
`PASTED_TEXT` + `needs_ai` rather than a confident wrong answer — the same direction chosen for
Champions. Pinned by `test_a_table_of_four_digit_numbers_is_not_a_uwm_sheet` (five cases, the fifth
being genuine UWM rows without their heading), `test_the_discriminator_is_the_heading_and_not_the_codes`,
`test_a_heading_shaped_line_is_not_enough`, and `test_every_real_conditions_block_carries_a_known_heading`.

### The residual, named rather than patched

Review pushed on the new rule and found one that survives it. **It is a family, not a list**, and
that correction matters more than the count — I first recorded five example shapes, which invites the
next reader to treat a sixth as a new defect. Measured, 11 of 14 headings tried were accepted above
the same tax table:

```
Master · UW - Prior To Final Approval (PTD) · Compliance - Prior To Closing (PTD)
Underwriter To Obtain And Clear · Closing (PTF)     <- all five _HEADINGS entries
Document Checklist (PTD) · Trailing Documents · Trailing
Shipping (PTF) · Anything At All (PTC) · Whatever (PTA)   <- invented, not UWM headings at all
Tax Returns / Checklist / Outstanding Items -> pasted_text (controls, refused)
```

The rule, stated rather than sampled: `_heading_kind` accepts a line that is in `_HEADINGS`, **or**
carries a `(PTD|PTF|PTC|PTA)` parenthetical, **or** contains `Trailing`. The middle clause is
open-ended — any title-cased line ending in one of four parentheticals qualifies, which is why
`Whatever (PTA)` passes.

**It is left in place, and the reason is the shape of the alternative.** Real conditions blocks
interleave headings with rows — 3, 2 and 5 headings against 6, 6 and 16 row starts across the
fixtures — while every one of these carries exactly one heading at the top. So "a known heading that
is not the first content line" refuses all five and accepts all three fixtures. It would **also**
refuse a genuine single-bucket excerpt, which is a real thing a processor pastes, and trading a
constructible wrong answer for a plausible one is precisely the move that produced three failed gap
rules earlier in this stage.

The original five were material a processor pastes weekly. These five require a document carrying
**both** a four-digit-first-column table **and** a line reading as a lender bucket heading; they had
to be constructed deliberately, and no real document of that shape has been named. A named residual
a reader can check beats a fourth heuristic that makes the wrong answers rarer and more believable.
Recorded in `uwm_block_start`'s docstring so it is found at the code rather than only here.

## Section 2 — enriching a pasted round with its PDF

### ⚠️ A required column that nothing has ever written

`conditions.text_fingerprint` has been `NOT NULL` and indexed `(loan_file_id, text_fingerprint)`
since LP-904. The model's own docstring calls it "the distinction the matching depends on", and
`uwm.py` recorded that "the stored `text_fingerprint` is computed at import". **No code computed
one.** The only value anywhere in the repo was `uuid4().hex * 2` in a test helper.

It has never failed because nothing constructs a `Condition` row yet — so LP-909's first real insert
would have hit a NOT NULL column with no writer. Two review rounds over LP-904 read the migration,
the CHECK constraints, the readonly views and the tenancy guards and never asked *which code fills
this*. "Reviewed the schema" and "asked what writes it" are different questions.

`app/conditions/fingerprint.py` is that function, written by the first caller that genuinely needs
it and shared with the import that comes next.

**What is removed before hashing, and why each:** underwriter notes (an annotated condition is the
same condition — including the note would make round 3 create a new row instead of recognising the
one already there); case and whitespace runs (a PDF and a paste of the same sheet differ in spacing,
and both doors must fingerprint identically or attaching a PDF to a pasted round matches nothing).
**What is not removed:** amounts, names, punctuation — the page-break sheet lists `0571` three times
with three different amounts, and collapsing those would drop two of the lender's demands.

### One normalisation, not two

`_fingerprint_text` was private to the UWM reader, where rule 6 uses it to drop page-overlap
duplicates. The stored fingerprint now hashes exactly that, so it is public as `note_stripped` and
both callers share it. Two answers to "is this the same wording?" that could drift apart would
deduplicate a row *within* a sheet and then duplicate it *across* rounds — and each would look
correct on its own, which is why `test_the_readers_dedup_key_and_the_stored_fingerprint_cannot_drift`
compares them directly rather than asserting each separately.

The deliberate difference: rule 6's key carries the notes as a third element, the stored fingerprint
does not. That is now stated in the docstring rather than implied.

### The merge

`enrich_round_with_pdf` — **its own transition, never the parse task's compare-and-set.** Moving a
round back to `PARSING` so that machinery could re-read it would leave the guard unable to tell "a
retry of the parse that created this round" from "a re-parse of a round a processor is reviewing",
and would turn a deliberate, auditable re-parse into something a file upload does silently through
another door.

**The guard is "an active round with no PDF source yet"**, not `status = DRAFT`: the spec says the
merge works for DRAFT *and* IMPORTED rounds, S1-08 puts the button on an imported card, and one
predicate covers both statuses while also making a second attach refuse — the same shape as the
forward door's duplicate guard.

**⚠️ ADDITIVE ONLY, AND THIS RULE IS OURS RATHER THAN THE SPEC'S.** The spec says to fill *missing*
code, category and bucket, add unmatched PDF rows, and keep unmatched pasted ones with a warning. It
is silent on a PDF row whose code *contradicts* a pasted row's. The rule taken: the PDF may fill a
hole, never overwrite a value a processor can see, and `verbatim_text` is never touched by a merge.
A full re-read stays a separate, explicit act. Recorded so a later reader does not assume the spec
settled it.

A DRAFT round merges into `draft_rows` (JSON, no identity yet); an IMPORTED round merges into its
`Condition` rows, filling codes and writing a `CONDITION_EDITED` event per row changed.

### The endpoint, and closing LP-905's `501`

`POST /api/v1/condition-rounds/{id}/attach-pdf` → **200**. Not 201 or 202: nothing is created, and
nothing is queued, so there is nothing to poll.

The path carries no loan file, so `ScopedLoanFile` — the tenant gate every nested condition route
uses — cannot apply. `get_scoped_round` filters on `company_id` **inside the statement**, so a
mismatched (company, round) pair is unfetchable rather than fetched-then-rejected.

`attach_to_round_id` on the forward endpoint now runs the merge. Its `round_id` arrives in a
**request body**, which makes it the one id here that cannot be trusted to belong to the file in the
path — so the round is loaded scoped to that loan file.

**⚠️ The `sources` duplicate guard is deliberately NOT applied to a merge.** Forwarding refuses an
attachment whose id already appears in some round's `sources`, because a second round from one
attachment broke the one-to-one S1-13's link derives from. Merging is the opposite: it puts that id
into a round that already exists and creates nothing. Attaching the same PDF twice is still refused
— by the "already has a PDF source" guard, which is the one that fits the question.

### Four defects of my own, caught by execution rather than reading

1. **`fingerprint.py` imported a function that did not exist.** It imported `note_stripped` from
   `uwm.py` while the name there was still the private `_fingerprint_text`. Nothing imported the new
   module yet, so it sat there looking finished; the `ImportError` was waiting for its first real
   use. The same shape as the `ConditionRound` `TYPE_CHECKING` `NameError` caught in LP-905 §3.
2. **A monkeypatch quietly detached from its target.** `test_a_crash_mid_parse_leaves_the_round_untouched`
   patched `task_module.lines_from_pdf`; moving the read into `sheet_read` left it naming an
   attribute the module no longer had. It failed loudly here — but a patch on a name that still
   existed and was no longer *called* would have passed while testing nothing.
3. **A docstring asserting behaviour the code did not have.** The forward handler's decorator sets
   `status_code=202` for the whole handler, so the merge branch answered 202 while the docstring I
   had just written said "two outcomes, two status codes". Fixed by injecting `Response` and setting
   200 explicitly, the pattern `auth.py` already uses.
4. **An assertion checking a sentence the code never emits.** A non-PDF attach was asserted to say
   "must be a PDF"; plain text is not identifiable at all, so `assess` never reaches the mismatch
   branch and the real message is "The file type could not be identified."

### ⚠️ Review fix — one attachment reached two rounds' `sources`

The same one-to-many the LP-905 §3 fix closed, reopened through the door section 2 added. Reproduced
end to end before changing anything:

```
forward attachment A                              -> 202, round 1 (PARSING), A's id in sources
paste a second round on the same file             -> DRAFT, no PDF source
forward A again with attach_to_round_id = round 2 -> 200, merged
                                                     -> TWO rounds carry A's id
```

**Both guards were individually correct and neither could see it.** The endpoint branches on
`attach_to_round_id` *before* `forward_attachment_as_sheet`, so the `sources` containment guard never
ran on the merge path; and `enrich_round_with_pdf` asks only whether **the target round** already has
a PDF source, which is blind to a different round.

My section 2 docstring argued the duplicate guard deliberately did not apply to a merge, because
merging creates no second round. True as far as it went, and the hole was the space between that
sentence and the next one.

**Worse than the original**, which is what makes it worth this much text: there the two rounds were
identical duplicates a processor would notice. Here round 1 is a `PARSING` round from the email and
round 2 a `DRAFT` under review — they look legitimately different, so nothing hints they share a
source.

**Fixed by extracting the guard rather than adding one.** `_round_carrying` now answers "is this
attachment already in a round on this file?" once, for both paths, with a single exception: the round
already carrying it **is** the merge target. That is a re-attach, and the round refuses it on its own
terms with a message the processor can act on.

**A mutation run then showed the exception was untested** — tightening the guard to refuse the
same-round case left all 16 tests in both endpoint files green, so it could have been deleted
silently. `test_re_attaching_to_the_round_that_already_has_it_refuses_on_the_rounds_own_terms` closes
that. Writing it also corrected me: I expected the PDF-source refusal and the real one is about
status, because `enrich_round_with_pdf` checks status first and a forwarded round is still `PARSING`.
Wrong about the order, not about the behaviour.

### What was agreed with review before any of it was written

- **Enrich gets its own transition and does NOT reuse the parse compare-and-set.** That CAS is
  guarded on `status = PARSING`; borrowing it would make it unable to distinguish "a retry of the
  parse that created this round" from "a re-parse of a round a processor is already reviewing", and
  would turn the deliberate, auditable re-parse LP-905 described into something a file upload does
  silently through a different door.
- **The guard is "an active round with no PDF source yet"**, not `status = DRAFT`. Spec §LP-907 says
  the merge "works for DRAFT and IMPORTED rounds", and S1-08 puts the button on an imported round.
  One predicate covers both statuses and makes attaching twice refuse the way the forward door now
  does.
- **⚠️ ADDITIVE ONLY, AND THIS PART IS OUR RULE RATHER THAN THE SPEC'S.** The spec says to fill
  *missing* code, category and bucket on matched rows, add unmatched PDF rows, and keep unmatched
  pasted ones with a warning. It is **silent on what happens when a PDF row's code contradicts a
  pasted row's** rather than filling a hole. The rule taken here: the PDF may fill a hole, never
  overwrite a value a processor can already see, and `verbatim_text` is never touched by a merge. A
  full re-read stays a separate, explicit action. Recorded as a decision so a later reader does not
  assume the spec settled it.
- Closing LP-905's `501`: `attach_to_round_id` on the forward endpoint runs this merge.
