# LP-617 — A finding should name the documents it is talking about

## The ask

> "just saying other documents disagree makes a processor check all documents — it would be helpful
> to show what documents it is referring to, and this should be the case of all rules."

LF-T9HD's ID-4 today:

> Confirm the borrower's current residence address and reconcile the discrepancies across the W-2s,
> pay stubs, bank statements, driver's license, homeowners insurance, and property tax bill.

Ten documents named as a category, none as the culprit. The processor opens all of them. What the
rule actually knew at evaluation time was:

> The two **2023 W-2s** state 298 Sewall Street, Boylston MA. The other **eight** documents state
> 1013 Whispering Creek Court, Knightdale NC.

Two documents to open. The rule had this and discarded it.

## What already exists

**The schema.** `Finding.source_document_id` (the trigger) and `Finding.source_document_ids` — a JSON
array whose own comment says a cross-source finding's "provenance is a SET, not one".

**The service.** `populate_finding_source_documents` value-matches each finding's cited values against
every document's extraction and stores the set. It already selects **all** active findings for the
file, not just cross-source ones.

**The provenance, exactly.** For consistency rules `_Gathered` carries `source_id` (content id) and
`source_label` (document type) per gathered value. ID-4 knows precisely which document said what.

## What is actually wrong

On LF-3CVT and LF-T9HD:

```
deterministic_rule   148 findings   0 with a document link
ai_cross_source        7 findings   1 with a document link
```

The governed rule engine never populates either field — `verification_run.py` contains no reference
to `populate_finding_source_documents` or `source_document`.

**And as of LP-614 the populator no longer runs at all.** It had exactly two call sites:

- `services/cross_source.py:212` — the legacy pass, switched off by LP-614;
- `services/verification_engine.py:129` — the LP-74 engine, imported by **tests only**, with no
  production caller.

So this is not "build a new capability". It is: the capability exists, was wired only into a path
that is now off, and was never wired into the path that produces 148 of the 155 findings.

## What the build found: Tier 1 was a no-op

The plan was "wire the existing populator into the governed run, then refine". That would have
shipped nothing. `populate_finding_source_documents` value-matches through `distinctive_values`,
which reads exactly two things:

```python
details["document_value"]      # governed findings: never set
finding.source_snippet         # governed findings: never set
```

`_details()` in `services/rule_findings.py` builds verdict/threshold/derivation/apply metadata and
neither of those. So the matcher returns `[]` for every governed finding, and calling the populator
would have produced the same 148-findings-0-links it produces today. The cheap tier did not exist.

## What was built instead: exact provenance

The rules already KNOW their sources, so they carry them rather than having them guessed back out of
the prose:

- **`RuleEvaluation.source_content_ids`** — the documents a verdict was derived from, as snapshot
  content ids.
- **Consistency rules** populate it from the gathered sources, *after* the filter and LP-616's
  exclusion — so it is exactly the set the verdict rests on, and a source that was excluded is not
  claimed as evidence.
- **`per_document` rules** populate it from their own subject, which IS the document. Any other
  enumerator's `subject_id` is a borrower / liability / account key, and emitting it would produce a
  link to a document that does not exist.
- **`document_id_by_content_id`** in `documents_section.py` resolves those back to real document ids,
  mirroring `document_filenames_by_content_id` (LP-377-B) exactly — the same reshape, so the keys
  cannot drift.
- **Write path** — `_build_finding` AND `_update_finding`. Both, because of the lesson recorded three
  lines away in that file: LP-598 set the category on mint only, so every finding that already
  existed kept the wrong one and "a fix that looked applied was not". On a re-run every finding is
  carried forward, not minted.
- **Read path** — `RuleFindingPublic.source_documents`, resolved against the file's CURRENT documents
  using the same `document_names` map `FindingPublic` already receives, so a stored id whose document
  was deleted is skipped rather than rendered as a broken link.
- **UI** — the governed row lists them, each linking to the document, mirroring the legacy card's
  `SourceDocLink`.

## Edge cases

**Not every rule can do this, and it must not pretend.** A loan-level rule over a computed tag — DTI,
reserves, LTV — often has no document to point at. Inventing one is worse than silence. Link where
the rule genuinely knows its sources; stay silent elsewhere.

**The snapshot holds no database ids.** `DocumentEntry` has `content_id` and no `document_id` — that
is what makes it content-addressed and run-independent, and it should stay that way. Naming documents
in the TEXT needs nothing new. Making them CLICKABLE needs a `content_id → document_id` map emitted
where the snapshot is built (which reads both), carried beside the snapshot rather than inside it.

**Content ids must never reach a processor.** LP-607 is the precedent: ID-4 shipped "differs across
sources (docdbbe8db1f5a7d9ff, doc6abd650d555473b0, …)" into a sentence a person reads, because the
composer's identifier guard matched only DOTTED ids and `doc<hex>` walked through. Use `source_label`
in text; keep `source_id` for identity and the link.

**The composer must not invent a document.** It may rephrase but never change the request, and it
already receives `document_kinds_on_file` (LP-610) so it can only name kinds actually present. Adding
per-document detail widens what it could hallucinate — the guard needs to cover the specific
documents cited, not just the kinds.

**Order must be deterministic.** An unsorted set re-renders in a different order each run, churning
the text and changing the composer's `cache_key`, which re-asks the model and moves the wording under
a processor on an unchanged file — the exact problem the snapshot-scoped cache was built to stop.

**Cardinality.** Naming ten documents is the same noise in a different shape. The useful form names
the minority group and counts the rest: "the two 2023 W-2s … the other eight".

**Deleted and superseded documents.** `source_document_id` is a FK with `ON DELETE SET NULL`;
`source_document_ids` is JSON with no FK and can dangle. Findings are retained after resolution
(ADR-061), so a stored set outlives the documents it names. Resolve links at read time against
current, non-deleted documents, and follow `version_group_id` / `is_current` to the live version.

**Tenancy.** Resolution is company-scoped (ADR-052) — a document id must never cross a company
boundary, and the read path must scope, not trust the stored id.

**Duplicate uploads are fine.** `assign_content_ids` folds an occurrence index into byte-identical
payloads, so two copies of one document get distinct content ids and the map stays 1:1.

## Suggested order

Tier 1 first — it is small, it restores a capability that silently stopped, and it makes the gap
visible on every finding. Tier 2 per rule family after, starting with the consistency rules.
