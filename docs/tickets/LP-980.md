- **Ticket:** LP-980 (the owner, 2026-10-15: "write the ticket and build it, keep it simple, do not make

- **Source:** the owner, 2026-10-13: "Once we confirm the plan it should display what we decided in plan

- **Status:** built. Mostly frontend, plus one server rule (see "A sent ask marked done").

## What it does

Today, once she confirms, the plan panel disappears and the conditions list is all that is left. Now the
plan she confirmed stays at the top of the page as the working view:

- **The heading** says it is the round's plan, when she confirmed it, and how many are ready. Three
  counts follow: **To do**, **Waiting on others**, **Ready to send**. They come from each condition's own
  status (`prep_status`), which the app already moves as work happens (a send moves it to Waiting, a
  wait's or an email's document coming back moves it on, LP-977).
- **Each condition** shows its status chip, **Now:** with the step it is on (`nextOf`, as before), and,
  when that step is an email to review, **Review and send**, which opens the draft.
- **Show steps** opens the steps she confirmed: steps already done are ticked (a sent email says
  "Sent Tue 13 Oct"), the step she is on is marked **Now**, and her task's upload and link buttons stay
  where they were.
- **Changing the plan is one click away, not in the way.** The editing tools (how it gets done, each
  task's next step, Already done, Not needed, Remove step, Add a step, Describe it, I'll handle it my
  own way) are hidden until she presses **Change the plan for 1947**. That opens the same tools as
  before Confirm, in place, under "Changing 1947's plan. Changes apply as you make them." with **Done**.
  - Changes apply at once; there is no second Confirm, because the condition's plan stays confirmed
    (the server already keeps `plan_confirmed_at` through edits).
  - Done steps stay ticked: they are the record.
  - **A task whose email already went out (the owner's choice a):** marking it Already done or Not
    needed just records it. Nothing more is sent; if the person sends it anyway, it is linked to the
    task. Remove step is already offered only on a step she added that is still open, so a sent ask
    cannot be removed (unchanged).
- **Conditions added after confirming** keep their own "Added after you confirmed" section and Confirm,
  as before (LP-976).
- **The conditions list stays below,** unchanged: its filters, bulk actions and the lender's answers are
  there.

## What was built

- **The working view** (`round-plan-panel.tsx`): once the round is confirmed, the panel shows "Plan for
  round N · confirmed MM/DD/YYYY", "X of N ready to send" and three counts, then one row per confirmed
  condition on the round. It reuses the plan's own row (`PlanRow`, now with `working`), so the steps,
  drafts and upload buttons are the ones she already knows.
  - **The status chip** uses the conditions list's own words (`CONDITION_PREP_STATUS`): To do, Waiting on
    Title, Ready to send, Sent to lender. The mock said "Your turn"; the list's words keep one vocabulary.
  - **Now:** is `nextOf`, as the plan's "Next:" was.
  - **Review and send** opens the draft of the task whose step she is on. "Now" passes over the app's own
    steps, so the step she is on is "Review the email…" and the draft id sits on the same task's "We
    drafted the email" step; the button reads it from there.
  - **Show steps** draws the timeline with `keepDone` (`plan-path.ts`): the steps already done stay,
    ticked, instead of being trimmed off; "Now" is marked on the step she is on; `nextOf` passes over
    done steps. A sent email's steps read "We drafted the email to Title / escrow" and "Sent 10/13".
    Before, its draft step still said "We draft the email … when you confirm the plan", which nobody saw
    while done steps were trimmed off.
  - **Change the plan for 1947** sets the row's own `editing` state: the same tools as before Confirm,
    with "Changing 1947's plan. Changes apply as you make them." and Done. Without it, the timeline hides
    each task's Already done / Not needed / Remove step.
  - **Conditions added after confirming** keep their own section below it (LP-976), and the dialogs (the
    step guide, the link dialog) moved outside both so either can open them.
- **A sent ask marked done (the owner's choice a).**
  - **On screen:** an asked task (`requested`) now offers Already done and Not needed, with "Its email went
    out. Marking it done or not needed sends nothing more; if it comes anyway, we link it to this
    task." "I'll do this step myself" stays for open tasks only. The server already allowed both, with a
    reason or a link (`update_item`).
  - **On the server:** marking it done left the condition "Waiting on Title" for good, because LP-977
    lets a Waiting move on by itself only when a WAIT made it. `_waiting_moves_on` now also accepts one a
    sent EMAIL made. `ready_because` still decides: while the asked task is out it is not done, so the
    Waiting stays, which is what LP-977 protected. A Waiting she picked (no `by`) is never moved.
  - **The LP-977 test that pinned the old rule** (`…an_email_made_is_not_moved_on…`) set every asked
    task to Not needed and expected Waiting. It is now two tests from one setup: with the ask still out
    it stays Waiting; with nothing asked it moves to Ready. A third marks the asked task done through
    `update_item`, the button's own door.

## Review (peer session, 2026-10-15)

Reviewed at `89e58056`. Three findings, all fixed here; every fix reproduced first and mutated after.
The five questions the builder asked are answered below, each by running something.

### Finding 1 — a refused edit on a confirmed row appeared under the other section

This is the LP-978 review's finding, one section later. That review split the refusal into two slots
because "a 409 from `confirm_round_plan` renders below every row, off the screen on a file with more
than a handful", and it left the row slot where it was: under the conditions, which was right while the
rows were all in one list. LP-980 adds a second list above it. The working rows' refusal line was
guarded `refusal && !showPlan`, so as soon as both sections are on screen — a condition imported after
the confirm, LP-976's own case — a refused edit on a CONFIRMED row ("Not needed" on a task whose email
went out, which the server can refuse) rendered at the bottom of the *plan to confirm* section, past
every row of both lists. Every test in the LP-980 block has `rows.length === 0`, so `showPlan` is false
and only one section renders: the configuration where the two slots can disagree was untested.

Fixed by making the refusal carry the condition it came from (`{conditionId, text}`, set by
`onErrorFor(condition)` — every call site already had the condition), and each section showing the one
its own rows raised. Reproduced in "shows a refused edit in the section whose row raised it", which
asserts the message IS on screen before asserting where, so its red says "wrong section", not "absent";
"and a refused edit on the plan to confirm stays there" is the control. The `useUpdateItem` mock could
not refuse, for the same reason LP-978 gave for the confirm mock, so it now can.

Mutations: the old `!showPlan` guard → the first test red; the plan section unconditional → the first
test red (the message renders twice); the working section unconditional → the control red.

### Finding 2 — "Review and send" was hidden on a condition that asks two people

`toReview` asked for the draft of the NOW task, and "Now" is one step for the whole row. On a condition
that asks two people — the code's own example, kept in `plan-path.ts`, is 0132, title's wire instructions
and the LO's disclosure — once the first email has gone, the row's Now is "Title / escrow sends it
back", someone else's step, and `next?.who === "you"` is false. The second email, still unsent and hers
to send, offered no button at all, and nothing else sends it. Reproduced in "offers the unsent email of
a condition that also waits on an earlier ask": no `Review and send` existed on the row.

Fixed by asking what the button is for: an unsent email of hers on this condition
(`entries.find((entry) => entry.step.draftId && !entry.step.done)`). A step carries a draft id only
while the draft is UNSENT (`taskPath`: `item.draft?.status === "draft"`), so this is sound rather than
wider. The `!entry.step.done` clause had no test, so it has one — "does not offer an email behind her:
the document came another way" (an ask never sent, the document linked by hand, so the path ticks the
draft and the send), with the same task before the document came as its control.

Mutations: back to the Now task's draft → the two-asks test red; the `!done` clause dropped → the
behind-her test red.

The row still offers ONE button, which opens the first unsent email; a condition with two of them has
the second on its "We drafted the email to …" step, which offers **Review draft** when the steps are
open (LP-968). So the collapsed row names one and the open row reaches them all.

One consequence to note: "Review and send opens the email the step is about, **only where that is the
step**" still passes (exactly one button across the three conditions), but what it now pins is "only
where there is an email to send". The name is worth rereading in that light.

### Finding 3 — the Waiting rule was restated as the enumeration a previous review had removed

`condition_plan._waiting_moves_on` reads `by in ("wait", "email")`. `condition_drafts` asked the same
question — is this status ours or hers? — and the LP-977 review replaced exactly that shape there,
because "a mechanism the list does not name reads as a status she picked", which is permanent: the event
history does not change. Its docstring says so, one commit before this one wrote the list again.

The list is green today only by luck of the five `by` values written in `app/services`: `wait` and
`email` are the only ones that reach Waiting (`plan` and `evidence` go to Ready, `unlink` to To do). So
the predicate and the property agree on every case reachable now, and the next mechanism to move a
condition to Waiting would be excluded in silence.

Fixed as one rule, in the module that writes the events: `condition_status.last_move_was_not_hers`,
called by `condition_drafts._wait_on_first_asked` and by `_waiting_moves_on`. No behaviour changes
today — both callers answer the same on every `by` that exists. Pinned by "a Waiting no person chose
moves on whatever made it" (`by: "reminder"`, standing for the next one), whose control is the existing
"a Waiting she set herself is not moved on by the plan" — a move with no `by` at all.

Mutations: the enumerated predicate restored → the new test red, the other 20 green; the shared rule
always "not hers" → both callers' controls red
(`test_a_waiting_she_set_herself_is_not_moved_on_by_the_plan` and
`test_a_send_never_overrides_her_own_move`).

### The questions, measured

1. **`keepDone`'s ticks.** Measured across five cases; exactly one was wrong. An ask, RECEIVED, with no
   check row left "Link it to this task" unticked although RECEIVED means it *is* linked, and `nextOf`
   named it as what to do next on a document she had already linked. The step now names what is still
   open ("Link it to this task, or mark the task done" when nothing checks it), and a tick-table test
   pins all of it. See the plan-path note in `plan-path.ts`.
2. **Can `toReview` open a sent draft, or another task's draft?** No, and the reason is structural: one
   draft id exists in `taskPath` and it is written only while `item.draft.status === "draft"`, so a sent
   email has none — "Review and send … only where that is the step" already covers it with 1947's sent
   draft beside 1228's unsent one. The id it picks is the drafted step's own. The real defect was the
   opposite one: no button at all (finding 2).
3. **One `open` set, two lists of rows.** They cannot collide: `confirmedRows` requires
   `plan_confirmed_at` and, when `late`, `onRound` requires it to be null, so no condition is in both
   sections and no condition has two rows. The dialogs are safe for the same kind of reason — `linking`
   holds its own condition, `help` holds a title and an option, `justAdded` is keyed by condition id.
   The one piece of shared state that was NOT keyed to where it came from was the refusal (finding 1).
4. **The server rule.** Probed through the real services: send → one task DONE (the condition stays
   WAITING, `waiting_on` the borrower, the done task keeps its sent-draft link) → both DONE (READY,
   `waiting_on` None) → the document arrives anyway (the done task stays DONE, the condition stays
   READY). Nothing misbehaves; what holds the middle case is `ready_because`, as the test says.
5. **A carried condition confirmed on its old round.** It IS in the working view: `confirmedRows` is
   keyed on `last_seen_round_id`, which a condition seen again on this sheet carries. That is what makes
   this screen's own sentence true — "N conditions from earlier rounds keep their plan. You'll see it in
   the list after you confirm" promised a list that, before LP-980, it never appeared in: after confirm,
   `onRound` holds only conditions with no confirmed plan. Pinned in "a carried condition is in the
   working view, as this screen promises" (not listed before the confirm, in the working view after it,
   and not asked to confirm a second time); mutation: key the working view on `first_round_id` → red.
   - Not changed, and worth the owner knowing: the working view is keyed on THIS round's confirm
     (`late`), so while a newly imported round waits for her, a carried condition's in-flight work is
     off this panel until she confirms — the same hold LP-975 put on its emails. The conditions list
     below is unaffected.
