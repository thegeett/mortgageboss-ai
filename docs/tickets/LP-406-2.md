# LP-406-2 — Write AS-8 (statement chaining / continuity) — **STOPPED at Phase 0 (D2)**

## What this ticket is

The Bucket 2 rule with **no AI dependency**: AS-8 verifies that a borrower's bank statements form an unbroken
sequence **per account** — no missing statement period, and each statement's ending balance carries into the
next statement's opening balance. Because it reads only **parsed** statement data (no AI tag), it has nothing to
calibrate — so unlike OC-1 (LP-406-4, held on calibration), *if it is expressible it can activate*.

**Phase 0's D2 (expressibility) is the whole ticket, and it refutes the premise.** AS-8's check is a
**cross-statement, per-account, consecutive-pair** comparison (statement N's ending vs statement N+1's
beginning; period N's end vs period N+1's start). The deterministic evaluator compares **single operands within
one subject enumeration** and has **no pairwise / "next" / sequence operand**; the `per_account` enumerator
**drops** exactly the per-statement balances/periods AS-8 needs; and `ConsistencyEval` checks *all-equal*, not
*ordered pairwise*. So AS-8 **cannot be expressed on the existing DSL/enumerators** — it needs a **new derived
per-account continuity producer**, whose construction this ticket explicitly scopes OUT ("propose, don't
build"). Per the ticket's own guardrails (and the PC-7 precedent, `LP-406-1.md`), I **stopped before writing the
spec, changed no rule code, and report the finding + a concrete proposal.** The only files this ticket writes
are this report and one ADR (ADR-322). `ACTIVE_RULE_IDS` stays **24**.

This is the third data point in the same pattern: **"produced" ≠ "checkable."** LP-405 verified the inputs are
produced (they are), but writability also needs the *check* to be expressible. PC-7 needed a `today` operand;
AS-8 needs a pairwise-sequence mechanism. Both are derived-producer work, not rule-writing.

## D1 — What does AS-8 actually check?

**Quoted:** `rule_kinds.csv`: *"AS-8, Statement chaining (continuity), Assets, structural, deterministic_only,
… , ending == next beginning — equality check per pair (not a ratio)."* Classification doc line 70 mirrors it.

**One plain sentence:** *AS-8 verifies that, within each bank account, the borrower's statements form an
unbroken sequence — consecutive statements have no missing period between them, and each statement's ending
balance equals the next statement's beginning balance.*

The description is clear (not thin). ⚠️ **Scope nuance (D4):** the rationale names only the **balance-carryover**
equality ("ending == next beginning"); the "no missing period" gap check is the ticket's framing and overlaps
AS-10 (statement-recency completeness, which already counts distinct months per account). See D4.

## D2 — EXPRESSIBILITY (the crux) — **NOT expressible; STOP**

**The check is inherently pairwise-across-documents.** For each account, order its statements by period, then for
every consecutive pair (N, N+1) test `ending_balance[N] == beginning_balance[N+1]` (and, if in scope, period
contiguity). Nothing in the deterministic stack can express that:

1. **The operand resolver** (`deterministic.py:128–159`) resolves each operand to **one typed value** per
   subject, from `tag` / `loan_tag` / `reference` / `calc` / `product`. There is **no operand for "the next
   statement's value"** — no sequence, no index, no pair. A comparison is `left <op> right` over two
   single values, not a fold over an ordered series.
2. **The `per_account` enumerator** (`enumerators.py:224–251`) is the obvious candidate — and it **actively
   removes** what AS-8 needs. It merges an account's statements into one tag map and, by design, **drops any
   per-statement tag whose value differs across statements** (each statement's own `ending_balance` /
   `beginning_balance` / `period_start` / `period_end`), leaving a rule to `couldnt_check`. Its own comment is
   explicit: *"A rule that needs the per-statement series uses resolve_accounts directly."* So a `per_account`
   deterministic AS-8 would see the balances **dropped** → couldnt_check on every multi-statement account
   (structural death — see D7).
3. **`ConsistencyEval`** (`specs.py:426`) gathers a tag across sources and checks they are **all equal** after
   normalization. Chaining is **not** all-equal — it is an **ordered pairwise** relation
   (`ending[N] == beginning[N+1]`, which are *different* balances) plus a period-contiguity check. Consistency
   cannot express order or the pair relation.

**Therefore AS-8 needs a new DERIVED producer** — the established pattern for "compute a cross-document,
per-group result in Python, expose it as a loan-level tag, and let a deterministic rule read it." Two existing
producers are the exact template (so this is a *known* mechanism, not a novel one):
- **`_stmt_min_account_months`** (`derived.py`) — groups statements per account via **`resolve_accounts`**
  (LP-336), reads each statement's own `stmt.period_end` from the document-subject tag maps, computes a
  per-account aggregate, **fires-if-any**, and **fail-closes to `unknown`**. AS-8's grouping + per-statement
  reads are identical.
- **`_income_max_employment_gap`** (`derived.py`) — the **consecutive-pairing** precedent: within a group,
  order records and pair each end with the *next* start to detect gaps, never pairing across groups. AS-8's
  "no missing period" + "ending→next beginning" is the same consecutive-pair fold.

**Building that producer is OUT of scope** (the ticket's D2 stop condition: "propose, don't build"). So: **STOP
and REPORT.** The proposal is in "The concrete proposal" below.

## D3 — The account-grouping key — **exists; not a blocker**

The per-account trap (global date-chaining fabricates false gaps across checking/savings) is **already solved**.
`resolve_accounts` (`enumerators.py:180`) groups statements by **`(normalized institution, masked last-4)`** —
both parsed extraction fields (`bank_name` + `account_number_masked`), **fail-closed**: a statement missing
either identifier is **unresolvable** and surfaced (never merged, never dropped), so a guessed grouping cannot
fabricate or hide a break. The proposed producer reuses this verbatim. **Known limitation (accepted, LP-336):**
the key excludes `account_type`, so a checking + savings sharing a last-4 at one bank collide into one key
(rare; adding `account_type` trades it for a more common over-split). Report it, but it is **not** a blocker —
the grouping key is reliable enough to chain within.

## D4 — The sequence + balance checks (real semantics)

All read-tags are produced from the **already-extracted** bank statements (parsed, subject **document**):

| read-tag | producer | subject | semantics |
|----------|----------|---------|-----------|
| `stmt.beginning_balance` | parsed | document | the statement's opening balance |
| `stmt.ending_balance` | parsed | document | the statement's closing balance |
| `stmt.period_start` / `stmt.period_end` | parsed | document | the statement period (ordering + the gap check) |
| `stmt.account_masked` | parsed | document | (with `bank_name`) the account-grouping identity |
| `txn.amount` / `txn.date` / `txn.is_money_in` | parsed / ai | transaction | per-transaction facts (see the scope note) |

**So the INPUTS all exist** — AS-8 is "writable-now" in LP-405's producer sense. The blocker is purely
**expressibility** (D2), not a missing producer. **Two/three candidate checks, and which AS-8 owns:**
- **Balance carryover** (`ending[N] == beginning[N+1]`) — the rationale's explicit check. **In scope.**
- **Period contiguity** ("no missing month") — the ticket's framing; **overlaps AS-10** (statement-recency
  completeness already counts distinct months per account via `_stmt_min_account_months`). Recommend AS-8 own
  the **balance chain** and coordinate with AS-10 on the gap dimension (avoid two rules firing on one missing
  month). A build decision, flagged.
- **Intra-statement reconciliation** (`ending == beginning + Σ money-in − Σ money-out`) — the `txn.*` read-tags
  in `rule_tags.csv` hint at this, but the rationale does **not** call for it. Treat as **out of AS-8's core**
  unless Priya wants it (it is a different, heavier check).

## D5 — The four outcomes (argued; encoded in the proposal)

| situation | correct outcome | how the proposal encodes it |
|-----------|-----------------|------------------------------|
| no statements at all | `not_applicable` | producer → `n/a`; the rule's applicability predicate rules the subject out (no finding) |
| exactly ONE statement for an account | **`not_applicable`** (NOT couldnt_check) | producer treats a 1-statement account as "nothing to chain" → does not contribute a break; if **every** account is ≤1 statement → `n/a` → not_applicable |
| two+ statements, a period missing | `fired` | producer detects a gap in a consecutive pair → `broken` (reason names the account + the missing period) |
| two+ statements, balances don't carry | `fired` | producer detects `ending[N] != beginning[N+1]` → `broken` (reason names the account + the two balances) |
| a statement's period/balance unreadable | `couldnt_check` | producer → `unknown` (fail-closed); the gate couldnt_checks — never a fabricated pass |

⚠️ **The one-statement → not_applicable requirement is the subtle part**, because `not_applicable` is **not a
deterministic *outcome* verdict** (the outcome verdicts are `fired`/`satisfied`/`needs_review`/`couldnt_check`).
It is produced by the **applicability** layer. So the proposed producer must emit a **distinct `n/a` value** for
"nothing to chain," and the rule declares an `applicability` predicate (`stmt.continuity == n/a → not
applicable`) so a file whose accounts each have ≤1 statement resolves to **not_applicable**, never
`couldnt_check`. This is the single most important design point for the build ticket — collapsing it into
`couldnt_check` would make AS-8 look broken on ordinary single-statement files.

## D6 — A Priya threshold?

**Likely none.** The balance carryover is an **exact** equality (statement N's ending balance *is* statement
N+1's beginning balance at the same instant — no interest posts "between" them), so no tolerance is needed; the
rationale says "equality check." The period-gap dimension (if AS-8 owns it) is contiguity, not a
count-threshold (the "how many months required" threshold belongs to AS-10). So AS-8 as scoped carries **no
Priya numeric threshold** — meaning that, once the producer exists, it could activate through the
`no-ai-dependency` gate without a sign-off (its input resolving on the fixture). One thing to confirm with Priya
at build time: whether a **tiny** rounding/pending-item delta should ever be tolerated (default: no — exact).

## D7 — The subject match (anti-structural-death) — confirms the STOP

AS-8's balance/period tags are all `subject: document` (per statement). There is **no subject enumeration at
which a deterministic AS-8 can read the pair**: `per_document` sees one statement at a time (can't reach "the
next"); `per_account` **merges and drops** the differing per-statement balances (→ couldnt_check on every
multi-statement account — the ID-5 structural-death class). So a deterministic AS-8 written today is **born
structurally dead**. The derived-producer approach sidesteps this exactly as `_stmt_min_account_months` does: the
**producer** reads the document-subject tags directly (via `resolve_accounts` + `by_subject`) and emits a
**loan-level** result the rule reads at the `loan` subject — subjects then match.

## The concrete proposal (for a build ticket — NOT built here)

**New derived tag `stmt.continuity` (loan-level).** Mirrors `_stmt_min_account_months` (grouping + fail-closed)
and `_income_max_employment_gap` (consecutive pairing):

- **Group** statements per account via `resolve_accounts(snapshot)` (reuse — solves the per-account trap;
  unresolvable statements surface, never merge).
- **Per account:** read each statement's `stmt.period_start`/`period_end`/`beginning_balance`/`ending_balance`
  from the document-subject tag maps (`snapshot.tags.by_subject[content_id]`); order by period; for each
  consecutive pair test `ending[N] == beginning[N+1]` (and period contiguity if AS-8 owns it).
- **Emit** one of: `"broken"` (a real break — reason names the account, the pair, and balance-vs-period),
  `"ok"` (every account chains cleanly), `"n/a"` (no account has ≥2 statements — nothing to chain), `"unknown"`
  (a needed period/balance is unparseable — fail-closed, never a fabricated pass). Fire-if-any (one broken
  account is not masked by clean ones), the `_stmt_min_account_months` discipline.
- **Size:** ~40–60 lines + one derived-registry entry + one `tag_production.yaml` declaration + one
  `fact_tags.csv` row — the same footprint as `_stmt_min_account_months`.

**Then AS-8's spec** (a follow-up, once the tag exists) is trivial and deterministic: read `stmt.continuity`;
`broken → fired`, `ok → satisfied`, `unknown → couldnt_check` (gate), `n/a → not_applicable` (applicability
predicate). No per-rule Python.

**Recommended sequencing:** a small producer ticket (`stmt.continuity`) — analogous to LP-407's producer-wiring
wave, or a standalone — then AS-8 rides it. AS-8 remains the low-risk, no-calibration rule the epic wants; it
just needs its input computed first, like PC-7 needs `contract.days_until_closing`.

## THE PROOF

None to report — no rule was written. Writing a deterministic AS-8 today would read per-statement balances that
either aren't reachable (`per_document`) or are dropped (`per_account`) → a uniformly-`couldnt_check`,
structurally-dead rule, which the ticket forbids shipping. Root cause named: **inexpressibility + the enumerator
merge-drop**, not absent data (the data is produced) and not a bug.

## Every assumption / decision

- **The gate is producer-existence × DSL-expressibility.** Producer existence read from `tag_production.yaml`
  (all AS-8 tags produced); expressibility read from `deterministic.py` (operand sources), `enumerators.py`
  (`_per_account` merge-drop), and `specs.py` (`ConsistencyEval` all-equal). Every claim is a read.
- **A derived producer is the fix, and it is an EXISTING pattern**, not a new mechanism — `_stmt_min_account_months`
  already does per-account grouping in Python and exposes a loan tag a rule reads; `_income_max_employment_gap`
  already does consecutive-pairing. Building it is out of scope (D2 stop).
- **The account key exists** (`resolve_accounts`) — D3 is not a blocker; I did **not** discover a
  no-grouping-key blocker.
- **Scope call flagged, not decided:** whether AS-8 owns the period-gap dimension (overlaps AS-10) and the
  txn-reconciliation dimension (hinted by the `txn.*` read-tags, not in the rationale) — deferred to the build
  ticket / Priya, not invented here.
- **I did not invent a different AS-8** to force a writable rule; the rationale is unambiguously per-pair
  chaining.
- No rule code changed. `ACTIVE_RULE_IDS` stays 24. This report + ADR-322 are the only deliverables.

## The NEW gap (for the backlog)

**`stmt.continuity` — a derived, loan-level per-account continuity tag** (spec above). It unblocks AS-8 and is
the reusable substrate for any per-account statement-sequence check. It is the direct analog of PC-7's
`contract.days_until_closing` gap: a small derived producer that a cheap deterministic rule then rides.

## What this means for IN-6 (LP-406-3, the last Bucket 2 rule)

Apply the **same D2 expressibility check first.** IN-6 ("pay-stub ↔ W-2 employer coverage") is a **set-match
across documents** (are the pay-stub employers ⊆ the W-2 employers and vice-versa). That is a **cross-document
gather-and-compare** — which is exactly what **`ConsistencyEval`** exists for (gather `income.employer_normalized`
across the income documents, compare). So IN-6 is **more likely expressible than AS-8** *if* a set/coverage
compare fits the consistency shape (all-present-both-ways), and its AI tag `income.employer_normalized` is
already **measured 100%** (live via IN-5) — so unlike OC-1 it would **not** be held on calibration. But confirm:
`ConsistencyEval` checks *agreement of gathered values*, not *two-way set coverage* — if "every stub employer
has a matching W-2 and vice-versa" doesn't reduce to its agree/disagree model, IN-6 too may need a small derived
set-coverage tag. **Run IN-6's D2 before writing** — the lesson of PC-7, AS-8, and this session: verify the
*check* is expressible, not just that the inputs are produced.

## ADR

**ADR-322** (added to `decisions.md`): the deterministic DSL cannot express cross-document / ordered-pairwise
comparisons; per-account (and per-sequence) continuity checks must be computed in a **derived producer** (the
`_stmt_min_account_months` / `_income_max_employment_gap` pattern) and read as a loan-level tag — which shapes
AS-8 and every future statement-sequence / continuity rule. Recorded because the ticket asked for it explicitly
("record if D2 finds the DSL cannot express cross-document pairing"), and because it is the durable pointer that
saves the next author from rediscovering the limit mid-build.
