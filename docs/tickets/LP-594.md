# LP-594 — Run history: a real tooltip, and a dropdown that floats

## What prompted it

Two observations on the run-history control shipped in LP-593, in the same breath:

> "mouse pointer on that count should not standard type pointer it should show something different
> so that user know that there is tool tip, infact current hover over looks old style tooltip"

> "run history drop down should not expand the page it should display drop down in front of all
> components"

Both are the same underlying defect: the control was built as markup rather than as a control.

## The tooltip

LP-593 put the three counts (needs attention / satisfied / cross-checks) in each history row as bare
numbers, with the native `title` attribute carrying what each one means. That was wrong in three
ways, in increasing order of importance:

1. `title` is drawn by the OS after roughly a second, and cannot be styled — it does not match the
   tooltips used everywhere else in the app (`components/ui/tooltip.tsx`, Radix-backed).
2. It is not reachable by keyboard, and a screen reader reads a bare figure with no label.
3. **It gives no affordance.** The cursor over a `title` element is the ordinary arrow, so nothing
   tells a processor the number is explainable. The meaning was present and unreachable.

`components/ui/tooltip.tsx` already existed and was already in use in the LTV calculator — this was
a case of writing new markup instead of reaching for the component that was there. The counts are now
Radix tooltip triggers: `cursor-help` plus a dotted underline as the visible affordance, an
`aria-label` (`"26 Needs attention"`) so the accessible name carries the meaning, and a `<button>`
element so the tooltip opens on focus as well as hover.

The provider is local (`delayDuration={150}`), matching the LTV calculator, because no
`TooltipProvider` is mounted at the app root. 150ms rather than the Radix default: these are dense
adjacent numbers a processor scans across, so a slower tooltip gets missed and a zero-delay one
flickers as the pointer travels.

## The dropdown

The panel was in normal flow, so opening it pushed every component below it down the page. On a file
with twenty runs that displaced the findings a processor was reading, and closing it moved everything
back — the page reflowed twice around an action that should have been weightless.

It is now `absolute left-0 z-20` over an opaque background with `shadow-lg`. Specifics worth
recording, since each was a decision rather than a default:

- **`inline-block` on the root.** The root is `relative` so the panel can anchor to it, but as a
  plain block it spans the header's left column, which would put the panel's edges nowhere near the
  button that opened it. `inline-block` shrink-wraps the anchor to the trigger.
- **`left-0`, not `right-0`.** The trigger sits in the card header's left column.
- **An explicit `bg-white`.** Out of flow, the panel no longer paints over the card behind it; without
  a background it would be transparent.
- **`max-h-80` with its own scroll, and `max-w-[min(28rem,calc(100vw-3rem))]`.** The run list is
  unbounded — twenty runs today, no cap on a busy file.
- **No clipping ancestor.** `components/ui/card.tsx` sets no `overflow` rule, so the overlay is not
  clipped by the card it sits in. This is a real failure mode for absolute overlays and was checked
  rather than assumed.

### Dismissal came with it

Overlaying introduced a problem the in-flow version did not have: the panel now *covers* what is
underneath. Left open, it sits over the processor's findings with no way out but the trigger, which
reads as stuck. So it now closes on an outside pointer-down and on Escape.

The outside-click handler has one non-obvious guard: Radix portals tooltip content **outside** this
component's subtree, so a plain `root.contains(target)` check would treat hovering a tooltip as an
outside click and close the panel under the pointer. `isInsideTooltip` checks for the popper wrapper.

## Tests

`version-selector.test.tsx` — nine tests. The three that asserted `getByTitle` now assert the
accessible name (`getByRole("button", { name: "26 Needs attention" })`); this is the more honest
assertion, since tooltip text only enters the DOM on hover while the name is always there. Four are
new: the `cursor-help` affordance, the overlay positioning, outside-click dismissal, Escape
dismissal, and that a click *inside* the panel does not dismiss it.

Every guard was mutation-checked — dropping `cursor-help`, dropping `absolute`/`z-20`, dropping the
`aria-label`, deleting the dismissal effect, and dropping the `contains` guard each fail the suite.

**Not covered:** the `isInsideTooltip` portal guard. Driving a Radix tooltip to open in jsdom is
awkward enough that the test would assert the mock rather than the behaviour, so it is verified by
reading rather than by a test.
