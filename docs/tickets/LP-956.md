## 10a — "Waiting on Processor"

**What was measured.** There is no separate waiting-on picker. A move to Waiting sends the condition's OWNER
as who it waits on (the row's select, the move-back dialog, and the bulk move, which falls back to each row's
owner). 0006's owner, from UWM's code map, was `processor`, so it became "Waiting on Processor".

**The fix, at every door, leaving the processor a valid owner (her task):**
- **Server:** `move_prep_status` refuses `waiting_on = processor` (`waiting_on_self`, "You can't wait on
  yourself. Choose who you are waiting on, or keep it in To do."). The bulk move goes through it, so a
  processor-owned row is refused with that sentence while the others move.
- **Screen:** a move to Waiting on a condition whose owner is the processor opens "Who is 0006 waiting on?"
  (`WaitingOnDialog`), offering every owner but the processor, instead of sending her. The move-back dialog
  carries her reason into it. `waitingOnFor(condition)` is the one rule both moves use.
- The owner pickers (`OFFERED_OWNERS`) keep Processor, as asked.
- `imported-view.tsx` still sends the owner, but it is unreachable since LP-913 (nothing renders it); the
  server refusal covers it.

## 12 — the readonly views

`upgrade()` (a dropped view drops its grants, LP-842). The re-grant IS tested:

- `readonly.condition_items` (new): ids, key, who acts, step, status, origin, documents and checks (codes),

**Guards.** `condition_items` leaves `EXCLUDED_TABLES` and gets a per-column EXCLUDED set. `acceptable` and

`condition_evidence` exclusion reason, which said "Excluded whole, like `condition_items`", is corrected.

**Docs.** `docs/querying-staging.md` gains a "Conditions (LP-956)" table: what each condition view carries and
leaves out, and that `condition_evidence`, `condition_drafts` and `condition_packages` stay out.

## Review (of `3d862cca`)

**One finding, fixed here: the new `readonly.conditions` carried `plan_reason`, which can quote a found
document's file name — and `documents.document_name` is in `NEVER_EXPOSED` precisely because a file name
can hold a person's name that the scrub cannot match. Item 10a is right, and right at a layer the spec
did not ask for: the spec said "remove it from the pickers", the build measured that there are no
waiting-on pickers and refused the state at the server instead.**

### Finding — `plan_reason` walks a document's file name around `NEVER_EXPOSED`

The view selects `plan_reason`. That column is assigned at `condition_plan.py:605`:

```python
reason = reason or f"Found: {found.document_name or found.document_type}, page 1"
```

so it can hold a document's FILE NAME — and `test_round_one_plan_is_plan_section_6`
(`tests/conditions/test_condition_plan.py:158`) already pins exactly that:
`plan_reason == "Found: Credit invoice 07/15, page 1"`. The path is LP-953's door 2 ("Already in the
file", found at plan time), which runs on most plan builds.

`("documents", "document_name")` is in `NEVER_EXPOSED`, and the reason written beside it is the strong
form: *"the scrub matches identifier SHAPES, and a person's name is not digit-shaped, so a name in this
column would cross a view intact."* `NEVER_EXPOSED` matches `(table, column)` names over the migration
text, so the same string arriving under `conditions.plan_reason` was invisible to it. Measured against
the real view object rather than the migration text — the migration's own DDL executed into the test
database, then read back from `pg_get_viewdef`:

```
plan_reason in readonly.conditions' columns : True
as Postgres stores it                       : 'plan_reason,'   (a bare column)
any scrub() anywhere in the stored view     : False
```

A query result is the thing CLAUDE.md says is "safe to read into a transcript", which is what makes this
worth more than a column list. The new `docs/querying-staging.md` table said it plainly two lines apart:
`plan_reason` under "Carries", and then "`condition_evidence`, `condition_drafts` and
`condition_packages` stay out entirely: their rows restate amounts, account endings and **document
names**."

**Where it came from, because it is not this ticket's mistake.** The `EXCLUDED` note LP-956 acted on read
*"`plan_reason` is built by code and names no borrower; `next_step` is a category. Both excluded only to
avoid rebuilding the view."* `git log -S` puts that comment and the `Found: {document_name}` writer in
the **same commit** (`106de9af`, LP-920) — so the claim was wrong the day it was written, nothing
enforced it, and two tickets later it was read as a cleared check. A comment recording a safety property
is the thing this repo has been bitten by before; the fix puts the property where it is executable.

**Fixed:** `plan_reason` is out of the view (`next_step` stays — it is a `PlanOption`, a category); it is
in `EXCLUDED` with the real reason and the writer's line number; and it is in `NEVER_EXPOSED`, so
re-adding it fails `test_never_exposed_columns_are_absent_from_every_view[conditions-plan_reason]` rather
than shipping. Re-adding it to the view fails exactly that one case and nothing else. The builder's own
run is the evidence the guard could not see it before: 9117 passed with the column exposed.

I did **not** change the writer. The document's name is the right thing for her to read on screen
("Found: Credit invoice 07/15, page 1" is more use than "Found a document"); it is the view that is the
wrong place for it. If a staging query ever needs the reason, the shape is a derived category
(`plan_reason IN (<the eight REASON_* constants>)`), not the free string.

### Checked and not findings

- **Item 10a is fixed at the layer the bug lives on.** The spec named two pickers to edit; there are no
  waiting-on pickers — a move to Waiting sends the condition's OWNER, which for the trial's 0006 was
  `processor` from UWM's code map. So editing a list would have fixed nothing, and the build refuses
  `waiting_on = processor` in `move_prep_status`, the one door, which is why the bulk move refuses just
  that row and moves the rest. This is the right answer to a spec that asked for the wrong change, and
  the ticket says so rather than quietly doing something else.
- **The dialog is derived, not hand-written.** `WAITING_ON_CHOICES` is `OWNER_LABEL`'s keys minus
  `processor`, so a new `OwnerHint` appears in it automatically. That is the failure LP-955's review had
  to fix in `ASK_WHO` (a hand-written subset of an enum, three recipients short), arrived at correctly
  one ticket later.
- **The move-back path carries her reason through the dialog.** `setWaitingAsk({condition, to, reason})`
  and `onChoose` sends it on. Interposing a dialog on a backward move and dropping the reason would have
  earned the server's "a backward move needs a reason" refusal; it is the detail most likely to be lost
  and it is handled.
- **An existing "Waiting on Processor" row can still be corrected**, which I expected to be the defect:
  the no-op short-circuit compares `new_waiting_on == condition.waiting_on` as well as the status, and
  its comment says "same status with a different owner … IS a change and is recorded". So the trial's
  0006 is not stuck; a move to Waiting naming someone else writes.
- **`waiting_on_when_sent` cannot derive PROCESSOR.** It and the real move both go through
  `first_asked_owner`, which returns `WAITING_ON[recipient]`; that table maps nine `DraftRecipient`s and
  none to `PROCESSOR`, and `DraftRecipient` has no processor member. So the prediction line cannot say
  "Becomes Waiting on Processor" — this was my first hypothesis, from the derived-sibling defects in
  LP-953 and LP-955, and it does not hold here.
- **`imported-view.tsx` is genuinely unreachable.** It still sends `effective_owner`, and it is rendered
  only from its own test file (`conditions-list-view.tsx:59` records that it replaced it). The server
  refusal covers it, and its tests pin no `processor` owner, so nothing is green on a state the server
  now refuses.
- **The new items view carries no NPI.** `documents` and `checks` on `condition_items` are `list[str]` of
  library-validated codes — the loader refuses `checks: ["vibes"]` and `documents: ["napkin"]` — not
  `condition_evidence`'s `list[dict]` whose check reasons restate amounts, which is why that table stays
  excluded whole. `name`, `acceptable` and `specifics` are out, with `name` pinned by a per-view test
  because other views carry a `name` legitimately; they measured that gap before closing it.
- **The rollback is correct, measured rather than read.** The LP-842 trap is a downgrade copied from an
  older definition, which silently drops columns a later migration added. I extracted both downgrade
  bodies and diffed their select lists against the most recent prior definition of each view:
  `readonly.conditions` 33 columns against LP-912's, `readonly.condition_rounds` 31 against LP-915's,
  with no column on either side only. No test covers downgrades, so this is worth having been checked.
- **The re-grant is tested, and I told the builder otherwise mid-build.**
  `test_every_migration_that_recreates_a_readonly_view_regrants_it` pre-dates this ticket, is a rule over
  the tree rather than a list, and slices the `upgrade()` body so a module-level GRANT constant that is
  never executed does not satisfy it. I had conflated it with the module docstring's "privileges are NOT
  tested", which is about the role's cluster-scoped privileges. My note was wrong, the ticket had
  repeated it, and both are corrected.
- **Their disclosed gap is closed.** They reported 9114 passed / 3 failed — the named sonnet test plus
  the two refusal-code censuses, which caught the new code unregistered and unexercised — then fixed
  those and re-ran only those files plus the readonly tests (127 passed). The full suite at `3d862cca`:
  **9117 passed, 1 failed** (the named sonnet test), 8 skipped, 1 xfailed. The censuses pass; their fix
  was complete.
