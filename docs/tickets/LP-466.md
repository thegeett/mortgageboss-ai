# LP-466 — Add three catalog types: `home_value_estimate`, `wire_instructions`, `lender_dashboard_screenshot`

Ticket 2 of the missing-types work. The three ship together because the UWM portal
**dashboards embed an AVM block**, so the AVM type and the dashboard type resolve as a
pair (one decides where an embedded value block routes). Same four-piece mechanism as
LP-465: catalog entry · classifier indicator (CI-locked with the catalog) · JSON spec ·
generate.

Guiding constraint, load-bearing throughout: **an AVM is not an appraisal and is not
evidence of value for underwriting.** The name and the indicator must make that
impossible to miss, so nobody later wires it into a property rule as an appraised value.

### A2 — the three indicators (quoted)

**`home_value_estimate`** — the most important separation in the ticket (vs `appraisal` and
`property_profile_subject`):
> *an Automated Valuation Model (AVM) / Home Value Estimate — a software-generated estimated
> market value of a property (an estimated value, a value range, and basic property facts:
> beds/baths/sq ft/taxes), typically from a lender portal's "Home Value Estimator" tool. It
> **explicitly states it is NOT an appraisal** ("does not constitute an appraisal; should not
> be relied upon in lieu of an appraisal"). It is NOT an `appraisal` (a licensed URAR/Form
> 1004 with comparables, condition, and a certified appraised value) and NOT a
> `property_profile_subject` (a data-vendor profile with APN, owner, tax status, and
> ownership history). It is a non-binding value estimate only.*

**`wire_instructions`** (vs `general_correspondence`, where these currently land):
> *closing/settlement wire instructions — a payee sheet from a title company, law firm, or
> escrow/settlement agent giving where to send closing funds: a beneficiary name/address, a
> receiving bank name/address, an **ABA routing number and account number**, and often a
> callback phone to verify. It is transactional funds-routing, NOT general correspondence,
> and NOT a bank_statement or verification_of_deposit (it moves funds, it does not evidence
> a borrower's assets).*

**`lender_dashboard_screenshot`** (vs the document types whose data it displays):
> *a screenshot/print of a lender or broker PORTAL (e.g. `uwm.com/dashboard`) — software UI
> chrome: navigation, pipeline/loan alerts, rankings/points, marketing tiles, and embedded
> tools. It is a capture of an application, NOT the underlying document — the borrower/loan
> data it happens to display (a loan status, an AVM block, a rate) is not itself this type.
> Route a capture DOMINATED by one embedded artifact (e.g. the Home Value Estimator screen)
> to that artifact's type (`home_value_estimate`); use this only for a broad dashboard where
> no single embedded document dominates.*

### A3 — the embedded-AVM decision (one label per document)

**Decision: classify by DOMINANCE — one label per document.**
- A capture whose **substance is the HVE/AVM block** (070, 197 — the Home Value Estimator
  *is* the screen, even with the portal's tab bar) → **`home_value_estimate`**, and its value
  fields are extracted.
- A **broad dashboard** where the AVM is one buried panel among many (061 — a 4-page portal
  with the HVE on page 3 amid ranking/alerts/leads/production) → **`lender_dashboard_screenshot`**,
  identity only; **the embedded AVM value is deliberately NOT extracted.**

**Why not dual-label / why not always extract the embedded value.** A document gets one
label (the closing-package limit, in miniature). Losing the embedded AVM value on a full
dashboard is acceptable precisely because **an AVM is not underwriting evidence** — there is
no rule that needs it, so not capturing it costs nothing a rule relies on. The dashboard
type's job is (1) stop diluting `unknown` and (2) let the classifier route an *HVE-dominant*
capture to `home_value_estimate` instead of burying it as "dashboard." The indicator encodes
exactly this dominance test.

⚠️ **This is a prediction to be proven in Phase C.** 061/063/160 are dashboards with a
salient HVE block; whether the classifier honors "dominance → dashboard" (vs being pulled to
`home_value_estimate` by the value block) is an empirical question. Phase C re-classifies all
three and reports which way each goes; a 061 that lands on `home_value_estimate` is a finding,
not a silent pass.

### A4 — PII registrations + the digit-run guard

The at-rest guard is `_LONG_DIGITS = \b\d{9,}\b` (persistence.py) — a run of **9+ CONTIGUOUS
digits**, word-bounded, **no internal separators** (distinct from the dash/space-tolerant
`_DESC_REDACT` used for list-row scrubbing). Against that:

- **`aba_routing_number`** — `121000248`, 9 bare contiguous digits → **trips the guard →
  MUST mask.** Not yet in `_PII_FIELDS` → **register `(ACCOUNT, False)`** (from_raw: masked
  display + per-file match-hash, so two wires to the same bank can correlate).
- **`account_number`** — `6968528577`, trips → must mask. **Already registered** `(ACCOUNT,
  False)` (added for form_1099). Reuse — no change.
- **`loan_number`** (dashboard, when present) — already registered `(ACCOUNT, False)`. Reuse.
- **`verification_phone` stays UNMASKED** (the ticket's requirement — it is the anti-fraud
  callback a processor must read). Safe under this guard: a formatted phone `(877) 838-0777`
  / `877-838-0777` has no 9-contiguous-digit run, so it does not trip. **Residual (flagged):**
  a phone printed as 10 *bare* contiguous digits *would* trip and refuse that one snapshot —
  rare; the extractor prompt will be told to preserve the phone's printed formatting.
- **`reference_or_memo`** — free text; on 154 it carries no digits. **Residual (flagged):** a
  memo that embeds a bare ≥9-digit file/loan number could trip the guard. Low risk; I
  recommend adding `reference_or_memo` to `_SCRUB_FREE_TEXT_FIELDS` for `wire_instructions`
  as a belt-and-braces backstop (the same 9+-digit scrub the credit_report alert fields use).
- **AVM / dashboard:** no PII. Every AVM number is < 9 digits; dashboard identity fields carry
  no long digit runs (capture date, platform, section label). `home_value_estimate` and
  `lender_dashboard_screenshot` need **no** `_PII_FIELDS` entries (dashboard `loan_number`
  rides the existing global registration if ever populated).

Net new PII registration: **`aba_routing_number` only.** Plus a recommended
`reference_or_memo` scrub.

### A5 — tiers, categories, and the dashboard Tier-1 tension

**Categories/tiers (proposed):**
- `home_value_estimate` → **Tier 1**, `PROPERTY` — property valuation data a processor reads.
- `wire_instructions` → **Tier 1**, `MISC` — a closing/settlement operational doc; no
  category fits better than MISC (there is no settlement/closing bucket), and it earns Tier 1
  on the PII-handling need (typed+masked routing/account).
- `lender_dashboard_screenshot` → **Tier 1**, `MISC` — a software capture; MISC is the honest
  home.

**The Tier-1 tension for `lender_dashboard_screenshot` — reported, not silently resolved.**
The LP-441 invariant (`test_tier_1_iff_the_type_has_a_schema_spec`) is a strict bijection:
a catalog type is Tier-1 **iff** it has a schema spec. So the choice is binary:
- **(A) Tier 1 + a minimal identity spec** — the 5 identity scalars, generated extractor.
- **(B) Tier 2 + no spec** — recognized/summarized only, no typed fields.

**Recommendation: (A) Tier 1 + minimal spec.** "Extracts almost nothing" is about
*deliberately not schematizing the dashboard's panels* — not about being Tier 2. A 5-field
identity extractor IS "almost nothing," done as Tier 1, and it delivers the useful bit
(loan_number/borrower_name tie a file-specific capture to its loan). Critically, **(A) keeps
the invariant intact with no special case** — spec ⟺ Tier-1 still holds. (B) would also be
defensible (a dashboard as a "recognized but not extracted" Tier-2 type) and would avoid a
spec entirely, but it forfeits the identity capture the ticket asked for and would need the
type added to the classifier's Tier-2 listing instead. I lean (A); flagging (B) as the live
alternative rather than choosing for you.
