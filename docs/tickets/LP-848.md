# LP-848 — a draft written before its template existed

Status: spec. Third of four.

## What the report was, and what it actually was

> "Looks non borrower parties still showing 'We are working through your loan file…'"
> "I am talking about new draft, it does not shows new changes."

Measured on staging: the lender and employer drafts on that file were created **2026-09-12
01:11:39 UTC**. LP-843 was committed at **03:39 UTC** — two and a half hours later. Staging confirms
it from the other side: no draft anywhere has ever carried `document_request_third_party`, and those
rows still record `template_version = v4`, which is the BORROWER template's version.

So a genuinely new party draft does get the new voice. The drafts in front of the processor predate
the fix. **That is not a reason to close this**, because the reason they predate it is a defect:

## Two real defects behind it

**1. A stored body is never corrected.** `_regenerate` runs only when documents are added or
removed, so an open draft composed before any template change keeps its old words forever. There is
no path by which those lender and employer drafts become right — a processor either notices and
deletes them, or sends the borrower's words to a lender.

**2. `_regenerate` updates the body and the version but NOT the `template_key`.** So when one of
those drafts IS regenerated, it becomes `document_request_lender` + `v1` — and no such template has
ever existed at any version. That is precisely the ADR-401 breakage LP-843 was written to fix,
reintroduced through the back door on exactly the rows most likely to hit it.

Defect 2 is the sharper one: LP-843 asserted that every party's **new** draft names a template that
resolves, and said nothing about a draft that already existed.

## The change

- `_regenerate` re-stamps `template_key` from the party, not only the version. Key and version are
  produced by one render and must be written by one statement.
- A stale open draft is brought current. The options are to regenerate on read, or to migrate the
  existing rows once. **Decided at build time, on one question: whether a processor may be reading a
  draft mid-edit when it is rewritten** — regeneration that discards an unsent edit would be a worse
  bug than the one being fixed.
- A test that a draft carrying a pre-LP-843 key and an old version does not stay that way.

## The class, not the instance

Any template change has this shape: new sends are fixed, open drafts are not, and nothing says so.
That is worth naming in the ticket rather than fixing generically — a version bump is rare enough
that a per-bump decision is honest, and a generic "regenerate everything on deploy" would throw away
processor edits.

# Built

Both defects, and a third that this fix created and a two-ticket-old test caught.

## The key and the version are one fact

`_regenerate` stamped the version alone, so a draft carrying LP-841's `document_request_lender`
became `document_request_lender` + `v1` — naming no template that has ever existed. Both now come
from the same `rendered` object in adjacent statements.

## A stale draft heals when it is read

`refresh_if_stale` compares what the draft records rendered it against what would render it now.
**Staleness is derived, not guessed**, so it keeps working for the next template bump without
anybody remembering this function exists.

Called from `draft_for_reading`, which is the function the message dialog uses — healing anywhere
else leaves the screen that produced the report showing the old words.

**Regeneration is lossless for an unsent draft, and that is measured rather than assumed.** Exactly
two things write `Communication.body`: `_regenerate`, from the template, and `send_draft`, which
stores the processor's own edit at the moment of sending. There is no save-without-sending endpoint,
so before a send the stored body is always template-generated and there is no human edit to discard.
Recorded in the function: **if an edit-and-save path is ever added, this becomes destructive** and
must move behind an explicit action.

A sent message is never touched. Its body is the record of what went out.

## THE WORSE BUG THIS FIX SHIPPED FIRST

The first version used `_party_of_draft`, which falls back to BORROWER for a key it cannot place —
correct for choosing a greeting, catastrophic here. An unrecognised key is "not the borrower's
template", which reads as stale, so a **title company's draft was re-rendered as a borrower email
and greeted the title company by the borrower's first name.**

Caught by `test_a_party_draft_is_editable_and_keeps_its_own_address`, which had been asserting
exactly that for two tickets. The lesson is the one about scoping a guard by symptom: the property
is not "this differs from what I expect" but **"I know what this should say, and it does not say
it"**. `_known_party_of` has no default, and a draft whose audience cannot be established is left
exactly as it is, because no version of it is known to be better.

## Two of my own tests were wrong before they were right

- One asserted regeneration by adding a second document — a *title* document, which routes to the
  title company, so it created a new draft and never regenerated the lender one. It failed for the
  right reason by luck.
- Its replacement was then redundant: under LP-832 a request creates a NEW draft, so an existing one
  is never regenerated by a request at all. Deleted, and the key-stamp claim is covered by the heal
  test — verified by mutation rather than by assumption.

## The wiring, for the fourth time

Removing the `refresh_if_stale` call from the read path passed **1647 tests**, because every test
above calls the heal directly. That is the fourth time in this run that something was built
correctly and connected to nothing — the shape of the original LF-JR4T report. Closed by a test that
reads a stale draft through `draft_for_reading` and asserts both the returned words and the
corrected row.

## Review (second session)

Reviewed `40684050`. One defect found, and it is the one the ticket suspected: the guard protects one
of five entrances.

### The finding — `_regenerate` re-derived the audience leniently

`refresh_if_stale` resolves the audience strictly and refuses a draft it cannot place. But the
regeneration it guards is shared, and it resolved the party *again* with the lenient helper that falls
back to the borrower. Five functions reach it:

| caller | guarded before this review |
|---|---|
| `refresh_if_stale` | yes |
| `_add_to_party_draft` | no |
| `attach_upload_link` | no |
| `remove_need_from_draft` | no |
| `compose_open_draft_prose` | no |

So the worse bug the ticket caught itself was still reachable by four other routes. Reproduced at the
layer it would be seen — removing a line from a title company's draft whose key cannot be placed
rewrote it from the borrower template:

```
- Hello,                                    + Hello $borrower_first_name,
- Please send the title commitment.         + We are working through your loan file and there are
                                              a few documents we still need from you.
```

That is the exact sentence LP-843 was written to stop a title company reading.

**Fixed at the choke point rather than at the four doors.** `_regenerate` now resolves with
`_known_party_of` and returns without touching the words when the audience is unknown — the position
the heal already took, now held in one place. The membership change still stands, because what was
asked for is a fact the caller has already recorded; only the prose is left alone. The lenient helper
is **deleted**, not left beside the strict one: it had exactly one caller, and an always-answers
variant one keystroke from the strict one is reached for precisely because it always answers. Its
three prose references were updated rather than left pointing at a ghost.

**Scope of the measurement, since it changes how urgent this is.** Not live on data: of the ten
communications on staging, every one carries `party`, so nothing reaches the fallback today
(`select template_key, party is null, status, count(*) from readonly.communications`). The column is
nullable, the suite already contains such a row, and LP-843's own `_legacy_draft_keys` exists for
`party IS NULL` rows — so the gap is structural rather than hypothetical, but it is not a second bug
report.

### A — the safety case re-derived independently

It holds. Three sites assign `Communication.body`, not two: `_regenerate`, `party_requests` (also a
template render), and `send_draft`. Both of the first two are template renders, so the ticket's claim
is right as a count of *kinds* and one short as a count of *sites*. No `PATCH` or `PUT` route touches
a draft, so there is no save-without-sending path — checked across every router, not just this one.

The hinge the ticket does not name is that the send writes the processor's edited body back onto the
row, so "regeneration is lossless" is only true of an unsent draft. It is: the heal returns early on
anything that is not `DRAFT`. That early return is what the safety case actually rests on.

### A — the concurrency question, now tested

Two readers of the same stale draft both regenerate, and that is safe. `test_two_concurrent_reads_of_one_stale_draft_both_heal_it_safely`
opens two independent sessions that meet at an `asyncio.Barrier` before either writes — the barrier
completing *is* the proof both were inside the heal at once, rather than a sleep that would have run
them in sequence and passed while proving nothing. Both return True, the heal sticks, and the body is
rendered once rather than over itself.

What makes the second writer harmless is that nothing on the read path inserts: `_cached_framing` only
reads the prose cache. That is the property worth guarding, and the test does — putting an insert back
on the read path produces `UniqueViolationError: duplicate key value violates unique constraint
"pk_email_draft_prose"` and the test fails.

The test commits, so it cleans up after itself. It did not at first, and a single committed user failed
**thirteen tests in `test_add_user.py`**, a file this change has nothing to do with, and only when the
whole suite ran — `test_refuses_outside_the_allowlist` asserts a global `count(User) == 0`.

### B — the class, enumerated

`_party_of_draft` had one remaining caller and it was inside `_regenerate`, which is the finding above.
So the class had exactly two members and the ticket had fixed one. Deleting the lenient helper makes
a third impossible rather than documented.

### The wiring gap — a check for the class

Asked for, and worth more than the fix: a function can now be caught when production calls it and
nothing else does. `tests/test_unwired_services.py` walks `app/services/` for undecorated module-level
functions whose names are never loaded anywhere in `app/`, `alembic/` or `scripts/`. Tests calling it
does not count — "tests call it, nothing else does" **is** the defect shape.

The census as it stands: **24 functions that tests call and production does not, and 3 with no caller
and no test at all.** Those are recorded as a baseline with a reason each, so the check is a ratchet: a
28th fails the build. Mutated both directions — a new uncalled service function fails it, and putting
a wired function (`send_draft`) into the baseline fails the other assertion, so the list cannot rot
into a fiction. A positive control pins both ends of the scan itself.

Limits stated in the test rather than implied: a name reached by `getattr` or string dispatch reads as
unwired. `register` is in the baseline for that reason — it *is* the wiring mechanism, and §5 says ship
no provider, so only tests call it.

Three entries have no caller and no test, all predating these commits (LP-809, LP-811a, LP-93) and so
left alone rather than deleted, because removing code three tickets outside the blast radius is how a
review becomes a refactor: `_is_borrower_facing`, `open_draft_preview`, `existing_identities`.

### Standing three

Tenancy untouched — the heal derives nothing from a sender, and `remove_need_from_draft`'s cross-file
refusal is intact. The new log line carries a loan-file id and a draft id, no words. No model call was
added to a request path; `_cached_framing` still never composes.

Backend: ruff + `mypy --strict` clean, **7570 passed / 6 skipped / 1 xfailed**. Frontend: biome clean
across 381 files, `tsc` exit 0, **1563 tests in 134 files**, `next build` succeeded.
