# LP-383 — Map LE/CD consumers + extract if needed

## What this ticket is

LP-383 was queued as "extract Loan Estimate / Closing Disclosure (LE/CD)." Following LP-381/382's discipline, an
extraction ticket first **maps which rule its field unblocks**, then extracts **only if a real consumer
resolves** once the field exists. This ticket does the map — and the map's verdict is **premature: no rule in
this engine consumes an LE/CD field today**, so nothing was extracted. A reported "not needed yet, here's what
would need it" is the deliverable (LP-381/382 both shrank on contact with the code; this one shrinks to zero
production change).

## Acceptance criteria

- The map is built: which rules consume LE/CD, does an extractor emit it, does the classifier route it, does
  LF-6T3N carry one.
- The verdict (needed now vs premature) is reported, with the future wave that would need it.
- **No extractor is built for a field no rule reads** (dead code + a future field-name trap).
- `ACTIVE_RULE_IDS` unchanged; the 14 live rules identical; full suite green.

## THE MAP

| Question | Answer |
|----------|--------|
| Which rules consume LE/CD? | **Only AS-3** (cash-to-close), conceptually, via `calc.cash_to_close`'s `closing_costs` breakdown line. |
| Does an LE/CD extractor emit those fields? | **No** — `loan_estimate` / `closing_disclosure` are not in `EXTRACTORS`; no extractor file exists. |
| Does the classifier emit the LE/CD doc-type? | **Yes** — `loan_estimate` + `closing_disclosure` are in `DOCUMENT_TYPE_INDICATORS` (a routing target exists). |
| Is there a declared name to emit against? | **No** — there is no `*.closing_costs` / `le.*` / `cd.*` tag. `closing_costs` appears only as a breakdown *line* inside `calc.cash_to_close`'s description, never as a materialized tag. |
| Does AS-3's recipe read `closing_costs`? | **No** — `_cash_to_close_shortfall` is a **stub that always abstains**; there is NO cash-to-close calculator (§3B). `CALCULATORS = (mortgage_insurance, self_employed, reserves, max_loan)` — no `cash_to_close`. |
| Do the TRID compliance rules consume LE/CD? | **No** — DC-1..DC-7 (LE timing, ITP, CD 3-day timing, fee tolerance, APR change, appraisal delivery, changed-circumstance) are all `out_of_scope` (LOS-owned). |
| Does LF-6T3N carry an LE/CD document? | **No** — even a built extractor could not be verified against it. |

## The verdict — PREMATURE

**Extracting LE/CD now would emit a `closing_costs` field that nothing reads.** AS-3 — the only conceptual
consumer — is inert, and its `calc.cash_to_close` recipe is a stub that abstains regardless of extraction
because the **cash-to-close calculator (§3B) does not exist**. `closing_costs` is only *one* input to that
missing calculator (need = down_payment + closing_costs + required_reserves − credits, vs available_funds). So
extraction alone cannot move AS-3 from `couldnt_check` to a real verdict. Building the extractor now would be
dead code plus a future field-name trap (the LP-333/369 silent-death class the ticket warns against), and there
is no declared consumer field name to even emit against.

The natural LE/CD consumers — the TRID compliance rules (DC-1..DC-7) — are all `out_of_scope` by design
(LOS-owned TRID timing/tolerance), so the compliance path is not a consumer in this engine either.

## What would need it (the future wave)

LE/CD extraction is a **sub-task of the cash-to-close calculator wave (§3B / LP-323-AS-B)**, not a standalone
extraction ticket. That wave must, together:
1. Build the cash-to-close calculator/recipe (need vs available), with a declared `closing_costs` input tag —
   the **name** an extractor then emits against (closing the LP-333/369 trap up front).
2. Add the LE/CD extractor for `closing_costs` (and whichever other cash-to-close inputs the LE/CD supplies),
   emitting the calculator's exact declared names.
3. Verify against a fixture that carries an LE/CD (LF-6T3N does not) — so the consumer actually resolves, the
   LP-381/382 "extract only when a consumer resolves" discipline.

Separately, if the TRID compliance rules (DC-1..DC-7) are ever moved from `out_of_scope` (LOS) into this
engine, they would become LE/CD consumers — but that is a scope decision, not an extraction one.

## What was built

**No production change** — no extractor, no recipe, no tag, no activation. A guard test
(`tests/verification/tag_materialization/test_le_cd_premature_lp383.py`) pins the map so the finding cannot
silently rot: it asserts the classifier catalogs LE/CD but no extractor is registered; AS-3 is inert and its
recipe only abstains (with no `cash_to_close` calculator); no declared tag is sourced from an LE/CD field; and
the DC-1..DC-7 TRID rules are out of scope. **The moment a real consumer (or an extractor) is added, a
canary here fails — forcing the extractor↔consumer chain to be completed together.**

## Assumptions, decisions & gaps

- **No ADR forced** — this is a planning finding (premature, deferred to the §3B cash-to-close calculator
  wave), not an architectural decision. Recorded here and in the guard test.
- **The classifier already routes LE/CD** — so no classifier work is needed when the extractor is eventually
  built; the routing target exists.
- **A reported gap:** AS-3 is blocked on more than extraction — it needs the §3B cash-to-close calculator AND
  its inputs (down_payment, closing_costs, required_reserves, credits, available_funds), of which `closing_costs`
  (LE/CD) is one. This ticket does not build any of that.
- **Nothing activated** — `ACTIVE_RULE_IDS` unchanged (14).
