# LP-632 — the liability the credit report already documents

- **Ticket:** LP-632
- **Status:** Built + review-fixed — CI green, not yet deployed
- **Date:** 2026-08-26
- **Scope:** Backend (the first LP-631 coverage predicate) + tests
- **Depends on:** LP-631 (the flag mechanism)

## The rule this encodes

Fannie Mae **B3-6-01**, verbatim:

> "For each liability, the lender must determine the unpaid balance, the terms of repayment, and the
> borrower's payment history, and verify any other liability **that is not shown on a credit report**
> by obtaining documentation from the borrower or creditor."

So a need asking the borrower to document a liability's payment has a checkable precondition: it
applies only where the liability is **absent** from the credit report. That is not AI reasoning. It
is a join between two tables the system already populates.

Worth stating because the AI got it wrong on LF-AWBB in a second way: the need's reasoning asks to
verify the lease's *"remaining term"*. **B3-6-05** says the term does not matter —

> "Lease payments must be considered as recurring monthly debt obligations regardless of the number
> of months remaining on the lease."

That is the installment-debt rationale (the ten-payment rule) misapplied to a lease. The DTI
treatment is unconditional, so the term is not a reason to chase a document.

## The predicate

`stated_liabilities` × the completed credit report's extracted `tradelines`
(`ai/extraction/credit_report.py` already carries `creditor_name`, `account_type`,
`monthly_payment` per row).

Need types in scope, by the liability type each documents:

| needs_type | liability_type |
|---|---|
| `lease_agreement` | `LeasePayment` |
| `installment_statement` | `Installment` |
| `credit_card_statement` | `Revolving` |

**Every liability of the mapped type must match, not any.** A need reading *"most recent statements
for all four revolving credit accounts"* is answered only when all four are on the credit report.
This is LP-108's discipline arriving from the coverage side: under-claiming costs a click,
over-claiming is the dangerous direction. Zero liabilities of the type → no flag, because there is
no basis for one.

**Matching is creditor name plus monthly payment.** Names are normalised (upper, alphanumerics only)
and compared by prefix in either direction; payments are compared rounded to whole dollars, so a
stated `438.00` matches a reported `438`.

Prefix matching covers **truncation** (`BANK OF AMER` for `BANK OF AMERICA`) and nothing else. It does
not cover **abbreviation**, which is what LF-AWBB's report actually does: `UNITED WHSLE MORT` and
`DIGITAL FED CREDIT UNI` are not prefixes of their expansions and will not match. Accepted rather than
solved — a non-match leaves the need standing, which is the safe direction, and fuzzy creditor
matching is a far larger problem than this predicate should own. On the file that prompted the work it
costs nothing: both sides come from the same import, the four names agree exactly, and prefix matching
is only the margin.

Name alone is not enough and the same file proves it: it carries two `CAPITAL ONE` rows and two
`SYNCB/TJXDC` rows. Requiring the payment to agree as well is what makes the pair identifying. Where
the payment is absent or zero on the tradeline, there is no match — a $0 tradeline is not evidence of
a $438 obligation.

## What it would do to staging today

All six open needs this predicate can reach, and the outcome for each:

| file | need | credit report on file | flagged? |
|---|---|---|---|
| LF-AWBB | `lease_agreement` | yes — `ALLY FINANCIAL / AUTO / 438` | **yes** |
| LF-AWBB | `credit_card_statement` | yes | yes, if all revolving rows match |
| LF-BVFU | `lease_agreement` | no | no |
| LF-BVFU | `credit_card_statement` | no | no |
| LF-4A5V | `installment_statement` | no | no |
| LF-ABRS | `credit_card_statement` | no | no |

Four of the six are **correct needs** — those files have no credit report, so B3-6-01 says the
liabilities genuinely must be verified from the borrower or creditor. The predicate keeps all four.
That asymmetry is the point: this is not a suppressor, it is the guideline's own condition evaluated.

## Assumptions

- The credit report reports an auto lease as `AUTO`, not distinguishing lease from loan. The match
  therefore establishes "this obligation appears on the credit report at the stated payment", which
  is exactly what B3-6-01 asks — not that the *lease terms* are documented. B3-6-05 removes the need
  for the terms, so nothing is lost.
- Prefix matching in either direction is a heuristic. It is safe only because the outcome is a flag a
  human disposes of; it would not be safe attached to an auto-close.
- Scoped to needs whose `needs_type` is one of the three. A need with `needs_type=null` that cites a
  liability is out of reach here by construction — that is LP-633's territory.


## Review fixes

Seven findings, all verified against the code and all real. Five were in this predicate; each now has
a regression test named after the failure.

**The length floor rejected exact matches.** `_names_match` returned False whenever *either* name was
shorter than six characters — so `ALLY`, `AMEX`, `CHASE`, `USAA` never matched themselves, even with
an identical payment, which is the strongest evidence this predicate can have. Worse, one non-match
breaks the all-must-match loop, so a single short-named liability suppressed the flag for the whole
need. The floor now guards the prefix branch only; equality short-circuits it.

**A tradeline could answer two liabilities.** `next(...)` re-scanned the full reported list per stated
liability, so two stated CAPITAL ONE cards at $25/mo both matched the single $25 row the report
carries: the loop completed, the need read fully covered, and the second card was documented by
nothing. That is exactly the false-green "every liability must match, not any" exists to prevent,
arriving through the back door. Each match is now consumed out of a working copy.

**A failing predicate poisoned the session.** The bare `except` is best-effort only for non-DB errors;
a SQLAlchemy error poisons the session, so the warning was logged and the CALLER's `commit` two lines
later would raise `PendingRollbackError` — discarding the LP-68 document match and the LP-69 needs
written earlier in the same session. An optimisation would have destroyed the work it runs after.
`verification_run` documents this exact failure twice and contains it with `begin_nested()`; so does
this now. The initial load is deliberately left undefended, and the docstring now says so instead of
claiming "never raises".

**The map named a type the canonicaliser never stores.** `installment_loan_statement` is the CATALOG
type, so it is what `canonical_need_type` writes; the map had only `installment_statement`, which is
uncatalogued and therefore reaches just the rows whose type failed canonicalisation and was stored
raw. Both are now mapped — the uncatalogued spellings kept because those are the rows staging actually
has, not because the names are good. `student_loan_statement` is deliberately still absent: that
statement is chased for IBR/deferment terms a credit report routinely misreports, so "it is on the
report" does not answer that ask.

**A `{"value": ...}`-wrapped row would have disabled the predicate silently.** Rows ship bare, but the
snapshot's own reader unwraps defensively because "a hand-written extractor could store either" — and
it is right to: a wrapped row handed `_normalize_creditor` a dict, raised `AttributeError`, and was
swallowed by the blanket catch into a predicate that quietly did nothing for that file.
