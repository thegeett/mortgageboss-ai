# LP-974 — The plan screen, laid out as the agreed mockup

- **Ticket:** LP-974 (the owner, 2026-10-08).
- **Source:** the owner: "current design and mock design is different", then "go". The mockup is the
  "Plan screen explained" artifact, board "The plan as a path" (`Path.dc.html`).
- **Status:** built (frontend only).

## Why

LP-966 to LP-968 added the path, drafts and edits onto LP-966's layout, one card per task with its
select, ⓘ and meaning line. The owner had approved a different layout. The LP-967 ticket did say "each
task keeps its Next step select", but nobody told the owner that this meant the screen would not look
like the mockup. This ticket fixes every difference that is a layout choice. The differences that are
features still to come stay out of it.

## What changed

| Area | Before | Now (as the mockup) |
|---|---|---|
| Heading | "Check the plan, then confirm it" and three numbered how-to cards | "Here's how we'll get these N conditions cleared", plus one sentence; the cards are gone |
| Collapsed condition | One line per task, with an action chip, "Waits on…" and "Found:…" | **Route:** what the steps say. **Next:** the first step still ahead |
| Open button | "What you need to do" / "Hide details" | "See the plan" / "Hide the plan" |
| Opened, left | What the lender wants, when, why we suggest this, the lender's words, then Good to know on the right | What the lender wants, when, **How it gets done**, the lender's words, Good to know |
| Opened, right | A card per task (select, ⓘ, meaning, a small-dot path), then a dashed "Then" block | **One numbered timeline** for the condition: its own step, each task's steps, then the ending, with 26px numbered dots coloured by who acts |
| Edits | Under each task card | On each task's first step in the timeline. Each task's name is a badge there when the condition has more than one |
| Third box | "Already in the file" | "Already handled": it counts `willBeReady`, which includes tasks she marked done |
| "I'll do this myself" | as written | "I'll do this step myself" (the mockup's words) |

**"How it gets done"** holds each task's Next step select, its ⓘ and its meaning, plus the condition's
own step and "Why we suggest this". Until LP-970 brings routes, this is the only way to change how a
task gets done, and it is where the routes will go. **"Route:"** comes from the same `actionFor` phrase as
before, so it cannot disagree with the selects.

## Not the mockup yet, on purpose

- Route choices with Suggested and a reason: **LP-970**.
- "Add a step" and "I'll handle it my own way": **LP-969**.
- "Describe what you want to do": **LP-971**.
- **"Remove step"**: LP-968 chose not to build it. Delete is permanent, and Not needed covers the same need
  with a reason.
- **"Changed by you"** beside "Go back to the suggested plan": nothing on the condition says whether she
  changed it (that is only in the event history), so the link shows on its own, as before.
- **"Watch the file's inbox … and tell you when each condition is ready"** in the confirm list: left out.
  Accepting an attachment is hers (`accept_attachment` has one caller, the route), and no notification
  fires when a condition becomes ready. The sentence would not be true.

## Found on the way

**A condition whose only task she dropped was called unread.** `unworked` counted live tasks, so marking
the only task Not needed turned the row into "We couldn't work out what this one needs". The old card
layout showed that message alongside the crossed-out card; the new timeline would have hidden the card.

Fixes:
- `unworked` now counts every task.
- The timeline shows the crossed-out task with its reason and Undo.
- There is no ending: `ready_because` needs a live task.
- The collapsed row says "Nothing left: you marked every task not needed".

## Review (of `9b6f78a3`)

**Two findings, both fixed here, and one of them is mine: a sentence I wrote in the LP-966 review
describes a layout, and LP-974 reuses it in a layout where the description is false. The other is the
accessibility point this ticket raised about its own selects, which was worth raising — it is real. The
rebuild itself holds up: every new claim traces to the server, and the places this ticket could most
easily have disagreed with itself do not, because it reads through the same helpers rather than
restating them.**

### Finding 1 — "the tasks below" is in a row with nothing below it

`routeOf` builds the collapsed row's "Route:" through `actionFor`, which is right — the same phrase the
selects produce, so the two cannot disagree. But for a condition-level ask `actionFor` returns
**"Ask the borrower — the tasks below are what go in the email"**, and in the collapsed row there is no
"below": the tasks appear only once she opens "See the plan".

That phrase is mine. The LP-966 review found that the whole condition's ask named an email the server
fills from items, and I replaced the claim with one that pointed at the tasks — correct for LP-967's
expanded card, which was the only place it rendered. LP-974 then reused `actionFor` in a second layout,
which is exactly the right instinct and is what exposed the wording.

**Fixed:** "Ask the borrower — **its tasks** are what go in the email" (and the same for someone else).
It says the same true thing about where the content comes from without describing where anything sits,
so it travels between the two layouts. The comment above it now records that a phrase reused in two
layouts cannot describe one. `ownStepPath`'s own detail still says "The tasks below set to ask are what
go in the email", and that one is **correct** — it renders only inside the timeline, above the task
steps, which I checked rather than assumed.

### Finding 2 — every "Next step" select had the same accessible name

Each `HowRow` renders the task name in a `<span>`, then a `<label htmlFor>` reading "Next step", then
the select. The visible pairing is obvious; the accessible one is not. A screen reader announces three
or four identical "Next step" combo boxes, and nothing connects any of them to the task name beside it,
so she cannot tell which task she is about to change — on the screen whose whole purpose is knowing
what each task will do.

**Fixed** with `aria-labelledby` over the name and the label, making each select's name
"Credit report invoice Next step". It **adds** a name rather than replacing one: the visible label and
its `htmlFor` are untouched, so the existing `getAllByLabelText("Next step")` queries still work, which
is also why nothing failed when I made the change and why the test I added asserts the accessible name
directly. Removing the attribute fails that test alone.

### Checked and not findings

- **Every new sentence traces to the server.** The heading's "prepared the emails we could" is carefully
  hedged and true: LP-968 drafts when the plan is ready, except a condition whose reading still needs her
  (`_needs_her`) and except a plan built before LP-968 — "we could" is exactly the claim that survives
  both. "Already handled" is keyed on `willBeReady`, which has been the one shared rule since the LP-967
  review moved it into `plan-path.ts`, so this box and the confirm summary cannot disagree about a
  condition — the defect LP-967 had, now impossible rather than fixed twice.
- **`nextOf` is right about what is "ahead".** It skips a dropped task and the `FINISHED` step, so the
  collapsed "Next:" never offers her something already done; and for `item: null` entries (the own step,
  the ending) `entry.item?.status` is `undefined`, which passes the filter, so a condition whose own step
  leads still shows that step. One fragility worth naming rather than changing: the skip is
  `entry.step !== FINISHED`, an object-identity test against the module constant. It holds because
  `taskPath` returns that very object as a task's whole path, and a second construction site would break
  it silently — the constant is the coupling, so it should stay the only way a finished task is spelled.
- **`conditionPath`'s ending rule matches the server.** It drops the ending when there is no own step and
  no live task, and `ready_because` does return None for exactly that case (`if not live: return None`),
  so "when every task is done, the condition is ready" would otherwise promise what the server refuses.
- **Counting dropped tasks in `unworked` is the right choice, not an oversight.** `unworked` is
  `condition.items.length === 0 && ownStep === null`, so a condition whose only task she marked not
  needed is NOT "unworked" — which is correct: we did work out what it needed, and she dropped it.
  Counting only live items would have put "We couldn't work out what this one needs" on a condition she
  had just finished deciding about. `routeOf` covers the same case from the other side with
  "Nothing left: you marked every task not needed".
- **The edits land where they belong on every trimmed path**, which was this ticket's question 3 and the
  one I could answer from having written the trim. `leads: index === 0` attaches `TaskEdits` to a task's
  first rendered step, and after LP-967's status trim that is: the "they send it back" step for a
  `requested` task, the check for a `received` one, the `FINISHED` row for a `done` one (where Undo is
  exactly what belongs), the "Not needed" row for a dropped one, and the waits-on prefix when a task
  waits on another condition. The last is the only arguable one — the controls sit on "Starts once 1228
  is done" rather than on the work — and it is defensible, because the prefix IS that task's first row
  and the trim preserves it deliberately. No case puts a task's controls on another task's step.
- **Nothing in this ticket's copy was falsified by the LP-968 review.** I checked specifically, because
  that review stopped the borrower's upload link being minted before confirm: no new sentence here
  mentions an upload link, so there is nothing to fall out of step.
