## The two things that are different here, and why

### The model does not write the document instructions

The plan asks that the model quote LP-800's `GUIDANCE` and never invent an instruction, **"enforced
the way `unsupported_numbers_in` enforces numbers"**.

That enforcement works because a number is a **token**: it is either in the source text or it is
not, and no judgement is involved. A reworded instruction is not a token. Deciding whether "send us
all the pages" is a faithful rewording of "every page of each statement, including pages that say
this page intentionally left blank" is exactly the judgement a deterministic guard cannot make — and
a guard that has to make one has the same failure mode as the thing it is checking.

So the rule is made **structural** instead. The model writes three things — an opening, a bridge and
a closing — and the document list is interpolated deterministically from the catalog by
`render_document_block`. That removes the legitimate case for an instruction in the model's output,
which leaves any obligation sentence there always being an invented one. `states_a_requirement` then
refuses it, and **that** is decidable.

This is a departure from the letter of the plan and is flagged for the reviewer below. It is
stricter than what was asked for, not looser: the model cannot get an instruction wrong because it
never writes one.

### The compliance scanner is regulatory, not stylistic

`finding_prose`'s guards keep a processor from reading something silly. These keep a lender from
making a statement it is not allowed to make. Seven deterministic checks, in the order
`rejection_reason` applies them:

| Check | What it refuses | Source |
|---|---|---|
| `rate` | any percentage, "APR", "annual percentage rate", "interest rate" | [12 CFR §1026.24](https://www.consumerfinance.gov/rules-policy/regulations/1026/24/) |
| `money_amount` | any currency amount | §1026.24(d)(1)(i), (iii), (iv) |
| `triggering_term` | downpayment, monthly payment, number of payments, period of repayment, finance charge, closing costs | §1026.24(d)(1) |
| `commitment` | approved / denied / committed / guaranteed / cleared to close | — |
| `settlement_service` | a recommendation **and** a settlement service, together | RESPA |
| `payment_routing` | nine consecutive digits, routing/account number, wire instructions | — |
| `invented_instruction` | an obligation sentence anywhere in the model's output | see above |

then the two shared guards — `leaked_identifiers_in` and `unsupported_numbers_in`, **imported** from
`finding_prose` rather than re-derived, because bug-006 was a second copy of that union drifting from
the first.

**§1026.24 read 2026-09-07**, heading and paragraph numbers verified on the page itself rather than
from a search caption — the failure that produced a stale Selling Guide citation in LP-800's sourcing
pass one commit earlier.

**The scanner refuses the term rather than the argument.** Whether a document request to an existing
applicant is an "advertisement" under Reg Z is a real question with a defensible answer either way.
It is not a question this code should be deciding on the fly, per draft, so a triggering term is
refused outright. Nothing in a document request needs one.

## Decisions

### Template v2, not an edit — ADR-401's first real exercise

The initial-request template needed three framing slots. That is a change to the words, so it is a
**new version**: `initial_documentation_request.v2.txt`, with v1's fingerprint still pinned and v1's
file still on disk. An audit row naming v1 still resolves to the words it named.

This is the case the hash pin exists for. An in-place edit here would have left every v1 audit row
describing an email that no longer exists in that form, and nothing else in the system could have
detected it.

### The plain framing is a file, not string constants

`framing.plain.v1.txt` carries v1's three sentences unchanged, and is fingerprinted like a template.
With the flag off a reader sees exactly what v1 sent, and a test asserts each sentence appears in
v1's own file rather than in a copy — so the claim cannot drift into agreeing with itself.

### The borrower's name is not in the fact bundle

`DraftFacts.borrower_first_name` is the literal string `"the borrower"`. The greeting is the
template's, and the model does not write it. Keeping the real name out means the cache key does not
vary per borrower for an otherwise identical request — so the cache actually hits — and the model has
no use for a name it is not writing.

### The cache is re-checked on the way out

`compose` runs only on a cache **miss**, so a composition stored before a guard existed would be
served forever and the guard would never see it. LP-601 cost a shipped defect to learn that. The
cached body is parsed back into a composition and run through the same `rejection_reason`; a row
today's guards refuse falls back to the plain framing rather than being served.

## Tests

`tests/ai/test_email_draft_lp810.py` (27) — the guards, each refusal paired with an acceptance of
ordinary prose sharing its vocabulary. `tests/services/test_email_draft_ai_lp810.py` (5) — the
wiring, at the layer a draft is actually built.

`test_ordinary_framing_passes` is the control the whole file rests on: a `rejection_reason` that
refused everything would satisfy every other test here, and the symptom would be a draft that always
falls back to the plain template — **indistinguishable from the flag being off**.

The flag-off test replaces `compose` with a function that fails if called. Asserting only on the
output would pass while the model was called and its result discarded, which is the expensive version
of the same bug. The cache test **counts** calls rather than inferring from the output, because
"cached" and "composed the same thing twice" produce identical text and only one of them is the
claim.

Verified by mutation, each confirmed applied before the run was believed:

| Mutation | Result |
|---|---|
| the `rate` guard disabled | 3 fail |
| the `commitment` guard disabled | 4 fail |
| the `invented_instruction` guard disabled | 4 fail |
| settlement-service guard widened from `and` to `or` | 1 fails |
| `unlicensed` dropped from the numbers check | 1 fails |
| the flag check removed | 1 fails |
| the cache re-check removed | 1 fails |
| the cache lookup removed | 2 fail |
| one word changed in the plain framing file | 2 fail |

One mutation in the first batch was a **no-op I chose badly** — adding a trailing comment to a
constant, which cannot change behaviour. It "survived", and would have read as a surviving mutant to
anyone scanning the output. Replaced with one that edits the framing file's content.

## Assumptions

- **A rejected composition is not cached.** Only compositions that pass `rejection_reason` are
  stored, so the cache never has to be cleaned of them. The re-check on the way out exists for guards
  added *later*, not for rows stored bad.
- **Three paragraphs round-trip through the cache.** A cached body is split on blank lines back into
  opening/bridge/closing. A row that does not split into exactly three is treated as unusable and the
  plain framing is used — the same fallback as a rejection, and safer than guessing.
- **`account number` is refused even in an otherwise innocent sentence.** The model does not write
  instructions, so there is no legitimate use for the phrase in its output. It would be over-wide in
  a component that let the model describe documents; here it is not.

## Deliberately not done

- **No API, no frontend, no send.** LP-811 owns the send and the copy-to-clipboard; there is still no
  way for a processor to see a draft. Stated so nobody assumes otherwise.
- **The flag stays off.** Nothing turns it on, and turning it on is a decision about borrower-facing
  AI text that belongs to a person.
- **No prompt-version column.** `phase4.md` §6 wants "model + prompt version" in the audit record.
  The prompt is a file with no version discipline of its own yet, and inventing one here without the
  send path to store it against would be machinery with no reader. **Flagged as an escalation**, not
  quietly dropped.
- **No tone profile wired in.** LP-822 built the mechanism and nothing populates it; joining an empty
  style profile to the drafting prompt would add a variable that is `is_default` for every user.
  LP-811 or a later ticket, once a profile can actually be entered.

## For the reviewer

The three standing reviewer checks:

- **Tenancy** — no `company_id` anywhere. The cache has no foreign key at all; the service takes an
  already-resolved `LoanFile`.
- **Message content in logs** — actively load-bearing here, and checked. `compose` logs
  `email_draft_rejected` with the **reason only**, never the text. The composed body reaches
  `Communication.body` and the prose cache and nowhere else, and the readonly view drops it.
- **AI in the decision path** — the model writes three sentences of framing. It does not choose what
  is requested, does not decide whether a need is satisfied, and does not write the instructions. The
  document list is deterministic.

The judgement calls worth a second opinion, in the order I would attack them:

1. **The structural reading of "never invents an instruction."** The plan asked for a check like
   `unsupported_numbers_in`; I removed the legitimate case instead. Stricter, but it is my reading of
   the requirement rather than the requirement, and it constrains what LP-811's compose flow can ask
   the model to do.
2. **Refusing every money amount and every triggering term outright**, rather than deciding whether
   Reg Z's advertising rules bind a request to an existing applicant. I think refusing is right and
   cheap. If you think the scanner should be narrower, the place to argue it is `_MONEY`, which is the
   broadest pattern here.
3. **`is_follow_up` on `DraftFacts` has no writer.** It is in the bundle because the reminder template
   will need it and the key should not change shape then — which is the "field with no reader"
   pattern I have declined twice. I think the cache-key stability argument is real; hold me to it if
   you disagree.
