## Two gaps that look unrelated and are the same one

`Lender.contact_email` has existed since LP-13, its docstring says it is *"for direct underwriter
communication"* — and **there was no create or update path for a lender anywhere in the product.**
Every lender in every environment came from the seed script.

So LP-805 seeds participants from three sources, and one of them was always NULL on a real
installation. The lender side of the allowlist could not be populated, which means an underwriter's
reply could never route to the file it was about.

And one address per lender is the wrong shape regardless. UWM has many underwriters, a file is with
one of them, and the one on this file is not the one on the next. `lender_contacts` holds the
people; `loan_files.underwriter_contact_id` says which of them this file is with.

That is why this ticket moved ahead of LP-815 in the plan: **without it the assignment is
decoration.** An underwriter who is not on the participant list is a stranger to the routing ladder
and to §2.3's trust decision, so assigning one would change what a screen said and nothing else.

---

## The one place two ownership chains meet

A loan file is owned by a company. A contact is owned by a lender, which is owned by a company.
`underwriter_contact_id` is **the only column in the schema where a loan file points at a row
reached through a different ownership chain** — so it is the only place those two companies can
disagree, and nothing but `assign_underwriter` proves they do not.

Three things must hold, and each fails differently:

- **The contact belongs to this company.** Otherwise a loan file points at another tenant's row and
  every later read of "who is the underwriter" answers with their data. The refusal is the *same
  message* as for an id that never existed — telling them apart confirms the id exists.
- **The file has a lender.** "The underwriter for this file" means nothing before anyone has decided
  where it is going.
- **The contact is at THAT lender.** Same-company is not enough. *"Submitted to Sun-West,
  underwriter at UWM"* reads as complete and is wrong in the one field a processor acts on — they
  would email a stranger about somebody else's loan.

Clearing needs none of them: removing something is not an assertion about what it was.

### And the invariant is not self-enforcing

`assign_underwriter` proves the contact is at the file's lender **at the moment of assignment**. A
later `PATCH` of `lender_id` — an ordinary edit, through `update_loan_file`, which setattrs whatever
it is given — silently makes that false, and nothing on the screen would say so.

`update_loan_file` now clears the assignment when the lender moves. Clearing rather than refusing:
changing where a file is submitted is a decision a processor is entitled to make, and the
underwriter is a consequence of it, not a constraint on it.

The test for that has a **control beside it** — an unrelated `PATCH` must leave the underwriter
alone. Without the control, a guard that cleared on every edit would be green.

## No `company_id` on `lender_contacts`

Reached only through its lender, which is company-owned, so scoping is transitive — the shape
ADR-052 gives file-owned children. Storing the company here as well would make a contact whose
`company_id` disagreed with its lender's a **representable state that nothing would notice**, which
is a worse failure than the join it saves.

The same underwriter really does work with several processing companies; each configures its own
`Lender` row for UWM (ADR-045), so each gets its own contact row, and one company editing a phone
number cannot change what another sees.

---

## Reads open, writes admin, on one prefix

The gate is declared **per route**, not on the router. On the router it would have taken the
existing processor-facing `GET /lenders` with it and 403'd the intake form's lender dropdown for
every processor.

A per-route gate is easy to forget on the next route added, so every write has a test that a
processor is refused — and the fixture builds **both** an admin and a processor, because one that
only has an admin cannot tell a working gate from an absent one.

**Assigning is deliberately not gated.** Configuring which lenders exist is administration; deciding
who is handling this file is the processor's own work, and gating it would make every reassignment
wait on somebody else.

---

## Duplicates, because two rows for one person breaks routing

The unique index is `(lender_id, lower(email))`, partial on `email IS NOT NULL AND deleted_at IS
NULL`. Two rows for one underwriter means a file assigned to one of them and mail arriving from the
other — the participant lookup misses and the reply goes to triage.

Case-insensitive, matching `normalise_address`, so "is this the same person" has one answer across
the codebase. Partial, because a phone-only contact is a legitimate row and several of them must not
collide; and excluding soft-deleted rows so an address can be reused after somebody leaves.

The service checks first so the caller gets a sentence rather than an `IntegrityError`; the index is
what makes it true under a race. Both are tested.

## What the screen says

Three states, and merging any two says something false:

| | |
|---|---|
| **no lender** | there is nothing to choose from — *not* "this lender has no underwriters" |
| **not assigned** | an ordinary state |
| **assigned but departed** | the file names someone the lender's active list no longer contains |

The third is the one that would be got wrong. A picker that resolves the name from the contacts list
and falls back to "Not assigned" on a miss tells a processor the field is empty when it is not. The
component notices that the **id is set and the name is missing**, which are different facts.

The picker is separate from the loan editor, and not because it was easier: it saves through its own
endpoint with its own refusals, and folded into the editor's save a refused assignment would fail
the whole edit and tell the processor their *loan amount* could not be saved.

The response carries the contact **id**, not the name. Resolving the name server-side would mean a
second eager load on every detail read, and an async session cannot lazy-load on attribute access —
so the first file whose relationship was not loaded would raise rather than return a null.

The readonly view drops `name`, `email`, `phone` and `notes` — a contact is a person, and `notes` is
free prose an admin typed *about* them, which is where a name arrives in a shape no scrubber
predicts. `loan_files.underwriter_contact_id` is excluded and the view exposes
`has_named_underwriter` instead: which **lender** a file is with stays visible, which **person**
does not.

The migration hit LP-806's trap in a new form and the guard named it: hoisting the rollback's
`CREATE VIEW` to a module constant makes the drift scanner read *that* as the live definition. The
rollback body is inline, and it is copied from LP-806's **upgrade**, not its downgrade.

## Deliberately not done

- **No lender delete.** Soft-deleting a lender with live files raises questions this ticket has no
  answer to — the FK is `RESTRICT`, files reference it, and "what happens to the files" is a
  product decision, not a service one. Deactivating (`is_active: false`) is available. **Escalated.**
- **No contact edit UI**, though the endpoint exists. Add and remove cover the workflow; an edit form
  is the third state of a form component and was not worth it against the rest of this ticket.
- **The underwriter is not yet a request target.** LP-820 is the ticket where needs sorted to the
  underwriter get their own draft and their own clock; today they are on the participant list, which
  is what makes their **inbound** mail work.

## For the reviewer

- **Tenancy** — this is the most tenancy-sensitive ticket since LP-805, for a different reason: not
  an inversion, but the only cross-chain pointer. `assign_underwriter` is the one gate and it is in
  the service. No new code derives a company from anything; every route takes it from `current_user`.
- **Message content in logs** — the assignment logs a loan-file id and a role. Never the name, the
  address or the phone number.
- **AI in the decision path** — none. Nothing here suggests, ranks or pre-fills.

Worth a second measurement:

1. **The clear-on-lender-change.** It is a side effect inside `update_loan_file`, which every caller
   of that function now inherits. That is deliberate, and it does mean a general-purpose update
   function has a special case in it.
2. **The per-route admin gate.** Correct today, and one forgotten `_ADMIN` on a future route is an
   ungated write. Each existing write has a refusal test; there is nothing that would catch a *new*
   route added without one.
3. **`notes` is 512 characters of admin-typed prose about a named person.** Excluded from the view
   for that reason. It is returned by the API to the company's own users, which I think is right,
   and it is the field most likely to end up holding something it should not.
