# LP-369 — The parsed declaration field-name audit + a guard that closes the class

## WHAT THIS IS

Two LIVE rules were silently dead because their parsed tag declarations named fields that don't exist.
LP-368's diagnosis found the first (`id.dob` → ID-3); this ticket's full sweep found a second (`id.ssn_hash`
→ ID-2) and corrected a mistaken third (`id.marital_status` → ID-7 does NOT read it). **The fixes are
declaration edits; the GUARD is the durable deliverable** — the parsed analogue of LP-333's classifier
mismatch catch, closing a bug class that has now surfaced FOUR times.

**The class:** *a declaration names something that doesn't exist → the thing is ABSENT → the rule
couldnt_checks on every file → silently, forever, with every test green.* Prior instances: AS-1's calc
dependency (LP-366), IN-8/IN-9's classifier document types (LP-333), the orphaned `housing.insurance_monthly`
/ `dti.qualifying_income_monthly` (LP-366-A/367). **The root:** the loader validates declarations that EXIST;
it does not validate that what they POINT AT exists. Absent is indistinguishable from "the document genuinely
doesn't have this" — so it is silent.

## ACCEPTANCE CRITERIA (met)

- Every `mode: parsed` declaration swept; a verdict (RESOLVES / MISMATCH / exempt) for each — no blanks.
- The confirmed mismatches fixed as declaration edits (no engine Python).
- A GUARD that FAILS when a parsed declaration names a field no producer emits, proven to fire on the pre-fix
  shape by a self-test.
- The real before/after for ID-3 (and the newly-found ID-2) on DB LF-6T3N, reported not predicted.
- `ruff` + `mypy` clean; full suite **2338 passed**.

## THE FIXES + THE SUBJECT REASONING

- **`id.dob` → `date_of_birth` (subject stays `document`).** ID-3 is a CONSISTENCY rule
  (`gather_tag: id.dob`, `source_scope: borrower_documents`) that gathers a document-keyed DOB across the
  borrower's sources and compares. A borrower-keyed tag would give ONE value → nothing to compare → a lateral
  move. Only the field name was wrong.
- **`id.ssn_hash` → `employee_ssn:hash` (subject stays `document`).** Same shape — ID-2 gathers document-keyed
  SSN hashes per borrower. `employee_ssn` is the W2's real SSN field (routed to a `PiiField` with a
  match_hash). **Scope note:** this compares SSN across the W2 sources a borrower has; the broader cross-source
  check (1003 / credit) is a domain-scoped extension for the live-rule audit — recorded, not silently claimed.
- **`id.marital_status` → `{subject: borrower, data: marital_status}`.** Wrong on BOTH axes: no document has a
  `marital_status` field, and it lives on the borrower in MISMO (`borrower.{n}.marital_status`). **But ID-7
  reads only `id.title_vesting_consistent`** (the marital/vesting judgment is baked into that AI tag), so
  fixing this is correct hygiene that does NOT resurrect ID-7. The tag now materializes; no live rule reads it.
- **`id.id_expiration` → `expiration_date`; `income.employment_start/end` → `start_date`/`end_date`.** Clean
  renames to real fields (DL / VOE). ID-5, IN-4, IN-7 are dormant; `income.*` are UNVERIFIABLE on LF-6T3N (no
  VOE document), but the declarations now point at real fields, so the guard passes and they are no longer
  permanently broken.

**Not changed:** no rule spec, no vocabulary meaning, no allowed values. The declarations were wrong; the tags
were not.

## THE GUARD — what it covers, what it does NOT, and why

`tests/verification/tag_materialization/test_parsed_declaration_fields.py`: every `mode: parsed` declaration's
field must be a real member of its subject's resolution universe.
- **Covers:** `subject: document` (against the extraction models' field union + the `asserted_name` alias) and
  `subject: transaction` (against `_TXN_FIELDS`) — a static, complete universe. All four parsed mismatches
  lived here. The `:hash` suffix is split before the check.
- **Does NOT cover:** `subject: borrower`/`loan` — MISMO keys are DATA-DEPENDENT (not enumerable from the
  models); the guard SKIPS them and this is documented. Nor the other three seams of the class (calc inputs,
  classifier types, tag producers) — each needs its own analogous guard.
- **Fires on the pre-fix state** (proven by construction): a synthetic `id.dob {document, data: "dob"}` →
  flagged; `data: "date_of_birth"` → passes. A guard that cannot fail is not a guard.
- **Two loud exemptions** (`income.stated_monthly`, `stmt.page_count_declared`): documented with a reason,
  feed dormant rules, and a test asserts each is STILL a genuine mismatch so the allow-list can't rot into
  hiding a fixable declaration.
- **Why a test, not a load-time check:** a load-time validation would force the deterministic tag-vocabulary
  loader to import `app.ai.extraction.*` — a layering inversion. The test fails CI just as loudly.

## THE REAL BEFORE / AFTER (DB LF-6T3N — deterministic replay, reported not predicted)

Re-materialized the fixed parsed tags on the persisted LF-6T3N snapshot (real extraction data; only the
declarations changed) and re-evaluated. Tag materialization: `id.dob` 0→2, `id.ssn_hash` 0→3,
`id.id_expiration` 0→2, `id.marital_status` 0→2.

- **ID-2 (SSN) — RESURRECTED.** Before: both borrowers `couldnt_check` ("0 sources carry id.ssn_hash" — tag
  absent). After: borrower A → **satisfied** ("the SSN matches across all 2 sources", two W2s); borrower B →
  `couldnt_check` ("only 1 source" — one of B's two W2 SSNs was non-matchable, correctly excluded). A real
  verdict where there was silent death.
- **ID-3 (DOB) — the tag is fixed and materializes, but ID-3 still `couldnt_check` on this file — CORRECTLY.**
  Each borrower has exactly ONE document stating DOB (their driver's licence; LF-6T3N has no 1003/URLA document
  surfacing a comparable DOB), so there is nothing to compare. The reason improved from "0 sources (tag
  broken)" to "1 source (genuinely one)". **This is NOT the lateral move** — because the tag is document-keyed,
  a file WITH a second DOB source would now compare; a borrower-keyed tag never could. The silent death is
  fixed; the file is simply thin on DOB sources.
- **ID-7 — unchanged.** `not_applicable` on non-title documents, `couldnt_check` on the 4 untyped ones — blocked
  by the absent title document (correct, the AS-4/insurance class of genuinely-absent source, NOT a false
  dependency). `id.marital_status` now materializes but ID-7 does not read it as a tag.

## ASSUMPTIONS + DECISIONS

- **`id.marital_status`'s consumer:** the ticket premised ID-7 was "starved" of it; ID-7's spec reads only
  `id.title_vesting_consistent`. Fixed the declaration anyway (hygiene + guard) but do NOT claim it resurrects
  ID-7. (Code beats ticket text.)
- **`id.ssn_hash` → `employee_ssn:hash`:** a real, correct (if narrow) comparison — a borrower's W2s must share
  an SSN. Recorded the narrowing; the full cross-source SSN set is for the live-rule audit. Not a fiction.
- **`income.employment_start/end`:** fixed to the VOE fields but UNVERIFIABLE on LF-6T3N (no VOE) — the guard
  confirms they now point at real fields; materialization on a VOE-bearing file is unproven here.
- **Exemptions over invented fixes:** `income.stated_monthly` (MISMO-indexed → needs a derived source) and
  `stmt.page_count_declared` (no extractor emits it) have no clean target; exempting them loudly beats a
  fiction. Both dormant.
- **Deterministic replay, not a fresh AI run:** the parsed producers this ticket touches are deterministic; the
  replay isolates the change exactly (as LP-366 did).
