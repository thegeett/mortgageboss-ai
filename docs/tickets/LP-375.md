# LP-375 — The read path: surface satisfied, separate the counts, stop the DTI card fabricating 0

## WHAT THIS TICKET IS

Three read-path problems, backend only (the UI is LP-376):
1. **Tab 2 (Satisfied) is unreachable from the API** — `_build_status` returns findings where `status IN
   (RED, YELLOW)`, dropping GREEN (which is where `satisfied` lands). §8 makes `satisfied` first-class: it is
   how a processor knows a rule RAN and PASSED rather than silently not running.
2. **The DTI card lies** — the display path (`services/dti.py`) collapses an unknown insurance input to a
   rendered `$0.00 "Extracted"` and a confident back-end DTI, while the snapshot path correctly GATES on the
   same `auto_amount=None`. Two paths contradicting each other on one page.
3. **The two finding systems' counts must never merge** — an ungoverned 75%-confidence AI sweep observation
   and a governed, gated, provenance-carrying rule finding are not the same kind of thing.

## ACCEPTANCE CRITERIA

- The discriminator confirmed; rule findings surfaced (incl. `satisfied`); counts structurally separate.
- The $0.00 fixed in the display layer only (the snapshot path + gates untouched); absent ≠ 0.
- Honesty contract in tests; the real LF-6T3N payload reported; equivalence; ruff + mypy + full suite green.

## PHASE 0 — THE ARGUMENT

**The discriminator is `evaluation_outcome IS NOT NULL`, NOT `origin`.** Confirmed on the real DB (LF-6T3N):
`origin=deterministic_rule` spans TWO systems — the governed rule engine (outcome present, from the 2026-07-17
run) AND retired `xsrc.*` rules (`xsrc.identity.name_consistency`, `xsrc.income.employer_name_consistency`,
outcome **null**, stale from 2026-07-08). So `origin` cannot separate them; `evaluation_outcome` can. **"Tab 5
— Old Findings" is genuinely TWO legacy systems** (7 `ai_cross_source` sweep + 9 `xsrc` deterministic-null) =
16. The LP-74/legacy engine is not actively re-run, but its rows persist and share the `deterministic_rule`
origin — so the guard uses the outcome column, and Tab 5 must be labelled as two legacy systems.

**The response shape — a SEPARATE typed list.** `rule_findings: list[RuleFindingPublic]` beside `findings:
list[FindingPublic]`. Two *different types* → they cannot be concatenated into one list or their counts summed
(the structural, not merely conventional, separation the ticket demands). `rule_findings` =
`evaluation_outcome IS NOT NULL`, **all** outcomes (no status filter) → Tabs 1–4 incl. `satisfied` (Tab 2).
`findings` gains `evaluation_outcome IS NULL` → the clean legacy quarantine (Tab 5); the sweep's own findings
are byte-identical within it (the sweep behaves identically). `RuleFindingPublic` carries what LP-376 needs:
the outcome (tab discriminator), the reason, the **spec's guideline citation** (read-time via
`load_rule_spec(rule_id).guideline_reference` — NEVER AI-recalled), inline `load_bearing_tags`
(value/confidence/reasoning), and the ratification marker (`gated_pending_signoff`).

**Is the LP-74 typed-fact engine still unwired?** Yes — the 9 `deterministic_rule`/null rows are stale (dated
2026-07-08, `xsrc.*` rule-ids from the old cross-source engine), not produced by the current run. Confirmed,
and reported so Tab 5's dual nature is honest.

**The subject problem (a finding for LP-376, not faked).** `subject_key` is a stable content-id (`txn54c6…`,
a borrower_id, or `"loan"`) — not human-legible. The `message` carries prose and `load_bearing_tags` carry
values, but a compact per-row label ("Deposit of $20,000 on 3/27") needs per-rule-family logic not uniformly
derivable from the stored data. `RuleFindingPublic` exposes `subject_key` + `load_bearing_tags` + `message`;
**a legible subject label is LP-376's, and is reported here, not fabricated.**

**The $0.00 fix layer — DISPLAY.** The collapse is `services/dti.py` `_to_items`: `effective = ... (auto.auto
or Decimal(0))`, then `compute_dti` returns a confident ratio on the 0. The snapshot path
(`calculations_section.map_dti`) already gates on the same `auto_amount=None` — **not touched.** A subtlety
found while building: `build_calculations_section` calls the *same* `build_dti_calculation`, and `map_dti`
returns `None` (absent DTI) when `back_end_dti is None`. So nulling the ratio inside `build_dti_calculation`
would have flipped the snapshot's honest *gated* entry to *absent*. The fix therefore lives at the API
boundary (`gate_display_ratios`): `build_dti_calculation` computes `gated`/`gate_reason` and marks the unknown
line, but leaves the ratio computed (so `map_dti` re-gates unchanged); the `/dti` endpoint nulls the ratio for
display. No gate / `_REQUIRED_DTI_TAGS` / `calculations_section.py` change.

**GREEN's blast radius — none on the legacy path.** GREEN is NOT un-dropped for the sweep: `findings` keeps its
`RED/YELLOW` filter, so the sweep, its counts, and its banner are untouched. GREEN/`satisfied` surfaces ONLY in
the new `rule_findings` list (outcome filter, no status filter). The submission gate
(`blocked`/`in_scope_open_count`, LP-75) still spans both systems — that is the blocking computation, not a
display tab count; a per-system blocking split is a policy question left to LP-377.

## WHAT WAS BUILT

- `schemas/verification.py`: `RuleFindingPublic` (a distinct type) + `_guideline_for(rule_id)` (spec-sourced);
  `rule_findings` added to `VerificationStatusPublic`.
- `api/verification.py` `_build_status`: split the query by `evaluation_outcome` — `findings` (null, legacy,
  RED/YELLOW, unchanged) vs `rule_findings` (not-null, all outcomes).
- `schemas/dti.py`: `gated`/`gate_reason` on `DtiCalculation`; `unknown` on `DtiLineItem`.
- `services/dti.py`: `_REQUIRED_HOUSING_KEYS`; the `unknown` flag in `_to_items`; `gated`/`gate_reason` in
  `build_dti_calculation` (ratio kept for the snapshot's re-gate); `gate_display_ratios(calc)` — the display
  transform that nulls the ratio when gated.
- `api/dti.py`: the 3 endpoints wrap their result in `gate_display_ratios`.

## ASSUMPTIONS / DECISIONS

- **`evaluation_outcome` is the discriminator, not `origin`** — proven on real data (the `xsrc` legacy rows).
- **Two types, not one list with a flag** — a shared type could be concatenated; two types cannot. This is the
  structural guarantee against merged counts.
- **The $0.00 fix is display-layer** — `build_dti_calculation` keeps the ratio so the snapshot's `map_dti`
  re-gates unchanged; `gate_display_ratios` nulls it at the API. The snapshot path is the honest one and is
  untouched.
- **DTI tests updated deliberately** — several asserted a confident ratio on files with NO tax/insurance docs
  (the pre-fix bug; the snapshot path already gated those). They now seed real housing inputs (so the math
  holds) or assert the gate; a new test pins the gated display.

## WHAT LP-376 STILL NEEDS

- **A human-legible subject label** — not derivable uniformly from `subject_key`; needs per-family logic.
  Reported here as a finding, not papered over.
- **The five tabs / provenance card / §10 actions** (LP-377) render from `rule_findings`.
- **Tab 5 must be labelled as two legacy systems** (sweep + retired `xsrc`), and Tab 4 (`not_applicable`) has
  no backing rows (those subjects are not persisted) — a display nuance for LP-376.
