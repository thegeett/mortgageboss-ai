# LP-336 — The `per_account` enumerator + a fail-closed account-identity resolution

LP-323-AS-A found AS-6/AS-8/AS-10 group a borrower's bank-statement DOCUMENTS by account, but no
`per_account` enumerator exists — and the account identity available today is UNSAFE to match on. This is
a small reusable primitive (the `per_borrower` pattern from LP-332) with one genuinely dangerous part: the
resolution.

## What it is (and is not)

- **IS:** a `per_account` ENUMERATOR (a registry entry in `enumerators.py`) + the fail-closed
  account-identity resolution it needs (`resolve_accounts`).
- **IS NOT a SubjectType.** LP-323-AS-A refuted that: a bank statement IS a `document`, so `stmt.*` facts
  key under the existing DOCUMENT subject. Grouping by account is an ENUMERATION concern, not a second
  keying (no fact keys under two subjects — the divergence risk LP-331/332 rejected). **`subjects.py` is
  UNTOUCHED.**
- **IS NOT AS-8's evaluator.** AS-8 (pairwise-sequential statement chaining) is a NEW SHAPE, DEFERRED to
  its own ticket (the IN-6 precedent). This ticket gives AS-8 its ENUMERATOR (+ `resolve_accounts` for the
  ordered statements); it does NOT build the shape.

## The design argument

### D1 — the account identity (deterministic; no new tag; no upstream ask)
`fact_tags.csv` flags `stmt.account_masked` *"display only, non-matchable"* — and it is right: `****1234`
at Chase and `****1234` at Wells Fargo look IDENTICAL. So the masked number ALONE is unsafe. **The
institution disambiguates it, and it is extractable:** `bank_statement.py` extracts `bank_name` (a
`Field`) alongside `account_number_masked` (a `PiiField`, masked last-4), and BOTH land in
`DocumentEntry.fields` (`documents_section.py`). So the identity is `(institution, masked-number)` —
**both parsed extraction fields, no uncalibrated AI, no calibration consequence.** **`stmt.institution`
did NOT need to be added as a tag:** the enumerator reads `bank_name` directly, exactly as `_per_borrower`
reads `belongs_to` (the enumerator-reads-document-attributes pattern). No new vocabulary, no declaration,
no bucket-C upstream ask.

### The failure modes (both directions) — each fails CLOSED
| Case | Resolution |
|---|---|
| same institution + same masked → | **ONE account** (grouped) |
| same masked, DIFFERENT institution → | **TWO accounts** (the collision trap caught — NOT a silent merge) |
| missing institution → | **UNRESOLVABLE** — surfaced, not grouped → couldnt_check with a reason |
| missing masked number → | **UNRESOLVABLE** — surfaced, not grouped → couldnt_check with a reason |
| a single-account file → | resolves cleanly (the common case still works) |
| a non-statement document → | ignored (not an account, not a *failed* one) |

**THE INVARIANT (mirroring LP-332's borrower_id resolution):** an ambiguous or unresolvable identity → the
statement is NOT grouped → the rule couldnt_checks WITH A REASON. **NEVER a guessed grouping** — a
mis-group FABRICATES a chaining break (a false positive), an over-split HIDES one (a false-green); a guess
makes a confident, wrong claim, worse than abstaining.

### D2 — where the resolution lives
In the enumerator: `resolve_accounts(snapshot) -> ({account_key: [content_id, …]}, [unresolvable_id, …])`,
exported (AS-8's future evaluator uses it for the ordered statements); `_per_account` wraps it. Reads
document fields (deterministic) — no derived tag needed. Mirrors `_borrower_enumerate`.

### D3 — `stmt.institution`?
**Not added.** `bank_name` already exists in extraction, and the enumerator reads it directly. If a future
RULE needs the institution as a first-class FACT (not just the enumerator's identity), AS-B adds the tag —
it would be `parsed` (deterministic), so not a calibration concern either.

## Acceptance criteria

- [x] `per_account` registered (`enumerate_subjects("per_account", …)` works); **no SubjectType added**
  (`subjects.py` untouched); no rule-id/family branch.
- [x] The resolution fails closed both directions (collision trap → two accounts; missing identifier →
  unresolvable, surfaced not dropped, not a guessed merge). Asserted.
- [x] The enumerator yields N subjects for N accounts (each its stable key + its statements' merged tags)
  + one surfaced subject per unresolvable statement (an `account.unresolved` marker naming why).
- [x] Stable `account_key` across runs (LP-322 reconciliation); display-safe (bank name + masked last-4).
- [x] EQUIVALENCE: every live rule identical; suites + the LF-6T3N trace unchanged (per_account is
  additive — no live rule uses it). ruff + mypy + full suite green (2213 passed).

## Assumptions & decisions

- **The `account.unresolved` marker** is a synthetic structural tag (never in `fact_tags.csv`), mirroring
  `DOC_TYPE_TAG`. It carries the reason (missing institution/masked) so a per_account rule couldnt_checks
  the statement WITH that reason (and a test/consumer can inspect it) — the statement is surfaced, not
  silently dropped (absent≠empty, the invariant now handled at TAG/OPERAND/GATHER/RULE/SUBJECT and here at
  the ENUMERATOR level).
- **The account subject's tag map** is its statements' tags MERGED — a grouping-key convenience. A rule
  that needs the ORDERED statements (AS-8) uses `resolve_accounts` directly (its deferred shape); a
  colliding per-statement tag (each statement's `stmt.ending_balance`) is not meaningfully mergeable into
  one flat map, which is precisely WHY AS-8 is a separate shape.

## `stmt.institution` — exists / added / upstream ask?

**Neither added nor an upstream ask.** `bank_name` is already extracted (`bank_statement.py`); the
enumerator reads it directly. No new tag, no calibration consequence.

## What this unblocks

AS-6 (account ownership), AS-8 (chaining — its enumerator + `resolve_accounts`), AS-10 (recency), and
**every future per-account rule** — from `subject_enumeration: per_account` in a spec, no new Python. This
is the one new granularity primitive LP-323-AS-A (and IN-C before it) predicted the Assets wave would need.

## NEW gap (reported, not patched)

**Masked-last-4 collisions within one institution.** The identity is the MASKED last-4 (raw account numbers
are never stored, ADR-149), so two DISTINCT accounts at the SAME institution with the SAME last-4 mask
identically → they would mis-group, and this is UNDETECTABLE from the masked display. Rare, but real. A
follow-on could add a fuller (still-masked) discriminator IF extraction surfaces one (e.g. account type,
or more masked digits). Reported for its own ticket — not worked around here.

## Priya / upstream items

None new. The institution + masked number are deterministic extraction fields (already present). The
masked-collision gap above is an extraction/identity refinement, not a guideline value.

## ADR

**ADR-277** — per_account as an enumeration concern (why no SubjectType) + the fail-closed identity (its
failure mode: ambiguous → not grouped → couldnt_check, never a guessed grouping, because a mis-group
fabricates a chaining break and an over-split hides one) + the masked-collision residual gap.
