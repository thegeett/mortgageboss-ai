# LP-548 — a deploy silently kills an in-flight verification, and nothing recovers it

Observed on staging 2026-08-18. Not started.

## What happened

| Time (UTC) | Event |
|---|---|
| 19:32:22 | worker deployment starts — new task `74edade7` launching |
| **19:32:42** | verification `38efd997` starts, picked up by the **old** task `c2d40de1` |
| 19:32:49 | new task `74edade7` reports `celery@… ready` — and logs nothing further |
| **19:33:33** | ECS sends SIGTERM to the old task |
| 19:34:54 | Stage A completes on the old task (57 transactions) |
| **19:35:33** | SIGKILL — `stopTimeout` expires exactly 120s after SIGTERM |
| 19:35:34 | old task's last log line, mid-Stage-B |
| +11 min | verification row still `running`; nothing is working on it |

The run was executing inside the container ECS was replacing. Graceful shutdown behaved exactly as
designed — SIGTERM reached Celery, the task kept working for the full grace period — and then the
container was killed with the run half finished.

## Why graceful shutdown cannot fix this

`worker_stop_timeout_seconds = 120`, and the module README is explicit that **120 is the Fargate
maximum**. A verification run takes about **7 minutes** (the two completed runs that day took 6m57s
and 6m31s). So the grace period is short by a factor of three and cannot be extended — this is
structural, not a misconfiguration.

The variable's own description says "A Celery worker killed mid-extraction loses the task". That
sizing is right for a document extraction, which fits inside 120s. A verification run never will.

## Why the run is never recovered

`acks_late` is not set, so Celery's default (`False`) applies: the message is acknowledged when the
worker RECEIVES it, not when it finishes. When the container died the message was already gone from
the queue, so nothing redelivered it. The new worker sat idle.

The task's own limits do not help either — `soft_time_limit=900` / `time_limit=1200` only fire while
the worker is alive to fire them.

**This violates the invariant the task docstring states outright:**

> mark FAILED on exhaustion (fail-closed — never a silent permanent RUNNING or a false COMPLETED via
> the sweep alone)

`_mark_failed` runs on retry exhaustion. A SIGKILL is not exhaustion, so it never runs, and the row
stays RUNNING forever. The UI spins on a job that no longer exists.

## Why it matters beyond the stuck row

A killed run and a genuinely hung run look identical from outside: a `running` row and silent logs.
Every future "why is verification still running?" costs a CloudWatch investigation to tell the two
apart. That ambiguity is the real cost.

## Scope

Two fixes, and both are worth having — they cover different failures.

**1. A stale-run reaper (cheaper, do first).** Mark any `RUNNING` verification older than
`RULE_ENGINE_HARD_LIMIT_SECONDS` (1200s) as FAILED, with an error_detail naming the reason. The hard
limit is the natural threshold: past it, a live worker would have been killed by Celery anyway, so a
still-RUNNING row past that point is definitionally orphaned. Stops the UI spinning forever and makes
the state honest. There is **no Celery beat schedule in the project today**, so this needs either a
beat entry or a check on the read path.

**2. Redelivery (`task_acks_late=True` + `task_reject_on_worker_lost=True`).** Makes a worker-loss
redeliver the task to the surviving worker, so a deploy costs a restart rather than a lost run.

### Constraints on the redelivery half

- **A poison task would loop.** With `acks_late`, a task that reliably kills its worker (OOM) is
  redelivered forever. It needs an attempt cap, and the existing `max_retries` does not cover
  worker-loss redelivery — that is a broker-level redelivery, not a Celery retry.
- **Redelivery must be safe on a half-finished run.** The run persists findings through the
  reconciler keyed by `run_id`; whether re-entering an already-partly-persisted run is idempotent has
  to be established, not assumed. If it is not, the reaper alone is the correct scope.
- The two completed runs on 2026-08-18 (6m57s, 6m31s) are the baseline to size any new timeout
  against — re-measure rather than reusing these, since rule count and file size both move.

## Immediate operator workaround

Re-run the verification. The replacement worker is healthy and idle, so it picks up immediately. The
orphaned row stays RUNNING until something clears it.
