# LP-823 — The draft shows placeholders where it already knows the answer

- **Ticket:** LP-823 · Phase 4 follow-up, from processor feedback on LF-JR4T
- **Status:** Built — awaiting review
- **Date:** 2026-09-07
- **Scope:** `services/email_draft.py`, `api/communications.py`,
  `components/file/communication/outbound-draft-panel.tsx`
- **Migration:** none expected

---

## What was reported

Three things in one screen, all the same shape — the draft asks the processor for something the
file already holds.

1. **The To: field starts empty.** The borrower's email is on the application. A processor types it
   by hand on every send.
2. **`$borrower_first_name` is shown literally** in the draft body.
3. **`$processor_name` is shown literally** at the signature.

**It is worse than reported.** These reach the borrower, not just the screen — see below.

## Measured

`render_draft_body` (`services/email_draft.py:112`) passes the two names through as their own
placeholder strings, deliberately:

> *"The processor's name is left as the template's own placeholder rather than resolved here. A
> draft is not addressed to anyone until it is sent, and LP-811 owns the send — resolving a signer
> now would bake in whoever happened to click 'request', who is not necessarily who sends it."*

`finalise_draft_body` exists to resolve both. **It has no caller.** Searched every `.py`, `.ts` and
`.tsx` in the repository: the only references outside its own definition are in
`tests/services/test_email_draft_lp809.py`. Nothing in `app/` invokes it — not `send_draft`, not the
draft endpoint, not the panel.

**So this is not a preview problem. The borrower receives the placeholders.** There is no send
button; the message leaves through "Copy message" or "Open in mail client", both of which take the
textarea's contents — `draft.body`, placeholders and all. `send_draft` then RECORDS that it went out
and stores that same unresolved text as the body as sent. Every document request mailed from this
system so far opened with `Hello $borrower_first_name,` and was signed `$processor_name`.

This ticket was first written on the belief that the sent mail was correct and only the screen was
wrong. That belief came from `finalise_draft_body`'s own docstring — *"THE ONLY SUPPORTED WAY TO DO
IT"* — read as a description of what happens rather than of what the function is for. The docstring
is accurate about intent and silent about whether anything calls it. Corrected by grep, not by
re-reading.

The seventh form of the pattern this phase kept finding: a function nothing calls.

`GET /outbound/draft` returns `draft.body` straight through `build_outbound` with no finalise pass,
and the panel renders exactly that into the textarea — which is both what the processor reads and
what they copy.

`OutboundDraftPublic` carries no `recipient` field at all, and the panel seeds
`useState("")` — so the To: box is empty by construction, not by accident.

`borrowers.email` is `String | None` (`models/borrower.py:97`), which is why it was never assumed.

## The decision that has to be made, and my reading

The deferral reasoning is right about the SIGNER and wrong about the DISPLAY. Whoever sends should
sign, and that is not known until the send — but a processor reading `$processor_name` on screen
cannot tell whether the send will fill it in or whether the borrower is about to receive that
string. The two goals do not conflict: resolve for the preview using the **current viewer** as the
prospective signer, keep the stored body's placeholders untouched, and let `send_draft` resolve
again from whoever actually sends. The stored body stays the deferred artifact; only the rendering
of it changes.

For the borrower's first name there is no such tension — it does not depend on who sends — but it
is still resolved at the same point rather than baked into storage, so there is one rule and not
two.

## Done when

- The draft preview shows the borrower's first name and the viewing processor's name, with no `$`
  placeholder visible for either.
- `GET /outbound/draft` returns the borrower's email as a suggested recipient, and the panel seeds
  the To: field from it — still editable, because a co-borrower or a corrected address is ordinary.
- A file whose borrower has **no** email still renders a draft, with an empty To: field and nothing
  claiming otherwise. That is the case `borrowers.email` being nullable makes real.
- A file with two borrowers has a defined answer for whose address is suggested, and it is written
  down rather than left to `.first()`.
- **Nothing a borrower can receive contains a `$` placeholder.** The paths that matter are the
  clipboard and the `mailto:` link, because those are how the message actually leaves. A test that
  only covers the API response would pass while the copied text stayed broken.
- The stored `Communication.body` keeps its placeholders, and `send_draft` resolves from whoever
  sends when it records the body as sent — so the evidence row holds the words the borrower got.
- A test asserts the stored body still has both placeholders, because resolving on the way in would
  bake in whoever clicked "request" and would look identical on every screen.

## For the reviewer

The trap is fixing this in `render_draft_body` and storing resolved names. Every screen would look
right, and the first send by a processor other than the one who clicked "request" would go out
signed by the wrong person — a defect no preview can show.

## Built, 2026-09-07

**`primary_borrower()`** — `is_primary` first, then `borrower_position`, then `id`. Ordered, not
`.first()` over an unordered set: two borrowers must give the same answer on two requests, because
the answer decides which mailbox a document request goes to. The positional fallback matters —
`schemas/loan_file.py`'s `_primary_borrower_name` returns None when no borrower is flagged, which is
right for a display name and wrong for choosing who to write to.

**`draft_for_reading()`** — resolves the stored body for the READER, and returns the borrower's
email with it. The reader is the prospective signer, which is the whole reconciliation: whoever
sends should sign, so the stored body keeps its placeholder; whoever is looking should see a name,
because a processor cannot tell a placeholder that will be filled from one that will not.

**The send path resolves too, and that is not a duplicate.** The panel posts text it read from the
endpoint, so `send_draft`'s pass is a no-op on the ordinary path. It exists for the path that is not
ordinary — any caller posting the STORED body would otherwise record, and once a transport exists
actually deliver, `Hello $borrower_first_name,`. The signer there is the **approver**, not the
composer and not whoever last previewed it.

**`BORROWER_NAME_FALLBACK = "there"`.** A file whose borrowers were all soft-deleted has no name to
put in the greeting. "Hello there," is ordinary English; "Hello ," is not, and the placeholder is
one copy-and-paste from a stranger's inbox. Rare by construction — `first_name` is NOT NULL, so a
borrower cannot exist without one.

**`suggested_recipient` is nullable and the panel honours it.** `borrowers.email` is nullable, so a
file can have a borrower and no address. An empty box is the honest render.

### What the tests pin, and the mutants that prove they can fail

Nine API tests plus three panel tests. The three mutations run:

| mutation | result |
|---|---|
| the endpoint stops resolving | **5 failed** |
| the send path stops resolving | **1 failed** — the stored-body test, and only that one |
| `is_primary` dropped from the ordering | **1 failed** — the primary-at-position-2 test |

The primary-borrower test puts the primary at the **later** position deliberately. With both at the
obvious positions, an implementation ordering only on position passes by coincidence.

The absence assertions carry positive controls. `"$borrower_first_name" not in body` passes on an
empty body and on a body whose placeholders were deleted rather than resolved, so each one is paired
with `"Hello Sarah," in body`.

### One existing test changed rather than deleted

`cannot be sent without a recipient` used the default fixture, which now seeds an address. Rewritten
to use the file with no borrower email — the rule it asserts is still the rule, and a seeded default
must not be allowed to hide it.

### Not done here

The dialog in LP-829 must render `draft_for_reading`'s output, not `draft.body`. It would otherwise
reintroduce this defect in a third place.

### The three standing checks

**Tenancy:** the borrower is loaded by `loan_file.id`, and the loan file is the one the route already
resolved under the authenticated user's company. No `company_id` derived anywhere new.
**Logging:** nothing added; no name, address or body reaches a log line.
**AI:** none — `finalise_draft_body` is `string.Template.safe_substitute`.
