# LP-995 — Delivery events

Step 2 of the email work (`loan-email.md` §15a). Code, tests and a dev check. No AWS or Terraform
changes, no migration, no new tables or columns.

## What and why

SES reports what happened to every email we send: delivered, bounced, marked as spam, refused.
Since LP-983 those reports land in the events queue (`EVENTS_QUEUE_URL`, set on the tasks since
LP-988), and nothing read them. So a Send ended at `sent` forever, a bounce never blocked the
address, and a request that never arrived kept its reminder clock running.

Now a worker job reads the queue every minute and applies each report to its email.

## What each report does

The email is found by `external_message_id` (SES's MessageId, stored by LP-994's worker), outbound
emails only. **Only the email's own To recipient counts**: every email is CC'd to the processor, and
SES reports on each recipient. An event about the processor alone changes nothing and blocks
nothing. Addresses are compared lower-cased and trimmed.

| SES event | Status | Address | Needs | On the file |
|---|---|---|---|---|
| `Delivery` | `sent` → `delivered`. Already `delivered`: duplicate. `failed` stays `failed` after a permanent bounce or a refusal; after a temporary or unclear bounce it becomes `delivered` (review #8) | — | stay pending | after a temporary bounce: "A document request was delivered after an earlier temporary failure. The documents it asked for are still pending: request them again if needed." |
| `Bounce`, permanent (`bounceType: Permanent`) | `failed`, `error_detail` = SES's diagnostic | blocked (`hard_bounce`) | back to pending | "A document request did not reach the borrower" |
| `Bounce`, `OnAccountSuppressionList` | `failed`, `error_detail` = "Not delivered: this address bounced or complained before. Ask the borrower for another address." | blocked (`hard_bounce`) | back to pending | same as permanent |
| `Bounce`, temporary (`bounceType: Transient`) | `failed`: SES already retried, so this is final | not blocked | back to pending (review #1; LP-819 left them requested) | "…was not delivered because of a temporary problem at the recipient's mail server" |
| `Bounce`, `Undetermined` | from the status code: `5.x.x` permanent, `4.x.x` temporary, none unknown (`failed`, not blocked) | as the class | back to pending | unknown: "…for a reason the mail server did not make clear" |
| `Complaint` | unchanged (stays `delivered`) | blocked (`complaint`) | — | "The recipient marked this email as spam. Their address is now blocked." |
| `Reject`, `Rendering Failure` | `failed`, `error_detail` = "Not sent: SES refused it (<reason>)." | — | back to pending | "Not sent" |
| Unknown MessageId, or a deleted email | — | — | — | logged `unmatched` |
| Any other `eventType` (`Open`, `DeliveryDelay`, …) | — | — | — | logged `ignored` |
| No `eventType` at all (an SNS envelope, an identity notification) | — | — | — | raises: left on the queue for the DLQ |

**Duplicates.** SQS delivers at least once, so every event can arrive twice. A second Delivery,
a Bounce/Reject on an email already `failed`, or a second Complaint about the same email answers
`duplicate` and changes nothing: no second unwind, no second activity entry.

**A bounce after a Delivery** (the receiving server accepted it and bounced later) still fails the
email.

## What changed

- **Handler** `services/delivery_events.py`: `apply_delivery_event(db, event) -> str` takes one
  parsed SES event and returns what it did (`delivered`, `bounced`, `complaint`, `rejected`,
  `duplicate`, `ignored`, `unmatched`). Flush only; the caller commits. An event with no
  `mail.messageId` raises (it is not an SES event), so the queue job leaves it for the DLQ. Logs carry
  the event type, the outcome and the communication id only.
- **`parse_ses_bounce`** reads SES's own `bounce.bounceType` first (`Permanent`, `Transient`) and
  falls back to `classify_status` only for `Undetermined`. Without this, `OnAccountSuppressionList`
  (no status code) came out `unknown` and the address stayed unblocked.
- **`record_delivery_failure` wording**: the temporary case said "was delayed and will be retried",
  which stopped being true (SES has already retried). Now three texts, one per class (table above).
- **`record_not_sent`** (new, in `bounce_handling.py`): the clean-failure path LP-994's worker had in
  `_fail` (status `failed`, "Not sent: …", needs unwound, "Not sent" activity), moved so `Reject` and
  `Rendering Failure` use the same code. The worker's `_fail` now calls it and commits.
- **`send_draft` suppression refusal**: "<address> is blocked: an earlier email to it bounced or was
  marked as spam. Confirm the address with the borrower before sending again." (was "is suppressed —
  … bounced permanently"). One message for both reasons.
- **Setting** `events_queue_url` (`EVENTS_QUEUE_URL`), blank is None. `.env.example`:
  `EVENTS_QUEUE_URL=` (no SQS locally).
- **Queue job** `communications.read_delivery_events` in `tasks/outbound.py`:
  - No URL → one debug line, no SQS call.
  - SQS client in the app's region (`S3_REGION`, as every other client), connect 5 s, read 10 s.
  - `receive_message(MaxNumberOfMessages=10, WaitTimeSeconds=1)`, up to 5 batches per run; stops
    early when a batch is short.
  - Each message: parse, apply, **commit, then delete**. A crash between the two redelivers an event
    already applied, which answers `duplicate`; the other order would lose it.
  - Not JSON, or the handler raises → rolled back, logged with the SQS message id and the error
    class, **not deleted**, and the batch goes on. After 3 receives SQS moves it to the DLQ, which
    alarms (LP-987). Message bodies are never logged.
- **Beat**: `read-delivery-events` every 60 s, `expires: 60`.
- **Dev script** `app/scripts/inject_delivery_event.py --communication <id> --type
  delivery|bounce|bounce-suppressed|bounce-transient|complaint|reject`: builds the SES event for that
  email (its MessageId and recipient) and calls `apply_delivery_event`. No SQS. Refuses an email with
  no `external_message_id`, and refuses to run outside development.
- `tests/test_unwired_services.py`: `parse_ses_bounce` and `record_delivery_failure` came off
  `KNOWN_UNWIRED`; they have a production caller now.

### Decisions made here

- **A complaint is logged as `communication_failed`** with `detail.event = "complaint"`. A new
  activity type needs a constraint-swap migration listing every value; the brief kept this ticket
  small. The type is wrong for what happened (the email arrived), so if LP-997 or a report filters on
  `communication_failed`, it must read `detail.event`. A new `communication_complained` type is the
  clean fix.
- **"Duplicate" for a bounce or refusal means the email is already `failed`**, whatever failed it.
  Realistically only one final report comes per recipient.
- Both `Rendering Failure` (what SES sends) and `RenderingFailure` (how `loan-email.md` writes it)
  are accepted. We send raw MIME with no SES template, so it should never arrive.
- `OnAccountSuppressionList` blocks the address locally as `hard_bounce`, even if SES listed it
  because of a complaint: SES does not say which.

## Review follow-up

A code review of the first version raised ten candidates; all ten were fixed ("fix all"). Each fix
has a test, and each condition it adds was mutation-checked.

| # | Finding | Fix |
|---|---|---|
| 1 | A temporary or unclear bounce failed the email but left its needs `requested`, so the reminder clock ran against a request the borrower never got | `record_delivery_failure` unwinds for every bounce class; only a permanent one blocks the address. Two LP-819 tests that pinned the old behaviour were rewritten (`test_a_soft_bounce_unwinds_too`, `test_a_soft_bounce_unwinds_both_records`) |
| 2 | A message with no `eventType` (an SNS envelope if raw delivery were switched off, an identity notification) was `ignored` and deleted, so every report would vanish without a DLQ alarm | No `eventType` raises; the job leaves it for the DLQ. A present but unknown type is still `ignored` |
| 3 | The dev script could run in staging and block a real address | Refused unless `ENVIRONMENT=development`, before the database is opened |
| 4 | An SQS error on delete or receive ended the whole run | A failed delete is logged (`delivery_event_delete_failed`, id and error class) and the batch goes on; a failed receive ends the run with one log line |
| 5 | LP-994's comment said LP-995's events settle a row left `sending`; they cannot (no MessageId was stored, so they are `unmatched`) | Comment corrected |
| 6 | The complaint duplicate check loaded every failure entry on the file | Filtered in SQL on `detail.communication_id`; shared with #8 |
| 7 | `record_delivery_failure` looked the email up again, without the outbound or deleted filters | Optional `communication=` argument; the handler passes the row it matched |
| 8 | A Delivery after a temporary bounce left a delivered email `failed` | It becomes `delivered`, `error_detail` cleared, and an activity entry says the needs stay pending. Not done: putting the needs back to requested, which would also mean restoring finding markers and the approver. A permanent bounce or a refusal is never undone |
| 9 | A deleted email still took events | The lookup excludes deleted rows (`unmatched`), as LP-994's worker does. A bounce for a deleted email therefore does not block the address |
| 10 | `loan-email.md` §15a said "up to 10 messages" | One line changed: "up to 50 messages per run (5 batches of 10), deletes each one after it is committed" |

**Mutations of the fixes** (snapshot restore, `cmp` checked): 12, all killed in the end. One survived

## For LP-997

The thread must show:

- `delivered`, including an email that failed with a temporary bounce and was delivered after all
  (activity `communication_sent`, `detail.event = "delivered_after_failure"`).
- `failed` with `error_detail`, which can be:
  - "Not delivered: this address bounced or complained before. Ask the borrower for another address."
  - a raw SES diagnostic for other bounces (permanent, temporary, unknown), e.g. `smtp; 550 5.1.1
    user unknown`; or the status code alone when there is no diagnostic;
  - "Not sent: SES refused it (<reason>)." (Reject / Rendering Failure);
  - LP-994's "Not sent: <reason>." for worker failures.
- A complaint does not change the status: show the activity entry ("The recipient marked this email
  as spam. Their address is now blocked.") on the thread or the file, and note it is logged as
  `communication_failed` with `detail.event = "complaint"`.
- The Send refusal for a blocked address: "<address> is blocked: an earlier email to it bounced or was
  marked as spam. Confirm the address with the borrower before sending again."
- Condition drafts still read only `sent` (LP-994), so a delivered condition email shows as draft.
