# LP-609 — Asking for a document that is already in the file

## The finding

IN-3, on a file carrying two pay stubs:

> "Upload the borrower's most recent pay stub showing year-to-date gross and the pay period."

## Why the composer could not fix it

Its instruction is explicit:

> "The action must make **THE SAME REQUEST** as `suggested_fix`. Sharpen its wording, name the document
> it names — but never ask for a document or a step it does not ask for."

That rule earned its place: without it the composer read background context and sent processors after
a purchase contract on a refinance, which can never exist. So it may rephrase a request, never replace
one. If the template asks for a pay stub, the composed text asks for a pay stub — even when two are
sitting on the file.

**The template is therefore the only place this can be fixed**, which answers the question directly:
not hardcoded text *or* AI composition, but the template setting the options and the composer choosing
between them.

## Two halves, and neither works alone

**1. The template must offer both branches.** IN-3 now reads: upload the stub — *or*, if the stubs are
already in the file, confirm the year-to-date gross and pay date are legible on the most recent one.
Both are requests the template makes, so whichever the composer voices it is still obeying the rule.

**2. The composer must know which kinds are on the file.** LP-597 gave it a *count*, which was enough
to stop it inventing a corpus on an empty file and useless here: "2 documents" says nothing about
whether either is the one being asked for. `document_kinds_on_file` now carries the readable kinds
("pay stub", "W-2"), deduped and sorted — sorted because `cache_key` hashes this JSON, and an
unordered set would re-compose every finding on every run.

Without (1), (2) would push the composer to disobey its own instruction. Without (2), (1) is a
sentence with two branches and no way to pick. The question that surfaced this — *"what does IN-3
display when there is no pay stub?"* — is what made the first half visible; the answer is that it says
what it says today, which is correct in that case.

## Why this matters beyond IN-3

IN-3's shape is **invisible to a static audit**. Its spec declares one document and its fix names that
document; nothing is out of place. The real blocker lives inside `income.ytd_annualized_shortfall_pct`,
whose own dependencies reach past the pay stub. LP-608's audit could not have found it, and only
reading live findings on a real file did.

The kinds list works from **what is on the file** rather than what the spec declares, so it covers
that class without anyone having to diagnose each instance first.
