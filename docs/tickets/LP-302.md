# LP-302 — Stage-2 codebase recon (READ-ONLY)

A survey of what exists vs. must be built for the Stage-2 evaluator pipeline, so the
Phase-A build tickets (LP-303…307) build on reality. **No code was written or
changed** — the only file created is this report. Findings are backed by
`file:line` references; where something couldn't be found, that is stated (it means
build-new).

**No ADR-level decisions** — this is recon. Two architectural choices it *surfaces*
(the finding model is EXTEND-not-fork; AS-1's per-deposit inputs aren't in the
snapshot) are called out below as decisions to be made in their home tickets
(LP-306, LP-303/305), not decided here.

## Summary

- **Biggest reuse wins:** the AI call layer is mature and a near-exact precedent
  exists. `complete()` (`app/ai/client.py:183`) + the cross-source reasoning pass
  (`app/ai/cross_source.py` + `app/services/cross_source.py`) are the *shape* the
  evaluator clones: static/file spine + JSON context in the user message → Opus-4.8
  → defensively-parsed structured findings, with cost + input-fingerprint recording.
  The deterministic **compare primitive the numeric bookend needs already exists** —
  `satisfies(Condition(op, value), observed)` (`app/verification/rules/schema.py:269`),
  pure and DB-free. The snapshot load path (`build_snapshot`, `load_snapshot`) and
  the LP-301 rule-kinds table (`load_rule_kinds`, 133 rules) are reuse-as-is.
- **Biggest build-new gaps:** (1) **spine+body prompt assembly** — there is no
  templating mechanism; prompts are static `.txt` with essentially no injection.
  (2) **the four-state finding output** — the existing `Finding` model has no
  `couldn't-check`, no first-class `no-longer-applies` (it soft-deletes instead), and
  **no DB-enforced `(rule_id, subject_key)` identity or event log** — the design doc
  itself calls the Stage-2 persistence "Net-new schema." (3) **the AS-1 large-deposit
  evaluator does not exist on this branch** (it's only on `phase3_5_1`), and — the
  real surprise — **bank-statement transactions are not in the snapshot** (the
  documents assembler skips nested lists), so AS-1's per-deposit inputs aren't
  reachable from the snapshot the evaluator reads. (4) **no golden-file eval harness**
  exists.
- **Surprises:** the snapshot ↔ AS-1 input gap (above); `app/verification/evaluators/`
  looks populated but is **stale `.pyc` bytecode from `phase3_5_1`** — dead, do not
  import; the AI layer has **no timeout** and **raises** (no structured-outputs /
  tool-use — all prompt-JSON + defensive parse); truncation at `max_tokens` silently
  yields zero findings.

## Per-area findings

### 1. AI call layer — mostly REUSE; the spine+body template is BUILD-NEW

- **`complete()`** — `app/ai/client.py:183` `async complete(*, model, messages, max_tokens, system=None, temperature=None) -> AICompletion`. Wrapper owns retries (SDK `max_retries=0`; up to `settings.ai_max_retries=3`, exp backoff + jitter, transient-only), returns `AICompletion{text, input/output_tokens, model, stop_reason}`. **Verdict: reuse-as-is.** Gotchas: it **RAISES `AIClientError`** (the evaluator must own its try/except graceful fallback); **no per-call timeout** is configured (a large-snapshot reasoning call could hang on the SDK default).
- **Model tier:** `settings.anthropic_model_extraction = "claude-opus-4-8"` (`app/core/config.py:59`) is the reasoning tier every pass already uses; `claude-opus-4-8` is priced in `app/ai/cost.py:27`. **Reuse-as-is.**
- **Structured output / parsing:** **no** tool-use / structured-outputs / `response_format` anywhere — it is 100% "ask for JSON in the prompt + defensively parse text." `extract_json_object` (`app/ai/parsing.py:15`) + `coerce_confidence`/`coerce_optional_confidence` (`parsing.py:61,76`) reuse-as-is; the cross-source **array-of-findings** parser (`app/ai/cross_source.py:208-296` — `_json_candidates`/`_load_findings_list`/`_coerce_finding`) is the pattern to **copy** for the evaluator's result shape.
- **Prompt templating:** `load_prompt` (`app/ai/prompt_loader.py:19`) loads cached `.txt` prompts. **There is no templating engine.** The *only* injection in the whole AI layer is a single `template.replace("{document_type_catalog}", …)` in `classification_prompt.py:172-174` — deliberately `.replace()` (not `.format()`/f-string) because prompts contain literal `{}` JSON braces. **Verdict: build-new** the spine+body assembly. Lowest-risk route (matches the design doc's `{{ }}` placeholders): keep a static/file spine + inject the rule spec + snapshot via the **user message** (the cross-source/needs pattern), or named-token `.replace()`.
- **Closest reasoning precedent:** `reason_cross_source` (`app/ai/cross_source.py:144`) + `run_cross_source` (`app/services/cross_source.py:97`): deterministic context assembly (`assemble_cross_source_context:485`, ordered rows — reproducibility is load-bearing), injected reasoner (`Reasoner` alias — stubbable, tests run without a key), `AIClientError`→graceful, `total_tokens/cost` + `input_fingerprint` (SHA-256) so an identical re-run skips the AI call, and a **truncation guard** (`stop_reason=="max_tokens"` → logged; a cut JSON array parses to zero findings). **Verdict: extend (clone this two-file split).**

### 2. Finding model — EXTEND (do not fork); the four-state axis is net-new

- Existing `Finding` (`app/models/finding.py`) is a **two-axis** model: severity `FindingStatus` = red/yellow/green (`:46-51`) × lifecycle `FindingResolutionStatus` = open/applied/overridden/resolved/accepted_risk/waived (`:66-90`), plus `FindingOrigin` (`:98-113`). Neither axis is the Stage-2 evaluation-outcome axis.
- **Vs the target four (open / satisfied / no-longer-applies / couldn't-check):** `open` maps; `satisfied` is only expressible as severity `GREEN` (semantic mismatch — "passed" vs "processor acted"); **`no-longer-applies` is not a state** — it's implemented as a **soft-delete DROP** in reconcile (`app/services/finding_reconcile.py:90-92`), so it's invisible; **`couldn't-check` has no representation at all.** The design doc §8 is explicit that collapsing these is "the core failure mode."
- **Identity:** `(rule_id, subject_key)` exists only as an **app-level normalized tuple** (`app/services/finding_identity.py:83-93`); `subject_key` lives inside the `details` JSON, **not a column**; **no DB UNIQUE** on `(loan_file_id, rule_id, subject_key)` (the `create_findings` migration has only non-unique indexes). **No append-only event log** table — provenance is mutable status + generic `activity_logs`.
- **What's wired & reusable:** `Verification` run entity (`app/models/verification.py:58`), `Finding.verification_id` linkage, cross-run reconcile (`finding_reconcile.py:50` — keep/add/drop/retain, wired to the cross-source passes).
- **Verdict: extend the `Finding` table, don't build a new model** — but LP-306 must add a **new evaluation-outcome enum/column** (the four states), stop the reconcile DROP hiding `no-longer-applies`, and add a real `subject_key` column + `(loan_file_id, rule_id, subject_key)` UNIQUE + an event-log table (the design doc's "Net-new schema"). **This is a genuine architectural decision for LP-306** (extend-with-net-new-schema vs. a parallel Stage-2 findings table) — flagged, not decided here.

### 3. Deterministic calculators / numeric bookend — compare primitive REUSE; calculators-as-verifiers BUILD-NEW wrapper

- Calculators: `build_dti_calculation` (`app/services/dti.py:275`→`DtiCalculation` with `DtiLimit.status` pass/over/unknown), `build_ltv_calculation` (`app/services/ltv.py:177`→`LtvLimit.status`), `compute_loan_mi` (`app/services/mi.py:119`→`MiResult.required` bool, **no limit/status object**), `build_reserves_view` (`app/services/calculators.py:348`→`CalculatorView.status` sufficient/insufficient). **All four are full DB-reading breakdown builders** — none accepts a bare `(value, threshold)`.
- **The bookend's compare primitive EXISTS:** `satisfies(condition, observed) -> bool` (`app/verification/rules/schema.py:269`) with `Operator` (LE/LT/GE/GT/EQ/NE, `:65`), `Condition(op, value, unit)` (`:156`), `_COMPARATORS` (`:259`). Pure, no DB, no AI — "the *only* place a threshold comparison happens." **Verdict: reuse-as-is** for LP-305's `compare(value, op, threshold)`.
- **Gotcha (drift risk):** the calculators **re-implement** the comparison inline (`dti.py:340`, `ltv.py:264`, `mortgage_insurance.py:60`) rather than calling `satisfies`; and `None`-handling differs (calculators map `None→"unknown"`; `satisfies` would raise via `_to_decimal`). So the bookend should call `satisfies` **directly on the AI-surfaced operands** — not invoke the calculators — and beware operator/`None` drift.

### 4. Snapshot load path — REUSE (build fresh in tests, don't load)

- `build_snapshot(db, *, loan_file_id, run_id, company_id) -> Snapshot` (`app/verification/snapshot/builder.py:114`) — **`company_id` required** (tenant boundary), non-nil `run_id`, stateless, resilient (per-section savepoints → absent-with-reason). `load_snapshot(db, run_id) -> Snapshot | None` (`persistence.py:89`), `load_snapshots_for_loan_file` (`:97`). **Reuse-as-is.**
- **Injected shape** (`app/verification/snapshot/model.py`): `Snapshot{loan_file_id, run_id, created_at, snapshot_version, mismo, documents, calculations}`, serialized `model_dump(mode="json")`. `mismo.facts: dict[str, Field|PiiField]`; `documents.entries: [DocumentEntry{document_type, belongs_to: tuple[BorrowerRef]|None, fields}]`; `calculations.{dti,ltv,mi,reserves}: CalculationEntry|None` (`value` numbers are **strings**). Cells: `Field{value, confidence, source, absent}`; `PiiField{display, match_hash (v1:… or None), confidence, source, absent}` — **no raw value**; cross-section matching is by `match_hash` equality.
- **Gotcha:** `absent != present-empty` at field **and** section level (a section can be present-empty or `absent` with a `reason`). The prompt must distinguish "never carried" from "carried blank."
- **LF-6T3N testability:** **no committed persisted snapshot row**; tests **build fresh** via `build_snapshot` against a seeded LF-6T3N-*shaped* file (as `tests/verification/snapshot/test_e2e.py` does). Treat `load_snapshot` as production-only.

### 5. Eval-harness placement — BUILD-NEW (none exists)

- Tests split by concern under `backend/tests/`; DB-backed via `tests/conftest.py` `db_session` (rollback-isolated, `create_all`, flush-not-commit). Base builders in `tests/integration/factories.py`; the fuller loan-file setup is hand-rolled in `test_e2e.py`/`test_builder.py`.
- **No golden-file / scoring / eval scaffold exists** (grep-confirmed: zero `golden` hits). **Verdict: build-new** — place a `tests/verification/eval/` (or `stage2/`) subpackage mirroring `snapshot/`/`rules/`, pairing a rule spec + a `build_snapshot` fixture → expected finding, indexed off `load_rule_kinds()`. Mirror `stage1_artifact.py`/`*smoke*.py` for the real-LF-6T3N runner, but the CI-safe form is a seeded deterministic test like `test_e2e.py`.
- **Trap:** `app/verification/evaluators/` is **stale `.pyc` only** (a dead `phase3_5_1` LP-119…125R framework) — `git ls-files` returns no `.py`. Ignore/do not import it.
- **LP-301 artifact confirmed present + loadable:** `app/verification/rules/rule_kinds.csv` (133 rules) + `load_rule_kinds()` (cached read-only `MappingProxyType`, header/contract validated). Routes via `EvaluationPath`.

## AS-1 readiness (the first vertical-slice rule)

- **AI layer ready?** Yes for the call/parse/cost; **the spine+body template assembly is build-new** (LP-304). Clone the cross-source two-file shape; inject spec + snapshot via the user message.
- **Snapshot loadable?** Yes — build fresh via `build_snapshot` against a seeded LF-6T3N-shaped file (no committed persisted row).
- **Large-deposit calculator to reuse + a head-to-head baseline?** **Not on this branch.** The `evaluators/large_deposit.py` bookend exists **only on `phase3_5_1`** — build-new (or cherry-pick). A weak baseline exists here: the cross-source `_check_large_deposit_unsourced` (`verification/cross_source/rules.py:296`) + the `unsourced_large_deposits` fact — but it works on a **pre-aggregated scalar**, not per-transaction.
- **⚠️ Input gap (the sharpest AS-1 risk):** AS-1 is per-deposit, but **bank-statement transactions are not surfaced in the snapshot** (`documents_section.py:93-99` skips nested lists) — they live only in raw `extraction.extracted_data` (`bank_statement.py:59-94`, ADR-059, no transactions table on this branch). So an AS-1 bookend cannot get its operands from the snapshot the evaluator reads. **Decision needed (LP-303/305):** either extend the snapshot/documents section to surface transactions (a snapshot change → re-run Stage-1), or give the AS-1 bookend a separate transaction-input path that reads extraction JSON. This is the biggest thing to resolve before the AS-1 slice.
- **Finding model ready?** No — the four-state output + `subject_key` (per-deposit) identity + uniqueness + event-log are net-new (LP-306), and AS-1's per-deposit `subject_key` (deposit = account+date+amount, per §8) is exactly the case that needs the new identity column.

## Open questions / risks for Phase A

1. **AS-1 input path (highest):** transactions absent from the snapshot. Surface them in the snapshot (clean, but a Stage-1 schema change + re-run) vs. a bookend-only extraction-JSON reader (contains the change but breaks "the evaluator reads only the snapshot"). Owner: LP-303 spec + LP-305 bookend.
2. **Finding persistence is net-new schema** (subject_key column, `(loan_file_id, rule_id, subject_key)` UNIQUE, append-only event log, four-state column) and the reconcile DROP currently *hides* `no-longer-applies`. Extend the `Finding` table vs. a parallel Stage-2 table — LP-306 call.
3. **Subject enumeration** (§3C open item): does the AI enumerate per-deposit subjects, or does the pipeline pre-enumerate and call per `(rule, subject)`? Affects `subject_key` stability + cost. Undecided in the docs — LP-304/306.
4. **No AI timeout** (`client.py`): a per-rule snapshot can be large; add a timeout for the evaluator or risk a hung call.
5. **Truncation → zero findings:** reuse the `stop_reason=="max_tokens"` guard (or the extraction truncation-retry `run_extraction_completion`, `ai/extraction/model_call.py`) — a per-rule result must not silently vanish.
6. **Calculator↔`satisfies` drift:** the bookend and the calculators independently implement `<=`; keep the bookend on `satisfies` and treat the calculators as candidate-producers only.
7. **Priya-validation gate is data, not enforced:** `threshold_needs_signoff` is tracked (LP-301) but nothing blocks shipping yet — the orchestrator must consult `pending_threshold_signoff()`.

## Recommendations per Phase-A ticket

- **LP-303 (rule spec format):** author AS-1's spec as *data* matching the prompt placeholders in `docs/stage2-evaluator-prompts.md` (`criteria`, `applicability`, `required_inputs`, `reference_values`, `evidence_required`, `guideline_reference` + structured `operative_values`). **Decide the AS-1 transaction-input source here** (snapshot vs extraction JSON) — it shapes the spec's `required_inputs`.
- **LP-304 (evaluator):** clone the cross-source two-file split (`ai/cross_source.py` + `services/cross_source.py`). Static/file **spine** + kind **body** + spec + snapshot injected via the **user message** (avoid `.format()` on braces). Reuse `complete()` (add a timeout + `AIClientError` fallback), the `extract_json_object`/array-of-findings parser, the `stop_reason` truncation guard, deterministic context ordering, the injected-`Reasoner` test seam, and cost/`input_fingerprint` recording.
- **LP-305 (numeric bookend):** reuse `satisfies(Condition(op, value), observed)` as the re-verify compare. Pre-compute candidate figures deterministically, hand them into the prompt, re-run `satisfies` on the AI's surfaced operands; split disagreement (arithmetic slip → silently correct; input-selection → surface). Do **not** call the four calculators; mind `None`/operator drift.
- **LP-306 (finding output + four states):** **extend** the `Finding` table — add the four-state evaluation-outcome column, a real `subject_key` column + `(loan_file_id, rule_id, subject_key)` UNIQUE, and an append-only event-log table; change reconcile so `no-longer-applies` becomes a state, not a DROP. Reuse the `Verification` run, identity/normalize, and reconcile keep/add/carry-forward logic.
- **LP-307 (golden-file eval harness):** build-new under `tests/verification/eval/`; pair AS-1's spec + a `build_snapshot` fixture (seeded LF-6T3N-shaped) → expected finding; index cases off `load_rule_kinds()`; mirror `test_e2e.py` for determinism and `stage1_artifact.py` for the real-file runner. Build it **with** AS-1, not after (probabilistic AI needs a day-one regression guard).
