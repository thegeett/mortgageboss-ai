- **Ticket:** LP-822 · Phase 4, M1, ticket 5 of 26
- **Status:** Built — awaiting review. **Priya's real emails are outstanding**, and the progress row
  says to ship the mechanism with a neutral default and fill it in later. That is what this is.
- **Date:** 2026-09-06
- **Plan:** [`phase4-build-plan.md`](../phases/phase4-build-plan.md) LP-822 section
- **Scope:** `models/style_profile.py` (new), `services/style_profile.py` (new), one migration,

- **Migration:** `e4a1c7d90b3f` — creates `style_profiles` and its readonly view.

The plan does not describe this ticket as adding a field. It describes it as resolving a
**conflict**: spec 4.1 wants drafts to sound like the processor, and LP-810 scopes the per-draft
fact bundle to "the requested needs plus borrower name and file basics — nothing else", on bug-008's
lesson that a wide bundle reworded every draft whenever anything in it changed.

---

## What was done

### Two caches, keyed apart

Voice belongs to a **person** and moves when they edit it. Facts belong to a **draft** and move when
the file does. `style_profiles` is keyed on `user_id` and carries no loan-file reference at all;
`ResolvedStyle.fingerprint` is the key LP-810 caches style on, separate from whatever it keys its
fact bundle on.

That separation is the ticket. Keyed together — which is what widening the fact bundle would amount
to — editing a signature block invalidates every draft's content, and a new document on a file
re-derives a voice that did not move. bug-008 again, by another route.

The fingerprint hashes **content**, not `updated_at`: a save that changed nothing must not
invalidate a cache, and two people who write identically share one entry. `is_default` is excluded
from it — it labels the voice for a UI, it is not part of the voice.

### The neutral default

`NEUTRAL_STYLE`, returned by `resolve_style` when a user has no profile. `resolve_style` returns a
value object rather than `StyleProfile | None` so no caller branches and nobody can send with a
half-populated voice.

`is_default` is carried on it deliberately. The spec's failure mode is that the drafter writes in
generic assistant voice, the processor rewrites every email, and an AI drafter whose output is
always rewritten is slower than a template. That failure is **silent** unless something can say
which voice was used — this is the one bit that can.

### Exemplar containment

This is the part I would not have built if the plan had not said where the exemplars come from. The
spec's collection list asks Priya for *"examples of her current borrower-request emails (templates
and **actual sends**)"*.

An actual send names a borrower, their address, and what they owe. An exemplar is put in front of
the model on **every** draft, for **every** borrower — so one borrower's details stored here can
surface in another borrower's email, and no prompt instruction reliably prevents it.

`validate_exemplars` refuses four identifier shapes (SSN, email address, phone number, 8+ digit
account or loan number), a length cap of 1200 characters, and more than three exemplars. It runs
**before** any write.

**It is a tripwire, not a guarantee**, and the code says so twice because the difference matters: it
matches shapes, and a borrower's *name* — the likeliest thing left in a pasted email — has no shape.
The control that actually holds is that whoever enters an exemplar redacts it first. The refusal
message names what it found but never quotes it: the message travels into logs, and an error about
a leaked identifier should not be the thing that leaks it.

## Decisions

### No `company_id`

The row hangs off exactly one user, and a user carries their company, so scoping is transitive —
ADR-052's reasoning for file-owned children applied to a user-owned row. A copy here would be a
second answer to "which company is this?" that drifts when a person moves, for a column no query
needs: every read is "the profile for this authenticated user".

No new ADR. This applies existing reasoning rather than deciding something new, and the migration
carries the argument where a reader will meet it.

### Not soft-deletable

One row per user. The way to stop using a profile is to clear it or delete it; a soft-deleted
profile would leave the drafter choosing between a tombstone and the default, and the safe answer to
"no profile" is already the default.

### The readonly view drops every free-text column — and does not count the exemplars

`greeting`, `closing` and `signature_block` are hand-typed, which is where an identifier arrives in
a form no scrubber predicts — the same reason `dti_custom_lines.label` is excluded. `exemplars` is
stronger than that and is listed in `NEVER_EXPOSED`, not merely `EXCLUDED`: what it most likely
still carries is a person's name, and a name is not digit-shaped, so it would cross a scrubbing view
intact.

**The cost is real and was paid deliberately.** `cardinality(exemplars) AS exemplar_count` answers a
genuinely useful operational question, and `NEVER_EXPOSED` asserts over the view *text* that the
column is never named in any select list — crude on purpose, because a per-column exposure check can
be satisfied by a column appearing in a predicate about itself. So the count went rather than the
guarantee. If the number is ever needed it belongs in a maintained column carrying no content.

## Tests

`tests/services/test_style_profile_lp822.py`, 21 tests.

The fingerprint pair is the one that matters: editing a voice moves the key, and an unchanged voice
does not. Plus a case that would otherwise be invisible —
`test_the_key_separates_fields_rather_than_concatenating_them`. Without a separator, greeting `"AB"`
+ closing `"C"` and greeting `"A"` + closing `"BC"` hash identically, so **one processor's drafts
would be written in another's voice** with nothing anywhere to show it.

Verified by mutation, each confirmed applied before the run was believed:

| Mutation | Result |
|---|---|
| fingerprint concatenates without a separator | 1 test fails |
| `set_style_profile` skips validation | 1 test fails |
| a saved profile still reports `is_default` | 1 test fails |
| loan-number threshold widened to 4 digits | 2 tests fail |
| loan-number threshold widened to 7 digits | 1 test fails |
| loan-number rule removed entirely | 2 tests fail |

### A control that did not control, and how it was found

The first version of `test_ordinary_prose_about_tone_is_not_refused` used `"$12,500.00"` and its
docstring claimed to pin the 8-digit threshold. It did not: the commas break the digit run, so
widening the rule to four digits left the test **green**. The mutant survived, which is the only
reason it was found.

Fixed by putting numbers in the control that a narrower rule would actually reject — an unseparated
amount, a tax year, a form number — and adding an explicit boundary test at 7 and 8 digits, both
sides. A control has to contain the thing it says it protects.

Two of the mutation runs in that first round also failed to apply at all, through shell quoting, and
reported a clean suite. Those greens meant nothing. Every mutation above now prints the before and
after line and asserts it changed.

## Assumptions

- **Priya's emails have not been collected.** Every field is populated from a neutral default, and
  nothing in this ticket claims to sound like anyone. LP-810 is where the profile is read; until
  someone fills one in, `is_default` will be `True` for every user and every draft is in generic
  voice — which is the spec's stated failure mode, now at least visible.
- **The greeting uses `$borrower_first_name`** and the signature `$processor_name`, matching
  LP-817's placeholder convention so one substitution pass covers both. Nothing yet performs that
  pass over a style profile; LP-810 does.
- **8 consecutive digits is the account-number line.** Seven is still a plausible figure in prose;
  eight is not something anyone writes about tone. Calibrated, and the boundary is tested on both
  sides rather than asserted.

---

## Deliberately not done

- **No API and no UI.** The plan says ship the mechanism; the settings screen that lets Priya enter
  her voice is not specified in any ticket I can see, and LP-812's compose flow is the nearest
  candidate. **This is worth a decision:** the mechanism has no way to be populated except by a
  script or a later ticket, and until one exists `is_default` is `True` everywhere.
- **No AI-assisted profile extraction.** Deriving a voice from her sent mail is a plausible future
  feature and a much larger surface — it would mean ingesting exactly the unredacted material this
  ticket refuses to store.
- **No per-company default voice.** A company-wide house style is plausible; nothing asks for it,
  and the resolution chain would need a decision about precedence.
- **No exemplar redaction tooling.** The tripwire refuses the obvious shapes; actually redacting a
  pasted email is a person's job and I did not want to ship something that looks like it does it.

## For the reviewer

The three standing reviewer checks:

- **Tenancy** — no `company_id` in this diff at all, by the decision above. Nothing here is
  reachable from an email address; `resolve_style` takes a `user_id` the caller already
  authenticated. LP-805 remains the only resolver.
- **Message content in logs** — no logging added. Actively relevant here: `InvalidExemplar`'s
  message is the one string in this ticket that could carry borrower content, and a test asserts it
  does not quote what it matched.
- **AI in the decision path** — none. This ticket produces the words a model is *given*, and decides
  nothing.

The judgement calls worth a second opinion, in the order I would attack them:

1. **The exemplar guard's honesty.** I believe the tripwire framing is correct and I have said so in
   three places — but the risk is that a future reader treats "validated" as "safe" and pastes a real
   send. If you think the guard is more likely to create false confidence than to catch anything, the
   argument for dropping it and relying only on the documented redaction rule is real.
2. **Dropping `exemplar_count` from the readonly view.** I chose the guarantee over the metric. The
   counter-argument is that `NEVER_EXPOSED`'s text-matching is crude and the right fix is to make the
   check smarter rather than to remove a useful column from a view.
3. **`is_default` on `ResolvedStyle`.** It has no reader today, which is the failure mode I have
   flagged in two previous tickets. I argue it earns its place because the spec's failure mode is
   silent without it — but it is the same shape as things I have declined to build before, and you
   may hold me to that.

**LP-822 has no "Done when" clause** — the third, after LP-802 and LP-817. Judged against the
section prose: the two caches are separated, the profile is keyed on `user_id`, it holds a signature

## Review (second session, protocol §3)

Four findings, two of them about the migration — which is where the ticket asked for eyes, and
rightly, because CI does not run migrations at all. The design is right: two caches keyed apart is
the correct resolution of the spec-vs-bug-008 conflict, and `fingerprint` over content rather than
`updated_at` is the detail that makes it work.

### A — The model was invisible to Alembic, and autogenerate would have proposed dropping its table

`StyleProfile` was not imported by `app/models/__init__.py`. `alembic/env.py` does
`from app.models import Base` and sets `target_metadata = Base.metadata`, so autogenerate compares
the live database against whatever that package imports.

Measured, not inferred: after `import app.models`, `Base.metadata` held **42 tables and
`style_profiles` was not among them**. Autogenerate would therefore have seen a table in the
database with no model behind it and written a migration to **drop it** — a table created one
commit earlier. That is the kind of diff someone accepts without reading closely.

The suite could not have caught it. `tests/conftest.py` builds the schema with
`Base.metadata.create_all`, not migrations, and the LP-822 tests import the model directly, so the
table existed for exactly the tests that needed it and for nothing else.

**The gap was a class, not an instance.** Adding the guard test found three more models in the same
state, all pre-existing and all with real tables: `FindingProse` (`finding_prose`, LP-527),
`StatedHousingExpense` (`stated_housing_expenses`, LP-627) and `StatedOwnedProperty`
(`stated_owned_properties`, LP-596) — the last of which the rental-treatment service reads on every
refinance. `stated_financials.py` was exporting four of its six models. All four are now exported
and `Base.metadata` holds 44 tables. Fixing only LP-822's instance would have left the guard failing
and two live drop candidates in place.

`test_every_model_module_is_reachable_from_app_models` pins it, and fails if any export is removed.

### B — The new readonly view had nothing that ever ran it

`EXCLUDED` and `NEVER_EXPOSED` match against the migration's **text**, which catches a column that
should not be exposed but cannot catch a view that does not compile. A mistyped column name in
`_VIEW` passes every check in the suite and fails at `alembic upgrade head` on deploy — which, on
this branch, is the failure mode that already cost a staging deploy once.

The repo already had the pattern: `readonly.saved_views` (LP-UI-015) is executed against the real
test database for exactly this reason. LP-822's view was not.
`test_the_style_profiles_view_is_valid_sql` now creates it and asserts both that it compiles and
that it exposes only `{id, user_id, has_signature_block, created_at, updated_at}`. Verified by
mutation: typing `signatur_block` into the view fails the test rather than the deploy.

### C — Two indexes on one column

`unique=True, index=True` on `user_id`, plus `op.create_index` in the migration. PostgreSQL
implements a UNIQUE constraint with a unique btree index, so the second, non-unique index is a write
on every insert and update and serves no query the first cannot. Dropped from both the model and the
migration. (Asserted from PostgreSQL's documented behaviour rather than measured against a live
table — the test database is built by `create_all`, so it has no migration-created indexes to count.)

### D — A comment describing a column the view does not have

The `EXCLUDED` entry said the view answers "how many exemplars they gave". It does not, and the
migration's own docstring explains at length why the count was dropped rather than kept. Two
statements about the same decision, disagreeing, six lines apart in files a reader consults together.
Corrected to say what the view actually answers, and why.

### The builder's three, ruled on

1. **The exemplar guard — KEEP IT, and I would not drop it.** The question asked was whether it
   creates more false confidence than it catches. It does not, for a reason worth stating: its scope
   is exactly right. Every shape it matches is an identifier *wherever it appears*, so refusing one
   cannot turn away a legitimate sentence about tone — the guard cannot be over-wide, which is the
   usual way a tripwire earns its keep and then quietly costs more than it saves. Against that, the
   false-confidence risk is real but it is a documentation problem, and the ticket already treats it
   as one: "tripwire, not a guarantee" appears in the model, the service and the error message, and
   the error message names redaction as the control. Dropping it would mean a pasted SSN or email
   address is stored. Four shapes caught beats none.
   One thing the ticket did not say, now said in the model: the guard deliberately does **not** run
   over `signature_block`, because a signature block is supposed to carry a phone number and an
   email address — the processor's own. A future reader "fixing" that asymmetry would refuse every
   real signature.
2. **The readonly view and the exemplar count — endorsed.** The guarantee is worth more than the
   metric, and the reasoning generalises: a count is an expression over a column, and a text-based
   never-expose check cannot tell an expression from a projection. If the number is wanted later it
   belongs in a maintained column carrying no content, exactly as the docstring says.
3. **`is_default` — not special pleading, and it passes the earlier standard.** What I objected to
   in LP-800 and LP-817 was a *second spelling of one fact*: a `requestable` field on a schema would
   have duplicated a predicate the server already computes, and two spellings drift. `is_default` is
   not a duplicate — it is the same function reporting which branch it took, on the value object it
   returns. Without it the only way to ask "is this her voice or the default?" is to compare against
   `NEUTRAL_STYLE`, which IS the second spelling. It prevents the failure it looks like an instance
   of.

**No new ADR — agreed.** No `company_id` on a user-owned row is ADR-052's reasoning applied, not a
new decision, and the migration docstring records it where someone reading the table will find it.

### Done when, and the standing checks

**LP-822 has no "Done when" clause** — the third, after LP-802 and LP-817. Judged against the section
prose as the builder did: the style profile is keyed on `user_id`, cached independently of the
per-draft fact bundle so editing style invalidates style and not content, and a neutral default ships
so the mechanism works before Priya's exemplars exist. All met. The Phase 0 input the section names
is still outstanding and is recorded in the escalations table.

The three standing checks pass. Tenancy is the one worth spelling out: this row has no `company_id`
and derives none — it is keyed on a user, reached only as "the profile for this authenticated user",
and nothing here starts from an email address. LP-805's resolver remains the only place that
inverts the invariant. No logging in either new module, so no message content. No AI: `resolve_style`
is a select and `fingerprint` is a hash.
