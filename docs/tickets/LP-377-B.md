# LP-377-B — The subject label: a finding names the document, not a hash

## WHAT THIS TICKET IS

A governed finding's row identity was a content-id: `subject_key = doc067c28e496b10b5f`, a `txn…`, a borrower
UUID, or `"loan"`; the provenance card rendered `Subject id: 59e173ce-…`. A processor reads *"a document in
the file could not be classified"* — over 30 documents, WHICH one? **The finding model knows exactly which; it
just never said.** Two prior tickets reported this wall and stopped at it:

- LP-376-C: *"the FILENAME is not reachable — `subject_key` is a content-id; no doc index at the reason site.
  I did NOT plumb it."*
- LP-375: *"a legible subject label needs per-family logic — not uniformly derivable from the stored data."*

**This ticket goes through the wall.** It affects EVERY per-subject finding (ID-7/ID-9's untyped documents,
ID-4's "other document", AS-1's deposits, the provenance card) — and it still matters after LP-377-A (the
classifier gap): there will always be documents the classifier cannot type, and *"a document"* over 200 is
useless forever.

## ACCEPTANCE CRITERIA (met)

- Every per-subject finding shows a human subject label (a filename / amount / borrower / "Loan-level"),
  declared per subject TYPE, dispatched on the key's shape — **no rule-id branch**.
- The provenance card's `Subject id: <uuid>` becomes the label; a processor never sees the hash.
- An unresolvable subject (a removed / `no_longer_applies` document) reads honestly — **never a hash**.
- Expanding a collapsed group (LP-376-C) shows WHICH documents (each member's label).
- No verdict / outcome / tab / count changes; `ACTIVE_RULE_IDS` unchanged; the legacy list identical. Backend
  suite **2407 passed**, frontend **299 passed**; ruff + mypy + biome + tsc clean.

## PHASE 0 — THE ARGUMENT

### Is the filename in the snapshot? **No — this decided the design.**
`DocumentEntry` carries `content_id` / `document_type` / `belongs_to` (borrower refs **with names**) /
extraction `fields` — but **not `original_filename`.** The evaluator holds only the snapshot and is DB-free,
so **option (a) — naming the document in the evaluator's reason — is impossible** without plumbing a filename
through the whole tag/rule pipeline. The filename lives only in DB `Document.original_filename`.

### What AS-1's `$20,000` does today (checked, and generalised — not duplicated).
It was a **frontend** derivation (`ruleSubjectChip` reading the `txn.amount` load-bearing tag). It works only
because the amount is load-bearing; it returns `null` for documents (no filename in the tags) and the card
still showed the raw hash. **I generalised it into ONE backend mechanism (`subject_label`) and retired the
frontend chip** — the ticket's "don't build a second mechanism beside a working one."

### D1 — the label resolves in the READ PATH (option b).
`_build_status` has DB access and the finding's `subject_key`. `RuleFindingPublic` gains a `subject_label`,
resolved once per finding with the file's borrower + document maps. Fixes the **row AND the card in one
place**, for **all findings old and new**, with **nothing persisted**.

### D2 — declared per SUBJECT TYPE, dispatched on the key's SHAPE (no rule-id branch).

| subject | key shape | label | source | reachable? |
|---|---|---|---|---|
| loan | `"loan"` | "Loan-level" | literal | ✓ |
| transaction | `txn…` | "Deposit of $20,000 on 3/27" | inline `txn.amount`/`txn.date` tags | ✓ |
| document | `doc…` | the filename | the content-id bridge (below) | ✓ |
| borrower | a UUID | "Dana Sample" | DB borrowers (id→name) | ✓ |
| account | `account:…` | "a bank account" | honest generic (no active per_account rule) | ✓ |

`declared-key-resolved-by-registry` again (the pattern has held ~13 times). **The document bridge:**
`build_documents_section` iterates the DB documents and `assign_content_ids(DOC_PREFIX, …)` aligned, so
`{content_id → filename}` is a `zip`. The content-id derivation is **shared, never duplicated**
(`_reshape_and_assign_ids` — `build_documents_section` and the map build from it, so the ids match the
findings' subject_keys; a duplicate would drift and silently resolve to nothing). Built only when a governed
finding actually has a `doc…` subject.

### D3 — the honest fallback, never a hash.
A content-id rebuilt from the CURRENT documents won't contain a removed / re-extracted document's id (a Tab-3
`no_longer_applies` finding's subject is gone by definition) → *"a document no longer in this file"*; a
borrower who left → *"a borrower no longer on this file"*. Never fabricate a name, never print the id.

### D4 — PII posture: read-time, not persisted.
A filename can carry a borrower's name (`Bansari_Patel_W2.pdf`). Read-time resolution means it is **never
written into the finding row** — consistent with the existing posture (borrower names already appear in
read-time finding messages; `BorrowerRef.name` is in the snapshot). This is the argument FOR option (b).

## WHAT WAS BUILT

- `app/services/rule_subject_label.py` — `resolve_subject_label(subject_key, load_bearing_tags, *,
  borrower_names, document_filenames)`: the declared per-subject-type labeler (dispatch on key shape).
- `app/verification/snapshot/documents_section.py` — `_reshape_and_assign_ids` (extracted shared primitive) +
  `document_filenames_by_content_id` (the read-time `{content_id → filename}` map).
- `app/schemas/verification.py` — `RuleFindingPublic.subject_label`; `from_model(…, subject_label=None)` (a
  maps-free fallback when a unit caller resolves no maps; `_build_status` passes the DB-resolved label).
- `app/api/verification.py` — `_borrower_names` + the (gated) document-filename map in `_build_status`,
  resolving each governed finding's label.
- Frontend — `RuleFinding.subject_label`; the row chip + provenance card render it; `ruleSubjectChip` retired.

## TESTS

- `test_rule_subject_label.py` — per subject type (loan/deposit/document/borrower/account); the honest
  fallback (gone document/borrower → no hash); **the guard**: no label contains a content-id, a UUID, or a
  dotted tag id (a filename extension is stripped first so `statement.pdf` isn't mistaken for `id.dob`).
- Endpoint (`test_verification_endpoints.py`) — loan → "Loan-level"; borrower UUID → the name; a per-document
  finding → the filename **through the content-id bridge, end-to-end** (`subject_key` untouched, no hash in
  the label); a gone document → the honest fallback.
- Frontend — the row renders `subject_label` and never the raw `subject_key`; the card names the document; a
  collapsed group expands to WHICH documents (each member's label).
- **Equivalence:** no verdict/outcome/tab/count changed — labels only.

## ASSUMPTIONS / DECISIONS + WHAT'S STILL OPEN

- **`subject_key` stays the reconciler's key** (LP-322) and is unchanged; only the card stops rendering it.
  The label is cosmetic; the key is identity.
- **Cost (reported):** resolving document labels rebuilds the documents section at read time — the only honest
  way to recover a content-id → filename (the id is a content hash). Gated on a `doc…` subject being present.
- **NEW gap (reported):** the `account:…` subject reads a generic "a bank account" — no ACTIVE rule enumerates
  per_account yet, so a richer label (e.g. "Chase …1234") is deferred until one does. Every other active
  subject type resolves to a specific label.
- **The classifier gap (LP-377-A)** is unchanged and out of scope — but this ticket makes its symptom
  actionable: an untyped document now reads by its filename, so a processor can find and classify it.
