# LP-835 — Writing to the other parties, from the mailbox

- **Ticket:** LP-835 · Phase 4 follow-up, from processor feedback
- **Status:** Built — awaiting review
- **Date:** 2026-09-07
- **Scope:** the Communication page, a party modal, `services/party_requests.py`
- **Migration:** none expected

---

## What was asked

> *"For other parties email add new button on communcation on click new model comes where user can
> add those. You can use your suggestion on it."*

## The escalated defect this has to close

LP-820 built party requests: title, agent, lender, CPA, insurer, employer, each drafted from the same
template under its own key. LP-829's review found what happens next.

`get_open_draft` filters on the **borrower** template key, so the outbound panel never returns a party
draft. And the party panel's success message says **"Send it from the document request above"** —
where the draft above is the borrower's. A processor who follows that instruction emails the
**borrower**, believing they contacted the title company.

So a party draft is built today and **no screen can send it**. Any button added here that does not
end in a sendable draft repeats that.

## The suggestion, since one was asked for

**A party is an address on the file, and the modal should be about the address, not about the email.**
LP-820 made `loan_file_participants` the address book, and of 166 document types **13 across title,
agent, CPA, insurer and employer had no address anywhere in the schema**. That is the actual blocker:
not "no way to compose", but "nobody to send to".

So the modal does two things in one place, in this order:

1. **Who.** Pick the role, give a name and an email. Existing participants are listed and reusable —
   a title company on this file should be typed once, not once per request.
2. **What.** The documents that party is responsible for, from LP-800's catalog, filtered to that
   party. A processor should not have to know that a verification of deposit goes to the bank.

Then "Create draft", and the draft lands in the **same list** LP-831 builds, alongside the borrower's,
and is sent the same way. One list, one modal, one send path — which is what makes the escalated
defect impossible rather than fixed.

**The address book stays per file** (the known limitation from LP-820: a title company used on thirty
files is typed thirty times). Making it per company is a real feature and a bigger one; doing it here
would hide this ticket inside it.

## Done when

- A button on the Communication page opens a modal to add or choose a party and compose to them.
- The resulting draft is in the drafts list and **can be sent**. This is the escalated LP-820 defect;
  it closes here.
- The party panel's message no longer tells a processor to send from the borrower's draft. That
  sentence is currently false in a way that mails the wrong person.
- Existing participants on the file are offered rather than retyped.
- The document choices are filtered to that party's responsible types, and a party with **no**
  catalogued types still gets a draft — the ask is typed by hand, which is what a processor does
  today anyway.
- LP-829's review fix holds: a party draft's greeting resolves to the generic form, not to the
  borrower's first name. Four surfaces have now put that defect back; this is a fifth.

## For the reviewer

Check the send path, not the compose path. A modal that produces a party draft is easy; a party draft
that reaches the right mailbox through the same guards as a borrower draft — suppression list, rate
limit, approver — is the thing that has already failed once here.

## Built, 2026-09-09

### The sentence was as much the defect as the missing button

`party-requests-panel.tsx` said, on success: **"Send it from the document request above."** The draft
above is the **borrower's**. A processor following that instruction emailed the borrower believing
they had contacted the title company — and the drafts themselves have existed since LP-820, so this
was a live wrong-mailbox path rather than a gap.

It now says the draft is in this file's drafts, which since LP-831 is where every draft is reachable
and sendable regardless of which template rendered it. **Asserted as a literal**, so a revert reads
as a failure rather than as a rewording nobody notices.

### Address first, documents second — which is a measurement, not a preference

LP-820 counted: of 166 document types, **13 across title, agent, CPA, insurer and employer had no
address anywhere in the schema**. The blocker was never "no way to compose", it was "nobody to send
to". So the modal leads with who, and a party with no address shows what is stuck rather than
disappearing.

**An unreachable party still shows what it is owed.** A screen showing only what it can send renders
a stuck file as having nothing to do, which is the failure LP-820 named and this could easily have
reintroduced by hiding the row.

### What a party is owed is derived, never typed

`open_requests` groups the file's outstanding needs by LP-800's responsible party, so a processor
does not have to know that a verification of deposit goes to the bank. A party with nothing
outstanding is not offered, because there would be nothing to ask for.

**The borrower is filtered out.** Their requests are the file's own draft, which the mailbox already
carries; offering them here would be a second route to the same email.

### The question this ticket had to answer before a party could hold a link

Raised at review of LP-834: a party draft is addressed to somebody who is not the borrower, so if it
can carry a secure upload link — **whose file does that link open, and can the title company see what
the borrower uploaded?**

Measured on the endpoint rather than read off the schema. `GET /upload/{token}` returns exactly
`{reference, purpose, max_bytes, remaining_uses}` and nothing else: no name, no address, no needs
list, no documents. The reference is the file's display id. **The page is write-only by
construction**, so a credential meant for sending a title commitment cannot read a borrower's file.

Pinned as an exact key set, so a field added later has to be a decision. The holder of that token is
whoever the email reached, which after a forward is more people than the borrower.

### Mutations

| mutation | result |
|---|---|
| the old "document request above" sentence restored | 1 failed |
| the borrower offered as another party | 2 failed |
| an unreachable party's needs hidden | 1 failed |

### A panel became a modal, and the panel is deleted

It was an always-open panel with an inline address form per party. It is one button and a dialog now
— an occasional act on a mailbox rather than a permanent fixture of one. Mounted only while open, so
its `usePartyRequests` query does not run on every visit to the page.

### Not done here, and recorded rather than assumed

**A party draft cannot yet carry a secure upload link.** LP-834's control is gated on `is_editable`
and a party draft satisfies it, so the button appears — but `attach_upload_link` mints a link with no
`recipient_email` or `purpose`, and for a party those are exactly the fields that would say who the
credential was for. A document arriving through it would be recorded as `SECURE_LINK` with no actor
and nothing distinguishing the title company's upload from the borrower's.

That is a provenance gap rather than an exposure one — the check above shows the link exposes
nothing — and closing it means passing the party's address and purpose through. Its own ticket.

### The three standing checks

**Tenancy:** unchanged — every call goes through the existing `ScopedLoanFile`-gated party endpoints.
**Logging:** nothing added. **AI:** none.
