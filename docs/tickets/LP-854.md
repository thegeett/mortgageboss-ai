# LP-854 — the toolbar Gmail has

Status: spec. **Blocked by LP-853.** Screen 2.

Epic: [`docs/domain/communication/v1-epic.md`](../domain/communication/v1-epic.md) · Screens: [`v1-screens.md`](../domain/communication/v1-screens.md) · Spec: [`comm-v1-draft-only-spec.md`](../domain/communication/comm-v1-draft-only-spec.md)

## The report

> "I did not like current rich text area, It just has Bold and Bullet option. Check how many Gmail
> provide while compose, and make it like that."

## Gmail's bar, button by button

| Gmail has | Take | Why |
|---|---|---|
| Undo · Redo | **yes** | Table stakes anywhere people type paragraphs. Tiptap ships `History`. |
| Font family | **no** | A document request in Comic Sans is a real outcome, and the font does not survive `mailto:` or a paste into a themed client anyway. The reader's own default is the right font. |
| Text size (S/M/L/Huge) | **no** | Harmless and unused in a business letter. Cheap to add later if anyone asks. |
| **Bold** · **Italic** | have them | LP-849. |
| **Underline** | **yes** | New. Survives a paste into Outlook and Gmail. |
| Text colour · highlight | **no** | **Colour means status in the Ledger.** A processor colouring a sentence red inside a compliance record is a claim nobody intended, and it is the one addition that could contradict a status glyph sitting two inches away. |
| Align left / centre / right | **no** | Centred body text in a letter is a formatting accident. Keeping the button out is cheaper than repairing the output. |
| **Numbered list** | **yes** | "Send these three, in this order" is a thing processors write. |
| Bulleted list | have it | LP-849. |
| **Indent more / less** | **yes** | It is how LP-846's nested detail block is built. The structure is already in the output; give it a button. |
| **Quote** | **yes** | Quoting the borrower's own sentence back is common, and the Ledger already reserves Plex Serif italic for verbatim quotation — so the mark has a meaning here, not just a style. |
| **Link** | **yes** | Gmail keeps it in the footer rather than the format bar. Most-wanted, and absent from the schema today. |
| **Remove formatting** | **yes** | The repair tool for everything pasted in from elsewhere. Without it a bad paste is unfixable and the processor retypes the message. |

Net: **seven added, three declined.** Declining three is the argument, not an omission — record it
so the next person does not re-litigate it from the screenshot.

## The schema and the sanitiser are the same list

Tiptap extensions, LP-853's server allowlist and `emailBodyToHtml`'s output must name the **same
tags**. LP-849's own notes record formatting vanishing on save when two of the three drifted:
`htmlToEmailBody` stripped `**` from any `<strong>` ending in a colon while the renderer re-bolded
only a capitalised run of 3–41 characters, and everything in the gap lost its asterisks.

**Derive the list once and import it into all three places.** Not three copies that agree today.

## Links are the one element with a security dimension

A link in an email to a borrower is a phishing surface if we let it be. `href` accepts `http`,
`https` and `mailto` only — enforced in the editor **and** in LP-853's sanitiser, because the editor
is not a security boundary. Display text defaults to the URL; a link whose text is a *different*
URL is the classic deception and should be left alone rather than cleverly rewritten.

## What it must not break

- **No classes, no inline styles, no stylesheet dependency in the output.** Outlook desktop renders
  with Word's engine. Every new mark must be a tag Word keeps: `<u>`, `<ol>`, `<li>`,
  `<blockquote>`, `<a href>`.
- LP-844's `text/html` + `text/plain` clipboard pairing.
- **No markup visible to the processor, anywhere.** LP-849's requirement: a `**` on screen is a
  failure, and so is a raw `<a href>`.

## Measurement

The communication route was **195 kB first-load** at LP-849. Re-measure and state the new number in
the PR — `Link`, `Underline`, `OrderedList` and `Blockquote` are small, `History` is not free, and
the number is only meaningful if somebody keeps writing it down.

## Acceptance

1. Each of the seven marks round-trips: apply → save → reopen → still there, and the stored HTML
   contains only allowlisted tags.
2. Paste a styled block from Word or a web page → **Remove formatting** returns it to plain
   paragraphs with no residue.
3. A `javascript:` href is rejected by the editor **and**, sent directly to the API, by the
   sanitiser.
4. Copy a message using all seven and paste into Gmail and Outlook on the web: bold, italic,
   underline, both list types, indent, quote and the link all survive. **Manual, and recorded.**
5. No markup is visible in the editor at any point.

# What was built

Status: **done**, except acceptance 4, which is manual and is **not claimed** — see below.

## Seven added, three declined, one the ticket thought we already had

| | tag | notes |
|---|---|---|
| Undo · Redo | — | `UndoRedo` from `@tiptap/extensions`. A history stack, not a tag. |
| **Italic** | `em` | **New.** LP-854's table lists it under "have them | LP-849" and that is wrong: `EXTENSIONS` had no `Italic` and `emailBodyToHtml` emits no `<em>`. Screen 2's bar reads `B I U`, so it ships here. |
| Underline | `u` | |
| Numbered list | `ol` | Reuses `li`; an ordered list is a different container, not a different item. |
| Indent / outdent | — | List nesting (`sinkListItem` / `liftListItem`). The only indentation that survives a paste, because it comes from a tag rather than a margin — and it is how LP-846's detail block is built. |
| Quote | `blockquote` | |
| Link | `a href` | The one tag with an attribute, and the one with a security dimension. |
| Remove formatting | — | `unsetAllMarks()` **and** `clearNodes()`. A pasted quote or list is a node and survives the first alone. |

Declined, with the reasons in the toolbar's own comment so nobody re-litigates them from a
screenshot: **font family**, **text colour / highlight** (colour means status in the Ledger — a red
sentence inside a compliance record is a claim nobody intended, and the one addition that could
contradict a status glyph two inches away), and **alignment**.

## "Derive the list once" — made true rather than asserted

`frontend/lib/markdown/schema.ts` is the one place the tag set is written down. Python cannot import
TypeScript, so the agreement is a test: **`schema-drift.test.ts` parses `ALLOWED` out of
`sanitise.py`** and compares tags, attributes and link schemes against `EMAIL_SCHEMA`, plus the
Tiptap extension set and the renderer's output.

The relation is deliberately not the same for all three:

- Tiptap extensions **== the schema**. A mark the editor makes and the sanitiser strips is
  formatting that vanishes on save (LP-849's notes record exactly that); a tag the sanitiser allows
  and the editor cannot make is a hole nothing watches.
- The server allowlist **== the schema**, for the same two reasons from the other side.
- `emailBodyToHtml`'s output **⊆ the schema**. The plain body format has no syntax for underline,
  links, ordered lists or quotes, so requiring the renderer to emit them would be requiring it to
  parse something no template writes. What must hold is that everything it *does* emit is allowed.

**The reviewer's challenge was that this is the kind of claim that is true of the code and false of
the tests.** So it is mutated, not asserted — each list changed alone, in the real files:

| mutant | result |
|---|---|
| a tag added to the **server allowlist** only | 1 fails |
| a tag added to the **schema** only | 3 fail |
| an extension removed from the **editor** only | 1 fails |

## Three things found by running it

1. **The extension scan could not see `@tiptap/extensions`.** LP-849's guard matched
   `@tiptap/extension-([a-z-]+)`, which does not match the bundle package — so `UndoRedo` was
   imported from a package the scan was blind to. Same shape as every other narrow-guard finding in
   this epic.
2. **The drift parser's tag pattern excluded digits.** `"([a-z]+)"` made a planted `h1` invisible —
   the exact tag an allowlist most needs to notice. Found by the planted case, not by reading.
3. **The Link extension emits `target="_blank" rel="noopener noreferrer nofollow"` by default**,
   which the server's allowlist strips. Harmless in itself and precisely the drift this ticket
   exists to prevent. Nulling them has to happen in `HTMLAttributes`; there are no `target`/`rel`
   options to set instead, which `tsc` confirms by refusing them.

Also changed while extending the allowlist: **a refused `href` now drops the `<a>` and keeps the
text.** The first version kept the tag and dropped the attribute, leaving `<a>click</a>` — something
that looks like a link, is styled like one in every mail client, and goes nowhere.

## Acceptance

| # | Criterion | Test |
|---|---|---|
| 1 | each mark round-trips; stored HTML has only allowlisted tags | `the seven marks round-trip` — apply → `getHTML()` → reload → assert, per mark, plus `produces ONLY tags the schema allows` and `test_each_new_mark_survives` server-side |
| 2 | a styled paste → Remove formatting → plain paragraphs, no residue | `Remove formatting` — asserts every tag is gone **and** every word survives; a "clear" that deleted the content would pass the first half alone |
| 3 | a `javascript:` href is refused by the editor **and** by the sanitiser | `a link's address` (8 hostile schemes + 4 legitimate as the control, plus the schema refusing a pasted one) and `test_a_refused_link_loses_the_TAG_not_just_the_href` |
| 4 | paste into real Gmail and Outlook | **NOT DONE — see below** |
| 5 | no markup visible in the editor | `no markup is visible to the processor` — asserts the text contains no `<` or `href`, and that the elements really are elements |

## Acceptance 4 is not done, and is not claimed

*"Copy a message using all seven and paste into Gmail and Outlook on the web… **Manual, and
recorded.**"* Nothing here has been pasted into a real mail client, and no test can stand in for it.

What is done instead is to make the manual pass cheap: `AT_RISK_IN_WORD` in `schema.ts` names the
four tags to look at and what to look for, so "check it survives" is a list rather than a feeling.

- `blockquote` — Word keeps the element and applies its own indent; expect indentation rather than a
  left rule, and check the text is not flattened into the paragraph above.
- nested `ul` / `ol` — the indentation *is* the nesting, so a composer that flattens one level loses
  LP-846's detail block.
- `u` — survives, but is also how several clients render a link; check an underlined word that is
  **not** a link does not become clickable.
- `a` — check the href survives intact and the display text is not rewritten.

`p`, `br`, `strong` and `em` are not on the list because they are the four every engine keeps.

## Measurement

The ticket asks for the first-load number, and the honest answer needs both halves:

| | LP-849 | LP-853 | LP-851 | LP-852 | **LP-854** |
|---|---|---|---|---|---|
| communication route, first load | 195 kB | 197 kB | 199 kB | 200 kB | **200 kB** |

**First-load did not move, and saying only that would hide the cost.** The editor is behind
`next/dynamic`, so the seven marks land in the chunk a processor downloads when they open a draft,
not in the page. Measured by building both extension sets and summing every chunk containing
ProseMirror:

- LP-849's extension set: **338,273 bytes**
- LP-854's: **394,066 bytes**
- **+55,793 bytes (+55.8 kB, +16.5%)** on the click that opens an editor.

That is what `History` not being free looks like. It is paid once per session on a click that
already waits for a modal, which is why `next/dynamic` was the right call at LP-849 and is what
makes this affordable now.

## What was not done

- **Acceptance 4**, above.
- **A link popover.** The Link button uses `window.prompt`. Screen 2 specifies a toolbar button and
  says nothing about the shape of the asking; a custom popover is a second focus trap inside a
  dialog, which is the class LP-UI-008's review found announcing itself wrongly to a screen reader.
  `promptForLink` is the function a designed popover replaces.
- **Text size.** The ticket marks it *optional* ("harmless and unused in a business letter"). Not
  built; it is the cheapest of the three to add later if anyone asks.

# Review (second session)

Reviewed at `cb75d2d8`. Findings measured; fixes mutation-checked.

## Fixed

**`href_is_safe` answered about a string the browser never sees.** It removed every character that
is not `isprintable()` or that `isspace()` — far wider than the URL parser's rule, taking a
zero-width space, a non-breaking space and a BOM, none of which a browser removes.

Over-stripping cannot let a dangerous scheme through: deleting characters from `javascript:` still
spells `javascript`. It does the opposite. `h​ttp://x.com` cleaned to `http`, passed as safe,
and was **stored with the invisible intact** — and no browser resolves that as http, so what reached
the borrower was a link to nowhere that this function had called safe. Measured on three such hrefs
before the fix.

WHATWG strips leading and trailing C0 controls and space, and removes tab, CR and LF anywhere. That
is the whole list, and it is what makes `java<TAB>script:` run. The rule matches it now: strictly
narrower than before — every href refused before is refused still, asserted with a positive control
— and it removes the only measured divergence from `isSafeHref`.

**`AT_RISK_IN_WORD` was not derived from anything**, which I found by mutating the wrong list:
renaming a tag there changed nothing, because no test read it. It is guidance rather than a schema,
which is fine until the schema moves without it — a stale entry sends the person doing the manual
paste hunting for a tag the renderer can no longer produce, and a dropped one is a tag they will not
think to check. Every at-risk tag must now be a tag the schema emits. The reverse is deliberately
not asserted: `p`, `br`, `strong` and `em` are excluded because every engine keeps them.

## Checked and correct

- **The bundle measurement stands, and the worry about it was unfounded.** The three chunks matching
  ProseMirror reproduce the 394,066 figure exactly, and **none of them appears in
  `app-build-manifest.json`** — which lists 65 chunks across 29 routes, so the check has a positive
  control. They are genuinely lazy, not chunks that load anyway. One refinement worth writing down:
  the largest matched chunk is 207 kB and carries far more than ProseMirror, so the **absolute**
  394 kB is not "what the editor costs". The **delta** is the trustworthy number, because shared
  content appears on both sides of it and cancels.
- **Dropping a refused link neither duplicates nor loses its text.** Six shapes the existing test did
  not cover — nested markup inside the refused anchor, an adjacent link in either order, no closing
  tag, a nested anchor, and an empty one — all preserve the text exactly once. The early `return`
  never pushes the element, which is what keeps `</a>` from closing something it did not open and
  keeps the unwinding loop from popping past it.
- **The derivation really is enforced by tests, not asserted in prose.** Renaming `blockquote` in the
  canonical list fails 3 of them, exactly as claimed. My first attempt mutated `AT_RISK_IN_WORD` by
  accident and found the gap above instead.
- **The two implementations do not diverge.** Twenty-four hrefs run through both: identical answers,
  including NBSP, zero-width space, BOM, NUL and mid-scheme invisibles. They reached the same answer
  by different routes before the fix above, and by the same rule after it — so pinning the
  normalisation in a shared corpus would add machinery to protect a property that now holds by
  construction. Not worth it.
- **`window.prompt` is an acceptable floor.** The reason given is the right one — a custom popover is
  a second focus trap inside a dialog — and the implementation handles both of its awkward returns
  (`null` on cancel, `""` on empty), then refuses an unsafe scheme out loud rather than doing nothing
  visible. It should be replaced when somebody designs the popover, which is what the docstring says.

## Round two — the two href implementations were not one rule

The review fixed `href_is_safe` (it over-stripped, calling `h<ZWSP>ttp://x.com` safe and storing a
link to nowhere) and, on the strength of running 24 hrefs through both sides, advised **against**
pinning the normalisation: *"a shared corpus would be machinery guarding a property that now holds
by construction."*

**It does not hold by construction.** The two were different rules that agreed on the cases somebody
tried. Measured across a wider set — four divergences, every one in the same direction:

| href | `href_is_safe` (server) | `isSafeHref` (editor) |
|---|---|---|
| `htt<VT>p://x.com` | refused | **safe** |
| `htt<FF>p://x.com` | refused | **safe** |
| `htt<DEL>p://x.com` | refused | **safe** |
| `ht<SOH>tp://x.com` | refused | **safe** |

The direction is what makes it matter. **The editor said yes and the sanitiser said no**, so the
editor would accept a link the server then strips — a link vanishing on save, which is the precise
failure this ticket exists to prevent, reached from the security check rather than from the schema.
And the server is the correct one: WHATWG removes only tab, CR and LF from the middle of a URL, so
none of those four resolves as `http` in any browser.

`isSafeHref` implements WHATWG's rule now — the same one, not a rule that agrees.

### And the corpus is shared, because "we compared them once" is what failed

`frontend/lib/markdown/href-cases.json` is one list of 12 safe and 21 refused hrefs, read by
`schema-drift.test.ts` **and** by `test_sanitise_lp853.py`. Both assert their own implementation
against it, so a change to either side that moves the rule fails on both — rather than being caught
the next time somebody thinks to compare them.

Both suites carry a positive control on the corpus itself: two empty lists would satisfy every
assertion, and a path that stopped resolving would produce exactly that.

Mutated by restoring the over-stripping editor rule: `refuses every href the corpus calls refused`
fails, naming `htt\u000bp://x.com`.

### Also from round two, accepted as found

- **`AT_RISK_IN_WORD` was read by nothing** — found when a mutation to it changed no test. Every
  at-risk tag must now be one the schema emits. The reverse is deliberately not asserted, because
  `p`, `br`, `strong` and `em` are excluded on purpose.
- **The bundle measurement was verified**: the three ProseMirror chunks reproduce 394,066 exactly and
  none appears in `app-build-manifest.json` (65 chunks across 29 routes — a positive control), so
  they are genuinely lazy. The refinement is right and is worth repeating here: **the delta is the
