# LP-494 — Condo: CO-3 · CO-4 · CO-5

⚠️ **Written as the work happened** (standing policy 10 — LP-491/492/493 all wrote the doc at the end).
Phase A landed before a line of rule code was written, and it changed the shape of all three rules.

## What this ticket is

The condo lane's remaining three rules. **Phase A overturned the ticket's own premise on two of them**,
so the outcome is not the one the ticket anticipated:

| rule | ticket expected | ⚠️ what Phase A established | outcome |
|---|---|---|---|
| **CO-3** | judgment on `property.is_warrantable_condo` | master half duplicates **live IH-7**; fidelity half's *requirement* inputs never resolve | ⚠️ **DROPPED** |
| **CO-4** | AI parses an HOA budget | HOA budgets **have no catalog type at all**; the condo questionnaire carries a typed `reserve_contribution_percentage` | **built deterministic** |
| **CO-5** | judgment on `property.is_warrantable_condo` | needs **none** of that tag — its four inputs are typed questionnaire fields | **built deterministic** |

⚠️ **NEITHER CO-4 NOR CO-5 NEEDS AI**, which is the ticket's most consequential finding: both were

question — *has typed extraction already spent the perception step?* — answering **yes**.

## PHASE A — the blockers, established before any rule code

### 1. ⚠️ `property.is_warrantable_condo` still has NO source — and NEITHER RULE NEEDS IT

LP-487's finding holds: the tag appears in the generated `fact_tags.csv` (row 72) and **nowhere else** —
no `tag_production.yaml` declaration, no producer, and `test_co1_condo_questionnaire_lp488.py:86` pins it
out of `load_declarations()`. Warrantability is a project-review conclusion (Form 1076 / PERS), not a
readable datum. **Nothing was wired to it.**

⚠️ **But the planning tag map is shorthand, and Phase A item 6 says resolve against the real key set —
which overturns the ticket's own blocker.** CO-5 does not need a warrantability verdict; it needs
delinquency, concentration and litigation, and **every one of those is a typed field on the condo
questionnaire extractor**:

| CO-5 leg | real field on `CondoQuestionnaireExtraction` |
|---|---|
| delinquency | `units_delinquent_over_60_days`, `delinquency_percentage` |
| commercial / mixed-use | `commercial_space_percentage` |
| single-entity concentration | `single_entity_owned_units`, `single_entity_max_percentage`, `total_units` |
| litigation | `litigation_indicator`, `litigation_description` |

**So CO-5 is NOT blocked by the warrantability tag. It is buildable on real fields.**

### 2. ⚠️ CO-3 ADDS NOTHING BEYOND LIVE IH-7 — DROPPED

**The master half is a duplicate.** IH-7 (live, LP-487) already reads the derived `ins.condo_master_policy`
and decides presence, replacement-cost basis (B7-3-03) and general liability ≥ $1,000,000 (B7-4-01). CO-3
would produce **a second verdict on the same comparison from the same documents** — the one-matcher-per-
comparison rule (ADR-375), which already dropped PC-1 in LP-493.

**The fidelity half cannot be computed, and I read the primary rather than reusing IH-7's assertion.**
**Fannie Mae Selling Guide B7-4-02, page dated 08/05/2026 · tier P** (fetched):

> exceptions: "…projects that qualify for a waiver of project review as described in B4-2.1-02, …
> **condo or co-op projects consisting of 20 units or less**, or condo or co-op projects that would need
> fidelity/crime insurance coverage of **$5,000 or less**"
>
> required amount: "…the fidelity/crime insurance coverage amount must equal at least … **the sum of
> three months of assessments on all units in the project**."

⚠️ **Both the applicability gate and the required amount need the UNIT COUNT, and the amount also needs the
assessment base.** The master policy document carries neither: `total_units` lives on the condo
questionnaire, which fills it **0/4** (see §4). So CO-3's fidelity leg could only ever say *"coverage
exists"*, never *"coverage is adequate"* — and firing on absence would be **wrong** for a ≤20-unit project.

⚠️ **A correction to IH-7's spec, found here.** `fidelity_crime_coverage_present` and
`fidelity_crime_coverage_amount` fill **8/8** on the bench's master policies. IH-7's header implies the
fidelity leg is unbuildable because its inputs are missing; the honest statement is narrower — **the
COVERAGE reads fine; the REQUIREMENT is what cannot be computed.** Recorded, not silently left.

**Verdict: CO-3 is dropped.** The fidelity leg, if it is ever built, belongs **inside IH-7** — one rule,
one verdict on the master policy — not as a second rule. Logged for Priya.

### 3. The loan application date — ⚠️ IT EXISTS AND POPULATES, but does NOT reach the snapshot

`LoanFile.application_received_date` is a real column (`app/models/loan_file.py:173`) and it is **populated
on 22 of the 28 loan files** in the local database (LF-6T3N `2026-06-08`, LF-96SV `2026-06-17`, LF-XU26
`2025-09-15`, …). **But `mismo_section.py` never emits it**, so no tag and no rule can see it.

**Fixed here with one line** — the MISMO fact map is explicitly "free strings … so new facts never need a
schema change", so `SNAPSHOT_VERSION` stays **4**. See Phase B.

### 4. ⚠️ HOA budgets have no catalog type — and the questionnaire that DOES carry reserves is blank

**No HOA budget document type exists**, so a budget cannot be classified, cannot be extracted, and cannot
reach a loan file. The ticket's premise — *"AI parses the budget"* — has no document to parse. **The
reserve percentage is instead a typed field on the condo questionnaire**: `reserve_contribution_percentage`.

**The corpus, measured (shape only — nothing copied):**

| | n | what it shows |
|---|---|---|
| `condo_questionnaire` | **2 unique** (×2 bench runs = 4 files) | one is a **cancellation notice**; one is a **standard Form-1076-style questionnaire** |
| `master_insurance_policy_for_condominium` | **4 unique** (×2 = 8) | extracts richly — 15–17 of 17 typed fields |

⚠️ **EVERY substantive questionnaire field fills 0/4** — `total_units`, `delinquency_percentage`,
`commercial_space_percentage`, `single_entity_*`, `litigation_indicator`, `reserve_contribution_percentage`.
Only identity fields fill (project name/address, HOA name, management company, form type, who completed it).

⚠️ **I chased this to the document before accepting it, because the shape looked like the LP-493a defect.**
The standard questionnaire is 450 KB and produced **90 catch-all labels** against **1** typed field — the
signature of an extractor dropping data into the catch-all. **It is not.** All 90 catch-all entries have
an **empty value**: the document carries the form's printed QUESTIONS and **no answers**. The second bench
run of the same file failed outright (`ValueError`). **The form is genuinely unanswered** — LP-488 and the
ticket were right, and this is now verified at the document rather than inferred from a fill rate.

⚠️ **And no loan file carries a condo questionnaire or a master policy at all** — `condo_docs=[]` on all 28
files. `property_type` is `None` on every file that has documents. **The entire condo lane is unexercised
by the live corpus, and CO-1 and IH-7 are already live in exactly that state.**

### 5. Catalog vs repo — divergences reported, repo wins

| planning artifact says | repo says |
|---|---|
| CO-4 `condo.reserve_pct` produced by **AI**, "AI parses budget" | no budget document type exists; the value is a **typed questionnaire field** |
| CO-3/CO-5 read `property.is_warrantable_condo` | that tag has no producer; CO-5's real inputs are seven other typed fields |
| CO-3 = "Master insurance / fidelity" | the master half is **live already** as IH-7 |

### 6. Vacuity, triggers, distrust

- **ADR-330 vacuity — neither rule.** CO-4 compares a questionnaire percentage against a *guideline*
  threshold; CO-5 compares questionnaire percentages against *guideline* limits. No operand pair traces to
  one field.
- **CR-3 trigger test — both pass.** The trigger is `property.type == condo`, a document/application-stated
  fact, and it is the same trigger IH-7 and CO-1 already ship on.
- **Distrust overlap (LP-508): none.** `distrusted_fields.yaml` lists `homeowners_insurance`,
  `drivers_license`, `credit_report`, `appraisal` — no `condo_questionnaire`, and no derived tag of this
  lane in the `tags:` block.

## PHASE B–C — what was built

### The tag layer (9 new declarations)

| tag | mode | source |
|---|---|---|
| `condo.reserve_pct` | parsed, doc | `reserve_contribution_percentage` — **already in the generated `fact_tags.csv`**, so declared in `tag_production.yaml` only |
| `condo.delinquent_units_pct` · `condo.commercial_space_pct` · `condo.total_units` · `condo.single_entity_owned_units` · `condo.litigation_disclosed` | parsed, doc | the five CO-5 questionnaire fields (`vocabulary_extra.yaml`) |
| `loan.application_received_date` | parsed, loan | the new MISMO fact |
| `condo.reserve_adequacy` · `condo.project_eligibility` | derived, loan | the two verdict recipes |

⚠️ **Every parsed tag is `document_type`-scoped to `condo_questionnaire`** (LP-487's discipline), and a
test pins it. `total_units` is the reason it matters — a plausible field name on other forms, and an
unscoped read would let an unrelated document decide a project's concentration tier.

⚠️ **`condo.litigation_disclosed` is a STRING, not an enum, deliberately.** The recipe recognises a closed
set of yes/no spellings (ADR-376) and abstains on anything else, so `"PENDING — SEE ATTACHED"` can never be
read as *"no litigation"* and clear the project. A test pins that direction.

### ⚠️ How the date-keyed threshold was expressed — and the mechanism I did NOT build

The rule DSL cannot express it directly: an outcome carries **one** `when_compare`, and a `reference`
operand resolves to `Decimal` only, so there is no date reference. Expressing *"application < 2027-01-04
AND reserve_pct ≥ 10"* would have needed **two** DSL changes (a list of comparisons, and a typed date
reference).

**I did not build them.** The date branch went into a **derived recipe** — the live IH-7 pattern, unchanged
— which resolves the whole comparison to `adequate` / `inadequate` / `unknown`, leaving CO-4's rule body a
plain tag-value switch. **No mechanism was added; ADR-379 records the shape and the choice.**

⚠️ **And "declared as data" was made REAL rather than decorative.** Both percentages *and* the boundary
date live in CO-4's `reference_values`, and `test_thresholds_match_their_declared_reference_values` pins
every recipe constant against them — for CO-5's four limits too. IH-7 has no such guard; this is the first
place the citation and the code cannot drift apart.

### The application date

One line in `mismo_section.py`. The MISMO fact map is explicitly free-string keyed "so new facts never
need a schema change", so **`SNAPSHOT_VERSION` stays 4**.

## Assumptions and decisions

1. **`input_resolves` is LP-485's development-mode meaning** — and it is **false** for both rules, which is
   the honest reading of that definition ("the producer resolves it on real stored data"), not the
   convenient one.
2. **Built rather than dropped, and the distinction from TI-3/4/5 is the reason.** There, four **richly
   extracted** title commitments left the fields null — the documents do not carry the data. Here the
   fields exist, the document type classifies, and the two documents on hand are **blank**. One completed
   questionnaire unblocks both rules with no code change.
3. **CO-5 abstains below 5 units** rather than inventing a single-entity limit the guide does not state.
4. **The questionnaire's own `single_entity_max_percentage` is deliberately NOT read** — the concentration
   is computed from the count and the total, so one stated number cannot contradict the other.
5. **`property.is_warrantable_condo` stays inert**, and the CO-1 test that pins it inert now has a sibling
   asserting neither new rule reads it.
