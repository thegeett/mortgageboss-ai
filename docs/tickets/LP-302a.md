# LP-302a — Surface bank-statement transactions in the snapshot

## Summary

A Stage-1 extension closing the gap LP-302 found: the documents assembler skipped
nested lists, so bank-statement **transactions** never reached the snapshot. This
surfaces them as structured snapshot data (a nested `TransactionRecord` list on
`DocumentEntry`) so per-transaction rules (AS-1 large-deposit, later
NSF/chaining/recurring-debit) can read them **from the snapshot** — preserving the
"evaluator reads only the snapshot" invariant. This is **Option A** from LP-302.

Architectural decisions recorded in **ADR-248** (`decisions.md`).

## Acceptance criteria

- [x] Frozen `TransactionRecord` = `{ date, amount, direction, description, account }`:
      date/amount/direction/description each a `Field` (source=extracted, nullable
      confidence, absent≠empty); **`account` a PRE-MASKED `PiiField`** (display=`****NNNN`,
      `match_hash=None`) — display/context only, never a match key.
- [x] `DocumentEntry.transactions: tuple[TransactionRecord, ...] | None` (immutable).
- [x] Absent ≠ empty: `None` = not surfaced/absent; `()` = statement present with
      zero transactions. Preserved through JSON.
- [x] Assembler surfaces bank-statement transactions; direction derived; description
      redacted (PII-safe at rest); account resolved once per statement.
- [x] **Non-matchability enforced structurally:** `PiiField.matches()` treats a `None`
      hash as never-equal — two `None`-hash accounts NEVER match each other (no
      same-last-4 false collision), and a `None` hash never matches a real hash
      (absent-is-not-matchable, LP-203).
- [x] `snapshot_version` = 2 (bumped 1 → 2 when transactions landed); change is additive
      (non-bank docs unaffected).
- [x] Lossless JSON round-trip incl. transactions + account; persist/load (LP-209)
      round-trips; the at-rest guard passes.
- [x] Cross-section account match: **KNOWN GAP — not achievable on this branch** and NOT
      faked (see below) — pre-masked account (no raw to hash) + no MISMO asset-account
      column.
- [x] Real LF-6T3N: transactions surfaced (50), account masked, description PII masked;
      eyeballed.
- [x] Tests + ADR; CI green (ruff, mypy, snapshot suite).

## Phase 0 findings (incl. two contradictions flagged)

- **Transaction shape** (`bank_statement.py:59-71`): `{date, description, amount,
  transaction_type, running_balance, source}` — **no `direction`** (derive it), **no
  per-transaction account** (it's on the statement's `account_number_masked`). Only
  `bank_statement` carries transactions.
- **Skip point** (`documents_section.py` `_scalar`): lists → `None` → dropped.
- **Contradiction 1 — account can't be hash-matched here.** The account is only ever
  **pre-masked** (`account_number_masked` = `****NNNN`, `match_hash=None`), and MISMO
  `StatedAsset` has **no account column** — so a transaction-account ↔ asset-account
  hash match is impossible on this branch. **Decision (amended): carry the account on
  `TransactionRecord` as a pre-masked, non-matchable `PiiField`** (display/context only),
  and document the cross-section-match gap loudly (see KNOWN GAP). *Superseded the earlier
  "no account on the record" call:* the account is useful per-row context (which account a
  deposit landed in) and carrying it **honestly** — `match_hash=None`, structurally
  non-matchable — papers over nothing; the hash-match impossibility is explicit in the
  type, not hidden by omission. **Do NOT** `from_raw`/hash the mask: hashing `****5667`
  would collide with every same-last-4 account (the LP-203 colliding-hash bug).
- **Contradiction 2 — raw descriptions are unpersistable.** 37/50 real LF-6T3N
  descriptions contain a 9+-digit run (payroll/confirmation/transfer IDs) → the LP-209
  at-rest guard **rejects** them, so "raw and faithful" conflicts with "persist
  round-trips." **Decision (you): redact** `\d{9,}` / SSN patterns in the description
  (keeps the sourcing signal AS-1 needs).

## Assumptions & decisions (ADR-248)

- **`TransactionRecord` shape:** date/amount/direction/description each a `Field`
  (per-attribute absent≠empty; no confidence — extraction transactions carry none),
  plus `account`.
- **`account` = pre-masked, non-matchable `PiiField`** (amended): the statement's
  masked account (`display=****NNNN`, `match_hash=None`), resolved once per statement,
  carried for display/context. Built with `pre_masked` (NOT `from_raw`) — no raw form
  exists and hashing the mask would false-collide. `PiiField.matches()` makes the
  `None` hash structurally non-matchable.
- **Description redacted** (deviation): `\d{9,}` / SSN → `[redacted]`; PII-safe at
  rest, keeps the sourcing signal. Applied at the assembler, not by weakening the
  guard.
- **Direction** derived from `transaction_type` (deposit→credit / fee→debit), amount
  sign fallback.
- **Version bump 1→2**: additive; a v1 blob won't load under the v2 reader
  (acceptable — no production-persisted snapshots exist).
- **Absent ≠ empty:** `None` (not surfaced) vs `()` (zero transactions).

## ⚠️ KNOWN GAP — deposit↔MISMO-asset account matching is NOT achievable on this branch

**Do not read the pre-masked `account` on `TransactionRecord` as enabling a
cross-section account match. It does not, and it is not faked.**

- **Why it's impossible here:** (a) extraction only ever holds a **pre-masked** account
  (`account_number_masked` = `****NNNN`) — there is **no raw account value** to hash; and
  (b) MISMO `StatedAsset` has **no account column** — there is nothing on the MISMO side
  to match against. Both halves are missing, so a real `match_hash` cannot be produced and
  a deposit cannot be hash-matched to an asset account.
- **What we did NOT do:** we did not hash the masked value (`****5667` would collide with
  every same-last-4 account — the LP-203 colliding-hash bug), and we did not build
  speculative raw-account plumbing / a synthetic-raw hash test — there is **no consumer** on
  this branch. `account.match_hash = None` is the honest value; `PiiField.matches()` makes
  it structurally non-matchable.
- **Consequence for AS-1:** the deposit↔asset **sourcing-corroboration** path is
  unavailable. **AS-1 still works** — it evaluates the deposit amount vs a threshold plus the
  AI sourcing judgment; the account match was *corroboration*, not a core input. The account
  is carried for display/context ("$8,076 into ****5667"), nothing more.
- **Unblock condition (a future ticket):** (1) surface a **RAW** account in extraction and
  (2) add a **MISMO asset-account column**. Then a real `match_hash` (via
  `PiiField.from_raw`) enables the match — purely **additive**: the `PiiField` shape already
  supports it and the None-is-unmatchable invariant is already enforced, so turning it on
  later changes no existing behavior.
