# LP-473 — the three remaining extractor failures (222, 069, 174)

v1 had 10 extractor failures; v2 has 3. The `ValueError` cluster (8 of 10) was fixed by the streaming change
(`dcc2196`) and the rate-limit crashes are gone. These three are what remains. **LP-471 changed the stakes:**
all three now fall back to Tier-3 and yield untyped, rule-UNREADABLE data, so this ticket is about recovering
**typed, rule-readable** fields — not rescuing empty documents. "Not worth fixing — the fallback already
captures it" is an allowed outcome.

---

## Phase A — diagnosis (no fix). Root cause per doc, one-bug-or-three, worth-it.

**This is THREE distinct root causes, not one bug.** None is a shared regression.

### 069 — uncapped typed-extraction call path hits the provider's 100-page limit  ·  ROOT CAUSE CONFIRMED (free)

- **Facts (measured, no AI):** 118 pages, 2.53 MB on disk (~3.4 MB as base64). `build_document_message` and
  `cap_pdf_pages` both succeed locally — the failure is provider-side.
- **Root cause:** `_extract_branch` calls `extractor(content, mime_type)` with the **full, uncapped** content.
  118 pages exceeds the documented **100-page / 32 MB document-block limit** (`client.py:288` handles exactly
  this: HTTP 400 → `_classify_infra_failure` → `INFRA_OVERSIZED`; `generic_analyzer.py:190` names the same
  limit). Classification survives because LP-462 caps it to 15 pages; the Tier-3 fallback survives because
  LP-463/471 cap it to `tier3_max_pages = 50`. **Typed extraction is the ONE call path with no cap**, so it
  alone hits the wall. Not transient; a retry re-sends 118 pages and fails identically.
- **This is not a bug in an extractor — it is a call-path-coverage gap.** A limit was applied to classification
  (LP-462) and to Tier-3 (LP-463), but never checked against the typed-extraction path.
- **Proposed fix / worth-it:** ⚠️ **Do NOT add a naive extraction page cap.** 069 is a *package* (CD + Note +
  Deed of Trust + 1003 + riders); a 1003's liabilities/REO sit deep in the file. A 50-page cap would extract
  the first ~50 pages of a 118-page package and **silently drop the later documents** — a crash traded for
  silent, wrong data. The honest fix is **the splitter** (its own ticket; backlog already holds 066/167/204/271).
  Meanwhile the crash is already graceful: LP-471 falls it back to Tier-3 (50 pp), which the ticket confirms
  captures the substance ($688,500 loan, 8.070%, 2-1 buydown, $54,184 cash-to-close). **→ NOT worth a fix in
  this ticket. Defer to the splitter; record the call-path lesson as an ADR.**

### 174 — the `ValueError` is already fixed; residual is the image-only gap  ·  ROOT CAUSE CONFIRMED (free)

- **Facts (measured, no AI):** 8 pages, 1.49 MB. `pypdf` reads it, `build_document_message` and `cap_pdf_pages`
  all succeed. LP-464 recorded it as **image-only (0 extractable text)**, defeating pypdf text on both readers.
- **Root cause of the historical `ValueError`:** the pre-streaming SDK ceiling — `.create()` raised
  `ValueError("Streaming is required …")` for `max_tokens > 21,333`, client-side, before the call. LP-464
  attributed 8 of the 10 v2 failures (incl. 174/175/176) to it. The fix (`dcc2196`, *"Stream completions to
  fix the truncation-retry ValueError"*) **is an ancestor of HEAD** and the extraction path now uses
  `client.messages.stream` — **that specific `ValueError` cannot recur.** 174's v2 `ValueError` is stale (the
  v2 bench predates the fix); its siblings 175/176 already succeed on the fixed path.
- **What remains** is that 174 is an image-only scan: post-fix, typed extraction (vision) either reads the scan
  or returns empty → Tier-3 captures the lease terms. Either way it is **the ADR-365 image gap** (same class as
  266 and 294), **NOT a parse bug.** No OCR is attempted here (ADR-365).
- **Proposed fix / worth-it:** none. The parse/ValueError path is already fixed; the residual is image
  preprocessing (ADR-365, deferred). **→ NOT a parse bug; NOT worth a fix here. Record as a third instance of
  the image gap.**

### 222 — honest-none / transient on a misclassified-but-overlapping Services Agreement  ·  THE PRIORITY

- **What it is (read the PDF):** a **CCRES *Services Agreement* for a Registered Behavior Technician** (Sridevi
  Muthusamy; $30.00/hr RBT; $1.82/quarter-hour travel; $10.00/hr non-direct supervision; part-time
  fee-for-service, hours not guaranteed; signed 01/25/2026 / director 7/1/2025). It is genuinely a services
  agreement, **not** an offer letter — so classification as `employment_offer_letter` is a **near-miss**
  (employment-adjacent), a *classification* matter, not an extraction bug.
- **"Empty failure, NO error type" — is it a crash or honest-none?** **Honest-none, not a crash.** An exception
  records `error_type` (that is how the `ValueError` cluster was tagged). 222 has none because no exception
  occurred: `derive_status` returned `FAILED` from an **all-null typed core** (the model returned nulls), with
  `reasoning = None` → `error_detail = None`. "Empty, no error type" is precisely the *signature* of an honest
  all-null FAILED, as opposed to an exception FAILED. **Nothing is swallowed; the logging is not hiding a
  traceback — there is no traceback.**
- **Was it a v1→v2 regression in the extractor?** **No.** The offer-letter spec (023, single commit
  `a1347af`), prompt (`0ac8b8d`, LP-440) and module (LP-440/443) were **never touched by LP-460/461** — the
  ticket's "the schema/prompt may have been touched" hypothesis is disproven by git. The extractor code is
  unchanged between v1 and v2.
- **So why 14 typed in v1 and 0 in v2 with unchanged code?** The offer-letter schema's fields **overlap
  heavily** with this Services Agreement and are all plainly present and readable — `candidate_or_borrower_name`
  (Muthusamy, Sridevi), `position_title` (RBT), `employer_legal_name` (CCRES), `employer_address`,
  `employer_contact`, `base_salary_or_hourly_rate` ($30/hr), `document_issue_date`, the two signature/date
  fields, etc. A schema that fits this well should read ~14 fields (as v1 did). Unchanged code + readable
  overlapping fields ⇒ the v2 0-typed is a **transient / non-deterministic all-null model response**
  (extraction runs on Haiku), **not a reproducible code fault.** A re-run today should return ~14 again.
- **Proposed fix / worth-it:** the extractor is **not broken** and the code is unchanged; there is nothing to
  fix in the extraction path. The real "misfiled" issue is *classification* (a separate ticket — do NOT change
  classification here), and the Tier-3 fallback already captures the income the ticket lists. ⚠️ Note the
  LP-472-A6 trap in reverse: forcing offer-letter fields onto a services agreement can yield *plausible-wrong*
  fields — so even the v1 "14 typed" deserve a skeptical eye. **→ NOT worth an extraction fix.** One optional,
  tiny in-scope improvement: record a synthetic `error_detail` ("all typed fields null") for all-null FAILEDs so
  a future "empty, no error type" is self-explaining — logging polish, not a bug fix.
- **Confirmation available (~$0.05, 1 call):** run `extract_employment_offer_letter` on 222 today. If it returns
  ~14 typed, the v2 empty was transient (as diagnosed) and the verdict stands. **Reported, not run — awaiting
  the go-ahead per the cost rule.**

## Phase B — the only changes (no extractor fix; Geet: accept "no fix" for all three)

**222 confirmed transient (the $0.05 spend).** Ran `extract_employment_offer_letter` on 222 live today:
**SUCCEEDED, confidence 0.88, 14/16 typed** — Muthusamy Sridevi / RBT / CCRES / $30/hr / employer address +
contact / both signature-dates — matching v1's 14 exactly. The v2 "0 typed, no error type" was a one-off

reasoning names it "a Services Agreement," yet reads the overlapping employment fields correctly — the values
are genuine, not force-fit, because a services agreement and an offer letter share these basics.)

**Logging polish — the LP-464 lesson ("a symptom with no location is expensive").** A FAILED extraction that
carried no reasoning showed as a blank — "empty failure, no error type" — which cost a diagnosis cycle on 222.
Now self-locating:
- `app/ai/extraction/parsing.py`: new `failure_detail(status, reasoning)` + `FAILED_ALL_NULL_DETAIL`
  ("all typed fields null — model returned no values (no exception)"). One helper so the production record and
  the bench name it identically. An infra/parse failure keeps its own reason (`.failed(...)`); an all-null
  FAILED gets the named marker; a non-FAILED gets `None`.
- `app/tasks/document_processing.py`: the persisted extraction version's `error_detail` now uses it.
- `app/dev/bench/engine.py`: **also fixes a latent bug** — the bench read `getattr(result, "failure_reason",
  None)`, but the result attribute is `reasoning`, so it *always* recorded `None` for a FAILED extraction. That
  wrong attribute name is a second reason 222 showed "no error type" in the v2 bench. Now reads `reasoning`
  through `failure_detail`.
- Test: `tests/ai/test_failure_detail.py`.

**Two ADRs.** ADR-370 (069 — a limit on one call path must be checked against every path; typed extraction is
the one uncapped path; a naive cap = silent loss on a package → the splitter). ADR-371 (174 — the `ValueError`
is already fixed by `dcc2196`; the residual is the ADR-365 image gap, a third instance with 266/294).
