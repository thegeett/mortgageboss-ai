# LP-607 — Five internal keys in a sentence, and a conflict that wasn't one

Both from the run after the W-2s landed on LF-3CVT.

## 1. ID-4 put content ids in front of a processor

> "the borrower's current residence differs across sources (**docdbbe8db1f5a7d9ff,
> doc6abd650d555473b0, docafdf7653352bf74d, docfdf4385a90bf5cf0, docd0015582725c420b**) — a real
> discrepancy"

LP-377-B exists to keep exactly those away from a person. Two things had to fail together:

- **The template asked for them.** Consistency reasoning rendered `{sources}` as
  `", ".join(inst.source_id ...)` — content ids, by construction, for every consistency rule.
- **The composer's guard could not see them.** `IDENTIFIER` matches a *dotted* pattern
  (`occupancy.consistent_with_signals`); `docdbbe8db1f5a7d9ff` has no dot, so it walked straight past.

Fixed at both ends. `_Gathered` now carries a `source_label` — the document TYPE — and the template
renders that, deduped and order-preserving, so five documents of two kinds read "pay stub, W-2" rather
than repeating a name five times (`{count}` already carries the number). And `CONTENT_ID` catches the
four subject-key prefixes (`doc`, `lia`, `txn`, `acct`) followed by a hex run, so a composition that
reintroduces one is rejected and retried.

The type is also **more useful** than the id: it says which *kind* of source disagrees. The real
sentence becomes "the SSN differs across sources (pay stub, W-2)".

Worth noting the finding itself is questionable: it compares a **2023** W-2's address against the
current one. A prior address on a two-year-old document is expected, not a discrepancy. Not fixed here.

## 2. A conflict the finding's own sentence disproves

> "Stated monthly income of $13,166.67 **conflicts with** documented biweekly pay stubs showing gross
> pay of approximately $6,028–$6,063 per period (**annualizes to ~$13,061–$13,136/month**)"

$13,166.67 against $13,061–$13,136 is **0.2%–0.8%**. The rule that owns this question uses a **10%**
threshold. The income agrees; the model compared a per-period figure to a monthly one, then annualised
correctly in prose and refuted itself.

### What was NOT changed, and why

`_check_income_variance` is correct — it compares `stated_income_monthly` to
`documented_income_monthly` and abstained here because no documented monthly figure had been computed.

The AI layer then filled the gap, which is **deliberate**: `OWNED_CANONICAL_TYPES`' comment says the AI
"still surfaces a type the deterministic pass was silent on — e.g. when its Tier-2 facts aren't
present". Making that deferral unconditional would have fixed this symptom by reversing a documented
design decision, on one example. So the fix targets the actual error — the arithmetic — and the
deferral design is left alone and reported instead.

The prompt now requires converting a per-period amount to a monthly one before deciding anything
disagrees, names the three conversions, and carries the real numbers that caught it. A test checks the
arithmetic the prompt asserts is itself right, so the guidance cannot teach an error.

## Tests

and the unit guidance removed each fail. The composer guard initially had NO test — the mutation
passed — which is how that gap was found.

Two fixtures were changed so their documents carry distinguishable types: reasoning names sources by

the reasoning says WHERE it disagreed.
