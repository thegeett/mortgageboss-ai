# LP-842 — A request says WHY, not just what

Status: spec. Build order: first of four (LP-842, LP-843, LP-844, LP-845).

## The report

> "The bigger improvement I would make in your email-generation system is to stop generating generic
> document requests and instead generate them from the finding that caused the request."
>
> IH-1 finding: dwelling loss-settlement basis cannot be verified.
> BAD: "Send homeowners insurance declarations page."
> BETTER: "Please ask your insurance agent for documentation confirming that Coverage A — Dwelling
> is insured on a replacement-cost loss-settlement basis."

The critique is right, and the more interesting fact is that **the system already has the answer and
throws it away.**

## What is actually there

A request from a finding creates a needs item carrying, in `reasoning`:

    Requested from verification findings: IH-1

The rule ids, as text. `_document_line` (`services/email_draft.py:144`) renders the catalog's
guidance or the need's title and **never reads `reasoning`**, so it reaches nobody.

The finding's own sentence — the one a processor reads on the Needs-Attention tab, "dwelling
loss-settlement basis cannot be verified" — is on the `Finding` row and is **not copied to the need
at all**. So the specific evidence gap exists twice in the database at request time and appears in
the email zero times.

There is a comment at `finding_resolution.py:633` explaining why the two cannot be joined: the
`NeedsItem.source_finding_id` foreign key points at `document_findings`, a different table from
verification findings. That is a real constraint on a FK and not a reason the TEXT cannot travel.

## The defect this closes, stated as a borrower sees it

A processor clicks Request on IH-1. The borrower receives "Homeowner's insurance — Where to get it:
your insurance agent". They send another declarations page. It does not state the loss-settlement
basis, because the first one did not either — that IS the finding. The file is now one round trip
older and no closer, and neither party can tell why.

## The change

Carry the finding's own sentence onto the need it creates, and render it under its document.

1. `request_docs_for_finding` and the bulk path copy the finding's `message` onto the need (a new
   column, or the existing `reasoning` given real structure — decided at build time; the FK cannot
   be reused, per the note above).
2. `_document_line` renders it under the document, in the same slot LP-839 gave the processor's
   own note. That slot already survives the body being regenerated on every add and remove.
3. The two are different voices and both belong: the catalog says how to obtain the document, the
   finding says what the document has to establish. They render as separate lines.

## Where this is NOT a fix

Rewording "provide a letter of explanation" into "explain why the May 2026 Toyota Financial payment
was 30 days late" needs the finding to NAME the tradeline, not merely to have fired. Whether each
rule's message carries that much detail is a per-rule question and is not in scope here: this ticket
makes the message REACH the email. Which messages are worth rewriting is the follow-up, and it is
measurable once the text is visible.

## Assumption recorded

Deferred-placeholder safety (LP-823) applies to anything new that enters a body. A finding message
is engine-written text and can contain a `$`, which would collide with the template's own
placeholders. It must be escaped at the point of interpolation, and a test must prove a `$` in a
finding message survives into the rendered body as a literal.

# Built

The spec above was written before reading the rule specs, and two things it assumed turned out to be
wrong. Both are recorded here rather than edited above, because the second is a safety decision.

## The source is NOT the finding's message

`Guidance` (LP-522) already carries exactly the structure the report asks for — `action`, `why`,
`how_to_fix` — and **all 84 specs declare `how_to_fix`**. On IH-1 it already says the right thing:

    Obtain a homeowners policy (or endorsement) that settles the dwelling on a replacement-cost
    basis, and replace the binder in the file.

So the sentence the report wanted does not need writing. It needed routing. The ticket's premise —
"copy the finding's `message`" — was aiming at the weaker field.

## …AND IT MUST NOT BE ROUTED OUTWARD

`how_to_fix` is written for a PROCESSOR, on the assumption that only a processor reads it. Measured
across the 84 specs, **nine carry language that must never reach the person it is about**:

| Rule | Says |
|---|---|
| ID-1, ID-2, ID-3 | a mismatch "may indicate **identity fraud** and must be escalated" |
| CO-5, CR-6, IH-7 | "**ineligible**" |
| DT-6, FR-5 | "**undisclosed**" |
| PR-6 | "**decline**" |

Forwarding that to a borrower accuses them of fraud in an email they keep. Forwarding it to a lender
discloses an internal posture about their file. ID-3 is the rule from the ORIGINAL bug report in this
series, so this is not a hypothetical corner.

**So the field is new and separate: `RuleSpec.outbound_ask`, an allow-list.**

A deny-list was the obvious cheaper answer and is the wrong one. Filtering `how_to_fix` for alarming
words scopes the guard by SYMPTOM: it passes everything nobody thought to add to the list, and every
sentence it lets through is judged safe because it lacks a keyword rather than because a person
decided it was safe. A rule is silent here until somebody writes a sentence and means it.

`test_no_rule_reuses_its_processor_how_to_fix_as_its_outbound_ask` defends the one way that property
is lost — an author copying the processor field across, which is harmless on the rule they copy and
establishes the habit that reaches ID-3. Verified by mutation: copying IH-1's `how_to_fix` into its
`outbound_ask` fails the test.

## What shipped

- `RuleSpec.outbound_ask` (optional; absent → today's behaviour exactly, so the feature cannot
  half-appear).
- `NeedsItem.outbound_ask` + migration `f4a1c9d2e7b3`, **hand-written**. `--autogenerate` against
  this dev database proposed dropping five `borrowers` address columns and rewriting
  `communication_evidence` — it read the local database's drift from the models as intent. That
  migration would have deleted borrower addresses in every environment it reached.
- `_outbound_ask(findings)` — one ask, and only when the contributing rules agree on it. A need can
  be created from several findings at once; two rules wanting the same document for different
  reasons have no single sentence between them, and picking one would be a coin toss the reader
  cannot see.
- `_document_line` renders it above the processor's own note (LP-839): what the document must show,
  then anything the processor adds about this particular one.
- **21 rules authored** — the request-driving ones, including every rule named in the report.
  The remaining 57 that declare `requires_documents` are silent and render exactly as today.

## A trap that was already closed

A `$` in an ask looked like a live hazard: the stored body keeps `$borrower_first_name` unresolved,
so a later `Template.substitute` pass sees whatever the ask contains, and a rule author writing about
money will eventually type one. It is already safe — `finalise_draft_body` uses `safe_substitute`
precisely because need titles contain dollar amounts (LP-823 measured that). Pinned end to end
anyway, through the second pass rather than only at composition: `$AMOUNT` is the test, not `$2,000`,
because a digit cannot begin a placeholder identifier and so proves nothing.

## Note for review

The 21 asks are authored prose about mortgage documents. They are the part of this ticket least
defended by tests — every one of them can be well-formed, pass every check, and still be wrong about
what a document has to show.

## Two defects this build introduced and the tests caught

Recorded because both are the same shape — a rebuild copied from the wrong baseline — and only one
of them had a test.

**The view rebuild dropped three columns.** `readonly.needs_items` had to be re-cut to expose the new
column, and the first version was copied from C7's definition. LP-631 had since added
`covered_by_document_id`, `coverage_note` and `coverage_reviewed`, and LP-634 added `explanation`.
Rebuilding from C7 silently removed all four. `test_no_model_column_drifts` caught it, which is
exactly the case its docstring names: "or worse, passing while a rebuilt view quietly dropped one."

**The same rebuild dropped the GRANT, and nothing caught it.** `CREATE OR REPLACE VIEW` cannot change
a column list, so a new column means `DROP VIEW` + `CREATE VIEW` — and Postgres takes the privileges
with the old view. The rebuilt view would have had every right column, passed the drift guard, and
`mbai_readonly` could not read it: the entire `./scripts/deploy staging query` path returns
"permission denied for view", and nothing in the suite says a word, because a grant is not a column.

`test_every_migration_that_recreates_a_readonly_view_regrants_it` now derives the rule over the whole
versions directory rather than listing migrations, for the reason b7's field-name guard gives: a list
goes stale precisely when someone adds the migration it needed to cover.

**Its first version passed against the bug.** It sliced the file from the top down to `def downgrade`,
so the module-level `_GRANT = """… GRANT SELECT …"""` constant satisfied the check whether or not
`upgrade()` ever executed it — and the mutant that deleted the `op.execute(_GRANT)` call passed. The
constant's existence is not the property; running it is. It reads the `upgrade()` body now, and the
mutant fails.
