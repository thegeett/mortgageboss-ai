# LP-372 — Settle ID-4's filter gate (the last uncertain rule of the 11)

## WHAT THIS TICKET IS

ID-4 (current-address consistency) is a **LIVE, auto-shipping** consistency rule on an **identity-fraud**
signal. LP-370's audit found it **UNCERTAIN** and explicitly refused to call it correct — *"this is exactly the
call that let AS-1/ID-2/ID-3 survive, so I am NOT calling it correct."* The worry: when ≥2 address candidates
exist, if ANY candidate's `id.current_address_type` is `unknown`, the engine **vetoes the whole per-borrower
comparison → couldnt_check**. Since realistic files carry documents whose address the AI types `unknown`, ID-4
might be **structurally incapable of ever firing** — a false-green on identity fraud. This ticket settles it
**with evidence**, on the real DB file (run `01039e93`, LF-6T3N). Backend only.

**The NEW shape** (LP-370 §7): not an absent tag, not a wrong field — **a present, materialized filter tag whose
`unknown` value on ONE candidate vetoes an entire per-subject comparison.**

## ACCEPTANCE CRITERIA

- D1/D2/D3 argued from the real reasoning strings, not assumed.
- The decision implemented **generically** (no rule-id branch in the engine) OR reported as a producer fix.
- ID-4's **real before/after** on LF-6T3N reported (not predicted).
- Tests both directions (agree → satisfied; disagree → surfaces); the accepted trade-off **named in a test**.
- Equivalence for every other live rule; ruff + mypy + full suite green.

## D1 — WHAT THE 28 `unknown`s ACTUALLY ARE (the pivot — it nearly dissolves the question)

I read the reasoning strings from the persisted snapshot (run `01039e93`). **`unknown` is honest and correct,
not a mislabelled absent.** The address-bearing sources typed `unknown` are **subject-property documents**:

| document | address | `current_address_type` reasoning |
|---|---|---|
| purchase_agreement | 2619 Mary Butler Way | *"This is the subject property being purchased, not the buyer's residence address."* |
| mortgage_statement ×4 | 340 Uptown West Drive | *"shows the mortgaged property address but does not indicate whether this is the borrower's residence."* |
| property_tax_bill ×2 | 340 Uptown West Drive / 2619… | *"does not indicate whose residence it is."* |

- The bank_statements, pay_stubs, W-2s, and investment_accounts all have **`id.address_normalized = unknown`** →
  they are excluded **before** the candidate stage (`consistency.py`, the `_UNKNOWN` gather-skip), so they
  **never reach the filter gate.** LP-370's "bank statements poison it" hypothesis is **not** what happens on
  this file — they drop out one step earlier via the gather tag.
- So `unknown` on the filter tag means *"there is an address, but it is not the holder's residence"* — the
  **producer is doing its job.** `absent ≠ unknown` holds. `id.current_address_type` even declares `unknown` as
  an allowed enum value (`fact_tags.csv`), meaning "a stated address I cannot type."
- **Per-borrower reality:** each borrower has exactly ONE residence-typed source — their driver's license.
  There is no 1003/URLA, no VOE — no second residence source. The only other candidate reaching the gather is
  the shared purchase agreement (property address, typed `unknown`).

**Decisive consequence:** on LF-6T3N, ID-4 couldnt_checks **under either policy** — excluding the `unknown`
candidate still leaves 1 residence source per borrower (`<2` → couldnt_check, ID-3's thin-data shape). **So this
file cannot, by itself, exercise the veto-vs-exclude choice** — settling it needs a file with ≥2 confidently-
typed residences plus an `unknown` candidate. That is the honest limit. But the choice is decidable **on
principle** (below), and D1 shows the gate is **innocent of a producer bug**.

## D2 — IS IT A PRODUCER PROBLEM? (No, on this file)

The AI correctly types property addresses as non-residence — that is not under-typing, it is the tag reporting
what the document STATES (LP-335's principle). No prompt change is warranted, and the `id_address` prompt is
**UNMEASURED** (LP-343/334) — iterating it against numbers would repeat the LP-335/340 mistake. **A Priya /
domain question remains (flagged, not decided):** *is a bank statement's stated address a `residence`?* On this
file the bank statements were typed `address_normalized=unknown` (no address surfaced), a separate producer
question this ticket does not touch.

## D3 — THE GATE (both failures named)

The veto is **inconsistent with the codebase's own invariant**:

- A **gather-tag** `unknown` is *already* treated as "absent-for-comparison → exclude" (`consistency.py`; the
  bank-statement case, `test_id4_non_address_document_with_unknown_tags_does_not_poison`).
- An **absent** filter tag is *already* silently excluded, no veto.
- Only a **present** filter tag valued `unknown` VETOED → **"honest unknown" punished more harshly than
  "absent"** — an inversion of `absent ≠ unknown`.

Its rationale ("if I can't trust the classification I can't trust the comparison") is **refuted by the reasoning
strings**: the classifier is confidently, correctly declining to call a property address a residence — that is
it working, not failing. And because the purchase agreement is in **every purchase file** and correctly typed
`unknown`, the veto made ID-4 **uniformly couldnt_check** on realistic files (LP-333: a uniformly-couldnt_check
rule is a FAILURE).

**The two failures:**
- **veto** → uniform couldnt_check → Tab 1 noise → processors learn to ignore the tab that matters, and ID-4
  never protects anything.
- **plain-exclude** → a disagreeing residence hiding behind `unknown` is silently dropped → an auto-shipped
  false-green on identity fraud.

## THE DECISION — (c) EXCLUDE + SURFACE

Treat an AI `unknown` filter-type as **absent-for-comparison**: exclude the source (like an absent filter tag,
like the gather-tag `unknown`), keep it out of the veto gate, **and surface the count of type-undetermined
exclusions in the finding's reason** so a residence hiding behind `unknown` is not silently dropped. **KEEP** the
confidence gate for a present, CONCRETE-but-shaky type (a `residence`/`mailing` label below the floor) — that is
a genuine shaky inclusion decision. This closes plain-exclude's gap (the human sees what was dropped) while
avoiding the veto's uniform failure.

**Accepted trade-off (named in a test so a reversal is findable):** if the ONLY disagreeing residence were hidden
behind an `unknown` type, the discrepancy surfaces only as an exclusion count, not as a `fired`. Accepted over
couldnt_checking every purchase file on its subject-property address. Reversible by restoring the veto.

## WHAT WAS BUILT

`backend/app/verification/rule_engine/consistency.py` — GENERIC, no rule-id branch:
- `_borrower_documents`: a candidate whose **present** filter tag value is `unknown` is now excluded WITHOUT
  being added to `filter_tags` (so it cannot veto), and counted in a new `type_undetermined` field. Only a
  present, CONCRETE filter tag still enters the confidence gate.
- `_GatherResult.type_undetermined` (new); the evaluator builds an `excluded_note` and appends it to the
  `<2`-couldnt_check reason and to the `on_agree` / `on_disagree` outcomes (`_outcome_result` gained a
  `reason_suffix`). Empty for the common case and for every filterless rule → their reasons are unchanged.

**ID-4 is the only spec with a `gather_filter`** — ID-1/2/3 and IN-5 have `gather_filter=None` and skip the
branch entirely, so no other live rule's behavior changes.

## ID-4's REAL BEFORE/AFTER (run `01039e93`, LF-6T3N — reported, not predicted)

Replayed deterministically (no AI call — `<2` residence sources per borrower):

- **BEFORE:** 2 couldnt_check — *"the 'id.current_address_type' classification that decides which sources to
  compare is not trustworthy: load-bearing tag 'doc067c2…' is unknown"* (`doc067c2` = the purchase agreement,
  2619 Mary Butler Way — the veto fired on the subject property).
- **AFTER:** 2 couldnt_check — *"only 1 source(s) carry 'id.address_normalized' of type 'residence' … nothing to
  compare across sources (1 other address-bearing source(s) could not be typed as 'residence' and were excluded
  from the compare)."*

**Same verdict, HONEST root.** The couldnt_check is now attributed to **thin data** (one residence source per
borrower — the DL; no 1003), with the excluded property document surfaced — not to a fabricated "classifier
untrustworthy." **The named root of the remaining couldnt_check: thin data, not the gate.** On a richer file
(DL + 1003 both `residence` + an `unknown` candidate) ID-4 now COMPARES and satisfies/fires (pinned by tests).

## TESTS

`backend/tests/verification/rule_engine/test_consistency.py`:
- **DELIBERATELY CHANGED** `test_id4_unknown_residence_classification_gates_to_couldnt_check` →
  `test_id4_unknown_type_is_excluded_not_vetoed`: 2 residences agree + 1 `unknown`-typed candidate → **satisfied**

- **NEW** `test_id4_unknown_type_does_not_mask_a_real_discrepancy`: 2 residences DISAGREE + 1 `unknown` candidate

  residence + 1 `unknown` purchase agreement) → couldnt_check with the honest "only 1 source … excluded" reason;

- KEPT (unchanged, still green): the low-confidence CONCRETE-type gates (`…gates_to_needs_review`,
  `…shaky_excluded_source_still_gates_the_subject`), the confident-mailing clean exclusion, and the
  non-address-document (`address_normalized=unknown`) no-poison test.

Full suite: **2349 passed, 5 skipped, 1 xfailed**; ruff + mypy (284 files) green.

## ASSUMPTIONS / DECISIONS

- **The gate was INNOCENT of a producer bug on this file** (D1) — evidence: the reasoning strings show correct
  `unknown` typing of property addresses; bank statements dropped out via `address_normalized=unknown`, not via
  the filter gate.
- **The decision is generic and touches only ID-4** — evidence: ID-4 is the sole spec declaring a `gather_filter`;
  filterless rules skip the branch (their reasons byte-identical; full suite green).
- **This is NOT a "correct, not a bug" pass on ID-4** — the veto *was* over-aggressive (uniform couldnt_check on
  the correctly-typed subject property). The change is a real fix, evidenced by the before/after and the new
  both-direction tests.

## THE HONEST LIMIT

- **One file, and it cannot exercise the veto-vs-exclude choice directly** — LF-6T3N has 1 residence source per
  borrower, so it couldnt_checks under either policy. A file with a 1003 (a second residence source) + an
  `unknown`-typed candidate would exercise the compare path on real data. The principle-level argument (the
  `absent ≠ unknown` invariant, the reasoning strings) is what settles it here; the tests exercise the compare
  path on synthetic data.
- **The `id_address` prompt is UNMEASURED** (LP-343/334) — it should join **LP-379**'s calibration worksheet.
- **Priya item:** is a bank statement's stated address a `residence`? Not decided here.
