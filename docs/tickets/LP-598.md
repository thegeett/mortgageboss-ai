# LP-598 — The cross-check tab renamed seven findings and called it resolution

## What you saw

> "Some of Cross check has Resolved by a file change, not sure what make them resolve."
> "Non-permanent resident alien status has no supporting documentation is open but Non-permanent
> resident alien status vs. supporting documents is also Resolved by a file change"

Both halves of the same defect. One snapshot change on LF-3CVT — LP-596's owned-property schedule
landing in it — and **every** cross-check finding changed identity at once:

| resolved (old key) | open (new key) |
|---|---|
| `citizenship_documentation` | `citizenship_status_no_supporting_documents` |
| `credit_report_absent` | `liability_balances_no_credit_report` |
| `income_documentation_absent` | `stated_income_no_documentation` |
| `asset_documentation_absent` | `asset_value_no_statements` |
| `property_taxes_insurance_missing` | `property_taxes_insurance_hoa_missing` |
| `existing_mortgage_payoff_balance` | `existing_mortgage_balance_mismatch` |

Nothing resolved. The model re-phrased its own category slugs, seven findings read as *"resolved by a
file change"*, and eight identical ones opened beside them. This is precisely the consistency
requirement it was built to meet — *"it should change only if there is real change in snapshot"* — and
it failed on the first snapshot change it met.

## Why

`finding_key` hashes `kind` + `sources`. Its docstring already explains that model-authored strings
drift and normalises the **sources** for exactly that reason:

> "The SOURCE strings are model-authored too, which the first version missed: it hashed them verbatim
> ... They are normalised first, so identity survives the model's phrasing of its own evidence."

And then hashed `kind` **verbatim**, immediately beside that comment. `kind` was
`<short_snake_case_category>` — free text, drifting exactly as much as the title it deliberately
excluded. The reasoning was right and applied to one of the two fields.

## The fix

`kind` is now a **closed vocabulary** of six: `value_mismatch`, `identity_mismatch`,
`date_inconsistency`, `undisclosed_obligation`, `calculation_blocked`, `other`. Anything off-vocabulary
collapses to `other` rather than being kept verbatim, because a verbatim slug is what broke identity.
Identity stays `(kind, normalised sources)` rather than sources alone, so two genuinely different
observations about the same fact pair remain two findings — the kind can now only change when the
model actually re-categorises.

A test pins that the prompt offers exactly the six the code enforces: a prompt advertising a seventh
that the code silently rewrites would reintroduce drift by another route.

## The second defect in the same run

Three of the eight "findings" were passes:

- `loan_amount_vs_note_amount` — *"These figures match"*
- `property_value_consistency` — *"All three figures agree"*
- `existing_mortgage_balance_mismatch` — titled a mismatch, detail reading *"These figures match,
  confirming consistency"*

The prompt caused it. It said *"Also say when figures that LOOK inconsistent are actually
consistent"*, and the model obliged. Well-intentioned — it was meant to stop a processor chasing
amortization — but it filled a discrepancy tab with confirmations, and the third one is worse than
noise: **the title is what a processor scans**, and that one sends them after nothing.

The invitation is replaced by a prohibition (agreement is silence), backed by a narrow check on the
**contradiction** — a mismatch headline over a body stating the figures agree. Deliberately narrow: a
finding that merely mentions agreement while reporting a real discrepancy elsewhere is kept, and a
test pins that.

## And the category fix that looked applied and was not

The same run showed all thirty findings still filed as `assets` — after LP-595 deployed. `reconcile_run`
reads the category map only when **minting**; carry-forward never refreshed it. So the fix was correct
and invisible, which is worse than one that visibly fails.

`_update_finding` now refreshes the category. Safe to overwrite because a category is *derived* from
the rule id rather than chosen by anyone — unlike `resolution_status`, which stays untouched and has
its own test.

## Tests

12 new, all mutation-checked: hashing `kind` verbatim again, dropping the vocabulary, removing the
contradiction guard, removing the category refresh, and clobbering a human's resolution each fail.
The rename table above is asserted as data, so a future change to normalisation has to face the real
slugs. Full suite green: **5429 passed**.

## Expect one more churn

Changing the key derivation changes every stored key once. None of the existing slugs were in the new
vocabulary, so on the next run all of them resolve and reopen a final time. After that they are
stable, and a snapshot change moves only the findings it actually affects.
