# LP-403 — Widen the holder_name_variance gate to `yes OR unknown`

## What this ticket is

LP-402 refined `owner_matches_borrower` to Priya's rule (yes=certain, unknown=flag-for-evidence, no=non-match)
— which broke `holder_name_variance`: it gated on `owner_matches == "yes"`, so the flag cases (now `unknown`)
answered `none` and LOST the specific difference. That difference is HOW "the document still counts via
holder_name_variance" works. This widens the gate to `yes OR unknown` and re-scores. **The coupling is fixed —
the flag-for-evidence documents now record their difference again.**

## Acceptance criteria (met)

- The variance gate is `owner_matches in ("yes","unknown")`; `none` only for a genuine `no`; the value set
  unchanged.
- Re-scored: the flag/`unknown` cases now RECORD a difference (not `none`); `owner_matches` + `co_holder`
  unchanged (11/11 each); the 5 real LF-6T3N goldens intact.
- Only the variance gate clause changed; AS-6 untouched; `ACTIVE_RULE_IDS` = 24; full suite green.

## Phase 0 — the report

- **The gate clause** was: *"DESCRIBE how the stated holder name DIFFERS from the borrower it matched (this
  applies when owner_matches_borrower is 'yes'). … use 'none' when owner_matches_borrower is NOT 'yes'."*
- **The flag targets (Priya's variance goldens):** N2→`nickname`, N7→`surname_differs`, P2→`other`. These are
  the `unknown` cases that lost their difference under the old gate.
- **A finding surfaced in Phase 0:** Priya's variance goldens describe the difference even for the `no` cases —
  N1→`middle_differs`, N3/N4/N6→`other` (all `owner_matches=no`). The `yes OR unknown` gate keeps those at
  `none`. Reported below.

## Phase 1 — the gate change (quoted, before → after)

- **Before:** `… (this applies when owner_matches_borrower is "yes"). … use "none" when owner_matches_borrower
  is not "yes" …`
- **After:** `… how the stated holder name DIFFERS from the borrower it matches or PLAUSIBLY matches (this
  applies when owner_matches_borrower is "yes" OR "unknown" — a flagged-for-evidence "unknown" is still a
  plausible borrower whose specific difference MUST be recorded). … use "none" when owner_matches_borrower is
  "no" (a genuine non-match — there is no borrower to differ from).`

The value set, the descriptive-not-verdict framing, `unknown` first-class, and the always-output rule are
unchanged. **No other prompt touched.**

### The coupling is CLOSED (the ticket's goal)

The three flag/`unknown` cases now **RECORD a difference instead of `none`:** N2→`other`, N7→`surname_differs`,
P2→`nickname`. So a flagged-for-evidence document once again carries the reason (the specific name difference),
which is exactly the mechanism Priya's ruling depends on. **The flag documents no longer lose their difference.**

### Two residual divergences vs her exact labels (NOT gate issues — a Priya round)

1. **A taxonomy swap on the flag cases:** she labeled **N2 (Roberta) = `nickname`, P2 (Bob) = `other`**; the AI
   says **N2 = `other`, P2 = `nickname`**. The AI's calls are the conventional ones (Bob IS the classic
   nickname of Robert; Roberta is a distinct given name) — **her labels may be swapped.** The difference is
   RECORDED either way (both non-`none`), so the coupling works; the exact value is a label question for her.
2. **The `no` cases (N1/N3/N4/N6):** her goldens describe rejected non-matches (N1→`middle_differs`,
   N3/N4/N6→`other`); the gate yields `none` (`owner_matches=no`). Whether variance should ALSO describe a
   genuine non-match (to explain the rejection) is a design question — for the flag-for-evidence mechanism it
   is NOT needed (a `no` is a rejection/finding, not a flag). Her `no`-case labels suggest a possible further
   "describe non-matches too," but that is beyond this coupling fix.

The 5/11 is these residuals plus the 4 `yes` cases (all correct) + N7 (`surname_differs`, correct). **No flag
case still says `none`** — so the ADR trigger ("variance still `none` for `unknown`") did not fire.

### The real-LF-6T3N check (the equivalence that matters most)

The 5 real LF-6T3N owner_matches goldens are **all still `yes`**, and `is_reserve_eligible` is **unchanged (all
`yes`)**. Variance on those statements is `middle_absent` (the holder "Jordan A Rivera" carries a middle the
roster "Jordan Rivera" lacks — a `yes` case, so unaffected by the gate widening; it was `middle_absent` before
too). **The sibling tags + real goldens are intact.**
