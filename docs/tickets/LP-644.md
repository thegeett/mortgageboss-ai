# LP-644 — make a verification run faster without moving a verdict

- **Status:** Not started — §1 (instrumentation) should land before anything else is chosen
- **Date:** 2026-09-05
- **Asked for by:** the user, 2026-09-05: *"How can we make each run verification faster without
  lossing quality"* and *"what percentage we might save?"*
- **Scope:** Backend — `services/tag_production.py`, `verification/tag_materialization/producer.py`
  and `ai.py`, `services/verification_run.py` (`TagCaches`), `services/tag_correlation.py`
- **Does not touch:** any prompt, any context, any threshold, any rule. That constraint is what
  makes most of this ticket safe, and §5 is the one item that breaks it.

## The constraint this ticket is written under

"Without losing quality" is doing real work here. Every change below is sorted by whether it can
move a verdict:

* **Cannot** — the same questions, asked at the same time as each other rather than one after the
  next (§2), or the same question whose answer was already computed (§3).
* **Can** — anything that changes what is in a prompt (§5).

LP-635 already made that argument once, for Stage B, and it held: the prompts, contexts and
resolution logic were untouched, so a verdict could not move, and a test pinned the serial and
concurrent paths tag-for-tag. §2 is applying the same proven change to the two stages that did not
get it.

## Where the time goes today

Four places make AI calls. **Exactly one of them is concurrent.**

| Stage | Batching | Concurrency | Shape in code |
|---|---|---|---|
| `stage_a` | 15 subjects/call | **sequential** | `tag_production.py:191` — `for batch in _chunks(...)`, `await` inside |
| `stage_b` | none — one call per money-in deposit | **8** | `tag_correlation.py:423` — LP-635 |
| `materialization` | 15 subjects/call | **sequential x sequential** | `producer.py:88` loops 23 groups, each awaiting `ai.py:343`'s batch loop |
| `cross_source` | — | single call | `verification_run.py:1224` |

The `rules` stage is deterministic (ADR: AI for perception only), so there is nothing to win there.

**Materialization is doubly sequential** and that is the least-known fact in this ticket:
`producer.py` awaits each of the 23 declared AI groups in turn, and inside each,
`produce_ai_group_tags` awaits each batch in turn. Nothing overlaps with anything.

## The measured baseline

From `LP-635.md`, over LF-ZE9N's failed run (44 documents): **591 AI calls, 2,542s of cumulative
model latency, 4.3s mean**. The same ticket records the per-stage split: **12 Stage A calls, 26
AI-group calls**, ~1 needs, ~1 cross-source.

That leaves ~551 for Stage B. That figure is a remainder, so it is corroborated rather than trusted:
LP-635 states independently that Stage B "judges once per money-in deposit, with no batching at all,
so on a document-heavy file it makes the great majority of the calls." Two independent statements
agreeing is the basis for using it; it is still the number to check first when §1 lands.

Applying each stage's current concurrency to those counts:

| Stage | Calls | Concurrency | Wall-clock at 4.3s |
|---|---:|---:|---:|
| Stage A | 12 | 1 | ~52 s |
| Stage B | ~551 | 8 | ~296 s |
| Materialization | 26 | 1 | ~112 s |
| cross_source | ~1 | 1 | ~4 s |
| **AI waiting** | **591** | | **~464 s** |

LF-ZE9N's completed run took **946 s**. So AI waiting is roughly half of it, and **~49% is the
ceiling for everything in this ticket** — the rest is snapshot build, the rule engine and DB work,
which no amount of AI concurrency touches.

## 1. Instrument the stages before changing them

**This should land first, and on its own.** Every number above is derived from call counts times a
mean. Nothing in the system records how long a stage actually took, so the split between AI and
non-AI time — the number that decides whether the rest of this ticket is worth doing — is the one
with the least evidence behind it.

The log lines already exist (`stage_a_production_done`, `stage_b_production_done`) and already carry
token counts and cost. Add elapsed seconds and call count to those, add the equivalent for the
materialization producer and cross_source, and record the run's non-AI remainder.

Cost: an hour or so, no behaviour change, no quality risk. What it buys: the four rows of the table
above stop being projections. **Three things could each move them materially**, and only measurement
separates them:

* the 4.3s mean predates every fix since and was taken on a FAILING run;
* per-call latency under concurrency 8 may be higher than serial latency (server-side contention),
  which would shrink §2's win specifically;
* the call counts are from ONE file — a file with fewer bank statements shifts the balance away from
  Stage B entirely.

## 2. Concurrency for materialization and Stage A — ~15%

Apply LP-635's pattern to the two stages that never got it. `_judge_concurrently` in
`tag_correlation.py` is the existing shape: plan the calls, dispatch the distinct ones under a
bounded semaphore, apply the results in the original order so accounting and the breaker see the
same sequence.

Two levels for materialization, and the outer one is the bigger win: across the 23 groups
(`producer.py:88`), then across batches within a group (`ai.py:343`).

| | now | after | saved |
|---|---:|---:|---:|
| Stage A | ~52 s | ~9 s | ~43 s |
| Materialization | ~112 s | ~17 s | ~95 s |
| **Total** | | | **~138 s** |

**~30% of AI waiting, ~15% of a 946s run.** Quality risk: none, by the §0 argument.

Carry over LP-635's hard-won details rather than rediscovering them: the breaker must be able to
stop DISPATCH and not only counting (an outage otherwise pays for the whole stage before the counter
sees one failure); an outcome must be applied once per CALL, not once per subject sharing it; and
`gather` must collect before re-raising, or a bug leaves siblings billing against an unwound caller.

## 3. Persist the tag caches across runs — up to ~44% on a re-run

`TagCaches` (`verification_run.py:321`) is `field(default_factory=dict)`, and
`verification_run.py:963` does `caches = caches or TagCaches()`. **It is rebuilt every invocation.**
So a re-run re-pays for every AI call the previous run already made.

The keys are already content fingerprints, so persisting them is safe by construction — same input,
same cached answer. `tag_production.py:101-106` says so in as many words:

> Keyed on the four raw Fields (not the content_id), so identical-content transactions share one AI
> judgment and **an unchanged transaction is a cache hit across re-runs.**

That last clause is not true today. The cache cannot outlive the invocation, so the docstring
describes a behaviour the code does not provide — the same defect class LP-637/638/639 kept finding,
sitting in the middle of the performance path.

**Why this matters more than its percentage suggests.** The API already short-circuits a re-run whose
inputs are byte-identical (`verification.py` returns the cached findings without calling the AI). The
case this fixes is the common one that endpoint does NOT cover: a processor corrects one document's
type, or uploads one more, and the file re-pays for all 44 documents' worth of AI work to answer 43
questions it has already answered.

Sizing: if 90% of subjects are unchanged on a typical re-run, AI waiting drops from ~464 s to ~46 s
— **~44% of a 946 s run**. The real hit rate is unknown and is the second thing §1 should measure.

Design notes for whoever builds it: the cache is per loan file and keyed by content fingerprint, so a
table keyed `(loan_file_id, cache_kind, fingerprint)` with the resolved value is the obvious shape.
It must store only cacheable outcomes — `tag_correlation.py` already draws that line (a failed,
truncated or malformed judgment is `cacheable=False` and must retry next run). And it needs an
eviction story, or a file edited fifty times accumulates fifty generations of dead fingerprints.

## 4. Raise the concurrency bound above 8 — unknown, measure first

`_MAX_CONCURRENT_JUDGMENTS = 8` was chosen conservatively and the requests axis has room:
`bedrock_rpm_budget = 2000` across `worker_desired_count 1 x worker_concurrency 4` = 500 RPM per
process = **~8.3 calls/s**, against ~1.9 delivered at concurrency 8 and a 4.3s mean. That is roughly
4.5x headroom.

**Do not turn this knob on that arithmetic alone.** `bedrock_rpm_budget`'s own comment records that
TOKENS per minute is expected to bind before requests do on document-heavy work, and that TPM is
unmeasured. A rejected Bedrock request still counts against quota, so pacing at the ceiling turns one
throttle into a self-sustaining one. Instrument TPM in §1, then decide.

## 5. Batch Stage B — ~29%, and the only item with real quality risk

Stage B is the only stage still making one call per subject. Fifteen deposits per call, the way
Stage A and the AI groups already work, would take ~551 calls to ~37: at concurrency 8 that is
~296 s to ~21 s, **~29% of a 946 s run** — the largest single win available.

**It changes the prompt, so a verdict can move.** That is a different category from everything above
and it is why LP-635 deferred it. It needs the calibration harness, and a batched run compared
subject-for-subject against a serial one on the same file before it ships.

Take it last, after §1 has measured what §2 and §3 actually delivered.

## Not worth doing

**Prompt caching.** Settled in LP-635 and not worth re-litigating: every stable prefix was measured
below the 4,096-token minimum for the model in use — Stage A ~1,127, Stage B ~787, the 23 AI-group
system prompts 131-1,127, needs ~2,936. The call that repeats hundreds of times (Stage B) is the one
furthest under. Nothing on this path can cache.

**Raising the time limit.** `run_limits.py` already ranks it last and says why: it buys a file the
ability to finish, it does not make finishing cheap. `MEASURED_SECONDS_PER_DOCUMENT = 35.6` also
carries its own instruction to re-measure — §1 is the occasion.

## Summary

| # | Change | Saved (946 s run) | Quality risk | Order |
|---|---|---:|---|---|
| 1 | Instrument per-stage timing | 0% | none | **first** |
| 2 | Concurrency: materialization + Stage A | ~15% | none | second |
| 3 | Persist tag caches across runs | ~44% *on a re-run* | none | third |
| 4 | Raise the concurrency bound | unknown | throttle risk | after §1 measures TPM |
| 5 | Batch Stage B | ~29% | **real** | last, with the harness |

§2 and §3 compose: §2 helps the first run of a file, §3 helps every run after it. Together they
approach the ~49% ceiling without touching a prompt.

Every percentage here is a projection from one file's call counts and a stale latency mean. §1 is
what turns them into measurements, and it is cheap enough that guessing instead is the worse trade.
