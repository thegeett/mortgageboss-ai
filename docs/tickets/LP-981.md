# LP-981 — Inbound mail module becomes shared plumbing; one mail bucket

- **Ticket:** LP-981, the first of the step-1 tickets in `loan-email.md` §15.
- **Status:** code only. Not applied. Receiving stays off
  (`inbound_mail_enabled = false`, `inbound_malware_scan_enabled = false`).

## What and why

The Terraform for receiving email was written for one inbox domain that MortgageBoss owned,
`imboxstaging.mortgageboss.ai`. It created that domain's SES identity, its DNS zone and its MX
record. The plan has changed: every customer gets their own email subdomain, and our own test
domain is `mail.staging.mortgageboss.ai`, which the outbound module already set up. So the receiving
module no longer owns a domain. It keeps only the parts every domain shares: the bucket, one SES
receipt rule, the notification topic, the queues and the malware scan.

Two more fixes come with that. The receipt rule now accepts mail for every verified domain instead
of one named domain, and it no longer asks SES to encrypt the message itself (that mode produces
files our worker cannot read; the bucket encrypts them instead). And the bucket becomes the one
place for all raw mail: `mbai-staging-mail`, with `inbound/` for mail SES receives and `outbound/`
for copies of mail we send (used from step 2).

## What changed

- `infra/modules/inbound_mail/main.tf`:
  - The SES domain identity, its verification, and the verification TXT and MX records are deleted.
  - The receipt rule loses `recipients` and the S3 action's `kms_key_arn`, and no longer waits on the deleted verification.
  - `local.outbound_prefix = "outbound/"` is added.
  - Lifecycle is one rule per prefix with identical settings.
  - The header and the comments on the rule are rewritten for the new shape.
- `infra/modules/inbound_mail/variables.tf`:
  - `mail_domain` and `route53_zone_id` are removed. Nothing else used them.
  - The `bucket_name` and `kms_key_arn` descriptions are updated.
- `infra/modules/inbound_mail/outputs.tf`:
  - `mail_domain` is removed.
  - `object_prefix` becomes `inbound_prefix`. Nothing outside the module read it.
  - `outbound_prefix` and `rule_set_name` are added.
- `infra/envs/staging/main.tf`:
  - `module "inbox_dns"` and its comment block are deleted, replaced by a three-line note.
  - `module "inbound_mail"` loses `mail_domain` and `route53_zone_id`.
  - `bucket_name` is now `"${var.name_prefix}-mail"`.
- `infra/envs/staging/outputs.tf`: `imbox_name_servers` is deleted. It read `module.inbox_dns`.

**Lifecycle choice.** I used one rule per prefix rather than one rule with no prefix filter. The
bucket does hold one other object: the GuardDuty validation object at the bucket root
(`malware_scan.tf`, `validation_object_key`). That object is meant never to expire, and an
unfiltered rule would expire it after five years. Both rules come from one `dynamic` block, so the
settings cannot drift apart.

## What was deliberately left alone, and why

- **`inbox_domain` stays, and so do its tfvars value and the `INBOX_DOMAIN` task env var**
  (`envs/staging/main.tf`, `environment[]`). The app reads it today to build every file's address,
  and removing it would break staging. Its only other uses fed the deleted `inbox_dns` zone and the
  module's `mail_domain`, and both of those are gone. Its description in `variables.tf` still talks
  about the imbox zone; I left it unchanged because the brief said to leave the variable exactly as
  it is.
- **`envs/dev`** has no `inbound_mail` or `inbox_dns` module. It sets only
  `INBOX_DOMAIN = "imboxdev.mortgageboss.ai"` in the task env, which is the same app setting as
  above, so it was left alone.
- **The rule name `${var.name_prefix}-inbound`** is unchanged, because the KMS key policy
  (`ses_receipt_rule_arns` in `envs/staging/main.tf`) and the bucket and topic policies are
  conditioned on that exact ARN.
- **The topic and queue names** still say `inbound-mail`. That is accurate: they carry received
  mail only.
- **Outputs not in the brief's list** (`queue_arn`, `dlq_arn`, `topic_arn`, `receipt_rule_name`,
  `scan_results_queue_arn`, `malware_scan_role_arn`) are kept. They are still correct, and
  LP-986 (IAM) and LP-988 (task wiring) are the likely readers.
- **The GuardDuty scan** stays scoped to `inbound/` (`object_prefixes`). `outbound/` holds mail we
  generated ourselves.

## KMS check (modules/secrets)

When `ses_receipt_rule_arns` is non-empty, the key policy grants `ses.amazonaws.com`
`kms:GenerateDataKey*` and `kms:Decrypt`. The grant is conditioned on `AWS:SourceAccount` and
`AWS:SourceArn` = the receipt rule. That matches AWS's page "Giving permissions to Amazon SES for
email receiving" (section "Give SES permission to use your AWS KMS key"), which says to add
`kms:Decrypt` when SES writes to an S3 bucket with server-side encryption. No change was made.

**One gap found, not changed:** the key policy has no statement for `sns.amazonaws.com`. The inbound
SNS topic and both SQS queues are encrypted with this same key, and SNS cannot deliver to a
KMS-encrypted SQS queue unless the key policy lets SNS use the key (`kms:GenerateDataKey*` and
`kms:Decrypt`). Without it, SES would store the message and publish to SNS, and the SNS-to-SQS
delivery would fail with nothing arriving in the queue. None of LP-982–989 covers this. It needs
adding before LP-989 proves the path end to end. See follow-ups.

## What this does NOT do

- No `terraform apply`. Receiving stays off, and both flags stay false in `terraform.tfvars`.
- No MX record on `mail.staging.mortgageboss.ai`. That is LP-982.
- The receipt rule set is not activated. It remains a manual, once-per-account step.
- `outbound/` stays empty and unused until step 2, when the worker writes a copy of each sent message there.

## Follow-ups

- **Remove `inbox_domain` / `INBOX_DOMAIN`** once the app builds addresses from the tenant's
  subdomain (step 2, address format `lf-<display_id>@<tenant subdomain>`). Do it in staging and dev
  together.
- **KMS: add a `sns.amazonaws.com` statement** (`kms:GenerateDataKey*`, `kms:Decrypt`) to the shared
  key policy, conditioned on the inbound topic. Without it, SNS cannot deliver to the encrypted
  queues. It belongs before LP-989, and could go into LP-982 or LP-983 (the events queue is likely
  to be encrypted with the same key and have the same need).
- **Refresh the `inbox_domain` description** in `envs/staging/variables.tf` when the variable is
  removed. It still describes the imbox zone.
