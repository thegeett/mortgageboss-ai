# LP-377 — LP-365's three run-level fail-open bugs

## WHAT THIS TICKET IS

The verification run wrapper claims fail-closed and, at LP-365's original commit, was fail-open in all three
of its paths. All three are **run-level false-greens** — the run reports COMPLETED when the governed engine
never ran, or serves stale findings as current. This is the exact class the architecture spends every ticket
preventing at the FINDING level (gates, confidence floors, `couldnt_check`, `absent ≠ 0`). **The honesty
contract did not survive one layer up.** One of the three already cost real time: it served ~12-hour-old
findings as current, and a human concluded the engine was broken when five fixes simply had not been re-run.

## THE GATE-OF-RECORD FINDING (Phase 0)

The ticket was written from LP-365's **original** commit (`a697cbb`). A **review commit landed after it** —
`0000088` *"LP-365 review: make the fail-closed run status atomic across the two tasks"* — which **already
fixed BUG 1 and BUG 2 and replaced the false-confidence test.** Verified against the live code:

- **BUG 1 (atomic status) — already fixed, correct.** `cross_source.py` re-reads status under a row lock
  (`SELECT status ... FOR UPDATE`) and sets COMPLETED only if the fresh DB value is not FAILED; the lock is
  held to commit, so the rule pass's unconditional `UPDATE status=FAILED` serializes after and stays sticky.
  Checked both orderings — **FAILED wins regardless of commit order.** The stale in-memory ORM check is gone.
- **BUG 2 (visible enqueue failure) — already fixed, symmetric.** `_enqueue_rule_engine` returns a bool and
  the caller marks the run FAILED on an enqueue failure, mirroring `_enqueue_cross_source`. A run can no
  longer read COMPLETED with the governed pass never enqueued.
- **The false-confidence test — already gone.** `test_sweep_completion_never_overwrites_a_failed_run` (which
  pinned a `SimpleNamespace(status=FAILED)` that cannot occur cross-session) no longer exists; the review
  commit rewrote it to model the guard as a function of the LOCKED DB value.

→ **LP-377's real remaining work is BUG 3 — the rule-aware cache key**, which the review commit explicitly
deferred: *"Not fixed (acknowledged in-commit, its own ticket): the cross-source-keyed fingerprint cache can
skip a rule-relevant-only change — needs a rule-aware key."* This ticket is that.

## ACCEPTANCE CRITERIA

- A rule/spec/tag change with UNCHANGED documents re-runs the governed pass (no stale hit) — the bug that bit.
- The cache still hits on a genuine no-op (same inputs + same engine → no wasted AI sweep); the force-run link
  (LP-376-A) still bypasses it.
- No engine/rule/tag/spec change; `ACTIVE_RULE_IDS` unchanged; the sweep's happy-path behaviour identical; the
  frozen fixture trace unchanged; the run's status decisions (BUG 1/2, already shipped) recorded, not altered.
- Every fix has a test that FAILS on the pre-fix code. Full backend suite green; ruff + mypy clean.

## THE PHASE-0 ARGUMENT

### The run's status on partial failure (BUG 1, already decided)

**FAILED.** A run reads COMPLETED only if BOTH passes completed. A COMPLETED run atop a dead governed engine
is the false-green; the sweep's valid findings do not rescue the wrapper's contract ("COMPLETED = the engine
ran"). No new PARTIAL status (it would touch the UI, the watchdog, `_build_status`, the version selector for
no gain today). **No UI change is forced** — the existing FAILED surface + the force-run link handle it.

### The rule-aware key (BUG 3 — the design decision)

**Decision: an engine-aware fingerprint. NOT always-enqueue, NOT a manual constant.**

Fold an `engine_fingerprint()` into `compute_input_fingerprint`:
`sha256(engine_fingerprint ⊕ canonicalized cross-source context)`, where `engine_fingerprint()` hashes
`sorted(ACTIVE_RULE_IDS)` + the content bytes of every declarative artifact under `app/verification/rules/`
(the rule specs, `tag_production.yaml`, the fact/rule/tag/dependency CSVs, `vocabulary_extra.yaml`). Cached
per process (`@cache`) — these artifacts are immutable within a running process. A cache HIT now means "inputs
AND engine unchanged → the prior run's findings are genuinely current"; ANY declarative engine change misses
and re-runs the governed pass.

**Verified: all five historical incidents each touched a declarative file** →
`AS-1.yaml` (LP-366), `tag_production.yaml` (LP-369, LP-371, LP-374), `ID-4.yaml` (LP-372) — so all five would
now miss the cache.

**The rule pass's REAL per-run cost (why not always-enqueue).** LP-365 measured a real run at **~282s and
~$0.15–0.30 of AI** (Stage A + Stage B transaction tagging ≈ $0.087 for 17 deposits, plus AI materialization
for the live rules' groups). And `run_rule_engine_pass._run` calls `run_verification` **without threading
`caches=`**, so it builds a fresh `TagCaches()` every invocation — **the tag cache does not persist across task
runs.** Re-running is full re-materialization = full cost. Always-enqueue would DOUBLE AI spend on every no-op
Run — exactly what the cache exists to prevent. The rule pass cost is **not** small; the ticket's "if it's
cheap, always-enqueue is the honest answer" premise is falsified by the code.

**Why not a manual `ENGINE_VERSION` / `app_version`.** `settings.app_version` is a static `"0.1.0"`, never
bumped. A manual constant relies on a human remembering to bump it — the discipline that already failed five
times (LP-366/369/371/372/374). A key that can be forgotten re-introduces the exact silent miss. **A cache
MISS is cheap; a cache HIT that serves stale governed findings is a false-green. Fail toward re-running.**

**The alternatives weighed:**

| candidate | verdict |
|---|---|
| spec versions (`RuleSpec.spec_version` exists) | subsumed — hashing the spec files captures `spec_version` and everything else in them |
| hash of `tag_production.yaml` | included — it is one of the declarative artifacts hashed |
| prompt texts | partially — the extraction prompt FILES are not read at rule-run time; the engine's AI-group/judgment prompts are Python constants (the reported residual) |
| global `ENGINE_VERSION` constant / `app_version` | **rejected** — manual, forgettable; the exact failure that bit |
| always-enqueue the rule pass, cache only the sweep | **rejected** — the rule pass is ~$0.15–0.30/run with no cross-run tag cache; doubles AI spend on no-ops |
| **engine-content hash folded into the key (chosen)** | automatic, catches all five incidents, preserves the sweep-cost saving on genuine no-ops |

## WHAT WAS BUILT

- `app/services/cross_source.py`:
  - `engine_fingerprint()` — `@cache`d SHA-256 over `sorted(ACTIVE_RULE_IDS)` + the content bytes of the
    declarative `app/verification/rules/` surface (specs + `tag_production.yaml` + the CSVs + vocabulary).
  - `compute_input_fingerprint` now returns `sha256(engine_fingerprint ⊕ canonicalized context)` — both call
    sites (the sweep's stored fingerprint at completion, and the API's cache comparison) get the binding for
    free and stay consistent.
- BUG 1 and BUG 2: **verified already fixed** (review commit `0000088`); recorded here, not re-implemented.

## THE REPLACED TEST (and why the old one could not fail)

`test_sweep_completion_never_overwrites_a_failed_run` (BUG 1) hardcoded `status=FAILED` into one in-memory
object — a state that cannot occur cross-session — so it asserted a scenario that can't happen and missed the
one that can. **The bug shipped WITH a passing test.** The review commit replaced it with a test that models
the guard as a function of the LOCKED DB value. For BUG 3, this ticket adds:

- `test_input_fingerprint_binds_the_engine_version` (unit) — same inputs, different engine token → different
  fingerprint. **Fails on the pre-fix code** (which ignored the engine → equal hashes).
- `test_engine_fingerprint_changes_with_the_active_rule_set` — editing `ACTIVE_RULE_IDS` changes the digest.
- `test_rule_relevant_change_reruns_the_governed_pass` (endpoint) — a rule/spec/tag change with unchanged
  documents MISSES the cache and enqueues BOTH passes on a fresh RUNNING run. **Fails on the pre-fix code**
  (returns `completed` — the stale hit — instead of `running`). *Proven by reverting the binding and running
  the two tests: both fail; restored.*
- `test_governed_pass_enqueued_alongside_the_sweep_on_a_miss` — a miss enqueues the governed pass alongside
  the sweep.
- The LP-78.1 cache tests still pass unchanged (`test_unchanged_rerun_returns_cached_without_calling_ai`,
  `test_force_reruns_even_when_unchanged`, `test_cached_return_reconciles_staleness`).

## ASSUMPTIONS / DECISIONS + WHAT'S STILL OPEN

- **The reported residual (NOT worked around):** the engine's Python-resident logic and the AI-group/judgment
  prompts that live as Python constants (`tag_materialization/ai.py`, `subjects.py`, `ai/rule_judgment.py`) are
  not hashed — a change to those with zero declarative edit would not invalidate. Mitigations: such changes
  nearly always co-ship a spec/tag/registry edit (which does invalidate); the force-run link is the manual
  escape hatch; closable later by wiring `app_version` to the build/git-SHA or moving the Python-resident
  prompts to files. **Strictly smaller than the prior behaviour, which ignored the engine version entirely.**
- **Old runs' fingerprints** (engine-unaware) will not match the new key → the next Run re-runs. Correct —
  they were computed under an old engine; fail toward re-running.
- **The two passes still share ONE cache decision** (enqueue both or neither). Kept — the rule pass MUST run
  whenever the sweep does on a real change, and splitting the cache per-pass would fork the one-run-two-passes
  model for no benefit here.
- **No UI change** is forced by BUG 1's FAILED-on-partial-failure decision (reported per the ticket).
