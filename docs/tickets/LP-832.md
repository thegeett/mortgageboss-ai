# LP-832 — A request creates a new draft, and the old one stays

- **Ticket:** LP-832 · Phase 4 follow-up, from processor feedback
- **Status:** Built — awaiting review
- **Date:** 2026-09-07
- **Scope:** `services/email_draft.py`, `services/finding_resolution.py`, `api/communications.py`
- **Migration:** `b3f8d61a4c92` — drops the index that assumed one

---

## What was asked, and confirmed

> *"if user has request one document it creates draft. again if user request new document it creates
> new draft with two documents in it. if the previous darft has been marked sent, then next draft
> will be created fresh."*

Asked directly, because the alternative reading — one draft that grows — is what the system does
today and the sentence admits both. **Confirmed: a new draft row each time.**

| event | result |
|---|---|
| request Bank statements | **Draft 1**: Bank statements |
| request Pay stub | **Draft 2**: Bank statements, Pay stub · Draft 1 still in the list |
| mark Draft 2 sent | — |
| request W-2 | **Draft 3**: W-2 only — the set resets at a send |

So a draft carries **everything requested since the last send**, and each request writes a new one.

## What this breaks, stated before it is built

`get_open_draft` ends in **`scalar_one_or_none()`**. With two open drafts on a file it does not
return the newer one — it **raises `MultipleResultsFound`**, and it is called by the draft endpoint,
the send path, `open_draft_preview` and LP-826's badge. This ticket is not "also allow a second
draft"; it is the removal of a single-row assumption that four callers depend on.

Every one of those callers needs a defined answer to "which draft", and the answer is not the same
for all of them:

* the **send** path is given a `draft_id` already — it needs no lookup and must not acquire one;
* the **badge** (LP-826) counts what is waiting, which is now a set of drafts rather than one;
* `open_draft_preview` exists for the mail-client link and needs the newest, or to be given an id.

## The index that assumes one

LP-809 added a unique index so a file could not have two open drafts under one template key. If that
index is a partial unique on (loan_file_id, template_key) where status = DRAFT, it must go — and its
removal is the whole risk in this ticket, because it is the thing that has been preventing the state
this ticket now wants. **Check it before writing code**; if no such index exists, say so rather than
assuming the guard was elsewhere.

## Superseded drafts are the user's to manage

Confirmed with the ask: prior drafts stay in the list and are deleted or ignored by the processor.
Nothing supersedes automatically. That is a deliberate choice and it has a cost worth naming: a file
where five documents were requested one at a time carries five drafts, four of them subsets of the
fifth. If that reads as clutter in use, the answer is a "supersede" action a person takes, not an
automatic delete — a draft disappearing because the system decided it was stale is worse than a list
that needs tidying.

## Done when

- Two requests without a send produce two drafts; the second lists both documents; the first is
  unchanged and still in the list.
- A request after a send produces a draft carrying **only** what has been requested since — asserted
  with a document requested BEFORE the send, so a draft that carried everything would fail.
- `get_open_draft`'s single-row assumption is gone from every caller, and no path can raise
  `MultipleResultsFound`. A test creates two open drafts and exercises each caller.
- Deleting a superseded draft does not touch the needs items it named. They are on the needs list,
  which is the record; the draft is not.
- The needs a draft carries are the ones outstanding **at the moment it was created**, so an older
  draft does not silently gain a line when a newer request happens.

## For the reviewer

`scalar_one_or_none()` raising rather than returning is the part that will not show up in review by
reading. A file with one draft behaves identically before and after this change, so every existing
test passes either way — the two-open-drafts fixture is the only thing that exercises it, and it has
to be built deliberately.

## Built, 2026-09-09

### The index existed, and dropping it is the ticket

`uq_communications_open_draft` — a partial unique index on `(loan_file_id, template_key)` where
`status = 'draft' AND deleted_at IS NULL`. It is what made `scalar_one_or_none()` safe, so four
callers were written against a guarantee the **database** was holding rather than one they checked.

**What it was really buying is not lost.** Its own comment gave the reason as two near-simultaneous
requests each creating a draft *"with no basis for choosing between them"*. Under this model two
drafts are correct — two drafts each **missing the other's new document** is not, and that is what a
concurrent pair produces when both compute the outstanding set from the same pre-state.
`add_needs_to_draft` takes a row lock on the loan file instead: a guarantee the application holds.

A non-unique index on `(loan_file_id, status)` replaces it, because the reads it serves went from "at
most one row" to "as many as the processor has made".

**The downgrade raises rather than deleting.** Recreating a unique index over data this ticket makes
legal fails if any file holds two unsent drafts — which is the state the upgrade exists to allow. A
downgrade that deleted drafts to fit the old shape would destroy a processor's unsent work to satisfy
a constraint. It names the affected files so the decision is answerable.

### The outstanding set is a union, and one test proves it

*"Everything requested since the last send"* is expressed as the thing that is actually true rather
than as a time comparison: **a send closes its draft**, so the needs it carried leave the set by the
same statement that sent them. No clock, no window.

The union across open drafts and a read of the newest give identical answers while each draft is a
superset of the last. They diverge **only** when a processor deletes the newest — an action this
model invites, since superseded drafts are left in the list on purpose.

### The mutation that survived, and what it found

Three mutations run. Two were killed immediately. The third — **dropping `deleted_at IS NULL` from
the outstanding-set query** — passed every test.

The deleted-draft test had a comment saying *"the deleted draft's own document is gone with it"* and
**no assertion for it**. The fixture happened to satisfy the property either way; the words did the
work. Adding `assert "Pay stubs" not in body` kills it. That is the same failure this run has found
on both sides repeatedly: a green test that reads as proof.

| mutation | result |
|---|---|
| grow one draft instead of creating a new one | 3 failed |
| outstanding set ignores `deleted_at` | **survived → test fixed → 1 fails** |
| the row lock removed | 1 failed |

### Nothing new means no draft

A second click on a finding already carried adds nothing, and minting a duplicate draft with
identical contents would put a second identical email in the list for a request that did not happen.
The existing newest draft is returned and `added` is empty, so LP-826's outcome still reports
honestly that the draft took nothing — which is what keeps b7's ID-3 double-click fix meaningful.

This widens LP-809's review guard rather than adding a second one: *"do not mint an empty draft for a
request the borrower has no part in"* and *"do not mint a duplicate for a request that adds nothing"*
are the same rule — this request added no document, so the list must not change.

### Two tests inverted, one restated, none weakened

* `test_a_second_request_joins_the_first_draft` asserted `one.draft.id == two.draft.id` and a row
  count of 1. Now asserts two drafts — **and that the newest carries both documents**, because a
  model where each request drafted only its own document would satisfy the row count and mail the
  borrower twice. It also asserts the FIRST draft is unchanged: silently rewriting it would mail a
  borrower a list they were never shown.
* `test_a_second_open_draft_is_refused_by_the_database` asserted the index. Inverted, with the
  guarantee it provided moved to `test_the_draft_creation_path_locks_the_file` rather than dropped.
* `test_both_request_routes_accumulate_into_ONE_draft` → `..._ONE_LIST`. The membership count is what
  survived the model change, and it is what separates "two drafts" from "two emails".

The lock is asserted on the **emitted SQL**, and the limitation is stated in the test: this suite is
a single rollback-scoped transaction, so a genuine concurrent writer cannot be started without
leaving that isolation. The claim pinned is narrow — the statement is issued, before anything is
read — which is better than a comment nothing checks.

### The three standing checks

**Tenancy:** every new query is scoped by `loan_file_id` on a file the caller already resolved.
**Logging:** nothing added. **AI:** none — `_regenerate` is LP-817's deterministic render.
