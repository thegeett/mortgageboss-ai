# LP-476 — the rule census: verify LP-451 against post-v2 reality

## What this ticket is

`docs/tickets/LP-451.md` is the planning basis for everything downstream: it names all **83 unwritten in-scope
rules** and gives each a blocker. But it was written **2026-08-03, before the v2 bench**. It could name the
field a rule needs; it could not check whether that field **populates on a real document**. That gap is
**ADR-354** (schema presence ≠ data availability), and it is why three prior tag-writing attempts
under-delivered.

This ticket re-verifies LP-451 against the **303 stored extractions** — no re-run, no model calls, **$0**.
Where LP-451 or `work_breakdown_130_rules.md` claims something the documents contradict, **the documents win
and the contradiction is named**.

Three outputs were planned: the six-extractor answer (Phase A), the 83-rule census (Phase B), and a populated
`tag_dependencies.csv` (Phase C). **Two landed. Phase C did not, and why is itself a finding** — the file is
generated and its emptiness is deliberate and test-pinned.

## PHASE B — the 83-rule census

### Method (as specified, and where it bit)

`typed_core` is a flat map, so a wrong field name and an empty field are indistinguishable. Every measurement
therefore: (1) enumerated the **real key set** per document type from the records; (2) took the field list from
the specs + LP-451; (3) reported a miss as **NAME MISMATCH** or **FIELD ABSENT**, never as 0% fill; (4)
computed fill **within the document type**.

**⚠️ LP-451's field names are shorthand, not literal.** Three of the names it gives do not exist; the real
fields do, and fill:

| LP-451 wrote | the real key | fill |
|---|---|---|
| `aus_dti` | `aus_dti_ratio` | 1/1 |
| `aus_ltv` | `aus_ltv_ratio` | 1/1 |
| `repairs_required` | `repairs_required_indicator` | 2/2 |

Measured naively these read as 0% — the exact failure the method warns about. **PE-2's `fha_case_number` is the
one genuine absence** (it exists nowhere), which is why the census separates NAME-MISMATCH from FIELD-ABSENT.

## PHASE C — `tag_dependencies.csv` — NOT populated, and the reason matters

**The file was populated, the suite went red, and the change was reverted. That is the finding.**

The ticket describes the file as "a header with zero rows" and asks the census to fill it. It is not an empty
stub. Two things make hand-filling it wrong:

1. **⚠️ It is a GENERATED file.** `app/scripts/generate_fact_tags.py` emits it from the vocabulary xlsx, and
   emits it **header-only** because the xlsx has no `depends_on` column. A test —
   `test_generated_csvs_are_committed_and_current` — exists precisely to catch this, and its own docstring
   names the failure mode: *"someone edited the xlsx without re-running the generator (or hand-edited a CSV)."*
   Any hand-authored rows would also be **silently destroyed** the next time anyone runs the generator.
2. **⚠️ It is a PROJECTED table, pinned empty.** `projection.py` mirrors the file into the `TagDependency` DB
   table, and `test_projection_counts_match_files` asserts that count is **0**, with
   `test_desired_state_shape` asserting `tag_deps == set()` and the comment *"No depends_on authored yet
   (LP-311 Phase 0): the DAG is empty."* **The empty DAG is a deliberate, documented state — not an oversight.**

Populating it with 19 edges turned **4 tests red** (projection counts, desired-state shape, the generated-CSV
guard, and a persistence test sharing the projected state). The change was reverted; the file is unchanged.

**What the census did establish** — kept here so the work is not lost, and so the next ticket has the data:
**19 genuine tag→tag edges**, extracted from each derived recipe's source and its `tag_production.yaml` output
mapping, e.g. `stmt.nsf_count ← txn.is_nsf_or_overdraft` (the AS-7 chain LP-451 describes),
`income.employer_coverage ← income.employer_normalized` (IN-6), `stmt.continuity ←
stmt.beginning_balance / ending_balance / period_start`, `income.ytd_annualized_shortfall_pct ←
income.documented_monthly / pay_date / ytd_gross`. It is a **lower bound**: most recipes read extraction
*fields* rather than tags (so produce no edge), and the extraction reads string literals from recipe bodies, so
a dynamically-constructed tag name would be missed.

**And the header still cannot express what the ticket actually wanted.** It is `tag_id,depends_on_tag_id` —
**tag→tag**. The census produces **rule→tag**, which is a different relation and is **already** recorded in
`rule_tags.csv`. So filling this file would not have delivered "which rules unblock together" in any case.

**The decision:** leave the file untouched and report. Landing the DAG properly needs a `depends_on` column in
the vocabulary xlsx (or a generator change), plus updates to the three tests that pin the empty state — **a
separate ticket and a separate decision**, exactly as the ticket instructed when the shape does not fit.

## Every place the census contradicts LP-451 or the work breakdown

**This is the section for whoever picks this up next.**

1. **The work breakdown's "six missing extractors" is wrong on all six.** Every one exists and is registered.
   ~30 rules leave the extractor-gated bucket. The probable cause is `"existing_extractor": null` still sitting
   in five of the six schema specs.
2. **CL-1 is not extractor-blocked** (LP-451: `XF`, rate lock). `rate_lock_expiration` fills 3/3 on the LE.
3. **Flood is not an engineering gap** (LP-451: IH-5 `PT+DR`; the work breakdown: missing extractor). The
   extractor exists and has simply never seen a document. It is a **document ask**.
4. **TI-4 is not a "nearest miss to write-now"** (LP-451 roll-up, line 190). Its `judgments_indicator` is
   `None` on all 4 title commitments. Same for TI-3's `open_liens_indicator` and TI-5's
   `vesting_marital_recital`. **The field existing is not the field filling — this is ADR-354 recurring inside
   LP-451's own conclusion.**
5. **LP-451's field names cannot be used verbatim** — 3 of them are shorthand that resolve to different real
   keys (above). Any downstream ticket generating a field list from LP-451 must resolve against the real key
   set first.
6. **The insurance schema spec disagrees with its own extractor** on three names: spec `insurance_carrier` /
   `insured_property_address` / `dwelling_coverage_a` vs emitted `carrier_name` / `property_address` /
   `coverage_amount`. The spec even attributes IH-1/IH-7 to `dwelling_coverage_a`. **No live rule is broken**
   (IH-1 reads `ins.dwelling_settlement_basis`), so this is spec drift — but the spec is the stated source of
   truth for generating field lists, so it will mislead the next reader.
7. **CR-11 has no data**, despite LP-451 placing it in the `public_records` list-consumer cohort: the list is
   declared and captured, but **0 rows** across both credit reports.
8. **PC-6 and PC-9 are weaker than LP-451's `LC` verdict implies** — their lists fill, but the specific row
   field each rule needs (`addendum_date` 0/12, `deadline_date` 6/26) largely does not.
9. **AS-3's lineage disagrees with its bar.** `rule_tags.csv` shows an AI tag (`income.qualifying_monthly`);
   the bar says `no-ai-dependency` with no load-bearing AI tags. **The bar wins** — this is LP-451's own
   "lineage is not direct-read" caveat, and the census encodes that precedence.

## Assumptions and decisions

1. **The documents are the gate of record** where they and the tickets disagree — the ticket's instruction,
   applied throughout.
2. **"Verified hop" is the FIRST broken hop, not the only one.** A rule can be blocked at hop 2 and still need
   calibration later; that is carried in a separate `also_needs_later` column so "only 10 need Priya" cannot be
   misread as "only 10 rules ever reach Priya."
3. **The activation bar outranks lineage.** Where a rule has a bar, its `load_bearing_ai_tags` is authoritative
   over `rule_tags.csv` (LP-451's caveat). And **a rule carrying a bar is by definition held** — it has been
   through the eligibility gate — so it can never be scored "writable-now" by this census.
4. **A judgmental rule is never "writable"** even when its lineage resolves: for PE-4 the lineage lists only
   `program.type` while the rule is an `ai_judgment`. **The lineage under-states judgmental rules** — a limit
   of this method, stated rather than hidden.
5. **The five VAC/RED rules are taken as LP-451 states them** (DT-2, DT-3, DT-5, CO-2, IH-4); the vacuity proof
   was not re-derived from operand tracing. Inherited, flagged — same caveat LP-451 itself carries.
6. **Fill = non-null.** A field present-but-null counts as unfilled. `n=0` types report "no docs", never 0%.
7. **`docs/schema-specs/*.json` was treated as the source of truth for what a schema declares**, and the
   shipped extractor as the source of truth for what it emits. Where they diverge, both are reported (finding
   6) rather than one silently preferred.

## What this changes downstream

- **The extractor-building tickets should be resequenced or dropped.** ~30 rules were filed as
  extractor-gated; **1** actually is (AU-4, and it needs run-state, not an extractor). MI certificate is the
  only genuinely missing document extractor, and with **n=0** it cannot be validated even if built.
- **The largest single lever is now a document ask, not engineering.** 26 rules are blocked on corpus, not
  code. The credit report (n=2), AUS (n=1), appraisal (n=2) and flood (n=0) types need **real files from
  Priya** before any of their rules can be measured — this is the same ask ADR-332 makes for the calibration
  lane, and the two should be batched into one request.
- **The tag-production stage is the real bottleneck: 54 of 83.** LP-451's build order (property.type → the
  tradelines consumer → the parsed-tag dividend) is **confirmed correct** by the census — tradelines is the one
  list whose row fields are uniformly populated (35/35), so the 8-rule credit cohort remains the best move.
- **Three LP-451 "cheap" rules are not cheap** — TI-3, TI-4 (and TI-5's second field) need extractor-prompt
  work first. They should leave the parsed-tag dividend list.
- **The tag DAG needs its own ticket.** `tag_dependencies.csv` cannot be filled by hand: add a `depends_on`
  column to the vocabulary xlsx (or change the generator), then update the three tests that pin the empty DAG.
  The 19 edges this census found are listed in Phase C as the starting data.
- **LP-477 (the agency/overlay shape) is unaffected** — its six gates hold regardless of anything here.

**No ADR written.** Every finding here is a correction of fact against an existing ADR's principle (ADR-354,
schema presence ≠ data availability) rather than a new architectural decision. The one candidate — the fifth
classification category — is a finding about *this ticket's* taxonomy, recorded above; it does not change how
the system is built.
