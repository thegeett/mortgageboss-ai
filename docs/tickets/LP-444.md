# LP-444 — Make generic list data AI-visible (opt-in, capped, truncation-safe, PII-scrubbed); CR-4 inert

## What this ticket is

LP-443 wired the generic lists onto the snapshot (`entry.lists` — tradelines, etc.), but no AI reasoner
could see them: the tag-materialization context builders (`subjects.py`) predate lists and serialise
`entry.fields` only. So a rule that needs a list — **CR-4: is a credit-report tradeline undisclosed on the
application?** — had no way to perceive it. This makes list data visible to an AI context, **opt-in per
group**, and builds CR-4 as the first consumer, shipping it **inert**.

## D1–D5

- **D1 — the context builder.** `_doc_context` / `_borrower_context` build from `raw.fields` only; `_context`
  in `ai.py` fingerprints the result for the AI cache, so the equivalence constraint is byte-identity. The
  builders now serialise `entry.lists` when the group opts in.
- **D2 — the declaration shape.** `AiGroup.include_lists` (+ `list_row_cap`, `include_stated_liabilities`),
  DECLARED like `include_borrower_roster`/`applies_to` — a group that omits them is byte-unchanged. Threaded
  as a small `ContextOptions` bundle. Gated: `include_lists` → document/borrower subjects only;
  `include_stated_liabilities` → borrower only.
- **D3 — truncation visibility (the safety requirement).** Enforced by **both** a context marker
  (`{"rows": …, "truncated": true, "shown": M, "total": N}`) and a prompt line (in CR-4's prompt: *an item
  you can't match may be beyond the shown rows → answer `unknown`, never a confirmed absence*). Neither alone
  works. The count-cross-check discipline, applied to reasoning.
- **D4 — PII in serialised rows (the STOP that I did NOT ship naive).** A `ListRow.fields` value is a plain
  `Field`, never a `PiiField` — so `_field_value` would emit it raw (unlike a top-level PiiField's masked
  display). **Yes, without a guard a raw value could reach a reasoner.** So the serialiser runs every list-row
  string through the shared `_DESC_REDACT` 9+-digit scrub at the context boundary — the last gate before an
  AI, where a leak is worst. This is the universal backstop layered on top of the LP-443-review per-list
  declared redact at storage (which covers only named fields); the context scrub catches undeclared fields
  and any future list. **Proven:** a tradeline built with a raw `4471000000001` → `[redacted]`.
- **D5 — token cost, measured.** The CR-4 borrower context: **~53 tokens without lists → ~967 with** (a
  credit report's tradelines, capped at 50). Per-group cap so a dense report can be given more rows.

## PHASE A — the mechanism + the actual serialised context (reported, not predicted)

```
credit_report doc in the OPT-IN borrower context:
  lists.tradelines: truncated=True  shown=25  total=30   (Phase-A cap was 25; now 50 per Geet)
  row[0]: {creditor_name: 'CREDITOR 1', account_number_masked: '[redacted]', balance: '100', ...}
equivalence:  opt-out context has NO 'lists' key anywhere
```

**The Phase-A finding that shaped Phase B:** CR-4's two inputs are asymmetric — the report **tradelines** are a
generic list (this mechanism), but the app **liabilities** are file-level MISMO facts (`liability.{k}.*`), NOT
a document list (the 1003 spec has no liabilities list). And the borrower context carried only
`borrower.{index}.*` MISMO — so it did NOT see the file-level liabilities. **Geet's call: extend the borrower
context with the file-level liabilities** (`include_stated_liabilities` → `stated_liabilities`), and **raise
the cap to 50, per-group**. Both applied. The borrower context now carries both inputs CR-4 compares.

## PHASE B — CR-4, inert (the verdict, reported)

- **`credit_profile`** (`tag_production.yaml`): a borrower group, `context_builder: borrower`, `applies_to:
  [credit_report, uniform_residential_loan_application]`, `include_lists: true`,
  `include_stated_liabilities: true`, `list_row_cap: 50`, producing `credit.undisclosed_tradeline`. Its prompt
  carries the truncation-discipline line and the verdict definition.
- **The tag** `credit.undisclosed_tradeline` (borrower, enum yes/no/unknown) — `vocabulary_extra.yaml`.
- **`CR-4.yaml`** — a per-borrower deterministic spec reading the tag: `yes` → **fired**, `no` → **satisfied**,
  `unknown`/absent → **couldnt_check** (never a finding on a missing document, never a confident pass over
  unseen rows). `priya_validated: false`.
- **The verdict, proven end-to-end** (the `credit_profile` group compares the tradelines list vs the MISMO
  liabilities straight from the context, then CR-4 reads the tag):

| fixture | tag | CR-4 verdict |
|---|---|---|
| undisclosed (Amex on the report, NOT in the app) | `yes` | **fired** |
| clean (every tradeline disclosed) | `no` | **satisfied** |
| uncomparable (truncated / no report / no liabilities) | `unknown` | **couldnt_check** |

- **INERT:** CR-4 is NOT in `ACTIVE_RULE_IDS`, so `credit_profile` is not required and **does not run on a live
  file**. A new AI judgment is never activated on arrival — activation needs calibration + Priya's bar.

## CR-4 registration (the rule-engine integration finding)

A rule with a **spec** is a "candidate" — `activation_bars.yaml` must cover EXACTLY the candidate (non-base)
rules, and the pending-checks / projection machinery counts them. So giving CR-4 a spec required registering
its **activation bar** (`status: not-calibratable-yet`, `ships: auto`, `validated: false`,
`load_bearing_ai_tags: [credit.undisclosed_tradeline]`) — the same way every written-but-inactive rule (OC-1)
is tracked. This is what keeps CR-4 a *declared, held* rule rather than an untracked one: it appears in the
blocked-candidate set with an honest reason (its AI tag is unscored), and `is_eligible=false` keeps it out of
`ACTIVE_RULE_IDS`. (CR-1 / CR-5 have no spec, so they are inert-by-absence; CR-4 has a real verdict spec, so it
is inert-by-bar — the OC-1 model.)

## Assumptions / decisions

- Opt-in only (existing contexts byte-identical); file-level liabilities in the borrower context; cap 50,
  per-group — all per Geet.
- The universal context-boundary scrub is layered on the LP-443-review storage redact — defense in depth.
- CR-4 uses a NEW borrower tag `credit.undisclosed_tradeline` (the per-liability `liab.in_application` in the
  playbook does not fit a per-borrower producer). `rule_tags.csv` still maps CR-4 → `liab.in_application` (the
  planned input); the spec reads the new tag — the same tolerated registry drift PC-2/AS-8/IN-6 carry
  (reconcile upstream in the xlsx). Reported, not silently absorbed.

## NEW gaps / what remains (what CR-1 / RE-1 / AU-2 now need)

- **CR-4 activation** — a calibration round on varied files + Priya's bar (its own ticket); today inert.
- **CR-1 / RE-1 / AU-2** are the other list-consuming rules — they now build on THIS mechanism: a group opts
  into the lists it needs (RE-1: an appraisal's comparables; AU-2: a bank statement's transactions or a
  credit report), with the same cap + truncation + scrub. Each is its own ticket.
- **The truncation/ un-shown-subject gap for a long list** — CR-4 judges per-borrower over the tradelines it
  is shown; a report with more tradelines than the cap has un-shown rows the marker makes `unknown` (safe),
  but a per-tradeline enumeration (a tradeline SUBJECT) would be needed to judge each — out of scope.
- **`rule_tags.csv` drift** for CR-4 (above) — reconcile in the xlsx.

## ADR

**ADR-349** — the opt-in list-visibility mechanism (cap + truncation marker + the context-boundary PII scrub),
the borrower-context liabilities extension, and CR-4 as the first (inert) consumer.
