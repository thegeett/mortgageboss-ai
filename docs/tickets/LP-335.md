# LP-335 — Fix FINDING-1: the `id.current_address_type` prior-presumption bias

LP-334's first live calibration measured `id.current_address_type` at **50% accuracy-when-concrete** on a
LIVE tag that feeds ID-4's deterministic residence FILTER. The AI's reasoning: *"Driver's licenses often
contain addresses that are not current"* → predicted `prior`, golden `residence`. This is the fix. A
prompt/data change only — no engine/spec/allowed-values touched.

## The bug + its traced consequence

`id.current_address_type` is ID-4's declared GATHER FILTER (`== "residence"`, LP-325/326): only
residence-typed sources are compared. When the reasoner presumed a driver's-licence address is `prior`:
1. the DL address is EXCLUDED from the gather → fewer residence sources → frequently `<2` →
   **couldnt_check** (LP-325: a single source is not agreement); or, worse,
2. if the DL was the one source that would DISAGREE with the 1003, excluding it turns a **real discrepancy
   into a clean pass** — a silent false-green on identity, exactly the signal ID-4 exists to catch.

`test_the_old_bias_would_have_masked_it` reproduces (2): DL `prior` + a differing 1003 residence →
couldnt_check (masked). `test_dl_and_1003_residence_that_DISAGREE_surfaces` is the fix: DL `residence` +
the differing 1003 → **FIRED** (the discrepancy surfaces).

## THE ROOT CAUSE — it was IN THE PROMPT (not a subtle model bias)

The `id_address` prompt literally defined `prior` as *"a former address, **e.g. an old driver's-licence
address**."* **The prompt's own exemplar taught the model DL→prior.** The AI faithfully followed it. This
makes the fix unambiguously principled — the exemplar was wrong — not a fit-to-the-eval.

## The PRINCIPLE (right independent of LP-334's two cases)

**A driver's licence STATES the holder's address of record. The tag reports what the document SAYS the
address type IS — it does not speculate about whether the address is still current.** Staleness is handled
DOWNSTREAM by design: a stale DL address vs a current 1003 address IS the discrepancy ID-4 surfaces to a
human. Pre-filtering the DL away at the tag layer destroys the very signal the rule was built to catch —
the tag must not do the rule's job. This is defensible with zero reference to LP-334's two observations;
the failing case passes as a CONSEQUENCE, never as the target.

## The vocabulary's declared meaning (the fix matches it — no ambiguity to escalate)

`fact_tags.csv`: `id.current_address_type`, enum `[residence, mailing, prior, unknown]`, described as
*"**Type of a STATED address** (so DL vs residence compares correctly — the absent≠empty address trap)."*
The vocabulary is explicit: the tag classifies the type the document STATES, not a verified-current-
residence judgment (which would be the deterministic engine's job, §3D). The mild "residence-as-stated vs
verified-current" nuance in the old prompt gloss ("the borrower's current home") is resolved by the
`fact_tags` "STATED address" semantics + §3D — **not a Priya question, no ADR.** The `current` in the tag
name means "the present/stated address the document gives" (vs a mailing or a document-marked-prior), not
"verified as the true current residence."

## The prompt: before → after (`tag_production.yaml`, `id_address` group)

**Before:** `"prior" (a former address, e.g. an old driver's-licence address)` — the DL→prior exemplar.

**After:** the type THIS DOCUMENT STATES, judged from what the document INDICATES, not speculation about
currency (checked downstream). `residence` = an address the document states as the holder's home (a DL /
1003 / ID states the residence of record UNLESS marked otherwise; *"do NOT presume a driver's-licence
address is stale or 'prior' — a licence states the holder's address of record"*); `mailing` = the document
marks it mailing-only / PO box; `prior` = the document EXPLICITLY marks it former; `unknown` = the type is
genuinely unindicated (*"never force a guess into 'residence'"*). No allowed values changed; the co-located
`id.address_normalized` + `id.current_address_type` outputs (the LP-325 gather contract) are untouched.

## The over-correction guards (both directions tested)

Inverting a presumption can over-correct — labeling genuinely-stale/mailing addresses `residence` would
fabricate a FALSE discrepancy on every borrower who moved. The principle guards against this intrinsically
(`mailing`/`prior` only when the document says so; `unknown` when unindicated), and the tests + the live
re-measure confirm it:

| Case | Expected | Live result |
|---|---|---|
| a DL stating an address (FINDING-1) | `residence` | ✅ `residence` (was `prior`) |
| a plain DL address | `residence` | ✅ `residence` |
| a PO box / mailing-marked | `mailing` | ✅ `mailing` |
| a document-marked PREVIOUS address | `prior` | ✅ `prior` |
| no address stated | `unknown` | ✅ `unknown` (not forced to residence) |

## ID-4 end-to-end (the consumer — keyless, tag values set directly)

- DL residence + 1003 residence that AGREE → **satisfied**, no AI call (the DL is no longer excluded).
- DL residence + 1003 residence that DISAGREE → **FIRED** — the discrepancy surfaces (the most important
  test: the signal the old bias silently destroyed).
- MAILING-only borrower → still **couldnt_check**, not a false discrepancy (LP-325 / LP-323-ID-A §4 trap —
  the fix did not relabel the PO box as residence).
- Document-marked PRIOR → still excluded → couldnt_check (the guard the filter exists for, intact).

## The ONE re-measure (measured once; did NOT iterate)

| | n | unknown-rate | accuracy-when-concrete |
|---|---|---|---|
| **BEFORE (LP-334)** | 2 | 0% | **50%** (`dl_addr_1` → `prior`, wrong) |
| **AFTER (LP-335)** | 5 | 20% (1 correct abstention on the no-address doc) | **100%** |

Per-case AFTER: `dl_addr_1`→residence ✅, `dl_addr_2`→residence ✅, `mail_1`→mailing ✅, `prior_1`→prior ✅,
`noaddr_1`→unknown ✅. **STATED LOUDLY: n=5 finds BIASES, not RATES.** A 100% here does NOT validate the
tag — LP-334's conclusion stands: validation needs the larger labeled set (n≥20/tag) LP-334 asked for.
This ticket removed a *systematic* bias (a wrong exemplar) and confirmed both directions; it did not
measure the tag's true field accuracy. **I did not tune further on the result** — one principled change,
measured once.

None. The fix was a single misleading exemplar; the vocabulary's meaning was clear; the guards hold.
