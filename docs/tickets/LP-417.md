## D0 — the redundancy check (the new lesson, done first)

The DTI-component cluster (DT-2/3/5, CO-2, IH-4) was abandoned because the product already surfaces what they'd
flag (the calculator UI marks an overridden value). **IH-3 is not redundant:** the insurance `effective_date` is
surfaced **nowhere** in the product (grepped services/api/findings/calc — the only "in force" hit is an unrelated
confidence-cutoff comment). The DTI reads `annual_premium`, not the effective date. **No STOP.**

## D1 — the expressibility gate (verified, not assumed)

**Native date compare — no derived day-count tag needed.** The deterministic operand path supports `type: date`
via `coerce_date` (LP-328; `KNOWN_OPERAND_TYPES = {decimal, date}`), and **ID-5 already compares two date
operands** (`id.borrower_id_expiration` vs `contract.loan_closing_date`, `op: "<"`). IH-3 is ID-5 with the
direction flipped: fire when `effective_date > closing_date`. (Contrast PC-7, which needed a derived day-count
because it compared against *today*; IH-3 compares two real dates, both present.) **No ADR** — the DSL already
handles date-vs-date.

## D2 — the producer (`ins.effective_date` + the loan promotion)

`ins.effective_date` is already in `fact_tags.csv` as a **document** parsed tag (from the binder's typed-core
`effective_date`), but IH-3 is loan-enumerated. So — mirroring `contract.closing_date` → `contract.loan_closing_date`
(LP-389-A) — I add:
- **`ins.effective_date`** (parsed / document) — the binder fact.
- **`ins.loan_effective_date`** (derived / loan) — the promotion. The recipe `_loan_effective_date` mirrors
  `_loan_closing_date` exactly: dedup by parsed date; **two binders disagree → `unknown`** (the
  `housing.insurance_monthly` multi-binder abstain, LP-374); absent → `unknown`. Fail-closed, never a picked date.

## D3 — the subject match (anti-structural-death)

IH-3 `subject_enumeration: loan`; both operands loan-subject (`ins.loan_effective_date` derived/loan;
`contract.loan_closing_date` loan_tag). Verified against `load_declarations()`. Not born structurally dead.

## D4 — provability + the fixture

**No fixture carried a homeowners binder** (LP-414's A3 deliberately kept it off LF-6T3N — a binder would move
the DTI insurance line). So IH-3 could not be proven on LF-6T3N. I **extended LP-414's standalone
`fire_path_scenarios.py`** (own `95…` id namespace, NOT LF-6T3N) with three binder scenarios — the one-problem-
per-file discipline:
- `build_insurance_in_force_snapshot` — effective 2026-06-01 ≤ closing 2026-07-15 → **satisfied**.
- `build_insurance_late_snapshot` — effective 2026-08-15 > closing 2026-07-15 → **fired**.
- `build_insurance_two_binder_snapshot` — two binders disagree → **couldnt_check**.

Each carries a `homeowners_insurance` binder (effective date) + a `purchase_agreement` (closing date, which
`contract.loan_closing_date` promotes). **LF-6T3N was NOT touched.**

## D5 — no binder → `couldnt_check`, not `not_applicable`

Insurance is **required** on every mortgage, so a missing binder is an honest gap, not scope-false. IH-3 carries
**no applicability predicate** (which would hide the gap); a missing/unreadable effective date → the operand
coerces to `None` → `couldnt_check` (the gate catches it). **No live rule flags a missing binder today** (IH-1 is
unwritten; the DTI insurance gate is a *calc* gate, not a rule), so IH-3 does not double-fire. This mirrors
PC-2/PC-7 (couldnt_check on an absent input, no not_applicable).

## D6 — the threshold question

**Exact, no Priya threshold.** `effective > closing` fires; `effective == closing` → satisfied (in force ON the
closing day). No tolerance → `no-ai-dependency` bar → **activates** (not held). **Priya confirmation (optional,
non-blocking):** is same-day-effective acceptable? — today yes (in force on the day), the ID-5 `==` boundary,
benign here.
