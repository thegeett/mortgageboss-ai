# LP-406-3b — Write IN-6 (pay-stub ↔ W-2 employer coverage), now that `income.employer_coverage` exists

## What this ticket is

LP-406-3 stopped IN-6 at Phase 0: its two-way employer **set-coverage** relation is not expressible in the DSL
(`ConsistencyEval` is all-equal, not set-coverage — ADR-323). LP-410 built the derived **per-borrower** tag
`income.employer_coverage` that computes it. IN-6 is now a trivial deterministic rule branching on one enum (the
AS-8 pattern + an applicability predicate for `not_applicable`).

**The one real decision (D2):** the `uncovered` branch routes to **`needs_review`**, not `fired`, because the
producer's deterministic matching has a known false-positive source (short-form employer names). **IN-6 is
written + producing but HELD** — it has a transitive AI dependency (the coverage tag reads the AI
`income.employer_normalized`), so its bar is proposed `validated: false` pending Priya, the IN-3 pattern.
`ACTIVE_RULE_IDS` stays **25**.

## D1 — The subject match (anti-structural-death) — confirmed

`load_declarations()["income.employer_coverage"].subject == "borrower"`, and IN-6's
`subject_enumeration == "per_borrower"`. The `_per_borrower` enumerator hands a deterministic rule the
borrower's own tags merged with loan tags (`{**loan, **borrower_own}`), so IN-6 reads *this* borrower's
`income.employer_coverage`. Not born structurally dead. Asserted + verified live.

## D2 — The `uncovered` routing decision (the substance)

**Decision: `uncovered → needs_review`** (surface for human confirmation), **not `fired`**.

**Why (the FP/FN cost).** `income.employer_coverage` does the DETERMINISTIC half of IN-5's comparison (the
exact-normalized bookend, reusing IN-5's own normalizers) but NOT IN-5's AI fuzzy-residue judge (LP-410's
documented limitation). A pay stub's short form ("Acme") vs a W-2's legal name ("Acme Freight Co") normalizes to
`acme` vs `acme freight` → `uncovered` — when it is very likely the same employer. **Short-form employer names
on pay stubs are common, so `uncovered` has a KNOWN false-positive source.**
- `fired` = a confident finding → **false-fires on common short forms** → noise, processor distrust.
- `needs_review` = surfaced to a human → catches a **genuine** gap *and* doesn't false-fire. So it **strictly
  dominates** `fired` until the fuzzy residue is closed (a later refinement). The error cost either way is a
  human confirmation, never a false auto-verdict.

**The mechanism (confirmed from the code).** `needs_review` is a valid deterministic **outcome** verdict
(`VERDICT_BY_NAME` includes it; the `OutcomeRule` pattern allows it). So the spec declares
`uncovered → needs_review` while `covered → satisfied` — only the uncertain branch goes to a human, the certain
branch still auto-ships. This is a **per-branch outcome**, NOT `ships: ratify` (a rule-WIDE mode that would also
ratify the satisfied branch, and whose runtime honoring on a structural rule is the unresolved IN-7/ADR-316
question). Recorded as **ADR-325** (a reusable precedent: a deterministic rule whose input carries a known FP
residue routes that branch to `needs_review`).

## D3 — The transitive AI dependency → IN-6 is HELD (the honest ending)

`income.employer_coverage` is **derived**, but it reads `income.employer_normalized` — an **AI** tag (measured
**100%**, LP-379-D, via live IN-5). This is exactly the **IN-3 case** (LP-384 reclassified IN-3 from `no-ai` to
`calibratable-now` for the same reason). So IN-6 does **not** get AS-8's free `no-ai-dependency` activation. Its
bar is:

```
status: calibratable-now      # NOT no-ai — the declared AI tag folds income_employer into _required_ai_groups
ships: auto
threshold: 0.95               # IN-5's exact precedent: SAME tag, SAME evidence Priya already approved for IN-5
validated: false              # PROPOSED — Priya's sign-off is the activation; I do not validate it
load_bearing_ai_tags: [income.employer_normalized]
measured_accuracy: 1.0        # LP-379-D — the same measurement live IN-5 rests on
```

`is_eligible` (calibratable-now) requires `validated=true` AND `measured ≥ threshold`; `validated=false` →
**not eligible → held**. **Honest ending: IN-6 is written + producing + bar proposed, pending Priya's
sign-off.** `ACTIVE_RULE_IDS` stays 25. When she validates, `1.0 ≥ 0.95` → eligible → live (the IN-1/IN-5/IN-3
path). Because live IN-5 already requires the `income_employer` group, `income.employer_normalized` (and thus
`income.employer_coverage`) is produced regardless of IN-6's activation — no couldnt_check-forever trap.

## D4 — `one_sided` → `not_applicable` at the BORROWER subject

Reuses AS-8's applicability predicate, at the borrower subject: `applicability: {income.employer_coverage ne
one_sided}`. Verified against `resolve_applicability` (subject-agnostic) + `_per_borrower` (gives the borrower's
own tag map): `one_sided` → predicate false → **NOT_APPLICABLE**; `unknown` → the resolver's unknown-handling →
**couldnt_check**; `covered`/`uncovered` → the predicate holds → proceed. Proven per-borrower (not just
loan-level like AS-8).

## D5 — The IN-5 overlap boundary

- **IN-5** — employer NAME CONSISTENCY: do all the mentions of the employer agree (tolerant of variance)? Fires
  on a genuinely different employer with no explanation.
- **IN-6** — employer COVERAGE across document types: is each employer documented by both a pay stub and a W-2?
  Surfaces a missing counterpart.

Distinct concerns on the same underlying tag. IN-6's reason names a **missing counterpart** ("an employer
appears on this borrower's pay stubs or W-2s but not both"), and is asserted **not** to read like IN-5's "the
employer differs across sources" — so a processor never sees two findings for one employer problem.

## D6 — Reason strings

Plain processor language (LP-376-C), no dotted tag ids in the surfaced verdicts (asserted). The `uncovered`
reason names the concept and asks for confirmation; the **specific** uncovered employer lives in the
`income.employer_coverage` provenance the finding carries (the producer's reasoning names it), not interpolated
into the static outcome reason — the AS-8/OC-1 convention. A plain `fact_label` for `income.employer_coverage`
("pay-stub / W-2 employer coverage") was added to `reasons.py` for the couldnt_check reason.

## D7 — A Priya threshold (beyond the bar)?

**None beyond the activation bar.** The producer does pure name-set coverage — no temporal (tax-year) alignment
requirement — so there is no spec threshold (`threshold_needs_signoff: false`, matching `rule_kinds.csv`). The
name-match tolerance is IN-5's inherited normalization (the ADR-281 `drop_entity_suffix` trade-off, already
Priya-flagged for IN-5). The bar's 0.95 is the activation gate (Priya's), separate from any spec threshold.

## THE PROOF (reported, not predicted)

The coverage tag is computed **end-to-end by the real LP-410 producer** from injected
`income.employer_normalized` tags (no AI call), so the rule + producer are exercised together:

```
covered   ("Acme Corp" stub + "Acme" W-2, normalize-equal)     -> satisfied
uncovered ("Acme" stub + "Acme Freight Co" W-2, short-form)    -> needs_review   (the D2 decision)
one_sided (W-2 only)                                           -> not_applicable
one_sided (pay-stub only)                                      -> not_applicable
unknown   (an employer name unreadable)                        -> couldnt_check
per-borrower isolation (A stub-only, B W-2-only, same employer) -> each not_applicable (A does not cover B)
```

**On the real LF-6T3N fixture** (no-AI materialization): both borrowers → **couldnt_check**. Root cause,
named: `income.employer_coverage` depends on the AI `income.employer_normalized`, which a no-AI run does not
produce → `unknown` → couldnt_check. HONEST (an AI-not-produced gap, the OC-1 fixture situation) — **not** a bug
and **not** structural death (the subject matches; the branch proof above ran through the producer). The
scenario that exercises the covered/uncovered paths on a real fixture needs the `income_employer` AI group
materialized (a live/stubbed run) — a fixture concern, not this ticket.

**Activation:** `is_eligible(IN-6 bar) == False` (calibratable-now, `validated: false`); `"IN-6" not in
ACTIVE_RULE_IDS`; `len(ACTIVE_RULE_IDS) == 25` (unchanged). **IN-6 awaits Priya's sign-off of its 0.95 bar.**

## The fuzzy-residue caveat IN-6 ships with

IN-6's `uncovered` branch will surface a `needs_review` on legitimate short-form employer names (a pay stub's
"Acme" vs a W-2's "Acme Freight Co") that IN-5's AI judge would forgive — the LP-410 limitation. Routing to
`needs_review` (not `fired`) is the mitigation: a human confirms rather than seeing a false finding. **Closing
the residue** (a fuzzy-coverage pass, or IN-6 consuming an AI residue judgment) is a **separate refinement
ticket**, not this one. Until then, `needs_review` is the honest routing.
