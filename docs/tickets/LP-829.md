# LP-829 — Clicking a message on the timeline opens it

- **Ticket:** LP-829 · Phase 4 follow-up, from processor feedback
- **Status:** Built — awaiting review
- **Date:** 2026-09-07
- **Scope:** `api/communications.py` (new read endpoint), `schemas/communications.py`,
  `components/file/communication/timeline-panel.tsx`, a message detail dialog
- **Migration:** none expected
- **Depends on:** [LP-825](LP-825.md) — the timeline has to be messages before opening one is useful

---

## What was asked

> *"it should open dialog box on clicking that draft, with all draft email information."*

## Measured — there is nothing to open it with

Two gaps, and the second is the bigger one.

**The timeline row does not carry the message.** `TimelineEntry` (`services/timeline.py:81`) has
`subject`, `status`, `counterparty`, `attachments`, `is_important`, `unread` — and **no body**. The
row is a summary by construction.

**There is no endpoint that returns one message.** The whole surface is:

| route | what it does |
|---|---|
| `GET /outbound/draft` | the file's ONE open draft |
| `POST /outbound/draft/{id}/send` | record it as sent |
| `GET /messages/{id}/reply-context` | recipient + subject for a reply |
| `POST /messages/{id}/reply`, `POST /messages` | write |
| `POST /messages/{id}/important`, `/read` | flag |

`MessagePublic` states it outright: *"Never the body — the caller already has what they typed."*
That reasoning is correct for a **write** response and does not transfer to a read. Nothing in the
product can currently show a processor the text of a message that was already sent.

So today: the open draft is visible only in the panel at the top of the page, and **a sent message's
words are visible nowhere at all.**

## The scope decision, and my reading

The request names the draft. Restricting it to drafts would be the wrong shape, for a reason worth
stating: a processor who learns that clicking a draft opens it will click a **sent** message next,
and that one is more valuable — it is the only record of what actually reached the borrower, and
there is no other way to see it. An asymmetry here is a class, not an instance.

So: **every message row opens; activity rows do not.** After LP-825 the communication timeline is
messages anyway, and on Recent activity an activity row has nothing behind it to show.

## Read-only, and the draft is the interesting case

The open draft is **already fully rendered and editable** in `OutboundDraftPanel` at the top of the
same page. A dialog that also edited it would be two components holding separate local state for one
body, and the second one to save wins silently — the LP-818 `ReplyBox` problem, but with data loss
instead of a wasted fetch.

The dialog is therefore a **reader** in every case:

* **Sent / received** — read-only by definition. The evidence record must not change (LP-821), and a
  received message is not ours to edit.
* **Open draft** — read-only, with "Edit this draft" moving focus to the panel that owns editing.
  One editor, one source of truth, and the dialog answers "what does this say" without becoming a
  second way to change it.

## What "all information" means, per state

| field | draft | sent | received |
|---|---|---|---|
| subject, body | yes | yes — **as sent** | yes |
| recipient / sender | suggested recipient | recipient, and the approver who sent it | sender, and its auth verdicts |
| documents included | the needs it carries | the needs it asked for | attachment manifest |
| timestamps | created, last regenerated | sent at | received at |
| template + version | yes | yes — the version that rendered it | n/a |
| delivery | n/a | status, and `failure_reason` where there is one (LP-821) | n/a |

## Done when

- Clicking any message row on the timeline opens a dialog carrying that message's full text and the
  fields above for its state. Nothing summarised, nothing truncated silently.
- A new `GET /messages/{communication_id}` returns it, tenant-scoped through the loan file the same
  way every other route is, and **404 for another company's message id** — asserted, because an id
  is guessable in a way a file identifier is not.
- The body is never logged. It is a borrower's document request and can quote their circumstances.
- The dialog does not edit. A test asserts the draft's stored body is unchanged after opening and
  closing it.
- The open draft's dialog offers "Edit this draft" and that goes to the panel, so there is exactly
  one editor.
- **The placeholder fix (LP-823) applies here too.** A dialog showing `Hello $borrower_first_name,`
  is the same defect in a third place, and it would be introduced by this ticket if the dialog
  renders the stored body raw.
- Keyboard-dismissable, focus-trapped, focus returned to the row on close.

## For the reviewer

Two checks. **The dialog must not become a second editor** — if it holds the body in local state
with a save button, the panel and the dialog will disagree and the last save wins with no warning.
And **the read endpoint is a new way to reach a message by id**: every other communication route
reaches one through the file, so this is the first place a bare `communication_id` is the whole
address. That is where cross-tenant reads get in.

## Built, 2026-09-07

### One correction to this ticket's own reasoning

It said the new route would be *"the first place a bare `communication_id` is the whole address"* and
therefore where a cross-tenant read gets in. **It is not.** `message_router` is
`/loan-files/{file_identifier}/messages`, and every route on it already declares `ScopedLoanFile` —
so the file is resolved under the caller's company before the handler runs, exactly like the reply
and flag routes beside it. The id was never the address.

The real axis is one step in: two files in the SAME company. A company-scoped check passes that
while showing one borrower's mail under another borrower's file, so `message_detail` checks
`loan_file_id` on the row itself rather than trusting the id in the path. Both are tested, and the
sibling-file case is the one that fails when the row check is removed — the cross-company case is
caught a layer earlier by the file gate.

### The placeholder rule is not uniform, and must not be

LP-823 leaves `$borrower_first_name` and `$processor_name` in a stored draft so the send decides who
signs, and resolves them for whoever is reading. That resolution belongs here too, or this dialog
puts `Hello $borrower_first_name,` back on screen one ticket after it was taken off the panel and
the send path.

It applies to **outbound drafts only**:

* a **sent** message was resolved when it went out, so substituting again is a no-op — and a no-op
  is indistinguishable from a body that was never resolved, so running it would prove nothing;
* an **inbound** message is a borrower's own words. Someone who writes `$processor_name` in their
  email must get it back unchanged. Substituting there rewrites what a person wrote to us, which is
  the one thing a record of their message must never do — **and it would look exactly like the fix
  working**. `test_an_inbound_body_is_returned_exactly_as_written` is the assertion standing between
  those two.

### A reader, never an editor

The open draft is already rendered and editable in `OutboundDraftPanel` on the same page. A dialog
that also edited it would be two components holding separate local state for one body, and whichever
saved last would win with nothing on screen to say so — the `ReplyBox` problem from LP-818's review,
with data loss instead of a wasted fetch.

So the dialog reads in every state, and the draft's own dialog points at the panel that owns
editing. Two tests assert there is no textbox and no save control, including on the draft, because
"it currently has no editor" and "it must not grow one" are different claims.

### What opens it

The summary line, as a `<button>`. A whole-row click would swallow the reply and flag controls beside
it; a separate "open" affordance would be a second thing to find. The line naming the message is
what a processor is already reading when they want to see it — and a button rather than a div with a
handler, so it is keyboard-reachable and announced as something that does anything at all.

The dialog's state is separate from the inline reply box's. Reading a message and answering one are
different acts, and sharing the state would make opening one close the other.

### Fetched on open, not with the timeline

A timeline row is a summary and there can be two hundred. Loading every body to render a list would
make the browser hold the fullest copy of a borrower's prose in the product, for messages nobody
opened.

### Mutations

| mutation | result |
|---|---|
| the `loan_file_id` check dropped | 2 failed — sibling file, and soft delete |
| soft deletion ignored | 1 failed |
| the draft rendered raw | 1 failed — the placeholder case |
| the body rendered as HTML | 1 failed — the borrower's-text case |

The first is worth reading twice: dropping the row check does **not** fail the cross-company test,
because `ScopedLoanFile` catches that a layer earlier. Only the sibling-file case fails. A ticket
that tested tenancy with the cross-company case alone would have shipped this with no row check and
a green suite.

### The three standing checks

**Tenancy:** the file gate plus the row check, both tested, and a 404 that is the same answer for
"another company's", "another file's" and "does not exist". **Logging:** nothing added — this route
serves the fullest copy of a borrower's prose in the product and puts none of it in a log line, for
the same reason `communications.body` is dropped from every readonly view. **AI:** none.

### Not done here

Marking an inbound message read on open. The dialog is the natural moment for it and `read_at`
already exists with an endpoint behind it, but a read that fires from a render is a write nobody
asked for — and this ticket's whole design is that the dialog does not write. It belongs with
whoever decides what "read" should mean on this screen.
