# LP-114 — Findings name their SOURCE DOCUMENT (capture + expose + display; clickable to open it)

- **Ticket:** LP-114
- **Status:** Completed
- **Date:** 2026-07-04
- **Scope:** Backend (finding generators + schema) + frontend (finding card + Documents deep-link)

## The gap

A finding showed "source p.N" + a Details snippet but **not which document** it came from, and nothing
was navigable — so a processor couldn't easily verify the AI/rule judgment against the actual
document. This is the findings analog of LP-110 (which gave *needs* their source provenance).

The `Finding` model already had a `source_document_id` FK + a `source_document` relationship, but it
was **hidden AND empty**: not in `FindingPublic`, and never populated at creation (worse than needs'
`source_finding_id`, which was populated-but-hidden). And the id was **already computed and thrown
away** — deterministic findings' `source_location` often carries a `document_id`, but
`_source_location_fields()` extracted only page + snippet and dropped it.

## The V1 slice — capture + expose + display (+ clickable, since it was cheap)

**1. Capture = stop dropping what we compute.**
- **Deterministic** (`verification_engine._source_location_fields`): forward the `document_id` that
  `source_location` already contains → `source_document_id`. Null for file-level/computed rules.
- **AI cross-source** (`cross_source`): `details["source_document"]` is a document TYPE string, not an
  id. Resolve it to a concrete id **only when the type maps to exactly ONE document** on the file
  (`_unique_type_document_map`, normalized via `_normalize_doc_type`); 0 or 2+ → **NULL**. Never guess
  a wrong document — a null source is honest, a wrong link is not.

**2. Expose.** `FindingPublic` gains `source_document_id` + `source_document_filename` (the readable
`original_filename`, eager-loaded — no N+1). The frontend `VerificationFinding` type mirrors it.

**3. Display.** The finding card NAMES its source document — **"Source: {filename}, p.{N}"** — at a
glance (below the description) and in the Details "Source" section, replacing the bare "source p.N".
Graceful when null: keep the existing page/snippet; never a broken empty "Source:".

**4. Clickable — the lightweight nav was cheap, so it's built.** Verification and Documents are
**separate routes**, and the Documents page already opens a drawer from local state. So the source-doc
name links to `/loan-files/[id]/documents?doc=<id>`, and the Documents tab reads `?doc` to open that
document's existing drawer (then strips the param so it can be closed / doesn't re-open). A `<Link>` +
a small `useSearchParams` effect — no new store, no viewer.

## Coverage is partial by design (honest)

Naming populates mostly for **deterministic findings that read a specific document field** (their
`source_location` carries the id). File-level/computed rules (e.g. a DTI threshold) and multi-doc-type
AI findings stay null (graceful — no name shown). No heavier snippet-search fallback was added —
honest over exhaustive.

## No migration

The `source_document_id` column already existed — so **no migration**. Existing findings stay null
until re-verified (no backfill).

## Deferred to V2 (documented in the plan)

An in-app **document VIEWER** (PDF.js / embedded PDF), **PAGE deep-linking** ("open to page N"), and
**TRANSACTION HIGHLIGHTING** (needs the bbox/position data deferred in LP-75). V1 is name +
link-to-open; the viewer/page/highlight staircase is V2. See `phase3.md §2.7`.

  resolves type→unique doc or null.
- `app/schemas/verification.py` — `FindingPublic.source_document_id` + `source_document_filename`.
- `app/api/verification.py` — eager-load `Finding.source_document`.
- `frontend`: `lib/types/verification.ts`, `components/file/verification/finding-card.tsx`
  (`SourceDocLink`), `findings-list.tsx` (thread `fileId` to resolved), `documents/page.tsx` (`?doc=`).
- Tests: `tests/services/test_finding_source_document.py`, `finding-card.test.tsx` + fixtures.
