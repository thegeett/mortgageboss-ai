# LP-317 — Golden eval harness: tag-level + finding-level + calibration

**Status:** Complete. **Branch:** `phase3_new_AI_arch_finding_stage2`.
**ADR:** [ADR-257](../../decisions.md). **Depends on:** LP-313/314/314a (tags + source strength),
LP-315 (rule + gate), LP-316 (finding outcomes + provenance), LP-312 (content_ids).

## What it is

The **GO/NO-GO instrument** for the Stage-2 fact-tag pipeline: labeled fixtures with expected
outcomes, scored automatically against the *real* Stage-A → Stage-B → AS-1 path at **two levels**
(tags and findings), proving AS-1 fires when it should and stays quiet when it should not, plus the
LP-314a source-strength distinction, plus calibration. The harness **evaluates**; it never edits
rule/tag logic — a failing case is a reported regression, and a revealed bug is a separate fix
ticket.

Run it:

```
uv run python -m app.scripts.run_eval          # keyless, deterministic (the CI regression gate)
uv run python -m app.scripts.run_eval --live   # + real-model calibration (skips cleanly w/o a key)
```

## The 12 golden cases

**Finding-level (1–7):** 1 FIRES (unsourced large transfer) · 2 verified→satisfied (matched debit)
· 3 self_asserted→needs_review (claim, no debit) · 4 intrinsic payroll→satisfied · 5 REGRESSION (a
non-`credit` label still fires) · 6 is_money_in=unknown→couldnt_check · 7 intrinsic-not-a-loophole
(the word "PAYROLL" without markers fires, not auto-satisfied).
**Tag-level (8–11):** 8 is_money_in resolves label variance (credit/transfer/ACH/wire/'' → in;
debit → out) · 9 `verified` requires a real matched debit cited by content_id · 10 `self_asserted`
= a claim with no matched debit · 11 `has_identified_source=no` for a third-party Zelle (the $147
pattern), under threshold.
**Real-file (12):** the frozen LF-6T3N tagged snapshot — **0 fired**, ≥1 `verified`, ≥1
`self_asserted`.

## Assumptions & decisions

- **Two levels because a passing rule can mask a broken tag.** A mis-classified `is_money_in` or a
  fabricated `verified` strength would slip past finding-only scoring; the tag level catches it
  upstream.
- **Both directions, explicitly — the case LF-6T3N can't provide.** The real fraud file has no
  unsourced large deposit, so it can only prove no-false-fire. Cases 1/5/7 supply the
  fires-when-it-should direction, and the harness asserts coverage of both.
- **Keyless scoring replays labeled AI judgments; the deterministic layer runs for real.** In
  keyless mode the tag values are the stub's (so `is_money_in` / category / `has_source` match
  trivially — meaningful only in live mode), but the **derived** `source_strength`, the candidate
  search, the gate, and the rule arithmetic are NOT stubbed — that is what keyless meaningfully
  proves. Live mode scores the real model's tags (calibration).
- **The real file is a FROZEN tagged snapshot, not a keyword re-derivation.** LF-6T3N lives in the
  dev DB, not the test DB, and re-deriving its tags with a stub could diverge from the real trace
  ("per the actual trace" would be a lie). So case 12 loads a snapshot captured from one live
  post-LP-314a run — deterministic at test time, no key, faithful to what the model actually did.
  Pinned loosely (exactly 0 fired; ≥1 verified; ≥1 self_asserted) so a faithful regen doesn't churn
  the test on model-confidence wobble, while the fraud direction (any FIRE) is hard-pinned at zero.
- **The committed fixture is REDUCED + PII-SCRUBBED — the real trace, not the real identities.** The
  raw snapshot is a whole loan file (30 documents: W2s with SSNs, licenses with DOB/address, pay
  stubs, a purchase agreement — all real borrower PII). The AS-1 scorer reads only the
  transaction-bearing documents' tags + the DTI income, so the fixture is stripped to exactly that:
  the 5 bank-statement documents (all other documents dropped), `fields` + `belongs_to` removed, the
  MISMO section blanked, every transaction description replaced with a generic label derived from its
  (non-PII) tags, and every tag `reasoning` scrubbed. What is KEPT is the real trace the assertions
  need — amounts, dates, the tag VALUES (is_money_in / has_identified_source / source_strength), and
  the DTI income — so the verdict counts (0 fired; verified/self_asserted) are byte-for-byte the real
  ones. A token sweep for the real names/employers/SSN/DOB markers returns zero. To regenerate:
  re-run the live pipeline over the raw snapshot, then re-apply the reduce+scrub before committing.
- **Calibration flags are dimension-aware.** `unknown` is a true abstention for `is_money_in` /
  `has_identified_source` (→ couldnt_check) but a legitimate value for `apparent_category`, so
  over-abstention is only flagged on the former; accuracy-when-concrete is flagged everywhere.
- **Evaluate, don't fix.** No rule/tag logic was touched. Every golden expectation was derived from
  the pipeline's actual, intended behavior; where a case revealed a surprising real-trace detail
  (LF-6T3N's two low-confidence needs_review), it was recorded, not patched away.

## What the GO/NO-GO decision should weigh

**A pass (GO) looks like:** all 12 cases green at both levels; both-directions coverage `ok`;
LF-6T3N 0 fired; every FIRED/NEEDS_REVIEW verdict carries inline provenance with a WHY; and in
**live** mode, low unknown rates on `is_money_in` / `has_identified_source` with high
accuracy-when-concrete (the tags commit, and are right when they commit).

**Red flags (NO-GO):** any must-fire case that does not fire, or any FIRE on LF-6T3N (a
false positive on real data); a `verified` strength without a cited matched debit; an
empty-reasoning FIRED/NEEDS_REVIEW verdict; **over-abstention** (`is_money_in` /
`has_identified_source` unknown-rate high → everything routes to couldnt_check, the check is
useless); or **under-abstention** (accuracy-when-concrete below the floor → the model fabricates
confident wrong values, the dangerous direction for a fraud check). Keyless is a plumbing baseline
only — a real GO on tag *accuracy* needs the live calibration numbers.
