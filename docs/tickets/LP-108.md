# LP-108 — Honest needs satisfaction (graded needs "attach, confirm coverage") + always show the matched document

- **Ticket:** LP-108
- **Status:** Completed
- **Date:** 2026-07-03
- **Scope:** Backend (satisfaction logic + API) + frontend (needs card/actions)

## The bug — a dangerous false-green

The needs engine matched a document to a need at TYPE granularity (`needs_type == document_type`)
and, on a completed match, auto-advanced RECEIVED → VERIFIED ("satisfied"). Fine for a
**simple-presence** need (one document IS the requirement). But for a **graded** need — the
requirement is inherently more than "one document exists" (2 years of tax returns, 2 months of bank
statements, "all asset accounts covering two months") — the FIRST matching statement flipped the
whole requirement to "satisfied". A processor sees green and believes the documentation is COMPLETE
when 7 of 8 statements are missing. Unlike the project's other bugs (loud/safe), this **claims more
verification than performed** — the dangerous direction.

On LF-6T3N it was masked only by an unrelated pay-stub truncation (LP-102); fixing/reprocessing that
would have UNMASKED it — so the honesty fix had to ship, not a display-only change.

## The fix (Option B — honest satisfaction; NOT Option A account-level coverage)

### 1. Classify simple-presence vs graded (safe-default graded)

`_SIMPLE_PRESENCE_NEEDS_TYPES` (an allowlist) names the needs where ONE document is the whole
requirement: drivers_license, purchase_agreement, gift_letter, letter_of_explanation,
homeowners_insurance, title_commitment, appraisal, verification_of_employment, payoff_statement,
existing_mortgage_statement. **Everything else — including every AI-proposed need and any
unknown/None type — is GRADED** (safe default: under-claiming is a mild annoyance; over-claiming a
false-green is the danger). **Grounded starter — validate-with-Priya.**

### 2. Honest transition

`apply_document_to_needs`: a matched completed document → RECEIVED. Then:
- **simple-presence** → auto **VERIFIED** (the match IS the verification), as before;
- **graded** → **stops at RECEIVED = "documents attached — confirm coverage"** (never a false-green).

The processor confirms the coverage the system can't (all accounts / months / years) via a new
`POST /needs/{id}/confirm-coverage` (RECEIVED → VERIFIED) — the `confirm_need_coverage` service. Since
RECEIVED was already a transient "arrived, not verified" state, a *persisting* RECEIVED now means
"confirm coverage" — **no new status, no migration**.

### 3. Always show the matched document

`NeedsItemPublic` already carries `satisfied_by_document_id` + `_filename`. The card shows the
document by name for BOTH states — **"Attached: {doc}"** (received) and **"Satisfied by {doc}"**
(verified) — plus, on a received graded need, an **honest note** ("Documents attached — confirm this
covers the full requirement (all accounts / months / years); the system verified a document is
present, not the complete coverage") and a **"Confirm coverage"** action. A new
`requires_coverage_confirmation` flag on the response makes the graded/coverage nature explicit.

### 4. Umbrella needs match by category

An AI umbrella need naming a category (`asset_statement`) matched no concrete document type, so it
never attached. It now matches any document in the mapped category (`asset_statement → ASSETS`,
`income_document → INCOME_EMPLOYMENT`) — a **coarse, category-level** match landing in the same honest
RECEIVED state. This is **NOT** account-level coverage matching.

## Scope boundaries

- **Option B only.** No account-level coverage matching (parse which account, track N accounts × M
  months, a coverage grid) — that is **Option A / V2**, documented in the plan's V2 section.
- **Need generation unchanged** — only satisfaction/matching honesty + display.
- **Grounded-starter classification** — the simple-vs-graded allowlist is validate-with-Priya.

## The LF-6T3N asset need

Its `needs_type = "asset_statement"` (umbrella) previously matched no document → it sat **Pending**
(already honest — not a false-green). With the umbrella→category match it attaches an ASSETS-category
document and shows **RECEIVED = "documents attached — confirm coverage"** — never a false "satisfied".
Verified by `test_umbrella_asset_need_matches_asset_document_by_category` (the exact scenario). No
real-data mutation was required to confirm the honest model prevents the false-green.
