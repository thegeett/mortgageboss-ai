# LP-391 — Pending-check surfacing: a blocked-but-applicable rule flags manual review instead of silence

## What this ticket is

A BLOCKED rule (not in `ACTIVE_RULE_IDS` — uncalibrated tag / missing producer) runs NOTHING, so a file that
qualifies for it produces SILENCE — which reads as "checked, nothing found" when it is really "didn't look".
For real-file testing (a processor on staging) that hides real issues. This makes a blocked-but-APPLICABLE
rule surface to Tab 1 (Needs Attention) as an explicit **"manual review — automated check not yet active"** —
**without shipping the uncalibrated verdict**. A THIRD rule state (applicable-but-manual), between live
(trusted) and inert (silent).

## Acceptance criteria (met)

- A blocked rule that is applicable-with-data emits a `PENDING_AUTOMATION` manual-review flag; renders NO
  verdict (no-leak asserted).
- The flag is a DISTINCT outcome (Tab 1), never mistakable for satisfied/open/needs_review.
- A blocked rule that can't detect applicability (data / producer absent) stays silent — no fabricated flag.
- The 20 live rules are IDENTICAL; `ACTIVE_RULE_IDS` unchanged (this is NOT activation); full suite green.

## Phase 1 — the mechanism (generic, declared, no per-rule branch)

`pending_checks.evaluate_pending_checks`: evaluate each blocked candidate rule (generic — activation-bar
candidates **minus the active set**) with the SAME dispatch the live rules use; convert each
satisfied / fired / needs_review into a `PENDING_AUTOMATION` flag; drop couldnt_check / not_applicable.

- **The verdict is DISCARDED, never shipped.** The flag carries `verdict = PENDING_AUTOMATION`,
  `load_bearing_tags = ()`, `verdict_confidence = None` — the uncalibrated value never rides along.
- **The surface:** new `Verdict.PENDING_AUTOMATION` + `EvaluationOutcome.PENDING_AUTOMATION` (Tab 1, YELLOW);
  a distinct frontend label **"Manual review"** — unmistakable as "not yet automated", never a trusted
  pass/fail (its own tone/blurb, separate from `needs_review` / `couldnt_check` / `satisfied`).
- **Materialization, isolated + best-effort:** a blocked rule reaches a verdict only if its tags are
  materialized, and production materializes only the LIVE groups. So the pass materializes the blocked rules'
  groups too — the deliberate extra AI cost — but on a THROWAWAY snapshot copy, wrapped so a
  blocked/uncalibrated group can **never** flip `run.degraded` or leak its tags into the persisted snapshot,
  and any failure yields no flags rather than failing the run.
- **Additive + disjoint:** the pending pass runs a rule set DISJOINT from the live pass (blocked ≠ active), so
  the 20 live verdicts are byte-untouched.

## Phase 2 — the proof (reported, not predicted; a point-in-time real run)

On `build_lf6t3n_plus` (real AI), `evaluate_pending_checks` produced **7 manual-review flags**:
`IN-7` ×2, `IN-8` ×2, `IN-10` ×1, `IN-11` ×2 — each naming its scope ("Declining income", "Variable income
averaging / history", "Same line of work (job change)", …). **Zero leaks:** every flag is
`pending_automation` with zero load-bearing tags — no satisfied/fired verdict, no uncalibrated tag value,
escaped. The dark rules (AS-4/5/6/7/11, IN-12/13/14, AS-3, IN-9) surfaced **nothing** — honest silence where a
verdict couldn't be reached.

## Phase 3 — tests + equivalence

- A blocked rule reaching a verdict → a `PENDING_AUTOMATION` flag with empty load-bearing tags (no leak);
  a blocked rule with no data → nothing (no fabricated flag); the blocked set is exactly bars − active
  (generic); the pending outcome is DISTINCT from satisfied/open. (`test_pending_checks_lp391`.)
- Frontend: `pending_automation` maps to Tab 1 with a distinct "Manual review" label
  (`rule-findings-tabs`, tsc/biome green).
- **EQUIVALENCE:** `ACTIVE_RULE_IDS` unchanged (20); the live pass + the persisted snapshot + `run.degraded`
  unchanged (the pending materialization is isolated/best-effort); full suite green (ruff + mypy clean).

## Assumptions, decisions & gaps

- **ADR-312** records the third state, the applicability-vs-verdict line, the can/cannot split, and that this
  never ships an uncalibrated verdict.
- **The AI cost of surfacing** is real and accepted (the user's "materialize + convert" choice): a run now
  materializes the blocked rules' groups (on a throwaway copy). A future optimization could short-circuit
  judgment rules (a judgment rule always reaches needs_review when applicable, regardless of the AI answer we
  discard) to avoid those model calls.
- **Reported gaps (not this ticket):** AS-11's `retirement_account`-only applicability vs the fixture's
  `investment_account` assets (a spec scope gap); the CANNOT-surface rules (AS-7 NSF, IN-14 rental) stay dark
  until their producer (LP-390-8); the document rules (AS-5/AS-11/IN-12) surface only on a file that carries
  the gift-letter / retirement-account / tax-return document.
- **The path to a real verdict** replacing a manual-review flag, per rule: calibration (a Priya-signed bar) or
  a producer — the LP-390 status of each blocked rule is the roadmap.
