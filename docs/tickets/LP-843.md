# LP-843 — A non-borrower email in a non-borrower voice

Status: spec. Build order: second of four. Shares a template version bump with LP-844.

## The report

> "Current email message says 'We are working through your loan file and there are a few documents
> we still need from you.' to send an email to Employer. Also to send email to lender it says [the
> same]. These look like processor sending email to borrower. Because we say we are working through
> your loan file. It is actually borrower's file."
>
> "borrower emails explain; lender emails specify."

## Why it happens

LP-841 files a lender draft under the template key `document_request_lender`. **There is no such
template.** `TemplateKey` has five members and that is not one of them, so `render_draft_body`
renders `initial_documentation_request.v4.txt` for every party. An employer receives:

    Hello $borrower_first_name,
    We are working through your loan file and there are a few documents we still need from you.
    ...
    Anything sent to that address reaches your loan file directly...
    If anything on the list is unclear ... That is quicker for both of us than sending the wrong
    thing twice.

Every one of those sentences is addressed to the borrower. The routing LP-841 built is correct; the
words it routes are not.

A second consequence, smaller and worse: a non-borrower document gets **no guidance at all**.
`render_document_block` raises on a non-borrower type, and `_document_line` only calls it when the
catalog has a `borrower_label` — which non-borrower types do not. They fall through to the bare
title, which is why a lender list is four naked nouns.

## THE SECURITY DECISION, made here and recorded

The shared template interpolates `$inbox_address`, so every lender, employer and title draft
**currently contains the loan file's inbox address**. That address is a bearer capability (ADR-397):
anyone holding it can post documents into that file, and nothing authenticates the sender.

**Decision: non-borrower templates do NOT carry the inbox address.** Reply-to-this-message is the
return path for a third party.

The reasoning is asymmetry of cost, not certainty of harm. Handing a third party write access to a
borrower's file is not obviously wrong — it is how the borrower's own path works — but it is a
capability we cannot withdraw once an email leaves, and the party who bears the consequence is not
the party we gave it to. Adding it later is one template version; un-sending it is impossible.

This is recorded as a decision rather than a finding because the user was asked and did not answer,
and the reversible direction is the one to be wrong in. It is worth re-raising once someone wants to
send a title company documents at volume.

## The change

A template per non-borrower party, at a new version under ADR-401 (a new file, never an edit — the
pinned fingerprint of v4 must keep resolving to the words v4 sent).

**Every non-borrower template opens by identifying the file**, which today's does not at all:

    Borrower:  {name}
    Property:  {address}
    Reference: {display_id}

`display_id` (LF-XMB2) is OUR identifier. A lender matches on borrower name and property address; a
lender's own loan number is not a field this system holds today, and the ticket must not imply it
does — check before putting one in a subject line.

**Lender / title: specify, do not explain.** No "where to get it" — they know. What helps is which
version: "Closing Disclosure — most recent", "Credit report — the one used for underwriting".

**Employer: name the employee and the fields.** Not "VOE" but "Verification of Employment", the
employee's name prominently, and the fields a complete verification carries. The catalog has exactly
ONE employer type and no guidance entry for it, so that content has nowhere to live yet — this
ticket adds it.

## Not in scope

Third-party verification services (The Work Number) as a branch in the employer email. Real, and it
needs a decision about what we do with the answer, not just a sentence in a template.

# Built

## The structural problem the spec did not see

The spec assumed this was a copywriting ticket. It is not: `template_key` was being asked to mean two
things, and that is why there was no template to write.

LP-841 stored `document_request_lender` in `Communication.template_key` so the communication page
could bucket by it. That forced a choice with no good branch — either give each party its own
template (six near-identical files, six ADR-401 fingerprints, one edit to get wrong five times), or
share a template and lose the tabs the report explicitly asked for.

**And it had already broken ADR-401.** A lender draft stored `template_key="document_request_lender"`
with `template_version="v1"`, and no such template has ever existed. The pair named nothing. The
pin's entire purpose is that a stored key and version resolve to the words that were sent; a row
resolving to nothing cannot be audited and cannot be told apart from one that resolves.

So `Communication.party` is a new column, and the two questions separate:

- **`template_key`** — what rendered it. Resolves again, for every party.
- **`party`** — who it is for. What the tabs read.

Five parties share one professional template and still get five tabs.

## Two voices, not six

Lender, title, accountant, agent and insurer are third-party professionals being asked for a document
they already hold; the same words serve all of them and the document list is what differs. The
employer needs its own, because a VOE is a form to **complete** rather than a document to retrieve,
and an incomplete one costs another round trip — so that template names the fields.

Both open with an identification block. `display_id` is OURS: a lender files by borrower name and
property address, and "LF-XMB2" names nothing they can search. It is still included, because it is
what they quote back. A line the file has nothing for does not appear at all — a purchase file often
has no address for weeks, so that is the ordinary case, not the degraded one.

## The inbox address: decided, and now asserted

Neither non-borrower template carries `$inbox_address`. The reasoning is in the spec above; what
changed is that it is a test rather than a comment, and it asserts on the **rendered body** rather
than on the declared variables — a template that does not declare the slot could still be handed the
address through the identification block, which is built from file data and is exactly where it would
arrive.

Both templates do carry the security caution and a route out of email, via LP-834's
`secure_upload_block`. A time-limited upload link is a different risk from the permanent, unscoped
inbox address, and a third party emailing a credit report deserves the caution more than the borrower
does, not less.

## The rest of a class the LP-842 review opened

That review found three asks written to a reader who could never receive them. Making the renderer
party-aware let IH-7's be re-aimed — it now addresses the insurer who holds the master policy, rather
than telling them to go and ask the association — and `test_every_ask_has_exactly_one_possible_reader`
then found **two more of the same class**: ID-5 and IH-3 each declare documents held by two different
parties, so one sentence would be read by the borrower and the lender both.

Both asks are dropped with the reason in the spec. The real fix is choosing the ask per DOCUMENT
rather than per rule, which is a model change this ticket did not make.

Voice is not checkable. WHO WILL READ IT is, and that is the half now pinned.

## What the mutations caught

The timeline mutant — ignoring the stored party — **survived twice**. The first time because
`template_key` was still per-party, so the fallback still worked: the column was not yet load-bearing
and I had not noticed. Fixing `draft_template_key` to store the rendering key made it load-bearing
and the mutant still survived, because no test built a third-party draft at all. It dies against
`test_a_lender_and_a_title_draft_land_in_different_buckets`, which needs TWO parties sharing ONE
template — one draft would pass against a build that reads the key, because one key still maps to one
something.

## Review — REVIEWED

Two findings, both in the placement of a draft rather than in its prose, and both found by deriving
a mapping rather than reading one.

**1. The compatibility arm matched the NEW key against rows carrying the OLD one (question B).**
`_open_drafts_stmt`'s second arm compared `template_key` against `draft_template_key(party)` — this
ticket's value. Re-derived for all eight parties:

| party | the arm looked for | LP-841 actually wrote |
|---|---|---|
| lender | `document_request_third_party` | `document_request_lender` |
| title | `document_request_third_party` | `document_request_title` |
| cpa / agent / insurer / processor | `document_request_third_party` | `document_request_<party>` |
| borrower | `initial_documentation_request` | also `document_request_borrower` |
| employer | `document_request_employer` | `document_request_employer` ✓ |

**Six of eight covered nothing**, and `employer` matched only because its new key happens to equal its
old one. So the one row the arm exists for — a draft created by the old code *after* the migration,
`party IS NULL` with an LP-841 key — was invisible to `open_drafts`, and the next request would mint a
second: the fork the arm was written to prevent. Rows that predate the migration are fine either way;
the backfill sets `party` and the first arm finds them.

Fixed with `_legacy_draft_keys(party)`, derived from `template_key_for` — LP-841's own function, so
the set comes from the thing that wrote the rows rather than being restated. The borrower carries
both keys, matching what the migration's CASE maps. Tested by writing the row the old code would have
written, with a control that a different party must not adopt it; mutating back to the new key fails
it, and widening the arm to any unlabelled draft fails it too.

**2. An outbound reply can be placed and was not.** Of the seven `Communication(...)` construction
sites in `app/`, only `email_draft` and `party_requests` set `party`. Reply and compose drafts carry
`template_key=None` (LP-818, so several can be open at once), so `_party_of` fell through both arms
and returned None — and a processor who replies to the title company got a draft in **no tab**, on the
screen this ticket exists to give them tabs on. The most natural follow-up action was the one that
fell out.

Unlike the inbound case this is placeable: we chose the recipient, it is on the row, and `by_address`
is already built for the page. Added as a third arm. None stays the answer for an address nobody on
the file recognises — that is genuinely "cannot place it" — and both halves are asserted.

### Question C — the judgement holds, and the mechanism is stronger than the assertion it replaced

Checked independently rather than reasoned about. The third-party template's greeting is a bare
`Hello,` with **no** name slot, and `borrower_name` appears only in the subject line
(`Outstanding documents — $borrower_name — $loan_reference`), which is the identification the change
is for. So "subject of the message, never its addressee" is an accurate description of what shipped.

Re-ran the mutation the judgement rests on — restoring `Hello $borrower_first_name,` to the
third-party template — and **13 tests fail**, not two. The reason matters: the template's *declared
variable set* is what makes the leak impossible, so a greeting cannot be added without declaring the
variable, which changes the spec, which changes the fingerprint. That is a structural guard where the
old assertion was a string check. Weakening two content assertions and landing on that is a net
strengthening.

### Question A — the backfill is complete; the view is right

`template_key_for` over every `ResponsibleParty` produces eight keys and the CASE covers all eight,
plus `initial_documentation_request`. Nothing it can produce is missed. The four unmapped
`TemplateKey`s (`reminder_follow_up`, `status_update`, `condition_response_request`, `custom`) have
never had a writer, so no rows carry them; `document_request_third_party` is new in this commit, so no
historical row carries it either.

`readonly.communications` re-derived against a live database: model 25 / table 25 / view 19, and the
six excluded are exactly `body`, `subject`, `sender`, `recipient`, `in_reply_to_message_id`,
`upload_link_url` — the never-exposed set. Grant to `mbai_readonly` present. No repeat of last
ticket's mistake.

### The `git checkout` warning — checked directly, registry intact

Seven `TemplateKey` members, seven specs, twelve pinned versions, every pin with a file, every hash
matching, no file on disk unpinned and no pin without a file. Nothing is half-applied.

### Question D, and the per-document ask model

The employer VOE field list is a domain question and goes to the resident expert, like ID-8 — it is
the same class and CLAUDE.md is explicit. Noting for them that immigration status is correctly absent,
so the ID-8 concern does not apply to this template.

**The per-document ask model belongs in its own ticket, not this one.** Three asks have now been
deleted for the same reason across two tickets, which is evidence for building it rather than for
widening a ticket that already carries a new column, a backfill, a view rebuild and two authored
templates. The deletions are recorded and reversible; none of them is urgent.

**No template text changed in this review**, so the LP-844 version bump is unaffected.
