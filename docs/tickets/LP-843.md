# LP-843 — A non-borrower email in a non-borrower voice

Status: spec. Build order: second of four. Shares a template version bump with LP-844.

## The report

> "Current email message says 'We are working through your loan file and there are a few documents
> we still need from you.' to send an email to Employer. Also to send email to lender it says [the
> same]. These look like processor sending email to borrower. Because we say we are working through
> your loan file. It is actually borrower's file."
>
> "borrower emails explain; lender emails specify."

## Why it happens

LP-841 files a lender draft under the template key `document_request_lender`. **There is no such
template.** `TemplateKey` has five members and that is not one of them, so `render_draft_body`
renders `initial_documentation_request.v4.txt` for every party. An employer receives:

    Hello $borrower_first_name,
    We are working through your loan file and there are a few documents we still need from you.
    ...
    Anything sent to that address reaches your loan file directly...
    If anything on the list is unclear ... That is quicker for both of us than sending the wrong
    thing twice.

Every one of those sentences is addressed to the borrower. The routing LP-841 built is correct; the
words it routes are not.

A second consequence, smaller and worse: a non-borrower document gets **no guidance at all**.
`render_document_block` raises on a non-borrower type, and `_document_line` only calls it when the
catalog has a `borrower_label` — which non-borrower types do not. They fall through to the bare
title, which is why a lender list is four naked nouns.

## THE SECURITY DECISION, made here and recorded

The shared template interpolates `$inbox_address`, so every lender, employer and title draft
**currently contains the loan file's inbox address**. That address is a bearer capability (ADR-397):
anyone holding it can post documents into that file, and nothing authenticates the sender.

**Decision: non-borrower templates do NOT carry the inbox address.** Reply-to-this-message is the
return path for a third party.

The reasoning is asymmetry of cost, not certainty of harm. Handing a third party write access to a
borrower's file is not obviously wrong — it is how the borrower's own path works — but it is a
capability we cannot withdraw once an email leaves, and the party who bears the consequence is not
the party we gave it to. Adding it later is one template version; un-sending it is impossible.

This is recorded as a decision rather than a finding because the user was asked and did not answer,
and the reversible direction is the one to be wrong in. It is worth re-raising once someone wants to
send a title company documents at volume.

## The change

A template per non-borrower party, at a new version under ADR-401 (a new file, never an edit — the
pinned fingerprint of v4 must keep resolving to the words v4 sent).

**Every non-borrower template opens by identifying the file**, which today's does not at all:

    Borrower:  {name}
    Property:  {address}
    Reference: {display_id}

`display_id` (LF-XMB2) is OUR identifier. A lender matches on borrower name and property address; a
lender's own loan number is not a field this system holds today, and the ticket must not imply it
does — check before putting one in a subject line.

**Lender / title: specify, do not explain.** No "where to get it" — they know. What helps is which
version: "Closing Disclosure — most recent", "Credit report — the one used for underwriting".

**Employer: name the employee and the fields.** Not "VOE" but "Verification of Employment", the
employee's name prominently, and the fields a complete verification carries. The catalog has exactly
ONE employer type and no guidance entry for it, so that content has nowhere to live yet — this
ticket adds it.

## Not in scope

Third-party verification services (The Work Number) as a branch in the employer email. Real, and it
needs a decision about what we do with the answer, not just a sentence in a template.
