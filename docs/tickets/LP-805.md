## This module contains the one inversion of the tenancy invariant

Everywhere else `company_id` comes from an authenticated user and scopes the query before it runs.
`resolve_loan_file_by_address` starts from an address a stranger typed, finds a file, and the company
is read **off the file**. Nothing else in the tree may do this; the protocol makes a second one a
blocking finding.

Three properties, each for a non-obvious reason:

- **Unknown and expired behave identically**, and both behave like an address that was never valid.
  A resolver that distinguished them is an **oracle**: send to a guessed token and a different
  response tells you whether that file exists.
- **The lookup is case-insensitive.** Relays rewrite case in the local part freely, and a
  case-sensitive lookup sends a borrower's documents to triage because their phone capitalised the
  first letter. The cost is stated in the code: `inbox_token` comes from `secrets.token_urlsafe`,
  which *is* case-significant, so this is a deliberate narrowing of its entropy — accepted because a
  borrower whose documents vanish is worse than roughly one bit per alphabetic character against an
  attacker who already has to guess 128.
- **The domain is part of the credential.** Matching the local part alone would let a token lifted
  from one environment resolve against another — staging tokens opening production files.

## Rungs 1 and 2 only, and the docs disagree about that

`phase4.md` §7 assigns LP-805 *"ladder rungs 1–2"* and LP-808 *"rungs 3–5"*. The build plan's LP-805
section says *"the six-rung ladder"*. **Recorded rather than resolved by picking the larger
reading** — rung 3 in particular is one line away, since LP-811a already built `loan_reference_in`,
and if the reviewer reads the build plan as authoritative it should come here.

**Rung 2 matches the whole `References` array**, which the plan calls out. Clients truncate the
middle of a long chain differently, so the entry that survives in one borrower's reply is not the one
that survives in another's — matching only the tail makes a long thread route for some clients and
not others, which reads as intermittent rather than as a bug. The test puts our id in the **middle**,
neither first nor last; truncating to the tail fails it.

## A surviving mutant found a negative test that could not fail

Dropping rung 2's id filter entirely — matching **any** communication — left all 27 tests green. The
negative test created a company and a file and **no communications at all**, so "match anything"
found nothing and the assertion held.

The reachable danger is another company's message. The fixture now contains a communication that
exists and does not match, and the mutant fails.

That is the same lesson as LP-804b's deny-list and LP-811a's `_setup`, and it is the third distinct
form: **a negative assertion is worth only what the fixture makes reachable.**

## Quarantine is the default

`phase4.md` §2.3, implemented as written. `TRIAGE` is what happens unless every auto-accept condition
holds; `REJECT` is reserved for the three cases where there is nothing for a person to decide.

**`GRAY` is not `PASS`** — the subtlety §2.3 names. SES's `dkimVerdict: GRAY` most often means
*signed by a domain that does not match `From:`*, precisely the spoofing case. Verdicts are compared
for **equality with PASS** rather than tested for "not FAIL", so an unrecognised verdict fails closed.

**Auto-accept is unreachable in production today.** `LoanFile.auto_accept_inbound` is LP-806's column
and does not exist. The branch is written and tested anyway, deliberately: LP-806 turns a flag on
rather than inventing the policy under time pressure.

## Membership is not trust

Seeding from `borrowers.email`, `loan_files.loan_officer_email` and `lenders.contact_email` — all
populated today, so the allowlist is real on day one rather than a table somebody has to fill in.

Seeding sets membership and **never** sets `is_trusted_sender`. An estate agent belongs on the file
and is not somebody whose attachments should bypass review. Re-seeding also never *revokes* trust: it
runs again whenever a borrower's email is edited, and it must not quietly undo a decision a person
made.

Participants are **file-owned, not company-owned** (ADR-052), and here that is more than convention:
the same address is routinely on two companies' files — a borrower shopping two brokers — and a
company-scoped table would make "is this sender known?" a question with a cross-tenant answer.

## What routing writes

`Communication(direction=INBOUND, status=RECEIVED)` and `COMMUNICATION_RECEIVED` — the model and the
enum value have both existed since LP-20 and **neither has ever been used**.

The inbound `Communication` carries **no subject, no body, no sender**: they are on the
`inbound_message` row, whose readonly view already drops them, and copying them here would put
borrower prose in a second place with its own exposure decisions. It also carries no arrival
timestamp — `Communication.sent_at` is about outbound mail, and reusing it would make "when did we
send this" answer with a time nobody sent anything.

**An unrouted message gets no `company_id`.** Guessing one from the sender is exactly the derivation
this module exists to confine.

## Review (second session, protocol §3)

One finding. The tenancy work — which is the reason this ticket is the one to hold hardest — is
correct, and I checked it by sweeping rather than by reading the resolver.

### The invariant, swept rather than assured

The builder asked me to look for a second address→company path including one it might not have
noticed building. Every assignment to `company_id` in `services/`, `api/` and `tasks/` is either a
filter, a value from `current_user`, or a read off an already-resolved loan file. **Exactly one
writes it on an inbound message:** `inbound_routing.py:308`,
`message.company_id = outcome.loan_file.company_id`. An UNROUTED message gets none, which is right —
guessing from the sender is the derivation this module exists to confine.

**Rung 2 is not a second inversion**, though it was the first thing I went after. It resolves through
`Communication.external_message_id`, a message-id we generated, not an address. What I actually
suspected was worse: `In-Reply-To`/`References` are unauthenticated sender-supplied headers, they
carry confidence `1.0` — identical to the 128-bit token — and confidence gates auto-acceptance. So a
forged reference looked like it could file an attacker's attachment onto a loan file.

It cannot, for two reasons I confirmed rather than assumed. `phase4.md` §2.2 assigns rung 2
**certain** itself, so the confidence is the plan's decision and faithfully implemented. And
auto-accept requires far more than confidence: DMARC PASS, virus PASS, not a DSN or auto-reply, and
`is_trusted_sender` **on that specific file**. A forged thread reference from an unknown sender goes
to triage. The defence is layered exactly where it needed to be, and my concern dissolved on
reading the gate.

Worth stating for anyone who re-opens it: the token is not more secret than a message-id in
practice. The initial-request template prints the inbox address in the body and it is the `Reply-To`
on everything we send, so both are known to precisely the same population — anyone who has seen one
of our emails. Treating them as equal evidence is defensible for that reason, not merely because the
spec says so.

### A — The case-insensitive token lookup cannot use any index

`resolve_loan_file_by_address` compares `func.lower(LoanFile.inbox_token)`. The only index on that
column is the plain unique btree from LP-13, and PostgreSQL cannot use a btree index for an
expression.

Measured with `enable_seqscan = off`, which costs a sequential scan at ten billion:

```
exact  (index-friendly): Index Scan using ix_loan_files_inbox_token on loan_files  (cost=0.14..8.15)
lower() (as written)   : Seq Scan on loan_files  (cost=10000000000.00..10000000010.45)
```

The planner chose the sequential scan anyway, which means no index could serve the query — not that
it preferred not to.

This is the hottest path in inbound routing: every message resolves a token. It is also the path an
attacker probes by mailing guessed addresses, which this ticket itself records as having no rate
limit — so a full table scan per guess is the wrong cost to hand them, and the two escalations
compound.

Fixed with a functional index on `lower(inbox_token)`, in the migration and on the model so
`create_all` builds it and a test can observe it. Non-unique deliberately: the raw-token unique
index already prevents duplicates, and a unique functional index could fail to build on an existing
database over a case-only collision.

The test asserts through the **planner**, not `pg_indexes`, because the index existing and the query
using it are different claims — a differently-spelled expression would leave this scanning while the
catalogue still looked right. Verified by removing the index: the test fails.

### The builder's three, ruled on

1. **Case-insensitive matching — keep it.** It costs roughly 128 bits down to ~115: `token_urlsafe`
   draws from 64 symbols and lowercasing collapses to 38, over 22 characters. That is not a
   meaningful reduction against guessing, and the failure it prevents is concrete — a relay
   rewriting case makes a borrower's documents vanish into triage with nothing to explain it. The
   right instinct was flagging that you were weakening a capability rather than doing it quietly.
   The index above is the cost that actually needed paying.
2. **Rungs 1–2 only — right, and the narrower reading is the correct one.** `phase4.md` §7 assigns
   LP-805 rungs 1–2 and LP-808 rungs 3–5, and its ticket table (line 824) says the same. The build
   plan's "the six-rung ladder" is the looser phrasing of the two, and rungs 3–5 need the
   original-hop trust evaluation LP-808 builds. Rung 3 being one line away is not a reason to take
   it: it would arrive without the ARC and surviving-DKIM checks that make it safe to trust a
   forwarded hop.
3. **`AUTO_ACCEPT` returnable but unreachable — keep it, and the counter is answered by the gate.**
   The worry is that policy never exercised in production gets flipped on carelessly. But the policy
   is not "trust certain matches" — it is certain match AND DMARC PASS AND virus PASS AND a trusted
   sender on that file. LP-806 flipping a flag inherits all four. Writing it here, with tests, is
   what makes that true; inventing it under time pressure in LP-806 is what would not.

### Both escalations are real and correctly recorded

Rung 1 missing Cc/Bcc is a genuine behaviour gap — §2.2 names To/Cc/Bcc/`X-Gm-Original-To` and
LP-803 collects only `To` and `Delivered-To`, so a borrower who CCs the file address lands in triage.
Not reaching into a REVIEWED ticket to change behaviour is the right call. The probing rate limit
needs `receipt.sourceIp`, which LP-803 does not store — also correctly left rather than half-built.

Saying plainly in the docstring that `EmailThread` is created by nothing is the right way to ship a
table the plan asks for ahead of its first writer. A name that implies a mechanism which does not
exist is how the next reader wastes an afternoon.

subject, body or sender address; no AI on this path.
