# LP-569 — the LP-566 scrub was a no-op on the real data shape

**Status:** done · **Source:** code review of LP-565/566/567, 2026-08-19

## Finding 1 (HIGH) — the fix and its test shared the same wrong assumption

`property_tax_bill.tax_year` is `TypedField[int]`, parsed with `coerce_int`, so a leaked digit run
reaches the snapshot as the **int** `202520261234`. The LP-566 scrub was gated on
`isinstance(scalar, str)`, so the int walked straight past it. Reproduced against the real
functions:

```
int  (real extractor shape)  -> stored 202520261234   -> RawPiiAtRestError, SNAPSHOT REFUSED
str  (LP-566 test fixture)   -> stored '[redacted]'   -> guard passes
```

The whole loan file still lost its snapshot — the exact failure LP-566 set out to prevent,
surfacing further from its cause.

**Finding 2 is the same defect, and is why it shipped green.** The LP-566 test passed
`"2025 998877665544"` — a `str` the extractor can never produce — directly into
`build_document_fields`, bypassing the coercion. It asserted the one path that worked while
production took the one that did not. My "verified by removing the fix" check passed for the same
reason: the check was sound, the fixture was not.

**Fix.** Scrub the value's TEXT FORM, not just a `str` instance, and only replace when the scrub
actually changed something — so a clean `tax_year` of 2025 keeps its int type while a leaked run
becomes the redacted string. Losing the int on a value that was never a year is the correct trade.

## Finding 5 (LOW as reported, wider in fact) — close the class

The review named three sibling `policy_status` fields. Grepping every extractor found the class is
larger: **`tax_year` is declared by nine document types** (property_tax_bill,
property_tax_bill_non_subject, form_1098, 1099, transcripts_of_1099, k1_statement,
k_1_shareholder_profit_and_loss_transcripts, tax_return, w2) and **`policy_status` by four**. A
defect on any one refuses the whole file's snapshot. All thirteen pairs are registered.

`test_every_declaring_doc_type_is_registered` fails when a new extractor declares either field
without registering it. It covers those two field *names*, not leak-prone fields in general — a
genuinely new one still has to be noticed the hard way.

## Finding 4 (MEDIUM) — a failed re-extraction wiped correct links

`assign_document_borrower_links` opens with an unconditional `DELETE` and only then looks for
names, so a call that **succeeds while finding nothing** commits the wipe; only an exception rolls
back. A FAILED extraction is exactly that path — all-null data, `asserted_names_for` returns `[]` —
so a pay stub correctly linked to a borrower lost that link on a retry or an LP-44 type override,
before the FAILED branch was even reached. The LP-567 comment claimed the savepoint left the
previous version's links standing; that is true only for an exception, not for the common path.

**Fix at the call site, not in the service.** "A re-match is authoritative" is correct for a genuine
re-match — a document retyped to something with no name field *should* lose its links. Only the
caller knows the extraction read nothing, and absence of data is not a determination that the
document names nobody (§8).

## Finding 6 (LOW, pre-existing) — recorded as LP-570, not fixed

`policy_number` is registered `(ACCOUNT, pre_masked=True)`, but `_PII_FIELDS` is keyed by field
**name alone** and four types declare it with disagreeing prompts: `flood_insurance_policy` says
"Mask the policy number" (pre-masked, correct), `homeowners_insurance` asks for "the policy number"
plain (raw → truncated to last-4 with `match_hash=None`, lossy *and* non-joinable — the LP-461 bug
described on `loan_number`). One name-keyed entry cannot be right for both.

Left as-is deliberately: correcting it means doc-type-aware PII routing, and flipping the flag
globally breaks the flood case in the other direction. The LP-566 test case is annotated so a
passing row is not read as endorsing the routing.

## Finding 3 — deploy, not code

`image_tag = "staging-ab6506d"` names LP-566; LP-567 (`0cf6515`) and LP-568 landed after. Staging
must be redeployed from HEAD — and LF-WCHG's documents **re-extracted** — before `belongs_to`
populates, since links compute at extraction time.

# Second review round — five more findings

## Finding 1 (HIGH) — the LP-568 downgrade could not run

`downgrade()` used `CREATE OR REPLACE VIEW` to go from 11 columns back to 9. PostgreSQL only allows
a replace to **append** columns. Confirmed against the local instance:

```
CREATE OR REPLACE VIEW scratch.v AS SELECT 1 AS a, 2 AS b, 3 AS c;
CREATE OR REPLACE VIEW scratch.v AS SELECT 1 AS a, 2 AS b;
ERROR:  cannot drop columns from view
```

The migration aborted on that statement, and both `drop_column`s would have failed anyway while the
view still SELECTed those columns. My own comment described the right fix and the code did the
opposite.

Rewritten to DROP VIEW → drop columns → CREATE VIEW → **re-grant**, the LP-509-B1 pattern. The
re-grant is required on this path specifically: dropping loses the grant that `CREATE OR REPLACE`
preserves, so without it the read-only role silently loses access after a rollback.

`upgrade()` is unchanged — appending is legal and keeps the grant.

**Verified by running it**, not by reasoning: `alembic upgrade head` then `downgrade -1` against a
scratch database, ending with 9 columns and the `mbai_readonly` grant intact. The suite never
exercises migrations (tests use `create_all`, ADR-039), which is why this needed a real round trip.

## Finding 2 (MEDIUM) — an override on an excluded line was accepted, then discarded

The endpoint validated, persisted and audited an override on an excluded debt line, and the UI keeps
the pencil on every row — but `_to_items` skipped `engine_lines.append` regardless, so the figure was
echoed back and the DTI never moved. A processor who believed a mortgage was actually being retained
had no way to re-include it.

**An override now re-includes the line.** The exclusion is a claim about the file; overriding it
disputes that claim. Same precedent as the fail-closed housing gate, which already documents that
"an override on the line clears the gate (a processor-supplied figure is trusted)".

## Finding 3 (MEDIUM) — the two ternary chains disagreed on precedence

Caption tested `overridden → excluded → unknown`; amount styling tested `unknown → excluded →
overridden`. A row that was both rendered struck through while the caption read "overridden", so the
reason never appeared — a struck-through number with no stated reason, which is exactly the
silently-vanishing debt the feature exists to prevent. Finding 2's fix makes the states mutually
exclusive at the source; the chains are now identical anyway so a future change cannot re-open it.

## Finding 4 (LOW) — the exclusion indicator was recorded as a payoff

`LiabilityPayoffStatusIndicator` (retired at closing) and `LiabilityExclusionIndicator` (omit from
liability totals — paid by another party, a duplicate trade line) were collapsed into one flag with
`payoff_source="mismo"`. A file where only the exclusion fired got a line reading "paid off at
closing" and an audit trail asserting a payoff the export never stated.

Now `mismo_payoff` / `mismo_exclusion`, with the DTI line's wording derived from it:
"excluded from liabilities per the application" rather than a payoff claim.

## Finding 5 (LOW) — the flag had no human write path

Correct, and it made the mechanism inert on the very file that motivated it: the real export carries
`payoff=false` everywhere, so nothing could set the flag. `StatedLiabilityInput` now accepts
`paid_off_at_closing` and `StatedLiabilityPublic` returns both columns. `payoff_source` is **not**
accepted from the client — the route stamps it `processor`, and clears it when the flag is retracted,
so a caller cannot label their own judgement as the export's.

## A mypy syntax error that was really a prose bug

While fixing the above, mypy reported `Expected an indented block` on a line Python parsed fine. The
comment began `# type: tax_year 2025 stays the int 2025` — mypy read it as a **PEP 484 type comment**
and failed the file. Reworded, with a note not to open a comment line that way.
