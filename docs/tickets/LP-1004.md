# LP-1004 — AWS access for domain setup

Groundwork for step 3 (tenant domains). Terraform only; no app code.

## What and why

In step 3, a command run during a customer's onboarding call sets up their mail domain. It creates a
hosted zone for `mb-mail.<customer>`, writes the DKIM, MAIL FROM and DMARC records in it, and creates
and configures the SES identity. After that, an hourly check reads the zone and the identity to see
whether setup has finished or has broken (`loan-email.md` §3, decisions dated 10-31).

That needs two things the tasks did not have:

- **A network path to Route 53.** Tasks run in private subnets with no NAT and reach AWS only through
  interface endpoints (LP-985). SES already had one (`email`); Route 53 did not.
- **Permissions.** Only the role that runs setup (the api role, which the one-off command runs on via
  the migrate task definition) may create and change things. The worker only reads. Nobody can delete
  a zone or an identity, and the app can never touch what Terraform owns: our own zone and our own
  sending identity.

## What changed

**Route 53 endpoint.**
- `infra/envs/staging/terraform.tfvars` adds `"com.amazonaws.route53"` to `interface_endpoint_services`.
- Private DNS is on, with the same security group and subnet as the other seven endpoints.
- **Module fix:** the network module used to build every endpoint name as `com.amazonaws.<region>.<name>`. Route 53's name has no region, so a name that already starts with `com.amazonaws.` is now used as is (`infra/modules/network/main.tf`, with a one-line comment). The Name tag drops the prefix (`mbai-staging-route53`). The seven existing endpoints are unchanged.

**IAM (`infra/modules/compute/iam.tf`)**, all gated on the new `domain_setup_enabled` flag:

- **api role, `DomainSetupCreate`:** may create a hosted zone and look one up by name. These two can't be scoped to a zone that doesn't exist yet, so they take `*`.
- **api role, `DomainSetup`:** may read a zone, change and list its records, and follow a change until it is done; and may create, read and configure (MAIL FROM, DKIM) an SES identity. Resources are limited to hosted zones, changes and identities. It's one statement in the brief; it had to be two, because one statement can't give two actions `*` and the rest something narrower.
- **api role, `DomainSetupProtectOurs` (Deny):** may never change records in our Terraform-managed zone (`staging.mortgageboss.ai`, `Z10367452DVEMRBNRGRMY`), and may never change MAIL FROM or DKIM on our identity (`mail.staging.mortgageboss.ai`). An explicit Deny beats the wildcard allows, so a bug or a mistyped customer domain can't rewrite staging's own DNS or DKIM.
  - The ARNs come from Terraform (new outputs `module.dns.zone_arn` and `module.outbound_mail.send_identity_arn`), not typed by hand.
  - The account has exactly one hosted zone and one SES identity (checked with `list-hosted-zones` and `list-email-identities`), and both are in the Deny.
- **worker role, `DomainCheckRead`:** may read a zone and list its records, and read an SES identity. Read only.
- **Left out:**
  - delete actions, on any role;
  - `ses:GetAccount`, which setup doesn't need.

**The flag.**
- `domain_setup_enabled` in the compute module defaults to false, so dev is unchanged. Staging sets it from `var.outbound_mail_enabled`, the same as `ses_send_enabled`, so it is on there.
- `domain_setup_protected_zone_arns` refuses an empty list while the flag is on. Without a zone ARN the Deny wouldn't render at all, and nothing would say so.

**Inside the VPC.** These were one-off tasks on the migrate task definition (api role), using boto3 with `connect_timeout=5, read_timeout=10, total_max_attempts=1`. Nothing was created in AWS.

*First run* (task `1688951f…`, about 4 minutes after the endpoint was created):

```
route53.list_hosted_zones_by_name: NO PATH:ConnectTimeoutError
sesv2.get_email_identity: OK
getaddrinfo(mortgageboss.ai): NO PATH:gaierror
```

I stopped and reported, as the brief says, then checked without changing anything:

- **`getaddrinfo("mortgageboss.ai")` was the wrong test.** The bare `mortgageboss.ai` has no A or AAAA record at all, and it fails from outside AWS too. It says nothing about the VPC. The rerun asks for `staging.mortgageboss.ai`, which has an address.
- **The Route 53 endpoint was wired like the seven that work:** same security group, subnet and private DNS. The rerun also printed the hostname boto3 calls and what it resolves to.

*Second run* (task `5efba11a…`, with no change in between, run at the user's go-ahead):

```
route53.list_hosted_zones_by_name: OK
route53 host called: route53.amazonaws.com -> 10.30.42.87
sesv2.get_email_identity: OK
getaddrinfo(staging.mortgageboss.ai): OK   (32.194.49.46, 44.215.207.76)
```

So boto3 calls `route53.amazonaws.com`, and inside the VPC that name now resolves to a private address (the new endpoint). The first timeout was the endpoint's private DNS not having taken effect yet, a few minutes after creation. Public DNS works from the VPC, which the hourly check needs.

## Doc changes (for `docs/email-communication/loan-email.md`, not edited here)

- §15b LP-1004: done. The Route 53 endpoint is in staging, and the api role may set up domains while the worker may read them.
- Record the Deny: the app can never change records in our Terraform-managed zone(s) or the MAIL FROM and DKIM settings of `mail.staging.mortgageboss.ai`. When production gets its own zone and identity, they must be added to the Deny the same way (via `domain_setup_protected_*_arns`).
- No delete permission anywhere: removing a customer's domain is done by hand.
- Note for LP-1005 and later: give a new interface endpoint a few minutes before testing through it. The first call 4 minutes after creation timed out.
- Note for the hourly check: test public DNS against a name that has records. The bare `mortgageboss.ai` has no A record.
