# LP-964 — After Import, one step at a time: the reading, then the plan, then the list

- **Ticket:** LP-964 (the owner, 2026-10-06)
- **Source:** the owner, on LF-Y36E's conditions page after importing round 1: "it shows Plan for round 1
  and actual condition below it. this is confusing. Plus after import it shows all conditions and have
  loading button on top of it and then Plan for round 1 section loads. I think on import there should be
  loading icon but no condition should be display, then plan should load and user take action on plan
  then all condition with plan appear."

## What was wrong

`ConditionsListView` rendered everything as soon as a round was imported:

- **The same conditions appeared twice.** The plan showed them as proposals, and the list below showed
  them again, with the AI's proposals already in its Next step column ("Lender + LO emails", "In title
  email") as if they were decided.
- **The page jumped.** The list appeared at once, "Reading 6 conditions…" appeared above it, and the
  plan landed on top a moment later.

## The change

**`lib/conditions/plan-gate.ts`** decides the step from the newest imported round's reading and plan:

| Step | When | What the page shows |
|---|---|---|
| `loading` | either request still pending | a placeholder where the plan goes |
| `reading` | the reading is queued or running; or nothing is planned and it failed or never started | the reading card (with Read again) |
| `plan` | a plan is waiting to be confirmed | the plan |
| `list` | no imported round, plan confirmed, or nothing to plan | the normal page |

In the first three steps, the summary counts, filters, list and withdrawn section are held back, and
**nothing stands in for them**:

- **While the page loads or the AI reads,** only the loading state shows. The owner asked: "why we still
  display '6 conditions are on the file…' while loading plan?"
- **While the plan waits,** only the plan shows, with no line or link to the list. The owner: "showing
  condition again makes confusing… once plan confirm then show it." The list appears when she confirms the
  plan, or when she clicks **Hide** on it. Hide is remembered per round, so the next sheet's plan holds its
  list back again.
- **The one exception is a reading that FAILED.** There is no plan then, so nothing is duplicated, and Read
  again may fail too. One line keeps the conditions reachable:

  > 6 conditions are on the file. The list opens once they are read and you confirm the plan. · **Show
  > them now**

  On round 2 and later it names the rest ("…, 4 from earlier rounds."), because earlier rounds' conditions
  are work in progress.

**It fails open.** A plan or reading request that errors is neither pending nor carrying data, so the step
is `list`. A broken endpoint does not hide the conditions.

**When the list is shown before the plan is confirmed (after Hide), Next step reads "Plan not confirmed yet"** for the new round's conditions
instead of the AI's proposal. This applies to conditions *first seen* on the round. A condition seen again
keeps the plan it already had: `condition_plan.py` does not re-plan it (its carry-over rule), so marking it
unconfirmed would be false.

**Discarded rounds fold** (`round-strip.tsx`). Beside a live round they collapse to "1 discarded · show",
which opens them in place. A file whose only rounds are discarded still draws them as cards.

The plan panel, the reading card, the comparison panel, the figures check, the lender package and the
drafts line are unchanged and still render on their own conditions. `ReadingStatus`, `RoundPlanPanel` and
the gate call the same two queries, which React Query shares.

## Review (of `2e8095d4`)

**No defects. The gate is a pure function with one job, it fails open, and the premise its trickiest line
rests on is pinned by a test rather than by its comment. I went looking for three ways it could strand her
and found none.**

### What I verified, and how

- **It fails open, by construction rather than by intent.** A reading or plan request that errored is not
  pending and has no data, so every branch falls through to `list`. I checked this because the cost of
  getting it wrong is the whole page: a broken endpoint that hid the conditions would be worse than the
  jumping it replaced.
- **The list is collapsed, never removed.** `loading`, `reading` and `plan` all keep the "Show them now"
  line, so a stuck reading has an escape hatch, and the ticket names that as the reason.
- **A file with no imported round goes straight to `list`.** `if (!hasImportedRound) return "list"` is the
  first line, so the gate keys on whether a sheet was imported and not on round status. I checked this
  because LP-965 put a `MANUAL`-source round on files that have never imported a sheet, and a gate keyed
  on status could have parked such a file behind a placeholder for ever. It cannot.
- **"First seen on it, not last seen" is pinned, not just commented.** `unplannedIds` is
  `first_round_id === newestImported.id`, whose stated reason is that a condition seen again keeps the
  plan it already had (`condition_plan.py` carry-over). Swapping it to `last_seen_round_id` fails
  `marks only the new round's conditions as not confirmed: one seen again keeps its plan` — a test whose
  name is the property. That is the line I would have bet on being comment-only, and it is the one case
  where getting it wrong would mislabel conditions she has already planned.
- **A confirmed plan settles it, whatever the reading says** (`plan?.confirmed_at` is checked before the
  pending and running branches), so a slow or failed reading cannot pull a confirmed round back behind the
  plan step.
- **Runs.** `plan-gate.test.ts` and `conditions-plan-gate.test.tsx`: **20 passed**. Frontend untouched by
  this review, so the builder's **2253** stands; no backend file is in this commit, so no pytest was run
  for it. Their 12 mutations are credible — the one I chose independently, which is the one I would most
  expect to survive, was caught.
