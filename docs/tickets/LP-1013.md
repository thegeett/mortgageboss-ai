# LP-1013 — Automatic follow-ups (backend)

Step 5 (Follow-ups), first ticket. Code, tests and a dev check. Nothing deployed, nothing committed.
LP-1014 is the screen; LP-1015 tests every scenario in staging.

## What and why

A processor sends emails that need an answer: a document request to the borrower, a question to the
title company or the lender. Today nothing chases them. Now **each email she sends with Send can be
followed up automatically**: off by default; when on, the app replies in the same thread every N days
(default 3), up to M times (default 2), at a time of day she picks (default: the time she sends, in
her time zone), from her, with her in Cc. A document request lists only what
is still missing; any other email gets a short general follow-up. A reply from that person pauses it.

Per email, not per file: a file has requests out to several people, and each is chased on its own.

## The rules

| Rule | What happens |
|---|---|
| **Due** | All of: follow-up `on`; the email `sent` or `delivered`; fewer automatic reminders than M; the due moment reached; for a document request, at least one of its needs still requested (`pending`, `requested` or `rejected`). **Due moment** = the clock's date in `follow_up_tz`, plus N days; a Saturday or Sunday moved to the following Monday; at `follow_up_time` in `follow_up_tz` (wall clock, so it keeps its local time across a daylight-saving change). The job runs every 15 minutes, so a reminder goes within 15 minutes after its due moment. |
| **Pause** | An email routed to the file at ingest, from the email's recipient (lower-cased, trimmed), not an out-of-office, delivery notice, bulk mail or a rejected message → `paused`, `follow_up_paused_at` = now. One activity entry "Follow-up paused: <recipient> replied". The job also re-checks for such a reply just before it sends, and pauses instead. |
| **Resume** | Only from `paused` → `on`; the clock restarts from the recipient's **latest** reply on the file (or `follow_up_paused_at`, whichever is later); the time of day stays. The response's `next_reminder_at` says when the next one goes; she changes it with PATCH. |
| **Finish** | A document request whose needs are all no longer requested (received, verified or waived) → `finished`, nothing sent. A general email is never finished this way. |
| **Stop** | She clicks Stop; or the original is `failed` (a clean failure or a bounce); or the recipient is on the suppression list; or nothing records who sent the original → `stopped`, nothing sent. |
| **Waits** | The company cannot send (no `active` domain: none, or in `problem`; or sending switched off), the file is deleted, or the original has not gone out yet → the job does not pick it at all; it stays `on` and due, and goes on the first run after that changes. No mail set up on the server → the run sends nothing. |
| **Refused** | Rate limit, or the company blocked between the job's query and the send → nothing sent, counts and clock unchanged, logged with its code; the next run (15 minutes later) tries again. |
| **Send now** | Any time, whatever the status: the same reminder at once, from whoever clicks, without the automatic footer. The clock restarts now (so the next automatic one waits a full interval, at the same time of day); the automatic count is unchanged. |
| **Start** | On an email already sent from the app (`sent`/`delivered`): `on` with her settings, clock from now, the automatic count back to 0; time of day and time zone as given, or the moment she clicks in `America/New_York`. |

The clock (`follow_up_clock_at`) is the Send time, then each automatic reminder's run time, then the
latest reply on resume (never earlier than it already is), or the Send now time. `follow_up_time` / `follow_up_tz` are set when it is
first turned on (Send or Start) and change only with PATCH or a new Start.

## The reminder email

A reply in the same thread: subject `Re: <original subject>` (no second `Re:`), `In-Reply-To` and
`References` = the original's Message-ID in the form it arrives, `<{external_message_id}@email.amazonses.com>`
(LP-998). SMTP (dev) already returns a bracketed id; that is used as it is. From her name and company
at the file address, Cc her, Reply-To the file address: the worker reads these off the approver, as
for any Send. Automatic reminders carry `Auto-Submitted: auto-generated` and nothing else (no
`Precedence: bulk`, no `X-Auto-Response-Suppress`).

**Document request** (`reminder_follow_up` v4), from the dev check, step 2:

```
Subject: Re: Documents we need for your loan (LF-F38B)

Hello Jane,

Just following up. We've received your W-2, thank you. We are still waiting on the following:

- Bank statements — the two most recent months

You can reply with them attached, or send them to lf-f38b@mb-mail.localhost.

Email is not a fully secure channel. If you would rather not send documents this way, reply and ask — we will send you a secure upload link instead.

If you have already sent any of these, tell us and we will go looking rather than asking you for it again.

Priya Desai

This is an automatic reminder from Summit Mortgage Processing's loan file system. Replies go straight to Priya Desai.

[LF-F38B]
```

**Any other email** (`follow_up_general` v1), step 4:

```
Subject: Re: Closing date for Jane Borrower

Hello there,

Just following up on my email below. Could you let me know when you get a chance?

Email is not a fully secure channel.

Priya Desai

This is an automatic reminder from Summit Mortgage Processing's loan file system. Replies go straight to Priya Desai.

[LF-F38B]
```

The greeting is the original's: the borrower's first name on her own request, "there" for anyone
else (`greeting_name_for`). The file address is offered only where the original was the borrower's
request (LP-843 keeps it from third parties). The still-waiting list names each need by its borrower
label; the thanks uses the plain document name ("W-2", "bank statement"), because the label carries a
qualifier ("W-2s — the last two years") that reads oddly in a thank-you.

## Decisions made in this ticket

- **`reminder_follow_up` v4, not v3 as it was.** The brief and §3 describe the template as "received
  so far, still waiting"; v3 has no received line and opens "A short follow-up." v4 opens "Just
  following up." (§3 wording) and adds `$received_sentence` (empty when nothing arrived). v3 stays on
  disk and pinned (ADR-401).
- **`follow_up_general` carries "Email is not a fully secure channel."** Every template must
  (protocol decision; `test_every_template_carries_the_security_caution`). It sits alone, which reads
  a little abruptly after the question. Worth a look by the owner; changing it is a v2.
- **`Auto-Submitted` on automatic reminders only, not on Send now.** Send now is a person's Send, and
  the codebase's rule is that a human-approved send carries no auto-reply headers. An automatic
  reminder is told apart by `follow_up_of_id` set and `initiated_by_user_id` empty (Send now records
  the clicker there), so no extra column.
- **The one-open-draft index.** `uq_communications_open_draft` no longer exists (dropped in LP-832).
  The reminder is created as a draft and sent by `send_draft` **in the same savepoint**, so it is
  never committed as a draft and never appears in a drafts list; a refusal rolls the savepoint back,
  so no reminder row is left either. It uses its own `template_key` (`reminder_follow_up` /
  `follow_up_general`).
- **The reminder is not linked to the needs.** The original keeps the link; linking the reminder
  would make `send_draft` re-stamp `requested_at` (LP-814's clock) and a bounced reminder unwind the
  needs.
- **Refusal codes.** `CannotSendError` gains `code`: `suppressed`, `rate_limited`, the
  `company_send_blocker` codes (`no_address`, `domain_problem`, `sending_off`, `no_sender`), or
  `refused`. Messages unchanged.
- **Activity.** `send_draft` writes "Sent a document request for 0 item(s)" for a reminder; it is
  renamed, as `condition_drafts` does: "Automatic reminder sent (for <her>)" or "Sent a reminder"
  (actor: the clicker), with `follow_up_of_id` in the detail. The pause uses `communication_received`
  with `kind: follow_up_paused`. No new activity type, so no constraint swap.
- **`waiting_for`** uses the needs' own titles (what she sees on the needs list), or `["a reply"]`.
- **`next_reminder_at`** is the due moment itself; the job sends within 15 minutes after. None when
  not `on` or the count is reached.
- **Time of day per follow-up (amendment, 11-07)**, replacing the 09:00–17:00 Eastern window.
  `follow_up_time` (`time`) and `follow_up_tz` (IANA name, up to 64 characters), null while `off`;
  a CHECK (`follow_up_time_set`) requires both on any other status. **Added to the same migration**:
  `e3a9d4c7b512` is uncommitted and has been applied only to the dev DB (staging's last image,
  `staging-2f41b8ed`, was set at 08:58 on 11-07, before the migration file existed at 10:01); dev was
  downgraded and upgraded again, and the round trip repeated, clean.
- **Default time zone `America/New_York`** when the caller gives none. Nothing stores a user's time
  zone; §3 says "in her own time zone", which only the browser knows, so LP-1014 always sends `tz`.
  The default time is the moment of the Send or Start, to the minute, in that zone.
- **An unknown time zone is refused** (422 on Send, Start and PATCH; `ValueError` in `FollowUp`):
  only names `zoneinfo.available_timezones()` lists. Paths, offsets like `EST-5` and the empty string
  are refused.
- **The job orders by due moment, in SQL.** `due_moment_sql` is the same rule in Postgres
  (`timezone()`, `isodow`), used to pick and order the candidates, so the cap of 50 takes the
  earliest due, not the oldest clock (an old clock with a late time of day would otherwise take a
  slot ahead of one already due). `evaluate` still decides on each row, and a test checks the SQL
  and Python agree on seven cases (weekend, Los Angeles, the November change, London, Kolkata, a
  30-day interval, midnight). Weekends never meet a US or EU daylight-saving day as a due day: those
  changes are on Sundays, which move to Monday.
- **Resume from the latest reply (review finding 1).** A paused follow-up stays paused through later
  replies, and only the first set `follow_up_paused_at`; resuming from it left the later replies
  "since the clock", so the job's re-check paused it again at the first due run and nothing ever
  went. `resume_clock` takes the latest of the recipient's replies on the file.
- **Only what can be sent is picked (review finding 2).** A refused or skipped email was left as it
  was, so it stayed the earliest due and was picked again every run; 50 of them (one company with a
  domain problem, or switched off) filled every run and no other company's reminder went. The
  query now leaves out a company that cannot send (no `active` domain, or sending off), a deleted
  file, and an original not yet `sent`/`delivered`/`failed` (stuck `queued` reads "wait" every run);
  they stay due and go once that changes. No sender recorded for the original (permanent) now stops
  it, `stopped_no_sender`, rather than being skipped every run. No mail sender on the server: the
  run returns at once. The row lock is `FOR UPDATE OF communications` (the query joins the file).
- **Resume never moves the clock back.** Send now while paused restarts the clock; Resume after it
  took the reply's time, earlier, and an automatic reminder became due a day or two after the one
  she had just sent. `resume_clock` is the latest of the reply, `paused_at` and the clock.
- **The company send check once per send (review finding 8).** `_refuse_if_cannot_transmit` reads
  `company_send_blocker` (for the code) and then the draft half only (`_draft_blocker`), instead of
  `transmit_blocker`, which asked the company question again. The button and the refusal still use
  the same sentences.

On `/api/v1/loan-files/{file}/messages/{communication_id}` (404 for anything not an outbound email on
the caller's company's file; 409 when it is not an email sent from the app, or for start/send-now one
that has not gone out):

| Call | Body | Does |
|---|---|---|
| `POST …/follow-up/start` | `{interval_days?: 1–30 = 3, max_auto?: 0–10 = 2, time?: "HH:MM", tz?: IANA}` | `on`, clock now, count 0; time/tz default to now in `America/New_York` |
| `POST …/follow-up/stop` | — | `stopped` |
| `POST …/follow-up/resume` | — | `paused` → `on`, clock from the latest reply (409 if not paused); show `next_reminder_at` |
| `PATCH …/follow-up` | `{interval_days?, max_auto?, time?, tz?}` | settings only; the next reminder moves with them |
| `POST …/follow-up/send-now` | — | the reminder now, from the caller; 409 with the Send refusal sentence |

Each returns `FollowUpPublic`: `status`, `interval_days`, `max_auto`, `auto_sent`, `clock_at`,
`paused_at`, `next_reminder_at`, `time` (`"HH:MM"`), `tz`, `waiting_for`. An unknown `tz` is a 422.

The Send dialog posts `follow_up: {interval_days, max_auto, time, tz}` with `transmit: true` on
`POST /outbound/draft/{id}/send` (ignored without `transmit`). **A time picker** next to the interval
and count, defaulting to the current time; `tz` is the browser's
(`Intl.DateTimeFormat().resolvedOptions().timeZone`), always sent, because the server's default is
New York. Show `next_reminder_at` in her zone after Send, Start, Resume and a change ("Next reminder
Mon 9 Nov, 9:30 am"), so she can change it if it is not what she wants.

`GET …/messages/{id}` adds `follow_up` (that object, or null for inbound mail, reminders, and emails not
sent from the app), `follow_up_of_id` (on a reminder) and `automatic_reminder` (true for one nobody
clicked: label "Automatic reminder (for <her>)"; her name is in the activity entry and the From).

## Open

- **No list endpoint.** LP-1014's Follow-ups list (one line per email with follow-up on) needs a
  per-file list of originals with their `follow_up`; only the detail carries it today.
- **§3 says Send now "counts as a reminder"; this brief says it does not count toward M.** Built to
  the brief (and mutation-tested). §3 / §15d LP-1015 step 7 need to agree.
- **A reply moved from the company Inbox to the file** does not pause at once (the hook is on
  `apply_routing` only). The job's re-check pauses it at the next due run **only if the reply was
  received after the clock last started**; one that arrived in the Inbox before an automatic
  reminder went, and was moved afterwards, is not seen, and the next reminder goes (review finding
  6, left as is).
- **"Success" is "queued".** The count and clock move when `send_draft` queues the reminder; if the
  worker then fails it cleanly, that reminder is spent. A bounce then suppresses the address and the
  next run stops the follow-up.
- **"My email below" is not quoted.** Gmail shows the thread; a client that does not thread shows
  only the reminder. Quoting the original is its own decision (body size, HTML originals).
- **Run-out to-do** ("2 reminders sent, no reply") is LP-1014's; `auto_sent == max_auto` with status
  `on` is the signal.
- **Start resets the automatic count to 0** (a fresh start); not stated in the brief.
- **The general template's lone security sentence** (see Decisions).
- **No activity entry for Start / Stop / Resume / settings changes.**
- **Rate limit**: two due follow-ups to the same address in one run — the second is refused
  `rate_limited` and goes on the next run 15 minutes later (one email per address per 5 minutes,
  three per 24 hours, per company). A reminder refused for the 3-a-day limit is retried every run
  until the oldest of the three is 24 hours old.
- **Still picked every run, by design or rarely:** a `rate_limited` refusal (clears within 24
  hours); a generic `refused` (an original whose recipient is not one valid address, which the
  original's own Send would have refused) and an `error` (an exception on that row). Each holds one
  of the run's 50 places while it lasts.
- **Two follow-ups to one person on one file, due the same run**: the second is rate-limited and goes
  15 minutes after the first, so she gets two reminders a quarter of an hour apart.
- **Review findings left as they are** (the owner's call, 11-07): 3, a document request with all
  its needs deleted gets the general reminder; 4, a deactivated sender's follow-ups keep sending in
  her name; 5, Send now and the job can both send in the same second; 6, above; 7, the
  `amazonses.com` id form is us-east-1's; 9, a third copy of the address normaliser; 10,
  `_name_the_send` reads every send entry on the file and is copied from `condition_drafts`.
- **Postgres and Python must know the same zone names.** The API checks `tz` against Python's list;
  the job's SQL uses Postgres's. A name only Python knows would fail the job's query for everyone.
  Both follow the IANA database, so in practice this means keeping the two up to date.
