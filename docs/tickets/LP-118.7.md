# LP-118.7 — Store-everything: persist parsed-but-dropped MISMO fields + stop the parser silently losing data

**Type:** Story · **Epic:** Phase 3.5 / Epic B · **Depends:** LP-118.6, fact-namespace-foundation, ADR-239
**Status:** complete · **Date:** 2026-07-07

## What this ticket is

The store-everything principle (ADR-239): it is always correct to persist what we parse. The
fact-namespace foundation audit (§7) found the MISMO parser **consumes** each leaf it reads and
then **silently drops** anything the import doesn't persist — it doesn't even fall through to the
catch-all, so the data is genuinely lost. Two confirmed casualties block real rules: the borrower's
**current residential address** and the property **county**. This ticket, in two parts:

- **(A)** adds the two columns and wires their (already-parsed) MISMO values into persistence.
- **(B)** the general fix — a value the parser reads but does **not** persist now falls through to
  the catch-all instead of vanishing, so no parsed leaf is ever silently lost again.

**Scope held:** this is a MODEL + IMPORT change only. It does NOT build the rules that consume these
fields (address-consistency, flood), does NOT modify the fact namespace (LP-118.6 will surface the
new fields on its next build), and does NOT re-architect the parser.

- [x] **The already-parsed current address + county are wired into the new columns; values flow

  two columns + import wiring + a targeted `peek` for one read-but-not-persisted leaf.

## What was built

- **Models:** `Borrower.current_address_*` (5 structured columns mirroring `Property`) +
  `Property.county`. Additive, nullable.
- **Migration `e2d5b8c1f4a9`** — adds the six columns; reversible.
- **Import wiring** (`app/mismo/import_service.py`) — `_build_borrower` persists the current
  address; the property mapping persists `county`. Updated the module's "known gap" docstring
  (the gap is now closed).
- **Parser leaf-survival** (`app/mismo/parser.py`) — `_Ctx.peek` (non-consuming read) + routing
  `full_name` through it so it reaches the catch-all.
- **Tests** (`tests/mismo/test_store_everything.py`, 5) — current-address persists, county persists,
  the unmapped leaf survives to the catch-all, mapped subject leaves are not double-stored, and
  existing mapped fields are unchanged.

## Assumptions and decisions

- **Structured address columns (not a single normalized string).** The audit + ticket said to match
  the existing address-storage pattern; `Property` stores address STRUCTURED (`address_line` / `city`
  / `state` / `postal_code`). Mirroring that lets the fact-builder join the borrower current address
  the same way it joins the property address, and lets the address-consistency rule compare
  like-for-like. Added `current_address_type` too (the MISMO `AddressType` — Current/Mailing/Prior)
  so the address's *kind* isn't lost; the parser reads the first `ADDRESSES/ADDRESS` (whatever its
  type), which is pre-existing parser behavior left unchanged.
- **The general fix is narrow by necessity — and that's correct.** `_parse_catch_all` already
  captures every **non-consumed** leaf, so leaves the parser never reads already reach the catch-all
  (the existing `FIPSCountyCode` test proves it). The only silently-lost leaves are the ones the
  parser **reads (consumes) but import drops**. After Part A persists address + county, the sole
  residual read-but-not-persisted leaf is `FullName` (redundant with first+last). The general
  mechanism is `peek` (read-without-consume): any value the parser reads for validation/derivation
  but does not persist should use `peek` so it survives. `FullName` is the concrete case and the
  demonstrable test leaf.
- **`FullName` chosen as the demonstrable leaf.** It's a real MISMO element (`INDIVIDUAL/NAME/
  FullName`) currently consumed-and-dropped; routing it via `peek` proves the fall-through with a
  genuine leaf, without persisting a redundant column.
- **No double-storage discipline.** A value that IS persisted stays on `ctx.text` (consumed → out of
  the catch-all); only read-but-not-persisted values use `peek`. Verified: subject county/address are
  consumed (in columns, not in the catch-all); `FullName` is in the catch-all (no column).
- **No backfill.** Existing rows keep NULL — the values were never retained, so there is nothing to
  backfill; a re-import populates them. Raw-enum strings that DRIVE a derived column
  (`mortgage_type`→`loan_program`, `classification`→`is_primary`, `usage_type`→`occupancy_type`) are
  deliberately left consumed (not routed to the catch-all): they are *mapped* (their semantics are
  captured by the derived column), so surfacing the raw string would be noise, not recovery.

## Follow-ups

- **LP-118.6 next build** will surface `borrower.current_address` and `property.county` as
  **present** facts (they are currently marked `ABSENT_NOT_PERSISTED` in the fact namespace) — a
  small change in the fact-builder to read the new columns (LP-118.6 or its consumers).
- **`current_address_consistency` rule** (DL address vs stated residence) becomes buildable.
- **Flood / jurisdiction rules** keyed on county become buildable.
- **`fact-namespace-foundation.md` §7** records these as the parsed-but-dropped gaps; they are now
  closed (the audit stands as the point-in-time record that motivated this ticket).
