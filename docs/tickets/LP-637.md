# LP-637 — a document can never be re-classified

- **Ticket:** LP-637
- **Status:** In progress
- **Date:** 2026-09-01
- **Found on:** staging `LF-ZE9N`, while reading the first successful verification of that file
- **Scope:** Backend — `api/documents.py`, `tasks/document_processing.py`; Frontend — document list + row actions

## The report

LF-ZE9N's first completed verification produced **407 findings, 298 of them needing attention**. That
number is arithmetically correct and almost entirely one problem:

| source of `couldnt_check` | documents | findings |
|---|---|---|
| untyped, `needs_review`, no tier | 6 | **132** |
| `unknown`, `completed`, tier 3 | 4 | **88** |
| everything else (typed documents) | 20 | 36 |

**Ten documents — 23% of the file — that the classifier could not identify.** Each fails every one of
the 22 rules that needs a typed field from it, so one problem is reported 220 times. The genuine,
actionable signal underneath is roughly 41 items: 7 red, 34 `needs_review`, and a scatter of
`couldnt_check` on properly-typed documents.

The tell was visible before the cause was: sixteen unrelated rules each reporting **exactly ten**.

## Why the LP-636 fixes did not help

These are the same ten documents LP-636 was written about. Its defects 1-4 are the ten in
`needs_review`; defect 5 is the four that classified as `unknown` with high confidence. All eight
LP-636 commits are in the deployed image. They still did not help, and the reason is the whole point
of this ticket:

| | |
|---|---|
| the ten documents last processed | **2026-08-30 00:33–00:35** |
| the LP-636 fixes landed | **2026-08-30 19:48–20:42** |

**Classification happens once, at upload.** These documents were classified nineteen hours before the
code that would have classified them correctly existed, and nothing has re-read them since. Re-running
verification re-evaluates rules against stored document data; it never re-reads a document. So a
classifier fix helps every document uploaded after it and no document uploaded before it.

## What exists today, and why none of it is this

* **`process_document`** — the full classify-then-extract pipeline. Runs **only on initial upload**.
* **`reprocess_document`** — enqueued by the PATCH type-override endpoint. Its own docstring says it
  **"skips classification"**, deliberately: a human has supplied the type and it sets
  `classification_confidence = 1.0`, so re-classifying would overwrite their decision.
* **Replace** — needs the file uploaded again.

So the only route to a corrected classification is a processor typing the type by hand. That is
exactly the work the classifier fix removes, and it cannot help the four `unknown` documents at all,
because nobody knows what they are — that is why they are `unknown`.

## What this builds

**1. Per-document reprocess.** `POST /documents/{document_id}/reprocess` — re-runs the FULL pipeline,
classification included, on the stored file.

**2. Bulk reprocess.** A loan-file-level endpoint that reprocesses the documents that would benefit,
because this file needs ten and clicking ten times is the wrong shape. Every classifier improvement
from here will leave a cohort of already-processed documents behind it; this is the tool for that
cohort, not a one-off for LF-ZE9N.

**3. The UI for both** — a per-row action, and a file-level action.

## Decisions this has to make

**A human override must survive.** `classification_confidence = 1.0` means a person chose that type.
Re-classification must refuse to touch those by default — silently replacing a processor's decision
with a model's guess is a worse bug than the one being fixed. An explicit force is a separate
question; the default is refuse.

**Verification goes stale.** The override endpoint already calls `mark_verification_stale`, and for
the same reason: a re-classified document sitting under findings computed from its old type is a
false-green. This must do the same.

**It must be audited.** The override path writes an activity log entry. A reprocess changes what the
file says about itself and needs the same trail.

**Bulk needs a bounded default.** "Reprocess everything" on a 44-document file is 44 model calls and
a re-extraction each. The default should be the documents that plausibly benefit — untyped,
`unknown`, or `needs_review` — with reprocessing a healthy `completed` document available but not the
default.

## Review of feature 1

### The one that would have broken staging on the first click

**`DOCUMENT_REPROCESSED` shipped with no Alembic migration.** `activity_type` is a VARCHAR + CHECK
(ADR-037), not a native enum, so adding a member changes what the code writes and nothing about what
the database accepts. `log_activity` is the first write the endpoint makes: the CHECK would have
rejected the value, `IntegrityError` on commit, and the activity, the stale marker and the enqueue
would have failed together — a 500 on the first click on staging. Every previous activity-type
addition shipped a constraint swap (LP-71, LP-98, LP-70, LP-76/77/87); this one did not.

**The suite was fully green throughout, and structurally could not have been anything else.**
`tests/conftest.py` builds the schema with `Base.metadata.create_all`, which regenerates the CHECK
from the *current* enum — so the test database always agrees with the code, whatever the migrations
say. A check that would pass if the migration never existed is not evidence about the migration.

Fixed by the migration plus `tests/test_activity_type_migrations.py`, which reads the migration files
as text and fails by name when an `ActivityType` value is not in any constraint swap. Deliberately
not a database test: the failure is a disagreement between two source artifacts, and a migrated
database is exactly what a developer adding an enum value does not have in front of them.

### The in-flight guard, and the claim it could not support

Nothing stopped a reprocess landing on a document already being processed. Two overlapping
`_process_document` runs both write a current extraction, and `UNIQUE (document_id) WHERE is_current`
admits one: the loser absorbs the IntegrityError into FAILED, so the document reads FAILED while
carrying the winner's good extraction. Before this endpoint, `process_document` was enqueued exactly
once — at upload — so the race was not reachable.

**`CLASSIFIED` had to be in the guard**, and a first draft left it out. `_process_document` commits
CLASSIFIED and only then runs the Tier 3 free-extraction call; `EXTRACTING` is set inside
`_extract_branch`, i.e. Tier 1 only. So for an `unknown` or low-confidence document — this feature's
entire cohort — the longest in-flight window is spent at CLASSIFIED, and a guard listing CLASSIFYING
and EXTRACTING alone would have waved a second reprocess straight into it.

**It does not stop a double-click, and three places briefly claimed it did.** No status guard can:
the status only moves when a worker starts, so two clicks seconds apart both read the row as it was
before either was picked up. Closing that needs task-level deduplication or a lock; the feature-3
action should also disable on submit. `test_two_clicks_before_a_worker_starts_both_enqueue` pins the
gap so it stays visible rather than assumed closed.

**PENDING is deliberately not treated as in-flight.** Both enqueue helpers are fire-and-forget and
never raise, so a broker failure strands a document at PENDING with no task behind it — a state
upload has been able to produce since LP-42. Reprocess is the only route out. Guarding PENDING would
have made a stranded document permanently unreachable.

### A superseded version could be reprocessed

`get_document_for_company` filters soft-deleted rows but not `is_current`, so a replaced document was
reachable. It cannot affect an answer — `documents_section` selects `Document.is_current.is_(True)` —
yet reprocessing one re-classified a record kept for audit, spent a full classify+extract on work
that provably changes nothing, and marked the whole file's verification stale. The replace endpoint,
forty lines below, already refuses exactly this. Now a 409, and `force` does not reach it: `force`
overrides a HUMAN's type decision, which a processor is entitled to reverse, and sharing one flag
between two unrelated refusals would widen the escape hatch beyond what it was opened for.

### Findings are not versioned, and a re-run duplicated them

`create_document_finding` adds unconditionally; nothing removed the previous run's rows. Reprocess a
Tier 3 document twice and its `key_finding` rows double. Worse, reprocess an `unknown` that
re-classifies to a Tier 1 type — the success case, the whole point of the feature — and its Tier 3
findings stay OPEN on a document that is no longer Tier 3, still surfaced through
`/document-findings` and still reachable as `NeedsItem.source_finding`: noise added to the queue this
ticket exists to shrink.

`supersede_open_findings` runs **before classification**, not inside the Tier 3 branch, precisely
because of that second shape — a re-classification away from Tier 3 never enters that branch. Only
`OPEN` findings; `REVIEWED` and `DISMISSED` mean a person decided, and a reprocess is not entitled to
erase that. Nothing writes those two today (the lifecycle is Phase 3 and the API only lists), so it
changes nothing now and is already right when it lands. The tradeoff worth naming: a pipeline that
fails after this point leaves neither old findings nor new ones — they described an extraction being
replaced anyway, the document ends FAILED or NEEDS_REVIEW rather than looking trustworthy, and a
re-run regenerates them.

### Smaller ones

**A body-less POST was a 422.** FastAPI makes a Pydantic body parameter required even when every
field on it has a default. The natural call — the feature-3 button, posting nothing — failed
validation, and every test passing `json={}` would never have noticed. Defaulted now.

**`processing_error` was not cleared.** `_process_document` only ever writes that column; no path
through it clears one. A document that failed, reprocessed and then succeeded reached COMPLETED still
carrying the error string from the run that no longer exists — the common case here, since the
documents this was built for are the ones sitting in NEEDS_REVIEW with an error on them. The override
endpoint clears it for the same reason. (`readonly.documents` selects it, so the stale text is what
someone querying staging reads. A comment in `document_processing.py` also calls it UI-shown; no
response schema exposes it today, so that half looks stale.)

**The 409 asserted something the code cannot know.** `classification_confidence` has two writers —
the override endpoint (1.0) and the pipeline, whose value `coerce_confidence` clamps into `[0, 1]`,
so 1.0 is reachable from the model. "This document's type was set by a person" is therefore untrue
for a model-produced 1.0, and the LP-463 mismatch path stores `document_type = "unknown"` with the
model's own confidence, so the refusal can land on precisely the confidently-mislabelled unknown the
ticket was written about. Reworded to "looks as though". Staging currently tops out at 0.98, so this
is latent rather than live.

**The proxy deserves the explicit column after all.** A forced reprocess overwrites the 1.0 with the
model's number, so the human-set marker is destroyed and a later reprocess will no longer refuse. The
signal is doing two jobs — "how sure was the classifier" and "did a person decide" — and only one of
them survives a re-run. A boolean `type_set_by_human` would make both refusals exact and is worth
taking before feature 3 puts a button on this.

### Endorsed as built

The **stale-marker-before-enqueue** ordering is right: a false "stale" costs one re-verification,
while a false "current" is a false green on findings computed from an old type. Erring toward the
recoverable side is correct. Note the asymmetry with the override endpoint, which makes a durable
type change — its marker is true whether or not the enqueue lands, and this one's is not.

Tenant scoping is a 404 and stays one: every new refusal is evaluated after the not-found check, so
another company's document is still indistinguishable from a missing one.

### For feature 2

Bulk selects documents by status. Both new refusals must apply there as **filters, not errors** — a
bulk call should skip a superseded version and a document mid-pipeline, not fail the batch on one.
And bulk multiplies the double-click gap by the batch size, which is the strongest argument for
taking task-level deduplication before feature 2 rather than after.

## Feature 2: bulk reprocess

`POST /loan-files/{id}/documents/reprocess`. **The per-document endpoint's refusals become filters**,
which is the design rather than a shortcut: a single reprocess is a processor pointing at one
document, so "no, and here is why" is the right answer; a bulk reprocess is a processor pointing at a
file, and failing all ten because one is mid-pipeline would make the button useless exactly when a
file is busy. Each document is judged on its own, **the skips are reported per reason**, one activity
entry covers the batch, and the stale marker is set once for the file.

The default set is bounded (`_would_benefit`): no type, the literal `unknown`, or a status that
already says it went badly. Not "anything not COMPLETED" — LF-ZE9N's four `unknown` documents are
COMPLETED with no flag (LP-636 defect 5), so that rule would have missed half the motivating cohort.

### Review: the second press re-queued the first press's work

`_would_benefit`'s docstring claimed it prevented this. It could not, and the reason is worth keeping:
**nothing in it looks at status except to include NEEDS_REVIEW and FAILED.** An untyped or `unknown`
document is still untyped while it sits at PENDING, so it stayed eligible — and that is precisely the
cohort the feature exists for. Two presses a minute apart (the worker is serial, the soft limit is
600s, so "nothing has changed yet" is the normal experience) sent every document twice. Confirmed by
running it, not by reading it: two calls, two enqueues, same document.

The consequence is written down in the same file — two overlapping `_process_document` runs both
write a current extraction, `UNIQUE (document_id) WHERE is_current` admits one, and the loser absorbs
the IntegrityError into FAILED while the winner's extraction is the current one. Since the feature-1
review, `supersede_open_findings` runs twice too, so the second run can supersede the first's fresh
findings.

Fixed with an explicit `already_queued` skip for PENDING, overridden by `all_documents` — which is
what keeps a genuinely stranded PENDING document reachable in bulk, and is the same flag with the
same meaning rather than a second one. The per-document endpoint still takes PENDING
unconditionally, and that asymmetry is deliberate: there a processor is naming one document, so
"queue this again" is exactly what they asked for.

**What this does not close:** two requests genuinely in flight at once, both reading before either
commits. That needs row locking or task-level deduplication.

### Review: a lost enqueue threw away the reason a document failed

Both endpoints write `status = PENDING` and clear `processing_error` **before** a fire-and-forget
enqueue. With the broker down, a FAILED document became a PENDING one with a type and no error. That
reads as healthy, shows nothing wrong in the UI, and — being typed and unflagged — falls outside
`_would_benefit`, so the *default* bulk path would then skip it as `already_classified` for good. At
batch scale that is a whole file's diagnostics, gone silently, and the comment above the enqueue loop
asserted the opposite ("recoverable by reprocessing again").

`_enqueue_full_reprocess` now reports whether the task landed, and both endpoints put the document
back the way they found it when it did not. Bulk reports it as an `enqueue_failed` skip rather than
counting it as queued. Applied to **both** paths deliberately — fixing only the one the review
happened to look at would have left the identical defect one function away.

### Review: the smaller ones

The **`superseded_version` filter had no test**, though the batch was reported as mutation-checked.
`list_documents` applies only `only_active` (`deleted_at IS NULL`), not `is_current`, so superseded
rows really are in the loop and the branch is load-bearing: delete it and the suite stayed green
while superseded versions got re-classified and the file was marked stale.

A one-document batch logged **"1 documents sent for reprocessing"** into the feed a processor reads.
The upload handler ninety lines above pluralizes.

**Nothing capped the batch.** `all_documents` on a large file enqueues one 600s-limit task per
document onto a serial worker, from a single request — one press could hold the document worker for
hours and put every other file's uploads behind it. `_MAX_BULK_REPROCESS = 100` is a foot-gun guard,
not a capacity limit: comfortably above the largest real file (44) and well below a pathological
press.

### Endorsed as built

`FAILED` belongs in the default set. A non-recoverable failure will fail again, but with the
`already_queued` skip a repeated press cannot retry it faster than the pipeline runs, and excluding
it would strand every *transient* failure — the more common case, and the one bulk is for.

`list_documents` eager-loading extractions and the `is_current` filter running in Python are both
fine at this scale; the cap now bounds it explicitly. `queued_document_ids` leaks nothing — they are
the caller's own documents, gated by `ScopedLoanFile`.

### Recommended before feature 3

**Task-level deduplication, ahead of the `type_set_by_human` column.** Both are worth taking, but
dedup is live and demonstrable — two presses, two enqueues, reproduced above — while the confidence
proxy is latent: staging tops out at 0.98, so no model-produced 1.0 exists yet. Feature 3 puts a
button on the live one.

## Feature 2a — the duplicate-run race, closed at the only place it can be

The API refuses a reprocess for a document already in flight, and that guard cannot close a
double-click: **a status only moves when a worker starts**, so two clicks seconds apart both read the
row as it was before either was picked up, and both enqueue. Bulk multiplies it by the batch size.

The consequence is written down in the endpoint's own comment. Two overlapping `_process_document`
runs both write a current extraction, `UNIQUE (document_id) WHERE is_current` admits one, and the
loser absorbs the `IntegrityError` into FAILED — so the document reads FAILED while carrying the
winner's perfectly good extraction. Since findings superseding moved ahead of classification, the
second run can also supersede the first run's fresh findings.

**Closed with an atomic claim** in `_process_document`: one conditional UPDATE into `CLASSIFYING`,
permitted only from a status that is not already in flight. Whoever the database lets through owns
the run; every other task returns having touched nothing.

*At the pipeline, not the enqueue*, because this is the only place that can be authoritative — by the
time two tasks could be compared they are both already in the queue. And *a database claim rather
than the Redis lock* used for needs: that lock takes a timeout, and this pipeline is bounded by
`DOCUMENT_SOFT_LIMIT_SECONDS`, so any timeout short enough to release a crashed worker is short
enough to expire under a slow document and admit the second worker — the exact failure it would be
added to prevent.

The claim runs **before** the storage read and before superseding, so a losing worker cannot destroy
the winner's findings on its way out.

`_PIPELINE_IN_FLIGHT` moved to `app/models/document.py`. The API's refusal and the pipeline's claim
must mean the same thing by construction, and a task importing from `api/` would be the wrong
direction; both already import the model. That set has been wrong once — `CLASSIFIED` was left out,
the status a Tier 3 document holds for its entire free-extraction call — so it is now covered by a
property test over the whole set rather than by examples.

## Feature 2a: the atomic claim, and what it cost

One conditional UPDATE into `CLASSIFYING`, permitted only from a status that is not already in
flight. The database picks the winner; a duplicate task finds nothing to do. Taken at the pipeline
rather than the enqueue because that is the only place that can be authoritative — by the time two
tasks could be compared they are both already queued, whatever a dedup key is computed from.

### A claim with no release stranded documents permanently

The claim set `CLASSIFYING` with no expiry, so a worker killed mid-run left the document in flight
forever: refused by the reprocess endpoint, skipped by bulk, unclaimable by any later task. **No
route back through the product at all** — and worse than before the claim existed, where a
hard-killed worker simply left the document as it was.

That is not hypothetical, it is scheduled. LP-630 stops staging's services every night at 22:00
Eastern, killing whatever is mid-pipeline. An OOM or a deploy does the same.

Fixed with `PIPELINE_PRESUMED_ABANDONED_AFTER_SECONDS`: an in-flight status stops counting once the
row has gone longer without a write than a live worker possibly could. **The window is derived, not
guessed** — past `DOCUMENT_HARD_LIMIT_SECONDS` there is no worker, because that is the SIGKILL
ceiling. A test asserts the relationship rather than a comment describing it.

The API half is what makes it matter: reclaiming inside the pipeline is useless on its own, because
a stuck document is only re-enqueued when a processor asks, and on status alone the endpoint refused.
`is_pipeline_in_flight` is now the single definition the endpoint's 409, the bulk skip and the claim
all consult.

**This also answers the Redis-lock argument, which was overstated.** The objection was that any
timeout short enough to release a crashed worker is short enough to expire under a slow document —
but a window derived from the SIGKILL ceiling cannot expire under a live run, because past that
ceiling there is none. The claim now has exactly the timeout the lock was rejected for. The real
difference is that the expiry lives on the row the work is about, so one fact serves all three
readers and a claim cannot be lost to a cache eviction.

### The retry escape hatch reopened the race it closed

A draft of the fix let a retry reclaim unconditionally, reasoning that a retry of the task holding
the claim would otherwise find its own status set and give up. **A retry can only ever be scheduled
by a failure before the claim is taken.** Everything after it is inside the pipeline's `try`, which
absorbs every exception into a terminal status, and the one it re-raises is in `terminal_on` and
never retried. So a retrying task has never owned anything.

What the hatch actually did: task A fails in `task_session()` before claiming and is retried; task B
claims the document and starts a 500s extraction; A's retry takes it unconditionally, and both run —
the partial unique index admits one current extraction and the loser lands in FAILED holding the
winner's work. The ticket's own bug, through the fix for it. The test written alongside it asserted
the stealing behaviour and passed.

Removed. The rare double-fault it was meant to cover is now recoverable through the abandoned
window instead of permanently stuck, which is the honest trade.

### A claim only exclusive against itself is not exclusive

`reprocess_document` — the extraction-only task the LP-44 type override enqueues — never took the
claim. Run alongside a claimed `_process_document` it produced the same collision, and its terminal
status write **released the other run's claim mid-flight**, letting a third task in behind it. It now
claims into `EXTRACTING`, which is what that path actually does, and the override endpoint refuses a
document mid-pipeline rather than enqueuing work the claim would silently drop.

### Smaller

An abandoned document *with* a type fell past the in-flight skip into `_would_benefit`, which saw a
typed, unflagged document and reported `already_classified` — so the default bulk press still could
not recover it, and described a stranded document as one the classifier was content with.

The safety margin was 60 seconds. `updated_at` is stamped app-side by the **worker** and compared
against the **API host's** clock, with no database clock on either side, so that margin is the
tolerance for cross-host skew as much as for commit latency; the test asserted only `>`, which passes
at one second. Now 900s against a 660s ceiling, with the margin itself asserted.

### Known limitation, not fixed here

**`updated_at` is a row mtime, not a pipeline heartbeat.** Any write to the document row resets the
abandonment clock — a version supersede, a staleness resolution — so a stranded document can have its
clock refreshed by something unrelated and be reported "already being processed" for another fifteen
minutes. Bounded and self-correcting rather than permanent, and the type-override path (the likeliest
such write) now refuses outright. A dedicated `pipeline_heartbeat_at` written only by the pipeline
would remove the property entirely and is the right fix if this is ever seen in practice.

## Feature 3 — the UI for both

**Per document**, in the drawer beside "Correct type", because they answer different questions:
correcting the type is for when a processor KNOWS what a document is; re-reading is for when nobody
does, or when the classifier has since improved. It is not a row action — the list row is itself a
`<button>` that opens the drawer, so nesting one would be invalid markup.

**Per file**, above the list, as "Re-read unidentified documents".

**The client does not decide what qualifies.** Re-implementing `_would_benefit` in TypeScript to
show a count in advance would put two definitions of "worth re-reading" in the codebase, and the one
on screen would be the one that drifts. The server decides; the result reports what actually
happened.

**The skips are shown.** A bulk press reports "Re-reading 7 documents… Skipped: 2 already
processing, 1 type set by a person" rather than a bare success, and a press that queued nothing says
so instead of claiming success. A processor watching for ten documents to change when seven were
sent cannot otherwise tell that from a slow queue.

**Both buttons disable while pending, and that is load-bearing rather than polish.** The server's
in-flight refusal cannot stop a double-click, because a document's status only moves once a worker
picks the task up — the reason the atomic claim exists at all. At batch scale a second press would
double-enqueue the whole file.

## Impact

Ten documents on one staging file are generating 220 of its 256 `couldnt_check` findings, and there
is no way to fix them short of a processor guessing ten document types by hand. More generally: every
improvement to the classifier is invisible to every document already in the system, and nothing in
the product says so.
