# LP-378 — The dormant tag-layer smoke test: do the income/asset producers produce?

## WHAT THIS TICKET IS

The orchestrator materializes only the AI groups a LIVE rule consumes (`_required_ai_groups()`), and **no
income or asset judgment rule is live** — so the 6 income/asset structuring groups have **never been requested,
never run, never produced a tag on a real file.** The ~15 dormant income/asset rules are believed "gated on
calibration," but calibration measures a tag's **accuracy** — it presupposes the tag **materializes.** This
ticket forces the dormant groups to run **once** on the real DB LF-6T3N and reports what they actually produce,
**before Priya's LP-379 calibration time is spent.**

**It is a read-only diagnostic**, not an activation or a fix. **It does NOT prove the tags are correct** — a
tag that produces a *value* is not a tag that produces the *right* value. **This proves the pipe carries
water, not that the water is clean** (LP-379 measures that). A uniform-`unknown` result is a **real finding**
(a producer/applicability gap), not a pass.

## ACCEPTANCE CRITERIA

- The dormant groups run once on LF-6T3N with the **real** model, **off the normal path**, persisting nothing.
- A per-group report: produces / abstains / errors, the doc-type distribution, real reasoning strings, cost.
- The probe is OFF by default — a normal run's `_required_ai_groups()` is byte-identical; it cannot leak.
- No rule/tag/spec/engine/model-config change; `ACTIVE_RULE_IDS` unchanged; full suite green.

## HOW THE PROBE RUNS OFF-PATH WITHOUT SIDE EFFECTS

`app/verification/eval/dormant_probe.py` — a diagnostic module **never imported by `verification_run`** (a
test asserts this), so it cannot leak into a normal run. It reuses the existing `materialize_tags(...,
only_subjects={"document"}, only_groups=<dormant>)` — which runs *only* the named groups, resolves each to the
**real** `reason_ai_group` when no stub is injected, returns a **new** snapshot, and **writes nothing**. The
probe reads the produced tags off that (discarded) snapshot and returns a report. **The only DB call is
`build_snapshot` (a read)** — a test asserts there is no write call site (`db.add(` / `.commit(` /
`persist_snapshot(` / `reconcile_`). `dormant_ai_groups()` is derived from the same `_required_ai_groups()` the
orchestrator uses, so the dormant set can never disagree with the live set.

## THE PER-GROUP REPORT (LF-6T3N — real sonnet-4-5, reported not predicted)

**All 6 dormant groups RAN; none errored.** The probe took **205s** and cost **~$0.10–0.15** (comparable to
the live 6-group materialization pass, LP-377-C). Each group runs on ALL 30 documents (per-document subject),
so most observations are honest abstentions on out-of-scope doc-types — the signal is *where it produced a
real value*. **The pipe carries water: 5 of 6 groups produce usable tags on the doc-types they apply to.**

| group | ran/error | real / total | produced a REAL value on | verdict |
|---|---|---|---|---|
| `income_amounts` | ran, ok | 44 / 90 | **W-2, pay_stub** (+ over-produces on mortgage_statement/property_tax_bill/bank_statement) | ✅ produces — **but over-produces** |
| `income_employer` | ran, ok | 8 / 30 | **W-2, pay_stub**; abstains cleanly elsewhere | ✅ clean |
| `income_docs` | ran, ok | 78 / 90 | every doc-type (yes/no presence signals; mostly "no" — correct for this file) | ✅ produces |
| `stmt_facts` | ran, ok | 8 / 60 | **bank_statement**; abstains cleanly elsewhere | ✅ clean |
| `asset_facts` | ran, ok | 6 / 60 | **investment_account**; abstains cleanly elsewhere | ✅ clean |
| `income_stability` | ran, ok | **0 / 120** | **nothing — 100% abstention** | ❌ producer/context gap |

**The model's own words (LP-334 — the evidence):**
- `income_amounts` ✅ — W-2 → `income.type='base'`, `documented_monthly='18697.06'` (*"Box 1 wages of $224,364.77 ÷ 12 = $18,697.06 monthly"*). Real, structured monthly income from W-2s and paystubs.
- `income_employer` ✅ — W-2 → `'Wells Fargo Bank, N.A.'` (*"normalized spacing in 'N.A.' … preserving the complete name"*); abstains on a driver's licence (*"does not contain employer information"*).
- `stmt_facts` ✅ — bank statement → `owner_matches_borrower='yes'` (*"'AKASH V PATEL BANSARI N PATEL' matches borrowers …"*), `is_reserve_eligible='yes'`.
- `asset_facts` ✅ — investment account → `liquidation_terms='fully_liquid'`, `usable_value='211688.19'` (*"total_value of $211,688.19 … no restrictions"*).
- `income_stability` ❌ — W-2 → `has_2yr_history=unknown` (*"W-2 shows only tax year 2025; a single year does not evidence 2-year history"*). It abstains on **every document** because it is asked **per-document** a **cross-document** question (2-year history / decline / continuance need multiple years of docs seen together). The per-document framing cannot answer it — a real architecture gap, not a calibration one.

## THE ACTIVATION-PLAN IMPACT (the finding that reorders Epic 1)

**Priya's LP-379 calibration is well-aimed for 5 of the 6 groups** — `income_amounts`, `income_employer`,
`income_docs`, `stmt_facts`, `asset_facts` all materialize real values on the doc-types they apply to, so
measuring their *accuracy* is the right next step. The dormant rules reading them (DT-1, IN-1, IN-3, IN-5,
IN-6, IN-11, IN-12, IN-13, AS-4, AS-6, and the asset rules) are **genuinely calibration-ready**: their tags
exist on real data.

**But `income_stability` is blocked on MORE than calibration.** It produces **nothing** — 0 real values on 120
observations — because a per-document structuring pass cannot evidence a cross-document property. The 5 rules
that read it (**IN-7, IN-10, IN-11, IN-13, IN-14**) are **NOT calibration-ready** — calibrating a tag that is
uniformly `unknown` measures nothing. **They need a producer re-architecture (a per-borrower, multi-document
income-stability context) BEFORE Priya's time.** Calibrating them now (LP-379) would be aimed at the wrong
blocker — the LP-368 warning made concrete.

**And `income_amounts` over-produces:** it emitted a `documented_monthly` on mortgage statements, property-tax
bills, and bank statements — documents that are not income. Materializing ≠ correct: those values are almost
certainly wrong, and calibration (LP-379) must catch them, or LP-377-D must gate the group to income
doc-types. This is the clearest live demonstration of *the pipe carries water, but the water is not
guaranteed clean.*

## HONESTY / WHAT THIS DOES NOT CLAIM

- **Materializing ≠ correct.** This proves the producers RUN and emit values on real data; whether those
  values are RIGHT is calibration (LP-379), unmeasured here.
- **A uniform-`unknown` group is a finding, not a pass** — reported as its own verdict, not hidden.
- **This ran the real model on real borrower data** — a real cost, reported above. It persisted nothing.

## PRODUCER GAPS FOUND (each its own fix ticket — reported, not fixed)

1. **`income_stability` produces nothing per-document** — a per-document pass cannot answer a cross-document
   question (2-year history / decline / same-line-of-work / 3-year continuance need the borrower's income
   docs across years, seen together). Its 5 rules (IN-7, IN-10, IN-11, IN-13, IN-14) are blocked on a
   producer re-architecture (a per-borrower, multi-doc income context), **not** on calibration. **Its own
   ticket, and it must precede LP-379 for these rules.**
2. **`income_amounts` over-produces on non-income docs** — a `documented_monthly` on a mortgage statement /
   property-tax bill / bank statement is not income. A doc-type gate (LP-377-D) and/or a calibration finding
   (LP-379). **Its own ticket / LP-377-D input.**
3. **`brokerage_statement` extraction gap** — "Wells Statement Savings May.pdf" is typed `brokerage_statement`
   but extracted 0 fields (the LP-377-A extraction-failure class), so `asset_facts` correctly abstains on it.
   The gap is upstream (extraction), not `asset_facts`. Already flagged in LP-377-A; noted here as the cause
   of asset_facts missing the brokerage statement.
