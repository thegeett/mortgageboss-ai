# LP-994 — Sending runs in the worker

Step 2 of the email work (`loan-email.md` §15a). Code, one migration, tests and a dev check against
MailHog. No AWS or Terraform changes. Backend only, apart from one timeline label; the Send button is
LP-997.

## What and why

Rule 8: only the worker sends mail. The API never calls the mail provider.

When a processor clicks **Send** (`transmit=true`), the API runs every guard, records the email as
`queued`, commits, and hands its id to the worker. The worker builds the email (LP-993), saves an
exact copy, sends it, and marks it `sent`.

**"I've sent it" is a different action** (§3): the processor sent the email from her own mail app,
and the app only records that. It never sends. `send_draft` takes an explicit `transmit` flag that
defaults to false, so "I've sent it", condition drafts and every other existing caller behave exactly
as before.

## The flow

| Step | Who | Status | What is saved |
|---|---|---|---|
| Send clicked | API | `queued` | final body and subject, recipient, `send_requested_at`, evidence record (with the approver), needs → requested, activity "Sent a document request…". `sent_at` stays empty |
| Commit, then enqueue | API | `queued` | nothing more; if the broker is down the request still succeeds |
| Claim | worker | `sending` | committed before anything else |
| Build and copy | worker | `sending` | `outbound/<id>.eml` in the mail storage, `raw_storage_path`; committed before the provider is called |
| Send | worker | `sent` | SES `MessageId` in `external_message_id`, `sent_at`; committed |

The email: From `"<approver name>, <company name>" <lf-…@<domain>>`, To the recipient, Cc the
approver, Reply-To the file address, `In-Reply-To` and `References` when the row replies to a
message. The approver is read from the evidence record `send_draft` already writes
(`communication_evidence.approver_user_id`); no new column.

## The safety rules

- **Atomic claim.** `UPDATE communications SET status='sending' WHERE id=… AND status='queued' AND
  send_requested_at IS NOT NULL AND deleted_at IS NULL RETURNING id`, committed. No row → the task
  logs `send_skipped` and stops. So a duplicate task (the re-enqueue job, a second enqueue, a broker
  redelivery) sends nothing.
- **`send_requested_at`.** Only a person's Send sets it. LP-815's automatic replies are `queued`
  without it, so the worker can never claim one and the re-enqueue job never picks one up
  (§3 "Automatic replies to inbound": not sent in step 2).
- **Re-enqueue job.** `communications.requeue_stale`, on the beat every 5 minutes (dropped if late,
  like the heartbeat): `queued` rows with `send_requested_at` older than 5 minutes, oldest first, at
  most 50 per run. It covers a Send whose enqueue failed or whose worker was down.
- **Clean failure vs not confirmed.**
  - *Clean failure* — nothing reached the provider, or the provider refused it: no domain any more,
    no sender, no approver, `build_mime` refused the data, the copy could not be saved, or
    `SendError(outcome_unknown=False)`. Status `failed`, `error_detail` "Not sent: <reason>.", the
    needs go back to pending with `requested_at` cleared (`bounce_handling._unwind_requests`), and an
    activity entry "Not sent".
  - *Not confirmed* — the email may have gone: `SendError(outcome_unknown=True)`, or any other
    exception during the provider call (a soft time limit, a bug). The row stays `sending`,
    `error_detail` "Not confirmed: <code>. Check before sending again.", nothing is unwound.
  - A crash after the provider answered but before the last commit leaves the row `sending` with no
    MessageId. That is the not-confirmed case by design: the claim is committed, so no later task can
    send it again.
- **No automatic retry.** The task has no retry policy; the SES client makes one attempt (LP-993).
  After a clean failure the processor sends again; after "not confirmed" a person checks first.
- **Logs carry ids and error codes only.** Never the recipient, subject, body or the provider's text.
  `SendError` is caught explicitly, and every other exception from the call is caught and reduced to
  its class name, so the provider's message never reaches a traceback.

## What changed

**Migration `4b7e2c9d1a63`** (hand-written, with downgrade): `sending` added to
`ck_communications_communicationstatus`; `communications.send_requested_at` (timestamptz, null) and
`communications.raw_storage_path` (text, null); `readonly.communications` rebuilt from LP-853's
upgrade body with `send_requested_at` exposed raw (a time; LP-998 reads it to check a staging send).
`raw_storage_path` is excluded: it points at the whole sent email, the reason the inbound one is
excluded (changed in review, below). The downgrade rewrites rows the old code
cannot describe instead of failing the constraint: `sending` → `failed` "Not confirmed: rolled back
while sending…", and `queued` with `send_requested_at` → `failed` "Not sent: rolled back before the
worker sent it." (without the column it would look like an automatic reply). Applied, rolled back and
re-applied on the dev database.

**`send_draft(..., transmit=False)`** (`services/email_send.py`). With `transmit=True` it first
refuses (`CannotSendError`) when the file has no address ("This company can't send email from the
app yet."), when `get_mail_sender()` is None ("Sending email is not set up here."), when the
recipient is empty ("Add the recipient's email address before sending."), or when it is not exactly
one address, parsed the same way as `build_mime` ("The recipient must be one email address.").
Then every existing guard runs as before (plan confirmation, suppression, rate limit) and everything
is recorded as before, except status `queued`, `send_requested_at = now` and no `sent_at`. The old
mailbox-connection path (`_transmit_if_possible`) is skipped for transmit sends and left unchanged
otherwise, with a comment that the company-domain path is the one in use.

**Rate limit fix.** `_refuse_if_rate_limited` and `_recent_sends` counted only `sent` rows, so a
second Send went through while the first was still `queued`. They now count outbound rows in
`queued`, `sending`, `sent` or `delivered`, timed by `coalesce(sent_at, send_requested_at)`. A
copy-and-send row (sent, no `send_requested_at`) counts as before; an automatic reply (no time) and a
clean failure (`failed`) do not.

**API.** `SendDraftRequest.transmit: bool = False`. After `db.commit()`, a `queued` row is handed to
`send_communication.delay(id)`; if enqueueing raises, it is logged (`send_enqueue_failed`, id only)
and the response is still 200 with status `queued`. The response carries the status.

**Task module `app/tasks/outbound.py`** (in `_TASK_MODULES`): `communications.send` and
`communications.requeue_stale`. The provider call runs in `asyncio.to_thread`, since the task code is
async and the sender is sync. **Beat:** `requeue-stale-sends` every 300s, `expires: 300`.

**Read paths.** Every place that switches on `CommunicationStatus` was checked:
- Timeline summary: `queued`/`sending` with `send_requested_at` reads "A message is being sent";
  without it, still "An automatic reply is queued". The Drafts pill includes `sending` (not gone
  yet, like `queued`); the Sent pill does not.
- Frontend timeline label: `sending` reads "Queued", like `queued`. Without it, it fell through to
  "Created". The frontend's status fields are typed `string`, so there was no union to add
  `"sending"` to; nothing else in the UI changed (LP-997).
- Reminders read `sent`/`delivered` with `sent_at`, which the worker sets: a queued Send starts no
  "no reply" clock until it has gone. Message detail, email reply, condition withdraw and the open
  draft lookups check `draft` only, so they are unaffected.
- **Condition drafts read only `sent`** (`_question_sent`, the draft tail's `"sent" | "draft"`). A
  condition draft sent with `transmit=true` through the general endpoint shows "draft" while it is
  `queued`/`sending`, and also once it is `delivered` (that part is older than this ticket, and
  appears once LP-995 writes `delivered`). Pressing Mark sent then gets "this message is already
  queued", so nothing breaks, but the label is wrong. Left for LP-997, which decides what the
  condition surfaces show for a Send.

## Review follow-up

A code review of the first version found ten candidates. Five were fixed here (the rest are listed
under Not yet). Each fix has a test, and each condition it adds was mutation-checked.

| # | Finding | Fix |
|---|---|---|
| 1 | A clean failure unwound every requested need on the message, including one an earlier email that went out had asked for. Reachable: re-requesting a need after its email was sent puts it in a new draft (probed). The bounce path had the same defect, since it shares `_unwind_requests` | `_unwind_requests` (both paths) skips a need that another live outbound email (`sending`, `sent`, `delivered`, or a person's `queued` Send) also asked for, and gives it back that email's time as `requested_at` (`send_draft` had overwritten it). Only the needs this message alone asked for go back to pending, and only their finding markers are cleared |
| 2 | Any error before the provider call other than the expected ones (a database error, a bug building the body, the commit after the copy) left the row `sending` ("not confirmed") although nothing went, and no job picks up a `sending` row | Caught, rolled back, row reloaded, then the normal clean failure with the exception's class name as the code |
| 3 | The rate limit matched the stored recipient exactly, so `Borrower@x.com` or ` borrower@x.com` passed a minute after `borrower@x.com`; suppression and the transmit check both normalise | Both rate-limit queries compare `lower(trim(recipient))` with the stripped, lower-cased address. "Blank" is now blank after stripping, so LP-847's "two blanks are not one mailbox" still holds |
| 4 | `raw_storage_path` was exposed in the readonly view, against the inbound precedent | Excluded (`EXCLUDED` entry with the reason) and a targeted test that the communications view does not name it. Not in `NEVER_EXPOSED`: that check matches the name in every view, and the inbound view derives `has_raw_stored` from its own column of that name |
| 5 | A row left `sending` with "Not confirmed" read "A message is being sent" on the timeline forever | Reads "Sending was not confirmed; check before sending again". The prefix is one constant (`NOT_CONFIRMED_PREFIX`) shared by the worker that writes it and the timeline that reads it |

**Mutations of the fixes** (restored from a snapshot, `cmp` checked): 13, all killed in the end.
Three survived the first run, and each one showed a gap in the tests rather than in the fix:

- Dropping "not this email" from fix 1 survived because the worker tests' session autoflushed and the
  worker's own session (`task_session`) does not. In the worker the failing row is still `sending` in
  the database when the unwind query runs, so without that clause it counts itself as "went out" and
  unwinds nothing. The test session now has `autoflush=False`; the mutation fails 8 tests.
- Dropping the rollback from fix 2 survived plain `RuntimeError`s. A case with a real database error
  (`SELECT 1 / 0`) kills it.
- Putting `raw_storage_path` back in the view survived the drift test (an excluded column that is
  also exposed passes it). The targeted test kills it.

The dev database's migration was re-applied (down, up), so its view has `send_requested_at` only.

Not fixed, from the same review: the audit trail records "Sent a document request…" and a SENT
evidence event at queue time (as the brief asked; a design point); condition-draft screens read only
`sent` (LP-997); `delay()` is a synchronous publish inside an async route, which blocks the event
loop while the broker is down (the upload routes do the same); the re-enqueue job can add harmless
duplicate tasks behind long verification runs (its own queue or `expires`); `_refuse_if_cannot_transmit`
imports a private helper and repeats the `file_address` query.

## Not yet

- **Send button** (LP-997), including the "not confirmed" notice for a row left `sending`, and what
  condition surfaces show for a queued Send (see Read paths).
- **Delivery events** (LP-995): `delivered` / bounce from SES.
- **Pre-send content check** (LP-996, rule 5).
- **Staging** (LP-998). **`FILE_ADDRESSES_ENABLED` is off in every environment**, and `file_address`
  returns None while it is off, so every `transmit=true` Send is refused ("can't send email from the
  app yet") until it is on. The setting exists because the inbound resolver does not route the new
  address until step 4. LP-998 has to choose: turn it on for staging, or make sending depend on the
  company's domain alone. Every sent email carries the address as From and Reply-To, so sending
  publishes it either way.
- **No "Send again"** for a failed send. After a clean failure the needs are pending again, and the
  next request picks them up.
