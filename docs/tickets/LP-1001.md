# LP-1001 — recurring cash withdrawals have no rule, and no category to hang one on

- **Ticket:** LP-1001 · new rule, successor to bug-026
- **Status:** **Specified and BLOCKED** — on two artifacts the domain expert owns, and on nothing
  else. No code is written, deliberately: everything a code change could do today either misdescribes
  the transaction or deletes the finding (both measured — see below).
- **Date:** 2026-09-12
- **Predecessor:** bug-026, which found the gap and proved it cannot be closed where it was found
- **Scope when unblocked:** `docs/snapshot-fact-tags.xlsx` (one vocabulary value),
  `app/ai/tag_production.py` (the Stage-A value set and prompt), `rule_kinds.csv` + a new
  `specs/<id>.yaml`

---

## What was asked

> *"Yes recurring cash withdrawal need to be take care."*

Answering a direct question about what bug-026 should do with the ATM withdrawal it found. That answer
is what created this ticket — and it **inverted** bug-026's own recommendation, which is the whole
reason this is separate rather than a line in that ticket.

## Why bug-026 could not carry it

bug-026 recommended adding a `cash_withdrawal` category, on reasoning that was mechanically correct:
the §8 honesty contract forbids *absorbing* a data-missing into `not_applicable`, but a predicate that
is **definitely false** resolves `not_applicable` legitimately, and `apparent_category eq debt_payment`
is definitely false against an explicit `cash_withdrawal` where it can never be against `unknown`.

**And that is precisely the problem.** Today the *absence* of a category is the only reason the
withdrawal is visible at all. FR-5 abstains on it, and the abstention carries real text:

> *"Confirm the source and purpose of the $500 ATM withdrawal on 3/16. This withdrawal recurs across
> multiple months."*

Add the value and FR-5's scope goes definitely-false, the row resolves `not_applicable`, and **that
sentence disappears**. The recommended fix would have silenced the finding it was meant to serve.

**And FR-5 cannot simply be widened to keep it.** `TagCondition.op` is `PydField(pattern="^(eq|ne)$")`
— eq or ne, no disjunction — and its own comment warns that a third operator added without giving every
comparison site a shared comparator "would be silently evaluated as `ne` — wrong, and invisible".
There is no `debt_payment OR cash_withdrawal`; `ne vendor` would be far too broad.

**Nor should it be.** FR-5 asks a DTI question — *is this recurring payment a monthly obligation the
1003 omits?* — and its spec says in as many words that it must never claim a debt is undisclosed. A
recurring cash withdrawal is a different question: not an obligation to add to the liability list, but
**cash leaving the account on a pattern**, which bears on asset seasoning and source-of-funds rather
than on the debt ratio. One rule answering both would answer neither honestly.

## What exists today, measured

**Nothing in the vocabulary names cash.** `APPARENT_CATEGORY_VALUES` (`app/ai/tag_production.py:39`)
is closed at eleven values plus `unknown`: `payroll`, `transfer_own`, `transfer_third_party_in`,
`transfer_third_party_out`, `debt_payment`, `gift`, `loan_proceeds`, `refund`, `interest`, `fee`,
`vendor`. A repo-wide search for a cash *category* finds only refinance purpose (`CASH_OUT`,
`cash_out_refinance`, the MISMO cash-out determination) — a different domain entirely.

**The prompt already knows the concept the vocabulary lacks.** Stage A's own instructions cite it, at
`tag_production.py:104`, as an example of a transaction with no counterparty to read:

> *"Return null when the description names no other party (a fee, **a cash withdrawal**, an interest
> credit)"*

So the model is told cash withdrawals exist and given nowhere to put one. `_AI_TAG_ALLOWED`
(`services/tag_production.py:89`, enforced at `:489`) coerces any off-vocabulary value to `unknown`,
which is why this cannot be fixed by prompting alone and why a deterministic floor beneath the enum is
impossible: there is no value to floor *to* that is not a lie. `fee` is wrong (staging carries
`Non-Wells Fargo ATM Transaction Fee` as its own separate transaction), `vendor` means goods or
services, and `transfer_third_party_out` requires a named party the description does not have.

**The recurrence machinery already exists and needs nothing.** `txn_is_recurring`
(`tag_materialization/derived.py:5906`, LP-546) is deterministic — no model call, no calibration — and
counts **distinct months**, not occurrences (`_RECURRENCE_MIN_MONTHS = 2`, `:5884`). Two charges three
days apart are a shopping habit; the same payee in two different months is the shape an obligation
makes.

⚠️ **And one accident of that producer is load-bearing here.** `_payee_key` (`:5899`) strips digits
and bracketed text before comparing descriptions, so `ATM WITHDRAWAL 1234` and `ATM WITHDRAWAL 5678`
collapse to **one payee** — which is the only reason a monthly cash habit reads as `is_recurring=yes`
at all. For FR-5 that collapse is incidental. For this rule it is the mechanism, so it must be
**tested as such** rather than inherited quietly: if `_payee_key` ever stops stripping digits, FR-5
loses a few edges and this rule stops working entirely.

**The exposure, from bug-026's measurement.** Of 15 FR-5 abstentions caused by a missing category,
coming from **7 distinct transactions**, exactly **one** is a cash withdrawal — an ATM withdrawal of
$500 on 2026-03-16, producing 2 of the 15 findings. The other six are payments to unnamed accounts
(`ACCT# 0586`, `CRD 2060`) and generic unreadable descriptions, which this ticket does **not** address.

⚠️ *That 2-from-1 ratio is bug-025 showing through — the statement sits on the file three times — and
bug-025's guard now prevents it. So expect **one** finding here, not two. The population is small
today: one transaction on one file. It is worth a rule anyway because cash intensity is a pattern
question that only gets more visible as statements accumulate, not because the current count is
alarming.*

## The rule, as far as it can be specified without a domain call

```
applicability:                                    # all three required (LP-517 conjunction)
  - {tag: txn.is_money_in,       op: eq, value: out}
  - {tag: txn.apparent_category, op: eq, value: cash_withdrawal}   # ⚠️ does not exist yet
  - {tag: txn.is_recurring,      op: eq, value: "yes"}
```

- **Surfaces, never asserts** — `needs_review` only, following FR-3 and FR-5's inverted bar (a
  fraud-adjacent finding names a person; a false accusation costs real trust, a missed one costs a
  review underwriting does anyway).
- **A one-off withdrawal stays out of scope by construction.** `txn_is_recurring` returns a definite
  `"no"` for a payee in a single month, so scope-false resolves `not_applicable` — not a gap — exactly
  as it does today. Only "money out, cash, two or more distinct months" is in scope.
- **An unreadable description abstains**, as everywhere else: absent is not "no" (§8).

## Two things only the domain expert can supply

**1. The category value, in `docs/snapshot-fact-tags.xlsx`.** `fact_tags.csv` is generated from that
workbook (LP-311) and `vocabulary_extra.yaml` **cannot** substitute — `declarations.py` raises
`DeclarationError` if an overlay tag duplicates a `fact_tags.csv` tag, deliberately, so the two readers
can never disagree about one domain. Their call, not a code change: whether the value is
`cash_withdrawal`, or a broader `cash` covering deposits too, and whether an explicit `other` is worth
having alongside it (the eleven values have no "none of these" that is distinguishable from "could not
tell").

**2. The rule itself.** A rule id plus a row in `rule_kinds.csv` — which, worth stating because I
assumed otherwise first, is **not** generated by `generate_fact_tags.py`: it came from LP-301's
separate conversion of the rule-classification workbook, so the CSV is editable in-repo but its
upstream is a second human artifact. Needed from them: the id and category, the `criteria` text, the
`guideline_reference`, whether there is a **threshold** (FR-5 deliberately has none, on the grounds
that where a recurring debit becomes material is a domain call with no agency text behind it — the same
argument applies to a cash amount, and the same answer is available), and the finding's wording.

⚠️ **The guideline question is open and I am not going to invent an answer.** Fannie's B3-4.2 asset
guidance is about money *entering* an account — large deposits, sourcing, seasoning. A recurring cash
*withdrawal* has no obvious published hook, and the honest possibilities are that it belongs under
source-of-funds scrutiny, that it is a house rule with no agency citation, or that it is not a rule at
all and the right answer was the abstention all along. FR-5 carries a real B3-6 citation; this rule
needs one or an explicit acknowledgement that it has none.

## ⚠️ Sequencing — the one thing that can make this worse

**The enum value must NOT ship alone.** The day `cash_withdrawal` appears in the vocabulary, FR-5 goes
silent on every recurring cash withdrawal — correctly, by scope — and if the new rule is not live, that
transaction is covered by nothing. Coverage goes **backwards** on the exact case this ticket exists to
protect.

So: either the value and the rule land together, or the value lands and the rule follows immediately
with the gap acknowledged in between. A test pinning the withdrawal's visibility across the change is
the cheap way to make that non-negotiable.

**And the value change is not free.** `_stage_a_version` keys the Stage-A cache
(`tag_cache_store.py:124`), so editing the value set or the prompt re-runs the model over every
transaction in the corpus and invalidates the calibration of a measured tag. Its live readers are
**AS-2, AS-12 and FR-5**. That is work to schedule, not a tweak to slip in.
