# LP-619 — A deposit's finding can name the bank statement it is on

## Why LP-617 was not enough

LP-617 gave a finding its source documents, but only where the rule already knew them: a consistency
rule (which gathers per source) and a `per_document` rule (whose subject IS the document). On
LF-3CVT that covered 11 rules of 46 — and missed the bulk:

| Rule | Findings on LF-3CVT | Subject |
|---|---|---|
| AS-1 | **11** | a deposit |
| AS-12 | 10 | a deposit |
| FR-5 | 6 | a transaction |
| CR-6 | 4 | a liability |

Thirty-one findings, each about something that came off a document, none able to say which one. A
processor reading "this deposit" still has to work out which statement it is on.

## The parent link was never missing

A transaction is not stored loose. It is nested INSIDE the statement it came from, and the traversal
that feeds the enumerator flattens exactly that:

```python
# traversal.py — all_transactions
return [txn for entry in snapshot.documents.entries for txn in (entry.transactions or ())]
#            └────── the parent ──────┘                        └── the child ──┘
```

The parent is known one expression earlier and dropped. `all_list_rows` does the same for a credit
report's tradelines. So this is not a derivation — it is keeping what the structure already says.

## The change

**`source_document_by_subject(snapshot)`** in `snapshot/traversal.py` — every subject a rule can be
keyed on, mapped to the document it came from:

- a document maps to **itself** (a `per_document` rule's subject IS its source);
- a transaction maps to the statement carrying it;
- a stable list row maps to the document declaring the list (a tradeline to the credit report).

**`_attach_document_provenance(results, snapshot)`** in the run, applied once before persisting:

1. What the RULE carried always wins. A consistency rule knows which sources it compared *and which
   it excluded*; nothing here can reconstruct that, so it is never overwritten.
2. Otherwise the subject's own document, from the map above.

## Subject-derived provenance now lives in ONE place

LP-617 put the `per_document` case inside `deterministic.py` and `judgment.py` — two evaluators each
deciding whether their subject was a document. That is now removed: both cases are the same question
("what document is this subject from?"), the map answers both, and the rule evaluators carry only
what ONLY they know (a consistency rule's gathered sources).

## What stays empty, deliberately

The map is a lookup, and a missing key means the caller says nothing:

- **a borrower, the loan, an account key** — the verdict is not about a document;
- **a MISMO-stated liability** — it came from the 1003 import, not from any document on the file.
  `LiabilityRow.source` already distinguishes `_SOURCE_MISMO` from `_SOURCE_CREDIT_REPORT`, and
  pointing a MISMO liability at the credit report would be a confident lie;
- **an id-less tradeline** — the enumerator SYNTHESIZES a subject id for a row whose own `row_id` is
  absent, so that id is not this row's and mapping it would attach a finding to a document by
  coincidence. A real gap, and the honest one: it names no document rather than the wrong one.

## Tests

`tests/verification/snapshot/test_source_document_by_subject_lp619.py` — 9 tests:

- a deposit resolves to the statement it is on, and to the SECOND statement rather than just any;
- a tradeline resolves to the credit report; a document is its own source;
- an id-less row, a borrower, the loan, and a MISMO liability all resolve to nothing;
- an absent documents section yields an empty map (a degraded build cannot claim provenance);
- the attach step: a deposit gains its statement, a subject with no document is left alone, and what
  a consistency rule carried is never overwritten.

Full suite: 5589 backend, 376 frontend, mypy and tsc clean.
