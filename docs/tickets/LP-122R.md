# LP-122R — Certify AS-5 gift-letter as completed rule #1 + freeze the per-rule pattern

**Type:** Story · **Epic:** Phase 3.5 / Epic B · **Depends:** LP-118.6, LP-119, LP-120, LP-121 (+ fix-ups)
**Status:** complete · **Date:** 2026-07-08

## What this ticket is

AS-5 (gift funds present but no gift letter) has been the *vehicle* for building the engine — LP-119
(applicability filter), LP-120 (evaluator framework + AS-5 evaluator), LP-121 (runner), plus fix-ups.
Its machinery EXISTS and its applicability is ALREADY CORRECT in `verification_rules`.

So this ticket does **NOT build or re-save AS-5**. It **CERTIFIES** AS-5 as a completed, validated
rule — rule **#1** — and **FREEZES the repeatable per-rule pattern** the remaining ~123 rules follow.
The pattern is the real deliverable.

**Scope held:** no engine/evaluator/runner rebuild; AS-5's applicability was verified, not re-saved; no
other rules built; PC-2's malformed legacy row left untouched; the live verification path unchanged.

## The canonical AS-5 wire-format applicability

This is the shape in `verification_rules` (confirmed against the DB), the LP-119 migration, and
`rule_seed.json` — all three agree:

```json
{
  "scope": {},
  "triggers": {
    "all": [
      { "kind": "entity_exists", "collection": "assets", "field": "is_gift", "op": "eq", "value": true }
    ]
  },
  "required_inputs": [
    { "kind": "data_field", "path": "assets[].is_gift" }
  ]
}
```

**Correctness points (all certified):**
- `scope {}` = applies to ALL files (gifts can appear on any loan).
- Trigger on `assets[].is_gift == true` (the real derived bool) via `entity_exists`
  (collection=assets, field=is_gift, op=eq, value=true). No `min_count`, no nested `where` — the real
  schema shape.
- The gift **LETTER is the CHECK-TARGET** → deliberately NOT in `required_inputs`; its absence is the
  FINDING (produced by the evaluator), NOT a couldn't-check.
- `is_gift` IS a `required_input` (data_field) → if asset/gift data is absent → couldn't-check (the
  honesty guard).

It parses against `Applicability.model_validate` (`extra="forbid"`) with **zero errors**.

## Decision — AS-5 validated status

**AS-5 is flipped to `validated=true`.** Rationale: AS-5 has **no tunable numeric threshold** — its
trigger is the boolean `is_gift`, not a Priya-threshold with a number to confirm — and its
evaluator **reproduces the live rule's verdict** (certified above). With nothing left to validate and
known-correct behaviour, it emits at **full confidence**; the runner (LP-121 FIX 5) no longer marks it
provisional.

**Implemented reversibly, in both authoring + data layers:**
- **Seed (authoring source of truth):** `generate_rule_seed.py` gained `_VALIDATED_NO_THRESHOLD =
  {"xsrc.asset.gift_without_letter"}`; `rule_seed.json` regenerated → AS-5 `validated=true`. A fresh DB
  seeds it validated.
- **Data migration:** `20260708_1100_b6f2d9c4e1a8_lp_122r_as5_validated.py` sets `validated=true` on the
  existing AS-5 row (mirrors the LP-119 data-migration pattern). Downgrade is an intentional NO-OP (the
  seed now carries validated=true; reverting to false would leave AS-5 provisional, matching neither the
  seed nor the certified reality).

**THE CRITERION FOR FUTURE RULES (applied ~123 times — kept strict):**

> Seed a rule `validated=true` **ONLY** if it has **NO tunable numeric threshold** (nothing for Priya
> to confirm) **AND** it reproduces known-correct behaviour. Threshold-bearing rules (AS-1, DT-1, PR-1,
> MI-1, …) stay `validated=false` until Priya confirms the number — **even after they are built**.

This criterion is guarded by `test_rule_as5_certification.py::test_validated_criterion_is_narrow`
(only the two Priya-confirmed threshold rules + AS-5 are validated); adding a validated row must be a
deliberate, documented certification.

## THE REPEATABLE PER-RULE PATTERN (how to build rule N)

Rules #2..N are **fill-in-this-pattern**. Adding a rule is authoring data + one evaluator — **no engine,
filter, or runner change**.

1. **Take the readable design.** Start from the rule's authored applicability in the readable design
   format (the playbook: `docs/rules/consolidated_rule_master_list.md` + `rule_seed.csv`; the intended
   scope/trigger/inputs logic). *(Note: an `rule_applicability_authored.md` split-out was referenced in
   planning; today the authoring source is the playbook/CSV. Keep the readable design and the wire JSON
   in sync.)*

2. **TRANSLATE design → wire format** (`app/verification/applicability/schema.py`). The mechanical map:
   | readable design | wire format |
   |---|---|
   | `type: entity_exists` | `kind: "entity_exists"` |
   | `entity: assets` | `collection: "assets"` |
   | `where: is_gift == true` | flatten → `field: "is_gift", op: "eq", value: true` |
   | `min_count`, `purpose:` (flat) | **drop** — not schema keys; express purpose via `scope` |
   | required inputs | **FLAT LIST**, each with a `kind` tag (`data_field` / `document` / `derived_field`) |
   | scope values | **strings** (`["fha"]`, `["purchase"]`) |
   | a refi-type rule | emit **BOTH** `scope.loan_purpose=["refinance"]` **and**
     `scope.refinance_type=["cash_out"|…]` (LP-121 FIX 10 — the generic FALSE-precedence path then
     handles purchase files with no engine special case) |

   AS-5 above is the reference. **PC-2's DB value `{"purpose": "purchase"}` is the example of a WRONG
   legacy shape** — the flat `purpose` key that `extra="forbid"` now rejects; it must be translated to
   `{"scope": {"loan_purpose": ["purchase"]}}` when PC-2 is built (do NOT touch it before then).

3. **VALIDATE the JSON** against `Applicability.model_validate` (`extra="forbid"`) — it must parse with
   **zero errors**. If the rule's logic **can't** be expressed in the schema (e.g. it needs a nested
   `entity_exists` or a `min_count`), **FLAG it** — don't force wrong JSON. Resolve the schema gap first.

4. **SAVE that rule's applicability** to `verification_rules` (a per-rule data migration mirroring
   `a7c4e9f2b6d3` / this ticket's migration, plus the seed row). **This is the only save.**

5. **Build any missing derived fact** into the fact-builder (LP-118.6) if the rule reads a fact that
   isn't in the snapshot yet (e.g. `computed.dti`). A required derived field that is absent →
   couldn't-check, never a silent skip.

6. **Implement the evaluator** per the LP-120 contract (`app/verification/evaluators/`): a pure reader
   of the frozen snapshot returning FINDING / SATISFIED / (COULDN'T-CHECK when undeterminable) with a
   message, confidence (`deterministic` vs `computed` — never a false 100%), and provenance. Register it
   (`register(...)` / it is picked up by `ensure_registered()`). Model it on `gift_letter.py`.

7. **CERTIFY** (mirror `test_rule_as5_certification.py` + the LP-119/120/121 test shapes): applicability
   classifies correctly across the buckets; the evaluator verdict is correct (and, where a live rule
   exists, matches it); end-to-end through the runner it lands in the right bucket with reasons/provenance.

8. **Set `validated`** by the criterion above (true ONLY if no unconfirmed threshold + known-correct;
   else false → the runner emits it provisional).

9. **Document** `docs/tickets/LP-XXXR.md` — what the rule is, the canonical wire applicability, acceptance
   criteria + how met, and any assumptions/decisions.

## Assumptions and decisions

- **Check-target-not-in-inputs** — the thing a rule *checks* is never a required input; its absence is
  the finding, not an awaiting-data skip. (AS-5: the gift letter.) This is a load-bearing pattern rule.
- **Validated criterion** — as above; strict, guarded by a test, precedent for ~123 rules.
- **No-asset → couldn't-check** — accepted LP-119 tradeoff, re-certified here.
- **PC-2 legacy row** — `{"purpose": "purchase"}` in the DB is malformed under `extra="forbid"`; noted
  as the canonical "wrong legacy shape to translate", **not fixed here** (fixed when PC-2 is built).
- **`rule_applicability_authored.md`** — referenced in planning as a split-out readable authoring doc; it
  does not exist as a separate file today. The readable design currently lives in the playbook /
  `rule_seed.csv`; the pattern's step 1 points there. If the split-out is later created, step 1's source
  updates but the translate→validate→save flow is unchanged.
