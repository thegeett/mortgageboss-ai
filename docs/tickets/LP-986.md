# LP-986 — IAM for email: worker and api task roles

- **Ticket:** LP-986, the sixth of the step-1 tickets in `loan-email.md` §15.
- **Status:** applied to staging (account `058190633983`, us-east-1) on 2026-10-20 (US Eastern). With
  receiving off, only the worker's outbound statements are live.

## What and why

Each task role gets exactly the email permissions its code uses today or in step 2.

**Worker** (receives, sends, reads delivery events):

- reads raw received mail: `s3:GetObject` on the mail bucket's `inbound/*`;
- saves a copy of each sent email (step 2): `s3:PutObject` on `outbound/*` only;
- consumes the inbound queue, the malware-scan-results queue and the delivery-events queue: receive,
  delete, change visibility, get attributes, get URL. It has no `SendMessage`, because only SNS and
  EventBridge put messages on those queues;
- sends email: `ses:SendEmail` and `ses:SendRawEmail` on this account's and region's `identity/*`
  and on our configuration set. `identity/*` because tenant identities are created at onboarding (step 3);
- uses the shared key the mail bucket and queues are encrypted with: `kms:Decrypt`, `kms:GenerateDataKey`.

**Api** (accepting an attachment runs here: `api/inbound.py` →
`services/inbound_triage.accept_attachment`, which reads the raw message):

- reads raw received mail: `s3:GetObject` on `inbound/*`;
- `kms:Decrypt` on the shared key.

**What each role deliberately cannot do:**

- **The api cannot send** (no SES permission), cannot write to the mail bucket, and has no queue access.
- **The worker still cannot write documents.** It stays read-only on the documents bucket, and its
  existing statements are unchanged.

## What changed

- `infra/modules/compute/variables.tf`: new `mail_bucket_arn`, `mail_kms_key_arn`, `worker_queue_arns`,
  `ses_configuration_set_arn`, `ses_send_enabled`, all defaulting to empty or off.
- `infra/modules/compute/iam.tf`:
  - worker: new `MailInboundRead`, `MailOutboundWrite`, `MailQueuesConsume`, `SesSend`, `MailKey`;
  - api: new `MailInboundRead`, `MailKeyDecrypt`;
  - each is a `dynamic` statement that disappears when its input is empty, and each has a comment;
  - both role header comments are updated.
- `infra/modules/outbound_mail/outputs.tf`: new `configuration_set_arn` (the module had no such output).
- `infra/envs/staging/main.tf`: `module "compute"` gets the five inputs, from module outputs, with the
  inbound ones behind `inbound_mail_enabled`.

**Two guards beyond the brief, so no environment can render an empty `Resource: ""`, which IAM rejects:**

- the api's `MailKeyDecrypt` also requires `mail_kms_key_arn != ""`;
- `SesSend`'s resource list is wrapped in `compact()`, in case sending is on without a configuration set.

Staging passes both values, so its result is the same either way.

There is no dependency cycle: neither `inbound_mail` nor `outbound_mail` reads anything from `compute`.

## Found for step 4: accept reads raw mail from the wrong bucket

Checked in `backend/app/services/inbound_triage.py`.

- **What the code does.** `_attachment_bytes()` takes `InboundMessage.raw_storage_path`, strips an
  `s3://<bucket>/` prefix, and reads the remaining key through `get_storage_backend()`. That backend is
  bound to `settings.s3_bucket`, the **documents** bucket (`S3_BUCKET` in the task env).
- **Why that breaks.** Raw mail lives in the mail bucket (`mbai-staging-mail/inbound/...`), so once SES
  delivers, every read looks for the key in the wrong bucket.
- **What the error will look like.** S3 will most likely answer **AccessDenied, not "not found"**.
  Neither task role has `s3:ListBucket`, and without it S3 reports a missing key as 403.
- **Who is affected.** `_attachment_bytes()` has four call sites in that module, including accept and
  the attachment preview.
- **What step 4 needs.** A mail-bucket reader that honours the bucket in `raw_storage_path`, or a
  second storage backend bound to the mail bucket.
