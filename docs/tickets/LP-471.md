# LP-471 — Fall back to Tier 3 on no-extractor types and extraction errors

The highest-leverage change from the v2 bench: one fallback rescues ~59 documents now and every future one.
A document that classifies correctly can still yield zero data via two paths that bypass Tier 3 — a type with
no registered extractor, and an extractor that errors. Route both to the existing Tier-3 scoped free extraction
so **no document is ever fully empty**. No classification change, no new extractor (LP-472), no rule reads the
untyped output.

---

## Phase A — design (code traced; STOP for sign-off before Phase B)

### A1 — the routing points (two hooks, quoted)

Both terminal paths live in `app/tasks/document_processing.py`.

**Path 1 — a no-extractor type terminates in `_route_by_tier` (line 276-286):**
```python
if document.tier == Tier.TIER_1:
    extractor = EXTRACTORS.get(document.document_type or "")
    if extractor is not None:
        return await _extract_branch(db, document, content, extractor)
    await _summarize_document(db, document, content)      # Tier-1 promoted-but-unwired
elif document.tier == Tier.TIER_2:
    await _summarize_document(db, document, content)      # <-- warranty_deed, passport, CD-of-deposit, ...
else:  # Tier.TIER_3
    await _tier3_analyze(db, document, content)           # unknown/uncataloged (the path that WORKS)
```
A Tier-2 type (and a promoted-but-unwired Tier-1) gets **`_summarize_document`** — a 1-2 sentence Haiku
*summary* stored on `document.summary`. ⚠️ **That summary is NOT surfaced into the snapshot's untyped section**
(only `_tier3_analyze`'s `generic_analysis` is → `DocumentEntry.untyped_extraction`). So from the snapshot /
verification view a Tier-2 type yields **no usable data** — the "nothing" the ticket names. **Hook 1: route the
no-extractor cases to `_tier3_analyze` instead of `_summarize_document`.**

**Path 2 — an extraction error terminates in `_extract_branch` (line 442-449):**
```python
if result.status == ExtractionStatus.FAILED or result.confidence < _CONFIDENCE_THRESHOLD:
    document.status = DocumentStatus.NEEDS_REVIEW
    document.processing_error = "extraction failed or low confidence"
    ...
    return False
```
A FAILED extraction (069 `BadRequestError`, 222 empty-failure — the extractor returns `ExtractionResult.failed()`,
all-null data) lands here: `NEEDS_REVIEW`, **no data**. (A FAILED *version* is persisted just above at line 429
with `error_detail=result.reasoning`.) **Hook 2: on `status == FAILED`, after the throttle gate, fall back to
`_tier3_analyze`.** (A third, rarer path: an extractor that *raises* — an uncaught `ValueError` — is caught by
`_process_document`'s outer `except` → `_mark_failed` → `FAILED`. Post-LP-464 extractors are graceful and
return FAILED rather than raise, so Phase C checks whether 174 raises or returns FAILED and whether the
`_mark_failed` path also needs the hook.)

**Two hooks, not one shared path** — the no-extractor case is in `_route_by_tier`, the error case in
`_extract_branch`. Both call the SAME existing `_tier3_analyze`, so there is one fallback mechanism, reached
from two sites.

### A2 — what the record shows afterwards (a failure must not look like a success)

Reuse `_tier3_analyze(review_reason=...)` — its `review_reason` already distinguishes COMPLETED vs NEEDS_REVIEW
and carries the reason:

| case | typed extraction | fallback | terminal status | how it's distinguishable |
|---|---|---|---|---|
| **no-extractor** | none (no version) | `_tier3_analyze(review_reason=None)` | `COMPLETED` | `generic_analysis` present, **no extraction version**; document_type is the real type, tier ≤ 2 |
| **extraction error** | a **FAILED version** (`error_detail=result.reasoning`) | `_tier3_analyze(review_reason="extraction_error:<reason>")` | `NEEDS_REVIEW` | FAILED extraction version **with the error reason** + `generic_analysis` present + `processing_error` |
| **normal** | a SUCCEEDED/PARTIAL version | none | `COMPLETED`/`NEEDS_REVIEW` | typed fields present, `generic_analysis` **absent** |

So a fallback document always shows: **no typed fields** (no version for no-extractor; a FAILED version for an
error), **why** (the tier/absence for no-extractor; the FAILED version's `error_detail` for an error), and —
for an error — **the error type** (`result.reasoning`; ⚠️ `rate_limited` is excluded upstream by the throttle
gate, per LP-462, so it can never masquerade). The presence of `generic_analysis` marks "fell back to untyped";
it never overwrites or hides the typed failure.

### A3 — retry vs fallback ordering (fallback AFTER retries, never instead)

The extractor's own retries — the LP-462 rate-limit backoff and the LP-464 truncation retry — run **inside**
the `await extractor(...)` call. Only its final result reaches `_extract_branch`. Then, in order:
1. **Throttle gate (line 399):** `status == FAILED and reasoning == INFRA_RATE_LIMITED` → `NEEDS_REVIEW`
   **re-runnable**, no data, **return** — a sustained throttle after retries is transient and re-runnable, so
   it must **NOT** fall back (a re-run may extract fine; falling back would silently degrade it).
2. **FAILED gate (line 442, AFTER the throttle gate):** a *non-throttle* FAILED → **fall back**.
So the fallback is structurally after retries and after the re-runnable-throttle carve-out. **Confirmed: no
transient throttle can trigger the fallback.**

### A4 — cost

- **No-extractor types (56 in v2):** these already make one `_summarize_document` Haiku call; the fallback
  **swaps** that for one `analyze_document` call (scoped free extraction) — **same call count**, marginally more
  output tokens. **~zero net new calls.**
- **Extraction errors (3 in v2):** the failed extractor call already happened; the fallback **adds** one
  `analyze_document` call each. **+3 net calls** (~1% of the 303-doc corpus).
So the added volume is dominated by a cheap swap, not new calls — **at or below LP-463's measured +2-6% of
calls for Tier 3.** In a real loan file, a handful of Tier-2 documents cost ~one analyze call each, mostly
displacing the summary call.

### A5 — the untyped constraint (existing enforcement covers the new path)

The fallback reuses `_tier3_analyze`, which stores `document.generic_analysis`. The snapshot builds
`DocumentEntry.untyped_extraction = _scrub_untyped(document.generic_analysis)` (documents_section.py:1773) —
**keyed on `generic_analysis` presence, regardless of how it got there**. That section is:
- **identifier-scrubbed** at build time (`_scrub_untyped`);
- **opt-in for AI reasoning** only (`ContextOptions.include_untyped`, default `False`, subjects.py:148 — a
  group must declare it);
- **read by NO deterministic rule or service** (grep-confirmed: nothing under `app/verification/rules/` or
  `app/services/` references `untyped_extraction`).
So the new no-extractor/error fallbacks inherit the LP-463 constraint automatically — **no new enforcement is
needed**, and none of the 37 rules can read the fallback output.

### A6 — does a partial extraction fall back? (NO)

`derive_status` (parsing.py:255): **nothing read → FAILED; a coercion loss → PARTIAL; else SUCCEEDED.** So
`FAILED` means `non_null == 0` — **genuinely empty**; `PARTIAL` means some typed fields were captured. **The
fallback triggers ONLY on `status == FAILED`** (empty). A `PARTIAL` (2 of 30 fields) is not FAILED → it keeps
its typed fields and does not fall back — mixing typed + untyped for one document would invite a reader to
conflate them (the A6 concern, confirmed).

⚠️ **One refinement to the current gate:** today the FAILED gate *also* fires on `confidence < 0.5` (a
low-confidence extraction that DID capture fields). Those must **not** fall back — they have typed data. So the
fallback branch keys on **`status == FAILED` alone** (empty), and the existing low-confidence → `NEEDS_REVIEW`
(keep the typed fields, no fallback) is left exactly as is. In practice FAILED is the "almost nothing" case;
PARTIAL/low-confidence are not.

### FLAG — anything inexpressible

- **069 (oversized `BadRequestError`) cannot be saved by the fallback** — the fallback `analyze_document` call
  sends the SAME oversized content and will also fail on size; `_tier3_analyze` is graceful (analysis `None`),
  so 069 falls back, the fallback also fails, and the document ends `NEEDS_REVIEW` with the FAILED version +
  no untyped data. That is the honest outcome; **069 needs the LP-464 page-cap work, not this fallback** — Phase
  C reports it plainly.
- The `_mark_failed` (raise) path is a rarer third site; Phase C confirms whether 174 needs it.

### Plan, cost, ADR, and STOP

**ADR (required):** (1) the principle — **no document should ever yield zero data**; a missing type, missing
extractor, or crash costs *typed* data, not *all* data. (2) This **deliberately reduces the pressure to re-tune
the classifier** — LP-463's declining was correct and caused over-declining; making the failure mode cheap
(no-extractor/crashed still "read anyway") is a safer fix than loosening the classifier and risking the
force-fits returning. (3) The **fallback-after-retry** ordering and why (the re-runnable throttle must never
fall back).

**Phase C cost estimate:** ~$0.30 (Haiku) — re-processing ~8-10 named documents (264, 228 no-extractor; 222,
174, 069 errors; a normal control) through the two hooks. **The 303-doc bench is NOT re-run** (a separate
checkpoint).

**STOP — awaiting sign-off before Phase B.** Open questions:

1. **Two hooks** — `_route_by_tier` (no-extractor Tier-2 + Tier-1-unwired → `_tier3_analyze`) and
   `_extract_branch` FAILED gate (fall back after the throttle gate). Agree?
2. **Record shape** — reuse `_tier3_analyze(review_reason)`: no-extractor → COMPLETED; error → keep the FAILED
   version (error type) + NEEDS_REVIEW + untyped. Agree?
3. **PARTIAL / low-confidence do NOT fall back** — the fallback keys on `status == FAILED` alone (empty). Agree?
4. **`_mark_failed` (raise) path** — I lean to add the fallback there too for completeness (a raised error is
   the same "no data" outcome), pending Phase C confirming whether 174 raises. OK to include it if 174 needs it?

**Sign-off (Geet):** all four confirmed. FAILED version staying is the important half. PARTIAL doesn't fall
back. Include `_mark_failed` only if Phase C shows 174 raises (don't add untested code on a path nothing
reaches). 069 reported plainly.

## Phase B — build

Both hooks reach the SAME existing `_tier3_analyze`:
- **Hook 1 (`_route_by_tier`):** collapsed to "Tier-1 **with** a registered extractor → `_extract_branch`;
  everything else → `_tier3_analyze`". So a Tier-2 type, a promoted-but-unwired Tier-1, and unknown all get
  scoped free extraction. The LP-65 `_summarize_document` wrapper is **removed** (+ its now-unused import).
  **`document.summary` is preserved** — `_tier3_analyze` now also sets `document.summary = analysis.summary`
  (the DocumentResponse field the UI shows), additively for every long-tail doc.
- **Hook 2 (`_extract_branch`):** the FAILED gate is split — `status == FAILED` (genuinely empty) →
  `_tier3_analyze(review_reason="extraction_error")` **after** the throttle gate, keeping the FAILED version
  (`error_detail`) + `processing_error` (error type) + `NEEDS_REVIEW`; a separate `confidence < 0.5` gate
  keeps a low-confidence-**with-fields** extraction exactly as before (no fallback — A6).

Tests: the 6 Tier-2/promoted-Tier-1 tests rewritten (summarize → free extraction); the failure test rewritten;
**+3 new** — the fallback keeps the FAILED version + error type; low-confidence does NOT fall back;
fallback-also-fails stays empty-but-diagnosable. Full suite **4186 passed**, ruff + mypy clean.

**174 does NOT raise** in the current code (it returns a graceful result), so the `_mark_failed` (raise) hook
is **not added** — an untested hook on a path nothing reaches would be worse than the gap (per the sign-off).

## Phase C — proof (live `analyze_document` — the fallback's core call — Bedrock/Sonnet)

`analyze_document` IS what `_tier3_analyze` runs, so its output on each target doc is exactly what the fallback
captures. **Every document yielded real, substantive content — no boilerplate, so the Tier-3 scoping is good.**

**No-extractor types fall back and capture substance:**
- **264 passport** → *"Indian passport for Thangavel Jagadeesan, born November 6, 1978, issued December 17,
  2024 in Coimbatore, expiring December 16, 2034"* + finding (nationality, expiry). Name, DOB, issue/expiry —
  exactly the identity a passport should yield.
- **228 warranty_deed** → *"special warranty deed dated December 4, 2023, transferring a condominium unit
  (Lot 86, Creekside Subdivision Phase 2) in Charlotte from **NVR, Inc.** to **Chetan Reddy Patel**"* + a
  property-interest finding. **Grantor, grantee, property, recording date** — exactly what the ticket
  specified.

**Extraction errors fall back and capture substance:**
- **222 (empty-failure)** → an employment services agreement (RBT with CCRES), with **income findings**:
  $30/hr, $1.82/quarter-hour travel, $10/hr supervision. The income the typed extractor failed to get is
  captured untyped.
- **174 (ValueError, a scanned/image lease)** → a full PA residential lease: 1928 Boulder Drive, landlord/
  tenant, **$3,000/mo rent, $3,000 deposit**, term, utility + subordination obligations. The scanned document
  the lease extractor errored on reads cleanly through the fallback.

**069 (oversized `BadRequestError`) — ⚠️ the fallback SUCCEEDED, contrary to the Phase A prediction.** The
typed extractor failed on 069 as oversized, but `analyze_document` **captured the full closing package** —
*"$688,500 conventional loan on a $765,000 purchase, 30-yr fixed 8.070%, lender-paid 2-1 buydown, ~$6,023/mo,
$54,184 cash-to-close"* + 5 findings (payment, escrow, HOA, buydown schedule, purchase). **Why:** the Tier-3
path applies the LP-462 `tier3_max_pages` cap that the typed extractor lacks, so the fallback sends a capped
payload (121k input tokens) and succeeds. **So the fallback rescues even the oversized-typed-extraction case**
— better than predicted; the LP-464 page-cap concern is already handled on the Tier-3 path. (A genuinely
enormous package could still exceed the limit after capping; 069 does not.)

**Control (a normally-extracting document is UNCHANGED):** proven by `test_happy_path_pay_stub` (a SUCCEEDED
extraction → `COMPLETED`, `analyze.call_count == 0`, no fallback) and the full suite staying green.

**The record distinguishes fallback from success (A2):** proven by the new unit tests — the FAILED extraction
version is kept with `error_detail`, `processing_error` names the error type, the document is `NEEDS_REVIEW`,
and `generic_analysis` marks "fell back to untyped" without hiding the typed failure.

**Equivalence anchors:** `ACTIVE_RULE_IDS = 37` (unchanged) and the 37 live rules identical — **no verdict
moves**, because untyped data is unreadable by every deterministic rule (A5, grep-confirmed + the full suite
green). `SNAPSHOT_VERSION = 4` (unchanged), full suite **4186 passed / 5 skipped / 1 xfailed**, ruff + mypy
clean.

**Assumptions / decisions:** two hooks into one `_tier3_analyze`; `document.summary` preserved from
`analysis.summary`; PARTIAL/low-confidence do not fall back; `_mark_failed` hook not added (174 doesn't raise);
the fallback uses the Tier-3 analysis model (Sonnet, LP-463's choice) — unchanged by this ticket.

**NEW / updated findings:**
- **069 is RESCUED by the fallback** (the Phase A "cannot be saved" prediction was pessimistic — the Tier-3
  page cap handles it). A package larger than the cap allows could still fail after capping; none observed.
- The fallback runs on **Sonnet** (the analysis model), so a no-extractor/error document costs one Sonnet
  call — pricier per call than a Haiku typed extraction, but it is the existing Tier-3 cost, not new.

**What LP-472 and the classifier-cue ticket must now do:** LP-472 (the shared identity schema) gives the
no-extractor identity types (passport, warranty_deed, certificate_of_deposit, …) a **typed** home so their
identity fields become rule-readable — the fallback makes that non-urgent (untyped beats nothing) but not
unnecessary. The classifier-cue ticket can now re-tune more freely: with the fallback, an over-decline or a
misroute costs untyped data, not nothing, so loosening the classifier no longer risks the LP-463 force-fits
returning at the cost of empty documents.
