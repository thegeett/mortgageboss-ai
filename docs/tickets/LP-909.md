## What the survey establishes, before any code

**The import's two-pass match is already indexed for.** `conditions` carries
`ix_conditions_file_lender_code (loan_file_id, lender_id, lender_code)` and
`ix_conditions_file_fingerprint (loan_file_id, text_fingerprint)` — "the two lookups import does, in
the order it does them", per LP-904's own comment. The spec's order (code+fingerprint, then
fingerprint alone) and the indexes were designed together; the queries must use them rather than
scan.

**`fingerprint()` exists and is shared** (LP-907). The reader's rule-6 dedup and the stored
`text_fingerprint` normalise identically through `note_stripped`, with the notes as rule 6's third
element the only deliberate difference.

**⚠️ `round_number` is assigned here and nowhere else — and the INDEX is the mechanism, not the
lock.** An earlier draft of this line said `max + 1` "must be computed inside the lock or two
concurrent imports collide", which credits `loan_file_needs_lock` with a guarantee it does not
offer. Review found it; verified:

`loan_file_needs_lock` yields `bool(acquired)` and its own docstring says *"the caller proceeds
either way — a missed lock just means another worker is applying, and a re-run is safe"*. That is
sound for idempotent needs recomputation and is **not mutual exclusion**. All three existing call
sites (`tasks/needs.py:72`, `:92`, `services/verification_run.py:1499`) use a bare `async with` and
bind nothing, so under contention the body runs anyway and two imports can compute the same
`max + 1`.

What actually prevents two rounds sharing a number is
`uq_condition_rounds_file_number (loan_file_id, round_number) WHERE round_number IS NOT NULL AND
deleted_at IS NULL`. So **§2 must handle the unique violation** — catch `IntegrityError`, recompute,
retry — rather than assume the lock prevented it. The alternative, binding `as acquired` and
branching, would make this the repo's first such caller and needs its own justification; the
catch-and-recompute is the smaller claim and matches what the index already guarantees.

Nothing writes `round_number` today (`api/conditions.py:328` is a read), so §2 is its first writer
and this costs nothing to get right. LP-904's migration reasons carefully about *which predicate*
belongs in that index and never addresses concurrent assignment — the gap is real, not a
misreading.

**And branching could not remove the catch even if it were taken.** `loan_file_needs_lock` takes
`timeout: int = 30`, which auto-expires a **held** lock. An import running past 30 seconds — a large
sheet, a slow code-map pass — loses the lock *mid-transaction while still working*, and the next
import then proceeds legitimately. So an `as acquired` caller would still collide and would still
need the `IntegrityError` catch. The catch alone is sufficient; the branch would be load-bearing for
a guarantee it does not deliver.

**The code map has no service** — LP-910 shipped the model, the YAML seeds and
`scripts/seed_lender_codes.py::_upsert`. Import step 4 owns its own upsert: unknown `(lender, code)`
→ insert `OBSERVED_UNMAPPED`; known → `times_seen += 1`, `last_seen_at`, and apply `info_only`,
`canonical_type_id` and `default_owner_hint` only where no prefix/bucket hint was found.

⚠️ **`loan_file.lender_id` is nullable**, and `(lender, code)` is meaningless without it. A file with
no lender must still import — the conditions land, and the code-map step is skipped rather than
guessed at. That is a real state, not an edge case: LP-905 already notes a round takes the *file's*
lender and warns rather than blocks when the sheet disagrees.

**`loan_file_needs_lock` wraps the session, not the other way round** —
`async with loan_file_needs_lock(id), task_session() as db` is the established shape, and it yields
whether the lock was acquired rather than raising.

**Stage 2's event kinds do not exist.** `ConditionEventKind` has no `CONDITION_CLEARED`, no
`CONDITION_REMOVED`, no `ROUND_COMPARED` — "an enum member nothing writes is an invitation"
(ADR-404). Import may emit only `CONDITION_CREATED`, `CONDITION_SEEN_AGAIN`, `CONDITION_NOTE_ADDED`,
`CONDITION_EDITED`, `ROUND_IMPORTED`.

**The UI template is `components/file/needs/`** — a dashboard that lists and acts, with a test that
mocks the hook layer and drives the data. `frontend/lib/api/conditions.ts` does not exist; `inbound.ts`
is the nearest sibling for query keys and invalidation. The Conditions tab today is a 13-line
`TabPlaceholder`, so there is nothing to reconcile with.

## ⚠️ Two constraints this ticket inherits, already paid for

**1. The AI split cannot check boundaries, and the screen as specified cannot show the worse half.**
LP-908 measured it: a partition constrains coverage, not boundary placement, so *the correct split of
two conditions and the wrong merge of two conditions are the same shape to every check that exists*.
Of the two failure modes, one condition cut in two is **findable** on screen (two rows reading as
halves of one sentence); two conditions merged into one is **invisible** — one plausible, correctly
worded condition with a second demand inside it, nothing flagged, nothing unassigned.

§LP-909's review screen surfaces the input text nowhere except unassigned lines, so there is no view
in which boundaries are visible against the text they were drawn on. The data for one exists:
`ParsedRow.source_line_numbers` is populated and `_Coverage` knows each claimed span. **Rendering the
paste once with each row's span delimited, for AI-split rounds only**, is what turns the invisible
case visible. S1-10's Must-match list does not require it; this is the constraint arriving before the
layout is fixed rather than after.

**2. A `PARSING` round can still strand.** LP-905 recorded it and LP-908 narrowed it on the paste
door only (a failed enqueue marks `PARSE_FAILED`). The window is narrowed, not closed — the
`PARSE_FAILED` write is a second transaction — and the upload and forward doors are deliberately
unmitigated, each carrying a comment saying so. S1-02 must poll and S1-03 must offer a retry, because
neither is decoration.

### ⚠️ Discarded rounds are listed, and §2's discard endpoint owes two answers

`list_rounds` includes `DISCARDED` on purpose — a processor who threw a draft away should see that
they did, and a round silently vanishing reads as data loss. Keeping it forces two questions the
spec does not settle, and §2 is where they are decided rather than discovered:

1. **A discarded DRAFT has `round_number` NULL**, while the round strip card is specified as
   "number, date, source chips, completeness, counts". The strip must render a numberless card, and
   nothing says how.
2. **Discarding an IMPORTED round is a real state**, argued explicitly in LP-904's migration: such a
   round *keeps* its number, stays in the unique index, and its `ROUND_IMPORTED` event survives
   forever because the table is append-only. Combined with §LP-909's "never delete, never clear",
   discarding an imported round leaves **every one of its conditions alive and still chipped to
   it** — so "discarded" would mean the round is out of the workflow while its conditions remain.
   That is defensible, and it is a different meaning from a discarded draft, shown in the same list
   under one word.

So §2's discard endpoint must state whether an IMPORTED round is discardable at all, and if it is,
what becomes of its conditions — because the migration already guarantees they survive.

### ⚠️ The invariant belongs on the WRITERS, not on the read side

Review found that `condition_enrich.py::_merge_conditions` created conditions and emitted no
`CONDITION_CREATED` — so an enrich-added condition had empty `round_numbers` (no chips) while its own
NOT NULL `first_round_id` and `last_seen_round_id` both pointed at the round that created it, and the
round's count was short by exactly `result.added`. Not incidental: `_merge_conditions` runs *only*
when `status is IMPORTED`, and `rows_on_sheet` reads the event-derived count *only* when
`status is IMPORTED`, so the only path creating eventless conditions is the only path whose count
comes from events. Fixed in the enrich service, with the test that pins it.

**The general lesson is sharper than the bug.** A read side that derives a fact from events is only
as good as its enumeration of the writers — and the first version of §1 was correct about import and
blind to enrich. That is the same family as a field with no producer at all, one layer up:
`text_fingerprint` had none; `round_numbers` and `condition_count` had none; this would have had one
that covered half its writers.

So the rule is stated where it binds: **every writer of a `Condition` emits `CONDITION_CREATED`.**
There are two today (import in §2, enrich in LP-907) and §2 adds the third.

**⚠️ The third writer needs a decision, not a default.** `POST /api/loan-files/{id}/conditions` adds
one by hand into the latest imported round, and the spec does not say which event it writes. Emitting
nothing reproduces exactly the bug above. Emitting `CONDITION_CREATED` gives it a round chip for a
sheet **it was never printed on**, which is a different lie. `origin: ConditionOrigin` (`SHEET` /
`MANUAL`) already exists on the model and is the column that should decide: a manual condition is
real and belongs to the file, but it did not *appear on a sheet*, so the chips must be able to say
so. Settled in §2, not discovered in §4.

## Open questions to settle in section 2, not later

- **A draft row edited on the review screen changes its fingerprint.** The spec's frontend test is
  "editing a row and importing sends the edited text", so an edited row imports as the processor
  wrote it — and therefore may match a different condition, or none. That is correct and worth
  stating: the fingerprint is of what is imported, not of what was read.
- **`possible_match` on a same-code/different-fingerprint collision** goes in the event detail for
  Stage 2 to interpret. It is an id, not a decision.
- **Optimistic concurrency on `PUT draft`** uses `expected_updated_at`, already on
  `ConditionDraftUpdate`. There is no other precedent in this repo — `draft-conflict.ts` is a
  different mechanism (a 409 carrying a whole plan), so this one needs its own conflict shape.
