# LP-933 — the pipeline's borrower search, out of the URL

- **Ticket:** LP-933 · Phase 4.5 follow-up · frontend (dashboard, saved views, one store)
- **Raised:** Stage 2's follow-ups in [`phase4.5-progress.md`](../phases/phase4.5-progress.md);
  ADR-405's LP-912 amendment named the exposure for the product owner
- **Decision record:** ADR-405, amended again (LP-933) in [`decisions.md`](../../decisions.md)

## What was wrong

The dashboard's search box wrote its term into the URL as `?q=` (`dashboard/page.tsx` →
`writePipelineUrl`), and the search matches borrower NAMES (`services/loan_files.py`, `ilike` over
first and last name). So a copied or shared pipeline link carried a borrower's name into someone else's
clipboard, chat and browser history. ADR-405 as amended says a filter that matches NPI stays out of the
shareable URL; the conditions list (LP-913) already followed that, and the pipeline did not.

## What changed

1. **The search is out of the URL; every other filter stays in it.** `PipelineUrlState` has no
   `search` field any more, so `writePipelineUrl` cannot write one and `readPipelineUrl` ignores `q`.
   Statuses and `?view=` are unchanged, so a link still reproduces the filters.
2. **The term lives in `lib/stores/pipeline-search-store.ts`**, a Zustand store (the repo's
   client-state idiom) persisted to **`sessionStorage`, never `localStorage`**. Every storage access is
   inside a try/catch through a small `StateStorage` wrapper; when storage refuses, the search keeps
   working in memory and only loses the refresh. The store skips hydration and the dashboard rehydrates
   it on mount, so the server's empty render and the first client render agree. The list request waits
   for that read, so a refresh never renders the unsearched list first.
3. **A link that still carries `?q=` is stripped, not obeyed.** Bookmarks and pasted links from before
   this ticket: the dashboard replaces the URL with the same filters minus `q`, and does not apply the
   term. Obeying it would keep the name in the history entry being viewed.
4. **Sign-out clears it.** The tab outlives a sign-out, so the store subscribes to the auth store and
   clears itself (memory and storage) when the signed-in user goes away or changes. Without this, the
   next person to sign in on that tab would open the pipeline already searching the last person's
   borrower. There are three sign-out paths (`auth-provider.tsx`, `api/client.ts`, `api/auth.ts`); a
   subscription covers all three without touching them.
5. **"All files" and "Clear the filters" clear the search too**, as they did when the search was in
   the URL they navigated away from.

## Saved views: they can store a search term, and now it stays out of the URL

`SavedViewFilters` is `{ statuses, search: string | null }`, so a view **can** store a term, and
`SavedViews` wrote it into each view's link as `?q=`. Removing the search box's URL write alone would
have left every view with a stored term still putting a name in the URL.

Now:

- A view's link carries its statuses and `?view=<id>` only.
- **Clicking a view** applies its term to the store before navigating.
- **Arriving at a view any other way** (the back button, a pasted `?view=` link, a refresh after the
  stored view changed) is handled by the dashboard: when the URL's view is not the one the stored
  search belongs to, it looks the view up in the saved-views list (the same query the context column
  already makes, so no extra request) and applies that view's own term. The term comes from the
  server's copy of the view, never from the URL.
- **A refresh on the same view keeps what was typed on top of it**, because the stored view id still
  matches.
- **A view that cannot be found** (deleted, or the list failed) applies no term rather than keeping the
  previous one.

Found while checking: no screen creates or edits a saved view (`useSavedViews` is the only hook called
from a component), so nothing captures a search into a new view. Views reach the database through the
API directly. If a "save this view" screen is ever built, it must read the search from the store, not
from the URL, where it no longer is.

A pasted `?view=` link opened by a colleague applies that view's stored term for them. That is the
view's definition, which they can already read in the context column, not the sender's typed search,
so it discloses nothing the link did not.

## Tests

`app/(protected)/dashboard/dashboard-search.test.tsx` renders the real `DashboardPage`, records every
URL the page gives the router and every search the page asks the list endpoint for, and asserts the
term is in none of the URLs:

| Case | Asserted |
|---|---|
| Typing | the list is searched; no URL has the term; sessionStorage has it |
| Refresh in the same tab | the box and the request have the term; no request ran without it first; no URL has it |
| Link opened in a new tab (empty sessionStorage) | filters apply, no search |
| Saved view with a stored term | the term is applied from the view; no URL has it |
| Term typed on top of a view, then refresh | kept; no URL has it |
| Link from before LP-933 with `?q=` | URL replaced with `?status=draft` only; term not applied |
| Clear the filters | search cleared; no URL has the term |
| sessionStorage throws on every access | search still works; no URL has it |
| Sign-out | store and sessionStorage no longer hold the term |

**The URL assertion is live, not vacuous.** The legacy-link case is its positive control (the page
must call `router.replace`, and the test reads the call back). And a mutation that puts only the old
write back (`router.replace` with `?q=` after the term is committed) fails the five typing cases on
exactly `expected '/dashboard?q=Ellis' not to contain 'Ellis'`. Against HEAD's `page.tsx` and
`view-url.ts` 8 of the 9 fail.

`components/dashboard/saved-views.test.tsx` gains two: a view with a stored term links to exactly
`/dashboard?status=in_conditions&view=v1` and applies the term on click; "All files" clears it.
`lib/loan-files/view-url.test.ts` now asserts `q` is not read, is dropped when a link is rewritten,
and is recognised for stripping; `isFiltered` counts the search passed to it.

`dashboard-paging.test.tsx` needed two mock changes and no assertion changes: the page now calls
`useSavedViews`, and its auth-store mock needed the store's `subscribe`.

## Not measured

- **Behaviour in a real browser.** Everything above is jsdom. Two things only a browser settles: how
  "Open link in new tab" treats sessionStorage (current browsers give a `noopener` tab a fresh one,
  which is the case this relies on), and that **Duplicate Tab** copies sessionStorage by design, so a
  duplicated tab keeps the search. The second is the browser's behaviour and acceptable (the tab is
  the same person's), but it is a way the term outlives the original tab.
## Review (of `4c58e6a7`)

**One finding, demonstrated rather than argued: the sign-out clear does not survive a reload, so the
property this ticket exists to establish has a hole.** The URL work itself is sound — `?q=` is gone at
the type level, and I could not find a path that puts the term back.

### The finding: a tab reloaded after a sign-out it did not witness keeps the previous user's term

`auth-store.ts` holds the user IN MEMORY only — its own docstring says the token "vanishes on a full
page reload", after which AuthProvider's silent refresh re-establishes the session. So on every
reload `user` starts at `null`. The subscription clears only when `previous.user !== null`, which is
a transition **this JS context witnessed**. A reload is a new context, and `null -> someone` is not a
change it fires on.

So: tab X has a search; the sign-out happens somewhere tab X cannot see it — another tab, a session
expiry, or simply the tab being reloaded while signed out; the next person signs in; tab X rehydrates
its sessionStorage and applies the previous user's borrower name for them. That is verbatim the case
the store's docstring says it prevents: *"the next person to sign in on that tab would open the
pipeline already searching the last person's borrower."*

Reproduced against the real `DashboardPage`, in this ticket's own harness: seed the tab's
sessionStorage as user A's search, reset the in-memory store the way `refresh()` does, let the auth
store go from `null` to a DIFFERENT user, render. Asserting the claimed property fails with

```
AssertionError: expected 'Ellis' to be '' // Object.is equality
```

The same-tab sign-out path, which their test covers, does work — the guard fires there.

**The fix, and the decision inside it.** Stamp the persisted entry with the user id it was typed
under, and once the signed-in user is known keep the term only if the ids match. The wrinkle worth
settling at the same time: on a real reload the dashboard mounts while `isInitializing` is still
true and `user` is `null`, so the comparison cannot run at rehydration — it has to run when the user
arrives. And because the list request is gated on `hydrated` alone, it can fire once with the
previous user's term before that moment. Both close together if the gate becomes "hydrated AND we
know who is signed in" rather than "hydrated", which is why this is entangled with question 1 below.
Not applied here: it changes the persisted shape and the gating design, which belong to the builder.

### The four questions

1. **`enabled: hydrated` is right as far as it goes.** It removes the unsearched first render, and
   "no request ran without it first" is the assertion that pins it rather than prose claiming it. The
   gap is the one above: `hydrated` says the term has been read, not that it belongs to the person
   now signed in.
2. **"A view that cannot be found applies no term" is the right choice**, for the reason given — a
   leftover term would filter a view its owner never set up that way, and the alternative (keep the
   previous search) silently attributes one person's typing to a named, shared object. Waiting for
   the list (`if (!views && !isError) return`) and treating an error as "no term" both fail toward
   showing more rows rather than fewer, which is the safe direction for a filter.
3. **The module-level subscription is the right mechanism, and its costs are the ones named.** It
   covers all three sign-out paths without touching any of them, which is worth more than the tidiness
   of an explicit unsubscribe on a singleton that lives as long as the tab. Two notes: it runs at
   import, so it also executes when the client tree is imported during SSR — harmless, because nothing
   mutates auth on the server, but it is a side effect at import time rather than at mount. And the
   test cost is real but small and now paid: a mocked auth store must offer `subscribe`.
4. **The Duplicate Tab caveat is stated correctly.** Duplicating a tab copies sessionStorage by
   design, and a tab opened from a link gets a fresh one. Both are browser behaviour, correctly
   described as unmeasured here.

### Also measured

- **The URL layer cannot carry the term by construction, not merely by convention.**
  `PipelineUrlState` has no `search` field, so `writePipelineUrl` has nothing to write and a
  regression would have to add the field back; `readPipelineUrl` ignores `q`, and `carriesSearchTerm`
  exists only so the dashboard can strip it.
- **The full frontend suite is 2048 passed, 0 failed** on this tree — including
  `conditions-screens.test.tsx`'s stranded case, which this ticket records as failing. It did not
  reproduce here, which supports the diagnosis rather than undermining it: a test whose fixture sits
  exactly on the threshold passes or fails with the clock, so an intermittent result is the symptom.

## After the review

- **The finding is fixed in `1e2d97c1`**, as the review proposed. The persisted entry carries the
  `userId` it was set under; `adopt(userId)` discards a term that is not the signed-in user's (and an
  entry from before the fix, which has no stamp); the dashboard's `useTrustedPipelineSearch` trusts the
  stored term only once it is hydrated AND the user is known AND the stamp matches. Until then the box
  is empty and the list request is disabled. Two tests emulate a real reload (the auth store reset
  without a witnessed sign-out): a different user gets no term and no request with it; the same user
  keeps it. Setting the gate back to `hydrated` alone fails the first. The review verified the fix.
- **One correction to "Also measured" above, made by the reviewer afterwards:** the stranded
  `conditions-screens.test.tsx` case is not intermittent at file scope. Four runs of that file failed
  four times; it passed in a whole-suite run. See the follow-up in
  [`phase4.5-progress.md`](../phases/phase4.5-progress.md).
