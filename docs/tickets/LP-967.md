## What LP-967 is

In the plan panel, each condition's "What you need to do" becomes **the plan, step by step**: a numbered
timeline per task, from now until the lender clears the condition. Every step says who does it:
- **we**: the app prepares or checks something;
- **you**: the processor;
- **someone else**: the app waits on them;
- **the lender**.

Each task keeps its Next step select (LP-966), and the select now visibly changes the path.

At the top, **"Your first moves"** says what the processor does first across the round, for example
"Review and send 2 emails, then upload 1 invoice". Beside it: who the round then waits on, and what is
already handled.

**Built only from what exists. No new server behaviour, and every step must be true of the server
today:**

| Task's step | Its path |
|---|---|
| Ask the borrower / a third party | We draft the email to {recipient} when you confirm → You review and send it → {recipient} replies; the reply arrives in the file's inbox → You accept the attachment and link it to this task (we suggest the match) → We check it against what was asked |
| I'll do it | You {library task, or "do it"} → You upload it here, or mark the task done → We check what you upload |
| Already in the file | We found {document, page} on the file → You check it's the right one |
| Lender is doing it | {Lender} does it → You watch for it to clear |
| Information only | Nothing to do |
| The condition's own push back / ask the underwriter | We draft a note to the underwriter when you confirm → You review and send it → The underwriter answers |

A task that waits on another condition starts with "Waits on {code}". Every path ends with "When every
task is done the condition is ready, and goes in the package for the lender" → "{Lender} clears it". The
condition-level step "information only" ends without the package.

## Done when

- **The path:** every condition's opened view shows the path for each task, plus the shared ending, with
  who-colours and a legend.
- **The select changes it:** changing a task's Next step changes its path at once (the cache updates, as
  LP-966).
- **"Your first moves"** counts emails to send (the plan's drafts), tasks for you, and what is already in
  the file. It is derived, never typed.
- **Every step's wording is checked against the server,** and each server fact it depends on is named in
  the module docstring.
- **Tests:** the path for each step type, the waits-on step, a condition-level question, the first-moves
  summary, and a mutation pass.
- **Peer review.**

## What was built

**`lib/conditions/plan-path.ts`** (pure functions):
- `taskPath(item)`: one task's steps, from its next step, as in the table above.
- `ownStepPath(option)`: the condition's own step.
- `endingPath(condition)`: ready → package → the lender clears it; nothing for information only.
- `firstMoves(rows, drafts)`: what she does first.

Every server fact a step leans on is named in the module docstring. Two were checked against the code for
this ticket: marking a draft sent moves the condition to Waiting (`condition_drafts.mark_sent`), and
uploading straight to a task exists (`useUploadToItem`, LP-953).

**The plan panel:**
- The opened condition's right column is now **"The plan, step by step"**. Each task card keeps its Next
  step select, ⓘ and meaning line, and shows its path under them. The library's "should be" moved from the
  card's "Done when you have" into the check step's detail.
- A dashed **"Then"** block shows the shared ending.
- **"Your first moves"**, "Then we wait on" and "Already in the file" replace the pills.
- **A legend** names the four kinds of step; each dot and label is coloured by who does it.
- The "need you to check" warning stays.

**Not in LP-967, on purpose:** drafts before confirm. The ask path says "We draft the email … when you

## Review (of `75a76fd1`)

**Four findings, all fixed here. The module's own docstring lists the server facts each step leans on,
which is the right shape and is why this review could be a verification rather than a hunt — three of the
four are steps whose leaned-on fact says something narrower than the step does. The fourth is a rule that
got copied, and the LP-966 review is why it could be.**

### Finding 1 — two rules for "will confirm make this ready?", on one screen

`firstMoves` put a condition in "Already in the file" when every live item's **option** was
`already_in_file`. The confirm summary on the same screen asks the same question through `willBeReady`,
which keys on each item's **status**, because that is what `condition_plan.ready_because` does. So a
condition whose items are all "Already in the file" with one document still being read — a hand link is
`RECEIVED` until `check_link` passes it (LP-953) — appeared in the "Already in the file" box and was
left out of "Mark … ready", two boxes on one screen disagreeing about one condition. The builder
predicted this exactly.

**It is partly the LP-966 review's fault, which is worth saying plainly.** That review found the same
option-vs-status confusion in the confirm summary and fixed it with a function left module-private in the
panel. Nothing then stopped the next ticket writing a second copy of the rule, and LP-967 wrote one. The
fix for a rule that exists twice is not to correct the second copy.

**Fixed:** `willBeReady` moves into `plan-path.ts`, exported, with its history in the docstring, and both
the confirm summary and `firstMoves` call it. One rule, one place, and the next screen that needs it has
somewhere to get it.

### Finding 2 — a task's path began at the beginning however far along the task was

The path is "every step from **now** until the lender clears it", and `taskPath` always started at "We
draft the email to … when you confirm the plan". For a task whose ask had already gone out, or whose
document was already linked, the card described work behind her as though it were ahead.

The statuses say where it is: `requested` means the ask went (`mark_sent`), `received` means a document
is linked but has not passed its checks, `done` means finished. **Fixed:** `alreadyBehind` trims the
steps that have happened, and a finished task says so rather than showing an empty card. Two details
worth having got right:

- the **waits-on prefix survives the trim**, because "Starts once 1228 is done" is not one of the task's
  own steps;
- **"Already in the file" is deliberately not trimmed.** `build_plan` sets that option and `DONE`
  together, so a blanket "done means nothing left" would have emptied the one card she most wants to
  read ("We found HR Loan Processing invoice, page 1 on the file"). That asymmetry is in the code as a
  comment and in the test as a control.

### Finding 3 — "waiting on {who}" promised this task's recipient

Each ask step said *"Once you mark it sent, the condition shows as waiting on {this task's recipient}."*
`_wait_on_first_asked` opens by denying exactly that:

> NOT "WHOEVER WAS EMAILED FIRST". 0132's disclosure is the LO's and its wire instructions the title
> company's; S3-12 reads "Waiting on LO" because the disclosure comes first, whichever email she
> happened to mark sent first.

So on a condition that asks two people, the step is right for whichever ask comes first in item order
and wrong for the other — and 0132, the server's own example, is a condition on these very sheets.

**Fixed:** the step now says what the rule is — "waiting on Title / escrow. If it asks more than one
person, it waits on whichever of them it asks first." `taskPath` sees only the item, so it cannot know
how many askers the condition has; naming the rule is true in both cases and costs no signature change.

### Finding 4 — the ending promised a package two kinds of condition never reach that way

`endingPath` returned "When every task is done, the condition is ready and goes in the package" for
everything except `information_only`. `ready_because` returns None for **any** condition-level step that
is not "Already in the file" or "I'll do it" — so for "Lender is doing it", a push-back, a question to
the underwriter, or a condition-level ask, finishing the tasks does not make the condition Ready and it
never reaches `_goes_in`'s package by that route. Only one of the five was excluded.

**Fixed:** those keep the half that is true — the lender answers and she records it — and lose the
readiness claim. `information_only` still returns nothing at all.

### Checked and not findings

- **"Review and send N emails" is right even when a draft covers several conditions.** `plan.drafts` is
  the server's own list, one entry per recipient with its codes, so counting entries counts emails. This
  was the builder's other suspicion and it does not hold.
- **Nothing is filed by itself, so "you accept the attachment" is true.** `accept_attachment` has one
  caller in the whole tree, the route at `api/inbound.py:237` — no task, no automatic path. I checked
  because `inbound_triage.py:567` quotes "confidence gates auto-acceptance, never visibility", which
  reads like an auto-accept until you see it is about whether UNROUTED messages are visible.
- **"We suggest the document that matches" is exactly right**, and I would know: LP-958's
  `link_candidates` sorts matches first and never filters, so the dialog suggests without hiding the
  rest — which is what this sentence claims and no more.
- **Checks do run on an upload to a task**, not only on a link: `documents.py:365` resolves the
  `condition_item_id` target before anything is stored, and LP-953's door 6 links the upload and checks
  it once the document has been read. "We check what you upload" holds, with the nuance that it happens
  after the read rather than at upload.
- **`_goes_in` covers the prior-to-funding case the step implies** — its docstring says a READY
  prior-to-funding condition goes in too, and only the not-yet-ready ones wait for the closing package —
  and excludes `info_only`, which is why `endingPath`'s `information_only` branch was right before this
  review and still is.
- **The item-level question branch is correct, and cites the review that found it.** A task set to
  `ask_underwriter` or `push_back` says "This step does nothing on a single task", which is the honest
  companion to LP-966's narrowing: the select no longer offers them, but an item already holding one
  still renders.
- **Accessibility is right** (their focus area 4). The timeline is a real `<ol>`/`<li>`; the dots and the
  connecting lines are `aria-hidden`; and every step renders `whoLabel` as text, so the who-colour is
  never the only cue. The legend's swatches are `aria-hidden` beside their own labels.
