### Correction to the previous pass — the ticket contradicted itself about bounces

The earlier version said both of these, four paragraphs apart:

> *"the lookup returns NXDOMAIN and the borrower gets an **immediate bounce**"*
> *"A borrower who replies with their documents attached gets **no bounce and no delivery**"*

**The first is right and the second is wrong.** With no MX and no A record on a name that does not
exist in the zone, the lookup is NXDOMAIN, the sending MTA cannot queue, and it issues a hard NDR
(`5.1.2 / domain not found`) to the borrower straight away. Nothing is silently swallowed today.

That is worth stating precisely because it changes the harm: the borrower is not left wondering, they
are told by their own mail provider that the address their mortgage company gave them does not
exist — which is the shape of the fraud they are warned about on a transaction. `phase4.md` §3 rules
out Route C on that same reasoning.

## Blocker 2 — nothing drains the queue

`poll_queue` exists (`tasks/inbound.py:88-89`) and is registered in `_TASK_MODULES`. It is invoked by
nothing: there is no `beat_schedule`, no `crontab`, no scheduled ECS task, no cron entry anywhere in
`backend/`, `infra/` or `docker-compose.yml`. LP-803's own progress note says it plainly — *"Poller
written but NOT scheduled"* — and no later ticket picked it up.

So the end state of applying INFRA-1 and publishing DNS is: SES accepts the mail, writes it to S3,
notifies SQS, and it **sits in the queue indefinitely**. Every symptom looks like a DNS or
permissions failure, and every AWS-side check comes back green — `Received` and `PublishSuccess` both
increment.

This is the same class as the defect LP-807's reviewer caught (*"the ingest chain had NO CALLER…
both suites green"*). It survived because a scheduled task is invisible to a test suite.

## Blocker 3 — SES would encrypt the mail so the worker cannot read it

`infra/modules/inbound_mail/main.tf:339` sets `kms_key_arn` inside the `s3_action`. Per AWS, that is
**not** server-side encryption:

> *"Mail is encrypted using the S3 encryption client… You must use the S3 encryption client to
> decrypt emails after retrieval"* — and only the SDK for **Java or Ruby** provides it.
> ([Deliver to S3 bucket action](https://docs.aws.amazon.com/ses/latest/dg/receiving-email-action-s3.html))

The ingest path is Python: `tasks/inbound.py:56` calls `storage.read(key)`, which is
`storage/s3.py:208` — a plain `aioboto3` `get_object` followed by `Body.read()`. **boto3 cannot
decrypt a client-side-encrypted object.** Every message would arrive as an unparseable blob and
`parse_message` would raise on all of them.

The bucket already has SSE-KMS at rest (`main.tf:110`), which is what the design actually wants.
**Recommendation: unset `kms_key_arn` on the `s3_action` and rely on bucket SSE-KMS**, then grant the
worker's task role `kms:Decrypt` on that key.

Flagged rather than fixed here because it is a one-line Terraform change with a real security
argument attached, and it should be made deliberately with the INFRA-1 author.

## Blocker 4 — inbound must not be switched on before the routing defect is fixed

`inbound_routing.py:162` (rung 2, thread matching) selects on `Communication.external_message_id`
with **no `company_id` filter, no `direction` filter and no `deleted_at` filter**, ordered
`sent_at DESC` — which in Postgres sorts NULLs *first*. `inbound_routing.py:597` writes
`external_message_id = message.message_id`, the **sender-written header**, on every inbound row, and
that is currently the column's only populated source because outbound ids require a transport that
does not exist.

Consequence: anyone who has ever been copied on a thread can read a `Message-ID`, plant it on a file
they control, and capture that borrower's next reply — attachments included — at confidence 1.0, on
another company's file.

**This ticket cannot be closed by route 1 while that stands.** Applying the infrastructure is what
turns a latent defect into a live one. Raise it as its own ticket and make it a hard predecessor.

## The routes

### Route 1 — make the inbox real

Now four jobs, not one:

1. Fix rung 2 (blocker 4) — **predecessor, non-negotiable**
2. Unset `kms_key_arn` on the `s3_action`, grant the worker `kms:Decrypt` (blocker 3)
3. Schedule `poll_queue` (blocker 2)
4. Apply INFRA-1/2, publish DNS (blocker 1)

**The staging DNS half is cheaper than the previous pass implied and this should be said:**
`staging.mortgageboss.ai` is already a delegated Route 53 zone this account controls, and a zone is
authoritative for everything beneath it. So `inbox.staging.mortgageboss.ai` is **records inside an
existing zone — no new zone, no registrar step, no NS propagation wait.** Production is the two-phase
registrar dance; staging is not.

#### The sandbox correction stands, and is endorsed

The previous pass was right and the citation is solid: **the SES sandbox restricts sending only.**
Receiving works in sandbox. The documented prerequisites for receiving are three — verify the domain,
publish an MX record, grant resource permissions — and production access is not among them.

One carve-out to add: `services/auto_reply.py` **is** outbound. In sandbox it reaches only verified
addresses, so a borrower acknowledgement would silently not arrive. That is INFRA-3's flag with the
AWS turnaround, not INFRA-1's.

#### Runbook for step 4 — researched 2026-09-09, ordering matters more than the values

**Pre-flight, before any apply.** One active receipt rule set exists per account per region, and
`aws_ses_active_receipt_rule_set` has no safety rails in either direction: creating it **clobbers**
whatever is active region-wide, and destroying it calls `SetActiveReceiptRuleSet(null)`, disabling
**all** inbound mail for the account in that region. The module already declines to create it
(`main.tf:382`) and sets `prevent_destroy` at `:81` — both correct. Check what is active first and
record it:

```bash
aws ses describe-active-receipt-rule-set --region us-east-1 \
  | tee /tmp/ses-active-before-$(date +%F).json
aws ses list-receipt-rule-sets --region us-east-1
```

**Two ordering traps.**

1. **The bucket policy must exist before the receipt rule.** SES test-writes to the bucket at
   *rule-creation* time, not first-mail time, so a missing policy fails the apply with
   `InvalidS3Configuration: Could not write to bucket` — which reads like a Terraform bug and is not.
   Because the documented policy conditions on the rule's own `aws:SourceArn`, this is a genuine
   circular dependency: break it by building the rule ARN as a string and adding explicit
   `depends_on` from the rule to the bucket and KMS policies.
2. **Publish the MX record last**, after the rule set is active. Mail arriving before then is
   rejected in the SMTP conversation and the sender gets a hard bounce.

**The permission that is easy to miss.** The base policy AWS shows grants `kms:GenerateDataKey*`
only; a following sentence adds that **`kms:Decrypt` is also required when the bucket has
server-side encryption enabled.** Ours does. Verify both are present for principal
`ses.amazonaws.com` with `AWS:SourceAccount` + `AWS:SourceArn` conditions — `aws:Referer` is the
legacy pattern and INFRA-1's review already corrected it.

**The failure mode to alarm on before pointing real mail at this.** Permission errors are
**accept-then-drop**, not bounce: SES returns `250` to the sender, then fails the action and retries
for **four hours** before giving up. The sender believes it was delivered and it is gone. The only
signal is CloudWatch `PublishFailure` and `PublishExpired` on the rule — there is no S3 log for a
write that never happened. The four-hour window is also the recovery: fix the policy inside it and
SES redelivers.

**Verification, in order.** `dig +trace MX inbox.staging.mortgageboss.ai` (the `+trace` catches an
orphan child zone, the most common Route 53 mistake here) → `get-identity-verification-attributes`
reads `Success` → `describe-receipt-rule` shows `Enabled: true` and a recipient condition naming the
domain → send with `swaks --server inbound-smtp.us-east-1.amazonaws.com --port 25` to isolate SES
from external deliverability → then a real message from Gmail → then check `Received`,
`PublishSuccess`, the S3 object, the SQS depth, **and that the poller consumed it**.

**Two more worth knowing.** Recipient matching is on the SMTP envelope (`RCPT TO`), not the `To:`
header — which is exactly how a Bcc'd message matches, and is what makes the Bcc claim routable at
all. And a rule with **no** recipient condition accepts mail for *every* verified identity in the
account; confirm ours has one.

**Timings.** Identity verification 1–15 minutes typical (45-minute Terraform default; **72 hours and
it hard-fails and must be restarted**). Rule-set activation is instantaneous. MX propagation minutes
at TTL 300. Realistically **45–75 minutes** for step 4 once steps 1–3 are done.

**Cost.** $0.10/1,000 messages received plus $0.09/1,000 256 KB chunks. At pilot volume, low single
dollars a month. Max message to S3 is **40 MB** — the real ceiling for scanned loan documents.

**Rollback** is disabling the single rule (`update-receipt-rule` with `Enabled: false`), not
`terraform destroy`, which would take the region's inbound mail down.

## Done when

Three claims, each needing its own answer.

1. **The template sentence.** Either mail to a file's inbox address arrives, routes, **and is
   consumed by the poller** — demonstrated end to end on staging with a real message — or the
   address is not in the words a borrower reads.
2. **The Bcc instruction.** Either a processor who Bccs that address finds the copy filed against the
   loan **as a sent copy, not as an inbound message from themselves** — demonstrated by doing it — or
   the panel stops telling them it will be.
3. **The Reply-To label.** Either something sets that header on a message that actually goes out, or
   the label stops claiming a reply address the product never writes. **Route 1 does not satisfy
   this one.**

Predecessors that gate closure by route 1: the rung-2 fix (blocker 4), the `kms_key_arn` decision
(blocker 3), and a scheduled poller (blocker 2).

Standing constraint: `outbound_mail_enabled` and `dmarc_report_address` are coupled — INFRA-3's
review made that fail at plan time — so turning outbound on requires naming a DMARC mailbox someone
reads.

## Not in scope, worth its own ticket

claim 3 cannot be closed by infrastructure — but it is written down nowhere except implicitly in a
Terraform flag and an empty transport registry. Whether the pilot transmits mail is a product
decision that belongs in `decisions.md`.
