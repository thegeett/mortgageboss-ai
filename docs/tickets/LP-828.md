## The question, answered plainly

> *"we are saying send to lf-99lDjO7cX24WT_A6@inbox.staging.mortgageboss.ai, are we ready to receive
> email flow with this email route? All infrastructure has been created? We did not update any DNS
> change yet."*

**No. Nothing is created, and mail to that address goes nowhere.**

Measured:

- `infra/envs/staging/terraform.tfvars:402` — `inbound_mail_enabled = false`
- `infra/envs/staging/terraform.tfvars:414` — `outbound_mail_enabled = false`
- Both modules are `count = var.*_enabled ? 1 : 0`, so with the flags false the SES receipt rule
  set, the receiving S3 bucket, the SQS queue and the MX records **do not exist as resources**.
- INFRA-1, INFRA-2 and INFRA-3 are all `REVIEWED (HUMAN_GATED)` in `phase4-progress.md`:
  written and validated, `terraform plan` never run, nothing applied. No AWS credentials in the
  build environment.
- The SES sandbox exit has not been requested. **This does not block the inbox** — see the
  correction below.

**Confirmed against live DNS, 2026-09-07**, which is stronger evidence than the flag:

| name | MX | A |
|---|---|---|
| `inbox.staging.mortgageboss.ai` | none | **none** |
| `staging.mortgageboss.ai` | none | 44.210.219.193, 98.85.34.247 (the app) |
| `mortgageboss.ai` | mx1/mx2.hostinger.com | none |

The inbox domain does not exist in DNS at all — no MX to deliver to and no A record to fall back
to. So a borrower's mail server does not queue the message and does not silently drop it: the
lookup returns NXDOMAIN and the borrower gets an **immediate bounce** saying the address does not
exist.

That is better than silent loss and worse than it sounds. The borrower has just been told, by their
own mail provider, that the address the mortgage company gave them is not real — which is the exact
shape of the fraud they are warned about on a mortgage transaction. `phase4.md` §3 rules out Route C
on that same reasoning: an unfamiliar sender on a mortgage file reads as phishing.

So the address in the draft is well-formed, correctly scoped to the file, and connected to nothing.
A borrower who replies with their documents attached gets no bounce and no delivery — the mail is
refused at the MX lookup, because there is no MX record.

## The address is promised in THREE places, not one

Found while answering a follow-up question, and it is the reason this ticket is scoped to the claim
rather than to the template line. `outbound-draft-panel.tsx` shows the same address twice more, as
its own labelled facts:

* **Reply-To** — `draft.reply_to`, presented as where the borrower's reply will go.
* **Bcc this address** — `draft.suggested_bcc`, with the sentence *"so the sent copy is filed
  against this loan"*.

The Bcc line is the strongest claim of the three: it tells a processor that blind-copying that
address files their sent message against the loan file. It does not, and will not until inbound mail
is applied. A processor who follows the instruction gets no error — the Bcc simply vanishes.

**The Reply-To line is wrong for a second, independent reason, and it is worse than one path.**
`mailtoUrl` (`lib/api/communications.ts:117`) builds `mailto:` with `subject`, `body` and `bcc` —
and **no reply-to**. But that is not one path out of several.

**Nothing in this product transmits mail.** Grep for `send_raw_email`, `send_email(`, `sesv2`,
`smtplib` or `ReplyToAddresses` across `backend/app/` returns nothing, and `send_draft`'s own
docstring says it plainly: *"Record that ``draft_id`` was sent, and start the clock on everything it
asked for."* The Send button records an outbound event and moves needs to REQUESTED. The panel's
three actions — **Send**, **Open in mail client**, **Copy message** — all end with the processor
sending from their own mailbox.

So `reply_to` is composed at `email_send.py:150`, displayed in the panel at line 119, and **never
travels on any path**. The label is not false on one route and true on another; there is no route on
which it is true. It is a header that nothing writes.

That matters for route 1 below: **applying the inbound infrastructure does not make the Reply-To
line true.** It gives the address somewhere to land, which fixes the Bcc claim and the template
sentence. The Reply-To label stays false until either something transmits mail with that header, or
the label stops claiming to be one.

So fixing the template alone leaves two instructions on screen that are still false, and one of them
is aimed at the processor rather than the borrower. Whatever route is taken below, it has to cover
all three.

## This is the standing M1 sequencing escalation, and it just became concrete

`phase4-progress.md` has carried it since LP-817's review, as the first item in *"must be decided
before the pilot mails a real borrower"*:

> *"M1 can send an email advertising an inbox that receives nothing until M3."*

It was a sequencing risk on paper. A processor has now read the sentence on a real draft and asked
the question, which is the same discovery a borrower would make with their documents.

## What has to happen, and it is a person's call

Three routes, and they are not equivalent:

1. **Apply the infrastructure.** Run `terraform plan` and apply INFRA-1/2/3 for staging, set
   `inbound_mail_enabled = true`, publish the MX and DKIM records, request the SES sandbox exit.
   Then the sentence is true. This is the real fix and it is measured in days, not minutes, because
   the sandbox exit is a request to AWS with a turnaround.
2. **Remove the address line from the template until the infrastructure exists.** A new template
   version (ADR-401), so v2's words stay attached to what v2 sent. The email still works: the
   borrower replies with attachments, which the processor reads in their own mailbox.
3. **Ship knowing it, and accept that a borrower may send documents into a void.** Recorded as an
   option because it is the one that happens by default if nobody decides.

### Correction: the SES sandbox is not on route 1's critical path

An earlier version of this ticket listed the sandbox exit as evidence the inbox does not work, and
priced route 1 in days because of it. **The sandbox restricts SENDING, not receiving.** AWS states
it directly: *"While your account is in the sandbox, you can use all of the features of Amazon
SES"*, and the sandbox limits are enumerated entirely in terms of outbound — recipients must be
verified, 200 messages per 24 hours, 1 per second.

The documented prerequisites for email RECEIVING are three, and none of them is production access:

1. verify the domain with SES by publishing DNS records,
2. publish an MX record permitting SES to receive — `10 inbound-smtp.us-east-1.amazonaws.com`,
3. grant SES permission to the AWS resources the receipt-rule actions touch (S3, SQS).

`infra/modules/inbound_mail/main.tf` already does all three: the verification TXT at :48, the MX at
:69 with exactly that value, and the resource policies below. **The module is not waiting on AWS.**
It is waiting on someone running `terraform plan` with credentials.

The repo's own Terraform never made this mistake — the sandbox lead time appears once, in the
INFRA-3 **outbound** block at `infra/envs/staging/main.tf:747`, correctly scoped to sending. Only
this ticket conflated the two.

**What that changes.** Route 1 splits into two jobs of very different size:

* **Receiving borrower documents** — apply INFRA-1/2, publish DNS, wait for propagation. Hours, not
  days, and no AWS turnaround. This is what makes the template sentence and the Bcc line true.
* **Sending anything back** — the auto-reply path (`services/auto_reply.py`) is outbound, so in
  sandbox it reaches only verified addresses. A borrower acknowledgement would silently not arrive.
  This is the part with the AWS lead time, and it is INFRA-3's flag, not INFRA-1's.

So the sequencing question the pilot actually faces is narrower than the ticket claimed: the inbox
can be made real without waiting on Amazon. Whether the system may write back to a borrower is a
separate gate on a separate flag.

## Done when

Three claims are on screen and each needs its own answer. The earlier version of this list covered
only the first, which is why it read as smaller than it is.

1. **The template sentence.** Either mail to a file's inbox address arrives and routes, demonstrated
   end to end on staging with a real message — or the address is not in the words a borrower reads.
   Not both, and no version of the template promises a route that does not exist.
2. **The Bcc instruction.** Either a processor who Bccs that address finds the copy filed against
   the loan file, demonstrated by doing it — or the panel stops telling them it will be.
3. **The Reply-To label.** Either something sets that header on a message that actually goes out, or
   the label does not claim a reply address the product never writes. **Route 1 does not satisfy
   this one**, so it cannot be closed by applying infrastructure.

Plus the constraint that was already here and still holds: `outbound_mail_enabled` and
`dmarc_report_address` are coupled (INFRA-3's review made that fail at plan time), so turning
outbound on cannot happen without naming a DMARC mailbox.

## Not in scope, and worth its own ticket

**That the product composes mail and never sends it.** `send_draft` records an outbound event; the
processor sends from their own mailbox by mailto, copy-paste, or by hand. That is a legitimate
design for a pilot and it is not what this ticket is about — but it is the reason claim 3 cannot be
closed by infrastructure, and nothing in `phase4.md` or the build plan states it as a decision.
Whether the pilot transmits mail is a product call that should be written down somewhere other than
inside a Terraform flag.
