## The question, answered plainly

> *"we are saying send to lf-99lDjO7cX24WT_A6@inbox.staging.mortgageboss.ai, are we ready to receive
> email flow with this email route? All infrastructure has been created? We did not update any DNS
> change yet."*

**No. Nothing is created, and mail to that address goes nowhere.**

Measured:

- `infra/envs/staging/terraform.tfvars:402` — `inbound_mail_enabled = false`
- `infra/envs/staging/terraform.tfvars:414` — `outbound_mail_enabled = false`
- Both modules are `count = var.*_enabled ? 1 : 0`, so with the flags false the SES receipt rule
  set, the receiving S3 bucket, the SQS queue and the MX records **do not exist as resources**.
- INFRA-1, INFRA-2 and INFRA-3 are all `REVIEWED (HUMAN_GATED)` in `phase4-progress.md`:
  written and validated, `terraform plan` never run, nothing applied. No AWS credentials in the
  build environment.
- The SES sandbox exit has not been requested. Until it is, SES will not deliver to unverified
  recipients regardless of DNS.

So the address in the draft is well-formed, correctly scoped to the file, and connected to nothing.
A borrower who replies with their documents attached gets no bounce and no delivery — the mail is
refused at the MX lookup, because there is no MX record.

## The address is promised in THREE places, not one

Found while answering a follow-up question, and it is the reason this ticket is scoped to the claim
rather than to the template line. `outbound-draft-panel.tsx` shows the same address twice more, as
its own labelled facts:

* **Reply-To** — `draft.reply_to`, presented as where the borrower's reply will go.
* **Bcc this address** — `draft.suggested_bcc`, with the sentence *"so the sent copy is filed
  against this loan"*.

The Bcc line is the strongest claim of the three: it tells a processor that blind-copying that
address files their sent message against the loan file. It does not, and will not until inbound mail
is applied. A processor who follows the instruction gets no error — the Bcc simply vanishes.

So fixing the template alone leaves two instructions on screen that are still false, and one of them
is aimed at the processor rather than the borrower. Whatever route is taken below, it has to cover
all three.

## This is the standing M1 sequencing escalation, and it just became concrete

`phase4-progress.md` has carried it since LP-817's review, as the first item in *"must be decided
before the pilot mails a real borrower"*:

> *"M1 can send an email advertising an inbox that receives nothing until M3."*

It was a sequencing risk on paper. A processor has now read the sentence on a real draft and asked
the question, which is the same discovery a borrower would make with their documents.

## What has to happen, and it is a person's call

Three routes, and they are not equivalent:

1. **Apply the infrastructure.** Run `terraform plan` and apply INFRA-1/2/3 for staging, set
   `inbound_mail_enabled = true`, publish the MX and DKIM records, request the SES sandbox exit.
   Then the sentence is true. This is the real fix and it is measured in days, not minutes, because
   the sandbox exit is a request to AWS with a turnaround.
2. **Remove the address line from the template until the infrastructure exists.** A new template
   version (ADR-401), so v2's words stay attached to what v2 sent. The email still works: the
   borrower replies with attachments, which the processor reads in their own mailbox.
3. **Ship knowing it, and accept that a borrower may send documents into a void.** Recorded as an
   option because it is the one that happens by default if nobody decides.

**Route 2 is what I would do today, with route 1 in parallel.** The address is the only part of the
message that is currently false, and it is one line.

## Done when

- Either mail to a file's inbox address arrives and routes, demonstrated end to end on staging with
  a real message — or the address is not in the words a borrower reads.
- The two are not both true, and no version of the template promises a route that does not exist.
- `outbound_mail_enabled` and `dmarc_report_address` are still coupled (INFRA-3's review made that
  fail at plan time), so turning outbound on cannot happen without naming a DMARC mailbox.

## For the reviewer

There is no code to review. The check is whether the claim in the template and the state of the
infrastructure agree — and the way to establish that is to send a message to a file address and see
whether it arrives, not to read the Terraform.
