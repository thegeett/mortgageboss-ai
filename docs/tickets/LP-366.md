# LP-366 — AS-1 reads income via the `loan_tag` operand, not the gated DTI calc

## WHAT THIS IS

A **one-line spec change** that ends a live, auto-shipping rule's permanent silence. AS-1 (the
large-deposit sourcing sweep) had **never evaluated a single deposit** on any real file: it read income
*through* the DTI calculator, which fail-closes on `housing.insurance_monthly` — an input AS-1 never uses,
and an orphaned tag with no producer (LP-367). The calc gated → the threshold operand resolved to `None` →
**every money-in deposit was an unresolved `couldnt_check` regardless of size**. LP-366-A built the
`loan_tag` operand (a per-deposit rule reading a loan-level tag); this walks through it.

The lesson: **a rule must read the narrowest source that answers its own question. Reading income through a
calculator inherited every input that calculator needs** — including one that has no producer at all.

## THE CHANGE (data only)

`app/verification/rules/specs/AS-1.yaml`, the `threshold` operand:

```
FROM: {product: [{reference: large_deposit_threshold_pct}, {calc: [dti, gross_monthly_income]}]}
TO:   {product: [{reference: large_deposit_threshold_pct}, {loan_tag: dti.qualifying_income_monthly}]}
```

**That is the whole production change.** No engine Python (LP-366-A removed the need). AS-1 references the
DTI calculator nowhere anymore (asserted).

## ACCEPTANCE CRITERIA (met)

- AS-1's `threshold` reads `{loan_tag: dti.qualifying_income_monthly}`; it references the DTI calc **nowhere**.
- **Fail-closed preserved:** income absent/unknown → the operand resolves to `None` → `couldnt_check` **with
  a reason**. Never `0` (a `0` threshold would fire on every deposit — the inverse failure). Tested both ways.
- **The headline, asserted:** with the DTI calc GATED (the real orphaned-insurance state), AS-1 **still
  evaluates** — the gated calc is now irrelevant to it.
- Every other live rule (OC-2, ID-1..ID-9, IN-2) **identical**; the `calc` operand **untouched** (AS-4 keeps
  it — its reserves→PITI→insurance dependency is legitimate); `ACTIVE_RULE_IDS` unchanged.
- `ruff` + `mypy app/` clean; **full backend suite 2333 passed**.

## PHASE 0 — VERIFICATION (the make-or-break check)

**Does `dti.qualifying_income_monthly` MATERIALIZE on a real run, or is it one of LP-365's 95 degradations?**
If it were degraded, AS-1 would move laterally from "couldnt_check because the calc is gated" to
"couldnt_check because the tag didn't materialize" — not a fix.

**Verified via the ACTUAL production pipeline on the real persisted LF-6T3N snapshot** (`load_declarations`
→ `produce_derived_tags`): it materializes to **`28168.80`**, `produced_by=derived`, `subject=loan`. It is
**NOT** one of the 95 degradations — those were **AI-stage** failures (`income.qualifying_monthly` is mode
`ai`); `dti.qualifying_income_monthly` is a **deterministic `derived` recipe** reading already-persisted
MISMO stated-income facts. **The fix is real, not lateral.** The value matches LP-365's reported
`gross_monthly_income` ($28,168.80) exactly — one income figure, produced once, shared by AS-1 and the DTI.

- **`type`:** the operand defaults to `decimal` — correct for a dollar income figure (`_COERCERS["decimal"]`).
- **Threshold semantics unchanged:** 50% of monthly qualifying income; `reference_values` untouched, so
  `priya_validated: false` stays. **PRIYA ITEM: AS-1's 50% is NOT validated** (LP-323-AS-A: no Assets
  threshold is). Unchanged by this ticket.
- **F2 stays off AS-1's path:** AS-1's income is the MISMO **stated 1003 total** (`source='parsed'`), NOT the
  AI `income.qualifying_monthly` tag (which did not materialize). LP-343's F2 warned an over-stated
  *qualifying* figure would raise the 50% threshold and let a large deposit slip under — that path is not
  taken.

## THE REAL BEFORE / AFTER (DB LF-6T3N)

Measured by a **deterministic replay** on LP-365's persisted 30-doc snapshot: the real Stage-A/B AI txn tags
are reused verbatim (so the only variable is the income read + rule eval), the derived income tag is
materialized, and AS-1 is re-evaluated. This isolates the swap's effect precisely and costs nothing; a fresh
end-to-end AI run would reproduce it modulo AI nondeterminism, and — because materialization now produces the
income tag from MISMO — the reconciler (LP-322) would transition the 15 persisted `couldnt_check` findings to
`satisfied` and keep the 2 `needs_review`.

| outcome | BEFORE (income via gated DTI calc) | AFTER (income via `loan_tag`) |
|---|---|---|
| **couldnt_check** | **15** | **0** |
| **satisfied** | 0 | **15** |
| **needs_review** | 2 | 2 |
| not_applicable (not persisted) | 33 | 33 |

**The threshold now resolves: 50% × $28,168.80 = `$14,084.40`.** AS-1 went from **100% blind** (15
`couldnt_check`) to **evaluating every deposit**.

**0 fired — and that is CORRECT, not a miss.** The report was told to observe, not predict (the ticket
predicted the large deposit would fire). The truth is better:
- The **17 money-in deposits** sort to a max of **$20,000**, then $12,000, then ≤ $5,048.
- The **$20,000** deposit is the only one above threshold — and it is **already sourced**
  (`has_identified_source=yes`, `source_strength=verified`, conf 0.95: a matching debit was found). AS-1
  correctly rules it **satisfied**, not fired. (Verified it is not a coercion bug: a large *unsourced*
  deposit would have fired; this one carries a verified paper trail.)
- Every other money-in deposit is **below $14,084.40** → satisfied.
- The **2 `needs_review`** ($2,000 and $12,000) are gated by a load-bearing tag at **confidence 0.4 below the
  0.5 floor** — a **separate root**, unchanged by this swap, explicitly out of scope (do NOT fix here). Both
  are also sub-threshold, so the confidence gate is the only thing distinguishing them.

So AS-1 now does exactly its job: it evaluates every deposit, clears the sub-threshold noise ($0.07 / $0.16 /
$0.53 / $1.93 → satisfied and invisible), and correctly does not false-fire on a legitimately-sourced large
deposit. The engine was previously suppressing all of this behind `couldnt_check`.

## THE FROZEN FIXTURE + THE EVAL HARNESS

- **`lf6t3n_tagged_snapshot.json`** (the stripped 5-statement frozen artifact) has **no income tags and MISMO
  absent**. On it, `dti.qualifying_income_monthly` cannot materialize → AS-1 there is **still `couldnt_check`**.
  **That is CORRECT and HONEST** — the fixture genuinely lacks income data. **The fixture was NOT edited to
  make AS-1 fire.** (`test_real_file_no_false_fire` asserts 0-fire on this trace, which still holds.)
- **The eval HARNESS (`_build_snapshot`)** is a different thing: it synthesizes a snapshot from an `EvalCase`
  that *carries* `income` (default `10000`). Previously it surfaced that income as a DTI calc. Post-swap AS-1
  reads the loan tag, so the harness now **also** surfaces `case.income` as a MISMO **stated-income line**
  (`borrower.1.income.1.monthly_amount`) — the real, faithful source — and `run_case` now runs the
  **derived-materialization stage** it was previously skipping (production runs it after Stage A/B; Stage A
  rebuilds `by_subject`, so a pre-injected tag would be wiped — the recipe must run *after*). The DTI calc is
  KEPT in the harness for the DTI/AS-4 story. This is not "faking the fixture": the case's income is real
  case data, now represented the way production represents it.

## ASSUMPTIONS / DECISIONS

- **Deterministic replay, not a fresh AI run**, for the before/after — the rigorous instrument for isolating a
  data-only change (the AI stages this ticket does not touch are reused from LP-365). A fresh run would
  reproduce it modulo AI nondeterminism.
- The DTI calc is **kept** in the eval harness (AS-4 and the DTI view still consume it); only AS-1's *read* moved.
- No ADR — **ADR-285** (LP-366-A) already records the operand and the reasoning; this ticket is its data
  consumer. Nothing in the real run contradicts the ADR (the tag materializes as ADR-285 states).
