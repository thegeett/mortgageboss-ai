# LP-837 — A drafts indicator that follows you off the page

- **Status:** Built — awaiting review
- **Date:** 2026-09-07
- **Scope:** `components/file/file-header.tsx`, a drafts popover, the communication route
- **Migration:** none expected
- **Depends on:** [LP-831](LP-831.md) (the modal it deep-links into), [LP-832](LP-832.md) (more than one draft to count)

## What was asked

> *"When user clicks on Request document from any where there should be some badge draft icon with
> count of drafts (or just simple dot saying new items in draft) near top right corner to show this
> has been added, clicking on it shows list of few draft, clicking on idividural draft goes to
> communication page and open that draft pop up. At max show 5 draft and have see more link to
> communication page."*

## What exists and why it is not enough

LP-826 built `DraftBadge` — a count derived from the draft's contents, on the verification screen.
Two limits, and this ticket is both of them:

* **it is on one screen.** A processor requesting documents from the needs list, or from a party
  panel, sees nothing. "From anywhere" is the requirement and one screen is not it;
* **it counts one draft.** It reads `useOutboundDraft`, which returns the file's single open draft.
  After LP-832 there are several, and a badge reading the first one is worse than none.

## Where it goes, and the precedent is already written down

**In the file header, beside the file's other actions — not in the app topbar.** `file-header.tsx`
already argues this for `FileContextDrawer`:

> *"It lives beside the file's other actions rather than in the topbar, because it is about THIS
> file."*

Drafts are per loan file. A global topbar badge would have to answer "whose drafts" on the files
list, the dashboard and the inbound queue, and the honest answer on those screens is "none of
them" — which is a badge that is absent most of the time and therefore not a place anybody looks.
The file header renders on **every** page of a file (`layout.tsx`), so "from anywhere" is satisfied
within the scope the number is true for.

## The count, and what it will actually say

Asked for as "count of drafts". Worth stating what that number does under LP-832: **a new draft per
request** means five requests give **5**, four of them supersets of each other. That is the model
that was chosen deliberately, so the count is honest — but it reads as "five emails waiting" when it
is closer to "one email, requested five times".

Built as asked. Recorded here so that if it reads wrong in use, the fix is known: count the
**documents** outstanding rather than the drafts holding them, which is one line and a different
sentence.

## Deep-linking the modal

"Goes to communication page and open that draft pop up" means the modal has to be openable from a
URL — the popover navigates, and the page opens the right draft on arrival. A query parameter
(`?draft=<id>`) is the mechanism, and it is worth having beyond this ticket: a draft becomes a thing
a processor can link a colleague to, and the modal's open state stops being unreachable component
state.

**LP-831 should build the modal with that in mind** rather than having it retrofitted here.

## Done when

- The indicator is in the file header, on every page of a file, and updates after a request without
  a reload — the same query invalidation LP-809's fix already wires.
- It is **absent, not zero**, when the file has no drafts. A "0" badge is a permanent decoration on
  every file that has never requested anything.
- Clicking it lists at most **5** drafts, newest first, each showing what it is and when it was made.
- **The time comes from `lib/message-time.ts` and is not formatted here.** LP-838 moved this
  requirement into this ticket rather than building for a component that did not exist: a formatter
  call in an unbuilt popover is a function nothing runs. The module is built, has callers, and
  `message-time.test.ts` fails if this surface formats its own — so the rule attaches by
  construction rather than by being remembered.
- Clicking a draft goes to the communication page **and opens that draft's modal**. Landing on the
  page with the modal shut is the failure this is most likely to ship with, and it looks like a
  navigation that worked.
- "See more" goes to the communication page. It appears only when there are more than 5 — a link
  offering more when there is no more is the LP-825 pill again.
- Keyboard: the trigger opens on Enter, the list is arrow-navigable, Escape closes it.

## For the reviewer

Two.

**The deep link is the half that fails quietly.** Navigating to the page is visible; opening the
modal on arrival is a second thing, and if it is missed the processor lands on a list and assumes
they mis-clicked. Assert the modal is open after the navigation, not that the URL changed.

**The count must survive a superseded draft being deleted.** LP-832 leaves that to the processor, so
the number has to come from a query, not from anything cached at request time.

## Built, 2026-09-09

### Where it went, and the precedent was already written down

The file header, beside `FileContextDrawer`, whose own comment argues the case: *"it lives beside the
file's other actions rather than in the topbar, because it is about THIS file."* The header renders
on every page of a file (`layout.tsx`), so "from anywhere" holds wherever the number is true.

A topbar badge would have to answer "whose drafts" on the files list and the dashboard, where the
honest answer is none — and a badge absent on most screens is not a place anybody looks.

### LP-826's `DraftBadge` is deleted, not left beside it

Both of its limits were this ticket: it was on the verification screen alone, and it counted **one**
draft — it read `useOutboundDraft`, which returns the file's newest, and LP-832 made several the
ordinary state. A badge reading the first of many is worse than none, so leaving it as a second
opinion on the same page would have been two numbers disagreeing.

### The list is the server's word for "drafts"

`TimelineFilter.DRAFTS` decides what counts, asked for over the wire rather than filtered here.
LP-812 put that filter on the server so one word has one definition; deciding again on the client is
how the header and the mailbox start disagreeing about what a file contains.

**It includes QUEUED**, deliberately and not by my choice: *"a queued automatic reply is a message
not yet gone, which is what a processor means by looking at drafts."* So a queued auto-reply would
count. None exist today — `record_auto_reply` still has no caller — and the alternative was a second
definition of the word, which is worse than a number that is occasionally broader than expected.

### A menu, not a bare popover

There is no popover primitive in this repo, and a menu is what this is: a short list of things to go
to. Radix supplies the keyboard behaviour the ticket asked for — Enter opens, arrows move, Escape
closes, focus returns to the trigger. Hand-rolling that is how a control ends up mouse-only.

### The deep link is the half that fails quietly

Navigating is visible; opening the modal on arrival is a second thing, and if it is missed a
processor lands on a list and assumes they mis-clicked. LP-831 built the panel to read `?draft`, so
this ticket only had to carry it — which is the whole reason that was built there rather than
retrofitted here.

### The timestamp requirement, enforced rather than documented

LP-838 moved the popover's timestamp into this ticket because the surface did not exist yet, and its
review then put `file-header.tsx` into the guard's scanned set — so a local date format here **fails
`message-time.test.ts` before a reviewer sees it.** Verified before building in this file: planting a
`toLocaleString()` in the header fails the guard, and did not before.

That is the difference between a requirement in a document and a requirement in a test, in the ticket
whose own subject is that distinction.

### Two things worth a second opinion

**The count is drafts, as asked, and under LP-832 that means supersets.** Five requests give **5**,
four of them subsets of the fifth — it reads as "five emails waiting" when it is closer to "one
email, requested five times". Built as specified; if it reads wrong in use the fix is one line, to
count the documents outstanding rather than the drafts holding them.

**Opening the menu in the test is spelled out** — a pointer-down/up pair rather than a click, because
Radix does not open on `fireEvent.click` alone. `user-event` is not a dependency here and adding one
to open a menu would be a heavier answer than the question.

### The three standing checks

**Tenancy:** the indicator reads the file's own timeline endpoint, `ScopedLoanFile`-gated; nothing
new derived. **Logging:** nothing added. **AI:** none.
