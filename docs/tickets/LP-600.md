# LP-600 — Nine review findings against LP-593…LP-599

All nine were real. Verified each in the code before fixing — two of them turned out to be worse than
reported, and one was proved by an existing test failing when I fixed it.

## 1 (HIGH) — Per-run counts read zero for every historical run

LP-592 grouped findings on `Finding.verification_id`, on the stated reasoning that *"findings DO carry
`verification_id`, so the answer is exact and cannot drift from the findings themselves."* It drifts on
the very next run: `_update_finding` **reassigns** that column for every re-detected finding
(`rule_findings.py:198`) and the retire loop does the same (`:438`). After run 2, essentially all of
run 1's findings point at run 2 — so a run that produced 26 findings the day before rendered as
`—` / "This run produced no findings". My comment asserted the opposite of what reconcile does two
files away.

Fixed by counting from **`finding_events`**, which is append-only and genuinely per-run: each detected
finding gets exactly one event per run carrying `to_outcome`, and `detail->>'run_id'` is the
verification id (the task passes `run_id=run.id, verification_id=run.id` — verified). This fixes the
runs already in the database, with no migration and no denormalised column to keep in step.

## 2 — The count query dropped the two filters the panel applies

The panel's statement is `only_active(...)` plus `origin.in_(_SHOWN_ORIGINS)`; the count query had
neither, so a soft-deleted finding or one of a non-shown origin inflated the badge while being absent
from the tab. Both filters added in the same query as #1.

**No backend test covered this endpoint's counts** — also true, and the reason both bugs shipped. Two
now do.

## 3 — Re-keying would have discarded every dismissal

I had flagged "expect one more churn" and **understated it**. The reviewer's point is the one that
matters: every `signed_off` / `not_an_issue` row would be retained under a key nothing produces again,
while the same finding re-opens beside it **un-dismissed**. That is not churn, it is silently throwing
away processors' decisions — precisely what `finding_key` exists to protect.

Migration `b7c4e91f2d38` recomputes `finding_key` and rewrites `kind` for existing rows, so the
transition is invisible. It carries a **frozen copy** of the derivation, because a migration must keep
meaning the same thing forever and importing app code would let a later refactor rewrite history. The
risk of freezing is drift *before* it runs — which would leave every key mismatched and the bug fully
intact — so a test pins the frozen copy equal to the app's implementation across the real observed
slugs.

## 4 — "Not marked subject" was being read as "another property"

LP-596 and LP-597 both recorded that only a `true` identifies the subject, then both consumers treated
"not true" as "another property" — the same mistake in different clothes.

Working through it, the defect runs deeper than the indicator: **`OwnedPropertyDispositionStatusType`
describes the PROPERTY, not the lien.** A borrower refinancing their home retains it — of course they
do — while the lien is retired at closing. So "marked paid off" + "property Retain" is the *ordinary
refinance*, not a contradiction, unless the row is positively known to be a different property.

Fixed with `_schedule_marks_a_subject`: the indicator is trusted only on a schedule that uses it at
all. Where nothing is marked, `has_other_financed_properties` abstains (`unknown`, which does not match
AS-4's `eq "yes"`, so the rule lands where it was) and the contradiction is not reported.

The reviewer also noted the test *encoded* the ambiguity rather than resolving it. Correct — it
asserted a contradiction from `is_subject: "False"` alone. It now carries a second row that does mark
a subject, and a new test pins the abstention.

## 5 — The MI-1 guard was inert on every purchase

`_loan_ltv_basis_is_appraised` ignored `property.purchase_price`, which is `value_basis`'s denominator
for a purchase (the lesser of price and appraised value). A purchase stating a price with no appraisal
produced a perfectly good `loan.ltv_percent` while the tag returned `unknown`, so MI-1's `eq "no"`
never matched and it went on clearing the insurance requirement off a sales price — the exact failure
the guard was written for, from the other direction.

**An existing test proved it.** `test_ltv_at_or_below_80_is_satisfied` runs
`build_mi1_low_ltv_snapshot` — a purchase, a price, and no documents — and asserted `SATISFIED`. It
failed the moment the guard started working, because it encoded the bug. Flipped, with the reasoning
recorded, plus a companion test that a file *with* appraisals still clears at 75% so the guard is
discriminating rather than merely strict.

## 6 — A retained property with no stated lien balance vanished

`_other_financed` filtered out any row whose `lien_upb` was absent *or* zero, which made the
aggregate's own "states no lien balance" abstention **dead code** and let AS-4 assert "the application
lists no other retained financed property" about data it never saw. Absent and zero are different
answers: a zero balance is still excluded (owned, not financed), an absent one is kept and the
aggregate abstains.

## 7 — `_EDITORIALISING` matched substrings

"the application **in**correctly lists the property as a second home" contains "correctly", so a
finding reporting a genuine error was rejected, retried, rejected again, and shipped the raw template.
Same for "improperly". The negated forms are exactly what a finding *should* say. Word boundaries now.

## 8 — The document count widened the hallucination allow-list

`unsupported_numbers` derives its allowed set from `summary.to_json()`, and LP-597 injected
`documents_on_file` into that JSON — so on a file with 24 documents the token "24" was licensed
anywhere in the output. Subtracted from the allow-list rather than removed from the payload, since the
model genuinely needs to see it.

## 9 — The backfill's guard could not see its own inserts

`async_session_maker` is built with `autoflush=False`, so the `count()` did not see pending
`StatedOwnedProperty` rows. A loan file with two `MismoImport` rows would have its schedule written
twice — doubling `other_financed_count` and the aggregate, which is the "confident wrong number" the
guard exists to prevent, arriving through the guard itself. `await db.flush()` before the counters.
