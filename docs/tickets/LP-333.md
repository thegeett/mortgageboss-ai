# LP-333 — Income activation: diagnose and close the materialization gaps

Eleven Income rules were authored + evaluated + correct but INERT — their tags didn't materialize where
the rules read them. This is a DIAGNOSIS-FIRST ticket: the primary deliverable is the bucket table below
(exactly why each rule is inert); the build phases closed only what is genuinely closable.

## The discipline that drove every decision

**A rule that uniformly couldnt_checks is a FAILURE, not a shortcut** — it fills Tab 1 with noise and
trains processors to ignore the tab where real blockers live. And **no rule ships an uncalibrated AI tag
into a trusted verdict** (calibration is keyless — no income AI tag has ever been scored against real
content). Both disciplines forced the headline outcome: IN-2 activated (safe), IN-1 de-activated.

## What was closed (Phases 1–3)

**The data-flow fix (bucket B, generic — the linchpin).** `materialize_tags` now runs **parsed → ai →
derived**, and feeds the derived producer a snapshot carrying the freshly-built parsed + AI tags. Before,
`produce_derived_tags(decl, snapshot)` got the ORIGINAL snapshot, so every aggregate-derived income tag
read an empty tags layer and abstained — the reason all four derived income rules (IN-1/2/3/4) couldnt_checked
live. `id.app_required_fields_present` (reads raw MISMO, not tags) is unaffected — the asserted canary.

**IN-2 ACTIVATED.** `income.pay_date` (parsed) → `income.days_since_most_recent_pay` (derived, loan) →
IN-2. Verified end-to-end through `evaluate_rules` with **zero AI groups run**: fires for a stale stub
(56 days > the 30-day window), satisfied for a recent one, couldnt_check with no pay date. No uncalibrated
AI; loan-level recency is correct (no per-borrower masking).

**Two bucket-A spec fixes** (`IN-8` → `voe`, `IN-9` → `employment_offer_letter`) so their applicability
matches the classifier's actual `DOCUMENT_TYPE_INDICATORS`. Without this they were `not_applicable` on
every file — a silent inertness that would have survived any future wiring.

## IN-1 — de-activated, honestly (correcting LP-332)

LP-332 added IN-1 to `ACTIVE_RULE_IDS`, but the diagnosis proved it **couldnt_checks on every real file**
(the data-flow gap). Even fixed, activating it needs its uncalibrated `income.documented_monthly` wired
into a deterministic **fraud** verdict. Per the discipline, **IN-1 is de-activated**: the PIN #1 mechanism
(the per-borrower shortfall recipe, LP-332) is proven and unchanged — only the live activation is deferred
until (a) `income.documented_monthly` is calibrated and (b) its recipe dependency is declared/wired. This
is not a regression of PIN #1's fix; it is not shipping a fraud verdict on an unvalidated tag.

## IN-3 — deliberately left INERT

IN-3 carries PIN #1's SAME latent masking (a loan-level YTD aggregate masks one borrower's inflated YTD).
Activating it would re-ship the bug LP-332 just fixed. It stays inert; its per-borrower re-key (mirroring
IN-1's recipe) + calibration + wiring is a follow-on.

## The added AI-call cost per run

**Zero** for what activated — IN-2 runs no AI group (parsed → derived). Activating any bucket-B AI rule
later (IN-5/8/10) would add its `income_*` group: one bounded structuring call per rich file per group

## Uncalibrated-AI honesty

No activated rule ships an uncalibrated AI tag. IN-2 is parsed-only. Every deferred rule's blocker is
recorded, and **the top follow-on is live calibration of the income AI tags** (`income.documented_monthly`,
`income.employer_normalized`, the stability tags) against real (GLBA-safe) content before any of their
rules activate. Until then they stay inert — the correct state.

## New generalization gap (reported, not patched)

**Undeclared recipe dependencies.** `_required_ai_groups` traces a rule's DIRECT load-bearing tags, so a
DERIVED load-bearing tag's feeding AI groups are never marked required — the orchestrator won't run them.
A derived tag should DECLARE its `depends_on` feeding tags so the wiring is generic (and a completeness
check can verify a recipe reads only declared inputs). A bounded follow-on that unblocks IN-1/3/5/10's
live wiring.
