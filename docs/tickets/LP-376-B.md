# LP-376-B — Fix the ratification badge, the category, and ID-8's message

## WHAT THIS TICKET IS

The first time a human looked at the LP-376 tabs, three things were misrepresenting the engine — correctness
bugs, not cosmetics. **Phase 0 proved all three are BACKEND: LP-376's frontend rendering is correct; it was
fed wrong data. Zero frontend change.**

## ACCEPTANCE CRITERIA

- The ratification badge shows ONLY on AI-judgment verdicts (OC-2, ID-8 on LF-6T3N), never on deterministic/
  consistency rules or on a judgment rule that never judged (ID-9 couldnt_check).
- A finding's message states the VERDICT; the AI's reasoning lives in the provenance, not the message.
- Categories are each rule's OWN family from the gate of record — ID-8 ≠ "Assets", IN-2 ≠ "Assets".
- Both directions tested; no outcome/rule/spec/tag/gate change beyond the flag + message; suites green.

## PHASE 0 — THE DIAGNOSIS (payload = the gate of record)

**Bug 1 — the ratification badge: BACKEND.** `RuleFindingPublic.ratification_pending` (LP-375) was
`bool(details.gated_pending_signoff)`. But `gated_pending_signoff = not priya_validated` — it means "the
rule's THRESHOLDS await the domain expert's sign-off," which the payload confirms is `true` for nearly every
rule (AS-1 *satisfied*, ID-1, etc.), with `priya_validated=false` everywhere. **It has nothing to do with AI
ratification.** The real engine flag `RuleEvaluation.ratification_pending` (judgment.py, consistency fuzzy) is
set correctly BUT (a) it is **never persisted** (`_details` omits it) and (b) it is **over-set** —
judgment.py's `_result` hardcodes it `True` even for a judgment rule's couldnt_check/gate-fail, where no AI
verdict was ever made. **The bigger finding the ticket suspected: the armor's own flag is muddy, not just its
display.**

**Bug 2 — ID-8's message: BACKEND. The outcome is CORRECT.** Payload: `evaluation_outcome=needs_review`
(correct — a judgment always awaits ratification, even when the AI's answer is "eligible"); `message` = the
AI's raw reasoning + a suffix (`"Tag id.citizenship confirms 'USCitizen'… — 'yes' is an AI judgment and must
be ratified by a human"`), composed by `judgment.py:_verdict_reasoning` as `{ai_reasoning} — …`. ID-8's
`load_bearing_tags` reasoning was empty (parsed tags), so the AI reasoning lived ONLY in the message.

**Bug 3 — categories: BACKEND, two taxonomies merged (as the ticket predicted).** Rule findings' persisted
`category` is the legacy `FindingCategory` enum (`income/assets/credit/property/documentation/cross_source` —
**no Identity, no Occupancy**). The rule's own category (`rule_kinds.csv`/spec: ID-8=Identity, IN-2=Income,
OC-2=Occupancy) is coerced into it with `default=ASSETS` → ID-8→`assets`, IN-2→`assets`.

## WHAT WAS BUILT (all backend)

**Bug 1 — `schemas/verification.py`.** `RuleFindingPublic.ratification_pending` now derives from the gate of
record: `_ratification_pending(finding, spec)` = a JUDGMENT rule (`spec.judgment is not None`) that reached an
actual verdict (`open`/`satisfied`/`needs_review`). A couldnt_check/gate-fail never invoked the AI → `False`;
a deterministic/consistency rule → `False`. **Verified on the real run** — `ratification_pending=True` only for
OC-2 + ID-8; `False` for ID-9's couldnt_check and everything else. The engine flag is left untouched (10+
tests + the eval harness consume it) — this is a read-path derivation, not an armor change.

**Bug 2 — `rule_engine/judgment.py`.** `_verdict_reasoning` → `_verdict_message`: the message now STATES the
verdict (`"the AI judged 'yes' — an AI verdict a human must ratify (it never auto-ships)"`), never the raw
reasoning. The AI's reasoning is appended to the finding's provenance as a load-bearing tag (the judgment
verdict `id.residency_eligible = 'yes'` carrying the reasoning), which the LP-376 provenance card already
renders. **The outcome is unchanged** (still `needs_review`).

**Bug 3 — `schemas/verification.py`.** `RuleFindingPublic.category` now = the spec's category
(`_rule_category` → `load_rule_spec(rule_id).category`), the gate of record — not the coerced legacy enum.
**Verified**: ID-8→Identity, IN-2→Income, OC-2→Occupancy, ID-*→Identity, AS-1→Assets.

## VERIFICATION (a real governed run — reported, not predicted)

Re-ran the governed pass on LF-6T3N with the real model (run `96f55e9d`):
- **ID-8 message** = `"the AI judged 'yes' — an AI verdict a human must ratify (it never auto-ships)"` (clean).
- **ID-8 provenance** now carries `id.residency_eligible = 'yes'` with the reasoning `"Tag id.citizenship
  confirms 'USCitizen'…"`.
- **Ratification badge** (via `RuleFindingPublic`): `True` only for OC-2 + ID-8; `False` for ID-9's
  couldnt_check, ID-2/3/4 (consistency), AS-1 (deterministic), IN-2, ID-1/6.
- **Categories**: ID-8 Identity, IN-2 Income, OC-2 Occupancy — no more "Assets".

## ASSUMPTIONS / DECISIONS

- **ID-8's `needs_review` is CORRECT — not touched.** An AI judgment always awaits human ratification even
  when the answer is "eligible" — that is the armor (LP-319/327) working, not a bug. Only the message was
  wrong.
- **The two taxonomies were being merged, and are now separated.** The governed rule findings carry their own
  family (Identity/Income/Occupancy/Assets/…) from `rule_kinds.csv`; they no longer inherit the legacy AI
  sweep's `FindingCategory` (which has no Identity/Occupancy). This matches LP-375's structural quarantine —
  the two systems are different things down to their vocabularies. (ADR-293.)
- **Why `gated_pending_signoff` was `true` everywhere:** it is `not priya_validated`, and no live rule is
  Priya-validated yet — so it flags "thresholds await domain sign-off," a real but DIFFERENT concept from AI
  ratification. Reusing it as the badge conflated the two. The armor's true per-finding
  `ratification_pending` flag is also over-set (True on judgment couldnt_check) and unpersisted — a deeper
  cleanup than this display fix; noted below.

## KNOWN LIMITATION (reported, a follow-up — not this ticket)

The read-path derivation marks a JUDGMENT rule's verdict. A **fuzzy-CONSISTENCY** AI verdict (e.g. an ID-4
address disagreement the AI judged) is **under-marked** — it would need the engine's per-finding
`ratification_pending` PERSISTED (and de-muddied so a judgment couldnt_check reads `False`). It does not arise
on today's live files (no consistency rule reached its fuzzy AI leg on LF-6T3N), so the display is correct for
the current live set; the persisted-flag cleanup is a separate ticket.

## WHAT LP-376-A STILL MUST FIX (unchanged, next)

The couldnt_check reason text (`"applicability tag 'document.document_type' is unknown"`) still names the tag,
not the missing document + the action — the bigger reason-text rewrite (LP-376-A's scope), out of this ticket.
