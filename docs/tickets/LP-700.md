# LP-700 — not every extracted field can be pointed at on the document

- **Ticket:** LP-700
- **Status:** Open — researched, not started
- **Date:** 2026-09-06
- **Reported by:** the user, from the running app
- **Scope:** Backend — `ai/extraction/*`, `ai/prompts/extraction/*`, `services/field_boxes.py`; Frontend — the reviewer's box overlay

## The report

> Not all extracted fields are mapped on the document at document page? Why? It should map,
> also we should know the location on document as we extracted.

## Why it happens, and it is by construction

**The model is never given, and never returns, a coordinate.**

A document reaches Claude as a base64 `document` (PDF) or `image` block —
`ai/client.py::build_document_block`. Every extraction prompt then asks for two things
per field (`ai/prompts/extraction/*.txt`):

```
- "page"    (integer)  the 1-based page the value appears on
- "snippet" (string)   the verbatim text you read the value from
```

There is no geometry anywhere in that contract. The highlight rectangles the reviewer
draws (LP-UI-031) are **derived after the fact**: `services/field_boxes.py` opens the PDF
with PyMuPDF and calls `page.search_for(snippet)`. A box exists only when that text search
succeeds.

## What that costs, measured

Over the 105 stored PDFs / 752 valued fields at the time of LP-UI-031:

| | | |
|---|---|---|
| 548 | 72.9% | snippet found on the cited page |
| 32 | 4.3% | cite a page **the document does not have** |
| 89 | 11.8% | snippet absent from the text layer entirely |
| 83 | 11.0% | the document is a scan — **no text layer at all** |

So roughly **one field in four cannot be pointed at**, and the reasons are three different
problems wearing one symptom.

Note the 4.3%: not one of those is an off-by-one. Every one names a page beyond the
document's length — the model inventing a page number. The reviewer already says so
rather than silently showing a better page, and the ledger still prints `p.N`
unvalidated (AMENDMENTS A25).

## Why the obvious fixes do not work

**Asking the model for a bounding box.** It cannot know one. It is shown a rendered
document, not a coordinate space, and a fabricated rectangle is worse than none — it
points confidently at the wrong words.

**Fuzzy-matching the snippet.** Helps the 11.8% a little (reflowed whitespace, ligatures,
a table cell split across spans) and nothing at all for the 11.0% with no text.

**There is no OCR in this codebase.** Confirmed: no OCR module, no dependency, nowhere.
For a scan there is simply no text to search.

## The direction worth taking

**Give the model spans instead of asking it for prose.** PyMuPDF already returns every
word with its rectangle (`page.get_text("words")`). Extract those first, hand the model a
numbered span list alongside the document, and ask it to cite a **span id** rather than a
verbatim string. The mapping then becomes a dictionary lookup, exact by construction — no
search, no near-miss, and a fabricated page number becomes impossible because the span
carries its own page.

That is a real change to every extraction prompt and to the `{value, page, snippet}`
contract in `ai/extraction/shape.py`, so it wants its own decision. It also raises the
cost per call (the span list is tokens) and needs a fallback for the case the model cites
no span at all.

**Scans need OCR before any of that helps.** 11% of stored documents, and every field on
them. That is a separate build with its own dependency choice.

## Acceptance

- [ ] A decision recorded on span-citation vs. snippet-search, with the token cost measured
      rather than estimated
- [ ] Whatever ships, the coverage figure is **re-measured** over the current corpus, not
      carried over from LP-UI-031
- [ ] A field with no derivable location still says so on the row — never a silent absence,
      and never a box pointing at the wrong words
- [ ] The `p.N` a ledger prints is validated against the document's page count (A25's open
      half)
