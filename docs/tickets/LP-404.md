# LP-404 — AS-6 three-tag rule: Priya's surface-don't-reject ruling (the finale)

## What this ticket is

The finale of the owner-match thread (LP-390-8a → LP-403). The three tags —
`owner_matches_borrower` (the confidence), `holder_name_variance` (the difference),
`non_borrower_co_holder` (an extra holder) — are built and calibrated. This changes AS-6 from a
single-tag rule (`owner_matches=no` → fired, else satisfied) into the **first MULTI-TAG rule**, combining
all three into Priya's three outcomes: a certain match counts silently; a flag-for-evidence (plausible
match OR a non-borrower co-holder) surfaces to needs-attention **while the document counts**; a genuine
non-match is an open finding.

## Phase 0 — the argument (D1–D5)

**D1 — do all three tags reach AS-6's subject? YES — not structurally dead.** The three tags are declared
`subject: document` (`tag_production.yaml`) and produced together by the `stmt_facts` group; AS-6 is
`subject_enumeration: per_document` keyed on `content_id`. Same subject → every tag materializes onto
every statement AS-6 evaluates. (The ID-5/IN-12 structural-death class does not apply.)

**D2 — the outcome for the middle row is `needs_review`.** Priya's "surface WHILE THE DOCUMENT COUNTS" is
NOT a normal open finding (`fired` is AS-6's exclude verdict — a third-party account that does not count),
and NOT `couldnt_check` (a data gap — "we couldn't read it"). `needs_review` routes a subject to human
review WITHOUT excluding it: a real judgment (a plausible match / a non-borrower co-holder) the processor
confirms, with the statement staying in the borrower's assets pending confirmation. It is NOT
`PENDING_AUTOMATION` (that is for a BLOCKED/uncalibrated rule — AS-6's tags ARE calibrated, so AS-6 runs
and reaches a real verdict).

**D3 — the rule-as-data shape: the existing DSL, with two deliberate choices.** No new combinator. The
three-tag combination is expressed as ORDERED outcomes (first match wins) with single-tag `when_tags`:
`owner=no`→fired, `owner=unknown`→needs_review, `co_holder=yes`→needs_review, `owner=yes`→satisfied,
default→couldnt_check. Two constraints forced the shape:
  1. **Route on the CONFIDENCE (owner_matches) + the co-holder — NOT on the variance value.** The ticket's
     proposed table listed `holder_name_variance ∈ {middle_absent, …}` as an independent needs_review
     trigger. That would FALSE-FLAG the benign dropped middle — which is exactly the 5 real LF-6T3N
     goldens (`owner=yes, variance=middle_absent`). So the variance NAMES the reason (it is in the
     finding's load-bearing provenance) but does not independently trigger. **Consequence: N1 (a
     conflicting middle, `owner=no`) → fired** (an open finding), NOT needs-attention as the ticket's
     Phase-2 example said — because Priya's `owner_matches` label for N1 is `no` (ADR-320: a conflicting
     middle = a likely different person). Her label + the FP-harm requirement (the gate of record) beat
     the ticket text.
  2. **Gate on `holder_name_variance`, NOT `owner_matches`.** The generic fail-closed gate (LP-315) treats
     ANY `unknown` load-bearing tag as `couldnt_check`. But Priya's `owner=unknown` is a FLAG value that
     must reach `needs_review`. So AS-6 gates on variance (the "was the holder name read & compared"
     presence check — absent/`unknown` → couldnt_check) and routes owner_matches through the outcomes.
     (`gated_tags` cannot be empty — schema `min_length=1` — so a non-owner gated tag was required.)

**D4 — the reason strings (plain language, LP-376-C).** Each surfaced verdict carries a processor-facing
reason (below). The SPECIFIC (the co-holder's name, the variance kind) lives in the finding's load-bearing
tag provenance (the co_holder / variance tag reasoning), not interpolated into the static reason — a
rule-as-data limitation (the reasoning template interpolates only numeric operands), accepted rather than
adding a bespoke combinator.

**D5 — ratify interaction: no double-surfacing, because AS-6 is INERT.** This ticket changes the RULE, not
the activation. AS-6's bar is `validated:false` (LP-397 proposed `ships:auto`, ratify-only recommended
until a negative case exists). Its ships/ratify mode is an activation-time concern; the `needs_review`
middle branch routes to human review regardless of ships mode. Nothing double-surfaces at the rule level.

## The three-outcome table, as implemented

| condition (per statement) | verdict | document | reason string (plain language) |
|---|---|---|---|
| `owner=yes`, `co_holder=no` | **satisfied** | counts silently | "the account holder resolves to a borrower on the loan" |
| `owner=unknown` | **needs_review** | **counts**, surfaced | "…plausibly matches a borrower but the match is not certain (for example a nickname or a possible former surname) — confirm … the statement still counts…" |
| `owner=yes`, `co_holder=yes` | **needs_review** | **counts**, surfaced | "…a joint account with an additional holder who is not a borrower … confirm … the statement still counts…" |
| `owner=no` | **fired** | OPEN finding, does not count | "…does not resolve to a borrower … a third-party account (for example a trust, an LLC, or an unrelated person)…" |
| holder facts absent / `unknown` | **couldnt_check** | — | "…could not be determined — the account-holder facts were incomplete" (or the gate's absent-tag reason) |
