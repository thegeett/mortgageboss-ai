# LP-338 — fix the coverage function: file capacity vs pipeline yield (and replace the stripped fixture)

## WHAT THIS IS

A fix. LP-337's coverage function reported `id.*` / `income.*` / `asset.*` as **"0 — UNMEASURABLE"** on
LF-6T3N and concluded *"`txn.*` is the calibration ceiling; an n≥20 rate for other families needs varied
real files that don't exist in the repo yet."* **That reasoning rested on a bad number**, and it had begun
to propagate — the plan briefly treated acquiring synthetic files as *the* blocker standing between the
project and ~15 working rules. This ticket finds the bug, replaces the stripped fixture, and corrects the
record. **It changes no rule/tag/engine behavior — it MEASURES.**

## THE BUG — capacity conflated with pipeline yield

LP-337's `worksheet.py` hardcoded a static `COVERAGE` tuple of **only** the `txn.*` family and a static
`UNMEASURABLE_ON_LF6T3N` list asserting `id.*`/`income.*`/`asset.*` = 0. `build_worksheet` iterated **only
`doc.transactions`**. So the 20 non-txn declared AI tags were **never enumerated from their declared
subjects** — the function reported *what the wired pipeline happened to yield on that fixture* and **labelled
it the file's inherent capacity**, then drew a false conclusion from it. Two distinct facts were conflated:

- **FILE CAPACITY** — how many instances the SNAPSHOT could support for the tag's DECLARED subject. The
  labeling ceiling. Independent of wiring / `ACTIVE_RULE_IDS`.
- **PIPELINE YIELD** — how many the wired pipeline produces today. A wiring fact, not a file fact.

## PHASE 0 VERDICT — (c) BOTH

- **(a) the function is wrong.** `worksheet.py` (LP-337): `COVERAGE` static/txn-only (line 73);
  `build_worksheet` iterates only transactions (line 200); `UNMEASURABLE_ON_LF6T3N` hardcoded (line 137). It
  would report 0 for `id.*`/`income.*`/`asset.*` **regardless of fixture content**.
- **(b) the fixture is a stripped subset.** The repo's `lf6t3n_tagged_snapshot.json` is literally **5
  bank_statement docs, all `fields` empty, 50 transactions** — not the real ~30-document LF-6T3N. This is
  the LP-321a problem one layer up: the central eval fixture under-represented the real file (**ADR-280**).
- **Verdict: (c) both.** The numbers were 0 because the fixture has no id/income/asset docs (b); and the
  function hardcodes those families as unmeasurable anyway (a). Both are fixed.

## THE FIX — three facts, never conflated

The corrected `compute_capacity()` reports, per AI tag: **capacity** · **pipeline_yield** · **content_empty**
· **status** ∈ {`labelable`, `wiring_gap`, `content_empty`, `no_subject`}. It derives capacity generically
from `load_declarations()` (the declared subject) + a coverage map of document-type applicability (eval
metadata — the architecture keys AI groups by subject only). *Absent ≠ empty ≠ unwired*, now at the coverage
level. Keyless + deterministic (no key), like LP-337's.

## THE NEW FIXTURE — built IN CODE, no committed snapshot JSON (`app/verification/eval/lf6t3n_fixture.py`)

A representative, de-identified, synthetic 30-document snapshot (ADR-280), constructed **deterministically at
call time by `build_lf6t3n_snapshot()`** — NOT a committed snapshot JSON (a deliberate constraint: no
snapshot JSONs are added to the repo). The builder reads the already-committed `lf6t3n_tagged_snapshot.json`
for the **5 bank statements + 50 transactions verbatim** (so `txn.*` subject-ids/labels are stable),
populates their fields, and appends 25 synthetic documents in code. The OLD fixture stays for the frozen
golden-eval trace (unchanged — equivalence). Census: 5 bank_statement · 4 mortgage_statement · 4 pay_stub ·
4 w2 · 4 unknown · 3 investment_account · 2 drivers_license · 2 property_tax_bill · 1 brokerage_statement ·
1 purchase_agreement. The **brokerage_statement + 4 unknown docs are deliberately `fields={}`** (the
content-empty case). Keyless + deterministic (no clock/randomness/API).

## THE WIRING GAPS this exposes (reported, not fixed — LP-333 bucket B)

- **`txn.has_identified_source` / `counterparty` / `source_reference`** — capacity 16, yield 0: they are AI
  vocabulary tags with NO `tag_production.yaml` declaration (produced by the separate Stage-B sourcing pass
  `tag_correlation`, not the generic pipeline). Their scoring needs that separate producer wired in — a
  follow-in, not fixed here.

## THE HONEST CALIBRATION POSITION NOW

- **A BIAS HUNT across `id.*` (n=2) / `income.*` (n=8) / `asset.*` (n=3) is possible on LF-6T3N TODAY** —
  modest n, still a bias hunt (not a rate), but **not zero**. The difference changes the plan: the missing
  files are not the blocker to labeling those families.
- **A real RATE exists only for `txn.*` (n=50)** — on one conventional purchase file.
- **Varied files (FHA / refi / condo / self-employed) are still needed for RATES on the other families** —
  that part of LP-337 stands; the "n=0 / files don't exist" framing does not.
