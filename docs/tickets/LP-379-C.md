# LP-379-C — Add the source document to each calibration worksheet row

## What this ticket is

A worksheet row's `subject_id` is a content-id (`txncb49a70b58c386c4`) and its context is
`date/amount/direction/description` — but it never says **which document** the row came from. To verify a
label, the labeler had to hunt every bank statement for that date+amount; across multiple statements × 2
borrowers, that is a lookup per row. This adds a `source_document` column carrying the document's **real
filename — the same `original_filename` the Document tab shows** (`BofA checking April.pdf`), so the labeler
opens it directly. **Worksheet legibility only — no tag, golden, producer, or rule change.**

## Acceptance criteria

- Every row names its source document with the **real `original_filename`** (what the Document tab shows) —
  never a hash.
- Reuses LP-377-B's `resolve_subject_label` + its `original_filename` mechanism — no second resolver.
- Purely additive: row counts unchanged, every filled golden preserved, generation deterministic + keyless.
- `ACTIVE_RULE_IDS` unchanged; full suite green.

## Phase 0 — report

- **The document name is `original_filename`** (Document model → the Document tab → `DocumentPublic`). The
  governed finding path already resolves it: `document_filenames_by_content_id(db, loan_file)` maps
  `content_id → original_filename`, fed to `resolve_subject_label(document_filenames=…)`
  (`api/verification.py`). LP-379-C reuses exactly this.
- **Reachable?** A transaction is nested under its `DocumentEntry` (`doc.transactions`), so
  `transaction → parent document → content_id` is a pure snapshot traversal. The transaction parents are the
  bank statements, whose `doc`-prefixed content-ids **match the DB**, so their real filenames resolve.
- **The fixture gap:** the worksheet is generated from `build_lf6t3n_snapshot` (offline, no DB). Its 5 bank
  statements share content-ids with the DB (real names resolvable); the other 25 documents are synthetic with
  made-up content-ids that don't. So the real filenames are **wired into the fixture** as a committed
  `content_id → original_filename` map (`LF6T3N_DOCUMENT_FILENAMES`), read from the DB LF-6T3N — the same
  mirror-the-DB approach as LP-379-B.
- **PII / de-identification (decision for Geet — chosen):** the DB filenames carry real names
  (`Akash Pay stub 1.pdf`, `DL Akash Patel.pdf`), while the fixture's field VALUES are de-identified
  (Jordan/Taylor/Acme). Presented the fork; **Geet chose the real DB filenames** so the worksheet matches the
  Document tab a labeler actually uses. The consequence — real filenames alongside de-identified context — is
  deliberate: the labeler locates the document by its real tab name; the row's context is a stand-in.

## Phase 1 — what was added

A `source_document` column on every row, positioned right after `document_type`, carrying the real filename:

- **transaction row** → its parent bank statement's real filename (`BofA checking April.pdf`,
  `BofA savings May.pdf`, …). The 5 statements a labeler had to hunt across are now named per row.
- **document row** → that document's real filename (`DL Akash Patel.pdf`, `Akash Pay stub 1.pdf`,
  `Wells Brokerage April.pdf`).
- **borrower row** (income_stability, which aggregates several documents) → the borrower's attributed
  **income-document filenames**, semicolon-joined (`Akash Pay stub 1.pdf; Akash W2 BofA 2024.pdf;
  Akash W2 BofA 2025.pdf; Akash pay stub 2.pdf`) — exactly the files to open to judge the trend.

**Resolution reuses LP-377-B:** `resolve_subject_label` routes the `doc`-prefixed bank-statement keys through
its `document_filenames` map; the fixture's unprefixed synthetic ids are supplemented from the **same map**
(no branch added to the resolver). The transaction→parent-document step is a snapshot traversal. The real map
(`LF6T3N_DOCUMENT_FILENAMES`) **overrides** a field-derived descriptor fallback, so a document not in the map
still resolves to something legible — **never a hash**. The map is threaded through
`build_worksheet(…, document_filenames=…)` / `write_worksheets(…, document_filenames=…)`; without it the
generator stays generic (descriptor fallback).

**Labels preserved:** `write_worksheets` still merges by the stable `(tag_id, subject_id)` key, so the added
column reorders nothing and drops no golden.

## Phase 1 — the filename map (mirrors the DB LF-6T3N)

`LF6T3N_DOCUMENT_FILENAMES` (in the fixture) maps each fixture content-id to the real DB `original_filename`.
The 5 bank statements key by their DB-matching content-ids; the synthetic documents map by borrower + document
type + order (e.g. `dl1 → DL Akash Patel.pdf`, `ps1 → Akash Pay stub 1.pdf`, `w1 (2025) → Akash W2 BofA
2025.pdf`, `inv1 → Wells Brokerage April.pdf`). Row counts: mechanical 70 → 70 (goldens all preserved),
judgment 146 → 146; the `source_document` column added to both, every value a real `.pdf` (or a
semicolon-list of them for borrower rows), zero hashes.

## Phase 2 — tests

`tests/verification/eval/test_worksheet_source_document_lp379c.py` (7): every row has a non-hash source; a
transaction names its **parent bank statement's real filename** (a `.pdf` in the DB bank-file set, not a
deposit label, not the txn hash); a document names its real filename (`DL Akash Patel.pdf`); a borrower row
lists its real income-document filenames; the real map **overrides** the field-descriptor fallback; the column
is additive (present in both files, row counts unchanged, a filled golden survives regeneration); generation
deterministic + keyless; `ACTIVE_RULE_IDS` unchanged. Existing worksheet suites (LP-337/338, LP-379-A/B) stay
green. Full backend suite green.

## Assumptions & decisions

- **Real DB filenames, per Geet's choice** — the worksheet matches the Document tab a labeler uses, over
  keeping the committed artifact fully de-identified. Field VALUES remain de-identified; only the filenames
  (and thus `source_document`) are the real ones.
- **Reused `resolve_subject_label` + `original_filename`**, the exact governed-path mechanism; added no branch
  to the resolver. The `content_id → original_filename` map is wired into the fixture (mirroring the DB, as in
  LP-379-B) because the offline generator has no DB.
- **The synthetic→DB filename mapping is by borrower + type + order** — a defensible correspondence for the
  de-identified fixture; the bank statements resolve exactly (content-ids match the DB).
- **Borrower rows list their income documents** rather than a single filename, because income_stability is a
  multi-document judgment — the source is every file the labeler opens for the trend.
- **This changes the worksheet's LEGIBILITY, not any tag or golden.**

## ADR

None — worksheet legibility only. The de-identification decision (real filenames alongside de-identified
context) was surfaced to Geet and chosen by him; it is recorded here rather than as an ADR.
