# LP-990 — Deliver GuardDuty scan results to the encrypted queue

- **Ticket:** LP-990, the fix for the gap LP-989 found ("The scan-results gap").
- **Status:** applied to staging (account `058190633983`, us-east-1) on 2026-10-21, late evening US
  Eastern, and proven with one real email.

## What and why

GuardDuty scans each inbound email and tags the S3 object. The EventBridge rule
`mbai-staging-inbound-scan-results` should also copy the result onto the `mbai-staging-scan-results`
queue. In LP-989 the rule matched the event and **failed to deliver it**: MatchedEvents 1,
FailedInvocations 1.

**Cause.** The queue is encrypted with the shared CMK, and the key policy did not name
`events.amazonaws.com`. So EventBridge could not get a data key to send the message.

**Why a silent drop is dangerous.**
- **Nothing noticed.** The rule's target had no dead-letter queue, so a failed delivery left no trace.
  The DLQ alarm could not fire because nothing reached the DLQ, and no alarm watched the rule.
- **The plan-health events were lost too.** The same rule carries GuardDuty's "Resource Status"
  plan-health events, which exist to say the scan itself has stopped working. A broken scanner would
  have gone unnoticed in exactly the same way.

## What changed

- **Key policy** (`infra/modules/secrets`):
  - a new variable, `eventbridge_rule_arns`, empty by default;
  - a new statement, `AllowEventBridgeDeliveryToEncryptedQueues`, rendered only when that list is
    non-empty. It allows `events.amazonaws.com` to use `kms:GenerateDataKey*` and `kms:Decrypt`.
  - The statement copies LP-983's SNS statement: `StringEquals` on `AWS:SourceAccount` and
    `AWS:SourceArn`.
- **Staging wiring** (`infra/envs/staging/main.tf`):
  - The rule ARN is built from the rule's name, passed only when receiving and the scan are both on.
    Reading it from `module.inbound_mail` would be a cycle, the same reason as `sns_topic_arns`.
  - The ARN built by name equals the live rule's ARN (`aws events describe-rule`).
- **Failed deliveries are kept** (`infra/modules/inbound_mail/malware_scan.tf`):
  - the rule target now has a `dead_letter_config` pointing at the existing, already-alarmed
    `mbai-staging-scan-results-dlq`;
  - a new queue policy lets `events.amazonaws.com` send to that DLQ, only from the rule (`ArnEquals`
    on `aws:SourceArn`, the same as the main queue's policy);
  - the retry policy is left at its default.
- **New alarm** (`infra/modules/inbound_mail/alarms.tf`): `mbai-staging-scan-results-rule-failed`.
  - It alarms when the rule's `FailedInvocations` Sum is above 0 in a 5-minute period, with missing
    data counted as not breaching.
  - Both its alarm and OK notifications go to `mbai-staging-ops-alerts`.
  - It has the same gating as the scan-results DLQ alarm.

The rule's event pattern and the queues' settings are unchanged. `scan_results` is the only
`aws_cloudwatch_event_target` in `infra/`.

## Lesson

**Every AWS service that writes to a CMK-encrypted queue needs its own key-policy grant.** So far that
is three services. Two were found only when their writes failed; SNS was found by reading the key
policy during the LP-981 review, before anything failed:

- SES (INFRA-1), for the mail bucket;
- SNS (LP-983);
- EventBridge (this ticket).

The send that fails is the service's, not ours, so nothing in our code sees an error. When a new
service is set to write to a queue or bucket encrypted with this key, check the key policy in the same
change. Reading the key policy before the apply is free; finding the gap after
the apply needs a real message and a metric to notice it.
