# LP-551 — `txn.stated_liability_match`: give FR-5 the one input that makes it a finding

FR-5 is built ([LP-547](LP-547.md)), measured (below), and **deliberately not activated**. It matches
every recurring payment to a creditor, and it cannot see the application's disclosed debts — so
activating it as-is puts a list of the borrower's ordinary bills in front of a processor on every file,
forever. This ticket adds the input that turns that list into a finding.

context's tag order REVERSED so a temperature-0 model is measured for consistency rather than

Recorded HERE rather than in `activation_bars.yaml` because the two are coupled: `is_eligible()`
returns true for a `ratify-pending` bar as soon as a `self_consistency_rate` exists, and
`test_activation_gate_lp389` asserts `ACTIVE_RULE_IDS - _BASE_ACTIVE == eligible_rule_ids()`. **Writing
the rate into the bar activates the rule.** There is no measured-but-held state, so the number waits
here until the rule is worth activating.

What it establishes and does not: the plumbing works and every branch is reachable. It establishes
nothing about detecting a real undisclosed debt — the fixtures' author knew the intended answer, which
measures self-consistency, not correctness (ADR-332 / LP-487).

## The vocabulary row

For `docs/snapshot-fact-tags.xlsx`, from which `fact_tags.csv` is generated:

```
tag_id        txn.stated_liability_match
entity        transaction
type_raw      enum: exact | probable | none | unknown
description   Does this payment's payee match a liability stated on the application?
produced_by   derived
used_by_rules FR-5
decision      Deterministic-once-tagged
```

### The four values, and why four

| value | meaning | example from LF-WCHG |
|---|---|---|
| `exact` | normalised payee equals a disclosed holder | `UNITEDWHOLESALE LOAN PAYMT` ↔ `UNITED WHSLE MORT` |
| `probable` | one contains the other, or they share a distinctive token | `DISCOVER E-PAYMENT` ↔ `DISCOVER BANK` |
| `none` | no disclosed liability resembles this payee | `CARVANA PAYMENT` ↔ nothing |
| `unknown` | the application states no liabilities, or the payee is unreadable | — |

A yes/no tag was considered and rejected. Two of LF-WCHG's four matches are unmistakable and two are
inferences (`PAYPAL INST XFER · APPLE.COM BILL` ↔ `APPLE CARD/GS BANK USA` is a guess), and the cost of
a wrong weak match is a **missed undisclosed debt** — the exact failure the rule exists to prevent. A
binary tag forces that call inside the producer where it is invisible; a graded one moves it into the
spec, where it is declared and can be re-tuned without a second vocabulary round.

`unknown` is load-bearing and not decoration: a file whose application lists NO liabilities must not
read as "nothing matched", which would fire the rule on every payment the borrower makes. Absent is not
none (§8).

## The producer — deterministic, no model

Extends the LP-546 recurrence stage, which already normalises payees and already sees the whole
snapshot. Reuse `_payee_key` verbatim: it strips digit runs AND the `[REDACTED-ID]` marker, which is
what stops one obligation splitting into two groups.

Compare each transaction's normalised payee against `snapshot.mismo` stated-liability holder names,
normalised the same way. Name matching should reuse the borrower-name machinery
(`app/services/borrower_name_matching.py`) rather than author a second fuzzy matcher.

## The FR-5 spec change

One predicate on its applicability conjunction:

```yaml
applicability:
  - {tag: txn.is_money_in, op: eq, value: out}
  - {tag: txn.apparent_category, op: eq, value: debt_payment}
  - {tag: txn.is_recurring, op: eq, value: "yes"}
  - {tag: txn.stated_liability_match, op: eq, value: none}    # NEW
```

`exact` and `probable` become `not_applicable` — out of scope, not a gap — so the rule goes quiet on a
clean file. `unknown` is neither, so it correctly reaches `couldnt_check` through the existing
applicability resolver.

Its `pending_surface: false` (LP-549) can then be removed: once the rule only fires on an unmatched
payee, being in scope IS a signal.

## The constraint that this file proves: match by PAYEE, never by amount

```
bank debit:  CITI AUTOPAY PAYMENT   $3,122.77 / month
disclosed:   CITI  Revolving             $49.00 / month
```

A 64x gap, and the $49 is **correct**: the borrower pays the card in full, and Fannie uses the minimum
payment for a revolving account in the DTI. An amount-based comparison would fire a fraud-adjacent
finding on a borrower doing exactly the right thing — on the first real file it ever saw.

Note also that five disclosed liabilities have NO matching recurring debit (Digital Federal, Happen
Bank, AMEX, DISCOVERC, Bank of America). That is the reverse question — disclosed but not observed
being paid — and it is NOT FR-5's, which asks only about payments the statements show.

## Activation sequence

1. vocabulary row added and `fact_tags.csv` regenerated
2. producer + tests
3. the FR-5 predicate, and drop `pending_surface: false`
4. re-run the self-consistency measurement — the judgment context changes, so the number above no
   longer describes the rule
5. record the new rate on the bar at `status: ratify-pending`, which activates it

Step 4 is not a formality: adding a predicate changes what reaches the model, and reusing a rate
measured against a different context is exactly the stale-number habit LP-496a was written about.
