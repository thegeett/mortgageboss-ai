## The measurement came first

`b7`'s question going in was the right one: **which parties have a reachable address today?** — and
it decided the shape of the ticket, because a per-party clock without a per-party address is a
reminder nobody can act on.

Counted before anything was built, over LP-800's 166 document types:

| party | address source | reachable |
|---|---|---|
| borrower | 113 · `borrowers.email` | yes |
| processor | 24 · orders it themselves | n/a by design |
| lender | 16 · `lenders.contact_email` / the assigned underwriter | yes, **since LP-813** |
| title | 5 · role existed, **no writer** | no |
| agent | 3 · role existed, **no writer** | no |
| cpa | 2 · **no column anywhere in the schema** | no |
| insurer | 2 · **no column anywhere** | no |
| employer | 1 · **no column anywhere** | no |

Thirteen types across four parties had no address in the product at all — and the build plan's words
for the consequence are exact: they *"sit at PENDING forever, never get `requested_at`, and are
invisible to LP-814."*

`test_the_catalog_still_sorts_to_parties_this_module_can_reach` pins that measurement, so a document
type re-sorted to a party with no mapping fails here rather than silently becoming unaskable.

## `loan_file_participants` is the address book, and already was

LP-805 built it as the allowlist the trust decision needs, seeded from the data that existed — and
the roles for `agent` and `title` were there from the start with nothing writing them. LP-820 adds
`employer`, `cpa` and `insurer`, and a way for a processor to put an address in.

That makes one table answer both questions it was always shaped to answer: **may this sender post
documents here**, and **where do I send this request**.

An address a processor types is **never trusted**. `is_trusted_sender` stays false, exactly as
LP-805's seeding leaves it: somebody we can write *to* is not somebody whose attachments should
bypass review, and §2.3's default is quarantine.

---

## The unreachable rows are the point

`open_requests` returns a party with needs and no address as `reachable: false` rather than dropping
it. A screen that showed only what it could send would render a file with five outstanding title
documents as **having nothing to do** — which is the plan's "invisible to LP-814", rendered. The row
names what is stuck and carries the field that unsticks it.

`PROCESSOR` needs are excluded entirely, and its absence from `PARTY_ROLE` is the rule rather than an
omission: a party that *cannot* be written to is different from one that *must not* be, and mapping
it to any role would turn "we fetch this" into "we email somebody about it".

## The draft is a real draft on the existing send path

Each party gets its own accumulating request, carrying the same `communication_needs_items` join —
so LP-811a's `send_draft` calls `request_needs_item` on everything in it, which is what stamps
`requested_at` and starts LP-814's clock. **That call is the whole reason this is a draft rather
than a second mailer**: the complaint was that these needs never get the stamp, and reusing the send
path fixes it rather than adding a path that would have to remember to.

Its own `template_key` per party, because the one-open-draft index is `(loan_file_id,
template_key)` — a shared key would make a title request and a CPA request collide, and the second
would be refused by the database with an error about a draft the processor cannot see. Asserted by
building two.

The address is **refreshed on every build**: a processor who corrected a typo between opening the
draft and sending it must not send to the old one, and the draft is the thing they press send on.

A party with no address is **refused rather than drafted**. A draft addressed to nobody is a message
that will never be sent and a clock that will never start — exactly the state this ticket ends.

## A limitation, measured rather than assumed

**No non-borrower type has catalog guidance.** LP-800 wrote full entries for the borrower-facing
types and party-only for the rest: 28 of 113 borrower types have a `borrower_label`, and **none** of
the 53 belonging to any other party does. So a party request's body is the needs' *titles* with no
retrieval instructions.

That is honest rather than broken — "Title commitment" needs no explanation to a title company — and
`test_no_non_borrower_type_has_catalog_guidance_today` pins it, so the day somebody writes guidance
for a title type this fails and the claim gets re-read instead of quietly becoming false.

## Deliberately not done

- **The address book is per file, not per company.** A title company used on thirty files is typed
  thirty times. A company-level directory with per-file selection is a real feature and a bigger
  one; per-file is where the data already lives and where LP-805's trust decision reads it.
  **Escalated.**
- **No per-party reminder threshold.** LP-814's three thresholds apply to every party equally. A
  title company at three days and an employer at three days are not the same expectation, but
  nobody has calibrated either.
- **The renderer's greeting is generic**, not addressed by party. It reads correctly to a title
  company because it names no borrower — but a template written *for* a title company would read
  better, and that is LP-817's shape rather than this one's.

## For the reviewer

- **Tenancy** — everything is file-scoped through `ScopedLoanFile`; the needs query and the address
  book both filter on `loan_file_id`, tested same-company-two-files. Address removal re-checks the
  file, with the same 404 for missing and for another file's.
- **Message content in logs** — the two new lines carry a loan-file id, a role, a party and a count.
  Never an address, never a document title.
- **AI in the decision path** — none. The party comes from LP-800's static catalog.

Worth a second measurement:

1. **`PARTY_ROLE` maps `LENDER` to `UNDERWRITER`.** LP-813 made the assigned underwriter a
   participant; `lenders.contact_email` is *not* consulted here, so a file with a lender contact but
   no assigned underwriter reads as unreachable. I think that is right — the underwriter is who a
   processor corresponds with — and it is worth disagreeing with.
2. **"First wins per role"** when two participants share a role. Two title companies on one file is
   a data problem a processor can see; picking arbitrarily is one nobody sees. Check the ordering is
   stable enough to say that.
3. **`REJECTED` counts as outstanding.** A document arrived and failed, so the need is still open —
   and dropping it would lose exactly the re-request most worth making.
