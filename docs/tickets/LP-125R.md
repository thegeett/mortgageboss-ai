## What this ticket is

AS-1 (`xsrc.asset.large_deposit_unsourced`) checks that a LARGE deposit into a bank account is SOURCED —
an unexplained large deposit may be undisclosed borrowed funds or an undocumented gift. Built via the
LP-122R pattern, reusing the AS-8/employer_count primitives.

## Verdict mapping (per-deposit, rolled up)

| case | verdict |
|---|---|
| large non-payroll deposit, **no** sourcing doc anywhere on file | **FINDING** (determinately unsourced) |
| large non-payroll deposit, sourcing docs **present** on file | **COULDN'T-CHECK** (indeterminate — can't match; verify) |
| large deposit whose description matches payroll / an employer | excluded (already income) |
| large deposit with **no description** (can't tell payroll) | **COULDN'T-CHECK** for that deposit (P2) |
| large deposit whose **account can't be determined** | **COULDN'T-CHECK** for that deposit (P6) |
| deposit ≤ threshold, or no large deposits | **SATISFIED** |
| no stated monthly income (basis absent) | **COULDN'T-CHECK** (rule-level) |

Rollup: any unsourced → FINDING; else any indeterminate → COULDN'T-CHECK; else SATISFIED.

## The "sourced" decision — an intentional departure from a literal AC (P1/P2)

The ticket's ACs assume a large **sourced** deposit → SATISFIED. But the data only reveals whether
sourcing docs exist *somewhere on the file* — a specific deposit **cannot** be matched to a specific doc.
Per **P2** (a REQUIREMENT: indeterminate sourcing → couldn't-check) and **P1** (no false-green), a large
deposit with sourcing docs present is **COULDN'T-CHECK** ("verify"), NOT satisfied — because file-level
presence is not per-deposit proof, and treating it as "sourced" would be a false-green (the doc might
source a different deposit / a different account). SATISFIED means "no large deposits to source."

**PRIYA-FLAGGED:** (1) should file-level sourcing-doc presence be allowed to CLEAR a deposit (satisfied)
rather than require per-deposit verification (couldn't-check)? (2) the payroll exclusion is a heuristic
(description keywords + employer-name match) — confirm the signal. (3) the income basis is *stated* total
monthly income (no qualifying-income fact yet) — a future computed qualifying-income fact would refine it.
The data limitations mean many large deposits land in couldn't-check; that is honest (no false-green, no
over-flag), and useful (each couldn't-check surfaces a specific deposit for review).

## Review fixes (round-6 → LP-125R fix-up)

A read-only review found three FALSE-GREENS on the core job, an applicability over-gate false-negative,
and structural items. All fixed; AS-1 stays `validated=true` (the threshold is Priya-recorded) but the
income-basis flags below are recorded for Priya. **Deposit / sourced decisions are DETERMINISTIC — no AI
in the finding decision** (the AI only extracted the amount + the free-text type; classification on top is
inspectable logic).

**False-greens closed**

- **FIX 1 — deterministic `transaction_kind` (the shared transaction primitive).** Deposit detection no
  longer exact-matches the free-text `transaction_type` against `"deposit"` (which silently skipped a wire
  typed `"credit"`/`"ACH credit"`/`"mobile deposit"`/`"DEP"`). A normalized `TransactionKind` is
  materialized ONCE on `TransactionFacts` in the builder (`fact_namespace/transaction_kind.py`):
  amount-direction-anchored, refined by a word-boundary pattern list, **unrecognized credit → DEPOSIT**
  (never skipped), unclassifiable (unrecognized text + no usable amount) → `UNKNOWN`. AS-1 reads
  `transaction_kind == DEPOSIT`; AS-2/3/7/8/10 will reuse the same primitive. Snapshot schema → v3
  (`transaction_kind` defaulted so a persisted v2 snapshot loads).
- **FIX 2 — payroll exclusion by keyword + the `transaction_kind == PAYROLL` anchor, NOT employer-name
  substrings.** `_is_payroll` now matches only explicit payroll keywords (word-boundary); the
  employer-name matching was removed — an employer named "Ally"/"Amazon" is a legitimate word in
  "transfer to ally savings"/"amazon refund", so name-matching (even word-boundary) falsely excluded real
  deposits. Employer-payroll is caught by the deterministic `PAYROLL` kind instead.
- **FIX 4 — sourcing requires a VERIFIED document (present AND fields),** matching the AS-5 gift-letter
  semantics. A present-but-unextracted gift letter no longer softens a determinate FINDING to
  couldn't-check.

**Over-gate false-negative**

- **FIX 3+7 — dropped AS-1's `required_inputs`.** `transactions[].amount` is a single-level `[]` path
  with ALL-element semantics, so one fee/interest line missing its amount suppressed the whole rule to
  couldn't-check. The evaluator already self-guards (absent income → couldn't-check; a deposit with no
  amount → per-deposit couldn't-check), so the gate only over-gated. `required_inputs` is now empty; the
  bank-statement-exists trigger is the only gate.

**Correctness / spec**

- **FIX 5 — sourcing matched PER ACCOUNT.** A sourcing doc that carries account fields sources only that
  account (via the shared grouping token); a doc with no account identity is "unattributable" and
  conservatively covers any account. One account's gift letter no longer masks another account's unsourced
  deposit. (File-level docs without account fields remain unattributable — per-deposit linkage needs
  richer data; Priya flag stands.)
- **FIX 6 — income basis filtered to employment income** (`employment_income`), so non-qualifying income
  (rental/pension/dividend) no longer inflates the threshold and hides deposits. **PRIYA-FLAG:** (a) which
  income types count as "qualifying" (employment only vs. + self-employment / fixed), and (b) whether a
  point-in-time deposit vs 50% of *monthly* income is the intended basis.

**Structural / latent**

- **FIX 9 — grouping promoted to a shared module** (`evaluators/grouping.py`): `account_grouping_token` +
  `label_accounts`, imported by BOTH AS-8 and AS-1 (no private cross-module coupling; "account N" refers to
  the same account across rules). *(The account_type-in-primary-key split, a separate round-6 item, is left
  as-is and noted in the shared module — the fix, when made, now lands in one place.)*
- **FIX 8 — AS-1 added to `runner.LIVE_PATH_OWNED_RULE_IDS`** (dormant live rule today; gate prevents a
  double-fire the moment its fact is populated).
- **FIX 10 — threshold param parsed defensively.** A non-numeric/blank `large_deposit_pct` (e.g. `"50%"`
  from the admin UI) falls back to the documented default instead of raising out of `evaluate` and
  crashing the run.

**Tests** — `test_transaction_kind.py` (the classifier), `test_grouping.py` (shared grouping), and the
expanded `test_large_deposit.py` pin: free-text deposit types detected, debits not; word-boundary payroll
(employer name does not falsely exclude); present-AND-fields sourcing; missing fee-line amount still runs;
per-account sourcing; dedup-set membership; bad-param no-crash.
