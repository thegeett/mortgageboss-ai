# LP-468 — Two classification fixes from the missing-extractor diagnostic

Neither is an extractor problem. **FIX 1:** an EAD card classifies as `passport` and cannot
reach the `work_visa_ead_card` type that already exists — a classification gap, fixed by
sharpening two indicators. **FIX 2:** three W-2 employee compensation statements were
force-fit into `commission_income_statement` (a mortgage sales-commission type) and now
divert to Tier 3 — they need a home, `compensation_statement`, not an extractor for the
wrong type.

## Phase A — design (documents read; STOP for sign-off before Phase B)

### A1 — FIX 1: the EAD separators + the revised indicators

**266 confirmed (re-read).** It is an EAD card: the header **"EMPLOYMENT AUTHORIZATION"**,
**Form I-766**, category **C26** (H-4 dependent spouse), USCIS# 201-764-302, a valid-from /
card-expires pair (11/10/23 – 11/09/26), an MRZ on the back, and the line **"NOT VALID FOR
REENTRY TO U.S."** Those printed cues are the separators — and the last one is decisive: a
passport is *precisely* a reentry/travel document, so "NOT VALID FOR REENTRY" cleanly
excludes it (the same move LP-465 used with the I-797's "THIS NOTICE IS NOT A VISA").

**Why an indicator fix and not a guard:** the classifier returns `passport` @0.92 with
`type_matches_document = TRUE`. The model is confidently wrong *and self-consistent* — its
label matches its own reasoning ("a U.S. passport photo page"). LP-463's guard only catches
*admitted* contradictions (label vs reasoning disagree); a coherent-but-wrong read is the
class it structurally cannot see. See the ADR.

**Members I am touching (the failing pair only): `passport` and `work_visa_ead_card`.**

`passport` — current: *"a government passport used as photo identification; the photo page
and passport number"* (thin; does not exclude an EAD). **Revised:**
> *a government PASSPORT — a travel/identity booklet or photo page: the printed word
> "PASSPORT", a nationality / issuing country, place and date of birth, a passport number,
> and a machine-readable zone (MRZ). A passport is a TRAVEL and RE-ENTRY document. It is NOT
> an Employment Authorization Document — an EAD card is titled "EMPLOYMENT AUTHORIZATION",
> shows Form "I-766", a category code (e.g. C26), and states "NOT VALID FOR REENTRY"; route
> that to work_visa_ead_card.*

`work_visa_ead_card` — current (LP-465): *"a USCIS Employment Authorization Document (EAD) or
work-visa CARD evidencing authorization to WORK (category, valid-from/expiration) — … distinct
from visa_documentation, permanent_resident_card, and uscis_notice_of_action"*. It names its
neighbours but does not lead with the card's OWN printed separators. **Revised:**
> *a USCIS Employment Authorization Document (EAD) — a card titled "EMPLOYMENT AUTHORIZATION",
> Form I-766, with a CATEGORY CODE (e.g. C26), a USCIS#, valid-from/expiration dates, and the
> line "NOT VALID FOR REENTRY" — the physical work-authorization card ID-8 checks. Distinct
> from a passport (a travel/re-entry booklet — an EAD is expressly "NOT VALID FOR REENTRY"),
> visa_documentation (a travel visa), permanent_resident_card, and uscis_notice_of_action (an
> I-797 NOTICE, not a card).*

**Members I am deliberately NOT touching, and why:**
- `permanent_resident_card` — already Form I-551-specific. The historical failure #1 (a UK
  passport → PR card) is a *different* pair (passport↔PR), not this ticket's failure; my
  passport change neither targets nor re-triggers it, and adding a PR cue here is out of scope
  ("only the members implicated").
- `visa_documentation` + `uscis_notice_of_action` — LP-465 already sharpened both with the
  "THIS NOTICE IS NOT A VISA" separator (failure #2, fixed). Not the current failure.
- `drivers_license` + `government_issued_id` — not implicated in any of the three failures.
  Adding cross-cues would be noise that could destabilize the DL/passport boundary the
  regression check guards.

### A2 — FIX 2: compensation fields confirmed against all three; scalars, not a list

common, semantically-normalized core recurs. Confirmed presence:

| `effective_date` | ✓ | ✓ | ✓ | **keep** (see rename) |
| `base_pay_current`, `base_pay_new`, `base_pay_increase_amount`, `base_pay_increase_percent` | ✓ | ✓ | ✓ | **keep** |
| `bonus_actual_award` | ✓ (16,100) | ✓ (30,900) | ✓ (25,800) | **keep** |

| `bonus_target_percent` | ✗ | ✓ (20%) | ✓ (10%) | keep (optional) |

| `one_time_payment_amount` | ✓ (1,500) | ✗ | ✓ (5,100) | keep (optional) |

**Renames/drops:**
- ⚠️ **`statement_period_or_effective_date` → `effective_date`** (type `date`). All three print
  a single new-base-pay *effective* date (Deloitte 5/31/2026, Fidelity 1/1/2026, PayPal
  4/1/2025); a two-date "period" is not consistently printed. One coercible date field.
- **DROP `bonus_target_amount`** (only PayPal; derivable from base × target%).
- **DROP `document_date`** (only Fidelity has one distinct from the effective date).

**Final: 13 scalars** — `employee_name`, `employer_name`, `effective_date`, `base_pay_current`,
`base_pay_new`, `base_pay_increase_amount`, `base_pay_increase_percent`, `bonus_target_percent`,
`bonus_actual_award`, `equity_award_amount`, `equity_award_type`, `one_time_payment_amount`,
`performance_rating`.

**Scalars vs `compensation_lines[]` — recommend SCALARS, argued from the documents.** The three
itemize differently at the *raw* level (Deloitte: Merit / Market-Adj / AIP / Reward-Excellence;
Fidelity: Bonus-funding / Chairman's-Shares; PayPal: Company-Performance% / RSU / one-time), but
the *semantically meaningful* components — base pay (current/new/increase), the bonus award,
equity, a one-time payment, a rating — recur across employers with consistent MEANING. Fixed
scalars **normalize** those; a `compensation_lines[]` list would capture raw, employer-specific
labels ("Merit", "Company Performance %") that no rule can compare — i.e. it would just mirror
the catch-all. Since the value for IN-10/IN-11 is the normalized base-vs-variable split, scalars
serve it and a list does not. Employer-specific extras fall to the grouped catch-all.

**⚠️ Two honest flags:**
- **`equity_award_amount` conflates a share COUNT with a dollar value** — Fidelity prints "625"
  (Chairman's Shares, a count), PayPal prints "$50,000" (RSU dollar value). Captured as printed,
  with `equity_award_type` disambiguating (a count like "Chairman's Shares" vs a dollar RSU
  award). The unbuilt earnings classifier must not treat 625 shares as $625.
- **No total / qualifying figure.** 247 prints a "$195,000 total compensation" banner; per the
  ticket and Priya's decision procedure it is **NOT captured** as a typed field (a
  total-comp scalar would be misread as qualifying income — the base-vs-variable call is the
  earnings classifier's, not the extractor's). It falls to the catch-all. No
  `total_compensation`, no `qualifying_income`, no variable-vs-base classification.

### A3 — does `commission_income_statement` still earn its place?

**Its real subject is legitimate and distinct** — *commission income* is a borrower income
category (a commissioned salesperson's earnings, treated differently from base salary in DTI),
not the same thing as these salaried W-2 comp statements. So the type is conceptually valid.
**But in the diagnostic sample, no genuine commission-income document appeared** — all three docs
that classified as `commission_income_statement` are the salaried comp statements now re-homed to
`compensation_statement`. **Recommendation: keep it** (the ticket forbids deletion, and the
category is real), but note that its only observed members were misroutes; worth confirming a
genuine member exists before it is ever given an extractor. Not deleting, not building — just
recording the observation.

### A4 — category, tier, PII

- `compensation_statement` → **`INCOME_EMPLOYMENT`, Tier 1** (with spec 117). LP-441 invariant holds.
- **PII: none needed.** The only long-digit identifier on these docs is an **employee ID**
  (PayPal "00323165", 8 digits — under the 9-digit guard anyway), and I am **deliberately not
  capturing it** (not income-relevant, not a proposed field). Every captured scalar is a name, a
  date, a dollar amount (< 9 digits: 170,600 / 30,900 / 50,000 …), a percent, a rating, or an
  equity-type string — none is a bare 9+-digit run, so **no `_PII_FIELDS` entry and no free-text
  scrub backstop** are required. (Contrast LP-465's `i94_number`, which *was* captured and *was*
  a 9-digit run — the trigger there was capturing the identifier, which I avoid here.)

### FLAG — anything inexpressible

- 247 is an angled **phone photo of a screen** (not a clean PDF) — extraction confidence may be
  lower on it than on 246/248; Phase C reports the actual result rather than assuming.

**FIX 1 — the indicator is correct and works on readable EADs, but does NOT fix 266.**
- **Works on a readable EAD:** `Harshita sai Adagarla/EAD.pdf` → **`work_visa_ead_card` @0.95** matches=True.
- **266 (the target) is unreadable → NOT fixed.** It re-classifies as `passport` @0.92, and across three
  runs the model hallucinated: "UK passport" / "UK biometric residence permit (unknown)" / "UK passport". It
  is a **90°-rotated, low-res CamScanner photo**; the model never reads "EMPLOYMENT AUTHORIZATION" / "I-766" /
  "NOT VALID FOR REENTRY", so no indicator can route it. (The indicators ARE in the rendered prompt — verified.)
- **`type_matches_document` on 266 is NOT the win we wanted** — the guard "agrees" (matches=True) with the
  *wrong* label, exactly the confident-but-coherent misread the guard cannot catch (ADR-365, limit 1).

**⚠️ NEW GAP — the classifier cannot read rotated / low-resolution ID-card photos; its default in that state
is `passport`.** This is **systemic, not one bad scan**: a second EAD, `453__Saikumar_EAD`, also →
`passport` @0.95, and ID cards are routinely photographed rotated/low-res. **The strongest evidence it is a
preprocessing gap, not an illegible document:** the *extractor* (same image, EAD-primed prompt) pulled
"Employment Authorization Document / Form I-766" from 266 at confidence **0.35** — the text is there and
partially machine-readable; the classifier fails because it is choosing among ~160 types on a rotated image
and latches onto the visual gestalt. **The fix is classifier-side image preprocessing (auto-rotation / OCR),
out of scope for an indicator ticket** → follow-up ticket.

**Equivalence anchors:** `ACTIVE_RULE_IDS = 37` (unchanged), catalog↔indicator guard green (162 types),
`SNAPSHOT_VERSION = 4` (unchanged), full suite **4155 passed / 5 skipped / 1 xfailed** (deterministic order),
ruff + mypy clean, spec-count guards 116 → 117.

**ADR-365** records both limits: the LP-463 guard cannot catch a confident-but-coherent misread; an indicator
cannot fix an unreadable input. Plus why `compensation_statement` earns a type with no rule today.
