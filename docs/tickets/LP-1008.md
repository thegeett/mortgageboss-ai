# LP-1008 — Read incoming mail

Step 4 (Receive), first ticket. Code, tests and a dev check. Nothing deployed, nothing committed.

## What and why

**Reading is on.** `inbound.poll_queue` existed but nothing ran it. It now runs every minute.

**The file is found by address only** (decision 11-04). `lf-<display_id>@<domain>` finds the file with
that `display_id` whose company has that mail domain, status `active` or `problem`. The old resolver
matched only `lf-<inbox_token>@<INBOX_DOMAIN>`, so replies to the addresses we now send from matched
nothing. The four guesses (thread, footer tag, sender, subject) and the Route B company attach are no
longer called. Their code stays, each marked as off.

**The envelope, not To** (rule 7). To and Cc are text the sender wrote. SES `receipt.recipients` is
where the mail was actually delivered. It was not stored; it is now.

Anything else is unrouted: no match, no envelope, or recipients on more than one file.

**Accept and preview read the right bucket.** They read raw mail through the documents storage (the
step-1 bug). They now use `get_mail_storage()`.

## What changed

**Migration** `c4f7a92e1b36` (hand-written, with downgrade; up/down/up run on the dev DB):
`inbound_messages.envelope_recipients`, JSONB, not null, default `[]`. Existing rows get `[]`.
Excluded from `readonly.inbound_messages`, like `to_addresses`; the view lists its columns by name, so
it did not change. The drift test records the exclusion.

**Ingest** (`inbound_ingest.py`): fills the column from `receipt["recipients"]`, lower-cased and trimmed.

**Resolver** (`inbound_routing.py`):

- `resolve_loan_file_by_address`: as above. Unknown file, wrong domain, inactive domain, deleted file
  and malformed address all return None through one path, and log one line with no address in it.
- `route_message`: rung 1 only, over `envelope_recipients`. Exactly one distinct file → routed.
  None, or more than one → unrouted. One file plus an address that matches nothing is routed.
- Signal: stays `inbox_token`, confidence 1.0. A new value would have needed a frontend label, because
  the Communication tab already shows `inbox_token` as "Sent to this file's address".
- `inbox_token_in` is deleted (the old form). `_route_by_thread`, `_route_by_footer_tag`,
  `_route_by_participant`, `_route_by_subject`, `attach_route_b_company` and `record_original_hop` stay,
  uncalled, and are listed in `KNOWN_UNWIRED` with the reason. Their tests now call them directly.
- The company is still read off the resolved file and nowhere else.

**Schedule** (`celery_app.py`): `read-inbound-mail`, every 60 seconds, `expires: 60`.

**The reader saves before it deletes** (`tasks/inbound.py`; added after review, your instruction, and
different from the brief). `poll_queue` used to queue a separate `ingest_message` task and delete the SQS
message at once, so a failed save lost the mail with no alarm. It now saves each message itself and
deletes it after the commit. A message that fails stays on the queue, comes back after the visibility
timeout (300s), and reaches the DLQ after 5 receives, where the alarm sees it. The other messages in the
batch carry on. Running out of time stops the batch. A redelivery of a message already saved changes
nothing and is then deleted. `ingest_message` is removed; nothing else called it. Still one batch of 10;
unparseable bodies still stay for the DLQ.

**Ingest uses `task_session`** (added after review). It used the app's pooled engine in a new event loop
each run. Measured in one process: run 1 worked, run 2 raised "Event loop is closed", run 3 worked.

**Mail-bucket reader** (`inbound_triage._attachment_bytes`, which accept and preview both use): reads
through `get_mail_storage()`. For `s3://<bucket>/<key>` it uses the key, and refuses with the existing
"no longer available" error if the bucket isn't `settings.mail_bucket`. A raw file that can't be read
gets the same error instead of a 500 (added after review); `StorageError` covers a failed read as well as
a missing file, so a warning is logged. In staging the API task already
has what this needs: `MAIL_BUCKET`, `MAIL_KMS_KEY_ID`, GetObject on `inbound/*` and `kms:Decrypt`.

**`process_raw_message(store_raw=True)`** writes through `get_mail_storage()` at `inbound/<message id>`
and records that key (was `inbound-raw/<id>.eml` in documents storage).

**Dev injector** (`api/dev.py`): new form field `recipient`, repeated for several, becomes a fake
`receipt.recipients`. Verdicts are PASS unless `dmarc_verdict` says otherwise. No recipient means no
envelope, so unrouted.

**Seed**: its fake mail uses `lf-<display_id>@<the company's own domain>` (normally
`mb-mail.localhost`) and a fake receipt.

**No company sees another company's mail** (added after review, your instruction; ADR-420).
`list_triage_queue` returned rows with no company to every company, with the sender, subject and
filenames hidden. Each company still saw that a message existed, with its time, verdicts and attachment
sizes and types. It now returns only the caller's company's rows, and `include_unrouted` is gone. The
redaction in `_message_public` stays as a second lock. Two small screen changes follow, because the old
words would be false: the Inbox page shows "Not matched to a file" only when that company has such a row
(its "Everything has been matched" empty state is gone), and the card no longer says "shown to every
company". Mail with no company stays in the table; internally, `readonly.inbound_messages` shows that it
exists, without sender or subject.

**Comments this ticket made false** (no behaviour change): `core/config.py`, `models/loan_file.py`,
`services/mailbox_connections.py`, `services/mail_domain.py`, `services/inbound_ingest.py`,
`services/inbound_routing.py`, and one comment in `infra/envs/staging/main.tf` ("not on the beat
schedule"). No Terraform apply needed. The first pass missed several; review found them. `apply_routing`
no longer takes `raw`.

**Tests:** `tests/mail_address.py` swaps `token_address` for `file_mail_address` and `deliver` (real
ingest, with the `To` header as the envelope), for tests about what happens after routing. New:
`tests/services/test_inbound_address_lp1008.py`, `tests/api/test_dev_inject_lp1008.py`,
`tests/tasks/test_inbound_poll_lp1008.py`, one schedule test in `test_task_registration.py`. Removed: `test_the_token_rung_still_wins` (the ladder it tested is
off).

## Open

1. **Mail with no company now reaches nobody in the app. Needs a decision before LP-1009.** See "No
   company sees another company's mail" above. A mistyped address on a company's domain, or a two-file
   email, is therefore not in that company's unassigned list, as decision 11-04 says it should be. The
   company could be taken from the domain or the matched files when they point to exactly one company.
   That widens the "company only from a resolved file" rule, so it was not built.
3. **First poll after deploy.** Queue retention is 14 days and nothing has read the queue, so LP-1007's
   test replies will be ingested by the first poll. Expected, and harmless, but they will appear.
2. **Older `inbound-raw/` rows can't be opened.** They now say "no longer available" (dev: re-inject).
   Whether staging has any was not checked: raw paths are not in the readonly view.
4. **The dev injector and seed can't store raw mail on staging.** The API role reads `inbound/` and
   cannot write it. Dev only; staging mail comes from SES.
5. **`auto_accept` is still written as a label.** `decide_disposition` can return `AUTO_ACCEPT` for a
   trusted sender, and the activity detail then says so. It changes nothing (the row stays `routed`, the
   attachment `pending`), but the word is misleading if LP-1009 ever shows it. Its "certain" also rests on
   a 4-character display id, which is not secret; that matters if auto-accept is ever turned on.
6. **Route B's admin screen is still live**, with nothing behind it. LP-1011 hides it; ship them together.
7. **Throughput:** at most 10 messages a minute (as briefed). Fine for the pilot; a burst clears slowly.
8. **Small leftovers:** `_stored_body` still reads documents storage (only rung 3 uses it; fix if that rung
   returns). `ix_loan_files_inbox_token_lower` and its test no longer serve a query (LP-1011?). The resolver
   does not check whether the company is soft-deleted.
