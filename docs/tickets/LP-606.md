# LP-606 — Two rules contradicting each other, and a false all-clear on credit

Both surfaced on the first run after the pay stubs landed on LF-3CVT.

## 1. IN-5 and a cross-source rule answered the same question differently

On one run, on one file:

| | verdict |
|---|---|
| **IN-5** | satisfied — *"The employer name is consistent across all sources."* |
| **`xsrc.income.employer_name_consistency`** | yellow — *"Documented employer not among the stated employers: SUMITOMO PHARMA AMERICAS INC."* |

The pay stub says **AMERICAS**; the application says **America**. One trailing letter.

The cross-source rule's `_norm` folds case and whitespace and nothing else, so it cannot tell a
spelling variant from a different company. IN-5 is a structural rule with `ai_fuzzy_match`, and its
criteria say in words that it is *"tolerant of legal-vs-common-name and formatting variance"* — the
exact judgment the other one is unequipped to make. Its own note had already conceded the gap:
*"STARTER — employer-name normalization (DBA/legal name) to verify."*

**Retired**, per ADR-375's principle: one matcher per question, or a processor gets a file that says
both things at once. The definition object stays so the rule id resolves for findings already stored,
and `employer_mismatch` remains an owned canonical type through the employer-count rule, so the AI
layer still defers on that type.

### Two test files moved rather than died

`test_finding_reconcile.py` (9) and `test_finding_identity_dedup.py` (10) used this rule as a
*vehicle* — what they actually protect is reconcile behaviour and normalized-substance dedup, both
rule-agnostic. Re-pointed to `xsrc.liability.undisclosed_debt`, which has the same shape (one finding
per non-matching value) and is live. The en-dash/em-dash case that prompted `finding_identity` in the
first place transfers verbatim, because `ObligationRef.key` is a name string too.

## 2. A false all-clear on credit, from an application row

Four CR-6 findings went to `no_longer_applies` after an upload that had nothing to do with credit.

`liab.is_derogatory` is an **AI tag**, produced per liability, asking *"does this account carry ANY
derogatory mark?"*. It was asked about all four MISMO-**stated** liabilities — rows carrying a type, a
holder, a payment and a balance, on a file with **no credit report** — and answered **"no"** for every
one:

> "APPLE CARD/GS BANK USA revolving account with $36 balance and $25 monthly payment. **No indicators
> of derogatory status.** Account appears current..."

Absence of a derogatory field is not absence of derogatory history. The group's own prompt says *"when
you cannot determine a value, return unknown. Never guess."* — it read silence as evidence instead.

The consequence chain: `is_derogatory = "no"` → CR-6's applicability false → `not_applicable` → not
persisted → the four honest `couldnt_check`s from the previous run retired as "no longer applies". A
processor was shown four debts cleared of derogatory credit on the strength of an application row.

### Fixed by not asking

New declarative `subject_source` on an AI group: the subject source it can actually assess.
`credit_derogatory` declares `credit_report_reported`, so a MISMO-stated liability never reaches the
model, the tag stays absent, and CR-6 returns `couldnt_check` — the honest answer. It also stops four
model calls per run that could only ever be wrong.

Declared rather than branched, following `include_borrower_roster`'s precedent. **Deliberately not
behind `gate_ai_groups`**: that flag exists to make the *document* gate reversible, and that gate only
skips a redundant call with the prompt's own abstention as backstop. This is different — a group asked
about a subject it has no data for does not abstain, it answers — so leaving it switchable would leave
the false all-clear switchable with it.
