# LP-577 — Apply confirms before it writes

## What you asked for, and what already existed

Apply should open a dialog explaining what it will change, show the new DTI with its breakdown, and
frame every adjustment as add / remove / replace.

**Most of that was already built.** LP-97 shipped `FindingImpactPreview` and `ViewFixDialog`: a
dry-run that runs the REAL `apply_finding` inside a savepoint, rolls it back, and returns
`dti_before/after` + `ltv_before/after` with an itemized line-by-line table.

I started writing a second one before checking. It is deleted. The existing implementation is more
careful than what I had — it refreshes the ORM objects after the rollback, and detects change on the
RAW ratios so a gated calculation cannot hide a real move behind two nulls.

**What was actually missing was four things.**

## 1. The governed rule findings could not reach it

`ViewFixDialog` was wired only into the legacy cross-source `finding-card`. The Needs-Attention tab's
Apply button called the mutation directly — no preview, no confirmation. DT-8 and DT-6, the two rules
this whole thread is about, were exactly the ones without it.

The dialog reads **one** field off the finding: `id`. It was typed as the legacy
`VerificationFinding`, which is what kept the rule findings out. Narrowed to `{ id: string }`.

`fileId` then had to thread through six components. Worth noting how that could have gone wrong
silently: the prop is optional, so **TypeScript was satisfied by a chain where no call site passed
it** — it compiled clean and the dialog would simply never have opened. Eight call sites needed it;
the test asserts the dialog opens rather than trusting the types.

## 2. Four of six actions had no summary

`_summarize_change` covered `add_liability` and `correct_income`. Everything else fell through to
`"Apply: correct_liability_payment"`, which tells a processor nothing about their loan. All six now
say which of add / remove / replace, on what, and to what.

## 3. A removal rendered as an unchanged line

The dialog flagged NEW lines (`isNew = !beforeKeys.has(item.key)`). But an excluded debt **stays** in
`debt_items` carrying its real amount and simply stops being summed (LP-568 deliberately keeps the
line visible). So `exclude_liability_paid_off` — the whole point of DT-8 — rendered as a line with an
unchanged number while the total silently dropped. It now reads as a removal: struck through,
counting 0, tagged REMOVED.

## 4. The preview 500'd on a refusal

The dry-run runs the real `apply_finding`, so it raises on exactly what the write path raises on: an
ambiguous target (two liabilities from the same servicer), a target that is gone, a finding already
resolved. Unhandled, the **preview crashed** — so the one flow whose job is to say "this cannot be
applied, and why" was the flow that broke on it. Now a 409 carrying the reason.

## Verified by removing each fix

| removed | result |
|---|---|
| routing Apply through the preview | `opens the before/after preview instead of applying immediately` fails |

## Not built

The staleness question I raised: the preview is computed at T and confirmed at T+30s, and if another
processor edits that liability in between, the applied result differs from what was shown. Today the
apply just runs. Recomputing at confirm time and refusing on a changed diff is the safe behaviour,
and it is a separate decision.
