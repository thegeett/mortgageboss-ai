# LP-532 — Name the creditor on a `per_liability` finding

## The problem, as a processor sees it

LF-WCHG produced **four CR-6 findings that are byte-identical**, each with the subject
"a debt on this file". A processor cannot tell which debt any of them is about, nor that
the four are four different debts rather than one duplicated four times.

LP-531 got the label from "an item in this file" to "a debt on this file" — honest, and
still not actionable. This ticket finishes it.

## Why it was not finished there

`resolve_subject_label` resolves a document subject through `document_filenames`, a map
the read path builds with `document_filenames_by_content_id(db, loan_file)`. There is no
equivalent for liabilities, and it is not a one-liner: a liability subject is a UNION of
two sources (ADR-374) — credit-report tradelines and MISMO stated liabilities — and the
holder name arrives under a different column in each (`creditor_name` vs `holder_name`,
already aliased in `tag_materialization/subjects.py::_LIABILITY_FIELD_ALIASES`).

Building it means reaching the snapshot at read time, which the findings endpoint does
not do today.

## Scope

1. A `liability_labels_by_subject_id(db, loan_file)` builder, keyed on the SAME
   `subject_id` `liability_rows()` produces — reuse that function rather than deriving
   ids a third time (the LP-483 argument: drift removed by construction).
2. A `lia` branch in `resolve_subject_label` reading that map, falling back to the
   LP-531 generic when a liability is gone from the file.
3. Pass the map from all three callers: `api/verification.py`, `services/finding_prose.py`
   (so composed text can name the creditor too), and `eval/worksheet.py`.

## Constraints

- The label is **read-time only and cosmetic**. `subject_key` stays the reconciler's key
  (LP-322) — the label must never become the key.
- `creditor_name` goes through `_scrub_list_value` in the tag path because a bureau can
  print an account number inside it. Any label built here must scrub the same way.
- A MISMO liability with no holder is already flagged `unresolved_reason` by the
  enumerator; it has no name to show and must keep the generic.

## Not in scope

Whether four CR-6 abstentions on one file should be four findings at all. They are four
distinct subjects, so four is correct under the current model; if a processor should see
one grouped row instead, that is a UI grouping question like the AS-12 one, not a
labelling one.
