# LP-422 — The schedule-presence producer: Schedule C / E → a per-borrower income-scope fact

## What this ticket is

LP-421 surfaced Schedule C / Schedule E into the snapshot; **nothing read them**. This is the last mile: a small
**deterministic** producer that turns schedule PRESENCE into a consumable tag, unblocking IN-12 (self-employment)
and IN-13 (rental). The key property — **presence is a FACT, not a judgment** — means **no calibration round, no
worksheet, no Priya bar** for the tag. That is what sidesteps the LP-420 problem (income.type's
self_employment/rental couldn't be calibrated on synthetic data, ADR-332). **Producer only — no rules.**

## D1 — the tag target (the mixed-mode question, answered)

**A tag has exactly one producer.** `tag_production.yaml` is `dict[tag_id → one declaration]` with a single
`mode`; `income.type` is `ai` (`income_amounts`). So a **derived producer for `income.type` is structurally
impossible** — not a STOP to force, a fact that redirects the design. The cleanest shape:
- **Self-employment → extend `income.is_self_employed`** (LP-418, derived/borrower — the tag IN-12 already gates
  on) to also read **Schedule C presence**. Reuses the existing tag; feeds IN-12 directly.
- **Rental → new `income.has_rental_income`** (derived/borrower) reading **Schedule E presence** — the same
  shape, for IN-13's rental scope (IN-13 reads `income.type`, which can't carry rental; its ticket re-scopes to
  this tag, as LP-419 re-scoped IN-12 onto `is_self_employed`).
- **`income.type` untouched.**

See **ADR-334** for the named finding (a fact can't feed an AI-only tag) + the ADR-332 escape hatch.

## D2 — what counts as the signal (presence, conservative)

| signal | rule | producer says `yes` when… |
|---|---|---|
| self-employment (IN-12) | `income.is_self_employed` | an attributed tax return has a **Schedule C** — **presence, not `net_profit`** (a LOSS still counts) |
| rental (IN-13) | `income.has_rental_income` | an attributed tax return has a **Schedule E** — presence, not `rents_received` (a zero-rent year still counts) |

**No threshold** (ADR-324 — "is $500 of net profit enough" is a RULE question). **Fail closed:** no schedule →
`unknown` (or, for a filed return with no Schedule E, `no`) — **never a fabricated `base`** (a tax return without
a Schedule C says nothing about wage-earning).

## D3 — the starter-extractor question (surfaced for the rule ticket, NOT decided here)

The tax-return extractor is a self-declared **STARTER** (ADR-333), never validated against a real return. This
producer faithfully translates whatever it surfaces, so **IN-12 / IN-13 would activate on an unvalidated
extraction path.**
- **For:** presence is a coarse signal (a form is attached or not); its failure mode is a **wrong scope** (a
  rule applies or not), milder than a misread dollar figure.
- **Against:** no golden files exist for tax returns.
- **This ticket writes no rule and decides no activation.** The rule ticket (IN-12 / IN-13) must weigh this and
  decide whether to activate on the starter extractor or gate activation on golden-file validation first.

## D4 — the document→borrower chain (verified, anti-structural-death)

Schedules live on a `tax_return` **document**; IN-12 / IN-13 enumerate **per_borrower**. The bridge is
`_borrower_attributed_documents` (`belongs_to` attribution, LP-385/418) — both recipes iterate the borrower's
attributed documents. Verified end to end on LP-421's fixture: the tax return `belongs_to` borrower `01bb`, and
both tags materialize AT that borrower subject (the value a per_borrower rule reads).

## D5 — provability

LP-421's `build_tax_return_with_schedules_snapshot` already has a borrower the schedules attribute to (`01bb`) —
no fixture extension needed for the present case. The loss / neither / rental-only / no-tax-return cases are
built inline in tests.

## D6 — equivalence

No existing fixture carries a `schedule_c` / `schedule_e` on a `DocumentEntry` (LP-421 defaults them `None`), so
the extended `is_self_employed` reads exactly what it read before (its `income.type` path) on every existing
fixture, and `income.type` is untouched. Asserted (on the income-calibration fixture + no schedule leakage).

## What was built

- `derived.py` — extended `_income_is_self_employed` (Schedule C presence → `yes`, checked first, needs only the

- `tag_production.yaml` + `vocabulary_extra.yaml` — `income.has_rental_income` (derived/borrower, enum
  yes/no/unknown). The one new vocabulary tag (self-employment reused the existing tag).
- Count: 166 → 167 (`test_fact_tags_files.py`, `test_projection_db.py`).
- `decisions.md` — ADR-334.

## The proof (reported, not predicted)

Materialized at the **borrower subject** (the value a per_borrower rule reads):

| case | `income.is_self_employed` | `income.has_rental_income` |
|---|---|---|
| LP-421 fixture (Schedule C 82000 + Schedule E, 2 props) | **yes** | **yes** |
| Schedule C showing a **loss** (net_profit −15000) | **yes** (presence, not value) | — |
| Schedule E only (rental) | unknown | **yes** |
| Schedule E, zero-rent property | — | **yes** (presence) |
| tax return, **neither** schedule | **unknown** (never `base`) | **no** (filed, no Schedule E) |
| pay stub, **no** tax return | unknown | **unknown** (can't tell) |

- **D6:** on the income-calibration fixture `is_self_employed` reads exactly as before (no Schedule C anywhere);
  `income.type` unchanged.
- **`ACTIVE_RULE_IDS` = 30** (a producer activates nothing); the 30 live rules identical.

## What IN-12 / IN-13 now need (the next ticket)

- **IN-12** already gates on `income.is_self_employed` (LP-419) — it now materializes `yes` for a borrower with a
  Schedule C, so IN-12 is functionally unblocked on the tax-return path. Its **activation** is the open question:
  it would go live on the STARTER extractor (D3). The IN-12 activation ticket must decide.
- **IN-13** reads document-subject `income.type` today (a wiring quirk). It needs a **spec re-scope** to read the
  new borrower-level `income.has_rental_income` (the LP-419 shape) — then, the same activation decision on the
  starter extractor.

## Assumptions / decisions

- `income.type` deliberately NOT given a derived producer (structurally impossible — one producer per tag,
  ADR-334). Self-employment reuses `is_self_employed`; rental gets a new tag (no reuse candidate; the
  `is_self_employed` shape).
- The rental `no` (a filed tax return with no Schedule E → no rental) mirrors `is_self_employed`'s enum so IN-13
  can reach `not_applicable` — with the D3 caveat that a starter extractor missing a Schedule E would be a false
  `no` (the rule ticket weighs this).
- The self-employment extension checks Schedule C presence FIRST (it needs only the documents, not the tags
  layer) and adds no schedule-driven `no` (the existing `income.type` path handles `no`) — minimal, additive.

## New gap

- **The starter extractor** (ADR-333/334, D3): the signal is now reachable but rests on an unvalidated
  extraction path. Golden-file validation of the tax-return extractor is a prerequisite the IN-12 / IN-13
  activation ticket must weigh. Recorded in ADR-334.
