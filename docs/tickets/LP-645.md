# LP-645 — one bounded-dispatch implementation, not two

- **Status:** Not started. Small and well-bounded (~20 lines of deletion), but it carries a live
  defect fix, so it is not cosmetic.
- **Date:** 2026-09-05
- **Raised by:** the LP-644 §2 review, which fixed a defect in one implementation and could not fix
  it in the other without widening its own scope.
- **Scope:** Backend — `services/tag_correlation.py` (`_judge_concurrently`), `ai/concurrency.py`.
- **Does not touch:** any prompt, context, threshold or rule. Same §0 argument as LP-644 §2.

## The report

LP-644 §2 introduced `ai/concurrency.py`'s `dispatch_bounded` for Stage A and both materialization
levels. Stage B's `_judge_concurrently` (LP-635) is the original of that pattern and was deliberately
left alone at the time. The stated reason — *"it is live and was reviewed into its current shape"* —
argues for leaving its BEHAVIOUR alone. It does not argue for keeping a second copy of the logic, and
the review was right to push back on it.

**The gate / collect / re-raise body is now a line-for-line duplicate.** `_NotAttempted` is the only
real difference, and it is a caller concern that `CallOutcome.not_attempted` already expresses: the
sentinel exists to carry a processor-facing reason string, which the generic module has no business
knowing and does not need to.

## Why this is not cosmetic

**The duplicate already diverged, in the direction that costs a verdict.** Both implementations wired
their dispatch gate to `AiInfraBreaker.threshold` while counting every `AIClientError` alike — but
`record_failure` RESETS on `INFRA_OVERSIZED`, because one oversized document is not an outage. So
five consecutive oversized payloads, a CONTENT problem, close the gate; and a closed gate is not a
failed call, it is a call never made. Every remaining subject resolves unknown-with-reason without
reaching the model, without the breaker tripping, and without a log line. Serially those subjects are
judged normally.

The LP-644 §2 review fixed this in `dispatch_bounded` (by exposing `counts_toward_trip` so the gate
and `record_failure` share one definition of a trip-worthy failure). **It is still live in
`_judge_concurrently`**, on the stage that makes the most calls in the run.

That is the argument for this ticket. A module docstring noting the duplication will not carry the
knowledge of this defect to whoever next reads the other copy — and the next divergence will be found
the same way, by someone tracing a wrong verdict backwards.

## What to do

1. Fix the oversized-gate defect in `_judge_concurrently` FIRST, on its own, so the fix is reviewable
   independently of the refactor and can ship even if the refactor is deferred again.
2. Replace its body with `dispatch_bounded`, mapping a `not_attempted` outcome to `_NotAttempted` at
   the CALLER — which is where the reason string belongs.
3. Keep `_judge_concurrently` as the caller-facing function so nothing downstream changes shape.

## The safety net already exists

LP-635 pinned the serial and concurrent Stage-B paths tag-for-tag, and LP-644 §2 added an equivalence
suite that goes further (stubs finish in REVERSE order, so completion and input order disagree on
every run rather than by luck). Between them the refactor is checkable rather than argued: the
existing tests must pass unchanged, and that is the whole acceptance criterion.

Run the Stage-B equivalence tests before and after with no edits to them. If a test needs changing to
accommodate the refactor, the refactor changed behaviour and is wrong.

## Out of scope

- Any change to Stage B's concurrency BOUND (`_MAX_CONCURRENT_JUDGMENTS`) — that is LP-644 §4, and
  it waits on measured TPM.
- Batching Stage B — LP-644 §5, which has real quality risk and needs the calibration harness.
