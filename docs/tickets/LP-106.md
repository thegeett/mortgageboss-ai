# LP-106 — Expand staleness/recency to types that already extract a period

- **Ticket:** LP-106 (follow-up to LP-105)
- **Status:** Completed
- **Date:** 2026-07-03
- **Scope:** Backend (recency logic) — the frontend badge renders automatically

## The gap

Document staleness (`app/documents/staleness.py`, LP-71) is deterministic — it judges freshness from
the **extracted** date against a per-type window, exposes `as_of_date`, and drives the frontend
"Expired / May be stale" badge. It was wired for only **4 types** (pay_stub, bank_statement recency;
drivers_license, homeowners_insurance expiry). But **investment_account** and **retirement_account**
already extract `statement_period_end` — the *same field* bank_statement uses — yet weren't checked,
so a **stale asset statement was never flagged** even though the date to judge it existed. Asset
statements verify reserves / down-payment availability and lenders require a recent one, so this is a
correctness gap, not cosmetics.

## The fix — reuse the existing mechanism (`RECENCY_WINDOWS`), just add entries

Added to `RECENCY_WINDOWS` (grounded-starter windows — **validate-with-Priya**; the mechanism is the
fix, the exact day counts are hers):

| Type | Field | Window | Why |
| --- | --- | --- | --- |
| `investment_account` | `statement_period_end` | **90 d** | asset statement; often **quarterly**, so a bit longer than bank's 60 d to avoid false-flagging a normal current quarterly statement |
| `retirement_account` | `statement_period_end` | **90 d** | same (401k/IRA statements are frequently quarterly) |
| `profit_and_loss` | `period_end` | **120 d** | a self-employed P&L should be reasonably current (its period-end is the "through" date); lenient starter |

No parallel path: these reuse the existing `RECENCY_WINDOWS` → `evaluate_staleness` → `as_of_date` →
`stalenessBadge`, so the badge renders for the new types automatically (the badge is type-agnostic).
`package_fitness`/`package_qualification` also pick them up — a stale asset statement is now correctly
flagged as not package-fit.

## Under-vs-over — deliberately NOT wired

- **voe** — `end_date` is the employment **termination** date ("if former; else null"), null for a
  current employee, and it's an employment-history date, **not** a verification/issue date. There is
  no clean recency signal to key on, so voe is intentionally left out.
- **mortgage_statement** — `due_date` is a **future** payment obligation, not an as-of/recency date.
  Wrong concept for recency; left out.

Both are documented in the code (a comment in `RECENCY_WINDOWS`) so the omission is intentional, not
an oversight.

## Reported / flagged — the inert FHA (and Conventional) recency FACTS (a fast-follow, not built here)

There is a **separate** recency system: the verification engine's file-level facts consumed by rules.
Rules in both `conventional/__init__.py` and `fha/income_assets.py` **read**
`documents.income.most_recent_age_months` and `documents.asset_statement.most_recent_age_months`, but
**only `documents.paystub.most_recent_age_days` is built** in `build_file_facts` — so those
income/asset-statement recency **rules are currently inert** (graceful "not evaluated").

**This ticket does NOT build them, and wiring the staleness badge does NOT build them** — they live in
a different code path (`build_file_facts`, not `staleness.py`). Building them needs a new fact-builder
that aggregates the newest income-doc / asset-statement extraction date across the relevant document
types and converts to months (like `_most_recent_paystub_age` does for pay stubs), plus deciding which
types count as "income docs" vs "asset statements". That is a distinct piece of work.

→ **Flagged as a fast-follow (proposed LP-107):** build the
`documents.income.most_recent_age_months` + `documents.asset_statement.most_recent_age_months` facts so
the declared Conventional/FHA recency rules fire. Not silently left unaddressed.

## Grounded-starter

The windows (90/90/120 d) are grounded starters — **validate-with-Priya** (the exact recency windows
vary by lender/program; the quarterly-statement consideration for investment/retirement especially).
The mechanism (these types get staleness-checked from their already-extracted date) is the fix.
