# LP-416 — The vacuity sweep: how many unwritten rules compare a value to itself? (READ-ONLY)

## What this ticket is

Four rules have been killed at gate 0 (DT-5, DT-2, IH-4, CO-2 — ADR-330), all sharing one shape: **"X used in
the calculation vs X from the document."** The DTI/MI calculators DERIVE their lines from those same documents,
so the check is a value against itself. Four instances in two buckets suggested a structural flaw, not bad luck.
This sweeps every unwritten in-scope rule for the pattern — **gate 0 only** — and, critically, **splits each hit
into DEAD vs merely-BLOCKED.** **No file was changed except this report.**

**Two headline findings:**
1. **The sweep found a FIFTH instance — DT-3 "Mortgage insurance in DTI"** — completing the DTI
   "component-in-the-computation" family (DT-2 HOA / DT-3 MI / DT-5 insurance) plus their duplicates (CO-2, IH-4).
   **Five rules, one cluster, one root cause.**
2. **NONE of the five is inherently dead — all are `vacuous-today-fixable`.** The missing independent operand
   already EXISTS in the system: the **`DtiOverride`** (a processor-entered figure that CAN diverge from the
   document) is applied to each housing line but is **not surfaced as a rule-readable fact.** **ONE producer —
   "surface the override-applied DTI housing line as a fact" — recovers all five.** This CORRECTS ADR-330's
   "never write" framing: they are one producer away, not permanent noise.

## Phase 0 — the method + how many rules examined

Gate 0 only, three passes (not another full audit):

1. **`rule_kinds.csv`'s own annotations** — grep every `dup`/`overlaps`/`same as`. It surfaced exactly **IH-4
   "(dup DT-5)"** and **CO-2 "(overlaps DT-2)"** — the two known. No other annotation. (The CSV knew about the
   duplicates but not the third original, DT-3 — pass 3 caught that.)
2. **The phrasing pattern** — grep the classification doc for "used vs / applied vs / figure used / stated vs /
   vs binder / vs certificate / match … certificate". Surfaced 11 rows.
3. **The calculator-derived surfaces** — for every rule reading a **calculated** value (`services/dti.py`,
   `services/mi.py`, `calculators.py`, `calculations_section.py`), trace what the calculation READS; if it reads
   the same document the rule's other operand comes from → a hit.

**Authoritative sources:** `rule_kinds.csv` + `stage2-rule-classification.md` (descriptions, quoted);
`rule_tags.csv` (the planned operands — a HINT, drifted); `services/dti.py` / `services/mi.py` (what each
calculated line reads — the trace); `app/models/dti_override.py` + `calculations_section.py` (the override
surface — the systemic-unlock question); `tag_production.yaml` (what is produced). **~19 rules were examined
closely** (every one surfaced by passes 1–3); the remaining ~62 unwritten rules read no calculator-derived value
against its own source and are cleared by construction (they do not have the shape).

per-line override-applied amounts). Surfacing it makes each rule a real "did the processor enter a DTI figure
that contradicts the source document?" check.

### THE CORRECTED WRITABLE DENOMINATOR

Of the ~81 unwritten in-scope rules, **0 are permanently removed by gate 0.** The five self-compares are
recoverable, not dead — so the writable denominator §13 should carry is **~81, with a 5-rule cluster gated behind
ONE producer** (the override surface), + 1 unclear. This is the opposite of what four dead rules implied:
**the spec set's flaw is a missing producer, not five bad rules.**

### THE OVERRIDE UNLOCK (the highest-value find)

**One producer unblocks the whole class.** Surface the **override-applied DTI housing lines** as rule-readable
facts (e.g. `dti.insurance_used` / `dti.hoa_used` / `dti.mi_used` — the effective `override ?? auto` amount,
which the snapshot already computes in `calculations.dti`'s breakdown but does NOT expose to the operand path).
Then each rule compares **what the processor actually used** against **what the source document says** and fires
on a divergence:

| producer (one wave) | unblocks |
|---------------------|----------|
| `dti.insurance_used` (override-applied) | **DT-5, IH-4** |
| `dti.hoa_used` (override-applied) | **DT-2, CO-2** |
| `dti.mi_used` (override-applied) | **DT-3** (vs the LTV-driven requirement) |

- **It is ONE producer pattern, three tags** (one per overrideable housing line) — the LP-410 derived-wave shape.
- **Equivalents exist:** `DtiOverride` covers `housing.taxes` too (would serve a future stated-vs-used tax rule);
  the MI calculator has its own `CalculatorOverride` (`mortgage_insurance` namespace) — the same "surface the
  override" pattern generalizes.
- **Honest value caveat:** once fixed, these fire ONLY when a processor manually overrides a DTI line to
  contradict the uploaded document — a data-integrity / manipulation check, modest but real. The finding's value
  is that they are **recoverable and cheap** (one producer), not that they are high-priority rules.

### The cluster — where the spec set's assumption broke down

Every hit is a **DTI "component-in-the-computation" rule** (DT-2/3/5) or its cross-category duplicate (CO-2 dup
DT-2, IH-4 dup DT-5). The assumption that broke: the author expected a **STATED figure** (what the borrower/1003
claims for insurance/HOA/MI) distinct from the **DERIVED** DTI line — but the system auto-derives every housing
line from the source document and carries no separate stated figure. The ONE place a divergent figure exists —
the processor override — was never surfaced as a fact. The cluster is entirely in the **DTI-component authoring
era**; no hits appear in income/asset/identity/credit (those correctly use stated-vs-documented, two real
sources).

### Overlap boundaries (against LIVE rules)

None of the five overlaps a currently-live rule. The two duplicate PAIRS (IH-4↔DT-5, CO-2↔DT-2) must not BOTH be
written even after the fix — one rule per divergence, or a processor sees the same finding twice (the AS-8/AS-10
noise lesson). If the override producer lands, write DT-2/DT-3/DT-5 and mark IH-4/CO-2 as their duplicates.

## The spec-set recommendation

- **Do NOT mark the five out-of-scope** in `rule_kinds.csv` — that would discard recoverable work. They are
  `needs-producer`, not dead. (This ticket edits nothing; the recommendation is for a future planning pass.)
- **DO update ADR-330 / the census** to record the sharper distinction: the "component vs document" self-compares
  are `vacuous-today-fixable` via the override surface, not `vacuous-inherent`. A future census should count them
  as **1-producer-blocked**, not removed.
- **DO fold IH-4 and CO-2 into DT-5 and DT-2** as declared duplicates (they inherit the same fix and must not
  double-fire).
- **The gate-0 discipline stands** — a self-compare must not ship as-is — but the verdict is "surface the
  override, then write," not "never write."

## Every assumption / decision (esp. inferred)

- **DT-3 is a HIT — from the trace, not the name:** `rule_tags` maps DT-3 → `housing.mi_monthly` (one tag); the
  DTI MI line is `compute_loan_mi().result.monthly_premium`, the SAME calc that produces "required." Both
  operands trace to `compute_loan_mi` → self-compare. (The classification's own words: "the requirement is
  calc-driven.")
- **The override IS the independent operand — CONFIRMED, not inferred:** `dti_override.py` stores a per-`field_key`
  processor figure (`housing.insurance` / `housing.hoa` / `housing.mortgage_insurance` / `housing.taxes`) that
  "takes precedence over the auto value"; `calculations_section.py` carries the effective amount + a
  `source="override"` tag but the `calc` operand path (`_calc_operand`) reads only the headline `value` dict — so
  the per-line override amount is **not** rule-readable today. Fixable, not inherent.
- **MI-1 is `unclear`, not forced:** its planned tags read the calc (vacuous reading) but its intent is the cert
  (independent reading). Flagged, not classified.
- **MI-2 / MI-5 are NOT hits** — the MI factor/structure is a `PMI_STARTER_RATE_BPS` rate-card / pricing value,
  independent of the absent certificate (LP-415, re-confirmed).
- **The ~62 uncounted rules are cleared by construction** (they have no calculator-derived-vs-source shape); an
  exhaustive per-rule list was judged unnecessary for the shape (the three passes are complete for it) — flagged
  as a coverage assumption rather than a per-rule proof.
- No file was modified. This report is the only deliverable.

## What this changes about §13

- **The vacuity toll is NOT 4-5 dead rules — it is 0 dead + a 5-rule cluster recoverable via ONE producer.**
  §13 should carry the five as `needs-producer` (the override surface), not as removed. The writable denominator
  is essentially unchanged (~81); what changed is that a cheap producer converts a "dead" cluster into five
  real (if modest) checks.
- **The structural flaw is real but SMALL and LOCALIZED** — it is the DTI-component authoring assuming a stated
  figure the system doesn't carry, fixable at one seam (surface the override). It is not a pervasive rot across
  the 133-rule set: only the DTI-component family and its two duplicates exhibit it.
- **The census lesson, sharpened again:** gate 0 must distinguish `vacuous-inherent` from `vacuous-today-fixable`
  — collapsing them (as ADR-330 initially did) discards recoverable rules. The right question is not "do the
  operands trace to one field today?" but "**can** the second operand ever be independent?" — and here the answer
  is yes, via an input the system already has and merely hasn't surfaced.
