# LP-624 — the employment record the MISMO states and the import discarded

## The report

Chasing why a Need List item read *"two years of personal tax returns, because contract-basis income
must be qualified from tax history"*, on a file whose application says the borrower is **not**
self-employed.

LF-ABRS's MISMO carries a complete, dated, gapless two-year employment history:

| Employer | Position | From | To | Monthly | Self-employed |
|---|---|---|---|---|---|
| FINRA | Product Manager | 2022-09-01 | 2025-04-27 | $15,125.00 | false |
| Intriq Tech LLC | Associate Director | 2025-04-28 | 2026-02-28 | $16,666.67 | false |
| CFA Institute | Senior product manager | 2026-03-02 | current | $16,000.00 | false |

One day between the first two, two days between the next. Same line of work throughout.

The parser read `FullName` and nothing else. It imported as three bare strings.

## What that cost

* **IN-4** abstained — *"the file does not establish the dates of employment"* — over three start
  dates in the file it had just imported, and LP-623 then seeded a **VOE need** to chase what the
  application already states.
* **IN-7** exists to judge a job change. There is one: the current job started five months before
  application, after two prior positions. It could not see it.
* The **needs AI** proposed two years of personal tax returns, reasoning that contract income needs
  tax history — on a file stating `SelfEmployedIndicator = false` three times. It also described one
  current plus two previous jobs as *"three employers"*, which reads as three concurrent ones. Both
  inferences were reasonable from what it was given.
* **`StatedEmployer.is_current`** has had a column AND a comment naming `EmploymentStatusType` since
  the model was written. Nothing ever populated it. A nullable column nothing writes is
  indistinguishable from one that is legitimately null.

## How it stayed invisible

**The data was never lost.** All twenty employment leaves have been retained in `catch_all` since the
first import. The typed schema never lifted them, and the snapshot reads only the typed sections.

**This is the second instance of one mechanism.** LP-596's own comment, about the real-estate-owned
schedule:

> "The parser has always retained these leaves, but only in `catch_all`, which this section does not
> read and the snapshot therefore never carried. So the rule engine could not see them and AS-4 /
> DT-6 / DT-8 reported they could not determine facts the application states outright."

Word for word the same failure, one section over. The mechanism was named, fixed once, and never
swept.

**And a `couldnt_check` cannot tell the two kinds of missing apart.** "The borrower did not state it"
and "we did not import what they stated" produce the identical sentence. There is no signal anywhere
that says *this fact is in the file but not in the snapshot* — which is why the check added here lives
on the parse, where the difference is still visible.

## What changed

**The parse** — `ParsedEmployer` replaces `list[str]`: name, `is_current` (from `EmploymentStatusType`),
`self_employed`, `classification`, `position`, `start_date`, `end_date`, `monthly_income`,
`special_relationship`. A record with nothing in it at all is dropped; a name-only one still imports,
because that is what every existing file parses to.

**The model + migration** — seven nullable columns on `stated_employers`, additive so existing rows
stay valid. The `readonly.stated_employers` view carries them, or staging cannot see what was just
imported, which is the whole point of the ticket.

**The snapshot** — `borrower.<n>.employer.<m>.*` publishes the full record. This loop was previously
emitting one real field and one permanent null.

**The Need List** — the AI context carries the whole record, and the prompt now says in as many words
that these facts are STATED and must not be inferred: `self_employed: false` means ask for the 1099s
or the contract, not for business returns and a P&L; `is_current: false` is a previous job, not a
concurrent one; continuous dates mean there is no gap to explain.

**A backfill** — `scripts/backfill_stated_employment.py`, report-only by default. Unlike LP-596's,
which skipped a file with any existing row, this UPDATES existing rows in place matched by employer
name, because here the rows exist and are merely empty. It never creates, deletes or renames an
employer, so a name a processor edited is left alone.

## The guard — so the third instance announces itself

`tests/mismo/test_catch_all_holds_no_load_bearing_facts_lp624.py` flags leaves shaped like
underwriting facts — `Indicator`, `Date`, `StatusType`, `ClassificationType`, `Amount`, `Count` —
sitting unreachable in `catch_all`. Run against the real lender fixture, not a synthetic one.

The backlog is **41 fields**, pinned as an equality so a NEW one fails immediately and a LIFTED one
also fails until it is removed from the list. Recorded as debt, not approval. The ones a rule is
already abstaining over:

| Stranded | Wanted by |
|---|---|
| `LiabilityPaymentIncludesTaxesInsuranceIndicator` | DT-6 asks exactly this of a mortgage statement |
| `TotalMortgagedPropertiesCount` | LP-597 DERIVES this from the REO schedule; the export states it |
| `SellerPaidClosingCostsAmount`, `ClosingAdjustmentItemAmount` | FR-3 (interested-party contributions) |
| `SpecialBorrowerSellerRelationshipIndicator` | non-arm's-length; the FR family |
| `CurrentRateSetDate` | CL-1, which is waiting on a rate lock |
| `PropertyMixedUsageIndicator` | PR-3 (property eligibility) |
| `HousingExpensePaymentAmount` | the DTI housing side |
| `BalloonIndicator`, `InterestOnlyIndicator`, `NegativeAmortizationIndicator`, `PrepaymentPenaltyIndicator` | DT-7's ability-to-repay remit |

**The guard earned itself on its first run.** The baseline was generated while this ticket's own parser
change shadowed the borrower's XPath variable (`detail`), which silently stopped `BorrowerBirthDate`,
`BorrowerClassificationType`, `MaritalStatusType` and `DependentCount` being consumed at all. They
appeared as newly "stranded", the guard rejected the mismatch once the shadowing was fixed, and the
four came back out. A parser regression that produced no error and no warning was caught by the check
written for a different reason.

## Deliberately not done

**IN-4 is not auto-satisfied from the stated history.** The MISMO now gives dates, and the gap could be
computed from them — but that answers "has the borrower DISCLOSED a gap", not "is the history
verified", and `income.max_employment_gap_days` reads document-derived dates on purpose. Turning
stated data into a satisfied verification is a stated-vs-verified decision for the domain expert, not
a side effect of an import fix. The data is now available for whichever way that lands.

**The 41 stranded fields are not lifted.** Each needs its own read of what reads it and why; the list
exists so that work is scoped rather than rediscovered.
