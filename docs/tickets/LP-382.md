# LP-382 — Extract employment dates (unblock IN-4's employment-gap check)

## What this ticket is

LP-381's map found IN-4's derived producer (`income.max_employment_gap_days`) already exists and runs — it
resolves `unknown` only because (per the premise) employment start/end dates aren't extracted. **The gate of
record refuted that premise:** the dates ARE extracted (the VOE extractor), the tags read them, and the
producer computes a real gap. IN-4's blocker is **data, not extraction** — exactly LP-381's derived-4 pattern.
So this ticket **reports the refutation and pins the working chain** with a regression test; there is nothing
to extract, no producer change, and nothing is activated.

## Acceptance criteria

- The employment-date → gap → IN-4 chain is proven to work, and pinned so a future extractor rename can't
  silently break IN-4's input (the LP-333/369 trap).
- `income.max_employment_gap_days` computes a real gap given dates, and abstains (`unknown` with a reason)
  below two dated records — never a guessed gap.
- IN-4 reaches a real verdict (fired / satisfied / couldnt_check) on the gap.
- `ACTIVE_RULE_IDS` unchanged; no live rule's verdict changes; full suite green.

## Phase 0 — the argument (premise refuted)

**The chain already works, end to end:**
- **The VOE extractor emits the dates.** `VOEExtraction` has `start_date` / `end_date` (`TypedField[date]`) in
  its `_CORE_SPEC` with `coerce_date` (format-validated — an unparseable date → absent, never a guessed date),
  and it's registered (`"voe": extract_voe`).
- **The tags read them.** `income.employment_start` `{mode: parsed, subject: document, data: start_date}` and
  `income.employment_end` `{… data: end_date}` — LP-369 explicitly "corrected to the VOE extractor's real
  field names."
- **The producer computes the gap.** `_income_max_employment_gap` (loan-level) sorts the (end → next start)
  intervals across all documents and returns the largest. Proven: two VOEs (prior job ended 2024-06-30,
  current started 2024-09-15) → `income.max_employment_gap_days = 77`.
- **IN-4 resolves.** Given the gap tag: `77` → **fired** (beyond the 30-day window); `20` → **satisfied**;
  `unknown` → **couldnt_check**.

### D1 — what dates, from which documents
The **VOE** is the only source, and it already extracts them. Confirmed the negatives: LF-6T3N has **no VOE**;
its **MISMO carries employer *names* but no employment *dates***; there is **no 1003/URLA document extractor**;
pay stubs have **no hire/start date**. So there is no un-extracted employment-date source to add.

### D2 — per-document vs per-borrower (the crux)
The producer is **loan-level** — it aggregates `income.employment_start`/`income.employment_end` across all
document subjects and reports the file's largest gap. This **matches IN-4's spec exactly** ("the largest gap
across the file's employment records … per-borrower is a deferred refinement, LP-323-IN-B"). **So IN-4 does
NOT share the IN-10/IN-11 per-borrower shape gap** — it is loan-level by design. No `_borrower_context` reuse
is needed (it would be wrong here).

### D3 — the field names (the LP-333/369 trap)
Already closed: `income.employment_start` `data == start_date` and the VOE emits `start_date`;
`income.employment_end` `data == end_date` and the VOE emits `end_date`. A test pins this so a rename can't
reopen the silent-death gap.

### D4 — IN-4's threshold
The 30-day window (`employment_gap_window_days: "30"`) is already `priya_validated: false` in the spec ("the
exact window is an agency default pending Priya confirmation"). No change needed — it's already flagged for her.

## Phase 2 — IN-4's resolution (reported, not predicted)

- **Given employment dates, IN-4 resolves to a real verdict** — the chain computes a 77-day gap and IN-4 fires
  / satisfies / couldnt_checks on it (above).
- **On LF-6T3N, IN-4 does NOT resolve** — the file has no VOE and no MISMO employment dates, so the producer
  abstains ("fewer than two dated employment records — no gap to measure"). This is the **honest, correct**
  outcome (a single-or-zero-record file has no measurable gap), and it is a **data** gap, not a wiring one.
  Unlike AS-9 (LP-381), a re-extraction would NOT help — LF-6T3N has no employment-date-bearing document to
  re-extract.
- **IN-4 is activatable the moment a file carries ≥2 dated employment records** (e.g. a current-employer VOE
  plus a prior-employer VOE) — the input resolves, the name matches, the verdict is real. Its bar is a
  no-ai-dependency / wiring decision (LP-380), not a calibration one. **IN-4 is NOT activated here**
  (`ACTIVE_RULE_IDS` unchanged); LP-389 activates.

## What was built

Nothing in production — the extraction already exists. A **regression test**
(`tests/verification/tag_materialization/test_employment_gap_chain_lp382.py`) pins the chain: the tag `data`
names ARE the VOE fields (the LP-333/369 guard for this chain); the loan-level producer computes the gap across
documents and abstains with a reason below two dated records; IN-4 fires / satisfies / couldnt_checks on the
gap.

## Assumptions, decisions, and a reported gap

- **No new extraction** — the premise was refuted; the VOE dates are already extracted, name-matched, and the
  producer + IN-4 already resolve. Inventing an extractor change for already-extracted dates would be wrong.
- **No ADR** — the producer's declared names are correct and its loan-level shape matches IN-4's spec; nothing
  forced a decision.
- **A reported gap (out of scope, and not buildable today):** the loan-level producer reads VOE dates from
  document subjects. A file's PRIOR employment usually lives in the **1003's employment section**, not a
  second VOE — but there is **no 1003 employment extractor** and the **MISMO parser drops employment dates**
  (LF-6T3N's MISMO has employer names, no dates). So a common file (one current VOE + a 1003 with prior jobs)
  cannot compute a gap today. Closing that needs a 1003/MISMO employment-history source AND a producer that
  reads it — a larger change with no data on LF-6T3N to build against. Reported for its own ticket, not
  force-fit here.
