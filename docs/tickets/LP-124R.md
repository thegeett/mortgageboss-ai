# LP-124R — Employer-count matches income items: REPRODUCE the live rule (rule #3)

**Type:** Story · **Epic:** Phase 3.5 / Epic B · **Depends:** LP-122R (pattern), LP-123R (evaluator
patterns), the corrected live-rule audit · **Status:** complete · **Date:** 2026-07-08

## What this ticket is

`xsrc.income.employer_count_matches_items` is one of the **5 live, firing** cross-source rules
(`docs/audits/live-rule-inventory-corrected.md`). This **REPRODUCES** it in the new engine — so, unlike
AS-8 (a self-defined spec), it has a real **parity anchor**: the new verdict must MATCH the live rule.
It is **off our authored list** (no `playbook_id`) — the first step of reproducing live rules in the new
engine toward retiring the dormant old path (LP-161). Tracked in the audit's off-list section (→ BUILT).

## STEP 0 — the reproduced spec (read from the live rule, not assumed)

Live rule `_check_employer_count` (`app/verification/cross_source/rules.py`) + its fact-builder
(`services/cross_source_deterministic.py:225-258`):

- **What it compares (FILE-LEVEL, across all borrowers):**
  - `stated_employer_count` = number of stated EMPLOYERS with a truthy name (`employers[].name`),
    flattened across every borrower (`len(stated_employers) or None`).
  - `income_item_count` = number of INCOME ITEMS whose `employment_income` is truthy, across every
    borrower (`or None`).
  - It is **NOT per-borrower** — it flattens both sides file-wide. This reproduction matches that
    (file-level), deliberately — not "improving" it to per-borrower.
- **Pass/fail (exact, no threshold):** both counts non-zero AND **equal** → no finding; both non-zero and
  **unequal** → FINDING (`{employers}` vs `{items}`).
- **Edge cases (the `None` guard):** if either count is 0 → the live rule returns `[]` (no finding).
  `employment_income` is nullable and `None`/`False` are not counted (truthiness).

## The applicability (wire format — validates under `extra="forbid"`)

```json
{ "scope": {}, "triggers": {}, "required_inputs": [] }
```

**Why empty (STEP 0 corrected the candidate):** the live rule ALWAYS runs and **self-guards** (no-ops
when either count is 0) — it has no trigger or required-input gating. So:

- `scope {}` / `triggers {}` — always relevant (the live rule has no program/purpose/entity gate).
- `required_inputs []` — the counts are over STATED borrower data (income items + employers), which the
  snapshot always loads (0 is a real count, not "absent"); there is no "failed to load" state to guard.
  The honest 0-count handling lives in the evaluator (→ couldn't-check), mirroring the live `None` guard.
  The candidate's `required_inputs: [income_items[].income_type_canonical]` was **dropped**: requiring the
  nullable `income_items[].employment_income` (or a canonical that can be `UNMAPPED`) leaf would send a
  file with a `None`/unmapped item to couldn't-check where the live rule gives a verdict — a divergence.
  (This is `_default_applicability`'s output for a no-program/purpose rule, so the seed already had it.)

## Verdict mapping (updated — round-5 FIX 9)

| case (file-level) | live rule | new engine |
|---|---|---|
| both counts ≥1 and **equal** | `[]` (no finding) | **SATISFIED** |
| both counts ≥1 and **unequal** | **FINDING** | **FINDING** (parity) |
| **exactly one** count == 0 | `[]` (no finding) | **FINDING** — *intentional stricter-than-live divergence* |
| **both** counts == 0 (no employment at all) | `[]` (no finding) | **SATISFIED** (0 reconciles with 0) |

**Parity holds on the mismatch case** (both fire). The **zero-on-one-side case is a DELIBERATE divergence
(round-5 FIX 9, Geet's decision):** a loan file is always created with MISMO / initial income detail, so
employment income with no employers (or employers with no employment income) is a real DISCREPANCY the
live rule's `None`-guard silently misses — the new engine is intentionally stricter and FINDS it. This is
recorded so it isn't "fixed" back to match live. (Original LP-124R mapped the zero case to couldn't-check;
FIX 9 changed it to a finding.) `test_zero_case_is_intentional_divergence_from_live` asserts new fires
while live is silent.

## Assumptions and decisions

- **File-level, not per-borrower** — a faithful reproduction of the live rule (which flattens across
  borrowers). A per-borrower version would be more precise (and avoids the cross-borrower offset where
  one borrower's extra employer masks another's missing one), but that would DIVERGE from the live anchor.
  Noted as a future refinement, not this ticket.
- **Off-list** — no `playbook_id`; tracked in the audit's off-list section (now BUILT), not among the 124.
- **No-employment files → couldn't-check (not doesn't-apply)** — the engine can't trigger on nested
  `income_items` existence (no nested-`entity_exists` support), so a file with no employment income gets
  couldn't-check from the evaluator rather than doesn't-apply from applicability. Still parity-correct
  (no finding); a future nested-trigger or a top-level "has employment income" fact could upgrade it.

## Pattern feedback (reproduction of a live rule + a count-consistency rule)

- **The pattern held** for a reproduction. STEP 0 (read the live rule + its fact-builder) IS the spec —
  and it corrected the candidate applicability (the live rule requires no inputs; it self-guards). The
  lesson: for reproductions, author applicability from what the live rule *actually does*, not from a
  plausible-looking candidate.
- **Live parity is a stronger anchor than a self-defined spec** — the `_new_fires == _live_fires` tests
  are unambiguous, and caught nothing to fix here (the reproduction was clean).
- **A live rule with no playbook layer** exposed a small gap: `confidence_mode` was `None` while the rule
  is deterministic. Handled by defaulting validated-no-layer rules to `deterministic`. Future off-list
  reproductions will hit this too — now covered.
- **No new evaluator-pattern surface** — this rule reads only stated borrower facts (no document fields),
  so the LP-123R typed-materialized-fields pattern didn't apply; the Verdict-enum + no-PII-in-outcome
  patterns did.

## Double-firing gate (round-5 FIX 6)

This rule is enabled in BOTH the live deterministic path AND the new-engine seed, so once the runner
persists (LP-140/162) a single mismatch would create TWO `Finding` rows. `LIVE_PATH_OWNED_RULE_IDS`
(`app/verification/runner.py`) declares the reproduced live rules (this rule + `gift_without_letter`) that
a persist layer MUST skip while the live path still owns them — until LP-161 retires the live path.
Latent today (the runner computes but does not persist); the set is pinned by a test so wiring can't miss
it. Off-list coverage tracking updated in the audit.
