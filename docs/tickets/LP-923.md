## Design

**When a document arrives,** the evidence step runs in the needs update that already follows every
processed document (`tasks/needs._run_needs_update`, per file, serialised, after
`apply_document_to_needs`). The same function, `condition_evidence.check_document`, is callable directly
(tests, the harness).

**Linking (step 1).** A document is linked to every open item on the file that:
- asks for its document type (`item.documents`);
- has not been dropped or completed;
- is still waiting for evidence;
- has a statement month inside the statement's period, or asks for no month.

A statement for the wrong account IS linked, so that the right-account check can reject it with the
reason (Done when). One document answers several items (§4a change 2: the August statement answers 6132,
7086 and 6637's clearance) and is checked once for each.

**Checks (step 2), by code, each passed / failed / not run with a plain reason.** Only the checks the
library names for the item are run. Every input is read from the document's current extraction
(`bank_statement`: `page_count_present`, `page_count_declared`, `account_number_masked`,
`account_holder_name`, `statement_period_*`, `ending_balance`, `transactions`) and the letter.

| Check | Rule | Reason when it passes / fails |
|---|---|---|
| All pages | pages present = pages declared | "pages 1–5 of 6 — page 6 is missing" |
| Right account | last four = the item's (or the reading's) | "Capital One ending 9912, matches the condition" / "ending 4471 — the condition asks for ending 9912" |
| Right borrower | a borrower's first and last name appear in the holder name | "Alex Rivera" / "the statement is in the name of …" |
| Right period | the statement covers the month the item asks for | "Aug 1–31, 2026 — the month right after July, already in the file" |
| Inside the lender's dates | the statement date is not after the letter's asset-document expiry | "statement date 08/31/2026; asset documents expire 10/30/2026" |
| Amount matches | a transaction for the item's amount (6637's check clearing) | "$2,850.00 cleared 08/06/2026" |
| Enough for closing | the linked statements' latest ending balance per account ≥ the letter's required funds (7086) | "verified $41,914.42 against $38,210.40 required" |

- A check whose inputs are missing is **not run**. It is shown as such, and is never counted as passed
  (README).
- The library's other checks (signed and dated, mortgagee clause, VOE window, not expired) are not run
  yet; an item that has any is left for her to accept.

**The large deposit (step 3), by code.**
- A deposit in the statement over **50% of monthly income** (Fannie Mae B3-4.2-02) is a finding on the
  condition. Monthly income is the letter's Verified Income, else the stated income.
- Payroll-like deposits ("payroll", "direct dep", the employer's name) are explained by the statement.
- The finding records the date, amount, threshold, assets without the deposit, and required funds. When
  the deposit is **needed to close** (assets without it are below required), it must be sourced: the
  "No unexplained large deposit" check fails. Otherwise it is noted and can be excluded.
- The file's full verification (rule AS-1) still runs as it always does. This check applies the same
  guideline to the condition's own evidence, so it is flagged before submission.

**Outcome (step 4).**
- An item whose checks all pass is **done**.
- When every live item on a condition is done and it has no open finding, the condition moves to
  **Ready to send** from To do or Waiting. The move is `condition_prep_moved` with `by: "evidence"`.
  This is README rule 5; the lender's track is never touched.
- A failed check leaves the item open, with the reason.

**Her actions (S3-07, S3-08).**
- **Add "please send page 6" to the borrower email.** Adds an item to the condition, and so to the
  borrower's unsent draft: a new draft if the last one was sent (LP-922's accumulation).
- **Accept anyway…** needs a reason, is kept in the history, and marks the item done.
- **Ask the borrower to explain it** adds a "Letter explaining the $4,000.00 deposit on 08/21/2026" item
  to the borrower email.
- **It's already explained…** needs a reason and closes the finding.
- Every action is an event.

**Nothing is drafted by itself.** A re-ask and an explanation request go into the email when she presses
the button. The plan says a re-ask "is drafted", but S3-07 draws it as her button, and drafting on its
own would put a request in an email before she had seen the failure (for example a blank back page she
would rather accept).

**Migration.**
- `condition_evidence`: item, document, condition, checks JSONB, findings JSONB, `status` (checked,
  accepted), the accepting reason and user. It is unique per item and document.
- Event kinds `condition_evidence_checked`, `condition_evidence_accepted`, `condition_finding_answered`.

**Read side.**
- `ConditionPublic.evidence` feeds the sheet's document cards, checks and findings. The sheet's subtitle
  reads "Assets · evidence arrived".
- The Next step token puts "Evidence failed a check — page 6" first (red).
- The summary gains **Failed a check** (open conditions with a failed, unaccepted check): a red cell and a
  filter (`?check=failed`).

**The upload link's documents are processed.** A document the borrower sends through the secure link
was created and never queued for processing (LP-815), so nothing could ever read or link it. It is now
queued as an ordinary upload is.

**What changed from the design while building.** The deposit is not stored among the checks. The first
version appended "No unexplained large deposit" to the item's checks, so on the S3-08 harness shot the
deposit alone made 7086 read "Evidence failed a check" and counted in "Failed a check". LP-934 had
already said the deposit is a finding, not an item check. The row is now derived from the findings when
the sheet reads the evidence, and a test pins that it never counts (it was found by the shot, and is
tested at the API layer where it showed).
