# bug-002 — CR-1 flags every zero-payment tradeline as an undisclosed debt

- **Status:** Both defects fixed — CI green, not yet deployed
- **Date:** 2026-08-27
- **Found on:** staging `LF-AWBB`, verification completed 2026-08-27 03:37 UTC (`staging-fab23e4`)
- **Rules:** CR-1 (19 findings), CR-4 (1 finding)

## What happens

CR-1 enumerates every credit-report tradeline as a subject and asks whether the application states
it. It applies no materiality filter, so an account with **no balance and no payment** is a subject
like any other — and every one of them fires RED as *"the credit report reports this debt but the
application does not state it — an undisclosed liability that changes the debt-to-income picture."*

On LF-AWBB that produced **20 of the file's 21 red findings**.

## Evidence

The arithmetic is exact, which is what makes this a rule defect rather than a judgement call:

| | |
|---|---|
| tradelines on the credit report | 24 |
| carrying a monthly payment | 4 — UWM $3,907, ALLY FINANCIAL $438, BANK OF AMERICA $25, SYNCB/ROOMS TO GO $301 |
| stated on the application | **the same 4**, all matched correctly, none flagged |
| reporting `$0/mo` | **20** |
| undisclosed-debt REDs raised | **20** (19 CR-1 + 1 CR-4) |

Every finding's `load_bearing_tags` carries `liab.monthly_payment: "0"`. One states the case against
itself in its own reasoning field:

```
{"value": "CAPITAL ONE", "tag_id": "liab.creditor_name", ...}
{"value": "0",           "tag_id": "liab.monthly_payment", ...}
{"value": "no",          "tag_id": "liab.in_application",
 "reasoning": "CAPITAL ONE open account with $0 bal…"}
```

The rule read "$0 balance", called it an undisclosed debt, and asserted it "changes the
debt-to-income picture" — which cannot be true of a zero payment.

## Why it is wrong

A zero-balance, zero-payment revolving account is not a liability. Fannie Mae B3-6-01 defines the
set as debts **"of a recurring nature"**; an account with nothing owed and nothing due carries no
recurring obligation, and omitting it from the 1003 is correct practice, not an omission to chase.

Several of the twenty are worse than immaterial — they are duplicates the rule cannot see:

- `MACYS/CBNA` and `MACYSCBNA` — one account, two spellings
- `SYNCB/TJXDC` twice, `CAPITAL ONE` twice
- `UNITED WHSLE MORT` at $0, which is almost certainly the same UWM mortgage the application **does**
  state at $3,907 — reported twice, as a sold or transferred loan routinely is

CR-1's own `how_to_fix` anticipates precisely this ("a duplicate of a liability already stated")
while the rule has no way to detect it.

## The second defect: the Apply button

Each of the twenty findings carries a resolved apply block:

```json
{"action": "add_liability", "holder_name": "CAPITAL ONE", "monthly_payment": "0"}
```

So the file offers a processor a one-click action that writes a **$0 liability onto the 1003**,
twenty times over.

`docs/rule-engine.md` §5.8 wrote the guard for exactly this outcome and it does not catch this
route:

> "A value the subject does not carry means no apply block at all — the button simply does not
> appear… a partially filled `add_liability` would create a debt with no payment."

The guard tests for an **absent** value. Here the tag carries `"0"`, which is present, so the block
resolves — and produces a debt with no payment anyway. Presence was standing in for meaning.

## What is NOT wrong

Worth stating plainly, because the count reads worse than the situation is.

Nothing here escaped its gate. Every finding carries `ratification_pending: true`,
`gated_pending_signoff: true` and `priya_validated: false`, and CR-1 sits in `_LP490A_ACTIVATED`
(`rule_engine/registry.py:260`) — the activated-but-awaiting-sign-off set. The system did what it
promised: an unvalidated rule's output routed to a human rather than asserted. This run is the
evidence that CR-1 needs a materiality filter **before** ratification, not proof that something
shipped broken.

The rule is also right about the thing it exists for. All four payment-bearing tradelines matched
their stated liabilities and none was flagged. The signal works; the subject set is too wide.

## Where the fix goes — the rule, not the enumerator

The tempting fix is a filter in `liability_rows` (`rule_engine/enumerators.py:346`). **Don't.** That
enumerator is a deliberate pure union, and says so:

> "Nothing is matched or merged here — that is a rule's judgment, never an enumerator's."

Fourteen `liab.*` tags and every liability-subject rule read those rows. Filtering there would
silently narrow all of them to serve one, and would hide zero-payment accounts from rules that
legitimately want them — a closed-account or credit-history question needs the row CR-1 does not.

The filter belongs in **CR-1's own declared scope**, which is where the consistency family already
puts this kind of decision: the pipeline is "GATHER tag T across the declared source scope,
**applying the declared filter**" (`docs/rule-engine.md` §5.7). Excluding subjects whose
`liab.monthly_payment` is absent or zero removes all twenty findings and costs nothing real — the
four accounts that matter are all payment-bearing.

CR-4 needs the same filter; it fired once on the same population and reads as the same defect.

Two things to decide when implementing, neither obvious enough to settle here:

1. **Zero versus absent.** A tradeline with no payment field is not the same as one reporting `$0`,
   and today both would be excluded. Absent may deserve `couldnt_check` rather than silence.
2. **Balance without payment.** An account with a real balance but no reported payment is a genuine
   question — a charge-off, a collection, a deferred student loan — and a payment-only filter would
   drop it. The filter should probably be "no payment **and** no balance", which needs a
   `liab.unpaid_balance` tag to be reliably present. LF-AWBB's tradelines carried no balance in the
   extraction, so that is unverified here.

## Impact

A processor opening LF-AWBB sees 21 REDs. Twenty are noise and the one that matters — AS-10, an
account with only one month of bank statements — is buried among them. This is the failure mode that
stops people reading findings at all, and it is worse than a missing rule: a rule that cries wolf
twenty times teaches the reader to skip the twenty-first.

## The third defect: CR-1's text never reaches the UI composed

Found while checking why CR-1's message read as its raw template. `FINDING_PROSE_ENABLED=true` on
staging and the composer runs — the same run composed AS-10 into *"Obtain the missing recent statement
for the account that has only one month of coverage"* from a template reading *"Obtain the missing
recent statement(s) for the short account"*. CR-1's nineteen findings shipped their template verbatim.

The run's own log says why:

```
finding_prose_pass_done  cache_hits=0 composed=105 findings=130
  52 x finding_prose_rejected reason=stating_on_a_review
   9 x finding_prose_rejected reason=editorialising
   2 x finding_prose_rejected reason=unsupported_numbers:1
```

**25 of 130 findings went uncomposed**, and the guard doing it was `stating_on_a_review`:

```python
if not summary.settled and not asks_for_work(composition):
    return "stating_on_a_review"

_ASKING = ("obtain", "confirm", "verify", "review", "check", "upload", "provide", "request", "get ")
```

Every verb there is for CHASING PAPER. CR-1's remediation is not a document request — its how_to_fix
opens *"Add the liability to the 1003"* and its Apply action is literally `add_liability`. The model
wrote exactly that, `asks_for_work` found no approved verb, read a correct imperative as a statement,
and rejected it. The retry could not rescue it either: `_REJECTION_GUIDANCE` named the same short list
back to the model, steering it away from the one verb that fit.

**The fix, in two parts.** `_ASKING` gains the application-edit verbs — add, correct, disclose,
include, update, reconcile, document, remove. Widening serves both readings, which is what makes one
list safe to keep: an action opening "Add …" on a SETTLED finding is work on a pass, and rejecting it
is right.

The second part matters more than the first. **Three places named these verbs and only one was a
list** — the system prompt's settled-finding clause and the retry guidance each restated a
hand-written subset. Widening `_ASKING` alone would have fixed the guard while both instructions went
on steering the model toward the old words. All three now render from `_asking_phrase()`, and a test
asserts every verb in `_ASKING` appears in both.

This is not a CR-1 defect. Any rule whose remediation edits the application rather than requesting a
document hits it, and CR-1 was simply the one with nineteen findings on the file we looked at.

## Adjacent, not this ticket

The `verifications` summary columns (`red_count`, `yellow_count`, `green_count`,
`total_cost_estimate`) are zero/null on **every completed run on staging back to 2026-08-23**,
including this one with 130 findings and 213 AI calls. Pre-existing, unrelated to CR-1, and it means
anything reading those columns reports a clean file. Deserves its own ticket.


## What shipped

| defect | fix |
|---|---|
| every $0 tradeline flagged as an undisclosed debt | `liab.is_payment_bearing` (derived) + a second applicability predicate on CR-1 |
| CR-4 would then disagree with CR-1 | `_credit_undisclosed_tradeline` filters its population through the SAME `_payment_bearing` helper |
| CR-1's text never composed for the UI | `_ASKING` widened; the system prompt and retry guidance now render from it |

The filter went in **CR-1's declared scope**, not `liability_rows` — the enumerator is a deliberate
pure union serving fourteen `liab.*` tags, and narrowing it would have hidden zero-payment rows from
rules that legitimately want them.

Two abstain paths were kept honest rather than collapsed. A tradeline reporting NO payment resolves
"unknown", so CR-1 couldnt_checks it instead of dropping it silently — absent is not zero. And the
rollup distinguishes "no credit report" from "the report's tradelines are all $0"; one message for
both would tell a processor the report is missing when it is present and unremarkable.

13 new tests. Full suite: 5883 passed.

## Still open

- **`liab.unpaid_balance` does not exist**, so the filter keys on payment alone. A real balance with no
  reported payment — a charge-off, a collection, a deferred student loan — would be silenced by it.
  LF-AWBB's tradelines carried no balance in the extraction either, so the "no payment AND no balance"
  form could not be built or tested here.
- **The duplicate tradelines are untouched.** `MACYS/CBNA` beside `MACYSCBNA`, `SYNCB/TJXDC` twice,
  `UNITED WHSLE MORT` beside the stated UWM mortgage. All twenty happened to be $0 and are gone with
  this filter, but a DUPLICATE PAYMENT-BEARING pair would still produce two findings for one debt.
- **Nothing re-verified on staging yet**, so the 20-findings-to-0 claim is reasoned from the data, not
  observed. `./scripts/deploy staging verify LF-AWBB` after deploy is what settles it.
