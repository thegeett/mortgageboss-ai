# LP-332 — Borrower-keyed materialization + the borrower_id ↔ MISMO-index resolution

The highest-value follow-on: it fixes the #1 false-green (PIN #1), activates ID-8 (Wave-1's debt) and IN-1,
and makes every future family's per-borrower rules activate for free. A DESIGN ticket — the argument is in
Phase 0 below. It changed engine code (a producer + a snapshot fact), so — per the discipline — every such
change is called out loudly here.

## What it is

Per-borrower rules were authored + evaluated but could not ACTIVATE: LP-331 built the judgment CONSUMER
(`_per_borrower` reads `by_subject[borrower_id]`) but nothing PRODUCED borrower-keyed tags, and
`produce_derived_tags` was loan-only. This ticket builds the producer side + the prerequisite resolution.

## The design argument (options, code evidence, the choice)

### D1 — the resolution (a schema gap, FIXED not worked around)
**Evidence:** MISMO keys borrowers `borrower.{n}` where `n` is a re-derived SORT POSITION
(`sorted(borrowers, key=(borrower_position, id))`, `mismo_section.py`), and the snapshot carried NO link
back to a `belongs_to` UUID — `BorrowerRef` is `{borrower_id, name}` only, and its docstring explicitly
rejects cross-section name-matching as an anti-pattern. So there was no snapshot-internal resolution.
**Choice:** emit `borrower.{n}.borrower_id` (`str(borrower.id)`) into MISMO — deterministic, PII-safe (a
UUID, not identity data), the ONLY non-name-matching link. **The failure mode (the heart of the ticket):**
a group with no id link, or a DUPLICATE/blank id → the borrower is SKIPPED → its tags absent →
couldnt_check, NEVER a guessed attribution (misattribution fabricates or hides a discrepancy — worse than
abstaining). Asserted in `test_missing_id_link_skips_the_borrower_never_guesses`,
`test_duplicate_id_link_skips_the_ambiguous_borrower`, and end-to-end in
`test_id8_couldnt_check_when_the_id_link_is_missing`.

### D2 — the mechanism: generalize the derived producer (REUSE, option a)
**Evidence:** the parsed/AI producers ALREADY enumerate the subject registry (`producer.py` does
`subject_type(decl.subject).enumerate(...)`); only `produce_derived_tags` was loan-special-cased.
**Choice (option a):** the derived producer now enumerates the declared subject via the same registry —
mirroring how **LP-327** generalized judgment from single-subject to declared enumeration. A new `borrower`
subject type enumerates borrowers by the id link, reads `borrower.{n}.*`, and lets a borrower recipe gather
that borrower's `belongs_to` documents. **Option (b) rejected** (a bespoke gather-for-recipes): it invents
a second mechanism where generalizing the existing one suffices — the divergence risk LP-331 rejected.

### D3 — the recipe contract
`(snapshot) → (v, r)` became `(snapshot, subject_id, subject_raw) → (v, r)`. Loan recipes accept + ignore
the two new args — logic identical. `_app_required_fields_present` is the regression canary
(`test_loan_recipe_unchanged_regression_canary`). Loan- and borrower-level recipes coexist.

### D4 — the 4 income recipes
- **IN-1's shortfall → per-borrower** (fixes PIN #1). The recipe reads THIS borrower's MISMO stated income
  + gathers its own documents' `income.documented_monthly`. SIGNED (a raise is negative → never fires).
- **IN-2 (recency), IN-4 (gap) stay loan-level** — the most-recent paystub / any gap are legitimately
  file-level screens.
- **IN-3 (YTD) has the SAME latent masking as IN-1** — reported as a small follow-on (per-borrower YTD
  annualization), not expanded here to keep scope on the pinned #1.

## New generalization gap (reported, not patched)

**Borrower-set reconciliation:** a `belongs_to` borrower not present in MISMO (or a MISMO borrower on no
document) is not evaluated for per-borrower income — the borrower subject enumerates MISMO, the judgment
enumerates `belongs_to`. Today this fail-closes (couldnt_check for the unmatched borrower), which is
honest; a full reconciliation (union the two borrower sets) is a small follow-on.

## What this implies for future per-borrower rules

Any family's per-borrower rule now activates for free: a borrower-level fact is a `{mode: parsed/ai/derived,
subject: borrower, ...}` declaration; the borrower subject materializes it under `borrower_id`, and the
LP-331 consumer reads it. The arithmetic pattern (ADR-273) generalizes to per-borrower via a borrower
recipe. The lever LP-323-IN-C named has landed.
