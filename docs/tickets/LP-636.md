# LP-636 — five defects behind LF-ZE9N's document processing

- **Ticket:** LP-636
- **Status:** SPECIFIED. Nothing built.
- **Date:** 2026-08-29
- **Scope:** Backend — `ai/client.py`, `ai/classification.py`, `tasks/document_processing.py`, `ai/extraction/`, `services/pdf_utils.py`

## The report

A processor uploaded 44 documents to **LF-ZE9N** (staging, 2026-08-30 00:28–00:31 UTC) and asked
why several stayed "Processing / uncategorized" and why others were tagged **needs review**.

Nothing was stuck. Every document reached a terminal status: **34 completed, 10 `needs_review`.**
The ten flagged documents are four separate defects wearing one badge.

A fifth was found while diagnosing them, and it is the one that raises no flag at all — four
documents that classified as `unknown` with high confidence, completed cleanly, and produced no
typed data. Those four are inside the 34 "completed", not inside the 10.

| # | Defect | Documents on this file | Severity |
|---|---|---|---|
| 1 | A cached HTTP client's connection pool outlives the per-task event loop | 5 re-run by hand | **High** — every burst leaves rework |
| 2 | Every transient failure is labelled `rate_limited` | mislabels all 5 | **High** — sent the diagnosis to the wrong place |
| 3 | An absent extraction confidence is read as zero confidence | 4 falsely flagged | **Medium** — 13% of good extractions sent to review |
| 4 | Documents are capped by page count, never by payload size | 1 rejected | **Medium** |
| 5 | A confident `unknown` discards the model's own better answer | 4 silently untyped | **High** — no flag, no signal, no typed data. **FIXED** |

They are one ticket because they were found in one investigation and four of the five are in the
same call path. They are independently fixable and independently shippable.

**Defect 5 is the one with no safety net.** The other four end in `NEEDS_REVIEW`, which a processor
sees. Defect 5 ends in `completed` with no `processing_error` and nothing in the review queue.

## What was ruled out first

The five uncategorized documents carry `infra_failure = "rate_limited"`, so the obvious reading is
that the burst exceeded the Bedrock quota. **It did not.** Recorded here so nobody re-derives it:

| | |
|---|---|
| Account quota | 10,000 cross-region requests/minute; 5,000,000 tokens/minute |
| Daily cap | 27,000,000 tokens |
| Actual that day | ~90 calls; **657,607 tokens** across 33 extractions |
| HTTP 429s in the window | **zero** |
| HTTP 200s in the window | 189 |

`bedrock_rpm_budget = 2000` is our own pacing backstop, divided across four worker slots — it is a
self-imposed ceiling, not a grant, and at these volumes neither it nor the AWS quota was close to
binding.

## Defect 1 — the connection pool outlives the event loop

**Not silent, and not data loss — say it precisely.** An earlier draft of this ticket called it
silent data loss. It is neither. The affected documents reach `NEEDS_REVIEW` and a processor sees
them, which is LP-462's gate working exactly as designed; nothing is deleted and every one is
re-runnable. The real cost is **manual rework proportional to burst size, attached to a cause label
that points at the wrong thing** (defect 2). That is worth fixing on its own terms without
inflating it.

**The evidence.** 91 failures in the 15-minute window, all the same shape:

```
ai_call_failed  attempt=1  error_type=APIConnectionError  latency_ms=4  transient=True
```

Latency distribution: `1ms ×13  2ms ×29  3ms ×8  4ms ×10  5ms ×7` … max 808ms.

**A connection that fails in 1–5 milliseconds never reached AWS.** A throttle is an HTTP 429
*response*; a timeout takes seconds. These failed before meaningful network I/O.

**The mechanism.** Two facts that do not compose:

- `run_async()` is `asyncio.run(coro)` — **a fresh event loop per Celery task, closed when the task
  ends** (`tasks/base.py:41`).
- `get_anthropic_client()` is `@lru_cache(maxsize=1)` — **one process-wide httpx client whose
  connection pool persists across those loops** (`ai/client.py:204`).

The pool retains keep-alive connections whose transports are bound to loops that have since been
closed. A later task picking one up fails instantly.

**The corroboration is in the same repo.** The database layer hit exactly this and solved it:

```python
engine = create_async_engine(str(settings.database_url), poolclass=NullPool)
# "so no connection is shared across loops"
```

The DB uses `NullPool` for this reason. The AI client kept a shared pool.

It also explains the shape a quota problem would not: intermittent (~33% of attempts), usually
recovered by retry (78 failed at attempt 1, 7 at attempt 2, **6 exhausted all three**), and only
under burst — more tasks means more loops created and destroyed, so more stale connections.

**PROVEN, 2026-08-30.** An earlier draft of this ticket called the mechanism a strong hypothesis
and asked for `APIConnectionError.__cause__` to be logged to confirm it. That was not necessary —
it reproduces locally in a few lines, and the reproduction is the evidence.

One `httpx.AsyncClient` behind an `lru_cache(maxsize=1)` (the shape of `get_anthropic_client`),
called from eight successive `asyncio.run()` calls (the shape of `run_async`), against a
keep-alive HTTP server:

```
task 0: 200
task 1: FAILED  RuntimeError: Event loop is closed
task 2: 200
task 3: FAILED  RuntimeError: Event loop is closed
...
succeeded=4  failed=4
```

**The alternation explains itself, and matches production.** A task opens a connection; its loop
closes; the next task takes that dead connection from the pool and fails instantly; the failure
evicts it; the next task opens a fresh one and succeeds. The Anthropic SDK wraps
`RuntimeError: Event loop is closed` as `APIConnectionError`, which is exactly what the worker
logged — and it fails without network I/O, which is why the latencies were 1–5 ms.

Production saw ~33% rather than 50% because the SDK's pool sets `keepalive_expiry=5.0`: a
connection idle for more than five seconds is dropped anyway, so only tasks arriving inside that
window inherit a dead one. Under a burst, many do.

**`client.py:228-236`'s verification was not wrong, it was too gentle.** It measured "one client
issuing SUCCESSFUL requests across three separate `asyncio.run()` loops returned 200 each time".
Three sequential calls, each slow enough to clear `keepalive_expiry`, will pass every time. The
bug needs consecutive calls inside five seconds — which is a burst, which is exactly when it
matters.

**The fix.**

**Preferred: disable keep-alive**, `limits=Limits(max_keepalive_connections=0)` on an injected
`http_client`. Verified against the same reproduction — 8 of 8 succeed with it, on the same cached
client. It is the exact decision the DB layer already made with `NullPool` (do not reuse
connections), it needs no conditional logic, and it removes the whole class of bug rather than the
one path we found: any script, bench or test that runs its own loop is covered too. The cost is a
TCP+TLS handshake per call, which against a multi-second model call is noise.

**Two traps in doing it**, both of which would be silent regressions. Injecting an `http_client`
replaces the SDK's own defaults with httpx's, so both must be restated explicitly:

| | SDK default | httpx default if not restated |
|---|---|---|
| Timeout | `connect=5, read=600, write=600, pool=600` | **`5s` flat** |
| Limits | `max_connections=1000, max_keepalive_connections=100, keepalive_expiry=5` | `max_connections=100, keepalive=20` |

A 5-second read timeout would break every call that streams for longer than five seconds, which is
most of them. `max_connections` must stay at 1000.

**Alternative considered: key the `lru_cache` on the running loop.** Preserves keep-alive where it
is safe (the API's long-lived loop) but needs a weak-keyed cache to avoid a client per task leaking
forever, and leaves the bug latent wherever a new loop appears. Not worth the complexity for a
handshake.

**Rejected: retry harder.** Treats the symptom, and six documents already exhausted three attempts.

Prefer 1. Whichever is chosen, the fix needs a test that creates and closes several event loops
against one cached client under concurrency — the missing test is what let this ship.

## Defect 2 — `rate_limited` means "something transient", not "throttled"

`infra_failure_kind()` (`ai/client.py:345`) returns `INFRA_RATE_LIMITED` for **any** transient
cause: HTTP 429, Bedrock throttle codes, **5xx, connection errors and timeouts**. Its own docstring
says so.

So the activity log's *"Classification incomplete (rate_limited) — needs review"* actually meant
*"the connection died"*. The label is what made defect 1 look like a quota problem, and it is the
single line a reader would trust most when triaging.

`_is_transient` deliberately folds these together for the **retry** decision, which is correct — all
of them are worth retrying. The error is reusing that same predicate as an **observability label**,
where the distinction is the whole point.

**Fix.** Split the label from the retry predicate. `INFRA_RATE_LIMITED` only for a genuine 429 or a
Bedrock throttle code; add `INFRA_CONNECTION` for `APIConnectionError`/timeout and `INFRA_SERVER`
for 5xx. Retry behaviour must not change — only the recorded cause. Also log
`APIConnectionError.__cause__`, which defect 1 needs anyway.

`ai/extraction/bank_statement.py:460` branches on `reasoning == INFRA_RATE_LIMITED`; check every
such consumer before renaming, and keep the persisted vocabulary migrated or tolerant of both.

### The cutover, for anyone querying across it

The labels are **additive, not migrated**. A rename would rewrite history that was true as
recorded, and old rows stay readable — but it leaves an asymmetry worth stating, because the
string is identical on both sides and the data alone cannot locate the boundary.

**Before this deploy**, `rate_limited` meant *any transient cause* — throttles, connection
failures and 5xx together. **After it**, `rate_limited` means a genuine 429 or Bedrock throttle
code, and connection / server_error carry their own labels.

| | |
|---|---|
| Cutover commit | `5a11d0f` (+ `4dfd1cd`, and the branch-order fix that followed review) |
| Merged on | 2026-08-30 |
| Deployed to staging | **not yet — fill in the `staging-<sha>` tag and date at deploy** |

So a query asking "how often were we throttled?" over a window spanning the deploy over-counts
the older half. Bound the window at the deploy tag above, or treat pre-cutover `rate_limited` as
"transient, cause unknown" — which is what it actually was.

The same applies to the bench: `record["rate_limited"]` keeps its historical name and its
"re-runnable" meaning, with the honest cause now alongside it in `record["infra_kind"]`. Records
written before this change have no `infra_kind` key at all, which is the cleanest way to tell the
two eras apart.

## Defect 3 — an absent confidence is read as zero confidence

**The mechanism.** `coerce_confidence()` (`ai/parsing.py:61`) collapses a missing or non-numeric
value to `0.0`. The review gate at `tasks/document_processing.py:522` then evaluates
`0.0 < _CONFIDENCE_THRESHOLD` (0.5) and flags the document `NEEDS_REVIEW` with
`processing_error = "extraction low confidence"`.

The honest value is computed 87 lines earlier and used only for persistence:

```python
reported_confidence, confidence_source = document_confidence_provenance(result.confidence)
# a model that omitted confidence → (None, ConfidenceSource.NOT_PROVIDED)
```

LP-201 went to real trouble to keep absence honest in storage — `NOT_PROVIDED` is documented as
*"no confidence available — absence is a legitimate state"* — and the gate immediately re-conflates
it with zero. The four documents on LF-ZE9N flagged this way all read
`extraction_status = succeeded, confidence = NULL, confidence_source = not_provided`: the extraction
worked and captured typed fields.

**It is systemic, and it is not per-type.** Across every current successful extraction in staging:

| document_type | extractions | no confidence | reported |
|---|---|---|---|
| `w2` | 20 | **7** | 13 |
| `mortgage_statement` | 11 | **3** | 8 |
| `drivers_license` | 7 | **2** | 5 |
| `hoa_statement` | 3 | **2** | 1 |
| `property_tax_bill` | 4 | **1** | 3 |
| 15 other types | 70 | 0 | 70 |

**15 of 115 (13%).** The same extractor both reports and omits, so this is model
non-determinism rather than a missing schema field for particular types. Thirteen percent of good
extractions are being sent to manual review with a reason that is not true — which is how a flag
teaches processors to ignore it.

**Fix.**

1. **Gate on the pair, not the coerced float.** Flag only when
   `confidence_source is MODEL_SELF_REPORTED and reported_confidence < threshold`. Both values
   already exist at line 435.
2. **Decide the policy for absence explicitly.** Silently treating absence as good is not obviously
   right either. Measure first: compare field-fill rates between `not_provided` and
   `model_self_reported` extractions *of the same type*. If absence does not predict worse data,
   do not flag. If it does, flag with a distinct reason — `"extraction confidence not reported"` —
   so the two are separable in the UI and in every audit, which is impossible today.
3. **The same defect exists one layer up.** `document_processing.py:216` applies the same threshold
   to *classification* confidence through the same `coerce_confidence`. It has not bitten because
   every classification returned a number, but it is the identical latent bug.
4. **Backfill.** The 15 already-flagged documents can be cleared once the gate is fixed;
   `api/documents.py:235` already clears a stale `processing_error`.

## Defect 4 — capped by page count, never by payload size

One document — a 23.8 MB executed purchase contract — was rejected with HTTP 400 and recorded
`infra_failure = "oversized"`.

**It did not fail on pages.** Classification already caps at 15 pages
(`classification_max_pages = 15`, applied via `cap_pdf_pages` at `classification.py:178`) and it
*still* returned 400. So the cap was a no-op — the document was already within 15 pages, i.e. a
high-DPI scan — and **size in bytes was the binding constraint**. Base64 inflates a payload by a
third: 23.8 MB → ~31.7 MB, plus prompt overhead, against a 32 MB limit.

**There is a page cap. There is no byte cap anywhere.**

**And typed extraction caps nothing at all.** `cap_pdf_pages` is called from exactly two places —
`classification.py:178` and `generic_analyzer.py:194`. A long document that classifies fine on its
first 15 pages can still be rejected at extraction, which applies neither cap.

### Chunking does not solve this, and would make it worse

Worth stating plainly, because it is the natural first idea. LP-628's chunked extraction
(`ai/extraction/chunked.py`) **does not split the file**:

> WHAT IS NOT SPLIT IS THE DOCUMENT. Every chunk receives the WHOLE file and is told which pages to
> report on.

Slicing was rejected deliberately — a slice cannot see the account header, the "page 4 of 12"
footer, or the running balance carried in from earlier pages.

So chunking addresses an **output** limit: a bank statement whose transaction list overflows the
response ceiling. Applied to an oversized **input** it would issue N calls each carrying the same
rejected payload.

**Fix.**

1. **A byte-aware cap before the call. DONE.** `fit_pdf_to_payload_budget` caps by pages, then
   keeps halving the page count until the base64 payload fits. Applied to classification and
   Tier 3.

   Implemented by DROPPING pages rather than downsampling them, which is the safe answer rather
   than the best one: re-rendering at a lower DPI would keep every page, which matters for a
   contract whose signature is on the last one, but it needs image resampling with its own
   quality and OCR trade-offs. Dropping pages needs none, reuses the tested slicing path, and
   turns a hard rejection into a partial read. Downsampling is the follow-up if that proves
   insufficient.

2. **Apply a page cap at typed extraction too. NOT DONE — and the ticket was wrong to ask.**

   `document_processing.py` already carries a documented decision against exactly this, with an
   ADR behind it (LP-473): a 069-style multi-document PACKAGE keeps its 1003 liabilities and REO
   deep in the file, so capping there "trades an honest crash for SILENT wrong data". Since this
   cap works by dropping pages, applying it to a typed extractor would produce precisely that.

   An OVERSIZED failure at typed extraction is not a dead end: LP-471 falls it back to Tier 3,
   which IS byte-capped now, so the document still gets read.

   That makes the trade sharper than "partial data versus none". It is **a generic read of the
   whole document versus a typed read of the first N pages** — and the second is worse, not
   because it captures less, but because **typed data reads as authoritative**. A generic read
   that says nothing about liabilities is honest; a typed liability extraction that silently
   missed page 60 is a coverage gap presented as a finding. The fallback means refusing the cap
   costs nothing.

   The boundary is marked in the code so nobody "completes" this later.

3. **`chunked.py` has the same exposure and is NOT covered.** Recorded so the omission does not
   read as considered-and-safe.

   Chunked extraction sends the WHOLE document to every chunk by design (`chunked.py:178`, and
   line 264 passes the full `content` with `cache=True` per chunk). So a bank statement over the
   byte budget fails on **every chunk, not one** — the payload is full-size per request, and the
   cache breakpoint saves tokens, not bytes on the wire.

   This cap cannot fix it: trimming pages is precisely what chunking exists to avoid, since the
   point is reading all of them. It needs a different fix — the splitter, or per-chunk page-range
   payloads instead of whole-file ones.

4. **True page slicing** — unchanged as a future option.

**What this actually fixes for LF-ZE9N.** Its 23.8 MB contract failed at CLASSIFICATION, so it
never reached an extractor. With the byte cap, classification now succeeds and the document gets
a type. If its typed extraction then fails oversized, the Tier 3 fallback is byte-capped too, so
it no longer fails for the same reason — the document ends up read rather than blank.

A scanned contract is a rasterisation problem, not a splitting problem.

### Separately: generalising chunking is still worth doing

Not required by any defect here, and not to be conflated with them. `run_chunked_extraction` is
already generic; `bank_statement.py` supplies the type-specific merge, and the merge is the real
work — it needs the same "claim a row only if it *begins* in this chunk" discipline that avoids
double counting without needing row identity. Candidates are the types whose output scales with
content: `tax_return`, `mortgage_statement`, `closing_disclosure`. Its own ticket.

## Defect 5 — a confident `unknown` discards the model's own better answer

The other four defects end in `NEEDS_REVIEW`, where a processor sees them. **This one ends in
`completed`.** No `processing_error`, nothing in the review queue, nothing to notice. It is listed
last and ranked first-equal for that reason.

**What happened.** Four documents classified `unknown` at high confidence and routed to Tier 3
free-text analysis instead of typed extraction:

| Document | Classified | Confidence | Catalog has |
|---|---|---|---|
| `DL.pdf` | `unknown` → `misc` | 0.90 | `drivers_license` — **Tier 1**, `BORROWER_INFO` |
| `CD - 7112 -1.pdf` | `unknown` → `misc` | 0.85 | `closing_disclosure` — **Tier 1**, `DISCLOSURES` |
| `Credit report invoice.pdf` | `unknown` → `misc` | 0.85 | `credit_report` — **Tier 1**, `CREDIT` |
| `Earnest Money _ EMD Receipt image.pdf` | `unknown` → `misc` | 0.90 | `earnest_money_receipt` — **Tier 1**, `ASSETS` |

Each of those four types is present in `documents/catalog.py` as Tier 1, and
`render_classification_prompt()` puts all ~80 catalog types in the system prompt — so the model was
shown the right answer and did not take it.

**Why nothing caught it.** This is by design, and the design is right as far as it goes
(`classification.py:16-19`): a *low-confidence* result means "unsure which known type" →
`NEEDS_REVIEW`; a *high-confidence* `unknown` means "confident it is none of the known types" →
Tier 3. Confidence, not the `unknown` slug, decides. The review gate at
`document_processing.py:214` only tests `type_mismatch` and `confidence < 0.5`, so a confident
`unknown` sails through to `_route_by_tier`, hits the catalog default, and **completes**.

That contract is sound when the model is right. It has no answer for a model that is confidently
wrong.

**The signal we already collect and then throw away.** LP-463 added `document_name` to the
classification result — the model's free-text name for what the document actually is, produced
**before** it makes the constrained pick. Its own docstring (`classification.py:72-74`) says it is
*"a more reliable signal than the constrained pick"* and that **"on an `unknown` this names the
missing catalog type."**

That field is used for the `type_matches_document` self-check and then dropped. It is not persisted
on the document, not written to the activity log, and not logged — `classification_succeeded` emits
`confidence`, `document_type`, `model_category` and `type_matches_document`, and nothing else.

So the system very likely knew `DL.pdf` was a driver's licence, in a field built to say exactly
that, and discarded it.

**This is unproven, and it cannot be proven from the current data.** Because `document_name` is
persisted nowhere, there is no way to check retrospectively what the model called those four
documents. That is itself the first thing to fix, and the reason this defect has been invisible:
the failure leaves no trace anywhere.

**Fix, in order.**

1. **Persist `document_name`. DONE.** Stored on the document — but NOT in the activity detail as
   proposed, and not logged. It is model prose and can carry a borrower name, which the C7 scrub
   cannot catch (it matches identifier SHAPES, and a name is not digit-shaped), and activity detail
   is readable through `readonly.activity_logs`. Excluded from the readonly views alongside
   `summary` / `generic_analysis`, and in `NEVER_EXPOSED` so a later migration cannot re-add it
   quietly.

   Consequence to be honest about: this did NOT make the value queryable through
   `deploy staging query`, so "turns this from unmeasurable into a query" was too strong. What is
   queryable is how OFTEN a confident `unknown` happens; knowing WHAT it was requires reading model
   prose, which that path must not return.

2. **Reconcile against the catalog. DONE, as a FLAG, never as an applied type.**

   `match_catalog_type()` matches a free-text name against catalog slugs: normalise, then require
   every word of the slug to appear IN ORDER. Deliberately conservative — one-word slugs are
   ignored entirely (`survey`, `appraisal`, `w2` appear inside ordinary prose), there is no fuzzy
   distance and no stemming, and order is load-bearing so *"a receipt for the earnest money"* does
   not match `earnest_money_receipt` while *"Earnest Money / EMD Receipt"* does.

   **The type is surfaced, never applied**, and that is the load-bearing decision. Applying a type
   from a text match would put a wrong schema on a document — the T4→w2 harm LP-463 exists to
   prevent — and this is a text match, not a judgement. A false positive here costs one review; a
   false positive in an auto-applied version costs wrong data. The human applies the type through
   the LP-44 override.

   Two details found while building it, both of which had silently lost a real case: an apostrophe
   must be DELETED rather than turned into a space (`"driver s license"` matched nothing), and the
   match must allow gaps in order rather than require a contiguous phrase (`"Earnest Money / EMD
   Receipt"` has a word wedged mid-phrase).

3. **Flag rather than complete. DONE.** A confident `unknown` whose name names a catalog type now
   takes the path a flagged document already takes — read via Tier 3, terminal `NEEDS_REVIEW`,
   needs NOT advanced — with `suggested_type` in the log. All four LF-ZE9N documents match; LP-463's
   own correct declines (wire instructions, HOA budget, compensation summary, condo declaration) do
   not, and there is a test for each so a future fuzzier matcher fails rather than quietly making
   `misc` unreachable.

**Two caveats before treating this as four clean misses.** `Credit report invoice.pdf` may
genuinely be an *invoice* for a credit report rather than the report, in which case `unknown` is
defensible. And nobody opened any of the four — the filenames are suggestive, not proof. Confirm
against the documents before sizing the work.

**Also worth measuring once (1) lands:** how often a confident `unknown` happens at all. On this one
file it was 4 of 44 (9%), and each cost the typed extraction of a Tier-1 document.

## Suggested order

1. **Defect 5, step 1 only** — persist `document_name`. An hour's work, no behaviour change, and
   until it lands the whole defect is unmeasurable.
2. **Defect 1** — it costs work on every burst, and it scales with the size of the upload.
3. **Defect 5, steps 2-3** — the only failure here that a processor cannot see.
4. **Defect 3** — 13% of good extractions sent to review is actively training processors to
   distrust the flag.
5. **Defect 2** — cheap, and it is what cost this investigation its first stretch.
6. **Defect 4** — real but rarer; needs the byte cap designed rather than guessed.

Defects 1 and 2 touch the same file and should probably ship together — the extra logging that
proves 1 is the same logging 2 needs.

## How this was found

`LF-ZE9N` (`82ca98ed-3310-4097-b9c4-abad953c14a7`), staging, via `./scripts/deploy staging query`
against the `readonly.*` views, plus the `/ecs/mbai-staging/worker` log for the window
2026-08-30 00:25–00:40 UTC and `aws service-quotas` for the Bedrock limits. The per-document causes
are in `readonly.activity_logs` — `detail->>'infra_failure'` — which is the LP-462 audit trail doing
exactly what it was built for.
