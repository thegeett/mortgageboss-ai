# LP-817 — Template library

- **Ticket:** LP-817 · Phase 4, M1, ticket 4 of 26
- **Status:** Built — awaiting review
- **Date:** 2026-09-06
- **Plan:** [`phase4-build-plan.md`](../phases/phase4-build-plan.md) LP-817 section
- **Design:** [`phase4.md`](../phases/phase4.md) §6 (the audit record)
- **Scope:** `app/communications/` (new package), `decisions.md`
- **Migration:** none.

Spec 4.1 names five templates and none existed. The plan states the sharp edge plainly: LP-810's
compliance scanner falls back to "the plain template" and no ticket defines one — and since the AI
drafting flag ships **off**, that is not a fallback, it is the default path for every draft.

---

## What was done

### The five templates, as files

`initial_documentation_request`, `reminder_follow_up`, `status_update`,
`condition_response_request`, `custom` — under `app/communications/templates/`, one file per
`(key, version)`, all at `v1`.

Files rather than Python, on the same reasoning as prompts (LP-38): they are iterated on by a person
who should not have to touch code, and they diff cleanly in review. The file format is an email — a
`Subject:` line, a blank line, then the body — so a reviewer of a template edit sees what a borrower
will see.

### What "the plain template" is

Stated here because nothing else states it: **it is not a sixth file.** It is this module — a
deterministic render of whichever template the draft names, from structured data, with no model
involved. Recorded in the module docstring rather than left as an assumption, because the plan
identifies its absence as what would make M1 render nothing.

### Versioning that is enforced rather than documented

Each `(key, version)` carries a SHA-256 of the file as shipped, and a test refuses a file whose
content no longer matches. ADR-401 has the reasoning; the short form is that the audit record names
a *version*, so a wording change under a fixed version makes every historical row claim an email
said something it did not, and nothing else in the system can detect that.

### The security line, in all five

The execution protocol's fixed decisions require borrowers to be told email is not secure.
`SECURITY_NOTICE` is one constant appearing verbatim in every template, asserted on the **rendered**
body rather than the file, because the rendered body is what the borrower reads.

It cautions and offers a way out; it does **not** steer to an upload link. That is LP-815's, and a
link that resolves to nothing would be worse in an email than no link — the same reasoning ADR-398
gives for not attaching documents. A test pins that the notice contains no URL and no mention of a
link, so the day LP-815 lands, adding the steer is a deliberate edit and a version bump.

### `render_document_block` — where LP-800 stops being a data structure

The catalog knows what to call each type, where to get it, what "all of it" means and how it usually
arrives wrong. None of that reaches anyone until something renders it. This is the `$document_list`
a borrower reads.

**It refuses any type the borrower does not hold.** Every type it turns away is one they cannot
obtain — a lender-ordered appraisal, a title commitment, an employer's VOE — so the ask would waste
a round trip and cost their confidence in the rest of the list. An uncataloged type is refused by
the same rule rather than a special case: LP-800 defaults it to the processor, and a document nobody
has classified is not one to ask a borrower for.

## Decisions

### `render` refuses a missing variable instead of leaving a gap

`string.Template.safe_substitute` would leave `$inbox_address` sitting in the body of a real email,
and nothing downstream inspects a rendered body for leftovers. `substitute` raises, and `render`
checks the declared variables against the context first so the error names what is missing. A bug in
the caller should surface before a send, not after.

### The declared variable set is compared against the file, both ways

A placeholder in the file that the spec does not declare is never supplied, so it survives into the
sent body. A declared variable the file does not use makes callers assemble context for nothing and
hides that the template stopped using it. Neither raises on its own; a test refuses both.

### `RenderedTemplate` carries its own identity

Subject, body, key and version travel together rather than `render` returning a string. The audit
record has to name the template and version that produced the body it stores, and handing back a
bare string would let a caller record one template's identity against another's words with nothing
downstream able to tell.

### Only three templates take an inbox address

The two asks and the condition request. `status_update` asks for nothing and `custom` is free text,
so neither declares the variable — and a test asserts that, as the control for the test that the
other three do carry it. Without the control, an address in all five would satisfy the positive test
and say nothing about whether the distinction is real.

## Tests

`tests/communications/test_templates_lp817.py`, 36 tests. Shaped by what reaches an inbox without
raising anywhere: an unsubstituted placeholder, a template edited under a fixed version, a document
list asking for an appraisal, a catalog slug where an English name belongs.

`test_no_slug_survives_into_the_block` renders **every** borrower-held type in the catalog (113 of
them) and asserts no underscore appears, with a pinned floor so an empty fixture cannot pass it.

Verified by mutation, each killed:

| Mutation | Result |
|---|---|

## Assumptions

- **The wording is a first pass and Priya has not seen it.** Same standing as LP-800's party
  assignments. LP-822 brings the tone profile and is where her voice actually lands; these five are
  written to be correct and plain rather than to sound like her, and the version pin means her edits
  arrive as `v2` with `v1` still reconstructible.
- **`condition_list` and `status_summary` are pre-rendered by the caller.** LP-810 knows the
  conditions and the file's state; this module knows how to lay out a document list and nothing else.
- **All five templates carry the security notice, including `status_update`.** The protocol's
  decision says the templates carry the line without qualifying which. A status update asks for
  nothing, so the line is arguably noise there — but a borrower may still reply with a document, and
  the wording works in that position. Recorded rather than quietly narrowed.

---

## Deliberately not done

- **No HTML.** Plain text only. Multipart is a rendering concern for the send path (LP-811), and a
  second body per template would double what a version pin has to cover.
- **No template selector UI.** LP-812 lists one in the compose flow.
- **No `template_url` values in LP-800.** Still `None` everywhere; the blank forms a gift letter or a
  4506-C needs are files to be hosted, not templates to be rendered, and nothing serves them yet.
- **No non-borrower document block.** LP-820 owns those paths and will want its own; the guard here
  exists so this one cannot quietly become it.
- **No `v2` of anything.** Five templates, one version each.

## For the reviewer

The three standing reviewer checks:

- **Tenancy** — no `company_id` anywhere; no database access at all. `render` reads a file and
  substitutes strings.
- **Message content in logs** — no logging added. Worth stating explicitly for this module: the
  rendered body is borrower-facing content, and the audit record (LP-811's, not built here) is the
  only thing that should ever hold it.
- **AI in the decision path** — none, and this is the module that establishes there is a path
  *without* AI at all. `render` is deterministic; a test asserts two renders of the same input are
  byte-identical.

The judgement calls worth a second opinion, in the order I would attack them:

1. **`render_document_block` refusing non-borrower types.** It is a guard I added inside my own new
   API rather than one the plan asked for. I think the scope is exactly right — every type it
   refuses is one the borrower cannot obtain — but it makes the function unusable for LP-820 by
   design, and if you read that as the wrong seam it is cheaper to change now than after LP-810
   depends on it.
2. **The version-pin mechanism (ADR-401).** It makes a typo fix require a version bump. I argue that
   is the cost of the guarantee; the counter-argument that trivial edits should be free is not
   unreasonable, and if it wins, the pin should probably move to a normalised hash rather than be
   dropped.
3. **The security notice in `status_update`.** See Assumptions. Following the protocol's decision
   literally, where narrowing it would have read better.

**The build plan gives LP-817 no "Done when" clause** — the same gap you recorded for LP-802.
Acceptance was judged against the section's prose: five templates exist, they are versioned, the
initial request carries the address line M3 depends on, and the plain template is defined.

## Review (second session, protocol §3)

Three findings, all in the template text — which is where the ticket asked for eyes, and correctly:
the code, the version pin and the guard are sound, and the tests around them are the strongest in
Phase 4 so far. Every finding below is a sentence a borrower reads that no test could have judged.

### A — A promise the product does not keep

`initial_documentation_request.v1` said: *"Anything sent to that address is filed against your loan
automatically, so it reaches us even when we are away from our desks."*

Not true, and not true on the plan's own terms. LP-806 gives triage a per-file `auto_accept_inbound`
flag that **defaults to false**, so an emailed document lands in a queue and a person accepts it into
the file. Nothing is automatic about it. And today it is further from true than that: `rg` finds no
ingest, routing or triage code in the tree at all — the address accepts nothing until LP-803 through
LP-806 land in M2/M3, while these templates ship in M1.

Rewritten to claim only what routing will actually do: *"Anything sent to that address reaches your
loan file directly, so it does not get lost even when we are away from our desks."* The address line
itself stays — the plan requires it, and M3's routing depends on it being there.

**Escalation, not a fix (protocol §2.2, and it belongs to the plan rather than this ticket):** M1
can send an email advertising an inbox that does not receive mail until M3. The critical path has
LP-811 (send) inside M1 and LP-803/805 inside M2, and nothing sequences the two. Worth deciding
before M1 ships rather than after a borrower emails documents into a void.

### B — A statement about the borrower's own application, in text nothing scans

`condition_response_request.v1` said: *"They are not a sign that anything is wrong with your
application."*

That is a claim about this file's standing, which is not a processor's to make and may not survive
underwriting. The reason it matters more here than in an ordinary email: **LP-810's compliance
scanner falls back to "the plain template", so template text is the one borrower-facing path nothing
ever scans** — and with the drafting flag off by default it is not the fallback, it is the only path
M1 sends on. Anything a scanner would have caught, a template ships unread.

Narrowed to a fact about underwriting rather than about them: *"Conditions are a normal part of
underwriting, and most files have them."* The reassurance survives; the claim about their file does
not.

Added `test_no_template_makes_a_claim_nothing_scans`, a deny-list at the layer that would otherwise
skip the scan — application-status language (`approved`, `denied`, `guaranteed`, `wrong with your`,
`on track`) and over-promises about what the system does with what they send (`automatically`,
`instantly`).

One note on how that test was arrived at, because the first version of it was decoration: my initial
deny-list contained `nothing is wrong`, and the sentence I had just removed reads *"anything is
wrong"*. Restoring the original wording left the new test green. The list now carries
`wrong with your`, and restoring the sentence fails it.

### C — The status update offered a route out of something it never asked for

`status_update.v1` opened with *"nothing is needed from you in this message"* and then carried the
security notice — an offer to arrange another way to send, when nothing had been requested. The
builder flagged this as arguable noise and followed §5 literally rather than narrowing it. Following
§5 was right; the placement was the problem.

The notice stays verbatim in all five, and is now positioned after *"If you have any questions, just
reply here"* — the one thing the template does invite, and the only way anything sensitive could
travel. Pinned by `test_the_status_update_does_not_ask_and_then_offer_a_route_out`.

### The builder's three, ruled on

1. **`render_document_block` refusing non-borrower types — right seam, keep it.** I checked the
   guard's scope against its stated purpose rather than accepting the description: it refuses
   exactly the types whose party is not `BORROWER`, and LP-800's party map is precisely the
   statement that the borrower does not hold those. Nothing over-wide, nothing missed. Raising
   rather than filtering is also right — a caller passing a mixed needs list has made a mistake, and
   a silent filter would send a borrower a list with items quietly dropped. LP-809/810 must
   partition by party before calling, and the exception is what will tell them so on the first run.
2. **ADR-401's pin — keep as written.** A typo fix costing a version bump is the guarantee working,
   not a defect in it. One caveat now that these are re-pinned: the hash is over raw bytes, so a
   whitespace-only rewrite by a pre-commit hook breaks the pin. That surfaces as a clear test
   failure rather than a silent drift, which is the right failure.
3. **The security notice in `status_update`** — see finding C. Kept, moved.

**Re-pinning rather than bumping to v2.** Three files changed here, and ADR-401 says changing the
words means adding a version. I re-pinned `v1` instead, deliberately: no email has ever been rendered
from these templates, no audit row references `v1`, and the ADR's guarantee is about historical
records staying checkable. A `v2` whose `v1` was never sent would be a dead file and a misleading
audit trail of its own. The version mechanism starts from the reviewed text. The next edit bumps.

### Done when, and the standing checks

**LP-817 has no "Done when" clause** — the second in Phase 4, after LP-802. Judged against the
section's prose, as the builder did: five templates exist as versioned files, the plain template is
defined and is this module, and the initial request carries the address line M3 depends on. All met.
Worth adding the clause to the plan rather than each reviewer re-deriving it.

The three standing checks pass: no `company_id` handling anywhere in the package; no logging at all,
so no message content in logs; no AI — the renderer is `string.Template` and a file read, which is
the entire point of it being the scanner's fallback.
