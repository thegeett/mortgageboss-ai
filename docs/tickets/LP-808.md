## The third inversion, and a builder sanctioned it

§3.5 named two places allowed to derive ownership from something a stranger sent, said a third was a
blocking finding, and said that **if a third is ever sanctioned the line must be amended in the same
commit.** `resolve_connection_by_address` is that third; the line is amended in this commit; and the
argument is here so a person can reverse it rather than to settle it.

**Route B cannot work without one.** Its whole shape is that a customer's admin routes their own
alias to an address we minted. Mail arrives at `co-<token>@` with no session and no user, and the
token is the only thing that says whose it is.

**Where it matches §3.5's stated test:** one function; unknown, revoked, soft-deleted, wrong-domain
and malformed all collapsing to one answer; and the resolved row being the only thing that says
whose the data is.

**Where it is weaker, stated rather than glossed:** the other two resolve a loan *file*, and §3.5's
test says so in those words. This resolves a **company**. A wrong answer from the other two misfiles
one message; a wrong answer from this one puts a message in the wrong company's queue. Two things
narrow that and neither removes it — the connection decides only the *company* (the file still comes
from the ladder), and the token is 128 bits matched on both halves of the address as `inbox_token`
is.

It was a builder, not a human, who decided this. That is in the escalations.

## What a forwarded message's authentication is worth

§2.3 forbids reading `Authentication-Results` out of a message body, because RFC 8601's security
section says a stranger can write one claiming `dmarc=pass`. Route B is the single exception: the
message was authenticated at the borrower's own provider *before* the forward, and by the time SES
sees it every original signal is gone.

So `services/original_hop.py` is entirely about why that header might still be a lie:

- **SPF is never evaluated, and there is no field it could be read from.** A forward always fails
  SPF — the connecting IP is the forwarder's. Reading it is meaningless in both directions: a fail
  says nothing about the borrower, and a *pass* says the forwarder is who they claim, which we knew.
  Absence is enforced by the dataclass having no such field, which is stronger than parsing and
  ignoring it.
- **Only the first `Authentication-Results`.** RFC 8601 §5: headers are prepended, so the first is
  the forwarder's own. Anything below was in the message when they received it. The test writes the
  attacker's `dmarc=pass` *below* a real `dmarc=fail` and asserts the fail wins.
- **ARC only from an allowlisted sealer.** An ARC seal is a claim by whoever sealed it, so "trusting
  the chain" is exactly "trusting these domains" — a closed set, in code rather than settings, so
  widening it is a review and not an environment variable.
- **A surviving DKIM signature is worth more than any of it**, because it is checkable rather than
  asserted. What is implemented is *alignment*, not verification: the `d=` tag against `From:`, with
  relaxed organisational-domain matching. Verifying the cryptography needs a DNS lookup on the ingest
  path whose timing an attacker chooses. What alignment buys is narrow and real, and the docstring
  says which half is missing.

### The control found the bug

`test_an_arc_chain_from_an_allowlisted_sealer_is_read` failed on first run. RFC 8617 puts the
instance number first — `ARC-Authentication-Results: i=1; authserv-id; …` — so the parser was reading
`i=1` as the authority, which is in no allowlist. **Every ARC chain was being refused**, and the
"a stranger's seal is ignored" test passed exactly as it would against a working allowlist.

That is the fourth time this loop has met the same shape, and the first time the control was written
before the code was believed.

## Ladder rungs 3–5, and why they are scoped when 1–2 are not

Rungs 1 and 2 match on something unguessable — a 128-bit token, or a message id we generated — so
the match itself proves which company. Rungs 3, 4 and 5 match on a display id, a sender address and
a subject line, **none of which is unguessable**, so company scoping is the only thing between
`[LF-7K3M]` in a stranger's subject and whichever company happens to hold that id.

`_scoped_files` returns nothing when the company is unknown. Returning "all files" is what an
unscoped query does naturally, and it is the cross-tenant failure this exists to prevent.

Rung 4 requires **exactly one** matching file. A borrower with two files in progress is ordinary, and
picking either would file half their documents wrongly while looking confident.

Rung 3 reads the stored `.eml` for the footer tag, and never raises: storage being unavailable
degrades that rung to "no match" rather than failing the ingest, because an unrouted message is
recoverable in one click and a crashed task is not.

## A forward is judged on its original hop

`decide_disposition`'s auto-accept condition read SES's `dmarcVerdict`. On a forwarded message that
verdict is about **the forwarder** — a Google or Microsoft tenant, which essentially always passes —
so reading it would make every Route B message look authenticated whoever actually sent it.

`_sender_authenticated` asks the right question per path, and the original hop's findings are
recorded under `originalHop*` keys rather than overwriting SES's. Both are kept because they answer
different questions, and merging them is precisely the confusion the module exists to avoid.

## The guided flow is guidance, not automation

There is no button that creates a routing rule, because there cannot be one: on Google it needs
`gmail.settings.basic`, a *restricted* scope requiring a CASA assessment; on Microsoft a rule created
through Graph is blocked by the default external-forward policy, and asking an admin to relax that is
asking them to disable a standard exfiltration control.

So: mint the address, render the provider's exact click-path with the address substituted in, and
offer to mail it. The Google steps say **admin routing rule**, not user-level forward — a user-level
forward makes the target confirm a mailed code, which nobody here can do. The Microsoft steps say
**mail flow rule**, not inbox rule — inbox forwarding to external addresses has been blocked by
default since 2021, and sending an admin there sends them to a dead end and then to us.

The "email these steps" field is an address a processor types, not the current user. §3: the person
who can make the rule is usually not the processor, and defaulting to the caller makes the button a
no-op for the case it exists to serve.

**Verification has no button.** It flips when mail arrives. A button would let somebody mark a
connection working before the rule existed, and the staleness banner — which exists because the
failure here is silent — would then never fire. Re-sending the steps never moves a verified
connection backwards: asking a colleague to check the rule is not an outage.

**Staleness needs the connection to have worked once.** One that never received anything is
*unfinished*, not stale, and "no mail received in 4 days" describes a failure that has not happened
while hiding the one that has.

## Deliberately not done

- **Rung 6 (the AI suggestion) is not built.** §2.2 grades it "low, never auto-accepts", and the
  standing rule is that the model may classify and extract but may not decide. There is no source
  for a suggestion today — which is LP-807's open escalation, unchanged.
- **DKIM signatures are checked for alignment, not verified.** See above; the cryptographic check
  needs a DNS lookup on the ingest path. **Escalated.**
- **Nothing sends the connection steps.** Like LP-815's nudge, there is no transport (INFRA-3
  unapplied). The endpoint records the state change and logs; the mail itself waits on LP-816.
  **Escalated.**
- **No staleness sweep.** `is_stale` is computed on read, so the banner appears when somebody looks.
  A Celery beat that notices without being asked belongs with LP-814's reminder scheduler.
- **Route C is a schema, not a feature.** `cursor`, `watch_expires_at` and `encrypted_refresh_token`
  exist unused, per the plan, so Gmail or Graph is a service rather than a migration against a table
  with live rows.

## For the reviewer

- **Tenancy** — this ticket adds the third inversion and amends the rule that governs it. That is
  the finding to make if you disagree with it; the shape test is in §3.5 and the argument is in
  `services/mailbox_connections`'s docstring.
- **Message content in logs** — the new lines carry connection ids, a provider and a refused ARC
  authority (a domain, not content). Never the address, which contains the token.
- **AI in the decision path** — none.

Worth a second measurement:

1. **`TRUSTED_ARC_SEALERS`.** Membership is decided by being in a constant, reviewed like code. The
   list is Google and Microsoft because those are the two providers Route B supports and a forward's
   first hop is one of them by construction. A customer on a third provider gets no ARC trust and
   falls back to DKIM alignment — which I think is right, and is a real limitation.
2. **Rung 3 reads the stored message.** It is the only rung that touches storage, it fails soft, and
   it runs on every message that missed rungs 1 and 2.
3. **The Microsoft steps say "Bcc the message to".** That is the transport-rule action that
   preserves the original recipient; "Redirect" would take her copy away. Worth a second reading by
   somebody who has used the Exchange admin center.
