# LP-376-A — Restore the force-run link (the escape hatch from a cache that can't see engine changes)

## WHAT THIS TICKET IS

The "Re-run anyway" link — which forces a verification run past the input-fingerprint cache — had vanished
from the UI. It is the only escape hatch from a real trap: `compute_input_fingerprint` hashes the
cross-source inputs, so when the documents haven't changed a Run returns the cached run and enqueues nothing —
even though the **engine** changed (LP-366/369/371/372/374 all landed after run `01039e93`). The cache serves
findings from a version of the engine that no longer exists, presented as current. Without the force link,
there is no way to see the current truth. (The cache key itself needing to be rule-aware is **LP-377**, not
this — this restores the escape hatch only.)

## PHASE 0 — WHAT WAS ACTUALLY WRONG (it was not removed)

- **The link is still in the code**, unchanged since **LP-88 (`5644bf1`)**: `verification-panel.tsx` renders
  "Re-run anyway" → `run.mutate(true)` → `POST …/verification/run?force=true`. **LP-376 did not touch it** —
  `git show` of both LP-376 commits shows the header/escape-hatch untouched.
- **The backend force path is fully intact:** `run_verification(..., force: bool = False)`; `if not force and
  last is not None and last.input_fingerprint == fingerprint: return cached`. On the force/cache-miss path it
  enqueues **both** passes — `_enqueue_cross_source` **and** `_enqueue_rule_engine` (LP-365) — on one run.
- **The actual bug — a conditional-visibility gate.** The link rendered only under:
  ```tsx
  {data?.latest_run?.status === "completed" && !running && ( … Re-run anyway … )}
  ```
  LF-6T3N's latest run `01039e93` is **`failed`** (it timed out; `completed_at` 02:53). So `status ===
  "completed"` was false → the link was hidden. **The escape hatch appeared only after a *completed* run and
  was hidden after a *failed* one — precisely when forcing a re-run is the only way forward.** The default
  button doesn't rescue you either: it caches against the last *completed* run (2026-07-08), so it returns a
  stale cached run and enqueues nothing.

**Verdict:** not removed, not a refactor casualty — a pre-existing visibility bug in the render condition. The
backend force path was never touched.

## WHAT WAS RESTORED

`verification-panel.tsx` — broadened the render condition so the hatch is available whenever a prior run exists
and we're not currently running (completed **or** failed):
```tsx
{data?.latest_run != null && !running && ( … Re-run anyway … )}
```
Restoring the literal original (`=== "completed"`) would NOT have helped — the run is `failed`, so it would
still be hidden. Same place, same behaviour (force, bypass the cache, both passes), now available after a
failure. **No backend change** — the force path already did the right thing.

## ASSUMPTIONS / DECISIONS + HONEST NOTES

- **No backend change** — the force path (`?force=true`, both-pass enqueue) was intact; only the frontend
  visibility gate was wrong.
- **Equivalence:** no engine/rule/tag/spec change; `ACTIVE_RULE_IDS` unchanged; the normal (cached) path
  unchanged.
- **The out-of-band run's status.** I ran only the governed pass (not the cross-source sweep), so the new run
  `b35d02f3` is not a complete two-pass run; I marked it `failed` with an explanatory `error_detail` rather
  than leave it stuck `running` or fake a `completed` (which would be a run-level false-green the architecture
  forbids). Its findings — the current governed truth — persist. A proper full re-run (both passes) is what
  the restored button now enables through the real endpoint.
- **The cache key is still broken and is LP-377's.** The fingerprint hashes cross-source inputs only; the rule
  engine reads a superset, so an unchanged-document / changed-engine state still cache-hits. This ticket only
  restores the manual escape hatch; a rule-aware fingerprint is the real fix (its own ticket).
