# LP-520 — a judgment finding must state its question

**Built.** Two changes to how a finding reads, both found by a processor reading LF-WCHG's live output.
`verdict_labels` on `JudgmentEval` (validated total over `value_domain` at load), adopted by AS-12;
`_money` always renders cents.

One defect found while building, worth recording because it is the ticket's own subject matter turned
on itself: adding the new validator **orphaned LP-516's `exempt_unless_judgment_in`-outside-domain
check** behind an early `return self`, so it silently stopped running for every rule without labels.
Caught by an existing test, fixed, and pinned by
`test_the_exempt_override_domain_check_still_runs_on_an_unlabelled_rule` — asserted on an *unlabelled*
rule specifically, since that is the case that broke.

## 1. A bare verdict value is unreadable — the main item

The finding on staging today says:

> the AI judged **'yes'** — an AI verdict a human must ratify (it never auto-ships); $2,000 is above
> the $1,316.67 (10% of $13,166.67 qualifying income) materiality floor

Judged **what**? The message never states the question. And on AS-12 the polarity is the opposite of
the intuitive one: `yes` means *"this may be borrowed funds"* (the bad answer) and `no` means fine. A
reader has no way to know that, and a different judgment rule could invert it.

The same value is also rendered as a bare chip in the provenance card, via the `output_tag` load-bearing
entry LP-376-B adds — so the reader meets an unexplained `yes` / `no` / `unknown` twice.

`_verdict_message` renders `value` raw because it is generic across every judgment rule and has nothing
rule-specific to say. The fix is to let the spec say it, matching the rules-as-data pattern:

```yaml
judgment:
  verdict_labels:
    "yes":     this deposit may come from an undisclosed borrowed source
    "no":      this deposit does not appear to come from a borrowed source
    "unknown": the tags do not support a confident judgment
```

Reading, with LP-518's derivation intact:

> the AI judged that **this deposit may come from an undisclosed borrowed source** — a human must
> ratify; $2,000.00 is above the $1,316.67 (10% of $13,166.67 qualifying income) materiality floor

**Validation at load**, following `exempt_unless_judgment_in`'s precedent: every key must be in
`value_domain`, and the map must be **total** over it. A partial map silently falls back to the raw
value for the missing answer — which is the failure this ticket exists to remove, reappearing only on
the rarest verdict, where nobody would notice.

**Additive.** A spec declaring no `verdict_labels` keeps today's text exactly, so this can land on
AS-12 first and spread rule by rule. Every active judgment rule should eventually carry one; AS-12,
OC-2, CR-8 and DT-7 are the ones a processor sees on LF-WCHG today — all four confirmed `judgmental`
in `rule_kinds.csv`. **DT-6 also shows `needs_review` there and is deliberately out of scope**: it is
`structural`, so its verdict comes from a deterministic outcome branch with its own written reasoning
template, not from a model answering a domain value.

The provenance chip should use the same map, so the card and the message cannot disagree.

## 2. Always show cents

`judgment._money` prints `$2,000` when the cents are zero and `$1,316.67` otherwise. **No precision is
lost** — $1,999.87 renders in full, and the comparison always uses the unrounded value — but a reader
seeing `$2,000` cannot tell whether it is exact or rounded, and on a fraud-adjacent finding that doubt
is not worth the tidier line.

Change to always two decimals. One line, one test.

The floor itself is still *displayed* rounded to the cent ($1,316.667 → $1,316.67), which is correct:
`_resolve_floor` compares `observed > fraction * basis` at full `Decimal` precision and only the
rendering is quantized. Worth a comment so nobody later "fixes" the comparison to use the rounded value.

## Not in this ticket

**The three-cards-per-rule complaint.** LF-WCHG shows AS-12 as three separate cards in Needs attention.
That is the *old* `rule_id + message` grouping key — its five findings carry three distinct messages
(`'yes'`+$2,000 / `unknown`+$2,000 ×3 / `unknown`+$3,000), which is exactly three groups. LP-518's
`groupByRule` keys on the rule alone and renders one card. So this is a **deployment gap, not a code
gap** — confirm the frontend rebuilt before opening any work on it.

Note that item 1 above also *reduces* message variety: with `verdict_labels`, findings sharing a
verdict share a sentence, so more of them collapse under the shared-message path.
