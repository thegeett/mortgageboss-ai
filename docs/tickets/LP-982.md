# LP-982 — Receive on mail.staging.mortgageboss.ai

- **Ticket:** LP-982, the second of the step-1 tickets in `loan-email.md` §15.
- **Status:** code only. Not applied. Receiving stays off (`inbound_mail_enabled = false`).

## What and why

`mail.staging.mortgageboss.ai` can already send: the `outbound_mail` module verified it as an SES
identity with DKIM, DMARC and a bounce domain. To receive on it, the domain needs one more DNS record:
an MX that points at SES's inbound server for our region. LP-981 already built the receiving side
(bucket, receipt rule, queues), and that rule accepts mail for every verified domain, so this record
is the only missing piece.

The record is created only when receiving is switched on (`inbound_mail_enabled`). An MX tells the
world "deliver mail here", so it must not appear before the bucket and receipt rule exist. This is
the same shape every customer domain will use: a verified identity that sends, plus one MX to
`inbound-smtp.<region>.amazonaws.com`.

## What changed

- `infra/modules/outbound_mail/variables.tf`: new `receive_enabled` (bool, default `false`).
- `infra/modules/outbound_mail/main.tf`: new `aws_route53_record.receive_mx`, counted on
  `receive_enabled`: MX on `send_domain`, TTL 600 like the other records, value
  `10 inbound-smtp.${var.aws_region}.amazonaws.com`, with a comment on the gate and on why it does not
  conflict with the bounce MX (a different name).
- `infra/envs/staging/main.tf`: `receive_enabled = var.inbound_mail_enabled` in `module "outbound_mail"`.

No `receive_mx_fqdn` output: the module outputs domain names (`send_domain`, `bounce_domain`) but no
Route 53 record names, so per the brief it was skipped.

## What this does NOT do

- No `terraform apply`. Receiving stays off, so the record is not created.
- The receipt rule set is not activated. That is a manual, once-per-account step (LP-989).
- No change to SPF, DKIM, DMARC or the bounce domain's records.
- No change to `inbound_mail`.

## Follow-ups

- **Stale comments in `outbound_mail`, left alone because the brief said nothing else.** The module
  header still describes three non-overlapping subdomains: `inbox.<parent>` receives, `mail.<parent>`
  only sends, and `bounces.<parent>` is a sibling. The `send_domain` description says it is separate
  from the inbound domain and that "an outbound identity overlapping an inbound MX is the documented
  cause of an infinite mail loop". After LP-981 and this ticket, `mail.` both sends and receives, and
  the bounce domain is `bounces.mail.`, nested rather than a sibling. The loop risk AWS documents is a
  MAIL FROM domain that receives mail; ours (`bounces.mail.`) keeps its own single MX to
  `feedback-smtp`, so bounces never reach the receipt rule. The comments should be rewritten to say
  that, after checking the loop claim against the AWS page it came from.
- **The KMS gap from LP-981** (no `sns.amazonaws.com` grant on the shared key) is still open, and it
  must be fixed before receiving is switched on, or mail will be stored and never queued.
