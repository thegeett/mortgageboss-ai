# LP-413 — The DTI must not assume monthly on an unrecognized HOA frequency (a live 12× miscalculation)

## What this ticket is

`services/dti.py` `_extracted_hoa_monthly` normalized an HOA amount by its stated frequency but **defaulted an
unstated/unrecognized frequency to MONTHLY** (`divisor.get(frequency, 1)`). An HOA statement reading "600" with
a frequency string the map didn't recognize was treated as **$600/month** — if it is actually annual, the DTI
**overstated housing expense 12×**, silently, in a number that drives qualification, with **no cross-check**.
This is **live code** (the `/dti` card + the reserves/max-loan calculators), not a new tag. LP-407-2 found it
(ADR-328) and its `housing.hoa_monthly` tag already fails closed on the same input — the correct behaviour had
a reference implementation next to the bug.

The fix: an unstated/unrecognized frequency with a present dues amount now **gates** the DTI (the LP-375
degraded/unknown channel) — never a silent monthly assumption, never a silent drop to $0.

## D1 — what the DTI returns, and can it express "uncertain"?

Yes. `DtiCalculation` carries `gated: bool` + `gate_reason`, driven by the LP-375 machinery: a housing line
marked `unknown` → `gated_labels` → `gated=True`; `gate_display_ratios` then nulls the headline ratios at the
API boundary. So the honest degraded/flagged channel already existed — the fix routes the HOA-unconvertible case
into it (via a new `_AutoLine.unknown` flag), no new return type needed.

## D2 — who consumes the DTI (the blast radius)

| consumer | reads | honors gate? | effect of the fix |
|----------|-------|--------------|-------------------|
| `api/dti.py` — the **/dti card** (LIVE UI) | `build_dti_calculation` + `gate_display_ratios` | ✅ | an unconvertible HOA → card shows *unknown*, not a 12×-wrong number |
| `finding_impact.py` — before/after DTI preview | `build_dti_calculation` + `gate_display_ratios` | ✅ | consistent (nulled when gated) |
| `calculators.build_reserves_view` (feeds AS-4, LIVE) | `dti.housing_payment` directly | ❌ **ignores `.gated`** | gets HOA=0 → understated PITIA — **but this is the pre-existing behaviour for absent taxes/insurance too**; a NEW gap, not introduced here (out of scope) |
| `calculations_section.map_dti` → `snapshot.calculations.dti` | re-gates on `_REQUIRED_DTI_TAGS` only | ❌ HOA not required there | the snapshot DTI would not gate on an unconvertible HOA — **but NO live rule reads `calculations.dti`** (only AS-4 reads `calculations.reserves`; AS-1 uses the `dti.qualifying_income_monthly` loan_tag). A recorded gap; the ticket is scoped to the DTI service. |

**No live rule reads the DTI calc as a gated operand.** The live surface is the `/dti` card (fixed) and the
finding-impact preview (already consistent).

## D3 — the chosen behaviour: GATE (reject "drop the HOA")

In a calculation there is no "unknown number", so **fail closed = the gated/degraded state** (D1's channel),
which withholds the ratio rather than fabricating one. **The "drop the HOA to 0" option is rejected explicitly:**
HOA is *not* in `_REQUIRED_HOUSING_KEYS`, so a bare `return None` falls through `_to_items` to `auto or 0` — a
silently **smaller** housing expense that makes the borrower look **more** qualified (the invisible, dangerous
direction). Overstating (the status quo bug) is visible and conservative; understating is not; the honest answer
is neither — **withhold the number (gate).** Cost: for an unconvertible-frequency HOA the `/dti` card degrades
to *unknown* (a visible nudge to fix the frequency or override the line) instead of silently over/understating.
The processor can override the HOA line with the true figure (an override is trusted, clears the gate).

## D4 — the same bug elsewhere? No.

The HOA line is the ONLY DTI input that defaulted a **periodicity**. `_extracted_monthly` (taxes/insurance)
divides by 12 under `annual=True`, but that is the **field's contract** — `annual_tax_amount` / `annual_premium`
are annual *by name*, so ÷12 is definitional, not a guessed default. P&I is computed; MI comes from the MI
calculator (already monthly); income (`monthly_amount`) and debt (`monthly_payment`) are monthly columns. **No
sibling assume-a-periodicity site.** (Two out-of-scope consumer gaps are recorded in D2 — the reserves calc and
the snapshot `map_dti` — both pre-existing and read by nothing that this fix makes newly wrong.)

## D5 — what "unrecognized" looks like; why the map is NOT widened

The DTI's map covers `monthly / quarterly / semiannual / semi-annual / annual / annually`. Real HOA statements
also say "per month", "mo.", "/month", "yearly", "per year", etc. — so widening would have value. **But the map
is deliberately NOT widened here:** it is **byte-identical** to the frozen `housing.hoa_monthly` tag's
`_HOA_FREQUENCY_MONTHS` (LP-407-2, out of scope to change), and widening the DTI beyond the tag would make the
**calculation looser than the tag** — the exact ADR-328 discipline this ticket extends. I keep them identical,
fail closed on everything else, and add a **drift-guard test** asserting the two maps stay equal. A joint
widening (moving both the tag and the DTI together) is a future both-move ticket. **Widening is complementary,
never a substitute for failing closed.**

## What changed

- **`services/dti.py`** (the fix):
  - `_HOA_FREQUENCY_MONTHS` hoisted to a module constant (byte-identical to the tag's), **no default entry**.
  - `_extracted_hoa_monthly` → returns `tuple[Decimal | None, bool]` = `(monthly | None, present_but_unconvertible)`;
    an unstated/unrecognized frequency with present dues → `(None, True)`.
  - `_AutoLine` gains an `unknown: bool` flag; `_auto_housing_lines` sets it from the second return value.
  - `_to_items` ORs the line's own `unknown` flag into `DtiLineItem.unknown` (a data-driven gate, cleared by an
    override) — so `build_dti_calculation` gates on it via the existing `gated_labels`.
- **Comment-only** touch to two LP-407-2 files (`tag_materialization/derived.py`, `rules/tag_production.yaml`):
  past-tensed the "the DTI defaults to monthly" notes to "the DTI originally defaulted … LP-413 fixed it" so the
  codebase no longer carries the same under-documented-default hazard this ticket exists to remove. **No tag,
  producer, map, or behaviour changed** — the tag's logic and map are byte-identical.
- **`decisions.md`** — ADR-329 (+ a back-reference from ADR-328).
- **`tests/services/test_dti.py`** — `_seed_hoa` helper + 7 tests.

## THE BEFORE/AFTER (reported)

HOA dues **600** at each frequency; the DTI housing-expense contribution (base file: P&I 277.78 + taxes 300 +
insurance 100 = 677.78 before HOA):

| dues_frequency | HOA line — BEFORE | HOA line — AFTER | DTI |
|----------------|-------------------|------------------|-----|
| `monthly` | 600 | **600** (unchanged) | computed |
| `quarterly` | 200 | **200** (unchanged) | computed |
| `semiannual` | 100 | **100** (unchanged) | computed |
| `annual` | 50 | **50** (unchanged) | computed |
| `"per annum"` (unrecognized) | **600** (÷1 monthly assumption — the 12× bug) | **unknown → GATED** | ratios nulled |
| *(unstated / field absent)* | **600** (÷1) | **unknown → GATED** | ratios nulled |
| *(no HOA statement)* | 0 | **0** (unchanged) | computed — a legitimate no-HOA property |

Recognized frequencies are unchanged; **only the unrecognized/unstated path moves** — from a silent monthly
assumption (a 12× overstatement if the dues were annual) to an honest gate. Reported via the DTI line's
`auto_amount` and the calc's `gated` flag (tests below).

### On real data (LF-6T3N)

**LF-6T3N has no HOA statement** (LP-407-2 found this), so the DTI's HOA path returns `(None, False)` → a
legitimate `$0` HOA line, before and after. **The fix is therefore UNEXERCISED on LF-6T3N** — a fixture with an
`hoa_statement` carrying an unrecognized/absent `dues_frequency` would exercise it (a fixture ticket, noted). No
existing DTI value on any fixture changes (no fixture carries an HOA statement with an unconvertible frequency).

## Tests (7, all pass) + the affected consumers (66 pass)

`test_dti.py`: recognized frequencies convert unchanged; an unrecognized frequency gates (not monthly, not 0);
an unstated frequency gates; the **dangerous-direction guard** (an unconvertible HOA yields no confident,

`derived._HOA_FREQUENCY_MONTHS`); `ACTIVE_RULE_IDS == 27`. The DTI, finding-impact, calculators,
calculations-section, and demo-proof suites all stay green (the recognized-frequency path and the no-HOA path
are unchanged).

## Every assumption / decision

- **Gate, don't drop** — the only honest calculation-side "fail closed"; the understating option is rejected.
- **Map not widened** — kept identical to the frozen tag (never looser); a drift-guard test enforces it.
- **No sibling** — taxes/insurance assume annual by the field's contract, not a guessed default.
- **Comment-only** touch to the two LP-407-2 files — factual-accuracy correction, no behaviour change.

## NEW gaps (recorded, out of scope)

1. **`calculators.build_reserves_view` ignores `dti.gated`** — reserves (AS-4, live) use the raw
   `housing_payment`, so an unconvertible HOA (like an absent tax/insurance figure today) understates PITIA.
   Pre-existing; a DTI-gate-aware reserves change is a separate ticket.
2. **`calculations_section.map_dti` doesn't gate the SNAPSHOT DTI on a non-required unknown housing line** — so
   the snapshot DTI would not gate on an unconvertible HOA. Read by no live rule today; a snapshot-layer
   follow-up (this ticket is scoped to the DTI service).
3. **A fixture with an HOA statement + an unconvertible/absent `dues_frequency`** would exercise the fix on real
   data (LF-6T3N has no HOA).
