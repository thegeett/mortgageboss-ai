# LP-851 — one dialog, three doors

Status: spec. **Blocked by LP-850.** Screens 3, 4, 5, 6, 7.

Epic: [`docs/domain/communication/v1-epic.md`](../domain/communication/v1-epic.md) · Screens: [`v1-screens.md`](../domain/communication/v1-screens.md) · Spec: [`comm-v1-draft-only-spec.md`](../domain/communication/comm-v1-draft-only-spec.md)

## The report

> "If any draft is open then we should give pop up message on each request button click with message
> there is open draft, append or create new draft, with these action button. If user click append
> then append it otherwise create new draft. Message should also say mark sent if you want to create
> new one otherwise."
>
> "Currently if we select individual request button is ask to write a message lets remove that,
> instead have this pop up. And Request all button have one pop itself let's add this message."
>
> "Request documents button on current communication page should remain same."

## The dialog

One component, three callers, one 409 shape from LP-850 behind it.

> **There is already an open draft to the borrower**
>
> Created Tue 14:02, asking for: `Bank statement — March` `Pay stub`
>
> Add **Homeowner's insurance declaration** to it — or, if you have already sent that draft from
> your mail client, mark it sent and start a new one.
>
> `[Cancel]` · `[I've sent it — mark sent, start new]` · `[Add to the open draft]` ← primary

**It names the draft by its contents, not by an id.** "There is an open draft" is not enough to
decide with; three document names and a timestamp are, and they are what a processor remembers.

**Marking sent is a button, not advice.** Advice that requires closing the dialog, finding the
draft, marking it and coming back will not be followed on a busy Tuesday.

**"I've sent it", not "Mark as sent".** Nothing in the app observed a send — the record it writes
reads `Marked sent by Priya · Tue 16:41`. A neutral label invites pressing it to dismiss the dialog,
which is how `requested_at` ends up stamped on a message that never went out.

## When one request touches two parties

One dialog, **a row per party** — never two dialogs in sequence. A processor who has just confirmed
five documents and is then asked a second question clicks the primary without reading it, which is
exactly how the wrong draft gets chosen.

A party under `would_create` gets a row with **no buttons**: it needs no decision, but the processor
must leave knowing a second message exists. That is LP-852's rule appearing here.

## The three doors

| Door | File | Change |
|---|---|---|
| Individual request on a finding | `verification/rule-finding-actions.tsx` | **The `request-docs` form is removed.** `Request` fires the rule directly. |
| "Request all N" | `verification/bulk-request-button.tsx` | Its existing confirm **grows the party blocks and the extra button**. Unchanged when nothing is open. |
| "Request documents" | `communication/compose-request-dialog.tsx` | **Untouched.** The catalog, the needs-first ordering and the "already requested" markers all stay. |

### What removing the note form costs, said plainly

LP-839 built that field *and* made it render — the note appears under its own document in the email,
which is how a processor says "the March statement specifically, not February". Removing it means
that sentence has to be typed into the draft body instead.

**That is only acceptable because LP-853 makes the body keep an edit.** These two tickets ship
together or the feature is a regression.

## The edited-draft warning

When the 409's `body_edited` is true, the dialog gains a block **above** the buttons:

> **You have edited this draft.** Adding a document rewrites the message from the template, and your
> changes — including *"March statement only, not February"* — will be lost. Copy anything you want
> to keep first.

**It quotes the processor's own first edited line back at them.** "Your changes will be lost" is
abstract and gets dismissed; their own sentence does not. The primary becomes `Add anyway`.

## What it must not break

- **LP-839's row status.** `documents_requested`, the "requested — in the latest draft" line, and
  LP-841's per-party "requested — in a draft for the title company" clause all still render. Only
  the input form goes.
- **LP-833's catalog dialog** keeps its own "already requested" marking at selection time. Saying it
  before they pick is cheaper than saying it after, and this ticket does not move that.
- Nothing here decides anything. Every branch is LP-850's 409; the dialog renders it and sends back
  one `on_conflict` value.

## Acceptance

1. Requesting a document with no open draft shows **no dialog** and creates the draft.
2. Requesting with an open draft shows the dialog, and **Cancel writes nothing** — verified against
   the database, not the toast.
3. "Request all" shows **one** dialog, not two.
4. A borrower + title company selection shows two rows, one with buttons and one without.
5. `body_edited` shows the warning with the processor's own text quoted in it.
6. The `request-docs` form no longer exists, and `NeedsItem.description` is no longer written from
   that path.

# What was built

Status: **done**. Ships with LP-853 — the note form comes out only because the body now keeps an
edit.

## The four doors, not three

The ticket's table names three. There is a fourth, and it reaches the same endpoint: the **legacy
AI-sweep card** (`verification/finding-card.tsx`, rendered by `findings-list.tsx` in the "Old
findings" tab) carries its own "What to request (optional)" form and writes the same
`NeedsItem.description`. Leaving it would make acceptance 6 — *"the `request-docs` form no longer
exists, and `NeedsItem.description` is no longer written from that path"* — false by one door, on a
tab a processor can still reach. Removed from both; named here because the ticket did not.

There is also a **fifth entry point** for the bulk request: `layout/file-context-rail.tsx`, which
dispatches the identical `request-docs-bulk` and is deliberately not the only home for it
(LP-UI-020). It answers the same refusal with the same dialog — a rail button that surfaced a 409 as
a raw error would be the one door where a processor could not answer.

## The shape

- **`lib/api/draft-conflict.ts`** — the 409's types and `draftConflictFrom`, which is **narrow on
  purpose**: anything that is not a 409 carrying `decisions_required` is somebody else's error and
  still reaches the toast.
- **`open-draft-dialog.tsx`** — Screens 3, 4 and 5, plus `ConflictBlocks` exported so Screen 6 can
  render the same blocks inside its own confirm.
- **`use-draft-conflict.tsx`** — holds the refusal and re-fires the **same** request with the
  answer. The retry is a closure because each door has a different payload, and a shape that could
  hold all of them would be a fourth definition of "a request".

## Screen 6, and why it is not a second dialog

"Request all N" already has a confirm. Firing it, taking the 409 and then opening a separate dialog
would be exactly the two-dialogs-in-sequence the ticket forbids — so the confirm **grows**: the
title and the document list stay on screen while the party blocks and the new actions appear
underneath them. One dialog, two states.

`bulk-request-button.test.tsx::GROWS when a draft is open — one dialog, not two` asserts the
**count**, because `getByRole("dialog")` passes for one dialog and for the first of two. Mutated to
hand off to `conflict.dialog` instead: it fails.

## The quoted line

`_edited_excerpt` decides "theirs" **against the template**: the first line of the authored body the
current render does not contain. The greeting is the trap — it is the body's first line and the
processor did not write it, so `text_lines(body)[0]` would quote *"Hello Sarah,"* at somebody as
though they had typed it, and a warning that quotes a line you never wrote teaches you to stop
reading warnings. Truncation at 160 characters is **visible** (`…`), because a fragment that does
not look cut off is one a processor will not recognise as their own.

Three things checked because the reviewer asked:

- **It cannot reach a log.** `http_exception_handler` does not log at all;
  `unhandled_exception_handler` logs `type(exc).__name__`, the path and the method — never a body.
  `DraftDecisionRequired`'s own message is party names.
- **It is rendered as text.** `::renders the quote as TEXT, never as markup` feeds it
  `<img src=x onerror=alert(1)>` and asserts no `<img>` exists and the characters are visible. The
  column guarantee covers the column; this fragment is lifted out of it into a different field and
  inherits nothing.
- **A long paragraph** is `::a very long line is visibly truncated`.

## What it did not break, checked rather than assumed

- **LP-839's row status.** All nine cases in `rule-finding-actions-lp839.test.tsx` still pass, and
  their fixtures explicitly set `documents_requested: true` and `documents_other_party` — so
  "requested — in the latest draft" and LP-841's per-party clause are asserted from rows that can
  actually show them, not from a fixture where no row could.
- **`NeedsItem.description` does not go blank.** The removed form was **not** its only writer: the
  needs list writes it (`add-need-dialog`, `need-actions`) and `need-card` renders it, and
  `_document_line` still puts it under its document in the email. Removing the request-path writer
  removes a writer, not the field.
- **LP-833's catalog dialog** is untouched — same search, same needs-first ordering, same "already
  requested" marking at selection time. What is new is only that Generate can be refused.

## A Ledger rule I broke and corrected

The warning's quotation was first written in **Plex Serif italic**, reasoning that a quotation is a
quotation. AMENDMENTS **A18** reserves that face for *"text quoted verbatim from a **document**"*
and says so exceptionlessly — *"nothing decorative may borrow it"* — because its whole value is that
it reads as the document speaking without a label. A processor's own sentence is not a document.
Quotation marks and `text-foreground` carry it instead.

## What was not done, and one deviation

- **Screen 3/4 render the timestamp as `messageTimeFull`** ("8 Sep 2026, 14:02"), where Appendix A
  shows "Tue 14:02". The sentence around it is verbatim; the timestamp is data, and a third date
  format for one line is how two screens start disagreeing about when something happened.
- **No test drives all three doors end-to-end against a live server.** Each door's wiring is
  asserted at its own seam (the payload it sends, the error it routes) and the dialog is asserted on
  its own. A full-stack pass is not something this suite does for any feature.
- **The multi-party dialog's per-party buttons answer for one party each, and `Do both` answers for
  all of them with `append`.** Appendix A specifies both controls but not what `Do both` sends for a
  party whose row the processor answered individually first; `append` is the safe reading — it never
  marks anything sent that the processor did not say they had sent.
