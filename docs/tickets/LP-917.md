# LP-917 (lite) — The lender's dates on the file (S2-11)

**Goal:** the dates the lender printed, where the processor looks, without asking her to type anything.

Frontend only. Every date this shows was already on the wire — `ConditionRound.header.loan_facts` and
`ConditionRound.expiry_dates` have carried them since LP-906 — so this ticket is about reading them in
the three places a processor looks, and about one field nothing had ever read.

## What was built

- **`lib/conditions/lender-dates.ts`** — pure: pick the round, read the three printed dates, find the
  soonest document expiry and count the days to it. No React, no clock.
- **The file context rail's new "Lender dates" section** (S2-11), between Ratios and Recent activity.
- **The round card's date line** — "Lock 09/30/2026 · Not before 09/30/2026" (`round-strip.tsx`).
- **"Must Fund By" added to `FIGURES`**, which the round-details sheet already renders.

### `Must Fund By` had no reader at all

The spec asks the round card and the round-details sheet for "must not close before · must fund by ·
rate lock expiry". `review-side-panel.tsx`'s `FIGURES` — the single map both screens render the
letter's figures from — carried the first and third and **not the second**, so no screen in the app
could show it. The reader has always stored the key (`_FACTS` in `condition_compare.py` lists
`("Must Fund By", "must fund by")`); nothing ever asked for it. One line, at the one source, and both
screens gain it.

### `today` is a parameter, and S2-11's "38 days" is only true on the day it was drawn

The section draws a countdown. S2-11 was rendered with today = 09/26/2026 against a close-by of
11/03/2026, giving **38 days**; on 09/27 the same fixture is **37**. A test reading the real clock would
have passed the day it was written and failed the next morning, so `daysUntil(iso, today)` takes the day
as an argument and `lender-dates.test.ts` pins **both** numbers. The PNG's 38 is therefore not
reproducible on any other date, which is a fact about the screenshot rather than a defect.

Days are compared at **UTC midnight**, built from the parsed parts rather than from `new Date(iso)`
arithmetic: a local-midnight reading shifts the difference by one for any viewer east or west of UTC, and
a countdown reading 37 in London and 38 in Denver is the kind of defect nothing here would catch.

### A lapsed date is kept, not skipped

An expiry already in the past is the most important row on the lender's table, so it still wins the
"soonest" comparison and the line reads "Credit docs · 26 days ago" — in words rather than as a minus
sign. **Plain text, no colour**: the spec says "no colours for 'soon', no alerts, no attention-queue
items (Stage 4)" twice, so a date three days away and one three months away are the same muted grey.
Deciding which dates are alarming is the judgement this ticket deliberately does not make.

## Decisions taken without the product owner

| # | Question | Choice, and why it is the safe one |
|---|---|---|
| 1 | The tickets file's example reads "Asset docs expire 11/30/2026 · **65 days**"; S2-11 draws "Soonest doc expiry **11/03/2026**" and "Close by and income docs · 38 days". | **The design, and the Done-when agrees with it** ("the soonest expiry is income / close-by 11/03/2026"). 11/03 is genuinely the soonest on round 2's table; 11/30 is the asset row. The prose example appears to predate the fixture. |
| 2 | The rail is documented as never fetching anything of its own — every hook is one the current tab already calls. Lender dates needs the file's rounds. | **Behind a `tab === "conditions"` check**, like `DocumentsSection` and `VerificationSection`. Putting it on every tab would add a rounds request to every other tab to draw four lines. S2-11 is a Conditions-tab screenshot, so this matches the PNG. Widening it later is a BACKEND question — the dates would need to reach the file read — not a placement one. |
| 3 | Which round's dates does a round CARD show? | **Its own.** A card draws the round it names, so it reads that round's letter; the rail asks a different question ("what are this file's lender dates") and chooses the newest round carrying any. Two questions, one set of key constants, shared through `lenderFactsFor`. |
| 4 | "Full, or partial with its PDF attached" — how is that tested? | **By asking what the round HOLDS** (a header or any expiry date) rather than by combining `completeness` with a source check. A paste has neither until its PDF is attached, and attaching one is exactly what gives a partial round its letter — so the two formulations select the same rounds, and this one cannot disagree with itself. |
| 5 | A round whose letterhead the reader could not find, but whose expiry column parsed (S1-11). | **It counts as carrying dates.** The expiry table lives in its own column and survives a missing letterhead, which `LetterDetails` already relies on. |
| 6 | The card's line when the lender printed no dates. | **Absent entirely**, not a row of dashes. The rail's `Metric` uses an em dash to mean "this file has no such value"; a card with nothing to say says nothing. |

## Noted, not changed

- **The rail's section is Conditions-tab only** (decision 2). If the product owner wants lender dates on
  every tab, the clean way is for the loan-file read to carry them, not for the rail to fetch rounds
  everywhere.
- `daysUntil` returns `null` for an unparseable date and the caller renders 0 days rather than hiding the
  row. That is deliberate — a date the lender printed in a shape we cannot parse should still be visible
  — but it is the one place where a malformed value reads as "today".
- **Deferred to Stage 4, per the spec:** contract closing / signing / funding dates the processor enters,
  warnings such as "lock expires on the first allowed closing day", and the Today queue.
