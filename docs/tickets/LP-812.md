## Three rows, one event

A single inbound arrival writes **three rows in three tables**: LP-803's `inbound_message`,
LP-805's `Communication(INBOUND, RECEIVED)`, and LP-805's `ActivityLog(COMMUNICATION_RECEIVED)`. An
outbound send writes two. The build plan noticed that no ticket had reconciled them and asked this
one to decide which is the timeline's row.

**The `Communication` is.** It already carries direction, status, subject, recipient and `sent_at` —
what a message needs to render. The `inbound_message` is the raw artefact and its manifest; the
activity entry is a *description of* the Communication.

**The `ActivityLog` is the timeline's row for everything that is not a message** — a document
accepted, a need satisfied, a status change. `activity_logs` itself is untouched: it stays the
complete audit trail, and this is a read that composes for one screen.

**So every `COMMUNICATION_*` activity type is excluded, and the set is derived from the enum rather
than listed.** Three exist today. A fourth added next month would otherwise appear beside the
Communication it describes — the same double-count, arriving later and by a different route.

The derivation has its own control: a predicate that matched nothing would exclude nothing and read
exactly like a working exclusion, so the test asserts the set is **non-empty** before asserting what
is in it.

## The test drives a real message

b7's warning going in: *"a merge that picks per-source will show one arrival twice and look correct
in every test built from one source."*

So `test_one_real_arrival_is_one_timeline_row` runs a message through the **actual chain** — ingest,
safety, routing — asserts all three rows genuinely exist, and *then* asserts the timeline has one
entry. A fixture that hand-built a `Communication` would give a one-row timeline whether or not the
reconciliation existed, because the activity entry it duplicates would never have been written.

---

## Choosing the Communication left it needing the manifest

The attachments hang off `inbound_messages`, and `Communication` had no link to it.
`external_message_id` could not serve: it holds the RFC 5322 `Message-ID`, which is **written by the
sender**, is nullable, and is not unique — joining on it would attach a borrower's documents to
whatever else claimed the same id.

So a real FK, `SET NULL` rather than `CASCADE`: a retention purge that removed raw messages must
leave the evidence record standing, and a cascade would delete the record of a message having
arrived along with its bytes.

The backfill recovers the link from the sender-written id **only where it is unambiguous** — same
loan file, exactly one match. A timeline row with no manifest is a gap somebody can see; one
attached to another borrower's documents is not.

## Ordering, and the two things that are not `created_at`

A message sits at `sent_at` when it has one. A draft composed on Monday and sent on Thursday belongs
at Thursday — that is when the borrower heard from us, and ordering by composition puts the send
before a reminder that actually preceded it.

An inbound message has no `sent_at` (LP-805 declined to reuse that column for a received-at, because
"when did we send this" would then answer with a time nobody sent anything), so it falls to
`created_at`. The better answer is the `inbound_message`'s own `received_at`; using it means joining
that table to order a list, and the two differ by the ingest lag — seconds, except on the nights
staging is asleep. **Noted rather than resolved.**

---

## The pills are defined once, on the server

`sent` / `received` / `drafts` / `activity`, from spec 4.3. Defining them again in the client would
be two definitions of one word that nothing forces to agree, and the first to drift is "sent", which
would start showing drafts and tell a processor they had already asked for something they had not.

`drafts` includes `QUEUED`. A queued automatic reply is a message not yet gone, which is what a
processor means — and it is the one state no other pill shows, so excluding it makes it invisible
everywhere. An unknown filter is a **422**, not a silent fallback to `all`: a pill whose name changed
would otherwise show everything and read as "this filter matches everything".

The empty state distinguishes *nothing has happened* from *this pill hides it*. Telling a processor
who filtered to Drafts that nothing has ever happened is false, and sends them to look for a bug
rather than to clear the filter.

---

## What the timeline does not carry

**No message bodies.** A timeline is a list anybody scrolls past; the body lives on the message, is
dropped from every readonly view, and putting it here would make this the fullest copy of a
borrower's prose in the product. Asserted against a message that *has* a body with a distinctive
string in it, so the absence is a choice rather than an empty column.

Subjects and filenames do travel — a processor recognises a message by them. Filenames are
sender-written text rendered as text: no `title`, no `href`, nothing built into a URL. The inbox
address is shown and copyable and **never a `mailto:` link** — it is a bearer capability (ADR-397),
and a link invites a click that opens a compose window addressed to it from the processor's own
account, which is not what it is for.

## Deliberately not done

- **No compose-with-template-selector.** The design doc's ticket table lists it for LP-812; the
  build plan's M5 table does not, and LP-818 owns "compose a message with no needs behind it". The
  outbound draft panel above the timeline is the compose path today. **Recorded rather than resolved
  by picking the larger reading** — the same disagreement LP-805 hit between the two documents.
- **No pagination.** A hard limit of 200, newest first. A file with more history than that loses
  its tail silently, which is the wrong failure — it should say so. **Escalated.**
- **Ordering uses `created_at` for inbound**, not the message's own `received_at`. See above.
- **Nothing marks anything read.** Unread state and a badge are LP-818's, per the plan.

- **Message content in logs** — this module logs nothing.
- **AI in the decision path** — none.

Worth a second measurement:

## Review (second session, protocol §3)

Two findings. The reconciliation itself is right, and I checked it the way the ticket asked rather
than by agreeing with the reasoning.

### The reconciliation — the Communication is the correct row

Endorsed, and for a reason beyond the ones given: an unrouted message has no `Communication`, so it
appears on **no file's timeline**, which is exactly right — LP-806's redaction says an unclaimed
message belongs to nobody, and the timeline agrees without needing a second rule. The
`inbound_message` would have had the opposite property.

Deriving the exclusion from the `COMMUNICATION_*` enum rather than listing the three that exist is
the right shape, and the control the builder wrote for it — a predicate matching nothing excludes
nothing and reads exactly like a working exclusion — is the fourth-and-a-half instance of the lesson
this loop keeps circling.

### A — The backfill linked to soft-deleted rows, and its two halves disagreed

I ran the backfill rather than reading it. A one-shot `UPDATE` is the least reviewable thing in a
migration: it executes once, against data nobody has, and is unfalsifiable afterwards.

Neither side excluded soft deletes. Measured:

```
PROBE linked to a SOFT-DELETED message: True
```

So a timeline row could point at the manifest of a message somebody had deleted. And the same
omission ran the other way in the ambiguity guard: the `count(*)` counted deleted rows too, so a
soft-deleted duplicate made a genuinely unambiguous link look ambiguous and left it NULL. **One half
too permissive and the other too strict, from one missing predicate** — which is why finding it on
one side and not the other would have been worse than finding neither.

Both sides now exclude `deleted_at`. The SQL is hoisted to `_BACKFILL` so a test can execute it,
following the pattern `test_readonly_query.py` already uses for view DDL. Four tests: it refuses a
deleted target, it still links a live unambiguous one (the control — a query that links nothing
satisfies the first test and leaves every row without its manifest), a deleted duplicate no longer
suppresses a good link, and two live duplicates are still left alone.

**On "unreachable in practice":** the ambiguity guard *is* reachable. `message_id` is sender-written
and not unique, and since LP-807 keyed dedup on the SES id, two deliveries of one thread can carry
the same header and route to the same file. Right to write it; the belief that it could not fire was
the only wrong part.

Everything else about the FK is right. `external_message_id` genuinely could not serve — sender
written, nullable, not unique — and `SET NULL` over `CASCADE` is correct against §6's append-only
requirement: a retention purge must remove bytes without removing the record that a message arrived.
The backfill's `m.loan_file_id = c.loan_file_id` predicate is what makes cross-file linking
impossible, and it is the one I checked first.

### B — The cap dropped the oldest entries in silence

The builder named this and called the failure mode wrong. It is, and it was cheap to fix, so it is
fixed rather than left as a note: `build_timeline` returns whether the cap bit, `TimelinePublic`
carries `truncated`, and the panel renders *"Older entries are not shown"*.

The reason it matters is the direction of the loss. The dropped entries are the **oldest**, so a
processor hunting the message that started a thread finds a page that looks complete and does not
contain it — and concludes it never arrived. Pagination is still the real answer and stays
escalated; this is the difference between a known limit and a wrong answer.

Carried all the way to the screen deliberately. A flag no component reads is a value written
correctly to a record nobody looks at, which is exactly what LP-819's review found — so it is
rendered, with a control test that a complete timeline says nothing, because a panel showing the
notice always would pass the first test while telling every processor their history is incomplete.

### The builder's three, measured

1. **The reconciliation — see above.** Endorsed.
2. **The manifest FK and the backfill — see finding A.**
3. **`_message_at` using `created_at` for inbound — accepted, and the reasoning is sound.** The
   honest field is `received_at`, and reaching it means joining `inbound_messages` to order a list.
   The two differ by ingest lag: seconds, except on the nights staging sleeps, when the whole queue
   drains at 09:00 and every message in it shares a `created_at` while their `received_at` spread
   over eleven hours. That is a real ordering distortion, and it is a staging artefact of the LP-630
   shutdown rather than a production one. Noted rather than resolved is the right call at this size;
   worth revisiting if the timeline ever has to be evidence rather than a view.

### Done when, and the standing checks

The merge is single-counted and proven so by a test that drives the **actual chain** and asserts all
three rows exist before asserting one entry — which is the test I asked for, and it would fail
against a hand-built fixture that never exercised the reconciliation.

The compose disagreement between `phase4.md`'s ticket table and the build plan's M5 table is the
same conflict LP-805 hit between those documents, recorded rather than resolved by picking the
larger reading. That is right for a builder to do and it now belongs to whoever reconciles the two
documents.

Standing checks: no `company_id` derived here; the timeline carries subjects and filenames to an
authenticated user of the owning company and logs none of them; no AI.
