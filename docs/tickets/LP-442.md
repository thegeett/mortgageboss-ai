# LP-442 — Vocabulary reconciliation: make every schema'd document type reachable by the classifier

## What this ticket is

**Step 1b of the schemas-for-all-105 plan.** LP-441 merged the tiers and applied 10 unambiguous renames, but
found the real blocker: **the schema `document_type` vocabulary and the catalog/classifier vocabulary had
diverged — 72 spec types were not in the catalog.** The classifier emits **catalog** keys; `EXTRACTORS` is
keyed by **spec** `document_type`. An unreconciled type means `EXTRACTORS.get(...)` → `None` → the document
completes **classified-only** and its generated extractor is never reached — **no error, no warning.** A wrong
mapping produces the identical silent failure, which is why LP-441 applied only the unambiguous 10 and reported
the rest. This ticket reconciles all 72, so **every spec `document_type` now resolves to a catalog entry.**

**Nothing is wired** (`EXTRACTORS` / `_LIST_SPECS` / `_PII_FIELDS` untouched — that is step 7).

## D1–D5

- **D1 — Decision 3's target (VERIFIED).** Two candidates. `payoff_statement` (PROPERTY): *"a payoff/demand
  statement from a lienholder stating the amount to fully pay off an existing loan."* `debt_payoff_statement`
  (CREDIT): *"a statement or letter showing a debt has been or will be paid off (to exclude it from DTI)."* The
  `mortgage_payoff` spec serves **CR-3** (paid-off liability) + **TI-3** (lien on title) and carries
  `property_address` / `lien_release_timing` / `creditor_or_servicer_name` — it is the real-estate lien payoff.
  → **Merge target = `payoff_statement`.** `debt_payoff_statement` is the generic DTI-exclusion key — the wrong
  target; merging there would have been the silent-routing failure.
- **D2 — Decision 2 (`borrower_authorization` usage).** The bare key appears **only** in `catalog.py` +
  `classification_prompt.py` — not in `EXTRACTORS`, no rule, no fixture, no needs template, no test (repo-wide
  word-boundary check). **Not a STOP — safe to retire.** The two auth specs already have distinct
  `document_type`s (`authorization_to_run_credit`, `borrower_authorization_and_certification`) → each becomes a
  distinct NEW catalog type; the generic entry + its indicator are removed.
- **D3 — Decision 1 (the field difference).** The split **reuses the shared income-analysis field set** verbatim
  for both specs (party names, court basis, `ordered_amount` / `payment_frequency`, `start_date`,
  `arrears_balance`, `current_payment_status`, `deposit_account_last4` PII, + the `payment_history` list). The
  **one genuine divergence** is continuance (Priya's ruling): `alimony_income`'s continuance is the **order's
  end date**, already held by `end_date_or_termination_events` (no extra field); `child_support_income` **adds
  two fields** — `child_ages_or_dates_of_birth` + `support_termination_age_or_event` (child support terminates
  at the child's emancipation age, so the child's age is the fact that bounds continuance).
- **D4 — the final counts.** 72 uncataloged spec types → **4 merges** (into existing keys) · **1 split** (→ 2
  existing keys) · **67 new catalog types + 67 indicators** · **6 module regenerations** (4 merge + 2 split;
  the 67 new types keep their already-generated modules) · **1 catalog entry retired**
  (`borrower_authorization`). The split raised the corpus **108 → 109** spec `document_type`s (one more than
  the ticket's pre-split "108" figure). **THE MEASURE: 109 of 109 resolve to a catalog entry, up from 36.**
- **D5 — the confusable pairs and how each indicator separates them.**
  | pair | the distinguishing line in the indicator |
  |---|---|
  | `termite_report` vs `termite_completion` | INSPECTION findings/clearance vs treatment COMPLETION certificate |
  | `property_profile_subject` vs `_non_subject` | data-vendor profile of the SUBJECT vs a NON-subject property |
  | `property_tax_bill` (ship) vs `_non_subject` | tax bill for the SUBJECT vs a NON-subject property |
  | 5× `letter_of_explanation_*` + `application_loe` vs the generic `letter_of_explanation` | each names its scope: asset / childcare / income / property / misc / application |
  | `trust_agreement` vs `trust_documents` vs `trust_federal_tax_returns` (vs existing `trust_documentation`) | the AGREEMENT instrument vs a CERTIFICATION/excerpt vs the 1041 RETURN — ⚠️ see risk below |
  | `subject_property_note` vs `other_property_note` vs `unsecured_note` | the note on THIS loan's property vs another property vs an unsecured (non-RE) note |
  | `homeowner_s_insurance_quote` vs `homeowners_insurance` (ship) | a QUOTE/estimate vs a bound policy/dec page |
  | `boarder_proof_of_residency` vs `boarder_rental_payments` | lives-at-address evidence vs pays-rent payment history |
  | `verbal_voe` vs `voe` (ship) | a phone-call record vs a signed employer VOE form |
  | `verification_of_assets` vs `verification_of_deposit` (ship) | a multi-account aggregator report vs one bank/one account |
  | `work_visa_ead_card` vs `visa_documentation` (ship) | a USCIS work-authorization card (ID-8) vs a travel visa |
  | `disability_award_letter` / `retirement_pension_award_letter` vs the income/statement variants | the AWARD (with continuance) vs an amount/balance/payment |
  | the 5 tax-transcript types vs the forms and generic `tax_transcript` | each names its IRS form (1040/1065/1120/1099/K-1) and "TRANSCRIPT, not the form" |
  | `prior_closing_disclosure_final_cd_from_purchase` vs `closing_disclosure` (ship) | a PRIOR purchase's CD (seasoning) vs this loan's — "conflating them is dangerous" |

  **Recorded classification RISKS (hard to tell apart from the document alone — flagged, not papered over):**
  - `trust_documents` (a trust certification/excerpt) vs the pre-existing `trust_documentation`, and vs
    `trust_agreement` — three trust-paperwork keys a single document may not disambiguate.
  - `ira_401k` vs the generic `retirement_account` (both retirement-account statements).
  - `statement_of_account` is asset-or-liability ambiguous by nature.
  - `custom` / `miscellaneous_document` / `general_correspondence` / `letter_of_explanation_misc` are
    overlapping catch-alls by design.
  These are real per-type accuracy items for **refine-with-Priya / real-labeled-document** tuning.

## Every indicator written (for human review)

*(The parity test `test_indicators_exactly_cover_the_catalog` locks these to the catalog; each is written to
distinguish, not merely describe. The 6 merge/split targets reuse their pre-existing catalog indicators.)*

### INCOME / EMPLOYMENT (19)
- **form_1040_personal_tax_transcripts** — an IRS account/return TRANSCRIPT of a personal Form 1040 — the IRS transcript, not the taxpayer's own 1040 (`tax_return`) and not the generic `tax_transcript`
- **form_1065_partnership_tax_transcripts** — an IRS TRANSCRIPT of a partnership Form 1065 — not a personal or corporate transcript
- **form_1120_corporate_tax_transcripts** — an IRS TRANSCRIPT of a corporate Form 1120/1120-S — not a partnership or personal transcript
- **form_4506t_request_for_transcript** — IRS Form 4506-T — a signed REQUEST to release transcripts, not transcript data (distinct from `form_4506c`)
- **transcripts_of_1099** — an IRS wage-and-income TRANSCRIPT of 1099 records — not the 1099 form and not the generic `tax_transcript`
- **k_1_shareholder_profit_and_loss_transcripts** — an IRS TRANSCRIPT of a Schedule K-1 — distinct from `k1_statement` (the form from the entity) by issuer/layout
- **trust_federal_tax_returns** — a trust/estate Form 1041 tax RETURN — not the trust agreement/certification documents
- **cpa_letter** — a CPA-signed attestation of business existence/ownership/withdrawal ability — not a tax return or financial statement
- **business_existence_verification_cpa_ltr_bus_lic** — business-existence proof via CPA letter, license, or SoS record — broader than a single `cpa_letter`/`business_license`
- **business_license** — a government business LICENSE/permit to operate — an operating license, not a CPA attestation
- **disability_award_letter** — a disability AWARD letter (benefit + continuance) — distinct from `disability_income_letter` (income amount)
- **retirement_pension_award_letter** — a retirement/pension AWARD letter (benefit + lifetime, IN-13) — distinct from `pension_statement`/`retirement_income_letter`
- **retirement_check** — a retirement/pension CHECK or clearing evidence — not the award letter or a statement
- **verbal_voe** — a VERBAL (telephone) VOE call record — NOT a signed employer VOE form (`voe`)
- **military_leave_and_earning_statement_les** — a military LES pay statement — not a civilian `pay_stub`
- **foster_care_verification** — a state-agency foster-care payment verification used as income
- **boarder_rental_payments** — a boarder's rent PAYMENTS record — distinct from `boarder_proof_of_residency`
- **boarder_proof_of_residency** — evidence a boarder RESIDES at the address — not the rent-payment record
- **cancelled_checks_evidencing_receipt_of_note_income** — cancelled checks evidencing RECEIPT of note income

## Assumptions / decisions

- **The schema vocabulary moved to the catalog's**, not the reverse — the classifier is already trained on
  catalog keys (ADR-347).
- **No mapping guessed.** A name match alone never justified a merge; every merge is a same-document identity,
  every keep-separate is a document a processor treats differently.
- The split reuses the shared field set; the child-support continuance fields are the only divergence (D3).
- `borrower_authorization` retired only after proving it unused (D2).
- Category assignments are the LP-59 "refine-with-Priya" starter; category drives filing/prompt grouping, not
  routing, so a debatable choice (e.g. `verification_of_mortgage`/`_of_rent` filed under CREDIT for
  payment-history) is safe to revisit.

## NEW gaps

- **Recorded classification risks** (D5): `trust_documents`↔`trust_documentation`↔`trust_agreement`;
  `ira_401k`↔`retirement_account`; `statement_of_account` asset/liability; the catch-all cluster. Real per-type
  accuracy needs Priya + real labeled documents.
- **Reachability is now possible but not yet live** — every spec type is cataloged, but until step 7 wires the
  extractors, a classified document of a newly-cataloged Tier-1 type completes **classified-only** (the ADR-346
  D3 gate — safe, never errors).
