# LP-708 — a word-position map for a page that has no text layer

- **Ticket:** LP-708 (LP-700 series, 3 of 4)
- **Status:** Done (2026-09-06). Built with PyMuPDF's own Tesseract binding — no new Python dependency. 0% → 37.3% of fields placed on fully scanned documents.
- **Scope:** Backend — a new OCR step, `services/field_boxes.py`, storage; a vendor decision
- **Prompts changed:** none. **Extra AI calls:** none. **New dependency: yes — this is the point.**

## The idea in one line

Nothing else in this series can touch a scanned page, because there is no text in the file.
This ticket supplies the one thing that is missing — **where each word sits** — and nothing
else.

## READ THIS BEFORE SIZING IT: the reading is already done

The obvious assumption is that a scanned page needs OCR before anything can be extracted
from it. That is not the case here, and the corpus says so plainly:

```
SCANNED pdfs: 14   values extracted: 126   avg 9.0 per doc
TEXT    pdfs: 76   values extracted: 608   avg 8.0 per doc
```

Claude reads a photocopy about as well as a typed page — marginally better on this corpus.
Extraction on scans is not broken and this ticket does not touch it.

What Claude never returns is a POSITION. It is shown a picture, not a coordinate space. So a
box has always come from a second, separate source: `page.get_text("words")` on a text page,
and nothing at all on a scanned one. That absence is the whole of this ticket.

**Which lowers the bar a long way.** We do not need OCR that reads the document correctly —
Claude's value is authoritative and is what gets displayed. We need word positions good
enough that LP-706's fuzzy matcher can find Claude's value among them. OCR reading
`15,OOO.OO` for `15,000.00` is tolerable: the match still lands, the box is still right, and
the number on screen is still Claude's.

That is a much weaker requirement than "extract this document accurately", and it changes
which tool is right.

**Not because a free engine cannot read — it can.** Tesseract is a full OCR engine: it
returns text and positions, and plenty of production systems use it for reading. It is
simply LESS ACCURATE at reading than the hosted services on hard material — poor scans,
unusual layouts, faint photocopies. (An earlier draft of this ticket said accurate reading
"would need a paid service". That is not true and it is a worse argument than the real one.)

The real argument is narrower and stronger: **Tesseract's one known weakness is reading
accuracy, and reading accuracy is the thing this ticket does not need.** Claude has already
read the page and its value is what gets displayed. So the tool's weakness lands in the only
area that does not matter here.

## THE CHOICE IS MADE: local, and not on price

**Tesseract, on our own servers.** Not a shortlist, not a comparison to run — the decision,
recorded so it is not reopened by whoever picks this up.

**And not because it is cheaper.** Priced properly, the hosted services are ~$0.0015 a page
(Google Document AI, AWS Textract). Only 11.8% of pages need OCR at all, and documents
average 2.85 pages, so that is **$0.0005 per document** — a 1% increase on a $0.021-$0.051
extraction, or roughly fifty cents a month at a thousand documents. Cost is not the
deciding factor and should not be quoted as if it were.

**The reason is what is in the documents.** These are mortgage files: SSNs, account numbers,
borrower names, addresses. Sending them to a third-party API is a data-residency and
compliance decision. Nobody has been asked for one, and a ticket about drawing rectangles is
not where that gets decided by default. Local keeps the question open instead of answering
it by accident.

A hosted service is reconsidered only if BOTH are true: Tesseract's rectangles turn out too
poor for the matcher to place values, AND someone with the authority to make it signs off on
borrower documents leaving the estate. Not one without the other.

## The measured problem

**34 of 288 stored pages (11.8%) have no text layer.** They sit in 17 fully scanned PDFs and
6 mixed ones. On those pages every field is unplaceable today and stays unplaceable after
LP-706 and LP-707, because both match against words that do not exist.

**PER PAGE, NOT PER DOCUMENT.** The 6 mixed PDFs are the reason. A design that asks "is this
document a scan?" gets a document whose page 1 is typed and page 2 photocopied wrong in both
directions. The question is always about a page.

## What changes

Run OCR on any page whose word list is empty, store the resulting words with their
rectangles, and let LP-706's matcher read those words exactly as it reads a native text
layer. Everything downstream stays identical — the matcher does not know or care which kind
of page it is looking at.

**WHEN it runs is a decision, not a detail, and it decides which documents benefit.**

* **On demand, cached** — OCR a page the first time someone asks for its boxes. Existing
  scans benefit, including the 14 already stored, and nothing is spent on a document nobody
  opens.
* **At upload** — only documents uploaded after this ships, and every scan is paid for
  whether or not it is ever reviewed.

On-demand-and-cached is the recommendation. Recorded here so the choice is made rather than
inherited from whichever is easier to write.

**Native text stays authoritative.** Where a page has its own text layer we use it and do not
OCR: positions encoded in a PDF are the source of record, while OCR estimates them.

## A third option: ask Claude for the boxes

Claude can return bounding boxes — [Coordinates and bounding boxes](https://platform.claude.com/docs/en/build-with-claude/vision-coordinates).
It is a real alternative to any OCR engine for exactly the pages this ticket is about, and
it needs no new dependency at all. Three things decide whether it is actually cheaper:

* **It does not work with PDFs as we send them today.** The docs are explicit that PDF pages
  are rasterised server-side at dimensions the caller does not control, so the returned
  coordinates cannot be mapped back onto the page. We would have to send our own rendered
  page images instead — which we already produce for the reviewer, but switching the
  extraction path to them disturbs the prompt-cache breakpoint in `ai/client.py`, which is
  tuned against a 4,096-token minimum and fails SILENTLY when disturbed.
* **The coordinates are approximate**, and the docs warn that small elements lose precision
  when an image is downscaled. A gross-pay figure on a dense pay stub is a small element.
  Tesseract measures rectangles from pixels; Claude estimates them.
* **It could be nearly free** if the boxes are asked for inside the extraction call that
  already happens — a few more output tokens, no second call. That is the version worth
  wanting, and it only exists if the first point is solved.

**Decide it by measuring, not by arguing.** Render twenty scanned pages, ask Claude for boxes
on values we already know the answer for, and measure how far off they are. A day's work,
no commitment either way, and it settles a question neither option can win on reasoning.

## Behaviour by document kind

| | what happens |
|---|---|
| **Text PDF** (78 docs) | **Nothing at all.** Never invoked — the page already has words. No new cost, no new failure mode. |
| **Scanned PDF** (17 docs) | The whole benefit. These pages get words with rectangles for the first time, and LP-706's matching then works on them unchanged. |
| **Mixed PDF** (6 docs) | OCR runs on the scanned pages only. Handled correctly *because* the decision is per page. |
| **Image** (0 today) | Same path as a scanned page — an image *is* a scan. Also removes `field_boxes.py`'s remaining non-PDF refusal, so an uploaded photo of a pay stub can be highlighted like anything else. |

## What was built, and what it measured

**PyMuPDF's own OCR, so there is no new Python dependency.** `get_textpage_ocr` drives
Tesseract through the library that already renders the page and already supplies the native
word list. The rectangles come back **in the page's POINT space**, so the pixel-to-point
conversion this ticket's design worried about — the one it said "wants an assertion, not a
comment" — turns out to be PyMuPDF's problem rather than ours. There is a test asserting it
anyway, because the failure would be silent.

The only new requirement is the **system binary**, added to the backend Dockerfile with
`tesseract-ocr` and `tesseract-ocr-eng`. Its absence is not fatal: `ocr_available()` probes
for it and a false leaves scanned pages in exactly the no-box state they were already in.

### The result, measured

```
10 fully scanned documents, 83 valued fields with a snippet and a page

  before:   0  (0.0%)   — no text layer, nothing to match against
  after:   31 (37.3%)
```

Zero to thirty-seven per cent on documents that could never show a box.

### The dpi is derived from the page, and both extremes were measured

A fixed dpi fails at both ends, so the target is a **raster size**, exactly as
`MAX_RENDERED_EDGE` is and for the same reason — a dpi is a multiplier and the page it
multiplies is unbounded.

| page | dpi | raster | words | time |
|---|---|---|---|---|
| 612 × 1008 (normal) | 300 | 4200 px | 104 | 318 ms |
| 612 × 1008 | **214** | **2996 px** | **103** | **257 ms** |
| 612 × 1008 | 100 | 1400 px | **11** | 56 ms |
| 3331 × 5221 (oversized) | 300 | 21754 px | 767 | **7542 ms** |
| 3331 × 5221 | **70** | **5075 px** | **799** | **1639 ms** |

On a normal page the raster size *is* the quality — 1400 px finds eleven words where 2996 px
finds a hundred and three. On an oversized page a fixed 300 dpi costs five times the wall
clock for the same words. `TARGET_EDGE_PX = 3000` satisfies both.

Tesseract silently substitutes 70 for anything lower ("Invalid resolution 43 dpi. Using 70
instead"), so `MIN_DPI` is its floor rather than a choice of ours.

## Two mistakes worth recording

**The first version threw away exact rectangles.** It returned OCR whenever the native word
count was under the threshold — so a genuine two-word page was rasterised and re-read,
discarding two EXACT rectangles for however many estimates Tesseract produced. A pre-existing
test caught it immediately, which is the only reason it was not shipped.

The repair also had to be repaired. "OCR wins if it finds more words" still displaced two
exact rectangles with three estimates. **OCR now has to clear the same bar it was called in
to fill** — `NATIVE_WORD_THRESHOLD` words of its own — which says the honest thing: if OCR
cannot find a text layer either, the page has none, and the few exact positions it does have
are the best answer available.

**Two of the first five mutations survived**, and both survived for the same reason: the
tests compared word TEXT, and Tesseract reads a clean typed page accurately enough to produce
the same strings. What is lost when OCR runs on a typed page is not the text, it is the
**exactness of the rectangles**. The tests now assert geometry, and assert that OCR is not
reached at all for a typed page by making the call raise.

## Left as it is, deliberately

**No caching yet.** The whole-corpus sweep took 18.8 s across 10 scanned documents, and OCR
runs at most once per page per request because `_lookup_in` already caches the page index for
the document. A processor opening one document pays for its pages once. Caching across
requests is worth doing and is not free — it wants a store, an invalidation rule, and a
decision about where OCR output lives, which is more than this ticket should decide.

## Acceptance

- [x] A page with a native text layer is never sent to OCR — asserted by making the OCR call
      raise, not by comparing the words afterwards
- [x] The mixed-PDF case is handled by construction: the question is asked per page
- [x] Local engine chosen, and the data-residency reason recorded rather than the cost one
- [x] OCR-derived words are distinguishable downstream — a box from an OCR'd page carries
      `MatchKind` like any other, and native words always win where they exist
- [ ] Cross-request caching — deliberately not built, see above

## Review (LP-708 review commit)

Reviewed `8e1e38b`. Nine findings, and the answer to the ticket's own item 2 — the
third thing the tests could not see — is the sharpest of them.

### The rectangles were never asserted to be in the right PLACE

Every existing check on an OCR rectangle is a **bound**: inside the page, non-zero
area, small enough not to be pixels. All three hold for a rectangle at the origin,
so collapsing every OCR word to (0, 0) — a box in the top-left corner for every
field on every scanned page — **passed the entire suite**. Verified by making
exactly that change.

A position needs a positional assertion. The only ground truth available is a page
whose words have known rectangles: OCR a page that also has a text layer, and the
two must agree. Measured agreement on that fixture is ~1pt across and ~5pt down
(the glyph box against the text baseline), so the tolerance sits at 20pt — far
tighter than the ~300pt an origin collapse or an axis swap produces, and loose
enough to survive a Tesseract version change. Both of those mutations now fail.

### The guard was scoped by its symptom rather than by what it guards

`words_for` required OCR to reach `NATIVE_WORD_THRESHOLD` before its output could
be used **at all** — including on a page with no words of its own, where there was
no exact geometry at stake. A scan whose only legible text is a three-word header
therefore returned nothing, protecting rectangles that did not exist. The test for
the neighbouring rule could not see it, because it only ever exercised a page that
had native words.

The rule now asks whether there is anything to protect. Where there is, the
threshold still applies and a slightly luckier reading of the same page cannot
displace exact positions.

Its docstring also claimed native words are **never** discarded, which the code
does not do and cannot: a page carrying one stray stamp word is a scan, and giving
up that one rectangle to read the other four hundred is the right trade. The claim
is now about the text *layer*, which is what the threshold actually decides.

### OCR runs in the request path and nothing bounded it

Measured at 0.74s for a dense letter page here, 0.98s on the author's machine. A
30-page scanned bank statement is 22–30s in one request against a client that
gives up at **30s** (`frontend/lib/api/client.ts`) — the processor sees no boxes at
all, and with no cross-request cache the next viewer pays it again.

`MAX_OCR_PAGES_PER_REQUEST = 12`, chosen from the corpus rather than picked: the
most pages any stored document needs OCR'd is **9**, the 95th percentile is 1, and
the median is 0. It costs nothing on anything stored while bounding the worst case
near nine seconds, and a document past it keeps boxes for the pages that were read
— the same partial state a scan already produces.

### The OCR tests do not run in CI

Both real-OCR tests are `skipif(not ocr_available())` and the workflow installs no
tesseract — so the coordinate-space assertion the ticket highlights *because* its
failure mode is invisible was green by never running, and the positional test added
above would have been too. The workflow now installs `tesseract-ocr` and
`tesseract-ocr-eng`, the same two packages the Dockerfile does.

### Two claims that were not true

`has_native_words` existed, was called by nothing in production, and had its rule
inlined a second time in `words_for` — so a change made in one would have left the
tests asserting the other. `words_for` calls it now.

And `field_boxes`' docstring said an image document "is a scan by another name and
takes the same path". The boxes endpoint gates on `TEXT_SEARCHABLE_TYPES`, which is
`{"application/pdf"}`, so a photographed pay stub — which LP-704 taught the
reviewer to *display* — returns an empty boxes response and never reaches the
module. It is the case a reader would most reasonably assume is covered.

### Answers to the ticket's own questions

1. **The native-versus-OCR rule holds on real data, and I could not construct a
   counterexample from the corpus.** Every page in the 5–19 native-word band is a
   genuinely sparse page with real text — OCR finds the same count on all of them —
   and every page in the 1–4 band is one of the DEMO placeholders. The
   scan-with-junk-text case is untested because it is *unrepresented*, not because
   it is impossible.
2. Answered above.
3. **The point-space claim survives falsification.** Compared against native
   rectangles as ground truth rather than against a bound: ~1pt across, no
   degenerate rectangles, nothing exceeding the page. A pixel-space bug fails.
4. **The `@cache` cannot make those tests vacuous** — they monkeypatch the module
   attribute, not the cached call.
5. **`dpi_for` is sound for every real page shape.** The smallest short edge across
   all 297 stored pages is 1375px. The theoretical limit is worth recording: the
   short edge rasters below 400px past about a 7.5:1 aspect ratio, since the dpi is
   driven by the long edge. Nothing in the corpus is close.
6. **The Dockerfile is right.** Tesseract sits before the dependency install so a
   Python change does not invalidate it, `tesseract-ocr-eng` is genuinely required,
   and a build without either degrades to `[]` rather than failing — verified.

### Not reproduced

A rotated page was reported as producing misplaced coordinates. I could not
reproduce that: no rectangle exceeded the page in any of the four rotations. What
*is* reproducible is that OCR returns **garbage text** on a rotated page (`>`,
`se)`, `=s`), so a rotated scan yields nothing usable rather than something wrong.
**Zero of the 297 stored pages are rotated**, so it is latent — recorded rather
than fixed, because a fix wants a rotated fixture to test against and the corpus
has none.

### Verification

ruff 0, format 0, mypy strict 0, **6,724 pytest**. Eleven mutations, all caught —
including the origin collapse and the axis swap that the suite could not previously
see.
