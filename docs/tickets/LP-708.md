# LP-708 — a word-position map for a page that has no text layer

- **Ticket:** LP-708 (LP-700 series, 3 of 4)
- **Status:** Open. Independent of LP-706/707 — can run in parallel.
- **Scope:** Backend — a new OCR step, `services/field_boxes.py`, storage; a vendor decision
- **Prompts changed:** none. **Extra AI calls:** none. **New dependency: yes — this is the point.**

## The idea in one line

Nothing else in this series can touch a scanned page, because there is no text in the file.
This ticket supplies the one thing that is missing — **where each word sits** — and nothing
else.

## READ THIS BEFORE SIZING IT: the reading is already done

The obvious assumption is that a scanned page needs OCR before anything can be extracted
from it. That is not the case here, and the corpus says so plainly:

```
SCANNED pdfs: 14   values extracted: 126   avg 9.0 per doc
TEXT    pdfs: 76   values extracted: 608   avg 8.0 per doc
```

Claude reads a photocopy about as well as a typed page — marginally better on this corpus.
Extraction on scans is not broken and this ticket does not touch it.

What Claude never returns is a POSITION. It is shown a picture, not a coordinate space. So a
box has always come from a second, separate source: `page.get_text("words")` on a text page,
and nothing at all on a scanned one. That absence is the whole of this ticket.

**Which lowers the bar a long way.** We do not need OCR that reads the document correctly —
Claude's value is authoritative and is what gets displayed. We need word positions good
enough that LP-706's fuzzy matcher can find Claude's value among them. OCR reading
`15,OOO.OO` for `15,000.00` is tolerable: the match still lands, the box is still right, and
the number on screen is still Claude's.

That is a much weaker requirement than "extract this document accurately", and it changes
which tool is right.

**Not because a free engine cannot read — it can.** Tesseract is a full OCR engine: it
returns text and positions, and plenty of production systems use it for reading. It is
simply LESS ACCURATE at reading than the hosted services on hard material — poor scans,
unusual layouts, faint photocopies. (An earlier draft of this ticket said accurate reading
"would need a paid service". That is not true and it is a worse argument than the real one.)

The real argument is narrower and stronger: **Tesseract's one known weakness is reading
accuracy, and reading accuracy is the thing this ticket does not need.** Claude has already
read the page and its value is what gets displayed. So the tool's weakness lands in the only
area that does not matter here.

The hosted services (Google Document AI, AWS Textract, Azure Document Intelligence) stay in
the comparison and are judged on POSITION quality, since that is what is being bought. If
their rectangles are no better than Tesseract's, there is nothing to pay for.

## The measured problem

**34 of 288 stored pages (11.8%) have no text layer.** They sit in 17 fully scanned PDFs and
6 mixed ones. On those pages every field is unplaceable today and stays unplaceable after
LP-706 and LP-707, because both match against words that do not exist.

**PER PAGE, NOT PER DOCUMENT.** The 6 mixed PDFs are the reason. A design that asks "is this
document a scan?" gets a document whose page 1 is typed and page 2 photocopied wrong in both
directions. The question is always about a page.

## What changes

Run OCR on any page whose word list is empty, store the resulting words with their
rectangles, and let LP-706's matcher read those words exactly as it reads a native text
layer. Everything downstream stays identical — the matcher does not know or care which kind
of page it is looking at.

**Compare candidates on position quality, not on reading quality** — see above. Start with
Tesseract, because it is free and local, and only reach for a hosted service if its word
rectangles prove too poor for the matcher to use.

**WHEN it runs is a decision, not a detail, and it decides which documents benefit.**

* **On demand, cached** — OCR a page the first time someone asks for its boxes. Existing
  scans benefit, including the 14 already stored, and nothing is spent on a document nobody
  opens.
* **At upload** — only documents uploaded after this ships, and every scan is paid for
  whether or not it is ever reviewed.

On-demand-and-cached is the recommendation. Recorded here so the choice is made rather than
inherited from whichever is easier to write.

**Native text stays authoritative.** Where a page has its own text layer we use it and do not
OCR: positions encoded in a PDF are the source of record, while OCR estimates them.

## A third option: ask Claude for the boxes

Claude can return bounding boxes — [Coordinates and bounding boxes](https://platform.claude.com/docs/en/build-with-claude/vision-coordinates).
It is a real alternative to any OCR engine for exactly the pages this ticket is about, and
it needs no new dependency at all. Three things decide whether it is actually cheaper:

* **It does not work with PDFs as we send them today.** The docs are explicit that PDF pages
  are rasterised server-side at dimensions the caller does not control, so the returned
  coordinates cannot be mapped back onto the page. We would have to send our own rendered
  page images instead — which we already produce for the reviewer, but switching the
  extraction path to them disturbs the prompt-cache breakpoint in `ai/client.py`, which is
  tuned against a 4,096-token minimum and fails SILENTLY when disturbed.
* **The coordinates are approximate**, and the docs warn that small elements lose precision
  when an image is downscaled. A gross-pay figure on a dense pay stub is a small element.
  Tesseract measures rectangles from pixels; Claude estimates them.
* **It could be nearly free** if the boxes are asked for inside the extraction call that
  already happens — a few more output tokens, no second call. That is the version worth
  wanting, and it only exists if the first point is solved.

**Decide it by measuring, not by arguing.** Render twenty scanned pages, ask Claude for boxes
on values we already know the answer for, and measure how far off they are. A day's work,
no commitment either way, and it settles a question neither option can win on reasoning.

## Behaviour by document kind

| | what happens |
|---|---|
| **Text PDF** (78 docs) | **Nothing at all.** Never invoked — the page already has words. No new cost, no new failure mode. |
| **Scanned PDF** (17 docs) | The whole benefit. These pages get words with rectangles for the first time, and LP-706's matching then works on them unchanged. |
| **Mixed PDF** (6 docs) | OCR runs on the scanned pages only. Handled correctly *because* the decision is per page. |
| **Image** (0 today) | Same path as a scanned page — an image *is* a scan. Also removes `field_boxes.py`'s remaining non-PDF refusal, so an uploaded photo of a pay stub can be highlighted like anything else. |

## Acceptance

- [ ] A page with a native text layer is never sent to OCR — asserted, since the cost of
      getting this wrong is a bill and a worse box
- [ ] The mixed-PDF case is a test, not an assumption: one document, one text page, one
      scanned page, both placing fields correctly
- [ ] Candidates compared on whether the MATCHER can place Claude's values using their
      rectangles — not on transcription accuracy, which is not what this is for
- [ ] Claude-returned boxes measured on real scanned pages before being ruled in or out
- [ ] The on-demand-versus-at-upload choice is made explicitly, and the ticket records which
- [ ] OCR-derived words are distinguishable from native ones downstream, so a box's origin
      stays answerable
