# LP-105 — Surface document periods (consolidated display + period in standard_name)

- **Ticket:** LP-105
- **Status:** Completed
- **Date:** 2026-07-03
- **Scope:** Frontend + a backend naming/display change (no new extraction)

## The finding

A survey found **17 of 18 document types already extract a date/period**, but it was poorly
surfaced: shown only as individual raw rows in the detail drawer ("Pay period start", "Pay period
end" separately — no consolidated "Period: X–Y"), and reaching the list card only *indirectly* via
`standard_name` — which only **8 types** had a naming rule for, so ~10 types fell back to
`{Type}_{upload_date}` (undifferentiated names, e.g. eight identical `Pay-Stub_2026-07-02` cards).

This ticket **surfaces the already-extracted period** — no new extraction.

## Part A — consolidated, type-aware period display (card + drawer)

New `app/documents/period.py :: document_period(document, extraction)` derives **one** `{label,
value}` line per document from the already-extracted typed-core fields, formatted per the type's
concept:

| Concept | Types | Example |
| --- | --- | --- |
| Range | pay_stub, bank/investment/retirement statement, P&L, voe (employment) | `Period: Jun 1 - Jun 15, 2026` |
| Policy term | homeowners_insurance | `Policy: Jan 1 - Dec 31, 2026` |
| Tax year | w2, form_1099, tax_return | `Tax year: 2025` |
| Single labeled date | mortgage/hoa (Due), purchase_agreement (Closes), divorce_decree (Effective) | `Closes: Aug 15, 2026` |
| Expiry | drivers_license | `Expires: Mar 1, 2028` |
| Verbatim | property_tax_bill (`due_dates` string, as-is) | `Due: Nov 1, 2026 and Feb 1, 2027` |

- Computed in the backend response builder (`_enrich`, alongside `standard_name`/staleness) and
  exposed as `DocumentResponse.period` — so both the **card** and the **drawer** render one
  consistent, tested formatter.
- **Card** (`document-list.tsx`): a dedicated, emphasized period line under the name — the
  at-a-glance distinguisher for same-type documents.
- **Drawer** (`document-drawer.tsx`): a consolidated period line **above** `ExtractionView`; the
  per-field raw rows + source snippets in `ExtractionView` are **unchanged** (provenance preserved).
- **Graceful:** `None` when the type has no period concept (gift_letter) or the date isn't extracted
  yet (pending/failed) → the UI shows no period line (no empty "Period: –").

## Part B — the period in `standard_name` for all types

`app/documents/naming.py` — added `NAME_RULE`s for the ~10 types that fell back to the upload date,
so `standard_name` uses the **extracted** date:

- investment_account / retirement_account → `statement_period_end`; profit_and_loss → `period_end`;
  voe → `end_date`; hoa_statement → `due_date`; purchase_agreement → `closing_date`;
  divorce_decree → `effective_date` (no identifier); letter_of_explanation → `referenced_date`;
  drivers_license → gained `expiration_date` (previously no date).
- **Graceful fallback preserved:** when the date isn't extracted yet, `standard_name` still returns
  `{Type}_{upload_date}` (unchanged). The 8 existing rules are unchanged.
- e.g. `Investment-Account_Vanguard_2026-05-31`, `Purchase-Agreement_123-Main-St_2026-08-15`.

## Out of scope (unchanged)

- **No new extraction:** `gift_letter` (no date at all) and `property_tax_bill` naming
  (`due_dates` is a verbatim string, not a clean date — normalization is separate) keep the
  upload-date fallback. `property_tax_bill`'s verbatim string **is** shown in the period *display*.
- **Staleness / recency untouched** — that's a separate follow-up (LP-106). This is display + naming.
