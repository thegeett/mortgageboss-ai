## What was reported

The secure link does not open. A second question came with it: is it one-open-only?

## Correction to this ticket's first draft

It said this was "the same class as LP-802's finding that `inbox_domain` was unset in every
environment". **It is not, and the difference matters.** `upload_link_base_url`'s own comment argues
for the local default deliberately:

> *"The default is LOCAL, unlike `inbox_domain`, and the asymmetry is deliberate. A wrong inbox
> domain takes delivery of real borrower mail, so it fails to production. A wrong upload base URL
> sends a borrower to a link that does not resolve — visible, harmless and reported in minutes —
> while a default of the production origin would have a staging test email pointing a real borrower
> at production. The failure that is loud is the one to prefer."*

That reasoning holds and the default stays. The defect is the missing WIRING: `INBOX_DOMAIN` is set
in staging's ECS task definition (`infra/envs/staging/main.tf:472`) and `UPLOAD_LINK_BASE_URL` is
set in no environment at all. The comment's own plan — "staging and dev therefore set it explicitly
in their ECS task definitions" — was carried out for one setting and not the other.

## Measured — the cause

`services/upload_links.py:69`:

```python
@property
def url(self) -> str:
    return f"{settings.upload_link_base_url.rstrip('/')}/upload/{self.token}"
```

`core/config.py:288`:

```python
upload_link_base_url: str = "http://localhost:3000"
```

**`UPLOAD_LINK_BASE_URL` is set nowhere.** Searched the whole repository — every `.tf`, `.tfvars`,
`.yml`, `.env*` and shell script — and there is no assignment. So every link minted on staging is
`http://localhost:3000/upload/<token>`, which resolves to the reader's own machine. It does not
open, and if a dev server happens to be running there it opens a page that has never heard of the
token.

The borrower-facing page itself exists and is fine: `frontend/app/upload/[token]/page.tsx`, backed by
`GET /api/v1/upload/{token}`. Nothing about the link mechanism is broken. It is a configuration
value with a local-development default and no production value, which is the same class as LP-802's
finding that `inbox_domain` was unset in every environment.

## The second question, answered

**Opening a link is free.** `DEFAULT_MAX_USES = 20` and a use is spent on an **upload**, not on a
page view — `services/upload_links.py:169` states it: *"twice before sending anything has spent
nothing; `max_uses` bounds documents delivered"*. `DEFAULT_TTL_HOURS = 72`.

So the intended behaviour is: open it as often as you like for three days, upload up to twenty
documents. Not one-time. Whether the processor SAW one-time behaviour is a separate question that
this ticket must answer rather than assume — a link that never opened cannot have demonstrated its
use accounting either way.

## Done when

- `upload_link_base_url` is set for every deployed environment, and a link minted on staging opens
  the staging upload page.
- The setting cannot be silently absent. LP-802 made `inbox_domain` fail loudly for this reason;
  the same treatment belongs here, because the failure mode is identical — a plausible-looking URL
  that leads nowhere, produced by a system that started perfectly happily.
- A test asserts the minted URL's host is not a localhost default outside development. A test that
  merely checks the URL is well-formed passes today.
- The open-count question is settled by observation, not by reading the constant: mint a link, open
  it several times, confirm the remaining uses have not moved, then upload and confirm one is spent.
- The processor is told what the link permits — three days, twenty uploads — wherever it is offered.
  Right now nothing on screen says either.

## For the reviewer

The interesting check is the negative one: assert that a deployed configuration CANNOT fall back to
the localhost default. Setting the value in staging fixes today's report and leaves the next
environment to reproduce it.

## Built, 2026-09-07

**The wiring**, which is the actual fix: `UPLOAD_LINK_BASE_URL = "https://${var.domain_name}"` in
staging's task definition. Built from `domain_name` — *"the public domain this environment is served
on"* — and **not** from `cors_allowed_origins`, whose own variable block says it carries a
placeholder until after the first apply and should be updated later. A borrower's link is not a
thing to build out of a value documented as possibly stale.

**The guard**, so the next environment cannot repeat it: `Settings._require_a_reachable_upload_base_url`
refuses to start outside development when the host is `localhost`, `127.0.0.1`, `::1` or `0.0.0.0`.
Narrow on purpose — it checks the host, not reachability. A wrong domain or an http/https mix-up is
a value somebody chose, and config cannot tell a chosen mistake from a chosen intention. Loopback is
different: it means "this machine", and a deployed process that means it is misconfigured whatever
else is true.

**Not wired in `infra/envs/dev/`**, and the reason is written into the file. That template has no
`domain_name` variable, `terraform validate` runs on it, and a reference to a variable that does not
exist would fail the check. Its own banner says it is never applied. While there, recorded a second
thing: its tfvars carry `environment = "dev"`, and `Settings.environment` is
`Literal["development", "staging", "production"]` — an app started from those values is rejected by
config validation before reaching any guard. Pre-existing, same class of never-exercised value.

### The one-time-open question, answered by observation

`test_opening_the_page_spends_nothing` opens a **one-use** link three times, asserts
`remaining_uses` has not moved, then uploads successfully. Reading `DEFAULT_MAX_USES` would not have
answered it: the question was asked precisely because the link had never opened for anyone, so no
behaviour had been demonstrated either way.

The positive control corrected itself during the run. I asserted a spent link returns 200 with zero
remaining; it returns **404** — LP-815 gives every failure the same answer, so a spent token must
not be distinguishable from a wrong one. The measured behaviour is now what the test says.

### What the processor is told

The panel now says: *"A new link works for 3 days and accepts up to 20 documents. Opening it costs
nothing — a use is spent only when a document is uploaded."* Nothing said this before, on any
screen, which is why the question had to be asked.

**That sentence is a hand-copied duplicate of two Python constants**, so it is pinned:
`test_the_panel_says_what_the_constants_actually_permit` reads the `.tsx` and compares against
`DEFAULT_TTL_HOURS` and `DEFAULT_MAX_USES`. Verified by changing `DEFAULT_MAX_USES` to 12 — the test
fails. Reaching across the language boundary is deliberate; the alternative is a comment asking the
next person to remember, and a comment is not a guard.

### Mutations

| mutation | result |
|---|---|
| the loopback check can never match | 6 failed |
| `_LOOPBACK_HOSTS` narrowed to `{"localhost"}` | 3 failed — the `127.0.0.1`, `0.0.0.0` and `::1` cases |
| `DEFAULT_MAX_USES` 20 -> 12 | 1 failed — the copy pin |

Two positive controls sit against the guard: development still boots on localhost, and a real origin
is accepted. Without them a validator that refused **every** value outside development would satisfy
both refusal tests and stop staging booting at all.

### Not done here

`terraform plan` was not run — no AWS credentials in this environment, the standing INFRA blocker.
The staging change is written and formatted (`terraform fmt -check` clean) and needs a person to
plan and apply it. **Until that apply, links minted on staging still point at localhost.**

### The three standing checks

**Tenancy:** nothing touched. **Logging:** nothing added; the guard's message names the host and the
environment, never a token or a URL with one in it. **AI:** none.
