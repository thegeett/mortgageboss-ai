# LP-827 — The secure upload link points at localhost

## What was reported

The secure link does not open. A second question came with it: is it one-open-only?

## Measured — the cause

`services/upload_links.py:69`:

```python
@property
def url(self) -> str:
    return f"{settings.upload_link_base_url.rstrip('/')}/upload/{self.token}"
```

`core/config.py:288`:

```python
upload_link_base_url: str = "http://localhost:3000"
```

**`UPLOAD_LINK_BASE_URL` is set nowhere.** Searched the whole repository — every `.tf`, `.tfvars`,
`.yml`, `.env*` and shell script — and there is no assignment. So every link minted on staging is
`http://localhost:3000/upload/<token>`, which resolves to the reader's own machine. It does not
open, and if a dev server happens to be running there it opens a page that has never heard of the
token.

The borrower-facing page itself exists and is fine: `frontend/app/upload/[token]/page.tsx`, backed by
`GET /api/v1/upload/{token}`. Nothing about the link mechanism is broken. It is a configuration
value with a local-development default and no production value, which is the same class as LP-802's
finding that `inbox_domain` was unset in every environment.

## The second question, answered

**Opening a link is free.** `DEFAULT_MAX_USES = 20` and a use is spent on an **upload**, not on a
page view — `services/upload_links.py:169` states it: *"twice before sending anything has spent
nothing; `max_uses` bounds documents delivered"*. `DEFAULT_TTL_HOURS = 72`.

So the intended behaviour is: open it as often as you like for three days, upload up to twenty
documents. Not one-time. Whether the processor SAW one-time behaviour is a separate question that
this ticket must answer rather than assume — a link that never opened cannot have demonstrated its
use accounting either way.

## Done when

- `upload_link_base_url` is set for every deployed environment, and a link minted on staging opens
  the staging upload page.
- The setting cannot be silently absent. LP-802 made `inbox_domain` fail loudly for this reason;
  the same treatment belongs here, because the failure mode is identical — a plausible-looking URL
  that leads nowhere, produced by a system that started perfectly happily.
- A test asserts the minted URL's host is not a localhost default outside development. A test that
  merely checks the URL is well-formed passes today.
- The open-count question is settled by observation, not by reading the constant: mint a link, open
  it several times, confirm the remaining uses have not moved, then upload and confirm one is spent.
- The processor is told what the link permits — three days, twenty uploads — wherever it is offered.
  Right now nothing on screen says either.

## For the reviewer

The interesting check is the negative one: assert that a deployed configuration CANNOT fall back to
the localhost default. Setting the value in staging fixes today's report and leaves the next
environment to reproduce it.
