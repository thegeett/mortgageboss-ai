# LP-493a — Why did PC-5 abstain on LF-6T3N?

## What this ticket is

An investigation, not a build. LP-493 held PC-5 (*EMD amount & source*) because its derivation returned
a uniform abstain (`{unknown: 2}`), and a rate over one abstain value cannot distinguish **(A)**
correctly abstained from **(B)** could not see it.

## ⚠️ Verdict: **(B) — it could not see it.** Two independent context defects, either sufficient.

**The model was asked whether the earnest money deposit traces to a bank debit, and was shown neither
the deposit nor any transaction.** The assembled context is 1,927 bytes containing five bank statements'
**account-level fields only**. The strings `transaction`, `amount`, `debit`, `deposit` and — decisively —
`earnest` do **not appear in it at all**.

`unknown` was the only answer available. It was not a judgment about the evidence; there was no evidence.

⚠️ **(A) is also true as a fact, but it is not what caused the abstain.** No $7,300 debit exists among
LF-6T3N's 50 transactions. Both findings are real, and the ticket asked that they not be collapsed —
**but the rule never got far enough for the missing debit to matter.**

⚠️ **Both fixes were subsequently applied at Geet's instruction, and PC-5 re-derived. See "The fix and
the re-derivation" below — the outcome changed the picture again.**

## The evidence

### 1. The contract and its deposit

`contract.emd_amount` parses to **$7,300.00**, against a **$365,000** sales price (2.0% — an ordinary
deposit), closing **2026-07-15**.

⚠️ **There is no source PDF to compare against.** LF-6T3N is a **synthetic fixture**
(`build_lf6t3n_snapshot`), not an extraction of a real loan file — its parties have been invented test
data since LP-107. Criterion 1's comparison is therefore not available, and the parsed figure is the only
figure. **This matters for the whole investigation: LF-6T3N was never going to prove a real trace,
because its transactions were authored, not extracted.**

### 2. The bank statements

Five statements across **two accounts** (tails `****5678` ×3, `****2210` ×2), chaining cleanly by
balance: 8,412.55 → 11,233.78 → 9,880.12 → 10,544.90 on one, 40,200.00 → 45,200.00 → 45,320.44 on the
other.

⚠️ **No statement carries a period at all** — `statement_start_date` and `statement_end_date` are absent
on all five. Coverage can only be inferred from the transactions themselves, which span **2026-03-20 to
2026-06-08**. A deposit for a 2026-07-15 closing would plausibly fall inside that window, so the period
is not the reason.

### 3. The debit

**50 transactions**, amounts $0.07 to $60,000, both directions. **No $7,300 debit, exact or near.** The
largest movements are 60,000 (debit, 05-01), 20,000 (debit, 06-08), 20,000 (credit, 06-08).

So **(A) is factually true** — the trace is not in this file.

### 4. ⚠️ What the model actually received — the cause

```
context bytes: 1927
top keys:      ['borrower_mismo', 'documents']
documents:     5 × bank_statement, keys = ['document_type', 'fields']
contains 'transaction' : False
contains 'amount'      : False
contains 'debit'       : False
contains 'deposit'     : False
contains 'earnest'     : False
contains '[redacted]'  : False
```

**Two independent defects:**

**(i) The purchase agreement is missing from the context.** The group declares
`applies_to: [purchase_agreement, bank_statement]`, and the contract *is* on the file — but only the
five bank statements arrive. The borrower context gathers documents **attributed to the borrower**
(`belongs_to`), and the purchase agreement has **`belongs_to=0`** while every statement has 1. A
purchase agreement is a *property* document, not a borrower document, so borrower-scoped gathering drops
it — and with it the deposit amount the rule is about.

**(ii) Transactions are not serialised.** Each statement contributes `fields` only — account-level
figures. The 50 transactions live in the **legacy per-document `transactions` attribute** (`entry.transactions`,
which `all_transactions()` reads and AS-1 rides), and every statement's `lists` is **empty**. The
document context serialises `fields` and, opt-in, `lists` — **it never touches `transactions`.**

⚠️ **The PII scrub is not implicated.** `[redacted]` appears nowhere; this is not CR-8's cause. Nor is
subject enumeration wrong: 2 cases is **one contract × two borrowers**, correct for a borrower-scoped
tag.

### 5. ⚠️ A third finding — the prompt is stricter than the guideline

The prompt asks the model to answer:

> "yes" — a debit on a bank statement plausibly corresponds to the contract's earnest money […]
> "no" — you can see the statements covering that period and NO debit corresponds to it.

**B3-4.3-09 accepts either** *"a copy of the borrower's canceled check **or** a written statement from
the holder of the deposit."* The prompt admits **only a bank debit**, so a file evidencing its deposit
the second way — with the escrow holder's receipt, which LF-6T3N's contract names an
`earnest_money_holder` for — would abstain even with the evidence the guideline asks for. That is a
**prompt defect independent of the context defects**, and it would survive fixing them.

## Assumptions and decisions

1. **(B) is the verdict, and (A) is recorded rather than merged into it.** The missing debit is real, but
   the rule abstained before it could matter — reporting only (A) would have sent us looking for a
   document when the wiring is broken.
2. **Nothing was fixed.** All three defects are scoped below.
3. **LF-6T3N cannot settle this either way**, being synthetic. Even with the context repaired, a
   *correct* trace needs a real file.

## What this changes downstream

**Three scoped fixes, none applied here. PC-5 stays held regardless — each needs its own derivation run
and its own evidence.**

| # | fix | scope | affects other rules? |
|---|---|---|---|
| 1 | Borrower context must gather **non-borrower documents** a group declares in `applies_to` (or PC-5 must not be borrower-scoped) | the context builder, or PC-5's subject | ⚠️ **Yes** — any borrower-subject group needing a property document has this. `credit_inquiries` (CR-5) declares `letter_of_explanation`, which may be unattributed too |
| 2 | Serialise `entry.transactions` into the document context, opt-in like `include_lists` | the document context builder | ⚠️ **Yes** — every future cross-source rule reading a bank debit |
| 3 | Widen PC-5's prompt to the guideline's evidence list (cancelled cheque **or** deposit-holder statement) | PC-5's prompt only | No |

⚠️ **Fix 2 is the more general one** and is worth doing before more cross-source rules are written — the
transactions/lists split is a live trap: a group can declare `include_lists`, see an empty list, and
conclude the data is absent when it is one attribute away.

**PC-5 needs, to resolve honestly:** a **real** loan file carrying a purchase agreement *and* statements
covering the account the deposit left — plus fixes 1 and 2, without which no file will resolve it.
Recorded in `priya-open-questions.md` §15.

## No ADR

An investigation. Nothing architectural changed, and the three fixes are defects in existing mechanisms
rather than new decisions. If fix 2 lands, the transactions/lists split may deserve an amendment to the
context-assembly ADR — but that belongs to the ticket that makes the change.

## The fix and the re-derivation (added at Geet's instruction)

The investigation was scoped read-only; Geet then asked for both fixes and a re-derivation. Both shipped
as **`ContextOptions` opt-ins**, the established pattern (`include_lists`, `include_stated_liabilities`),
**defaulting off** — so every other group's context is byte-identical and the suite passed **unchanged at
4587**.

| fix | what it does |
|---|---|
| `include_unattributed_documents` | a borrower context also gathers documents with **no** `belongs_to` whose type is in `applies_to`. ⚠️ **Never another borrower's** — that would be the guessed attribution LP-332/LP-336 forbid, and a test pins it. |
| `include_transactions` | serialises the legacy `entry.transactions` attribute into a gathered document, capped and PII-scrubbed exactly like `_serialize_lists` |

**The context went 1,927 → 7,945 bytes**: the purchase agreement now arrives, and **50 transaction rows**
with it. `earnest`, `transaction`, `amount` and `debit` are all present; nothing is `[redacted]`.

### ⚠️ The re-derivation — and PC-5 still does not activate

```
contract.emd_sourced   cases=2   disagreements=1   rate=0.5000
d1 {unknown: 2}     d2 {no: 1, unknown: 1}     DISAGREE: 'unknown' vs 'no'
```

**Both results are informative, and they say different things:**

1. **The fixes worked.** The uniform abstain is gone — the model now engages with the data and produces
   different answers. The old `1.0000` was measuring blindness.
2. **PC-5 is held for a NEW reason: 0.5000 is far too unstable to activate.** It is no longer "could not
   see"; it is **"sees the data and cannot decide consistently."**

⚠️ **A perfect rate was hiding a coin-flip.** This is the sharpest illustration yet of why a
self-consistency rate is not an accuracy: PC-5's 1.0000 and its 0.5000 describe the same rule, and the
worse-looking number is the honest one.

**And the disagreement is explicable, which makes it useful.** Recall (A): **no $7,300 debit exists** in
the 50 transactions. So the model is oscillating between *"no matching debit → `no`"* and *"I cannot see
every account → `unknown`"* — exactly the boundary the prompt draws:

> "no" — you can see the statements covering that period and NO debit corresponds to it.

⚠️ **That instruction asks the model to judge whether the statements are COMPLETE, and nothing in the
context tells it.** No statement carries a period (`statement_start_date`/`_end_date` are absent on all
five), and there is no account roster to compare against. **The no/unknown boundary is unjudgeable as
written** — a fourth finding, and the one now blocking PC-5.

### What PC-5 needs now

1. **A statement-completeness signal** — periods on the statements, or an account roster — so the
   `no`/`unknown` boundary is decidable rather than guessed. Without it the rate will stay near 0.5
   whatever the file.
2. **The prompt widened to the guideline's evidence list** (cancelled cheque **or** the deposit holder's
   statement — finding 5 above), which is still unfixed.
3. **A real file** where the trace is known to exist (§15).

**Only (1) and (2) are ours.** Fixing them and re-deriving is a build ticket, not this one.

## Assumptions and decisions (revised)

1. **(B) remains the verdict for the ORIGINAL abstain.** The re-derivation confirms it: with the data
   visible, the answer changed.
2. **PC-5 still does not activate**, and the bar is updated to record the 0.5000 and its cause rather
   than the earlier "uniform abstain" reason — the old text is now wrong.
3. **The two opt-ins default off**, so no other group re-derives. A test pins that `contract_emd` is the
   only group declaring either.
