# LP-479 — `stable_row_id` on tradelines

## What this ticket is

LP-476's census established that only `bank_statement.transactions` declares `stable_row_id`; every other
captured list, tradelines included, produces rows with **no durable identity**. LP-480's per-liability
enumerator needs that identity to anchor a per-row finding to a subject that survives a re-run.

This ticket turns that identity on for the credit report's `tradelines` list and proves the ids are
content-derived, unique, and deterministic — against the **two stored credit-report extractions**, with no
re-run and no model calls.

**Phase C (writing a rule that reads `credit.tradeline_count`) was SKIPPED at the requester's direction**
after the Phase A finding below. `ACTIVE_RULE_IDS` therefore stays **37**, not 38.

## What Phase A found

**1. Both tags materialize — proven on real data, not a fixture.** Building a snapshot from the two stored
credit-report extractions through the real capture path (`build_list_rows` → `finalize_lists` →
`materialize_tags`) yields `credit.tradeline_count = "35"` (21 + 14) and
`credit.tradeline_monthly_payment_total = "6461"`. The producers are wired; the census's claim holds.

**2. `stable_row_id` is content-derived, with one honest caveat.** `finalize_lists` calls
`assign_content_ids(LIST_PREFIX, bases)` where each base is `{doc: <document_content_id>, list: <name>,
**the entire row content}` — a sha256 over the whole row, scoped by document and list name.
⚠️ **The one positional element:** byte-identical payloads get an incrementing occurrence index folded into
the hash, so exact duplicates still receive *distinct* ids, but which id lands on which duplicate is
order-dependent. That is an ordering dependency for exact duplicates only — never a collision.

**3. ⚠️ The ticket's composite-key premise does not apply.** The ticket asks which fields form "a durable
composite identity (creditor + account number fragment + date opened, or similar)". **The mechanism takes no
composite key** — it hashes all 14 fields. There is nothing to choose and no per-field null policy to design.
See "Assumptions" for what that means for nulls.

**4. Version/fixture risk is nil.** `ListRow.row_id` already exists as `str | None = None`, so populating it
is a **value** change, not a schema change (the LP-421 additive precedent ⇒ no bump). And the committed golden
`lf6t3n_tagged_snapshot.json` holds **5 bank statements and zero `lists`** — no credit report, no tradelines —
so flipping the flag cannot alter its bytes.

**5. ⚠️ The free-proof rule had no target — this is why Phase C was skipped.** `credit.tradeline_count` is read
by no spec and claimed by no activation bar (confirming the census), **but no rule in the 135-rule catalog is a
bare tradeline count**. All 13 CR rules need more: CR-3 payoff documents, CR-4 fuzzy matching, CR-7 a minimum,
CR-11 public records, and CR-12 — the tempting one, since `is_disputed` fills 35/35 — is explicitly a Priya/AI
question per LP-453's own docstring and ADR-353, so it fails the ticket's "no threshold, keep it boring" bar.

Worse, a spec **requires** a `rule_kinds.csv` row: `load_rule_spec` cross-checks kind / numeric_check /
priya_validated / threshold_needs_signoff and raises `RuleSpecInconsistent` otherwise. `rule_kinds.csv` is
hand-editable (only `fact_tags.csv`, `rule_tags.csv` and `tag_dependencies.csv` are generated — the LP-476
trap does **not** apply here), but two tests pin `len(rules) == 135` and `rules.inserted == 135`. So writing
the rule meant **adding a 136th rule to a domain catalog no domain expert asked for**. The requester chose to
skip it rather than pay that cost for a scaffold.

## Phase B — what changed

Two files, six lines:

1. **`docs/schema-specs/005-credit-report.json`** — the tradelines `nested_lists` entry gains
   `"stable_row_id": true` (and `"redact": ["account_number_masked"]`, see the new finding below).
2. **`backend/app/verification/snapshot/documents_section.py`** — `_TRADELINES_LIST` gains
   `stable_row_id=True` with a comment recording why no composite key is needed.

**Both were required, and neither is redundant.** `documents_section.py` is **hand-maintained**: the generator
emits a ListSpec *snippet* for it (`emitters.py`: "a merge-conflict factory, D2 — wiring is a later step"),
never a patch. The spec is what a regeneration would reproduce; the module is what actually runs.

**The LP-445 check holds.** Regenerating the extractor from the edited spec produces a **byte-identical**
`credit_report.py` — `stable_row_id` touches only the ListSpec snippet, not the extraction model — and the
regenerated snippet now emits exactly the `stable_row_id=True` + `redact=frozenset({"account_number_masked"})`
that the committed module carries.

### ⚠️ A NEW finding — a latent PII regression, fixed here

The committed `_TRADELINES_LIST` carried `redact=frozenset({"account_number_masked"})` — the deliberate LP-443
row-PII backstop — while **the schema spec never declared `redact` at all**. Since `documents_section.py` is
maintained by pasting the generated snippet, **anyone regenerating and pasting would have silently dropped that
redaction**, un-masking a leaked full account number. The spec now declares it, so the generated snippet
reproduces it. **No behaviour changed** (the module already redacted); the spec was corrected to match what
ships. This was not in the ticket's scope but is a direct consequence of the spec/module workflow it exercises.

### The ids, on the real documents

| report | rows | unique ids | sample |
|---|---|---|---|
| 250 | 21 | **21/21** | `lsta6ae6cd63e449070` PENNYMAC LOAN SERVICES |
| 251 | 14 | **14/14** | `lst923ec1ccd232120d` CAPITAL ONE |
| **combined** | **35** | **35/35 globally unique** | **0 cross-document collisions** |

Content-derivation proven, not assumed:

- **deterministic** — two builds of the same input produce identical ids;
- **order-independent** — reversing the row order yields the **same id set** (a positional scheme could not);
- **document-scoped** — the same rows under a different `document_content_id` produce a disjoint id set, so
  two borrowers with the same creditor row never collide.

## Phase D — the outcomes, and what the skip costs

**Outcome 1 — a real value.** `cr0` alone → count `21`, payment total `6370`. `cr1` alone → `14` / `91`.
Both together → `35` / `6461` (the loan-level aggregate spans reports).

**Outcome 2 — no credit report in the file** → both tags resolve to **`"unknown"`**.

**Outcome 3 — never zero.** Also proven for the subtler case: a credit report *present* but with **zero
tradelines captured** still yields `"unknown"`, never `"0"` — absent ≠ empty.

**The code path, not just the observation** (the ticket's requirement), is two-layered:

1. **The recipe fails closed.** `_credit_tradeline_count` returns `_UNKNOWN` when `not rows`;
   `_credit_tradeline_monthly_payment_total` returns `_UNKNOWN` when no row carries a payment figure, and
   skips an unparseable value rather than guessing. Neither can emit `0` from missing data. A *present* 0
   (a paid-off account) still contributes 0 honestly — the distinction the fail-closed design exists to keep.
2. **The gate blocks before any rule logic runs.** `gate.py` checks load-bearing tags in a fixed order:
   `tag is None` → `COULDNT_CHECK` ("could not be found in the file"), then `tag.value == _UNKNOWN` →
   `COULDNT_CHECK` ("present but unclear"). So **no rule can ever read a fabricated 0** — the value never
   reaches the rule body.

⚠️ **What the skip costs, stated plainly.** With no rule written, the `couldnt_check` **verdict** is proven at
the code path above rather than *observed* as a rule output. The list→tag path is proven end to end on real
data; the tag→rule hop is not exercised. **LP-480 is the first thing that will actually exercise it.**

### Regression check — AS-1, AS-2, AS-12, IN-12

These four ride the **legacy** `transactions` / `schedule_c` / `schedule_e` attributes, which coexist with
`lists` and were deliberately never migrated. Rather than re-evaluate them (see the cost note), the proof is
stronger and model-free: the **LF-6T3N snapshot these rules read is byte-identical before and after**, same
size and same md5 (`0ef2b731f9d963a8ab1e6a4c09074381`), built from a clean tree via `git stash` and compared.
Identical input ⇒ identical verdicts. Their targeted tests pass (162 selected), as does the full suite.

`ACTIVE_RULE_IDS` = **37**, unchanged (not 38 — Phase C skipped). `SNAPSHOT_VERSION` = **4**.

### ⚠️ The honest cost note

The ticket requires **$0 / no model calls**, and **no tokens were consumed**. But an early attempt at the
regression check called `evaluate_rules` live, and **AS-12 is judgmental**, so it reached for a real reasoner
and attempted AI calls. Every attempt failed non-transiently before any completion — **`ai_call_succeeded` = 0
in that run**, so nothing was billed. The approach was abandoned for the snapshot-diff proof, which touches no
model at all. Recording it because "no model calls" and "no model calls *attempted*" are not the same claim,
and a reader deserves the second one.

## Assumptions and decisions

1. **The row-identity scheme is whole-row content hashing — inherited, not designed.** No composite key was
   chosen because the mechanism does not accept one. This is a deliberate decision to reuse the
   `bank_statement.transactions` precedent unchanged rather than invent a tradeline-specific identity.
2. **What happens when identity fields are null.** A null is part of the content dump, so a row with a null
   creditor still derives an id from its other 13 fields. Two tradelines can only collide if **all 14 fields
   are byte-identical**, and `assign_content_ids`' occurrence tiebreak separates even those. Fully-absent rows
   are dropped before ids are assigned ("no hallucinated empty row"). **Nothing merges, so nothing
   guess-merges** — the `_per_account` (LP-336) failure mode does not arise here.
3. **The `redact` spec addition is a correction, not a feature.** It makes the spec describe shipped
   behaviour; no runtime behaviour changed.
4. **Byte-identical was proven on the rules' INPUT, not their output.** Re-evaluating AS-12 requires a live
   judgmental reasoner, which would cost money and be non-deterministic. An identical snapshot is a stronger
   guarantee than an identical verdict sampled once.
5. **No ADR written.** The row-identity scheme would have been a design choice worth an ADR had one been made
   — but the decision was to *reuse* the existing `assign_content_ids` contract verbatim. ADR-worthy content
   would duplicate what LP-437/LP-443 already record. The two findings that are new (the composite-key premise
   not applying; the spec/module `redact` drift) are recorded here.

## ⚠️ What this actually proves — read this before citing it

**The list → tag path works on 2 documents of apparently one bureau format.** Both stored credit reports came
from the same corpus and produced the same 14-field row shape.

**This is not evidence that the credit extractor generalises across bureaus.** Experian, Equifax and
TransUnion merges differ in layout, and a tri-merge differs again from a single-bureau pull. Nothing here
measures that, and **n=2 is not a measurement** (LP-476's corpus-thin flag applies in full).

**It must not be read as "7 credit rules are ready."** It says one thing: rows now carry durable ids, and two
aggregate tags compute correctly on the credit reports we happen to hold.

## What this changes downstream

- **LP-480 (the per-liability enumerator) is unblocked on identity.** Tradeline rows now carry `row_id`, so a
  per-row finding can anchor to a durable subject. LP-480 will also be the **first** exercise of the tag→rule
  hop that Phase C's skip left unproven — worth budgeting for, since a surprise there surfaces in LP-480
  rather than here.
- **LP-481 inherits an unanswered question:** which rule should read `credit.tradeline_count`. Phase A
  established that **no catalog rule fits**, so LP-481 must either add a 136th catalog rule (and move the two
  pinned counts from 135) or leave the tag consumer-less. That is a catalog decision, not an engineering one.
- **A corpus ask stands, unchanged.** Everything credit-related remains gated on n=2. Credit reports from more
  than one bureau format belong in the same document request LP-476 already recommends batching with the
  ADR-332 calibration corpus.
- **Any other list needing row identity is now a one-line spec edit** — `"stable_row_id": true` plus the
  hand-wired `_LIST_SPECS` line, with the regeneration check to confirm the module is unaffected.
