Everything in Phase 4 reads `settings`, so this goes first. It is deliberately small: four ADRs, one
constant moved, one number widened, three settings added that nothing reads yet.

---

## What was done

### The domain moves to settings

`INBOX_DOMAIN = "inbox.mortgageboss.ai"` was a module constant in `models/loan_file.py`, and its own
comment anticipated this move — *"may move to settings later if it needs to vary per environment."*
It needs to. A staging file advertising `@inbox.mortgageboss.ai` would take delivery of **real
borrower mail**, which is not a configuration inconvenience but a data-handling incident.

`settings.inbox_domain` now, defaulting to the production value. Staging sets
`inbox.staging.mortgageboss.ai`.

**The import is inside the method, and that is a decision rather than an oversight.** No model in
this package imports `core.config` — verified across `app/models/` — and this ticket's blast radius
is the setting, not the layering rule (protocol rule 2.6). A module-level import would also freeze
value at import time, which defeats the per-environment point and breaks any test that patches it.

### The token widens to 128 bits

`INBOX_TOKEN_BYTES` 12 → 16, so `token_urlsafe` yields 22 characters instead of 16.

The reasoning is worth keeping because it is what makes this "free now, expensive later": the token
is a **bearer capability with no expiry**. It is printed inside an email address, so it gets
forwarded, quoted in replies, and auto-filed by mail clients the system has no reach into. Entropy is
the whole of its security — there is no second factor and no revocation. 96 bits was already
adequate; 128 costs nothing today and cannot be retrofitted cheaply once tokens are in circulation on
real files.

Existing tokens keep working. Nothing validates length on read.

### Three inbound settings, read by nothing yet

`inbound_bucket`, `inbound_queue_url`, `inbound_kms_key_arn` — all `str | None`, all `None` until
INFRA-1 applies. LP-803 is the first consumer.

`None` is the honest state of an environment with no inbound pipeline, which is every environment
today. Defaulting them to plausible-looking strings would make a missing pipeline look configured.

The six `smtp_*` settings are untouched and still point at MailHog for local development, per the
plan.

### Four ADRs, and one amendment

- **ADR-395** — the ingestion source is pluggable; nothing downstream of ingest names its provider.
- **ADR-396** — SES over SendGrid, inbound and outbound.
- **ADR-397** — the inbox **address** is exposed; the `inbox_token` **field** is not.
- **ADR-398** — outbound mail never carries an attachment containing borrower NPI.
- **ADR-094 amended** by ADR-397.

---

## The ADR-094 change, stated plainly

The plan says: *"Expose `get_inbox_address()`; never the raw token."* Implemented as written — but
the framing deserves care, because it can be read as preserving ADR-094's guarantee when it narrows
it.

**The address contains the token.** `lf-{token}@{domain}`. Anyone holding the address holds exactly
the capability ADR-094 was protecting: the ability to post documents into a loan file. Exposing the
address is therefore a real change of posture, not a technicality that keeps the old rule intact.

What the rule still buys is worth having: the capability is handed over in **one shape, through one
accessor**, to a caller already entitled to the file — rather than riding along as a field on an
unrelated payload. That is a meaningful narrowing. It is not the same as the token being secret.

ADR-397 records it that way deliberately. Describing the address as safe because the field name is
absent would be the more dangerous position, because it invites treating it as ordinary metadata on
some future endpoint.

`tests/integration/test_contracts_leaks.py` continues to assert `inbox_token` is absent from
responses, and continues to pass.

## Why no migration

The plan says none, and it is right. `inbox_token` is `String(SHORT_STRING)` — `SHORT_STRING = 64`
(`models/types.py:28`), and `token_urlsafe(16)` produces 22 characters. Verified rather than assumed.

Existing 16-character tokens remain valid; the widening applies to tokens minted from here.

---

## Assumptions

- **The default stays production's domain.** A missing `INBOX_DOMAIN` env var in a non-production
  environment therefore yields the production domain rather than an error. Accepted for now: nothing
  receives mail until INFRA-1, so the failure is inert this cycle. It stops being inert the moment
  inbound DNS exists, and INFRA-1 is where the staging value must actually be set.
- **`token_urlsafe(16)` is 22 characters**, not 21 or 24 — base64url of 16 bytes without padding.
  The test asserts `>= 16` and so does not pin the exact figure; the column has 64 either way.

---

## Deliberately not done

- **No change to the six `smtp_*` settings.** The plan keeps them on MailHog; outbound identity is
  INFRA-3's.
- **No endpoint exposing the address.** ADR-397 establishes that it may be exposed; it does not
  expose it. The consumer is LP-808's connection flow.
- **No `EncryptedString` on anything.** The protocol defers body encryption to a backlog ticket —
  raised in LP-803's doc, where the column is actually created.
- **No provider implementation.** Route B only, per the protocol's pre-made decisions.

## For the reviewer

The three standing reviewer checks, and what this ticket does about each:

- **Tenancy** — no `company_id` derivation anywhere in this diff. LP-805 remains the only resolver.
- **Message content in logs** — no logging added.
- **AI in the decision path** — no AI touched.

The judgement calls worth a second opinion, in the order I would attack them:

1. **The method-level import of `settings` in a model.** It breaks no existing rule that is written
   down, but it is the first model in the package to reach for config, and the reviewer may prefer
   the accessor moved to a service instead. That would be a larger diff than this ticket warrants,
   which is why it was not done.
2. **The ADR-397 framing.** If the reviewer reads the address exposure as fully compatible with
   ADR-094 rather than a narrowing of it, one of the two readings is wrong and it matters which.
3. **The default domain being production's.** The alternative is no default, which fails closed and
   would make every existing test set it.
