# LP-201 — Per-field extraction confidence

## Summary

Thread a **per-field confidence** signal from the document extractors through to
storage, as additive/nullable plumbing. Each typed-core extracted field can now
carry a nullable `confidence` (0..1) plus a `confidence_source` tag; the model is
asked (per prompt) to rate each field, and that rating is parsed **honestly** —
a field the model doesn't rate is `null` / `not_provided`, **never a fabricated
default**. Separately, the model's already-computed **document-level** self-reported
confidence — which was used for the review gate but then dropped at storage — is
now persisted on the `extractions` row. Nothing consumes the confidence yet; this
is a prerequisite for the Stage-1 snapshot work.

## Acceptance criteria

- [x] Extraction output schema carries a nullable per-field `confidence` (0..1) +
      `confidence_source` tag, optional everywhere.
- [x] Additive & non-breaking: existing extracted values keep their shape; current
      consumers (DTI escrow reads, cross-source, finding source-matching) untouched.
- [x] Storage migration added (Alembic) for the persisted signal; nullable; no
      backfill of old rows.
- [x] Extractors with a genuine signal carry it through, tagged correctly.
- [x] Extractors without one store `null` / `not_provided`.
- [x] No fabricated/defaulted confidence anywhere (no silent `1.0` / `0.9` / `0.0`).
- [x] Tests: real-signal path, no-signal path, no-fabrication assertion, existing
      behavior unchanged, round-trip persistence.
- [x] CI green: ruff, mypy, pytest (affected suites).

## Phase 0 findings (what the code actually had)

- **Storage** is a single JSON blob — `extractions.extracted_data` (ADR-057), a
  flat `{field: {value, source:{page,snippet}}}` + `additional_sections`. Not
  columns. So per-field confidence is naturally **optional JSON keys inside that
  blob — no column migration is needed for the per-field part.**
- **Per-field confidence signal: NONE** for all 20 extractors. `TypedField` was
  `{value, source}` only; `parse_typed_core` emitted `{value, source}`; the model
  was not asked for per-field confidence. Structural hints exist at parse time
  (`coercion_lost`, field-presence) but are booleans, not genuine 0..1 numbers —
  turning them into a number would be fabrication.
- **The one genuine numeric signal** is a **document-level** model self-reported
  `confidence` (`coerce_confidence(payload["confidence"])`), present on every
  extractor result. It was used only for the low-confidence review gate
  (`result.confidence < _CONFIDENCE_THRESHOLD`) and structured logging, then
  **dropped** — `create_extraction_version` persisted only `result.data`, and the
  `extractions` table had no confidence column.
- **Consumers** read `extracted_data[field]["value"]` (`services/dti.py`,
  `cross_source.py`, `finding_source_matching.py`, `verification_engine.py`,
  `extractions.py`, `documents.py`) — adding sibling keys is safe.

## Decisions (agreed with the requester before building)

1. **Per-field confidence: the model rates each field.** The only honest source of
   a genuine per-field number is the model self-rating, so the extraction prompts
   were extended to request it. This deliberately overrides the ticket's default
   "no prompt redesign" guidance (explicitly approved).
2. **Mechanism: a `field_confidence` map, not inline keys.** Rather than interleave
   a `confidence` key into every field object of 18 heterogeneous prompts (some
   nested — bank_statement/tax_return), each prompt now asks for one top-level
   `"field_confidence"` object mapping *each typed-core field name → 0.0–1.0 | null*.
   This is a single, uniform, low-risk edit per prompt and is robust to varied
   prompt shapes. `parse_typed_core` reads that map by field name. Equivalent
   outcome (the model rates each field), cleaner and less truncation-prone.
3. **Honesty over completeness.** A field absent from `field_confidence` →
   `confidence=None, confidence_source="not_provided"`. A new
   `coerce_optional_confidence()` returns `None` (not `0.0`) for missing/garbage,
   so nothing is ever defaulted. `confidence_source="model_self_reported"` only
   when the model actually gave a number.
4. **Scope: typed-core fields only.** Catch-all (`additional_sections`) values are
   uncoerced strings where confidence is meaningless; they are left unchanged (and
   the prompt asks for confidence on typed-core only, limiting output growth).
5. **Rescue the document-level signal into columns.** Add nullable `confidence` +
   `confidence_source` columns on `extractions` (the Alembic migration), populated
   from the existing `result.confidence`, tagged `model_self_reported`.
6. **Regression goal relaxed (by agreement).** Because the prompts changed, we
   cannot guarantee byte-identical extracted *values* going forward (LLM output
   isn't deterministic once the contract changes). The regression guarantee is
   therefore: the shape stays backward-compatible, consumers still read `value`,
   and no confidence is fabricated — **not** "identical values".

## Which extractors emit confidence, and of what kind

- **All 20 typed extractors**: per-field confidence is now **requested** from the
  model (prompt contract) and, when the model returns it, stored as
  `model_self_reported`. Where the model returns nothing for a field, the field is
  `not_provided` — the honest, expected state until real signals mature.
- **No extractor** derives a per-field number from a structural/regex/presence
  signal — those remain reserved `ConfidenceSource` values, not emitted (would be
  fabrication otherwise).
- **Document-level** `model_self_reported` confidence is now persisted for every
  Tier-1 extraction (the previously-dropped signal).

## Assumptions & notes

- The document-level `coerce_confidence` keeps its legacy behavior (missing →
  `0.0`) because the review gate depends on it; that value is what we persist. The
  per-field path uses the new nullable coercer so per-field absence is honest.
- Tests build the schema from `Base.metadata.create_all` (not migrations), so they
  exercise the new columns directly; the Alembic migration is for real/deploy DBs.

## Post-review hardening (code review, 2026-07-09)

A code review of the first cut found that the *document-level* path reintroduced
the exact fabrication LP-201 exists to prevent, plus a clamp bug and some
redundant state. All MUST-FIX items were applied; see [ADR-238](../../decisions.md).

- **[correctness] Document-level provenance was fabricated.** The extract branch
  hard-coded `confidence_source="model_self_reported"` and passed
  `result.confidence` unconditionally. But `coerce_confidence` collapses a *failed*
  extraction (`.failed()` → `0.0`) or a model that omitted the key to `0.0`, so
  every such row was stored as `0.0 / model_self_reported` — a defaulted 0.0
  mislabelled as a genuine model rating, and the `not_provided` / NULL branch was
  unreachable. **Fix:** new `document_confidence_provenance(confidence)` (in
  `ai/extraction/parsing.py`) — only a **positive** confidence is a genuine
  self-report; a non-positive one is stored as `NULL` / `not_provided`. A defaulted
  0.0 and a real model rating are now distinguishable.
- **[correctness] `coerce_optional_confidence` fabricated `1.0` from garbage.**
  `NaN`/`Infinity` (which `json.loads` accepts) and out-of-range strings like
  `"85%"` were clamped to `1.0` (max certainty). **Fix:** it now returns `None` for
  non-finite or out-of-range values — never clamps a bogus number up. A shared
  private `_parse_confidence` primitive backs both coercers (removing the
  near-duplication); the doc-level `coerce_confidence` **keeps** its legacy clamp
  (classification / cross-source / the review gate depend on it) but no longer turns
  `NaN`/`Infinity` into a fake `1.0` (those now → `0.0`).
- **[simplification] Per-field `confidence_source` is derived, not stored.** It is a
  pure function of the number (`model_self_reported` iff present), so storing it
  alongside `confidence` risked a contradictory record. `parse_typed_core` now
  stores only the number; readers derive the tag via
  `ConfidenceSource.for_confidence`. The reserved `structural` / `field_presence`
  enum values (never emitted) were removed until the ticket that first emits them.
- **[altitude] `confidence_source` column is now CHECK-constrained.** `ConfidenceSource`
  moved from `ai/extraction/shape.py` to `app/models/extraction.py` (next to
  `ExtractionStatus`, the model that owns the column — an already-permitted
  `ai → models` import). The column uses `str_enum(ConfidenceSource)` (VARCHAR+CHECK,
  ADR-037) instead of a free `String`, so the vocabulary can't drift and a bad
  literal can't persist. The migration emits the matching enum DDL.
- **[conventions] ADR added.** [ADR-238](../../decisions.md) records the persisted
  columns, the `confidence_source` vocabulary, and the deliberate 18-prompt edit
  (per the repo CLAUDE.md rule that architectural decisions get an ADR), cross-refs
  ADR-144/145.

Net: the earlier notes above that say per-field confidence is stored as
`model_self_reported` / `not_provided`, or that the document-level column is always
`model_self_reported` when present, are **superseded** by the above — the tag is
derived per field, and the doc-level column is honestly `not_provided`/NULL for
failed/defaulted extractions.
