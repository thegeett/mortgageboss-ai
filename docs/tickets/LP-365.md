# LP-365 — Wire the snapshot/rules orchestrator into the real verification run

## WHAT THIS IS

The engine's **first contact with a real loan file.** The LP-316/321 fact-tag architecture — the
orchestrator, the reconciler (LP-322), the snapshot table (LP-209) — was built, tested, and migrated over
~20 tickets and **never executed on a real file, not once.** The Run button enqueued exactly one task: the
AI cross-source sweep. This ticket adds the second task. **The code is small; the report is the deliverable
— nobody knew what the rule engine says about a real loan file.**

## ACCEPTANCE CRITERIA (met)

- A Celery task builds+persists a snapshot, evaluates the ACTIVE rules, reconciles + persists findings —
  enqueued **alongside** the sweep, on the same run. Both run; both persist; outputs stay separate.
- Fail-closed run status; counts never summed; the LP-78.1 cache decision recorded.
- The real run executed on **DB LF-6T3N** with the honest per-tab counts reported (below).
- No engine/rule/tag/spec change; `ACTIVE_RULE_IDS` unchanged; AI sweep behaviour-identical; frozen fixture
  trace unchanged. `mypy app/` clean; full backend suite **2307 passed**.

## THE PHASE-0 DECISIONS

- **Run status — FAIL-CLOSED.** Two tasks write one `Verification` row. The rule task marks the run FAILED
  on exhaustion; the sweep's `COMPLETED` set is **guarded to never overwrite a FAILED**
  (`cross_source.py:183`). A run reads COMPLETED **only if both passes completed**; if either failed, FAILED.
  A run marked COMPLETED while the governed engine silently failed is a run-level false-green.
- **Counts — never summed.** The sweep keeps sole ownership of `red_count`/`yellow_count`. An ungoverned
  75%-confidence AI observation and a governed, gated, provenance-carrying rule verdict are not the same kind
  of thing; the rule findings carry their own `evaluation_outcome` axis, counted separately at read (LP-369).
- **The LP-78.1 cache — inherited, flagged as mis-keyed.** It hashes the *cross-source* inputs; the rule
  engine reads a *superset* (all documents), so a cache-hit could skip a rule run a rule-relevant-only change
  should have triggered. The rule task rides the same cache-miss trigger for now; a rule-aware fingerprint is
  a follow-up. Not silently inherited.
- **Concurrency** — two tasks, two sessions, one row: they touch disjoint fields (the rule task writes only
  `status`/`error_detail` on failure; the sweep owns counts), and the FAILED guard makes the status
  order-independent. **Cost/runtime** — a real run is **~282s and ~$0.15–0.30** on `claude-sonnet-4-5`
  (Stage A + Stage B ≈ $0.087 for 17 deposits, plus materialization for the live rules' groups). This now
  runs on every verification, for every file.
- **Real model, not a stub** — the task passes no reasoners → `run_verification` uses `reasoners=None`.

## THE FIXTURE-vs-DB DIFFERENCE (it was expected to break — it SURVIVED)

The DB file has **30 documents**; the fixture (`lf6t3n_tagged_snapshot.json`) is the **stripped 5-bank-
statement subset** (settled with a number). We were told to predict nothing because the fixture numbers might
not survive. **They survived, for a real reason:**
- **AS-1 = 15 couldnt_check + 2 needs_review — IDENTICAL to the fixture claim.** Distinct reasons: *"operand
  'threshold' could not be resolved"* ×15 and *"a load-bearing tag confidence (0.4) is below the floor
  (0.5)"* ×2.
- **`gross_monthly_income` DOES resolve on the real file → $28,168.80** (from the real income docs). But the
  **DTI is still gated**: `housing.insurance_monthly is unknown` (no insurance binder among the 30 docs), so
  AS-1's threshold is still None. **The insurance-orphan bug (LP-367) breaks the DTI on the real file too**,
  and AS-1's false DTI dependency (LP-366) makes it AS-1's problem. The fixture wasn't lying about AS-1 —
  it was right for a reason that holds on the real file.

## RUN #2 — THE RECONCILER'S FIRST-EVER EXERCISE (LP-322)

Every finding re-matched by `(rule_id, subject_key)` and carried forward, outcome unchanged — **no duplicate

(Run #1 minted all 38 — no prior; Tab 3 legitimately empty. Run #2 is the first proof the reconciler works.)

## THE SURPRISES — each its own ticket (REPORTED, not fixed)

- **LP-366 — AS-1's false DTI dependency**: AS-1 needs only `gross_monthly_income` (present, $28,168.80) but
  reads it through the whole gated DTI calc → 15 `couldnt_check` on the real file.
- **LP-367 — the orphaned `housing.insurance_monthly`**: no producer exists; unknown on every file; a
  REQUIRED DTI gate → the DTI can never compute anywhere.
- **95 `tag_production` degradations** on the real run — the AI materialization degraded 95 times (fail-closed
  to unknown, per the stage backstop). Worth its own investigation (rate limits? off-type docs? the
  `unknown`-doc-type entries?). Reported, not diagnosed here.
- **9 stale `xsrc.*` `deterministic_rule` findings** (created 2026-07-08, `evaluation_outcome` null) — older
  LP-74-engine artifacts still live in the DB. The five-tab read (LP-370) must place null-outcome
  deterministic findings deliberately (Tab 5, or a cleanup).

## WHAT THIS SURFACE CANNOT DO YET / what LP-366/367/369/370 must now address

- **LP-369** — the read path drops GREEN (`status in (RED, YELLOW)`), so **Tab 2 (Satisfied) has no read
  path**; and the DTI view schema lacks `gated`/`gate_reason` (the $0.00-insurance display false-green). Both
  are display-layer.
- **LP-370** — the five tabs, keyed on `evaluation_outcome` (§8 tabs 1-4) + origin (Tab 5) — and it must
  handle the 9 stale null-outcome `deterministic_rule` findings.
- **LP-366/367** — fix AS-1's income read + wire the insurance producer, so the 15 `couldnt_check` become the
  one genuine finding (the large deposit) the engine is currently suppressing.

## WHAT BUILDING IT REVEALED

The architecture worked on first contact: the orchestrator built a 30-doc snapshot, materialized the live
rules' tags, evaluated, reconciled, and persisted — end to end, on a real file, unchanged. **The four-tab
outcome axis mapped cleanly; a reason was present on every gap; the subject resolved.** The revelations were
all *upstream* (the insurance orphan, AS-1's dependency, the 95 degradations) — the engine reported them
honestly rather than papering over them, which is the whole point. **The tests asserted the parts for 20
tickets; the first time we asserted the path, it ran — and it told the truth about a real file.**
