- **Migration:** `d81b6e4c25f7`

---

## Reply was blocked by the data model, not by a missing button

§C.5 states it exactly: LP-809 creates a draft **plus a `communication_needs_items` join**, and
LP-811's send endpoint requires a `draft_id`. A reply to *"is page 4 really needed?"* has no needs
behind it — so it could not become a draft, so it could not be sent. Spec 4.3 asks for reply and
nothing existed.

**The needs-less draft needs no column**, and that is worth stating because it looks like it should.
The one-open-draft index is `(loan_file_id, template_key) WHERE status = 'draft'` with no
`NULLS NOT DISTINCT`, so Postgres treats every NULL `template_key` as distinct: several replies
coexist and none collides with the accumulating request. `get_open_draft` reads by that key, so a
reply is invisible to the request path rather than competing with it.

A NULL `template_key` is also **the truth** — `Communication`'s own docstring says the column is
"NULL for anything composed by hand".

That is a claim about Postgres, so `test_two_replies_can_be_open_at_once` asserts it by **writing the
rows**. Reading an index definition is not the same as it behaving that way, and a processor
answering two borrowers gets an `IntegrityError` if it does not.

---

## One column was carrying two meanings

`external_message_id` means *this message's own id* — it is what LP-805's rung 2 matches a
borrower's `References` against. **LP-815's nudge was writing the id of the message it was
answering into it.**

That routed correctly by accident: a reply's `References` carries the borrower's own id too, so
rung 2 found the nudge row and its loan file. It would break the moment anything stored a genuinely
generated outbound id — rung 2 would then match a thread to a row holding a borrower's id under the
wrong meaning.

`in_reply_to_message_id` is the separated meaning. The nudge is corrected, and the migration moves
existing rows across (and back, on the downgrade, so a rollback leaves rung 2 as it found it).

## Who a reply goes to

**From the stored `inbound_message`**, never from a header read at reply time, and never from the
`Communication` — which has no sender, because LP-805 deliberately declined to copy one: *"copying
them here would put borrower prose in a second place with its own exposure decisions."*

That decision is right and it left the timeline saying "A message arrived" with no From, which
LP-818 could not live with — a processor cannot decide whether to reply without knowing who sent it.
So `services/timeline` reads the sender from the row that already holds it, through the join it
already makes for the manifest. No second copy.

The address is normalised, so a borrower whose client capitalised theirs is answered at the address
the participant list would recognise. A message with no usable `From` is refused: replying to
nowhere is at best wasted and at worst backscatter — LP-815's rule, applied here too.

---

## Read state is a timestamp, importance is a judgement

`read_at` rather than a boolean, because *"unread"* and *"read four days ago"* are the same boolean
and different facts, and the second is what says a message was seen and left. Outbound rows are
never unread — we wrote them — and marking one read is **refused rather than ignored**, because a
caller doing that is confused about something and a silent success hides it.

Reversible in both directions. A processor who opens something at the end of the day and cannot deal
with it needs to put it back; a one-way flag makes the badge a thing to get rid of rather than a
thing to act on.

`is_important` is a **processor's own judgement**. Nothing computes it, no rule sets it and no model
suggests it — the standing rule is that AI may classify and extract and may not decide, and *"this
matters"* is the most decision-shaped flag on the record.

The badge counts over the **whole file**, not over the page. A count derived from `entries` would
shrink when somebody clicked a filter pill, which is a number that teaches its reader to distrust it.

## Deliberately not done

- **`email_threads` is still a table nothing writes and nothing reads.** LP-805 created it; the
  build plan says LP-805 "writes `email_threads` and `references[]`", and only the second half is
  true — `references[]` is written at ingest and read by rung 2. Threading a reply needs
  `In-Reply-To`, which is per-message, so nothing in this ticket needed the table. It is the fifth
  form of the pattern this loop keeps finding and I did not want to ship a sixth silently.
  **Escalated.**
- **A reply is a draft, not a send.** LP-811a's send endpoint takes it from there, with the same
  rate limit, the same suppression check and the same record of what went out. A reply that skipped
  that would be the one outbound message in the product with no guardrails on it.
- **The rate limit applies to replies.** One per address per five minutes, three per day. A genuine
  back-and-forth on one afternoon hits it. Correct as a guardrail, wrong as a conversation limit;
  **escalated** rather than quietly widened.
- **No "view full thread".** Spec 4.3 lists it. Grouping needs either `email_threads` populated or a
  walk of the `References` chains, and both are more than a button.

## Review (second session, protocol §3)

Two findings, both measured rather than read, and both in the two things the ticket asked me to run.

### A — The downgrade destroyed the id it exists to restore

The upgrade and the downgrade both filtered `deleted_at IS NULL`, which looks like symmetry and is
not. **The two statements do different jobs.** The upgrade *chooses* what to migrate, so skipping a
soft-deleted row correctly leaves its id where it already was. The downgrade *restores* a column the
next statement **drops**, so anything it skips is destroyed rather than left alone.

Round-tripped rather than reasoned about:

```
AFTER UP   live: ext=None  reply_to=<live@x>
AFTER DOWN live: ext=<live@x>                 round-trip ok
AFTER DOWN soft-deleted-in-between: ext=None  <- lost when the column drops
```

A row live at upgrade and soft-deleted before a rollback had its id moved out and never moved back.

It matters because of something worth stating on its own: **rung 2 matches `external_message_id`
with no `only_active`.** A soft-deleted outbound message is still routing input. That is defensible
— deleting our record does not unsend the message a borrower is replying to — but it means these
ids are live data rather than tombstones, and the migration was discarding some of them.

The `deleted_at` filter is gone from the downgrade only, with a comment saying why the asymmetry is
deliberate. Three tests: the round trip, the soft-deleted-in-between case, and a control that the
**upgrade's** filter stays — so the two are not later "fixed" into agreement.

`_BACKFILL_NUDGE_REPLY_TO` was hoisted "so a test can execute it" and nothing was executing it. That
is the hook-with-no-consumer shape one size down, and it is now used.

### B — The reply context fetched once per render, not once per open

`ReplyBox` called `fetchReplyContext` in the render body under `if (context === null)`. The fetch is
async, so **any** re-render while the response is outstanding re-fires it — and typing in the reply
textarea re-renders on every keystroke. Measured:

```
PROBE fetches after open: 1
PROBE fetches after two keystrokes (response still pending): 3
```

A processor who starts typing before the context lands is the ordinary case, not a contrived one.
The ticket's own description — "idempotent and fires once per open" — is the half that was wrong;
idempotent it is, once per open it is not.

Moved into a `useEffect` keyed on `(fileId, entry.id)`, with a `live` flag so a resolve after unmount
does not set state. One fetch, before and after keystrokes, pinned by a test whose mock never
resolves so the pending window stays open. Verified by reverting: the test fails.

**This is not the LP-811b pattern and the distinction is worth keeping.** There, state was DERIVED
FROM PROPS during render — React documents that, this codebase already uses it, and I endorsed it.
Here a side effect ran in render, which is a different thing with a different failure mode. An
effect with an honest dependency list is the right tool; the objection in LP-811b was to a
*suppressed* dependency list, not to effects.

### The builder's three, measured

1. **The NULL-`template_key` trick — correct, and tested the right way.** `uq_communications_open_draft`
   is `(loan_file_id, template_key) WHERE status='draft'` with no `NULLS NOT DISTINCT`, so every NULL
   key is distinct and replies coexist. Asserting it **by writing two rows** rather than by reading
   the index is exactly right: it is a claim about PostgreSQL's behaviour, and LP-803's review turned
   on the opposite default mattering.
2. **`ReplyBox` — see finding B.** The instinct to flag it was right and the characterisation was
   optimistic.
3. **The timeline reading the sender through the join — right.** LP-805 deliberately writes no sender
   onto the `Communication`, and LP-812 left the timeline saying "A message arrived" with no From,
   which a processor cannot act on. Reading it through the manifest join rather than denormalising
   keeps one source of truth.

### The column carrying two meanings

Worth recording as the builder's own find in its own code: `external_message_id` means *this*
message's id and is rung 2's input, and the nudge was writing the id of the message it was
**answering** into it. It routed correctly by accident — a reply carries the borrower's own id too —
and would have broken the moment anything stored a genuinely generated outbound id. Separating the
meanings is right, and the migration moving the rows both ways is what made finding A findable.

### The fifth form, and one that already had a net

`email_threads` is a table nothing writes and nothing reads. LP-805 created it because the plan says
so, and the plan's claim that LP-805 "writes `email_threads` and `references[]`" is half wrong. That
is the fifth: a function nothing called (LP-807), a column nothing wrote (LP-813), a spec clause
nothing implemented (LP-815), a hoisted constant nothing executed (above), and now a table nothing
touches. Correctly escalated rather than quietly shipped.

The duplicate `"communications"` key in the exclusion dict is the one case in this loop where the
guard already existed and was not needed twice: `ruff`'s `F601` catches a repeated dict key literal
and is enabled here, so that mistake had two nets under it. Checked rather than assumed.

### Done when, and the standing checks

The reply threads on `In-Reply-To`, read state and importance work, and the needs-less draft needed
no schema change. "View full thread" is unbuilt because grouping needs `email_threads` populated or
a walk of the `References` chains — correctly escalated, and it is the same table above.

The send rate limit applying to replies, so a genuine back-and-forth caps at three a day, is a real
product problem and correctly escalated: three messages is a short conversation, and the limit was
designed for nudges rather than for a processor answering a borrower's question.

Standing checks: no `company_id` derived here; the reply path carries subject and recipient to an
authenticated user of the owning company and logs neither; no AI.
