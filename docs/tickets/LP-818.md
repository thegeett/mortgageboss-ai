## Reply was blocked by the data model, not by a missing button

§C.5 states it exactly: LP-809 creates a draft **plus a `communication_needs_items` join**, and
LP-811's send endpoint requires a `draft_id`. A reply to *"is page 4 really needed?"* has no needs
behind it — so it could not become a draft, so it could not be sent. Spec 4.3 asks for reply and
nothing existed.

**The needs-less draft needs no column**, and that is worth stating because it looks like it should.
The one-open-draft index is `(loan_file_id, template_key) WHERE status = 'draft'` with no
`NULLS NOT DISTINCT`, so Postgres treats every NULL `template_key` as distinct: several replies
coexist and none collides with the accumulating request. `get_open_draft` reads by that key, so a
reply is invisible to the request path rather than competing with it.

A NULL `template_key` is also **the truth** — `Communication`'s own docstring says the column is
"NULL for anything composed by hand".

That is a claim about Postgres, so `test_two_replies_can_be_open_at_once` asserts it by **writing the
rows**. Reading an index definition is not the same as it behaving that way, and a processor
answering two borrowers gets an `IntegrityError` if it does not.

## One column was carrying two meanings

`external_message_id` means *this message's own id* — it is what LP-805's rung 2 matches a
borrower's `References` against. **LP-815's nudge was writing the id of the message it was
answering into it.**

That routed correctly by accident: a reply's `References` carries the borrower's own id too, so
rung 2 found the nudge row and its loan file. It would break the moment anything stored a genuinely
generated outbound id — rung 2 would then match a thread to a row holding a borrower's id under the
wrong meaning.

`in_reply_to_message_id` is the separated meaning. The nudge is corrected, and the migration moves
existing rows across (and back, on the downgrade, so a rollback leaves rung 2 as it found it).

## Who a reply goes to

**From the stored `inbound_message`**, never from a header read at reply time, and never from the
`Communication` — which has no sender, because LP-805 deliberately declined to copy one: *"copying
them here would put borrower prose in a second place with its own exposure decisions."*

That decision is right and it left the timeline saying "A message arrived" with no From, which
LP-818 could not live with — a processor cannot decide whether to reply without knowing who sent it.
So `services/timeline` reads the sender from the row that already holds it, through the join it
already makes for the manifest. No second copy.

The address is normalised, so a borrower whose client capitalised theirs is answered at the address
the participant list would recognise. A message with no usable `From` is refused: replying to
nowhere is at best wasted and at worst backscatter — LP-815's rule, applied here too.

## Read state is a timestamp, importance is a judgement

`read_at` rather than a boolean, because *"unread"* and *"read four days ago"* are the same boolean
and different facts, and the second is what says a message was seen and left. Outbound rows are
never unread — we wrote them — and marking one read is **refused rather than ignored**, because a
caller doing that is confused about something and a silent success hides it.

Reversible in both directions. A processor who opens something at the end of the day and cannot deal
with it needs to put it back; a one-way flag makes the badge a thing to get rid of rather than a
thing to act on.

`is_important` is a **processor's own judgement**. Nothing computes it, no rule sets it and no model
suggests it — the standing rule is that AI may classify and extract and may not decide, and *"this
matters"* is the most decision-shaped flag on the record.

The badge counts over the **whole file**, not over the page. A count derived from `entries` would
shrink when somebody clicked a filter pill, which is a number that teaches its reader to distrust it.

## Deliberately not done

- **`email_threads` is still a table nothing writes and nothing reads.** LP-805 created it; the
  build plan says LP-805 "writes `email_threads` and `references[]`", and only the second half is
  true — `references[]` is written at ingest and read by rung 2. Threading a reply needs
  `In-Reply-To`, which is per-message, so nothing in this ticket needed the table. It is the fifth
  form of the pattern this loop keeps finding and I did not want to ship a sixth silently.
  **Escalated.**
- **A reply is a draft, not a send.** LP-811a's send endpoint takes it from there, with the same
  rate limit, the same suppression check and the same record of what went out. A reply that skipped
  that would be the one outbound message in the product with no guardrails on it.
- **The rate limit applies to replies.** One per address per five minutes, three per day. A genuine
  back-and-forth on one afternoon hits it. Correct as a guardrail, wrong as a conversation limit;
  **escalated** rather than quietly widened.
- **No "view full thread".** Spec 4.3 lists it. Grouping needs either `email_threads` populated or a
  walk of the `References` chains, and both are more than a button.

## For the reviewer

- **Tenancy** — every route is `ScopedLoanFile`; the service re-checks that the message id in the
  path is on that file, and returns the *same* sentence for "not found" and "another file's", so the
  id is not an oracle. The badge is file-scoped, tested same-company-two-files.
- **Message content in logs** — the new lines carry a loan-file id. Never a body, a subject or a
  recipient.
- **AI in the decision path** — none. `is_important` is explicitly a person's.

Worth a second measurement:

1. **The NULL-`template_key` trick.** It is the whole reason no schema change was needed for the
   needs-less draft, and it depends on the LP-809 index not carrying `NULLS NOT DISTINCT`. Tested by
   writing two rows; check I have not misread what that index would do to a third shape.
2. **The nudge migration.** It moves data in both directions and the downgrade restores rung 2's
   input exactly. Worth running rather than reading — that was your LP-812 finding and it was right.
3. **The reply's `useEffect`-less fetch.** `ReplyBox` calls `fetchReplyContext` during render when it
   has no context yet, rather than in an effect. It is idempotent and fires once per open, but it is
   the kind of thing that behaves differently under Strict Mode and is worth a second look.
