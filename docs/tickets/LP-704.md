# LP-704 — the document preview shows nothing while it loads, and never for an image

- **Ticket:** LP-704
- **Status:** Done (2026-09-06). The reported symptom had two causes, and the bigger one was not in the ticket.
- **Date:** 2026-09-06
- **Reported by:** the user, from the running app
- **Scope:** Backend — `api/documents.py` page endpoint, `services/page_render.py`;
  Frontend — `components/file/documents/reviewer/page-canvas.tsx`, the document drawer

## The report

> Document sometimes takes longer to display, we should display skeleton loading. I noticed
> more on image, but it's worth having loading for all types of document preview.

## What is already there

`PageCanvas` does render a skeleton while the page request is in flight:

```tsx
{isPending ? (<div aria-busy><output className="sr-only">Loading page {page}</output>
  <Skeleton className="mx-auto h-[60vh] w-full max-w-[46rem]" /></div>) : …}
```

So the plain "no loading state" reading does not hold for the reviewer. Two other things
are true and either could be what was seen.

## Confirmed: an image document can never preview at all

Uploads accept three types —

```python
ALLOWED_CONTENT_TYPES = frozenset({"application/pdf", "image/jpeg", "image/png"})
```

— and the page endpoint refuses two of them:

```python
if document.mime_type != "application/pdf":
    raise _NOT_FOUND
```

`services/page_render.py` opens the bytes with `pymupdf.open(stream=…, filetype="pdf")`,
so a JPEG or PNG could not render even if the guard were removed.

The reviewer therefore shows its **no-page state** — *"No page image for this document…"* —
permanently, for a document whose bytes are a perfectly displayable image. That is not a
loading problem; it is a missing capability wearing a loading problem's clothes, and it
would read to a processor as "still loading, forever".

**Blast radius today: latent.** Staging holds 220 documents, all `application/pdf` — zero
images. So nobody is hitting it yet, and the upload path can produce it at any time.

## Likely, not confirmed: scanned PDFs are slow

The slow case is more likely a **scanned** PDF, which is a PDF and does render. Those pages
are full-page images; PyMuPDF rasterises at `DEFAULT_ZOOM = 2.0` and the result ships as a
PNG. 12 of 105 stored PDFs were scans when LP-UI-031 measured, and they are the largest
pages in the corpus.

This wants measuring rather than assuming: render time and payload size for a scanned page
against a text page, at the zoom the reviewer actually requests. The local servers were
stopped before this could be checked.

## Directions

**Render images as images.** They need no PDF engine — the page endpoint can serve the
bytes with their own media type, with `X-Page-Count: 1`. Small change, removes a permanent
dead end.

**Make the wait honest rather than shorter, first.** A skeleton that appears instantly and
stays for four seconds is still a four-second wait; if scans are genuinely slow, say so
("rendering a scanned page") rather than only animating. Measure before optimising.

**Check the other preview surfaces.** The reviewer has a skeleton; the document drawer and
anything else that shows a page should be checked for the same, rather than assumed to have
it — the LP-UI-034 lesson was that a skeleton existing somewhere says nothing about the
surface actually being looked at.

## Acceptance

- [ ] A JPEG or PNG document previews, with its page count reported as 1
- [ ] Render time and payload measured for a scanned page vs. a text page; the ticket records
      the numbers rather than an impression
- [ ] Every surface that previews a document has a loading state, listed and checked
      individually — not inferred from the reviewer having one
- [ ] The no-page state stays reachable and honest for what genuinely cannot render, and is
      never shown for something that is merely slow

## What the measurement changed

The ticket guessed that scanned PDFs were slow at `DEFAULT_ZOOM`. Measured on synthetic
letter-size pages, that guess is nearly wrong:

| page | zoom | median render | PNG |
|---|---|---|---|
| text, US Letter | 2.0 | 30 ms | 0.33 MB |
| scan, US Letter | 2.0 | 45 ms | 0.39 MB |
| text, US Letter | 8.0 | 336 ms | 1.37 MB |

A scan is about 1.5× slower than a text page and the same size. Nobody waits on that.

**The docstring's "a page at 8x is a ~50MB PNG" was wrong by about 35×.** It was reasoned
(pixels × 3 bytes) rather than measured, and PNG compresses a mostly-white page to almost
nothing. It was also wrong about the mechanism it claimed to describe: "the cap is what
stops one query making the server do that".

Then the same measurement against **real stored documents**:

```
doc 45a951ed — 25 MB source, ONE page of 4047 × 4998 points (56 × 69 inches)
  zoom 2.0, the production default →  69.3 MB PNG in 4.91 s
  zoom 1.0                        →  23.4 MB PNG in 1.68 s
doc ec2dc5e5 — 20 MB source, 2832 × 5148 points
  zoom 2.0                        →  57.3 MB PNG in 3.29 s
```

There is the four-second wait, and it is not a rendering cost or a missing spinner. It is a
69 MB image on the wire. `MAX_ZOOM = 4.0` never applied, because 2.0 is already under it —
**it caps a multiplier, and the page it multiplies is unbounded.** Four of 101 stored
documents are over 5 MB and three are over 10 MB, so this is rare and enormous rather than
common and mild.

## What was built

**A budget on the result.** `MAX_RENDERED_EDGE = 3000` px on the longest side, applied by
`fit_to_budget`, which reduces the zoom until the render fits. The number is not round: the
reviewer shows a page in a column of at most 46rem (736 px) at a CSS zoom of at most 2.0
(`zoom.ts`), so 1472 CSS px, or 2944 device px on a 2× screen. Pixels past that are
shipped, decoded and never seen.

It can reduce **below 1.0**, and it has to — `render_page` floors a caller's zoom at 1.0,
and a 4998 pt page at 1× is still 23 MB. A floor applied after the budget would put it out
of reach of the only pages that need it.

`X-Page-Zoom` now reports the zoom that was **applied**, not the one requested. The client
scales highlight boxes by that number, so reporting the request would put every box off by
the reduction.

**Images render.** `RENDERABLE_TYPES` maps the three types uploads already accept, and the
endpoint gates on that map rather than on `!= "application/pdf"`. MuPDF opens an image as a
one-page document, so page count, geometry and zoom all keep their meanings and nothing
downstream needs a second path.

### Two things measurement contradicted mid-build

**An image's page rect is not its pixel size.** MuPDF reads an image at 96 DPI and reports
72-dpi points, so a 400 × 300 px image is a 300 × 225 pt page — pixels × 0.75. A normalised
box uses the ratio and is unaffected; anyone reading `width_points` as "pixels" would be off
by a third on every image. Written down in a test rather than left to be rediscovered.

**The `filetype` hint selects nothing.** MuPDF sniffs the bytes: PDF bytes open under
`filetype="png"` and even `"xps"`, all returning the real page. So `RENDERABLE_TYPES` is an
allow-list of what this endpoint will serve, **not** a parser selector. That is the safe
direction — upload validation already derives the stored mime type from the content — but a
future reader could otherwise build a check on the hint that enforces nothing.

## Result, on the same real documents

| document | before | after |
|---|---|---|
| 25 MB survey, 4047 × 4998 pt | 69.3 MB, 4.91 s | **9.7 MB, 0.91 s** |
| 20 MB, 2832 × 5148 pt | 57.3 MB, 3.29 s | **7.3 MB, 0.59 s** |

US Letter pages are untouched: still `zoom=2.0`, 612 × 792 points, byte-for-byte as before.

## The loading-state item, answered by counting

There is exactly **one** surface that previews a page: `PageCanvas`, used by the reviewer.
The document drawer shows extraction data and never renders a page. `PageCanvas` already
had a `Skeleton` on `isPending` and a distinct broken-image state, so the plain reading of
the report — "we should display skeleton loading" — had nothing to add. Listing the surfaces
was the useful part; the count is one, not "several".

## Left open, recorded rather than fixed

**An image uploads and previews but does not classify.** Both test uploads landed at
`needs_review` with `processing_error` null. Out of scope here — the ticket is about
preview — but a document type the pipeline cannot classify is worth its own ticket.

**Every page request re-reads the whole document from storage.** Paging through a 40-page
25 MB scan reads 25 MB forty times. Locally that is a disk read; on S3 it is the dominant
cost. A cache has tenancy and memory questions this ticket should not answer.

      the API and in the running app, light and dark
- [x] Render time and payload measured for a scanned page vs a text page, and for real

- [x] Every surface that previews a document has a loading state — enumerated, and there is

- [x] The no-page state stays reachable for what genuinely cannot render, and is no longer
