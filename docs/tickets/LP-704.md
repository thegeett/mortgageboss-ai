# LP-704 — the document preview shows nothing while it loads, and never for an image

- **Ticket:** LP-704
- **Status:** Open — one cause confirmed, one needs reproduction
- **Date:** 2026-09-06
- **Reported by:** the user, from the running app
- **Scope:** Backend — `api/documents.py` page endpoint, `services/page_render.py`;
  Frontend — `components/file/documents/reviewer/page-canvas.tsx`, the document drawer

## The report

> Document sometimes takes longer to display, we should display skeleton loading. I noticed
> more on image, but it's worth having loading for all types of document preview.

## What is already there

`PageCanvas` does render a skeleton while the page request is in flight:

```tsx
{isPending ? (<div aria-busy><output className="sr-only">Loading page {page}</output>
  <Skeleton className="mx-auto h-[60vh] w-full max-w-[46rem]" /></div>) : …}
```

So the plain "no loading state" reading does not hold for the reviewer. Two other things
are true and either could be what was seen.

## Confirmed: an image document can never preview at all

Uploads accept three types —

```python
ALLOWED_CONTENT_TYPES = frozenset({"application/pdf", "image/jpeg", "image/png"})
```

— and the page endpoint refuses two of them:

```python
if document.mime_type != "application/pdf":
    raise _NOT_FOUND
```

`services/page_render.py` opens the bytes with `pymupdf.open(stream=…, filetype="pdf")`,
so a JPEG or PNG could not render even if the guard were removed.

The reviewer therefore shows its **no-page state** — *"No page image for this document…"* —
permanently, for a document whose bytes are a perfectly displayable image. That is not a
loading problem; it is a missing capability wearing a loading problem's clothes, and it
would read to a processor as "still loading, forever".

**Blast radius today: latent.** Staging holds 220 documents, all `application/pdf` — zero
images. So nobody is hitting it yet, and the upload path can produce it at any time.

## Likely, not confirmed: scanned PDFs are slow

The slow case is more likely a **scanned** PDF, which is a PDF and does render. Those pages
are full-page images; PyMuPDF rasterises at `DEFAULT_ZOOM = 2.0` and the result ships as a
PNG. 12 of 105 stored PDFs were scans when LP-UI-031 measured, and they are the largest
pages in the corpus.

This wants measuring rather than assuming: render time and payload size for a scanned page
against a text page, at the zoom the reviewer actually requests. The local servers were
stopped before this could be checked.

## Directions

**Render images as images.** They need no PDF engine — the page endpoint can serve the
bytes with their own media type, with `X-Page-Count: 1`. Small change, removes a permanent
dead end.

**Make the wait honest rather than shorter, first.** A skeleton that appears instantly and
stays for four seconds is still a four-second wait; if scans are genuinely slow, say so
("rendering a scanned page") rather than only animating. Measure before optimising.

**Check the other preview surfaces.** The reviewer has a skeleton; the document drawer and
anything else that shows a page should be checked for the same, rather than assumed to have
it — the LP-UI-034 lesson was that a skeleton existing somewhere says nothing about the
surface actually being looked at.

## Acceptance

- [ ] A JPEG or PNG document previews, with its page count reported as 1
- [ ] Render time and payload measured for a scanned page vs. a text page; the ticket records
      the numbers rather than an impression
- [ ] Every surface that previews a document has a loading state, listed and checked
      individually — not inferred from the reviewer having one
- [ ] The no-page state stays reachable and honest for what genuinely cannot render, and is
      never shown for something that is merely slow
