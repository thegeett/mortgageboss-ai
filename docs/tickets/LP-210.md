# LP-210 — End-to-end Stage-1 test + real-file validation

## Summary

The Stage-1 capstone: one end-to-end test exercising the **complete** pipeline
(build → persist → load → validate), asserting the cross-ticket invariants that only
surface when the whole thing runs together, plus the real **LF-6T3N snapshot as a
reviewable masked-JSON artifact** and the Stage-1 wrap-up. Test + validation + docs
only — **no new production code**.

**No ADR-level decisions** — this is a validation ticket; it adds no architecture.
(The one issue the earlier real-file run surfaced — unmasked business tax ids — was
fixed in its home ticket, LP-206, ADR-243, not here.)

## Phase 0 findings (incl. the flagged gap)

- **Chain present & callable:** `build_snapshot` (LP-208), `persist_snapshot` /
  `load_snapshot` (LP-209), the three assemblers (LP-205/206/207), the LP-204 model,
  LP-203 primitives — all wired. Verified working on real LF-6T3N during the dev-DB
  reconciliation.
- **Cross-section hash source (real):** the account path is **not** provable on
  LF-6T3N (MISMO has no account-number column on this branch; extracted accounts are
  pre-masked → `match_hash=None`). But a **borrower SSN** appears raw in *both* the
  MISMO borrower section and a W-2 (`employee_ssn`), both via `from_raw` — so they
  hash identically. That is the real cross-source proof (confirmed: SSN ending `0373`
  in both).
- **⚠️ FLAGGED GAP — the LP-202 matcher is not pipeline-wired.** LF-6T3N had **0**
  stored `document_borrower_links`, so on the raw file `belongs_to` is `None`
  everywhere. This is a real gap owned by a future "wire the matcher into document
  processing" ticket — **not** papered over here. The e2e test seeds links
  deterministically; the artifact script runs the existing LP-202 matcher service
  explicitly (not new pipeline logic) so the real snapshot shows resolution.
- **Test layout:** DB-backed snapshot tests live in `tests/verification/snapshot/`
  (via the `db_session` fixture, `create_all` test DB). The e2e fits there.

## What was built

- `tests/verification/snapshot/test_e2e.py` — the deterministic e2e (seeds a
  complete LF-6T3N-shaped file: 2 borrowers, documents with links, assets, property;
  Akash's SSN is deliberately the same on his borrower record and his W-2 to prove
  the cross-section hash). Runs the full chain + all cross-ticket assertions.
- `app/scripts/stage1_artifact.py` — runs the LP-202 matcher (existing service),
  builds the real LF-6T3N snapshot, verifies no raw PII, writes the masked pretty
  JSON. Uses a fixed run_id so re-runs are stable.
- `docs/tickets/LP-210-LF-6T3N-snapshot.json` — the deliverable (74 KB; 122 MISMO
  facts, 30 documents (18 resolved to a borrower), all four calculators; PII masked;
  no raw value).
- `docs/tickets/STAGE-1-SUMMARY.md` — the Stage-1 wrap-up.

## Real-file validation result (LF-6T3N)

Full chain runs; artifact written. In it: a W-2 `employee_ssn` `match_hash` **equals**
`borrower.2.ssn`'s (display `***-**-0373`) — cross-source matching demonstrated on real
data; a whole-artifact scan finds **no raw SSN/account** (only masked display + hex
hashes); DTI/LTV/MI/reserves all computed. 18 of 30 documents resolved to a borrower
after running the matcher (the other 12 either name no borrower — appraisal, tax bill —
or didn't clear the threshold).

## Assumptions & decisions

- **Two deliverables, deliberately split:** a *deterministic seeded* e2e (CI-safe,
  asserts belongsTo + cross-section hash because the data is controlled) and a
  *real-file artifact* from LF-6T3N (for human faithfulness review). LF-6T3N lives in
  the dev DB, not the test DB, so the pytest test can't reach it directly.
- **The artifact runs the matcher explicitly** — calling the existing LP-202 service,
  not adding pipeline logic — because that step isn't auto-wired yet (flagged gap).
- **No bug found that belongs here.** The tax-id masking issue the smokes surfaced was
  fixed in LP-206 before this ticket.
