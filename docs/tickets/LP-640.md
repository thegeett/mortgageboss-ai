# LP-640 — an unidentified document costs 22 queue items; consolidate to one

- **Ticket:** LP-640
- **Status:** SPECIFIED. Nothing built.
- **Date:** 2026-09-01
- **Scope:** Backend — finding aggregation over `verification/rule_engine/` `couldnt_check` results;
  no rule spec, no threshold, no verdict semantics change.
- **Family:** [LP-636](LP-636.md), [LP-637](LP-637.md), [LP-638](LP-638.md), [LP-639](LP-639.md) —
  all found on the same file, all attacking the same symptom from the other side.

## Where this sits in the LP-636…639 chain

Four tickets already attack the **cause** — why a document is unidentified:

| ticket | fix | effect on N |
|---|---|---|
| LP-636 | classification defects (incl. a confident `unknown` discarding a better answer) | fewer land `unknown` |
| LP-637 | a document could never be re-classified → reprocess | 10 → 3 on LF-ZE9N |
| LP-638 | a misclassified document could not be corrected → type picker | processor can fix by hand |
| LP-639 | a confident `unknown` could not be explained → failure reason | tells you which to fix |
| **LP-640** | **22 rules × N documents floods the queue** | **any N costs 1 item, not 22N** |

**This is the only one addressing the cost of a document that is still unidentified**, and the
fan-out was named first by LP-637 itself: *"one problem is reported 220 times"*, *"sixteen unrelated
rules each reporting exactly ten."*

Every fix above shrinks N. **None of them bounds the cost per document**, and none can:

- LP-639's own subject, `CD - 7112 -1.pdf`, is a Closing Disclosure that classified `unknown` at
  **0.85 confidence** with a good Tier 1 indicator in the catalog. Some documents defeat the
  classifier.
- LP-637's commit line concedes it outright — *"stop retrying one that never can."*

So N never reaches zero, and while it is non-zero the queue carries 22N rows for what a processor
experiences as one task.

**It also makes LP-638's remedy discoverable.** A processor facing 66 rows has no signal telling them
to open the type picker; one row saying *"3 documents could not be identified — set their type"*
points straight at the control LP-638 just built. Consolidation is what connects the cause-side fixes
to the person who has to use them.

## The report

On **LF-ZE9N** (staging, conventional investment purchase, $200,000 sales price / $150,000 loan)
a processor's queue holds **148 non-satisfied findings**. Of those, **66 — 45% — are three
unclassified documents.**

Each unclassified document raises **22 findings from 22 different rules**:

| subject | findings | distinct rules |
|---|---|---|
| unclassified doc `docb60ccc7adcda9ceb` | 22 | 22 |
| unclassified doc `doc1ad75b575e70d0ac` | 22 | 22 |
| unclassified doc `docf643a47d20d8296f` | 22 | 22 |
| loan-level | 16 | 16 |
| borrower-level | 11 | 11 |
| ~35 other subjects (transactions, typed docs) | 1–3 each | — |

The document table agrees on the count — exactly three documents are unidentified:

| document_type | status | n |
|---|---|---|
| `unknown` | completed | 2 |
| `(null)` | needs_review | 1 |

Every one of the 22 rules is asking the same question of the same PDF — *"is this the document I
need?"* — and each answer becomes its own queue row. What the processor actually has is **one
task: identify three files.**

Two of the three are named `CD - 7112 -1.pdf` and `Purchase 1312 Killashee Ct executed
contract.pdf`. The first is LP-639's subject — a Closing Disclosure that classified `unknown` at 0.85
despite a Tier 1 catalog indicator. The second names its own type in its filename. Both are worth
stating plainly because they set the division of labour: **the misclassification belongs to
LP-636/637/638/639; the volume belongs here.**

## The mechanism is correct — the aggregation is missing

Say this precisely, because the obvious fix is the wrong one.

A rule scoped to a document type resolves an `unknown` type predicate to `couldnt_check`, never to
`not_applicable` (LP-329 / LP-330). **That is right and must not change.** Dropping a rule on a
guess about an unclassified document is the dangerous direction: it is how a missing VOE becomes a
green check.

Nothing in the pipeline collapses 22 identical "I am waiting on this file" signals into one. That
is the entire defect. No rule is too conservative; no threshold is wrong.

Measured on the same file, only **3 of 148** items come from a rule judging too harshly (OC-2,
IN-7, DT-7 each fire `needs_review` while their own message says every signal agrees — tracked
separately, not in this ticket). Loosening thresholds would cost real conditions and reclaim
almost nothing.

## The constraint: do not trade noise for silence

`pending_checks.py` (LP-391) already records the failure mode the naive fix walks into:

> Today a BLOCKED rule runs NOTHING, so a file that qualifies for it produces **SILENCE, which
> reads as "checked, nothing found" when it is really "didn't look"**.

Suppressing the 22 findings outright recreates exactly that. IN-8 would show nothing on a file
whose VOE may be sitting in an unidentified PDF, and nothing reads as clean. On a file submitted to
underwriting that is a materially worse outcome than 22 noisy rows.

**So: consolidate the queue item, never the verdict.**

| layer | today | after |
|---|---|---|
| Processor's queue | 66 items | **1** |
| Rule verdicts | 66 × `couldnt_check` | unchanged — 66 × `couldnt_check` |
| Can a blocked rule read `satisfied`? | no | **no** |

## Proposed shape

**One loan-level finding for all unclassified documents on the file** — not one per document.

> **3 documents in this file could not be identified.**
> `CD - 7112 -1.pdf`, `Purchase 1312 Killashee Ct executed contract.pdf`, +1
> Identify each one. 22 checks are blocked waiting on them — they may include the VOE, the
> purchase agreement, and the retirement account statement.

The trailing clause costs nothing to produce and is strictly better information than today: the
blocked rules already carry the document types they were waiting for, so the consolidated finding
can **name them once** instead of asking 22 times.

### Behaviours to get right now

- **Partial progress.** Classify 2 of 3 and the finding stays open, re-rendered as "1 document
  could not be identified." It clears only when the last one resolves.
- **Zero unclassified.** No finding at all — not a satisfied "all documents identified" row.
  There is nothing to action.
- **Subject key** is the loan, not a document — there is one finding regardless of count.
- **The underlying 66 `couldnt_check` evaluations still happen and are still stored.** This
  changes what a processor is shown, not what the engine concluded.

## Expected effect

| change | items removed |
|---|---|
| Consolidate unclassified-document fan-out (66 → 1) | **−65** |
| **LF-ZE9N queue: 148 → 83** | **−44%** |

No coverage is lost, no threshold moves, no rule spec changes.

LP-636…639 shrink N further; a correctly classified document raises no consolidated finding at all.
But they cannot reach zero — a document that never classifies keeps its fan-out forever — which is
why this fix is worth having on its own and does not become obsolete when they land.

  [LP-636](LP-636.md), [LP-637](LP-637.md), [LP-638](LP-638.md), [LP-639](LP-639.md). This ticket
  assumes some documents remain unidentified no matter what, and bounds their cost.
- **AS-6 duplication** — fires 4× for the same non-borrower co-holder across 4 bank statements

## Verification

```sql
select evaluation_outcome, count(*)
from readonly.findings
where loan_file_id = (select id from readonly.loan_files where display_id='LF-ZE9N')
  and deleted_at is null
group by 1;
```

Expect `couldnt_check` unchanged at the evaluation layer, and the processor-facing count for
unclassified documents to be exactly 1. A regression test should assert that a file with N
unclassified documents (N ≥ 1) produces exactly one consolidated finding, and that each blocked
rule still records `couldnt_check` rather than `satisfied` or `not_applicable`.
