# LP-311 — Rule + tag storage: files → DB projection

**Status:** Complete. **Branch:** `phase3_new_AI_arch_finding_stage2`.
**ADR:** [ADR-250](../../decisions.md). **Depends on:** LP-301 (`rule_kinds.csv`),
LP-303 (`load_rule_spec`/`AS-1.yaml`), LP-310 (recon that found the orphan table).

## What it is

The fact-tag architecture (§3D) needs rules and the tag vocabulary to be
**queryable**. LP-311 builds four global DB tables — `rules`, `tags`, `rule_tags`,
`tag_dependencies` — as a **projection** of the version-controlled source files,
plus the loader that keeps them in sync, load-time consistency checks, and runtime
read accessors. **Storage only:** no tag production (Stage A/B), no rule evaluation.

The clean §3D separation: **SCHEMA/POLICY** (tag vocabulary + rule specs) lives in
git as files — human-governed, audit-trailed, Priya-signed; **DATA/RESULTS** (tag
values in snapshots, findings) lives in the DB. These tables are a queryable
read-copy of the policy files, **never a second source of it** — the DB is
regenerated from the files and is never hand-edited.

## The phase3_5_1 conflict: REPLACE (decided before building)

`verification_rules` (LP-118 / ADR-238, branch `phase3_5_1`) was storage for the
**abandoned** pre-pivot code-evaluator engine. Per the LP-310 decision, LP-311
**replaces** it: build the tag tables fresh, salvage any useful seed metadata into
the files first, drop the orphaned tables, and resolve the AS-1 validation
contradiction in favour of this branch's files. `phase3_5_1` is abandoned and will
not be merged, so there is **no Alembic fork** on this branch (`alembic heads` is
the single head `c4e9a7f2b8d3`); the new migration simply stacks on it.

## Assumptions & decisions

- **Files → committed CSVs → DB (the LP-301 precedent).** The xlsx is human authoring;
  the committed CSVs are the machine source of truth the loader reads. Exactly how
  `rule_kinds.csv` relates to its upstream classification xlsx. Avoids an `openpyxl`
  runtime dependency and fragile xlsx parsing at load time.
- **Projection is not a hand-edit path.** The loader reconciles the DB back to the
  files (insert/update/**remove**) every run; a hand-mutated row is overwritten. The
  DB carries no truth the files do not (docstrings + ADR-250 state this).
- **Global / un-scoped tenancy.** Rules and the vocabulary are identical for every
  company → no `company_id`. Per-tenant overrides are a future ticket (out of scope).
- **AS-1 / IN-1 validation resolved to the files.** LP-118's seed marked AS-1
  (`large_deposit_pct=50`) and IN-1 (`variance_pct=5`) `validated=TRUE` — the only 2
  validated rows in its 140. **Files win:** both stay `priya_validated=false` /
  `threshold_needs_signoff=true`. The seed's `TRUE` is not adopted anywhere. **Both
  are flagged for Priya review** (see below). General policy: the files' validation
  state is authoritative; a seed's `TRUE` is never auto-adopted.
- **Orphan drop + no fork.** The migration `DROP TABLE IF EXISTS` the two orphans
  (CASCADE, audits first) so a dirty dev DB converges with a fresh one; no-op on a
  fresh DB; `downgrade` does not resurrect them. No merge migration needed — the
  LP-118 revision is absent on this branch.
- **`none_as_null=True` on nullable JSONB** (`rules.spec`, `tags.allowed_values`) so a
  rule without a spec / a non-enum tag is SQL `NULL`, not a JSONB `'null'` (else
  `spec IS NULL` is meaningless). Bug caught + fixed during the build.
- **`load_rule_spec` stays file-backed**, signature preserved as the swap seam; the
  full spec is mirrored into `rules.spec` and exposed via `get_rule`, so a DB-backed
  spec source is a later drop-in without breaking callers.
- **Range pseudo-rows expanded.** The Rule→Tags sheet's `CO-1..5` / `PE-1..5` rows are
  expanded to `CO-1…CO-5` / `PE-1…PE-5` (all valid `rule_kinds.csv` ids).
- **Loader flushes; caller commits** — composes with the transaction-rollback test
  fixture (tests never commit) and the CLI commits once.

## Deferred / out of scope

- **The tag DAG is empty.** The vocabulary xlsx has no `depends_on` column yet
  (LP-311 Phase 0), so `tag_dependencies.csv` is header-only and the table projects 0
  rows. The table + the loader's cycle check exist so the DAG is a drop-in once
  authored. Same for `tag_role` (null) and per-tag `tag_version` (defaults to 1) —
  not yet columns in the file.
- **Partial coverage (faithful).** Only **107 of 133** rules have a tag mapping in the
  Rule→Tags sheet; only **AS-1** has a spec file. The `rules` table holds all 133
  (from `rule_kinds.csv`); `rule_tags`/`spec` are populated where the files provide
  them. The vocabulary's "Used by rules" reverse-index disagrees with the forward
  Rule→Tags sheet for a few rules — the **forward sheet is authoritative**; the
  discrepancy is flagged for a future vocabulary-authoring pass.
- Tag PRODUCTION (Stage A/B), rule EVALUATION, the stable content-id snapshot change
  (LP-312), per-tenant overrides, any hand-edit path to the DB, and a UI.
- **`verification_rules` is NOT resurrected** — neither the table nor its
  evaluator-shaped columns.
