# LP-374 — Wire the homeowners insurance producer (the DTI's last vocabulary orphan)

## WHAT THIS TICKET IS

`housing.insurance_monthly` was the **last known vocabulary orphan** — declared in `fact_tags.csv` with a
producer (`produced_by=AI`) but with **no declaration in `tag_production.yaml` and nothing in `app/` writing
it**. LP-373's guard exempted it (`_KNOWN_LIVE_ORPHANS`) pending this fix. The extractor already exists
(`app/ai/extraction/homeowners_insurance.py` emits `annual_premium`); nothing wired `annual_premium ÷ 12 → the
tag`. This ticket wires it as a derived recipe and closes the orphan.

**⚠️ A Phase-0 finding overturns the ticket's stated premise — reported in full below.** The ticket says "the
DTI calculator can never compute on ANY file because the tag never materializes." **That is false: the DTI
reads the extraction directly, not the tag.** The wiring is still correct and valuable — it closes the orphan
and serves the tag's own consumers — but it does **not** unblock the DTI (the DTI was never blocked by this
tag).

## ACCEPTANCE CRITERIA

- D1-D5 argued from the code, especially **how the DTI actually reads insurance**.
- The declaration + a derived recipe; fail-closed to `unknown` with a reason, **never 0**.
- A with-binder fixture proving the tag materializes as `annual ÷ 12`; the no-binder outcome on LF-6T3N.
- The real run on LF-6T3N reported (not predicted).
- LP-373's guard passes with the exemption removed; equivalence; ruff + mypy + full suite green.

## D1 — THE SUBJECT, AND THE DTI'S ACTUAL READ PATH (the finding that overturns the premise)

**How does the DTI read insurance?** Not from the tag. `app/services/dti.py:149`:
```python
insurance = await _extracted_monthly(db, loan_file.id, "homeowners_insurance", "annual_premium", annual=True)
```
`_extracted_monthly` reads the **homeowners_insurance document's extracted `annual_premium` field ÷ 12**,
directly from the DB extraction. The snapshot's DTI section (`calculations_section.py map_dti`) wraps that
value into a breakdown line and labels it with `from_tag="housing.insurance_monthly"` — a **lineage tag id, not
a tag read**. `_gate_reason` groups lines by `from_tag` and fires when the insurance **line** is `None` (no
extraction). **So the `_REQUIRED_DTI_TAGS` gate is driven by the extraction; the `housing.insurance_monthly`
tag layer is never consulted by the DTI.**

**Consequences:**
- **The DTI already computes today on any file with a binder** — the tag being an orphan never blocked it. The
  ticket's "structural break: the DTI can never compute" is **incorrect**.
- `housing.insurance_monthly` (vocab `subject=loan`) is consumed only by **inert** rules (DT-1/DT-5/IH-1, per
  `rule_tags.csv`). So it is really an **inert orphan**; LP-373's "live-orphan(dti-calc)" label rested on
  treating `_REQUIRED_DTI_TAGS` membership as a tag read — but that is lineage. (LP-373's guard still correctly
  *required it to be produced*; this ticket produces it.)

**The subject decision:** `subject: loan, mode: derived`. This matches the vocabulary and the (inert)
consumers, and mirrors LP-371's `occupancy_stated` and LP-366-A's `dti.qualifying_income_monthly`. A
`document`-subject tag would be a lateral move (the loan-level consumers can't read it). **Recipe feasibility
confirmed:** a derived recipe reads the whole **snapshot**, and `annual_premium` is present in the snapshot's
`homeowners_insurance` document fields (`build_document_fields` copies extraction fields into
`DocumentEntry.fields`) — so it is NOT limited to MISMO the way LP-371's loan-subject *AI context* was.

**What wiring accomplishes (honestly):** closes the orphan (LP-373's guard passes without the exemption); makes
the tag materialize on a binder file; **aligns** the tag with the same `annual_premium ÷ 12` the DTI computes;
readies DT-1/DT-5/IH-1. It does **not** feed or unblock the DTI.

## D2 — MULTIPLE BINDERS (fail-closed)

The recipe gathers the **distinct** `annual_premium` across all `homeowners_insurance` documents:
- one distinct value → `÷ 12`;
- conflicting values → `unknown`, the reason **naming the conflicting premiums** ("cannot tell which is
  current" — the LP-332/LP-336 fail-closed-on-ambiguity discipline);
- identical duplicates (a declarations page + a renewal at the same premium) → the one value (not a conflict).

**Reported divergence:** the DTI's `_extracted_monthly` takes the single *current* binder without a conflict
check, so on two conflicting binders the DTI would use one while the tag abstains. The **tag is stricter**;
this is deliberate (the tag is a governed fact) and reported, not "fixed" (the DTI is out of scope).

## D3 — HAZARD vs FLOOD vs MI (no conflation)

The classifier distinguishes them cleanly (`classification_prompt.py`): `homeowners_insurance` = "a homeowner's
**hazard** insurance policy… the I in PITI"; `flood_insurance_policy` = "separate from hazard insurance";
`life_insurance_statement` = an asset; MI has its own calculator. **The recipe reads ONLY
`homeowners_insurance`.** No new gap here.

## D4 — THE ANNUAL→MONTHLY DIVISION

`Decimal(annual) / Decimal(12)`, **full precision** (matches `_extracted_monthly`; 1300/12 → 108.333…, never
rounded to 0). A present binder with **no** `annual_premium`, an **unparseable** premium, or a **non-positive**
premium (a $0 binder would make the DTI confidently too-low) → `unknown` with a reason. **Never 0.**

## D5 — AS-4 (reported, not chased)

AS-4 is **inert**. It reads the reserves calc → PITI → insurance, which (like the DTI) comes from the
**extraction**, not this tag. So wiring the tag does **not** change AS-4's behavior on any file. Not activated,
not tuned.

## WHAT WAS BUILT

- `derived.py`: the `housing_insurance_monthly` recipe (registry entry only — `produce_derived_tags`
  unchanged). Gathers distinct `annual_premium` from `homeowners_insurance` docs, `÷ 12`, fail-closed to

- `test_vocabulary_orphans.py` (LP-373's guard): removed `housing.insurance_monthly` from
  `_KNOWN_LIVE_ORPHANS` (now produced) and updated `test_guard_catches_the_dti_calc_orphans_when_not_exempted`
  to `{housing.taxes_monthly}` — **the guard closing on the instance it exempted.**

**No engine change** — a declaration + a recipe-registry entry (the sanctioned LP-326 extension point).

## TESTS

`test_insurance_wiring.py` (10):
- **the structural fix** — a binder → the tag materializes `annual ÷ 12` (1200 → "100"); full precision kept;
  the declaration is derived/loan; end-to-end `materialize_tags` keys it under the loan subject.
- **fail-closed / never 0** — no binder, present-but-no-premium, non-positive premium, conflicting binders all

## THE REAL RUN ON LF-6T3N (reported, not predicted)

Run `01039e93` (the LP-365 real snapshot). LF-6T3N document types: bank_statement ×5, brokerage_statement,
drivers_license ×2, investment_account ×3, mortgage_statement ×4, pay_stub ×4, property_tax_bill ×2,
purchase_agreement, w2 ×4, unknown ×4 — **no `homeowners_insurance` document.**
- `housing.insurance_monthly` = **`unknown`**, reason: *"no homeowners insurance binder in the file — insurance
  is unknown, not 0."*
- The DTI section: **`gated=True`**, reason: *"calculation gated (fail-closed): housing.insurance_monthly is
  unknown."*

**This is the correct, honest outcome, and it is UNCHANGED by this ticket** — the DTI gate is driven by the
extraction (no binder → the insurance line is `None`), and the tag id in the gate reason is the lineage label,
not a tag read. LF-6T3N has no binder, so the DTI stays gated; AS-4 still couldnt_checks there. **The
structural artifact this ticket removes is the ORPHAN (nothing produced the tag), not the LF-6T3N gate.**

## THE UI's $0.00 BUG — reported precisely for LP-375 (NOT fixed here)

The DTI *display* path (`DtiCalculation` via `services/dti.py`) collapses the unknown insurance input
(`auto_amount=None`) to a rendered **$0.00 "Extracted"**, and the UI DTI card shows a confident back-end DTI
computed on it — while the *snapshot* calc path (`calculations_section.py`) correctly gates on the same
`auto_amount=None`. The two paths contradict each other on the same page: the rule/snapshot path is honest
(gated), the display path fabricates a zero. **This ticket does not touch the display — it is LP-375's.** (Note
this is a display collapse, independent of the tag wiring; wiring the tag does not change it.)

## ASSUMPTIONS / DECISIONS

- **The DTI reads the extraction, not the tag** (D1) — the central finding; the code is the gate of record and
  it beats the ticket text. The wiring closes the orphan and aligns the tag; it does not unblock the DTI.
- **`housing.insurance_monthly` is really an inert orphan** (consumed by DT-1/DT-5/IH-1, all inert) — LP-373's
  guard still correctly required it produced, and this ticket produces it.
- **The tag is stricter than the DTI on multiple binders** (D2) — deliberate, reported.
- **Never 0** — a non-positive/absent premium abstains; a 0 would make the DTI confidently too-low.
