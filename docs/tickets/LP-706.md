# LP-706 — match the model's snippet against the text we already have, properly

- **Ticket:** LP-706 (LP-700 series, 1 of 4)
- **Status:** Done (2026-09-06). Built and measured — and the measurement contradicted the ticket's own premise. See *What measuring showed*.
- **Scope:** Backend — `services/field_boxes.py`
- **Prompts changed:** none. **Extra AI calls:** none. **New dependencies:** none.

## The idea in one line

We already know where every word on a text page is. Stop requiring the model to retype
those words *exactly* before we will look for them.

## How it works today

`field_boxes.py` calls `page.search_for(snippet)` — a literal, exact search. If the model
wrote `Gross Total 15,000.00` and the page's text layer holds `Gross  Total  15,000.00`
(two spaces), or the figure sits in a table cell split across two text spans, or the page
uses a ligature, the search returns nothing and the field gets no box.

## What changes

Match against `page.get_text("words")` — the word list with a rectangle per word — instead
of searching for a literal string. Normalise both sides before comparing (collapse
whitespace, fold ligatures, strip currency symbols and thousands separators), then take the
**union rectangle of the matched words** as the box.

Fall back down a chain rather than giving up, which is what production grounding systems do:
the verbatim snippet → the normalised snippet → the extracted **value** itself. Always try
to ground rather than return nothing.

When the same text appears more than once on the page, prefer the occurrence on the cited
page and nearest the cited position, and where it is still ambiguous, return **no box**
rather than a guess — see LP-709.

## What measuring showed — the premise was wrong

Re-measured across the stored corpus, **excluding four seeded placeholders whose entire text
layer is `DEMO <filename>`** (their extractions are fabricated and never came from the file,
so every field on them is unfindable by construction) and ten documents with no usable text:

```
76 real documents, 608 valued fields with a snippet and a page

  515  (84.7%)   found by the EXACT tier — the behaviour that already existed
  525  (86.3%)   found after this ticket
  +10  (+1.6pt)  gained, ALL of them from the value tier
    0            gained by folding the snippet
```

**Folding contributed nothing, because `search_for` was already better than this ticket
assumed.** It tolerates doubled spaces, tolerates case, and spans separate text runs — so
whitespace, which the ticket named as the first cause, was never a cause at all. The
original "11.8% whose snippet is absent from the text layer" figure was also computed over a
corpus including scans and seeded placeholders; on real text documents the exact tier was
already finding 84.7%.

### What folding does fix, and why it is kept anyway

`search_for` genuinely cannot match a figure written in another notation — `15000.00`
against a page's `15,000.00`, or `$15,000.00`, or `15 000,00` — nor an accented word spelled
without its accent. Those are real failure modes; each is asserted in the tests with a
control proving the exact tier fails first. They simply do not occur in this corpus.

So the folded tier ships, labelled honestly rather than claimed as a win: it costs a page
index only after the exact tier has already failed, and it closes demonstrated failure modes
that fired zero times against real data. A reviewer is entitled to argue it out on that
basis.

### What is actually left, and why some of it can never be fixed

Of the 83 real fields still without a box: **54 number-ish, 25 text, 4 ISO dates.** So date
normalisation — the gap folding does *not* close — is not the prize either.

The commonest unplaced keys are `ytd_gross`, `hours`, `pay_frequency` and
`total_deductions_current`, and their snippets read like:

> "Total Taxes $3,663.31 + Total Pre-Tax $1,410.00 + Total Post-Tax $335.00"
> "Pay period 12/01/2025 to 12/31/2025 spans full month"

**Those are values the model DERIVED, not text it read.** No matching strategy can locate a
number that was never printed on the page. A meaningful share of the remaining gap is not a
matching problem at all, and the LP-700 series' framing — "one field in four cannot be
pointed at" — quietly counted them as failures.

## How a box is computed — the shared design for LP-706/708/709

Written here rather than split across three tickets, because whoever builds any one of them
needs the whole shape. **Only step 2 differs between document kinds. Everything before and
after is identical.**

### When it runs

Boxes are **not** stored, and are not computed at upload or during extraction. They are
worked out fresh when the reviewer opens a page — `find_all_field_boxes` opens the document
once and answers for every field on it.

That is why LP-706 and LP-709 reach every document already in the system on the day they
ship: there is nothing persisted to migrate and nothing to re-extract.

### The flow

```
1.  The reviewer opens page N of a document
2.  Get the word list for page N          <-- THE ONLY STEP THAT BRANCHES
        [(word, x0, y0, x1, y1), ...]
3.  Per field: fuzzy-match the value / snippet / anchors against that list
4.  Union rectangle of the words that matched
5.  VERIFY the matched words contain the value   (LP-709)
        no  -> no box, and the reviewer says why
6.  Normalise the rectangle to 0..1 of the page box   (`_normalise`, unchanged)
7.  The client places it as a percentage over the page image
```

Step 6 is what makes a box zoom-independent: stored as "38% across, 51% down", it lands
correctly whether the page is displayed at 50% or 200%, and it is why nothing downstream has
to know which zoom the page was rendered at.

### Step 2, branch A — a text-based PDF (78 of 101 stored)

```python
words = page.get_text("words")   # [(x0, y0, x1, y1, word, block, line, word_no), ...]
```

The file itself carries every word and its rectangle. Instant, free, and **exact** — these
are the positions the document was typeset with, not an estimate. Coordinates arrive in PDF
points, the same space `page.rect` reports, so `_normalise` needs no conversion.

### Step 2, branch B — an image-based PDF, i.e. a scan (17 of 101) — LP-708

```
words = page.get_text("words")   -> empty. There is no text in the file.

  render the page to an image     (the same PyMuPDF renderer the reviewer uses)
  OCR that image                  -> words + PIXEL rectangles
  cache the result per page
  convert pixels -> points        divide by the render zoom (DEFAULT_ZOOM, 2.0)
```

**The conversion is the whole coordinate bridge and it is silent when wrong.** OCR measures
in pixels of the image *we* rendered. Render at 2x and forget to divide, and every box lands
at exactly twice its correct offset — no error, no exception, just a systematically wrong
overlay. It wants an assertion, not a comment.

**Cache it.** OCR is the slow step (~1s a page). Once per page, on first open, never again.

### Step 2, branch C — an image document, JPEG or PNG — LP-708

An image *is* a scan, so it takes branch B. One extra factor, measured during LP-704 rather
than read anywhere:

> PyMuPDF reports an image's page rect as its **pixels x 0.75** — it reads the image at 96 DPI
> and reports 72-dpi points. A 400x300 px image is a 300x225 pt page.

So this branch's pixel-to-point conversion carries that factor as well as the render zoom.
It is exactly the kind of thing that produces boxes which are consistently, slightly wrong.

### The case that catches people out: mixed PDFs (6 of 101)

Six stored documents have **some pages typed and some photocopied**. So the branch is chosen
**per page**:

```python
words = page.get_text("words")
if len(words) < WORDS_THRESHOLD:      # this PAGE is a photocopy
    words = ocr_words(page)
```

A design that asks *"is this document a scan?"* gets those six wrong in both directions — it
OCRs pages that already have text, and skips pages that need it. The question is always
about a page.

## Behaviour by document kind

| | what happens |
|---|---|
| **Text PDF** (78 docs) | The whole benefit lands here. Recovers most of the 11.8% of fields whose snippet is absent from the text layer only because of formatting. |
| **Scanned PDF** (17 docs) | **Nothing changes.** There are no words to match against. Needs LP-708. |
| **Mixed PDF** (6 docs) | Works on the pages that have text; the scanned pages are unaffected. The matching is per page, so this falls out naturally. |
| **Image** (0 today) | Nothing changes — an image has no text layer. Needs LP-708. |

## Review (LP-706/709 review commit)

Reviewed `e694859`. The measurement work is the best thing in this series — a
premise disproved by measuring it, a contaminated corpus found and excluded, and
the "one field in four" framing shown to be counting derived values as failures.
Seven findings, two of them severe, and one against my own first fix.

### The fold was blind to magnitude

`_FOLD_AWAY` deleted `.`, `,` and `-`, so `fold("1,500.00")` and `fold("150,000")`
were both `"150000"`. A field worth 1,500.00 drew a confident NORMALISED box over a
page's **$150,000** — a figure a hundred times larger. `str(field["value"])` on a
JSON float gives `1500.0`, which boxed over `15,000`.

This is exactly what LP-709 exists to prevent, reached from the other side, and
the word-boundary guard cannot see it because both sides are whole words.
Separators are **content** in a number and formatting only between equivalent
renderings of one. What tells those apart is positional: the decimal separator is
the last `.` or `,` with one or two digits after it; everything else is grouping.
That keeps `15,000.00`, `15 000,00` and `15000.00` equal — including the European
case the ticket wanted — while `150,000` and `1,500.00` stay apart.

### The fold joins words the page kept apart

`index.text` is the page's words concatenated with **nothing** between them, so a
needle can span two words that are far apart and still begin and end on word
boundaries. A pay stub showing `40` and `00` in adjacent table **cells** matched a
needle of `4000` — a figure not on the page at all, boxed across two unrelated
cells and reported unambiguous because the spurious run was the only occurrence.

The word-boundary rule is necessary and not sufficient: a real match is always a
whole run of the page's words; a whole run of the page's words is not always
something the page says. Restored the adjacency the fold destroyed — a space
measures ~0.2 of line height on this corpus and a column gap ~2.4, so the
threshold sits clear of both — and a wrap is allowed by its shape rather than
waved through.

**My first version of that guard was wrong in the way this series keeps
producing.** It `continue`d on any pair not sharing a line, so a run crossing a
line had no bound at all and two words at opposite corners joined into one box
spanning most of the page. And my first test for the fix could not fail: both
cases were rejected by the reading-order check before the distance bound was
reached, so the bound could be deleted with everything green. The distinguishing
case is *down and to the left* — a genuine wrap in every respect except distance.

### A weak tier on an early page beat a strong tier on a later one

Tier precedence was applied per page while the page walk sat outside it, so a bare
VALUE guess on page 1 beat a verbatim EXACT match on page 3. That **moves a box
that was correct before this commit**, against the guarantee that running the exact
tier first means none can move — a guarantee that only ever held within a page.
The walk is tier-major now, with the cited page still tried first inside each tier.

### The ambiguity rule could not see the case it exists for

"One occurrence, or none" was counted per page while the search is document-wide,
so the same figure once on page 1 and once on page 2 — exactly as unresolvable as
twice on one page — was called unambiguous and boxed. It bites hardest on the ~4%
of fields citing a page that does not exist, which always fall through to the
document-wide walk. Counted across the document now.

This is the ticket's own item 4, which I first confirmed as defensible on the
strength of "the cited page is tried first". That is true for the cited-page case
and says nothing about the fall-through, which is the common one.

### `match_kind` reaches no reader

`FieldBoxPublic` has no such field, the response does not carry it, and the
frontend never mentions it — so a bare-value guess and a verbatim match render
identically. The module docstring claimed "the screen is entitled to say which it
has". The distinction is computed, correct, and stops at the service boundary.
The claim is corrected rather than an unread field added to the API; surfacing it
is a UI decision about how a weaker box should look.

### The index was rebuilt per field, per page

`_index_page` ran for every (field, page) pair. Measured on a 12-page document
with 30 fields missing the exact tier: **1.88 s** in the request path. One index
per page for the whole document brings the same work to **0.021 s**. The single
`open()` above `find_all_field_boxes` is justified on precisely this argument, and
the new tier had reintroduced the multiplication it was avoiding.

### Answers to the ticket's own questions

1. **Keep the folding.** The machinery earns its place on the value tier's +10,
   and the normalised tier costs one extra search after exact fails. Its benefit is
   unobserved on 76 documents, which is worth saying plainly — but it is now
   materially safer than it was measured being, since the fold no longer confuses
   magnitudes.
2. Falsified — see above.
3. `MIN_FOLDED_LENGTH` is genuinely load-bearing after the rewrite: `net,` folds to
   three characters and would match the page's own `Net` at both boundaries.
4. Not defensible as it stood — see above.
5. Clean. One caller constructs a `BoxRequest`; no stale `tuple[str, int]` outside
   a test, which is fixed (CI runs mypy over `app/` only, so nothing flagged it).

### Verification

ruff 0, format 0, mypy strict 0, **6,700 pytest**. Seven mutations, all caught —
including the two that initially escaped: the cross-line bound and the
reading-order check, each now isolated by a case only it can reject.
