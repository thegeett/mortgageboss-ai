# LP-845 — The communication page notices what another tab did

Status: spec. Build order: fourth of four, independent of the other three.

## The report

> "I have to refresh the communication page, after requesting document if communication page is
> opened in different tab of the browser. Can we make it auto appear on change?"

## Why it happens

`frontend/lib/query-client.ts:10-12`:

    staleTime: 60 * 1000,
    refetchOnWindowFocus: false,

Tab A requests a document and invalidates its own cache (LP-840 made sure of that). Tab B is a
different React tree with a different QueryClient and was told nothing, so it serves its cached
timeline for a minute, and `refetchOnWindowFocus: false` means even switching to it does not
recheck.

## The options, and what each actually reaches

| Approach | Reach | Cost |
|---|---|---|
| `refetchOnWindowFocus` on the timeline query | Same browser, refreshes when the tab is looked at | one line |
| `BroadcastChannel` | Same browser, instant, no server | ~30 lines, no infra |
| `refetchInterval` polling | Any device or browser | a request per interval per open tab |
| SSE / WebSocket | Any device, any user, true push | ALB, Fargate, auth — real infra |

## The change

**The first two together.** Focus-refetch covers "I switched to that tab"; BroadcastChannel covers
"both tabs are visible at once" and fires immediately. Neither needs a server change.

Polling is the established house pattern for a DIFFERENT problem — `lib/api/documents.ts:79` and
`needs.ts:60` both use a *function* `refetchInterval` that polls only while work is in flight and
idles otherwise. That shape suits a job that finishes. A draft changing is an event, not a job, and
polling every open tab forever to catch it is the wrong trade.

SSE is deliberately not built. It is the only option that reaches a second processor on a second
machine, and until two people work one file at once it buys nothing the first two do not.

## Scope note

`BroadcastChannel` is same-origin and same-browser. It will not reach a second device, a second
browser, or another user — and it must not be described in the UI as though it does.

# Built

Both halves, as specced. Frontend only; no server change and no new dependency.

## The defect the build found in its own fix

**`refetchOnWindowFocus: true` does nothing while the data is inside `staleTime`,** and `staleTime`
is 60s client-wide. So the reported case — switch to the verification tab, request a document,
switch back within the minute — got the cached mailbox exactly as before. The setting was present,
the behaviour was not.

It is `"always"` now, which ignores staleness. The cost is one request when the tab is focused, on
the one screen whose job is to show what has happened since you last looked.

**The first version of the test would have shipped it.** It read
`query.options.refetchOnWindowFocus` back off the cache and asserted `true` — which passed, and
typechecked as `unknown` because that is an OBSERVER option rather than a query option, so the value
being there at runtime is an implementation detail of this version of TanStack. Rewriting it to
drive `focusManager` and count requests failed immediately, against code I had already convinced
myself was correct. Asserting a SETTING asserts that somebody typed something; asserting the
BEHAVIOUR asserts what a processor gets.

## The echo loop

`invalidateDraftViews` announces; `invalidateDraftViewsLocally` does not. The split exists for one
reason: `BroadcastChannel` does not deliver back to the sender but does deliver to every other tab,
so a listener that called the announcing variant would have two tabs refreshing each other forever —
a request storm rather than a stale screen, and one that only appears with two tabs actually open.
Pinned by counting messages on a third channel.

## What the mutations found

Four claims, each mutated with the absence check b7 named in the LP-844 review — after planting,
positively confirm the original behaviour is gone rather than that the file changed. That is the
discipline that was missing from three earlier invalid mutations in this run, and here it worked as
advertised.

Two survived first time, and both were real gaps rather than bad mutations:

- **The focus refetch** had no test at all, so removing it passed 1535 tests.
- **The listener registration** had no test, because every broadcast test called
  `listenForDraftChanges` itself. All six passed against a build where nothing ever registered it —
  the feature complete and connected to nothing, which is the exact shape of the LP-840 defect that
  started this run of tickets.

## Scope, stated so nobody describes it as more

`BroadcastChannel` is same-origin and same-browser. A second device, a second browser and another
processor are all outside it. Reaching them needs the server to push, which is real infrastructure
and is deliberately not built here: until two people work one file at once, it buys nothing the two
cheap halves do not.

## Review (second session)

Reviewed `b3684b4c`. Every conclusion below came from running something; the four questions the
builder left open are answered by measurement, not by reading.

### A — does the focus test discriminate, or does it pass under both settings?

The builder's own worry: "if the test passes under BOTH it is pinning less than it looks." It does
not. `timeline-focus.test.ts` was run against two mutants, each confirmed applied first
(`rg -c 'refetchOnWindowFocus: "always"'` → 0 before the run):

| Mutant | Result |
|---|---|
| `refetchOnWindowFocus: true` | **1 failed**, 1 passed |
| `refetchOnWindowFocus: true` + `staleTime: 5 * 1000` | **1 failed**, 1 passed |

So `"always"` is genuinely pinned. On whether it is still worth keeping now that the broadcast
exists: the two halves do not cover the same case. The broadcast covers a second tab of the *same*
browser; focus-refetch covers a second browser or a second device, which `BroadcastChannel` cannot
reach by construction. They overlap only on the same-browser case. `"always"` earns its place.

### B — is jsdom's `BroadcastChannel` faithful about not echoing to the sender?

Yes, so the echo guard's "exactly one" is sound in the direction the builder worried about. Three
channels on one name, counting deliveries, returned `{sender: 0, other: 1, third: 1}` — the sender
never hears itself and every other subscriber hears it once, which is what the spec requires.

### C — `announceDraftChange` opens and closes a channel per call

Not a problem, and the specific risk was not cost but loss: `close()` immediately after
`postMessage` could plausibly drop the message. It does not. A probe announced 50 changes in a tight
loop with one listener attached; all 50 arrived, all distinct. Probe deleted afterwards — it asserted
a platform guarantee, not this repo's behaviour.

### D — how many times is `makeQueryClient` actually called?

**Once per page, so the duplicate-listener concern does not occur.** There is exactly one production
call site, `components/providers.tsx:13`, reached through the lazy form `useState(() => makeQueryClient())`,
and `Providers` is rendered once from the root `app/layout.tsx` — which does not remount across
client-side navigation. One client, one listener, one channel.

What the question surfaced is narrower and was worth writing down. `listenForDraftChanges` returns a
teardown and `makeQueryClient` drops it, which the comment justifies by analogy to the two blob-url
eviction handlers beside it. The analogy is inexact in one way: those return a QueryCache
subscription, which the client owns and discards along with itself, while this returns `bus.close()`
on a BroadcastChannel whose `onmessage` closes over the client — so a discarded client stays
reachable and its channel stays open for the life of the page. Dropping that teardown is free only
while there is one client. Nothing is leaking today; the precondition was simply unrecorded.

Two guards now record it, in `draft-broadcast.test.ts`:

- **`one production call site builds the client`** — scans the source tree (test files and the
  defining module excluded) and asserts exactly one caller. It asserts the scan *found*
  `components/providers.tsx` before asserting the count, because a walker that returns nothing would
  otherwise satisfy a count check for the wrong reason.
- **`and builds it in a lazy initialiser, not on every render`** — the realistic regression here is a
  simplification rather than a mistake: `const queryClient = makeQueryClient()` in the component body
  reads fine, runs on every render, and with the teardown dropped would leave another open channel
  behind each time.

Both mutated, each failing only its own test: a second call site → `one production call site` fails;
the bare-call form → `lazy initialiser` fails; a walker pointed at the wrong directory → the positive
control fires first, with `expected [] to include 'components/providers.tsx'`.

### The wiring test, which is the item that most deserved attention

The builder flagged it as "the third time in four tickets that a thing was built correctly and wired
to nothing" — and in this ticket they caught it themselves and added
`a client from makeQueryClient refreshes on another tab's announcement`. Verified that the test they
added actually holds the wiring down: with `listenForDraftChanges(client)` removed from
`makeQueryClient` (confirmed absent, `rg -c` → 0), that test fails and only that test fails, across
nine runs including three with the Vite cache cleared.

One run out of ten reported two failures under that mutant instead of one. It did not reproduce in
nine further attempts, cold or warm, and the unmutated suite was then run twelve times, four
concurrently, with all 7 tests passing every time. Recorded as observed-once-unexplained rather than
written off; if it recurs, the thing to suspect is `delivered()` assuming a single macrotask is
enough for a `BroadcastChannel` message.

### Standing three

Frontend-only ticket with no new network call, no logging and no model call: tenancy, message content
in logs, and AI in the decision path are all untouched. `invalidateDraftViewsLocally` takes a
`fileId` that came from a same-origin message and is used only as a cache key — it reaches no API and
no query it invalidates is scoped by anything but that id, and a malformed one is dropped before use.

`biome` clean across 377 files, `tsc --noEmit` exit 0, **1540 tests in 132 files passing**,
`next build` succeeded.
