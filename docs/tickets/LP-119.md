# LP-119 — Applicability filter engine (thin slice, proven on AS-5 gift-letter)

**Type:** Story · **Epic:** Phase 3.5 / Epic B · **Depends:** LP-118 (rule table), LP-118.6 (fact snapshot), ADR-239
**Status:** complete · **Date:** 2026-07-08

## What this ticket is

The first data-driven engine piece that RUNS: the **applicability filter**. For a loan file, it
classifies each rule — by reading the rule's applicability (scope / triggers / required_inputs) from
`verification_rules` (LP-118) against the fact snapshot (LP-118.6) — into three states:

- **DOESN'T-APPLY** — scope or a trigger is FALSE → rule irrelevant → silently excluded.
- **COULDN'T-CHECK** — rule applies but data it needs is MISSING/UNKNOWN → surfaced, **never a
  silent pass**.
- **READY-TO-RUN** — applies AND required data present → eligible for the evaluator (LP-120).

A **vertical thin slice**: the engine is GENERAL (reads applicability as DATA, works for any rule),
proven on ONE rule — **AS-5** (gift-letter present) — plus synthetic cases. **Scope held:** no
evaluators, no findings, no runner wiring, no other rules; read-only classification; live path
unchanged.

**THE FALSE-GREEN GUARD (the core):** UNKNOWN (the data needed to DECIDE a condition is missing)
resolves to COULDN'T-CHECK — **never** collapses to doesn't-apply or ready-to-run. A file must never
look checked-and-clean when the data to decide was absent.

## Assumptions and decisions

- **present/empty/absent → true/false/unknown mapping.** For a DECISION input (scope/trigger/
  field_condition), a Fact with a concrete value → its truth; **a Fact with no value — `absent` OR
  empty (`value is None`) — → UNKNOWN.** This is the conservative false-green reading ADR-239
  mandates ("unset enum → None → applicability unknown"): if we don't have a concrete value we
  cannot decide, so we must not guess. (The snapshot still distinguishes empty vs absent; the
  engine's *choice* is to treat both "no value" states as "can't decide".)
- **`entity_exists` is three-valued.** TRUE if any element matches; **UNKNOWN if the collection is
  EMPTY** (no data to confirm the entity is truly absent) or an element's field is unknown; FALSE
  only when there ARE elements and none matches. This is exactly what gives AS-5 its three cases:
  gift asset → ready; other assets, no gift → doesn't-apply; **no assets at all → couldn't-check**
  (we can't confirm there's no gift — the file may just have no asset data captured).
- **Empty scope constraint = applies to all** (a `{}` scope or an empty list for a dimension is no
  constraint) — tested to avoid the off-by-one.
- **FALSE precedence over UNKNOWN.** A definitively-false scope/trigger → doesn't-apply regardless
  of missing required inputs (the rule is genuinely irrelevant). Only when scope+triggers are TRUE
  do required inputs decide ready vs couldn't-check.
- **The check-target is NOT a required input.** AS-5's gift LETTER is what the rule checks (its
  absence is the finding, evaluated in LP-120) — so it is **not** in `required_inputs`. AS-5 with a
  gift but no letter is READY-TO-RUN, not couldn't-check. (Getting this wrong would turn a findable
  problem into a can't-check.)
- **AS-5's applicability lives in the table** (seed + migration), so the engine reads it as data;
  the test-suite `create_all` DB has no seed, so the integration test inserts the row itself to
  prove table-reading.
- **`property`-scoped dimensions** resolve through `property` (single); when the file has no
  property, the scope value is UNKNOWN → couldn't-check (honest).

## Review fixes (hardening before LP-121)

A read-only review of the committed LP-119 engine found latent issues (nothing was wired to the
live path, so they were dormant until the runner dispatched them). **Guiding principle applied to
every fix: fail toward COULDN'T-CHECK or a LOUD error — never a silent pass or a silent over-apply.**

- **FIX 1 — required-input inspects the NAMED/nested field.** `_required_input_satisfied` for a
  `[]` path used to check only that the outer collection was non-empty. Now it resolves the named
  (possibly multi-level) leaf — `assets[].value`, `borrowers[].income_items[].monthly_amount` — and
  requires it PRESENT on every element (fail closed); an absent field → couldn't-check, named. (The
  false-green guard.)
- **FIX 3 — malformed applicability fails LOUDLY + the seed stops over-applying.**
  `extra="forbid"` on the applicability parse models (a class-level guard for the 124 rules to come)
  means a flat `{program, purpose}` or an unknown nested key now RAISES at parse instead of silently
  degrading. The seed generator no longer emits the flat shape — it translates program/purpose into
  a real `scope` (engine keys `loan_purpose`/`refinance_type`), and unauthored rules get an explicit
  valid empty applicability.
- **FIX 4 — unknown scope dimension fails CLOSED.** An unrecognized dimension (`{"state":["TX"]}`)
  → couldn't-check (never "no constraint → fires nationwide"). The dimension→path map is now DERIVED
  from the `FileFacts`/`PropertyFacts` fields, so it can't rot out of sync.
- **FIX 5 — refinance_type scope on a purchase → DOESN'T-APPLY**, not couldn't-check (mirrors
  `purpose_applies`): absent-because-irrelevant is distinguished from absent-because-missing, so
  purchase files don't flood with couldn't-check for refi-scoped rules.
- **FIX 6 — a present-but-None Fact is a real answer.** `_known_value` now treats `value=None,
  absent=False` as KNOWN **iff it carries a `source`** (a deliberate determination, e.g.
  `computed.mi_monthly` = None = "MI not required" → READY_TO_RUN). An unset scalar (source None)
  stays UNKNOWN, so the scope-unknown false-green guard is preserved.
- **FIX 8 (accepted + documented):** the plain-list collections can't distinguish "reviewed, zero
  rows" from "not loaded", so an EMPTY collection → couldn't-check (errs safe). A no-asset file
  carries a gift-rule couldn't-check until these collections become Fact-wrapped (a future ticket).
- **FIX 7 (migration):** the AS-5 applicability migration's downgrade is now a documented **no-op**
  (the LP-118 seed carries AS-5's applicability; reverting to NULL would leave AS-5 with no trigger →
  universally ready-to-run). Verified: any up/down sequence leaves AS-5 authored, never NULL.
