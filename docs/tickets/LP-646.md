# LP-646 — `--autogenerate` proposes dropping a live table, every time

- **Status:** Not started. Diagnosed, root cause found, fix is small; the risk is in what has already
  been shipped around it.
- **Date:** 2026-09-05
- **Raised by:** LP-644 §3, whose autogenerated migration had to be hand-trimmed to avoid dropping a
  table as a side effect of adding a cache. Confirmed by its review against a database migrated to
  head from scratch.
- **Scope:** Backend — `app/models/__init__.py`, and an audit of the drift behind it.

## The report

Running `alembic revision --autogenerate` in this repo emits **22 operations that nobody asked for,
four of them destructive**, on a database migrated to head from scratch:

| operation | why it is wrong |
|---|---|
| `drop_table('finding_prose')` | **the table is LIVE and in use** — see the root cause below |
| `drop_index('ix_documents_full_text_fts')` | the documents full-text search index |
| two `stated_housing_expenses` index drops | replaced by re-created equivalents under new names |
| ~18 `alter_column` type changes | `validation_verdicts`, `needs_items`, `verifications` |

LP-644 §3 caught this only because the diff was read line by line before committing. **Shipping the
generated file would have dropped a live table as a footnote to adding a cache**, and the next person
to autogenerate inherits the same loaded gun.

## Root cause of the destructive half

`alembic/env.py` builds `target_metadata` from `Base.metadata`, populated by importing
`app.models`. **`FindingProse` is never imported there.**

```
app/models/finding_prose.py        -> defines FindingProse, __tablename__ = "finding_prose"
app/services/finding_prose.py:38   -> imports and USES it
app/models/__init__.py             -> does NOT import it
```

So the class exists, the table exists, the application reads and writes it — and
`Base.metadata` has never heard of it. Autogenerate compares a database containing
`finding_prose` against metadata that does not, concludes the table is orphaned, and proposes
dropping it. The model is not missing; its *registration* is.

This is a one-line fix, and the reason it deserves a ticket rather than a drive-by is the question it
raises: **how many other models are unregistered?** Every one of them is invisible to autogenerate,
which means both that autogenerate will propose dropping its table and that a future change to it
will silently produce no migration at all. That second failure is the quieter and worse one.

## What to do

1. **Audit registration.** Every module under `app/models/` that declares a `__tablename__` should be
   imported by `app/models/__init__.py`. Find the gaps; `finding_prose` is one, and it was found by
   accident.
2. **Pin it with a test.** A test that walks `app/models/*.py`, collects every `__tablename__`, and
   asserts each appears in `Base.metadata.tables` turns this from a thing someone notices into a
   thing CI refuses. Without it the next unregistered model reintroduces the same gun.
3. **Then triage the remaining drift separately.** The `alter_column` and index operations are a
   different problem from the registration one and must not be swept into the same commit — several
   are genuine model/DB divergences that need deciding one at a time (does the DB follow the model,
   or was the model edited without a migration?).

## What NOT to do

**Do not "fix" this by running autogenerate and committing the result.** That is precisely the action
this ticket exists to prevent. The index drops in particular look harmless and are not: the documents
FTS index backs search, and rebuilding it on a large table is not free.

**Do not fix it inside another ticket's migration.** LP-644 §3 deliberately hand-trimmed rather than
resolving any of it, so the drift could be reviewed as the schema change it is.

## How to verify

Against a database migrated to head from scratch, `alembic revision --autogenerate` should emit an
EMPTY migration. That is the acceptance criterion, and it is currently 22 operations away.
