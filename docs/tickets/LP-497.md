### A1 — AS-4's 0/5, diagnosed: **outcome 1, the tag asks the wrong question at the wrong scope**

This is the ticket's main question, and the answer is not a calibration gap. Four pieces of evidence,
each checked rather than inferred.

**1. The prompt asks about account TYPE, explicitly.** `stmt_facts`, tag 2:

> "is_reserve_eligible — are the funds in this account usable as reserves as the statement shows them
> (a normal checking/savings balance), vs restricted or a retirement/discounted account? …
> **(This is about the ACCOUNT TYPE/BALANCE only** — ignore "loan_borrowers", which is not relevant
> to reserve-eligibility.)"

So a model answering "standard checking account → eligible" is **obeying its prompt correctly**. The
0/5 is not the model failing at the task it was given.

**2. Fannie's test is not account type.** Per the FAQ (tier P, taken from this ticket): liquid assets
usable as reserves include "readily available funds, stocks, bonds, mutual funds, CDs, money market
funds and trust accounts". A checking account **is** an eligible asset type. The exclusion —
"funds that cannot be withdrawn under circumstances other than the account owner's retirement,
employment termination, or death" — is a **withdrawal-terms** question. And separately:
**"Funds to close are subtracted from available assets when considering sufficient assets for
reserves."**

**3. LP-390-5 recorded the cause as a guess, and the guess was right.** Its finding 3 reads: "Priya's
`no` reflects a stricter underwriting call (these specific accounts are not counted as reserves —
**likely because they hold the down-payment / EMD**, or another agency nuance)". That "likely" was
never tested. It is the funds-to-close rule.

**4. The code already implements the rule Priya was applying.** `app/verification/reserves.py`:

```python
eligible_raw = liquid_assets + retirement_counted - down_payment - closing_costs
```

**The funds-to-close subtraction is already there, at loan level, where it belongs.**

So the model and Priya were answering different questions, and both answered their own correctly:

| | question answered | answer | correct? |
|---|---|---|---|
| the tag | is this ACCOUNT TYPE an eligible asset class? | `yes` | **yes**, per the prompt and per Fannie |
| Priya | do THESE funds count as reserves for THIS loan? | `no` | **yes** — they are the funds to close |

That is why the disagreement is systematic rather than noisy: every borrower's deposit account holds
the money they are about to spend at closing, so the two questions diverge on **every** file.

**The tag is structurally unable to answer Priya's question.** `stmt_facts` is document-subject with
`include_documents=False`, `include_lists=False`, `include_transactions=False` — it receives one
statement's own fields plus the borrower roster. It never sees the loan's cash-to-close, so it cannot
know how much of a balance is spoken for. This is the same structural limit LP-390-5 found in
finding 2 for `stmt.owner_matches_borrower`, which it correctly called a context gap rather than a
scoring gap.

**Consequence, and it is the ticket's stated consequence for outcome 1: AS-4 needs a different
input.** It should not read `stmt.is_reserve_eligible` at all. The reserves calculation already
subtracts funds to close, so the eligibility judgment the tag was invented to supply is redundant with
arithmetic that is already correct. AS-4 therefore activates without a 0/5 tag anywhere in its chain,
satisfying acceptance criterion 3 by construction rather than by waiting.

**No producer change, so no ADR and no blast radius.** `stmt.is_reserve_eligible` keeps producing for
anything else that wants it; AS-4 simply stops depending on it. An ADR would be required only if the
tag's scope changed, and it does not.

### AS-4 — the blocker was wrong twice over

The 0/5 never justified holding this rule, for two independent reasons found this ticket:

1. **The tag is not in AS-4's chain.** Its bar named `stmt.is_reserve_eligible` load-bearing "via the
   reserves calculator". `build_reserves_view` sums assets from the **DB** (`_sum_assets` /
   `_sum_assets_excluding`) and takes its PITI divisor from the **DTI calculation**;
   `reserves.required_months` reads **MISMO** occupancy and unit count. Nothing AI-produced feeds
   either operand. The rule was blocked by a measurement of a tag it never reads — the LP-495b shape
   (`occupancy.rental_support` had a producer its own bar denied), inverted.
2. **The 0/5 was a question mismatch, not a model failure** (the A1 diagnosis above).

So the bar moved to `no-ai-dependency` with `load_bearing_ai_tags: []`, and a test pins that empty
list — an incorrect load-bearing claim is what held this rule for three tickets.

### What AS-4 actually lacked: its threshold — and a false-green

`reserves.required_months` keyed on **occupancy only** and returned `0` for every principal residence.
Its own source comment recorded the consequence: *"a NON-1-unit or multiple-financed-property PRIMARY
gets required=0 here and AS-4 can false-green a real reserve shortfall."* B3-4.1-01 requires **6
months** for a two- to four-unit principal residence, so such a file reported `satisfied` on a real
shortfall.

B3-4.1-01 is now fetched (tier P, page dated 08/07/2024) and the matrix keys on occupancy **and** unit
count:

| cell | required | verdict on the fixture |
|---|---|---|
| one-unit principal residence | 0 | `satisfied` at 0.5 months |
| **2-4 unit principal residence** | **6** | **`fired` at 2.0 months — was `satisfied` before** |
| 2-4 unit primary, 7.0 months | 6 | `satisfied` (the cell is a real comparison, not a blanket fire) |
| second home | 2 | `satisfied` at 4.0 |
| investment | 6 | `fired` at 3.0 |
| **principal residence, unit count unknown** | — | **`couldnt_check`** |
| above four units | — | `couldnt_check` |
| no occupancy | — | `couldnt_check` |
| gated calculator (null months) | — | `couldnt_check`, never read as zero |

The unknown-unit cell is the one that cannot be defaulted: the answer is **0 or 6 and nothing
between**, so a default decides the verdict rather than informing it. The fixture is built so the two
answers disagree (2.0 months clears 0 and fails 6), and the unit count reaches only 10 of 19 corpus
files, so this is a common branch rather than an edge case.

### What AS-4 does NOT check, stated in its own finding text

B3-4.1-01 also requires 2% / 4% / 6% of aggregate UPB for 1-4 / 5-6 / 7-10 other financed properties,
and 6 months for a cash-out refinance over 45% DTI. Neither the financed-property count nor the
aggregate UPB reaches the snapshot (`property.is_retained_reo` and `property.retained_pitia` are
vocabulary orphans with no recipe). Both overlays can only **raise** the requirement, so the encoded
figure is a **floor** and the rule never errs toward clearing — but `satisfied` means "meets the
occupancy/unit requirement", not "meets every reserve requirement", and the spec, the bar and the
verdict text all say so.

`stmt.nsf_count` (derived) → AS-7. The aggregator already abstains rather than reporting `0` when the

It is held because **(1)** LP-495c has not landed, so an honest abstain still coerces to

**No tolerance was invented.** The Selling Guide sets no NSF or overdraft count tolerance, confirming
Priya's ruling that it is internal policy. AS-7 reports the count; any tolerance must arrive as a
