# 1. The rule → verdict chain

**AS-1 was traced end to end**, and it is representative in the way that matters: it is the only rule
that exercises *every* operand kind (`tag`, `loan_tag`, `reference`, `product`), it runs on the busiest
enumerator (`per_deposit`), and it mixes all three production modes (parsed + AI + derived) in one gate.
Its one unrepresentative trait — the only leftover per-rule Python module — is itself informative, so it
is shown.

## 1a. The spec

`backend/app/verification/rules/specs/AS-1.yaml` — the executable half (the prose half is quoted in §4):

```yaml
rule_id: AS-1
name: Large-deposit sourcing sweep
category: Assets
kind: calculative        # must equal rule_kinds.csv (AS-1 = calculative)
numeric_check: true

subject_enumeration: per_deposit
subject_key_fields: [account, date, amount]

reference_values:
  large_deposit_threshold: "50% of total monthly qualifying income"
  priya_validated: false          # NOT confirmed
  threshold_needs_signoff: true
  values:
    large_deposit_threshold_pct: "50%"

deterministic:
  load_bearing_tags: [txn.is_money_in, txn.amount, txn.has_identified_source, txn.source_strength]
  gated_tags:        [txn.is_money_in, txn.amount, txn.has_identified_source]

  applicability: {tag: txn.is_money_in, op: eq, value: in}

  operands:
    observed: {tag: txn.amount}
    threshold:
      product:
        - {reference: large_deposit_threshold_pct}     # 0.5 (parsed from "50%")
        - {loan_tag: dti.qualifying_income_monthly}

  outcomes:
    - verdict: fired
      when_tags: [{tag: txn.has_identified_source, op: ne, value: "yes"}]
      when_compare: {op: ">", left: observed, right: threshold}
      reasoning: "deposit {observed} exceeds the large-deposit threshold {threshold} and is not sourced..."
      how_to_fix: "Document this deposit's source..."
    - verdict: needs_review
      when_tags:
        - {tag: txn.has_identified_source, op: eq, value: "yes"}
        - {tag: txn.source_strength, op: eq, value: self_asserted}
      when_compare: {op: ">=", left: observed, right: threshold}
      ...
    - verdict: satisfied
      default: true
      reasoning: "deposit {observed} is at or below the large-deposit threshold {threshold}, or is already sourced"
```

Note the gate/load-bearing split: `txn.source_strength` is **load-bearing but not gated** — it refines
a verdict but its absence must never force `couldnt_check`.

### Three disagreements to name

> **`txn.source_strength` exists in no vocabulary file.** Not `fact_tags.csv`, not
> `vocabulary_extra.yaml`, not `tag_production.yaml`. It is referenced by `AS-1.yaml`, `as1.py`,
> `reasons.py`, `services/tag_correlation.py`, `services/rule_findings.py`. It works only because it is

> symptom. `worksheet.py:125` acknowledges the sibling case (`has_identified_source` "is a vocabulary AI

> **`rule_tags.csv` and the spec disagree about what AS-1 reads.** The CSV lists
> `AS-1,txn.apparent_category`, `AS-1,txn.date`, `AS-1,txn.source_reference`,
> `AS-1,income.qualifying_monthly` — none of which the deterministic block references — and *omits*
> `txn.source_strength`, which it does. The spec is what runs; `rule_tags.csv` is authoring metadata
> that has drifted.

> **The `txn.*` entries in `tag_production.yaml` do not run on a live file.**

## 1c. Extracted field → tag value, the actual code path

For `txn.amount` (the declared path, used by every non-transaction subject; the legacy producer mirrors it):

1. **`producer.py:materialize_tags`** iterates declarations, `mode is PARSED`, resolves
   `subject_type(decl.subject)`, strips any `:hash` suffix: `field_name = decl.data.split(":", 1)[0]`.
2. **`subjects.py:_txn_read_field`** — the subject type's reader. For transactions the universe is a
   literal 4-key map:
   ```python
   _TXN_FIELDS = {"date": "date", "amount": "amount", "direction": "direction", "description": "description"}
   def _txn_read_field(raw, field):
       assert isinstance(raw, TransactionRecord)
       attr = _TXN_FIELDS.get(field)
       return getattr(raw, attr) if attr is not None else None
   ```
3. **`parsed.py:produce_parsed_tag`** maps `Field` → `Tag`, and this is where the fail-closed discipline lives:
   ```python
   if field is None or not field.is_present:
       return None  # absent — never a fabricated value
   ...
   return Tag(value=value, confidence=None,  # a parsed passthrough — never a fabricated confidence
              source_facts=(subject_id,), produced_by=TagProducedBy.PARSED,
              tag_role=TagRole.STRUCTURAL_FACT, stage=TagStage.A)
   ```
   `confidence=None` matters downstream: `gate.py` ignores `None` confidences in the min, so parsed
   passthroughs never drag a verdict to `needs_review`.

Upstream of that, the `TransactionRecord` came from `snapshot/documents_section.py:build_transactions`,
which reads the extractor's `transactions` rows off `Extraction.extracted_data`. **PII routing happens at
this boundary**, not at extraction: `_PII_FIELDS` (`documents_section.py:189`) maps each sensitive field
name to `(PiiKind, pre_masked)` and routes it to `PiiField.pre_masked` or `PiiField.from_raw`.

For the derived operand `dti.qualifying_income_monthly` the path is different —
`derived.py:_qualifying_income_monthly` reads **MISMO stated income**
(`borrower.<n>.income.<m>.monthly_amount`), not any extraction, and abstains to `unknown` rather than 0.

> The spec carries its own honesty note: `dti.qualifying_income_monthly` sums **stated** 1003 income
> while the guideline is 50% of **qualifying** income. Stated ≥ qualifying, so the threshold ships
> **looser than the guideline** — a false-green band for variable-income files. Recorded in the YAML,
> `priya_validated: false`. Separately, `fact_tags.csv` still describes this tag as "sum of
> income.qualifying_monthly" — the recipe's docstring flags its own vocabulary row as **STALE**.

## 1d. Where the threshold lives, and how activation gates on it

Two separate things share the word "threshold" and they are not the same mechanism:

- **The rule's arithmetic threshold** (50%) is *in the spec*, under `reference_values.values`, parsed by
  `deterministic.py:_reference_operand` (`(\d+(?:\.\d+)?)\s*%` → `Decimal/100`). It rides onto the
  verdict as `threshold_used`.
- **The activation bar** is in `rules/activation_bars.yaml`, one entry per non-base rule (34 of them),
  loaded by `activation_bars.py`. It is the accuracy a rule's AI tags must reach before it may ship a
  trusted verdict.

AS-1 has no bar — it's in `_BASE_ACTIVE` (the pre-LP-389 set), so `_candidate_rule_ids()` excludes it.
`is_eligible` is the gate:

```python
if bar.status == "calibratable-now":
    return (bar.validated and bar.threshold is not None
            and bar.measured_accuracy is not None and bar.measured_accuracy >= bar.threshold)
if bar.status == "no-ai-dependency":        return bar.input_resolves
if bar.status == "no-ai-threshold-pending": return bar.input_resolves and bar.validated
return False
```

The loader is aggressively fail-loud: bars must cover **exactly** the candidate set; `validated` must be
an explicit bool; a threshold outside `calibratable-now` is rejected; `ships: auto` on a judgmental rule
raises (`ActivationBarError`); `input_resolves: true` on a non-no-AI status raises. There's even a guard
for `threshold: true` coercing to `1.0` (`bool ⊂ int`).

## 1e. The verdict, and how the outcome states get assigned

`evaluate_deterministic_rule` (`deterministic.py:191`) is the whole engine — **326 lines, zero per-rule
branches**. Per subject, in fixed order:

| step | assigns |
|---|---|
| 0. `absent_document_couldnt_check` | `COULDNT_CHECK` keyed `missing:<type>` when an *expected* document is confidently absent |
| 1. `resolve_applicability` | predicate false → **`NOT_APPLICABLE`**; predicate absent/`"unknown"` → **`COULDNT_CHECK`** |
| 2. `evaluate_gate` over `gated_tags` | absent tag → `COULDNT_CHECK`; value `"unknown"` → `COULDNT_CHECK` (different reason); contradiction → `NEEDS_REVIEW`; min confidence < floor → `NEEDS_REVIEW` |
| 3. operand resolution | any operand `None` → `COULDNT_CHECK` ("never a fabricated value") |
| 4. ordered outcomes, first match wins | `FIRED` / `NEEDS_REVIEW` / `SATISFIED` from the spec's `verdict:` strings |
| 4b. `for…else` | no outcome matched → `COULDNT_CHECK`, "NEVER silently drop a subject" |

The **five states** in `result.py:Verdict` are `FIRED / SATISFIED / COULDNT_CHECK / NEEDS_REVIEW /
NOT_APPLICABLE`, plus a sixth, `PENDING_AUTOMATION`, that no spec can author — it's emitted only by
`pending_checks.py` for a *blocked-but-applicable* rule (applicability holds, data present, rule not
activated → the would-be verdict is discarded and a manual-review flag ships).

`VERDICT_BY_NAME` deliberately excludes `not_applicable`: it is derived from scope, never declared. The
§8 honesty contract in `applicability.py` is the load-bearing distinction — `not_applicable` (Tab 4,
never relevant) must never absorb `couldnt_check` (Tab 1, a real gap).

The `RuleEvaluation` carries provenance inline: every load-bearing tag with its
value/confidence/reasoning/`source_facts`, the `threshold_used`, `priya_validated`, and
`gated_pending_signoff = not priya_validated`. **For AS-1 that last flag is `True` on every verdict it
produces** — the 50% bar is unsigned.

## 1f. The same trace for an inert rule

Both AS-3 and AS-7 were traced, because they break at *different hops* — which is the useful thing to see.

### AS-7 (NSF/overdraft) — breaks at the **calibration** hop

The chain is fully built end to end. `AS-7.yaml`:

```yaml
deterministic:
  load_bearing_tags: [stmt.nsf_count]
  gated_tags:        [stmt.nsf_count]
  operands:
    count:     {tag: stmt.nsf_count}
    tolerance: {reference: nsf_tolerance}      # "3"
  outcomes:
    - verdict: fired
      when_compare: {op: ">", left: count, right: tolerance}
```

- `stmt.nsf_count` **is** declared — `vocabulary_extra.yaml:323` (the hand-editable overlay, not the
  xlsx-generated CSV).
- It **is** produced — `tag_production.yaml:149`: `{mode: derived, subject: loan, data: stmt_nsf_count}`.
- The recipe **exists** and is careful — `derived.py:_stmt_nsf_count` abstains to `unknown` if the
  per-transaction tag is on no transaction (absent≠no) *and* if any transaction's NSF status is
  `"unknown"` (the count would be a lower bound).
- The per-transaction tag `txn.is_nsf_or_overdraft` **is** declared (`fact_tags.csv:10`) and **is**
  produced (`tag_production.yaml:21`, its own AI group `txn_nsf`, deliberately not `txn_stage_a` so it's
  scoped to depository statements).

Everything resolves. The single broken hop is the bar:

```yaml
AS-7:
  status: not-calibratable-yet
  ships: auto
  threshold: null
  validated: false
  load_bearing_ai_tags: [txn.is_nsf_or_overdraft]   # via the derived stmt.nsf_count
  rationale: >-
    reads the derived stmt.nsf_count, aggregated from txn.is_nsf_or_overdraft (AI), UNSCORED.
```

`is_eligible` returns `False` at the first branch — `not-calibratable-yet` isn't `calibratable-now`, so
it can't even be signed off (the loader raises if you set `validated: true` on it).

**What repairs it:** a labeling round on `txn.is_nsf_or_overdraft` → set `measured_accuracy`, flip
`status: calibratable-now` with a proposed `threshold`, Priya sets the height and flips
`validated: true`. That's it — **no code**. The `tag_production.yaml:19` comment already anticipates this
("AS-7 auto-ships, so it is HELD on calibration… the OC-1 position").
*Caveat from Priya's rulings: NSF is an internal policy, not an agency rule, and event type matters — so
the encoded `nsf_tolerance: "3"` is a placeholder, and the bar isn't the only open question.*

### AS-3 (cash-to-close) — breaks at the **producer** hop

Different failure entirely. `calc.cash_to_close` is declared (`fact_tags.csv`) and produced
(`tag_production.yaml:151`), and the recipe is registered — but the recipe is a **deliberate abstention
stub**:

```python
def _cash_to_close_shortfall(snapshot, _subject_id, _subject_raw) -> tuple[JsonValue, str]:
    """BUCKET C: there is NO cash-to-close calculator (§3B), and ``closing_costs`` is not a fact today
    (no Loan-Estimate extraction), so this recipe cannot compute the need and ABSTAINS."""
    return (_UNKNOWN, "cash-to-close needs the closing-costs figure, which is not extracted today ...")
```

It returns `unknown` unconditionally → `gate.py` step 2 → `COULDNT_CHECK` on every file, forever. Its bar
records this honestly rather than pretending:

```yaml
AS-3:
  status: no-ai-dependency
  input_resolves: false   # LP-381: calc.cash_to_close resolves `unknown` on LF-6T3N (inputs absent) — HELD
```

**What repairs it:** closing-disclosure / loan-estimate closing-cost extraction, then a real recipe, then
flip `input_resolves: true`. No calibration, no Priya, no bar height — a pure upstream-data blocker.

### The generalizable shape

An inert rule is broken at exactly one of four hops:

**vocabulary** (tag undeclared) → **production** (no declaration or no producer) → **producer
resolution** (declared but abstains/never resolves: AS-3) → **calibration** (resolves but its AI input is
unscored: AS-7).

Only the last needs Priya; the first three need engineering or documents.

## The LP-450 tag guard — a correction

> **The planning docs say "every tag must pass the LP-450 load-time guard." The parsed-mode guard is not
> load-time — it's a pytest.** `backend/tests/verification/tag_materialization/test_parsed_declaration_fields.py`.
> Its own docstring explains why, and the reasoning holds: the authoritative field universes live in
> `app.ai.extraction.*` and `app.models.*`, so a load-time check would force the deterministic vocabulary
> loader to import the AI/ORM layers — a layering inversion. It fails CI just as loudly. But the
> distinction matters if declarations are ever loaded outside pytest.

What each mode validates:

| mode | where | validates |
|---|---|---|
| `derived` | **load** (`validate_declarations`) | `data` is a key in `_RECIPES`; subject ∈ `{loan, borrower, document}` (transaction rejected) |
| `ai` | **load** | group exists, lists the tag, and its `subject` agrees |
| `parsed` | **test** (LP-369, extended by LP-450) | field is a legal member of its subject's universe: document → extraction model field names; transaction → `_TXN_FIELDS`; loan → a `mismo.facts` key; borrower → the suffix after `borrower.{n}.` |

Universal load-time rejections: unknown mode, unknown subject, empty `data`, **a tag declared for
production but absent from the vocabulary**, and `document_type:` on anything but a `parsed:document` tag.

**Residual gap, documented in the guard itself:** `borrower.{n}.declaration.<slug>` is accepted by
*prefix* — the slug comes from free-form declarations JSON and cannot be validated.

The bug class this exists to kill, quoted because it has recurred four times: *"a declaration names
something that doesn't exist → the thing is ABSENT → the rule couldnt_checks on every file → silently,
forever, with every test green."* (`id.dob` read `dob` when it's `date_of_birth`; `id.ssn_hash` read
`ssn` when it's `employee_ssn` — both silently killing **live** rules ID-3 and ID-2.)

## The two that should worry most

**IH-1 / doc 104.** IH-1 is `no-ai-dependency`, ships **auto**, and its verdict is a direct function of
one string:

```python
field = subject_raw.fields.get("replacement_cost_or_coinsurance_basis")
```

`replacement_cost` → satisfied, `actual_cash_value` → **fired**, anything else → `unknown` →
couldnt_check. A misread of that one field flips a trusted, auto-shipped verdict between "insurance is
adequate" and "insurance is inadequate" with no human in the loop. And from the stored bench output,
**that field populates on only 7 of 15 homeowners_insurance documents (46.7%)** — the lowest fill rate of
any live rule's sole input. The recipe does fail closed on an *unrecognised* basis; it cannot fail closed
on a *confidently wrong recognised* one. That is exactly the ADR-365 failure mode the guard cannot catch.

**AS-1 / doc 049.** `txn.amount` is operand `observed` — the left side of both comparisons. A transaction
row whose `amount` holds the running balance instead of the transaction amount produces a number that is
arbitrarily larger than the real deposit, compared against a threshold that is *already known to be too
loose* (stated-vs-qualifying income). It fires as an unsourced large deposit against a fabricated figure.
AS-1 mitigates only partially: `gated_pending_signoff=True` on every verdict, so it should be withheld
from "shipped" — but AS-2 (auto) and AS-12 (ratify) read the same transaction rows.

**ID-3 / ID-5 / docs 146, 294.** Both are `parsed` passthroughs, which means `confidence=None`, which
means `gate.py` **ignores them in the confidence min entirely**. A hallucinated DL date of birth or expiry
enters the gate looking exactly like a certain fact. ID-5 is auto and its `_borrower_id_expiration` recipe
fails closed on *disagreement* between IDs and on *absence* — but a single hallucinated DL with no sibling
to disagree with sails through.

## The structural point

The gate's fail-closed armor is built entirely around **absence, unknown-ness, contradiction, and low
confidence**. It has no defense against a confidently-wrong extracted value, and the parsed path
explicitly strips confidence. That's not a bug in the gate — it's the boundary of what a gate can do, and
it's the same boundary LP-474's accuracy layer was built to sit outside of. Worth noting: **LP-474's
self-consistency checks are not wired into the rule engine** — they flag at the extraction layer, not at
the verdict layer. The four direct exposures above are not currently covered by either mechanism.

## `loan_number_masked` — the issue is real, and narrower than "the DB stores it unmasked"

1. **The snapshot layer is safe.** `loan_number_masked` is registered at `documents_section.py:215` as
   `(PiiKind.ACCOUNT, True)` — `pre_masked=True`. `PiiField.pre_masked` re-renders the display from the
   value's **last four alphanumerics**, so even a badly- or un-masked input reveals at most four
   characters by the time it reaches the snapshot. Defense in depth works here.

2. **The extraction row is not.** `Extraction.extracted_data` is `mapped_column(JSON, ...)` — plain,
   unencrypted. Whatever the model returned is persisted verbatim. So the unmasked number lives in the
   extraction record even though it never reaches the snapshot.

3. **The prompt is the actual defect, and it's inconsistent.** `payoff_statement.txt:53` and
   `verification_of_mortgage.txt:57` both carry *"For any masked field, output the LAST 4 CHARACTERS ONLY
   — never the full value."* **`mortgage_statement.txt` has no masking instruction at all** — grep for
   "mask" in that file returns only the JSON schema line. Its extractor is asked for a field named
   `loan_number_masked` and told nothing about masking it. **Only 36 of 119 extraction prompts carry that
   masking line.**

So: the field is masked where it's read, unmasked where it's stored, and the prompt that should prevent
that is missing on one of the three extractors that emit it. Worth also noting the *reported* sibling gap
at `documents_section.py:208-211`: **PII inside a captured list row is not routed through `_PII_FIELDS`
at all** — it relies entirely on prompt masking, and prompt masking is on 30% of prompts.

# 4. Where the authored applicability lives

**The prose authoring did land — but split across three places, and the dependency map did not survive.**

**Yes, the specs carry it.** All three fields, as first-class prose. From `AS-1.yaml`:

```yaml
applicability:
  scope: >-
    Loan files that have at least one bank statement with surfaced transactions
    (a documents entry with document_type == "bank_statement" and a non-empty
    transactions list). No bank-statement transactions → not_applicable.
  trigger: >-
    Evaluated per qualifying deposit — each credit (money-in) transaction is a candidate;
    the deterministic bookend flags those at or above the threshold for AI sourcing judgment.

required_inputs:
  - name: deposit_transactions
    snapshot_path: 'documents.entries[document_type=="bank_statement"].transactions[direction=="credit"]'
    description: >-
      Each credit (money-in) transaction on a bank statement — the candidate deposits.
  - name: monthly_qualifying_income
    snapshot_path: 'mismo.facts["borrower.<n>.income.<m>.monthly_amount"]'
    ...
```

These are **documentation, not execution**. The `snapshot_path` strings are never parsed — execution goes
through `subject_enumeration` + `deterministic.applicability`. The header says as much: *"⚠️ FORMAT IS
PROVISIONAL… Nothing consumes this yet."* AS-1's own `applicability.scope` prose still describes the
pre-LP-324 `direction=="credit"` filter, while the executable predicate is
`{tag: txn.is_money_in, op: eq, value: in}` — the tag exists precisely *because* the `direction==` filter
was a bug. **The prose is one generation behind the predicate.**

**Yes, applicability is three-valued** — and the tri-state is the whole point of `applicability.py`:

```python
tag = subject_tags.get(applic.tag)
if tag is None:
    return (Verdict.COULDNT_CHECK, _undetermined_reason(applic, present_but_unclear=False))
if tag.value == _UNKNOWN:
    return (Verdict.COULDNT_CHECK, _undetermined_reason(applic, present_but_unclear=True))
matches = (tag.value == applic.value) if applic.op == "eq" else (tag.value != applic.value)
if not matches:
    return (Verdict.NOT_APPLICABLE, ...)
return None   # the rule APPLIES
```

`true → runs`, `false → not_applicable`, `absent/unknown → couldnt_check`. "Awaiting-data" is
`couldnt_check`, and the module's docstring states the contract: *"not_applicable (scope-false) must
NEVER absorb couldnt_check (data-missing)… conflating them would hide a real gap behind a false 'not
applicable'."* There's a fourth case too — `absent_document_couldnt_check` (LP-330) distinguishes "no
document matched the filter" from "this document SHOULD exist for this file", the latter emitting a
stable `missing:<type>` subject id so it reconciles across runs.

**What happened to the ~123-rule pass:**

| artifact | state |
|---|---|
| `rule_kinds.csv` | **135 rules** — kind, evaluation_path, numeric_check, exact_match, priya_validated, signoff, rationale. Generated to `docs/stage2-rule-classification.md`: *calculative 28, structural 63, judgmental 29, out-of-scope 15. **Priya-validated: 0/135.** Thresholds needing sign-off: 21.* → 135 − 15 out-of-scope = **120 real targets** |
| `rule_tags.csv` | **107 distinct rules** mapped to tags — the machine-readable half of `required_inputs`. Drifted from the specs where both exist |
| `specs/*.yaml` | **45** carry the full prose (scope/trigger/required_inputs/evidence_required/guideline_reference) |
| **`tag_dependencies.csv`** | ⚠️ **header only. Zero rows.** `tag_id,depends_on_tag_id` and nothing else |

So the authoring pass **was** saved, at two levels of fidelity: kinds+tags for ~107–135 rules, full prose
for the 45 that got specs. **The Appendix A dependency map is the empty CSV** — the file was created and
never populated. That's the piece that didn't survive, and it's the one that would say which of the ~75
unspecced rules unblock together.

# 6. Lists — the built-but-unused surface

**Where declared:** `snapshot/documents_section.py:1384`, `_LIST_SPECS: dict[str, tuple[ListSpec, ...]]`.
**67 document types carry lists; 78 list specs; 71 distinct list names.** The generator emits both the
`ListSpec` and its registration (`generator/emitters.py:834`).

**Shape** (`snapshot/model.py:221`):

```python
class ListRow(BaseModel):
    model_config = {"frozen": True}
    fields: dict[str, Field]      # same typed shape as DocumentEntry.fields — value + confidence + source
    row_id: str | None = None     # stable content-derived id, ONLY where a list declares stable_row_id

class DocumentEntry(BaseModel):
    ...
    lists: dict[str, tuple[ListRow, ...]] = PydField(default_factory=dict)
```

**Exactly one list declares `stable_row_id`: `bank_statement.transactions`.** Everything else is
aggregate-read-only, so the first list a rule enumerates as finding subjects will need that flag flipped
on its spec.

**How "no rule reads a list" was verified** — three passes, because the first was wrong:

1. Found the derived recipes that touch list data. A first grep for `.lists` returned **zero** — the
   recipes use an `all_list_rows(snapshot, name, document_type=...)` helper, not attribute access.
   Re-grepping for both found **2**: `credit_tradeline_count`, `credit_tradeline_monthly_payment_total`.
2. Found AI groups with `include_lists: true` → **1**: `credit_profile`.
3. Resolved those to tags → `credit.tradeline_count`, `credit.tradeline_monthly_payment_total`,
   `credit.undisclosed_tradeline`. Then walked **all 45 specs**, collecting
   `deterministic.load_bearing_tags` + every operand `tag`/`loan_tag`/`product` factor +
   `consistency.gather_tag`, and intersected.

```
tags sourced from lists: ['credit.tradeline_count',
                          'credit.tradeline_monthly_payment_total',
                          'credit.undisclosed_tradeline']
specs reading a list-sourced tag: {'CR-4': ['credit.undisclosed_tradeline']}
ACTIVE rules reading a list-sourced tag: NONE
```

**Confirmed: no live rule reads any list.** The only reader is CR-4, which is inert
(`not-calibratable-yet` — its tag is unscored). And the two tradeline *aggregate* tags are fully declared,
materialized, and read by **nothing at all** — not even an inert spec.

**The legacy attributes.** `transactions` / `schedule_c` / `schedule_e` are separate bespoke attributes on
`DocumentEntry` (`model.py:275-276`) that coexist with `lists`. `bank_statement`'s transactions populate
**both** — `documents_section.py:679-683` is explicit that the same rows feed `entry.transactions`
(legacy, byte-unchanged) *and* `entry.lists["transactions"]` (generic, read by no rule).

Live rules depending on the legacy attributes:

| attribute | live rules |
|---|---|
| `transactions` (via `all_transactions` in `_per_deposit`) | **AS-1, AS-2, AS-12** |
| `schedule_c` (`derived.py:1398`) | **IN-12** — Schedule C presence is its self-employment scope gate |
| `schedule_e` (`derived.py:1458`) | **none live** — IN-13 only, which is inert |

So "never migrate the legacy list attributes" protects five rules, three of which run on every file with
a bank statement.

**AS-1's per-row enumerator — the pattern a list consumer copies:**

```python
def _per_deposit(snapshot: Snapshot) -> list[Subject]:
    """One subject per bank-statement transaction (its stable content_id + its tag map)."""
    if snapshot.tags.absent:
        return [(txn.content_id, {}) for txn in all_transactions(snapshot)]
    return [(txn.content_id, snapshot.tags.by_subject.get(txn.content_id, {}))
            for txn in all_transactions(snapshot)]
```

Four properties to copy: (1) the subject id is the row's **stable content id**, never a position — that's
what makes findings reconcile across runs; (2) an absent tags layer yields subjects with **empty** maps
rather than no subjects, so the gate reports `couldnt_check` per row instead of the rule vanishing; (3) it
returns `(id, tags)` pairs and nothing else — no filtering, no domain logic, all of that is the spec's
`applicability` predicate; (4) `subject_key_fields: [account, date, amount]` in the spec gives the finding
a human-readable identity separate from the content id.

For a generic list the equivalent enumerator would read `entry.lists[name]` and use `ListRow.row_id` —
which is why `stable_row_id` has to be declared on the spec first.

# What to flag before starting Phase 2

Three things, in order:

1. **§3 is a live correctness question, not a hygiene one.** IH-1 is auto-shipping trusted verdicts off a
   field that populates 47% of the time and has a confirmed wrong value in the corpus. AS-1/AS-2/AS-12,
   ID-3, and ID-5 have direct exposure too. The fail-closed gate cannot see any of this by construction —
   and the parsed path (`confidence=None`) actively hides it from the confidence floor. LP-474's accuracy
   checks run at the extraction layer and are not wired to the verdict layer.

2. **The lists are cheaper to unlock than they look, and there's already a free proof.**
   `credit.tradeline_count` and `credit.tradeline_monthly_payment_total` are declared, materialized, and
   read by nothing — no spec at all. Writing the first rule against one of those needs no new mechanism,
   no AI, no Priya. It also surfaces the one real prerequisite early: `stable_row_id` is declared on
   exactly one list, so any list whose rows should be finding subjects needs that flipped first.

3. **Two provenance artifacts have quietly rotted, and Phase 2 leans on both.** `rule_tags.csv` disagrees
   with the specs about what AS-1 reads. `tag_dependencies.csv` is an empty header — that's the Appendix A
   dependency map, and it's the artifact that would say which of the ~75 unspecced rules unblock together.
   Both are the *inputs* to "write ~25 deterministic rules," and neither is currently trustworthy.
   `txn.source_strength` — declared in no vocabulary file, read by a live rule — is the same rot in its
   most advanced form.
