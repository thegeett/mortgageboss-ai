01 — Who builds itDesign here, implement there

You asked who implements. The honest split follows from what each environment can actually do.

This session

Design and specification

  • Renders and screenshots every screen in both themes, so a change is visible in seconds rather than after a build
  • Reads the whole repo through the bridge, so the mockups stay grounded in real routes, statuses and fields
  • Writes the token file, the StatusToken component and the codemod script as proposed files under docs/design/ledger/ — nothing wired in, nothing that can break a build
  • Cannot run pnpm dev or look at the running app: the browser here can't reach a localhost server. Writing app code from here means coding blind.

Local Claude Code

Implementation

  • Runs the dev server and sees the real app change as it edits
  • Runs biome, tsc, pnpm test and the pre-commit hooks — the loop your CI already enforces
  • Runs the codemod and reviews the 67-file diff before it goes anywhere near a commit
  • Works ticket by ticket in the docs/tickets/LP-XXX.md convention this repo already has
The handoff Everything in docs/design/ledger/ is the contract: the mockups, the screenshots, the token file, and a SPEC.md local Claude Code reads at the start of each ticket. It never has to guess what a screen should look like — it opens the mockup for that screen and matches it.

03 — Getting to "finalized"Four review passes, not one sign-off

Pass 1you, now

Walk the sixteen screens and mark what's wrong

Not "do you like it" — specifically: does a screen show a processor something they don't need, or hide something they do? You and your domain expert will catch things in the Verification and Needs screens that no amount of code reading would surface. Anything vocabulary-related matters most; the wrong word on a status is worse than the wrong colour.

Pass 2me

Revise, then draw the six that are missing

Your notes go back into the same kit, and the six secondary surfaces above get drawn so nothing is left to be improvised during implementation. This is also where the four open decisions from the direction doc get resolved into the tokens.

Pass 3me

Extract the pattern library

Once the screens are locked, every repeated element is pulled out into one page: buttons, inputs, tables, status tokens, rail-coded rows, banners, empty and error states, dialogs, toasts — each with the React snippet beside it. This is the artefact local Claude Code actually builds from, and it is what keeps screen twelve consistent with screen one.

Pass 4local Claude Code

Build, screen by screen, against the mockups

Each ticket opens its mockup, matches it, and runs the CI loop. The design stops being a proposal at this point and starts being the app.

04 — The four pull requestsOnly the last one is per-screen

The leverage argument, restated as work: 95 non-test components, but the look lives in eight primitives and one token file. Roughly 80% of the visual change lands before anyone opens a page component.

PR 1~2 days

Tokens, fonts, and the bug

Land the Ledger token block and the dark palette the config has always promised. Add IBM Plex via next/font. Fix the danger colour that is silently disarming the failed-run banner. Nothing looks different yet — this PR only makes the foundation real.

app/globals.css · tailwind.config.ts · app/layout.tsx · 20 danger call sites
PR 2~1 day

The codemod

784 hardcoded gray-* classes across 67 of 95 components bypass the token layer entirely — that is why dark mode has never been switchable, and why a token swap alone would only half-work. Twenty-one class names cover 780 of them, so this is a scripted find-and-replace with a reviewable diff, not a rewrite. It also fixes a real accessibility failure on the way through: text-gray-400, used 178 times, sits at 2.54:1 on white and fails AA for text and the 3:1 bar for icons.

67 component files — mechanical, reviewed as one diff
PR 3~2 days

Primitives and one status component

Density retune on the shadcn primitives — 53px rows to 28px, radius to 5px, the type scale. Then one StatusToken component that takes a semantic state and renders rail, glyph and word, replacing the six competing status maps. After this PR the five screens nobody designed already look like Ledger.

Build order, and why this order

Flow order, not difficulty order. Each screen a processor meets earlier sets the vocabulary for the ones after it, so building in the order they are encountered means the language settles once rather than being retrofitted.
