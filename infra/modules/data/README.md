# `modules/data`

RDS PostgreSQL, ElastiCache Redis, and the CloudWatch log groups.

**Neither the database nor the cache is publicly reachable.** Both live in private
subnets with security groups admitting only the ECS tasks' group; RDS also sets
`publicly_accessible = false`. No group in this stack permits `0.0.0.0/0` on 5432
or 6379.

## ⚠️ `DATABASE_URL` must use `?ssl=require` — `?sslmode=require` crashes the app

The database enforces TLS (`rds.force_ssl = 1` in the custom parameter group), so
the client's SSL behaviour is load-bearing. The application uses SQLAlchemy 2.0.50
with asyncpg 0.31.0, and that combination does **not** understand libpq parameter
names:

- SQLAlchemy's asyncpg dialect contains **no SSL handling at all**, so unrecognised
  query parameters are forwarded as raw keyword arguments to `asyncpg.connect()`.
- `asyncpg.connect()` has an `ssl` parameter, **no `sslmode` parameter, and no
  `**kwargs`**.

So `?sslmode=require` — the spelling RDS documentation uses — is not ignored. It
raises `TypeError: connect() got an unexpected keyword argument 'sslmode'` and the
application cannot connect at all. The same trap applies to `?sslrootcert=`.

**Correct:** `postgresql+asyncpg://USER:PASS@HOST:5432/DB?ssl=require` <!-- pragma: allowlist secret -->

### Certificate verification is a separate question

With no SSL argument at all, asyncpg defaults to `prefer` for TCP connections
(`asyncpg/connect_utils.py:652-656`). Against `rds.force_ssl = 1` that still
connects and the traffic **is** encrypted — but `prefer` sets `verify_mode =
CERT_NONE` and no hostname check, so there is no protection against an in-path
attacker.

Reaching `verify-full` requires the **`PGSSLROOTCERT` environment variable**
pointing at an RDS CA bundle baked into the image; asyncpg reads that variable
directly. It cannot be done through the URL. **That is a C3 image and
task-definition requirement, not a Terraform one.**

## ⚠️ `REDIS_URL` must use `rediss://` — and the two client libraries disagree

`transit_encryption_enabled = true` is unconditional here, so a `redis://` client
cannot connect. The scheme must be `rediss://`.

That much is expected. The trap is that the application uses **two different Redis
clients** and they resolve the same URL to opposite security postures:

| Client | Used by | `rediss://…` with no query param |
|---|---|---|
| redis-py 6.4.0 | the cache (`backend/app/core/redis.py:39`) | `ssl_cert_reqs` defaults to `'required'` → **CERT_REQUIRED (verifies)** |
| kombu 5.6.2 | the Celery broker and result backend | resolves to `{'ssl_cert_reqs': CERT_NONE}` → **does NOT verify** |

Both read the same `REDIS_URL` (`celery_broker_url` falls back to `redis_url`,
`backend/app/core/config.py:236`). So the default behaviour is inconsistent
between the API's cache client and the worker's broker client.

**Set it explicitly rather than relying on either default:**

```
rediss://HOST:6379/0?ssl_cert_reqs=required
```

Verified: both libraries accept that query parameter and both then verify.
ElastiCache's in-transit certificates chain to a public CA, so no custom bundle is
needed — unlike RDS.

### AUTH token

`redis_auth_enabled` decides whether `REDIS_URL` is a SECRET or CONFIG:

- **with a token** — the token is embedded in the URL, making the whole URL a
  credential → Secrets Manager;
- **without** — the URL is topology only, protected by security-group isolation →
  plain `environment[]`.

The token is **not** set by Terraform (it would land in state). Apply it out of
band and record it in the `redis-url` secret; `ignore_changes = [auth_token]`
stops Terraform reverting it.

## Engine versions

`postgres_version` is **major-only** (`"16"`) on purpose. AWS then selects the
current minor, so there is no pinned minor to be retired between writing this and
applying it, and `auto_minor_version_upgrade` keeps it current. Local development
runs `postgres:16-alpine`, so this must stay on 16.x.

`redis_version` is `"7.1"`; local runs `redis:7-alpine`.

`postgres_family` / `redis_family` must agree with the respective major — AWS
rejects a mismatch at apply time.

## The master password

Generated by `random_password` and surfaced **nowhere**: not an output, not a
secret version, not a variable. It exists in Terraform state, which is why the
state bucket is encrypted, versioned, and access-blocked. The operator assembles
`DATABASE_URL` by hand — see `infra/README.md`.

The character set is restricted to `!$&*()-_=+,.;~` so the value really is safe to
paste into a URL unencoded, which is what that assembly step does. `#`, `?`, `%`
and `:` are excluded deliberately and **must not be added back**:

| Char | What it does in a URL | Symptom |
|---|---|---|
| `#` `?` | Gen-delims — terminate the authority component | Pydantic rejects the DSN; the app refuses to start reporting an *invalid port* |
| `%` | Starts a percent-escape | `%` + 2 hex digits is silently decoded by SQLAlchemy, so the password sent to Postgres is not the one in Secrets Manager — an auth failure with no visible cause |
| `:` | Separates user from password | A password containing one splits the credential |

The original set included `#`, `?` and `%`; over a 32-char password that is roughly
a 55% chance of an unbootable environment per generation.
